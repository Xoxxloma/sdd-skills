# Task Decomposition (epic-БТ → child БТs)

This skill is the middle stage of the pipeline: `business-requirements-doc` (эпик-БТ) →
**task-decomposition-doc** (this) → `technical-spec-doc` (per child). It takes ONE
confirmed epic-level business-requirements document and splits it into several
separately-shippable child parts (части) — each a self-contained БТ in its own task folder,
ready for `technical-spec-doc` with zero changes.

Its whole job is **partitioning**, not authoring. The parent epic-БТ already holds the
confirmed business truth; this skill only distributes that truth across parts. Getting
the "distribute, never invent" discipline right is the entire job.

## TL;DR — 5 правил, держи в голове всегда (ниже — только справка)

1. **Нет подтверждённого эпик-БТ → не работай.** Единственный ответ — попросить эпик-БТ
   (или запустить `business-requirements-doc`). Есть БТ → первый ход всё равно = ТОЛЬКО
   вопросы (предложенный split + ключи + порядок), файлов не пишешь.
2. **Разрезаешь уже подтверждённое — не выдумываешь ничего.** Каждый детский FR и его
   критерий приёмки копируются ДОСЛОВНО из эпик-БТ. Новое требование, новый scope,
   расщепление смысла одного FR — нельзя: детский БТ лежит в той же форме, что и
   подтверждённый, и ниже по потоку его читают как бизнес-правду, не сверяясь с эпиком.
   Нужного нет в эпик-БТ → это сигнал вернуться в `business-requirements-doc` и дополнить
   ЭПИК, а не дописать здесь.
3. **Покрытие механическое:** каждый FR эпика попадает РОВНО в одну дочернюю часть (или
   явно помечен `shared`/сквозной пользователем). Ни один FR не потерян, ни один молча не
   задвоен. Не сходится — не пиши, спроси.
4. **Пиши файлы, ТОЛЬКО когда реестр частей чист:** каждый дочерний ключ = реальный
   `SMSEC-1234` (regex `^[A-Z][A-Z0-9]+-\d+$`, ≠ эпику, уникален), split подтверждён,
   покрытие сходится, порядок задан. Ни одного ❓.
5. **Дочерний БТ самодостаточен и живёт ВНУТРИ папки эпика** —
   `docs/<EPIC-KEY>/<CHILD-KEY>/business_requirements.md`, подпапкой, а не сиблингом эпика.
   Общий бизнес-контекст (§1.0–1.4, §2.1–2.3, §3.4, §4.3, §5.1–5.3) КОПИРУЕТСЯ из эпика; часть несёт свой
   поднабор FR + свои критерии + свой scope in/out; в шапке frontmatter `parent: <EPIC-KEY>`.
   `technical-spec-doc` потом работает по каждой папке БЕЗ изменений.

Остальная часть скилла разворачивает эти правила. Если правило ниже кажется противоречащим
этому списку — прав список.

## Precondition (entry guard): нет подтверждённого эпик-БТ → нет декомпозиции.

Скилл работает ТОЛЬКО поверх подтверждённого business-requirements документа («эпик-БТ»).
До всего остального проверь, что БТ реально есть. Присутствующим он считается ТОЛЬКО так:
пользователь назвал **путь к записанному файлу** `docs/<KEY>/business_requirements.md`, и ты его
прочитал. Вставленный в сообщение текст БТ входом НЕ считается — даже полный: из пути выводится
папка эпика, а у текста её нет. Попроси записать файлом (`business-requirements-doc`) и дать путь.

Нет такого файла (бриф, идея, одна строка, вставленный текст) → **не интервьюируй, не предлагай
split, не пиши файлы.** Ответ — ровно: декомпозиция строится на записанном БТ, запусти
сначала `business-requirements-doc` (или дай путь к готовому файлу). Это весь ход.

**Почему отказ, а не «разрежу по брифу».** Разрез — это распределение уже подтверждённого.
По брифу распределять нечего: всё, что попадёт в детские БТ, будет придумано здесь — а
лежать будет в той же форме, что и подтверждённое бизнесом. Ниже по потоку эту разницу уже
не увидит никто: `technical-spec-doc` проектирует по детскому БТ и в эпик не заглядывает.

Дополнительные жёсткие проверки перед работой:
- В шапке БТ есть реальный ключ эпика `<EPIC-KEY>` (regex `^[A-Z][A-Z0-9]+-\d+$`). Это и
  есть `<EPIC-KEY>`, и имя папки `docs/<EPIC-KEY>/`.
- В БТ есть **хотя бы 2 нумерованных FR-***. Если FR всего один (или ноль) → задача НЕ
  делится: скажи это прямо, декомпозицию не делай (см. «Edge cases: одна часть»).
- В БТ статус «Готово к оценке» и блок «Открытые вопросы» пуст. Если в БТ висят TBD/⚠️ →
  предупреди: части унаследуют пробел; предложи сперва закрыть эпик через
  `business-requirements-doc`. Не «чини» БТ здесь.

## Turn 1 = questions only. No file.

Твой **первый ответ — только вопросы**: предложенный split, сквозные FR, реальные ключи
детей, порядок сборки. В turn 1 ты не вызываешь инструменты записи файлов, не создаёшь
индекс и детские БТ. Файлы появляются только со **второго** ответа, после того как
пользователь подтвердил части и дал ключи.

**Почему не «напишу, а потом поправим».** Границы частей и ключи задач — решение
пользователя, а не твоя догадка (ключ ты вообще не можешь знать: он заводится руками в
трекере). Записанный до подтверждения разрез стоит дороже несделанного: файл ложится в
`docs/<EPIC-KEY>/<CHILD-KEY>/` под ключом, которого нет в трекере, и правка — это уже не
переписать текст, а разобрать дерево папок, по которому дальше идёт весь пайплайн.

Если чего-то не хватает для гейта — это **вопрос к пользователю**, а не значение, которое
ты придумываешь, и не `TBD`, который ты присваиваешь сам.

## Goal

Из ОДНОГО подтверждённого эпик-БТ произвести: (а) индекс декомпозиции
`docs/<EPIC-KEY>/decomposition.md` и (б) по одному самодостаточному дочернему БТ на часть
в `docs/<EPIC-KEY>/<CHILD-KEY>/business_requirements.md`, так чтобы `technical-spec-doc` мог быть
запущен по каждой дочерней папке без единой правки. Каждая часть — связная группа FR
(отдельная поставка, покрывающая FE+BE вместе), а не под-требование.

## The contract (read before anything)

- **Единственный источник контента детей — эпик-БТ.** Читаешь только его. Репозиторий,
  база знаний, свои соображения — НЕ источник; в детский БТ не попадает ничего, чего нет
  в эпик-БТ.
- **Партиционирование, не авторинг.** Ты распределяешь уже подтверждённые FR по частям.
  Ты не создаёшь новых FR, не расщепляешь смысл одного FR на два, не переписываешь
  критерии, не добавляешь scope, которого нет в эпике.
- **Кардинальный грех этого скилла:** протащить в дочерний БТ требование/критерий/scope,
  которого нет в эпик-БТ. Если части что-то нужно, а в эпике этого нет — это сигнал
  вернуться в `business-requirements-doc` и дополнить ЭПИК, никогда не «дописать здесь».
- **Ответы пользователя определяют split.** Ты предлагаешь границы; пользователь
  подтверждает/правит. Число частей, состав FR, сквозные FR, ключи, порядок — за
  пользователем.
- **Output — только новые файлы:** индекс + детские БТ. Ты НЕ редактируешь эпик-БТ и любой
  другой файл репозитория.

## Process — do these in order

### Step 0 — Intake эпик-БТ
Прочитай эпик-БТ **по пути** (без пути работы нет — см. entry guard). Извлеки МЕХАНИЧЕСКИ,
ничего не переписывая:
- `<EPIC-DIR>` — **папка прочитанного файла** (путь, по которому открыл, минус имя файла). Якорь
  всех записей ниже; держи строкой, заново по шаблону не собирай;
- `<EPIC-KEY>` из шапки БТ;
- SHARED-контекст ДОСЛОВНО: §1.0 тип, §1.1 проблема, §1.2 потребители, §1.3 заказчик, §1.4 как сейчас
  (нет в эпике — у ребёнка «не применимо: в эпике `<EPIC-KEY>` раздела нет»), §2.1 бизнес-цель,
  §2.2 ценность, §2.3 риски, §5.1 приоритет, §5.2 сроки, §5.3 роли;
- полный список FR-* (§4.1) с их формулировками ДОСЛОВНО;
- по каждому FR-N — его критерий `[FR-N] Дано–Когда–Тогда` (§4.2) ДОСЛОВНО;
- §3.1/§3.2/§3.3 (общий scope in/out и архитектурные изменения эпика), §3.4 внешние зависимости
  (нет в эпике — у ребёнка «не применимо: в эпике `<EPIC-KEY>` раздела нет»);
- §4.3 «Бизнес-данные» ДОСЛОВНО (нет в эпике — у ребёнка «не применимо: в эпике `<EPIC-KEY>`
  раздела нет»);
- **§4.5 «Разбиение на части», если она есть** — таблицу целиком: имена частей, состав
  FR-*, ценность в одиночку, зависимости.

Построй внутренний **«инвентарь FR»**: `{FR-N → текст, критерий}`. Это единственный
источник контента для FR детей; разделы-копии берутся по таблице «2) Дочерний БТ» в Output template.
Ничего вне инвентаря и разделов-копий в детский БТ попасть не может.

### Step 1 — Предложи части как ГРУППЫ FR (proposal, не запись)

**Есть §4.5 — работай ПРАВКОЙ, а не с нуля.** Разрез в ней сделан тем же скиллом, который писал
эпик-БТ, и уже показан аналитику: имена частей, состав FR, зависимости. Возьми таблицу как своё
предложение и проверь её инвариантом покрытия (Step 2) — потерянный FR, задвоенный без пометки,
часть без собственной ценности. Нашёл дефект — почини и назови вслух, что поправил и почему.
Нашёл всё сходящимся — так и неси её аналитику на подтверждение, не перекраивая ради того, чтобы
предложить своё. Зачем: сгруппировать FR с нуля — генеративная задача, а проверить и поправить
готовую группировку та же модель делает надёжнее. **§4.5 нет** (старый или чужой БТ) либо в ней
«не применимо», а аналитик всё равно просит разрез — группируй сам, как ниже; это штатный вход,
просто дороже.

Сгруппируй FR-* в связные, отдельно поставляемые части (каждая — цельная поставка,
покрывающая FE+BE вместе). Часть = группа FR, а не под-требование. Правила группировки:
- каждый FR — кандидат ровно в одну группу (владелец);
- FR, который реально нужен нескольким частям, помечай кандидатом **«сквозной/shared»** —
  НЕ дублируй его молча. Предпочитай отдать сквозной FR одному владельцу (базовой части,
  от которой другие зависят), а не делать его shared, — так дети остаются независимо
  поставляемыми; `shared` только когда FR реально обязан жить в обеих.
- это только ПРЕДЛОЖЕНИЕ; пользователь подтвердит границы, число частей, сквозные.

**Проверка атомарности каждой части** (адаптировано под разрез по группам FR — контрактов
ещё нет):
- **Отдельно поставляем?** Часть едет в прод в одиночку и даёт ценность (или явный порядок:
  «B бесполезна до A» допустимо, но фиксируется зависимостью в Step 3).
- **Свой набор AC?** У части есть собственные критерии приёмки из БТ. Часть без своих AC — не
  самостоятельная часть, а технический шаг чужой; переклей её FR к владельцу.
- **Зависимость/порядок явные?** Опирается на другую часть — это зависимость, не общий FR.

**Ловушка «разреза по фичам».** Деление по пользовательским функциям выглядит независимым, но
часто все части трогают одну концептуальную сущность (общий журнал, счётчик, справочник) — тогда
они НЕ независимы. Две части пишут/меняют одну сущность → это вопрос пользователю (Step 3),
кто владелец и как разрешается конфликт; молча не разрезай.

Ничего не пишешь. Ключи детей и порядок — ещё не заданы, спросишь в Step 3.

### Step 2 — Проверь покрытие ДО показа (инвариант)
Прогони инвариант покрытия по своему предложению:
- каждый FR-* эпика присвоен РОВНО одной части ЛИБО помечен «сквозной»;
- ни один FR не выпал; ни один не задвоен без пометки «сквозной»;
- в предложении нет ни одного FR/scope/критерия, которого НЕТ в эпик-БТ.

Не сходится — чини предложение, не «досочиняй» FR.

### Step 3 — Confirmation gate: спроси всё до записи
Спрашивай через интерактивный инструмент вопросов (tappable-опции; в Claude Code это
`AskUserQuestion`, в другом раннере — его аналог); если недоступен — прозой. Короткая рамка прозой,
затем вызов. Инструмент вопросов — это и есть «первый ход = только вопросы», не файл.

**Каждый вопрос — твой готовый разрез на подтверждение, а не пустое поле.** Границы частей
ты уже посчитал в Step 1–2: предъявляй их конкретно (состав FR по частям) и давай
содержательные альтернативы («2 части: «индикатор онлайн» = FR-1,2,3; «история регламентных
работ» = FR-4,5» / «3 части, просмотр и редактирование истории — отдельно»). **«Опишу в поле
ввода» вариантом не бывает** — свободный ввод есть всегда; пара «Опишу сам / Пока не знаю»
означает, что ты не сделал разрез. Исключение — ключи задач: их вывести неоткуда, спрашивай
текстом (п. 3 ниже).

**Номер FR без его текста — это не вопрос, а загадка.** Пользователь видит вариант в отрыве от
БТ и не помнит наизусть, что такое `FR-3`. Везде, где в вопросе или варианте стоит `FR-N`,
рядом стоит его формулировка — дословная из §4.1 или сжатая до узнаваемой фразы. То же для
имён частей и любых других идентификаторов: `A` и `B` пользователю не говорят ничего,
«индикатор онлайн» и «история регламентных работ» — говорят. *(Предметная область здесь и
ниже иллюстративная — подставляй свою.)*

❌ «Что выбираете: FR-1 или FR-3?»
✅ «FR-1 (в шапке показывать число активных пользователей) или FR-3 (в списке — регламентные
работы за период)?»

У варианта два поля: короткая метка и описание. Номер ставь в метку, текст требования — в
описание; тогда и метка читается, и смысл не теряется. Не помещается дословно — сжимай до
узнаваемой фразы, но не выбрасывай.

Ставь пользователю батчами:
1. **Границы частей:** «Предлагаю N частей: «индикатор онлайн» = {FR-1, FR-2}, «история
   регламентных работ» = {FR-3}. Годится / поправьте состав / другое число?» Покажи для
   каждой части её имя словами и список её FR ДОСЛОВНО — номера без формулировок
   выбирать не из чего.
   **Разрез пришёл из §4.5 и уже подтверждён аналитиком** (его показали в хендоффе БТ) —
   тогда не задавай его заново открытым вопросом: сверься одной строкой-пересказом («беру
   разрез из §4.5: «индикатор онлайн» = {FR-1, FR-2}, «история работ» = {FR-3}») и трать ход
   на то, чего в §4.5 нет, — ключи и порядок. Переспрашивать подтверждённое — потеря хода, а
   не осторожность.
2. **Сквозные FR:** «FR-4 (журнал действий пользователя) нужен и в «индикаторе онлайн», и в
   «истории регламентных работ» — сделать его `shared` (войдёт в обе как унаследованный) или
   отдать одному владельцу?» Формулировку требования и имена частей называй, а не одни
   номера. Явное решение пользователя, не догадка.
3. **Ключи детей:** по одному реальному ключу Jira/SberTrack на часть
   (`^[A-Z][A-Z0-9]+-\d+$`), ≠ `<EPIC-KEY>`, уникальные между собой. Спрашивай ТЕКСТОМ
   (свободное значение — не вариант из списка). Не выдумывай, не подставляй плейсхолдер,
   не помечай `TBD`. Нет ключа для части → ❓, файл этой части не пишется.
4. **Зависимости и порядок сборки:** «Часть B зависит от A? Порядок 1) A 2) B?»
5. **Общая сущность (если сработала «ловушка по фичам»):** две части пишут/меняют одну
   концептуальную сущность (общий журнал/счётчик/справочник)? — спроси, кто владелец записи и
   как разрешается конфликт при расхождении. Без явного ответа это НЕ независимые части: либо
   переклей FR к одному владельцу, либо зафиксируй политику словами пользователя.

**Каскад, но не вечно.** Ответ пользователя может породить новый вопрос (перекроил границы
→ всплыл осиротевший FR; отдал сквозной FR одному → вторая часть потеряла поведение). Задай
ЭТОТ новый вопрос в том же интервью, до записи. Отвеченное второй раз не переспрашивай. Как
только split подтверждён, каждый FR присвоен-или-`shared`, у каждой части валидный ключ,
порядок задан и новых вопросов нет — переходи к реестру.

**Если пользователь просит часть, которой нужно то, чего НЕТ в эпик-БТ** (новый FR,
расширенный scope) — НЕ выдумывай. Скажи прямо: этого нет в эпик-БТ; сначала дополни ЭПИК
через `business-requirements-doc`, потом вернись к декомпозиции. Это сигнал «назад к
эпику», не «дописать здесь».

### Step 3.5 — Реестр частей: последняя проверка до записи
Выведи компактный реестр. По одному маркеру на пункт:

```
Реестр декомпозиции (перед записью):
Эпик: <EPIC-KEY> — ✅ подтверждён БТ
Инвариант покрытия:
  FR-1 → часть A (владелец)            ✅
  FR-2 → часть A (владелец)            ✅
  FR-3 → часть B (владелец)            ✅
  FR-4 → сквозной (A, B) — по решению  ✅|❓
  ⟹ все FR эпика присвоены? ✅   потерянных: нет   задвоенных-без-пометки: нет
Части:
  A <CHILD-KEY-1> «<имя части словами>»  ключ ✅|❓   порядок 1
  B <CHILD-KEY-2> «<имя части словами>»  ключ ✅|❓   порядок 2 (зависит от A)
Ключи: все матчат ^[A-Z][A-Z0-9]+-\d+$, ≠ эпику, уникальны — ✅|❓
```

> Буквы `A`/`B` — короткие якоря для строк покрытия выше; имя части словами обязано
> появиться хотя бы раз, в блоке «Части». Реестр читает аналитик, и по одним буквам он
> неверное присвоение FR не поймает.

**Пункт, решающий, можно ли писать:**
- Любой FR не присвоен и не помечен «сквозной» → ❓ покрытия → **не пиши**, спроси.
- Любая часть без валидного уникального ключа → ❓ → эта часть не пишется.
- Есть хоть один ❓ → **не пиши файлы**, добери вопросы (один батч) и останови ход.
- Пиши только когда покрытие сходится И у каждой части ✅-ключ И порядок задан.

**Зачем печатать реестр, а не проверять в уме.** Несходящееся покрытие — потерянный FR,
задвоенный без пометки — до записи чинится правкой одной строки предложения, после записи
живёт в N файлах и N папках. Реестр вслух ещё и показывает аналитику ровно то, за что он
отвечает: какой FR к какой части ушёл.

**Не выдумывай, чтобы закрыть ❓.** Недостающий FR/scope/критерий — это ❓ (спроси) или
сигнал вернуться к эпику, но не правдоподобная вставка с пометкой «готово». Разница в
цене: **вопрос видно, вставку — нет.** ❓ стоит один ход и его закрывает человек; вставка
уезжает в детский БТ, оттуда в тех-спеку и в код, и на всём пути выглядит как
подтверждённое требование.

### Step 4 — Запись артефактов
Когда реестр чист, напиши (см. «Output»):
- индекс `<EPIC-DIR>/decomposition.md`;
- по одному `<EPIC-DIR>/<CHILD-KEY>/business_requirements.md` на часть.

**Якорь обеих записей — `<EPIC-DIR>` из Step 0, папка прочитанного эпик-БТ.** Путь ребёнка — эта
строка плюс `/<CHILD-KEY>/`, и ничего больше: не собирай его по шаблону `docs/<KEY>/` заново, не
отсчитывай от текущей директории, не поднимайся на уровень вверх. Правило «ключ задачи → своя папка
под `docs/`» на ребёнка НЕ распространяется: он не задача под корнем, а часть внутри дерева эпика.
Ключ ребёнка — имя ПАПКИ внутри `<EPIC-DIR>`; имя файла всегда голое `business_requirements.md`.

❌ `docs/ARS-101/business_requirements.md` — ребёнок уехал сиблингом, папки эпика в пути нет.
❌ `docs/ARS-100/ARS-101_business_requirements.md` — ключ в имени файла, папки ребёнка нет.
✅ `docs/ARS-100/ARS-101/business_requirements.md`

Оба промаха тихие: файл записан, ключ виден, разрез верный — а пайплайн ниже адресуется к папке
ребёнка внутри эпика (`technical-spec-doc` запускается по ней, `stage-breakdown-doc` считает от неё
`stages/`, оркестратор глобит `docs/<EPIC-KEY>/**/`, узел #0 встаёт в `_foundation/` на одном уровне
с детьми) и молча ничего не найдёт. Между стадиями контекст чистят: единственная память процесса —
диск, и вся она в одной папке.

**Перед записью назови собранный путь первого ребёнка вслух** и проверь: путь начинается с
`<EPIC-DIR>` (ключ эпика в нём есть), `<CHILD-KEY>` стоит папкой. Несобранный путь превращается в
имя файла.

НЕ редактируй эпик-БТ и другие файлы репозитория. Покажи индекс в чате И сохрани файлы, затем
дай пути.

### Step 5 — Self-Review (before handoff) — construction-time проверки

Проверь и почини всё, что не проходит:
1. **Ноль изобретений.** Каждый детский FR и его критерий присутствуют ДОСЛОВНО в эпик-БТ
   (сравни токен-в-токен с инвентарём Step 0). Ни одного FR/scope/критерия, которого нет
   в эпике. Расщепления смысла одного FR на два — нет.
2. **Покрытие.** Объединение владельцев-FR по всем частям = полный набор FR эпика.
   Пересечение владельцев (без пометки `shared`) = пусто. Сквозные — ровно те, что отметил
   пользователь.
3. **Ключи и пути.** Каждый детский ключ реальный, матчит regex, ≠ эпику, уникален; в шапке
   `parent: <EPIC-KEY>`. Пути, по которым ты РЕАЛЬНО записал, начинаются с `<EPIC-DIR>`, ключ
   ребёнка стоит папкой, индекс лежит в `<EPIC-DIR>`.
4. **Самодостаточность.** Каждый детский БТ несёт скопированный SHARED-контекст + ровно
   свой поднабор FR + совпадающие критерии + свой scope in/out. Валиден как вход
   `technical-spec-doc` (есть проблема/потребители/ценность/приоритет/роли/FR-*+критерии).
   **§4.5 у ребёнка — «не применимо: это часть эпика `<EPIC-KEY>`»**, а не копия эпической
   таблицы частей: иначе ребёнка отправят резать повторно.
5. **Номера FR.** Дети сохранили ОРИГИНАЛЬНЫЕ номера эпика (FR-1, FR-3…), НЕ перенумерованы
   в FR-1/FR-2. Перенумерация ломает трассировку и меняет смысл — запрещена.
6. **Индекс.** Таблица трассировки эпик-FR → ребёнок покрывает все FR; build order и
   зависимости заданы; список детей полон.
7. Записаны только индекс + детские БТ; эпик-БТ и прочий репозиторий не тронуты.

### Step 6 — Handoff

Коротко: путь индекса, список детских папок с ключами, порядок сборки, и следующий шаг —
«по каждой папке `docs/<EPIC-KEY>/<CHILD-KEY>/` запусти `technical-spec-doc`». Если в эпик-БТ были
унаследованные TBD/⚠️ — назови, в какие части они попали, и предложи закрыть их на стороне
эпика через `business-requirements-doc`.

В хендофф не идут: имена полей файла (`owned_fr`, `shared_fr`, `parent:`, `slice:`, `SHARED`),
`§`-адреса как предмет, голый `FR-N` без формулировки рядом.

## Coverage invariant (одной строкой)

Объединение owned-FR по частям == полный набор FR эпика; попарное пересечение owned-FR ==
∅; FR в ≥2 частях обязан быть помечен пользователем `shared`; ни одна часть не содержит
FR/критерия, которого нет в эпике.

## Edge cases

- **Одна часть (не делится).** `< 2` FR в эпике → откажись декомпозировать, скажи прямо,
  направь запустить `technical-spec-doc` напрямую по папке эпика. Если после предложения
  пользователь хочет одну часть = все FR — допустимо, но декомпозиция ничего не даёт: скажи
  это и порекомендуй `technical-spec-doc` по эпику вместо создания дубль-ключа.
- **Сквозной FR.** Никогда не дублируй молча. Только помеченный пользователем `shared` FR
  появляется в >1 ребёнке (в `shared_fr` и колонке «Также в (shared)» индекса).
  Предупреждение: shared FR → два тех-спека независимо спроектируют контракт для него →
  риск расхождения на интеграции. Предпочитай одного владельца + зависимость. А если общий
  кусок — это не столько требование, сколько **общий источник/сервис, на который опираются
  обе части**, скажи об этом в хендоффе: у оркестратора `analyst-workspace` для такого есть
  узел-фундамент #0 (спроектировать общий контракт один раз и раздать детям неизменным). Сам ты #0 не
  заводишь — это не твой слой; твоё дело назвать риск.
- **Унаследованные пробелы эпика (TBD/⚠️).** Пропагируются в часть, владеющую затронутым
  FR; статус ребёнка считается механически; в хендоффе назови их для закрытия на уровне
  эпика — здесь не «чини».
- **Ключ невалиден / = эпику / дубль.** → ❓, часть не пишется; переспроси, не подставляй.

## Formatting rules

- **Партиционируй, не сочиняй.** Каждая строка детского БТ трассируется к строке эпик-БТ.
  Единственная полу-авторская секция — §3.1 «Входит в проект»; её выводи механически из owned-FR и
  сверяй в Self-Review.
- **Номера FR неизменны.** Ребёнок владеет `FR-1, FR-3` — так и пиши; не сжимай в
  `FR-1, FR-2`.
- **Общий контекст — копия, не пересказ.** §1.0–§1.4, §2.1–§2.3, §3.3, §3.4, §4.3, §5.1–§5.3, §6
  байт-в-байт из эпика.
- **Сквозной FR — только явный `shared`.** Молчаливое дублирование запрещено.
- **Статус — механически** (см. таблицу): посчитай унаследованные TBD/⚠️, попавшие в часть, —
  это N. N ≥ 1 → «Требуются уточнения (N)», N = 0 → «Готово к оценке».

## Example (эпик-БТ in → confirm split → write)

**User:** даёт путь `docs/ARS-57/business_requirements.md` (эпик «Индикатор онлайн-
пользователей + история регламентных работ», FR-1…FR-5) и говорит «разбей на подзадачи».

**Agent** читает эпик-БТ, строит инвентарь FR, и через инструмент вопросов предлагает split:
«Предлагаю 2 части. **A — индикатор онлайн** = {FR-1, FR-2, FR-3}; **B — история
регламентных работ** = {FR-4, FR-5}. FR ни одного не потеряно, сквозных нет. Годится, или
поправить границы? Дальше: дайте по реальному ключу Jira на каждую часть (напр. `ARS-58`,
`ARS-59`), и порядок сборки — A раньше B?»

Пользователь просит: «в часть B добавь ещё выгрузку истории в Excel». Agent: «В эпик-БТ
такого FR нет — выгрузки в Excel в требованиях не было. Не могу добавить его здесь (я
только разрезаю подтверждённое). Если это нужно — допишем ЭПИК через
`business-requirements-doc`, затем вернёмся к декомпозиции.» — и не выдумывает FR.

**Только после подтверждения** (split, ключи `ARS-58`/`ARS-59`, порядок) Agent выводит
реестр, убеждается что покрытие сходится (FR-1..5 присвоены, ❓ нет), и пишет
`docs/ARS-57/decomposition.md` + `docs/ARS-57/ARS-58/business_requirements.md` (FR-1,2,3) +
`docs/ARS-57/ARS-59/business_requirements.md` (FR-4,5) — дети ВНУТРИ папки эпика, каждый с
общим контекстом из эпика дословно и `parent: ARS-57`. Затем говорит: по каждой папке запусти
`technical-spec-doc`.
