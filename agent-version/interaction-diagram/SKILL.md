# Схема взаимодействий: проекция источника

Ты не проектируешь — ты перерисовываешь пункты источника в картинку. Всё, что есть на схеме, должно
находиться в пункте источника или в ответе аналитика на твой вопрос. Стрелка или путь, которых нет ни
там, ни там, — выдумка, и читатель схемы проверить её не может.

## TL;DR — четыре правила, держи в голове всегда

1. **Вход — только из таблицы Step 0.** Дали другое — схемы нет: ответь строкой отказа из таблицы и
   закончи ход.
2. **Источник — пункты входа и ответы аналитика на вопросы Step 1 и Step 3.** Что из пункта идёт на
   схему — файл входа. Ни `services/`, ни `context/`, ни другие документы и разделы, ни то, что ты
   знаешь о системе.
3. **Одно звено — одна стрелка.** `A → B` — одна, `A → B → C` — две, у обеих id своего пункта.
   В короткой и сценарной служебных стрелок, `alt` и `loop` нет. В короткой нет ответов и пометок; в сценарной — только
   стрелка от пользователя, ответы, пометки с телами и внутренние шаги по файлу типа. В пути
   пользователя звеньев нет — шаги, развилки и возвраты по файлу типа.
4. **Сам не додумываешь и источник не правишь.** Вход даёт два типа — тип схемы и формат (если он не
   назван) спрашиваешь первым ходом (Step 1), вопросы Step 3 — следующим; вход даёт один тип — формат идёт
   вместе с вопросами Step 3 в первом ходе. Всё — до записи файла; о другом не спрашиваешь — остальное
   рисуешь по файлу входа буквально. Выход — один файл схемы рядом с источником.

Если правило ниже противоречит этому списку — прав список.

## Файлы скилла

За прогон открываешь три файла из `reference/`, по одному из каждой папки:

| Папка | Файл | Когда открываешь | Что в нём |
|---|---|---|---|
| `inputs/` | вход — таблица Step 0 | ход 1, до вопроса о типе | как читать источник, как пункт становится моделью, когда рисовать нечего, вопросы о чтении, слова для аналитика |
| `kinds/` | тип — таблица Step 1 | после ответа аналитика о типе; вход даёт один тип — сразу после файла входа | что рисовать, вопросы типа, шапка, самопроверка, отчёт |
| `notation/` | формат — таблица Step 1 | перед записью файла (Step 4) | строки, скелет файла, алиасы, самопроверка записи |

Они лежат в папке этого скилла, а не рядом с источником и не в рабочей папке, — искать их не нужно:
возьми путь, по которому ты открыл этот `SKILL.md`, и замени в нём `SKILL.md` на `reference/` и путь из
таблицы Step 0 или Step 1 (открыл `…/interaction-diagram/SKILL.md`, в таблице `kinds/short.md` → открой
`…/interaction-diagram/reference/kinds/short.md`).
Читай файл целиком. Не открылся по этому пути — так и скажи и дальше не иди: по памяти его не
восстанавливай. Других файлов из этих папок не открывай.

## Step 0 — вход

| Дали | Вход |
|---|---|
| путь к `technical_specification.md` или папку `docs/<KEY>/`, где она лежит | `inputs/spec.md` |
| путь к `business_requirements.md` или папку `docs/<KEY>/`, где лежат только БТ | `inputs/bt.md` |
| другое: `bug_report.md`, `change_request.md`, текст в чате | входа нет — ответ «Схема рисуется по готовой спецификации или бизнес-требованиям. Сначала `technical-spec-doc` или `business-requirements-doc`.» Файл не пишешь |

Дали папку `docs/<KEY>/`, где лежат и спека, и БТ: просят путь пользователя — вход БТ, иначе — спека.

Вход нашёлся → открой его файл и прочитай источник по нему. По файлу входа рисовать нечего — ответ из
него, файл не пишешь, ход закончен.

## Step 1 — тип и формат: первый ход

Какие типы схем даёт вход — строка «Типы» в его файле.

**Вход даёт один тип** — о типе не спрашиваешь: открой файл этого типа и в этом же ходе переходи к Step 3.
Формат не назван в запросе — в этом же ходе задай вопрос о формате (его текст — в следующем абзаце,
пояснение — в таблице форматов) первым среди вопросов Step 3; других вопросов нет — только его, и закончи
ход. Строка «больше в этом ходе ничего» следующего абзаца здесь не действует.

**Вход даёт короткую и сценарную** — источник прочитан, рисовать есть что → первым ходом спроси тип схемы,
всегда, что бы ни было в запросе:
«Какую схему рисовать: короткую — кто кого вызывает, по времени, — или сценарную — по диаграмме на
действие пользователя, с ответами и телами запросов?» Вариантов ответа два: «короткая» и
«сценарная» — «не знаю» и других не добавляй. Формат не назван в запросе («в mermaid», «плантюмл») —
в том же ходе спроси и его:
«В каком формате нарисовать: Mermaid или PlantUML?» — с пояснением из таблицы ниже. Больше в этом
ходе ничего: ни списка пунктов, ни других вопросов, ни файла. Вызов `AskUserQuestion`; инструмента
нет или вызов не прошёл — вопросы текстом, каждый со знаком `?`, и закончи ход.

Ответ аналитика однозначно называет один из двух типов вопроса — это он («длинная» — сценарная); иначе
задай вопрос о типе ещё раз: без типа схемы нет. Формат без ответа — Mermaid.

| Тип | Файл типа |
|---|---|
| короткая | `kinds/short.md` |
| сценарная | `kinds/scenario.md` |
| путь пользователя | `kinds/user-flow.md` |

| Формат | Файл формата | Короткая | Сценарная | Путь пользователя | Где рисуется |
|---|---|---|---|---|---|
| Mermaid | `notation/mermaid.md` | `interaction_diagram.md` | `interaction_scenarios.md` | `user_flow.md` | в GitHub, GitLab и JetBrains без установки, в VS Code — с расширением |
| PlantUML | `notation/plantuml.md` | `interaction_diagram.puml` | `interaction_scenarios.puml` | `user_flow.puml` | в IDE с плагином PlantUML; в GitHub виден как текст |

Тип выбран → открой файл своего типа. Дальше — Step 3.

## Step 2 — модель: что на схеме

Файл входа переводит пункт источника в эти элементы; файл типа и файл формата говорят только о них.

| Элемент | Что это |
|---|---|
| пункт | единица источника: id и название |
| участник | сторона звена; имя и что не склеивать — по файлу входа; порядок участников — по файлу входа, у сценарной — по файлу типа |
| звено | пара соседних сторон пункта: от кого к кому и вид — запрос, событие или двустороннее; у пункта одно звено или цепочка из нескольких |
| подпись звена | `<id>` или `<id> · <токен подписи>`; токен — по файлу входа |
| триггер пункта | что его запускает: действие пользователя, другой пункт, внутри которого он идёт, или ничего из этого — для сценарной |
| тело запроса, тело ответа | имена полей у своего звена — для сценарной |
| шаг, развилка, возврат, конец | для пути пользователя: действие, условие с ветками, стрелка к прежнему шагу, конец ветки — по файлу типа и файлу входа |

Слова для аналитика — в разделе «Слова» файла входа: в вопросах, шапке файла и отчёте `<пункты>`,
`<пунктов>`, `<пункту>`, `<пунктах>` — слово входа в этой форме, `<id>` — id пункта, `<образец id>` —
образец id из «Слов» как есть, без номера пункта.

## Step 3 — вопросы аналитику

Сначала покажи аналитику, как ты прочитал источник: по строке на каждый пункт, по порядку id, в том
числе на пункты, где направление не указано или не решено, — id, название и звенья, как ты их прочитал
по файлу входа, стороны буква в букву. Пункт без знака направления — «направление не указано» и две
стороны так, как их называет вопрос «нет направления» файла входа, так же буква в букву.

```
<id> «<название>»: A → B
<id> «<название>»: B → C → D
<id> «<название>»: направление не указано — E, F
```

Файл типа может дополнить строку или задать свою форму — тогда так, как сказано в нём. Этот список — основа вопросов; в нём
самом вопросов нет, знака `?` не ставь. Вопросы — только из таблиц «Вопросы»: этой, файла входа и файла
типа, и вопрос о формате, если его сюда ставит Step 1; каждый задаёшь, когда выполнено его условие.

| Вопрос | Условие | Что спрашиваешь |
|---|---|---|
| участники | участников больше двух | «Участников N: A, B, C, D. Считаю всех разными. Есть ли среди них один сервис под двумя именами? Если да — назовите пару» — каждое разное имя стороны из этого списка, буква в букву, по порядку участников; ни одного не пропускай |

Задаёшь все вопросы одним разом, сразу после списка, до записи файла. Вызов `AskUserQuestion`:
варианты ответа — твоя гипотеза (у направления и звена тела — все варианты) и «не знаю»; своё
аналитик впишет в поле свободного ответа. Вариантов вместе с «не знаю» больше четырёх — в вариантах
первые три и «не знаю», все — в тексте вопроса. Не поместились в четыре вопроса — следующий вызов
сразу следом. Инструмента нет или вызов не прошёл — задай вопросы текстом, нумерованным списком после
списка пунктов, каждый со знаком `?`, и закончи ход: ни файла, ни отчёта. Условие ни одного вопроса
не выполнено и вопроса о формате нет — сразу Step 4.

Ответ аналитика главнее твоего прочтения источника — рисуй, как сказано, второй раз не спрашивай.
Двоих назвали одним сервисом → один участник; имя — какое назвал аналитик, не назвал — то, что в
источнике встретилось первым. Как применить остальные ответы — сказано рядом с вопросом.

Есть вопросы о дырах источника — о том, чего пункту не хватило, чтобы нарисовать его без вопроса. Какие
это вопросы, сказано рядом с таблицей «Вопросы» в файле входа и файле типа; здесь — «участники», если
аналитик назвал пару имён одного сервиса. Ответ на такой вопрос, который что-то добавил, идёт в строку
отчёта «в источник стоит внести». Ничего не добавили только «да, верно» на твою единственную гипотезу и
«не знаю»; выбор одного из вариантов, своё слово или поправка — добавили.

Аналитик сказал «не знаю», пропустил вопрос или ответил непонятно — вопрос остался без ответа, и ты
не додумываешь: что делаешь — в таблице «Без ответа» того файла, где задан вопрос. Участники без
ответа — все отдельные, как в источнике.

## Step 4 — запись и самопроверка

Открой файл формата. Файл схемы пишешь по скелету своего типа из файла формата, рядом с источником, в
той же папке, с именем из таблицы Step 1. Есть старый файл того же типа и формата — перепиши целиком,
по одной стрелке не правь. Есть другие файлы схем (другой формат или тип) — не трогай и назови их в
отчёте: схемы одного источника разъезжаются при первой правке пунктов.

Записал — перечитай файл и пройди самопроверку файла типа, затем файла формата. Не сошлось — перепиши
файл и проверь снова.

## Step 5 — отчёт

Отчёт — в ответе аналитику; в файл схемы он не идёт.

```
схема: <путь к записанному файлу> (Mermaid)
<пунктов>: 4 из 4, стрелок: 4
порядок: по времени, со слов аналитика
со слов аналитика: участники — все разные
без ответа: —
без стрелки: —
в источник стоит внести: —
другие схемы рядом: —
```

- «Порядок» и «стрелок» — строки короткой; у другого типа вместо них — строки из раздела «Отчёт» его
  файла.
- «В источник стоит внести» — ответы на вопросы о дырах, которые что-то добавили (Step 3): по пункту
  «<id>: <что сказал аналитик>», несколько ответов одного пункта — через «,»; ответ об участниках —
  «участники: X = Y»; записи — через «;», в конце строки один раз в скобках `<кто правит источник>` из
  «Слов» входа; таких ответов нет — «—».
- «Со слов аналитика» — каждый вопрос про участников и пункты, на который аналитик ответил, даже
  если он подтвердил твою гипотезу, с его ответом («X = Y», «<id> — два звена», «<id>: A → B»).
- «Без ответа» — вопросы, оставшиеся без ответа («порядок», «<id> — цепочка»).
- «Без стрелки» — id пунктов, которых нет на схеме, с причиной.
- Рядом одна строка, где схема рисуется для выбранного формата (из таблицы Step 1).

Больше ничего: пересказ схемы словами — то же, что вторая схема.

## Чего ты не делаешь никогда

- **Не правишь источник.** Даже если пункт без направления и ответ очевиден.
- **Не пишешь схему внутрь источника.** Схема — отдельный файл; источник остаётся одним файлом одного
  автора.
- Остальное, чего не делаешь со своим входом, — в его файле.
