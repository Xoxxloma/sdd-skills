## 1. Что берём из `diagram-plan.md`

## 2. Каркас

```
interaction-diagram/
  SKILL.md               # ядро: маршрут входа, ходы, словарь модели, типы и форматы, вопросы ядра,
                         #   «без ответа» ядра, запись, отчёт, «никогда»
  reference/
    inputs/spec.md       # спека: отказ без INT, чтение карточки → модель, вопросы о чтении, тела
    kinds/short.md       # короткая: что рисуем, порядок, вопрос о порядке, самопроверка
    kinds/scenario.md    # сценарная: сценарии, ответы, тела, внутренние шаги, вопросы, самопроверка, отчёт
    notation/mermaid.md  # строки, скелет на каждый тип, алиасы, экранирование, расширение файла
    notation/plantuml.md
```

Порядок открытия:
1. Ход 1: `SKILL.md`, затем вход по маршруту → `inputs/<вход>.md`. Вход говорит, какие типы он даёт; из
   них строится вопрос о типе.
2. После ответа о типе → `kinds/<тип>.md`.
3. Перед записью → `notation/<формат>.md`.

**Маршрут** — таблица в `SKILL.md` «признак файла → вход», по строке на вход. Это отступ от «SKILL.md не
трогаем» из плана владельца: frontmatter у наших документов нет, признак — имя файла. Новый вход = файл
в `inputs/` + строка маршрута.

**Типы и форматы** — таблицы в `SKILL.md`: тип → одна строка описания для вопроса → основа имени файла
(`interaction_diagram` / `interaction_scenarios`); формат → расширение → где рисуется. Всё нужное для
хода 1 — в ядре.

## 3. Модель — словарь ядра

| Элемент | Что это | Кто задаёт |
|---|---|---|
| пункт | единица источника: id и название | вход (`INT-N`, заголовок карточки) |
| участник | имя стороны буква в букву | вход; склейка двух имён — ответ аналитика |
| звено | от → к; вид: вызов, событие, двусторонний | вход |
| подпись звена | `<id пункта> · <метод с путём или имя события>` или только id | вход |
| что запускает пункт | действие пользователя или «внутри пункта X» | вход |
| тело запроса / ответа | имена полей у своего звена | вход |
| ответ | пунктир на каждое звено-вызов | тип (сценарная) |
| внутренний шаг | только со слов аналитика | тип (сценарная) |
| порядок, сценарии | гипотеза + ответ аналитика | тип |

Модель живёт в чате: список прочтения хода 2 — её видимая часть, как сейчас (решение Р1).

**Слова входа.** Ядро и типы говорят «пункт»; аналитик видит слово входа. Файл входа держит раздел «Слова»:
`<пункты>`/`<пунктов>`/`<пункту>`/`<пунктах>` (у спеки — «карточка» в той же форме), `<образец id>` (`INT-N`),
`<пункты источника>` (шапка файла), `<KEY>`. Так шапка и вопросы по спеке остаются прежними («по номерам
карточек, не по времени»), а ядро о спеке не знает.

## 5. generic — как не падать в него

В шаге 1 generic нет: ветка «вход не опознан» — отказ, как сейчас. Схема на потом (шаг 3, решение Р5):

1. Сначала известные входы по признаку. Опознан — только его файл. Всё, что с ним не так (нет
   карточек, нет раздела), — отказ этого входа, не generic.
2. Известный документ, который не вход (баг-репорт, запрос на правку), — отказ с подсказкой, как сейчас.
3. Не опознан (текст в чате, чужой файл) — не generic сразу, а вопрос: «Это не спека, не БТ и не список
   пунктов. Нарисовать по тексту черновиком — что не сказано прямо, спрошу, — или сначала собрать документ
   (`technical-spec-doc` / `analyst-notebook`)?» Рекомендация — документ.
4. В generic модель всегда идёт на подтверждение, в шапке файла — «черновик по тексту».

Стенд для шага 3: ловушки «спека без INT», «спека с битой карточкой», «БТ» — ни одного захода в generic.

## 8. Шаг 2 — БТ и список пунктов

Два среза, каждый со своим замером: 2а — БТ и новый тип «путь пользователя», 2б — список пунктов. Срез 2б
начинается после зелёного 2а.

### 8.1. Что видно в источниках

- БТ §4.1 — абзацы `**FR-N. <название>**` прозой: кто что делает, развилки словами («если…», «иначе»), без
  структуры полей. Выдумать шаг или ветку легче, чем у INT-карточки, — список прочтения и вопросы здесь важнее.
- `*.points.md` — одна форма у `/analyst-notebook собери пункты` и у `/meeting-intake`: шапка `# Пункты: <тема>`,
  строки `- [вид] текст — хвост · <ссылка>`; ссылка — `<дата> №<n>` (ноут) или `L<строка>` (встреча).
  Взаимодействия и шаги — прозой в тексте пункта.

### 8.2. Срез 2а — БТ, «путь пользователя», строка «в источник стоит внести»

Скилл:
- `kinds/user-flow.md` — «путь пользователя»: актор, шаги, развилки (не меньше двух веток, у каждой — куда),
  исходы; возврат назад — ветка к прежнему шагу. Вопросы типа: описана только одна ветка развилки — «что при
  „нет“?»; ветка без исхода — «чем кончается?». Без ответа: ветки нет на схеме, в отчёте «без ответа».
- `inputs/bt.md` — `business_requirements.md`, читается только §4.1; пункт — `FR-N`, слово — «требование»;
  шаг — действие актора или системы из текста FR, развилка — условие («если», «в случае», «иначе»); FR без
  действия (роли, ограничения) — не шаг, в отчёте «не на схеме». Отказ: §4.1 пуст или TBD.
- Тип по входу: файл входа говорит, какие типы он даёт, и дословно задаёт вопрос о типе. Спека — короткая и
  сценарная, вопрос прежний (без изменений для спеки); БТ — один тип, вопроса о типе нет, только о формате, если
  не назван. Таблица типов в ядре + строка «путь пользователя» (`user_flow.md` / `user_flow.puml`).
- `notation/*` — строки и скелет пути: Mermaid `flowchart TB` (узлы `N1`, `N2`… — не кебаб; текст в кавычках;
  начало и исходы `(["…"])`, развилка `{"…?"}`, ветка `-- <метка> -->`); PlantUML activity (`start`/`stop`,
  `:шаг;`, `if … then … else … endif`; возврат назад — `repeat … repeat while`, граф не укладывается — упростить,
  сказать что и предложить Mermaid).
- Источник у каждого элемента: в тексте узла `FR-N · <шаг>` (как `INT-N ·` на стрелке).
- Ядро: строка отчёта «в источник стоит внести: <ответы аналитика, закрывшие дыры>»; кто правит источник —
  файл входа (спека — доработка `technical-spec-doc`, БТ — `business-requirements-doc`). Ответ о типе —
  «однозначно называет тип», вместо слова «длинная».

Стенд:
- Фикстура БТ (своя предметная область, не из прошлых фикстур): FR с линейными шагами, FR с «если/иначе», FR
  только с позитивной веткой, FR с возвратом («повторяет ввод»), FR-роль без действия. Собирает отдельный
  субагент; реплики аналитика — слепое прочтение свежим субагентом до пула.
- Грейдер `grade-uf.mjs`: разбор Mermaid flowchart и PlantUML activity в граф (узлы, ветки, исходы); истина —
  руками по фикстуре; якоря: файл и имя, источник не тронут, шаги = истине (с `FR-N`), развилки и метки веток,
  исходы, возврат — `repeat`/`while` в PlantUML, нет узлов от себя, синтаксис, по файлу из папки; вопросы хода
  2 — о негативной ветке и об исходе. `--selftest` с эталоном и известными красными.
- Пробы: `bt-uf-mmd`, `bt-uf-puml` (реплика с ответами), `bt-uf-idk` («не знаю»), `bt-uf-y` («да, всё верно»).
- Регресс спеки — пул шага 1 (вопрос о типе и отчёт в ядре тронуты).

|---|---|---|---|
| новые пробы БТ | Sonnet | 4 × 5 | ≈ $5–14 |
| новые пробы БТ | Haiku | 4 × 10 | ≈ $2 |
| регресс спеки (как шаг 1) | Haiku + Sonnet | 150 | ≈ $6 |
| пилот | обе | ~25 | ≈ $2 |

Итого среза 2а ≈ $15–25. Пороги новых проб — до пула: схема верна ≥ 4/5 на Sonnet по каждой пробе, вопрос о
негативной ветке и исходе — 5/5; Haiku — диагностика, не порог (прод — уровня Sonnet).

### 8.3. Срез 2б — список пунктов

- `inputs/points.md` — `*.points.md`; пункт — строка, id — ссылка после ` · `, слово — «пункт». Типы: короткая и
  путь пользователя (сценарной нет: тел и триггеров в пунктах нет). Рисуются `решено` и `сведение`; `открыто` —
  вопрос аналитику, без ответа не рисуется; `мысль`, `набросок` — не рисуются, в отчёте «не на схеме: N» (Р3).
  Кто правит источник — новая запись в ноут (`/analyst-notebook`); список пунктов не правится.
- `analyst-notebook` — одна строка в «Сборке», рядом с отсылкой про вход в БТ/спеку: просят схему взаимодействий
  или путь пользователя — «схему рисует `/interaction-diagram` по списку — сначала `/analyst-notebook <тема>
  собери пункты`», конец (Р2). Версия ноута — patch.
- Стенд: фикстура списка пунктов (ноут и встреча — по одной), пробы короткой и пути по списку, проба ноута
  «собери схему» → отсылка. Грейдеры — `grade-id.mjs` (истина короткой — таблица руками) и `grade-uf.mjs`.
- Цена — по итогу 2а; ориентир ≈ $15.

Уточнено при работе (2026-10-18):
- id пункта — `п.N` (номер строки-пункта в списке), не ссылка после ` · `: у пунктов одной записи ноута ссылка одна,
  у списка встречи из сообщения у всех ` · сообщение`; по `п.N` аналитик называет порядок.
- `открыто` — гипотеза «не рисую, пока не решено», варианты — прочтения пункта; выбранный вариант — дыра списка.
- Имя файла схемы — с основой имени списка (`meeting-<дата>.interaction_diagram.md`): без неё схема по встрече
  затирает схему по спеке в `docs/<KEY>/`.
- Ядро: вопрос о типе — на пару «короткая и путь пользователя» вторым дословным текстом; ноут вместо списка — отсылка
  к `собери пункты`.
- Стенд: фикстура `ID-PT` (встреча — короткая, выгрузка ноута — путь), пробы `pt-sh-mmd`, `pt-sh-idk`, `pt-uf-puml`,
  `pt-uf-idk`, `pt-raw`, `pt-nb`; грейдер `grade-pt.mjs` (короткая — свой разбор стрелок, путь — `grade-uf.mjs` с id
  `п.N`).

## 9. Правила расширения (не в скилл)

- Новый вход → файл в `inputs/` + строка маршрута в `SKILL.md` + какие типы он даёт.
- Изменился формат входа → правится только его файл.
- Новый тип → файл в `kinds/` + строка в таблице типов + скелет и строки в каждом файле `notation/`.
- Новая нотация → файл в `notation/` со скелетом на каждый тип + строка в таблице форматов.
- Имя входа или его поля в `SKILL.md` / `kinds/` — утечка, переносится в `inputs/`.
