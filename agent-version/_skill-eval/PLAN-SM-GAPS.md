# План: service-map-2.0 4.4.0 → 4.5.0 — недобор карточки по корню

Основание — разбор 2026-10-24/25: прод (ueb ×3, geo ×2, adjutant 25–28, v1 против 2.0), стенд SM-GAPS (синтетика,
три модели) и SM-APOLLO (настоящий код, v1 против 2.0 на Sonnet и DeepSeek). Числа — `runs/2026-10-24-gaps*`,
`runs/2026-10-24-apollo-*`; разбор — память `service-map-2-0-gap-diagnosis`.

## 0. Корень

**2.0 собирает в карточку то, что перечислил конвейер, и сверяет только перечисленное.** Перечень ключей строят
маркеры разведчика, факты — строки описи под ключом, полноту — скрипт по этому перечню. Чего в перечне нет, то
теряется одинаково на любой модели (Sonnet и DeepSeek в 2.0 ошибаются одинаково). v1 перечня не строит — её
полнота держится на усердии модели (на Sonnet лучше 2.0, на DeepSeek хуже). Решение: остаёмся на 2.0 и закрываем
дыры перечня, а не отдельные потери.

Дыр четыре. Каждая — механизм, а не правка под симптом:

| | Дыра перечня | Симптомы, которые она даёт |
|---|---|---|
| К1 | ключи есть, только если их пометил маркер разведчика | внешний API по чужой спеке: 15–20 из 153 (Apollo, обе модели; v1 Sonnet — 141); вес и нарезка скачут от выбора маркера (ueb 54 / 25 / 29) |
| К2 | ключ без полной формы «метод + путь» удаляется, а не помечается | объявленная без реализации ручка исчезает молча (ueb 0/3, adjutant 0/4, SM-GAPS 0/7 на всех моделях); путь без спеки — потеря или выдумка |
| К3 | у фактов о сервисе целиком нет строки в описи | вход (geo — догадка «шлюз» 2/2; Apollo — вшитый пользователь у 2.0 0/2 в «Ролях»); связь не через клиента (ueb 2/3, geo 2/2); точки встраивания фронта (geo 0/2, SM-GAPS 0/1) |
| К4 | секции сверяются с минимумом, а не с перечнем | «Что умеет» вдвое беднее (прод 5/5; Apollo Sonnet 38 → 25): проверка требует «хотя бы строку на группу» и разрешает «сворачивать по несколько ключей»; у задачи нет места для параллельного запуска (ueb 0/3) |

Не лечим (известные стыки, в CHANGELOG): разброс свободных фактов между прогонами, глубина внутри экранов,
чужие таблицы во «Владеет данными», имена соседей вне манифеста.

## 1. Механизмы

### М1 — перечень ключей от кода, а не от маркера (К1)

- `plan.sh` находит **реализации сгенерированных интерфейсов** сам, мимо разведчика — так же, как с 3.7.0 находит
  спецификации и топики конфига. Признак: класс `implements X`, интерфейс `X` в исходниках репы не объявлен, а в
  файле сборки есть генератор (openapi-generator, swagger-codegen). Каждый публичный метод с `@Override` в таком
  классе — ключ контракта.
- Ключ — `Класс.метод` (класс реализации; форма gRPC, её уже понимают `keys.awk` и `check.sh` — грамматика ключа не
  меняется). Спека на диске есть — работает текущая ветка: метод и путь из спеки.
- Эти ключи идут в вес (класс «контракт», вид «ключ»), в части — по файлу реализации, в маркерный гейт и в строку
  плана `реализация` — для сверки, как `операция` у спеки.
- **Решение о нарезке — по весу ключей.** Ориентир только раскладывает работу по частям: его число зависит от
  маркера, выбранного разведчиком.
- `check.sh`: строка плана `реализация` без блока в карточке — пункт добора автору (вид как `SPEC`).

Почему корень: перечень и вес перестают зависеть от решения разведчика.

### М2 — статус ключа вместо удаления (К2)

- Одна строка второго уровня описи под любым ключом — `недоступно: <почему> — <файл>`: обработчика нет, заглушка
  (501, «не реализовано»), экран или категория на заглушках или убраны из меню, клиент объявлен и не вызывается.
- В карточке — первой из строк `- ` блока `- недоступно: …`, у строки таблицы — в последней колонке, и строкой «Что умеет»
  «<возможность> — недоступно: <почему>».
- Правило 3.1.1 («обработчика нет — блока не пиши, строка `> объявлено без реализации`») снимается: ключ пишется со
  строкой `недоступно: объявлено без реализации — <файл спеки>`. `check.sh`: вид `DECL` переворачивается — ключ с
  `недоступно:` в описи без пометки в карточке → добор.
- Ключ из М1 без пути — тот же принцип: `путь: не определено — спецификация вне репозитория (<адрес из сборки>)`,
  а не выдуманный путь и не удаление.

Почему корень: снято само правило «нет полной формы — нет ключа».

### М3 — строки уровня сервиса в описи (К3)

- `вход: <как запрос получает пользователя и права: фильтр, интерсептор, откуда токен, профиль по умолчанию> — <файл>`
  — одна на сервис, у всех типов; в коде нет — `вход: не определено: в коде нет`. В карточке — строка `вход` в
  «Ролях и доступе». `check.sh`: строки `вход:` в описи нет → добор; пара со строкой таблицы ролей.
- `зависит:` — по смыслу связи, а не по файлу клиента: вызов или клиент; чтение таблиц и представлений чужой схемы;
  переход пользователя по ссылке; загрузка чужого файла, конфига, скрипта. Источник — место связи. `check.sh`: имя
  из `зависит:` без строки «Зависит от» → добор.
- Точка встраивания фронта и библиотеки (Module Federation `exposes`, веб-компонент) — ключ «Экранов»
  (`MF ./Имя`), то, что передаёт хост, — факты под ним. Новой секции нет. `exposes` из конфига сборки находит
  `plan.sh` (строки плана `точка`), `check.sh`: точка без строки «Экранов» → добор (вид `EXPOSE`).
- Подсказки «роли ставит шлюз» (бриф) и «роли проставляет шлюз» (шаблон) заменяются на «что об этом видно в коде».

Почему корень: у фактов о сервисе целиком появляется место в перечне — их перечисляет и сверяет конвейер.

### М4 — секции сверяются с перечнем, а не с минимумом (К4)

- «Что умеет»: строка на **действие** (глагол); два действия в одной строке — две строки; «сворачивать по несколько
  ключей» разрешено только для ключей одного действия (список и его фильтр). Снимается разрешение складывать.
- `check.sh`: строка «Что умеет» с двумя действиями-глаголами → добор «разбей» (вид новый). Группы для полноты:
  сегменты-обвязка пути (`api`, `openapi`, `v1…vN`) группой не считаются — сейчас весь `/openapi/v1/…` одна группа.
  Проверка групп в Шаге 4 остаётся.
- Блок задачи: строка-метка `- наложение: <блокировка и её срок | блокировки нет — что будет при нескольких
  репликах>`, как метки «Событий»; вид `SLOT` в `check.sh` распространяется на задачи.

Почему корень: требование секции — по перечню (действия, метки формы), а не «хотя бы одна строка».

## 2. Согласование — одна грамматика описи

| Строка описи | Уровень | Пишет (один читающий / нарезка) | В карточке | Сверка |
|---|---|---|---|---|
| `Класс.метод — <файл>` | ключ | читающий / часть по файлу | `### Класс.метод` + `путь: не определено …` | план `реализация`, гейт |
| `недоступно: … — <файл>` | под ключом | автор ключа | первая строка блока / колонка / «Что умеет» | `DECL` (перевёрнут) |
| `вход: … — <файл>` | сервис | читающий / голова | «Роли и доступ», строка `вход` | новый вид |
| `зависит: <имя> — <зачем> — <файл>` | сервис | читающий / части → голова | «Зависит от» | новый вид + `INFRA` |
| `MF ./Имя — <файл>` | ключ экрана | читающий | «Экраны» | пара ключей таблицы, план `точка` |
| — | секция | голова / читающий | «Что умеет», строка на действие | новый вид, группы |
| — | метка | автор блока задачи | `наложение` | `SLOT` |

Точки согласования:
- `keys.awk`: ключ `Класс.метод` уже ключ контракта, правок нет; разбор строки `вход:` (пара с ролями) и
  `недоступно:` (строка второго уровня — как `·`, не ключ) — в `check.sh`.
- Нарезка: части пишут ключи М1 со статусом М2 и строки `зависит:`; голова — `вход:` (в своей описи), «Роли»,
  «Зависит от», «Что умеет»; `assemble.sh` ничего нового не склеивает — проверить, что строки `недоступно` и метки
  задач проходят склейку как обычные строки блока.
- Шаг 4 `SKILL.md`: «Полнота возможностей» — добавить склейку; отчёт — строки `недоступно` вместо «объявлено без
  реализации»; 3.5 — вес по ключам; 3.1 — строка вывода `plan.sh` о реализациях интерфейсов.
- Обратные рёбра (`edges.sh`): «Зависит от» шире → больше зеркал вида «сервис — зачем»; механика есть.
- Гард рескана: новые ключи — появление, не исчезновение. Стык: появилась спека в репе — ключ меняет форму
  `Класс.метод` → «метод путь», гард увидит исчезновение; в CHANGELOG.
- Потребители: `business-requirements-doc` берёт «Что умеет» как есть — «недоступно» в строке ему полезно;
  `technical-spec-doc` читает «Зависит от» и «Роли» — новых секций нет.
- Утечка: примеры — домен шаблона (обсерватория), без имён прода и фикстур; grep-проверка в каждом этапе.
- Не трогаем: v1 (`service-map`), `archive-spec`. `keyed-update.md` — проверить упоминания `> объявлено без реализации`.

## 3. Порядок работ

3. **М3** — брифы читающего, части, головы; шаблон; `check.sh`. Самотесты: `вход` есть / нет / не определено;

4. **М4** — бриф, шаблон, `check.sh`, Шаг 4. Самотесты: склеенная строка, группы `/openapi/v1/…`, метка задачи.

7. **CHANGELOG** (номер — по `origin/main`), версия 4.5.0; прод — владелец.

## 6. Риски

- Добор — одна волна, видов больше: новые виды срабатывают только на явном условии.
- Ложные «сгенерированные интерфейсы»: условие двойное — интерфейса нет в исходниках и генератор есть в сборке.
- Склейку ищем по глаголам-действиям — эвристика; срабатывание — добор, запись не останавливает.
- Нагрузка на читающего: на сервис +3–10 строк описи; под ключом новая только `недоступно` (редко).
