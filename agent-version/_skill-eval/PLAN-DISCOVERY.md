# План: досье дискавери — запись с проверкой, ответ с опорой, проекции

Дата: 2026-10-14. Статус: **стратегия, реализации нет.** Решения, которые нужны от владельца до начала
работ, собраны в последнем разделе.

## Повод

На дискавери аналитик неделями собирает сведения: созвоны, переписку, ответы смежников, свои заметки. В
пайплайн это попадает пересказом по памяти во время интервью `business-requirements-doc`, а противоречия
между людьми всплывают на приёмке БТ или уже в разработке. `meeting-intake` разбирает одну встречу, а
прошлых встреч не видит: решение, переигранное через неделю, и спор юриста с заказчиком, высказанный в
разные дни, он не сопоставит. Сверяет он только с документами задачи.

Нужен один файл на задачу, куда складывается всё, и три режима работы с ним:

1. **запись** — явный поиск противоречий и вопрос «чего на самом деле хотят»;
2. **чтение** — ответ на вопрос по накопленному, с опорой на записи;
3. **проекция** — из того же файла: вход для БТ и спеки, схема взаимодействия, картинка для бизнеса и всё,
   что понадобится дальше.

## Доктрина: досье — источник, всё остальное — проекции

| Режим | Аналог | Главное правило |
|---|---|---|
| запись | запись в базу с проверкой ограничений | сначала на диск, потом вопросы; противоречие — находка дискавери, а не ошибка ввода |
| чтение | запрос с происхождением | у каждого ответа ссылка на запись; «в досье нет» — законный ответ |
| проекция | представление (view) | только из действующих записей; пересобирается целиком; руками не правится — правят досье |

Из доктрины три следствия.

- **Один файл — да, но это источник, а не свалка.** В досье лежат атомарные утверждения с
  происхождением. Сырьё живёт в своих местах: расшифровка — у `meeting-intake`, регламент — в `context/`
  через `context-doc`. Проекции — отдельные файлы рядом. Это та же доктрина, что у карточек сервисов
  (`PLAN-PROJECTION.md`): каждый выход пересобирается из своего происхождения.
- **Проекция честна настолько, насколько типизирована запись.** Схема без выдуманных стрелок возможна,
  только если при записи отмечено, кто кому что передаёт. Поэтому у записи есть необязательные **грани**
  (`обмен`, `термин`, `переход`, `данные`). Их ставят при записи, когда они очевидны, а проекции берут их
  механически, не додумывая по сути.
- **Противоречие чаще всего — симптом невыясненной цели.** Юрист говорит «храним 3 года», аналитика —
  «5 лет»: спорят не о числе, а о том, зачем хранить. Поэтому вопрос «чего хотят» и поиск противоречий —
  один механизм, а не два.

## Что кладём в досье и чего не кладём

| Кладём | Не кладём — и куда вместо |
|---|---|
| решения, условные решения, открытые вопросы, вынесенное за рамки, сведения, поручения со сроком | расшифровку целиком → `meeting-intake`; в досье идёт его разбор |
| цели: проблема, для кого, результат, как поймём | регламент, стандарт, справочник → `context-doc` |
| допущения («считаем, что …» — никем не подтверждено) | устройство кода соседей → `service-map` |
| слова аналитика — с пометкой «со слов аналитика» | оценки людей, офтоп, статусы работ без решений |

## Устройство файла

Путь — `docs/<KEY>/discovery.md`. Ключа ещё нет — `docs/_inbox/discovery-<слово>.md` (как у
`meeting-intake`); перенос в папку задачи, когда ключ появится, делается при очередной записи.

```markdown
# Досье <KEY>: <рабочее название>

> Задача: <KEY | ключа нет> · начато: <дата> · документы задачи: <пути | нет>
> Роли: заказчик — <ФИО>; владелец процесса — …; архитектор — …; <чужая система> — …

## Чего хотят
- Проблема: <суть> [D-003]
- Для кого: <суть> [D-005]
- Результат: <суть> [D-003]
- Как поймём: —

## Источники
| # | дата | что | кто | записи |
|---|---|---|---|---|
| S-1 | 2026-10-08 | заметки аналитика после звонка | Орлова | D-001–D-006 |
| S-2 | 2026-10-12 | встреча, `meeting-2026-10-12.razbor.md` | Орлова, Ким, Лаптев | D-007–D-019 |

## Записи

### D-012 · решение · БТ · отмена брони
- суть: бронь можно отменить без штрафа не позже чем за час до начала
- кто: предложил Ким; принял Орлова (заказчик)
- источник: S-2 · разбор #5
- зачем: переговорки простаивают из-за неотменённых броней [D-003]
- связи: заменяет D-004
- статус: действует

## Выдано
| дата | проекция | файл | из записей |
|---|---|---|---|
```

**Запись.** Заголовок `### D-<N> · <вид> · <слой> · <предмет>`, по нему ищут все три режима. Обязательны
поля `суть`, `кто`, `источник`, `статус`; остальные — когда есть что писать.

**Словарь — общий с `meeting-intake`** (`reference/extract.md`): тогда разбор встречи импортируется без
перевода. Правится в обоих скиллах вместе, как `skills.sh` и `skills.ps1`.

- **вид:** решение · условное · открытый вопрос · вне рамок · сведение · поручение — и два своих:
  **цель** (проблема, для кого, результат, мера) и **допущение** (принято без подтверждения);
- **слой:** БТ · спека · чужая система · вне документов;
- **связи:** `заменяет D-…` (тот же вопрос, новый ответ) · `уточняет D-…` (добавляет, не спорит) ·
  `спорит с D-…` (два ответа, выбора нет) · `отвечает на D-…` (закрывает открытый вопрос);
- **статус:** действует · заменено D-… · спорно · закрыт (у вопроса) · снято;
- **грани** (необязательны): `обмен: <A> → <B>: <что>[, синхронно | фоном]` ·
  `термин: <слово> = <значение>` · `переход: <статус> → <статус>: <когда>` · `данные: <объект>: <атрибут>`.

**Инварианты.**

1. Записи только дописываются. Записанная `суть` не переписывается: новый ответ — новая запись со связью
   `заменяет`, история остаётся.
2. Номер записи не меняется и не переиспользуется: на него ссылаются проекции и раздел «Выдано».
3. У существующей записи меняются только `статус`, `связи` и строка `подтвердил: <кто>, S-N` — тот же факт
   из другого источника не дублируется новой записью. Исключение — ошибка записи по слову аналитика
   («поправь D-012: за два часа, не за час»): правка с пометкой `исправлено: <дата>, со слов аналитика`.
4. «Чего хотят» — единственная сводка в файле. Она пересобирается из действующих записей вида «цель»,
   когда такая запись появляется или заменяется.
5. Один писатель на досье (почему — в «Рисках»).

## Режим 1 — запись

### Входы

| Дали | Что делаешь |
|---|---|
| текст в сообщении до ~150 строк: заметки, кусок переписки, диктовка «запиши: …» | извлекаешь записи сам |
| путь к `*.razbor.md` | импортируешь записи разбора как есть: вид, слой, кто, `решение аналитика`. Источник — разбор и номер записи, цитаты остаются в разборе. При повторном импорте того же разбора — только записи, которых ещё нет |
| путь к текстовому файлу длиннее (письмо, заметки) | извлекает субагент по `reference/entry.md`, ты сверяешь |
| расшифровка встречи | стоп: «сначала `/meeting-intake <файл>`, потом сюда его разбор» |
| ответ на вопрос этого скилла | запись с источником «ответ аналитика <дата>» |

### Шаги

1. **Файл.** Есть — читаешь шапку, «Чего хотят» и заголовки записей. Нет — создаёшь. Ролей в шапке нет, а
   во входе есть решение слоя БТ — вопрос о ролях встаёт в очередь (последним): без ролей не понять, кто
   решает, но запись их не ждёт.
2. **Записи** — по `reference/entry.md`.
3. **Сначала на диск:** дописать записи, источник — строкой в «Источники».
4. **Проверки** по каждой новой записи (таблица ниже) → связи и статусы.
5. **Отчёт:** записано N (по видам), какие связи, что нашлось — и один вопрос.

**Почему сначала на диск, а не после подтверждения, как у `meeting-intake`.** Вход `meeting-intake` уходит
прямо в пайплайн, поэтому подтверждение до записи там оправдано. Досье — рабочая тетрадь: запись в нём
ничего не решает до проекции, а проекция проверяется отдельно. Подтверждение до записи стоило бы хода на
каждую заметку, а аналитик пишет посреди созвона; оборванный разговор не должен терять записанное. Ошибку
записи исправляет строка «поправь D-…».

### Проверки при записи

Кандидаты на сравнение — записи того же предмета: `Grep` по словам предмета и ключевым существительным
сути в заголовках `### D-` и строках `суть:`. Весь файл при каждой записи не читается. Предмет новой записи
сначала подбирается из уже записанных; новый заводится, только если не подошёл ни один, — иначе одно и то
же разойдётся по двум предметам и проверка не увидит спора.

| Что нашлось | Как опознать | Что делаешь |
|---|---|---|
| тот же факт | тот же ответ на тот же вопрос | новой записи нет; `подтвердил:` у старой |
| уточнение | добавляет срок, состав, пример — и не спорит | `уточняет D-…`, без вопроса |
| тот же человек передумал | тот же вопрос, другой ответ, тот же человек, позже | `заменяет D-…`, старая — `заменено`; строкой в отчёте, без вопроса |
| спор людей | тот же вопрос, другой ответ, разные люди | обе — `спорно`, связь `спорит с`; **вопрос** |
| расхождение с документом | запись слоя БТ говорит обратное БТ задачи (слоя спеки — спеке) | `спорно`; вопрос «к автору документа» |
| ответ на открытый вопрос | новое решение или сведение по предмету открытого вопроса | `отвечает на D-…`, вопрос — `закрыт` |
| решение без цели | слой БТ, решение названо предметом («кнопка», «выгрузка», «поле», «рассылка»), `зачем` нет, и ни одной действующей цели оно не служит | **вопрос** «зачем» — один раз на предмет |
| решение не от того, кто решает | решение слоя БТ принял не заказчик и не владелец процесса (по ролям) | вид → `условное` |

**Противоречия между разными предметами** («доступ только у администраторов» и «участник сам переносит
бронь») локальная проверка не ловит. Для них есть **ревизия**: `/discovery-log <KEY> ревизия` — и
автоматически перед проекцией во вход БТ или спеки. Субагент с чистым контекстом читает досье целиком по
`reference/audit.md` и возвращает пары записей, которые не могут выполняться вместе, термины в двух
значениях, решения без цели и вопросы без адресата. Ведущий открывает названные записи сам и только потом
спрашивает. Досье длиннее ~800 строк — по субагенту на группу предметов.

### «Чего на самом деле хотят»

- **Цель — запись первого класса** (вид «цель»), а не поле анкеты. Четыре строки «Чего хотят» — это гейты
  10, 12, 5 и 4 `business-requirements-doc` (проблематика, потребитель, цель, ценность). Проекция во вход БТ
  их закрывает, а не переспрашивает.
- **«Зачем» — не больше двух ступеней:** «зачем это нужно?» → «что будет, если не сделать?». Дальше —
  открытый вопрос к заказчику.
- **Варианты ответа строятся из досье:** первыми — действующие цели («это ради «переговорки простаивают»
  [D-003]?»), затем «это новая цель — запишу» и «в вопросы к <заказчик>».
- **В споре сначала спрашиваешь о цели, потом о числе.** У сторон разное `зачем` — спорят цели, и решает
  владелец цели. Одинаковое — спорят средства, и решает владелец слоя.
- **Аналитик не знает ответа — нормальный исход:** открытый вопрос с адресатом. Он попадёт в проекцию
  «вопросы к встрече».

### Вопросы

Один вопрос за ход, гипотезой, рекомендация первой — как во всей петле. Порядок: спор людей слоя БТ →
расхождение с документом → прочие споры → решение без цели → роли. В вопросе — оба номера и обе стороны:
«D-009 (Ким, 10.10): храним 3 года. D-021 (Лаптев, 14.10): 5 лет. Что действует?»

| Ситуация | Первым вариантом (рекомендация) |
|---|---|
| новое сказал владелец решения этого слоя | «D-021 заменяет D-009» |
| старое — от владельца, новое — нет | «В вопросы к <владелец>» |
| владелец неизвестен или его нет среди сторон | «В вопросы к <владелец; неизвестен — «кто решает?»>» |

Всегда есть вариант «Остальные K — в открытые вопросы»: вопросы не блокируют запись. Аналитик перестал
отвечать — всё неразобранное уже стоит в файле: статус `спорно` и открытые вопросы.

## Режим 2 — чтение

- **Источник ответа** — досье и документы задачи (артефакты петли). `services/`, `context/` и общие знания —
  нет: «как обычно делают» — не ответ на «что решили».
- **Поиск:** `Grep` по словам вопроса в заголовках и `суть:`; к найденному — цепочка связей (`заменяет`,
  `спорит с`, `отвечает на`). Широкий вопрос («что решено по всему?») — файл целиком.
- **Форма:** короткий ответ первой строкой, ниже — опора с номерами и статусами. В ответе — только
  действующее; заменённое — когда спросили «почему» или «как менялось». Спорное — спором, с обеими
  сторонами; за стороны ответ не выбирается.
- **«В досье этого нет»** — тоже ответ, и с ним одно предложение: «записать открытым вопросом к <кому>?».
  Сама запись — режимом 1.
- **Обязательные виды вопросов:** факт («какой срок отмены?»); кто решает и кто сказал; что открыто и к
  кому; что изменилось с даты или с последней выдачи (раздел «Выдано»); почему решили так (цепочка
  `заменяет` с источниками).

## Режим 3 — проекции

### Общий контракт

1. **Только действующие записи.** Заменённое и снятое не идёт; спорное и условное — только с пометкой.
2. **Каждый элемент — от записи.** В проекциях для людей номер `[D-…]` стоит у каждой строки, стрелки,
   клетки. Во входе БТ и спеки номеров нет: принимающий скилл принял бы их за содержание (решение
   `meeting-intake`, 5.44). Соответствие «пункт ← записи» пишется строкой в «Выдано».
3. **Неподтверждённое видно.** Условное, спорное, допущение, сведение о чужой системе со слов — с
   пометкой, на схеме — пунктиром.
4. **Пробел виден — но не везде одинаково.** В проекции для людей пробел называется: «как поймём — не
   обсуждалось». Во входе БТ — нет (то же правило у `meeting-intake`): «рисков не обсуждали» скилл БТ может
   прочесть как «рисков нет», а такой ответ закрывает гейт.
5. **Пересобирается целиком,** руками не правится. В шапке: «собрано из досье <дата>; правки — в досье».
   Так же устроены схемы `interaction-diagram`.
6. **Досье проекция не правит** — кроме одной строки в «Выдано».
7. **Проверка.** Вход БТ и спеки сверяет субагент с чистым контекстом: каждый пункт — с записями, плюс
   самопроверка Шага 8 `meeting-intake`. Проекции для людей — самопроверка: каждый `[D-…]` существует и
   действует.

### Ключевые проекции

**Вход БТ и спеки (1, 2).** Форма — ровно форма входа `meeting-intake`. Стык с принимающими скиллами
(файл — слова аналитика, `user-stated`) уже замерен пробами `jm-br-*` и `jm-ts-*`, и пайплайн не меняется.
Отличие одно — дельта: если БТ уже есть, во вход идёт только то, чего в нём нет или что с ним расходится
(сверка с документом своего слоя, как поле `документ:` у `meeting-intake`). Перед проекцией — ревизия.
Открытые споры слоя БТ уходят в «Открыто» с тем, кто решает, а перед этим — один вопрос: «K споров уйдут в
открытые вопросы БТ — разобрать сейчас?».

**Вопросы к встрече (3).** Замыкает цикл: вопросы → встреча → `meeting-intake` → импорт разбора → связь
`отвечает на D-…` закрывает вопросы. Порядок — по цене незнания: сначала то, без чего не закрыть гейты БТ,
потом споры, потом остальное.

**Готовность к БТ (4).** Субагент раскладывает действующие записи по 18 гейтам `business-requirements-doc`.
Номера и названия гейтов он берёт из `SKILL.md` скилла БТ, а не из копии: шаблон БТ меняется. Выход — в
чат: что закрыто, что частично, что спросить; отсюда же пополняются вопросы к встрече.

**Карточка фичи (5).** Для заказчика, не для аналитика: зачем (проблема → результат → как поймём); как
сейчас → как будет — два Mermaid `flowchart` или один, где изменения выделены; что входит и не входит;
главные решения; открытое — с тем, кто решает и к какому сроку; риски и зависимости; кто что решает.
Mermaid рисуется в GitLab, GitHub и JetBrains без установки (таблица форматов `interaction-diagram`).
HTML-страница — v3 и по запросу: в закрытом контуре только без внешних библиотек.

**Эскиз взаимодействий (6).** Это не замена `interaction-diagram`: тот рисует по INT-карточкам готовой
спеки, а эскиз — до спеки, чтобы было что обсуждать. Правила те же, что у `interaction-diagram` (TL;DR 3,
Step 2): одно звено — одна стрелка, имена участников буква в букву, служебных стрелок нет. Добавляются
подпись `[D-…] <что>` и пунктир у неподтверждённого. По умолчанию — `flowchart LR` («кто с кем»): порядок
вызовов на дискавери обычно не известен, а `sequenceDiagram` его утверждает. `sequenceDiagram` — только
если порядок записан. В шапке: «эскиз по досье, не по спеке; после спеки — `/interaction-diagram`».

**Свободная проекция.** Цели нет в каталоге — работает общий контракт без рубрики, а в отчёте стоит строка
«рубрики нет — проверь по номерам». Если цель повторяется, она получает рубрику и пробу: каталог растёт по
спросу, а не заранее.

## Устройство скилла

| Файл | Что |
|---|---|
| `discovery-log/SKILL.md` | TL;DR, выбор режима, инварианты, «чего не делаешь никогда»; шагов режимов в нём нет |
| `reference/entry.md` | форма файла и записи, словарь, грани, примеры в чужой предметной области |
| `reference/write.md` | режим 1: входы, шаги, таблица проверок, вопросы |
| `reference/audit.md` | рубрика ревизии для субагента |
| `reference/read.md` | режим 2 |
| `reference/project.md` | общий контракт проекций, каталог, проверка входа |
| `reference/targets/<цель>.md` | рубрика проекции: что берёт, скелет, самопроверка |

**Режим выбирается по смыслу строки вызова:** вопрос («что решили …?», «кто …», «что нового с …») —
чтение; «собери / нарисуй / сделай <что>» — проекция; «ревизия», «проверь досье» — ревизия; остальное —
запись. Не понять — один вопрос с тремя вариантами. В одной сессии режимы чередуются по сообщениям.

Frontmatter: `user-invocable: true`, `disable-model-invocation: true`,
`allowed-tools: AskUserQuestion, Read, Glob, Grep, Write, Edit, Agent`.
Вызов: `/discovery-log <KEY> <текст | путь | вопрос | цель>`.

Под слабую модель прода (DeepSeek-V4-Flash): маршрут — таблицей; файл режима читается целиком до первого
слова аналитику (как стадии `analyst-workspace`); поиск — `Grep` по заголовкам, а не чтение файла целиком;
номер следующей записи — по `Grep "^### D-"`. Импорт большого разбора (40+ записей) может упереться в
лимит вывода — урок 5.48. Правило «порциями не больше 10» там не держалось и было откачено, поэтому размер
порции не предписываем, а меряем пробой `disc-w`.

## Чего скилл не делает никогда

- Не решает споры сам — ни при записи, ни в ответе, ни в проекции.
- Не переписывает записанную `суть` (кроме ошибки записи по слову аналитика).
- Не правит документы задачи и не зовёт под-скиллы.
- Не читает `services/` и `context/`, иначе сведения карточек уедут в досье под видом «сказано» (довод
  `meeting-intake`). Сверка с ними как сигнал «расходится с карточкой» — кандидат в v3, и только сигналом,
  не записью.
- Не кладёт в досье расшифровки и чужие документы целиком.
- Не пишет «не обсуждалось» во входе БТ.

## Проверка

Культура стенда та же: фикстуры и `expected.md` до первого прогона, эталон руками, детерминированный
грейдер с самопроверкой на порченых вариантах, слепое прочтение фикстур свежим субагентом.

**Фикстура `DISC-ROOM`** — дискавери одной фичи за две недели, в предметной области, которой нет ни в
скиллах, ни в других фикстурах. Шесть источников идут по очереди:

| # | Источник | Ловушка |
|---|---|---|
| S-1 | заметки аналитика | решение без цели («нужна выгрузка в Excel»); цели в досье нет |
| S-2 | разбор встречи (`*.razbor.md`) | условное решение не от владельца; открытый вопрос |
| S-3 | письмо второго стейкхолдера | спор людей (срок хранения); тот же факт, что в S-2, → `подтвердил` |
| S-4 | заметка: человек из S-2 передумал | `заменяет` без вопроса; рядом уточнение без спора |
| S-5 | чат с архитектором | грани `обмен`; деталь реализации против решения слоя БТ |
| S-6 | ответ аналитика | закрывает открытый вопрос из S-2 |

Плюс скрытое противоречие между предметами — для ревизии — и термин в двух значениях.

| Проба | Что мерит (красное) |
|---|---|
| `disc-w` | после каждого источника: записи с верными видом и слоем; спор найден и спрошен с обоими номерами; «передумал» — без вопроса; уточнение не помечено спором; ни одна `суть` не переписана; номера не переиспользованы; не больше одного вопроса за ход |
| `disc-audit` | скрытое противоречие названо парой номеров; ложных пар не больше одной |
| `disc-r` | 8 вопросов: в ответе действующее, а не заменённое; спор — спором; «нет в досье» там, где нет; «что нового с даты»; номера в ответе существуют |
| `disc-p-bt` | стык досье → `-bt` → `business-requirements-doc`: заменённого в БТ нет, спор — в открытых вопросах, пробел не закрыл гейт (грейдер — по образцу `grade-junction.mjs`) |
| `disc-p-agenda` | все открытые и спорные — по адресатам; закрытых нет |
| `disc-p-sketch` | у каждой стрелки номер записи с гранью `обмен`; стрелок без записи нет; неподтверждённое — пунктиром |
| `disc-p-card` | у каждой строки номер действующей записи; пробелы названы |

Модели: Sonnet — уровень прода, Haiku — нижняя граница; DeepSeek на стенде не запустить. Объём: пилот —
по прогону на пробу; пул называю числом «N проб × M прогонов ≈ $X» и жду ответа.

## Риски

- **Шум вопросов.** Скилл, который спрашивает на каждую заметку, бросят на второй день. Против — вопрос
  только на спор, расхождение с документом и решение без цели; вариант «остальные — в вопросы»; запись не
  ждёт ответов.
- **Ложные противоречия.** Уточнение, принятое за спор, стоит хода и доверия. Против — таблица «уточняет /
  заменяет / спорит» с признаками; на пробе — счётчик ложных.
- **Пропущенные противоречия.** Локальная проверка видит только свой предмет, и один предмет под двумя
  именами даёт пропуск. Против — предмет подбирается из уже записанных; ревизия перед входом БТ.
- **Рост файла.** У большого эпика — сотни записей. Против — `Grep` по заголовкам вместо чтения целиком,
  ревизия по группам предметов. Заменённое не удаляется (это история), но в проекции не идёт.
- **Расхождение словаря с `meeting-intake`.** Две копии словаря разъедутся. Против — пометка «правится в
  обоих», сверка на `/skill-review`, импорт разбора на пробе.
- **Два писателя.** В двух ветках номера записей совпадут. Против — один писатель на досье; повторившийся
  при слиянии номер чинит человек.
- **Ручные правки.** Аналитик допишет запись руками, без полей. Терпим: для чтения обязателен только
  заголовок; запись без номера ревизия предложит оформить.
- **Эскиз вместо спеки.** Эскиз начнут отдавать в разработку. Против — шапка «эскиз по досье, не по спеке»
  и отсылка к `/interaction-diagram`.
