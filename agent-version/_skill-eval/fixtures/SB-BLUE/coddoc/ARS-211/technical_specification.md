## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В шапке существующей административной панели «Арсенал» (фронт arsenal-web) появляется неяркий счётчик — число активных пользовательских сессий в текущий момент. Фронт обновляет его раз в минуту без перезагрузки страницы; если источник числа недоступен, вместо числа показывается «—», нулевое значение показывается как «0». Счётчик виден только роли «Администратор»; оператор его не видит.
**Тип:** доработка
**Стороны:** Fullstack — фронт arsenal-web добавляет счётчик и опрос; сторона, отдающая число, — существующая, её контракт не подтверждён (INT-1).
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Фронт административной панели «Арсенал» (arsenal-web) | изменение: счётчик в шапке, опрос раз в минуту | команда «Арсенал» (из БТ; эксперт — тимлид «Арсенал-Core») | 🔵 подтверждено аналитиком (со слов: «существующий фронт»; валидировать при интеграции) |
| Источник числа активных сессий | потребляемый существующий источник | не известен | 🟡 к валидации |

### 1.3. Связь с бизнес-требованиями
Реализует цель БТ «видеть текущую активность пользователей, чтобы планировать безопасные окна регламентных работ»; только текущий момент, график (ARS-202) и выгрузка (ARS-203) сюда не входят.

### 3.2. Данные и хранение

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
🟢 Шапка существующей административной панели: добавляется неяркий счётчик активных сессий (пожелание БТ — не отвлекать от работы). Данные — из INT-1.
### 4.2. Пользовательские сценарии
- Администратор открывает панель → в шапке число (FR-1).
- Раз в минуту без перезагрузки страницы число перезапрашивается и обновляется (FR-1).
- Источник недоступен → «—», прежнее значение не остаётся (FR-5).
- Активных нет → «0» (FR-6).
- Оператор открывает панель → счётчика нет (FR-7).
### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос | неяркий индикатор загрузки на месте числа |
| `value` | число > 0 | число |
| `zero` | число = 0 (валидный ноль) | «0» (не «—») |
| ~~`empty`~~ | ~~Не применимо: БТ не вводит состояния «нет данных», недоступность источника — `error_source`~~ | ~~—~~ |
| `error_source` | источник недоступен, таймаут, 5xx, сеть | «—» (не ноль, не старое значение); без отдельного retry-элемента |
| `error_forbidden` | 403 | счётчик не показывается |

### 4.3.1. Loading и таймауты (обязательно, если есть FE)
- **Таймаут cold-path** (первый запрос): 8 с; **warm-path** (повторные): 3 с — по конвенции оформления. 🟢
- **Polling:** 60 с (со слов аналитика: «раз в минуту, чаще не требуется»); jitter не нужен — администраторов десятки. 🟢
- Таймаут, 5xx и сетевая ошибка → `error_source`; следующий опрос идёт по расписанию.
### 4.4. Доступ по ролям в UI
- Администратор — видит счётчик. 🔵 подтверждено аналитиком (со слов; валидировать при интеграции)
- Оператор — панель и счётчик не видит. 🔵 подтверждено аналитиком (со слов; валидировать при интеграции)

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Синхронный опрос с фронта раз в 60 с; таймауты — §4.3.1; кэш на нашей стороне не проектируется. Нагрузка: администраторов десятки (🔵 со слов аналитика), то есть порядка десятков запросов в минуту.
### 5.2. Надёжность/деградация
Источник недоступен → «—» (`error_source`), последнее удачное значение не показывается; каждый следующий опрос пробует снова. Записи на нашей стороне нет.
### 5.3. Безопасность/доступ (сводно)
| Роль | Видит счётчик |
|------|---------------|
| Администратор | да |
| Оператор | нет |
Проверка на стороне источника — 🟡 к валидации.
