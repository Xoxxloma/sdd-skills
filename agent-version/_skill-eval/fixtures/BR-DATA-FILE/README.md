# Фикстура BR-DATA-FILE — состав данных в файле пользователя (регресс прода)

Заведена 2026-10-07 под `business-requirements-doc` 1.2.0 (PLAN-BR-SECTIONS, батч A). Повторяет
полевую жалобу: на вопрос о составе бизнес-данных пользователь отдаёт структурированный файл
(сущности → сведения), а в БТ уезжает только верхний уровень.

## Вход

```
seed/docs/MNT-410/data.md   три объекта (станок, неисправность, заявка на ремонт) и 12 сведений;
                            у каждого сведения — кодовое имя в скобках (`machine.invNo`…)
```

Засев — только `seed/` (`SEED_SUB=seed`). Форма файла — вложенный список; нарочно не таблица и не
разделы по сущностям, чтобы проба не подстраивала скилл под одну форму образца.

## Проба

`br-data-file`: один ход «ПРОДОЛЖЕНИЕ» (`file-prompt.txt`) — аналитик закрывает все гейты 0–17,
про данные: «состав описан в файле docs/MNT-410/data.md — бери оттуда». Грейдер —
`grade-br-data.mjs --case=file`.

## Что должно произойти

БТ пишется этим ходом (`docs/MNT-410/business_requirements.md`). В §4.3 — все 12 сведений файла
бизнес-названиями. Засчитывается смысловая основа, а не фраза файла: «инвентарный номер» в строке
объекта «Станок» — то же, что «Инвентарный номер станка»; форма раздела (таблица, список) не важна. Кодовых имён файла
(`machine.invNo`, `request.urgency`…) нет нигде в БТ: материал пользователя — его слова, но запрет
кодовых имён в БТ действует и на них.

## Критерии (названы до прогонов)

PLAN-BR-SECTIONS §1.0: N = 3; провал → разбор. На 1.1.2 (база) ожидаемо красная: §4.3 нет.
