Напиши техническую спецификацию узла-фундамента #0 эпика PRT-600.

Эпик-БТ — бизнес-контекст: coddoc/PRT-600/business_requirements.md. Узел #0 обслуживает FR-1 (часть PRT-601) и FR-3 (часть PRT-602). Это узел-фундамент #0, своего БТ нет; спеку клади в coddoc/PRT-600/_foundation/technical_specification.md.

Черновая форма ответа, собранная из детских БТ:
{ "partId": string, "partName": string, "shelfQty": int, "minQty": int|null, "stockLevel": "ok"|"low"|"out", "recountedAt": string|null }
- partId, partName — нужны PRT-601 (FR-1) и PRT-602 (FR-3): какая запчасть
- shelfQty — нужен PRT-601 (FR-1) и PRT-602 (FR-3): остаток на складе; 0 — «нет на складе», валидный ноль
- minQty — нужен PRT-602 (FR-3): минимальный остаток; null — минимум не задан
- stockLevel — нужен PRT-601 (FR-1) и PRT-602 (FR-3): отметка «мало» / «нет на складе»
- recountedAt — нужен PRT-601 (FR-1) и PRT-602 (FR-3): дата последнего пересчёта; null — остаток ни разу не пересчитывали

Это ПРОДОЛЖЕНИЕ: ты уже задал вопросы по тех-гейтам, аналитик отвечает.

ТВОЙ ПРОШЛЫЙ ХОД (вопросы по тех-гейтам):
1. Кто отдаёт остатки и кто их вызывает? Предлагаю: новая ручка в бэке сервисного центра, вызывает веб мастеров и кладовщика.
2. Контракт: GET /v1/parts/stock, фильтры partId (повторяемый) и level (low | out, повторяемый); ответ items[] по черновой форме; stockLevel: out — shelfQty = 0; low — 0 < shelfQty < minQty; ok — иначе, в том числе при minQty = null. Так? [Да, так] [Иначе — поправлю]
3. Ошибки: неизвестный level — 400 UNKNOWN_LEVEL; база склада не ответила — 503 STOCK_UNAVAILABLE; неизвестный partId — просто нет в ответе, без ошибки. Так? [Да, так] [Иначе — поправлю]
4. Кто вправе вызывать ручку и где это проверяется?
5. Откуда данные: остаток, минимальный остаток и дата пересчёта уже где-то лежат или их нужно заводить?
6. Кэш, нагрузка, время ответа?
7. Выкат: порядок, флаги, преднастройка?

ОТВЕТЫ АНАЛИТИКА:
- По 1: да. Отдаёт repair-api — бэк сервисного центра, наш, команда «Сервис». Вызывает repair-web — веб мастеров и кладовщика, тоже наш; экраны делаются в частях PRT-601 и PRT-602, не здесь.
- По 2: да, так. Порядок в items — по partName.
- По 3: да, так. Тело ошибки — { "error": код, "message": текст }.
- По 4: роли MASTER и STOREKEEPER, проверяет repair-api; остальным — 403. Роли уже заведены.
- По 5: всё уже лежит в таблице склада repair-api: остаток, минимальный остаток, дата последнего пересчёта — кладовщик ведёт их в разделе «Склад». Новых таблиц и полей не нужно; stockLevel не храним, считаем при ответе.
- По 6: синхронно, без кэша. Около 40 мастеров, до 2 000 открытий заказа-наряда в день; кладовщик открывает список несколько раз в день. Ответ — до 1 секунды.
- По 7: обычным релизом repair-api, раньше частей PRT-601 и PRT-602. Фиче-флага нет, миграций нет, новых настроек нет.
- Сроки и приоритет — как в эпике.
