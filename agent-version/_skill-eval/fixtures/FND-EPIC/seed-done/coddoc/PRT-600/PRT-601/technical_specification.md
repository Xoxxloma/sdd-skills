## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В карточке заказа-наряда у каждой запчасти появляются остаток на складе и отметка «мало», «нет на складе» или «остаток не пересчитан» — по общему контракту остатков узла-фундамента #0. Мастер может отметить запчасть «ждём поставку» с ожидаемой датой и снять отметку; отметку видят все мастера в карточке заказа.
**Тип:** доработка
**Стороны:** Fullstack — `repair-web` показывает остатки и отметки в карточке заказа-наряда; `repair-api` хранит отметки «ждём поставку» и отдаёт их.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `repair-api` | новый вызов (INT-2, INT-3); отдаёт контракт #0 (INT-1) | команда «Сервис» | 🟢 |
| `repair-web` | изменение: карточка заказа-наряда | команда «Сервис» | 🟢 |
### 1.3. Связь с бизнес-требованиями
Мастер видит, есть ли запчасть, не уходя на склад, и отмечает ожидание поставки в самом заказе вместо комментария. Требования — в §7.

## 2. Взаимодействия (ядро)

### INT-1. Остатки запчастей — 🔵 depends-on #0 — унаследовано, не переопределять
- **Вид:** потребление существующего
- **Граница/направление:** FE → BE (`repair-web` → `repair-api`)
- **Триггер:** мастер открывает карточку заказа-наряда; один запрос с `partId` всех запчастей заказа
- **Контракт (запрос):** `GET /v1/parts/stock`; параметры: `partId` — string, повторяемый, необязательный; `level` — enum `low | out`, повторяемый, необязательный. Неизвестный `partId` в ответ не попадает, ошибки нет.
- **Контракт (ответ):** `items[]`, порядок — по `partName`. Элемент: `partId` string; `partName` string; `shelfQty` int, ≥ 0, `0` — валидный ноль; `minQty` int или `null` — `null`: минимум не задан; `stockLevel` enum `ok | low | out` — `out`: `shelfQty = 0`; `low`: `0 < shelfQty < minQty`; `ok`: иначе, в том числе при `minQty = null`; `recountedAt` string (дата-время ISO 8601, UTC) или `null` — `null`: остаток ни разу не пересчитывали.
- **Пример запроса:** `GET /v1/parts/stock?partId=P-1042&partId=P-2210`, тело отсутствует
- **Пример ответа (успех):**
  ```json
  {
    "items": [
      { "partId": "P-1042", "partName": "Ремень привода 6PK", "shelfQty": 2, "minQty": 5, "stockLevel": "low", "recountedAt": "2026-10-20T09:00:00Z" },
      { "partId": "P-2210", "partName": "Термостат ТС-40", "shelfQty": 0, "minQty": 3, "stockLevel": "out", "recountedAt": null }
    ]
  }
  ```
- **Ошибки:** `400 UNKNOWN_LEVEL`; `403`; `503 STOCK_UNAVAILABLE` — как в контракте #0. Тело: `{ "error": "<код>", "message": "<текст>" }`.
- **Состояния UI по ответу:** `stockLevel = ok` → `stock_ok`; `low` → `stock_low`; `out` → `stock_out`; `recountedAt = null` → `stock_not_recounted`; `503` → `stock_unavailable`.
- **Авторизация:** `MASTER` и `STOREKEEPER`; проверяется в `repair-api` (контракт #0).
- **Происхождение:** 🔵 depends-on #0 — унаследовано, не переопределять
- **Трассировка:** FR-1

### INT-2. Отметка «ждём поставку»: поставить и снять — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE (`repair-web` → `repair-api`)
- **Триггер:** мастер ставит или снимает отметку у запчасти заказа
- **Контракт (запрос):** поставить — `PUT /v1/orders/{orderId}/parts/{partId}/awaiting`, тело: `expectedDate` string (дата `YYYY-MM-DD`), обязательное; повторный `PUT` перезаписывает дату. Снять — `DELETE /v1/orders/{orderId}/parts/{partId}/awaiting`, тела нет.
- **Контракт (ответ):** `PUT` → `200`: `orderId` string; `partId` string; `expectedDate` string (`YYYY-MM-DD`); `markedBy` string — логин мастера; `markedAt` string (дата-время ISO 8601, UTC). `DELETE` → `204`, тела нет; отметки не было — тоже `204`.
- **Пример запроса:**
  ```json
  { "expectedDate": "2026-11-12" }
  ```
- **Пример ответа (успех):**
  ```json
  { "orderId": "WO-5512", "partId": "P-2210", "expectedDate": "2026-11-12", "markedBy": "petrov", "markedAt": "2026-10-26T08:15:00Z" }
  ```
- **Ошибки:** `400 EXPECTED_DATE_IN_PAST` — дата раньше сегодняшней; `404 ORDER_PART_NOT_FOUND` — запчасти нет в заказе; `403` — роль не `MASTER`. См. «Каталог ошибок».
- **Состояния UI по ответу:** `200` → `awaiting_set`; `204` → `awaiting_none`; `400` → сообщение у поля даты; `404` → «запчасти нет в заказе», карточка перечитывается; `403` → `error_forbidden`.
- **Авторизация:** только `MASTER`; проверяется в `repair-api`; `STOREKEEPER` и иные роли — `403`.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-2

### INT-3. Отметки «ждём поставку» заказа — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE (`repair-web` → `repair-api`)
- **Триггер:** мастер открывает карточку заказа-наряда
- **Контракт (запрос):** `GET /v1/orders/{orderId}/awaiting`, параметров нет.
- **Контракт (ответ):** `items[]`, элемент — как ответ `PUT` в INT-2: `orderId`, `partId`, `expectedDate`, `markedBy`, `markedAt`. Отметок нет — `items: []`, не `null`.
- **Пример запроса:** `GET /v1/orders/WO-5512/awaiting`, тело отсутствует
- **Пример ответа (успех):**
  ```json
  { "items": [ { "orderId": "WO-5512", "partId": "P-2210", "expectedDate": "2026-11-12", "markedBy": "petrov", "markedAt": "2026-10-26T08:15:00Z" } ] }
  ```
- **Ошибки:** `404 ORDER_NOT_FOUND` — заказа нет; `403` — роль не `MASTER` и не `STOREKEEPER`.
- **Состояния UI по ответу:** отметка есть → `awaiting_set` («ждём поставку к 12 ноября»); `items: []` → `awaiting_none`.
- **Авторизация:** `MASTER` и `STOREKEEPER`; проверяется в `repair-api`.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-2

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 | `EXPECTED_DATE_IN_PAST` — «Дата поставки уже прошла» | `PUT` INT-2 с датой раньше сегодняшней | сообщение у поля даты |
| 404 | `ORDER_PART_NOT_FOUND` — «Запчасти нет в заказе» | INT-2 по запчасти не из заказа | «запчасти нет в заказе», карточка перечитывается |
| 404 | `ORDER_NOT_FOUND` — «Заказ не найден» | INT-3 по несуществующему заказу | карточка не открывается, «заказ не найден» |
| 403 | — | роль без права на ручку | `error_forbidden` |
| 503 | `STOCK_UNAVAILABLE` — «Остатки склада недоступны» | INT-1: база склада не ответила | `stock_unavailable` |

## 3. Backend — ответственность
### 3.1. По сервисам
- `repair-api` (🟢): реализует INT-2 и INT-3 — хранит отметку «ждём поставку» по паре заказ — запчасть, проверяет дату и наличие запчасти в заказе; логин мастера для `markedBy` берётся из контекста пользователя, не из запроса.
- `repair-api` отдаёт INT-1 по контракту #0; он реализуется в узле-фундаменте и здесь не меняется.
### 3.2. Данные и хранение
- [🟢] `AwaitingMark` — новая сущность `repair-api`: `orderId` string, `partId` string, `expectedDate` date, `markedBy` string, `markedAt` datetime UTC. Одна отметка на пару (`orderId`, `partId`): повторный `PUT` перезаписывает дату, `DELETE` удаляет строку. Индекс по `orderId` — под INT-3.

Миграция: да — новая таблица; точный DDL финализирует `repair-api`. Изменённых таблиц нет, уже лежащих строк это не касается. Остатки — данные узла #0, здесь не меняются.
### 3.3. Авторизация/доступ на бэке
`repair-api`: INT-2 — только `MASTER`; INT-3 — `MASTER` и `STOREKEEPER`; иные роли — `403`. Роли уже заведены.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Карточка заказа-наряда в `repair-web`: у каждой запчасти — остаток и отметка уровня (INT-1), отметка «ждём поставку» с датой и кнопки «Ждём поставку» / «Снять» (INT-2, INT-3).
### 4.2. Пользовательские сценарии
- Мастер открывает заказ-наряд → видит у каждой запчасти остаток и отметку «мало» / «нет на складе» / «остаток не пересчитан» (FR-1).
- Мастер нажимает «Ждём поставку», выбирает дату → у запчасти «ждём поставку к <дата>» для всех мастеров; «Снять» убирает отметку (FR-2).
- Остатки недоступны → «остатки недоступны», отметки «ждём поставку» показываются как обычно.
### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `stock_loading` | запрос INT-1 в пути | скелетон на месте остатка |
| `stock_ok` | `stockLevel = ok` | остаток числом, без отметки |
| `stock_low` | `stockLevel = low` | остаток числом и «мало» |
| `stock_out` | `stockLevel = out` (`shelfQty = 0`, валидный ноль) | «нет на складе» |
| `stock_not_recounted` | `recountedAt = null` | рядом с остатком «остаток не пересчитан» |
| `stock_unavailable` | `503` / таймаут / сеть по INT-1 | «остатки недоступны» |
| `awaiting_set` | у запчасти есть отметка | «ждём поставку к <дата>» и кнопка «Снять» |
| `awaiting_none` | отметки нет | кнопка «Ждём поставку» (только `MASTER`) |
| `error_forbidden` | `403` | «нет доступа» |
### 4.3.1. Loading и таймауты (обязательно, если есть FE)
- **Таймаут cold-path** (первое открытие карточки) — 5 с, **warm-path** (повторный запрос) — 3 с; по таймауту — `stock_unavailable`.
- ~~Polling: Не применимо: опроса нет, данные читаются при открытии карточки.~~
- Таймаут / 5xx / сеть по INT-1 → `stock_unavailable`; по INT-2 → сообщение «не удалось сохранить отметку», кнопка доступна для повтора.
### 4.4. Доступ по ролям в UI
`MASTER` видит остатки и отметки, ставит и снимает отметку; `STOREKEEPER` видит остатки и отметки, кнопок отметки нет.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Синхронно, без кэша. Остатки — один запрос INT-1 на открытие карточки по всем запчастям заказа; отметки — один запрос INT-3. Нагрузка: около 40 мастеров, до 2 000 открытий заказа-наряда в день.
### 5.2. Надёжность/деградация
INT-1 не ответил → `stock_unavailable`, остальная карточка работает. INT-2 не прошёл → отметка не сохранена, мастер видит сообщение и повторяет; частично записанного не бывает — одна строка.
### 5.3. Безопасность/доступ (сводно)
| Граница | Кто вправе |
|---------|------------|
| INT-1 | `MASTER`, `STOREKEEPER` (контракт #0) |
| INT-2 | `MASTER` |
| INT-3 | `MASTER`, `STOREKEEPER` |
