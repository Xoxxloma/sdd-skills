## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. `booking-api` начинает отдавать сводку занятости комнат, `floorplan-web` показывает её
на плане этажа.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `booking-api` | новый эндпоинт сводки | Рабочие места | 🟢 |
| `floorplan-web` | потребитель | Фронт | 🟢 |
| `calendar` | источник броней | Корпоративный календарь | 🔵 подтв. аналитиком |

### 1.3. Связь с бизнес-требованиями

## 2. Взаимодействия (ядро)

### INT-1. Сводка занятости комнат для плана этажа — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** открытие плана этажа, далее опрос раз в минуту
- **Контракт (запрос):** `GET /v1/rooms/occupancy`, параметр `floor: int` обязателен
- **Контракт (ответ):** `asOf: iso8601` — момент, на который снята сводка;
  `rooms: массив`, элемент — `roomId: string`, `state: free|busy`,
  `busyUntil: iso8601|null` — `null` всегда при `state = free`, у занятой комнаты заполнено
- **Пример ответа (успех):**
  ```json
  {
    "asOf": "2026-08-05T12:03:00Z",
    "rooms": [
      { "roomId": "7-01", "state": "busy", "busyUntil": "2026-08-05T15:30:00Z" },
      { "roomId": "7-02", "state": "free", "busyUntil": null }
    ]
  }
  ```
- **Ошибки:** `400` — этаж не передан или не число; `503` — календарь недоступен
- **Авторизация:** любой аутентифицированный сотрудник, отдельной роли не требуется
- **Происхождение:** 🟢
- **Трассировка:** FR-1, FR-2

### INT-2. Чтение броней из корпоративного календаря — 🔵
- **Граница/направление:** Сервис `booking-api` → Сервис `calendar`
- **Триггер:** сборка сводки занятости
- **Контракт (запрос):** `GET /api/v2/calendar/events`, параметры `resourceIds`, `from`, `to`
- **Контракт (ответ):** массив событий с полями `resourceId`, `start`, `end`
- **Ошибки:** обрабатываются как недоступность источника
- **Авторизация:** сервисный токен `booking-api`, выдан командой календаря
- **Происхождение:** 🔵 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Трассировка:** FR-1

### Каталог ошибок (сводно)

| Код | Когда | Что видит пользователь |
|-----|-------|------------------------|
| `400` | этаж не передан | план не строится, показывается сообщение об ошибке |
| `503` | календарь недоступен | план строится, признаки занятости не показываются |

## 3. Backend — ответственность

### 3.1. По сервисам
`booking-api` собирает сводку занятости по этажу, обращаясь к календарю за бронями на текущий
момент, и отдаёт её плану этажа.

### 3.2. Данные и хранение
Новая сущность `RoomOccupancySnapshot` — снимок занятости этажа на момент времени: `floor: int`,
`asOf: timestamp`, `rooms: jsonb`. Хранится не дольше пяти минут, служит кэшем между опросами.
Происхождение: 🟢

### 3.3. Авторизация/доступ на бэке
Эндпоинт сводки доступен любому аутентифицированному сотруднику. К календарю `booking-api` ходит
сервисным токеном, пользовательский контекст не передаётся.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
План этажа (`/floorplan/:floor`): у каждой комнаты появляется цветовой признак и подпись.

### 4.2. Пользовательские сценарии
Сотрудник открывает план этажа, видит свободные и занятые комнаты, у занятой читает время
освобождения.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос сводки | комнаты серые, подписи нет |
| `ready` | сводка получена | цветовой признак и время у занятых |
| `stale` | `asOf` старше пяти минут | признак показан приглушённо, подпись «данные устарели» |
| `source_down` | ответ `503` | признаков нет, подпись «занятость недоступна» |

### 4.3.1. Loading и таймауты
Скелетон плана показывается сразу; сводка догружается отдельно и не блокирует отрисовку комнат.
Таймаут запроса сводки — 3 секунды, по истечении переходим в `source_down`.

### 4.4. Доступ по ролям в UI
Не применимо: признак виден всем аутентифицированным сотрудникам, ролевого ветвления нет.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
Запрос синхронный. Сводка кэшируется на бэке пять минут, фронт опрашивает раз в минуту.

### 5.2. Надёжность/деградация
Календарь недоступен — план этажа продолжает работать без признаков занятости. Отсутствие данных
и «все комнаты свободны» показываются по-разному: это разные состояния, `source_down` и `ready`.

### 5.3. Безопасность/доступ (сводно)
Сервисный токен к календарю хранится в секретах `booking-api` и в ответах не появляется.

## 6. Релиз и интеграция

### 6.1. Порядок выката
Сначала `booking-api` с новым эндпоинтом, затем `floorplan-web`.

### 6.2. Обратная совместимость
Существующие эндпоинты плана этажа не меняются, ничего не удаляется.

### 6.3. Фиче-флаги
Флаг `floorplan.occupancy` на фронте, по умолчанию выключен, включается после проверки на этаже 7.

### 6.4. План отката
Выключить флаг `floorplan.occupancy` — план возвращается к прежнему виду. Эндпоинт сводки при
этом можно оставить: потребителей у него больше нет.

### 6.5. Преднастройка до релиза
- Сервисный токен `booking-api` в календаре — запросить у команды календаря.
- Соответствие `roomId` плана этажа и идентификаторов ресурсов календаря — выгрузить и сверить.

## 7. Трассировка приёмки

| FR | Как проверяется |
|----|-----------------|
| FR-1 | Комната с бронью на текущий момент приходит в сводке как `busy`; на плане у неё признак «занята сейчас» |
| FR-2 | У комнаты со `state = busy` поле `busyUntil` заполнено; на плане видно время освобождения |
