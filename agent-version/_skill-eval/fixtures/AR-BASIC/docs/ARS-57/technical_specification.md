# Техническая спецификация: показ IP последней сессии

> **Статус готовности:** Готово к разработке
> **Задача:** ARS-57
>
> 🟢 — спроектировано в этой спеке.
> 🔵 подтверждено аналитиком — существующее, аналитик подтвердил.
> 🟡 к валидации — существующее, не подтверждено.
> ❓ — открытое архитектурное решение.

## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. Счётчик сессий начинает отдавать IP последней активности, фронт показывает его в плашке.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `auth` | изменение существующего эндпоинта | Платформа | 🔵 подтв. аналитиком |
| `incident-web` | потребитель | Фронт | 🟢 |
| `geo` | обогащение IP до города | Гео | 🟡 к валидации |

### 1.3. Связь с бизнес-требованиями
Аналитик безопасности должен видеть, откуда заходили под учёткой, не открывая журнал аудита.

## 2. Взаимодействия (ядро)

### INT-1. Счётчик сессий отдаёт IP последней активности — 🔵
- **Граница/направление:** FE → BE
- **Триггер:** открытие любого экрана, плашка в шапке
- **Контракт (запрос):** `GET /v1/sessions/count`, параметров нет
- **Контракт (ответ):** `count: int`; `updatedAt: iso8601|null`; **новое поле** `lastIp: string|null` —
  `null`, если активности не было ни разу; для отозванных сессий IP не отдаётся
- **Пример ответа (успех):**
  ```json
  { "count": 3, "updatedAt": "2026-07-27T10:00:00Z", "lastIp": "10.24.5.7" }
  ```
- **Ошибки:** без изменений
- **Авторизация:** свой счётчик — любой авторизованный; чужой — только `security_analyst`
- **Происхождение:** 🔵 подтверждено аналитиком
- **Трассировка:** FR-1

### INT-2. Обогащение IP до города — ❓
- **Граница/направление:** Сервис auth → Сервис geo
- **Контракт (запрос):** не определён
- **Происхождение:** ❓ — не решено, делать ли обогащение на бэке или на фронте
- **Трассировка:** FR-2

## 2.5. Этапы работ и порядок сборки

| # | Этап | Вход (шов) | Выход (шов) | Проверка в одиночку |
|---|------|-----------|-------------|---------------------|
| 01 | расширение ответа счётчика полем последнего IP | хранилище сессий `auth` | INT-1 | сессия с известным IP → в ответе `lastIp`; сессия без IP → `null` |
| 02 | показ IP в списке сессий админки | INT-1 | — | на моке INT-1: значение, `null` → «—», ошибка |

> **Разработка: 01–02 параллельно** — шов INT-1 зафиксирован в §2. **Выкат: 01 → 02.**
> Владельцы: 01 — команда `auth`, 02 — команда `incident-web`.

## 3. Backend — ответственность

### 3.1. По сервисам
`auth` реализует расширение ответа `GET /v1/sessions/count` полем `lastIp`.

### 3.2. Данные и хранение
Сущность `Session` получает поле `last_ip: inet|null` — IP последней активности по сессии.
Заполняется при каждом продлении. Миграция нужна, поле nullable, дефолта нет.
Происхождение: 🔵 подтверждено аналитиком.

### 3.3. Авторизация/доступ на бэке
Без изменений: чужой счётчик доступен роли `security_analyst`.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Плашка активных сессий в шапке (`/incidents`, `/incidents/:id`) дополняется строкой «последний
вход с <IP>». Новых экранов нет.

### 4.2. Пользовательские сценарии
Аналитик открывает список инцидентов, видит в шапке число сессий и IP последнего входа.

### 4.3. Состояния

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос | скелетон плашки |
| `empty` | `lastIp = null` | «входов не было» |
| `error_source` | `updatedAt = null` | «данные недоступны» |

### 4.4. Доступ по ролям в UI
Чужой счётчик виден только роли `security_analyst`.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
Запрос синхронный, кэш на фронте 60 секунд.

## 6. Релиз и интеграция

### 6.1. Порядок выката
Сначала `auth` с миграцией, затем фронт.

### 6.2. Обратная совместимость
Поле `lastIp` добавляется, ничего не удаляется. Легаси-эндпоинт `GET /v1/session` объявляется
устаревшим и будет удалён в следующем квартале.
