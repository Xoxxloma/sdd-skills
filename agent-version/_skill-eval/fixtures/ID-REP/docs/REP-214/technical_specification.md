## 1. Обзор изменения

### 1.1. Что делаем и тип изменения

**Суть:** Заказчик ремонта сможет оплатить этап работ онлайн прямо из своего кабинета в repairy: выбирает этап, сумма подставляется из акта приёмки, оплата проходит на платёжной странице ЮKassa. После успешной оплаты платёж сам появляется в ленте проекта (сейчас его вносит сотрудник руками), чек сохраняется в документы проекта, прораб и владелец компании получают уведомление в Telegram. Сотрудник компании может оформить возврат.

**Тип:** новый функционал

**Стороны:** Fullstack — новый контракт между кабинетом заказчика и repairy-api, новая интеграция repairy-api с платёжным провайдером.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `repairy-web` | Фронт: кабинет заказчика — кнопка «Оплатить этап», статус оплаты; кабинет сотрудника — возврат | Команда repairy | 🟢 |
| `repairy-api` | Бэк: создаёт платёж у провайдера, принимает уведомления, фиксирует `ProjectPayment` | Команда repairy | 🟢 |
| ЮKassa | Внешний платёжный провайдер: платёжная страница, уведомления о статусе | Внешний (договор компании) | 🔵 подтв. аналитиком |
| S3-хранилище | Хранение чеков (бакет документов проекта) | Команда repairy (инфраструктура) | 🔵 подтв. аналитиком |
| Telegram-бот (`apps/telegram`) | Уведомление прорабу и владельцу об оплате | Команда repairy | 🟡 к валидации |

### 1.3. Связь с бизнес-требованиями

Реализует цель БТ «сократить разрыв между приёмкой работ и оплатой»: заказчик платит сразу после приёмки, без перевода по реквизитам и без ручного ввода платежа сотрудником (FR-1…FR-6).

### INT-1. Создание онлайн-платежа за этап — 🟢
- **Граница/направление:** `repairy-web` (кабинет заказчика) → `repairy-api`
- **Триггер:** заказчик нажимает «Оплатить этап» на принятом акте приёмки
- **Контракт (запрос):** `POST /projects/:pid/payments/online`; тело: `acceptanceId` (string, uuid, обяз.), `returnUrl` (string, обяз.)
- **Контракт (ответ):** `paymentId` (string, uuid), `status` (enum: `pending`), `amount` (number, рубли, 2 знака), `confirmationUrl` (string — адрес платёжной страницы провайдера)
- **Пример запроса:**
  ```json
  { "acceptanceId": "5b0c1f9e-7a41-4c1e-9d2a-0f3e6b1c2d44", "returnUrl": "https://app.repairy.ru/p/1842/payments" }
  ```
- **Пример ответа (успех):**
  ```json
  { "paymentId": "d1f0a8c2-33b4-4f7e-b1a0-9e2c5d7f8a10", "status": "pending", "amount": 184500.00, "confirmationUrl": "https://yoomoney.ru/checkout/payments/v2/contract?orderId=2c9f..." }
  ```
- **Ошибки:** `404` акт не найден; `409` акт уже оплачен или по нему есть платёж в статусе `pending`; `422` акт не принят заказчиком; `502` провайдер не ответил (см. каталог)
- **Состояния UI по ответу:** значение → переход на `confirmationUrl`; загрузка → кнопка в состоянии `creating`; ошибка `409` → «По этому этапу уже есть платёж», ссылка на статус; `502` → «Платёжный сервис недоступен, попробуйте позже»
- **Авторизация:** только заказчик этого проекта (`ProjectCustomer` с `acceptedAt`); сотрудник и владелец — `403`
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2

### INT-2. Регистрация платежа у провайдера — 🔵
- **Граница/направление:** `repairy-api` → ЮKassa
- **Триггер:** обработка INT-1, синхронно
- **Контракт (запрос):** `POST /v3/payments` — `amount.value`, `amount.currency` (`RUB`), `confirmation.type` (`redirect`), `confirmation.return_url`, `capture` (`true`), `metadata.paymentId`; заголовок `Idempotence-Key` = `paymentId`
- **Контракт (ответ):** `id` (id платежа у провайдера), `status` (`pending`), `confirmation.confirmation_url`
- **Пример запроса:**
  ```json
  { "amount": { "value": "184500.00", "currency": "RUB" }, "capture": true, "confirmation": { "type": "redirect", "return_url": "https://app.repairy.ru/p/1842/payments" }, "metadata": { "paymentId": "d1f0a8c2-33b4-4f7e-b1a0-9e2c5d7f8a10" } }
  ```
- **Пример ответа (успех):**
  ```json
  { "id": "2c9f1a7e-000f-5000-8000-1b2c3d4e5f60", "status": "pending", "confirmation": { "type": "redirect", "confirmation_url": "https://yoomoney.ru/checkout/payments/v2/contract?orderId=2c9f..." } }
  ```
- **Ошибки:** `4xx` провайдера → `502` наружу с логом тела; таймаут 10 с → `502`
- **Авторизация:** Basic-auth `shopId:secretKey` из конфига компании
- **Происхождение:** 🔵 подтверждено аналитиком (по договору и документации провайдера; валидировать при интеграции)
- **Трассировка:** FR-2

### INT-3. Оплата на платёжной странице — 🔵
- **Граница/направление:** Браузер заказчика ↔ ЮKassa (платёжная страница)
- **Триггер:** переход по `confirmationUrl` из INT-1
- **Контракт (запрос):** переход по `confirmation_url`; оплата картой или СБП целиком на стороне провайдера; по завершении провайдер возвращает браузер на `return_url`
- **Контракт (ответ):** не применимо — страница провайдера
- **Пример запроса:** тело отсутствует, браузерный переход
- **Пример ответа (успех):** редирект на `return_url`
- **Ошибки:** отказ банка показывает сама страница провайдера; repairy о нём узнаёт только из INT-4
- **Состояния UI по ответу:** после возврата на `return_url` кабинет показывает `awaiting_confirmation` и опрашивает INT-7
- **Авторизация:** не применимо — сторона провайдера
- **Происхождение:** 🔵 подтверждено аналитиком
- **Трассировка:** FR-2

### INT-4. Уведомление о статусе платежа — 🟢
- **Граница/направление:** `repairy-api` ← ЮKassa (HTTP-уведомление)
- **Триггер:** платёж у провайдера перешёл в `succeeded` или `canceled`; возврат — в `refund.succeeded`
- **Контракт (запрос):** `POST /webhooks/yookassa`; тело: `event` (enum: `payment.succeeded`, `payment.canceled`, `refund.succeeded`), `object.id`, `object.status`, `object.metadata.paymentId`
- **Контракт (ответ):** `200` без тела; любой другой код — провайдер повторяет уведомление
- **Пример запроса:**
  ```json
  { "type": "notification", "event": "payment.succeeded", "object": { "id": "2c9f1a7e-000f-5000-8000-1b2c3d4e5f60", "status": "succeeded", "amount": { "value": "184500.00", "currency": "RUB" }, "metadata": { "paymentId": "d1f0a8c2-33b4-4f7e-b1a0-9e2c5d7f8a10" } } }
  ```
- **Пример ответа (успех):** `200`, тело отсутствует
- **Ошибки:** неизвестный `paymentId` → `200` и запись в лог (не провоцировать повтор); повтор того же события → `200`, без повторной фиксации (идемпотентность по `object.id` + `event`)
- **Авторизация:** запрос принимается только с IP-адресов провайдера из списка в конфиге; статус перепроверяется запросом `GET /v3/payments/{id}` к провайдеру перед фиксацией
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3, FR-4

### INT-5. Сохранение чека в документы проекта — 🔵
- **Граница/направление:** `repairy-api` → S3-хранилище
- **Триггер:** обработка `payment.succeeded` в INT-4
- **Контракт (запрос):** PutObject в бакет документов, ключ `projects/{pid}/receipts/{paymentId}.pdf`, `Content-Type: application/pdf`
- **Контракт (ответ):** ETag объекта
- **Пример запроса:** тело — PDF чека, сформированный repairy-api
- **Пример ответа (успех):** `ETag: "9b2cf535f27731c974343645a3985328"`
- **Ошибки:** недоступность хранилища → платёж фиксируется, чек ставится в повтор (3 попытки, интервал 1 мин); после трёх неудач — алерт
- **Авторизация:** сервисный ключ repairy-api к бакету
- **Происхождение:** 🔵 подтверждено аналитиком (тот же бакет и SDK, что у документов проекта)
- **Трассировка:** FR-4

### INT-6. Уведомление об оплате в Telegram — 🟡
- **Граница/направление:** событие: `repairy-api` → `repairy-telegram` (через очередь BullMQ в Redis)
- **Триггер:** платёж зафиксирован (INT-4, `payment.succeeded`)
- **Контракт (событие):** `payment.succeeded` — `projectId`, `paymentId`, `amount`, `customerName`
- **Потребители:** Telegram-бот — сообщение прорабу проекта и владельцу компании, если у них канал уведомлений `TELEGRAM`
- **Пример запроса:**
  ```json
  { "projectId": 1842, "paymentId": "d1f0a8c2-33b4-4f7e-b1a0-9e2c5d7f8a10", "amount": 184500.00, "customerName": "Анна Кравец" }
  ```
- **Пример ответа (успех):** не применимо — событие
- **Ошибки:** бот недоступен — событие остаётся в очереди, повтор средствами очереди
- **Авторизация:** не применимо — внутренняя очередь
- **Происхождение:** 🟡 к валидации — механизм доставки событий боту не подтверждён
- **Трассировка:** FR-5

### INT-7. Статус онлайн-платежа — 🟢
- **Граница/направление:** `repairy-web` → `repairy-api`
- **Триггер:** возврат заказчика с платёжной страницы; далее опрос до финального статуса
- **Контракт (запрос):** `GET /projects/:pid/payments/online/:paymentId`
- **Контракт (ответ):** `paymentId`, `status` (enum: `pending`, `succeeded`, `canceled`, `refunded`), `amount`, `paidAt` (string, ISO-8601, `null` пока не оплачен), `receiptUrl` (string, `null` пока чек не сохранён)
- **Пример запроса:** тело отсутствует
- **Пример ответа (успех):**
  ```json
  { "paymentId": "d1f0a8c2-33b4-4f7e-b1a0-9e2c5d7f8a10", "status": "succeeded", "amount": 184500.00, "paidAt": "2026-09-29T11:42:05Z", "receiptUrl": "/projects/1842/documents/771" }
  ```
- **Ошибки:** `404` платёж не найден или чужой проект
- **Состояния UI по ответу:** `pending` → `awaiting_confirmation`; `succeeded` → `paid`; `canceled` → `failed`; `refunded` → `refunded`; сеть/5xx → `error_source`
- **Авторизация:** заказчик проекта, прораб проекта, владелец компании
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

## 3. Backend — ответственность

### 3.1. По сервисам
- **repairy-api** — реализует INT-1, INT-4, INT-7 и эндпоинт возврата (🟢); вызывает INT-2, INT-8 у провайдера, INT-5 в хранилище; публикует событие INT-6. Фиксация платежа по `payment.succeeded` создаёт `ProjectPayment` с `source = ONLINE` в одной транзакции со сменой статуса `OnlinePayment` (🟢).
- **Telegram-бот** — потребляет событие INT-6 и шлёт сообщение по существующему шаблону уведомлений (🟡 к валидации).

### 3.2. Данные и хранение
- 🟢 `OnlinePayment` — `id` (uuid), `projectId`, `acceptanceId`, `providerPaymentId` (unique), `amount` (decimal), `status` (enum `pending|succeeded|canceled|refunded`), `paidAt`, `receiptDocumentId`, `createdAt`
- 🟢 `ProjectPayment` — новое поле `source` (enum `MANUAL|ONLINE`, по умолчанию `MANUAL`) и `onlinePaymentId` (nullable, unique)
- 🟢 `ProviderNotification` — `providerObjectId` + `event` (уникальный индекс) для идемпотентности INT-4
- Миграции: да — две новые таблицы, два поля в `ProjectPayment`; DDL финализирует repairy-api.

### 3.3. Авторизация/доступ на бэке
Создание платежа — только `ProjectCustomer` проекта; статус — заказчик, прораб, владелец; возврат — только `OWNER`. Вебхук — список IP провайдера плюс перепроверка статуса запросом к провайдеру.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
- Кабинет заказчика, вкладка «Приёмка»: у принятого акта кнопка «Оплатить этап» (INT-1), после возврата с платёжной страницы — блок статуса (INT-7).
- Лента проекта: платёж с пометкой «онлайн» и ссылкой на чек.
- Кабинет владельца, вкладка «Платежи»: кнопка «Вернуть» у онлайн-платежа.

### 4.2. Пользовательские сценарии
1. Заказчик принял акт → «Оплатить этап» → платёжная страница → возврат → «Ожидаем подтверждение» → «Оплачено», платёж в ленте (FR-1…FR-4).
2. Заказчик закрыл платёжную страницу без оплаты → через 30 минут статус `canceled`, кнопка «Оплатить» снова доступна.
3. Владелец оформляет возврат → статус `refunded`, платёж в ленте помечен «возвращён» (FR-6).

### 4.3. Состояния

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `creating` | запрос INT-1 в полёте | кнопка со спиннером |
| `awaiting_confirmation` | INT-7 вернул `pending` | «Ожидаем подтверждение оплаты» |
| `paid` | INT-7 вернул `succeeded` | «Оплачено», сумма, ссылка на чек (если `receiptUrl` ≠ null) |
| `failed` | INT-7 вернул `canceled` | «Оплата не прошла», кнопка «Оплатить снова» |
| `refunded` | INT-7 вернул `refunded` | «Платёж возвращён» |
| `error_source` | 5xx / таймаут / сеть | «Не удалось получить статус», повтор |
| `error_forbidden` | 403 | «Нет доступа» |

### 4.3.1. Loading и таймауты
- Таймаут INT-1 — 15 с (внутри синхронный вызов провайдера); INT-7 — 5 с.
- Опрос INT-7: каждые 3 с с jitter ±500 мс, не дольше 2 минут; дальше — кнопка «Обновить».

### 4.4. Доступ по ролям в UI
«Оплатить этап» видит только заказчик; «Вернуть» — только владелец; статус платежа видят заказчик, прораб и владелец.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
INT-1 синхронный, включает INT-2 (таймаут 10 с). INT-4 и INT-5 асинхронны относительно заказчика. Кэша нет. Ожидаемая нагрузка — до 200 платежей в сутки.

### 5.2. Надёжность/деградация
Провайдер недоступен → INT-1 отдаёт `502`, кнопка остаётся активной. Уведомление не пришло → ночная сверка `pending` старше 1 часа запросом статуса у провайдера. Хранилище недоступно → платёж фиксируется без чека, чек догружается повтором.

### 5.3. Безопасность/доступ (сводно)
Секреты провайдера — в конфиге компании, не в репозитории. Вебхук без IP из списка → `403`. Сумма берётся только из акта на бэке, с фронта не принимается.

## 6. Релиз и интеграция

### 6.1. Порядок выката
repairy-api (миграции, вебхук) → настройка адреса уведомлений в кабинете провайдера → repairy-web.

### 6.2. Обратная совместимость
`ProjectPayment.source` по умолчанию `MANUAL` — существующие платежи и ручной ввод не меняются.

### 6.3. Фиче-флаги
`online_payments` на уровне компании; проверяется в repairy-api (INT-1) и repairy-web (кнопка). Включает владелец платформы по заявке компании.

### 6.4. План отката
- **Откат только BE:** кнопка скрыта флагом; уже созданные `OnlinePayment` остаются в БД.
- **Откат только FE:** бэк продолжает принимать уведомления; ручной ввод платежей работает.
- **Откат DDL:** новые таблицы можно удалить без потери существующих данных; поле `source` — только после выгрузки онлайн-платежей.

### 6.5. Преднастройка до релиза

- [x] DDL-миграция в репо repairy-api

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано принятый акт, когда заказчик жмёт «Оплатить этап», тогда создаётся платёж `pending` и открывается страница провайдера |
| FR-2 | INT-2, INT-3 | Дано платёж `pending`, когда заказчик оплачивает картой, тогда браузер возвращается на `return_url` |
| FR-3 | INT-4, INT-7 | Дано уведомление `payment.succeeded`, когда оно пришло дважды, тогда платёж зафиксирован один раз |
| FR-4 | INT-5 | Дано успешную оплату, когда хранилище доступно, тогда чек появляется в документах проекта |
| FR-5 | INT-6 | Дано прораба с каналом `TELEGRAM`, когда платёж зафиксирован, тогда он получает сообщение |
| FR-6 | INT-8 | Дано оплаченный онлайн-платёж, когда владелец жмёт «Вернуть», тогда статус `refunded` |
