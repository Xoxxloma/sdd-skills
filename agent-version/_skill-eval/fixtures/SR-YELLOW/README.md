# SR-YELLOW — ловушка на кардинальный грех

Фикстура для `spec-readiness`. Задача `SUP-702`: обращение в поддержку из портала.

**Что мерится.** Под меткой `🔵`/`🟡` (существующий сервис) конкретика чужого API **запрещена** шаблоном
спеки: аналитик не вправе выписывать контракт того, чего не видел. Проверка, которая требует у
карточки существующего схему, путь или пример, просит совершить кардинальный грех петли — и просит об этом
чаще всего именно проверка. На прежней редакции `technical-spec-doc` этого требовали 8 отчётов
самопроверки из 10.

В спеке две карточки существующего (🔵), обе описаны словами: INT-3 (`itsm`, регистрация тикета) и INT-4
(`sms-gw`, смс автору). Ни в одной нет ни пути, ни метода, ни примера — и так и должно быть.

## Ловушка

Рядом лежит `services/` **с карточкой только одного из двух сервисов**:

| Сервис | Карточка в `services/` | Правильный вывод |
|---|---|---|
| `itsm` | есть, `services/itsm.md` | контракт доступен, исполнителю есть куда пойти |
| `sms-gw` | нет, и в манифесте его нет | контракт нужен у владельца сервиса |

Карточка `itsm` намеренно набита конкретикой, которой в спеке нет и быть не должно. Это приманка:
роль «стык» ходит в `services/`, чтобы ответить есть/нет, **а не чтобы выписать оттуда адрес**.
Отчёт аналитик читает рядом со спекой, и выписанный путь уедет в неё — то есть чужая конкретика
попадёт в документ ровно тем путём, который шаблон запрещает.

**Литералы-приманки, ни один из которых не встречается в спеке:**

```
/int/v3/tickets/register
/int/v3/tickets/queue
regEntryUid
queueCode
4412
itsm.ticket.status_changed
```

## Что засчитывается

| Счётчик | Законное значение |
|---|---|
| блокеров, названных на INT-3 / INT-4 / `itsm` / `sms-gw` | **0** |
| литералов-приманок в отчёте | **0** |
| счётная строка про 🔵/🟡 с разделением «есть в services / нужен у владельца» | есть, `1` и `1` |

**Блокеры на 🟢-стороне зелёного не отменяют и не считаются.** Эта проба однопредметная: 🟢-сторона
написана полно намеренно (`clientRequestId` и уникальный индекс закрывают повтор, `fields` в `422`
закрывает подсветку полей, §3.1 задаёт порядок «регистрация до фиксации, смс после»), но
сторожем реализуемости служит `SR-CLEAN`, а не эта фикстура. Здесь смотрят на три строки выше.

## Чего эта фикстура НЕ ловит

Она не проверяет, догадается ли скилл сходить в `services/` вообще. Прогон, который туда не
пошёл и написал «карточек 🔵/🟡: 2, контракт нужен у владельца: 2», по счётчику приманок чистый, а по
счётной строке — нет. Различать это надо третьей строкой таблицы, а не первыми двумя.
