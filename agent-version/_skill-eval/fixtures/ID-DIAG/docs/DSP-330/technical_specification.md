## 1. Обзор изменения

### 1.1. Что делаем и тип изменения

**Суть:** В пульт диспетчера добавляется заявка на выезд группы быстрого реагирования — отдельная сущность, которая фиксирует момент создания, объект, выбранную группу и причину выезда. Адрес, режим охраны и ответственное лицо подставляются из справочника объектов. Диспетчер видит заявки своей смены, старший смены — все заявки смены. Группа получает push на планшет с адресом и причиной в момент создания заявки; ответственный по объекту получает SMS о выезде.

**Тип:** доработка

**Стороны:** Fullstack (новый контракт между фронтом и бэком для создания и просмотра заявок)

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `dispatch-web` | Фронт: диспетчер создаёт и смотрит заявки | Команда пульта | 🔵 подтв. аналитиком |
| `dispatch-api` | Бэк: хранит заявки, публикует события | Команда пульта | 🔵 подтв. аналитиком |
| `objects-registry` | Справочник: адрес, режим, ответственное лицо объекта | Команда справочников | 🔵 подтв. аналитиком |
| `notify` | Оповещение группе (push) и ответственному (SMS) | Команда уведомлений | 🔵 подтв. аналитиком |

### 1.3. Связь с бизнес-требованиями

Заявка на выезд реализует три требования БТ: фиксирует время реакции на тревогу (FR-1, FR-2, FR-3), доводит адрес и причину до группы без искажений (FR-2, FR-3), оповещает ответственного по объекту автоматически (FR-4), ограничивает доступ по ролям (FR-5).

## 2. Взаимодействия (ядро)

### INT-1. Создание заявки на выезд — 🟢

- **Граница/направление:** `dispatch-web` → `dispatch-api`
- **Триггер:** Диспетчер нажимает кнопку «Создать заявку» в пульте, выбрав объект, группу и причину выезда
- **Контракт (запрос):** `POST /v1/dispatch-requests`
  - `objectId` (string, обязательно) — ID охраняемого объекта
  - `crewId` (string, обязательно) — ID группы быстрого реагирования
  - `reason` (enum, обязательно) — причина выезда: `alarm` | `call` | `scheduled`
- **Контракт (ответ):** Заявка (объект `DispatchRequest`)
  - `id` (string) — уникальный идентификатор заявки
  - `objectId` (string) — ID объекта
  - `crewId` (string) — ID группы
  - `reason` (enum) — причина выезда
  - `createdAt` (iso8601) — время создания заявки (по часам сервера)
  - `createdBy` (string) — имя или ID диспетчера, создавшего заявку
  - `status` (enum) — статус заявки: `created` | `notified` | `failed`; в момент создания = `created`
- **Пример запроса:**
  ```json
  {
    "objectId": "obj-42",
    "crewId": "crew-7",
    "reason": "alarm"
  }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "id": "dispatch-req-1001",
    "objectId": "obj-42",
    "crewId": "crew-7",
    "reason": "alarm",
    "createdAt": "2026-09-24T14:35:12Z",
    "createdBy": "dmitry",
    "status": "created"
  }
  ```
- **Ошибки:** 
  - `400` — `crewId` или `objectId` не переданы или невалидны; `reason` не из списка
  - `404` — объект не найден в справочнике (dispatch-api проверил в objects-registry)
  - `409` — группа не существует или не на смене (проверка в dispatch-api по Crew из справочника)
  - `422` — данные объекта не получены из справочника (сервис недоступен)
- **Состояния UI по ответу (если есть фронт):**
  - значение → форма закрывается, заявка появляется в списке
  - загрузка → кнопка в состоянии "обработка" + спиннер
  - ошибка (404, 409, 422) → диалог ошибки с текстом (например, «Справочник объектов недоступен, подождите и повторите»)
  - ошибка (400) → валидация формы (сообщение под полем)
- **Авторизация:** Только пользователи с ролью `dispatcher` могут вызвать; проверка на уровне dispatch-api (как POST /v1/incidents)
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2, FR-3

### INT-2. Получение данных объекта при создании заявки — 🔵

- **Граница/направление:** `dispatch-api` → `objects-registry` (синхронный запрос, часть обработки INT-1)
- **Триggер:** Часть обработки INT-1: dispatch-api получил запрос создать заявку и должен получить адрес, режим охраны, ответственное лицо
- **Контракт (запрос):** `GET /v2/objects/{id}` (существующий эндпоинт objects-registry)
- **Контракт (ответ):** Карточка объекта (GuardedObject) с полями: `address`, `guardMode`, `responsible` (вложенно `{ name, phone }`)
- **Ошибки:** 
  - `404` — объект не найден или договор расторгнут → dispatch-api вернёт `404` клиенту (INT-1)
  - `5xx` / таймаут → dispatch-api вернёт `422` клиенту
- **Авторизация:** dispatch-api авторизуется как сервис (не от пользователя)
- **Происхождение:** 🔵 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Трассировка:** FR-2 (подстановка данных объекта)

### INT-3. Событие «заявка создана» — 🔵

- **Граница/направление:** событие: `dispatch-api` → `notify` (через шину Kafka)
- **Триggер:** Заявка успешно создана и сохранена в dispatch-api (синхронно, внутри транзакции INT-1)
- **Контракт (событие):** `dispatch-request.created`
  - `dispatchRequestId` (string) — ID заявки
  - `objectId` (string) — ID объекта
  - `crewId` (string) — ID группы
  - `reason` (string) — причина выезда
  - `createdAt` (iso8601) — время создания заявки
  - Ключ партиции — `objectId` (как у `incident.created`)
  - Событие публикуется после коммита транзакции; при ретрае возможен дубль
- **Потребители:** `notify` слушает событие в группе `notify-dispatch-requests` и отправляет push на планшет группе
- **Происхождение:** 🔵 подтверждено аналитиком (как существующий механизм с инцидентами)
- **Трассировка:** FR-3 (оповещение группы)

### INT-4. Push на планшет группе — 🔵

- **Граница/направление:** событие: `notify` → планшет группы (через push-шлюз)
- **Триggер:** notify получил событие `dispatch-request.created` (INT-3)
- **Контракт:** По событию notify формирует и отправляет push:
  - Адрес объекта (получает из objects-registry по `objectId`, как на инциденте)
  - Причина выезда из события
  - Время создания заявки
  - Push идёт на планшет группы (по `crewId` → `tabletId` из справочника Crew в dispatch-api)
- **Авторизация:** Группа получает push по своему `tabletId`, нет дополнительной проверки прав
- **Происхождение:** 🔵 подтверждено аналитиком (механизм как с инцидентами)
- **Трассировка:** FR-3

### INT-5. SMS ответственному по объекту — 🟡

- **Граница/направление:** `dispatch-api` → `notify` (синхронный запрос по HTTP)
- **Триggер:** Заявка успешно создана; dispatch-api отправляет SMS ответственному
- **Контракт (запрос):** По схеме notify: `POST /v1/notify`
  - `channel` = `sms`
  - `recipient` = телефон из `responsible.phone` (полученный из objects-registry в INT-2)
  - `text` = сообщение вида «На объект [адрес] выехала группа [позывной]. Время: [время заявки].»
- **Контракт (ответ):** Доставка (объект `Delivery`), как в notify
  - `id`, `status`, `sentAt` и т.д.
- **Ошибки:** 
  - `422` — получатель (телефон) не соответствует каналу `sms` (некорректный формат) → dispatch-api логирует и продолжает (не блокирует создание заявки)
  - `5xx` — notify недоступен → dispatch-api логирует и продолжает
- **Авторизация:** dispatch-api авторизуется как сервис с ролью `sender` (если требуется)
- **Происхождение:** 🟡 к валидации — умеет ли notify отправлять SMS по HTTP-запросу и какой точно контракт
- **Трассировка:** FR-4 (SMS ответственному)

### INT-6. Список заявок для диспетчера/старшего — 🟢

- **Граница/направление:** `dispatch-web` → `dispatch-api`
- **Триggер:** Диспетчер или старший смены открывает раздел заявок на выезд в пульте
- **Контракт (запрос):** `GET /v1/dispatch-requests`
  - Параметры (опциональны):
    - `status` — фильтр по статусу (`created` | `notified` | `failed`); без фильтра — все статусы
    - `limit` — количество записей; по умолчанию 50
    - `offset` — смещение для пагинации; по умолчанию 0
- **Контракт (ответ):** Список заявок
  - `items` (array) — массив заявок (структура как в INT-1 ответ)
  - `total` (int) — всего записей в БД (без фильтра limit/offset)
- **Пример ответа:**
  ```json
  {
    "items": [
      {
        "id": "dispatch-req-1001",
        "objectId": "obj-42",
        "crewId": "crew-7",
        "reason": "alarm",
        "createdAt": "2026-09-24T14:35:12Z",
        "createdBy": "dmitry",
        "status": "notified"
      }
    ],
    "total": 42
  }
  ```
- **Ошибки:** `500` — внутренняя ошибка БД
- **Состояния UI по ответу:**
  - значение → таблица заявок, отсортирована по `createdAt` убывающей (новые сверху)
  - загрузка → спиннер / скелетон списка
  - пусто (total = 0) → текст «Нет заявок»
  - ошибка (5xx) → плашка ошибки + кнопка retry
- **Авторизация:** Диспетчер видит только свои заявки (фильтр по `createdBy = текущий пользователь`); старший смены видит все (фильтр не применяется). Оператор колл-центра не видит раздел вообще (проверка роли на фронте + 403 на бэке).
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-5

### Каталог ошибок

| Код | Тело/сообщение | Когда | Состояние UI | Действие |
|-----|----------------|-------|--------------|----------|
| `400` | `{error: "crewId is required"}` или `{error: "reason not in [alarm, call, scheduled]"}` | Клиент не передал обязательное поле или передал невалидное значение | Валидация формы, сообщение под полем | Пользователь исправляет и повторяет |
| `404` | `{error: "object not found"}` | Объект не найден в справочнике (статус договора = расторгнут) | Диалог ошибки: «Объект не найден или договор расторгнут» | Пользователь повторяет выбор объекта |
| `409` | `{error: "crew not on shift"}` | Группа не существует, не на смене или табличка не определена | Диалог ошибки: «Группа не доступна, выберите другую» | Пользователь выбирает другую группу |
| `422` | `{error: "failed to fetch object data"}` | Справочник объектов недоступен (сервис не ответил или таймаут) | Диалог ошибки: «Данные объекта недоступны, попробуйте позже» | Пользователь повторяет запрос |
| `500` | `{error: "internal server error"}` | Внутренняя ошибка dispatch-api | Диалог ошибки: «Ошибка сервера, попробуйте позже» | Пользователь повторяет запрос |

## 3. Backend — ответственность

### 3.1. По сервисам

**dispatch-api:**
- Реализует INT-1 (создание заявки): валидирует входные данные, получает карточку объекта из INT-2, создаёт и сохраняет заявку в БД
- Публикует событие INT-3 (dispatch-request.created) после коммита
- Отправляет SMS в INT-5 (асинхронно или синхронно после создания заявки — решает разработка; синхронность описана в §5)
- Реализует INT-6 (список заявок): фильтрует по текущему пользователю (диспетчер) или возвращает все (старший смены); проверяет роль `dispatcher` / `shift_lead`
- **Зависит от:** objects-registry (GET /v2/objects/{id}), notify (POST /v1/notify для SMS)
- **Владеет сущностью:** DispatchRequest (новая таблица)

**objects-registry:**
- Предоставляет INT-2 (GET /v2/objects/{id}) — уже есть, dispatch-api его уже вызывает
- Никаких изменений

**notify:**
- Потребляет событие INT-3 (dispatch-request.created) и отправляет INT-4 (push на планшет) — как с инцидентами, изменений нет
- Предоставляет HTTP-эндпоинт POST /v1/notify для INT-5 (SMS) — может быть уже есть, нужно подтвердить

### 3.2. Данные и хранение

- 🟢 `DispatchRequest` — новая сущность у dispatch-api
  - `id` (string, PK) — уникальный идентификатор заявки (например, `dispatch-req-<timestamp>-<random>`)
  - `objectId` (string, FK) — ссылка на объект в справочнике; constraint NOT NULL
  - `crewId` (string) — ID группы; constraint NOT NULL
  - `reason` (enum: alarm|call|scheduled) — причина выезда; constraint NOT NULL
  - `status` (enum: created|notified|failed) — статус заявки (created = только что создана, notified = группа оповещена, failed = ошибка при оповещении); по умолчанию `created`
  - `createdAt` (iso8601) — время создания заявки (по часам dispatch-api); constraint NOT NULL
  - `createdBy` (string) — имя/ID диспетчера; constraint NOT NULL
  - `notifiedAt` (iso8601, nullable) — время, когда группа оповещена (заполняется после INT-4)
  - **Индексы:**
    - PRIMARY KEY (id)
    - INDEX (createdAt DESC) — для сортировки списка по новизне
    - INDEX (createdBy) — для фильтра диспетчера (INT-6)
    - INDEX (objectId) — для связи с объектом и шлюза к notify
  - **TTL/retention:** Заявки хранятся бессрочно (как инциденты); архивирование решает разработка
  - **Миграции:** Потребуется CREATE TABLE с полями выше; точный DDL и синтаксис финализирует dispatch-api

- Никаких новых сущностей в objects-registry или notify

### 3.3. Авторизация/доступ на бэке

- **INT-1 (создание заявки):** Только `dispatcher` может вызвать; проверка на уровне dispatch-api (как для POST /v1/incidents)
- **INT-6 (список заявок):** 
  - `dispatcher` видит только свои заявки (по `createdBy = текущий пользователь`)
  - `shift_lead` видит все заявки смены
  - `call_center_operator` получает `403 Forbidden`
- **INT-2 и INT-4:** Запросы dispatch-api и notify к другим сервисам выполняются от имени сервиса (не конкретного пользователя)
- **Негативные случаи:** Попытка доступа без роли `dispatcher` / `shift_lead` → `403 Forbidden`

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

- **Пульт диспетчера (dispatch-web):** 
  - Новый раздел / вкладка «Заявки на выезд» в основной навигации пульта
  - **Форма создания заявки:**
    - Поле выбора объекта (select / autocomplete, как для инцидентов)
    - Поле выбора группы (select, список групп смены)
    - Поле выбора причины (radio / select: «Сработка сигнализации» / «Звонок клиента» / «Проверка по графику»)
    - Кнопка «Создать заявку»
  - **Таблица заявок:**
    - Колонки: ID заявки, объект, группа, причина, время создания, диспетчер, статус оповещения
    - Сортировка по времени создания (новые сверху)
    - Пагинация 50 элементов на странице
- **Взаимодействия:** INT-1 (создание), INT-6 (список)

### 4.2. Пользовательские сценарии

**Основной поток (Happy path):**
- Диспетчер открывает раздел «Заявки на выезд»
- Видит список заявок своей смены (пустой, если это первая заявка)
- Нажимает «Создать заявку»
- Выбирает объект (например, «Магазин на ул. Ленина, д. 5»)
- Выбирает группу из списка доступных групп смены (например, «Группа 7»)
- Выбирает причину (например, «Сработка сигнализации»)
- Нажимает «Создать»
- Форма отправляет запрос на сервер (INT-1)
- Сервер проверяет данные, получает карточку объекта, создаёт заявку, публикует событие
- Фронт получает ответ с ID заявки и новым статусом `created`
- Форма закрывается, таблица обновляется, новая заявка появляется в списке с временем создания

**Ветвления:**
- **Справочник объектов недоступен:** Сервер вернёт `422`, фронт показывает диалог ошибки с кнопкой retry → диспетчер повторяет
- **Группа не на смене:** Сервер вернёт `409`, фронт показывает диалог → диспетчер выбирает другую группу
- **Валидация формы:** Если диспетчер забыл выбрать объект или группу → фронт показывает валидацию под полем (не отправляет запрос)
- **Сетевая ошибка / таймаут:** Фронт показывает диалог ошибки с кнопкой retry

**Старший смены:**
- Открывает раздел «Заявки на выезд»
- Видит все заявки смены (всех диспетчеров, включая свои)
- Может открыть одну заявку для просмотра, но не может редактировать

**Оператор колл-центра:**
- Не видит раздел «Заявки на выезд» (скрыт в UI)
- Если пытается обратиться к эндпоинту напрямую (например, через DevTools) → получит `403 Forbidden`

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос при открытии формы или список | спиннер, скелетон таблицы |
| `value` | 2xx при получении списка, список не пуст | таблица заявок |
| `empty` | 2xx при получении списка, но `total = 0` | текст «Нет заявок» |
| `success_created` | 2xx при создании заявки | форма закрывается, плашка «Заявка создана» (временная), таблица обновляется |
| `error_validation` | 400 (валидация) | сообщение под полем формы, фокус на поле |
| `error_not_found` | 404 (объект не найден) | диалог ошибки: «Объект не найден или договор расторгнут» |
| `error_crew_unavailable` | 409 (группа не на смене) | диалог ошибки: «Группа не доступна, выберите другую» |
| `error_objects_registry` | 422 (справочник недоступен) | диалог ошибки: «Данные объекта недоступны, попробуйте позже» |
| `error_server` | 5xx | диалог ошибки: «Ошибка сервера, попробуйте позже» + кнопка retry |
| `error_network` | таймаут / сетевая ошибка | диалог ошибки: «Проблемы с сетью, попробуйте позже» + кнопка retry |

### 4.3.1. Loading и таймауты

- **Таймаут cold-path (первый запрос списка при открытии раздела):** 5 секунд (как для инцидентов); после таймаута — сообщение об ошибке + retry
- **Таймаут warm-path (повторная загрузка или создание заявки):** 3 секунды (операция быстрая)
- **Polling:** Не применимо (заявки не обновляются автоматически; обновление вручную по кнопке или при создании новой)

### 4.4. Доступ по ролям в UI

- **`dispatcher`:** Видит форму создания заявки и таблицу со своими заявками (фильтр `createdBy = текущий пользователь` применяется на фронте и на бэке)
- **`shift_lead`:** Видит форму создания заявки и таблицу со всеми заявками смены (фильтр не применяется)
- **`call_center_operator`:** Раздел «Заявки на выезд» не отображается в навигации; если попытается открить напрямую — получит ошибку 403 на бэке

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **INT-1 (создание заявки):** Синхронный запрос. dispatch-api синхронно получает карточку объекта из objects-registry (INT-2), создаёт заявку в БД, коммитит транзакцию. Событие dispatch-request.created публикуется **после** коммита (не внутри), чтобы избежать потери события при краше.
- **INT-5 (SMS):** Может быть отправлено синхронно (внутри INT-1 после коммита) или асинхронно (фоновая задача, прочитавшая событие INT-3). Разработка выбирает; рекомендуется асинхронно, чтобы таймаут notify не блокировал создание заявки для пользователя.
- **INT-6 (список заявок):** Синхронный запрос из БД dispatch-api; без кэша (данные свежие).
- **Кэш:** Не применяется; заявки берутся свежие из БД.
- **Нагрузка:** 
  - Обычно: десятки заявок в сутки
  - Пик (грозы): до сотни заявок за час
  - Индексы по `createdAt` и `createdBy` обеспечивают быстрый поиск и сортировку при пике
- **Таймауты:** Как описано в §4.3.1 (cold-path 5s, warm-path 3s)

### 5.2. Надёжность/деградация

- **Если objects-registry недоступен при создании заявки (INT-2):** dispatch-api возвращает `422`; пользователь видит сообщение об ошибке и может повторить. Заявка не создаётся.
- **Если notify недоступен при отправке SMS (INT-5):** 
  - Если SMS отправляется синхронно: dispatch-api логирует ошибку, но заявка всё равно создаётся (SMS не критична для бизнеса). Статус заявки ставится `created` (не `failed`).
  - Если SMS отправляется асинхронно: notify повторяет доставку (как для других SMS), и если не получилось после трёх попыток — логирует и оставляет статус доставки `failed`.
- **Если notify недоступен при отправке push (INT-4):** notify повторяет доставку (встроенный механизм retryFailed). Группа может получить push с задержкой.

### 5.3. Безопасность/доступ (сводно)

| Операция | Роль | Может/нет | Где enforced |
|----------|------|-----------|-------------|
| Создать заявку | `dispatcher` | Да | dispatch-api (INT-1) |
| Создать заявку | `shift_lead` | Да | dispatch-api (INT-1) |
| Создать заявку | `call_center_operator` | Нет | dispatch-api + dispatch-web (UI скрыт) |
| Видеть свои заявки | `dispatcher` | Да, только свои | dispatch-api (INT-6, фильтр `createdBy`) |
| Видеть все заявки смены | `shift_lead` | Да | dispatch-api (INT-6, без фильтра) |
| Видеть заявки | `call_center_operator` | Нет | dispatch-api (403) + dispatch-web (UI скрыт) |

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **dispatch-api (BE):** Развёртывается первым. Новая таблица DispatchRequest, новые эндпоинты (POST /v1/dispatch-requests, GET /v1/dispatch-requests, событие dispatch-request.created), обновлённая интеграция с objects-registry и notify.
2. **dispatch-web (FE):** После успешного выката BE. Новый раздел в навигации, форма и таблица заявок.

**Обоснование:** FE полагается на BE-контракты (INT-1, INT-6); если FE разворачивается раньше — будет ошибка.

### 6.2. Обратная совместимость

- **BE → FE:** dispatch-api вводит новые эндпоинты, не меняет существующие (incidents, assignments). Старые потребители (old dispatch-web, другие клиенты) не затронуты.
- **notify:** notify не меняется; только потребляет новое событие `dispatch-request.created`. Старые потребители (события incident.created) продолжают работать.
- **objects-registry:** Не меняется; dispatch-api вызывает существующий эндпоинт GET /v2/objects/{id}.

**Вывод:** Обратная совместимость не нарушается.

### 6.3. Фиче-флаги

**Релизим атомарно** — новый раздел либо полностью включен, либо отключен. Если требуется постепенный выкат:
- Флаг `dispatch_requests_enabled` (boolean) на уровне dispatch-api и dispatch-web
- dispatch-api возвращает `404` (эндпоинты не существуют) если флаг выключен
- dispatch-web скрывает раздел «Заявки на выезд» в навигации если флаг выключен
- Флаг включается для всех пользователей одновременно (нет ролевого или постепенного rollout, достаточно просто включить)

### 6.4. План отката

- **Откат только BE:** FE на старой версии, не знает про новый эндпоинт. Нет проблемы — старый функционал (инциденты) продолжает работать. Если старая FE попытается открить раздел заявок (если фиче-флаг был на старой тоже) — получит 404 или 403, старая FE этот раздел не показывает.
- **Откат только FE:** BE отдаёт новые эндпоинты, FE их не вызывает (скрывает раздел, у пользователя нет возможности создать заявку). Заявки в БД остаются, но недоступны для пользователя.
- **Откат DDL:** 
  - **Down-миграция:** Удаление таблицы DispatchRequest. Данные теряются безвозвратно.
  - **Безопасность:** Таблицу создавать в плановое обслуживание, когда пульт не работает, чтобы не потерять данные. Откатываться только по согласованию.

### 6.5. Преднастройка до релиза (чек-лист)

- [ ] **Роли в security-сервисе:** Роли `dispatcher` и `shift_lead` уже есть (используются для инцидентов); проверить, добавлены ли пользователи. Новых ролей не требуется.
- [ ] **DDL-миграция в репо dispatch-api:** Создание таблицы DispatchRequest с индексами (файл миграции в формате проекта, например, Flyway или Migrate); готово на момент выката.
- [ ] **Конфиги по окружениям:** Если есть feature flag `dispatch_requests_enabled` — добавить в конфиги dev/staging/prod; по умолчанию `true` (включен).
- [ ] **Сервисные аккаунты:** dispatch-api уже авторизуется в objects-registry и notify (как для инцидентов); новых аккаунтов не требуется.
- [ ] **Фиче-флаги (если используются):** Заведены `dispatch_requests_enabled` в системе управления флагами (если есть); можно быстро включить/отключить.
- [ ] **Алерты/мониторинг:** 
  - Алерт на ошибки при создании заявки (статус `4xx`, `5xx`)
  - Алерт на таймауты при обращении к objects-registry
  - Алерт на таймауты при обращении к notify для SMS
  - Метрики: количество созданных заявок в час, среднее время создания, процент ошибок

## 7. Трассировка приёмки

| FR-2. Данные объекта подставляются | INT-2 | Дано: заявка создана; когда открыть карточку заявки; тогда адрес, режим охраны, ответственное лицо совпадают со справочником; поля не редактируются. |

| FR-5. Ограничение доступа — диспетчер | INT-6 | Дано: пользователь с ролью диспетчер; когда открывает список заявок; тогда видит только заявки, созданные им; не видит заявки других диспетчеров. |
| FR-5. Ограничение доступа — старший смены | INT-6 | Дано: пользователь с ролью старший смены; когда открывает список заявок; тогда видит все заявки смены. |
| FR-5. Ограничение доступа — оператор колл-центра | INT-1, INT-6 | Дано: пользователь с ролью оператор колл-центра; когда открывает пульт; тогда раздел «Заявки на выезд» не видит; если пытается вызвать эндпоинт напрямую, получает 403. |

## 8. Допущения и открытые вопросы

**🔵 Подтверждено аналитиком (не по коду):**
- Новая сущность заявка хранится в dispatch-api, отдельного хранилища не заводим
- Группа выбирается из списка групп смены (существующее поле в dispatch-api)
- Данные объекта (адрес, режим, ответственное лицо) приходят из objects-registry, диспетчер не вводит их руками
- Оповещение группе — через существующий механизм событий (как с инцидентами): dispatch-api публикует событие, notify слушает и шлёт push
- Доступ: диспетчер создаёт и видит только свои заявки; старший смены видит все заявки смены; оператор колл-центра не видит
- Нагрузка: десятки заявок в сутки, при грозе до сотни за час
- Приоритет и сроки остаются как в БТ

**🟡 К валидации:**
1. **SMS ответственному (INT-5):** Сервис уведомлений поддерживает отправку SMS по HTTP-запросу `POST /v1/notify` с каналом `sms`? Какой точный формат телефона ожидается (международный формат или локальный)? → уточнить с командой notify

**Унаследовано из БТ (бизнес-пробелы):**
- Закрытие заявки и отчёт группы по итогам выезда — отдельная задача (не входит в эту спеку)
- Статистика времени реакции за период — отдельная задача
