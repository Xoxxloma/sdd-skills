# Фикстура SM-ASYNC — асинхронная половина сервиса

**Дерево на диске, а не текст.** Копируется в песочницу прогона; сама фикстура — только на чтение.
Деревом она лежит намеренно: жалоба, ради которой заведена, — про факты, которых **не видно в файле,
объявляющем ключ**. Имя топика стоит в конфиге, поля тела — в DTO, гарантии — в продюсере, группа
и число ретраев — снова в конфиге, расписание задачи — в третьем месте. В текстовой фикстуре всё это
лежит в одном блобе, и проба меряет не то.

**Зачем заведена.** С поля пришло: `service-map` расписывает REST и не расписывает брокер и
шедулеры — учитывает их в статистике и не разворачивает. `SM-BULK` и `SM-NEUTRAL` этого не ловят:
топики там есть, но **фактов второго уровня у них нет** (в описи стоит только «когда»), а фоновая
задача названа прозой, без имени и расписания, то есть ключа не даёт вовсе. Проба на таком
материале зеленеет при любой версии скилла.

**Стек и домен выбраны непересекающимися** с примерами в скилле (`auth`, Go/chi) и с `SM-NEUTRAL`
(логистика, Kotlin/Spring/RabbitMQ): энергосбыт, Node/NestJS, Kafka, Postgres. Совпадение имени или
числа с карточкой — признак копирования, а не чтения.

## Раскладка

```
tree/services/manifest.yaml     спек-репа: два сервиса, карточек нет ни одной
neighbours/metering-api/        backend: 8 эндпоинтов, 5 топиков, 3 задачи, 3 сущности, 3 роли
neighbours/billing-worker/      backend: 2 эндпоинта, 3 топика, задач нет, сущностей нет, ролей нет
```

**`billing-worker` нужен ради пустых форм, а не ради связей.** Зеркала асинхронных рёбер в скилл не
внесены (правка откачена 2026-08-12), и потребители событий в слепке не видны — по этому поводу проб
здесь нет. Второй сервис остаётся потому, что у него **нет ни одной фоновой задачи**: он проверяет,
что новая секция выходит пустой формой, а не исчезает и не подменяется фразой «задач нет».

## Якоря фактов — один якорь = один факт, счёт однозначный

**Топики `metering-api` (11).** Каждый лежит НЕ в том файле, где объявлен ключ:

| # | Факт | Где лежит |
|---|---|---|
| T1 | тело `accepted`: `accountId`, `value`, `takenAt`, `source` | `messaging/dto/events.ts` |
| T2 | ключ партиции `accountId`; порядок гарантирован в пределах счёта, между счетами нет | `reading.producer.ts` + `config/app.yaml` |
| T3 | `accepted` шлётся после коммита, отдельным шагом → при ретрае дубль | `reading.producer.ts` |
| T4 | `reason` у `rejected`: `out_of_range` \| `duplicate` \| `meter_sealed` | `dto/events.ts` |
| T5 | отклонённое показание в базу не пишется, пары в `accepted` не будет никогда | `reading.producer.ts` |
| T6 | `account.closed` шлётся один раз: повторное закрытие даёт `409` и события не даёт | `account.producer.ts`, `accounts.service.ts` |
| T7 | группа консьюмера `metering-billing` | `config/app.yaml` |
| T8 | offset коммитится вручную ПОСЛЕ записи в базу | `invoice.consumer.ts` |
| T9 | повтор безопасен: upsert по `invoiceId` | `invoice.consumer.ts`, `accounts.service.ts` |

## Ловушки

**`syncMeterCatalog` — задача без расписания, и это не повод её потерять.** Ключ есть: тело лежит
здесь. Два неверных исхода симметричны — выбросить задачу из инвентаря или выдумать ей cron.

**`/healthz` и `/api/version` — служебные, но из контракта не выпадают.** Восемь блоков, а не шесть.

**`billing-worker` — три пустых секции подряд.** Задач, сущностей и ролей у него нет; это пустая
форма, а не отсутствие секции и не фраза «задач нет».

**Заражение примером из скилла.** В карточках не должно быть `auth.session.revoked`, `user.blocked`,
`expireSessions`, `purgeAudit`, `/v1/sessions`, `AuditEntry` — это имена из `card.template.md`.
Появление любого = модель дописала пример вместо чтения кода.
