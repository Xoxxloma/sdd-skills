## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** Карта покрытия `/coverage` в incident-web сегодня берёт изохроны у geo по API v1, а команда гео выводит v1 из работы. incident-web переходит на API geo v2; что аналитик видит на карте, не меняется.
**Тип:** мелкая правка
**Стороны:** FE-only — incident-web меняет вызов к чужому сервису geo; бэкенд не меняется.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| incident-web | переходит на API geo v2 на карте покрытия | команда инцидентов | 🟢 изменение; владелец 🔵 подтв. аналитиком (со слов) |
| geo | потребление: изохроны по API v2 | команда гео | 🟡 к валидации (контракт v2), владелец 🔵 подтв. аналитиком (со слов) |
### 1.3. Связь с бизнес-требованиями
Карта покрытия продолжает строить изохроны после отключения API geo v1. Требование: FR-1 из `coddoc/ARS-343/change_request.md` (см. §7).

## 2. Взаимодействия (ядро)

### INT-1. Изохроны для карты покрытия по API geo v2 — 🟡
- **Вид:** потребление существующего
- **Граница/направление:** FE → чужой сервис (incident-web → geo)
- **Триггер:** построение изохроны на экране `/coverage`
- **Контракт (запрос):** 🟡 к валидации — `GET /v2/isochrone`, параметры `lat: number`, `lon: number`, `minutes: int`.
- **Контракт (ответ):** 🟡 к валидации — GeoJSON-полигон; пустой полигон — точка вне обслуживаемой зоны.
- **Пример ответа (успех):** 🟡 к валидации
  ```json
  { "type": "Polygon", "coordinates": [[[37.61, 55.75], [37.65, 55.76], [37.63, 55.73], [37.61, 55.75]]] }
  ```

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Экран карты покрытия `/coverage` в incident-web: изохроны запрашиваются по API geo v2 (INT-1) вместо v1. Внешний вид карты, выбор времени в пути и подписи не меняются.

Аналитик безопасности строит изохрону от точки внутри зоны — видит тот же полигон, что на v1 (FR-1); от точки вне зоны — карта показывает «вне зоны», как сейчас.
