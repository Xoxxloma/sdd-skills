## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** Сегодня в списке инцидентов на `/incidents` даты закрытия нет, и дежурный открывает каждый инцидент, чтобы её увидеть. incident-api добавляет в каждый инцидент ответа списка дату и время закрытия (у открытого — `null`), incident-web показывает её колонкой «Закрыт».
**Тип:** мелкая правка
**Стороны:** Fullstack — изменяется ответ существующей ручки списка инцидентов (incident-api) и таблица списка (incident-web).
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| incident-api | изменение: отдаёт дату закрытия в списке инцидентов | команда инцидентов | 🟢 изменение; владелец 🔵 подтв. аналитиком (со слов) |
| incident-web | потребитель списка: колонка «Закрыт» | команда инцидентов | 🟢 изменение; владелец 🔵 подтв. аналитиком (со слов) |
### 1.3. Связь с бизнес-требованиями
Дежурный отбирает закрытые за смену инциденты прямо в списке, не открывая каждый. Требования: FR-1, FR-2 из `coddoc/ARS-321/change_request.md` (см. §7).

## 2. Взаимодействия (ядро)

### INT-1. Список инцидентов: дата закрытия — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** FE → BE (incident-web → incident-api)
- **Триггер:** открытие экрана `/incidents`
- **Существующий стык:** `GET /api/v2/duty/incident-list` (incident-api) — 🔵 подтверждено аналитиком (по документу сверху; валидировать при интеграции). Прежние поля ответа в источнике не названы и здесь не приводятся.
- **Изменение:**

| поле | где | было | стало |
|------|-----|------|-------|
| `closedAt` | каждый инцидент в ответе списка | — | добавлено: строка, дата и время закрытия в ISO 8601; `null`, если инцидент открыт; поле присутствует всегда |

- **Контракт (запрос):** без изменений.
- **Контракт (ответ):** в каждый инцидент добавляется `closedAt` — `string | null`. Строка — дата и время закрытия, которые уже хранятся у инцидента. `null` — инцидент не закрыт. Остальные поля, порядок, фильтры и сортировка — без изменений.
- **Пример запроса:** параметры и заголовки без изменений, тело отсутствует.
- **Пример ответа (успех):** фрагмент одного закрытого инцидента: прочие поля — без изменений.
  ```json
  { "closedAt": "2026-10-20T14:35:00+03:00" }
  ```
  Открытый инцидент, фрагмент: прочие поля — без изменений.
  ```json
  { "closedAt": null }
  ```
- **Ошибки:** не меняются.
- **Состояния UI по ответу:** строка → в колонке «Закрыт» дата и время; `null` или поле отсутствует → ячейка пустая; загрузка и ошибка — как сейчас.
- **Авторизация:** не меняется; список отдаётся тем же, кому и сейчас.
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1, FR-2

## 3. Backend — ответственность
### 3.1. По сервисам
- **incident-api** — реализует INT-1 (🟢): в каждый инцидент ответа списка добавляет `closedAt` из даты закрытия, которая уже хранится у инцидента; у открытого — `null`. Выбор инцидентов, фильтры и сортировку не трогает.
- **incident-web** — потребляет INT-1, на бэке работ нет.
### 3.2. Данные и хранение
Новых сущностей нет. Полей и таблиц в базе не добавляется и не меняется, миграций нет: дата закрытия уже хранится у инцидента и берётся при формировании ответа. 🔵 подтверждено аналитиком (со слов; валидировать при интеграции).

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Таблица списка инцидентов на `/incidents` в incident-web: новая колонка «Закрыт» с датой и временем из `closedAt` (INT-1).
### 4.2. Пользовательские сценарии
Дежурный открывает `/incidents`. У закрытого инцидента в колонке «Закрыт» видит дату и время закрытия (FR-1, FR-2). У открытого (`closedAt = null`) ячейка пустая.
### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `closed_shown` | 2xx, `closedAt` — строка | в колонке «Закрыт» дата и время |
| `closed_empty` | 2xx, `closedAt = null` или поля нет в ответе | ячейка «Закрыт» пустая |
