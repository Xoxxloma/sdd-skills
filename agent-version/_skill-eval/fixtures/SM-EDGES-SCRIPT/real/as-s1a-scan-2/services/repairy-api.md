## Назначение

Сервис Reparo — «платформа для управления ремонтными проектами»: ремонтная компания ведёт смету по комнатам и работам, отмечает выполненный объём, а заказчик следит за ходом ремонта и принимает работы. Он поддерживает приглашение сотрудников и заказчиков по ссылке из письма, закупки с чеками и список «нужно купить», фиксацию оплат от заказчика, сдачу работ по актам приёмки и уведомления участников о комментариях, платежах и изменениях сметы. Вход возможен по почте и паролю или через Telegram. Главные объекты — компании со своими сотрудниками, проекты ремонта с комнатами и работами, закупки, платежи, акты приёмки, документы и лента комментариев.

## Бизнес-правила

### `EstimateChangeLog` — запись журнала изменений сметы
- работа добавлена (`WORK_ADDED`) — при добавлении работы или сразу пачки работ; на пачку одна запись с названием «первая работа и ещё N»; разница положительная
- работа удалена (`WORK_REMOVED`) — при удалении работы; разница отрицательная
- работа изменена (`WORK_UPDATED`) — только если изменилась стоимость, то есть цена или объём; отметка о выполненном объёме в журнал не попадает
- закупка добавлена (`PURCHASE_ADDED`) — при добавлении закупки и при переводе позиции из списка «нужно купить» в закупку
- закупка удалена (`PURCHASE_REMOVED`) — при удалении закупки; разница отрицательная; изменение закупки в журнал не попадает

### `Project` — проект ремонта
- активный (`ACTIVE`) — состояние по умолчанию; только такие проекты считаются в аналитике как активные, в дебиторке, в среднем прогрессе портфеля, в нагрузке сотрудников и в числе заказчиков
- на паузе (`PAUSED`) — ставит вручную прораб или владелец при редактировании проекта; из аналитики активных выпадает
- завершён (`COMPLETED`) — ставит вручную прораб или владелец; из аналитики активных выпадает
- в архиве (`ARCHIVED`) — ставит вручную прораб или владелец; из аналитики активных выпадает
- переход между состояниями — из любого в любое, ограничений в коде нет; каждая смена учитывается в метрике переходов

### `ProjectCustomer` — заказчик в проекте
- приглашён (ожидает) — прораб или владелец отправил приглашение на почту; пока не принято, повторная отправка на тот же адрес отвергается; при удалении такая запись стирается совсем
- принял — заказчик принял приглашение по письму, по общей ссылке проекта или уже будучи вошедшим; одноразовая ссылка и адрес приглашения после этого стираются
- удалён — прораб или владелец убрал заказчика либо он вышел сам; запись остаётся, из списков исчезает; по общей ссылке проекта вернуться нельзя; новое приглашение на тот же адрес оживляет эту запись и сбрасывает признак принятия

### `ProjectMember` — участник проекта
- прораб (`FOREMAN`) — назначается при создании проекта; только прораб или владелец управляют участниками и заказчиками, сотрудник-прораб редактирует проект; когда единственный прораб уходит, уволен или удалил аккаунт, прорабом становится владелец компании
- рабочий (`WORKER`) — добавляет прораб или владелец; особых прав сверх участника нет; при уходе сотрудника из компании членство стирается

### `User` — пользователь платформы
- владелец (`OWNER`) — роль по умолчанию при регистрации и при создании аккаунта через Telegram; тот, кто создаёт компанию, становится владельцем; владельца нельзя убрать из компании
- сотрудник (`EMPLOYEE`) — создаётся приглашением владельца; видит только проекты, где он участник; после ухода или удаления из компании остаётся без компании и без проектов
- заказчик (`CUSTOMER`) — появляется при принятии приглашения на проект; не вносит платежи и не создаёт акты, сам рассматривает акты; в компании не состоит
- получает уведомления на почту (`EMAIL`) — значение по умолчанию; письмо уходит, если у пользователя есть адрес
- получает уведомления в Telegram (`TELEGRAM`) — ставится при создании аккаунта через Telegram, пользователь может выбрать сам; без привязанного Telegram уведомление не уходит
- получает уведомления push в браузере (`WEB_PUSH`) — включается при оформлении push-подписки; устаревшая подписка удаляется при первом отказе браузера
- приглашён, но не принял — сотрудник создан владельцем без пароля, имя равно адресу почты; войти он не может; повторное приглашение выпускает новую ссылку и письмо, старая перестаёт работать
- принял приглашение — после того как по ссылке из письма задал имя и пароль; ссылка одноразовая, повторно принять нельзя

### `WorkAcceptance` — акт приёмки
- на рассмотрении (`PENDING`) — создаёт сотрудник или владелец из полностью выполненных работ; номер следующий по проекту; такой акт можно отозвать, он стирается, а работы возвращаются
- рассмотрен (`REVIEWED`) — заказчик рассмотрел все работы акта; повторно рассмотреть и отозвать нельзя

### `WorkAcceptanceItem` — работа в акте приёмки
- ожидает (`PENDING`) — создаётся вместе с актом
- принята (`ACCEPTED`) — заказчик принял работу; работа становится принятой и больше не меняется
- отклонена (`REJECTED`) — заказчик отклонил работу, с комментарием; работа возвращается в состояние «не на приёмке» и может уйти в новый акт

### `WorkItem` — работа в смете комнаты
- не на приёмке (`NONE`) — состояние по умолчанию; работа возвращается сюда при отзыве акта и при отклонении заказчиком; готовой к приёмке она считается, когда выполнен весь объём
- на приёмке (`PENDING`) — когда работа попала в акт; её нельзя удалить, как и комнату, в которой она лежит
- принята (`ACCEPTED`) — заказчик принял работу; выполненный объём больше не меняется

### ограничение «пользователь без компании не работает с проектами»
- условием управляет `OWNER`: он приглашает сотрудника в компанию и убирает из неё; пока пользователь не состоит в компании, каталог, список сотрудников и данные компании отвечают «Требуется компания», а список проектов пуст

### ограничение «исключённый заказчик не возвращается в проект по общей ссылке»
- условием управляет `EMPLOYEE` — прораб проекта (владелец тоже может): после исключения общая ссылка проекта отвечает «Вы были исключены из проекта. Запросите новое приглашение.», вернуть заказчика можно только новым приглашением

### сообщение «акт приёмки отозван»
- когда сотрудник или владелец отозвал акт; получают участники проекта, владельцы компании и принявшие заказчики, кроме автора; вид `ACCEPTANCE_REVOKED`; приходит сразу, без задержки

### сообщение «изменена смета»
- когда добавлена, изменена или удалена работа либо закупка, либо позиция списка перенесена в закупку; получатели те же, кроме автора; вид `ESTIMATE_CHANGED`; частые правки склеиваются, отправка через три минуты тишины, с пометкой «(+N изм.)»

### сообщение «код подтверждения удаления аккаунта»
- когда пользователь просит удалить аккаунт или повторно прислать код; получает сам пользователь на почту, если адрес есть; код действует 15 минут

### сообщение «код подтверждения удаления аккаунта в Telegram»
- то же, но для аккаунта без почты, с привязанным Telegram; уходит напрямую, при отказе Telegram запрос заканчивается ошибкой «Не удалось отправить код»; без почты и Telegram код выслать нельзя

### сообщение «новый комментарий»
- когда кто-то оставил комментарий в ленте проекта или в комнате; получатели те же, кроме автора; вид `COMMENT_ADDED`; отправка через 45 секунд тишины, с объединением

### сообщение «новый платёж»
- когда записана оплата от заказчика; получатели те же, кроме автора; вид `PAYMENT_REGISTERED`; в тексте сумма в рублях; отправка через 45 секунд тишины

### сообщение «обновлён прогресс»
- когда сотрудник отметил выполненный объём работы; получатели те же, кроме автора; вид `PROGRESS_UPDATED`; отправка через две минуты тишины, с объединением

### сообщение «приветствие после регистрации»
- после регистрации по почте; получает новый пользователь; в письме логин и напоминание про восстановление пароля

### сообщение «приглашение заказчика на проект»
- когда прораб или владелец приглашает заказчика или переотправляет приглашение; получает приглашённый на почту; в письме кнопка «Принять приглашение»

### сообщение «приглашение принято заказчиком»
- когда заказчик принял приглашение по ссылке из письма с созданием аккаунта; получает сам заказчик; при принятии уже вошедшим пользователем письмо не уходит

### сообщение «приглашение принято сотрудником»
- когда сотрудник принял приглашение по ссылке из письма; получает сам сотрудник; в письме название компании

### сообщение «приглашение сотрудника в компанию»
- когда владелец приглашает сотрудника или переотправляет приглашение; получает приглашённый на почту; в письме кнопка «Принять приглашение»

### сообщение «приёмка рассмотрена»
- когда заказчик рассмотрел акт; получатели те же, кроме автора; вид `ACCEPTANCE_REVIEWED`; приходит сразу

### сообщение «работы отправлены на приёмку»
- когда создан акт приёмки; получатели те же, кроме автора; вид `ACCEPTANCE_CREATED`; приходит сразу

### сообщение «сброс пароля»
- когда пользователь запросил сброс; получает владелец адреса, если такой пользователь есть; кто бы ни спросил, ответ одинаковый; ссылка действует час

### сообщение «уведомление по проекту web push»
- доставка любого уведомления по проекту пользователю с каналом push; уходит на все его подписки; подписка, от которой браузер отказался, удаляется

### сообщение «уведомление по проекту в Telegram»
- доставка любого уведомления по проекту пользователю с каналом Telegram; без токена бота уведомления в Telegram не отправляются совсем; отказ Telegram только записывается в журнал

### сообщение «уведомление по проекту письмом»
- доставка любого уведомления по проекту пользователю с каналом почты; не уходит, если адреса нет

## Стек
| Слой | Чем |
|---|---|
| Язык и фреймворк | TypeScript, NestJS |

## Фоновые задачи

### `flush`
Рассылает накопленные уведомления участникам проектов.
- расписание `*/30 * * * * *` (каждые 30 секунд)
- забирает записи очереди из Redis атомарно, поэтому несколько экземпляров не шлют дубль; запись берётся до отправки, сбой посреди прогона теряет её
- у вида события своя задержка: комментарий и платёж 45 секунд, прогресс 2 минуты, смета 3 минуты, акты без задержки; не истёкшая запись возвращается обратно
- события одного вида по одному проекту и получателю склеиваются в одно, в тексте «(+N изм.)»
- лимит 10 уведомлений в час на получателя и вид события; сверх лимита уведомление отбрасывается, в журнал пишется предупреждение
- отправляет пачками по 5; сбой отправки не повторяется; необработанная запись живёт в Redis 10 минут
- каналы: почта, Telegram, web push — по полю канала у получателя

## Владеет данными

### `Comment`
Комментарий в ленте проекта или в комнате.
- `id`: `string`
- `projectId`: `string`
- `roomId`: `string?`
- `authorId`: `string?`
- `text`: `string`
- `createdAt`: `timestamp`
— `roomId` пуст у комментария общей ленты
— `authorId` пуст у комментария удалённого пользователя; в ответах автор подменяется на «Удалённый пользователь»

### `CommentAttachment`
Вложение комментария.
- `id`: `string`
- `commentId`: `string`
- `url`: `string`
- `fileType`: `PHOTO` \| `VIDEO` \| `DOCUMENT`
- `createdAt`: `timestamp`
— удаляется вместе с комментарием; файл из хранилища удаляется кодом, а не базой

### `Company`
Компания ремонтной организации.
- `id`: `string`
- `name`: `string`
- `email`: `string?`
- `phone`: `string?`
- `logoUrl`: `string?`
- `createdAt`: `timestamp`
— удаляется вместе с аккаунтом владельца

### `EstimateChangeLog`
Журнал изменений сметы.
- `id`: `string`
- `projectId`: `string`
- `type`: `WORK_ADDED` \| `WORK_REMOVED` \| `WORK_UPDATED` \| `PURCHASE_ADDED` \| `PURCHASE_REMOVED`
- `entityName`: `string`
- `delta`: `decimal`
- `totalAfter`: `decimal`
- `createdById`: `string?`
- `createdAt`: `timestamp`
— пишется только внутри транзакции изменения; `totalAfter` — стоимость работ и закупок проекта после изменения
— `createdById` пуст у записи удалённого пользователя

### `Project`
Проект ремонта.
- `id`: `string`
- `companyId`: `string`
- `name`: `string`
- `address`: `string`
- `latitude`: `float?`
- `longitude`: `float?`
- `coverPhotoUrl`: `string?`
- `status`: `ACTIVE` \| `PAUSED` \| `COMPLETED` \| `ARCHIVED`
- `inviteToken`: `string`
- `publicToken`: `string`
- `createdAt`: `timestamp`
- `updatedAt`: `timestamp`
- `deadlineAt`: `timestamp?`
— `inviteToken` — общая ссылка для заказчиков, `publicToken` — ссылка публичного просмотра; оба уникальны и создаются вместе с проектом, в коде не перевыпускаются

## Роли и доступ
| Роль | Что может |
|---|---|
| `CUSTOMER` | роль пользователя на уровне компании; видит проекты, где он принятый заказчик и не удалён; читает смету, комнаты, работы, закупки, документы, историю сметы, акты и ленту; пишет комментарии; рассматривает акты приёмки; принимает приглашения и выходит из проектов; платежи, акты, правки сметы и закупок ему недоступны |
| `EMPLOYEE` | роль пользователя на уровне компании; работает только с проектами, где он участник; создаёт проекты, комнаты, работы, закупки, документы, платежи, акты и список «нужно купить»; читает список сотрудников и каталог; может покинуть компанию |
| `FOREMAN` | роль в проекте (ProjectMemberRole); сверх участника редактирует проект, добавляет и убирает участников, приглашает и убирает заказчиков |
| `OWNER` | роль пользователя на уровне компании; видит все проекты компании без членства; управляет компанией, сотрудниками, каталогом; видит аналитику; удаляет проект; удаляет чужие комментарии, закупки и позиции списка «нужно купить»; управляет участниками и заказчиками любого проекта |
| `WORKER` | роль в проекте (ProjectMemberRole); особых прав сверх участника нет |
| `без входа` | по публичной ссылке проекта видит проект с комнатами, прогрессом, названиями работ и объёмами, итогами по стоимости, оплате и закупкам, данными компании, адресом и координатами; скрыты расценки работ, список заказчиков, телефоны сотрудников, общая ссылка для заказчиков; открыты также регистрация, вход, сведения о приглашении по токену, открытый ключ push, имя бота, проверка живости и метрики |
| `бот Telegram` | не пользователь, а вызывающий бот; получает одноразовый код входа по общему секрету `BOT_INTERNAL_SECRET`; список ботов вне репозитория |
