## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** Запись сотрудника на рейс в портале шаттла проходит только если в службе пропусков у него есть пропуск в состоянии `active`; иначе сотрудник видит причину отказа. В карточке рейса появляется отметка «можно с велосипедом» по новому полю рейса `bikeRack`. В списке рейсов первыми идут рейсы, у которых код офиса совпадает с офисом сотрудника из справочника сотрудников.
**Тип:** доработка
**Стороны:** Fullstack — бэк шаттла (`shuttle-api`) ходит в две чужие системы и отдаёт новые поля/ошибки; веб-портал (`shuttle-web`) показывает отметку, сортирует список и выводит причины отказа записи.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `shuttle-api` | изменение: проверка пропуска при записи, поле `bikeRack`, офис сотрудника в списке | команда «Шаттл» | 🔵 подтв. аналитиком (со слов) |
| `shuttle-web` | изменение: отметка велосипеда, сортировка списка, сообщения об отказе | команда «Шаттл» | 🔵 подтв. аналитиком (со слов) |
| `badge-service` | потребитель: проверка пропуска сотрудника | команда «Безопасность зданий» | 🔵 подтв. аналитиком (со слов) |
| `org-directory` | потребитель: офис сотрудника | команда «Кадровые системы» | 🔵 подтв. аналитиком (со слов) |
### 1.3. Связь с бизнес-требованиями
Места не занимают люди с заблокированным пропуском, сотрудник заранее знает про место для велосипеда и сразу видит рейсы от своего офиса. Требования — в §7.

## 2. Взаимодействия (ядро)

### INT-1. Запись на рейс с проверкой пропуска — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** FE → BE (`shuttle-web` → `shuttle-api`)
- **Триггер:** сотрудник нажимает «Записаться» на рейс
- **Существующий стык:** 🟡 к валидации — существующая ручка записи текущего сотрудника на рейс; путь и прежние ответы не подтверждены.
- **Изменение:**

| поле | где | было | стало |
|------|-----|------|-------|
| проверка пропуска перед созданием записи (INT-2) | поведение ручки | 🟡 к валидации | запись создаётся только при пропуске в `active` |
| ответ `403`, тело `error` = `BADGE_NOT_ACTIVE`, `reason` | ответ | — | добавлено |
| ответ `503`, тело `error` = `BADGE_CHECK_UNAVAILABLE` | ответ | — | добавлено |

- **Контракт (запрос):** без изменений.
- **Контракт (ответ):** успех — без изменений. Новые ошибки:
  - `403 BADGE_NOT_ACTIVE`: `error` string, `message` string, `reason` enum `blocked | expired | none` (`blocked` — есть пропуск в `blocked`; иначе `expired` — есть пропуск в `expired`; `none` — пропусков нет).
  - `503 BADGE_CHECK_UNAVAILABLE`: `error` string, `message` string.
- **Пример запроса:** параметры и тело — как у прежней записи (без изменений).
- **Пример ответа (успех):** без изменений.
- **Пример ответа (пропуск не активен):**
  ```json
  { "error": "BADGE_NOT_ACTIVE", "reason": "blocked", "message": "Пропуск заблокирован" }
  ```
- **Пример ответа (служба пропусков не ответила):**
  ```json
  { "error": "BADGE_CHECK_UNAVAILABLE", "message": "Не удалось проверить пропуск, попробуйте позже" }
  ```
- **Ошибки:** см. «Каталог ошибок». Проверка идёт при каждой записи, сразу, без кэша; при `403` и `503` запись не создаётся и место не списывается.
- **Состояния UI по ответу:** успех → запись подтверждена; `403` → сообщение по `reason`; `503` → «Не удалось проверить пропуск, попробуйте позже», кнопка доступна для повтора.
- **Авторизация:** роль `EMPLOYEE`; проверяется в `shuttle-api`; логин для проверки пропуска берётся из контекста текущего сотрудника, не из запроса.
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1

### INT-2. Проверка пропуска сотрудника — 🔵
- **Вид:** потребление существующего
- **Граница/направление:** `shuttle-api` → `badge-service`
- **Триггер:** запись на рейс (INT-1), каждый раз
- **Контракт (запрос):** `GET /api/v3/badges?holderLogin={login}`; `login` — доменный логин текущего сотрудника.
- **Контракт (ответ):** `items[]`; в элементе `badgeId` string, `state` enum `active | blocked | expired`. Запись проходит, если хотя бы у одного элемента `state = active`.
- **Пример запроса:** `GET /api/v3/badges?holderLogin=ivanov`, тело отсутствует
- **Пример ответа (успех):** фрагмент: прочие поля — без изменений
  ```json
  { "items": [ { "badgeId": "B-1001", "state": "active" } ] }
  ```
- **Ошибки:** служба не ответила (таймаут 3 с — 🟢 наш клиент, либо ошибка) → INT-1 отдаёт `503 BADGE_CHECK_UNAVAILABLE`.
- **Авторизация:** 🟡 к валидации — способ авторизации бэка шаттла не подтверждён; доступ заводится заявкой до релиза.
- **Происхождение:** 🔵 подтверждено аналитиком (по карточке services/badge-service.md; обёртка `items[]` — со слов; валидировать при интеграции)
- **Трассировка:** FR-1

## 3. Backend — ответственность
### 3.1. По сервисам
- `shuttle-api` (🟢): INT-1 — перед созданием записи вызывает INT-2, без кэша; при `403`/`503` запись не создаётся. INT-3 — отдаёт `bikeRack` из рейса. INT-4 — по логину текущего сотрудника вызывает INT-5 и кладёт `employeeOfficeCode` в каждый рейс; сбой справочника не ломает список.
- `badge-service` — 🔵 отдаёт INT-2; работ нет.
- `org-directory` — 🔵 отдаёт INT-5; работ нет.
### 3.2. Данные и хранение
- [🟢] `Trip` (изменение существующей сущности `shuttle-api`) — добавляется `bikeRack`: boolean, обязательное, по умолчанию `false`.
- [🔵] Пропуск (читаем в `badge-service`) — `badgeId` string, `state` enum `active | blocked | expired`. Источник: по карточке services/badge-service.md.
- [🔵] Сотрудник справочника (читаем в `org-directory`) — `officeCode` string. Источник: со слов.

Миграция: да — добавить колонку `bikeRack` в хранилище рейсов; точный DDL финализирует `shuttle-api`. В уже лежащих строках: `false`. Значения `true` проставляет транспортная служба скриптом один раз при выкате, дальше — через поддержку; экрана редактирования нет. Новых таблиц нет.
### 3.3. Авторизация/доступ на бэке
`shuttle-api` пускает роль `EMPLOYEE`; других ролей нет. Не-`EMPLOYEE` — отказ прежним механизмом. Логин для INT-2 и INT-5 берётся из контекста текущего сотрудника.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
- Карточка рейса (`/trips/:tripId`): отметка «можно с велосипедом» по `bikeRack` (INT-3); сообщения об отказе записи (INT-1).
- Список рейсов (`/trips`): сортировка по `employeeOfficeCode` (INT-4).
### 4.2. Пользовательские сценарии
- Запись: «Записаться» → успех, либо причина отказа по `reason`, либо «попробуйте позже» с повтором (FR-1).
- Карточка: `bikeRack = true` → отметка (FR-2).
- Список: рейсы своего офиса сверху (FR-3); справочник недоступен → общий порядок.
### 4.3. Состояния
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `bike_available` | 2xx, `bikeRack = true` | «можно с велосипедом» |
| `bike_unavailable` | 2xx, `bikeRack = false` или поля нет | отметки нет |
| `office_sorted` | 2xx, `employeeOfficeCode` задан | свой офис сверху |
| `office_unknown` | 2xx, `employeeOfficeCode = null` или нет | общий порядок, без сообщения |
| `error_badge_blocked` | 403, `reason = blocked` | «Пропуск заблокирован» |
| `error_badge_expired` | 403, `reason = expired` | «Пропуск истёк» |
| `error_badge_none` | 403, `reason = none` | «Активного пропуска нет» |
| `error_badge_check` | 503 `BADGE_CHECK_UNAVAILABLE` | «Не удалось проверить пропуск, попробуйте позже», повтор |

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Синхронно: проверка пропуска (INT-2) и запрос офиса (INT-5) идут в запросе пользователя. Кэша нет. Таймауты 🟢: пропуск 3 с, справочник 2 с. Нагрузка: около 1 500 сотрудников, до 300 записей в день, пик 7–9 утра; одна проверка пропуска на запись, один запрос офиса на открытие списка.
### 5.2. Надёжность/деградация
- Служба пропусков не ответила → запись не проходит (`503`), в `shuttle-api` ничего не создаётся, места не теряются.
- Справочник не ответил → список общим порядком, без ошибки.
### 5.3. Безопасность/доступ (сводно)
| Граница | Кто вправе |
|---------|------------|
| INT-1, INT-3, INT-4 | `EMPLOYEE` |
| INT-2, INT-5 | сервисный вызов `shuttle-api`; авторизация 🟡 к валидации |

## 6. Релиз и интеграция
### 6.1. Порядок выката
Обычным релизом: сначала `shuttle-api`, затем `shuttle-web`. Скрипт отметки `bikeRack` у рейсов запускается транспортной службой при выкате бэка.
### 6.2. Обратная совместимость
Новые поля `bikeRack` и `employeeOfficeCode` — добавления, прежние потребители их игнорируют. Новые ответы `403`/`503` при записи: прежний фронт в окне между релизами показывает их так, как показывает неизвестные ошибки — 🟡 к валидации.
### 6.3. Фиче-флаги
~~Не применимо: задача не использует фиче-флаги.~~
### 6.4. План отката
- **Откат только BE:** новый FE получает ответы без `bikeRack` и `employeeOfficeCode` — отметки нет, общий порядок; запись идёт без проверки пропуска. Допустимо.
- **Откат только FE:** BE отдаёт новое, прежний FE игнорирует поля; ошибки записи показывает прежним способом (🟡, см. п. 4 открытых вопросов).
- **Откат DDL:** колонка `bikeRack` удаляется, пометки `true` теряются; после повторного выката транспортная служба проставляет их скриптом снова.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1. Запись только с активным пропуском | INT-1, INT-2 | Дано: у сотрудника пропуск `active`, когда записывается на рейс, тогда запись создана. Дано: пропуск `blocked`, когда записывается, тогда `403`, «Пропуск заблокирован», записи нет. Дано: служба пропусков не отвечает, когда записывается, тогда `503`, «Не удалось проверить пропуск, попробуйте позже», места не списаны |
| FR-2. Место для велосипеда в карточке рейса | INT-3 | Дано: у рейса `bikeRack = true`, когда сотрудник открывает карточку, тогда видна отметка «можно с велосипедом»; при `false` отметки нет |
| FR-3. Рейсы от своего офиса первыми | INT-4, INT-5 | Дано: офис сотрудника «Север», когда открывает список, тогда рейсы с `officeCode` «Север» идут первыми. Дано: справочник не отвечает, когда открывает список, тогда общий порядок, без ошибки |
