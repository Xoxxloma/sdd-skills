## 1. Обзор изменения

### 1.1. Что делаем и тип изменения

**Суть:** Покупатель оформляет возврат в мобильном приложении; сервис возвратов бронирует слот приёмки на складе, заказывает курьера у партнёра, после приёмки товара склад сообщает биллингу, биллинг возвращает деньги и сообщает сервису возвратов; покупатель получает SMS о каждом шаге.

**Тип:** новая функциональность

**Стороны:** Fullstack (новый контракт приложения с сервисом возвратов, интеграции с тремя существующими сервисами и партнёром)

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Мобильное приложение | Оформление возврата, статус | Команда приложения | 🔵 подтв. аналитиком |
| `returns-api` | Новый сервис возвратов | Команда возвратов | 🟢 новое |
| `warehouse-service` | Слоты приёмки, приёмка товара | Команда склада | 🔵 подтв. аналитиком |
| `courier-gateway` | Шлюз партнёрской курьерской службы | Команда интеграций | 🔵 подтв. аналитиком |
| `billing` | Возврат денег | Команда биллинга | 🔵 подтв. аналитиком |
| `notify` | SMS покупателю | Команда уведомлений | 🔵 подтв. аналитиком |

### 1.3. Связь с бизнес-требованиями

Возврат без визита в пункт выдачи (FR-1, FR-2), забор курьером (FR-3), возврат денег после приёмки (FR-4), информирование покупателя (FR-5).

## 2. Взаимодействия (ядро)

### INT-1. Оформление возврата — 🟢

- **Граница/направление:** Мобильное приложение → `returns-api`
- **Триггер:** Покупатель выбирает заказ и товар, указывает причину и адрес забора
- **Контракт (запрос):** `POST /v1/returns`
  - `orderId` (string, обязательно), `items` (array of {sku, qty}, обязательно), `reason` (enum: `defect` | `wrong_item` | `not_needed`), `pickupAddress` (string, обязательно)
- **Контракт (ответ):** `returnId` (string), `status` (enum: `created`), `createdAt` (iso8601)
- **Ошибки:** 400 — нет позиций; 409 — возврат по заказу уже оформлен
- **Авторизация:** покупатель — только свои заказы; чужой заказ → 403
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2

### INT-2. Бронь слота приёмки — 🔵

- **Граница/направление:** `returns-api` → `warehouse-service` (синхронно, часть обработки INT-1)
- **Триггер:** возврат создан
- **Контракт (запрос):** существующий вызов брони слота, `POST /internal/slots` — так назвал аналитик со слов команды склада
- **Контракт (ответ):** идентификатор слота и окно приёмки
- **Ошибки:** слотов нет → возврат в статусе `waiting_slot`
- **Авторизация:** сервисная учётка `returns-api`
- **Происхождение:** 🔵 подтверждено аналитиком (не по коду)
- **Трассировка:** FR-2

### INT-3. Заказ курьера у партнёра — 🟡

- **Граница/направление:** `returns-api` → `courier-gateway`
- **Триггер:** слот приёмки забронирован
- **Контракт (запрос):** 🟡 к валидации — предположительно `POST /partner/v3/pickups` с адресом и окном забора
- **Контракт (ответ):** 🟡 к валидации — идентификатор заявки курьера
- **Ошибки:** 🟡 к валидации
- **Авторизация:** 🟡 к валидации — ключ партнёра
- **Происхождение:** 🟡 к валидации
- **Трассировка:** FR-3

### INT-4. Статус курьера (вебхук) — 🟢

- **Граница/направление:** `courier-gateway` → `returns-api` (вебхук)
- **Триггер:** партнёр меняет статус забора: назначен, забрал, доставил на склад
- **Контракт (запрос):** `POST /v1/returns/{returnId}/courier-status`
  - `status` (enum: `assigned` | `picked_up` | `delivered`), `at` (iso8601)
- **Контракт (ответ):** 204 без тела
- **Ошибки:** 404 — возврат не найден; повтор того же статуса — 204 (идемпотентно)
- **Авторизация:** подпись вебхука ключом партнёра
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3, FR-5

### INT-5. Товар принят на складе — 🔵

- **Граница/направление:** событие: `warehouse-service` → `billing` (через Kafka)
- **Триггер:** кладовщик принял товар по слоту
- **Контракт (запрос):** существующее событие приёмки, биллинг уже его слушает для возвратов из пунктов выдачи
- **Контракт (ответ):** нет (событие)
- **Ошибки:** не применимо
- **Авторизация:** не применимо
- **Происхождение:** 🔵 подтверждено аналитиком (не по коду)
- **Трассировка:** FR-4

### INT-6. Результат возврата денег (колбэк) — 🟢

- **Граница/направление:** `billing` → `returns-api` (колбэк)
- **Триггер:** биллинг провёл или отклонил возврат денег
- **Контракт (запрос):** `POST /v1/returns/{returnId}/refund-status`
  - `result` (enum: `refunded` | `rejected`), `amount` (decimal), `at` (iso8601)
- **Контракт (ответ):** 204 без тела
- **Ошибки:** 404 — возврат не найден; повтор — 204
- **Авторизация:** сервисная учётка `billing`
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-4

### INT-7. Событие смены статуса возврата — 🟢

- **Граница/направление:** событие: `returns-api` → `notify`
- **Триггер:** любой переход статуса возврата
- **Контракт (запрос):** событие `returns.status-changed` — `returnId`, `status`, `phone`
- **Контракт (ответ):** нет (событие)
- **Ошибки:** не применимо
- **Авторизация:** не применимо
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-5

### INT-8. SMS покупателю — 🔵

- **Граница/направление:** `notify` → Покупатель (SMS)
- **Триггер:** событие INT-7
- **Контракт (запрос):** существующая отправка SMS по шаблону
- **Контракт (ответ):** нет
- **Ошибки:** SMS не доставлено — повтор по правилам notify
- **Авторизация:** не применимо
- **Происхождение:** 🔵 подтверждено аналитиком (не по коду)
- **Трассировка:** FR-5

### INT-9. Запрос возврата денег — 🟡

- **Граница/направление:** `returns-api` → `billing`
- **Триггер:** возврат оформлен по заказу, оплаченному бонусами (приёмка на складе для бонусов не ждётся)
- **Контракт (запрос):** 🟡 к валидации — предположительно `POST /v2/refunds` с `returnId` как ключом идемпотентности
- **Контракт (ответ):** 🟡 к валидации
- **Ошибки:** 🟡 к валидации
- **Авторизация:** сервисная учётка `returns-api`
- **Происхождение:** 🟡 к валидации
- **Трассировка:** FR-4

### INT-10. Отмена брони слота — 🟡

- **Граница/направление:** бэкенд возвратов → `warehouse-service`
- **Триггер:** покупатель отменил возврат до забора
- **Контракт (запрос):** 🟡 к валидации — отмена брони слота существующим вызовом склада
- **Контракт (ответ):** 🟡 к валидации
- **Ошибки:** 🟡 к валидации
- **Авторизация:** сервисная учётка `returns-api`
- **Происхождение:** 🟡 к валидации
- **Трассировка:** FR-2

### INT-11. Сверка остатков с 1С — ❓

- **Граница/направление:** ❓ не решено — склад забирает остатки из 1С или 1С присылает их складу
- **Триггер:** товар принят на складе
- **Контракт (запрос):** ❓ зависит от направления
- **Контракт (ответ):** ❓
- **Ошибки:** ❓
- **Авторизация:** ❓
- **Происхождение:** ❓
- **Трассировка:** FR-4

## 3. Backend — ответственность

### 3.1. По сервисам

**returns-api (новый):** принимает INT-1, INT-4, INT-6; вызывает INT-2, INT-3, INT-9, INT-10; публикует INT-7.

**warehouse-service, courier-gateway, billing, notify:** изменений нет, кроме подтверждения контрактов 🟡.

### 3.2. Данные и хранение

- 🟢 `Return` — `id`, `orderId`, `items`, `reason`, `pickupAddress`, `status` (enum: `created` | `waiting_slot` | `courier_ordered` | `picked_up` | `accepted` | `refunded` | `rejected` | `cancelled`), `slotId`, `courierRequestId`, `createdAt`

### 3.3. Авторизация/доступ на бэке

Покупатель — свои возвраты; сервисные учётки — вебхуки и колбэки с проверкой подписи.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Мобильное приложение: кнопка «Вернуть» в карточке заказа, форма возврата, экран статуса возврата.

### 4.2. Пользовательские сценарии

Оформить возврат → увидеть окно забора → получить SMS о заборе, приёмке и возврате денег.

### 4.3. Состояния (именованные)

`created`, `waiting_slot`, `courier_ordered`, `picked_up`, `accepted`, `refunded`, `rejected`, `cancelled`.

### 4.4. Доступ по ролям в UI

Только авторизованный покупатель.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

До тысячи возвратов в сутки; INT-2 синхронный, таймаут 3 с.

### 5.2. Надёжность/деградация

Склад недоступен → `waiting_slot`, повтор раз в 10 минут.

### 5.3. Безопасность/доступ (сводно)

Подпись вебхуков INT-4 и INT-6.

## 6. Релиз и интеграция

### 6.1. Порядок выката

returns-api → приложение за фиче-флагом → включение по регионам.

### 6.2. Обратная совместимость

Не применимо: новый сервис.

### 6.3. Фиче-флаги

`returns_courier_pickup`.

### 6.4. План отката

Выключить флаг; оформленные возвраты доводятся вручную.

### 6.5. Преднастройка до релиза (чек-лист)

Ключ партнёра для INT-3 и INT-4; сервисные учётки для INT-2, INT-6, INT-9.

## 7. Трассировка приёмки

| FR | INT | Проверка |
|----|-----|----------|
| FR-1 | INT-1 | возврат оформлен из приложения |
| FR-2 | INT-1, INT-2, INT-10 | слот забронирован и снимается при отмене |
| FR-3 | INT-3, INT-4 | курьер заказан, статусы доходят |
| FR-4 | INT-5, INT-6, INT-9, INT-11 | деньги возвращены после приёмки |
| FR-5 | INT-7, INT-8 | SMS на каждом шаге |
