# Этап 01 — Имя согласующего в списке заявок

## Что делает
portal-api добавляет в каждую заявку ответа списка `approverName`, а portal-web показывает под статусом строку «Согласует: <имя>».

## Вход (стык)
—

## Выход (стык) — контракт из спеки, дословно

### INT-1. Список своих заявок: имя согласующего — 🟢 изменение существующего
- **Вид:** изменение существующего
- **Граница/направление:** FE → BE (portal-web → portal-api)
- **Триггер:** открытие списка своих заявок в portal-web
- **Существующий стык:** GET списка своих заявок, отдаёт portal-api — 🔵 подтверждено аналитиком (со слов; валидировать при интеграции). Путь и прежние поля ответа в источнике не названы и здесь не приводятся.
- **Изменение:**

| поле | где | было | стало |
|------|-----|------|-------|
| `approverName` | каждая заявка в ответе списка | отсутствует | добавлено: строка; `null`, если согласующего нет (черновик); поле присутствует всегда |

- **Контракт (запрос):** без изменений.
- **Контракт (ответ):** в каждую заявку добавляется `approverName` — `string | null`. Строка — имя согласующего из этой же заявки, как оно в ней хранится. `null` — у заявки нет согласующего (черновик). Остальные поля заявки и порядок записей — без изменений.
- **Пример запроса:** параметры и заголовки без изменений, тело отсутствует.
- **Пример ответа (успех):** фрагмент одной заявки: прочие поля — без изменений.
  ```json
  { "approverName": "Смирнова А." }
  ```
  Черновик, фрагмент: прочие поля — без изменений.
  ```json
  { "approverName": null }
  ```
- **Ошибки:** не меняются.
- **Состояния UI по ответу:** строка → под статусом «Согласует: <имя>»; `null` или поле отсутствует → строки нет; загрузка и ошибка — как сейчас.
- **Авторизация:** не меняется; список отдаёт только свои заявки, как и сейчас.
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1

Из §3.1: portal-api в каждую заявку ответа списка добавляет `approverName` из согласующего, который уже хранится в этой же заявке; у заявки без согласующего — `null`. Выбор заявок, порядок и фильтры списка не трогает. Из §3.2: новых сущностей, полей и таблиц в базе нет, миграций нет.

Из §4.1: строка заявки в списке своих заявок в portal-web — под статусом выводится «Согласует: <имя>» из `approverName` (INT-1).

## Проверка в одиночку
- Заявка на согласовании, `approverName = "Смирнова А."` → под статусом «Согласует: Смирнова А.» (`approver_shown`).
- Черновик, `approverName = null` → строки нет, ничего вместо неё не выводится (`approver_none`).
- Ответ без поля `approverName` (откат portal-api) → как при `null`: строки нет (`approver_none`).
- Остальные поля заявок, порядок записей, фильтры списка — без изменений. Ошибки и загрузка — как сейчас.

## Из спеки — только относящееся к этому этапу
- **Трассировка:** FR-1 🔵 (решение аналитика Иванова) → INT-1; §4.1, §4.3. Тест-кейс: Дано заявка Смирновой на согласовании и черновик, когда сотрудник открывает список своих заявок, тогда у заявки на согласовании под статусом «Согласует: Смирнова А.», а у черновика строки нет.
- **Авторизация:** не меняется; список отдаёт только свои заявки, как и сейчас.
- **Состояния UI:**

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `approver_shown` | 2xx, `approverName` — непустая строка | под статусом «Согласует: <имя>» |
| `approver_none` | 2xx, `approverName = null` или поля нет в ответе | строки нет, ничего вместо неё не выводится |

- **НФТ:** не меняются (синхронность, кэш, надёжность, безопасность).
- **Порядок выката (§6.1):** общий релиз: сначала portal-api, затем portal-web.

## Чего этот этап НЕ делает
Других этапов нет. Не меняет выбор заявок, порядок и фильтры списка, карточку заявки, права на просмотр; не добавляет полей и миграций в базе.
