# Этап 01 — Запись на рейс с проверкой пропуска

## Что делает
Перед созданием записи на рейс бэк `shuttle-api` проверяет пропуск сотрудника через INT-2; действующего пропуска нет — запись не создаётся, места не резервируются; фронт `shuttle-web` показывает отказ.

## Вход (стык)
INT-2 — проверка пропуска сотрудника в `badge-service` (команда «Безопасность зданий»), стык извне, 🟡 к валидации. Из спеки: вызов `badge-service`, возвращающий пропуска сотрудника по его логину, и состояния пропуска. Путь, поля и значения состояний аналитиком не подтверждены, в спеку не вносятся. Что нужно от ответа: понять, есть ли у сотрудника действующий пропуск, а если нет — заблокирован он или истёк. Вызывается при каждой записи, сразу, без кэша. Способ авторизации `shuttle-api` в `badge-service` — 🟡 к валидации; доступ заводится заявкой до релиза. Значение таймаута — ⚠️ не названо (открытый пункт 7).

## Выход (стык) — контракт из спеки, дословно

### INT-1. Запись на рейс с проверкой пропуска — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** FE (`shuttle-web`) → BE (`shuttle-api`)
- **Триггер:** сотрудник нажимает «Записаться» на рейс
- **Существующий стык:** 🟡 к валидации — существующая ручка записи на рейс в `shuttle-api`; путь, прежние ответ и формат ошибок аналитиком не подтверждены.
- **Изменение:**

| поле | где | было | стало |
|------|-----|------|-------|
| проверка пропуска сотрудника | поведение ручки записи | — | перед созданием записи бэк проверяет пропуск через INT-2; действующего пропуска нет — запись не создаётся |
| ответ `422` с `code` `BADGE_BLOCKED` / `BADGE_EXPIRED` / `BADGE_MISSING` | ответ ручки | — | новые ошибки: пропуск заблокирован / истёк / не найден |
| ответ `503` с `code` `BADGE_CHECK_FAILED` | ответ ручки | — | новая ошибка: служба пропусков не ответила |

- **Контракт (запрос):** прежний — без изменений 🟡 (тело и путь — к валидации); логин сотрудника бэк берёт из сессии, в запрос он не добавляется.
- **Контракт (ответ):** успех — как прежде 🟡. Ошибки новые, тело: `code: string` (enum ниже), `message: string` (текст для показа сотруднику).
  Порядок на бэке: 1) проверка пропуска; 2) только при успехе — резервирование места и создание записи. Отказ по пропуску или сбой проверки не меняет число свободных мест и не создаёт записи.
- **Пример запроса:** тело — как прежде 🟡; параметры и заголовки добавляются только прежние.
- **Пример ответа (успех):** как прежде 🟡; фрагмент не приводится.
- **Пример ответа (ошибка, пропуск заблокирован):**
  ```json
  { "code": "BADGE_BLOCKED", "message": "пропуск заблокирован" }
  ```
- **Пример ответа (ошибка, служба пропусков не ответила):**
  ```json
  { "code": "BADGE_CHECK_FAILED", "message": "не удалось проверить пропуск, попробуйте позже" }
  ```
- **Ошибки:** `422` `BADGE_BLOCKED` «пропуск заблокирован», `BADGE_EXPIRED` «пропуск истёк», `BADGE_MISSING` «пропуск не найден»; `503` `BADGE_CHECK_FAILED`. Прежний отказ, когда мест нет, — без изменений 🟡. Выбор причины при нескольких недействующих пропусках — ⚠️ см. открытый пункт 9. Формат тела прежних ошибок надо привести к одному виду с новыми — 🟡 открытый пункт 4.
- **Состояния UI по ответу:** успех → запись подтверждена; `BADGE_*` → текст `message` на экране карточки рейса, кнопка «Записаться» остаётся; `BADGE_CHECK_FAILED` → «не удалось проверить пропуск, попробуйте позже», повтор нажатием той же кнопки; место не потеряно.
- **Авторизация:** вызывает сотрудник с ролью `EMPLOYEE` (БТ); проверяется в `shuttle-api`; без роли — отказ как прежде 🟡.
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1

### Каталог ошибок (сводно, строки INT-1)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| `422` `BADGE_BLOCKED` | «пропуск заблокирован» | пропуск сотрудника заблокирован | `bookingRefusedBadge` |
| `422` `BADGE_EXPIRED` | «пропуск истёк» | пропуск истёк | `bookingRefusedBadge` |
| `422` `BADGE_MISSING` | «пропуск не найден» | у сотрудника нет пропуска | `bookingRefusedBadge` |
| `503` `BADGE_CHECK_FAILED` | «не удалось проверить пропуск, попробуйте позже» | служба пропусков не ответила | `bookingCheckFailed` |

Из INT-2 (ошибки): служба пропусков не ответила (таймаут, сеть, 5xx) — 🟢 решение: запись не проходит, `503` `BADGE_CHECK_FAILED` (INT-1). Значение таймаута — ⚠️ открытый пункт 7.

## Проверка в одиночку
Вход подготавливается подменой ответа INT-2 (его формат в спеке не зафиксирован — подмена по тому, что нужно от ответа):
- действующий пропуск → запись создана, место зарезервировано (ответ успеха — как прежде 🟡);
- пропуск заблокирован → `422` `{ "code": "BADGE_BLOCKED", "message": "пропуск заблокирован" }`, записи нет, `seatsLeft` не меняется;
- пропуск истёк → `422` `BADGE_EXPIRED` «пропуск истёк», записи нет, `seatsLeft` не меняется;
- у сотрудника нет пропуска → `422` `BADGE_MISSING` «пропуск не найден», записи нет, `seatsLeft` не меняется;
- служба пропусков не ответила (таймаут, сеть, 5xx) → `503` `{ "code": "BADGE_CHECK_FAILED", "message": "не удалось проверить пропуск, попробуйте позже" }`, записи нет, `seatsLeft` не меняется;
- без сессии/роли `EMPLOYEE` → отказ как прежде 🟡.

## Из спеки — только относящееся к этому этапу
- **Трассировка (§7):** FR-1 Запись только с активным пропуском — INT-1, INT-2. Дано: пропуск сотрудника действующий, когда он записывается на рейс, тогда запись проходит. Дано: пропуск заблокирован, когда записывается, тогда запись не проходит, сотрудник видит «пропуск заблокирован». Дано: служба пропусков не ответила, когда записывается, тогда запись не создаётся, `seatsLeft` не меняется, сотрудник видит «не удалось проверить пропуск, попробуйте позже».
- **Авторизация (§3.3):** новые вызовы INT-1, INT-3, INT-4 доступны роли `EMPLOYEE`, проверка в `shuttle-api`. Негативный случай: без сессии или роли — `401`/`403`. Других ролей нет (аналитик). (§4.4) Всё видит и делает сотрудник с ролью `EMPLOYEE`; других ролей нет.
- **Состояния UI (§4.3):**

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `bookingRefusedBadge` | `422` `BADGE_*` | текст `message`, кнопка «Записаться» доступна |
| `bookingCheckFailed` | `503` `BADGE_CHECK_FAILED` | «не удалось проверить пропуск, попробуйте позже», повтор той же кнопкой |

- **НФТ (§5.1):** проверка пропуска — синхронно, внутри записи, без кэша, при каждой записи. Нагрузка: около 1 500 сотрудников, до 300 записей в день, пик 7:00–9:00. Таймауты вызовов — ⚠️ открытый пункт 7. **(§5.2):** служба пропусков не ответила: запись не проходит, `503` `BADGE_CHECK_FAILED`; запись не создаётся, место не резервируется, число свободных мест прежнее.
- **Совместимость (§6.2):** новые коды `422`/`503` при записи до выката фронта придут прежнему фронту; как он покажет неизвестную ошибку — 🟡 к валидации (открытый пункт 4).
- **Открытые пункты спеки, попавшие в этап:** 1, 4, 5, 7, 9 (🟡/⚠️ — контракт `badge-service`, формат прежних ошибок, авторизация, таймаут, выбор причины отказа).

## Чего этот этап НЕ делает
Не трогает поле `bikeRack` в карточке рейса и сущность `Trip` (этап 03). Не делает ручку офиса сотрудника и сортировку списка рейсов (этап 02). Контракт `badge-service` не проектирует — он вход извне.
