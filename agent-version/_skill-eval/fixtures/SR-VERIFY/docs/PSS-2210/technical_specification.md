## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. Новый сервис `pass-api` хранит заявки на разовые пропуска и обслуживает их жизненный
цикл; `office-web` получает раздел «Пропуска» с формой подачи и списком заявок.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `pass-api` | новый сервис заявок | Внутренний портал | 🟢 |
| `office-web` | раздел «Пропуска» | Фронт | 🟢 |
| `staff-directory` | подразделение и руководитель сотрудника | Персонал | 🟡 подтв. аналитиком |
| `notify-gw` | доставка уведомлений | Платформа | 🟡 подтв. аналитиком |

### 1.3. Связь с бизнес-требованиями
`docs/PSS-2210/business_requirements.md` — FR-1, FR-2, FR-3, FR-4.

## 2. Взаимодействия (ядро)

### INT-1. Подача заявки — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** сотрудник отправляет форму подачи заявки
- **Контракт (запрос):** `POST /v1/passes`, тело — `visitorName: string`,
  `documentNumber: string`, `visitDate: date`, `purpose: string`. Все поля обязательны.
- **Контракт (ответ):** `id: uuid`, `status: enum` — на подаче всегда `submitted`,
  `visitDate: date`, `createdAt: iso8601`
- **Пример ответа (успех):**
  ```json
  {
    "id": "b4f1c2ea-1d77-4a3e-9f0b-2c5d8e6a1104",
    "status": "submitted",
    "visitDate": "2026-09-03",
    "createdAt": "2026-08-17T09:12:44Z"
  }
  ```
- **Ошибки:** `422` — данные заявки не прошли проверку; `503` — справочник персонала недоступен
- **Состояния UI по ответу:** успех — `value` со списком заявок; `422` — `error_validation`;
  `503` — `error_source`
- **Авторизация:** аутентифицированный сотрудник
- **Происхождение:** 🟢
- **Трассировка:** FR-1

### INT-2. Список заявок — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** открытие раздела «Пропуска»
- **Контракт (запрос):** `GET /v1/passes`, параметр `scope: mine|to_approve` обязателен
- **Контракт (ответ):** `items: массив`, элемент — `id: uuid`, `visitorName: string`,
  `visitDate: date`, `status: submitted|approved|rejected|withdrawn`,
  `decidedAt: iso8601|null` — `null` у заявки в статусе `submitted`,
  `comment: string|null` — `null`, если решение принято без комментария
- **Пример ответа (успех):**
  ```json
  {
    "items": [
      {
        "id": "b4f1c2ea-1d77-4a3e-9f0b-2c5d8e6a1104",
        "visitorName": "Соколова Марина Игоревна",
        "visitDate": "2026-09-03",
        "status": "submitted",
        "decidedAt": null,
        "comment": null
      }
    ]
  }
  ```
- **Ошибки:** `400` — `scope` не передан или не из перечня; `503` — справочник персонала недоступен
- **Состояния UI по ответу:** непустой `items` — `value`; пустой `items` при `scope=mine` — `zero`;
  пустой при `scope=to_approve` — `empty`; `503` — `error_source`
- **Авторизация:** аутентифицированный сотрудник
- **Происхождение:** 🟢
- **Трассировка:** FR-2, FR-3

### INT-3. Решение по заявке — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** согласующий нажимает «Согласовать» или «Отклонить» в строке списка
- **Контракт (запрос):** `POST /v1/passes/{id}/decision`, тело — `decision: approve|reject`,
  `comment: string|null`
- **Контракт (ответ):** `id: uuid`, `status: approved|rejected`, `decidedAt: iso8601`,
  `comment: string|null`
- **Пример ответа (успех):**
  ```json
  {
    "id": "b4f1c2ea-1d77-4a3e-9f0b-2c5d8e6a1104",
    "status": "approved",
    "decidedAt": "2026-08-17T11:40:02Z",
    "comment": null
  }
  ```
- **Ошибки:** `403` — заявка не относится к подразделению вызывающего; `422` — `decision` не из
  перечня
- **Состояния UI по ответу:** успех — строка списка перерисовывается с новым статусом;
  `403` — `error_forbidden`
- **Авторизация:** аутентифицированный сотрудник
- **Происхождение:** 🟢
- **Трассировка:** FR-2

### INT-4. Отзыв заявки — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** заявитель нажимает «Отозвать» у своей заявки
- **Контракт (запрос):** `POST /v1/passes/{id}/withdraw`, тела нет
- **Контракт (ответ):** `id: uuid`, `status: withdrawn`, `withdrawnAt: iso8601`
- **Пример ответа (успех):**
  ```json
  {
    "id": "b4f1c2ea-1d77-4a3e-9f0b-2c5d8e6a1104",
    "status": "withdrawn",
    "withdrawnAt": "2026-08-17T10:05:19Z"
  }
  ```
- **Ошибки:** `403` — заявка принадлежит другому сотруднику
- **Состояния UI по ответу:** успех — строка перерисовывается со статусом «отозвана»;
  `403` — `error_forbidden`
- **Авторизация:** аутентифицированный сотрудник
- **Происхождение:** 🟢
- **Трассировка:** FR-3

### INT-5. Решение по нескольким заявкам сразу — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** согласующий отмечает несколько строк списка галочками и нажимает «Согласовать
  выбранные» либо «Отклонить выбранные»
- **Контракт (запрос):** `POST /v1/passes/decisions`, тело — `ids: массив uuid` (от 1 до 50),
  `decision: approve|reject`, `comment: string|null`
- **Контракт (ответ):** `results: массив`, элемент — `id: uuid`, `status: approved|rejected`,
  `decidedAt: iso8601`
- **Пример ответа (успех):**
  ```json
  {
    "results": [
      { "id": "b4f1c2ea-1d77-4a3e-9f0b-2c5d8e6a1104", "status": "approved", "decidedAt": "2026-08-17T11:40:02Z" },
      { "id": "3d90aa17-6c2b-4f11-9a55-0e7b12cc4480", "status": "approved", "decidedAt": "2026-08-17T11:40:02Z" }
    ]
  }
  ```
- **Ошибки:** `403` — среди выбранных есть заявка чужого подразделения; `422` — `ids` пуст или
  длиннее 50
- **Состояния UI по ответу:** успех — список перезапрашивается; `403` — `error_forbidden`
- **Авторизация:** аутентифицированный сотрудник
- **Происхождение:** 🟢
- **Трассировка:** FR-2

### INT-6. Подразделение и руководитель сотрудника — 🟡
- **Граница/направление:** Сервис `pass-api` → Сервис `staff-directory`
- **Триггер:** подача заявки и построение списка на согласование
- **Контракт (запрос):** запрос сведений о сотруднике по его идентификатору
- **Контракт (ответ):** подразделение сотрудника и идентификатор его руководителя
- **Ошибки:** обрабатываются как недоступность источника
- **Авторизация:** сервисная учётная запись `pass-api`, выдаётся командой персонала
- **Происхождение:** 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Трассировка:** FR-2

### INT-7. Уведомление согласующему — 🟡
- **Граница/направление:** Сервис `pass-api` → Сервис `notify-gw`
- **Триггер:** подача заявки
- **Контракт (запрос):** адресат, шаблон письма и ссылка на заявку в портале
- **Контракт (ответ):** подтверждение приёма уведомления к отправке
- **Ошибки:** обрабатываются как недоступность канала
- **Авторизация:** сервисная учётная запись `pass-api` в шлюзе уведомлений
- **Происхождение:** 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Трассировка:** FR-4

## 3. Backend — ответственность

### 3.1. По сервисам
`pass-api` принимает заявку, определяет подразделение и руководителя заявителя через справочник
персонала, создаёт заявку в статусе `submitted` и отправляет уведомление согласующему через шлюз
уведомлений. Он же обслуживает список заявок, решение согласующего и отзыв заявителем.

### 3.2. Данные и хранение
Новая сущность `VisitorPass`:

| Поле | Тип | Обязательность | Примечание |
|------|-----|----------------|------------|
| `id` | uuid | да | первичный ключ, генерируется сервисом |
| `requesterId` | string | да | идентификатор сотрудника-заявителя |
| `departmentId` | string | да | подразделение заявителя на момент подачи |
| `visitorName` | string | да | |
| `documentNumber` | string | да | |
| `visitDate` | date | да | |
| `purpose` | string | да | |
| `status` | enum | да | `submitted`, `approved`, `rejected`, `withdrawn` |
| `decidedBy` | string | нет | `null`, пока решение не принято |
| `decidedAt` | timestamp | нет | `null`, пока решение не принято |
| `comment` | string | нет | `null`, если решение принято без комментария |
| `createdAt` | timestamp | да | |

Индексы: по `requesterId, createdAt` — список «мои заявки»; по `departmentId, status` — список на
согласование. Миграция создаёт одну новую таблицу, существующих данных не затрагивает.

Переходы статуса: `submitted` → `approved`, `submitted` → `rejected`, `submitted` → `withdrawn`.
Из `approved`, `rejected` и `withdrawn` переходов нет — это конечные статусы.

Происхождение: 🟢

### 3.3. Авторизация/доступ на бэке
Все эндпоинты требуют аутентификации сотрудника. Список `scope=mine` отдаёт только заявки
вызывающего. Список `scope=to_approve` фильтруется по подразделению вызывающего. Отзыв доступен
только заявителю: чужая заявка даёт `403`.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Новый раздел «Пропуска» (`/passes`): форма подачи и список заявок с переключателем «мои» /
«на согласование».

### 4.2. Пользовательские сценарии
Сотрудник заполняет форму: ФИО посетителя, номер документа, дата визита, цель визита. На экране
проверяется, что все поля заполнены и что дата визита не раньше сегодняшнего дня; после отправки
заявка появляется в списке «мои» со статусом «на согласовании». Согласующий переключается на
«на согласование», видит заявки своего подразделения и в строке нажимает «Согласовать» или
«Отклонить», при отклонении вводит комментарий. Заявок за день набирается несколько десятков,
поэтому строки можно отметить галочками и решить их одним действием — «Согласовать выбранные». Заявитель у своей заявки в статусе «на
согласовании» видит кнопку «Отозвать».

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | запрос списка в процессе | скелетон строк списка |
| `value` | `items` непустой | список заявок |
| `zero` | `items` пуст при `scope=mine` | «вы ещё не подавали заявок», кнопка подачи |
| `empty` | `items` пуст при `scope=to_approve` | «заявок на согласование нет» |
| `error_source` | ответ `400` или `503` | «список недоступен, попробуйте позже» |
| `error_forbidden` | ответ `403` | «у вас нет прав на это действие» |
| `error_validation` | ответ `422` | форма остаётся открытой, показывается сообщение об ошибке |

### 4.3.1. Loading и таймауты
Раздел отрисовывается сразу, список догружается отдельно. Таймаут запроса списка — 5 секунд, по
истечении переходим в `error_source`.

### 4.4. Доступ по ролям в UI
Кнопки «Согласовать» и «Отклонить» видны только сотрудникам с ролью `Согласующий`; остальным
переключатель «на согласование» не показывается. Кнопка «Отозвать» видна заявителю у собственной
заявки в статусе «на согласовании».

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
Все запросы синхронные. Кэширования нет: статус заявки должен быть актуальным на момент открытия
списка. Ожидаемый объём — до 250 заявок в месяц на подразделение.

### 5.2. Надёжность/деградация
Справочник персонала недоступен — подача заявки отклоняется с `503`, потому что без подразделения
заявку некому согласовывать. Шлюз уведомлений недоступен — заявка всё равно считается поданной,
уведомление теряется, и согласующий увидит заявку при следующем открытии списка.

### 5.3. Безопасность/доступ (сводно)
Номер документа посетителя — персональные данные: в журналы приложения не пишется и в
уведомлениях не передаётся. Сервисные учётные записи хранятся в секретах `pass-api`.

**Срок хранения персональных данных посетителя — шесть месяцев после даты визита**, так требует
регламент службы безопасности. По истечении срока эти данные в системе не хранятся.

## 6. Релиз и интеграция

### 6.1. Порядок выката
Сначала `pass-api` с миграцией и эндпоинтами, затем `office-web` с разделом «Пропуска».

### 6.2. Обратная совместимость
Существующие разделы портала не меняются, ничего не удаляется.

### 6.3. Фиче-флаги
Флаг `portal.passes` на фронте, по умолчанию выключен, включается после проверки на одном
подразделении.

### 6.4. План отката
Выключить флаг `portal.passes` — раздел исчезает из портала. Таблица `VisitorPass` при этом
остаётся: удалять её откатом нельзя, в ней уже поданные заявки.

### 6.5. Преднастройка до релиза
- Сервисная учётная запись `pass-api` в справочнике персонала — запросить у команды персонала.
- Сервисная учётная запись `pass-api` в шлюзе уведомлений — запросить у платформы.
- Шаблон письма уведомления — согласовать со службой безопасности.

| FR | Взаимодействие | Тест-кейс (Дано–Когда–Тогда) |
|----|----------------|------------------------------|
| FR-1 | INT-1 | Дано: форма заполнена. Когда: сотрудник отправляет её. Тогда: ответ содержит `status: submitted`, заявка видна в списке `scope=mine` |
