## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** На портале шаттла запись на рейс проходит только при действующем пропуске сотрудника: бэк `shuttle-api` проверяет его в службе пропусков `badge-service` при каждой записи. В карточке рейса появляется отметка «можно с велосипедом» по новому полю `bikeRack`. В списке рейсов первыми идут рейсы от офиса сотрудника: офис бэк берёт в справочнике сотрудников `org-directory`, сортирует фронт `shuttle-web`.
**Тип:** доработка
**Стороны:** Fullstack — три изменения на границах `shuttle-web` ↔ `shuttle-api`, `shuttle-api` → `badge-service`, `shuttle-api` → `org-directory`; клиент один — веб.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `shuttle-api` | изменение: проверка пропуска при записи, поле `bikeRack`, отдача офиса сотрудника; потребитель двух чужих сервисов | команда «Шаттл» | 🔵 подтв. аналитиком (со слов: наш сервис) |
| `shuttle-web` | изменение: отметка про велосипед, сортировка списка, тексты отказа записи | команда «Шаттл» | 🔵 подтв. аналитиком (со слов: наш сервис) |
| `badge-service` | потребление: состояние пропуска сотрудника | команда «Безопасность зданий» | 🟡 к валидации (контракт), владелец 🔵 со слов |
| `org-directory` | потребление: офис сотрудника | команда «Кадровые системы» | 🟡 к валидации (контракт), владелец 🔵 со слов |
### 1.3. Связь с бизнес-требованиями
Места на шаттле не занимают люди с заблокированным пропуском; сотрудник заранее видит, возьмут ли велосипед, и находит рейсы от своего офиса без ручного поиска.

## 2. Взаимодействия (ядро)

### INT-1. Запись на рейс с проверкой пропуска — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** FE (`shuttle-web`) → BE (`shuttle-api`)
- **Триггер:** сотрудник нажимает «Записаться» на рейс
- **Существующий стык:** 🟡 к валидации — существующая ручка записи на рейс в `shuttle-api`; путь, прежние ответ и формат ошибок аналитиком не подтверждены.
- **Изменение:**

| поле | где | было | стало |
|------|-----|------|-------|
| проверка пропуска сотрудника | поведение ручки записи | — | перед созданием записи бэк проверяет пропуск через INT-2; действующего пропуска нет — запись не создаётся |
| ответ `422` с `code` `BADGE_BLOCKED` / `BADGE_EXPIRED` / `BADGE_MISSING` | ответ ручки | — | новые ошибки: пропуск заблокирован / истёк / не найден |
| ответ `503` с `code` `BADGE_CHECK_FAILED` | ответ ручки | — | новая ошибка: служба пропусков не ответила |

- **Контракт (запрос):** прежний — без изменений 🟡 (тело и путь — к валидации); логин сотрудника бэк берёт из сессии, в запрос он не добавляется.
- **Контракт (ответ):** успех — как прежде 🟡. Ошибки новые, тело: `code: string` (enum ниже), `message: string` (текст для показа сотруднику).
  Порядок на бэке: 1) проверка пропуска; 2) только при успехе — резервирование места и создание записи. Отказ по пропуску или сбой проверки не меняет число свободных мест и не создаёт записи.
- **Пример запроса:** тело — как прежде 🟡; параметры и заголовки добавляются только прежние.
- **Пример ответа (успех):** как прежде 🟡; фрагмент не приводится.
- **Пример ответа (ошибка, пропуск заблокирован):**
  ```json
  { "code": "BADGE_BLOCKED", "message": "пропуск заблокирован" }
  ```
- **Пример ответа (ошибка, служба пропусков не ответила):**
  ```json
  { "code": "BADGE_CHECK_FAILED", "message": "не удалось проверить пропуск, попробуйте позже" }
  ```
- **Ошибки:** `422` `BADGE_BLOCKED` «пропуск заблокирован», `BADGE_EXPIRED` «пропуск истёк», `BADGE_MISSING` «пропуск не найден»; `503` `BADGE_CHECK_FAILED`. Прежний отказ, когда мест нет, — без изменений 🟡. Выбор причины при нескольких недействующих пропусках — ⚠️ см. открытый пункт 9. Формат тела прежних ошибок надо привести к одному виду с новыми — 🟡 открытый пункт 4.
- **Состояния UI по ответу:** успех → запись подтверждена; `BADGE_*` → текст `message` на экране карточки рейса, кнопка «Записаться» остаётся; `BADGE_CHECK_FAILED` → «не удалось проверить пропуск, попробуйте позже», повтор нажатием той же кнопки; место не потеряно.
- **Авторизация:** вызывает сотрудник с ролью `EMPLOYEE` (БТ); проверяется в `shuttle-api`; без роли — отказ как прежде 🟡.
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-1

### INT-2. Проверка пропуска сотрудника в службе пропусков — 🟡
- **Вид:** потребление существующего
- **Граница/направление:** BE `shuttle-api` → `badge-service` (команда «Безопасность зданий»)
- **Триггер:** каждая запись на рейс (INT-1), сразу, без кэша
- **Контракт:** 🟡 к валидации — вызов `badge-service`, возвращающий пропуска сотрудника по его логину, и состояния пропуска. Путь, поля и значения состояний аналитиком не подтверждены, в спеку не вносятся. Что нужно от ответа: понять, есть ли у сотрудника действующий пропуск, а если нет — заблокирован он или истёк.
- **Ошибки:** служба пропусков не ответила (таймаут, сеть, 5xx) — 🟢 решение: запись не проходит, `503` `BADGE_CHECK_FAILED` (INT-1). Значение таймаута — ⚠️ открытый пункт 7.
- **Авторизация:** 🟡 к валидации — способ авторизации `shuttle-api` в `badge-service`; доступ заводится заявкой до релиза (§6.5).
- **Происхождение:** 🟡 к валидации
- **Трассировка:** FR-1

### INT-3. Поле «место для велосипеда» в карточке рейса — 🟢
- **Вид:** изменение существующего
- **Граница/направление:** BE `shuttle-api` → FE `shuttle-web`
- **Триггер:** сотрудник открывает карточку рейса
- **Существующий стык:** 🟡 к валидации — существующая ручка карточки рейса в `shuttle-api`; путь и прежний состав ответа аналитиком не проверены.
- **Изменение:**

| поле | где | было | стало |
|------|-----|------|-------|
| `bikeRack` | ответ карточки рейса | — | добавлено: `boolean`, обязательное, не `null`; `true` — в шаттле есть место для велосипеда, `false` — нет |

- **Контракт (запрос):** прежний, без изменений 🟡.
- **Контракт (ответ):** прежние поля — без изменений 🟡; добавлено `bikeRack: boolean`.
- **Пример запроса:** прежний 🟡.
- **Пример ответа (успех):** фрагмент: прочие поля — без изменений
  ```json
  { "bikeRack": true }
  ```
- **Ошибки:** новых нет.
- **Состояния UI по ответу:** `true` → отметка «можно с велосипедом»; `false` → отметки нет.
- **Авторизация:** как у карточки рейса — роль `EMPLOYEE`, без изменений.
- **Происхождение:** 🟢 изменение существующего
- **Трассировка:** FR-2

### INT-4. Офис сотрудника для списка рейсов — 🟢
- **Вид:** новое
- **Граница/направление:** FE (`shuttle-web`) → BE (`shuttle-api`)
- **Триггер:** сотрудник открывает список рейсов; бэк при этом берёт офис в справочнике (INT-5). Отдельная ручка, чтобы не менять форму ответа списка рейсов, который в спеке подтверждён только в части `officeCode` (INT-6).
- **Контракт (запрос):** `GET /v1/employee/office`; параметров и тела нет, сотрудник определяется по сессии.
- **Контракт (ответ):** `officeCode: string | null` — код офиса сотрудника; `null` — офис получить не удалось (справочник не ответил). Ответ всегда `200`.
- **Пример запроса:** `GET /v1/employee/office`, тело отсутствует.
- **Пример ответа (успех):**
  ```json
  { "officeCode": "NORTH" }
  ```
- **Пример ответа (справочник не ответил):**
  ```json
  { "officeCode": null }
  ```
- **Ошибки:** сбой справочника ошибкой не отдаётся — `officeCode: null`. Без сессии/роли — `401`/`403`.
- **Состояния UI по ответу:** значение → список сортируется (INT-6); `null` или сбой самого запроса → список идёт общим порядком, без сообщения об ошибке.
- **Авторизация:** роль `EMPLOYEE`; проверяется в `shuttle-api`.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### INT-5. Офис сотрудника в справочнике сотрудников — 🟡
- **Вид:** потребление существующего
- **Граница/направление:** BE `shuttle-api` → `org-directory` (команда «Кадровые системы»)
- **Триггер:** сотрудник открывает список рейсов (INT-4); без кэша, вызов при каждом открытии
- **Контракт:** 🟡 к валидации — вызов `org-directory`, возвращающий офис сотрудника по его логину. Аналитик знает только, что офис сотрудника в справочнике есть; вызов и состав ответа неизвестны, в спеку не вносятся. Допущение аналитика: значение офиса совпадает по виду с `officeCode` рейса — 🟡.
- **Ошибки:** справочник не ответил — 🟢 решение: INT-4 отдаёт `officeCode: null`, ошибки нет. Значение таймаута — ⚠️ открытый пункт 8.
- **Авторизация:** 🟡 к валидации — способ авторизации `shuttle-api` в `org-directory`; доступ заводится заявкой до релиза (§6.5).
- **Происхождение:** 🟡 к валидации
- **Трассировка:** FR-3

### INT-6. Список рейсов: сортировка по офису на фронте — 🔵
- **Вид:** потребление существующего
- **Граница/направление:** BE `shuttle-api` → FE `shuttle-web`
- **Триггер:** сотрудник открывает список рейсов
- **Контракт:** `GET /v1/trips` отдаёт у каждого рейса `officeCode` — 🔵 подтверждено аналитиком (со слов; валидировать при интеграции). Прочий состав ответа не используется и не меняется. При `officeCode: null` в INT-4 порядок остаётся прежним.
- **Ошибки:** новых нет.
- **Происхождение:** 🔵 подтверждено аналитиком (со слов; валидировать при интеграции)

## 3. Backend — ответственность
### 3.1. По сервисам
- `shuttle-api` (🟢): реализует INT-1 (проверка пропуска перед созданием записи), INT-3 (поле `bikeRack`), INT-4 (офис сотрудника из справочника); потребляет `badge-service` (INT-2, 🟡) и `org-directory` (INT-5, 🟡). Проверка пропуска — при каждой записи, без кэша; сбой проверки → запись не создаётся, места не меняются.
- `badge-service`, `org-directory`: изменений с нашей стороны не требуется; работы только у владельцев по заявке на доступ.
### 3.2. Данные и хранение
- 🟢 `Trip` (рейс, изменение существующей сущности) — добавляется `bikeRack: boolean`, не `null`, по умолчанию `false`.
- Новых сущностей нет. Миграция нужна: добавить поле `bikeRack` рейсу; в уже лежащих строках — `false` (у остальных рейсов места для велосипеда нет). Точный DDL финализирует владеющий сервис.
- Разметка рейсов с местом для велосипеда: транспортная служба один раз выставляет `true` скриптом при выкате, дальше — через поддержку; экрана для этого нет. Пересчёт остальных данных не нужен.
### 3.3. Авторизация/доступ на бэке
Новые вызовы INT-1, INT-3, INT-4 доступны роли `EMPLOYEE`, проверка в `shuttle-api`. Негативный случай: без сессии или роли — `401`/`403`. Других ролей нет (аналитик).

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
`shuttle-web`: список рейсов `/trips` — сортировка по офису (INT-4, INT-6); карточка рейса `/trips/:tripId` — отметка «можно с велосипедом» (INT-3), сообщения отказа записи (INT-1).
### 4.2. Пользовательские сценарии
- Запись: «Записаться» → пропуск действующий → запись подтверждена (FR-1); иначе сообщение из `message`, повтор возможен.
- Список: при открытии фронт запрашивает офис (INT-4), сортирует рейсы (FR-3); офис не получен — общий порядок.
- Карточка: `bikeRack: true` → отметка (FR-2).
### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `bikeRackYes` | карточка, `bikeRack = true` | «можно с велосипедом» |
| `bikeRackNo` | карточка, `bikeRack = false` | отметки нет |
| `tripsSortedByOffice` | список, `officeCode` из INT-4 не `null` | рейсы от офиса сотрудника первыми |
| `tripsDefaultOrder` | список, `officeCode = null` или запрос офиса не удался | общий порядок, без ошибки |
| `bookingRefusedBadge` | `422` `BADGE_*` | текст `message`, кнопка «Записаться» доступна |
| `bookingCheckFailed` | `503` `BADGE_CHECK_FAILED` | «не удалось проверить пропуск, попробуйте позже», повтор той же кнопкой |

### 4.3.1. Loading и таймауты (обязательно, если есть FE)
- Запрос офиса (INT-4) не блокирует показ списка: пока офис не пришёл, список в общем порядке, затем пересортировывается. Таймауты фронта: ⚠️ значения не названы (см. открытые пункты 7, 8 по бэку).
- Polling нет.
### 4.4. Доступ по ролям в UI
Всё видит и делает сотрудник с ролью `EMPLOYEE`; других ролей нет.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Проверка пропуска — синхронно, внутри записи, без кэша, при каждой записи. Офис сотрудника — синхронно, при каждом открытии списка, кэш не проектируется. Нагрузка: около 1 500 сотрудников, до 300 записей в день, пик 7:00–9:00. Таймауты вызовов — ⚠️ открытые пункты 7, 8.
### 5.2. Надёжность/деградация
- Служба пропусков не ответила: запись не проходит, `503` `BADGE_CHECK_FAILED`; запись не создаётся, место не резервируется, число свободных мест прежнее.
- Справочник не ответил: список идёт общим порядком, ошибка не показывается.
### 5.3. Безопасность/доступ (сводно)

### 6.4. План отката (обязательно, если задача деплоится — иначе «не применимо: причина»)
- **Откат только BE** (FE на новой версии): запрос офиса (INT-4) не находится — фронт показывает общий порядок; поле `bikeRack` отсутствует — отметки нет; записи идут без проверки пропуска. Допустимо.

- **Откат DDL**: поле `bikeRack` убирается; потеряется только разметка велосипедных мест, её можно выставить скриптом заново.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 Запись только с активным пропуском | INT-1, INT-2 | Дано: пропуск сотрудника действующий, когда он записывается на рейс, тогда запись проходит.
