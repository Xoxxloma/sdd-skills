# ID-CHAIN — граница-цепочка (interaction-diagram 4.3)

Спека CHN-4 (запись к врачу и направление на анализы) написана руками, 5 карточек; короткая синтетика, по форме далека
от реальной спеки. Проверяет границу из нескольких звеньев в одной карточке, вопрос о цепочке и что без ответа
делается с цепочкой со знаком в скобках и без него.

| Карточка | Граница | По ответу (`chain-q-mmd`) | Без ответа (`chain-q-idk`) |
|---|---|---|---|
| INT-1 | `clinic-web` → `booking-api` | одна стрелка, `INT-1 · GET /v1/doctors/{id}/slots` | так же |
| INT-2 | `clinic-web` → `booking-api` → `schedule-service`, оба метода в одной строке контракта | две стрелки подряд: `POST /v1/appointments`, `POST /internal/slots/{slotId}/hold` | так же: знака в скобках нет — звенья и методы как прочитаны |
| INT-3 | четыре знака, один в скобках (`gateway` → `records`); скобка после `clinic-core` закрыта только в конце строки; методы — подпунктами контракта | три стрелки: clinic-web → clinic-core `POST /v1/lab-orders`, clinic-core → lab-service `POST /internal/orders`, lab-service → LabNet `INT-3`; `gateway`, `records` не участники | знак в скобках — карточки на схеме нет: ни стрелок, ни clinic-core, lab-service, LabNet; номер в отчёте «без стрелки» |
| INT-4 | `событие: booking-api → notify (через брокер)` | асинхронная, `INT-4 · appointment.created` | так же |
| INT-5 | `clinic-web` ↔ `booking-api` (WebSocket) | одна двусторонняя, подпись `INT-5` | так же |

Граница INT-3 по скобкам читается двояко, поэтому истина для неё задана в грейдере (`TRUTH` в `grade-id.mjs`), а не
выводится из текста. LabNet в таблице сервисов нет — он назван строкой под ней; скилл с 4.0 таблицу не читает, LabNet
для него просто сторона INT-3. Вопросы хода 2: участники, порядок, цепочки INT-2 и INT-3 (у обеих два и больше знаков).
