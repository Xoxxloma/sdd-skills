## 1. Обзор изменения

### 1.1. Что делаем и тип изменения

**Суть:** Пациент в кабинете выбирает слот и записывается к врачу; врач из кабинета оформляет направление на анализы, направление уходит во внешнюю лабораторию.

**Тип:** новый функционал

**Стороны:** Fullstack

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `clinic-web` | Фронт кабинета: слоты, запись, направления | Команда кабинета | 🟢 |
| `booking-api` | Бэк записи: приём заявок на приём | Команда записи | 🟢 |
| `schedule-service` | Расписание врачей, удержание слотов | Команда расписания | 🟡 подтверждено аналитиком |
| `clinic-core` | Монолит медкарты: модули `gateway` и `records` | Команда медкарты | 🟡 подтверждено аналитиком |
| `lab-service` | Направления на анализы, обмен с лабораторией | Команда лаборатории | 🟡 подтверждено аналитиком |
| `notify` | Уведомления пациенту | Команда уведомлений | 🟡 подтверждено аналитиком |

*Внешняя лаборатория LabNet участвует в существующей цепочке направлений как есть.*

## 2. Взаимодействия (ядро)

### INT-1. Свободные слоты врача — 🟢
- **Граница/направление:** `clinic-web` → `booking-api`
- **Триггер:** пациент открыл карточку врача
- **Контракт (запрос):** `GET /v1/doctors/{id}/slots`
- **Контракт (ответ):** список слотов `{ slotId, startsAt }`
- **Происхождение:** 🟢 новое

### INT-2. Запись на приём — 🟢
- **Граница/направление:** `clinic-web` → `booking-api` → `schedule-service`
- **Триггер:** пациент выбрал слот и нажал «Записаться»
- **Контракт (запрос):** `POST /v1/appointments` от кабинета в `booking-api`; дальше `booking-api` удерживает слот вызовом `POST /internal/slots/{slotId}/hold` в `schedule-service`
- **Контракт (ответ):** `{ appointmentId, status: "booked" }`
- **Происхождение:** 🟢 новое

### INT-3. Направление на анализы — [🟡 подтверждено аналитиком / 🟢 новое]
- **Граница/направление:** `clinic-web` (кабинет врача) → `clinic-core` (медкарта (монолит: модули `gateway` → `records`, один процесс) → `lab-service` → LabNet).
- **Триггер:** врач нажал «Направить на анализы»
- **Контракт (существующий, 🟡 подтверждено аналитиком; валидировать при интеграции):**
  - **Вход со стороны кабинета:** `POST /v1/lab-orders` → `LabOrderController.create(...)` (модуль `gateway`).
  - **Внутренняя делегация (gateway → records):** сетевого контракта НЕТ — это модули одного монолита `clinic-core`, один процесс; прямой вызов сервиса.
  - **Вызов lab-service наружу (монолит → `lab-service`):** синхронный REST, `POST /internal/orders`, тело `{ patientId, tests[] }`, ответ `{ orderId }`.
- **Что меняется:** в тело направления добавляется список анализов `tests[]`.
- **Происхождение:** 🟡 подтверждено аналитиком — цепочка существующая; 🟢 новое — поле `tests[]`

### INT-4. Событие «запись создана» — 🟢
- **Граница/направление:** событие: `booking-api` → `notify` (через брокер)
- **Триггер:** запись успешно создана
- **Контракт (событие):** `appointment.created` — `appointmentId`, `patientId`, `startsAt`
- **Происхождение:** 🟢 новое

### INT-5. Живое обновление занятости слотов — 🟢
- **Граница/направление:** `clinic-web` ↔ `booking-api` (WebSocket)
- **Триггер:** открыта карточка врача
- **Контракт (запрос):** сообщения `{ slotId, busy }` в обе стороны по открытому соединению
- **Происхождение:** 🟢 новое
