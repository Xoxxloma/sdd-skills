## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** В портале заявок появляется новый вид заявки — заявка на доступ к корпоративной системе: сотрудник выбирает систему и пишет обоснование, владелец системы согласует или отклоняет её. После согласования портал сам заводит учётку в системе управления учётками, а владелец может отозвать выданный доступ — портал блокирует учётку. В справочнике систем портала у системы появляются владелец и код системы в системе управления учётками.
**Тип:** доработка
**Стороны:** Fullstack — новые экраны и действия во фронте портала, новые контракты в бэке портала, новая интеграция бэка портала с системой управления учётками.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Портал заявок (бэк и фронт) | новые заявки, действия владельца и сотрудника, расширение справочника систем | команда «Портал заявок» | 🟢 |
| Система управления учётками | потребляем: заведение учётки, блокировка, запрос состояния | команда «Управление доступом» | 🔵 подтверждено аналитиком (не по коду; валидировать при интеграции) |
### 1.3. Связь с бизнес-требованиями
Цель — чтобы у каждой учётки, выданной через портал, было зафиксировано согласование владельца, а команда «Управление доступом» не заводила учётки вручную и владелец отзывал доступ сам.

## 2. Взаимодействия (ядро)
> Общие правила форм — по `context/conventions.md`: путь `/v1/<сущности>`, действия `POST …/{id}/<глагол>`, ошибки `{ "error": { "code", "message" } }`, пагинация `page`/`size`, даты ISO 8601 UTC, enum строчными. Отступлений нет.

### INT-1. Список систем, на которые можно подать заявку — 🟢
- **Граница/направление:** FE → BE портала
- **Триггер:** сотрудник открывает форму подачи заявки на доступ
- **Контракт (запрос):** `GET /v1/access-systems`; параметров нет
- **Контракт (ответ):** `{ "items": [ { "id": string, "name": string } ] }`; только системы справочника, у которых есть код в системе управления учётками и указан владелец (FR-1); архивные не отдаются. Весь список одним ответом (около 40 систем). Пустой список — `[]`.
- **Пример запроса:** тело отсутствует
- **Пример ответа (успех):**
  ```json
  { "items": [ { "id": "7c1f0a52-3b0e-4d57-9a7e-1d2f5c8b9e01", "name": "Казначейство" } ] }
  ```
- **Ошибки:** см. каталог; `403 FORBIDDEN`
- **Состояния UI по ответу:** значение → выпадающий список систем; загрузка → спиннер; пусто → «Нет систем, доступных для заявки»; ошибка → сообщение + повтор
- **Авторизация:** любой авторизованный сотрудник; проверяется на бэке портала
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1

### INT-2. Подать заявку — 🟢
- **Граница/направление:** FE → BE портала
- **Триггер:** сотрудник нажимает «Подать заявку» на форме
- **Контракт (запрос):** `POST /v1/access-requests`; `systemId: string` (обяз.), `justification: string` (обяз., непустой, до 2000 символов)
- **Контракт (ответ):** `201`, объект заявки (см. INT-4): `id`, `status: "pending_approval"`, остальные необязательные поля `null`
- **Пример запроса:**
  ```json
  { "systemId": "7c1f0a52-3b0e-4d57-9a7e-1d2f5c8b9e01", "justification": "Нужен доступ для сверки платежей по проекту X" }
  ```
- **Пример ответа (успех):**
  ```json
  { "id": "b1d4e6f8-2a3c-4e5f-8a9b-0c1d2e3f4a5b", "systemId": "7c1f0a52-3b0e-4d57-9a7e-1d2f5c8b9e01", "systemName": "Казначейство", "applicantLogin": "kozlov", "justification": "Нужен доступ для сверки платежей по проекту X", "status": "pending_approval", "createdAt": "2026-10-13T09:15:00Z", "decidedByLogin": null, "decidedAt": null, "rejectReason": null, "accountLogin": null, "accountActive": null, "revokedByLogin": null, "revokedAt": null, "revokeComment": null }
  ```
- **Ошибки:** `400 VALIDATION_FAILED` (пустое обоснование, система не подключена или без владельца, архивная); `403 FORBIDDEN`
- **Состояния UI по ответу:** значение → переход к заявке; ошибка валидации → сообщения у полей; ошибка → сообщение + повтор
- **Авторизация:** сотрудник (`EMPLOYEE`); логин заявителя берётся из входа, не из тела запроса
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1

### INT-3. Списки заявок — 🟢
- **Граница/направление:** FE → BE портала
- **Триггер:** сотрудник открывает «Мои заявки»; владелец открывает «Заявки на мои системы»
- **Контракт (запрос):** `GET /v1/access-requests?scope=mine|owned&page=&size=`; `scope` обяз. `mine` — заявки текущего сотрудника; `owned` — заявки на системы, где текущий пользователь указан владельцем (по справочнику на момент запроса, поэтому после смены владельца заявки видит новый владелец)
- **Контракт (ответ):** `{ items, page, size, total }`; элемент: `id`, `systemName`, `applicantLogin`, `justificationPreview` (первые 120 символов обоснования), `status`, `createdAt`. Порядок для `owned`: «На согласовании» сверху, внутри и дальше — более ранние первыми; для `mine` — новые первыми. Состояние учётки в списке не отдаётся. Пустой список — `[]`.
- **Пример запроса:** `GET /v1/access-requests?scope=owned&page=1&size=20`
- **Пример ответа (успех):**
  ```json
  { "items": [ { "id": "b1d4e6f8-2a3c-4e5f-8a9b-0c1d2e3f4a5b", "systemName": "Казначейство", "applicantLogin": "kozlov", "justificationPreview": "Нужен доступ для сверки платежей по проекту X", "status": "pending_approval", "createdAt": "2026-10-13T09:15:00Z" } ], "page": 1, "size": 20, "total": 1 }
  ```
- **Ошибки:** `400 VALIDATION_FAILED` (неверный `scope`); `403 FORBIDDEN` (`owned` не владельцу ни одной системы)
- **Состояния UI по ответу:** значение → таблица; пусто → «Заявок нет»; загрузка → скелетон; ошибка → сообщение + повтор
- **Авторизация:** `mine` — любой сотрудник, только свои; `owned` — владелец системы. Проверка на бэке портала.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-2, FR-3

### INT-4. Просмотр заявки — 🟢 (с вызовом в систему управления учётками — 🔵)
- **Граница/направление:** FE → BE портала; BE портала → система управления учётками (запрос состояния учётки)
- **Триггер:** заявитель или владелец открывает заявку
- **Контракт (запрос):** `GET /v1/access-requests/{id}`
- **Контракт (ответ):** объект заявки: `id`, `systemId`, `systemName`, `applicantLogin`, `justification`, `status` (enum ниже), `createdAt`, `decidedByLogin`, `decidedAt`, `rejectReason`, `accountLogin`, `accountActive`, `revokedByLogin`, `revokedAt`, `revokeComment`.
  - `status`: `pending_approval` («На согласовании»), `withdrawn` («Отозвана»), `rejected` («Отклонена»), `approved` («Согласована» — ⚠️ название временное, решает ИБ; учётка ещё заводится), `access_granted` («Доступ выдан»), `access_revoked` («Доступ отозван»).
  - `null`: `decided*` — пока решения нет; `rejectReason` — не отклонена; `accountLogin` — учётка не заведена; `revoked*` — доступ не отзывали.
  - `accountActive`: `true`/`false` — учётка активна/неактивна (заблокирована или закрыта при увольнении); `null` — заявка не в статусе `access_granted` либо состояние узнать не удалось. Бэк запрашивает состояние при каждом открытии заявки в статусе `access_granted`; в списках не запрашивает.
  - Состояние учётки в ответе отличает «не удалось узнать» от «неактивна» через `accountActive: null` при `status: "access_granted"`.
- **Пример запроса:** тело отсутствует
- **Пример ответа (успех):**
  ```json
  { "id": "b1d4e6f8-2a3c-4e5f-8a9b-0c1d2e3f4a5b", "systemId": "7c1f0a52-3b0e-4d57-9a7e-1d2f5c8b9e01", "systemName": "Казначейство", "applicantLogin": "kozlov", "justification": "Нужен доступ для сверки платежей по проекту X", "status": "access_granted", "createdAt": "2026-10-13T09:15:00Z", "decidedByLogin": "smirnov", "decidedAt": "2026-10-13T10:02:00Z", "rejectReason": null, "accountLogin": "kozlov_t", "accountActive": true, "revokedByLogin": null, "revokedAt": null, "revokeComment": null }
  ```
- **Ошибки:** `404 NOT_FOUND` (нет заявки или она не видна пользователю); `403 FORBIDDEN`. Недоступность системы управления учётками ошибкой ответа не становится: ответ `200`, `accountActive: null`.
- **Состояния UI по ответу:** см. §4.3
- **Авторизация:** заявитель и владелец системы заявки; чужая заявка — `404`
- **Происхождение:** 🟢 новое; запрос состояния учётки — 🔵 подтверждено аналитиком (не по коду; валидировать при интеграции): портал запрашивает состояние при открытии заявки; не удалось узнать — заявка показывается с пометкой, «Отозвать доступ» скрыта
- **Трассировка:** FR-4

### INT-5. Решение владельца: согласовать или отклонить — 🟢 (с вызовом в систему управления учётками — 🔵/🟡)
- **Граница/направление:** FE → BE портала; фоновая задача BE портала → система управления учётками (заведение учётки)
- **Триггер:** владелец нажимает «Согласовать» или «Отклонить»
- **Контракт (запрос):** `POST /v1/access-requests/{id}/approve` — тела нет; `POST /v1/access-requests/{id}/reject` — `{ "reason": string }` (обяз., непустая, до 1000 символов)
- **Контракт (ответ):** `200`, объект заявки (INT-4). После `approve` статус `approved` и учётка ещё не заведена; после `reject` — `rejected`, `rejectReason` заполнена.
- **Пример запроса (`reject`):**
  ```json
  { "reason": "доступ нужен только сотрудникам казначейства" }
  ```
- **Пример ответа (успех):** объект заявки как в INT-4 со `status: "rejected"`, `decidedByLogin: "smirnov"`, `rejectReason` из запроса.
- **Поведение заведения (фон):**
  - 🔵 Решение владельца фиксируется сразу при согласовании; учётку в системе управления учётками заводит фоновая задача с повтором — паузы нарастающие, около суток (⚠️ график не задан), затем оповещение дежурному портала (⚠️ канал не назван), не в очередь «Управления доступом».
  - 🔵 Повторное заведение отвечает ошибкой `E_ACC_DUP` с идентификатором существующей учётки; портал берёт идентификатор из ответа и считает доступ выданным.
  - 🔵 Логин учётки берётся из ответа системы управления учётками и хранится в портале (у части систем он не совпадает с доменным).
  - 🟡 к валидации: что именно портал передаёт при заведении (идентифицирует сотрудника и систему) — в карточке сервиса есть вариант, аналитиком не подтверждён; путь и поля не пишутся.
  - Успех заведения → статус `access_granted`, `accountLogin` из ответа.
  - 🟢 Идемпотентность: задача берёт заявку в `approved` под блокировкой строки и переводит в `access_granted` одним условным обновлением; повтор и `E_ACC_DUP` дают тот же результат.
  - ❓ Заявка на систему, где учётка сотрудника заблокирована: портал выдать доступ не сможет; вариант решения не выбран — решает ИБ (открытый вопрос 2).
- **Ошибки:** `400 VALIDATION_FAILED` (нет причины при отклонении); `403 FORBIDDEN` (не владелец системы); `404 NOT_FOUND`; `409 REQUEST_STATE_CONFLICT` (заявка уже не «На согласовании» — отозвана заявителем или решение принято)
- **Состояния UI по ответу:** значение → заявка обновлена, кнопки решения скрыты; ошибка конфликта → «Заявка уже не ждёт решения», обновить; ошибка → сообщение + повтор
- **Авторизация:** владелец системы заявки (по справочнику на момент запроса); не владелец — `403`, чужая — `404`
- **Происхождение:** 🟢 новое; заведение учётки — 🔵 по перечисленным пунктам, остальное — 🟡
- **Трассировка:** FR-6

### INT-6. Отозвать заявку (сотрудник) — 🟢
- **Граница/направление:** FE → BE портала
- **Триггер:** сотрудник нажимает «Отозвать заявку»
- **Контракт (запрос):** `POST /v1/access-requests/{id}/withdraw` — тела нет
- **Контракт (ответ):** `200`, объект заявки (INT-4) со `status: "withdrawn"`. Переход условный: только из `pending_approval`.
- **Пример запроса:** тело отсутствует
- **Пример ответа (успех):** объект заявки как в INT-4 со `status: "withdrawn"`.
- **Ошибки:** `403 FORBIDDEN`; `404 NOT_FOUND`; `409 REQUEST_STATE_CONFLICT` (владелец уже принял решение)
- **Состояния UI по ответу:** значение → статус «Отозвана», кнопка скрыта; конфликт → «Решение уже принято», обновить; ошибка → сообщение + повтор
- **Авторизация:** только заявитель; проверяется на бэке портала
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-5

### INT-7. Отозвать выданный доступ (владелец) — 🟢 (с вызовом в систему управления учётками — 🔵)
- **Граница/направление:** FE → BE портала; BE портала → система управления учётками (блокировка учётки, при необходимости запрос состояния)
- **Триггер:** владелец нажимает «Отозвать доступ»
- **Контракт (запрос):** `POST /v1/access-requests/{id}/revoke`; `{ "comment": string | null }` (необяз., до 1000 символов)
- **Контракт (ответ):** `200`, объект заявки (INT-4) со `status: "access_revoked"`, `revokedByLogin`, `revokedAt`, `revokeComment`
- **Поведение (🔵):**
  - отзыв — синхронная блокировка; при ошибке владелец видит ошибку, статус заявки не меняется;
  - повторная блокировка отвечает ошибкой `E_ACC_STATE`: портал запрашивает состояние учётки; заблокирована → доступ отозван (`access_revoked`); закрыта при увольнении → статус не меняется, `accountActive: false`, ответ — `409 ACCOUNT_NOT_ACTIVE`;
  - разблокирует учётку только администратор системы управления учётками (портал не разблокирует).
- **Пример запроса:**
  ```json
  { "comment": "Сотрудник перешёл в другой отдел" }
  ```
- **Пример ответа (успех):** объект заявки как в INT-4 со `status: "access_revoked"`, `revokedByLogin: "smirnov"`, `revokeComment` из запроса.
- **Ошибки:** `403 FORBIDDEN`; `404 NOT_FOUND`; `409 REQUEST_STATE_CONFLICT` (заявка не в `access_granted`); `409 ACCOUNT_NOT_ACTIVE` (учётка закрыта при увольнении); `502 ACCOUNT_SERVICE_ERROR` (система управления учётками не ответила или отказала)
- **Состояния UI по ответу:** значение → «Доступ отозван» + кто и когда; `ACCOUNT_NOT_ACTIVE` → «Учётка неактивна», кнопка скрыта; `ACCOUNT_SERVICE_ERROR` → сообщение об ошибке, статус прежний, можно повторить
- **Авторизация:** владелец системы заявки
- **Происхождение:** 🟢 новое; блокировка и состояние — 🔵
- **Трассировка:** FR-7

| `403 FORBIDDEN` | «Нет доступа» | нет роли на операцию | `error_forbidden` |
| `404 NOT_FOUND` | «Заявка не найдена» | нет заявки или она не видна пользователю | «не найдена» |
| `409 REQUEST_STATE_CONFLICT` | «Статус заявки изменился» | действие недопустимо в текущем статусе (в том числе гонка отзыва и решения) | обновить заявку |
| `409 ACCOUNT_NOT_ACTIVE` | «Учётка неактивна» | отзыв доступа, когда учётка закрыта при увольнении | пометка «учётка неактивна», кнопка скрыта |
| `502 ACCOUNT_SERVICE_ERROR` | «Не удалось связаться с системой учётных записей» | блокировка не удалась | `error_source`, статус прежний |

## 3. Backend — ответственность
### 3.1. По сервисам
- **Бэк портала:** реализует INT-1…INT-7; хранит заявки; определяет владельца по справочнику; фоновая задача заведения учётки с повтором (INT-5); запрос состояния учётки при открытии заявки (INT-4); блокировка учётки при отзыве (INT-7). 🟢
- **Тест:** заглушка системы управления учётками по её контракту со сценариями ошибок `E_ACC_DUP` и `E_ACC_STATE`. 🔵 (решение встречи)
- **Система управления учётками** (команда «Управление доступом»): изменений с её стороны в задаче нет; портал — её клиент. 🔵 подтверждено аналитиком (не по коду; валидировать при интеграции):
  - лимит 20 запросов в секунду на клиента, сверх — ответ 429;
  - по понедельникам утром отвечает до 8–10 секунд;
  - сервисный токен для подключения выдаётся по заявке в очередь «Управления доступом», около двух недель, отдельно для теста и прома;
  - коды систем даёт «Управление доступом» из своей выгрузки;
  - тестовый стенд нестабилен;
  - уволенный сотрудник в портал не зайдёт, восстановленному заводят новый логин.
### 3.2. Данные и хранение
- 🟢 `AccessRequest` (новая) — `id` (UUID), `systemId` (ссылка на `System`), `applicantLogin` (string), `justification` (string), `status` (enum INT-4), `createdAt`, `decidedByLogin`, `decidedAt`, `rejectReason`, `accountId` (идентификатор учётки в системе управления учётками), `accountLogin`, `revokedByLogin`, `revokedAt`, `revokeComment`; повторные попытки заведения: `provisionAttempts` (int), `nextProvisionAt` (timestamp?). Индексы: `(applicantLogin, createdAt)`, `(systemId, status, createdAt)`. Заявки хранятся бессрочно, чтобы согласование оставалось видно аудиту.
- 🟢 `System` (существующая запись справочника портала, меняем мы) — добавляются `ownerLogin` (string?, `null` — владелец не указан) и `idmSystemCode` (string?, `null` — система не подключена; код есть — подключена; отдельного признака подключения нет, решение встречи).
- Миграции: да — новая таблица заявок и два необязательных поля у системы; точный DDL финализирует владеющий сервис. В уже лежащих записях справочника оба поля пустые (`null`) до разового заполнения владельцами и кодами перед запуском; пока пусто, системы в INT-1 не попадают.
- 🟢 Идемпотентность и гонки: все смены статуса — условные обновления (`WHERE status = <ожидаемый>`); конфликт даёт `409 REQUEST_STATE_CONFLICT`. Одновременные «Отозвать заявку» и «Согласовать» — выигрывает первый, второй получает конфликт.
### 3.3. Авторизация/доступ на бэке
- 🟢 Владелец определяется по `ownerLogin` в справочнике на момент запроса; отдельной роли в security-сервисе для него не заводится.
- Заявитель видит и отзывает только свои; владелец — заявки на свои системы; чужая заявка — `404`, нет права на операцию — `403` (по правилам оформления).
- Вызовы в систему управления учётками идут от имени портала с сервисным токеном; из ответов пользователю токен и внутренности `idm` не отдаются.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
- Форма подачи заявки (выбор системы из INT-1, обоснование) → INT-2.
- «Мои заявки» → INT-3 (`scope=mine`); «Заявки на мои системы» → INT-3 (`scope=owned`), в строке начало обоснования (`justificationPreview`).
- Экран заявки → INT-4; кнопки «Отозвать заявку» (INT-6), «Согласовать»/«Отклонить» (INT-5), «Отозвать доступ» (INT-7).
### 4.2. Пользовательские сценарии
- FR-1: сотрудник выбирает систему, пишет обоснование, подаёт; заявка «На согласовании».
- FR-2/FR-3: списки; заявки на согласовании у владельца сверху.
- FR-4: открытие заявки; для `access_granted` видны логин учётки и активность.
- FR-5: «Отозвать заявку» видна только в `pending_approval`.
- FR-6: «Согласовать»/«Отклонить» видны владельцу в `pending_approval`; при отклонении — причина. После согласования заявка в `approved`, затем `access_granted` (экран обновляется при открытии).
- FR-7: «Отозвать доступ» видна владельцу в `access_granted` при `accountActive === true`; при `false` — пометка «учётка неактивна», кнопки нет; при `null` — «не удалось узнать состояние учётки», кнопки нет.
### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос / после действия | спиннер/скелетон |
| `value` | 2xx, заявка получена | экран заявки по статусу |
| `empty` | 2xx, список `[]` | «Заявок нет» |
| `error_source` | 5xx / таймаут / сеть, `502 ACCOUNT_SERVICE_ERROR` | сообщение об ошибке + повтор |
| `error_forbidden` | 403 | «Нет доступа» |
| `error_not_found` | 404 | «Заявка не найдена» |
| `conflict` | `409 REQUEST_STATE_CONFLICT` | «Статус заявки изменился», обновить |
| `status_approved` | `status = approved` | «Согласована» (⚠️ название временное), «учётка заводится» |
| `account_active` | `access_granted`, `accountActive = true` | логин, «учётка активна», кнопка «Отозвать доступ» владельцу |

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- Подача, списки, отзыв заявки, решение — синхронно; заведение учётки — асинхронно (фоновая задача); блокировка при отзыве — синхронно (🔵).
- Состояние учётки — при каждом открытии заявки `access_granted`, без кэша; в списках не запрашивается (🔵).
- Нагрузка: порядка 300 заявок в месяц (по БТ); лимит `idm` 20 запросов в секунду на клиента (🔵), ответ 429 фоновая задача считает временной ошибкой и повторяет.
- Таймауты вызовов в `idm` — ❓ TBD (отложено аналитиком).
### 5.2. Надёжность/деградация
- Недоступность `idm` при согласовании: решение владельца уже записано, заявка в `approved`, фоновая задача повторяет с нарастающей паузой около суток (⚠️ график не задан), затем оповещение дежурному портала (⚠️ канал не назван).
- Недоступность при открытии заявки: `accountActive: null`, заявка показывается с пометкой, «Отозвать доступ» скрыта (🔵).
- Недоступность при отзыве: ошибка владельцу, статус не меняется (🔵).
- Блокировка в `idm` прошла, а запись статуса у нас не удалась: повторный «Отозвать доступ» получит `E_ACC_STATE`, портал запросит состояние, увидит блокировку и проставит `access_revoked` (🔵 по решению встречи).
### 5.3. Безопасность/доступ (сводно)

## 8. Допущения и открытые вопросы
- **🔵 Подтверждено аналитиком (не по коду):** решения встречи 2026-10-09 по `idm` (§2 INT-4, INT-5, INT-7; §3.1); аналитик подтвердил сведения команды «Управление доступом», записанные в файле встречи, — валидировать при интеграции.
- **🟡 К валидации:** данные, передаваемые при заведении учётки (открытый вопрос 7).
- **❓ Открытые решения:** повторная заявка на систему с заблокированной учёткой сотрудника (вопрос 2); таймауты вызовов в `idm` (вопрос 5); фиче-флаг (вопрос 6).
- **⚠️ Требует уточнения:** название промежуточного статуса (вопрос 1); график повторов (вопрос 3); канал оповещения дежурному (вопрос 4).
- **Технические риски:** гонка «отозвать заявку» / «согласовать» → условные обновления и `409`; сбой после блокировки, до записи статуса → повторный отзыв определяет блокировку по запросу состояния; повторный запуск фоновой задачи → идемпотентность через `E_ACC_DUP`.
- **Унаследовано из БТ (бизнес-пробелы):** Унаследованных бизнес-пробелов нет.
- **Приложения из БТ:** пожелание по UX — в списке заявок владельца показывать начало обоснования; учтено полем `justificationPreview` (INT-3).
- **Расхождения встречи с БТ:** между согласованием и выдачей доступа нужен промежуточный статус (в БТ его нет) — отражён в §2/§4.3, название — вопрос 1; повторная заявка при заблокированной учётке — вопрос 2. Не входит: подписка на событие увольнения сотрудника (неактивная учётка видна в заявке).
