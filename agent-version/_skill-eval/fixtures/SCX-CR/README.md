# Фикстура SCX-CR — маршрут мелкой правки, вход: `change-request-doc` после 5.74 (Р9)

Заведена 2026-10-26, ревью покрытия ветки `feat/blue-contract` (записи 5.74–5.81). `CR-SMALL` проверяет пример на
границе только в одну сторону: в `cr-lim-w` граница подтверждена, и запрос обязан её записать. Обратная сторона Р9 —
«аналитик подтвердил новое значение без границы → гейт закрыт» — и ход вопросов на правке без порога не проверялись.

**Дерево — копия `CR-SMALL`** (`services/{auth,geo,incident-web}.md`, `manifest.yaml`, ловушка `coddoc/ARS-102/`):
пробы сравнимы с `cr-lim-*` и `cr-btn-q`, отличаются только сообщением аналитика. Входы — сообщения аналитика, рукописи
нет.

Строки правил (`change-request-doc/SKILL.md` 1.3.0):
- `:339-344` — «Пример — форма гипотезы: закрытию гейта граница не нужна. Аналитик подтвердил „после“ без неё или дал
  своё — границу не переспрашивай»; «подтверждённый пример пишется в строку `FR-*`» — неподтверждённый не пишется;
- `:274-275` — `N = 0` → файл этим же ходом; `:170-171` — не выдумывать ответ, чтобы избавиться от ❓;
- `:339-341` — порог определён: «число, по одну сторону которого поведение одно, по другую другое»; правило касается
  только гипотезы «как должно стать» с новым порогом;
- `:149-151` — «поднять версию клиента… с 2 до 3» и «добавить в ответ ручки списка два поля» — правка; `:58` — ключ дан,
  не переспрашивать.

Грейдер — `grade-scx-cr.mjs --case=nob|own|api|ver`, самопроверка `--selftest` (ручные ответы). Детектор вопроса о
границе проверен на живых ответах: `cr-lim-q` (раунды `p2-base2`, `p2-r2`, `p2-s2`) — 8 из 8 гипотез с границей
пойманы («25 фото принимается, 26-е отклоняется. Верно?»); `cr-btn-q` (`2026-09-14-cr-pilot`) — 0 ложных из 2.
На тех же `cr-lim-w` грейдер плеча `nob` даёт «26 в файле» 3 из 3 — так и должно быть: там граница подтверждена.
`scx-cr-ver-q` (2026-10-26): «`minutes` (верхняя граница времени в пути)… Верно?» и «`minutes` как верхняя граница… Верно?» —
не вопрос о границе; после сужения детектора `cr-lim-q` по-прежнему 8 из 8, `cr-btn-q` 0 из 2.

**Справка у `nob` — пункт о границе в «Открытых вопросах»** (в зелёное не входит; решение владельца 2026-10-26).
Аналитик ответил про поведение сверх лимита «не проверял и подтвердить не могу» — записать это открытым вопросом
законно: «не знаю» — это TBD, а не выдуманный ответ (`:170-171`). 26 внутри такого пункта («прикрепить сверх нового
лимита (26-ю)») — не записанный пример: признак «26» краснит только вне «Открытых вопросов». На `main`
(`scx-main-cr`) такой пункт записан в 3 прогонах из 3.

Отсюда два следствия в грейдере. Строка хендоффа «Открытые пункты: … — ответите?» обязательна, когда открытые пункты
есть (`:310`): если в файле записан открытый вопрос о границе, эта строка (и пункты списка сразу под ней) его
пересказывает и переспросом не считается; переспрос — вопрос о границе вне неё («25-я проходит, 26-я — отказ?»,
«25 включительно?»). Строки `FR-*` берутся только вне «Открытых вопросов»: «в FR-1 не включено» там не спасает FR без 25.

## Что правила не определяют

- **Вопрос о границе на числе, которое не порог** (`scx-cr-ver-q`). Прямого запрета в тексте нет: правило границы
  условно (`:339-341`), а версия под определение порога не подходит. Критерий выведен из условия правила, а не из
  запрета. Если ведущий с этим не согласен — считать этот счётчик у `ver-q` справкой.
- **«Включительно» в записанном `FR-1` у `own`.** «До 25» по-русски двусмысленно; дописать «включительно» — решить
  границу за аналитика или пересказать «до»? Правило молчит. Грейдер «включительно» в файле не краснит, краснит
  только 26 и вопрос.
