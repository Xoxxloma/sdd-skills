## 1. Обзор изменения
### 1.1. Что делаем и тип изменения
**Суть:** Новая ручка `GET /v1/parts/stock` в `repair-api` отдаёт остатки запчастей склада: остаток, минимальный остаток, уровень («мало», «нет на складе») и дату последнего пересчёта. Это общий контракт, который наследуют части эпика PRT-601 (остаток в карточке заказа-наряда) и PRT-602 (список на исходе для кладовщика).
**Тип:** доработка
**Стороны:** BE-only — новая ручка в `repair-api`; вызывают её экраны частей PRT-601 и PRT-602, они проектируются в своих спеках.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `repair-api` | новый вызов: отдаёт INT-0 | команда «Сервис» | 🟢 |
| `repair-web` | потребитель INT-0 (экраны — в спеках PRT-601 и PRT-602) | команда «Сервис» | 🟢 |
### 1.3. Связь с бизнес-требованиями
Остаток в заказе-наряде (FR-1) и список на исходе (FR-3) стоят на одних и тех же данных склада — контракт проектируется один раз и отдаётся обеим частям неизменным.

## 2. Взаимодействия (ядро)

### INT-0. Остатки запчастей — 🟢 (фундамент, наследуют: PRT-601, PRT-602)
- **Вид:** новое
- **Граница/направление:** FE → BE (`repair-web` → `repair-api`)
- **Триггер:** мастер открывает карточку заказа-наряда (PRT-601); кладовщик открывает список запчастей на исходе (PRT-602)
- **Контракт (запрос):** `GET /v1/parts/stock`; параметры: `partId` — string, повторяемый, необязательный (только эти запчасти); `level` — enum `low | out`, повторяемый, необязательный (только запчасти с этим уровнем). Без параметров — все запчасти склада. Неизвестный `partId` в ответ не попадает, ошибки нет.
- **Контракт (ответ):** `items[]`, порядок — по `partName`. Элемент: `partId` string; `partName` string; `shelfQty` int, ≥ 0 — остаток на складе, `0` — валидный ноль; `minQty` int или `null` — минимальный остаток, `null` — минимум не задан; `stockLevel` enum `ok | low | out` — `out`: `shelfQty = 0`; `low`: `0 < shelfQty < minQty`; `ok`: иначе, в том числе при `minQty = null`; `recountedAt` string (дата-время ISO 8601, UTC) или `null` — `null`: остаток ни разу не пересчитывали.
- **Пример запроса:** `GET /v1/parts/stock?partId=P-1042&partId=P-2210&partId=P-3307`, тело отсутствует
- **Пример ответа (успех):**
  ```json
  {
    "items": [
      { "partId": "P-1042", "partName": "Ремень привода 6PK", "shelfQty": 2, "minQty": 5, "stockLevel": "low", "recountedAt": "2026-10-20T09:00:00Z" },
      { "partId": "P-2210", "partName": "Термостат ТС-40", "shelfQty": 0, "minQty": 3, "stockLevel": "out", "recountedAt": "2026-10-20T09:00:00Z" },
      { "partId": "P-3307", "partName": "Фильтр салона", "shelfQty": 7, "minQty": null, "stockLevel": "ok", "recountedAt": null }
    ]
  }
  ```
- **Ошибки:** `400 UNKNOWN_LEVEL` — значение `level` вне enum; `403` — роль не `MASTER` и не `STOREKEEPER`; `503 STOCK_UNAVAILABLE` — база склада не ответила. Тело ошибки: `{ "error": "<код>", "message": "<текст>" }`. См. «Каталог ошибок».
- **Состояния UI по ответу (если есть фронт):** для экранов частей: `stockLevel = ok` → остаток числом без отметки; `low` → «мало»; `out` → «нет на складе» (`shelfQty = 0` — валидный ноль, не «—»); `recountedAt = null` → «остаток не пересчитан»; `503` → «остатки недоступны».
- **Авторизация:** `MASTER` и `STOREKEEPER`; проверяется в `repair-api`; иная роль — `403`.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (PRT-601), FR-3 (PRT-602)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 | `UNKNOWN_LEVEL` — «Неизвестный уровень остатка» | `level` вне `low \| out` | ошибка запроса, на экранах частей не возникает |
| 403 | — | роль не `MASTER` и не `STOREKEEPER` | `error_forbidden` (в спеках частей) |
| 503 | `STOCK_UNAVAILABLE` — «Остатки склада недоступны» | база склада не ответила | «остатки недоступны» (в спеках частей) |

## 3. Backend — ответственность
### 3.1. По сервисам
- `repair-api` (🟢): реализует INT-0 — читает таблицу склада, считает `stockLevel` по правилу из INT-0, фильтрует по `partId` и `level`, сортирует по `partName`.
### 3.2. Данные и хранение
Новых сущностей нет: INT-0 читает существующую таблицу склада `repair-api` (наш сервис); остаток, минимальный остаток и дата последнего пересчёта в ней уже есть. Изменённых полей нет, миграции не нужны, пересчёт уже лежащих строк не нужен. `stockLevel` не хранится — считается при ответе.
### 3.3. Авторизация/доступ на бэке
`repair-api` пускает к INT-0 роли `MASTER` и `STOREKEEPER`; остальные — `403`. Роли уже заведены.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Синхронно, без кэша. Нагрузка: около 40 мастеров, до 2 000 открытий заказа-наряда в день; список на исходе кладовщик открывает несколько раз в день. Ответ — до 1 с.
### 5.2. Надёжность/деградация
База склада не ответила → `503 STOCK_UNAVAILABLE`; ручка только читает, при сбое ничего не записывается.
### 5.3. Безопасность/доступ (сводно)
| Граница | Кто вправе |
|---------|------------|
| INT-0 | `MASTER`, `STOREKEEPER` |
