# Бизнес-требования: быстрый поиск свободной переговорной

> **Статус готовности:** Готово к оценке
> **Задача:** RMS-5103

## 1. Введение и контекст

### 1.0. Тип изменения
Доработка существующего — бронирование переговорных уже есть, добавляется поиск свободной комнаты
на ближайшее время.

### 1.1. Описание проблемы (Problem Statement)
Чтобы найти свободную переговорную на ближайший час, сотрудник по очереди открывает расписание
каждой комнаты этажа. На это уходит несколько минут, и короткие встречи часто проводят в коридоре.

### 1.2. Конечные потребители (End Users)
Сотрудники офиса с ролью `ROLE_EMPLOYEE`, бронирующие переговорные.

### 1.3. Заказчик и стейкхолдеры (Stakeholder / Sponsor)
Заказчик — команда рабочих мест.

### 1.4. Как сейчас
Сейчас никак: быстрого поиска нет, сотрудник вручную перебирает расписания комнат.

## 2. Бизнес-требования (цели и ценность)

### 2.1. Бизнес-цель
Я как сотрудник (`ROLE_EMPLOYEE`) хочу одним действием увидеть переговорные, свободные на ближайший
час, чтобы забронировать комнату без перебора расписаний.

### 2.2. Ценность для бизнеса
По опросу команды рабочих мест поиск комнаты на короткую встречу занимает в среднем четыре минуты;
после доработки — меньше минуты.

### 2.3. Бизнес-риски и меры по снижению (Mitigation)
Рисков нет: поиск только показывает свободные комнаты, бронирование идёт как раньше.

## 3. Объём проекта (Scope)

### 3.1. Входит в проект (In-scope)
Поиск переговорных, свободных на ближайший час, на этаже сотрудника; переход к бронированию
найденной комнаты.

### 3.2. Не входит в проект (Out-of-scope)
Поиск на произвольный период и по оборудованию комнаты.

### 3.3. Архитектурные изменения и интеграции
Новых интеграций нет: поиск работает там же, где брони переговорных.

### 3.4. Внешние зависимости
Внешних зависимостей нет.

## 4. Функциональные требования

### 4.1. Описание функционала / бизнес-процесса
- **FR-1.** Пользователь с ролью `ROLE_EMPLOYEE` одним действием видит переговорные своего этажа,
  свободные на ближайший час.
- **FR-2.** Из списка найденных комнат пользователь с ролью `ROLE_EMPLOYEE` переходит к
  бронированию выбранной комнаты.

### 4.2. Критерии приёмки (Acceptance Criteria)
- **[FR-1]** Дано: на этаже сотрудника три переговорные, одна из них занята с 14:00 до 15:00.
  Когда: пользователь с ролью `ROLE_EMPLOYEE` в 14:10 запускает поиск. Тогда: он видит две
  свободные комнаты, занятой в списке нет.
- **[FR-2]** Дано: пользователь видит список свободных комнат. Когда: он выбирает комнату. Тогда:
  открывается бронирование этой комнаты с ближайшим часом.

### 4.3. Бизнес-данные
Не применимо: бизнес-данные не меняются — поиск читает переговорные и брони, которые уже есть, и
ничего в них не добавляет.

## 4.5. Разбиение на слайсы
Не применимо: один деливербл — поиск без перехода к бронированию проблему не снимает.
