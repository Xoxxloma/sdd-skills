## Общие правила всех шагов

**Стенд.** SM-REAL, плечо `scan`, **6 прогонов**, по 4 параллельно. Запуск и приёмы на macOS —
`runs/2026-09-14-golden/STATE.md`; правки раннера и грейдера лежат в рабочем дереве без коммита.

**Модель — sonnet (решение человека 2026-09-14).** Прод аналитиков перешёл на flash-модели с
рассуждением (deepseek-v4-flash, glm-5.3-flash, qwen3.8-flash-next, окно 262K); прокси к ним не
поднимаем, берём ближайшую модель Claude. Раннер: `SM_MODEL=sonnet`. Прогон ≈ 18 мин.
**Насколько flash-модели ближе к haiku или к sonnet — не измерено.** Если у аналитиков карточки
поплывут так, как у нас на haiku (`golden`: 0 из 8 годных), стабилизация возвращается — см. «Снято».

**Одна правка — одно плечо.** Плечо читает снимок из своей папки раунда (`SKILL_SRC`). Живой

нескольких правок нельзя разобрать, когда он просел.

**Считаются прогоны, а не суммы.** Основное число шага — **годных прогонов из 6**. Остальное —
вторичные метрики и сторожа. На n = 6 различимы только крупные эффекты; результат ровно на пороге —
добор 6 прогонов, а не вывод. **Пороги пишутся до плеча, а не после.**

## Снято: шаги 1–2 (откат сжатия, строка гейта)

Посылка «0 из 8 годных, стабилизировать до бизнес-слоя» была снята на haiku. На sonnet та же
редакция даёт **4 из 4 годных**, форма и ключи чисты во всех прогонах, гейты ведущий исполняет сам
(добор в 3 прогонах из 6; `STATE.md` раунда). Нестабильность была свойством модели, не текста.

- **Шаг 1 (откат сжатия `dd8abda`)** — не делается.
- **Шаг 2 (строка гейта числами перед `Write`)** — не блокирует. Грейдер её по-прежнему считает
  (`строка гейта: есть N, совпадает M`); если на flash-моделях у аналитиков карточки поедут — это
  первая правка, и её плечо уже описано в прежней редакции плана (`git log -- PLAN-BUSINESS-LAYER.md`).

Что из «настоящего» осталось и не относится к стабильности: факты «на один файл дальше» —
«приёмки без задержки» 0 из 4, «очередь Redis, TTL 600» 0 из 4, «окна 45/120/180» 1 из 4. Это
отдельная задача про плотность, не про бизнес-слой; сюда не входит.

## Шаг 4 — Секция «Бизнес-правила» (только если шаг 3 не дотянул)

**Вход:** шаг 3 дал медиану < 3 или нестабильные анкеры.

**Правка.** Производная секция сразу после «Что умеет для пользователя»: таблица
`Правило (языком аналитика) | Где действует`, где вторая колонка — ключ из описи (эндпоинт, сущность,
задача). Строка появляется из факта описи одного из классов: уникальность; лимит; срок хранения;
автоматический переход статуса; фильтр по умолчанию; запрет по роли.

**Гейт ключа — механический, у ведущего, по образцу «источник у каждого ключа»:** ключ во второй
колонке обязан быть заголовком `###` или строкой таблицы **этой же карточки**; нет — строка
вычёркивается, число пересчитывается. Правило без ключа — выдуманное правило, ровно как ключ без
файла. Грейдер: секция добавляется в `BIZ_SECTIONS`, новая строка «правил N · с ключом в карточке N».

**Чем она не ломает соседей:** новых классов ключей нет — строка выводится из уже собранной описи,
в инвентарь не идёт, `repo-split` не трогается; в таблице порядка секций +1 строка → в `SKILL.md`
греп порядка `-A 15` → `-A 16`; ключ секции нестрогий, как у «Что умеет»: гард на утоньшение её не
считает.

**Порог приёмки (плечо 4):**
- бизнес-анкеров в бизнес-слое: медиана **≥ 5 из 8**, минимум 5 анкеров стабильны (≥ 5 из 6);
- ключ найден в карточке у 100 % строк секции;
- технические метрики и годные — не ниже шага 3;
- объём карточки `repairy-api` вырос **не больше чем на 25 %**: карточка трижды проходит через
  контекст ведущего (на sonnet это 936–949 строк, ≈ 15–20K токенов, то есть 50–60K на сервис).

## Разбор 2026-09-14: «бизнес-контекст» — итог

Разбирались `GIGACODE.md` и `business-context-generator.md` (отдельная папка `business_context/`
с доменами, генерируемая по Java-коду). Два независимых архитектора (минимум подвижных частей;
целостность обновления) сошлись на одном: **код читается один раз — `service-map`; бизнес-слой живёт
в карточке; отдельной папки, второго скилла, описи файлом и триггеров нет.** Разошлись в одном —
нужен ли позже производный домен из карточек; это шаг 7, и решает его число из `BR-REAL`.

Почему карточка, а не папка: в замере `sonnet-base` бизнес-анкеры **в карточке уже есть** (6–7 из 8),
то есть код прочитан и факты на диске; проблема — в секциях, которые потребитель не открывает.
Старый генератор нарушал почти каждое правило, выстраданное на `service-map`: читал в основном
треде без описи и чисел покрытия, имел два взаимоисключающих гейта записи, дублировал секции
карточки (роли, сущности, возможности), не имел ни фикстуры, ни замера.
