#### 3.5 Большой сервис — читают части

**Когда.** Сумма маркеров `ключ` сервиса по всем классам (3.1) больше **K = 57** (вес строки `ориентир` — **w = 1**) — сервис читает не
один субагент, а части: окно одного читающего на таком сервисе кончается раньше, чем он дочитает, и
кончается молча — обрывом или тонкой карточкой. Сумма не больше K — 3.2–3.4 как обычно. Разведчик не
назвал маркеров — суммы нет, нарезки тоже, 3.2–3.4.

**Нарезка и склейка — скрипты этого скилла, и им нужна командная строка.** Её нет — нарезки нет:
склеить части нечем. Читай одним субагентом по 3.2–3.4 и назови в отчёте «сервис крупнее K, нарезка
без командной строки невозможна».

**План — скриптом, не тобой.**
1. Запиши вывод грепов 3.1 в `services/.work/<name>/counts.txt`: на каждую строку разведчика —
   заголовок `## <класс> :: <ключ|ориентир>`, под ним вывод `Grep … output_mode="count"` дословно.
2. `bash "<…/reference/plan.sh>" "<counts.txt>" <K> <w> "<пути сервиса через запятую>"` — он печатает
   итог по классам и части: номер, вес, классы с числами, папки (каждая — с подпапками) или файлы.
3. Итог плана по классам сверь со своими суммами 3.1. Разошлись — нарезки нет, строка в отчёт, 3.2–3.4.

**Кто что читает.** Части `01…S` из плана и **остаток** — номер `S+1`: всё, что вне папок и файлов
частей (там нет пометок, но бывают ключи без пометок — топики из конфига, обработчики без аннотаций,
сообщения из папки рассылок). Каждому — субагент с брифом 3.3, дословно, плюс абзац «Ты читаешь
часть» ниже; параллельно, не больше шести одновременно. Подстановки брифа: `<пути>` — папки или файлы
части (у остатка — пути сервиса целиком), `<корень>` — корень репозитория всегда, `<маркеры>` — числа
части из плана (у остатка фразу убери), `<опись>` и `<черновик>` — `services/.work/<name>/part-NN.opis.md`
и `services/.work/<name>/part-NN.md`.

```
## Ты читаешь часть сервиса — этот абзац старше всего выше
Ты — часть NN из S. Твои ключи — только из <папок и файлов части | файлов вне этих папок и файлов: …>;
за фактом иди куда угодно в репозитории. Имена сущностей бери по коду всей репы: сущность чужой части
у твоей ручки — сущность, а не «не сущность».
Первая строка обоих твоих файлов — `<!-- service-map: часть NN <дата> -->`.
В черновике — ТОЛЬКО секции со своими ключами: «Публичный контракт», «Владеет данными», «События»,
«Фоновые задачи», «Бизнес-правила» (свои сущности, сообщения и ограничения из своих файлов), строки
«Зависит от» и «Потребляемые API» своих ключей — без заголовка таблицы. Шапки, frontmatter,
«Назначения», «Что умеет», «Стека», «Ролей», «Заметок», «Кто меня потребляет» не пиши — их пишет голова.
Ролей в описи нет.
Прежнюю карточку целиком не открывай: найди грепом заголовки своих ключей из своей описи и читай
только эти блоки (`Read` с offset/limit).
```

**Голова — после частей.** Когда все части вернули по три строки и файлы на месте, запусти голову —
бриф ниже, дословно; подстановки как в 3.2 плюс `<описи частей>` — пути всех `part-NN.opis.md`.

````
Ты — голова скилла `service-map`. Сервис прочитан частями; ты пишешь каркас карточки и общие секции.
Три правила важнее всего: не выводится из кода — `не определено`; чужие репозитории только читаешь;
секреты не копируешь.
Сервис: <пути>, тип `<type>`. Имена сервисов манифеста: <имена>.
Прочитай целиком `<шаблон>`. Ответ начни строкой `шаблон прочитан, тип: <type>; голова`.
Описи частей: <описи частей> — читай их, а не код ключей.
Файл `<каркас>`: первая строка `<!-- service-map: голова <дата> -->`, дальше карточка по шаблону, в
порядке секций для типа `<type>`: шапка и frontmatter (`scanned: <дата>`), «Генерируется», «Заметки
команды» (дословно: <notes>), «Назначение» и «Что умеет для пользователя» — по группам описей частей,
словами, которыми сервис говорит с человеком; «Стек» — по файлам сборки и конфигам; «Роли и доступ» —
по коду (конфиг безопасности, перечисления ролей); «Кто меня потребляет» — пустой формой.
В секциях «Публичный контракт», «Владеет данными», «События», «Фоновые задачи», «Бизнес-правила» —
только заголовок секции и строка `<!-- части -->`; в «Зависит от» и «Потребляемые API» — заголовок
секции, заголовок таблицы, разделитель и строка `<!-- части -->`.
Файл `<опись головы>`: первая строка свежести, затем роли — строкой `роль — файл`.
Что вернуть — ровно три строки:
шаблон прочитан, тип: <type>; голова
опись: <опись головы>
карточка: <каркас>
````

`<каркас>` — `services/.work/<name>/head.md`, `<опись головы>` — `services/.work/<name>/head.opis.md`.

**Склейка — скриптом.**
`bash "<…/reference/assemble.sh>" "services/.work/<name>" <S+1> <дата> "services/.work/<name>.md" "services/.work/<name>.opis.md"`
Он проверяет, что все файлы на месте и свежие, сливает блоки частей в каркас (дубль ключа — один блок,
строки тела без повторов; порядок — по шаблону), суммирует итоги описи. Отказ — пустой ответ той
части, которую он назвал: 3.4. Дальше — Шаг 4 по склеенным файлам, как у любого сервиса.

**Что меняется на Шаге 4 и после.**
- Маркерный гейт — **по каждой части**: `check.sh` по `part-NN.opis.md` и `part-NN.md` даёт «опись
  по классам» части, её сравниваешь с числами части из плана. Остаток гейта не получает.
- Добор — той части, чей ключ: греп ключа по `part-*.opis.md` называет номер; бриф части плюс блок
  «Добор»; правит она свои файлы. После добора — склейка заново; **перезапуск склейки бюджет не
  тратит** — бюджет считается прогонами субагентов: два на часть, остаток, голову, разведчика.
- Часть упала дважды — карточку не пиши: прежняя байт-в-байт, сервис в отчёт с номером и папками части.
- Продвижение: `bash "<…/reference/promote.sh>" "<черновик>" "<путь>"` — копия и три счёта сверки;
  копировщик-субагент на нарезанном сервисе не нужен.
- Уборка — список файлов `services/.work/<name>/*` по именам плюс пустая папка `services/.work/<name>/`.
