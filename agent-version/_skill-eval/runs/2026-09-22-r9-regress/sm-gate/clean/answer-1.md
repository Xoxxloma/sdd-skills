Прогоняю гейт «Бизнес-правила» по пяти пунктам.

1. **Ключи.** Три заголовка секции: `` ### `Shipment` — отправление ``, `### сообщение «груз доставлен»`, `### ограничение «приём отправлений партнёра отключён»` — все три формы верны (имя сущности в бэктиках / «сообщение «» / «ограничение «»). Блок объекта один — Shipment. Сошлось.

2. **Состав.** Опись даёт 1 строку `состояние:` (Shipment) → в карточке 1 блок-объект (Shipment), справочники (`packageType`, `Attachment.kind`) блоков не получили — верно, справочник блока не имеет. Сообщений: опись 1 строка `сообщение:` + «События» дают 1 `публикует` → в карточке 1 сообщение. Ограничений: опись 1 строка → в карточке 1 блок. Сошлось.

3. **Значения.** У Shipman 3 значения в `состояние:` (NEW|ASSIGNED|DELIVERED) → в блоке ровно 3 строки, каждая с уникальным токеном-значением в бэктиках, без слипшихся правил и без второго поля на одну строку. «Владеет данными» — форма `- поле: тип`, одно поле на строку, значения через `|`. Сошлось.

4. **Код.** По всей секции «Бизнес-правила» вне бэктиков нет ни пути (` /[a-z]`), ни HTTP-глагола, ни camelCase, ни точечного ключа; в бэктиках встречаются только значения перечисления (`NEW`, `ASSIGNED`, `DELIVERED`), имя топика (`shipment.delivered`) и имя сервиса из манифеста (`partner-registry`) — всё разрешённые случаи. Сошлось.

5. **Переключатель.** Блок ограничения называет `partner-registry` как того, кто управляет условием; это имя есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
