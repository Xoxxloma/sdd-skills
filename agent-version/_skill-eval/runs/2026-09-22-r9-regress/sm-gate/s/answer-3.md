**1. Ключи.** Опись даёт 1 состояние + 2 справочника + 1 сообщение + 1 ограничение. Заголовки блоков: `` `Shipment` ``, «сообщение «груз доставлен»», «ограничение «приём отправлений партнёра отключён»» — все три формы верны, один блок на сущность. Сошлось.

**2. Состав.** Блоков-сущностей столько же, сколько строк `состояние:` — 1 (`Shipment`), блок есть. Сообщений: строка `сообщение:` — 1, блок `публикует` в «Событиях» — 1, в карточке 1 блок сообщения — сошлось. Ограничений: строка `ограничение:` — 1, блок — 1. Справочники (`packageType`, `Attachment.kind`) своих блоков не требуют и не имеют — верно.

**3. Значения.** Форма «Владеет данными» — построчно, по одному полю; слипшихся строк нет. Но: `- \`status\`: \`ShipmentStatus\` — перечисление` — тип назван, а значения не выписаны через `|` (сравни с `packageType`: `BOX` | `PALLET`, где значения на месте). Это ровно случай «тип без значений» из правила — добор. Число строк в блоке `Shipment` (3) совпадает с числом значений `состояние:` (NEW|ASSIGNED|DELIVERED), но сама «Владеет данными» не даёт эти значения как перечисление — не сошлось.

**4. Код.** Вне бэктиков в секции «Бизнес-правила» нет ` /[a-z]`, глаголов GET/POST/…, camelCase, многоточечных ключей. В бэктиках — только `NEW`/`ASSIGNED`/`DELIVERED`, `shipment.delivered`, `partner-registry` — всё разрешённые формы. Сошлось.

**5. Переключатель.** В блоке ограничения назван `partner-registry` — есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
