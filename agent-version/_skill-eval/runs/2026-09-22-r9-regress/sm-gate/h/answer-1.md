**1. Ключи.** Три `###`: `` `Shipment` `` (сущность в бэктиках), «сообщение «груз доставлен»», «ограничение «приём отправлений партнёра отключён»» — все три формы корректны, один блок на сущность. Сошлось.

**2. Состав.** Опись: состояние 1 (Shipment), справочников 2 (packageType, Attachment.kind), сообщений 1, ограничений 1. В карточке: блоков-сущностей в «Бизнес-правилах» — 1 (`Shipment`, у неё есть строка `состояние:`); справочники (packageType, kind) блоков не имеют — верно, они не состояние. Сообщений: 1 строка описи = 1 блок «сообщение» = 1 блок `публикует` в «Событиях». Ограничений: 1 = 1. Сошлось.

**3. Значения.** «Владеет данными» — форма `- поле: тип`, по одному полю на строку, с `|` для перечислений (`status`, `packageType`, `kind`). В блоке `Shipment` — 4 строки на 3 значения `состояние:`; повтор `ASSIGNED` оформлен как разрешённое исключение («переназначено (`ASSIGNED`, `assignedAt` сдвинут)») — дата-отличие в скобках рядом с токеном, не заполнитель. Токены строк — все из набора значений. Сошлось.

**4. Код.** Вне бэктиков в секции «Бизнес-правила» нет путей, HTTP-глаголов, camelCase, точечных цепочек. В бэктиках — только значения (`NEW`/`ASSIGNED`/`DELIVERED`), имя топика (`shipment.delivered`), имя сервиса из манифеста (`partner-registry`) и поле `assignedAt` как часть разрешённого дата-исключения. Заголовки сообщения/ограничения — без бэктиков. Сошлось.

**5. Переключатель.** Блок ограничения называет `partner-registry` — это имя есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
