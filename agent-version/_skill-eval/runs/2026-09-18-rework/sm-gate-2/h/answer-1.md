**1. Ключи.** Три заголовка `###` в секции — `` `Shipment` — отступление`` (сущность в бэктиках), «сообщение «...»», «ограничение «...»» — все три формы разрешены, чужих заголовков нет, блок объекта один (Shipment). Сошлось.

**2. Состав.** Блоков объектов 1 = строк `состояние:` в описи (1). Сообщений 1 = строк `сообщение:` (1) и = блокам `публикует` в «Событиях» (1). Ограничений 1 = строк `ограничение:` (1). Все перечисления Shipment/Attachment (status, packageType, kind) названы в описи состоянием/справочником — пропусков нет, чужих сущностей и справочников в секции нет. Сошлось.

**3. Значения.** «Владеет данными» — построчно `- поле: знач1 | знач2 | ...`, у status/packageType/kind значения через `|`, у weightKg/url (не перечисления) — тип без значений, это не нарушение. В блоке Shipment 4 строки ≥ 3 значений `состояние:`; токены — NEW/ASSIGNED/ASSIGNED/DELIVERED, каждый из перечня; строка «переназначено» — не дублирующий заполнитель, а разрешённое исключение (тот же токен `ASSIGNED` + дата `assignedAt` сдвинут в скобках), два токена через `/,|,` не встречаются. Сошлось.

**4. Код.** По всем строкам секции — нет `/путь`, нет GET/POST/…, нет `\b[a-z]+(\.[a-z-]+){2,}\b` (у `shipment.delivered` только один разделитель, под запрет не попадает), бэктиков в заголовках сообщений нет. Единственный кандидат на camelCase — `assignedAt`, но это ровно санкционированное пунктом 3 исключение (дата рядом с токеном состояния в скобках), а не код, просочившийся в правило. Сошлось.

**5. Хозяин.** В блоке ограничения хозяин — `partner-registry`, это имя соседа из манифеста (shipping, partner-registry, dispatch-web), не конфиг и не голый флаг. Сошлось.
