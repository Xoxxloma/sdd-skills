**1. Ключи** — заголовки: `` `Shipment` `` (сущность в бэктиках), `сообщение «груз доставлен»`, `ограничение «приём отправлений партнёра отключён»`. Все три — разрешённые формы, один блок на сущность. Сошлось.

**2. Состав** — опись: 1 строка `состояние:` (Shipment) → 1 блок объекта в карточке (есть). Сообщений: 1 строка `сообщение:` и 1 блок `публикует` в «Событиях» → в карточке 1 сообщение. Ограничений: 1 строка `ограничение:` → 1 блок. `Attachment.kind` — справочник, блока не требует и не имеет. Сошлось.

**3. Значения** — `Shipment.status` в «Владеет данными»: `NEW` | `ASSIGNED` | `DELIVERED` (3 значения через `|`), в описи «значений 3». В блоке `Shipment` — 3 строки, у каждой токен — значение перечисления в скобках (`NEW`, `ASSIGNED`, `DELIVERED`), без сдвоенных токенов через `/`, `|` или запятую. Сошлось.

**4. Код** — по секции «Бизнес-правила»: бэктики есть только в заголовке сущности (разрешено) и вокруг значений (`NEW` и т.п.) и топика `shipment.delivered` — ни один из пяти паттернов (путь с `/строчная`, HTTP-глагол целым словом, camelCase, точечный путь из 3+ сегментов, бэктик в заголовке сообщения) не сработал. `shipment.delivered` — только два сегмента через точку, под `{2,}` не попадает. Чисто.

**5. Хозяин** — блок ограничения: «пока условие действует, новые отправления не принимаются, диспетчер видит причину отказа». Здесь названа только роль `DISPATCHER` как получатель уведомления об отказе, а не хозяин условия. Ни имени из манифеста (`partner-registry`), ни внешней системы, ни роли-владельца в тексте нет — хотя файл в описи (`integration/PartnerGate.kt`) намекает на партнёрскую интеграцию. Не сошлось.

ГЕЙТ: ДОБОР — в блоке `ограничение «приём отправлений партнёра отключён»` назвать хозяина условия: сервис из манифеста (`partner-registry`), роль из «Роли и доступ» или внешнюю систему по имени, а не только того, кто видит причину отказа.
