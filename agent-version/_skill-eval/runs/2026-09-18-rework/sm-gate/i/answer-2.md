**1. Ключи.** Заголовки: `### \`Shipment\` — отправление`, `### сообщение «груз доставлен»`, `### ограничение «приём отправлений партнёра отключён»` — все три начинаются с имени сущности в бэктиках либо «сообщение «»/«ограничение «». Блок объекта один — на `Shipment`. Сошлось.

**2. Состав.** Строк `состояние:` — 1 (Shipment), блоков-объектов в карточке — 1. Строк `сообщение:` — 1, блоков `публикует` в «Событиях» — 1, сообщений в карточке — 1 (не меньше обоих). Строк `ограничение:` — 1, блоков ограничения — 1. Сошлось.

**3. Значения.** Вот тут расхождение. В «Владеет данными» `Shipment.status` и `Shipment.packageType` — оба перечисления по описи (состояние и справочник), но в карточке они поданы таблицей `| Поле | Тип | Описание |` со значением типа `ShipmentStatus` / `PackageType`, без самих значений через `|` в строке `- поле:`. Правило прямо называет это добором: «таблица или тип без значений — добор». `Attachment.kind` оформлен верно (`- kind: PHOTO | PDF`), но по двум полям Shipment — не сошлось.

**4. Код.** По тексту секции «Бизнес-правила» ни одной строки с ` /[a-z]`, HTTP-глаголом, camelCase или путём из трёх точечных сегментов; `shipment.delivered` — только два сегмента, под запрещённый паттерн не попадает; бэктиков в заголовке сообщения нет. Сошлось.

**5. Хозяин.** В блоке ограничения хозяин — `partner-registry`, это сосед из манифеста (`shipping`, `partner-registry`, `dispatch-web`). Флагов `true`/`false` в блоке нет. Сошлось.
