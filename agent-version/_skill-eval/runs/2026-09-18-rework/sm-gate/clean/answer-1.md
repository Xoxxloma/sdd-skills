**1. состояний (N=1)** — сравнил с числом блоков-сущностей в «Бизнес-правила» (по строкам `состояние:` в описи). Блок один — `### \`Shipment\` — отправление`. Сошлось.

**2. значений (K=3)** — сравнил с числом строк внутри блока `Shipment`: новое (`NEW`), назначено (`ASSIGNED`), доставлено (`DELIVERED`) — три строки на три значения из `состояние:`. Токен каждой строки — значение в бэктиках, не имя поля. Сошлось.

**3. справочников (S=2)** — сравнил `packageType` и `Attachment.kind`: оба во «Владеет данными» записаны как перечисления через `|` (`BOX | PALLET`, `PHOTO | PDF`) и блока в «Бизнес-правила» не имеют — верно для справочника. Сошлось.

**4. сообщений (M=1)** — сравнил с блоком `### сообщение «груз доставлен»` в карточке и с блоком `публикует \`shipment.delivered\`` в «Событиях» — 1 и 1, оба ≥ M. Сошлось.

**5. ограничений (L=1)** — сравнил с блоком `### ограничение «приём отправлений партнёра отключён»`; хозяин — `partner-registry`, имя из манифеста (не конфиг и не булев флаг). Сошлось.

Дополнительно: заголовки все начинаются по форме ключа (сущность в бэктиках / «сообщение «» / «ограничение «»), лишних заголовков нет — проверка 1 в порядке. Строка про топик `shipment.delivered` — два сегмента через точку, под грep `\b[a-z]+(\.[a-z-]+){2,}\b` (нужно ≥2 повторов «.сегмент») не попадает; camelCase, HTTP-глаголов, ` /[a-z]` в секции нет — проверка 4 чистая.
