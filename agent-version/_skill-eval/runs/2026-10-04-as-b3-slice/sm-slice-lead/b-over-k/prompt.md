#### 3.0 Разведчик — чем в этом коде помечены ключи

Какой пометкой отмечен ключ, зависит от стека, и стеков больше, чем уместится в любой список. Поэтому
пометку называет модель, а считает греп: прежде чем читать сервис, запусти по каждому сервису
**разведчика** — субагента только с чтением и поиском (`Read`, `Grep`, `Glob`; писать ему нечего),
параллельно, не больше шести одновременно. Бриф — блок ниже; разведчик читает его сам, как в 3.3:
вызов «Вызов разведчика скилла `service-map`. Твой бриф — в файле `<этот SKILL.md>`: первый блок в
четыре обратных кавычки после заголовка «#### 3.0 Разведчик». Прочитай его и выполняй дословно, с
подстановками: <пути> = …; <type> = …». `<пути>` — пути строки манифеста через запятую, абсолютные.

````

Сервис: <пути>, тип `<type>`.

Классы ключей:
- `контракт` — операция, которую сервис ПРИНИМАЕТ: HTTP-ручка, операция GraphQL на корневом типе
  (запрос, мутация, подписка), метод gRPC. Вызовы наружу (HTTP-клиент, Feign) — не контракт;
- `сущности` — класс хранения в ЭТОМ репозитории: сущность ORM, модель схемы БД;
- `задачи` — фоновая задача по расписанию;
- `топики` — топик или очередь, которые сервис потребляет или публикует.

Как искать:
1. Дерево целиком не листай — ни `Glob **/*`, ни `Glob <папка>/**`: на большой репе это сотни
   килобайт. Структуру смотри по уровням, `Glob` с одной звёздочкой (`*`, `src/*`, `src/main/*`),
   потом — поиск пометок контракта. **Все три поисковых грепа обязательны, каждый отдельно, даже
   если первый уже дал много**: в одной репе бывает два стиля сразу, и назвав первый попавшийся, ты
   потеряешь второй. Это не маркеры, а поиск кандидатов (`output_mode="count"`, по всему сервису):
   - HTTP: `@\w*(Get|Post|Put|Patch|Delete)\w*|\.(get|post|put|patch|delete)\(`;
   - GraphQL: `@\w*(Query|Mutation|Subscription)\w*` и отдельно `"(Query|Mutation|Subscription)"`
     — корневой тип строкой в параметре аннотации (общая форма: одна аннотация на любой тип);
   - gRPC: `^\s*rpc\s` в `*.proto`.
2. На каждого кандидата открой один файл — не больше одного на кандидата и не больше десяти за
   всю разведку — и реши: стоит ли он на самом ключе — методе ручки, классе-сущности, — а не на
   классе, который их группирует, и не на запросе ORM. В этом же файле посмотри все методы-ключи:
   часть помечена иначе — у класса ещё одна строка. Общая форма с корневым типом в параметре — тоже
   ключ, но в регэкспе обязан стоять корневой тип (`Query`, `Mutation`, `Subscription`): без него
   она поймает и резолверы полей.
3. Задачи и топики помечают кто как — и это тоже обязательный поисковый греп, без учёта регистра:
   `cron|schedul|interval|listen|consum|subscri|topic`; открой кандидата и смотри, что стоит на
   самом ключе.
4. Поисковый греп — не маркер. В ответ ставь узкий регэксп той пометки, которую нашёл и проверил
   (`@GetMapping\(`, а не `@\w*Get\w*` — тот поймает и чужое, например `@Getter`).

Правила маркера:
- одно совпадение — один ключ. Пометка класса-контейнера (контроллер, резолвер, компонент) — не
  маркер: на нём пять ручек, а совпадение одно;
- маркер узкий: аннотация запроса ORM — не контракт; резолвер поля не корневого типа — не операция;
  вызов, которым пользуется и HTTP-клиент или словарь, — не ключ; вызов, который сам регистрирует
  ключ (ручку на роутере, задачу по таймеру), — ключ: одно совпадение — одна ручка или задача;
- на одном объявлении две пометки (класс-сущность с аннотацией таблицы рядом) — бери одну;
- ключ, у которого в коде пометки нет (топики только в конфиге, обработчики без аннотаций), —
  строка `ориентир` по тому, что пометить можно, или ничего. Топик — `ключ`, только если пометка с
  именем топика стоит на каждом топике; обработчик, который читает несколько топиков или берёт
  их имена из конфига, — `ориентир`;
- `<glob>` — только расширение: `*.java`, `*.ts`, `*.prisma`, `*.proto`. Ни папок, ни части имени:
  `routes/*.js` и `prisma/schema.prisma` Grep не находит и считает ноль, а `*Controller.java`
  теряет ключи из файлов с другим именем. Узким должен быть регэксп, а не маска;
- в строке — регэксп, а не описание: пометку словами не опишешь — строки нет.

Примеры формы — НЕ список: у сервиса может быть стек, которого здесь нет, тогда пометку находишь сам.
контракт :: @(Get|Post|Put|Patch|Delete)Mapping\( :: *.java :: ключ
контракт :: @(Get|Post|Put|Patch|Delete)\( :: *.ts :: ключ
контракт :: ^\s*rpc\s :: *.proto :: ключ
сущности :: @Entity\b :: *.java :: ключ
сущности :: ^model\s :: *.prisma :: ключ
задачи :: @Scheduled\( :: *.java :: ключ
топики :: @KafkaListener\b :: *.java :: ключ
топики :: \.subscribe\( :: *.ts :: ориентир
Регэксп — для инструмента Grep (ripgrep). Экранируй только символы, буквальные в коде (`\(` у скобки
вызова, `\.` у точки); скобки группы и `|` альтернативы — без обратного слеша: `@(Get|Post)Mapping\(`,
а не `@\(Get\|Post\)Mapping\(`.

Ответ — только строки маркеров, по одной на строку, без чисел и пояснений:
<класс> :: <регэксп> :: <glob файлов> :: ключ|ориентир
Класса в сервисе нет — строки нет. Не нашёл ни одной пометки — ответь одной строкой `маркеров нет`.
````

**Ответ разведчика проверяешь только по форме:** строки `<класс> :: <регэксп> :: <glob> :: ключ|ориентир`
или `маркеров нет`. Пустой ответ, обрыв, ответ не по форме — второй запуск тем же брифом; бюджет —
два запуска. Не помогло — у сервиса нет маркеров: счёт пропущен, строка в отчёт «разведчик не
назвал маркеров — внешней сверки нет». Чтение сервиса от этого не откладывается.

```
Сущность этого сервиса — класс с маркером хранения в ЭТОМ репозитории: `@Entity`/`@Table` (JPA,
TypeORM), `model` в схеме Prisma, `@Document`/`@Schema` Mongo и подобные аннотации ORM. Аннотации
схем API (`@Schema` springdoc, `@ApiModel`, `@JsonProperty`) маркером не являются. Строка описи у
сущности — `Имя — файл (маркер)`, маркер в скобках в конце. Класс без маркера — DTO, схема ответа,
view чужой схемы, класс «на чтение» — не сущность: в «Владеет данными» не стоит, строки в описи не
получает; его поля идут строками `-` в блок ручки под `сущности: → не сущность, …` (таблица «Три
случая» шаблона). Сервис без единого маркера хранения — «Владеет данными» — `—`.
У каждого ключа контракта — строка `сущности:` (вход слева от `→`, выход справа; имена — из строк
сущностей описи; ответ не из них — `→ не сущность, агрегат по X и Y` или `→ не сущность, ответ
<сервис>`; у служебных строки нет). Итоги `⟹` — по каждому классу отдельно; класса нет в сервисе —
строки нет.
Четыре строки для «Бизнес-правил» (только `backend` и `fullstack`):
- `состояние:` — поле-перечисление или пара дат «принято / удалено» у СВОЕЙ сущности из «Владеет
  данными», с перечнем значений. Булево поле — не перечисление. Чужая сущность (на чтение, view,
  «схема <имя>») строки не получает и в «Владеет данными» не стоит.
- `справочник:` — перечисление той же формы, от значений которого не зависит ни одно правило.
- `сообщение:` — вид исходящего человеку или соседу, с получателем и файлом отправки; каждое имя
  в коде (шаблон письма, метод sendXxx, публикуемый топик) — своя строка. Ответ на запрос и
  ошибка сообщением не являются.
- `ограничение:` — условие, при котором сервис отказывает или меняет поведение целиком, и его
  ПЕРЕКЛЮЧАТЕЛЬ — тот, кто это условие включает и выключает: имя сервиса из списка манифеста выше
  либо роль этого сервиса. Пиши `переключатель: <имя из манифеста | роль>`. Валидация входа,
  формат файла, проверка «только автор», свой конфиг, недоступность соседа или инфраструктуры —
  НЕ ограничение: их место — строка ошибки в «Публичном контракте». Внешняя система, которой нет
  в манифесте, переключателем не бывает — она идёт строкой в «Зависит от».
В строке из кода — только токен: путь, HTTP-глагол, код ошибки, поле со значением, ключ конфига —
словами или никак. Значение без перехода в коде — строка `не определено`, а не придуманное правило.
Перед возвратом прогони по секции «Бизнес-правила» черновика четыре грепа и перепиши совпавшие
строки словами: ` /[a-z]`, `\b(GET|POST|PUT|PATCH|DELETE)\b`, `\b[a-z]+[A-Z][A-Za-z]*\b`,
`\b[a-z]+(\.[a-z-]+){2,}\b` — вне бэктиков; а в бэктиках допустимы только значение перечисления,
имя вида или топика, имя сервиса из списка выше и дата. Имя поля, метода, бина, класса-тела
события, ключ конфига — не допустимы нигде в этой секции. Ведущий прогонит те же грепы; каждое
совпадение — добор, и второй прогон у тебя один.

## Прежняя карточка `<прежняя>` — открой ТОЛЬКО после описи
Это прошлая формулировка, а не источник фактов. Три правила, в этом порядке:
1. Ключ, которого в коде больше нет, в новую карточку не переносится.
2. Ключ есть и в описи, и в прежней карточке, и факты те же — верни прежнюю формулировку
   дословно. Дословно возвращается формулировка, а не форма: строка не в форме шаблона
   переписывается по форме с теми же фактами.
3. Факт изменился — пиши по коду.

## Карточка → файл `<черновик>`
Разверни карточку по описи, проходя список подряд, по форме шаблона. Объём не нормируется:
сорок восемь эндпоинтов дают сорок восемь блоков. Обобщение вместо перечисления — худший исход.
«Назначение» и «Что умеет для пользователя» — словами, которыми сервис сам говорит с человеком:
сначала найди грепом тексты ошибок и уведомлений, подписи ролей и статусов, summary/description
в описании API, и пиши ими; имя класса объектом не является. «Что умеет» собирай по группам
описи (общий префикс пути или сущность в имени операции; каждая фоновая задача и каждый
потребляемый топик — своя группа): каждая группа даёт хотя бы одну строку, кроме служебной.
Шапку, frontmatter и блок «Генерируется» пиши по шаблону; `scanned: <дата>`.
Секция «Заметки команды» — сразу после блока «Генерируется», дословно этот текст:
<notes>
Секция «Кто меня потребляет» — пустой формой: заголовок и строка `| — | | |`. Её собирает ведущий
из чужих карточек. Соседние карточки `services/*.md` не открывай — только свою прежнюю.

## Что вернуть
Ровно три строки, и ничего больше:
шаблон прочитан, тип: <type>; прежняя карточка: есть|нет
опись: <опись>
карточка: <черновик>
Ни чисел, ни пересказа: всё, что нужно ведущему, лежит в двух файлах.
````

**Запасной путь, если субагента с правом записи нет.** Тогда последний абзац брифа замени на:
«верни ответ из двух частей под заголовками `## ОПИСЬ` и `## КАРТОЧКА`, и ничего больше», а два
файла запиши сам — **каждую часть как есть, без единого изменения**. Это единственное место, где
текст карточки проходит через тебя, и менять в нём нельзя ни байта: не сокращай, не «поправляй
форму», не пропускай блоки. Всё, что тебе кажется неправильным, ловит Шаг 4 — грепом по файлу.

#### 3.4 После возврата

**Строка `шаблон прочитан, тип: <type>; прежняя карточка: есть|нет` — единственный наблюдаемый
признак, что шаблон открылся.** Ищи её в любом месте ответа. Нет — субагент работал по памяти о
форме: перезапусти его (первая из двух попыток). Хвост расходится с переданным — тот же случай.
Субагент сообщил, что файл не открылся, — говори человеку про неполную установку скилла.

Дальше **`Glob` двух рабочих файлов и `Grep "^scanned: <дата>"` по черновику.** Оба есть и дата
сегодняшняя — иди на Шаг 4. Дата чужая — это черновик прошлого прогона: рабочие файлы лежат до
уборки в конце, и без грепа даты старый черновик сойдёт за свежий. Нет хотя бы одного файла, дата
чужая, ответ пустой,
это отказ, или инструмент вернул «прерван» / «interrupted» / ошибку вместо ответа — всё это **один
и тот же исход: пустой ответ**. Перезапусти этого субагента один раз, тем же брифом, **не спрашивая
человека**: слово «пользователь» в сообщении об обрыве — это про механику инструмента, а не про
того, кто тебя запустил, и отвечать тебе некому. Пустые ответы случаются без причины в самом
сервисе; изменённый бриф превратит случайный сбой в другой прогон.

**Чего ты не делаешь при обрыве ни при каких условиях — не читаешь код сам.** Ни файла сервиса,
ни «хотя бы контроллеров», ни сохранённых на диске обрывков ответа субагента. Карточка, собранная
тобой из кода, неотличима от карточки субагента и не проходит через опись — то есть все
проверки Шага 4 она пройдёт, не будучи проверенной. Упал второй запуск — сервис в отчёт, и всё.


**Бюджет: не больше двух прогонов субагента на сервис.** Первый и, если понадобился, ещё один.
Второй — единственный, и он один **на все причины**: пустой ответ, отказ, нет файлов, не сошлись
числа на Шаге 4, пустое тело больше чем у половины блоков. Исключение одно — второй добор по
строкам с кодом в «Бизнес-правилах», число 4 гейта Шага 4.

**Добор — это не перезапуск и не «верни всё заново».** Числа на Шаге 4 не сошлись — запусти
субагента того же типа с тем же брифом плюс блок в конце:

```
## Добор
Файлы `<опись>` и `<черновик>` уже написаны твоим предшественником и почти верны. Не переписывай
их и не создавай заново. Правь только через `Edit`, только перечисленное ниже, остальное не трогай.
Правка, которая меняет состав ключей — снята чужая сущность, разделено сообщение, добавлен или
убран ключ, — вносится в ОБА файла: и в черновик, и в опись, чтобы они сошлись; опись тоже твоя,
а ведущий сверяет одно с другим и сам не правит ничего.
<перечень: ключи, которые не развёрнуты; строки, которые надо переписать; класс, которого нет в описи>
```

Перечень — из Шага 4, дословно. Без перечня субагент ответит тем же: он уже один раз решил, что
суть передана. Целиком переписанный файл в доборе — не добор, а второй прогон, и цена ему —
потерянное в секциях, к которым добор отношения не имел.

**Вторая попытка не помогла — прекрати.** Третьей не делай ни по какой причине. Прежняя карточка,
если была, остаётся байт-в-байт, включая `scanned` — прочтения не состоялось. Рабочие файлы
уберёт уборщик в конце вместе с остальными, сервис — в отчёт с числами. Карточки не было — её и
не будет в этом прогоне.

И ни в каком случае **не выдумывай карточку за субагента**. Молча пропущенный сервис выглядит
как проанализированный, и это худший исход из возможных.

#### 3.5 Большой сервис — читают части

**Когда.** Вес сервиса по 3.1 — сумма маркеров `ключ` по всем классам плюс w × сумма `ориентир` —
больше **K = 80** (**w = 0.5**): сервис читает не один субагент, а части. Окно одного читающего на таком
сервисе кончается раньше, чем он дочитает, и кончается молча — обрывом или тонкой карточкой. Вес не
больше K — 3.2–3.4 как обычно. Разведчик не назвал маркеров — веса нет, нарезки тоже, 3.2–3.4.

**Нарезка и склейка — скрипты этого скилла, и им нужна командная строка** — `Bash`, твой или
субагента; запрет на shell скриптов `reference/` не касается. Её нет ни у тебя, ни у субагента — нарезки нет:
склеить части нечем. Читай одним субагентом по 3.2–3.4 и назови в отчёте «сервис крупнее K, нарезка
без командной строки невозможна».

**План — скриптом, не тобой.** Его уже напечатал `plan.sh` на 3.1, по файлу счётчика: части с номером,
весом, классами с числами и папками (каждая — с подпапками) или файлами. Сам ты частей не
составляешь и не правишь. Итог плана не сошёлся с итогом счётчика (3.1) — нарезки нет, 3.2–3.4.

**Кто что читает.** Части `01…S` из плана и **остаток** — номер `S+1`: всё, что вне папок и файлов
частей (там нет пометок, но бывают ключи без пометок — топики из конфига, обработчики без аннотаций,
сообщения из папки рассылок). Каждому — субагент с вызовом 3.3 плюс строка в том же вызове: «Затем
в том же файле прочитай блок в тройных кавычках, который начинается строкой «## Ты читаешь часть
сервиса», — он старше брифа; в нём NN = …, S = …, свои пути = …»; параллельно, не больше шести
одновременно. Читающих на весь прогон — частей, остатков,
голов и одиночных сервисов — больше пяти: скажи человеку одной строкой до запуска, как на Шаге 2.2. Подстановки брифа: `<пути>` — папки или файлы
части (у остатка — пути сервиса целиком), `<корень>` — корень репозитория всегда, `<маркеры>` — числа
части из плана (у остатка фразу убери), `<опись>` и `<черновик>` — `services/.work/<name>/part-NN.opis.md`
и `services/.work/<name>/part-NN.md`.

```
## Ты читаешь часть сервиса — этот абзац старше всего выше
Ты — часть NN из S. Твои ключи — только из <папок и файлов части | файлов вне этих папок и файлов: …>;
за фактом иди куда угодно в репозитории. Имена сущностей бери по коду всей репы: сущность чужой части
у твоей ручки — сущность, а не «не сущность».
Первая строка обоих твоих файлов — `<!-- service-map: часть NN <дата> -->`.
В черновике — ТОЛЬКО секции со своими ключами: «Публичный контракт», «Владеет данными», «События»,
«Фоновые задачи», «Бизнес-правила» (свои сущности, сообщения и ограничения из своих файлов), строки
«Потребляемые API» своих ключей — без заголовка таблицы. Шапки, frontmatter, «Назначения», «Что умеет»,
«Стека», «Зависит от», «Ролей», «Заметок», «Кто меня потребляет» не пиши — их пишет голова.
Ролей в описи нет.
Прежнюю карточку целиком не открывай: найди грепом заголовки своих ключей из своей описи и читай
только эти блоки (`Read` с offset/limit).
```

Ответ части проверяешь как в 3.4: эхо-строка шаблона, оба файла на месте; свежесть — по первой строке
файла (`<!-- service-map: часть NN <дата> -->`), а не по `scanned:` — шапки у части нет.

**Голова — после частей.** Когда все части вернули по три строки и файлы на месте, запусти голову.
Бриф — блок ниже; голова читает его сама, как в 3.3: «Вызов головы скилла `service-map`. Твой бриф — в
файле `<этот SKILL.md>`: первый блок в четыре обратных кавычки после строки, начинающейся
«**Голова — после частей.**». Прочитай и выполняй дословно, с подстановками: …» — подстановки как в
3.2 плюс `<описи частей>` — пути всех `part-NN.opis.md`, `<каркас>` и `<опись головы>`.

````
Ты — голова скилла `service-map`. Сервис прочитан частями; ты пишешь каркас карточки и общие секции.
Три правила важнее всего: не выводится из кода — `не определено`; чужие репозитории только читаешь;
секреты не копируешь.
Сервис: <пути>, тип `<type>`. Имена сервисов манифеста: <имена>.
Прочитай целиком `<шаблон>`. Ответ начни строкой `шаблон прочитан, тип: <type>; голова`.
Описи частей: <описи частей> — читай их, а не код ключей.
Прежняя карточка: <прежняя> (нет — абзац пропусти). Из неё открой только свои секции: строки заголовков
`## ` найди `Grep` с `-n`, читай `Read` с offset и limit. Роль или система та же — её имя пиши как в
прежней, дословно; факты строки те же — верни прежнюю формулировку дословно.
Файл `<каркас>`: первая строка `<!-- service-map: голова <дата> -->`, дальше карточка по шаблону, в
порядке секций для типа `<type>`: шапка и frontmatter (`scanned: <дата>`), «Генерируется», «Заметки
команды» (дословно: <notes>), «Назначение» и «Что умеет для пользователя» — по группам описей частей,
словами, которыми сервис говорит с человеком; «Стек» — по файлам сборки и конфигам; «Зависит от» —
по коду всего сервиса (клиенты, подключения, переменные окружения): одна строка на сервис или внешнюю
систему, имя сервиса — из имён манифеста, иначе как в коде и `вне манифеста`; «Роли и доступ» —
по коду (конфиг безопасности, перечисления ролей); «Кто меня потребляет» — пустой формой.
В секциях «Публичный контракт», «Владеет данными», «События», «Фоновые задачи», «Бизнес-правила» —
только заголовок секции и строка `<!-- части -->`; в «Потребляемые API» — заголовок секции, заголовок
таблицы, разделитель и строка `<!-- части -->`.
Файл `<опись головы>`: первая строка свежести, затем роли — строкой `роль — файл`.
Что вернуть — ровно три строки:
шаблон прочитан, тип: <type>; голова
опись: <опись головы>
карточка: <каркас>
````

`<каркас>` — `services/.work/<name>/head.md`, `<опись головы>` — `services/.work/<name>/head.opis.md`.

**Склейка — скриптом.**
`bash "<…/reference/assemble.sh>" "services/.work/<name>" <S+1> <дата> "services/.work/<name>.md" "services/.work/<name>.opis.md"`
Он проверяет, что все файлы на месте и свежие, сливает блоки частей в каркас (дубль ключа — один блок,
строки тела без повторов; порядок — по шаблону), суммирует итоги описи. Отказ — пустой ответ той
части, которую он назвал: 3.4. Дальше — Шаг 4 по склеенным файлам, как у любого сервиса.

**Что меняется на Шаге 4 и после.**
- Маркерный гейт — **по каждой части**: `check.sh` по `part-NN.opis.md` и `part-NN.md` даёт «опись
  по классам» части, её сравниваешь с числами части из плана. Остаток гейта не получает.
- Добор — той части, чей ключ: греп ключа по `part-*.opis.md` называет номер; бриф части плюс блок
  «Добор»; правит она свои файлы. После добора — склейка заново; **перезапуск склейки бюджет не
  тратит** — бюджет считается прогонами субагентов: два на часть, остаток, голову, разведчика.
- Часть упала дважды — карточку не пиши: прежняя байт-в-байт, сервис в отчёт с номером и папками части.
- Продвижение: `bash "<…/reference/promote.sh>" "<черновик>" "<путь>"` — копия и три счёта сверки;
  копировщик-субагент на нарезанном сервисе не нужен.
- Уборка — список файлов `services/.work/<name>/*` по именам плюс пустая папка `services/.work/<name>/`.

### Шаг 4 — Сверить и записать

**Опись и черновик ты не открываешь `Read` — ни целиком, ни страницами.** Счёты по ключам даёт
скрипт скилла, одной командой:

```
bash "<абсолютный путь к reference/check.sh>" "<опись>" "<черновик>" ["<прежняя карточка>"]
```

Он печатает состав черновика по секциям (блоков и сколько с телом) и границы секций, ключи описи по классам и
строки без файла-источника, итоги `⟹`, сверку «опись → черновик» поключево (нет в черновике, нет в
описи, факт в описи — пустой блок), группы для «Что умеет», а с прежней карточкой третьим
аргументом — гард по классам и маршрут. Ещё он печатает **«Кандидаты проверок»** — строки черновика с
номерами по проверкам, привязанным к секциям: форма заголовков и код вне бэктиков в «Бизнес-правилах»,
ограничения без переключателя, код в «Назначении» и в «Что умеет», цифры в «Стеке», слипшиеся
ячейки, имена не из манифеста, хвост-файл, похожие на секрет строки, события против брокера, ручки
без `сущности:`, порядок блоков. Это кандидаты, а не вердикты: по правилам ниже решаешь ты. Что в
выводе есть — грепом не перепроверяешь. Остальные проверки — `Grep` с узким паттерном
(`output_mode="count"` либо `content` с `head_limit`). Проверка внутри одной секции — тот же `Grep`
с `-n` по всему файлу: скрипт печатает «границы секций» номерами строк, и ты берёшь совпадения в
границах своей секции. `Read` по `.work/` не нужен ни на одну строку — даже чтобы увидеть заголовок. Выводу скрипта не спорь и не перепроверяй
его чтением: открытый черновик — это пересказ себе, и следующим движением станет «поправить».
Командной строки нет — те же счёты грепом, как описано у каждой проверки; `Read` по `.work/` и
тогда не открываешь. Шаблон не открываешь: таблица классов, по которой считаются ключи, стоит ниже,
в гарде, а правила проверок — здесь.

**Порядок: сверить опись саму с собой → маркерный гейт → проверки → гард → продвижение.** Ни один
шаг не переставляется: гейты умеют сказать «добор», гард — «в `_pending`», и после продвижения оба
слова ничего не значат.

**Проверки, помеченные ГЕЙТ, блокируют продвижение; остальные — один добор или строка в отчёт.**
Ни одна проверка не даёт тебе права изменить черновик: недостающее возвращает добор — у того, у
кого код. **Добор один на все проверки:** сначала пройди все, собери всё несошедшееся в один
перечень и только потом запускай — второй прогон субагента единственный, и разменять его на первое
же расхождение значит остаться без него для остальных.

**Первое — опись сверяется сама с собой: итоговые строки `⟹` с её же списком.** Итог субагент
считает руками, и он расходится с собственным списком. Разошлись — **эталон это список**: у каждого
ключа в нём стоит файл-источник, а у числа в итоге нет ничего. Дальше считай против списка и назови
расхождение строкой в отчёте. Добора это не требует: ключи на месте, ошибка в сложении. Обе
стороны — в выводе скрипта: «итоги описи» и «опись по классам».

**Второе — маркерный гейт (ГЕЙТ): опись против кода, класс за классом, только по строкам разведчика с пометкой `ключ`.** Число ключей класса в
описи против суммы маркеров `ключ` этого класса с Шага 3.1. Опись меньше **половины** маркеров — субагент
не дочитал: добор с перечнем «класс X: по коду не меньше N, в описи M — найди недостающие, начни с
файлов, где маркер встречается». Маркер дал ноль — сверки нет (это нижняя граница; верхняя сверка
сущностей — абзацем ниже). Это единственная проверка, которая
видит недочитанный модуль **на первом скане**: все остальные сверяют субагента с его же описью, и
недочитанный модуль отсутствует в обеих.

**Детектор узкого маркера (не гейт).** Ключей класса в описи больше чем **вдвое** против его маркеров
`ключ` — значит, разведчик назвал не все пометки класса, и нижняя граница ничего не сторожит. Добора
это не требует: опись не меньше маркеров, гейт пройден. В отчёт строкой «маркер видит N из M по
описи — внешней сверки по классу X нет», числами.

**Сущности — сверка и сверху (проверка, не гейт).** Блоков `###` в «Владеет данными» не больше
суммы маркеров `ключ` класса `сущности` с Шага 3.1. Больше — субагент записал сущностями классы без маркера
хранения: добор с перечнем «`X`, `Y` — маркера хранения в коде нет: убери из «Владеет данными»,
поля — строками в блоки ручек; строку `сущности:` каждой затронутой ручки перепиши на
`→ не сущность, агрегат по …` или `→ не сущность, ответ <сервис>`». Маркер сущностей у разведчика
есть, а греп дал ноль при блоках в «Владеет данными» — добор на все блоки. Маркера сущностей
разведчик не назвал — сверки сверху нет, строка в отчёт.
Не помог добор — карточка пишется, в отчёт строкой «Владеет данными: N блоков без маркера
хранения»; прежняя карточка из-за этого не остаётся.

**Три правила обхода, общие для всех гейтов.** Каждое выглядит как аккуратность, и каждое даёт
записанную карточку, которая врёт о сервисе.

- **Число описи берётся как есть, вычитать нельзя ничего.** «Эндпоинтов 20, из них два служебных,
  значит ждём 18» — это поправка на то, чего не хватило. Уменьшил ожидаемое число, чтобы оно
  сошлось с полученным, — гейт не пройден.
- **Сверяются числа, а не объяснения.** «В карточке 42 плюс шесть не развёрнуты — значит 48» не
  сходится: **42 против 48**. Объяснённое расхождение остаётся расхождением, оно просто получило
  имя, и знаешь ты про эти шесть ровно потому, что они не доехали.
- **Недостающее не дописывается тобой.** Кода ты не видел, метода и пути не знаешь; собранный по
  имени ключа блок будет безупречен по форме и сочинён целиком, а отличить его потом нельзя
  ничем. Возвращает недостающее добор — у того, у кого код.

**Гард гейт не отменяет.** «Не хватает всего двух ключей», «гард пропустил» — не основания для
продвижения: гард ловит обвал против **прежней** карточки, а не совпадение с описью.

**Проверки — по выводу скрипта и грепом по черновику.** Каждая ниже — счёт скрипта, регэксп или
счёт грепа; где сказано «в описи» — греп по файлу описи.

**Полнотные проверки считают РАЗНОЕ, и подменять их друг другом нельзя.** Инвентарь считает
**ключи** — ловит потерянный эндпоинт. Семантика считает **факты внутри блоков** — ловит блок,
пересказывающий свой заголовок при целом ключе. Источник проверяет, что ключ вообще **есть в
коде** — ловит выдуманный. Счёт пустоты — единственный, кто не смотрит в опись вовсе.

- **Полнота инвентаря (ГЕЙТ):** сверь число ключей карточки с описью **по каждому классу
  отдельно** — эндпоинты, топики (потребляемые и публикуемые врозь), фоновые задачи, сущности,
  роли, экраны. Общее число сходится и при недоборе целого класса, если в другом нашлось лишнее.
  Числа и пары — строки скрипта: состав черновика, «опись по классам», «нет в черновике», «нет в
  описи». Ключ контракта — метод и путь (у GraphQL — тип операции и имя, у gRPC — сервис и метод):
  строка скрипта «ключи контракта без метода» непуста — эти ключи в перечень добора.

  **Ключ — это блок `###` у `backend`, `fullstack` и `lib`, но строка таблицы у `frontend`:** у
  фронта блоков нет вообще, и счёт блоков даст ноль на карточке, куда доехала половина экранов.
  Единственная секция, где часть описи законно не отражается, — «Что умеет для пользователя»:
  там сверяются группы, а не числа.

  **Класс, которого в описи нет вообще, — расхождение самое дорогое.** Опись без единого топика
  при шине в «Стеке» означает не «событий нет», а «их не искали». Это добор с явным перечнем
  маркеров, а не разрешение записать.

  **Не хватает нескольких технических ключей** (`/healthz`, `/metrics`, версия) — самый частый
  промах: ты только что решал, какие группы не дают возможностей, и по инерции вычел их отовсюду.
- **Полнота семантики (ГЕЙТ):** возьми второй уровень описи и сверь **поключево**, а не числом.
  Ключ, под которым в описи стоял факт, обязан дать строку в своём блоке. Сравнение «не меньше»:
  один факт дробится на три строки законно. Ключ с фактом в описи и пустым блоком — **добор с
  перечнем таких ключей**, не твоя дописка. Перечень — строка скрипта «факт в описи, пустой блок».

  **Ключ, у которого фактов не было и в описи, добора НЕ требует и запись не блокирует.** Заставлять
  субагента искать там, где он уже смотрел, значит покупать выдумку за лишний прогон. Такой ключ
  идёт в **список для человека** (Шаг 6).
- **Источник у каждого ключа (ГЕЙТ):** в описи против каждого ключа стоит файл. Ключ без файла —
  выдуманный: он попал в оба списка, поэтому сверку с описью проходит. Вычёркивать самому нечем
  и незачем — в перечень добора: «ключи без файла-источника: X, Y — назови файл либо убери из описи
  и из черновика». После добора инвентарь пересчитывается. Перечень — строка скрипта «строк без
  файла-источника».
- **Полнота возможностей:** группы печатает скрипт («группы черновика для «Что умеет»»), строки
  «Что умеет» достань грепом таблицы по секции, как на Шаге 5. Группы — у HTTP по префиксу пути (`/v1/incidents/*`,
  `/v1/squads/*`, `/v1/chops/*`, `/v1/reports/*`, `/v1/admin/*`, …), у GraphQL и gRPC по сущности в
  имени операции, — добавь к ним **каждую фоновую задачу и каждый
  потребляемый топик** — они группы сами по себе — и проверь, что **каждая** дала хотя бы одну
  строку в «Что умеет для пользователя». Числа тут не сойдутся — строки сворачивают по несколько
  ключей, — но непокрытых групп быть не должно. Не считаются служебные (`/healthz`, `/readyz`,
  `/metrics`, `/v1/version`), задачи без видимого человеку результата (переиндексация, чистка
  временных файлов) и публикуемые топики — их читает сосед, а не пользователь. Группа пропущена —
  верни секцию субагенту. Это самое частое место недобора: ключи считают, а возможности пишут по
  первому впечатлению. Чаще всего теряется `/v1/admin/*` и ночные задачи.
- **Секреты:** нет ли строк длиннее 20 символов, похожих на токен, ключ, пароль или base64.
  Нашёл — замени на «`ИМЯ_ПЕРЕМЕННОЙ` в `<файл>`».
- **Версии:** нет ли номеров — включая сокращённые. `React 18`, `chi v5`, `MUI 5` — это версии
  ровно так же, как `^18.3.1`. В «Стек» идут имена: `React`, `chi`, `MUI`.
- **Бизнес-правила (ГЕЙТ, `backend` и `fullstack`): пять грепов; из описи берёшь только четыре
  её строки.** Любое расхождение — добор с перечнем, и добор — это **повторный запуск субагента**:
  ни одну строку черновика ты не пишешь сам, даже «тем же содержанием» — кода ты не видел; добор правит файл сам.
  **Ответ добора проходит все пять заново**, а не только то, за что назначен.
  1. **Ключи.** Каждый `###` секции начинается с имени сущности в бэктиках, `сообщение «` или
     `ограничение «`. Иной заголовок — «письмо», «событие», подпись впереди ключа, `Сущность.поле`
     — добор. Блок объекта один на сущность.
  2. **Состав.** Блоков объектов столько, сколько сущностей в строках `состояние:`. Сообщений не
     меньше строк `сообщение:` и не меньше блоков `публикует` в «Событиях». Ограничений столько,
     сколько строк `ограничение:`. Перечисление своей сущности, не названное в описи ни
     состоянием, ни справочником, — пропущено. Чужая сущность и справочник блока не имеют.
  3. **Значения.** Форма «Владеет данными» — строки `- поле: тип`; если секция оформлена таблицей
     `| Поле | Тип |` — добор раньше всего остального. Несколько полей в одной строке `- ` — **не
     расхождение и не добор**: карточка пишется, строка в отчёт с их числом. У каждого перечисления
     значения стоят через `|` в строке `- поле:`, тип без значений — добор.
     В блоке строк не меньше, чем значений в его строках `состояние:`; строка `не определено`
     считается, а две строки с одним и тем же правилом на разных значениях — заполнитель, добор:
     форма для значения без перехода — `не определено`. Токен строки — одно из значений.
     Исключение одно — дата, которой состояние отличается, в скобках рядом с токеном
     («продлена (`active`, `expiresAt` сдвинут)»): это законно. Любое другое имя поля — строка
     на поле, добор. Два токена в одной строке через `/`, `|` или запятую — справочник,
     записанный состоянием: добор.
  4. **Код.** Вне бэктиков ни одной строки секции с ` /[a-z]`, `\b(GET|POST|PUT|PATCH|DELETE)\b`,
     `\b[a-z]+[A-Z][A-Za-z]*\b`, `\b[a-z]+(\.[a-z-]+){2,}\b`; в бэктиках — только значение
     перечисления, имя вида или топика, имя сервиса из манифеста и дата-исключение из числа 3; ни одного бэктика в заголовке
     сообщения. Не помог добор — **второй, только по этим строкам**: единственное исключение из
     бюджета, секция уезжает в бизнес-спеку дословно.
  5. **Переключатель.** В блоке ограничения назван тот, кто условие включает и выключает, и это
     имя стоит в одном из двух списков: имена из манифеста либо роли из «Роли и доступ» этой же
     карточки — два грепа. Нет ни там, ни там — добор; «внешняя система» исключением не является.
     «Внешняя конфигурация», «настройка», ключ конфига — не переключатель. `true`/`false` в блоке —
     чужой флаг записан состоянием.
- **Хвост-файл (ГЕЙТ, по карточке, все секции):** считается по черновику;
  перед продвижением найди в нём **строки, которые кончаются путём к файлу** — `имя/имя.расш`
  в конце строки, как бы он ни был обёрнут: в бэктиках, в скобках, после тире, голый. Греп вроде
  `/\S+\.[a-z]{1,5}[\`)]*\s*$` — отправная точка, а не граница: субагент оборачивает путь по-разному
  от прогона к прогону, и шаблон, требующий расширение ровно в конце строки, промахнулся на
  `` `purchases/purchases.service.ts` `` и отчитался «чисто». Нашёл — это строки описи, попавшие не в ту часть: добор с перечнем
  строк, «убрать хвост, факт оставить». Считается по карточке, потому что опись писал тот же
  субагент.
- **Кодовый регистр в «Назначении» и «Что умеет для пользователя» (проверка, не гейт):** нет путей,
  HTTP-глаголов, имён файлов и компонентов, идентификаторов в camelCase (`companyId`,
  `hasPassword`). В «Что умеет» проверяется колонка «Возможность», в «Назначении» — весь текст, и к
  списку добавляется имя сущности в бэктиках. Грепы те же, что в числе 4 гейта «Бизнес-правил».
  Нашёл — **один добор с перечнем строк**: переписать словами пользователя. Не помог — запиши
  карточку и назови число в отчёте: строка с идентификатором хуже строки без него, но карточка без
  контракта хуже обеих. Колонка «Для кого» не проверяется: имя роли — ключ,
  `business-requirements-doc` берёт его дословно намеренно.
- **Имена сервисов:** в «Зависит от» и «Потребляемых API» стоят `name` из манифеста, а не имена из
  путей, URL или комментариев (`geo`, не `geo-service`).
- **Слипшиеся строки таблиц:** в ячейке ключа стоит перечисление через запятую. Это потеря ключей:
  полнота считается по строкам, а Шаг 5 собирает зеркала построчно. Возвращает их добор с перечнем
  слипшихся строк; сам не разбивай — вызовы ты не читал. Считается **по карточке**: опись пришла от
  того же субагента, который строку и слепил.
- **События против «Стека»:** в «Событиях» есть блоки, а в «Стеке» нет ни одного брокера — это
  противоречие, и разрешается оно **не** дописыванием брокера в «Стек». Почти всегда это
  внутренняя очередь, принятая за шину: кэш, таблица задач, пул воркеров. Такие факты живут в
  «Фоновых задачах», а не в контракте наружу. Возвращает их добор, с явным перечнем блоков.
  Считается **по карточке**: обе секции достаются грепом по черновику.
- **Полнота связей:** каждый вызов, который есть в коде, есть и в карточке. Сервиса нет в
  манифесте — строка всё равно остаётся, с именем как в коде и пометкой `вне манифеста`. Выброшенная
  строка делает карточку ложной; манифест неполон намеренно, и это не повод терять факт.
- **Аббревиатуры:** доменные сокращения (`ЧОП`, `ГБР`, `ГОСБ`) не расшифрованы, если расшифровки
  нет в коде.
- **Перечни:** нет списка файлов, папок и зависимостей из манифеста пакетов.
- **Сущности у ручек:** у каждого блока «Публичного контракта», кроме служебных, стоит строка
  `сущности:` — вход и выход именами из «Владеет данными» этой же карточки. Имя, которого в списке
  сущностей нет и которое не помечено как проекция или как «не сущность», — выдумка: сверку с
  описью она проходит, потому что попала в оба списка. Строки нет — **добор у субагента с перечнем
  таких ключей**, не твоя дописка: чем ручка оперирует, видно из кода, а кода у тебя нет.
- **Порядок элементов:** внутри каждой секции блоки и строки идут по возрастанию ключа — пути
  лексикографически, имена сущностей, экранов, ролей, задач и топиков по алфавиту; в «Событиях»
  ключ начинается с направления, поэтому сначала идут все `потребляет`, потом все `публикует`
  (правило в `card.template.md`). Порядок обхода файлов от прогона к прогону не повторяется, и без
  сортировки перечитывание неизменившегося сервиса даёт дифф во всю карточку.

Порядок секций и их состав — по таблице из `reference/card.template.md`; **достань саму таблицу
грепом**, а не чтением файла целиком: тебе нужны из него шестнадцать строк, а не шестьдесят
килобайт.

```
Grep pattern="^\| `backend`" path="<абсолютный путь к card.template.md>" -A 16
```

**Вертикальную черту в начале паттерна обязательно экранируй, и контекст задавай параметром.**
`^|` — это не «строка начинается с трубы», а альтернатива с пустой левой частью: такой паттерн
совпадает с КАЖДОЙ строкой файла, и вместо пятнадцати строк ты получишь все шестьсот с лишним,
то есть тот самый файл целиком, ради необхождения которого греп здесь и стоит. Число строк
контекста — это параметр `-A`, а не текст внутри паттерна.

Не собирай порядок по памяти и не сверяй с соседней карточкой: перечитывание неизменившегося
сервиса должно давать пустой diff.

**«Заметки команды» в таблице порядка нет** — она есть у всех типов и в ветвление не входит.
Заголовков `##` при непустых `notes` **на один больше**, чем строк в колонке шаблона: это
совпадение, а не расхождение, и субагента из-за него не перезапускают.

**Счёт пустоты (ГЕЙТ) — единственное число, которое ты считаешь САМ, по карточке, а не по описи.**

Посчитай в «Публичном контракте», сколько блоков всего и у скольких есть хоть одна строка `-`
сверх назначения и строки `сущности:` — это строка скрипта «контракт N (с телом M, …)». Опись не
открывай: весь смысл в том, что число получено мимо неё.

**Тело меньше чем у половины блоков — добор**, тот же и с тем же бюджетом, что при расхождении
чисел. Не помог — прежняя карточка остаётся байт-в-байт вместе со `scanned`, а сервис идёт в отчёт
с числами: «блоков 48, тело есть у 3».

**Почему мимо описи.** Опись писал тот же субагент: недобрав факты, он недоберёт их и в описи —
числа сойдутся, и карточка, под каждым заголовком которой стоит одна строка и больше ничего,
пройдёт остальные гейты. Порог грубый намеренно: он про один исход — тело не доехало вовсе.

**Гард на утоньшение — маршрутизатор записи, а не разрешение на неё.** Он отвечает не «писать или
нет», а «куда писать», и отвечает формулой: у тебя нет места, где ты решаешь.

**Зачем он вообще.** Все проверки выше сверяют субагента с его же описью. Не дочитал модуль —
модуля нет ни в карточке, ни в описи, и числа сходятся идеально. Единственная независимая точка
отсчёта — **прежняя карточка на диске**; гард сравнивает с ней. Прежней карточки нет — гарда нет,
и от недочитанного модуля на первом скане защищает только маркерный гейт.

**Считается по ключам, по классам, по таблице — не на глаз.** Ключ — заголовок блока `###` или
названная колонка таблицы:

| Класс | Где ключ |
|---|---|
| контракт | `###` в «Публичный контракт» / «Публичный API» |
| сущности | `###` в «Владеет данными» |
| задачи | `###` в «Фоновые задачи» |
| топики | `###` в «События» (направление плюс топик) |
| экраны | первая колонка «Экраны» |
| потребляемые API | первая и вторая колонки «Потребляемые API» (сервис плюс вызов) |
| роли | первая колонка «Роли и доступ» |
| зависит от | первая колонка «Зависит от» |

**Не считаются вовсе:** «Бизнес-правила» (их заголовки меняются при приведении формы к шаблону —
это переформатирование, и оно у тебя уже гейтится против описи), «Что умеет для пользователя»
(строки, не ключи), «Кто меня потребляет» (пуста по конструкции до Шага 5). Ключ нормализуй:
без бэктиков, пробелы схлопнуты, регистр HTTP-глагола приведён к верхнему.

По каждому классу `c` возьми множества ключей прежней карточки и черновика и посчитай **было_c,
исчезло_c, появилось_c**. Дополнительно по каждому классу с блоками: **опустело_c** — ключ цел, тело
блока было непустым, стало пустым (по счёту строк `- ` под заголовком). Эти числа с именами
печатает `check.sh`, когда третьим аргументом передана прежняя карточка, — решает по ним формула:

**Правило маршрута — одно на все классы:**

```
В _pending, если хоть у одного класса c:
    (исчезло_c ≥ 3  и  3·исчезло_c > было_c)
 или (опустело_c ≥ 3  и  3·опустело_c > было_c)
Иначе — ПОВЕРХ.
```

Три ключа из четырёх — `_pending` (3 ≥ 3, 9 > 4); три из десяти — поверх (9 не больше 10); два из
восьмидесяти девяти — поверх; тридцать три из сорока восьми — `_pending`; один из двух — поверх, с
именем в отчёте. Оба условия считай числами, не на глаз. Слов «законно», «форма», «урезали», «не
дочитал» в правиле нет — и в твоём рассуждении их быть не должно: ты не отличишь одно от другого,
потому что кода не видел, а решение, принятое вслепую, останавливало годные карточки и всё равно
обходилось рассуждением.

- **ПОВЕРХ** → продвижение в `services/<name>.md`. Исчезнувшие и опустевшие ключи — **именами в
  отчёт** (Шаг 6), сколько бы их ни было. Названная именами потеря молчаливой не является.
- **В _pending** → продвижение в **`services/_pending/<name>.md`**. Прежняя карточка остаётся
  **как есть: `scanned` не двигается, ни одна секция из кода не трогается** — прочтения, которому
  можно верить, не состоялось. Единственное, что в ней меняет этот прогон, — «Кто меня
  потребляет» на Шаге 5, как у всех карточек слепка. В отчёт —
  строка `ГАРД` с числами и именами и вопрос человеку: урезали сервис или скан не дочитал?
  Принять кандидата — переместить файл поверх; отклонить — удалить. **Ты сам ни того, ни другого
  не делаешь** и в `_pending/` ничего не правишь: это его решение, и он принимает его тогда, когда
  читает отчёт, а не посреди прогона.

Работа субагента не теряется ни при каком исходе — и поэтому нет мотива обходить гард.

**Появилось ≈ исчезло по одному классу** (например, весь контракт сменил префикс) — это
переименование, а не потеря; правило всё равно отправит в `_pending`, и строка отчёта обязана это
назвать: «появилось 96, исчезло 96 — похоже на переименование».

**И восстанавливать из прежней карточки ничего не смей.** Прежнюю карточку ты не склеиваешь с
черновиком и строк из неё не переносишь. Правило прежней формулировки на Шаге 3 — не то же самое:
там прежний текст читает субагент, у которого есть код. Здесь у тебя кода нет, и любая перенесённая
тобой строка — утверждение о сервисе, которого ты не видел.

**Продвижение — копия черновика без единого изменения, туда, куда указал гард.** Копирует
субагент-копировщик — **того же типа, что читающий субагент** (у него есть `Write`; отдельного
типа «копировщик» искать не надо), со свежим контекстом и одной задачей: «прочитай файл `<черновик>` целиком и
запиши его без изменений в `<путь>`; ничего не правь, не сокращай, не форматируй». Нет такого
субагента — копируй сам, `Read` целиком и `Write` как есть. После копии — **три грепа со счётом по
обоим файлам**: `^### `, `^\| ` и `^` — заголовки, строки таблиц и все строки вообще. Все три числа
равны — готово; хоть одно нет — вторая копия;
и вторая разошлась — черновик остаётся в `.work/`, сервис в отчёт как незаписанный. Рабочие файлы
`.work/` здесь не удаляй: они ещё нужны Шагу 6 для списка «фактов нет», а убирает их уборщик в
конце прогона — всё разом.

**Гард ловит потерю КЛЮЧЕЙ. Потерю ФАКТОВ внутри уцелевших ключей он видит только грубо — как
опустело_c.** Опустевшие ключи, не дотянувшие до `_pending`, идут в отчёт отдельной строкой: это
изменение между двумя сканами, и значит оно либо что фичу убрали из кода, либо что скан не
дочитал. Различить может только тот, кто знает, что релизили, — и это не ты.

## Что решить

Как читать этот сервис дальше.

Реши по правилам выше, что ты делаешь дальше. Ответ — в таком виде:
1. Разбор: что видишь и какое правило из текста выше применяешь — коротко.
