**1. Ключи.** Заголовки секции: `` `Shipment` `` (сущность в бэктиках), «сообщение «груз доставлен»», «ограничение «приём отправлений партнёра отключён»» — все три формы допустимы, других заголовков нет. Сошлось.

**2. Состав.** Опись: состояний 1, сообщений 1, ограничений 1, справочников 2. Карточка: 1 блок сущности (`Shipment`, у неё есть `состояние:`), 1 блок сообщения (= 1 строка `сообщение:` = 1 `публикует` в «Событиях»), 1 блок ограничения; `Attachment` (только справочник) и `packageType` (справочник у Shipment) блоков не имеют — верно по правилу «справочник блока не имеет». Сошлось.

**3. Значения.** Форма `- поле: тип` соблюдена (не таблица). Строка `состояние:` даёт 5 значений (NEW|ASSIGNED|DELIVERED|CANCELLED|LOST) — в блоке `Shipment` ровно 5 строк, токены `NEW`, `ASSIGNED`, `DELIVERED`, `CANCELLED`, `LOST` — каждый ровно одно из значений, два `не определено` — законная форма для отсутствующего перехода, дублей правил на разных значениях нет. Сошлось.

**4. Код.** Вне бэктиков в секции «Бизнес-правила» проверил все 4 паттерна (путь со слэшем, HTTP-глагол, camelCase, точечный ключ из ≥3 частей) — совпадений нет; в бэктиках встречаются только значения перечисления (`NEW`…) и имя сервиса из манифеста (`partner-registry`) и имя топика (`shipment.delivered`) — только имя топика/сервиса/значение, как разрешено; в заголовке сообщения бэктиков нет. Сошлось.

**5. Переключатель.** Блок ограничения называет `partner-registry` — это имя есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`), второй список (роли) не нужен, так как первый уже дал совпадение. Сошлось.
