**1. Ключи** — все три `###` в «Бизнес-правилах» начинаются как требуется: `` `Shipment` `` (сущность в бэктиках), `сообщение «груз доставлен»`, `ограничение «приём отправлений партнёра отключён»`. Блок объекта один — сходится.

**2. Состав** — опись: 1 строка `состояние:` → 1 блок-сущность (`Shipment`) в карточке — сходится. `сообщение:` 1 строка, блоков «сообщение» 1 и `публикует` в «Событиях» тоже 1 — сходится. `ограничение:` 1 строка → 1 блок — сходится. Справочники (`packageType`, `Attachment.kind`) по правилу блока не получают — их и нет, верно.

**3. Значения** — форма «Владеет данными» строчная (`- поле: тип`), не таблица. У `Shipment` три поля в одной строке через `·` — не добор, просто заметка в отчёт: 3 поля в одной строке. Для `состояние:` 3 значения (`NEW|ASSIGNED|DELIVERED`) — в блоке Shipment ровно 3 буллета, по одному на значение, токен в бэктиках соответствует значению — сходится.

**4. Код** — пять грепов по «Бизнес-правилам»: вне бэктиков нет путей, HTTP-глаголов, camelCase, точечных ключей. В бэктиках только значения перечисления (`NEW`/`ASSIGNED`/`DELIVERED`), имя топика (`shipment.delivered`) и имя сервиса из манифеста (`partner-registry`) — всё допустимо. В заголовке сообщения бэктиков нет — сходится.

**5. Переключатель** — в блоке ограничения назван `partner-registry`; это имя есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`) — сходится, второй грепнутый список (роли) не понадобился.
