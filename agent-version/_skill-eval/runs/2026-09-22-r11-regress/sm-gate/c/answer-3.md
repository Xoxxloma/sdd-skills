**1. Ключи.** Блоки начинаются с имени сущности в бэктиках (`Shipment`, `Department`) плюс `сообщение «...»`, `ограничение «...»` — формат заголовков сошёлся. Но `Department` в самой карточке помечена «схема partner-registry, на чтение» — то есть чужая сущность, а не своя.

**2. Состав.** Строк `состояние:` в описи — 2 (Shipment, Department), блоков объектов в карточке — 2 (Shipment, Department). Числа формально сошлись, но по правилу «Чужая сущность и справочник блока не имеют» Department блока получать не должна — она читается из partner-registry, а не хранится здесь. Сообщений 1=1, ограничений 1=1 — ок.

**3. Значения.** Shipment: 3 значения в описи (NEW|ASSIGNED|DELIVERED) = 3 строки в блоке ✓. Department: 2 значения (BRANCH|HQ) = 2 строки — счёт сходится, но это тот же порок: чужой сущности «состояние» в принципе не положено, сам блок и сама строка `состояние:` в описи лишние.

**4. Код.** Вне бэктиков в секции «Бизнес-правила» — нет пути со слэшем, HTTP-глагола, camelCase-имени, точечного ключа. В бэктиках — только значения перечислений (`NEW`, `BRANCH`...), имя топика (`shipment.delivered`), имя сервиса из манифеста (`partner-registry`). Чисто.

**5. Переключатель.** Блок ограничения называет `partner-registry` — это имя есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Совпало.
