**1. Ключи.** Все три `###` в «Бизнес-правилах» начинаются как требуется: `` `Shipment` `` (имя сущности), «сообщение «груз доставлен»», «ограничение «приём отправлений партнёра отключён»». Блок объекта один на сущность (только Shipment). Сошлось.

**2. Состав.** Опись: состояние — 1 (Shipment), справочников — 2, сообщений — 1, ограничений — 1. Карточка: блоков-объектов в «Бизнес-правилах» — 1 (Shipment, по числу строк `состояние:`); сообщений — 1 строка + 1 `публикует` в «Событиях»; ограничений — 1. Справочники (`Shipment.packageType`, `Attachment.kind`) блоков не получили — верно, им блок не положен. Сошлось.

**3. Значения — не сошлось.** Блок «Владеет данными» для `Shipment` оформлен таблицей `| Поле | Тип | Описание |`, а не строками `- поле: тип`, как того требует шаблон. Это прямое основание для добора «раньше всего остального». Заодно: поле `status` в этой таблице указано типом `ShipmentStatus` без перечня значений — тип без значений тоже добор; значения `NEW | ASSIGNED | DELIVERED` из описи в «Владеет данными» не попали (они есть только в тексте «Бизнес-правил», а не в строке поля).

**4. Код.** Вне бэктиков — только слова и статусы в скобках-бэктиках (`NEW`, `ASSIGNED`, `DELIVERED`), в бэктиках — только значения перечисления, имя топика `shipment.delivered` и имя сервиса `partner-registry` из манифеста. Ни путей, ни HTTP-глаголов, ни camelCase, ни dotted-конфигов. Сошлось.

**5. Переключатель.** В блоке ограничения назван `partner-registry` — есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
