Ключи.** Три заголовка секции «Бизнес-правила»: `` `Shipment` — отправление``, `сообщение «груз доставлен»`, `ограничение «приём отправлений партнёра отключён»` — все начинаются с сущности в бэктиках либо служебного слова. Блок один на сущность (только `Shipment`, у которой есть `состояние:`). Сошлось.

**2. Состав.** Блоков объектов 1 = строк `состояние:` в описи (1, Shipment). Сообщений 1 = строк `сообщение:` (1) = блоков «публикует» в «Событиях» (1, `shipment.delivered`). Ограничений 1 = строк `ограничение:` (1). Справочник `Attachment.kind`, названный в описи справочником, а не состоянием, своего блока в «Бизнес-правилах» не получил — верно. Сошлось.

**3. Значения.** Блок `Shipment` в «Бизнес-правилах» — 3 строки на 3 значения состояния (`NEW`/`ASSIGNED`/`DELIVERED`), по строке на значение — форма верна. Но секция «Владеет данными» для `Shipment` в карточке оформлена **таблицей** `| Поле | Тип | Описание |`, а не строками `- поле: тип`, как требует форма — это прямой триггер: «секция оформлена таблицей — добор раньше всего остального». Не сошлось.

**4. Код.** Прогнал пять грепов по секции «Бизнес-правила»: вне бэктиков нет ни ` /[a-z]`, ни HTTP-глаголов, ни camelCase, ни составных `a.b.c`-ключей. В бэктиках — только значения перечисления (`NEW`, `ASSIGNED`, `DELIVERED`), топик `shipment.delivered` и имя сервиса `partner-registry` из манифеста — всё допустимо, в заголовке сообщения бэктиков нет. Сошлось.

**5. Переключатель.** Ограничение называет `partner-registry` — есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
