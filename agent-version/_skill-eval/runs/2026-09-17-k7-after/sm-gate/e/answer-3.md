## Проверка по пяти числам

**(1) Блоки объектов = сущности из `состояние:`.** В описи одна строка `состояние:` (Shipment.status) → должен быть один блок объекта. В карточке ровно один блок объекта — `Shipment`; `Attachment` (только `справочник: Attachment.kind`) блока не получил — верно. Плюс по блоку на `сообщение:` (1) и `ограничение:` (1) — есть оба. Сошлось.

**(2) Строк в блоке объекта ≥ значений в `состояние:`.** У Shipment.status три значения (`NEW | ASSIGNED | DELIVERED`), в блоке `Shipment` три строки (новое/назначено/доставлено). Сошлось: 3 = 3.

**(3) Токены в блоках объектов — значения из «Владеет данными».** В блоке `Shipment` токены `NEW`, `ASSIGNED`, `DELIVERED` — все стоят справа от `:` в `- status: NEW | ASSIGNED | DELIVERED`. Ни одного токена-поля, ни одного выдуманного. Сошлось.

**(4) Блоков сообщений ≥ блоков `публикует` и ≥ строк `сообщение:`.** В «Событиях» один `публикует shipment.delivered`, в описи одна строка `сообщение:` — блок сообщения один, по счёту сошлось. Но заголовок блока — `### сообщение «`shipment.delivered`»` — содержит бэктик внутри заголовка вместо слов (в описи повод назван словами: «груз доставлен»). Это прямой добор по правилу гейта: «Бэктик внутри заголовка `сообщение «…»` — добор: заголовок пишется словами, токен стоит в строке». Не сошлось.

**(5) Блоков ограничений = строк `ограничение:`.** Одна строка `ограничение:` — один блок. В блоке нет `true`/`false`, условие названо словами («приём отправлений партнёра отключён... новые отправления не принимаются»), управляющий назван — `partner-registry`, сервис есть в манифесте. Сошлось.

Четыре числа из пяти совпали, пятое (сообщения) — совпало по счёту, но заголовок оформлен неверно (бэктик вместо слов).
