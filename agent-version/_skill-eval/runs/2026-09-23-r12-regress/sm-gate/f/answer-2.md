**1. Ключи.** Три заголовка секции: `` `Shipment` `` — отправление, `сообщение «груз доставлен»`, `ограничение «приём отправлений партнёра отключён»` — все три формы верны (имя сущности в бэктиках / «сообщение «» / «ограничение «»). Сошлось.

**2. Состав.** Опись даёт 1 строку `состояние:` (Shipment) → в карточке 1 блок сущности (`Shipment`); Attachment — только справочник, блока не имеет — верно. Сообщений: 1 строка `сообщение:` и 1 `публикует` в «Событиях» → 1 блок сообщения в карточке. Ограничений: 1 строка `ограничение:` → 1 блок. Сошлось.

**3. Значения.** «Владеет данными» — форма `- поле: тип`, не таблица, перечисления через `|` — верно. Блок `Shipment` в «Бизнес-правилах»: три строки на три значения состояния (`NEW`/`ASSIGNED`/`DELIVERED`) — токены совпадают, ок. Но четвёртая строка — «тип упаковки (`BOX` / `PALLET`) — задаётся при создании» — два токена в одной строке через `/`. Это ровно случай «справочник, записанный состоянием» — расхождение.

**4. Код.** Вне бэктиков во всей секции «Бизнес-правила» ни одного пути, HTTP-глагола, camelCase-токена или точечного ключа; в бэктиках — только значения перечислений (`NEW`, `ASSIGNED`, `DELIVERED`, `BOX`, `PALLET`) и имя сервиса из манифеста (`partner-registry`), топик `shipment.delivered` в бэктиках допустим. Заголовки сообщения/ограничения без бэктиков. Сошлось.

**5. Переключатель.** Ограничение называет `partner-registry` — есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.

ГЕЙТ: ДОБОР — в блоке `` `Shipment` `` секции «Бизнес-правила» переписать строку «тип упаковки (`BOX` / `PALLET`) — задаётся при создании»: два токена справочника через `/` в одной строке — это справочник, записанный как состояние (правило гейта Шага 4, п.3). Строку убрать или переписать без объединения двух значений в одной строке — справочник `packageType`, от значений которого не зависит ни одно правило, места в блоке бизнес-правил состояния не имеет.
