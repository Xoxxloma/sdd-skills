**Проверка гейта «Бизнес-правила» — `shipping`**

1. **Ключи.** Три `###`: `` `Shipment` `` — отправление; «сообщение «груз доставлен»»; «ограничение «приём отправлений партнёра отключён»». Все три формы соблюдены (сущность в бэктиках / «сообщение «» / «ограничение «»), блок объекта один на `Shipment`. Сошлось.

2. **Состав.** Опись: состояний 1, сообщений 1, ограничений 1. Карточка: блоков-сущностей 1 (`Shipment`), сообщений 1, ограничений 1 — по числу совпало. `packageType` и `Attachment.kind` — справочники, блоков не получили, как положено. Перечислимых полей своей сущности вне состояния/справочника не осталось непокрытых. Сошлось.

3. **Значения.** «Владеет данными» — форма `- поле: тип`, не таблица. У `status` (3 значения: `NEW`/`ASSIGNED`/`DELIVERED`) в блоке 4 строки — не меньше значений, ок. Строки «назначено» и «переназначено» держат один токен `ASSIGNED` дважды, но «переназначено (`ASSIGNED`, `assignedAt` сдвинут)» — это ровно санкционированное исключение «дата, которой состояние отличается» из правила, а не заполнитель. Двух токенов через `/`,`|`,`,` в одной строке нет. Сошлось.

4. **Код.** Вне бэктиков во всей секции «Бизнес-правила» — только кириллица, ни одного совпадения с ` /[a-z]`, `GET|POST|PUT|PATCH|DELETE`, camelCase, `a.b.c…`. В бэктиках — только значения перечисления (`NEW`,`ASSIGNED`,`DELIVERED`), топик (`shipment.delivered`), имя сервиса из манифеста (`partner-registry`) и поле `assignedAt` как часть санкционированного дата-исключения. В заголовке сообщения бэктиков нет. Сошлось.

5. **Переключатель.** Блок ограничения называет `partner-registry` — это имя есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
