**Проверка гейта «Бизнес-правила» — сервис `shipping`**

1. **Ключи.** Три `###`: `` `Shipment` `` — отправление, `сообщение «груз доставлен»`, `ограничение «приём отправлений партнёра отключён»` — все три формы верны (сущность в бэктиках / «сообщение «» / «ограничение «»), без посторонних подписей и без `Сущность.поле` в заголовке. Блок объекта один — на `Shipment`. Сошлось.

2. **Состав.** Опись даёт 1 строку `состояние:` (Shipment) → в карточке 1 блок объекта (Shipment), не 0. Сообщений в описи 1, публикаций в «Событиях» 1 → в карточке 1 блок сообщения. Ограничений в описи 1 → в карточке 1 блок. `Attachment` (только справочник) блока не получил — верно. Сошлось.

3. **Значения.** «Владеет данными» в форме `- поле: тип`, не таблица. У `status`, `packageType`, `kind` значения через `|`. В блоке `Shipment` 3 строки на 3 значения состояния (`NEW`/`ASSIGNED`/`DELIVERED`), каждая — свой токен, без заполнителей и без двойных токенов через `/`,`|`,`,`. Сошлось.

4. **Код.** Вне бэктиков в секции «Бизнес-правила» нет путей, HTTP-глаголов, camelCase или точечных ключей (текст на кириллице/прозой); в бэктиках только значения состояния, имя топика `shipment.delivered` и имя сервиса `partner-registry` из манифеста — всё допустимо. Заголовок сообщения без бэктиков. Сошлось.

5. **Переключатель.** В блоке ограничения назван `partner-registry` — это имя есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
