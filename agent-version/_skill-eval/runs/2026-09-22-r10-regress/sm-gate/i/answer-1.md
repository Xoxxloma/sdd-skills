**1. Ключи.** Три заголовка секции «Бизнес-правила»: `\`Shipment\`` (сущность), `сообщение «груз доставлен»`, `ограничение «приём отправлений партнёра отключён»` — все три формы верные, по одному блоку на сущность. Сошлось.

**2. Состав.** Опись: состояний 1 (Shipment) → в карточке 1 блок-сущность. Сообщений: строка `сообщение:` (1) и блок `публикует` в «Событиях» (1) → в карточке 1 блок сообщения. Ограничений: строка `ограничение:` (1) → 1 блок. Справочники (`packageType`, `Attachment.kind`) своих блоков не получили — верно. Сошлось.

**3. Значения.** «Владеет данными» → `Shipment` оформлен **таблицей** `| Поле | Тип | Описание |`, а не строками `- поле: тип` — по правилу это добор раньше всего остального. Дополнительно: `status: ShipmentStatus` в таблице дан без перечня значений через `|` в самой строке (значения `NEW | ASSIGNED | DELIVERED` есть только в тексте «Бизнес-правил», а не в блоке владения данными) — тоже нарушение формы. `Attachment` оформлен верно (`- kind: PHOTO | PDF`). Не сошлось.

**4. Код.** Вне бэктиков в секции «Бизнес-правила» нет пути с ` /[a-z]`, HTTP-глагола, camelCase или составного dotted-ключа; в бэктиках — только значения перечисления (`NEW`, `ASSIGNED`, `DELIVERED`), топик (`shipment.delivered`) и имя сервиса из манифеста (`partner-registry`). Заголовок сообщения без бэктиков. Сошлось.

**5. Переключатель.** Блок ограничения называет `partner-registry` — есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.
