**1. Ключи.** Все три заголовка секции — `` `Shipment` `` в бэктиках, «сообщение «...»», «ограничение «...»» — форма верна, блок объекта один (Shipment), у Attachment блока нет (корректно, у него только справочник, не состояние). Сошлось.

**2. Состав.** Блоков-объектов по строкам `состояние:` — 1 (Shipment), в карточке 1 блок `Shipment` — сошлось. Сообщений: 1 строка в описи, 1 блок `публикует` в «Событиях», 1 блок в «Бизнес-правилах» — сошлось. Ограничений: 1 = 1 — сошлось. **Но:** в «Владеет данными» у `Shipment` есть перечисление `priority: NORMAL | URGENT` — это перечисление СВОЕЙ сущности, а в описи оно не названо ни строкой `состояние:`, ни строкой `справочник:` (в описи справочников заявлено 2 — `packageType` и `Attachment.kind` — `priority` среди них нет). По правилу это «пропущено» — расхождение.

**3. Значения.** Форма «Владеет данными» — строки `- поле: тип`, не таблица — верно. У `status` (состояние) в блоке 3 строки на 3 значения (`NEW`/`ASSIGNED`/`DELIVERED`) — сошлось, токены — ровно значения. Форма перечислений через `|` соблюдена везде, включая спорный `priority`. Сама по себе форма не нарушена, но по п.2 сущность `priority` не имеет права быть в карточке без строки в описи.

**4. Код.** В тексте секции вне бэктиков не встречается ни `GET/POST/...`, ни camelCase, ни путей с `/`, ни точечных ключей — в бэктиках только значения перечислений (`NEW`, `ASSIGNED`, `DELIVERED`), имя топика (`shipment.delivered`) и имя сервиса из манифеста (`partner-registry`). Сошлось.

**5. Переключатель.** В блоке ограничения назван `partner-registry` — он есть в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`). Сошлось.

ГЕЙТ: ДОБОР — перечень: в описи не хватает строки `справочник: Shipment.priority NORMAL | URGENT — <файл>` (или, если это не факт из кода, поле `priority` нужно убрать из «Владеет данными» карточки) — правь ОБА файла (опись и черновик), чтобы состав ключей совпал.
