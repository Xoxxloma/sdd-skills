1. **Ключи.** Все три `###` в «Бизнес-правилах» начинаются как положено: `` `Shipment` `` (сущность), `сообщение «груз доставлен»`, `ограничение «...»`. Блок объекта один — на `Shipment`. Сошлось.

2. **Состав.** Опись: `состояние:` — 1 строка (Shipment) → 1 блок-объект в карточке. `сообщение:` — 1 строка, «публикует» в «Событиях» — 1 блок → 1 блок сообщения. `ограничение:` — 1 строка → 1 блок ограничения. Числа сошлись (справочники блоков не получают — верно, их и нет).

3. **Значения.** «Владеет данными» — в форме `- поле: тип`, не таблица. У `Shipment.status` в описи 3 значения — в блоке ровно 3 строки, каждая на своём токене (`NEW`/`ASSIGNED`/`DELIVERED`), без слипшихся значений через `/`. Сошлось.

4. **Код.** Прогнал все четыре регэкса по тексту секции «Бизнес-правила» вне бэктиков — совпадений нет (camelCase, пути, HTTP-глаголы, точечные ключи отсутствуют); в бэктиках только значения перечисления и топик `shipment.delivered`; в заголовке сообщения бэктиков нет. Сошлось.

5. **Переключатель.** У ограничения назван «АС Каскад» — это внешняя система, которой нет ни в списке манифеста (`shipping`, `partner-registry`, `dispatch-web`), ни в «Роли и доступ» (`DISPATCHER`, `COURIER`). Не сошлось: переключатель не найден ни там, ни там, а «внешняя система» исключением не является.

Дополнительно: сама классификация ошибочна ещё на уровне описи — по правилам описи «формат файла... — НЕ ограничение: их место — строка ошибки в „Публичном контракте“», а здесь это ровно проверка формата загрузки. То есть строка `ограничение:` в описи вообще не должна была появиться.
