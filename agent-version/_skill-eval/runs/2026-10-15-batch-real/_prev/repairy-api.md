Роли раздаёт он же: UserRole на компанию, ProjectMemberRole на проект.

## Назначение

Сервис позволяет ремонтной компании вести объекты ремонта целиком: смету по комнатам и видам работ, закупки, платежи заказчика и фактический прогресс. Заказчик видит ход работ и принимает выполненные работы актами приёмки, а команда и заказчик получают уведомления о событиях проекта. Процессы: регистрация и вход (в том числе через Telegram), приглашение сотрудников и заказчиков, ведение сметы и закупок, приёмка работ, обсуждение в комментариях, выгрузка сметы. Главные объекты: компании, проекты, комнаты и группы работ, работы сметы, закупки, акты приёмки, комментарии и документы проекта.

## Бизнес-правила

### `EstimateChangeLog` — запись журнала изменений сметы
- работа добавлена (`WORK_ADDED`) — при добавлении работы в комнату; в записи сумма изменения и итог сметы после него
- работа удалена (`WORK_REMOVED`) — при удалении работы; сумма изменения отрицательная
- работа изменена (`WORK_UPDATED`) — при правке работы, только если её стоимость (цена за единицу на объём) действительно поменялась
- покупка добавлена (`PURCHASE_ADDED`) — при добавлении покупки в проект
- покупка удалена (`PURCHASE_REMOVED`) — при удалении покупки
- итог сметы после изменения — сумма всех работ и всех покупок проекта
- работа добавлена (`WORK_ADDED`) — при добавлении работы в комнату; сумма изменения равна цене за единицу, умноженной на объём; пачка работ даёт одну запись на всю пачку
- работа удалена (`WORK_REMOVED`) — сумма изменения отрицательная; удаление комнаты вместе с её работами записи не создаёт
- работа изменена (`WORK_UPDATED`) — только если стоимость позиции изменилась; правка одного названия или срока записи не даёт; сдвиг выполненного объёма записи не даёт
- закупка добавлена (`PURCHASE_ADDED`) — при добавлении закупки и при переводе позиции списка покупок в закупку; правка суммы существующей закупки записи не создаёт, импорт сметы из таблицы записи не пишет
- закупка удалена (`PURCHASE_REMOVED`) — сумма изменения отрицательная

### `Project` — объект ремонта
- активен (`ACTIVE`) — состояние по умолчанию при создании проекта
- приостановлен (`PAUSED`) — переводится при правке проекта; ограничений на порядок переходов в коде нет
- завершён (`COMPLETED`) — переводится при правке проекта; ограничений на порядок переходов в коде нет
- в архиве (`ARCHIVED`) — переводится при правке проекта; ограничений на порядок переходов в коде нет
- активен (`ACTIVE`) — так проект создаётся и вручную, и импортом сметы; только активные проекты идут в сводку по компании
- на паузе (`PAUSED`) — выставляют владелец или прораб проекта, обновляя проект; ограничений на переход из любого статуса в код не заложено
- завершён (`COMPLETED`) — так же вручную; сама приёмка работ статус проекта не меняет
- в архиве (`ARCHIVED`) — так же вручную

### `ProjectCustomer` — доступ заказчика к проекту
- приглашён (`acceptedAt` пуст) — заказчика приглашают в проект по e-mail
- принят (`acceptedAt`) — заказчик принял приглашение; повторное принятие безопасно и лишь обновляет дату
- удалён (`removedAt`) — принятого заказчика убирают из проекта; доступ закрывается сразу, ссылка-приглашение гасится
- не приглашённого до конца заказчика удаляют физически, а не помечают
- ранее удалённого заказчика повторное приглашение оживляет: пометка удаления снимается, принятие сбрасывается
- ожидает принятия — запись с адресом приглашённого и без пользователя; создаёт прораб проекта или владелец, отправив приглашение на почту; повторное приглашение на тот же адрес отвергается; письмо можно отправить ещё раз с тем же одноразовым кодом; такую запись удаляют совсем
- принят (есть дата принятия) — заказчик переходит по ссылке из письма или по общей ссылке проекта; после ссылки из письма код и адрес приглашения стираются, после общей ссылки остаются; повторный переход по общей ссылке только обновляет дату принятия
- удалён (есть дата удаления) — заказчик вышел сам или его убрал прораб либо владелец; запись остаётся, одноразовый код сбрасывается; проект ему больше не виден; по общей ссылке вернуться нельзя, новое приглашение на почту запись оживляет и сбрасывает принятие

### `User` — пользователь
- приглашён (`invitedAt`, `acceptedAt` пуст) — сотрудника пригласили по e-mail; пока приглашение не принято, имя равно e-mail, пароля нет
- приглашён повторно (`invitedAt` обновлён) — приглашение в ту же компанию перевыпускается с новой ссылкой
- принят (`acceptedAt`) — сотрудник перешёл по ссылке; ссылка после этого гаснет и повторно не работает

### `WorkAcceptance` — акт приёмки работ
- ждёт рассмотрения (`PENDING`) — создаёт владелец или сотрудник; заказчику создавать нельзя; номер акта следующий по порядку в проекте
- рассмотрен (`REVIEWED`) — решение принимает только заказчик, сразу по всем работам акта; рассмотреть повторно нельзя
- ждущий акт можно отозвать, и он удаляется; рассмотренный отозвать нельзя
- при создании, рассмотрении и отзыве акта участники проекта получают уведомление

### `WorkAcceptanceItem` — работа в акте приёмки
- ждёт решения (`PENDING`) — работа попала в акт
- принята (`ACCEPTED`) — заказчик принял работу; работа становится принятой, менять в ней выполненный объём нельзя
- отклонена (`REJECTED`) — заказчик не принял работу; она снова доступна для отправки в новый акт, комментарий заказчика сохраняется

### `WorkItem` — работа в смете
- не отправлена на приёмку (`NONE`) — состояние по умолчанию; отправить можно только работу, выполненную на 100% и принадлежащую этому проекту
- на приёмке (`PENDING`) — работа вошла в акт; удалить её нельзя, пока акт не рассмотрен или не отозван
- принята (`ACCEPTED`) — заказчик принял работу; выполненный объём больше менять нельзя
- отказ заказчика и отзыв акта возвращают работу в `NONE`

### сообщение «акт приёмки отозван»
- когда `OWNER` или `EMPLOYEE` отзывает ещё не рассмотренную заявку; получают участники проекта, владелец компании и принявшие заказчики, кроме самого отозвавшего и тех, кто отключил уведомления
- уходит сразу, без задержки; текст называет номер акта; канал у каждого свой — почта, Telegram или push; не больше 10 таких уведомлений в час на получателя, остальные отбрасываются
- повод: отзыв акта приёмки; вид `ACCEPTANCE_REVOKED`; получают участники проекта, владелец компании и принявшие приглашение заказчики, кроме автора и отключивших уведомления
- заголовок «Акт приёмки отозван в «<проект>»», текст «<автор> отозвал(а) <пояснение>» или «<автор> отозвал(а) акт приёмки»; уходит без задержки

### сообщение «заказчик принял приглашение»
- после принятия заказчиком приглашения на проект по e-mail; получает сам заказчик; не отправляется, если у пользователя нет e-mail

### сообщение «изменена смета»
- повод: добавлена, изменена или удалена работа либо закупка, позиция списка покупок переведена в закупку; вид `ESTIMATE_CHANGED`; получатели те же, что у остальных уведомлений проекта, кроме автора изменения
- заголовок «Изменена смета «<проект>»», текст «<автор> изменил(а) смету — <название>»; ждёт три минуты, однотипные склеиваются с пометкой «(+N изм.)»; не больше десяти в час на получателя, лишние теряются

### сообщение «код подтверждения удаления аккаунта»
- когда пользователь запросил удаление аккаунта или повторную отправку кода; получает сам пользователь; на почту, а если почты нет — в Telegram
- код действует 15 минут; повторная отправка выдаёт тот же код
- при запросе удаления аккаунта и при повторной отправке кода; получает сам пользователь на e-mail; код из шести цифр действует 15 минут, повторная отправка не меняет код, а продлевает срок; если e-mail нет, но привязан Telegram, код уходит туда, а не письмом

### сообщение «новый комментарий»
- когда кто-то написал комментарий в проекте или в комнате; получают участники проекта, владелец компании и принявшие заказчики, кроме автора и отключивших уведомления
- несколько комментариев склеиваются: уведомление уходит через 45 секунд после последнего и несёт его текст с пометкой, сколько было ещё; не больше 10 в час на получателя
- повод: в проекте оставлен комментарий; вид `COMMENT_ADDED`; получатели те же, кроме автора
- заголовок «Новый комментарий в «<проект>»», текст «<автор>: <текст>» или «<автор> оставил(а) комментарий»; ждёт 45 секунд, однотипные склеиваются; не больше десяти в час на получателя

### сообщение «новый платёж»
- когда в проекте зарегистрирован платёж; получатели те же, что у комментария, без внёсшего платёж
- склейка и лимит как у комментариев: 45 секунд, не больше 10 в час; в тексте сумма в рублях
- повод: в проекте зарегистрирован платёж; вид `PAYMENT_REGISTERED`; получатели те же, кроме автора
- заголовок «Новый платёж в «<проект>»», текст «<автор> зарегистрировал(а) платёж — <пояснение>»; ждёт 45 секунд, однотипные склеиваются

### сообщение «обновлён прогресс»
- повод: у работы изменён выполненный объём; вид `PROGRESS_UPDATED`; получатели те же, кроме автора
- заголовок «Обновлён прогресс в «<проект>»», текст «<автор> отметил(а) выполнение — <название работы>»; ждёт две минуты, однотипные склеиваются; не больше десяти в час на получателя

### сообщение «приветствие заказчику»
- когда заказчик принял приглашение в проект и получил аккаунт или вошёл в существующий; получает сам заказчик на почту
- сбой отправки приём приглашения не отменяет

### сообщение «приветствие нового сотрудника»
- когда сотрудник принял приглашение в компанию; получает сам сотрудник на почту; в письме название компании и логин
- сбой отправки приём приглашения не отменяет

### сообщение «приветствие после регистрации»
- когда человек зарегистрировался по почте и паролю; получает он сам; в письме логин и напоминание про восстановление пароля
- при создании аккаунта через Telegram не отправляется
- после регистрации по e-mail и паролю; получает сам пользователь, в письме его логин; имя в письме экранируется; сбой отправки регистрацию не отменяет

### сообщение «приглашение заказчика на проект»
- когда заказчика приглашают на проект по e-mail и когда приглашение отправляют повторно; получает приглашённый заказчик; повторно нельзя отправить уже принятое приглашение

### сообщение «приглашение заказчику»
- повод: прораб проекта или владелец приглашает заказчика по адресу почты или пересылает приглашение ещё раз; получает приглашённый на этот адрес
- тема «Вас приглашают следить за ремонтом — <проект>», в письме кнопка «Принять приглашение» со ссылкой с одноразовым кодом; уходит без ожидания, сбой отправки отправителю не виден и только пишется в журнал

### сообщение «приглашение сотрудника в компанию»
- когда владелец приглашает сотрудника или переотправляет приглашение; получает приглашённый на почту; в письме название компании и ссылка для создания аккаунта
- при переотправке прежняя ссылка перестаёт работать; сбой отправки приглашение не отменяет, владелец о нём не узнаёт
- когда сотрудника приглашают в компанию по e-mail и при повторной отправке (ссылка заменяется новой); получает приглашённый; повторно нельзя пригласить сотрудника, уже активировавшего аккаунт

### сообщение «приёмка рассмотрена»
- когда заказчик рассмотрел заявку на приёмку; получают участники проекта и владелец компании, кроме самого заказчика и отключивших уведомления
- уходит сразу; текст называет номер акта; не больше 10 в час на получателя
- повод: акт приёмки рассмотрен; вид `ACCEPTANCE_REVIEWED`; получатели те же, кроме автора
- заголовок «Приёмка работ рассмотрена в «<проект>»», текст «<автор> рассмотрел(а) приёмку — <пояснение>» или «<автор> рассмотрел(а) акт приёмки»; уходит без задержки

### сообщение «работы отправлены на приёмку»
- когда создана заявка на приёмку; получают участники проекта, владелец компании и принявшие заказчики, кроме автора заявки и отключивших уведомления
- уходит сразу; текст называет номер акта; не больше 10 в час на получателя
- повод: работы отправлены на приёмку; вид `ACCEPTANCE_CREATED`; получатели те же, кроме автора
- заголовок «Работы отправлены на приёмку в «<проект>»», текст «<автор> отправил(а) работы на приёмку — <пояснение>»; уходит без задержки

### сообщение «сброс пароля»
- когда запрошена ссылка сброса пароля и аккаунт с такой почтой существует; получает владелец аккаунта на почту; ссылка действует 1 час
- для неизвестной почты ничего не уходит, а ответ тот же, что для известной
- по запросу восстановления пароля, только если пользователь с таким e-mail найден; получает сам пользователь; ссылка действует 1 час

### сообщение «сотрудник принял приглашение»
- после принятия сотрудником приглашения в компанию по e-mail; получает сам сотрудник; в письме название компании и логин

### сообщение «уведомление о событии»
- когда очередь уведомлений доставляет событие (`COMMENT_ADDED`, `PROGRESS_UPDATED`, `ESTIMATE_CHANGED`, `PAYMENT_REGISTERED`) получателю с выбранным каналом `EMAIL`; письмо с заголовком и текстом уведомления; без e-mail у получателя не уходит

## Публичный контракт

### `DELETE /api/auth/account`
Удаление собственного аккаунта по коду подтверждения.
сущности: ← `DeleteAccountDto` (поле `code`) · → ничего
- ответ `204` без тела; нужен вход и действует общий лимит запросов
- код подтверждения нужен всем ролям, хотя описание в swagger обещает «без кода» для `EMPLOYEE` и `CUSTOMER`
- ошибки: `400` — код неверный или истёк; сообщение «Неверный или истёкший код подтверждения»
- код гасится до удаления: если удаление упало, код потрачен и запрашивать его надо заново
- `OWNER` без компании (не прошёл онбординг): удаляется только пользователь
- `OWNER` с компанией, одной транзакцией: сотрудники-`EMPLOYEE` отвязываются от компании и остаются аккаунтами, удаляются все проекты компании (вместе с комнатами, работами, комментариями, платежами, закупками, журналом сметы), каталог компании, сама компания и пользователь
- `EMPLOYEE`: в проектах, где он `FOREMAN` и других `FOREMAN` не остаётся, прорабом становится `OWNER` компании; затем пользователь удаляется
- `CUSTOMER`: его строки доступа к проектам остаются, но теряют пользователя; затем пользователь удаляется
- все refresh-сессии пользователя удаляются; уже выданный access-токен перестаёт работать сразу, потому что пользователь перечитывается из БД
- комментарии и платежи удалённого пользователя остаются, автор показывается как «Удалённый пользователь» (`id` и `avatarUrl` — `null`)

## Фоновые задачи

### `flush`
Рассылка накопленных уведомлений из очереди.
- расписание `*/30 * * * * *` (каждые 30 секунд)
- записи очереди лежат в Redis; задача забирает их атомарно, поэтому несколько экземпляров не шлют дубль; запись, у которой задержка не истекла, возвращается обратно
- задержка по виду: `COMMENT_ADDED` 45 секунд, `PROGRESS_UPDATED` 120, `ESTIMATE_CHANGED` 180, `PAYMENT_REGISTERED` 45, `ACCEPTANCE_CREATED`, `ACCEPTANCE_REVIEWED`, `ACCEPTANCE_REVOKED` без задержки
- события одного вида одному получателю в одном проекте склеиваются в одно сообщение с пометкой «(+N изм.)»
- не больше 10 сообщений в час на получателя и вид события, остальные отбрасываются без повтора
- канал получателя: `WEB_PUSH`, `TELEGRAM` (нужны telegramId и токен бота, иначе сообщение молча пропускается) или почта; сбой отправки не повторяется
- отправка пачками по 5 штук; запись очереди живёт 600 секунд, дольше не ждёт
- защиты от наложения прогонов в коде нет; пропущенный прогон не догоняется, накопленное берёт следующий
- получатели: участники проекта, владельцы компании и заказчики, принявшие приглашение; автор события и отключившие уведомления исключаются

## Владеет данными

### `Comment`
Комментарий к проекту или комнате.
- `id`: `string`
- `projectId`: `string`
- `roomId`: `string?`
- `authorId`: `string?`
- `text`: `string`
- `createdAt`: `timestamp`
— `roomId` пуст у комментария ко всему проекту
— `authorId` обнуляется, когда автора удалили

### `CommentAttachment`
Вложение к комментарию.
- `id`: `string`
- `commentId`: `string`
- `url`: `string`
- `fileType`: `PHOTO` \| `VIDEO` \| `DOCUMENT`
- `createdAt`: `timestamp`
— удаляется вместе с комментарием

### `Company`
Компания-подрядчик: владелец проектов и сотрудников.
- `id`: `string`
- `name`: `string`
- `email`: `string?`
- `phone`: `string?`
- `logoUrl`: `string?`
- `createdAt`: `timestamp`

### `EstimateChangeLog`
Журнал изменений сметы проекта.
- `id`: `string`
- `projectId`: `string`
- `type`: `WORK_ADDED` \| `WORK_REMOVED` \| `WORK_UPDATED` \| `PURCHASE_ADDED` \| `PURCHASE_REMOVED`
- `entityName`: `string`
- `delta`: `decimal`
- `totalAfter`: `decimal`
- `createdById`: `string?`
- `createdAt`: `timestamp`
— `totalAfter` считается как сумма всех работ и покупок проекта на момент записи
— `createdById` обнуляется, когда автора удалили
— индекс по проекту и дате создания, свежие первыми

### `Project`
Объект ремонта компании.
- `id`: `string`
- `companyId`: `string`
- `name`: `string`
- `address`: `string`
- `latitude`: `float?`
- `longitude`: `float?`
- `coverPhotoUrl`: `string?`
- `status`: `ACTIVE` \| `PAUSED` \| `COMPLETED` \| `ARCHIVED`
- `inviteToken`: `string`
- `publicToken`: `string`
- `createdAt`: `timestamp`
- `updatedAt`: `timestamp`
- `deadlineAt`: `timestamp?`
— `inviteToken` и `publicToken` уникальны, создаются автоматически; `inviteToken` заказчику в ответах не показывается
— `publicToken` открывает проект без входа

### `ProjectCustomer`
Доступ заказчика к проекту.
- `id`: `string`
- `projectId`: `string`
- `userId`: `string?`
- `guestEmail`: `string?`
- `emailInviteToken`: `string?`
- `invitedAt`: `timestamp`
- `acceptedAt`: `timestamp?`
- `removedAt`: `timestamp?`
— уникальна пара проект + пользователь
— `userId` пуст, пока приглашённый по e-mail не принял приглашение
— `emailInviteToken` уникален и обнуляется при принятии и при удалении

### `ProjectDocument`
Документ проекта.
- `id`: `string`
- `projectId`: `string`
- `name`: `string`
- `url`: `string`
- `uploadedById`: `string?`
- `createdAt`: `timestamp`
— `uploadedById` обнуляется, когда загрузившего удалили

### `ProjectMember`
Участник проекта со своей ролью в нём.
- `id`: `string`
- `projectId`: `string`
- `userId`: `string`
- `role`: `FOREMAN` \| `WORKER`
- `specialty`: `string?`
— уникальна пара проект + пользователь
— удаляется вместе с проектом и вместе с пользователем

### `ProjectPayment`
Оплата по проекту.
- `id`: `string`
- `projectId`: `string`
- `amount`: `decimal`
- `note`: `string?`
- `createdById`: `string?`
- `createdAt`: `timestamp`
— `createdById` обнуляется, когда автора удалили

### `Purchase`
Покупка материалов по проекту.
- `id`: `string`
- `projectId`: `string`
- `name`: `string`
- `totalCost`: `decimal`
- `createdById`: `string?`
- `createdAt`: `timestamp`
— `createdById` обнуляется, когда автора удалили

### `PurchaseReceipt`
Чек к покупке.
- `id`: `string`
- `purchaseId`: `string`
- `url`: `string`
- `createdAt`: `timestamp`
— удаляется вместе с покупкой

### `PushSubscription`
Подписка браузера на push-уведомления.
- `id`: `string`
- `userId`: `string`
- `endpoint`: `string`
- `p256dh`: `string`
- `auth`: `string`
- `createdAt`: `timestamp`
— `endpoint` уникален
— подписка с ответом `410` от push-сервиса удаляется

### `Room`
Комната или группа работ проекта.
- `id`: `string`
- `projectId`: `string`
- `name`: `string`
- `type`: `ROOM` \| `WORK_GROUP`
- `area`: `decimal?`
- `sortOrder`: `int`
- `createdAt`: `timestamp`
— `type` по умолчанию `ROOM`; `sortOrder` по умолчанию 0

### `RoomPhoto`
Фото комнаты.
- `id`: `string`
- `roomId`: `string`
- `url`: `string`
- `uploadedBy`: `string?`
- `createdAt`: `timestamp`
— `uploadedBy` обнуляется, когда загрузившего удалили

### `ShoppingItem`
Позиция списка покупок проекта.
- `id`: `string`
- `projectId`: `string`
- `name`: `string`
- `quantity`: `float?`
- `unit`: `string?`
- `createdById`: `string?`
- `createdAt`: `timestamp`
— хранится в таблице `shopping_items`
— `createdById` обнуляется, когда автора удалили

### `User`
Пользователь: владелец, сотрудник или заказчик.
- `id`: `string`
- `companyId`: `string?`
- `email`: `string?`
- `phone`: `string?`
- `name`: `string`
- `avatarUrl`: `string?`
- `role`: `OWNER` \| `EMPLOYEE` \| `CUSTOMER`
- `passwordHash`: `string?`
- `telegramId`: `bigint?`
- `notificationsEnabled`: `boolean`
- `notificationChannel`: `EMAIL` \| `TELEGRAM` \| `WEB_PUSH`
- `createdAt`: `timestamp`
- `invitedAt`: `timestamp?`
- `acceptedAt`: `timestamp?`
- `emailInviteToken`: `string?`
— `email`, `telegramId` и `emailInviteToken` уникальны
— `passwordHash` пуст у приглашённого сотрудника и у вошедшего через Telegram; наружу хеш не отдаётся, вместо него признак «пароль задан»
— `telegramId` наружу отдаётся строкой
— `notificationsEnabled` по умолчанию включено; выключенному уведомления не рассылаются
— `notificationChannel` по умолчанию `EMAIL`; при подписке на push переключается на `WEB_PUSH`
— `acceptedAt` пуст, пока приглашённый сотрудник не принял приглашение

### `WorkAcceptance`
Акт приёмки работ.
- `id`: `string`
- `projectId`: `string`
- `number`: `int`
- `status`: `PENDING` \| `REVIEWED`
- `note`: `string?`
- `createdById`: `string?`
- `createdAt`: `timestamp`
- `reviewedAt`: `timestamp?`
— хранится в таблице `work_acceptances`
— уникальна пара проект + номер; номер следующий за последним в проекте, при одновременном создании второй запрос получает `409` и должен повторить попытку
— `reviewedAt` ставится заказчиком при рассмотрении
— `createdById` обнуляется, когда автора удалили

### `WorkAcceptanceItem`
Строка акта: одна работа и решение по ней.
- `id`: `string`
- `acceptanceId`: `string`
- `workId`: `string`
- `roomName`: `string`
- `status`: `PENDING` \| `ACCEPTED` \| `REJECTED`
- `comment`: `string?`
- `reviewedAt`: `timestamp?`
— хранится в таблице `work_acceptance_items`
— уникальна пара акт + работа
— `roomName` — название комнаты на момент создания акта, не меняется при переименовании комнаты
— `comment` — пояснение заказчика к решению

### `WorkCatalogItem`
Позиция справочника работ.
- `id`: `string`
- `companyId`: `string?`
- `category`: `string`
- `name`: `string`
- `defaultUnit`: `string`
- `defaultPrice`: `decimal?`
- `sortOrder`: `int`
— `companyId` пуст у общей позиции, доступной всем компаниям; компания видит общие и свои

### `WorkItem`
Работа в смете комнаты.
- `id`: `string`
- `roomId`: `string`
- `catalogItemId`: `string?`
- `name`: `string`
- `unit`: `string`
- `pricePerUnit`: `decimal`
- `totalVolume`: `decimal`
- `completedVolume`: `decimal`
- `sortOrder`: `int`
- `acceptanceState`: `NONE` \| `PENDING` \| `ACCEPTED`
- `createdAt`: `timestamp`
- `updatedAt`: `timestamp`
- `deadlineAt`: `timestamp?`
— `completedVolume` по умолчанию 0 и не может превышать `totalVolume`; у принятой работы не меняется
— `acceptanceState` по умолчанию `NONE`; в `PENDING` работу переводит создание акта, в `ACCEPTED` — решение заказчика, назад в `NONE` — отказ заказчика или отзыв акта
— `catalogItemId` пуст у работы, добавленной не из справочника

|---|---|
| `CUSTOMER` | роль пользователя на уровне компании: заказчик; вступает в проект по приглашению (`join` только для него), принимает или отклоняет работы в актах приёмки; создавать и менять акты не может |
| `EMPLOYEE` | роль пользователя на уровне компании: сотрудник; работает в проектах, где он участник, создаёт и отзывает акты приёмки; каталог и сотрудников компании не ведёт |
| `FOREMAN` | роль участника на уровне проекта (ProjectMemberRole): прораб; вместе с владельцем добавляет участников проекта и меняет их роли; при уходе единственного прораба из проекта прорабом становится владелец |
| `OWNER` | роль пользователя на уровне компании: владелец; создаёт компанию, ведёт каталог работ, приглашает и убирает сотрудников, смотрит аналитику, работает с актами приёмки |
| `WORKER` | роль участника на уровне проекта (ProjectMemberRole): рабочий; при уходе сотрудника из компании его членство в проектах компании удаляется |
| `без входа` | публичная страница проекта по `publicToken`: сводка проекта, контакт компании и общие суммы; скрыты цены по отдельным работам, список заказчиков и телефоны участников |
