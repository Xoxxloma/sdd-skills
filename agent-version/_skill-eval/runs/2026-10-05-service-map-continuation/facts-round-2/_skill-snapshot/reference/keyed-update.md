# Быстрое обновление карточки по задетому

Флаг: в запуске есть **подсказка «Задето»** — что изменила уехавшая работа, по сервисам. Её собирает
`archive-spec` из архивируемых спек. Этот файл читаешь вместе с `SKILL.md`; **где правила расходятся,
старше этот.**

Зачем режим. Полный скан перечитывает сервис целиком, чтобы подтвердить, что почти всё осталось
прежним: на repairy это 25–30 минут, и рескан поверх прежней карточки меняет в технической части
0–1 % строк. Быстрое обновление читает и переписывает только задетое, остальное не трогает.

## Когда режим, когда полный путь

- Сервис есть в подсказке и у него есть карточка → **быстрое обновление**.
- Карточки нет; в карточке нет секции, которую шаблон требует для её типа, или секция не в форме
  шаблона (таблица в «Владеет данными», ключ не в начале заголовка); `type` в манифесте не
  совпадает с `type` карточки → **полный путь** (Шаг 3 как обычно), причину — строкой в отчёт.
- Сервис передан именем, но в подсказке его нет → полный путь.
При техническом отказе или переполнении читающего действуют те же два запуска на автора.
После второго отказа не повторяй инвентаризацию: сохрани материалы и назови необходимость полного
скана. Полный путь не запускается скрыто как третья попытка быстрого режима.
Быстрое обновление правит карточку, а не собирает её: без прежней карточки или с карточкой старой
формы править нечего и не во что.

## Что такое подсказка

Слова спеки, а не ключи карточки: «напомнить заказчику о заявке на приёмку», «сущность приёмки —
новое поле». Путь в спеке мог быть спроектирован до кода и в другой форме, а у существующих систем
его там нет вовсе. **Ключи находит субагент по коду; подсказка говорит только, где искать.** Ни одна
строка подсказки в карточку не попадает — карточка по-прежнему пишется только по коду.

## Субагент — что добавить к брифу Шага 3

Бриф Шага 3 остаётся целиком: пути, тип, имена сервисов, путь к шаблону, три правила, путь к прежней
карточке с тремя её правилами, «Заметки команды» не выводит. Добавь:

1. **Строки подсказки по этому сервису — дословно.**
2. **Порядок работы — вместо «сначала перепись, потом карточка»:**
   - **а. Опись ключей всего сервиса — только первый уровень:** ключ — файл, по всем классам шаблона
     (эндпоинты, топики, фоновые задачи, сущности, экраны, вызовы, роли, строки `состояние:`,
     `справочник:`, `сообщение:` и `ограничение:`), с итогами `⟹` по классам. Фактов второго уровня здесь нет — ради этого режим и
     быстрее. Служебные ключи в описи есть, как всегда.
   - **б. Сопоставление:** каждую строку подсказки — к ключам описи, которые она задевает, или
     `не найдено`. Сопоставляй по коду, а не по буквам подсказки.
   - **в. Сверка с прежней карточкой** (открывай её только после «а»): ключи описи, которых в
     карточке нет, — `появились`; ключи карточки, которых нет в описи, — `исчезли`.
   - **г. Задетые ключи** — из «б» плюс `появились`. По ним — второй уровень описи и блоки или строки
     карточки по шаблону. Кроме них: блоки «Бизнес-правил» задетых сущностей; **все блоки сообщений
     «Бизнес-правил»** — виды сообщений спека не называет, а модуль отправки небольшой; строки «Что
     умеет» тех групп, куда попал задетый ключ; строки «Зависит от» и «Потребляемых API» для задетых
     вызовов.
   - **д. Правило прежней формулировки** — для каждого возвращаемого блока, как в Шаге 3: факты по
     коду те же — верни прежний текст дословно.
3. **Ответ** начинается эхо-строкой `шаблон прочитан, тип: <type>; прежняя карточка: есть; режим: по
   задетому` и дальше идёт пятью разделами:

```
## ОПИСЬ КЛЮЧЕЙ     первый уровень всего сервиса, итоги ⟹ по классам
## СОПОСТАВЛЕНИЕ    строка подсказки → ключи | не найдено
## ИЗМЕНЕНИЯ        появились: …   исчезли: …
## ОПИСЬ ЗАДЕТЫХ    второй уровень — только по задетым ключам
## ПРАВКИ           заменено N, добавлено M, исчезнувших оставлено K — с перечнем ключей (в запасном пути без права записи — `## БЛОКИ`: возвращаемые блоки под заголовками секций, в форме шаблона)
```

Задетых ключей нет (всё `не найдено`, ничего не появилось и не исчезло) — раздел «БЛОКИ» пуст, и это
законный исход: карточка остаётся как есть, в отчёте — строки подсказки без ключей.

## Ведущий — проверки

Эхо-строки нет, пустой ответ, ответ без описи — как в Шаге 3: перезапуск, бюджет тот же, два прогона
субагента на сервис. Добор — как в Шаге 3: тот же промпт плюс список задетых ключей, которые не
развёрнуты.

- **Направленная сверка — проверка по всей карточке.** Ключ с источником найден в описи,
  блока нет — подтвердить по коду и добавить в пределах добора. Нет пары описи у имеющегося
  блока — справка, не причина дописывать опись. Строка без источника не доказывает пропуска;
  совпавшую строку без источника нужно проверить. Расхождение счётов само по себе не гейт.
- **Гард на утоньшение — по `исчезли`, но мягче, чем в Шаге 4.** Исчезнувший ключ без ответа человека
  не удаляешь; остальные правки записываешь; в отчёт — имена исчезнувших и совет полного скана.
  Почему не «не пишешь вовсе», как в Шаге 4: здесь нетронутое остаётся на месте, тихой потери нет —
  исчезнувший ключ просто стоит в карточке, пока человек не решит.
- **Только по задетым блокам:** полнота семантики (второй уровень против блока), источник у ключа,
  сущности у ручек, хвост-файл, счёт пустоты (порог — половина **задетых** блоков), секреты, версии,
  кодовый регистр, слипшиеся строки.
- **По всей карточке, механически:** «Бизнес-правила» сверяются по источникам и ключам,
  число публикуемых событий не требует выдумывать сообщения; имена сервисов в задетых строках; порядок элементов в каждой секции, куда
  вставлял.

## Субагент — запись; ведущий — только грепы

Сначала подготовь копию прежней карточки в отдельной `.work`-папке этого запуска, через
`promote.sh <прежняя> <подготовленная копия> <run-id>`. До успешной сверки, переноса ограничений
и продвижения рабочая карточка остаётся прежней. Субагент получает путь к копии для правок.

**Копию правит субагент, блок за блоком, через `Edit`; ведущий текст карточки не набирает.** Это
то же разделение, что и в полном пути (Шаг 3): у кого код — у того и запись. Раздел «БЛОКИ» в ответе
субагента заменяется отчётом о правках, а сами правки он вносит в подготовленную копию:

- блок заменён: `old_string` — прежний блок целиком, от его заголовка `### ` до следующего
  заголовка; `new_string` — новый блок;
- новый ключ — вставка перед блоком со следующим по порядку ключом либо в конец секции;
- строка таблицы — так же, строкой;
- **исчезнувший ключ не удаляется** — остаётся в карточке, имя идёт в отчёт, решает человек;
- шапка: при реальном изменении `updated: <дата запуска>` — добавить или заменить; `scanned`, `description`, «Назначение» и
  «Заметки команды» не трогать.

Ответ субагента заканчивается разделом `## ПРАВКИ: заменено N, добавлено M, исчезнувших оставлено K`
с перечнем ключей. Ведущий по нему и по файлу считает проверки выше — грепами, как в Шаге 4, — и
нигде не открывает карточку целиком. Не сошлось — добор с перечнем, тем же субагентом, через `Edit`.

**Субагента с правом записи нет** — запасной путь тот же, что в Шаге 3: субагент возвращает раздел
`## БЛОКИ`, ведущий вносит их через `Edit` как есть, ни слова не меняя. `Write` целиком не вызывается.

Проверь подготовленную копию по направленной сверке и задетым блокам. Нетронутые блоки,
`notes` и `scanned` должны совпасть с исходником байт-в-байт. Сохрани полный TSV; для ограничения
области составь пары `класс<TAB>ключ` задетых блоков. `quality.sh <копия> <TSV> <дата> "задето"
<выбранные пары>` обновляет только их предупреждения, затем проверки повторяются и
`promote.sh <копия> services/<name>.md <run-id>` сохраняет результат. Сбой оставляет исходник
и рабочие файлы. Ноль реальных изменений — исходник и `updated` остаются прежними.

**Шаг 5 — только если изменились «Потребляемые API» или «Зависит от».** Тогда секцию «Кто меня
потребляет» у названных сервисов пересобираешь, как в Шаге 5, через `Edit`. Карточка, изменённая
только в этой секции, `updated` не получает: это производная секция, а не прочитанный код.

## Какие правила `SKILL.md` в этом режиме заменены

- «карточка собирается заново» → подготовленная копия меняется только по задетым блокам и
  продвигается после проверок; прежняя карточка сохраняется при отказе, рабочие файлы остаются в `.work/`;
- «прежнюю карточку не склеиваешь с черновиком и строк из неё не переносишь» (гард, Шаг 4) → нетронутые
  блоки ты не переносишь, а оставляешь на месте: они такие, какими их прочитал прошлый скан;
- «пять полей, больше ничего» → шесть: плюс `updated`;
- «`scanned` — единственная отметка о свежести» → две: `scanned` — последний полный скан, `updated` —
  последнее быстрое обновление;
- «карточка описывает рабочую копию на дату `scanned`» → кроме ключей, перечитанных быстрым
  обновлением: они — на дату `updated`.

## Отчёт — вместо Шага 6 для этих сервисов

По каждому сервису:

```
repairy-api — быстрое обновление (updated 2026-10-01; полный скан — 2026-07-01)
  по подсказке: «напомнить о приёмке» → POST /projects/:pid/acceptances/:id/remind
                «новое поле приёмки» → WorkAcceptance
                «экспорт в CSV» → не найдено (не уехало или названо иначе?)
  появились 1, исчезли 0; блоков заменено 3, добавлено 1
```

Строк `не найдено` больше половины подсказки или появившихся и исчезнувших ключей больше десяти —
добавь строку: «карточка заметно разошлась с кодом — нужен полный скан: `service-map <имя>` без
подсказки». Решает человек.

Заверши строкой о свежести: быстрое обновление перечитало только задетое; всё остальное в карточке —
на дату `scanned`. Полный скан — раз в квартал или когда отчёт это советует.
