# Приёмка готовой карточки

Этот контракт общий для одного читающего и нарезки. Ведущий проверяет файлы скриптами и передаёт
содержательные вопросы читающему; факты за него не сочиняет.

`check.sh` с `CHECK_REPORT=<полный TSV>` и `CHECK_LISTS=<перечень добора>` сохраняет все ключи и
кандидаты проверок, даже если краткий stdout показывает только первые 40 имён или 15 строк.
Существование указанного файла само по себе не доказывает истинность факта.
Если собран manifest объявлений, передай его в `CHECK_DECLARATIONS`: независимая диагностика
попадёт в этот же полный TSV, включая объявления, отсутствующие и в описи, и в карточке.
Для нарезки сверка всех первичных частей и остатка выполняется до общей волны добора;
последующая сверка собранного файла — контроль без третьей попытки.

| Сверка | Действие |
|---|---|
| Ключ с источником есть в описи, блока нет | Добор ключа по источнику |
| Факт в описи, блок пуст | Добор факта |
| В факте описи указан HTTP-код, в непустом блоке его нет | Кандидат частичной потери: читающий сверяет условие и ответ по источнику |
| Блок есть, пары в описи нет | Справка; опись ради этого не дописывать |
| Строка описи без пары и без источника | Справка, пропуск не доказан |
| Совпавший ключ описи без источника | Подтвердить по файлу либо снять неподтверждённое |
| Тип операции, дубль, заголовок, регистр, связи, хвост-файл | Проверка по источнику; кандидат не означает удаления |
| Пустой блок без найденного факта | Ограничение; автоматического добора ради заполнения нет |
| Несколько возможных пар разных классов | Не проверено; не угадывать класс |

Собери все исправляемые пункты в один добор на автора. Всего два запуска на автора, включая
перезапуск пустого ответа; отдельное уже описанное исключение для регистра бизнес-правил сохраняется.
После бюджета оставшиеся пункты становятся ограничениями. Расхождение описи не запрещает запись.
Кандидаты частичной потери входят в эту же волну добора, а не запускают третью попытку.
Проверка HTTP-кодов не сравнивает смысл всего текста и не доказывает полноту остальных фактов.

Только три независимые проверки направляют готовую карточку в `_pending`:

1. Тело не доехало: у блочного контракта меньше половины оцениваемых уникальных блоков с фактами.
   Frontend-таблицы этой формулой не проверяются. Назначение, `сущности:`, заглушки — не факты.
   Оцениваемые — число контрактов минус явно подтверждённые служебные блоки, напечатанные отдельно
   в `доставка тела`. Ноль оцениваемых блоков запрета не даёт. Имя с `health`/`version` не исключение:
   нужна пометка `(фактов нет — служебный)` в обоих файлах и источник у ключа описи.
2. Маркерный провал: в карточке меньше половины надёжных маркеров `ключ` класса. Счёт из
   `уникальные ключи карточки`, для частей — из их карточек; опись на него не влияет.
   Нулевой счёт, неизвестный счёт и `ориентир` запрета не дают. Если разведчик надёжно разделил
   REST / GraphQL / RPC, сравни протоколы отдельно; без такого счёта предел сверки назови в отчёте.
3. Гард: для класса `(исчезло ≥ 3 и 3·исчезло > было)` или `(опустело ≥ 3 и 3·опустело > было)`.

| После допустимых попыток | Исход |
|---|---|
| Кандидат готов, три проверки пройдены | Записать `services/<name>.md`; ограничения остаются видны |
| Кандидат готов, любая из трёх проверок не пройдена | Сохранить кандидат в `_pending`, прежнюю карточку оставить |
| Нет файлов или склейка отказала | Прежнюю оставить; существующие рабочие файлы сохранить |
| Копия отказала | Прежнюю оставить; черновик и диагностику сохранить |

На первом сборе непринятый готовый кандидат тоже сохраняется. Рядом с ним сохраняются полный
TSV и текст сверки, а при маркерном провале — числа разведчика, счётчика и плана, ожидаемое и
фактическое. Самого `check.sh` для объяснения маркерного провала недостаточно.

Дата фиксируется при начале запуска. Новый запуск получает отдельный идентификатор и рабочую
папку: прежние файлы той же даты не являются свежими только по дате. Переход полуночи дату не меняет.
Неразобранные кандидаты не затираются. `promote.sh <черновик> <путь> <run-id>` при коллизии в
`_pending` выбирает `<name>.<run-id>.md`, затем числовой суффикс; фактический путь напечатан в
`КОПИЯ ВЕРНА`. Диагностику сохраняй рядом с этим фактическим файлом.

Перед продвижением `quality.sh <черновик> <полный TSV> <дата> "полный скан"` сохраняет ограничения
в генерируемом блоке карточки; затем `check.sh` повторяется. При частичной проверке нужен отдельный
TSV выбранных пар `класс<TAB>ключ`: снимаются только ограничения этих пар, остальные сохраняют
исходные дату и область. Отказ вставки сохраняет черновик и диагностику, продвижения нет.

Продвижение — `promote.sh`, атомарная копия с проверкой байтов. Уборщику передаются только файлы
с подтверждённым сохранением карточки и диагностики; файлы любого незаписанного сервиса не удаляются.
