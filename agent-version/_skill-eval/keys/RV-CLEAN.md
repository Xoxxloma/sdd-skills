# Фикстура RV-CLEAN — отрицательный контроль для `spec-review`

Три артефакта задачи `RMS-4021`, написанные **по текущим шаблонам без единого нарушения**.
Ожидаемый результат ревью на каждом — `нарушений: 0`.

Фикстура нужна ровно затем, зачем в этой репе заводят отрицательные контроли: инструмент, который
красит верную работу, перестают запускать после третьего ложного срабатывания. Существующие
фикстуры на эту роль не годятся — `AR-BASIC` и родня написаны до правок шаблона: там нет §5.2,
§5.3, §6.3–§6.5, зато есть удалённая §2.5, и на текущем чек-листе они законно светятся.

Стек и предметная область (бронирование переговорных) намеренно не совпадают ни с одной другой
фикстурой набора: иначе слабая модель читает кейс фикстуры как предписание.

## Что лежит

| Файл | Роль |
|---|---|
| `docs/RMS-4021/business_requirements.md` | БТ: 2 FR, у каждого критерий, §4.5 «не применимо» с причиной, статус «Готово к оценке», открытых вопросов нет |
| `docs/RMS-4021/technical_specification.md` | Спека: все секции шаблона на месте, статус «Готово к разработке», §8 пуст |
| `docs/RMS-4021/stages/stage-01.md` | Файл задачи: отвечает на все десять вопросов исполнителя |

## Чего в фикстуре нет намеренно

- **Конкретики под «🟡 к валидации»** — такой карточки здесь вовсе нет. Единственная карточка существующего — INT-2,
  и она `подтверждено аналитиком`, где конкретный путь законен.
- **Пометок происхождения без значения** — у обеих INT-карточек и у сущности §3.2 пометка стоит.
- **Пустых секций** — нерелевантные (§4.4, §6 приложений БТ) закрыты формулой «не применимо: причина».

## Одна ожидаемая ненулевая строка

У спеки счётная строка обязана быть **1**:

```
утверждений, стоящих только на памяти аналитика: 1
```

Это INT-2 — законная метка `🔵 подтверждено аналитиком` с конкретным путём `GET /api/v2/calendar/events`.
Она не нарушение и в перечень идти не должна. Если ревью выносит её в список нарушений — это
ложное срабатывание, то есть красный.

## Три ловушки этой фикстуры

1. **Легенда в шапке спеки несёт `❓`** (`❓ — открытое архитектурное решение.`) при статусе
   «Готово к разработке». Это словарь пометок, стоящий по шаблону в каждой спеке, а не открытая
   развилка: пункт 10 чек-листа на нём сработать не должен. Сработал — ложное срабатывание.
   Оговорка внесена в чек-лист 2026-08-05 после статического ревью, до этого пункт красил бы
   **любой** корректный документ.
2. **§4.5 БТ — «не применимо: причина» вместо таблицы слайсов.** Законный ответ: деливербл один.
   Проверка «FR попал в слайс» к такому БТ не применяется — таблицы нет по построению.
3. **INT-2 — законная 🔵 с конкретным путём** (см. выше): счётная строка, не перечень.

## Все три файла — отрицательные контроли

До 2026-08-05 контроль на шум был только у спеки. Теперь евалы `bt-clean` и `stage-clean` гоняют
по этой же фикстуре БТ и файл задачи: у БТ ожидается `нарушений: 0`, у файла задачи —
`ответов из файла: 10 из 10`, «без ответа: нет», «секций не хватает: нет». Без них уровень ложных
тревог двух чек-листов из трёх был неизвестен, а самый шумный по своей природе пункт набора —
именно в БТ (он реагирует на любое техническое имя).

## Парная фикстура

`RV-DIRTY` — те же три артефакта с известными внесёнными нарушениями. `RV-LOOP` — та же спека с
дефектом живого прогона петли (🟢 без транспорта, без примера, без авторизации). Ключи ответов
там же.
