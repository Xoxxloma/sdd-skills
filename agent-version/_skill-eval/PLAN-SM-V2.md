## Б. Паритет с v1 — причины и исправления

Симптомы (разбор 2026-10-22): фронт → `_pending` («контракт 0 из 24», стенд 2026-10-20); у `fullstack` вызовы
API фронта раздувают «контракт»; нарезка `frontend`/`fullstack`/`lib` теряет «Экраны», «Состояние и
данные», «Публичный API»; клиентская спека соседа при неназванной серверной идёт в сверку → добор «найди
обработчик и допиши блок» на чужие операции. У v1 этой механики нет — нет и отказов.

### К1. Нет одного описания формы по типу → одна таблица в `keys.awk`

Причина: скрипты не знают, какие секции у типа и какие из них умеет нарезка. Знание «секция → класс»
уже живёт двумя копиями (`cls()` в `check.sh`, `kcls()` в `assemble.sh`), «секции частей» — регэкспом в
`assemble.sh`, «тип → секции» — только в шаблоне. Поэтому `plan.sh` считает и режет фронт как бэкенд.

Исправление — `keys.awk`, блок «Форма по типу» (подключают `check.sh`, `assemble.sh`, теперь и `plan.sh`):
- `k_cls(sec)` — секция → класс (`Публичный контракт`/`Публичный API` → `контракт`, `Владеет данными` →
  `сущности`, `Фоновые задачи` → `задачи`, `События` → `топики`, `Экраны` → `экраны`, `Бизнес-правила` →
  `бизнес`, `Роли и доступ` → `роли`, `Зависит от` → `зависит`, `Потребляемые API` → `потребляет`,
  `Состояние и данные` → `состояние`);
- `k_partsec(sec)` — секции, которые пишут части нарезки: `Публичный контракт`, `Владеет данными`, `События`,
  `Фоновые задачи`, `Потребляемые API` (как в брифе части);
- `k_typesecs(type)` — секции классов у типа, как таблица порядка шаблона: `backend` — контракт, события,
  задачи, данные; `frontend` — экраны, потребляемые API, состояние и данные; `fullstack` — все семь; `lib` —
  `Публичный API`;
- `k_typehas(type, cls)` — у типа есть секция класса (`клиенты` — у всех; тип неизвестен — да);
- `k_typesplit(type)` — тип режется, если все его секции классов — секции частей (`backend` — да;
  `frontend`, `fullstack`, `lib` — нет; тип неизвестен — да).

Использование — копии уходят:
- `check.sh`: `cls()` в `parse_card` → `k_cls`;
- `assemble.sh`: `kcls()` → из `k_cls` (только блочные классы); регэксп секций частей (метка `<!-- части -->`)
  → `k_partsec`;
- `plan.sh`: шестой аргумент `<type>` (необязательный; сводится: пробелы, комментарий, кавычки, регистр);
  класс, которого у типа нет, отбрасывается при разборе счёта — не идёт ни в итог, ни в вес, ни в строки
  плана, печатается «класс X: у типа T секции нет — пометок N, не считаются»; `!k_typesplit` — «нарезка не
  нужна: тип T не режется».

Тест: проба `SM-PLAN-TYPES` сверяет `k_typesecs` с таблицей порядка `card.template.md` — таблица и код не
разъедутся.

### К2. У разведчика нет слова «экран» → класс `экраны`

Причина: классов пять, роуту интерфейса места нет — он уходит в «контракт».
- `brief-scout.md`: класс `экраны` (у `frontend` и `fullstack`: маршрут роутера — `<Route path=…>`, объект
  `{ path: … }` в описании роутов; маршрутизация по файлам — строки нет); обязательный поисковый греп роутов
  `<Route\b|path:\s*['"]|createBrowserRouter|createRouter` у `frontend` и `fullstack` («Все поисковые грепы
  ниже обязательны»; спека и её пояснение остаются рядом); пример `экраны :: <Route\b :: *.jsx :: ключ`.
- `SKILL.md` 3.0: `экраны` в списке классов.

### К3. «Контракт — то, что сервис принимает» применено не везде → одно определение во всех местах

Причина: определение есть в брифе разведчика, но не доходит до фронта, `fullstack` и до текста добора по
спеке — там «найди обработчик по `operationId`» ловит и вызов клиента.
- `brief-scout.md`, класс `контракт`: «у `frontend` контракта нет: его роуты — `экраны`, его вызовы API —
  вызовы наружу; у `fullstack` вызовы API из кода фронта — тоже вызовы наружу: регэксп ручки — на объекте
  сервера (`router.`, `app.`), а не общий `\.get\(`».
- `check.sh`, текст добора `SPEC`: «… найди её обработчик — код, который принимает этот запрос (маппинг,
  реализация интерфейса API); вызов клиента к соседу — не обработчик …».

### К4. У разведчика нет способа сказать «эта спека — клиентская» → своя строка ответа

Причина: «спека в дереве, разведчик о ней молчит» `plan.sh` читает как «разведчик пропустил серверную» —
другого исхода у молчания нет.
- `brief-scout.md`: спека, по которой генерируется клиент к соседу, — строка `клиентская спека :: <абсолютный
  файл>`, без регэкспа и счёта; форма — в перечне форм ответа.
- `brief-counter.md`: строки `клиентская спека :: …` — не греп, заголовком как есть (как `контроль`).
- `plan.sh`: заголовок `## клиентская спека :: <файл>` → файл в `clientspec`; в `discover()` такая спека не
  печатается «СПЕКА НЕ РАЗМЕЧЕНА» и в сверку не идёт; веса и счёта у неё нет. Остальное правило — как сейчас
  (ни одной спеки `ключ` — неназванные идут в сверку: страховка серверной спеки).
- `SKILL.md` 3.0 (формы ответа разведчика) и 3.1 (повтор по «СПЕКА НЕ РАЗМЕЧЕНА»: «назови её: серверная —
  строкой спеки `ключ`, клиентская — `клиентская спека :: <файл>`»).
