Записан 2026-10-05, дополнен после проверки скиллов, скриптов и стенда.
Рабочая база — `agent-version/service-map-2.0` версии 3.0.7 из HEAD. Предыдущая незавершённая
попытка 3.0.8 сохранена в архиве раунда; изменения реализации ведутся отдельно от этой попытки.
Первая версия (`agent-version/service-map`, 2.2.1) этим планом не меняется.
Уточнение владельца 2026-10-06: `business-requirements-doc`, `technical-spec-doc` и другие
скиллы не менять. Добавленные в два потребителя абзацы отменены; допустима проверка

Требование владельца к переносимости: правила скилла должны работать независимо от языка.
Запрещена подгонка под имена, пути, значения и ответы конкретных проб. Языковые / фреймворковые
детекторы допустимы с явными границами поддержки; их отказ не доказывает отсутствия поведения.

**Пром-модель, по сообщению владельца:** DeepSeek v4 Flash, окно 262k, клиент — форк qwen-code.
Модель текущего стенда по выбору владельца: `gpt-6-luna`, reasoning `medium`, через встроенный пул агентов.

Luna medium дала 3/6, исторический Sonnet — 6/6; точный snapshot Sonnet не восстановлен.
Эта малая выборка не доказывает эквивалентность моделей. Результат Luna не является пром-проверкой.
Claude CLI и сторонние аккаунты для исполнения плана не используются.
Haiku — дополнительная проверка устойчивости, не порог приёмки прома.

**Цель.** Сохранить работающий сбор слепка и устранить четыре вида дефектов: ложный запрет записи,
доборы без улучшения карточки, потерю доступных в коде фактов и неполноту общих секций при нарезке.
Результат — доступная потребителям карточка с подтверждённым содержанием и видимыми ограничениями.
Успешная запись, полнота ключей и полнота фактов измеряются отдельно.

обеих серий в их `STATE.json` и `PROGRESS.md`.

на корректном входе. Ошибки грейдера, подготовки фикстуры, инфраструктуры и отсутствие входов

Если часть автоматических оценок ошибочна, круг можно отклонить только по другому,
независимо подтверждённому дефекту скилла; одного такого провала достаточно при критерии 3/3.

## 2. Общий контракт результата

### 2.1. Что идёт в добор

| Диагностика | Действие |
|---|---|
| ключ с источником есть в описи, блока в карточке нет | добор ключа; после бюджета — имя в ограничениях |
| факт есть в описи, соответствующий блок пуст | добор факта; после бюджета — имя в ограничениях |
| блок есть, соответствующего ключа описи нет | справка, опись ради этого не дописывается |
| строка описи без пары и без источника | неподтверждённая строка, справка; не доказательство пропуска |
| совпавший ключ описи без источника | добор: подтвердить по файлу либо снять неподтверждённое |
| дефект карточки: тип операции, заголовок, дубль, регистр, хвост-файл, связи | проверка и добор |
| блок пуст и в описи факта нет | ограничения; автоматического добора ради заполнения нет |
| остаток не отметил пункты либо сообщил «пропущено частью» | один добор соответствующему читающему |

Расхождение строк состояния, сообщений и ограничений описи остаётся проверкой; оно не доказывает
отсутствие блока. Классификация выполняется скриптом, ведущий не вычитает «форму» из гейта вручную.
Имена фактов не додумываются по ключу. Существование пути к файлу ещё не доказывает истинность факта.

### 2.2. Что запрещает запись поверх

После исчерпанного добора три проверки маршрутизируют готовый кандидат в `_pending`:

1. **Тело не доехало:** у контрактного класса есть ключи, но строки фактов есть меньше чем у половины
   его уникальных блоков. Назначение, `сущности:`, заглушки и служебные пометки фактом не считаются.
   Формула применяется к блочным контрактам backend/fullstack/lib; к таблицам frontend её не применять.
2. **Маркерный провал:** для класса с надёжными маркерами `ключ` в карточке меньше половины
   ожидаемого числа уникальных ключей. Проверять сервис целиком и каждую часть.
   Маркеры `ориентир`, отсутствующий счёт и нулевой результат не дают запрета.
3. **Обвал относительно прежней карточки:** существующая формула гарда без изменения:
   для класса c `(исчезло_c ≥ 3 и 3·исчезло_c > было_c)` или
   `(опустело_c ≥ 3 и 3·опустело_c > было_c)`.

Порог пустоты остаётся грубой проверкой доставки тела, а не критерием качества. Законно пустые
служебные блоки показываются отдельно; отдельная фикстура проверяет сервис, состоящий только из
служебных операций. Если действующая формула даёт ему ложный провал, исправлять исключение по
подтверждённому назначению, а не по подстроке `version` или `health` в любом имени.

Техническая невозможность — нет обязательных файлов, нечем выполнить склейку или копию —
не четвёртый содержательный гейт: завершённой карточки для продвижения нет.
Остаток с неполным самоотчётом после добора идёт в ограничения; сам его текст не становится
независимым запретом записи. Отсутствующие обязательные файлы остатка — технический сбой.

### 2.3. Единые исходы обычного и нарезанного сервиса

| После последней допустимой попытки | Файл для потребителей | Что сохранить |
|---|---|---|
| кандидат готов, три проверки не запрещают запись | новая `services/<name>.md` | ограничения в карточке и отчёте |
| готовый кандидат не прошёл хотя бы одну из трёх проверок | прежняя карточка, если была | кандидат в `_pending`, полная диагностика рядом |
| кандидат не собран: отсутствуют файлы / отказ склейки | прежняя карточка, если была | существующие части и описи в `.work`, список недостающего |
| копия / запись завершилась ошибкой | прежняя карточка | черновик и диагностика; уборка его не удаляет |

На первом сборе готовый, но непринятый кандидат тоже сохраняется в `_pending`.
Диагностика перечисляет конкретный гейт с ожидаемым и полученным числом; при маркерном провале
сам вывод `check.sh` недостаточен — рядом сохраняются числа разведчика, счётчика и плана.
Повторный прогон не затирает неразобранного кандидата: существующий файл остаётся, новый получает
суффикс идентификатора запуска. Дата — одна на запуск, включая переход полуночи; идентификатор
запуска дополнительно отличает два запуска одного дня.

Рабочие файлы удаляются только после подтверждённого сохранения результата и диагностики.
Незавершённые части не объявляются актуальными на следующем запуске только по дате.
Их повторное использование вне того же запуска требует подтверждённой свежести исходников;
по умолчанию — новый запуск, без смешивания частей.

### Этап 2. Порядок работы ведущего

**Файлы:** `SKILL.md` 3.4–3.5, при необходимости короткий бриф в `reference/`,
`SM-SLICE-LEAD` и `SM-SLICE-LEAD-2`, `SM-SPLIT-SCRIPTS`.

1. После возврата части проверить эхо-строку, оба файла, идентификатор / дату первой строки;
   выполнить `check.sh`, сохранить весь перечень. Сразу перезапускать только технически пустой ответ.
2. Содержательный добор части пока не запускать: её единственный бюджет должен учитывать
   «пропущено частью», которые обнаружит остаток. Остаток получает завершённые первичные описи.
3. После остатка объединить локальные проверки, маркерные расхождения и его находки.
   На этапе 5 сюда же включается сверка объявлений с блоками первых ответов частей и остатка.
   Одной волной запускать по одному добору тем читающим, у кого остался бюджет.
4. Дождаться всех доборов. Остаток не переписывает опись параллельно с читающим её агентом.
   Свод бизнес-правил и голова получают окончательные описи, после этой точки части не правятся.
5. Проверить общие секции, собрать одну волну добора их авторов; затем склеить и повторить сверку.
   Поздняя находка части с исчерпанным бюджетом идёт в ограничения; тайного дополнительного добора нет.
6. Бюджет — два запуска на автора: технический повтор уже расходует второй. Сохранить действующее
   отдельное исключение для кода в бизнес-правилах, явно учитывать его в журнале.
   Автоматическое дочитывание пустоты после этого не добавляется.

Так ранняя сверка сохраняется, но прежнее обещание «добор параллельно с остатком и головой» снимается:
оно расходует бюджет до обнаружения межчастных пропусков и создаёт чтение меняющихся описей.
Сообщение «читающих больше пяти» у одного уже выбранного сервиса не требует вопроса «продолжать?».
При первом отборе многих сервисов согласование манифеста сохраняется.
Проверить `allowed-tools`: процедура требует командной строки, сейчас `Bash` отсутствует в списке.
Добавить поддерживаемый клиентом инструмент команд, сохранив ограничение на скрипты `reference/`;
случай без командной строки остаётся явным запасным путём, не скрытой неисполнимой инструкцией.

**Готово:** по трассе нет чтения `.work` ведущим для анализа, ручных правок частей и преждевременного
запуска головы; не больше допустимых попыток; финальные описи соответствуют материалу головы.
Случаи ведущего — 3/3 на случай, затем один сквозной дым и итоговый круг ×3 на этапе 8.

### Этап 3б. Качество чтения и K

**Файлы:** бриф читающего и части в `SKILL.md` / `reference/`, `SM-FACTS`,
`run-sm-k.sh`, `grade-sm-k.mjs`, режим подмены K в `run-sm-mono.sh`, журнал пром-замера.

2. Уточнить бриф: обработчик — начало поиска, дальше читать источники поведения выбранного ключа.
   Часть ограничивает владение ключами, но не путь за фактом. Если чтение оборвалось или упёрлось
   в бюджет, писать «не проверено», а не «в коде фактов нет».
3. Сравнить K=50 с K=35 и K=25 на одном дереве, одной модели, одной редакции, по три прогона.
   Это кандидаты эксперимента, не заранее выбранные пороги. Сначала поправить явный дефект брифа,
   затем замерить K, чтобы изменение размера не маскировало изменение инструкции.
4. На Sonnet сохранить предел пика 200k для сравнимости прежнего стенда. На DeepSeek отдельно
   регистрировать окно 262k и фактическое использование; рабочий запас оценивается по пром-трассе,
   а не пересчётом Sonnet. Предварительный потолок 200k консервативен, увеличивать его без замера не нужно.
5. В проме сначала проверить доступность фактов у выборки не меньше 20 операций adjutant:
   изменяющие, читающие, REST / GraphQL и разные части. Источники и эталон фиксируются до сравнения.
   92 пустых и 109 однострочных — диагностическая база, не список доказанных пропусков кода.
6. Проверить переносимость тех же правил на независимых исходниках разных стеков. Сохранить
   ожидаемые факты до прогона; не передавать их читающему. Матрица должна охватить Java/Kotlin,
   JS/TS, Python, Go и C# либо явно показать отсутствующие входы и непроверенную поддержку.
   Пустой Go-файл и проверка названий не заменяют чтение поведения. После исправлений повторять
   затронутый случай и независимый случай другого стека; специфичный список ответов в скилл
   не переносить. Не считать языковую переносимость принятой по одной синтетической семье.

**Критерий выбора K:** 3/3 карточки, ключи не хуже базы; ≥90% эталонных фактов в каждом прогоне,
выдумок по эталону 0, восстановлены все факты специальной выборки за пределами обработчиков,
пик ниже принятого предела. Это новый целевой критерий, его достижимость ещё не измерена.
Среди подходящих K выбрать наибольший, зафиксировать цену и длительность.
Если ни один не проходит, не объявлять подбор завершённым: исправить способ чтения по конкретным
пропускам; отдельный управляемый добор этапа 6 остаётся необходимым, но не подменяет качество скана.

**Пром-порог:** на фиксированной выборке ≥90% подтверждённых фактов, выдумок 0;
доля блоков с доступными, но пропущенными фактами ниже базы во всех трёх сопоставимых прогонах.
Полный DeepSeek-замер ×3 нужен для переноса выбранного K в пром. Один прогон — только пилот.
Отсутствие доступа к пром-модели / исходникам означает «пром не измерен», а не запрет других этапов.

### Этап 4. Общие секции и согласованность

**Файлы:** `SKILL.md` 3.3 / 3.5 / Шаг 4, `card.template.md`, `assemble.sh`, `check.sh`,
`check-links.awk`, новый бриф `reference/business-summary.md`, `SM-SPLIT-SCRIPTS`, `SM-GATE`, новая `SM-SUMMARY`.

**Бизнес-правила:**

- Части пишут строки описи состояния, справочника, сообщения и ограничения, с источниками;
  секцию карточки больше не пишут. Режим одиночного читающего сохраняет своего автора секции.
- После окончательных описей отдельный сводный читающий собирает бизнес-правила. Он имеет доступ
  ко всему сервису, ищет реальные условия переходов, получателей и условия сообщений, переключатели;
  не выводит их из имён enum и не ограничивается папкой автора сущности.
- Файлы: `business.md` и `business.opis.md` с идентификатором запуска. В голове остаётся

  чужом запуске или одновременно двух авторах секции. Голова свод повторно не переписывает.
- Одно сообщение определяется источником отправки и условиями, а не только названием;
  общий файл с несколькими разными видами сообщения сам по себе не повод объединить их.
- Свод получает обзор и нужные фрагменты описей, не все тела карточек и не весь код.
  Если сам превышает бюджет, разделить сбор подтверждённых данных и их свод; не упрощать факты
  ради одного окна. Решение проверяется на `SM-SUMMARY`, в журнале фиксируется цена дополнительного автора.

**Зависимости и события:**

- Части и остаток добавляют `зависит: <система> — <зачем / канал / направление> — <источник>`.
  Брокер не подменяет систему второй стороны. Сторона не определяется из кода — «не определено»;
  конфиг топика не доказывает направление, нужны отправитель / слушатель или подключённый механизм.
- Голова строит таблицу по финальным описям, добавляет подтверждённые связи из конфигов и клиентов.
  `parse_opis` распознаёт класс зависимости отдельно, не превращая префикс в контрактный ключ.
- Сверять сообщения с публикуемыми событиями по связи источников; отсутствие пары — добор своду
  или ограничение. Сообщений не заставлять выдумывать ради совпадения количества топиков.
- Добавить проверки имён в `сущности:` против «Владеет данными», ролей между секциями и топиков
  без фактов. Чужое владение / проекция / ответ соседа сохраняются явно; суффикс класса не угадывается.
- Механическая сверка ссылок выполняется при `CHECK_CROSS_SECTIONS=1` по полной карточке,
  не отдельной части. Она сравнивает явные имена результата / агрегата, пометки ролей и роли
  в бэктиках таблицы возможностей. Свободная проза, сложные типы, область роли и связь
  сообщения с событием остаются смысловой проверкой по описям и источникам.
- Склейка убирает служебную заглушку «фактов нет», если есть факт. Разные назначения, схемы и
  противоречащие факты дубля показываются с обоими авторами; произвольный выбор первой части запрещён.

**Готово:** `SM-SUMMARY` ×3 — все эталонные переходы, условия и стороны событий на месте;
дублей сообщений, выдумок и справочников отдельными объектами 0; зависимости эталона 100%.
Скриптовые тесты вставки свода, отказов и конфликтов — 0 расхождений.
Проверка «Бизнес-правил» не становится обратно запретом записи из-за формы описи.

### Этап 5. Объявленный контракт и ключи без маркеров

  сверка повторяется как контроль. Она не появляется впервые, когда бюджеты авторов уже потрачены.
- «Объявлено, блока нет» — точный перечень добора автору реализации или остатку.
  Если реализацию создаёт подключённый механизм фреймворка, это действующий ключ;
  отсутствие рукописного метода не позволяет исключить его.
- Объявление без действующего обработчика получает подтверждённый статус и идёт в ограничения,
  но не смешивается с действующим контрактом. Непроверенное объявление — «не проверено».
- Общий префикс и исключения передавать всем читающим, включая одиночного; путь ключа — внешний
  путь вызова. Смена режима нарезки не должна менять ключи неизменившегося сервиса.
- Сверка объявлений — проверка полноты с добором, не новый гейт по отсутствию строки описи.
  У сервиса совсем без поддержанного счёта / схемы ограничение независимой проверки остаётся видимым.

**Готово:** в `SM-MONO-SPEC` 148/148 действующих операций и 0 лишних, два неработающих объявления
отмечены отдельно, в трёх прогонах. Включить мини-случай декларативного обработчика и переход
«один читающий ↔ части» с одинаковыми внешними ключами. Четыре операции adjutant проверить
по исходникам; если доступны, описать все четыре, иначе сохранить имена как непроверенные.

### Этап 6. «Задето» и управляемое дочитывание

**Файлы:** `SKILL.md` (выбор режима), `reference/keyed-update.md`, новый `reference/refill.md`,
`grade-sm-keyed.mjs`, `SM-REFILL`. Отдельный скрипт применения фактов в скилл не включается.
Предыдущая реализация и её пробы сохранены в стенде как эксперимент, не как условие приёмки.

**6а. Согласовать быстрое обновление:**

- Перенести направленную сверку и предел бюджета из раздела 2 в `keyed-update.md`:
  он старше общего скилла, его старый гейт сам не исчезнет.
- Сохранить назначение режима: после релиза по подсказке `archive-spec` обновляется задетое,
  исчезнувшие ключи не удаляются автоматически. Проверки — до продвижения подготовленной копии,
  а не после необратимого для процедуры изменения рабочей карточки.
- Для большого сервиса проверить три запуска: инвентарь всего сервиса всё ещё может переполнять
  читающего. При отказе не повторять его без конца, назвать предел и предложить полный скан.
- `scanned` не менять; `updated` менять при подтверждённой правке. Нетронутые блоки — байт-в-байт.
  Самопроверку и грейдер расширить: число совпадений текста / имён не заменяет проверку изменённых фактов.

**6б. Отдельный вход `Дочитать:` для известных пустых ключей:**

- Это явная команда человека, не автоматический дополнительный проход после любого скана.
  Она выбирает существующие ключи карточки, не запускает общую перепись сервиса и не наследует
  инвентарный гейт режима «Задето». Для вида ключей сначала механически получить их список из карточки.
- Ведущий фиксирует выбранные пары класса и ключа и готовит копию существующим `promote.sh`.
  Читающий получает выбранные блоки, правила фактов и пути исходников из диагностики, если есть.
  Размер области ограничивается бюджетом чтения; при разбиении сначала изменяющие операции,
  остаток выбранного списка сохраняется в отчёте. Пределы прежнего эксперимента 25 × 4 не
  являются обязательным протоколом нового режима.
- Нет источника — отдельная ограниченная задача найти его. Не найден / бюджет чтения закончился —
  «не проверено», а не фиктивное «фактов нет». Три перехода к файлам — начальный ориентир поиска,
  не доказательство отсутствия более далёкой логики.
- Узкий читающий правит выбранные блоки копии через `Edit`, сохраняя подтверждённые прежние
  факты. Для законной пустоты возвращает перечень проверенного. Новый ключ, удаление и
  переименование не допускаются. Без права записи возвращает блоки для дословного `Edit` ведущим.
- Ведущий сверяет факты с описью выбранных ключей и исходниками, запускает существующие проверки
  и продвигает копию только после приёмки. Источник должен быть в разрешённой репе; существование
  файла не доказывает смысл факта. В стенде полноту и выдумки проверяет независимый эталон.
  JSON-протокол фактов, ручные хеши и дословные цитаты не требуются от автора карточки.
- Сохраняются назначения, схемы, другие блоки, `notes` и `scanned`; при реальной правке обновляется
  `updated`. Связанные бизнес-правила включаются в область только по явному перечню, не целиком.
  Сбой до продвижения сохраняет исходную карточку и подготовленную копию с диагностикой.

**Готово:** три запуска на большом дереве — ≥90% фактов выбранных ключей, выдумок 0;
состав ключей и все незадетые блоки неизменны, отсутствующий источник не превращается в факт;
отказ приёмки или продвижения не портит карточку. Мини-случаи без источника / с неоднозначным ключом / с обрывом
показывают «не проверено». В проме проверить выбранную выборку adjutant, не обещая заполнить все 92 блока.

### Этап 7. Ограничения, которые переживают отчёт

**Файлы:** `check.sh` (полная диагностика), новый `reference/quality.sh`, `SKILL.md`,
`card.template.md`, `keyed-update.md`, `refill.md`; новая `SM-QUALITY`.

- Добавить компактный генерируемый блок под существующей строкой «Генерируется», с постоянными
  границами комментария. Это не новая обязательная секция, поле frontmatter или сводный индекс;
  старые карточки сохраняют форму, отсутствие блока не запускает принудительный полный скан.
- `quality.sh` вставляет блок в подготовленный черновик по полной диагностике перед продвижением.
  Модель ведущего содержание не пересказывает. Скрипт меняет только этот блок; остальная карточка
  остаётся байт-в-байт. После вставки повторяются механические проверки, затем копия.
- Писать конкретные ограничения: ключ не описан; фактов в блоке нет; найденный факт не перенесён;
  объявление не проверено; направление / связь неизвестны; остаток пройден не полностью;
  независимого счёта класса нет. Отделить «в коде проверено отсутствует» от «скан не проверил».
  Не утверждать полную достоверность карточки по отсутствию предупреждений.
- Полные ключи и типы ограничений хранить в блоке; короткое число — в обзоре. Рабочий файл
  диагностики для записанной карточки можно убрать после подтверждённого переноса ограничений.
- Пример формы, не новая обязательная секция:

  ```markdown
  <!-- service-map: ограничения -->
  > Ограничения слепка — проверка 2026-10-05, полный скан.
  > Фактов в карточке нет: контракт `mutation saveTask`.
  > Объявление не проверено: контракт `query taskHistory`.
  > Независимого счёта нет: топики.
  <!-- /service-map: ограничения -->
  ```

  Тип и ключ записываются полностью; блок доступен узким поиском по границам и ключам.
- Быстрое обновление и дочитывание снимают только подтверждённо закрытые ограничения выбранных
  ключей; ограничения остальных областей сохраняются. Даты и область проверки явны.
- Проверить использование карточки существующими БТ и тех-спекой без изменения их инструкций.
  Предупреждения должны быть видны в результате самого `service-map-2.0`. Отсутствие факта
  не должно превращаться в утверждение, что поведения нет; непроверенное — в подтверждённый факт.
  Если существующий потребитель игнорирует ограничения, зафиксировать несовместимость отдельно;
  править его скилл в рамках этой работы нельзя.
- `archive-spec` продолжает вызывать выбранный установленный скан, а не править карточки.
  В репозитории его вызов сейчас называется `service-map`; установку варианта 2.0 определить
  явно на этапе 8, не менять первую версию незаметно.

**Готово:** `SM-QUALITY` — повторная вставка идемпотентна; больше 40 ограничений не теряются;
нетронутые блоки неизменны; успешный добор снимает своё ограничение; чужое сохраняется.
Два потребителя по три прогона на одной карточке с известным пробелом: вопрос / гипотеза о пробеле
есть, неподтверждённого утверждения нет. Карточка без нового блока читается по прежним правилам.

## 7. Что требуется при исполнении

Для подготовки плана дополнительных ответов не нужно. До соответствующих замеров потребуются:

- снимок установленного пром-скилла и доступ к исходникам adjutant либо выполненная владельцем
  проверка фиксированной выборки; логи сами по себе не заменяют правду по фактам;
- возможность запуска DeepSeek v4 Flash в том же клиенте и с теми же настройками субагентов;
- цена и трасса встроенного пула, если интерфейс их раскрывает; иначе явно «не измерено»;
- подтверждение готовой пром-установки с явным соответствием имён `service-map` / `service-map-2.0`.

Рабочее решение плана: независимый маркерный провал сохраняется в `_pending`.
K выбирается экспериментом, исходное значение 50 остаётся до подтверждённого результата.
Автоматического дочитывания каждого пустого блока и автоматического принятия пром-кандидатов нет.
Кандидат adjutant можно оценить для ручного принятия отдельно; запись не объявляет его факты полными.
