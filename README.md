# coDDoc: скиллы SDD для БТ и аналитики

Набор скиллов GigaCode. Вход — идея, дефект или мелкая правка. Выход — `technical_specification.md`: вход для разработчика или агента генерации кода. Документы и контекст системы живут в репозитории **AI-SDD**.

## Установка

1. Скопировать все папки скиллов из `skills/` этого репозитория в `.gigacode/skills/` — папки проекта AI-SDD или глобальной. GigaCode Desktop: Навыки → Загрузить навык → SKILL.md.
2. Обновление — из чата: `/analyst-skills-update`. Скилл запускает скрипт из своей `reference/`, подтягивает свежие версии и показывает их. Нужны `git` и `bash` (на Windows — Git Bash) и доступ к репозиторию со скиллами, как для `git clone`.

## Скиллы

| Скилл | Назначение | Запуск |
|---|---|---|
| `analyst-workspace` | точка входа: интервью, документы, вызов под-скиллов | вручную |
| `business-requirements-doc` / `bug-report-doc` / `change-request-doc` | БТ / баг-репорт / запрос на правку | из `analyst-workspace` |
| `technical-spec-doc` | спецификация по любому из трёх документов | из `analyst-workspace` |
| `task-decomposition-doc` | разрез эпика на подзадачи | из `analyst-workspace` |
| `stage-breakdown-doc` | нарезка спеки на этапы для нескольких исполнителей | из `analyst-workspace`, по согласию |
| `spec-review` | приёмка записанного документа агентом с чистым контекстом | автоматически после каждого документа |
| `spec-readiness` | готовность спеки к разработке: бэкенд, фронтенд, стык, сверка | вручную, перед передачей |
| `service-map` | карточки сервисов по коду → `services/*.md` | вручную |
| `context-doc` | дословный перенос документа в `context/` | вручную |
| `archive-spec` | архивация фичи, обновление карточек | из `analyst-workspace` |
| `analyst-skills-update` | обновление скиллов скриптом из своей `reference/` | вручную |

## Процесс

![Схема](img/schema.png)

- Контекст собирается до работы над задачами: `/service-map` читает код сервисов и пишет карточки в `services/`; `/context-doc` дословно переносит в `context/` документы, которых в коде нет. Обе папки читают все скиллы ниже по схеме.
- Работа над задачей начинается с `/analyst-workspace`. Первым вопросом скилл выясняет, что за работа, и заводит документ-источник для спецификации: новая возможность → `business_requirements.md`; дефект прода → `bug_report.md`; мелкая правка работающего (текст, лимит, версия, поле) → `change_request.md`, без БТ.
- По документу-источнику системный аналитик тем же `/analyst-workspace` пишет `technical_specification.md`: контракты между сервисами и FE/BE, критерии приёмки, роли, трассировка к требованиям. Это конечный продукт процесса: разработчик или агент генерации кода берёт её как задание, строит по ней план реализации и затем пишет код. Всё после неё на схеме необязательно.
- Приёмка после каждого документа. Гейт: статус «Требуются уточнения» или ≥1 нарушение — процесс стоит до «Доработать» или явного принятия.
- `spec-readiness` — проверка, можно ли по спеке писать код. Приёмка отвечает только за форму: разделы заполнены. Готовность ищет логические дыры: спеку читают три агента с чистым контекстом — бэкенд, фронтенд и стык между ними, четвёртый сверяет их вопросы со спекой и вычёркивает те, на которые ответ уже есть. Остаток — список дыр, которые нужно закрыть в спеке до передачи. Запускается только вручную, перед передачей разработчику; `analyst-workspace` его не зовёт.
- Этапы `stages/stage-NN.md` — только когда задачу делят между исполнителями.
- Эпик: скилл предлагает разрез на подзадачи; общий источник данных → узел-фундамент без своего БТ.

```
AI-SDD/
├── services/          # карточки из кода; manifest.yaml ведёт человек
├── context/           # регламенты, договорённости, глоссарий — руками
└── docs/SMSEC-12345/
    ├── business_requirements.md | bug_report.md | change_request.md
    ├── technical_specification.md
    └── stages/        # необязательно: index.md, stage-01.md, …
```

## Этап 1. Контекст системы (один раз, далее точечно)

1. Создать репозиторий **AI-SDD**; рядом склонировать все репозитории системы.
2. В `AI-SDD` на ризонинг-модели: `/service-map`. До шести сервисов параллельно; больше десяти — по именам: `/skills service-map auth geo`. Плохая карточка — перечитать сервис по имени; карточка перезаписывается целиком.
3. `manifest.yaml`: состав сервисов и `notes` — договорённости вне кода, переносятся в карточку дословно.
4. Документы вне кода: `/context-doc путь/к/файлу` (txt, docx, pdf, xlsx, папка, текст из чата). Строка `description` обязательна — без неё файл не найдут. Файлы, положенные руками: `/skills context-doc` без аргументов.
5. Запушить.

Без контекста (`services/` и `context/`) скиллы работают, но вопросы общие, не про вашу систему и часто мимо задачи; варианты ответов агент выдумывает сам. Правила из `context/` применяются молча и с кодом не сверяются — держите папку актуальной.

## Этап 2. Роли

Общее: модель **DeepSeek-V4-Flash**, effort `high` / `xhigh` / `max`; работа в папке `AI-SDD`, кодовая база не нужна; прерванная работа — `/analyst-workspace` → «Продолжить начатое».

**Владелец продукта / бизнес-аналитик**
1. `git checkout -b feature/SMSEC-12345`.
2. `/analyst-workspace` → «Бизнес». Скилл спросит тип работы: идея, дефект, правка.
3. Ответить на вопросы. Дефект: скилл фиксирует шаги, факт, ожидание, критичность; причину и код не ищет. Правка: при объёме выше порога предложит идти через БТ.
4. Приёмка автоматически; прочитать документ.
5. `git push origin feature/SMSEC-12345`; передать ветку аналитику.

**Системный аналитик**
1. `git pull && git checkout feature/SMSEC-12345`.
2. `/analyst-workspace` → «Аналитика», путь к документу; тип определится по имени файла.
3. Ответить на вопросы; приёмка автоматически; прочитать спеку.
4. `/spec-readiness docs/SMSEC-12345/technical_specification.md`. Результат — список пропущенных и неявных логических дыр, недоработок и условностей спеки; разработчик их тоже может пропустить. Ответы дописать в спеку; скилл на диск не пишет.
5. Несколько исполнителей → согласиться на нарезку; приёмка пройдёт по `stages/`.
6. `git push`; передать ветку разработчику (и номер этапа, если нарезали).

**Разработчик**
1. В AI-SDD: `git pull && git checkout feature/SMSEC-12345`.
2. Рабочий документ — `technical_specification.md` или свой `stages/stage-NN.md`; этап самодостаточен.
3. Нехватка в документе — вернуться к аналитику, не дописывать самому.

## Этап 3. Завершение фичи

1. После вливания кода обновить локально затронутые репозитории сервисов.
2. `/analyst-workspace` → «Доработка готова». Агент перечислит, что архивирует, дождётся подтверждения, обновит карточки задетых сервисов, пометит папку фичи. Эпик — по ключу эпика разом. Если локальные репозитории не обновлены, агент сообщит, что не нашёл таких изменений в коде: карточка честна настолько, насколько свежа рабочая копия.
3. Запушить AI-SDD: в `develop` или в ветку с номером задачи — как предусмотрено вашим git-флоу.

## Правила

- Перед каждым этапом работы очищать контекстное окно командой `/clear`: перед БТ, перед спекой, перед архивацией, при переключении между задачами и перед обновлением контекста системы. Накопленная переписка предыдущего этапа портит ответы следующего.
- `--no-review` в строке вызова выключает приёмку на всю сессию. Отключается только проверка структуры итогового документа; проверка каждого пункта по ходу интервью и гейт по статусу остаются.
- Список нарушений приёмки `spec-review` передавать как есть, с цитатами и номерами строк, не пересказывая. Нарушений много — выбрать «Доработать», не править руками: на каждую новую редакцию документа по окончании её составления запустится новая приёмка.
- Не нарезать этапы «на всякий случай»: каждый этап — копия куска спеки. Если нарезка нужна, `spec-readiness` запускать до неё: правка спеки после нарезки означает правку и всех этапов.
- Метки в спеке: 🟢 — новое, спроектировано в этой спеке, строить как написано; 🔵 — существующий чужой сервис, аналитик подтвердил на интервью, но по коду не проверено, сверить при интеграции; 🟡 — существующий чужой сервис, не подтверждено, пункт открыт. Не просить скиллы дописать контракт под 🔵 или 🟡: кода чужого сервиса у агента нет, он его выдумает. Правильный ход — подтвердить у владельца сервиса и снять метку.
- Общие сведения о системе (роли и т.п.) — в `context/` или в отдельные файлы со строкой `description`; в `GIGACODE.md` — только ссылки на них.
