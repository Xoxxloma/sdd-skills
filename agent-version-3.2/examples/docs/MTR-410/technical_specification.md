## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. `metrolog-api` принимает файл графика поверок и отдаёт состояния поверок по цеху;
`metrolog-web` красит по ним приборы на существующей схеме цеха, фильтрует и показывает карточку.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `metrolog-api` | импорт графика, сводка состояний, карточка прибора | Метролог | 🟢 новые эндпоинты в существующем сервисе |
| `metrolog-web` | схема цеха: подсветка, фильтр, поиск, карточка | Метролог | 🟢 |
| Справочник приборов и схема цеха в `metrolog-api` | источник перечня приборов и их координат | Метролог | 🟡 подтв. аналитиком |
| Security-сервис | роль «Метролог» для импорта | Платформа | 🟡 подтв. аналитиком |

### 1.3. Связь с бизнес-требованиями
Мастер участка видит состояние поверок прямо на схеме цеха и выходит на данные конкретного
прибора без звонка метрологу. Трассировка FR-* — в §7.

## 2. Взаимодействия (ядро)

### INT-1. Импорт файла графика поверок — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** метролог выбирает файл и нажимает «Загрузить график»
- **Контракт (запрос):** `POST /v1/verification-schedule/import`, `multipart/form-data`,
  поле `file` обязательно. Формат файла задаём мы: CSV, UTF-8, разделитель `;`, первая строка —
  заголовки, колонки `inventory_no`, `device_type`, `responsible`, `last_verified_at` (`YYYY-MM-DD`,
  допускает пусто), `next_verification_at` (`YYYY-MM-DD`, обязательна).
- **Контракт (ответ):** `importId: string`; `importedAt: iso8601`; `accepted: int` — строк принято;
  `skipped: массив`, элемент — `row: int`, `inventoryNo: string|null` (`null`, если номер в строке
  нечитаем), `reason: unknown_device|bad_date|duplicate`
- **Пример запроса:** тело — `multipart/form-data`, единственное поле `file`; JSON-тела нет
- **Пример ответа (успех):**
  ```json
  {
    "importId": "imp-2026-08-07-01",
    "importedAt": "2026-08-07T09:14:00Z",
    "accepted": 412,
    "skipped": [
      { "row": 87, "inventoryNo": "ИТ-0431", "reason": "unknown_device" },
      { "row": 91, "inventoryNo": null, "reason": "bad_date" }
    ]
  }
  ```
- **Ошибки:** `400` — не CSV или нет обязательных колонок (импорт не применён целиком);
  `403` — роль не «Метролог»; `413` — файл больше 10 МБ
- **Состояния UI по ответу:** значение → «принято N, пропущено M» со списком пропущенных строк;
  загрузка → прогресс, кнопка заблокирована; ошибка → причина, прежний график на схеме не тронут
- **Авторизация:** только роль «Метролог»; проверяется в `metrolog-api`; мастеру участка кнопка
  не показывается (§4.4), прямой вызов даёт `403`
- **Происхождение:** 🟢
- **Трассировка:** FR-1

Импорт заменяет график целиком и атомарно: до фиксации транзакции схема отдаёт прежние данные,
частично разобранный файл не применяется никогда (§3.2).

### INT-2. Состояния поверок по цеху — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** открытие схемы цеха; повторно — по кнопке «Обновить» и сразу после успешного INT-1
- **Контракт (запрос):** `GET /v1/verification-schedule/overview`, параметр `workshopId: string`
  обязателен
- **Контракт (ответ):** `asOf: iso8601` — момент, на который посчитаны состояния;
  `importedAt: iso8601|null` — когда загружен действующий график, `null` если не загружался ни разу;
  `devices: массив`, элемент — `inventoryNo: string`, `state: overdue|due_soon|ok|no_data`,
  `nextVerificationAt: iso8601|null` — `null` всегда при `state = no_data`, иначе заполнено.
  `no_data` — прибор есть на схеме, но в действующем графике его нет; это **не** `ok`: отсутствие
  данных и исправный срок различаются намеренно (риск из §2.3 БТ).
- **Пример запроса:** `GET /v1/verification-schedule/overview?workshopId=CEH-3`, тело отсутствует
- **Пример ответа (успех):**
  ```json
  {
    "asOf": "2026-08-07T10:00:00Z",
    "importedAt": "2026-08-07T09:14:00Z",
    "devices": [
      { "inventoryNo": "ИТ-0102", "state": "overdue",  "nextVerificationAt": "2026-07-01" },
      { "inventoryNo": "ИТ-0107", "state": "due_soon", "nextVerificationAt": "2026-08-20" },
      { "inventoryNo": "ИТ-0231", "state": "ok",       "nextVerificationAt": "2027-02-11" },
      { "inventoryNo": "ИТ-0431", "state": "no_data",  "nextVerificationAt": null }
    ]
  }
  ```
- **Ошибки:** `400` — `workshopId` не передан; `404` — цех не найден
- **Состояния UI по ответу:** см. §4.3
- **Авторизация:** любой аутентифицированный сотрудник с доступом к схеме цеха — мастер участка и
  метролог; отдельной роли не требуется
- **Происхождение:** 🟢
- **Трассировка:** FR-2. FR-3 (фильтр) и FR-5 (поиск) работают на этом же ответе и своих вызовов
  не имеют — см. §4.2

### INT-3. Карточка прибора — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** клик по прибору на схеме
- **Контракт (запрос):** `GET /v1/devices/{inventoryNo}/verification`, тело отсутствует
- **Контракт (ответ):** `inventoryNo: string`; `deviceType: string`; `responsible: string|null`;
  `lastVerifiedAt: iso8601|null`; `nextVerificationAt: iso8601|null`;
  `state: overdue|due_soon|ok|no_data`. При `state = no_data` обе даты и `responsible` — `null`.
- **Пример ответа (успех):**
  ```json
  {
    "inventoryNo": "ИТ-0102",
    "deviceType": "Манометр МП-100",
    "responsible": "Соколов А. П.",
    "lastVerifiedAt": "2025-07-01",
    "nextVerificationAt": "2026-07-01",
    "state": "overdue"
  }
  ```
- **Ошибки:** `404` — прибора нет на схеме цеха
- **Авторизация:** как INT-2
- **Происхождение:** 🟢
- **Трассировка:** FR-4

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| `400` | `reason: bad_format\|missing_columns` | INT-1: файл не CSV или без обязательных колонок | ошибка импорта, график не заменён |
| `400` | `reason: workshop_required` | INT-2: не передан `workshopId` | `error_source` |
| `403` | стандартное | INT-1 вызван не метрологом | `error_forbidden` |
| `404` | стандартное | INT-2: цех не найден; INT-3: прибора нет на схеме | карточка не открывается |
| `413` | `reason: file_too_large` | INT-1: файл больше 10 МБ | ошибка импорта |
| `5xx` | стандартное | сбой `metrolog-api` | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам
`metrolog-api` реализует INT-1, INT-2, INT-3. Разбирает CSV, сверяет `inventory_no` со справочником
приборов (🟡 подтв. аналитиком) и заменяет действующий график.

`state` вычисляется **на чтении** (INT-2, INT-3) сравнением `nextVerificationAt` с текущей датой и в
хранилище не денормализуется: денормализованный статус протухает сам по себе, без нового импорта, —
прибор пересекает порог по календарю, а не по событию в системе.

### 3.2. Данные и хранение
Две новые сущности (🟢):

- `VerificationImport` — действующий импорт: `importId: string`, `importedAt: timestamp`,
  `importedBy: userId`, `fileName: string`, `accepted: int`. Хранится **одна** строка: новый импорт
  перезаписывает прежнюю. Истории загрузок нет — она вне объёма (§3.2 БТ).
- `DeviceVerification` — строка графика: `inventoryNo: string`, `deviceType: string`,
  `responsible: string|null`, `lastVerifiedAt: date|null`, `nextVerificationAt: date`,
  `importId: string`. Индекс по `inventoryNo` — под INT-3 и под сверку в INT-2.

Полная замена — одна транзакция: удалить все `DeviceVerification`, вставить новые, обновить
`VerificationImport`. Читатели видят либо старый график целиком, либо новый целиком.

Справочник приборов и их координаты на схеме — существующие, не меняются (🟡 подтв. аналитиком).
Миграции: добавляются две таблицы; точный DDL — в репозитории `metrolog-api`.

### 3.3. Авторизация/доступ на бэке
INT-1 — только роль «Метролог», проверяется в `metrolog-api` до чтения тела файла. INT-2 и INT-3 —
любой аутентифицированный сотрудник с доступом к схеме цеха. Негативный случай: мастер участка
вызывает INT-1 напрямую → `403`, график не тронут.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Экран схемы цеха: подсветка приборов по состоянию, панель фильтра состояний, строка поиска по
инвентарному номеру, карточка прибора, кнопка «Загрузить график» (видна только метрологу).
Вызывает INT-2 при открытии, INT-3 по клику, INT-1 при загрузке файла.

### 4.2. Пользовательские сценарии
Основной: мастер открывает схему → приборы подсвечены по состоянию (FR-2) → отключает `ok`, на
схеме остаются просроченные и близкие к сроку (FR-3) → кликает по прибору, открывается карточка с
ответственным и датами (FR-4).

Поиск: мастер вводит инвентарный номер, совпавший прибор подсвечивается и центрируется (FR-5).

**Фильтр и поиск не ходят на бэк** — оба работают по уже полученному ответу INT-2, где есть и
`inventoryNo`, и `state` по каждому прибору. Новых контрактов у FR-3 и FR-5 поэтому нет.

Ветвление: график не загружался ни разу (`importedAt = null`) → схема рисуется без подсветки с
подписью «график поверок не загружен», фильтр заблокирован.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | ответ INT-2 ещё не получен | схема отрисована, приборы серые, фильтр заблокирован |
| `ready` | 2xx, `importedAt ≠ null` | подсветка по состояниям, фильтр и поиск активны |
| `empty_no_schedule` | 2xx, `importedAt = null` | приборы нейтральные, подпись «график поверок не загружен» |
| `error_source` | 5xx / таймаут / сеть | схема без подсветки, подпись «состояния поверок недоступны» + «Повторить» |
| `error_forbidden` | `403` на INT-1 | «загрузка графика доступна только метрологу»; штатно не возникает — кнопка скрыта |

`zero` — не применимо: числовых значений экран не показывает.

Состояние прибора (`overdue` / `due_soon` / `ok` / `no_data`) — отдельная ось, приходит в INT-2.
`no_data` красится нейтральным, **не** зелёным: иначе прибор без данных в графике выглядит
поверенным.

### 4.3.1. Loading и таймауты
- **Cold-path** (первый INT-2 при открытии схемы, сотни приборов) — 5 с.
- **Warm-path** (обновление по кнопке и после успешного импорта, ответ уже в кэше бэка) — 2 с.
- INT-3 — 2 с; INT-1 — 60 с, разбор файла заведомо дольше обычного запроса.
- **Polling:** нет. График меняется только импортом; экран обновляется по кнопке «Обновить» и
  автоматически после успешного INT-1. Опрос был бы холостым.
- Таймаут, 5xx, сетевая ошибка → `error_source`; схема цеха остаётся рабочей без подсветки.

### 4.4. Доступ по ролям в UI
Мастер участка — схема, подсветка, фильтр, поиск, карточка. Метролог — то же плюс кнопка
«Загрузить график». Ролевая модель — §5.3 БТ.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
Все три взаимодействия синхронные. Ответ INT-2 кэшируется в `metrolog-api` на 60 с по `workshopId`;
инвалидация — успешный INT-1. Объём: приборов в цехе — сотни, один ответ INT-2 — порядка 500
элементов.

### 5.2. Надёжность/деградация
`metrolog-api` недоступен → схема цеха рисуется как раньше, без подсветки (`error_source`); задача
не ломает существующий экран. Импорт упал → продолжает действовать прежний график, а не пустой.
Файл разобран частично → не применяется вовсе: либо весь импорт, либо ничего.

### 5.3. Безопасность/доступ (сводно)

| Роль | INT-1 импорт | INT-2 состояния | INT-3 карточка |
|------|--------------|-----------------|----------------|
| Метролог | да | да | да |
| Мастер участка | нет (`403`) | да | да |
| Прочие сотрудники | нет | нет доступа к схеме цеха | нет |

## 6. Релиз и интеграция

### 6.1. Порядок выката
Сначала `metrolog-api` с INT-1…INT-3, затем `metrolog-web` под выключенным флагом.

### 6.2. Обратная совместимость
Существующие эндпоинты схемы цеха не меняются, ничего не удаляется. Новые таблицы на текущих
потребителей не влияют.

### 6.3. Фиче-флаги
Флаг `workshop-map.verification` на фронте, по умолчанию выключен; включает команда «Метролог»
после проверки на одном цехе.

### 6.4. План отката
- **Только BE:** фронт получает `404`/`5xx` на INT-2 и переходит в `error_source` — схема остаётся
  рабочей. Синхронный откат фронта не нужен.
- **Только FE:** выключить флаг, схема возвращается к прежнему виду; эндпоинты остаются без
  потребителей и вреда не наносят.
- **Откат DDL:** обе таблицы новые, down-миграция удаляет их вместе с действующим графиком.
  Потери невосстановимой информации нет — график восстанавливается повторной загрузкой того же
  файла, оригинал остаётся у метролога.

### 6.5. Преднастройка до релиза
- [ ] Роль «Метролог» в security-сервисе — заведена (🟡 подтв. аналитиком); сверить назначения.
- [ ] DDL-миграция (две таблицы) в репозитории `metrolog-api`.
- [ ] Конфиг порога `due_soon` по окружениям — значение см. открытый вопрос.
- [ ] Сервисные аккаунты — не применимо: межсервисных вызовов задача не вводит.
- [ ] Фиче-флаг `workshop-map.verification` заведён.
- [ ] Алерты: доля `skipped` в импорте выше 10 %, `5xx` на INT-2.

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано: файл с 412 корректными строками. Когда: метролог загружает его. Тогда: `accepted = 412`, прежние строки графика заменены, повторный INT-2 отдаёт новый `importedAt` |
| FR-1 | INT-1 | Дано: файл, где часть дат нечитаема. Когда: метролог загружает его. Тогда: битые строки приходят в `skipped`, остальные приняты, прежний график заменён целиком |
| FR-2 | INT-2 | Дано: прибор с `nextVerificationAt` в прошлом. Когда: мастер открывает схему. Тогда: `state = overdue`, прибор подсвечен красным |
| FR-2 | INT-2 | Дано: прибор со схемы, которого нет в графике. Когда: мастер открывает схему. Тогда: `state = no_data`, подсветка нейтральная, не зелёная |
| FR-3 | INT-2 | Дано: схема с подсветкой. Когда: мастер снимает фильтр `ok`. Тогда: исправные приборы исчезают со схемы, запрос на бэк не уходит |
| FR-4 | INT-3 | Дано: прибор на схеме. Когда: мастер кликает по нему. Тогда: карточка показывает инвентарный номер, тип, ответственного, дату последней и следующей поверки |
| FR-5 | INT-2 | Дано: введён инвентарный номер прибора из ответа INT-2. Когда: мастер нажимает поиск. Тогда: прибор подсвечен и центрирован, нового запроса нет |

## 8. Допущения и открытые вопросы

  `metrolog-api`, у приборов есть инвентарные номера и координаты; роль «Метролог» заведена в
  security-сервисе. Валидировать при интеграции.
- **🟡 К валидации:** нет.
- **❓ Открытые решения:** нет.
- **⚠️ Требует уточнения:** порог состояния «срок подходит» — предложено 30 дней до
  `nextVerificationAt`, подтверждает служба главного метролога. До подтверждения значение живёт в
  конфиге сервиса, а не в коде.
- **Унаследовано из БТ (бизнес-пробелы):** нет — БТ закрыт.
- **Приложения из БТ:** §6 БТ обещает образец файла графика поверок. Он нужен до начала разработки —
  колонки INT-1 заданы нами, и надо убедиться, что выгрузка метролога кладётся в них без ручной
  правки.
