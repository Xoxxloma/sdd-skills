## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack, целиком новый функционал. Появляется сервис `canteen-api` — меню, заказы и сводка — и
клиент `canteen-web`. Единственная связь с существующим ландшафтом — корпоративная аутентификация и
кадровая система как источник списка сотрудников.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `canteen-api` | меню, заказы, отсечение в 16:00, сводка | Внутренние сервисы | 🟢 новый сервис |
| `canteen-web` | экран сотрудника и экран заведующей | Внутренние сервисы | 🟢 |
| Корпоративный SSO | аутентификация сотрудника, роль «Заведующая столовой» | Платформа | 🟡 подтв. аналитиком |
| Кадровая система | актуальный список сотрудников, признак увольнения | Кадры | 🟡 к валидации |

### 1.3. Связь с бизнес-требованиями
Сотрудник заранее выбирает обед и получает гарантию, что блюдо будет; заведующая и повар готовят по
фактическим заказам, а не по среднему за прошлый месяц. Трассировка FR-* — в §7.

## 2. Взаимодействия (ядро)

### INT-1. Публикация меню на день — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** заведующая набрала список блюд и нажала «Опубликовать»
- **Контракт (запрос):** `POST /v1/menus`; тело — `date: date` (день, НА который меню),
  `items: массив` строк-названий блюд, минимум одно
- **Контракт (ответ):** `date: date`; `publishedAt: iso8601`;
  `orderingClosesAt: iso8601` — момент отсечения заказов, считает сервер;
  `items: массив`, элемент — `itemId: string`, `name: string`
- **Пример запроса:**
  ```json
  { "date": "2026-08-08", "items": ["Борщ", "Котлета по-киевски", "Салат овощной"] }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "date": "2026-08-08",
    "publishedAt": "2026-08-07T17:20:00Z",
    "orderingClosesAt": "2026-08-08T13:00:00Z",
    "items": [
      { "itemId": "itm-01", "name": "Борщ" },
      { "itemId": "itm-02", "name": "Котлета по-киевски" },
      { "itemId": "itm-03", "name": "Салат овощной" }
    ]
  }
  ```
- **Ошибки:** `400` — пустой `items` или дата в прошлом; `403` — роль не «Заведующая столовой»;
  `409` — меню на эту дату уже опубликовано (повторная публикация — отдельное решение, см. §3.1)
- **Состояния UI по ответу:** значение → «меню на \<дата\> опубликовано»; ошибка `409` → предложение
  открыть уже опубликованное меню
- **Авторизация:** только роль «Заведующая столовой», проверяется в `canteen-api`
- **Происхождение:** 🟢
- **Трассировка:** FR-1

### INT-2. Меню на день для сотрудника — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** сотрудник открывает экран заказа
- **Контракт (запрос):** `GET /v1/menus/{date}`, тело отсутствует
- **Контракт (ответ):** `date: date`; `publishedAt: iso8601|null` — `null`, если меню на этот день не
  опубликовано, и тогда `items` пуст; `orderingClosesAt: iso8601`; `serverTime: iso8601` — момент
  ответа сервера, по нему фронт решает, показывать ли форму (§4.3);
  `items: массив` — `itemId: string`, `name: string`
- **Пример ответа (успех):**
  ```json
  {
    "date": "2026-08-08",
    "publishedAt": "2026-08-07T17:20:00Z",
    "orderingClosesAt": "2026-08-08T13:00:00Z",
    "serverTime": "2026-08-08T09:41:12Z",
    "items": [
      { "itemId": "itm-01", "name": "Борщ" },
      { "itemId": "itm-02", "name": "Котлета по-киевски" }
    ]
  }
  ```
- **Ошибки:** `400` — дата не разобрана
- **Состояния UI по ответу:** см. §4.3
- **Авторизация:** любой аутентифицированный сотрудник
- **Происхождение:** 🟢
- **Трассировка:** FR-2

### INT-3. Свой заказ — чтение — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** открытие экрана заказа, следом за INT-2
- **Контракт (запрос):** `GET /v1/orders/my?date=<date>`, тело отсутствует
- **Контракт (ответ):** `date: date`; `itemIds: массив строк` — пустой массив означает «заказа нет»
  и «заказ снят», это одно и то же состояние; `updatedAt: iso8601|null` — `null`, если заказа не
  было; `editable: bool` — можно ли ещё менять
- **Пример ответа (успех):**
  ```json
  { "date": "2026-08-08", "itemIds": ["itm-01"], "updatedAt": "2026-08-08T09:12:00Z", "editable": true }
  ```
- **Ошибки:** `400` — дата не передана или не разобрана
- **Авторизация:** сотрудник читает только свой заказ; идентификатор берётся из сессии, а не из
  параметра — чужой заказ запросить нечем
- **Происхождение:** 🟢
- **Трассировка:** FR-3, FR-4, FR-5

### INT-4. Свой заказ — сохранение — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** сотрудник отметил блюда и нажал «Сохранить заказ»
- **Контракт (запрос):** `PUT /v1/orders/my`; тело — `date: date`, `itemIds: массив строк`.
  Заменяет состав заказа целиком: добавление, снятие блюда и отмена всего заказа (`itemIds: []`) —
  один и тот же вызов. Повторный вызов с тем же телом даёт тот же результат — операция идемпотентна.
- **Контракт (ответ):** то же тело, что у INT-3
- **Пример запроса:**
  ```json
  { "date": "2026-08-08", "itemIds": ["itm-01", "itm-03"] }
  ```
- **Пример ответа (успех):**
  ```json
  { "date": "2026-08-08", "itemIds": ["itm-01", "itm-03"], "updatedAt": "2026-08-08T09:41:12Z", "editable": true }
  ```
- **Ошибки:** `400` — `itemId`, которого нет в меню этого дня; `404` — меню на дату не опубликовано;
  `409` (`reason: ordering_closed`) — приём заказов на эту дату уже закрыт
- **Состояния UI по ответу:** `409` → экран переходит в `menu_locked` и показывает «заказы
  закрылись, пока вы выбирали»; сохранённым считается только то, что вернул ответ
- **Авторизация:** сотрудник меняет только свой заказ; заведующая чужие заказы не редактирует —
  отдельного эндпоинта под это нет ни у кого (§5.3 БТ)
- **Происхождение:** 🟢
- **Трассировка:** FR-3, FR-4, FR-5

### INT-5. Актуальный список сотрудников из кадровой системы — 🟡 к валидации
- **Граница/направление:** Сервис `canteen-api` → кадровая система
- **Триггер:** регулярная синхронизация
- **Контракт (запрос):** к валидации — механизм не подтверждён (вызов API либо регулярная выгрузка)
- **Контракт (ответ):** к валидации — по словам аналитика источник отдаёт перечень действующих
  сотрудников и позволяет узнать, что сотрудник уволен; поля, формат и периодичность не подтверждены
- **Ошибки:** к валидации
- **Авторизация:** к валидации — потребуется ли `canteen-api` сервисная учётная запись, не
  подтверждено
- **Происхождение:** 🟡 к валидации (§3.3 БТ: «механизм интеграции определяется на этапе технической
  спецификации» — на момент написания спеки он аналитиком не подтверждён)
- **Трассировка:** косвенно — ограничивает круг тех, кто вправе заказывать (§3.3)

Конкретный путь, метод и пример тела для INT-5 не выписаны намеренно: это существующая чужая
система, правдоподобная конкретика здесь затвердела бы ниже по потоку в мнимый факт.

### INT-6. Сводка заказов по блюдам — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** заведующая открывает сводку
- **Контракт (запрос):** `GET /v1/orders/summary?date=<date>`, тело отсутствует
- **Контракт (ответ):** `date: date`; `asOf: iso8601`; `closed: bool` — закрыт ли приём заказов на
  эту дату; `items: массив` — `itemId: string`, `name: string`, `portions: int`.
  **В `items` попадает каждое блюдо меню, в том числе с `portions: 0`** — ноль порций и отсутствие
  строки различаются: первое означает «никто не заказал», второе — «блюда в меню не было».
- **Пример ответа (успех):**
  ```json
  {
    "date": "2026-08-08",
    "asOf": "2026-08-09T07:05:00Z",
    "closed": true,
    "items": [
      { "itemId": "itm-01", "name": "Борщ", "portions": 34 },
      { "itemId": "itm-02", "name": "Котлета по-киевски", "portions": 21 },
      { "itemId": "itm-03", "name": "Салат овощной", "portions": 0 }
    ]
  }
  ```
- **Ошибки:** `403` — роль не «Заведующая столовой»; `404` — меню на дату не публиковалось
- **Авторизация:** только роль «Заведующая столовой»
- **Происхождение:** 🟢
- **Трассировка:** FR-6

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| `400` | `reason: empty_menu\|date_in_past` | INT-1: пустой список блюд или прошедшая дата | сообщение в форме публикации |
| `400` | `reason: unknown_item` | INT-4: блюдо не из меню этого дня | `error_validation` |

## 3. Backend — ответственность

### 3.1. По сервисам
`canteen-api` реализует INT-1…INT-4 и INT-6, потребляет INT-5.

**Отсечение в 16:00 живёт на бэке, и только там.** `orderingClosesAt` считает сервер при публикации
меню: 16:00 дня заказа в часовом поясе офиса, в хранилище — UTC. INT-4 сравнивает момент **начала
обработки запроса** с `orderingClosesAt` внутри той же транзакции, в которой пишет заказ. Запрос,
пришедший в 15:59:59, но обработанный в 16:00:01, получает `409` — иначе проверка и запись
разъезжаются, и в сводку попадает заказ, сделанный после отсечения. Фронт блокирует форму по своему
таймеру (§4.3.1) ради удобства, но истина — ответ бэка.

Повторная публикация меню на ту же дату отклоняется (`409`): молча заменить опубликованное меню
нельзя — часть сотрудников уже могла заказать блюда, которых в новом составе нет. Правка меню в
объём задачи не входит (§3.2 БТ).

Сводка INT-6 считается на чтении, суммой по заказам. Счётчик порций не денормализуется: при
редактировании заказа его пришлось бы менять инкрементами, а это чтение-изменение-запись по
конкурентным заказам.

### 3.2. Данные и хранение
Четыре новые сущности (🟢):

- `Menu` — `date: date` (ключ), `publishedAt: timestamp`, `publishedBy: userId`,
  `orderingClosesAt: timestamp`.
- `MenuItem` — `itemId: string`, `date: date`, `name: string`. Индекс по `date`.
- `Order` — `orderId: string`, `employeeId: string`, `date: date`, `updatedAt: timestamp`.
  **Уникальное ограничение по паре `(employeeId, date)`** — один заказ на сотрудника в день
  обеспечивается индексом, а не проверкой «есть ли уже заказ» перед вставкой: два одновременных
  сохранения такую проверку проходят оба. INT-4 пишет вставкой с разрешением конфликта по этой паре.
- `OrderItem` — `orderId: string`, `itemId: string`, уникальная пара `(orderId, itemId)`. Сохранение
  заказа заменяет набор строк целиком в одной транзакции с обновлением `Order.updatedAt`.

Локального справочника сотрудников нет: право заказать даёт аутентификация в корпоративном SSO
(🟡 подтв. аналитиком). Нужно ли хранить копию списка из кадровой системы и как отражать увольнение —
зависит от механизма INT-5 и решается вместе с ним (открытый вопрос №1).

Миграции: четыре новые таблицы, точный DDL — в репозитории `canteen-api`. Ретеншен заказов и меню
задачей не ограничен.

### 3.3. Авторизация/доступ на бэке
INT-1 и INT-6 — только роль «Заведующая столовой». INT-2, INT-3, INT-4 — любой аутентифицированный
сотрудник, причём `employeeId` берётся из сессии: параметра «чей заказ» в контракте нет вовсе, так
что доступ к чужому заказу не выражается запросом. Уволенный сотрудник отсекается на стороне SSO;
дополнительная проверка по кадровым данным — вместе с INT-5.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Два экрана в `canteen-web`. Экран сотрудника: меню на день, отметки блюд, кнопка «Сохранить заказ»,
подпись со временем отсечения. Экран заведующей: форма публикации меню и сводка заказов по блюдам.
Вызовы: INT-2 и INT-3 при открытии экрана сотрудника, INT-4 при сохранении, INT-1 и INT-6 — на
экране заведующей.

### 4.2. Пользовательские сценарии
Сотрудник: открывает экран → видит опубликованное меню (FR-2) → отмечает блюда и сохраняет (FR-3) →
до отсечения может добавить, снять блюдо или отменить заказ целиком (FR-4) → после отсечения форма
только на чтение (FR-5).

Заведующая: вечером публикует меню на следующий день (FR-1) → утром открывает сводку и видит по
каждому блюду число заказанных порций (FR-6).

Ветвления: меню на день не опубликовано → `menu_absent`; сохранение пришло после отсечения → `409`,
экран переходит в `menu_locked` с явным сообщением, а не молча теряет выбор.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | ответы INT-2/INT-3 не получены | скелетон списка блюд |
| `menu_open` | 2xx, `publishedAt ≠ null`, `serverTime < orderingClosesAt` | меню, отметки, кнопка «Сохранить заказ» |
| `menu_locked` | 2xx, `publishedAt ≠ null`, `serverTime ≥ orderingClosesAt` | меню и свой заказ на чтение, подпись «заказы закрыты» |
| `menu_absent` | 2xx, `publishedAt = null` | «меню на этот день ещё не опубликовано» |
| `error_validation` | `400` на INT-4 | сообщение у списка блюд, выбор сохраняется на экране |
| `error_conflict` | `409` на INT-4 | «заказы закрылись, пока вы выбирали», далее `menu_locked` |
| `error_source` | `5xx` / таймаут / сеть | «столовая недоступна» + «Повторить» |
| `error_forbidden` | `403` на INT-1 / INT-6 | «доступно только заведующей»; штатно не возникает |

`empty` — не применимо в привычном виде: пустой `itemIds` в INT-3 означает «заказ снят», это
валидное содержимое `menu_open`, а не отдельное состояние экрана. На экране сводки `portions: 0`
показывается как «0», а не как «нет данных» — блюдо в меню было, заказов не было.

### 4.3.1. Loading и таймауты
- **Cold-path** (первые INT-2 и INT-3 при открытии экрана) — 5 с.
- **Warm-path** (повторное открытие, INT-4, INT-6) — 2 с.
- **Polling:** нет. Переход `menu_open` → `menu_locked` фронт делает локальным таймером на
  `orderingClosesAt`, сверяя часы по `serverTime` из INT-2, — расхождение часов устройства на минуту
  иначе закрывает форму раньше или позже отсечения. Опрашивать бэк ради этого не нужно.
- Таймаут, `5xx`, сетевая ошибка → `error_source`; отмеченные блюда с экрана не сбрасываются, чтобы
  повтор не заставлял выбирать заново.

### 4.4. Доступ по ролям в UI
Сотрудник — экран заказа, только свой заказ. Заведующая — публикация меню и сводка; отметок в чужих
заказах ей не показывают, потому что менять их не может никто (§5.3 БТ).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
Все взаимодействия синхронные. Кэша нет: меню читается раз за сессию, сводка должна быть точной на
момент открытия. Объём: сотрудников — сотни, блюд в меню — единицы, сводка считается по нескольким
сотням строк заказов за день. Синхронизация INT-5 — фоновая, вне пользовательского запроса.

### 5.2. Надёжность/деградация
`canteen-api` недоступен → `error_source` на обоих экранах; заказы не теряются, повтор сохранения
идемпотентен. Кадровая система недоступна → приём заказов продолжает работать: список сотрудников
влияет на круг заказывающих, а не на уже сделанные заказы. Сводка недоступна утром → заведующая
готовит по старой норме, как предусмотрено мерой из §2.3 БТ на период обкатки.

### 5.3. Безопасность/доступ (сводно)

| Роль | INT-1 публикация | INT-2/3/4 свой заказ | INT-6 сводка |
|------|------------------|----------------------|--------------|
| Сотрудник офиса | нет (`403`) | да, только свой | нет (`403`) |
| Заведующая столовой | да | да, как сотрудник — свой | да |

Чужой заказ не читается и не меняется никем: в контрактах INT-3 и INT-4 нет поля, которым можно
указать другого сотрудника.

## 6. Релиз и интеграция

### 6.1. Порядок выката
Сначала миграции и `canteen-api`, затем `canteen-web`. Синхронизация с кадровой системой (INT-5)
включается последней и отдельно — до её готовности сервис работает на аутентификации SSO.

### 6.2. Обратная совместимость
Ломать нечего: сервис новый, потребителей у его контрактов нет. Существующих систем задача не
меняет — кадровую систему только читает.

### 6.3. Фиче-флаги
Флагов нет — релизим атомарно: у нового сервиса нет прежнего поведения, к которому мог бы вернуть
флаг. Пилот ограничивается доступом по группе SSO, а не флагом в коде.

### 6.4. План отката
- **Только BE:** фронт получает `5xx` на всех вызовах и показывает `error_source`. Для нового
  сервиса это равнозначно недоступности функции — допустимо, но заведующую надо предупредить, иначе
  утром не будет сводки.
- **Только FE:** экраны исчезают, эндпоинты остаются без потребителей; заказы в базе сохраняются.
- **Откат DDL:** down-миграция удаляет четыре таблицы вместе с заказами — восстановить их
  неоткуда, повторить сотрудники смогут только вручную. Перед откатом выгрузить сводки по датам,
  на которые заказы уже приняты.

### 6.5. Преднастройка до релиза
- [ ] Роль «Заведующая столовой» в security-сервисе — завести и назначить (🟡 подтв. аналитиком:
      механизм ролей в SSO существует).
- [ ] DDL-миграция (четыре таблицы) в репозитории `canteen-api`.
- [ ] Конфиги по окружениям: часовой пояс офиса и час отсечения (16:00) — значением конфига, не
      константой в коде.
- [ ] Сервисный аккаунт для обращения к кадровой системе — зависит от механизма INT-5, заводится
      вместе с ним.
- [ ] Фиче-флаги — не применимо: релиз атомарный (§6.3).
- [ ] Алерты: `5xx` на INT-4 (потерянный заказ виден пользователю), расхождение времени сервера с
      NTP, неуспешная синхронизация INT-5.

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано: заведующая авторизована. Когда: публикует меню из трёх блюд на завтра. Тогда: ответ содержит три `itemId` и `orderingClosesAt` = 16:00 дня заказа |
| FR-1 | INT-1 | Дано: меню на дату уже опубликовано. Когда: заведующая публикует повторно. Тогда: `409 menu_exists`, прежнее меню не изменено |
| FR-2 | INT-2 | Дано: меню на сегодня опубликовано. Когда: сотрудник открывает экран. Тогда: видит список блюд и время отсечения |
| FR-3 | INT-4 | Дано: время до 16:00, заказа нет. Когда: сотрудник отмечает блюдо и сохраняет. Тогда: `itemIds` содержит это блюдо, INT-3 отдаёт его же |
| FR-4 | INT-4 | Дано: в заказе два блюда, время до 16:00. Когда: сотрудник снимает одно и сохраняет. Тогда: в ответе остаётся одно; повторное сохранение того же тела результат не меняет |
| FR-4 | INT-4 | Дано: в заказе есть блюда, время до 16:00. Когда: сотрудник сохраняет пустой `itemIds`. Тогда: заказ снят, INT-3 отдаёт пустой массив и `updatedAt` обновлён |
| FR-5 | INT-4 | Дано: 16:00 наступило. Когда: сотрудник сохраняет заказ. Тогда: `409 ordering_closed`, заказ в базе не изменён, экран переходит в `menu_locked` |
| FR-5 | INT-3 | Дано: 16:00 наступило. Когда: сотрудник открывает экран. Тогда: `editable = false`, форма только на чтение |
| FR-6 | INT-6 | Дано: за день 34 заказа на борщ, 0 на салат. Когда: заведующая открывает сводку. Тогда: борщ — 34, салат — строка с `portions: 0`, а не пропуск |

## 8. Допущения и открытые вопросы
- **🟡 Подтверждено аналитиком (не по коду):** сотрудники аутентифицируются в корпоративном SSO, и в
  нём же выражается роль «Заведующая столовой»; источник актуального списка сотрудников в кадровой
  системе существует и отражает увольнение. Валидировать при интеграции.
- **🟡 К валидации:** механизм, формат и периодичность получения списка сотрудников из кадровой
  системы (INT-5); нужна ли `canteen-api` сервисная учётная запись для этого; нужно ли хранить
  локальную копию списка.
- **❓ Открытые решения:** нет — все развилки, кроме INT-5, закрыты в этой спеке.
- **⚠️ Требует уточнения:** нет.
- **Унаследовано из БТ (бизнес-пробелы):** нет — БТ закрыт.
- **Приложения из БТ:** приложений заказчик не передавал. Мера из §2.3 БТ (первый месяц повар
  готовит по старой норме плюс заказы) на технические решения не влияет, но объясняет, почему
  недоступность сводки утром не является аварией — см. §5.2.
