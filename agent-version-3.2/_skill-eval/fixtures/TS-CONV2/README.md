# Фикстура TS-CONV2 — конвенции на задаче другой формы

Второй вход к тем же конвенциям, что и `TS-CONV`, но **противоположной формы**. Заведена
не ради повторов на одном БТ, а ради разброса: «сработало пять раз на `ARS-201`» ничего не
говорит о том, что скилл работает на другой задаче.

| | TS-CONV | TS-CONV2 |
|---|---|---|
| БТ | счётчик активных в шапке (`ARS-201`) | приём заявок на пропуск (`SMSEC-410`) |
| форма | fullstack, потребление **существующего** эндпоинта | **бэкенд-only**, новая интеграция извне |
| центр тяжести | 🟡 — чужой сервис, гейт на выжимку | 🟢 — всё проектируется с нуля |
| новые сущности | нет | **есть** — заявка с состоянием и сроком |
| где бьют конвенции | семантика `null`, коды, таймауты | путь, именование полей, значения enum, идемпотентность |

## Почему именно 🟢-тяжёлая задача

В `TS-CONV` конвенции применяются к небольшому куску: контракт по сути уже описан в выжимке.
Здесь чужого контракта нет вообще — скилл проектирует путь, состав полей, значения состояния и
поведение на повторную присылку сам, и **каждое** из этих решений имеет правило в
`CONVENTIONS.md`. Если конвенции где-то не применяются, видно будет здесь.

## Что должно произойти

**Слоты, которые обязаны сработать:**

| Слот конвенций | Куда бьёт в этой задаче |
|---|---|
| 1. путь `/v1/<множественное>` | 🟢 новый эндпоинт приёма заявки |
| 4. идемпотентность повторов | FR-3: повторная присылка не создаёт дубликата — это ровно идемпотентность, и ключ называется в назначении блока |
| 6. формат дат `iso8601` UTC, суффикс `At` | дата визита и дата окончания срока |
| 7. поля `camelCase`, значения enum нижним регистром латиницей | состояние заявки из FR-4: принята / отменена / срок истёк |
| 2. коды ошибок | FR-2: отклонение с причиной |

**Слот 5 (семантика `null`) здесь почти не применим** — и это тоже проверка: растягивать правило
на решение, которого оно не касается, запрещено.

## Ловушки

**1. Выжимка есть, но к задаче не относится.** В `services/` лежат `auth` и `arsenal-web` — ни
один из них в этой задаче не участвует. Скилл не должен притягивать их в §1.2 только потому, что
карточки прочитаны, и тем более не должен строить контракт вокруг чужого `GET /v1/sessions/count`.

**2. Новая сущность — это 🟢 и она идёт в §3.2.** По ней потом `stage-breakdown-doc` считает
инвентарь стыков; сущность без пометки происхождения для него неразличима.

**3. FR-3 читается как «дедупликация», а конвенция называет это идемпотентностью.** Правило слота 4
применимо, хотя слово «идемпотентный» в БТ не встречается ни разу.

**4. Даты две — визита и окончания срока.** Обе обязаны получить формат из конвенции; применить
правило к одной и забыть про вторую — самый вероятный недобор.

## Красный исход

Контракт спроектирован мимо конвенций (путь без версии, состояние заглавными, дата без формата);
либо `auth`/`arsenal-web` затянуты в затронутые сервисы; либо повторная присылка описана без
ключа, по которому распознаётся дубль.
