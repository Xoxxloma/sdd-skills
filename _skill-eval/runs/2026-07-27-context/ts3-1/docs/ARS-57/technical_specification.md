## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. Новое взаимодействие между веб-админкой «Арсенал» (фронт + бэк) и существующим сервисом аутентификации: бэк Арсенала получает у сервиса аутентификации число активных сессий и отдаёт его на фронт для отображения в шапке.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Админка «Арсенал» — фронт | Новый вызов INT-1, рендер индикатора | Арсенал-Core (по БТ п.1.3) | 🟢 |
| Админка «Арсенал» — бэк | Новый эндпоинт INT-1, новый вызов INT-2, кэш 30с | Арсенал-Core (по БТ п.1.3) | 🟢 |
| Сервис аутентификации | Источник числа активных сессий; уже умеет их считать | Не назван аналитиком | 🟡 подтв. аналитиком (умение) / 🟡 к валидации (владелец, контракт) |

### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ: администратор видит число активных пользователей в шапке, чтобы выбрать безопасное окно для регламентных работ. Трассировка FR-* — §7.

## 2. Взаимодействия (ядро)

### INT-1. Число активных пользователей (FE Арсенала → BE Арсенала) — 🟢
- **Граница/направление:** FE Арсенала → BE Арсенала
- **Триггер:** монтирование шапки (первая загрузка) + периодический опрос раз в минуту (60 с), пока страница открыта, только для роли «Администратор».
- **Контракт (запрос):** GET, без тела и параметров; путь — деталь реализации бэка Арсенала (стеко-агностично); авторизация — текущая сессия администратора.
- **Контракт (ответ):**
  - `count` — `integer | null`. `null` → источник недоступен или кэш ещё не наполнен → фронт показывает «—». Любое целое (включая `0`) — валидное значение, отображается как есть.
- **Пример запроса:** тело отсутствует (GET, без параметров).
- **Пример ответа (успех):**
  ```json
  { "count": 128 }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  { "count": null }
  ```
- **Ошибки:** см. «Каталог ошибок». Ключевое решение (подтверждено аналитиком): недоступность источника — НЕ HTTP-ошибка этого контракта; бэк Арсенала перехватывает сбой INT-2 и отдаёт `200 { "count": null }`. Сбой самого INT-1 (бэк Арсенала недоступен целиком: 5xx/сеть/таймаут) — тоже ведёт к «—» на фронте, без баннера ошибки (UX-пожелание БТ §6: индикатор неяркий, не отвлекает).
- **Состояния UI по ответу:** значение → показать число; `count=null` (2xx) → «—»; сетевая ошибка/таймаут/5xx самого INT-1 → «—» (без ретрай-баннера); 403 (роль не «Администратор») → элемент не рендерится вовсе.
- **Авторизация:** только роль «Администратор» (подтверждено аналитиком). Бэк проверяет роль на каждом вызове (403 иначе); фронт также не рендерит элемент для «Оператора».
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2, FR-3

### INT-2. Число активных сессий (BE Арсенала → сервис аутентификации) — 🟡
- **Граница/направление:** BE Арсенала → сервис аутентификации
- **Триггер:** первый запрос INT-1 после истечения TTL кэша (30 с) в бэке Арсенала — лениво обновляет кэш вызовом к сервису аутентификации (🟢 дизайн-решение по кэшу; TTL и место кэша подтверждены аналитиком).
- **Контракт (запрос):** существующий механизм сервиса аутентификации для получения числа активных сессий — точный метод/путь **не подтверждён аналитиком** → 🟡 к валидации, путь и параметры не приводятся (не выдумываются).
- **Контракт (ответ):** ожидается число активных сессий; точная форма ответа (имя поля, тип, семантика при отсутствии данных) — 🟡 к валидации, конкретный JSON не приводится (правило: конкретика — только для 🟢).
- **Пример запроса/ответа:** не приводится — контракт существующего сервиса не подтверждён аналитиком.
- **Ошибки:** недоступность/таймаут/ошибка сервиса аутентификации → бэк Арсенала трактует как «нет данных» и отдаёт на INT-1 `count: null` (🟢 дизайн-решение бэка Арсенала). Собственный каталог ошибок сервиса аутентификации не описываем — вне зоны видимости.
- **Состояния UI:** не применимо напрямую — это межсервисный вызов, состояния формируются на INT-1.
- **Авторизация:** способ, которым бэк Арсенала аутентифицируется перед сервисом аутентификации (сервисный аккаунт/токен/сеть) — 🟡 к валидации, не описан аналитиком.
- **Происхождение:** 🟡 подтверждено аналитиком (сам факт «сервис уже считает число активных сессий», не по коду) + 🟡 к валидации (точный контракт/эндпоинт/владелец).
- **Трассировка:** FR-3 (косвенно, как источник данных для INT-1)

### Каталог ошибок
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200, `count: <int>` | `{ "count": N }` | Успех, есть значение (включая `0`) | Показать число, «0» — тоже число |
| 200, `count: null` | `{ "count": null }` | Источник (сервис аутентификации) недоступен либо кэш не наполнен | «—» |
| 403 | тело ошибки доступа (стеко-специфично) | Вызов не ролью «Администратор» | Элемент не рендерится |
| 5xx / таймаут / сеть (сам INT-1) | — | Бэк Арсенала недоступен целиком | «—» (без ошибки пользователю) |

## 3. Backend — ответственность

### 3.1. По сервисам
- **Бэк Арсенала:** реализует INT-1 (эндпоинт, проверка роли, кэш 30 с); потребляет INT-2 (вызов к сервису аутентификации). 🟢 новая логика: получить число активных сессий, закэшировать на 30 с, отдать `count` (int|null); при сбое INT-2 — отдать `null`, не поднимать ошибку на INT-1.
- **Сервис аутентификации:** уже считает число активных сессий (🟡 подтверждено аналитиком, не по коду; валидировать при интеграции). Точный способ получения этого числа — 🟡 к валидации.

### 3.2. Данные и хранение
Новых сущностей и таблиц нет (подтверждено аналитиком явно). Кэш на 30 секунд — эфемерный (не персистентная сущность), миграции не требуются.

### 3.3. Авторизация/доступ на бэке
Эндпоинт INT-1 проверяет роль вызывающего — доступ только роли «Администратор» (подтверждено аналитиком); иной роли — 403. Авторизация вызова INT-2 к сервису аутентификации — 🟡 к валидации, не описана аналитиком.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Шапка админки «Арсенал»: новый элемент-индикатор числа активных пользователей, виден только роли «Администратор». Вызывает INT-1.

### 4.2. Пользовательские сценарии
Основной: администратор открывает любой экран → шапка показывает индикатор → значение обновляется раз в минуту без перезагрузки (FR-1, FR-2). Ветвление: источник недоступен → «—» вместо числа, не ошибка (FR-3). «Оператор» индикатор не видит вовсе (ролевая модель БТ §5.3).

### 4.3. Состояния
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | Первый запрос INT-1 после открытия страницы | Обычный спиннер (подтверждено аналитиком) |
| `value` | 200, `count` — целое ≠ 0 и ≠ null | Число |
| `zero` | 200, `count = 0` | «0» (не «—») |
| `empty` | 200, `count = null` | «—» |
| `error_source` | Сетевая ошибка/5xx/таймаут самого INT-1 | «—» (без баннера ошибки — UX-пожелание «неяркий индикатор») |
| `error_forbidden` | 403 (роль не «Администратор») | Элемент не рендерится вовсе |

### 4.3.1. Loading и таймауты
- Таймаут cold-path (первая загрузка) и warm-path (последующий опрос) — конкретные значения аналитиком не обсуждались. 🟢 Предлагаемые дефолты: cold ~5 с, warm ~3 с — при превышении см. `error_source` → «—». **TBD: подтвердить или скорректировать** (см. «Открытые вопросы», п.5).
- **Polling:** интервал 60 с (подтверждено аналитиком); джиттер — не обсуждался, не применяется по умолчанию (нагрузка невелика — см. §5.1).
- Таймаут/5xx/сетевая ошибка → состояние `error_source` (см. §4.3).

### 4.4. Доступ по ролям в UI
«Администратор» — видит индикатор; «Оператор» — индикатор не отображается (роли из БТ §5.3). Преднастройка роли «Администратор» — до релиза (подтверждено аналитиком, см. §6.5).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- Опрос: FE → BE, раз в минуту (подтверждено аналитиком), синхронный HTTP request/response.
- Кэш: 30 секунд, в бэке Арсенала (подтверждено аналитиком). TTL короче интервала опроса одного пользователя — это ожидаемо: кэш снижает нагрузку не для одного администратора, а при **перекрывающихся опросах нескольких** одновременно открытых сессий администраторов.
- Ожидаемая нагрузка: несколько администраторов могут одновременно держать открытой админку; кэш держит число обращений к сервису аутентификации ограниченным независимо от числа открытых вкладок.

### 5.2. Надёжность/деградация
При недоступности сервиса аутентификации бэк Арсенала отдаёт `count: null`; фронт показывает «—» без сообщения об ошибке (FR-3, подтверждено аналитиком: «это не ошибка»). При недоступности самого бэка Арсенала фронт применяет тот же принцип через `error_source` (§4.3).

### 5.3. Безопасность/доступ (сводно)
| Кто | Может |
|-----|-------|
| Администратор | Видит индикатор, вызывает INT-1 |
| Оператор | Индикатор скрыт на фронте; бэк отдаёт 403, если вызов всё же произошёл |

## 6. Релиз и интеграция

### 6.1. Порядок выката
Бэк Арсенала выкатывается раньше фронта (подтверждено аналитиком): эндпоинт INT-1 должен существовать до того, как фронт начнёт его вызывать. Роль «Администратор» настраивается до релиза (см. §6.5).

### 6.2. Обратная совместимость
Изменение чисто аддитивное: новый эндпоинт INT-1, изменений в существующих контрактах нет, существующие потребители не затрагиваются.

### 6.3. Фиче-флаги
Флаги не описаны аналитиком — релизим атомарно (порядок из §6.1); видимость и так контролируется ролью «Администратор».

### 6.4. План отката
- **Откат только BE:** FE новой версии получит 404/5xx на INT-1 → трактуется как `error_source` → «—» — деградация без падения, откат безопасен.
- **Откат только FE:** BE отдаёт новый контракт, но FE старой версии (без индикатора) его не вызывает и не показывает элемент — безопасно, локального стейта у фичи нет.
- **Откат DDL:** не применимо — новых сущностей/миграций нет (§3.2).

## 7. Трассировка приёмки
