### 1.1. Тип и стороны
Fullstack: новый элемент UI в шапке админки «Арсенал» + новый бэкенд-эндпоинт в BE «Арсенала», который потребляет существующий сервис аутентификации как источник данных о числе активных сессий.

## 2. Взаимодействия (ядро)

### INT-1. Получение числа активных пользователей (FE → BE Арсенала) — 🟢
- **Граница/направление:** FE админки «Арсенал» → BE админки «Арсенал»
- **Триггер:** открытие любого экрана админки; далее — периодический опрос (раз в минуту, см. §5.1)
- **Контракт (запрос):** `GET /api/admin/active-users-count` (новый эндпоинт; точное соглашение об именовании пути — на усмотрение реализации BE Арсенала); без тела и параметров.
- **Контракт (ответ):**
  - `count` (integer | null, обязательное) — число активных пользователей; `null` означает «источник данных недоступен» → фронт показывает «—» (не 0 и не текст ошибки).
- **Пример запроса:** тело отсутствует (GET)
- **Пример ответа (успех):**
  ```json
  { "count": 42 }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  { "count": null }
  ```
- **Ошибки:** см. «Каталог ошибок» ниже.
- **Состояния UI по ответу:** значение → показать `count`; `count = 0` → показать «0» (валидный ноль, не «—»); `count = null` или сбой самого запроса INT-1 (сеть/5xx/timeout) → «—»; во время запроса → обычный спиннер.
- **Авторизация:** доступен только роли «Администратор»; enforced на BE (403 для прочих ролей) и элемент отсутствует в UI для роли «Оператор».
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2, FR-3

### INT-2. Число активных сессий (BE Арсенала → сервис аутентификации) — 🟡
- **Граница/направление:** BE Арсенала → сервис аутентификации
- **Триггер:** обновление локального кэша BE Арсенала (TTL 30 с, см. §5.1) — не на каждый вызов INT-1, а не чаще раза в 30 секунд
- **Контракт (запрос):** 🟡 к валидации — точный метод/путь не подтверждён аналитиком; конкретный путь не проектируется и не предполагается (существующий сервис — правило провенанса запрещает выдумывать даже как «предварительный пример»).
- **Контракт (ответ):** 🟡 подтверждено аналитиком, что сервис аутентификации умеет отдавать число активных сессий (факт, не по коду; валидировать при интеграции). Точная форма ответа (имя поля, тип, доп. метаданные) — 🟡 к валидации.
- **Пример запроса/ответа:** не приводится — существующий сервис, конкретные path/JSON не подтверждены аналитиком.
- **Ошибки:** недоступность/ошибка сервиса аутентификации → BE Арсенала транслирует это в ответ INT-1 как `{ "count": null }` (см. INT-1); наружу на фронт как ошибка не пробрасывается.
- **Состояния UI:** не применимо — эта граница фронту напрямую не видна (см. состояния INT-1).
- **Авторизация:** механизм межсервисной авторизации (сервисный токен/аккаунт и т.п.) — 🟡 к валидации.
- **Происхождение:** 🟡 подтверждено аналитиком (факт наличия возможности) / 🟡 к валидации (точный контракт)
- **Трассировка:** FR-1, FR-3 (источник данных для INT-1)

## 3. Backend — ответственность
### 3.1. По сервисам
- **BE Арсенала:** реализует INT-1 (🟢); потребляет INT-2 (🟡); держит кэш ответа INT-2 на 30 с (§5.1); при сбое/недоступности INT-2 транслирует это в `{ "count": null }` на INT-1, никогда не отдаёт устаревшее значение как актуальное.
- **Сервис аутентификации:** отдаёт число активных сессий (🟡 подтверждено аналитиком); точный контракт вызова — к валидации.

### 3.2. Данные и хранение
Новых сущностей/таблиц нет (подтверждено аналитиком явно). Кэш на 30 с — эфемерный, в памяти BE Арсенала, без персистентного хранения. Миграции не требуются.

### 3.3. Авторизация/доступ на бэке
Эндпоинт INT-1 доступен только роли «Администратор»; проверка — на BE Арсенала (переиспользует существующую ролевую модель, БТ §5.3), 403 для прочих ролей, включая «Оператор». Межсервисная авторизация BE Арсенала → сервис аутентификации (INT-2) — 🟡 к валидации.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Шапка админки «Арсенал»: новый неяркий индикатор числа активных пользователей (БТ §6, UX-пожелание). Вызывает INT-1.

### 4.2. Пользовательские сценарии
Администратор открывает любой экран → видит индикатор в шапке → значение обновляется каждую минуту без перезагрузки страницы (FR-1, FR-2). Оператор индикатор не видит — элемент не рендерится для этой роли (ролевая модель БТ §5.3).

### 4.3. Состояния
| Имя состояния | Условие | Что видит пользователь |
|----------------|---------|--------------------------|
| `loading` | Первый запрос INT-1 | Обычный спиннер |
| `value` | `count` — число > 0 | Число |
| `zero` | `count = 0` | «0» |
| `empty` | `count = null`, либо сбой/недоступность самого запроса INT-1 (сеть, 5xx, timeout) | «—» |
| `error_forbidden` | 403 (роль ≠ «Администратор») | Не применимо — элемент не рендерится для этой роли, до вызова |

### 4.3.1. Loading и таймауты
- Cold-path (первая загрузка) и warm-path (последующие обновления) таймауты — 🟡 к валидации, аналитик не называл конкретные значения.
- Polling: интервал 1 минута (подтверждено аналитиком). Джиттер — 🟢 не предусмотрен: единственный периодический вызов на клиента, фиксированный интервал, риск синхронной нагрузки низкий.
- При таймауте / 5xx / сетевой ошибке INT-1 — состояние `empty` («—»), без текста ошибки и без retry-баннера (согласовано с FR-3 и БТ §2.3: не показывать ошибку и не показывать устаревшее значение).

### 4.4. Доступ по ролям в UI
Индикатор виден только роли «Администратор»; роль «Оператор» индикатор не видит (БТ §5.3, подтверждено в этом раунде интервью).

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
FE опрашивает BE Арсенала раз в минуту (пуллинг, подтверждено аналитиком). BE Арсенала кэширует ответ INT-2 на 30 секунд — кэш выбран в бэке Арсенала (аналитик подтвердил из развилки «кэш в бэке Арсенала» / «кэш в сервисе аутентификации» / «без кэша»). Ожидаемая нагрузка — низкая: один периодический вызов на открытую сессию администратора.

### 5.2. Надёжность/деградация
При недоступности сервиса аутентификации (INT-2) BE Арсенала не ошибается наружу — отдаёт `{ "count": null }`; фронт показывает «—», не ошибку и не устаревшее значение (БТ §2.3, FR-3).

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Где проверяется |
|---------|-----------|-------------------|
| FE → BE (INT-1) | Роль «Администратор» | BE Арсенала (403 иначе) + скрытие в UI |
| BE Арсенала → сервис аутентификации (INT-2) | 🟡 к валидации | 🟡 к валидации |

## 6. Релиз и интеграция
### 6.1. Порядок выката
BE Арсенала (с новым эндпоинтом INT-1) выкатывается раньше FE (подтверждено аналитиком). Роль «Администратор» настраивается/включается для видимости индикатора до релиза (подтверждено аналитиком).

### 6.2. Обратная совместимость
Новый эндпоинт не меняет существующие контракты — обратная совместимость не нарушается. Старый FE, ещё не знающий об INT-1, продолжает работать без изменений после выката нового BE.

### 6.3. Фиче-флаги
Флагов нет — релизим атомарно; безопасность раскатки обеспечивает порядок выката (§6.1).

### 6.4. План отката
- **Откат только BE** (FE — новая версия, BE — старая): INT-1 недоступен (404/5xx) → фронт трактует это как `empty` → «—» (см. §4.3); деградация не критична, откат допустим.
- **Откат только FE** (BE — новая версия, FE — старая): FE не знает об INT-1 и не вызывает его — безопасно, локального стейта, требующего миграции, нет.
- **Откат DDL:** не применимо — новых сущностей/миграций нет (§3.2).

### 6.5. Преднастройка до релиза
- [x] Роли в security-сервисе — роль «Администратор» уже существует (БТ §5.3); настроить видимость нового индикатора для неё до релиза (подтверждено аналитиком).
- [ ] DDL-миграция в репо владеющего сервиса — не применимо: новых сущностей нет.
- [ ] Конфиги по окружениям (dev/staging/prod) — 🟡 к валидации: зависят от эндпоинта INT-2, который сам к валидации.
- [ ] Сервисные аккаунты для межсервисных вызовов — 🟡 к валидации (см. §3.3, §5.3).
- [x] Фиче-флаги заведены — не применимо, флагов нет (§6.3).
