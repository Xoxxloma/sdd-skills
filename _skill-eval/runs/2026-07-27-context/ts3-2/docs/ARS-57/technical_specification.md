## 1. Обзор изменения
### 1.1. Тип и стороны
Fullstack. Новый бэкенд-эндпоинт в «Арсенал» BE (INT-1) + новый UI-элемент в шапке «Арсенал» FE, потребляющий существующий сервис аутентификации через новый межсервисный вызов (INT-2).

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|-------------------|----------------|
| Админка «Арсенал» — фронтенд | новый UI-элемент (индикатор), вызывающая сторона INT-1 | команда «Арсенал-Core» (см. БТ 1.3) | 🟢 |
| Админка «Арсенал» — бэкенд | новый эндпоинт INT-1, потребитель INT-2, кэш 30с | команда «Арсенал-Core» (см. БТ 1.3) | 🟢 |
| Сервис аутентификации | существующий источник числа активных сессий (INT-2), сам не меняется | не указан аналитиком | 🟡 подтверждено аналитиком (сама возможность) / 🟡 к валидации (эндпоинт, владелец) |

### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ 2.1: администратор видит текущее число активных пользователей в шапке, чтобы выбрать безопасное окно регламентных работ (FR-1–FR-3, через INT-1).

## 2. Взаимодействия (ядро)

### INT-1. Получение числа активных пользователей — 🟢
- **Граница/направление:** FE «Арсенал» → BE «Арсенал»
- **Триггер:** открытие любого экрана админки (первый запрос) + периодический опрос (поллинг) раз в 60 секунд.
- **Контракт (запрос):** `GET /api/active-users/count` (путь концептуальный, стеко-агностичный). Параметров и тела нет. Авторизация — существующая сессия администратора (см. §3.3), отдельный механизм входа не вводится.
- **Контракт (ответ):**
  - `count`: `integer | null`.
    - целое ≥ 0 — текущее число активных пользователей (0 — валидное значение, «сейчас никого»);
    - `null` — источник данных (сервис аутентификации) недоступен/вернул ошибку/не ответил вовремя; BE Арсенала перехватывает это состояние сам и не пробрасывает ошибку на фронт (см. каталог ошибок).
- **Пример запроса:** тело отсутствует (GET).
- **Пример ответа (успех, значение):**
  ```json
  { "count": 128 }
  ```
- **Пример ответа (валидный ноль):**
  ```json
  { "count": 0 }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  { "count": null }
  ```
- **Ошибки:** см. «Каталог ошибок» ниже.
- **Состояния UI по ответу:** значение → показать число (`value`/`zero`); загрузка → спиннер (только на первом запросе, см. §4.3.1); `count: null` → «—» (`empty`, это НЕ ошибка — FR-3); HTTP-ошибка/сетевой сбой запроса → тоже «—» (🟢 авторское решение: расширяет принцип FR-3 на уровень транспорта FE↔BE ради единообразия и безопасного отката, аналитиком отдельно не оговаривалось).
- **Авторизация:** вызывать и видеть вправе только роль «Администратор»; BE проверяет роль независимо от фронта (см. §3.3); «Оператор» — негативный случай, 403.
- **Происхождение:** 🟢 новое.
- **Трассировка:** FR-1, FR-2, FR-3.

### INT-2. Получение числа активных сессий у сервиса аутентификации — 🟡
- **Граница/направление:** BE «Арсенал» → сервис аутентификации (существующий).
- **Триггер:** истечение TTL локального кэша в BE Арсенала (30 секунд) — то есть не на каждый запрос от FE, а не чаще, чем раз в 30 секунд.
- **Контракт (запрос/ответ):** 🟡 к валидации. Аналитик подтвердил, что сервис аутентификации уже умеет считать число активных сессий, но точный путь/метод/формат ответа сейчас не помнит. **Конкретный путь и JSON-пример намеренно не приводятся** — только словесное описание, чтобы не выдать правдоподобную догадку за факт.
- **Ошибки/недоступность:** любая ошибка, таймаут или некорректный ответ от сервиса аутентификации перехватывается BE Арсенала и транслируется в INT-1 как `count: null` (не как HTTP-ошибка наружу).
- **Авторизация:** механизм аутентификации BE Арсенала перед сервисом аутентификации (сервисный аккаунт/токен) — 🟡 к валидации.
- **Происхождение:** 🟡 подтверждено аналитиком (сама способность считать активные сессии) + 🟡 к валидации (эндпоинт, авторизация).
- **Трассировка:** поддерживает INT-1 косвенно; прямой трассировки к FR-* не имеет (аналитик: «FR-1, FR-2, FR-3 → INT-1»).

### Каталог ошибок (сводно)
| Код/случай | Тело/сообщение | Когда | Состояние UI |
|------------|-----------------|-------|---------------|
| 200 | `{ "count": <int> }` | источник доступен, значение известно | `value` (>0) / `zero` (=0) |
| 200 | `{ "count": null }` | сервис аутентификации недоступен/ошибка/таймаут (перехвачено BE) | `empty` — «—» (не ошибка, FR-3) |
| 401 | стандартный формат ошибок админки | нет валидной сессии | стандартная обработка приложения, не специфично для фичи |
| 403 | стандартный формат ошибок админки | роль вызывающего ≠ «Администратор» | `error_forbidden` — в норме не возникает, т.к. элемент скрыт на фронте для «Оператора»; сценарий актуален только при прямом вызове API |
| сетевой сбой / BE Арсенала недоступен целиком | — | нет ответа на INT-1 | 🟢-решение: трактовать так же, как «источник недоступен» → «—» |

## 3. Backend — ответственность
### 3.1. По сервисам
- **BE «Арсенал»:** реализует INT-1 (отдаёт `count`); потребляет INT-2 у сервиса аутентификации; держит кэш результата INT-2 с TTL = 30 секунд (снижает нагрузку на сервис аутентификации, когда несколько администраторов опрашивают BE Арсенала в пределах одного 30-секундного окна); перехватывает любые ошибки INT-2 и превращает их в `count: null`; проверяет роль вызывающего перед выдачей `count`.
- **Сервис аутентификации:** существующий, только потребляется (не изменяется в рамках задачи). Способность считать активные сессии — 🟡 подтверждено аналитиком; точный контракт — 🟡 к валидации.

### 3.2. Данные и хранение
Новых сущностей/таблиц нет — подтверждено аналитиком явно. Кэш TTL = 30 секунд — runtime-состояние BE Арсенала (не персистентная сущность, конкретный механизм кэширования — на усмотрение владеющего сервиса). Миграции не требуются.

### 3.3. Авторизация/доступ на бэке
BE Арсенала проверяет роль вызывающего пользователя перед выдачей `count` по INT-1: роль = «Администратор» → 200; иная роль → 403. Для INT-2 механизм авторизации между сервисами — 🟡 к валидации (см. §6.5).

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Шапка админки «Арсенал» — новый неяркий элемент-индикатор числа активных пользователей (пожелание УХ из БТ §6: не отвлекает от основной работы). Вызывает INT-1.

### 4.2. Пользовательские сценарии
Администратор открывает любой экран админки → шапка сразу инициирует INT-1 → значение отображается → далее автообновление раз в 60 секунд без перезагрузки страницы (FR-2) → если `count: null` (источник недоступен), в шапке показывается «—» вместо числа или ошибки (FR-3). «Оператор» индикатор не видит вовсе — элемент не рендерится и INT-1 для него не вызывается.

### 4.3. Состояния
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|--------------------------|
| `loading` | первый запрос при открытии экрана (до первого ответа) | спиннер |
| `value` | 200, `count` — целое > 0 | число |
| `zero` | 200, `count` = 0 | «0» (не «—») |
| `empty` | 200, `count` = null (источник недоступен) | «—» |
| `error_forbidden` | 403 | не применимо для «Администратора»; для «Оператора» элемент не рендерится вовсе |
| (нет отдельного `error_source`) | — | недоступность источника намеренно folded в `empty` (FR-3: «не ошибка») |

### 4.3.1. Loading и тайм-ауты
- Спиннер показывается только на первом (cold) запросе при открытии экрана; последующие фоновые опросы (warm, раз в 60с) обновляют значение «тихо», без спиннера — сохраняет текущее число на экране до получения нового (🟢 дизайн-решение, согласуется с УХ-пожеланием «не отвлекает» из БТ §6). Аналитик подтвердил только «обычный спиннер», без деления cold/warm — деление предложено автором спеки.
- **Polling:** интервал 60 секунд (подтверждено). Jitter — ⚠️ не обсуждался, не задан.
- Конкретные числовые тайм-ауты (мс до перевода в состояние ошибки) — ⚠️ не заданы аналитиком; при недоступности самого BE Арсенала действует то же правило «показать —», отдельного таймера ожидания не описано.
- 5xx/сетевая ошибка → состояние `empty` («—»), см. §2.

### 4.4. Доступ по ролям в UI
Индикатор виден только роли «Администратор» (см. ролевую модель БТ §5.3): FE проверяет роль текущего пользователя перед рендером блока; при роли «Оператор» элемент не рендерится и INT-1 не вызывается.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Синхронный HTTP-поллинг с фронта раз в 60 секунд (подтверждено). Кэш результата INT-2 — в BE Арсенала, TTL = 30 секунд (подтверждено). Точные тайм-ауты и ожидаемая нагрузка — не обсуждались отдельно (внутренняя аудитория, малый объём запросов ожидается, отдельно не оценивалось).

### 5.2. Надёжность/деградация
При недоступности сервиса аутентификации BE Арсенала не пробрасывает ошибку на фронт, а отдаёт `count: null` — пользователь видит «—» вместо ошибки или устаревшего значения (мера снижения риска из БТ 2.3). При недоступности самого BE Арсенала фронт трактует сетевой сбой так же («—», см. §2).

### 5.3. Безопасность/доступ (сводно)
| Роль | INT-1 (вызов) | Индикатор в UI |
|------|----------------|-----------------|
| Администратор | разрешено | виден |
| Оператор | 403 (при прямом вызове API) | скрыт |

## 6. Релиз и интеграция
### 6.1. Порядок выката
BE «Арсенал» (INT-1 + интеграция INT-2) выкатывается первым; FE «Арсенал» (индикатор) — после (подтверждено аналитиком). Причина: FE зависит от нового контракта BE.

### 6.2. Обратная совместимость
Новый эндпоинт INT-1 чисто аддитивный, существующие контракты не меняются. Со стороны сервиса аутентификации меняется только то, что появляется новый потребитель (чтение) — на существующих потребителей это не влияет.

### 6.3. Фиче-флаги
Флагов нет — релизим атомарно; безопасность обеспечивается самим порядком деплоя (BE → FE) и аддитивностью изменений.

### 6.4. План отката
- **Откат только BE** (FE уже новой версии): FE получает ошибку/недоступность по INT-1 → по дизайну §2 трактуется как «источник недоступен» → «—»; синхронный откат FE не обязателен.
- **Откат только FE:** BE отдаёт новый контракт, но старый FE его не вызывает и индикатор не показывает — безопасно, локального состояния у фичи нет.
- **Откат DDL:** не применимо — новых сущностей/миграций нет.

### 6.5. Преднастройка до релиза
- [x] Роли в security-сервисе — роль «Администратор» настраивается до релиза (подтверждено аналитиком).
- [ ] DDL-миграция в репо владеющего сервиса — не применимо: новых сущностей нет.
- [ ] Конфиги по окружениям (dev/staging/prod) — адрес/подключение к сервису аутентификации для INT-2 — 🟡 к валидации (зависит от эндпоинта, который сейчас не определён).
- [ ] Сервисные аккаунты для межсервисных вызовов — 🟡 к валидации (механизм авторизации BE→сервис аутентификации не определён).
- [x] Фиче-флаги заведены — не требуются (см. §6.3).
- [ ] Алерты/мониторинг на ключевые ошибки — не обсуждалось; ⚠️ рекомендация автора спеки — мониторить долю `count: null` в ответах INT-1 как индикатор деградации источника (аналитиком не подтверждено).

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|--------------------|-------------------------------|
| FR-1 | INT-1 | Дано открытую админку под ролью «Администратор», когда страница загрузилась и выполнен запрос INT-1, тогда в шапке отображается число активных пользователей (или «—», если `count: null`). |
| FR-2 | INT-1 | Дано открытую админку с активным поллингом (раз в 60с), когда число активных сессий на стороне источника изменилось, тогда счётчик в шапке обновляется без перезагрузки страницы в пределах следующего цикла опроса. |
| FR-3 | INT-1 | Дано, что сервис аутентификации недоступен (INT-2 завершается ошибкой/таймаутом), когда BE Арсенала обрабатывает запрос INT-1, тогда ответ содержит `count: null`, и в шапке отображается «—», а не ошибка или устаревшее число. |

## 8. Допущения и открытые вопросы
- **🟡 Подтверждено аналитиком (не по коду):** сервис аутентификации уже умеет считать число активных сессий — валидировать при интеграции.
- **🟡 К валидации:**
  - точный эндпоинт/контракт сервиса аутентификации для INT-2 (метод, путь, схема ответа);
  - механизм service-to-service авторизации BE Арсенала → сервис аутентификации;
  - владелец/команда сервиса аутентификации;
  - конфиги окружений и сервисные аккаунты для подключения INT-2 (зависят от пункта выше).
- **❓ Открытые решения:** нет нерешённых архитектурных развилок.
- **⚠️ Требует уточнения:**
  - конкретные числовые тайм-ауты (cold/warm) на фронте и необходимость jitter при поллинге;
  - нужен ли алертинг/мониторинг по доле `count: null` (рекомендация, не подтверждена).
- **Унаследовано из БТ (бизнес-пробелы):** нет — БТ имеет статус «Готово к оценке» без открытых пунктов.
- **Приложения из БТ:** УХ-пожелание — индикатор неяркий, не отвлекает от основной работы (учтено в §4.1/§4.3.1: без спиннера на фоновых опросах).
