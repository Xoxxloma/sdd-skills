## 1. Обзор изменения
### 1.1. Тип и стороны
Fullstack. Новый эндпоинт на бэке «Арсенала», новый элемент в шапке фронта «Арсенала», новый исходящий вызов от бэка «Арсенала» к существующему сервису аутентификации.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Админка «Арсенал» — фронт | новый UI-элемент, вызывает INT-1 | команда «Арсенал-Core» (из БТ) | 🟢 |
| Админка «Арсенал» — бэк | новый эндпоинт INT-1, вызывает INT-2, держит кэш 30с | команда «Арсенал-Core» (из БТ) | 🟢 |
| Сервис аутентификации | существующий источник счёта активных сессий (INT-2) | 🟡 к валидации — не назван | 🟡 подтв. аналитиком (возможность) / 🟡 к валидации (контракт, владелец) |
### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель БТ: администратор видит число активных пользователей в шапке, чтобы выбрать безопасное окно для регламентных работ. Связка с FR-* — §7.

## 2. Взаимодействия (ядро)

### INT-1. Получение счётчика активных пользователей — 🟢
- **Граница/направление:** FE Арсенала → BE Арсенала
- **Триггер:** открытие любого экрана админки (первая загрузка) и далее периодический опрос раз в минуту, пока экран открыт.
- **Контракт (запрос):** `GET /api/admin/active-users-count` (путь — предложение этого документа, финализируется в репозитории «Арсенала»); тело отсутствует; параметров нет.
- **Контракт (ответ):** `count: number | null`. `count` — целое ≥ 0, число активных пользователей. `null` — источник данных недоступен/не удалось получить вовремя → фронт показывает «—» (это не ошибка, см. FR-3).
- **Пример запроса:** тело отсутствует (GET); авторизация — текущая сессия администратора (существующий механизм аутентификации «Арсенала», не меняется).
- **Пример ответа (успех, есть данные):**
  ```json
  { "count": 17 }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  { "count": null }
  ```
- **Ошибки:** см. «Каталог ошибок» ниже.
- **Состояния UI по ответу:** `value` — count > 0 или count ≥ 0 (не null, не 0) → показать число; `zero` — count = 0 → показать «0»; `empty` — count = null → «—» (не ошибка); `loading` — до первого ответа; `error_source` — сеть/5xx/timeout самого BE Арсенала → сообщение + retry на следующем цикле опроса.
- **Авторизация:** только роль «Администратор». Enforced на бэке (403 иначе) и на фронте (для «Оператора» элемент не рендерится и запрос не выполняется).
- **Происхождение:** 🟢 новое.
- **Трассировка:** FR-1, FR-2, FR-3.

### INT-2. Счёт активных сессий у сервиса аутентификации — 🟡
- **Граница/направление:** BE Арсенала → Сервис аутентификации.
- **Триггер:** обновление закэшированного значения на BE Арсенала (не чаще раза в 30 секунд, по TTL кэша).
- **Контракт (запрос):** 🟡 к валидации — метод/путь/параметры эндпоинта сервиса аутентификации аналитик не помнит; конкретный путь не проектируем (правило провенанса для существующих сервисов).
- **Контракт (ответ):** 🟡 к валидации — ожидается число активных сессий; точное имя поля, тип и семантика отсутствия данных не подтверждены.
- **Пример запроса/ответа:** не приводится — конкретные path/JSON для неподтверждённого существующего сервиса не проектируются даже как гипотеза (см. «Провенанс»). Будет дополнено после валидации контракта.
- **Ошибки:** любая ошибка/timeout при вызове INT-2 перехватывается BE Арсенала и транслируется в ответ INT-1 как `{ "count": null }` — это дизайн 🟢 стороны BE Арсенала и не зависит от точного контракта INT-2.
- **Состояния UI по ответу:** не применимо — прямого потребителя на фронте нет, см. состояния INT-1.
- **Авторизация:** механизм межсервисного вызова (сервисный аккаунт/токен/mTLS) — 🟡 к валидации, не подтверждён.
- **Происхождение:** 🟡 возможность подтверждена аналитиком (сервис аутентификации уже умеет считать активные сессии) / 🟡 контракт и авторизация — к валидации.
- **Трассировка:** обеспечивает данные для INT-1 → FR-1.

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200, `{"count": <int>}` | значение счётчика | успешный ответ, данные есть | `value`/`zero` |
| 200, `{"count": null}` | явный null | BE не смог получить данные от сервиса аутентификации вовремя (см. INT-2) | `empty` → «—» (НЕ ошибка, FR-3) |
| 401 | стандартная ошибка аутентификации «Арсенала» (не меняется) | нет валидной сессии администратора | редирект на логин (существующее поведение) |
| 403 | стандартная ошибка доступа | роль ≠ «Администратор» | индикатор не отображается; в норме недостижимо — фронт не делает запрос для «Оператора» |
| 5xx / timeout / сеть | — | сбой самого BE Арсенала или сети до него | `error_source`: сообщение об ошибке + retry на следующем цикле опроса |

## 3. Backend — ответственность
### 3.1. По сервисам
- **BE Арсенала:** реализует INT-1 (🟢) — эндпоинт, серверная проверка роли, кэш TTL 30с (🟢, конкретная реализация кэша — на усмотрение реализующей команды); вызывает INT-2 к сервису аутентификации (🟡 к валидации по контракту); перехватывает ошибки/таймауты INT-2 и отдаёт `count: null` по INT-1 (🟢).
- **Сервис аутентификации:** уже считает число активных сессий — 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции); подходящий эндпоинт для чтения этого счёта — 🟡 к валидации (возможно потребуется доработка на стороне владеющей команды).
### 3.2. Данные и хранение
Новых сущностей/таблиц нет (подтверждено аналитиком). Миграции не требуются. Кэш 30с на BE Арсенала — не персистентная сущность (in-memory/TTL-кэш в процессе), схемы БД не требует.
### 3.3. Авторизация/доступ на бэке
BE Арсенала проверяет роль вызывающего перед возвратом `count` — только «Администратор», иначе 403. Межсервисная авторизация BE Арсенала → сервис аутентификации — 🟡 к валидации.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Шапка админки «Арсенал»: новый элемент-индикатор числа активных пользователей. Вызывает INT-1.
### 4.2. Пользовательские сценарии
Администратор открывает любой экран → индикатор запрашивает INT-1 → показывает значение или «—» → далее обновляется автоматически раз в минуту без перезагрузки страницы (FR-2). При недоступности источника — «—», не ошибка и не устаревшее число (FR-3). Роль «Оператор» индикатор не видит вовсе — элемент не рендерится.
### 4.3. Состояния

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос после открытия экрана | спиннер |
| `value` | 2xx, `count` не null и не 0 | число активных пользователей |
| `zero` | 2xx, `count` = 0 (валидный ноль) | «0» (не «—») |
| `empty` | 2xx, `count` = null | «—» (источник данных недоступен — не ошибка, FR-3) |
| `error_source` | 5xx / timeout / сеть до самого BE Арсенала | сообщение об ошибке + retry на следующем цикле опроса |
| `error_forbidden` | 403 | индикатор не отображается (в норме недостижимо — фронт не запрашивает для «Оператора») |

### 4.3.1. Loading и таймауты
- **Cold-path timeout** (первый запрос после открытия экрана): 5 секунд — 🟢 предложение этого документа.
- **Warm-path timeout** (последующие опросы): 3 секунды — 🟢 предложение этого документа.
- **Polling:** интервал 60 секунд (задано аналитиком); джиттер — не требуется: нагрузка от одного индикатора в шапке минимальна, а кэш 30с на BE Арсенала уже сглаживает частые обращения к сервису аутентификации независимо от числа открытых админ-сессий.
- При таймауте / 5xx / сетевой ошибке — состояние `error_source`; повторная попытка — на следующем плановом цикле опроса (без немедленного retry, чтобы не создавать всплеск нагрузки).
### 4.4. Доступ по ролям в UI
«Администратор» — видит индикатор. «Оператор» — индикатор не отображается: элемент не рендерится (не просто скрыт стилями), запрос к INT-1 не выполняется.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
INT-1 — синхронный HTTP request/response, опрос с фронта раз в минуту. INT-2 — синхронный вызов за кэширующим слоем: BE Арсенала обращается к сервису аутентификации не чаще раза в 30 секунд (TTL кэша), независимо от числа одновременно открытых админ-сессий. Ожидаемая нагрузка — низкая (внутренний инструмент поддержки, немного администраторов одновременно).
### 5.2. Надёжность/деградация
Недоступность сервиса аутентификации (источника данных) → BE отдаёт `count: null` по INT-1 → фронт показывает «—», это штатное поведение, не ошибка (FR-3). Недоступность самого BE Арсенала → фронт показывает `error_source`, повторная попытка на следующем цикле опроса.
### 5.3. Безопасность/доступ (сводно)
| Роль | Доступ к INT-1 |
|------|----------------|
| Администратор | разрешено, видит значение |
| Оператор | 403 на бэке; элемент не рендерится на фронте |
| Не аутентифицирован | 401 |

## 6. Релиз и интеграция
### 6.1. Порядок выката
BE Арсенала выкатывается раньше FE Арсенала (FE зависит от нового контракта INT-1). Роль «Администратор» уже существует в ролевой модели (БТ §5.3) — до релиза нужно убедиться, что доступ к новому элементу шапки привязан именно к ней (не заведение новой роли).
### 6.2. Обратная совместимость
INT-1 — полностью новый эндпоинт, существующих потребителей нет → ничего не ломает. Влияние на сервис аутентификации зависит от того, есть ли у него уже подходящий эндпоинт (🟡 к валидации, см. «Открытые вопросы»); если потребуется новый/изменённый эндпоинт на его стороне — совместимость и сроки уточняются отдельно с владеющей командой.
### 6.3. Фиче-флаги
Флаги не заводятся — релизим атомарно (аналитик флаги не упоминал, риск невысокий: новый некритичный UI-элемент).
### 6.4. План отката
- **Откат только BE:** эндпоинт INT-1 пропадает → FE получает 404/сетевую ошибку → показывает `error_source` с retry; допустимо на короткое окно, при длительном откате синхронизировать откат FE.
- **Откат только FE:** FE возвращается к версии без индикатора → контракт INT-1 просто не используется, данные и пользователи не затронуты.
- **Откат DDL:** не применимо — новых сущностей/миграций нет (§3.2).
### 6.5. Преднастройка до релиза
- [x] Роли в security-сервисе — роль «Администратор» уже существует (БТ §5.3); нужно подключить к ней проверку доступа к новому элементу до релиза (подтверждено аналитиком).
- [ ] DDL-миграция в репо владеющего сервиса — не применимо: новых сущностей нет.
- [ ] Конфиги по окружениям (dev/staging/prod) — нужен адрес/параметры вызова сервиса аутентификации; точные значения — 🟡 к валидации (зависят от контракта INT-2).
- [ ] Сервисные аккаунты для межсервисных вызовов — 🟡 к валидации, механизм авторизации BE→auth не подтверждён.
- [x] Фиче-флаги заведены — не требуются, релиз атомарный.
- [ ] Алерты/мониторинг на ключевые ошибки — рекомендуется настроить алерт на долю 5xx/timeout по INT-1 и на частоту `count: null` (может сигналить о деградации сервиса аутентификации); не подтверждено, отмечено как рекомендация.
