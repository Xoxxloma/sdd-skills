## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack (FE + BE). В шапку веб-админки добавляется новый элемент — индикатор числа активных пользователей. Фронт периодически запрашивает у своего бэка, бэк берёт данные из сервиса аутентификации.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (админка) — фронт + бэк | новая фича: индикатор + API для фронта | Команда Арсенал-Core | 🟢 новое |
| Сервис аутентификации | источник счёта активных сессий | Команда Auth | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель FR-1, FR-2, FR-3: администраторы видят в шапке число активных пользователей и выбирают безопасное окно для регламентных работ.

## 2. Взаимодействия (ядро)

### INT-1. Фронт Арсенала запрашивает число активных пользователей — 🟢

- **Граница/направление:** FE Арсенала → BE Арсенала
- **Триггер:** Страница админки загрузилась или истёк интервал пуллинга (1 минута)
- **Контракт (запрос):** GET (без тела). Параметры/заголовки: стандартные; авторизация по сессии FE.
- **Контракт (ответ):** JSON с полем `count` (целое число ≥ 0, или `null`).
  - Поля ответа:
    - `count`: `integer | null` — число активных пользователей, или `null` если источник недоступен.
  - Семантика `null`: источник данных недоступен или ошибка на этапе синхронизации. UI показывает «—», не ошибку.
- **Пример запроса:**
  ```
  GET /api/v1/active-users-count
  Authorization: Bearer <token>
  ```
- **Пример ответа (успех):**
  ```json
  {
    "count": 42
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null
  }
  ```
- **Ошибки:** 
  - `200` + `{ "count": null }` — источник недоступен (см. состояния UI)
  - `401` — неавторизован (но т.к. это внутренняя админка, ожидается редко)
  - `403` — запрещено (роль ниже "Администратор")
  - `5xx` — внутренняя ошибка BE, UI показывает «—»
- **Состояния UI по ответу (если есть фронт):**
  - `loading` → спиннер/скелетон в позиции индикатора
  - `value` → число (если `count > 0` и `count !== null`)
  - `zero` → не применимо, ноль не ожидается в бизнес-логике
  - `empty` → если `count === null` или источник недоступен, показываем «—»
  - `error_forbidden` → если 403, показываем «—» (нет прав)
  - `error_source` → если 5xx, показываем «—» + retry
- **Авторизация:** Только роль "Администратор" видит индикатор. Проверка — на уровне FE (скрытие виджета) + на уровне BE (403 для других ролей).
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2, FR-3

## 3. Backend — ответственность

### 3.1. По сервисам

**Арсенал (BE):**
- Реализует INT-1 (GET /api/v1/active-users-count) для фронта Арсенала.
- Логика: при запросе от фронта проверяет ролевую доступ (если не Администратор → 403). Если прошла проверка, возвращает закэшированное значение из памяти BE или делает синхронный запрос к сервису аутентификации (INT-2) и кэширует результат на 30 сек.
- При недоступности auth-сервиса (таймаут, 5xx) возвращает INT-1 ответ с `count: null`.

**Сервис аутентификации:**
- Уже имеет возможность считать активные сессии (подтверждено аналитиком). Точная реализация, эндпоинт, схема — не входят в эту спеку; валидируются при интеграции.

### 3.2. Данные и хранение

Новых сущностей и таблиц не требуется. 🟢

BE Арсенала кэширует результат вызова INT-2 в памяти процесса (или в выделённом кэше типа Redis, если архитектура предполагает). Время жизни кэша: 30 сек. Инвалидация: по TTL.

### 3.3. Авторизация/доступ на бэке

- INT-1: проверка роли на уровне обработчика. Если роль не "Администратор" → 403.
- INT-2: BE Арсенала аутентифицируется перед сервисом аутентификации. Механизм (служебный аккаунт, токен, mTLS и т.п.) — уточнить при интеграции (зависит от стека auth-сервиса).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Шапка админки (header компонент). Добавляется новый виджет — небольшой индикатор, который показывает число активных пользователей. Позиция: справа от логотипа (или у правого края шапки, по дизайну). Вызывает INT-1 при загрузке страницы и периодически (интервал 1 минута).

### 4.2. Пользовательские сценарии

**Основной поток:**
- Администратор открывает любой экран админки.
- При загрузке шапки фронт делает запрос INT-1.
- Если ответ успешен (200, `count` — число), показывает это число в индикаторе.
- Каждые 60 секунд фронт повторяет INT-1 и обновляет число.
- Администратор видит актуальное число активных пользователей.

**Ветвления:**
- Если INT-1 вернул `count: null` → показываем «—» вместо числа.
- Если INT-1 вернул ошибку 5xx или таймаут → показываем «—» и предлагаем retry (кнопка или автоматический повтор через N сек).
- Если роль не "Администратор" (403) → индикатор скрыт (либо не отправляем запрос, либо скрываем элемент).

Связь с FR-1, FR-2, FR-3 — см. §7.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос или после инвалидации | спиннер/скелетон |
| `value` | 2xx, `count` > 0 и !== null | число (напр., «42») |
| `empty` | 2xx, `count` === null, или 5xx/таймаут | пусто — показываем «—» |
| `error_forbidden` | 403 (нет роли) | индикатор не отображается (скрыт) |

### 4.3.1. Loading и таймауты

- **Cold-path (первый запрос):** таймаут 5 сек. Если за 5 сек ответа нет, показываем состояние `empty` («—»).
- **Warm-path (пуллинг):** таймаут 3 сек. Если за 3 сек ответа нет, показываем «—» (но не прерываем пуллинг).
- **Polling:** интервал 60 сек (1 минута), jitter не требуется (обновление некритично).

### 4.4. Доступ по ролям в UI

- **Администратор:** видит индикатор; может его использовать (запрос периодически отправляется).
- **Оператор и другие роли:** индикатор не отображается. На уровне вёрстки можно скрыть элемент, либо не отправлять запрос (экономия трафика).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** FE → BE (INT-1) — синхронный запрос (простой HTTP GET).
  BE → auth-сервис (INT-2) — синхронный запрос.
- **Кэш:** BE Арсенала кэширует результат INT-2 на 30 сек. Первый запрос от FE может попасть на кэш или на свежий вызов INT-2 — в зависимости от времени.
- **Частота опроса:** FE опрашивает BE раз в 60 сек (1 минута).
- **Таймауты:** см. §4.3.1.
- **Ожидаемая нагрузка:** индикатор обновляется раз в минуту на окне одного администратора. Нагрузка незначительна (1 GET в минуту на пользователя). Пиковая нагрузка: если N администраторов, то N запросов в минуту к BE Арсенала.

### 5.2. Надёжность/деградация

- При недоступности auth-сервиса BE Арсенала возвращает `count: null`, UI показывает «—» (graceful degradation).
- Без кэша число запросов к auth-сервису могло бы быть выше; кэш на 30 сек защищает от перегрузки.
- Если BE Арсенала недоступен полностью, фронт получит 5xx и тоже покажет «—».

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто/что может | Проверка | Негативный случай |
|---------|---------------|----------|-------------------|
| FE → BE (INT-1) | Администратор | Проверка роли в обработчике INT-1 | Оператор получает 403 или видит скрытый виджет |
| BE → auth-сервис (INT-2) | BE Арсенала (служебный аккаунт) | Аутентификация (токен / сертификат / иное) | 401 к auth-сервису → BE возвращает `count: null` → UI показывает «—» |

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **Backend Арсенала:** развернуть первым. Включает реализацию INT-1 (API) и INT-2 (синхронный вызов auth-сервиса).
2. **Frontend Арсенала:** развернуть вторым. Включает виджет в шапку и логику пуллинга INT-1.

Причина: если FE видит новый API, но BE ещё не готов, FE получит 5xx. Обратный порядок безопаснее.

### 6.2. Обратная совместимость

FE добавляет новый элемент в шапку (не трогает существующую функциональность). BE добавляет новый эндпоинт (не меняет существующие). Обратная совместимость **не нарушается**.

Если FE старой версии (до этого релиза) попадёт на новый BE, GET /api/v1/active-users-count вернёт 404 — это штатно, старый FE его не вызывает.

### 6.3. Фиче-флаги

🟢 Релизим атомарно. Фиче-флаг не требуется: как только BE готов, FE может запуститься. Если нужна поэтапная активация, добавить флаг на уровне роли или конфига (за скоупом этой спеки).

### 6.4. План отката

- **Откат только BE:** FE на старой версии не знает про новый API (GET /active-users-count), не вызывает. Откат BE безопасен.
- **Откат только FE:** BE выкатан, API готов, но FE откачиваем. Старый FE не вызывает новый API — безопасно. Новые админы будут видеть старую шапку.
- **Откат DDL:** новых таблиц нет, откат пуст.
