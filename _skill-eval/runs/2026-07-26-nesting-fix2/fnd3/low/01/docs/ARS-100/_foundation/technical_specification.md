## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 **Backend-only.** Узел-фундамент #0 предоставляет единый контракт данных активности пользователей (текущее число активных + агрегированная активность за период), который потребляют frontend-дети эпика. Никакого frontend-изменения в самом фундаменте нет.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (BE) | собирает данные активности, отдаёт контракт INT-0 | Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел #0 обслуживает FR-1..FR-5 эпика ARS-100 в части данных активности: текущее число активных пользователей и агрегированная активность за период (час / день / неделя). Это общий источник данных для счётчика в шапке, графика в модалке и выгрузки сводки.

## 2. Взаимодействия (ядро)

### INT-0. Данные активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** BE Arsenal → Frontend потребители (дети эпика)

- **Триггер:** Frontend запрашивает данные активности при загрузке страницы, при переключении периода или при явном обновлении счётчика.

- **Контракт (запрос):** 
  - HTTP GET `/api/admin/activity` (концептуальный путь)
  - Query параметры:
    - `period` (обязательно): `hour` | `day` | `week`
    - Дополнительно: `startDate` (ISO8601, опционально) — если передаётся, переопределяет период

- **Контракт (ответ):**
  - `currentActive` (int ≥ 0): текущее число активных пользователей в момент запроса
  - `period` (object, опционально): описание запрошенного периода
    - `label` (string): `hour` | `day` | `week` — тот, что был передан в запросе
    - `start` (ISO8601): начало периода (UTC)
    - `end` (ISO8601): конец периода (UTC)
  - `aggregates` (array или null): 
    - Массив объектов `{timestamp: ISO8601, count: int ≥ 0}` — активность по интервалам (часовые для дня, дневные для недели, поминутные для часа)
    - `null`, если `hasData === false` (нет данных за период)
  - `hasData` (boolean): `true` если за период есть хотя бы одна запись; `false` если период без данных или запрос вне истории
  - `sourceUnavailable` (boolean): `true` если источник данных недоступен (5xx, таймаут) — в этом случае остальные поля могут быть пустыми или прошлыми значениями для fallback. **При недоступности источника НИКОГДА не отдавать устаревшие данные как актуальные — только с флагом.**

- **Пример запроса:**
  ```
  GET /api/admin/activity?period=day
  ```

- **Пример ответа (успех, есть данные за период):**
  ```json
  {
    "currentActive": 42,
    "period": {
      "label": "day",
      "start": "2026-07-25T00:00:00Z",
      "end": "2026-07-26T00:00:00Z"
    },
    "aggregates": [
      {"timestamp": "2026-07-25T00:00:00Z", "count": 15},
      {"timestamp": "2026-07-25T01:00:00Z", "count": 18},
      {"timestamp": "2026-07-25T02:00:00Z", "count": 12},
      {"timestamp": "2026-07-25T03:00:00Z", "count": 19}
    ],
    "hasData": true,
    "sourceUnavailable": false
  }
  ```

- **Пример ответа (успех, нет данных за период):**
  ```json
  {
    "currentActive": 42,
    "period": {
      "label": "week",
      "start": "2026-06-01T00:00:00Z",
      "end": "2026-06-08T00:00:00Z"
    },
    "aggregates": null,
    "hasData": false,
    "sourceUnavailable": false
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "currentActive": null,
    "period": {
      "label": "day",
      "start": "2026-07-25T00:00:00Z",
      "end": "2026-07-26T00:00:00Z"
    },
    "aggregates": null,
    "hasData": null,
    "sourceUnavailable": true
  }
  ```

- **Ошибки:**
  - **403 Forbidden:** роль пользователя не является Администратором. Тело: `{ "error": "forbidden", "message": "Этот контракт доступен только администраторам" }`. Frontend должен спрятать виджет активности.
  - **5xx или таймаут (>5s):** источник данных недоступен. Frontend получит `sourceUnavailable: true` в ответе или ошибку. Показать сообщение об ошибке, не выдавать устаревшие данные.
  - **400 Bad Request:** неверный параметр `period`. Тело: `{ "error": "invalid_period", "message": "Допустимые значения: hour, day, week" }`.

- **Состояния UI по ответу (для потребителей):**
  - `currentActive > 0` + `hasData=true` + `sourceUnavailable=false` → состояние `value`: показать актуальное число и график
  - `currentActive = 0` + `hasData=true` + `sourceUnavailable=false` → состояние `zero`: показать ноль, не прочерк «—»
  - `hasData=false` + `sourceUnavailable=false` → состояние `empty`: показать прочерк «—» / пустой график
  - `sourceUnavailable=true` → состояние `error_source`: показать сообщение об ошибке, предложить повторить
  - HTTP 403 → состояние `error_forbidden`: спрятать виджет, не показывать ошибку

- **Авторизация:** 
  🟡 **подтверждено аналитиком:** Контракт доступен только для роли «Администратор»; проверка выполняется на BE Arsenal перед возвратом данных. Если роль другая (например, Оператор) → HTTP 403.

- **Происхождение:** 🟢 новое (узел-фундамент #0, наследуется всеми детьми эпика)

- **Трассировка:** FR-1 (отображение в шапке), FR-2 (обновление счётчика), FR-3 (открытие модали), FR-4 (переключение периода), FR-5 (выгрузка) — все зависят от INT-0 как единого источника данных

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 | `{…, sourceUnavailable: true}` | Источник данных недоступен (внутренняя ошибка BE) | `error_source` — показать ошибку, предложить повторить |
| 200 | `{…, hasData: false}` | Запрошенный период без данных (историческая лакуна) | `empty` — показать прочерк «—» / пустой график |
| 400 | `{ "error": "invalid_period" }` | Передан неподдерживаемый период | `error_source` — показать ошибку валидации |
| 403 | `{ "error": "forbidden" }` | Роль не Администратор | `error_forbidden` — спрятать виджет |
| 5xx | HTTP ошибка | Сервис недоступен, таймаут | `error_source` — показать ошибку |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal (BE):** реализует INT-0 `/api/admin/activity`, собирает данные активности пользователей, кэширует на 30 секунд (время жизни кэша), отдаёт контракт с текущим числом и агрегатами за период. Проверяет роль пользователя перед возвратом данных.

### 3.2. Данные и хранение
🟡 **подтверждено аналитиком:** Агрегаты активности считаются на лету в момент запроса; новых таблиц не заводим. Данные о сессиях/активности пользователей берутся из существующего источника Arsenal (внутренняя логика сервиса). Индексы и оптимизация запросов к этому источнику — в зоне ответственности Arsenal, не описываются в этой спеке.

**Миграции:** не требуются.

### 3.3. Авторизация/доступ на бэке
🟡 **подтверждено аналитиком:** Проверка роли `Administrator` выполняется на уровне HTTP-обработчика `GET /api/admin/activity`. Если пользователь имеет другую роль или не аутентифицирован → HTTP 403 Forbidden. Проверка привязана к текущему пользователю (из сессии/токена).

## 4. Frontend — ответственность
*Не применимо: узел #0 — чистая реализация BE, фронтовых изменений нет. Frontend-потребители (дети эпика) будут потреблять INT-0 контракт в своих собственных спеках.*

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
🟡 **подтверждено аналитиком:**
- **Синхронность:** запрос/ответ синхронный (не event-driven, не async job).
- **Кэш:** 30 секунд на стороне BE Arsenal. Кэш валидирует по ключу `(userId, period)` или эквивалентному.
- **Таймаут:** максимум 5 секунд на ответ. Если запрос к источнику данных превышает таймаут → возвратить `{sourceUnavailable: true}`.
- **Нагрузка:** ожидаемая частота запросов ≤ 1 раз в 30 секунд на администратора (кэш на клиенте + обновление при необходимости).

### 5.2. Надёжность/деградация
🟡 **подтверждено аналитиком:** При недоступности источника данных (5xx, таймаут, сетевая ошибка) → возвратить HTTP 200 с флагом `{sourceUnavailable: true}` и **не выдавать устаревшие/кэшированные значения как актуальные**. Frontend увидит ошибку и предложит пользователю повторить.

### 5.3. Безопасность/доступ (сводно)
| Границу | Проверка | Кто | Действие |
|---------|----------|-----|---------|
| GET /api/admin/activity | Роль = Administrator | BE Arsenal | Возвратить данные |
| GET /api/admin/activity | Роль ≠ Administrator | BE Arsenal | HTTP 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟡 **подтверждено аналитиком:** Узел-фундамент #0 выкатывается **ПЕРВЫМ**, раньше всех frontend-потребителей (детей эпика). После выката #0 фронты детей получают стабильный контракт INT-0 и начинают собственный разработку/тестирование независимо.

### 6.2. Обратная совместимость
Новый контракт INT-0; обратной совместимости с кем-то нет (это фундамент).

### 6.3. Фиче-флаги
🟡 **подтверждено аналитиком:** Фиче-флагов нет. Релизим INT-0 атомарно (весь контракт разом).

### 6.4. План отката (обязательно, если задача деплоится — иначе «не применимо: причина»)
- **Откат BE (#0):** Если контракт INT-0 имеет проблему после выката → откатить BE Arsenal на старую версию без INT-0 (или заблокировать эндпоинт 503). Frontend-потребители, уже зависящие от INT-0, будут получать ошибки и должны быть готовы их обрабатывать (см. §5.2).
- **Откат только FE:** Не применимо (фундамент не имеет FE части).

### 6.5. Преднастройка до релиза (чек-лист)
- [x] Роли в security-сервисе: роль `Administrator` должна быть определена в системе (проверить, не требует разработки, только валидация)
- [x] DDL-миграция: не требуется (агрегаты считаются на лету)
- [x] Конфиги по окружениям: TTL кэша 30s может быть настроен в конфиге; таймаут 5s может быть настроен
- [x] Сервисные аккаунты: не требуются (это внутренний BE Arsenal)
- [x] Фиче-флаги: не требуются
- [x] Алерты/мониторинг: алерт на 5xx и таймауты (`status=error_source`); мониторинг времени ответа; мониторинг попыток доступа с недостаточной ролью (403)

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано администратор, когда страница админки загружается, тогда BE отдаёт INT-0 с `currentActive` и он отображается в шапке |
| FR-2 | INT-0 | Дано открытую админку, когда число активных меняется и кэш истёк, тогда следующий запрос INT-0 возвращает новое значение; счётчик обновляется в пределах 30s (кэш) + время сетевого запроса |
| FR-3 | INT-0 | Дано счётчик в шапке, когда администратор кликает, тогда открывается модалка с графиком; график построен из `aggregates` INT-0 за период `day` (по умолчанию) |
| FR-4 | INT-0 | Дано открытую модалку, когда администратор выбирает другой период (hour/week), тогда отправляется запрос INT-0 с новым `period`; график перестраивается из новых `aggregates` |
| FR-5 | INT-0 | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда выгрузка содержит данные из `aggregates` и `currentActive` INT-0 за тот период |

## 8. Допущения и открытые вопросы

**Все технические решения приняты, спецификация готова к разработке.**

### Подтверждено аналитиком (не по коду):
- Существующий источник активности (сервис/таблица) в Arsenal позволяет считать активные сессии и их исторические агрегаты
- Роль `Administrator` установлена и используется в системе для контроля доступа
- Кэш на BE Arsenal может быть реализован и управляется стандартным механизмом (Redis, memory-cache, или встроенный в приложение)
- Таймаут 5 секунд приемлем для исходного источника данных

### Рекомендации для детей эпика (потребителей INT-0):
- Каждый child-нод будет иметь собственную спеку (FR-1/FR-3 — счётчик в шапке; FR-2 — polling; FR-4 — модалка с графиком; FR-5 — выгрузка)
- Каждый потребитель должен обрабатывать все три состояния ответа INT-0: `{hasData: true}`, `{hasData: false}`, и `{sourceUnavailable: true}` отдельно (см. §4.3 шаблона и §2 каталог ошибок)
- Состояния UI для потребителей: `value` (есть данные), `zero` (ноль, не пусто), `empty` (пусто, нет данных), `error_source` (недоступен источник), `error_forbidden` (нет доступа)
