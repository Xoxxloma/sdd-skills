## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 **BE-only.** Узел-фундамент #0 — чистая реализация на бэке «Арсенала» API контракта данных активности (текущее число активных пользователей + агрегированные метрики за период). Фронты детей (счётчик в шапке, модаль графика, выгрузка) потребляют этот контракт неизменно.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | Источник и поставщик контракта активности; кэширование, ограничение по времени | Arsenal-Core | 🟢 новое взаимодействие |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент обслуживает FR-1..FR-5 эпика в части данных активности: система отображает текущий счётчик активных пользователей и агрегаты активности за выбранный период (час/день/неделя). Контракт остаётся единым для всех потребителей; дети наследуют его без переопределения.

## 2. Взаимодействия (ядро)

### INT-0. Контракт активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Backend Arsenal → Frontend (и потенциально другие потребители данных активности)

- **Триггер:** 
  - Инициализация панели активности; 
  - обновление счётчика в шапке;
  - загрузка графика при изменении периода;
  - подготовка выгрузки сводки.

- **Контракт (запрос):** 
  ```
  GET /api/arsenal/admin/activity
  Query-параметры:
  - period: enum [current | hour | day | week] — тип агрегации; обязателен
  - timezone: string (ISO 8601 IANA timezone) — опционален, по умолчанию UTC
  ```

- **Контракт (ответ):**
  - `status`: enum [`available` | `unavailable`] — доступность источника данных
  - `current_count`: integer ≥ 0 или null — число активных пользователей *сейчас*; null означает данные недоступны (если status = `unavailable`)
  - `period_data`: object или null — агрегаты активности за запрошенный период
    - `period`: enum [`hour` | `day` | `week`] — отражает параметр запроса
    - `points`: array of objects — временные точки (от старой к новой)
      - `timestamp`: string (ISO 8601) — начало интервала агрегации (дни — 00:00 UTC, часы — HH:00 UTC)
      - `count`: integer ≥ 0 — число активных пользователей в интервале
    - `has_data`: boolean — true если за период есть хотя бы одна точка с count > 0; false если count везде 0 или точек нет
  - `cached`: boolean — true если ответ из кэша (последний обновление &lt; 30s назад), false если свежее вычисление

- **Пример запроса (current):**
  ```
  GET /api/arsenal/admin/activity?period=current&timezone=Europe/Moscow
  ```

- **Пример ответа (успех, current):**
  ```json
  {
    "status": "available",
    "current_count": 42,
    "period_data": null,
    "cached": true
  }
  ```

- **Пример ответа (успех, week):**
  ```json
  {
    "status": "available",
    "current_count": 42,
    "period_data": {
      "period": "week",
      "points": [
        { "timestamp": "2026-07-20T00:00:00Z", "count": 38 },
        { "timestamp": "2026-07-21T00:00:00Z", "count": 45 },
        { "timestamp": "2026-07-22T00:00:00Z", "count": 52 },
        { "timestamp": "2026-07-23T00:00:00Z", "count": 49 },
        { "timestamp": "2026-07-24T00:00:00Z", "count": 61 },
        { "timestamp": "2026-07-25T00:00:00Z", "count": 67 },
        { "timestamp": "2026-07-26T00:00:00Z", "count": 42 }
      ],
      "has_data": true
    },
    "cached": false
  }
  ```

- **Пример ответа (успех, нет данных за период):**
  ```json
  {
    "status": "available",
    "current_count": 42,
    "period_data": {
      "period": "week",
      "points": [
        { "timestamp": "2026-07-20T00:00:00Z", "count": 0 },
        { "timestamp": "2026-07-21T00:00:00Z", "count": 0 },
        { "timestamp": "2026-07-22T00:00:00Z", "count": 0 },
        { "timestamp": "2026-07-23T00:00:00Z", "count": 0 },
        { "timestamp": "2026-07-24T00:00:00Z", "count": 0 },
        { "timestamp": "2026-07-25T00:00:00Z", "count": 0 },
        { "timestamp": "2026-07-26T00:00:00Z", "count": 0 }
      ],
      "has_data": false
    },
    "cached": true
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "status": "unavailable",
    "current_count": null,
    "period_data": null,
    "cached": false
  }
  ```

- **Ошибки:**
  | Код | Тело/сообщение | Когда | Состояние UI |
  |-----|----------------|-------|--------------|
  | 400 | `{"error": "invalid_period", "message": "Period must be one of: current, hour, day, week"}` | параметр period отсутствует или некорректен | `error_input` |
  | 400 | `{"error": "invalid_timezone", "message": "Timezone is not recognized"}` | параметр timezone некорректен | `error_input` |
  | 403 | `{"error": "forbidden", "message": "Only Administrator role can access activity data"}` | вызывающий — не администратор | `error_forbidden` |
  | 500 | `{"error": "internal_error", "message": "Activity data source unavailable"}` | источник активности (внутренний механизм) вернул ошибку | `error_source` (+ response.status="unavailable") |
  | 504 | `{"error": "timeout", "message": "Request to activity data source timed out (5s limit exceeded)"}` | timeout при обращении к источнику активности | `error_source` |

- **Состояния UI по ответу (если есть фронт):**
  - `loading` → при первом запросе или после инвалидации кэша — показать спиннер/скелетон
  - `value` → 2xx, status = `available`, current_count ≠ null и ≠ 0 — показать число
  - `zero` → 2xx, status = `available`, current_count = 0 (валидный ноль) — показать «0» (не «—»)
  - `empty` → 2xx, status = `available`, period_data.has_data = false — показать «—» / «нет данных за период»
  - `error_source` → 5xx, 504, или status = `unavailable` — показать сообщение об ошибке + кнопка retry
  - `error_forbidden` → 403 — показать «нет доступа»
  - `error_input` → 400 — показать «ошибка параметров» (должна быть исправлена на фронте, не retry)

- **Авторизация:** 
  - Контракт доступен только роли **Администратор**. 
  - 🟡 подтверждено аналитиком: проверка осуществляется на бэке Arsenal при получении запроса (HTTP-заголовок авторизации / сессия → роль → verfiy role = Administrator).
  - Негативный случай (403): роль ≠ Administrator → вернуть 403 Forbidden с `error: "forbidden"`.

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (счётчик текущего числа), FR-2 (обновление счётчика), FR-3 (открытие графика), FR-4 (смена периода графика), FR-5 (выгрузка сводки) — все данные из этого контракта.

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal (Backend):**
- Реализует GET `/api/arsenal/admin/activity` согласно контракту INT-0 (🟢).
- При вызове с `period=current` отдаёт только `current_count` и `cached`; `period_data` = null.
- При вызове с `period=[hour|day|week]` отдаёт `period_data` с точками в запрошенном периоде и текущий счётчик.
- Проверяет авторизацию: только роль Administrator (HTTP 403, если иная).
- **Вычисление агрегатов:** 🟡 подтверждено аналитиком — агрегаты активности за период считаются на лету (не из таблицы, а из дополнительного источника или расчёта в реальном времени); новая таблица не закладывается.
- **Кэширование:** кэш 30 секунд на стороне Arsenal backend для результатов вычислений (текущий счётчик и агрегаты); поле `cached: true` отражает попадание в кэш (последнее вычисление < 30s назад).
- **Таймаут:** любой вызов к источнику активности (БД, внутренний сервис, и т.п.) должен быть завершён за 5 секунд; иначе вернуть 504 с `error: "timeout"`.
- **Недоступность источника:** если при вычислении возникла ошибка (исключение, 5xx от зависимости, таймаут), вернуть HTTP 500 с `status: "unavailable"`, **НЕ отдавать устаревшее значение** из кэша. Фронт видит ошибку и может переделать запрос.

### 3.2. Данные и хранение
**Новых сущностей и таблиц нет** (🟡 подтверждено аналитиком). Существующее хранилище активности пользователей уже в наличии и используется для вычисления текущего счётчика и агрегатов. Концептуальные требования к хранилищу (если оно рождалось ранее в Arsenal):
- Событие входа/выхода пользователя или состояние «активность на дату/час»; ведение по эпохе UTC.
- Индексы под типовые запросы: по датаинтервалу для агрегации за день/неделю.
- Retention: бизнес-требование не задано → 🟡 к валидации (уточнить во время разработки, сколько истории удерживать; обычно 30–90 дней для операционных отчётов).

### 3.3. Авторизация/доступ на бэке
- Проверка роли Administrator при входе в `/api/arsenal/admin/activity`: HTTP 403 с `error: "forbidden"`, если нет прав.
- 🟡 подтверждено аналитиком: проверка осуществляется через механизм сессии/заголовков Arsenal; точная реализация (сессионный токен, заголовок Authorization, внутреннийервис аутентификации) — в коде бэка.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
**Шапка админки:**
- Счётчик текущего числа активных пользователей (запрос INT-0 с `period=current`, обновление по расписанию).

**Модальное окно графика активности:**
- График активности за выбранный период (запрос INT-0 с `period=[hour|day|week]`); переключение периода = новый запрос.

**Выгрузка сводки:**
- Подготовка файла с агрегатами активности за выбранный период (данные из `period_data.points` при наличии `has_data=true`).

### 4.2. Пользовательские сценарии
1. **Инициализация и обновление счётчика (FR-1, FR-2):**
   - При загрузке админки: GET с `period=current` → получить current_count → отобразить в шапке.
   - По расписанию (каждые 30 сек, в пределах минуты): повторить запрос → обновить счётчик (состояние `value` или `zero`).

2. **Открытие и смена периода графика (FR-3, FR-4):**
   - Клик на счётчик: открыть модаль, GET с `period=day` (по умолчанию) → получить `period_data` → отрисовать график.
   - Выбор периода (час/день/неделя): новый GET с соответствующим `period` → перестроить график.

3. **Выгрузка сводки (FR-5):**
   - Клик «выгрузить»: взять `period_data.points` из последнего ответа (или переделать запрос свежий) → сформировать CSV/JSON и скачать как файл.

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | Первый запрос или инвалидация кэша на фронте | Спиннер или скелетон счётчика / графика |
| `value` | 2xx, status = `available`, current_count ≠ null и ≠ 0 | Число активных (напр. «42») |
| `zero` | 2xx, status = `available`, current_count = 0 | Ноль («0», не прочерк) |
| `empty` | 2xx, status = `available`, period_data.has_data = false (график за период без активности) | «—» / «нет данных за период» |
| `error_source` | 5xx, 504, таймаут, или status = `unavailable` | «Данные недоступны. Повторить попытку?» + кнопка retry |
| `error_forbidden` | 403 (нет доступа) | «У вас нет доступа к данным активности» |
| `error_input` | 400 (ошибка параметров) | «Ошибка: неверные параметры запроса» (на фронте — баг, не retry) |

### 4.3.1. Loading и таймауты
- **Cold-path (первый запрос при загрузке модали):** таймаут 5s (синхронизирован с серверным таймаутом).
- **Warm-path (переключение периода, обновление в шапке):** таймаут 3s (допускается быстрое переключение).
- **Polling (обновление счётчика в шапке):** интервал ~30s (синхронизирован с кэшем сервера) + jitter ±5s для разноса нагрузки.
- **При таймауте / 5xx / недоступности:** перейти в состояние `error_source`, показать сообщение + кнопка retry.

### 4.4. Доступ по ролям в UI
- 🟡 подтверждено аналитиком: счётчик активности, модаль графика и выгрузка видны только пользователям с ролью **Administrator**.
- Фронт может полагаться на:
  - Наличие поля `Administrator` в сессии/контексте пользователя (получено при логине).
  - HTTP 403 при попытке запроса (вернёт сервер, фронт скроет элементы).
- Рекомендуется скрыть виджеты панели активности на фронте сразу при загрузке, если роль ≠ Administrator, и не делать запросов (избежать лишних 403).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** 🟡 подтверждено аналитиком — синхронный режим (запрос-ответ); нет асинхронных задач / очередей / вебсокетов.
- **Кэширование:** 🟡 подтверждено аналитиком — кэш 30 секунд на стороне Arsenal backend; результат (current_count, period_data) кэшируется целиком per (period, timezone)-пара.
- **Частота обновления счётчика на фронте:** ~30s polling + jitter; в пределах минуты (FQA "в пределах минуты") гарантируется обновление.
- **Таймауты:** 
  - Общий таймаут запроса (клиент → сервер): 5s.
  - Таймаут источника активности (сервер → источник, БД, и т.п.): 5s.
- **Ожидаемая нагрузка:** ~10–20 запросов/мин на период активности (5 пользователей в админке × 4-5 обновления в минуту); peak при открытии модали графика может быть +5 запросов/мин разом. Кэширование на 30s должно поглотить большинство дублей.

### 5.2. Надёжность/деградация
- **При недоступности источника активности** (БД упала, сервис ошибает, таймаут): 
  - 🟡 подтверждено аналитиком — не отдавать устаревшее значение из кэша; вернуть 500/504 с `status: "unavailable"`.
  - Фронт видит `error_source` и может переделать запрос позже.
  - Панель активности временно скрыта или показана с индикатором ошибки, пока не восстановится доступ.
- **Если данных за период нет:** отдать `has_data: false` и массив `points` (возможно с нулевыми значениями); фронт отобразит «—» / «нет данных». Это **не ошибка**, это валидное состояние.

### 5.3. Безопасность/доступ (сводно)
| Кто / Что | Может | Не может | Проверка |
|-----------|-------|----------|----------|
| Administrator | Запрос INT-0 с любым period и timezone | — | HTTP 200 |
| Non-Administrator / Unauthorized | — | Запрос INT-0 | HTTP 403 Forbidden |
| Любой | — | Параметры period не из {current,hour,day,week} | HTTP 400 Bad Request |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟡 подтверждено аналитиком:
1. **Фундамент #0 выкатывается ПЕРВЫМ** (разработка + тестирование контракта INT-0 на бэке Arsenal).
2. **После стабилизации #0 выкатываются потребители** (дочерние задачи: счётчик, модаль графика, выгрузка) — они наследуют контракт и не переопределяют его.
3. **Фиче-флаги:** не используются; выкат атомарный (если #0 готов, фронты могут включить виджеты на тот же день/спринт).

### 6.2. Обратная совместимость
- 🟡 подтверждено аналитиком: фундамент #0 новый, потребителей старых нет; обратная совместимость не требуется.
- Если позже добавится новый потребитель контракта: изменение INT-0 координируется через обновление спеки #0 и каскадное обновление всех детей (без молчаливого override).

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **фиче-флагов нет**; панель активности и потребители (счётчик, модаль, выгрузка) выкатываются вместе и видны сразу всем администраторам, как только деплой завершён.

### 6.4. План отката
- **Откат только BE** (откатить Arsenal backend на старую версию, FE ждёт нового ответа): FE получит 404 / 5xx (старая версия не имеет `/api/arsenal/admin/activity`) → перейти в состояние `error_source` → показать ошибку retry. **Не ломает FE**, FE ждёт восстановления.
- **Откат только FE** (откатить фронт на старую версию, BE отдаёт новое): FE старой версии не запрашивает `/api/arsenal/admin/activity` → никаких вызовов. **Не ломает BE**. Новые данные в BE просто не потребляются.
- **Откат DDL:** не применимо (новых таблиц нет); агрегаты считаются на лету.

### 6.5. Преднастройка до релиза (чек-лист)
- [ ] **Роли в security-сервисе:** убедиться, что роль Administrator существует и применена к нужным админам в prod.
- [ ] **DDL-миграция:** не требуется (новых таблиц нет; используется существующее хранилище активности).
- [ ] **Конфиги по окружениям:** параметры подключения к хранилищу активности (dev/staging/prod) — проверить в коде Arsenal.
- [ ] **Сервисные аккаунты:** не требуются (вызовы от реальных администраторов, авторизация через их сессию).
- [ ] **Фиче-флаги:** не требуются (выкат атомарный).
- [ ] **Алерты/мониторинг:** настроить мониторинг на ошибки INT-0 (5xx, 504, таймауты), так как это критичная зависимость для админки.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 (period=current) | Дано открыта админка, когда страница загрузилась, тогда в шапке видно число активных (запрос GET с period=current вернул current_count) |
| FR-2 | INT-0 (period=current, polling) | Дано открыта админка, когда число активных изменилось, тогда счётчик обновляется в пределах минуты (polling INT-0 с интервалом 30s +jitter выполняется) |
| FR-3 | INT-0 (period=day) | Дано счётчик в шапке, когда администратор кликает, тогда открывается модаль с графиком (INT-0 с period=day возвращает period_data с points за последние 24ч) |
| FR-4 | INT-0 (period=hour\|week) | Дано открыта модаль, когда администратор выбирает период, тогда график перестраивается (новый запрос INT-0 с выбранным period получает обновлённый period_data) |
| FR-5 | INT-0 (period_data.points) | Дано открыта модаль с выбранным периодом, когда администратор нажимает выгрузку, тогда получает файл (FE берёт period_data.points из последнего ответа INT-0 и сохраняет как CSV/JSON) |
