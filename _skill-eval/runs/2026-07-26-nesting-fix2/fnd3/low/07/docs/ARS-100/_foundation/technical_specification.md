## 1. Обзор изменения

### 1.1. Тип и стороны
**BE-only.** Узел-фундамент #0 — чистая реализация на бэке (сервис «Арсенал»). Контракт данных активности становится новым, спроектирован в этой спеке и потребляется несколькими детскими фронтами (FR-1..FR-5 эпика). Новых фронт-сторон в самом фундаменте нет.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (BE) | Собирает данные активности, отдаёт контракт | Team Арсенал-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Фундамент #0 обслуживает FR-1..FR-5 эпика в части исходных данных о текущей и исторической активности пользователей. Контракт даёт возможность трём дочерним фронтам (счётчик в шапке, модалка с графиком, выгрузка) показать администратору живые данные и сводки активности.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Дочерний фронт (в составе админки) → BE Арсенала

- **Триггер:** 
  - Инициализация счётчика в шапке (cold path);
  - Периодическое обновление счётчика (polling, ~раз в минуту по требованию);
  - Запрос данных на период (час/день/неделя) при открытии модалки или смене периода;
  - Запрос сводки для выгрузки.

- **Контракт (запрос):**
  ```
  POST /api/v1/admin/activity
  ```
  | Поле | Тип | Обязательность | Описание |
  |------|-----|---|---|
  | `period_type` | enum: `current` \| `hour` \| `day` \| `week` | обязательно | `current` = текущее число активных; остальные = агрегаты за период |
  | `reference_date` | ISO 8601 datetime или null | опционально | Дата/время, от которого считать период. При `period_type: current` игнорируется. Если не передан — берётся текущее время сервера. |

- **Контракт (ответ):**
  | Поле | Тип | Семантика | Enum / Значения |
  |------|-----|-----------|---|
  | `status` | enum string | Статус доступности данных | `available` = данные получены; `unavailable` = источник недоступен; `no_data` = данных за период нет |
  | `current_active_users` | int \| null | Текущее число активных пользователей | `null` если `status != "available"` |
  | `data_points` | array of objects \| null | Время­ные точки для графика (по периодам: часы/дни) | пустой массив если данных нет; `null` если `status != "available"` |
  | `data_points[].timestamp` | ISO 8601 datetime | Начало интервала (часа, дня, недели) | — |
  | `data_points[].active_count` | int | Среднее/максимальное число активных за интервал (по дизайну BE) | >= 0 |
  | `period_type` | enum string | Какой период отдан | `current` \| `hour` \| `day` \| `week` |
  | `reference_date` | ISO 8601 datetime | На какую дату/время рассчитано (когда был взят слепок) | — |
  | `cache_ttl_seconds` | int | Рекомендуемый TTL кэша на фронте (опционально, для оптимизации) | обычно 30 |

- **Пример запроса (получить текущее число активных):**
  ```json
  {
    "period_type": "current"
  }
  ```

- **Пример запроса (получить данные за день):**
  ```json
  {
    "period_type": "day",
    "reference_date": "2026-07-26T15:30:00Z"
  }
  ```

- **Пример ответа (успех — текущее число):**
  ```json
  {
    "status": "available",
    "current_active_users": 127,
    "data_points": null,
    "period_type": "current",
    "reference_date": "2026-07-26T18:42:00Z",
    "cache_ttl_seconds": 30
  }
  ```

- **Пример ответа (успех — график за день):**
  ```json
  {
    "status": "available",
    "current_active_users": null,
    "data_points": [
      {
        "timestamp": "2026-07-26T00:00:00Z",
        "active_count": 45
      },
      {
        "timestamp": "2026-07-26T01:00:00Z",
        "active_count": 38
      },
      {
        "timestamp": "2026-07-26T02:00:00Z",
        "active_count": 22
      }
    ],
    "period_type": "day",
    "reference_date": "2026-07-26T00:00:00Z",
    "cache_ttl_seconds": 30
  }
  ```

- **Пример ответа (ошибка — источник недоступен):**
  ```json
  {
    "status": "unavailable",
    "current_active_users": null,
    "data_points": null,
    "period_type": "current",
    "reference_date": "2026-07-26T18:42:00Z",
    "cache_ttl_seconds": null
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "status": "no_data",
    "current_active_users": null,
    "data_points": [],
    "period_type": "week",
    "reference_date": "2026-07-19T00:00:00Z",
    "cache_ttl_seconds": 30
  }
  ```

- **Ошибки:**
  | Код HTTP | Тело/сообщение | Когда | Состояние UI |
  |----------|---|---|---|
  | 400 | `{ "error": "invalid_period_type", "message": "period_type must be one of: current, hour, day, week" }` | Передан неподдерживаемый `period_type` | error_validation |
  | 400 | `{ "error": "invalid_date_format", "message": "reference_date must be ISO 8601" }` | `reference_date` не в формате ISO 8601 | error_validation |
  | 403 | `{ "error": "forbidden", "message": "only Administrator role can access activity data" }` | Пользователь не имеет роли Администратор | error_forbidden |
  | 408 | `{ "error": "timeout", "message": "request timed out after 5 seconds" }` | Источник данных или вычисление не ответило в пределах 5 секунд | в ответе: `status: "unavailable"` (синхронно, таймаут обрабатывается на бэке как `unavailable`) |
  | 500 | `{ "error": "internal_error", "message": "failed to fetch activity data" }` | Ошибка на бэке при получении/обработке данных | error_source |

- **Состояния UI по ответу:**
  - **`status: "available", current_active_users: <число>`** → `value` (показать число);
  - **`status: "available", current_active_users: 0`** → `zero` (показать "0", не "—");
  - **`status: "available", current_active_users: null, data_points: [...]`** → `value` (график построен);
  - **`status: "no_data"` или `current_active_users: null` с пустым `data_points`** → `empty` (показать "—" / "нет данных");
  - **`status: "unavailable"`** → `error_source` (показать сообщение об ошибке, предложить retry);
  - **403** → `error_forbidden` (показать «нет доступа»);
  - **во время запроса** → `loading` (спиннер/скелетон).

- **Авторизация:**
  - **Кто вправе:** только пользователи с ролью **Администратор**;
  - **Где enforced:** на бэке Арсенала перед отдачей данных (проверка роли в security-контексте);
  - **Негативный случай:** запрос от пользователя без роли Администратор → 403 Forbidden (см. ошибки выше).

- **Происхождение:** 🟢 новое (узел-фундамент #0, спроектировано для общего потребления детьми)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (эпик)

## 3. Backend — ответственность

### 3.1. По сервисам
**Сервис Арсенал (BE)** реализует INT-0:
- Принимает запросы к `POST /api/v1/admin/activity` с параметрами периода;
- **Собирает данные активности сам** (🟡 подтверждено аналитиком: у бэка есть источник активности, чужих сервисов не привлекаем);
- Вычисляет текущее число активных пользователей и агрегаты (среднее/максимум за час/день/неделю) на лету;
- Проверяет авторизацию (роль Администратор) перед отдачей;
- Кэширует результат на 30 секунд (🟡 подтверждено аналитиком) на своей стороне;
- При недоступности источника возвращает `status: "unavailable"` вместо стального значения (🟡 подтверждено аналитиком);
- Обрабатывает таймауты (5 сек) на своей стороне, отдаёт `unavailable` если не укладывается.

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: **новых таблиц не заводим.** Агрегаты активности вычисляются на лету из существующих данных активности в Арсеналу. Индексы и запросы по подсчёту активности — всё на стороне Арсенала, в рамках существующей схемы (не входит в эту спеку).

### 3.3. Авторизация/доступ на бэке
- Проверка роли **Администратор** перед отдачей INT-0 (до вычисления);
- Негативный случай: 403 Forbidden (см. каталог ошибок в §2);
- 🟡 подтверждено аналитиком: проверка ролей делается в security-сервисе Арсенала (механика не входит в эту спеку).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Спецификация фундамента не описывает фронт-элементы — это в ответственности дочерних узлов. Фунди даёт только контракт данных (INT-0), который потребляют:
- **Счётчик в шапке** (дочерний узел, FR-1, FR-2);
- **Модалка с графиком** (дочерний узел, FR-3, FR-4);
- **Выгрузка сводки** (дочерний узел, FR-5).

Каждый потребитель реализует собственный UI поверх INT-0, обрабатывая состояния и ошибки по определению в §2.

### 4.2. Пользовательские сценарии
Не применимо: узел-фундамент #0 не имеет собственных фронт-сценариев (реализует только контракт данных).

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---|---|---|
| `loading` | первый запрос или инвалидация | спиннер / скелетон |
| `value` | 2xx, `status: "available"` и данные не null | значение (число или график) |
| `zero` | 2xx, `status: "available"`, `current_active_users: 0` | "0" (не "—") |
| `empty` | 2xx, `status: "no_data"` или данные null/пусто | "—" или "нет данных" |
| `error_source` | 5xx, таймаут, сеть, `status: "unavailable"` | сообщение об ошибке + retry |
| `error_forbidden` | 403 | "нет доступа" |

### 4.3.1. Loading и таймауты

- **Cold path (первый запрос):** подождать ответ с таймаутом на фронте >= 6 сек (BE отвечает в пределах 5 сек, фронт даёт запас);
- **Warm path (polling):** таймаут >= 6 сек (аналогично cold, можно общий);
- **Polling интервал:** оставить дочерним узлам (в их спеках, зависит от FR-2 требований: «в пределах минуты»); фундамент не диктует частоту;
- **При таймауте / 5xx / сетевой ошибке:** перейти в `error_source`, показать "Ошибка загрузки, попробуйте позже" + кнопка retry (реализация деталей в дочерних спеках).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- 🟡 подтверждено аналитиком: **синхронно** (не async);
- 🟡 подтверждено аналитиком: **кэш 30 секунд на стороне BE Арсенала** (не на фронте);
  - Запросы одного периода в пределах 30 сек возвращают кэшированный результат;
  - Кэш инвалидируется через 30 сек или при обновлении активности (если BE отслеживает это);
- 🟡 подтверждено аналитиком: **таймаут 5 сек на бэке** — если источник активности или вычисление не ответило, BE возвращает `status: "unavailable"` и прерывает запрос;
- **Ожидаемая нагрузка (ориентировочно, не входит в спеку, но контекст):** несколько админов, polling раз в минуту → несколько QPS на `/api/v1/admin/activity`. Точные метрики и план масштабирования — в режиме A при уточнении производительности.

### 5.2. Надёжность/деградация

- 🟡 подтверждено аналитиком: **при недоступности источника активности** отдаём признак `status: "unavailable"` (не устаревшее значение);
- 🟡 подтверждено аналитиком: **отдельно различаем "данных за период нет"** → `status: "no_data"` (когда за исторический период нет записей, но источник доступен);
- Пользователь видит:
  - Текущее число: показать "—" (если unavailable) или "0" (если данных за период нет);
  - График: пусто (empty) при no_data, ошибка при unavailable.

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто | Действие | Проверка | Результат при отказе |
|---|---|---|---|---|
| INT-0 | Только Администратор | Запрос данных активности | Роль Администратор на бэке Арсенала | 403 Forbidden |
| INT-0 | Другие роли (Оператор и т.п.) | Запрос данных активности | Роль не Администратор | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 подтверждено аналитиком: **фундамент выкатывается раньше потребителей.**
1. **Этап 1:** Выкат фундамента #0 — BE Арсенала с эндпоинтом `POST /api/v1/admin/activity`, кэшем, авторизацией, обработкой ошибок.
2. **Этап 2:** Выкат дочерних узлов (счётчик, модалка, выгрузка) — их фронты потребляют INT-0.

### 6.2. Обратная совместимость

- Новый эндпоинт не ломает существующее (новая фича);
- Дочерние узлы зависят от INT-0 → выкат фундамента перед ними гарантирует, что контракт уже доступен.

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком: **фиче-флагов нет** — фундамент и дочерние узлы релизят атомарно (в рамках этапов выката, 6.1).

### 6.4. План отката

- **Откат BE (фундамента):** Дочерние фронты получают 5xx / таймауты → переходят в `error_source`, показывают "Ошибка загрузки", retry доступен. UI остаётся видима (счётчик скрыт, модалка недоступна). Атомарный откат или откат BE + одновременный откат FE зависит от SLA эпика (не входит в спеку #0).
- **Откат FE (дочерних узлов):** BE отдаёт 2xx по INT-0, старый FE игнорирует ответ / не отправляет запрос → INT-0 не вызывается, счётчик не обновляется. Это нормально (откат не требует синхронного отката BE).
- **Откат DDL:** не применимо (новых таблиц не заводим, схема не меняется).

### 6.5. Преднастройка до релиза

- [x] **Роли в security-сервисе:** роль **Администратор** должна существовать и быть применима в security-контексте Арсенала (убедиться, что может быть проверена в 3.3);
- [x] **DDL-миграция:** не требуется (агрегаты на лету из существующих данных);
- [x] **Конфиги по окружениям:** таймаут 5 сек, TTL кэша 30 сек — внести в конфиги BE (dev / staging / prod) перед релизом;
- [ ] **Сервисные аккаунты:** не требуется (BE Арсенала вызывает сам себя, не межсервисный вызов);
- [x] **Фиче-флаги:** не требуются (релизим атомарно);
- [x] **Алерты/мониторинг:** мониторить 5xx на `/api/v1/admin/activity`, таймауты (если их можно отследить), rate limit (если есть в BE) — добавить алерт для операционной команды.

| FR-5 | INT-0 (период: `hour` / `day` / `week`) | Дано модалка открыта и администратор нажимает выгрузку, когда фронт получает данные за период (кэш 30 сек), тогда фронт формирует файл со сводкой (формат и детали в дочерней спеке выгрузки) |

## Итого

**Узел-фундамент #0 спроектирован:** один новый эндпоинт INT-0 `POST /api/v1/admin/activity`, который отдаёт текущее число активных пользователей и исторические агрегаты за период (час/день/неделя) в единой схеме с явной семантикой ошибок (`unavailable` / `no_data`) и состояниями UI. Контракт полностью конкретен, с JSON-примерами, enum'ами, таймаутом и авторизацией. Фундамент готов к потреблению тремя дочерними узлами (счётчик, модалка, выгрузка) без синхронизации логики.
