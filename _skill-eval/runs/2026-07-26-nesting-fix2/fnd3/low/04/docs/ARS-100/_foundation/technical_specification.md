## 2. Взаимодействия (ядро)

### INT-0. Получить данные активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** BE Arsenal → Фронтовые узлы-потребители (дети)
- **Триггер:** Инициализация админки, периодический polling счётчика в шапке, отрытие модального окна с графиком, переключение периода в модальном окне.
- **Контракт (запрос):** 
  - **Метод:** GET (концептуально; стек реализации уточняется на стороне Arsenal)
  - **Параметры:**
    - `period_hours`: целое число (1 | 24 | 168) — выборка активности за последние N часов. Обязателен.
    - `include_current`: логический флаг (по умолчанию `true`) — включать ли текущее число активных в ответ. Опционален.

- **Контракт (ответ):**
  - `current`: объект или `null` (если `include_current` → `false`)
    - `active_count`: целое число (≥ 0) | `null` — число активных пользователей на момент запроса. `null` → источник недоступен, см. `unavailable_source`.
    - `unavailable_source`: логический флаг — `true`, если источник данных недоступен; `false`, если данные актуальны. Если `true`, то `active_count` → `null`, поле «текущее значение недоступно» видит потребитель.
    - `measure_time_utc`: строка (ISO 8601) | `null` — момент измерения активности (UTC). При недоступности источника → `null`.
  - `period`: объект
    - `from_utc`: строка (ISO 8601) — начало периода (UTC).
    - `to_utc`: строка (ISO 8601) — конец периода (UTC).
    - `aggregates`: массив объектов (минимум 1 элемент) | `null`
      - `timestamp_utc`: строка (ISO 8601) — временная метка данного значения (UTC).
      - `count`: целое число (≥ 0) — число активных пользователей в момент `timestamp_utc`.
    - `no_data_for_period`: логический флаг — `true`, если за выбранный период нет данных активности (ни одного хотя бы нулевого значения, например при новых инсталляциях или чистых периодах). `false` → данные есть (включая `count` = 0). **Важно:** «нет данных» ≠ «недоступность источника». Если `no_data_for_period` → `true`, то `aggregates` → `null`.
    - `unavailable_source`: логический флаг — `true`, если источник данных для этого периода был недоступен на момент запроса; `false`, если данные полны и актуальны. Если `true`, то `aggregates` → `null`.

- **Пример запроса:**
  ```
  GET /arsenal/api/v1/activity/aggregated?period_hours=24&include_current=true
  ```

- **Пример ответа (успех, оба блока с данными):**
  ```json
  {
    "current": {
      "active_count": 42,
      "unavailable_source": false,
      "measure_time_utc": "2026-07-26T15:30:45Z"
    },
    "period": {
      "from_utc": "2026-07-25T15:30:45Z",
      "to_utc": "2026-07-26T15:30:45Z",
      "aggregates": [
        { "timestamp_utc": "2026-07-25T15:30:00Z", "count": 38 },
        { "timestamp_utc": "2026-07-25T16:30:00Z", "count": 41 },
        { "timestamp_utc": "2026-07-25T17:30:00Z", "count": 45 },
        { "timestamp_utc": "2026-07-25T18:30:00Z", "count": 43 },
        { "timestamp_utc": "2026-07-26T15:30:00Z", "count": 42 }
      ],
      "no_data_for_period": false,
      "unavailable_source": false
    }
  }
  ```

- **Пример ответа (недоступность источника):**
  ```json
  {
    "current": {
      "active_count": null,
      "unavailable_source": true,
      "measure_time_utc": null
    },
    "period": {
      "from_utc": "2026-07-25T15:30:45Z",
      "to_utc": "2026-07-26T15:30:45Z",
      "aggregates": null,
      "no_data_for_period": false,
      "unavailable_source": true
    }
  }
  ```

- **Пример ответа (нет данных за период, но текущий счёт есть):**
  ```json
  {
    "current": {
      "active_count": 42,
      "unavailable_source": false,
      "measure_time_utc": "2026-07-26T15:30:45Z"
    },
    "period": {
      "from_utc": "2026-07-26T00:00:00Z",
      "to_utc": "2026-07-26T15:30:45Z",
      "aggregates": null,
      "no_data_for_period": true,
      "unavailable_source": false
    }
  }
  ```

- **Ошибки:**
  - **400 Bad Request** — неверные параметры запроса (e.g., `period_hours` не целое число или не входит в `{1, 24, 168}`).
  - **401 Unauthorized** — отсутствует аутентификация или токен невалидный.
  - **403 Forbidden** — пользователь аутентифицирован, но роль не включена в список разрешённых (см. Авторизация). Тело: `{ "error": "access_denied", "message": "роль вашего пользователя не имеет доступа к данным активности" }`.
  - **500 Internal Server Error** — внутренняя ошибка бэка (не из-за недоступности источника; соответствует `unavailable_source` в теле и обрабатывается явно). Тело: `{ "error": "internal_error", "message": "not available at the moment" }`.

- **Состояния UI по ответу (маппинг для потребителей):**
  - `current.active_count` — число (≥ 0) → состояние `value` (показать число в счётчике).
  - `current.active_count` = 0, `unavailable_source` = `false` → состояние `zero` (показать «0» в счётчике).
  - `current.unavailable_source` = `true` → состояние `error_source` (показать «—» / пусто с иконкой ошибки в счётчике).
  - `period.aggregates` — массив → состояние `value` (построить график).
  - `period.no_data_for_period` = `true` → состояние `empty` (показать «Нет данных за период»).
  - `period.unavailable_source` = `true` → состояние `error_source` (показать сообщение об ошибке, предложить повтор).
  - 403 → состояние `error_forbidden` (показать «нет доступа»).

- **Авторизация:**
  - **Кто вправе:** Только пользователи с ролью `Администратор`.
  - **Где проверяется:** На стороне бэка Arsenal при обработке запроса (до выборки данных).
  - **Негативный случай:** Пользователь с ролью `Оператор` получает 403 Forbidden с сообщением об отсутствии доступа.
  - **Примечание:** 🟡 подтверждено аналитиком — Arsenal backend проверяет ролевую модель в существующей системе авторизации.

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (отображение числа активных), FR-2 (обновление без перезагрузки), FR-3 (график активности), FR-4 (переключение периода), FR-5 (данные для выгрузки сводки)

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal backend:**
- Реализует эндпоинт INT-0 (GET /arsenal/api/v1/activity/aggregated).
- Выполняет ролевую проверку доступа (только `Администратор`).
- Собирает и вычисляет данные активности пользователей (текущее число активных сессий, агрегаты за период).
- Возвращает структуру ответа в точном соответствии с контрактом (включая различие `unavailable_source` vs `no_data_for_period`).
- Обслуживает кэширование ответа на стороне бэка (см. Нефункциональные требования).

### 3.2. Данные и хранение
**Новых таблиц не заводим.** 🟡 подтверждено аналитиком — агрегаты активности вычисляются на лету из существующих источников (журналы сессий, событиявхода/выхода и т.п.). Точная схема и индексы — по существующей конфигурации Arsenal, уточнить при интеграции.

**Концептуально:**
- Источник данных: журнал/таблица активных сессий пользователей в Arsenal (существующая).
- Текущее значение: COUNT активных сессий на момент запроса.
- Агрегаты за период: временной ряд COUNT(active_sessions) с дискретизацией (часовой/дневной интервал, уточнить при реализации).
- Сохранение истории: не требуется (агрегаты вычисляются по LIVE-таблице, история не заводится).

### 3.3. Авторизация/доступ на бэке
- **Проверка ролей:** Перехватить запрос на уровне роутера/контроллера, прежде чем доступить к данным. Валидировать токен аутентификации и ролевой список.
- **Список разрешённых ролей:** `[Администратор]` (см. Бизнес-требования, §5.3).
- **Отклонение:** 403 Forbidden, если роль не в списке.
- **Существующая система:** 🟡 подтверждено аналитиком — Arsenal имеет встроенную систему авторизации (security-компонент), используем её.

## 4. Frontend — ответственность

Потребление контракта INT-0 возлагается на детские узлы (фронтовые компоненты). Каждый ребёнок реализует свой фрагмент UI (счётчик, модаль, выгрузку) и ответственен за:
- Формирование запроса с корректными параметрами (`period_hours` ∈ {1, 24, 168}, `include_current` по типу компонента).
- Обработку ответа и маппинг на состояния UI (см. маппинг в INT-0).
- Управление таймаутом и retrying (см. §5.1).
- Представление ошибок пользователю согласно каталогу ошибок.

На этом уровне фундамента (узел #0) фронтовых компонентов нет — разработка UI закреплена за детьми.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** Запрос синхронный (RESTful GET), ответ возвращается без задержки очереди.
- **Кэширование:** На стороне бэка Arsenal — кэш памяти (e.g., Redis / in-process cache) со TTL 30 секунд. Каждый новый запрос проверяет кэш; попадание → возвращает кэшированное значение; промах → вычисляет заново и обновляет кэш. 🟡 подтверждено аналитиком — механизм кэша оставляем на усмотрение Arsenal (реализация уточняется).
- **Таймаут:** Таймаут обработки запроса на бэке — **5 секунд**. Если за 5с данные не получены (блокирующий вызов, вычисление затянулось), бэк возвращает 500 или код таймаута, потребитель обрабатывает как `unavailable_source`.
- **Частота опроса (polling):** На стороне потребителей (детские узлы). Минимальный рекомендуемый интервал для счётчика в шапке — 10 секунд (с jitter ±20% для размазывания нагрузки). Для модального окна с графиком — по усмотрению (минимум 30 секунд при открытом окне).
- **Ожидаемая нагрузка:** До 100 админов, в пиках — до 5-10 одновременных запросов. Кэш на 30с должен уменьшить нагрузку на источник в 3+ раза.

### 5.2. Надёжность/деградация
- **При недоступности источника:** Возвращаем 2xx с `unavailable_source: true` и `active_count: null` (в секции `current`) или `aggregates: null` (в секции `period`), но НЕ устаревшие / cached данные из предыдущего запроса. Потребитель видит явный признак недоступности и может выбрать действие (показать placeholder, предложить retry).
- **Истечение таймаута (5s):** Если вычисление затянулось → возвращаем 500 Internal Server Error. Потребитель обрабатывает как ошибку и показывает «попробуйте позже».
- **Различие "нет данных" vs "недоступность":** Критично для потребителей. Если за период нет историй (новая инсталляция), `no_data_for_period: true`, но `unavailable_source: false`. Потребитель показывает «Нет данных за этот период», а не ошибку.

### 5.3. Безопасность/доступ (сводно)
| Граница | Действие | Разрешённая роль | Запрет | Результат |
|---------|----------|------------------|--------|-----------|
| GET /arsenal/api/v1/activity/aggregated | Читать текущую и историческую активность | Администратор | Оператор, гость | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката
1. **Этап 1 (фундамент #0):** Развернуть на бэке Arsenal новый эндпоинт INT-0 с контрактом ответа, кэшем 30s, ролевой проверкой. Фундамент готов и стабилен на production.
2. **Этап 2 (дети):** После стабилизации фундамента запустить разработку и откат детских узлов (фронтовые компоненты), которые потребляют INT-0.

**Причина:** Дети зависят от контракта фундамента; если фундамент нестабилен, дети не смогут интегрироваться.

### 6.2. Обратная совместимость
- **Фундамент (BE) → Дети (FE):** Контракт INT-0 фиксирован после выката фундамента. Если позже потребуется расширение (новые поля, новые коды ошибок), это будет обратно-совместимо: новые поля получают значения по умолчанию, старые потребители игнорируют неизвестные поля (JSON-契約).
- **Расширение контракта:** Добавление новых полей в `current` или `period` → не ломает старых потребителей. Удаление полей / изменение типов → новая версия эндпоинта (e.g., `/v2/`).

### 6.3. Фиче-флаги
Нет фиче-флагов. Фундамент выкатывается атомарно: либо работает вся цепь (BE + авторизация), либо откатывается вся.

### 6.4. План отката (обязательно)
- **Откат BE (фундамент):** Останавливаем эндпоинт INT-0 на бэке — дети (фронты) получат 404 или 503. Фронты должны обрабатывать это как ошибку `unavailable_source`, показывать «—» / placeholder и не ломаться.
- **Откат FE (дети):** Это ответственность каждого ребёнка. На уровне фундамента — нет фронтовых компонентов.
- **DDL откат:** Не применимо (новых таблиц нет).

### 6.5. Преднастройка до релиза
- [ ] Роли в security-сервисе: убедиться, что роль `Администратор` определена и используется в других местах Arsenal.
- [ ] Кэш-инфраструктура (Redis или in-process): подготовлена и сконфигурирована на dev/staging/prod с TTL 30s.
- [ ] Таймауты сетевых вызовов (если фундамент обращается к внешним источникам): настроены на 5s.
- [ ] Конфиги по окружениям: пути эндпоинтов, TTL кэша, адреса источников данных — задать для dev/staging/prod.
- [ ] Фиче-флаги: не требуются.
- [ ] Алерты/мониторинг: 
  - 5xx ошибки на эндпоинте INT-0.
  - Таймауты вычисления агрегатов.
  - Недоступность источника (при частых `unavailable_source: true`).

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано открытую админку, когда страница загрузилась и вызвана INT-0 с `include_current=true`, тогда в ответе `current.active_count` содержит число активных пользователей |
| FR-2 | INT-0 | Дано открытую админку, когда число активных пользователей изменилось и фронт повторно вызывает INT-0 в пределах минуты, тогда `current.active_count` отражает изменение (обновление каждые 10-30 секунд за счёт polling) |
| FR-3 | INT-0 | Дано счётчик в шапке, когда администратор кликает и фронт открывает модальное окно, тогда вызывается INT-0 с параметром `period_hours=24` (или другой период по умолчанию), возвращается массив `aggregates` с точками графика |
| FR-4 | INT-0 | Дано открытую модалку, когда администратор переключает период (1h / 1d / 1w), тогда фронт вызывает INT-0 с новым `period_hours`, получает обновленный `aggregates` и график перестраивается |
| FR-5 | INT-0 | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт использует данные из `period.aggregates` последнего вызова INT-0 для формирования сводки в файл (содержимое файла — на стороне ребёнка) |
