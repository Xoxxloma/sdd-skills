## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 BE-only. Arsenal backend предоставляет унифицированный контракт для отдачи данных активности пользователей (текущее число активных + агрегаты за период). Потребители — фронты дочерних узлов (FR-1..FR-5 эпика ARS-100).

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (BE) | новый контракт отдачи активности | Team Arsenal | 🟢 |
| Children FE (ARS-101, ARS-102, ARS-103) | потребители контракта | Team Frontend | 🟢 |

### 1.3. Связь с бизнес-требованиями
Фундамент реализует общую для всех детей требуемость (FR-1..FR-5): систему должна видеть текущую активность и активность за выбранный период. Этот контракт используют фронты для отображения счётчика, графика и выгрузки.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal BE → Children FE
- **Триггер:** Фронт запрашивает текущую активность (по загрузке страницы / при обновлении счётчика) или активность за период (когда пользователь открыл модалку / переключил период).
- **Контракт (запрос):**
  - Параметры (GET):
    - `period_type` (string, обязательно): `current` | `hourly` | `daily` | `weekly`
    - `period_end` (ISO 8601 datetime, опционально): конец периода для агрегации; по умолчанию — текущее время (UTC)
    - Заголовок: `Authorization: Bearer <token>` (валидируется на бэке Arsenal)

- **Контракт (ответ):**
  - `current_count` (integer ≥ 0, может быть null): число активных пользователей в данный момент
    - null → источник данных активности недоступен (см. `availability_status`)
  - `availability_status` (enum, обязательно):
    - `available` — данные актуальны
    - `source_unavailable` — источник недоступен, `current_count` и `aggregates` игнорировать
  - `aggregates` (object или null, опционально): агрегированная активность за период
    - Если `period_type = current`: aggregates отсутствует (не применимо)
    - Если `period_type = hourly|daily|weekly`:
      - `period_type` (string): повтор из запроса
      - `period_end` (ISO 8601): конец периода (из запроса или текущее время)
      - `data_available` (boolean):
        - true → массив datapoints ниже заполнен
        - false → данных за период нет (легитимная ситуация: в период не было активности или записи не дошли); datapoints пуст или отсутствует
      - `datapoints` (array of objects, опционально, если `data_available = true`):
        - Каждый datapoint:
          - `timestamp` (ISO 8601): время агрегата (начало часа, дня, недели)
          - `count` (integer ≥ 0): число активных в этом окне
      - `total` (integer ≥ 0): сумма по всем datapoints за период

- **Пример запроса (current):**
  ```
  GET /api/v1/activity/current
  Authorization: Bearer <token>
  ```

- **Пример запроса (period):**
  ```
  GET /api/v1/activity/aggregate?period_type=daily&period_end=2026-07-26T23:59:59Z
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех, current):**
  ```json
  {
    "current_count": 42,
    "availability_status": "available"
  }
  ```

- **Пример ответа (успех, hourly):**
  ```json
  {
    "current_count": 42,
    "availability_status": "available",
    "aggregates": {
      "period_type": "hourly",
      "period_end": "2026-07-26T15:00:00Z",
      "data_available": true,
      "datapoints": [
        { "timestamp": "2026-07-26T12:00:00Z", "count": 35 },
        { "timestamp": "2026-07-26T13:00:00Z", "count": 38 },
        { "timestamp": "2026-07-26T14:00:00Z", "count": 42 },
        { "timestamp": "2026-07-26T15:00:00Z", "count": 40 }
      ],
      "total": 155
    }
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_count": null,
    "availability_status": "source_unavailable",
    "aggregates": null
  }
  ```

- **Пример ответа (данных за период нет):**
  ```json
  {
    "current_count": 42,
    "availability_status": "available",
    "aggregates": {
      "period_type": "daily",
      "period_end": "2026-07-25T23:59:59Z",
      "data_available": false,
      "datapoints": [],
      "total": 0
    }
  }
  ```

- **Ошибки:**
  - `401 Unauthorized` — токен отсутствует или невалиден
  - `403 Forbidden` — роль пользователя не «Администратор»
  - `400 Bad Request` — некорректный `period_type` или `period_end`
  - `500 Internal Server Error` — внутренняя ошибка Арсенала (не путать с source_unavailable в теле)

- **Состояния UI по ответу (для детей):**
  - `availability_status = available` → использовать значения в ответе
  - `availability_status = source_unavailable` → показать UI-состояние `error_source` (сообщение вида «Данные активности недоступны» + кнопка retry)
  - `data_available = false` (в aggregates) → показать UI-состояние `empty` (пустой график / «нет данных за период»)
  - HTTP 403 → UI-состояние `error_forbidden` («нет доступа»)
  - HTTP 5xx или таймаут → UI-состояние `error_source`

- **Авторизация:** Доступ проверяется на бэке Arsenal; только пользователь с ролью «Администратор» может вызвать этот контракт. Возврат 403, если роль отсутствует.

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (счётчик активности), FR-2 (обновление счётчика), FR-3 (открытие модалки с графиком), FR-4 (переключение периода), FR-5 (выгрузка сводки)

### Каталог ошибок
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 OK, `availability_status: available` | согласно контракту | успешно получены данные активности | `value` (если count > 0) / `zero` (если count = 0) |
| 200 OK, `availability_status: source_unavailable` | `{"current_count": null, "availability_status": "source_unavailable"}` | источник данных активности недоступен | `error_source` («Данные активности недоступны») |
| 200 OK, `data_available: false` (в aggregates) | datapoints пусто | за выбранный период данных нет | `empty` («Нет данных за этот период») |
| 401 Unauthorized | `{"error": "missing_or_invalid_token"}` | токен отсутствует / невалиден | `error_forbidden` (повторная попытка входа) |
| 403 Forbidden | `{"error": "insufficient_role", "required_role": "Administrator"}` | роль не «Администратор» | `error_forbidden` («Нет доступа») |
| 400 Bad Request | `{"error": "invalid_period_type", "allowed": ["current", "hourly", "daily", "weekly"]}` | неверный параметр period_type | `error_source` + retry |
| 500 Internal Server Error | `{"error": "internal_error"}` | внутренняя ошибка Арсенала | `error_source` + retry |
| Таймаут (≥ 5 сек) | — | сеть или бэк не ответил вовремя | `error_source` + retry |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal (BE):**
- Реализует INT-0 (новый контракт отдачи активности) с двумя операциями: `GET /api/v1/activity/current` и `GET /api/v1/activity/aggregate`.
- Получает текущее число активных пользователей (из собственного источника, см. 3.2).
- Рассчитывает агрегаты активности на лету за период без сохранения в отдельные таблицы (см. 3.2).
- Проверяет авторизацию: только ролью «Администратор» (см. 3.3).
- Кэширует ответ на 30 секунд на уровне бэка (см. 5.1).
- Возвращает флаг `availability_status` при недоступности источника (не устаревшее значение).

### 3.2. Данные и хранение

🟢 **Новых таблиц не заводим.** Данные активности пользователей (текущее число активных и история для агрегирования) уже собираются в Arsenal BE из собственного источника (сессионные логи / session store / другой внутренний источник). Узел #0 не изменяет способ сбора и хранения, а лишь переформатирует существующие данные в контракт INT-0.

🟢 **Агрегирование на лету.** При запросе с `period_type = hourly|daily|weekly` бэк считает агрегаты за указанный период, не сохраняя их отдельно. Этап вычисления — внутри обработчика INT-0; материализации в таблицу нет.

⚠️ **Тип источника и механика сбора:** На данный момент источник, из которого берётся текущее число активных, подтвержден в общих чертах (Arsenal собирает сам, внешних сервисов не привлекаем), но точная реализация (session store / cache / Redis / иное) остаётся на уровне тактических решений BE — не меняет контракт. При интеграции уточнить. Для цели этого документа важно: данные есть и их можно вычислить.

### 3.3. Авторизация/доступ на бэке

🟡 **подтверждено аналитиком (не по коду).** Проверка ролей на Arsenal BE: контракт INT-0 доступен только пользователям с ролью «Администратор». Пользователи без этой роли получают 403 Forbidden с указанием требуемой роли.

## 4. Frontend — ответственность

Не применимо: фундамент — BE-only контракт. Ответственность фронтов (дочерние узлы ARS-101, ARS-102, ARS-103) — потреблять INT-0 и преобразовывать в UI-состояния согласно своим спекам.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

🟡 **подтверждено аналитиком (не по коду).** Обе операции INT-0 (`current` и `aggregate`) работают **синхронно** — фронт ждёт ответа.

🟡 **подтверждено аналитиком (не по коду).** **Кэш:** ответ кэшируется на **30 секунд на стороне Arsenal BE**. Повторный запрос за 30-секундный интервал возвращает закэшированный результат (не пересчитывается).

🟡 **подтверждено аналитиком (не по коду).** **Таймаут:** запрос должен быть обработан за **≤ 5 секунд**. При превышении таймаута считается ошибкой `error_source`.

### 5.2. Надёжность/деградация

🟡 **подтверждено аналитиком (не по коду).** **При недоступности источника данных активности:** если источник (session store / внутренний логер) недоступен или не отвечает, Arsenal BE **не возвращает устаревшее значение**, а **отдаёт флаг `availability_status: source_unavailable`** в теле с `current_count: null` и `aggregates: null`. Это позволяет фронту отличить «источник недоступен» от «данных за период нет».

🟡 **подтверждено аналитиком (не по коду).** **Различие состояний:** отдельно различаем:
- `availability_status: source_unavailable` — источник недоступен (сеть, сбой);
- `data_available: false` в aggregates — источник доступен, но за период данных не записалось (легитимный 0).

Первое → UI показывает ошибку; второе → UI показывает пустой график.

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто | Что может | Проверка |
|---------|-----|-----------|----------|
| INT-0 → FE | Администратор | GET /api/v1/activity/current, /aggregate | 403, если роль не Administrator |
| INT-0 → FE | non-Admin | любой запрос | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 **подтверждено аналитиком (не по коду).** **Фундамент выкатывается ПЕРВЫМ, до дочерних узлов.** Очередность:
1. Arsenal BE (узел #0) — новый контракт INT-0 готов к обслуживанию.
2. Children FE (ARS-101, ARS-102, ARS-103) — потребители начинают вызывать INT-0.

### 6.2. Обратная совместимость

🟢 **Новый контракт, обратная совместимость не применимо** — INT-0 добавляется заново. Старые фронты, не знающие о INT-0, просто его не вызывают.

### 6.3. Фиче-флаги

🟡 **подтверждено аналитиком (не по коду).** **Фиче-флагов нет.** Контракт INT-0 выкатывается атомарно на Arsenal BE; дочерние фронты начинают его потреблять после выката фундамента (зависимость по расписанию, не по коду).

### 6.4. План отката

**Откат Arsenal BE (только фундамент):** если контракт INT-0 откатить, дочерние фронты получат 404 или 5xx при вызове `/api/v1/activity/*`. Фронты должны иметь UI-состояние `error_source` и кнопку retry. Откат фундамента требует синхронного отката всех потребителей (или они должны маскировать ошибку до отката в другом окне).

**Откат FE без BE:** не применимо (это BE-only).

**Откат данных (DDL):** не применимо (новых таблиц не заводим; данные берутся из существующего источника Arsenal).

### 6.5. Преднастройка до релиза (чек-лист)

- [x] Роли в security-сервисе — убедиться, что роль «Администратор» определена (🟡 подтверждено аналитиком, что роль уже существует)
- [x] DDL-миграция — не применимо (новых таблиц нет)
- [ ] Конфиги по окружениям (dev/staging/prod) — уточнить список конфигов (TTL кэша 30s, таймаут 5s и т.п.) при интеграции
- [ ] Алерты/мониторинг на ключевые ошибки (5xx, таймауты, `source_unavailable`)

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 (счётчик активности в шапке) | INT-0 GET /current | Дано фронт загрузился, когда бэк отвечает 200 с `current_count: 42`, тогда счётчик в шапке показывает 42 |
| FR-2 (автообновление счётчика) | INT-0 GET /current (periodic) | Дано счётчик в шапке показывает 42, когда number активных изменилось на 50 и прошло ≤ 30с, тогда счётчик обновляется на 50 |
| FR-3 (открытие модалки с графиком) | INT-0 GET /aggregate?period_type=daily | Дано администратор кликнул на счётчик, когда бэк отвечает 200 с datapoints за день, тогда открывается модалка с графиком |
| FR-4 (переключение периода) | INT-0 GET /aggregate?period_type=hourly|daily|weekly | Дано модалка открыта с периодом daily, когда администратор выбирает hourly, тогда график перестраивается и показывает hourly datapoints |
| FR-5 (выгрузка сводки) | INT-0 GET /aggregate + FE-формирование файла | Дано модалка открыта, когда администратор нажимает кнопку выгрузки, тогда фронт получает datapoints из INT-0 и генерирует файл сводки |

## 8. Допущения и открытые вопросы

*(Все технические решения приняты, спецификация готова к разработке.)*

- **🟡 Подтверждено аналитиком (не по коду):**
  - Роль «Администратор» существует в security-сервисе Arsenal.
  - Arsenal BE собирает данные активности пользователей из собственного источника (нет привлечения внешних сервисов).
  - Таймаут 5 секунд и кэш 30 секунд на Arsenal BE.
  - При недоступности источника отправляется флаг `availability_status: source_unavailable`, а не устаревшее значение.

- **🟡 К валидации:**
  - Точный источник данных активности (session store / Redis / иное хранилище) — уточнить по коду Arsenal BE при интеграции.
  - Механика инвалидации кэша при изменении активности (если нужна более свежая отдача раньше 30 секунд) — согласовать при интеграции.
  - Список конфигов по окружениям (dev/staging/prod) для TTL и таймаута — подготовить при выкате.

- **Унаследовано из БТ (бизнес-пробелы):**
  - Точная целевая нагрузка (кол-во параллельных запросов в пиковый час) — закрывается на стороне БТ и в плане нагрузочного тестирования.
  - Деталировка выгружаемого формата файла в FR-5 (CSV / XLSX / иное) — закрывается дочерним узлом ARS-105 или в спеке фронта.
