## Что спроектировано

Единое взаимодействие INT-0 — контракт отдачи данных активности пользователей от Arsenal BE к фронтам дочерних узлов:

- **Операция 1:** `GET /api/v1/activity/current` — текущее число активных пользователей
- **Операция 2:** `GET /api/v1/activity/aggregate?period_type=hourly|daily|weekly&period_end=…` — агрегаты активности за период (datapoints по часам/дням/неделям)

**Ключевые особенности контракта:**

1. **Двойная семантика недоступности:** Поле `availability_status` различает:
   - `available` — данные актуальны
   - `source_unavailable` — источник недоступен (не отправляем устаревшее)
   
2. **Разделение пустоты:** Флаг `data_available` в aggregates отличает:
   - `true` — есть datapoints за период
   - `false` — период покрыт, но данных не было (легитимный 0)

3. **Авторизация:** Только роль «Администратор», проверяется на Arsenal BE, возврат 403 для остальных.

4. **Производительность:** Синхронно, 30-секундный кэш на Arsenal BE, таймаут 5 секунд.

5. **Хранение:** Агрегаты считаются на лету; новых таблиц не заводим.

6. **롤아웃:** Фундамент выкатывается ПЕРВЫМ, дочерние фронты начинают вызывать после. Фиче-флагов нет.

**Задача-родитель для шапки:** ARS-100 (из папки эпик-БТ)

## К валидации при интеграции

- Точный источник данных активности (session store / Redis / иное) в Arsenal BE
- Механика инвалидации кэша раньше 30 секунд (если нужна более свежая отдача)
- Конфиги TTL и таймаутов по окружениям

## Трассировка

- FR-1 (счётчик в шапке) → INT-0 GET /current
- FR-2 (автообновление счётчика) → INT-0 GET /current (periodic)
- FR-3 (открытие модалки) → INT-0 GET /aggregate
- FR-4 (переключение периода) → INT-0 GET /aggregate (разные period_type)
- FR-5 (выгрузка сводки) → INT-0 GET /aggregate + FE-генерация файла

Спецификация готова. Дочерние узлы могут теперь наследовать INT-0 и строить свои фронты на основе этого контракта.
