# Техническая спецификация узла-фундамента #0 — готово

## Что выполнено

На основе полных ответов аналитика по всем технически-значимым решениям разработана техническая спецификация узла-фундамента #0 эпика ARS-100.

## Реестр технических гейтов (все закрыты)

1. **Тип и стороны** — ✅ BE-only; Arsenal backend предоставляет контракт данных активности детским фронтам
2. **Инвентарь взаимодействий** — ✅ Одно новое взаимодействие INT-0: фундамент отдаёт данные активности (текущий счёт + агрегаты за период)
3. **Владение и допущения** — ✅ Arsenal backend собирает активность сам; чужих сервисов нет; своих допущений нет
4. **Контракт взаимодействия** — ✅ GET /api/v1/admin/activity-stats с параметрами period (hour/day/week) и endAt (опционально); ответ содержит currentActiveUsers, periodData, availabilityStatus (available/unavailable/no_data) и опциональное message
5. **Ошибки и состояния** — ✅ availabilityStatus различает три случая: источник доступен и данные есть, источник недоступен, данных за период нет. Соответствующие UI-состояния: value, zero, empty, error_source, error_forbidden
6. **Авторизация** — ✅ Только роль «Администратор»; проверка на бэке Arsenal; HTTP 403 для других ролей, HTTP 401 для неавторизованных
7. **Данные и хранение** — ✅ Новых таблиц нет; агрегаты считаются на лету из существующего источника сессий
8. **Синхронность и производительность** — ✅ Синхронный вызов; кэш 30 сек в памяти бэка Arsenal; таймаут 5 сек
9. **Порядок выката** — ✅ Фундамент раньше потребителей; фиче-флагов нет; релиз атомарный
10. **Трассировка** — ✅ FR-1..FR-5 эпика в части данных активности; таблица трассировки в §7

**Задача:** ARS-100 / узел-фундамент #0 (ключ эпика; своей задачи у #0 нет)

## Структура спецификации

Спецификация содержит:

- **INT-0** — полный контракт взаимодействия с тремя примерами JSON (успех, недоступность источника, нет данных)
- **Backend-ответственность** — реализация эндпоинта, без новых таблиц, авторизация по ролям
- **Frontend-ответственность** — использование контракта тремя детскими фронтами, состояния UI, обработка таймаутов, polling для счётчика
- **Нефункциональные требования** — синхронность, кэширование, надёжность при недоступности, безопасность
- **Релиз и интеграция** — порядок деплоя (фундамент первым), нет фиче-флагов, план отката
- **Трассировка приёмки** — связь FR-1..FR-5 → INT-0 → тест-кейсы

## Открытые вопросы (требуют уточнения при интеграции, не блокируют разработку)

- Ожидаемая нагрузка: количество активных администраторов и частота запросов к INT-0 (уточнить при интеграции)

## Статус готовности

**Готово к разработке.** Все технические решения приняты. Фронт-разработчик и бэк-разработчик имеют общий канонический контракт (INT-0 с примерами JSON), авторизацию, обработку ошибок и маппинг на UI-состояния.
