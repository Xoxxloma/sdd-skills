## 2. Взаимодействия (ядро)

### INT-0. Данные активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal backend → фронты детей (HTTP/JSON)
- **Триггер:** 
  - Инициализация шапки админки (запрос текущего счёта активных пользователей)
  - Открытие модального окна активности (запрос данных за выбранный период)
  - Переключение периода в модальном окне (повторный запрос за новый период)
  - Выгрузка сводки (запрос данных за выбранный период в формате для экспорта)

- **Контракт (запрос):**
  - Метод: `GET /api/v1/admin/activity-stats`
  - Параметры:
    - `period` (string, обязателен): `hour` | `day` | `week`
    - `endAt` (ISO-8601 timestamp, опционально): конец периода; по умолчанию текущее время

- **Контракт (ответ):**
  - `currentActiveUsers` (integer ≥ 0): число активных пользователей сейчас
  - `periodData` (array of objects): агрегированные данные активности за выбранный период
    - `timestamp` (ISO-8601 string): момент, к которому относится отчёт
    - `activeUsers` (integer ≥ 0): число активных пользователей в этот момент
  - `period` (string): тип периода, выбранный клиентом (`hour` | `day` | `week`)
  - `availabilityStatus` (string): статус доступности данных:
    - `available` — данные получены полностью и актуальны
    - `unavailable` — источник активности недоступен, данные не получены
    - `no_data` — источник доступен, но за выбранный период нет записей
  - `message` (string, опционально): сообщение об ошибке или уточнение (если `availabilityStatus` ≠ `available`)

- **Пример запроса:**
  ```
  GET /api/v1/admin/activity-stats?period=hour&endAt=2024-07-26T15:00:00Z
  ```
  (тело отсутствует)

- **Пример ответа (успех — availabilityStatus: available):**
  ```json
  {
    "currentActiveUsers": 42,
    "periodData": [
      { "timestamp": "2024-07-26T14:00:00Z", "activeUsers": 38 },
      { "timestamp": "2024-07-26T14:15:00Z", "activeUsers": 40 },
      { "timestamp": "2024-07-26T14:30:00Z", "activeUsers": 42 },
      { "timestamp": "2024-07-26T14:45:00Z", "activeUsers": 40 }
    ],
    "period": "hour",
    "availabilityStatus": "available"
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "currentActiveUsers": null,
    "periodData": [],
    "period": "hour",
    "availabilityStatus": "unavailable",
    "message": "Источник активности недоступен. Повторите запрос позже."
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "currentActiveUsers": 0,
    "periodData": [],
    "period": "hour",
    "availabilityStatus": "no_data",
    "message": "За выбранный период нет данных активности."
  }
  ```

- **Ошибки:**
  - HTTP 400 — некорректный параметр `period` (не `hour`, `day` или `week`) или некорректный формат `endAt`
  - HTTP 401 — запрос без авторизации
  - HTTP 403 — авторизованный пользователь не имеет роли «Администратор»
  - HTTP 408 — таймаут при получении данных (>5 секунд)
  - HTTP 5xx — ошибка на стороне сервера

- **Состояния UI по ответу:**
  - `value` (currentActiveUsers > 0 и availabilityStatus = `available`) → отобразить число (для шапки; для графика — отобразить periodData)
  - `zero` (currentActiveUsers = 0 и availabilityStatus = `available`) → отобразить «0» (валидный ноль)
  - `empty` (availabilityStatus = `no_data`) → отобразить «—» / «нет данных»
  - `error_source` (availabilityStatus = `unavailable`) → отобразить сообщение об ошибке + предложение повторить
  - `error_forbidden` (HTTP 403) → отобразить «нет доступа»

- **Авторизация:**
  - Доступен только пользователям с ролью «Администратор»
  - Проверка выполняется на бэке Arsenal (по токену в заголовке Authorization)
  - Негативный случай: пользователь с другой ролью (напр. Оператор) получает HTTP 403 Forbidden

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (эпик)

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal backend:**
- Реализует контракт INT-0: эндпоинт `GET /api/v1/admin/activity-stats` с параметрами `period` и `endAt` (опционально)
- Собирает текущий счёт активных пользователей из внутреннего источника активности (сессий/подключений)
- Агрегирует данные активности за выбранный период по запросу (на лету, без новых таблиц)
- Соблюдает разницу между состояниями: источник недоступен (`unavailable`), данных нет за период (`no_data`), данные есть (`available`)
- Кэширует результат на 30 секунд в памяти бэка Arsenal
- Укладывается в таймаут 5 секунд при возвращении ответа
- Проверяет авторизацию (роль «Администратор») перед отдачей данных

### 3.2. Данные и хранение

**Новых таблиц нет.** 🟡 подтверждено аналитиком (не по коду): агрегаты активности считаются на лету из существующего источника сессий/подключений Arsenal backend, без расширения схемы БД.

### 3.3. Авторизация/доступ на бэке

- Проверка роли «Администратор» выполняется на бэке Arsenal перед возвращением контракта INT-0
- Негативный случай (403): любой авторизованный пользователь, чья роль ≠ «Администратор», получает HTTP 403 Forbidden с сообщением «нет доступа»
- Негативный случай (401): неавторизованный запрос получает HTTP 401 Unauthorized

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Фронты детей используют контракт INT-0 для:
1. **Счётчик в шапке админки:** текущий счёт (`currentActiveUsers` из INT-0) обновляется без перезагрузки
2. **Модальное окно с графиком:** `periodData` из INT-0 отображается как график за выбранный период
3. **Выгрузка сводки:** данные из INT-0 преобразуются в формат для экспорта (CSV, Excel или иной)

### 4.2. Пользовательские сценарии

*(Детальное описание сценариев находится в бизнес-требованиях и будет отработано на уровне детских задач. Здесь фиксируем привязку к контракту фундамента.)*

- **Основной поток:** открыта админка → загружается шапка → счётчик показывает число активных пользователей → счётчик обновляется автоматически на основе INT-0 → администратор кликает на счётчик → открывается модальное окно → данные за период загружаются из INT-0 → отображается график.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос INT-0 или после инвалидации | спиннер / скелетон |
| `value` | HTTP 2xx, `availabilityStatus` = `available`, `currentActiveUsers` > 0 (для счётчика) или `periodData` не пусто (для графика) | число или график |
| `zero` | HTTP 2xx, `availabilityStatus` = `available`, `currentActiveUsers` = 0 | «0» (не «—») |
| `empty` | HTTP 2xx, `availabilityStatus` = `no_data` (или `periodData` пусто) | «—» / «нет данных» |
| `error_source` | HTTP 5xx, таймаут (>5с) или сеть, `availabilityStatus` = `unavailable` | сообщение об ошибке + кнопка повторить |
| `error_forbidden` | HTTP 403 | «нет доступа» |

### 4.3.1. Loading и таймауты

- **Cold-path таймаут** (первый запрос, счётчик при открытии админки): рекомендуется ≤2 секунды видимого ожидания перед показом ошибки (источник отвечает в пределах 5 сек по контракту, но FE может добавить собственное ограничение для UX)
- **Warm-path таймаут** (обновление счётчика / переключение периода): рекомендуется ≤1 секунда перед показом ошибки
- **Polling** (обновление счётчика в шапке): интервал обновления ≤1 минуты (по приёмке FR-2: обновление в пределах минуты); jitter — да (±10 секунд, чтобы избежать синхронизации всех клиентов)

### 4.4. Доступ по ролям в UI

- **Администратор:** видит счётчик, может открыть модальное окно, может выгрузить сводку
- **Оператор** (другие роли): счётчик и модальное окно скрыты / недоступны

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** синхронный вызов (фронт ждёт ответа)
- **Кэш:** 30 секунд в памяти бэка Arsenal (на уровне сервиса, не HTTP кэша). Каждый запрос идёт по сети (GET, кэш прозрачен для фронта).
- **Таймаут:** 5 секунд на возврат ответа (от начала запроса до получения тела или ошибки)
- **Частота опроса:** счётчик в шапке обновляется автоматически с интервалом до 1 минуты (FR-2), что синхронизируется с TTL кэша бэка (30с) с учётом jitter на клиенте
- **Ожидаемая нагрузка:** 🟡 к валидации (количество активных админов, частота запросов — уточнить при интеграции; предполагается, что это малое число и частота не критична)

### 5.2. Надёжность/деградация

- **При недоступности источника активности:** эндпоинт INT-0 возвращает HTTP 2xx с `availabilityStatus` = `unavailable` и `message`, содержащим подробность; `currentActiveUsers` и `periodData` остаются `null` / пусто
- **Никогда не отдаём устаревшее значение:** если источник был недоступен 30+ секунд (дольше кэша), кэшированное значение выбрасывается; при следующем запросе возвращается `unavailable`
- **Различаем три случая:** (1) источник недоступен (`unavailable`), (2) источник доступен, но данных нет за период (`no_data`), (3) данные есть (`available`)
- **Фронт видит этот контракт** и может показать разные сообщения (напр. для `unavailable` предложить повторить, для `no_data` показать «—»)

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто | Может ли вызвать | Действие |
|---------|-----|------------------|----------|
| Arsenal BE ← FE | Администратор | Да | GET /api/v1/admin/activity-stats → HTTP 200 + данные |
| Arsenal BE ← FE | Оператор / другие | Нет | GET /api/v1/admin/activity-stats → HTTP 403 Forbidden |
| Arsenal BE ← FE | Неавторизованный | Нет | GET /api/v1/admin/activity-stats → HTTP 401 Unauthorized |

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **Arsenal backend:** разработка и тестирование эндпоинта INT-0, деплой в test → staging → prod
2. **Фронты детей:** разработка счётчика, модального окна, выгрузки сводки на основе контракта INT-0 (в параллель с пп.1)
3. **Деплой фронтов:** только после подтверждения, что Arsenal backend выкатан в целевое окружение и контракт INT-0 доступен

**Фундамент раньше потребителей:** фиче-флагов нет; деплой атомарный после интеграционного тестирования.

### 6.2. Обратная совместимость

Новый контракт; нет текущих потребителей. После запуска фундамента фронты детей «подцепляются» к INT-0; обратная совместимость рассматривается по отношению к фронтам, которые будут выкатаны после фундамента.

### 6.3. Фиче-флаги

**Фиче-флагов нет.** 🟡 подтверждено аналитиком (не по коду): релизим атомарно — фундамент и фронты детей выкатываются как единое целое.

### 6.4. План отката

**Откат Arsenal BE:** если контракт INT-0 откатывается, фронты детей получат HTTP 404 или 5xx (в зависимости от того, как раньше был интегрирован эндпоинт); фронты должны обработать это как ошибку (состояние `error_source`).

**Откат фронтов:** фронты могут быть откачены независимо (каждый детский фронт отдельно); Arsenal backend продолжит отдавать контракт INT-0 корректно.
