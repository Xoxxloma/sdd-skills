## 1. Обзор изменения
### 1.1. Тип и стороны
**BE-only.** Узел-фундамент #0 предоставляет единый контракт данных активности пользователей, который потребляют дочерние узлы (UI-элементы админки: счётчик в шапке, модальное окно, экспорт). Все три потребителя опираются на одни данные, поэтому контракт проектируется один раз, в узле #0, и отдаётся детям неизменным.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend (данные активности) | Сборка данных активности пользователей, вычисление агрегатов, отдача контрактов | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Фундамент #0 обслуживает общее ядро всех пяти функциональных требований (FR-1..FR-5) эпика ARS-100: текущий счёт активных пользователей и агрегированную активность за период (час / день / неделя). Эти данные являются источником истины для счётчика в шапке (FR-1, FR-2), графика в модальном окне (FR-3, FR-4) и выгружаемой сводки (FR-5).

## 2. Взаимодействия (ядро)

### INT-0. Получение текущего счёта активных пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Внутренний API узла #0 → потребители (UI детей, backend детей)
- **Триггер:** Инициирование отображения счётчика в шапке; периодический запрос для обновления (polling каждые ~30с).
- **Контракт (запрос):** 
  ```
  GET /activity/current-count
  Заголовки: Authorization: Bearer <token> (роль должна быть в заголовке или проверяется на бэке)
  Параметры: нет
  ```
- **Контракт (ответ):** 
  - `count` (int ≥ 0) — число активных пользователей в текущий момент; обязательное поле.
  - `is_available` (bool) — признак доступности источника данных. Если `false`, источник недоступен (BD/сеть/timeout), `count` не актуален и должен трактоваться как N/A.
  - `timestamp` (ISO8601 string) — момент последнего обновления счёта (для UI-логики обновления и отладки).
  - Семантика null: никакое поле не null; `is_available: false` одновременно с `count: 0` означает, что значение неизвестно (пусто — состояние `empty_source`).
  - Enum нет (count — целое число).
- **Пример ответа (успех):**
  ```json
  {
    "count": 42,
    "is_available": true,
    "timestamp": "2025-07-26T14:32:15Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": 0,
    "is_available": false,
    "timestamp": "2025-07-26T14:30:00Z"
  }
  ```
- **Ошибки:** 
  - `401 Unauthorized` — нет валидного токена; пользователь не аутентифицирован.
  - `403 Forbidden` — пользователь аутентифицирован, но роль не `Administrator`; см. §5.3.
  - `500 Internal Server Error` — внутренняя ошибка бэка Arsenal; `is_available: false` в ответе вместо 500 предпочтительнее (graceful degradation).
  - `504 Gateway Timeout` — таймаут при обращении к источнику; рассматривается как недоступность → `is_available: false`.
- **Состояния UI по ответу (если есть фронт):**
  - `value` → `count` > 0 и `is_available: true` → показать число.
  - `zero` → `count = 0` и `is_available: true` → показать «0» (валидный ноль, пользователей нет).
  - `empty_source` → `is_available: false` → показать «—» (данные недоступны).
  - `error_forbidden` → 403 → скрыть элемент (нет роли).
  - `error_network` → 401 / 5xx / таймаут → показать ошибку (retry или пример ниже по цепи).
- **Авторизация:** Только роль `Administrator`. Проверка на стороне Arsenal Backend при приёме запроса. Негативный случай: `403 Forbidden`.
- **Происхождение:** 🟢 новое (узел-фундамент #0).
- **Трассировка:** FR-1, FR-2 (счётчик активных, обновление в реальном времени).

### INT-1. Получение агрегированной активности за период — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Внутренний API узла #0 → потребители (UI модального окна, экспорт; backend детей).
- **Триггер:** Открытие модального окна; переключение периода (час / день / неделя); инициирование экспорта сводки.
- **Контракт (запрос):**
  ```
  GET /activity/aggregates?period=<period>&from=<ISO8601>&to=<ISO8601>
  Заголовки: Authorization: Bearer <token>
  Параметры:
    - period (string, enum: 'hour' | 'day' | 'week') — гранулярность агрегирования.
    - from (ISO8601 datetime, обязательный) — начало периода.
    - to (ISO8601 datetime, обязательный) — конец периода.
  ```
  Ограничения на period: максимум 4 недели в запросе (для производительности).
- **Контракт (ответ):**
  - `aggregates` (array) — массив точек активности; упорядочен по времени (от ранней к поздней).
    - Каждая точка: `{ "bucket": "<ISO8601>", "count": <int ≥ 0> }`
      - `bucket` — начало временного окна (e.g., час начинается в 14:00:00, день в 00:00:00).
      - `count` — число активных пользователей в этом окне; >= 0.
  - `period_label` (string) — human-readable (e.g., «29 июля – 4 августа, неделя»); для UI-заголовков.
  - `is_available` (bool) — признак доступности данных. Если `false`, источник недоступен; массив пуст.
  - `has_data` (bool) — есть ли хоть одна точка за период (даже если 0 активных). Если `false`, период не содержит ни одного полного окна (например, запрос за 5 минут в прошлом → данные ещё не собраны / пока нет); пусто — состояние `empty_period`.
  - `timestamp` (ISO8601 string) — момент запроса (для отладки и UI-кэширования).
- **Пример ответа (успех, активность за день с часовой гранулярностью):**
  ```json
  {
    "aggregates": [
      { "bucket": "2025-07-26T00:00:00Z", "count": 5 },
      { "bucket": "2025-07-26T01:00:00Z", "count": 8 },
      { "bucket": "2025-07-26T02:00:00Z", "count": 3 },
      { "bucket": "2025-07-26T14:00:00Z", "count": 42 },
      { "bucket": "2025-07-26T15:00:00Z", "count": 38 }
    ],
    "period_label": "26 июля, день, часовая гранулярность",
    "is_available": true,
    "has_data": true,
    "timestamp": "2025-07-26T15:32:15Z"
  }
  ```
- **Пример ответа (период без данных — слишком свежий запрос):**
  ```json
  {
    "aggregates": [],
    "period_label": "26 июля 15:30–15:35, 5 минут назад, нет данных",
    "is_available": true,
    "has_data": false,
    "timestamp": "2025-07-26T15:32:15Z"
  }
  ```
- **Пример ответа (источник данных недоступен):**
  ```json
  {
    "aggregates": [],
    "period_label": "26 июля, день",
    "is_available": false,
    "has_data": false,
    "timestamp": "2025-07-26T14:30:00Z"
  }
  ```
- **Ошибки:**
  - `400 Bad Request` — невалидный period, from/to или диапазон > 4 недель.
  - `401 Unauthorized` — нет токена.
  - `403 Forbidden` — роль не `Administrator`.
  - `500 Internal Server Error` → `is_available: false` в ответе (preferred).
  - `504 Gateway Timeout` → `is_available: false`.
- **Состояния UI по ответу:**
  - `data_available` → `has_data: true` и `is_available: true` → отрисовать график с точками.
  - `empty_period` → `has_data: false` и `is_available: true` → показать сообщение «нет данных за этот период» (период валиден, но пуст).
  - `empty_source` → `is_available: false` → показать «—» / сообщение об ошибке источника.
  - `error_forbidden` → 403 → скрыть (нет роли).
  - `error_input` → 400 → валидация на UI (не должно быть видно пользователю, но для отладки).
- **Авторизация:** Только роль `Administrator`. Проверка на Arsenal Backend.
- **Происхождение:** 🟢 новое (узел-фундамент #0).
- **Трассировка:** FR-3, FR-4, FR-5 (график, переключение периода, выгрузка).

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 Bad Request | `{ "error": "invalid_period", "details": "..." }` | Невалидный period, from/to, диапазон > 4 недель | `error_input` |
| 401 Unauthorized | `{ "error": "unauthorized" }` | Отсутствует токен или истёк | `error_network` (retry) |
| 403 Forbidden | `{ "error": "forbidden", "required_role": "Administrator" }` | Роль не Administrator | `error_forbidden` (скрыть элемент) |
| 500 Internal Server Error | `{ "error": "internal_error" }` | Ошибка Arsenal Backend | Предпочтительно: INT-0/INT-1 вернёт 2xx с `is_available: false` |
| 504 Gateway Timeout | нет тела | Таймаут к источнику (BD, сеть) | Предпочтительно: INT-0/INT-1 вернёт 2xx с `is_available: false` |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal Backend:**
- Реализует оба взаимодействия (INT-0, INT-1) из §2: отдаёт `/activity/current-count` и `/activity/aggregates`.
- Собирает данные активности пользователей самостоятельно (🟡 подтверждено аналитиком: своих допущений нет, чужих сервисов не привлекаем). Логика сбора и источник данных (логи сессий, BD, внутренний трэкинг) — реализационный деталь; спека оперирует уже собранными/агрегированными данными.
- Вычисляет агрегаты на лету (час / день / неделя) для запрошенного диапазона (см. 3.2).
- Проверяет роль `Administrator` при приёме запроса; возвращает 403, если роль другая.
- Обрабатывает недоступность источника gracefully: возвращает `is_available: false` + пустой результат вместо 5xx (см. 5.2).

### 3.2. Данные и хранение
**Новых таблиц/хранилищ не заводим.** 🟡 подтверждено аналитиком: агрегаты вычисляются на лету из имеющихся данных активности. Таблица (или таблицы), в которых хранятся данные активности (сессии, логи, события), существует в Arsenal и не входит в объём этой задачи. Спека указывает, какие данные нужны на выходе контрактов (INT-0, INT-1), не предписывая, откуда их брать.

**На лету значит:**
- При запросе `/activity/current-count` → подсчитать активные сессии (или эквивалент) в текущий момент.
- При запросе `/activity/aggregates?from=...&to=...&period=...` → вычислить гистограмму активности по бакетам (час/день/неделя), вернуть массив с count в каждом бакете.

**Индексирование:** Если данные активности хранятся в BD, убедиться, что запросы к активности (текущей и за период) индексированы так, чтобы уложиться в таймаут 5с даже на историческом диапазоне до 4 недель. Точный DDL — на стороне Arsenal (🟡 существующая система).

**Кэширование:** Кэш 30с на стороне Arsenal Backend (см. 5.1). Инвалидация — при изменении данных активности или по TTL 30с, что наступит раньше.

### 3.3. Авторизация/доступ на бэке
- Проверка роли `Administrator` в каждом запросе к INT-0 и INT-1.
- Роль может быть передана в заголовке Authorization (в токене или в separate заголовке); точный механизм — на стороне Arsenal (🟡 подтверждено аналитиком: чекируется на бэке Арсенала, роль передаётся/проверяется стандартным образом).
- Если роль не `Administrator`, вернуть 403 с сообщением о требуемой роли.

## 4. Frontend — ответственность

**Примечание:** Узел #0 — BE-only фундамент. Frontend потребителей (дочерних узлов) будет потреблять INT-0 и INT-1 через свои компоненты. Спека фронтендов детей опишет, как они трактуют ответы фундамента (состояния, UI-поведение, retry-логика). Здесь перечисляем только базовые обязанности фундамента перед фронтом:

### 4.1. Что должно присутствовать для фронта
- **INT-0** предоставляет `is_available`, чтобы фронт различал `value` / `zero` / `empty_source`.
- **INT-1** предоставляет `has_data`, чтобы фронт различал `data_available` / `empty_period` / `empty_source`.
- **Таймаут и retry:** Оба запроса должны ответить в пределах 5s; если таймаут — фронт трактует как error_network и может retry (логика retry — на стороне потребителя).

### 4.2. Роли и видимость
Если пользователь не `Administrator`, фронт не должен видеть счётчик, модальное окно, кнопку выгрузки. На уровне бэка: попытка запроса без роли вернёт 403. На уровне фронта потребителей: элементы скрываются или не запрашиваются.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** INT-0 и INT-1 отвечают синхронно (как HTTP GET).
- **Кэш:** 30 секунд на стороне Arsenal Backend. После получения ответа фронт может кэшировать ещё, но не требуется. Инвалидация фронтом по времени или по пользовательскому действию (е.г., явный refresh).
- **Таймаут:** Максимум 5 секунд на ответ. Если источник данных недоступен, не ждём 5s заполнения; возвращаем `is_available: false` раньше.
- **Частота опроса (polling) на фронте:** Когда счётчик видим, рекомендуется polling INT-0 каждые 30–60 сек (на усмотрение потребителя). При открытии модального окна можно запросить INT-1 синхронно.
- **Нагрузка:** Ожидается O(100) одновременных пользователей админки, каждый может polling INT-0 каждые 30–60с (в пике ~2–3 запроса в секунду на фундамент). Для INT-1: всплески при открытии модального окна (~5–10 запросов при пике юзэйджа).

### 5.2. Надёжность/деградация
- **При недоступности источника (BD, сеть, сервис):** 
  - Вернуть 2xx (200) с `is_available: false` вместо 5xx.
  - Не отдавать устаревшие cached-значения — это нарушало бы trust (см. бизнес-риск в БТ).
  - Различать: `is_available: false` (источник not reached) от `has_data: false` (период пуст, но система online).
- **Таймаут источника:** Если запрос к BD/сеансам превышает ~3s, прервать и вернуть `is_available: false` (не ждём полные 5s).
- **Мониторинг:** Алерты на `is_available: false` дольше 5 минут или на 5xx при запросах к фундаменту.

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Что может | Как проверяется |
|---------|-----------|-----------|-----------------|
| INT-0, INT-1 | Administrator | Запросить текущий счёт и агрегаты активности | Проверка роли в заголовке / токене на Arsenal Backend → 403 если не Administrator |
| INT-0, INT-1 | Иные роли (Operator, Guest, etc.) | Ничего | 403 Forbidden |
| Данные активности | Administrator | Видит только агрегированные числа (не списков пользователей) | Не входит в scope; потребители (дети узла #0) отвечают за скрытие конкретных пользователей |

## 6. Релиз и интеграция

### 6.1. Порядок выката
**Фундамент #0 выкатывается ПЕРВЫМ,** раньше всех потребителей (дочерних узлов ARS-101, ARS-102, ARS-103 и выше по дереву). Это гарантирует, что контракт INT-0 и INT-1 уже живёт в prod перед тем, как фронтенды начнут его потреблять.

Порядок:
1. **Узел #0 (Arsenal Backend):** Deploy контрактов INT-0 и INT-1.
2. **Дочерние узлы:** Deploy потребителей (UI-компоненты) после подтверждения, что фундамент успешно live.

### 6.2. Обратная совместимость
- **Новые поля в ответе:** Если позже потребуется добавить поля в INT-0 или INT-1, старые потребители (фронты детей) должны их игнорировать (graceful ignore).
- **Изменение значения поля:** Не менять тип или enum-значения существующих полей без версионирования (e.g., не менять `count` с int на string).
- **Обратный вызов фронта:** Если фронт отправляет параметры в INT-0/INT-1, они должны быть в стабильной форме (period enum, date format ISO8601) и не меняться без координации.

### 6.3. Фиче-флаги
**Фиче-флагов нет.** 🟡 подтверждено аналитиком: релизим атомарно. Фундамент и его потребители выкатываются в одной очереди по порядку (см. 6.1), без условного вырубания контракта.

### 6.4. План отката (если фундамент нужно откатить)
- **Откат только BE (фундамента):** Если Arsenal Backend откатить на версию без INT-0/INT-1, фронты потребителей получат 404 или 5xx при запросе контракта. Требуется **синхронный откат фронтов потребителей** (они не смогут работать без контракта). Синхронность обязательна.
- **Откат фронтов потребителей при live BE:** Если фронт откатить, а фундамент live, UI просто не будет показывать счётчик/модалку (graceful degradation). BE продолжит работать.
- **Откат данных:** Нет новых таблиц, новых миграций; откат безопасен (no DDL down-миграции).

### 6.5. Преднастройка до релиза (чек-лист)
- [ ] Роли `Administrator` существуют в security-сервисе Arsenal и доступны для проверки при приёме запроса.
- [ ] Конфиги: таймаут 5s настроен в клиентской библиотеке фундамента; кэш 30s настроен в Arsenal Backend.
- [ ] Мониторинг: алерты на 5xx и `is_available: false` в течение > 5 минут.
- [ ] Логирование: каждый запрос INT-0/INT-1 логируется с role, is_available, duration.
- [ ] Фиче-флагов нет; развёртывание условное не требуется.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано администратора в админке, когда страница загрузилась, тогда `/activity/current-count` вернул `{ count: N, is_available: true }` и счётчик показывает N |
| FR-2 | INT-0 (polling) | Дано администратора с открытой админкой, когда активность изменилась и прошло 30–60с опроса INT-0, тогда новое значение count появилось в счётчике |
| FR-3 | INT-1 | Дано счётчика в шапке, когда администратор кликает, тогда запрос INT-1 с period=day за сегодня вернул массив aggregates и отрисовался график |
| FR-4 | INT-1 (с параметром period) | Дано открытую модалку с графиком, когда администратор выбирает period=week, тогда новый запрос INT-1 с from/to за неделю вернул другой массив aggregates и график перестроился |
| FR-5 | INT-1 (экспорт) | Дано модалку с выбранным периодом, когда нажимается выгрузка, тогда данные из INT-1 агрегируются, форматируются в CSV/JSON и скачиваются |
