## 1. Обзор изменения

### 1.1. Тип и стороны
**🟢 BE-only.** Фундаментальный слой — узел-фундамент #0 — реализует контракт данных активности, который потребляют несколько дочерних узлов (фронты админки). Сам #0 не содержит пользовательского интерфейса; это чистая реализация общей фиче-логики на стороне серверной части.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | Собирает данные активности, отдаёт контракт; реализует авторизацию | Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел #0 реализует **единый источник данных активности** для всех FR-1…FR-5 (счётчик в шапке, модальное окно с графиком, выгрузка сводки). Данные — текущее число активных пользователей и агрегированная активность за выбранный период. #0 спроектирован один раз и предоставляет контракт всем дочерним узлам неизменным.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → потребители (фронты дочерних узлов)
- **Триггер:** Запрос на текущую активность и/или исторические данные за период
- **Контракт (запрос):** `GET /api/admin/activity/summary`
  - **Параметры запроса:**
    - `period` (обязательный, enum): `current` | `last_hour` | `last_day` | `last_week`
    - Примеры: `?period=current`, `?period=last_day`

- **Контракт (ответ):** Структурированный JSON с данными активности
  - Поля ответа:
    - `current_active_users` (число, null-допустимо): Текущее число активных пользователей. `null` — источник недоступен.
    - `period_aggregates` (объект, может быть пуст): Агрегированные данные за выбранный период.
      - `period` (enum): `current` | `last_hour` | `last_day` | `last_week` — какой период описывает этот блок
      - `total_sessions` (число, ≥0): Всего сессий за период
      - `peak_concurrent` (число, ≥0): Пиковое одновременное число активных
      - `avg_concurrent` (число, ≥0): Среднее число активных за период
      - `data_available` (булев): `true` если есть данные за период, `false` если период не содержит записей
    - `timestamp` (ISO 8601): Время генерации ответа (время серверного момента вычисления)
    - `source_status` (enum): `available` | `unavailable` — статус источника активности
      - `available` — данные собраны полностью, используются свежие данные
      - `unavailable` — источник активности недоступен; в ответе `null` вместо значений, данные не кэшированы из прошлого

- **Пример запроса:** `GET /api/admin/activity/summary?period=last_day`
  - Тело отсутствует

- **Пример ответа (успех, источник доступен, есть данные):**
  ```json
  {
    "current_active_users": 42,
    "period_aggregates": {
      "period": "last_day",
      "total_sessions": 1247,
      "peak_concurrent": 58,
      "avg_concurrent": 35,
      "data_available": true
    },
    "timestamp": "2026-07-26T14:30:00Z",
    "source_status": "available"
  }
  ```

- **Пример ответа (источник доступен, но за период нет данных):**
  ```json
  {
    "current_active_users": 5,
    "period_aggregates": {
      "period": "last_day",
      "total_sessions": 0,
      "peak_concurrent": 0,
      "avg_concurrent": 0,
      "data_available": false
    },
    "timestamp": "2026-07-26T14:30:00Z",
    "source_status": "available"
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_active_users": null,
    "period_aggregates": {
      "period": "last_day",
      "total_sessions": null,
      "peak_concurrent": null,
      "avg_concurrent": null,
      "data_available": false
    },
    "timestamp": "2026-07-26T14:30:00Z",
    "source_status": "unavailable"
  }
  ```

- **Ошибки:**
  - `401 Unauthorized` — клиент не авторизован или токен истёк
  - `403 Forbidden` — авторизован, но роль не имеет доступа (не Администратор)
  - `400 Bad Request` — параметр `period` некорректен или отсутствует
  - `500 Internal Server Error` — ошибка сервера (источник данных упал или сетевая ошибка)

- **Семантика null и пустых значений:**
  - `current_active_users: null` → источник недоступен; потребитель должен показать «—» или заглушку ошибки
  - `data_available: false` и `total_sessions: 0` → период содержит данные, но за этот конкретный промежуток активности не было; потребитель показывает пустой график
  - Ненулевые числа (0, 1, …) — валидные значения; `0` — не ошибка, это значит, что активности не было, но данные доступны

- **Авторизация:** 🟡 подтверждено аналитиком (не по коду)
  - Требуется роль `Administrator` в системе Arsenal
  - Проверка выполняется на стороне бэка Arsenal (middleware авторизации)
  - Клиент передаёт авторизационный токен в заголовке `Authorization: Bearer <token>`
  - Если роль не `Administrator` → `403 Forbidden`
  - Если токен отсутствует или невалиден → `401 Unauthorized`

- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (счётчик активных), FR-2 (обновление), FR-3 (график), FR-4 (переключение периода), FR-5 (выгрузка)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние потребителя |
|-----|----------------|-------|----------------------|
| 401 | `{"error": "Unauthorized", "message": "Missing or invalid token"}` | Токен отсутствует или истёк | Перенаправить на логин |
| 403 | `{"error": "Forbidden", "message": "Only Administrators can access activity data"}` | Роль не Administrator | Показать «Нет доступа» |
| 400 | `{"error": "Bad Request", "message": "Invalid period parameter"}` | `period` некорректен | Показать ошибку (не должно попасть в UI) |
| 500 | `{"error": "Internal Server Error", "message": "Activity source unavailable"}` | Источник упал / таймаут | Использовать `source_status: unavailable` и показать «—» |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal Backend** реализует INT-0:
- Выставляет эндпоинт `GET /api/admin/activity/summary` с поддержкой параметра `period`
- Собирает данные активности из собственного источника (🟡 подтверждено аналитиком: Arsenal владеет сбором активности, внешних сервисов не привлекаем)
- Выполняет авторизацию: проверка роли `Administrator` перед возвратом данных
- Возвращает контракт с полной семантикой: `source_status` отражает доступность источника, `data_available` отражает наличие данных за период
- **Таймаут:** 5 секунд на операцию получения данных; при таймауте возвращает 500 и `source_status: unavailable`
- **Кэш:** 30 секунд на стороне бэка Arsenal; кэшируется результат полностью (включая `source_status`)

### 3.2. Данные и хранение
🟡 подтверждено аналитиком (не по коду): **новых таблиц не заводим.** Агрегаты активности (счёты за периоды, пики) вычисляются на лету из существующего источника активности пользователей в Arsenal. Существующая логика сбора и хранения активности на стороне Arsenal не меняется.

**Хранение кэша:** Процессовый кэш (in-memory) на стороне бэка Arsenal (🟡 подтверждено аналитиком: кэш 30 сек живёт в самом сервисе Arsenal).

### 3.3. Авторизация/доступ на бэке
- **Точка проверки:** Middleware авторизации перед обработкой запроса к `/api/admin/activity/summary`
- **Проверка:** Клиент должен иметь роль `Administrator`
- **Реализация:** 🟡 подтверждено аналитиком (не по коду) — проверка на стороне бэка Arsenal, встроена в сервис
- **Негативные случаи:**
  - Отсутствует токен → `401 Unauthorized`
  - Токен невалиден/истёк → `401 Unauthorized`
  - Роль не `Administrator` → `403 Forbidden`

## 4. Frontend — ответственность
Не применимо: узел-фундамент #0 не содержит UI. Фронтальные части реализуют дочерние узлы на основе этого контракта.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** 🟡 подтверждено аналитиком — синхронный вызов (request-response)
- **Кэш:** 30 секунд на стороне бэка Arsenal; кэш валиден для всех потребителей
- **Таймаут:** 5 секунд на получение данных от источника; при таймауте возвращается 500 и `source_status: unavailable`
- **Частота обновления:** Определяется потребителями (фронты могут запрашивать как часто нужно); бэк гарантирует, что данные будут новыми не старше 30 сек (кэш) + время запроса
- **Ожидаемая нагрузка:** Запросы от админских интерфейсов, не массовая нагрузка (дочерние узлы определяют частоту)

### 5.2. Надёжность/деградация
- **При недоступности источника:** Возвращается HTTP 500, `source_status: unavailable`, все значения `null`. Не выдаём устаревший кэш.
- **Видимо потребителю:** Потребитель (фронт) видит `source_status: unavailable` и показывает пользователю «—» или сообщение об ошибке источника, а не старые данные.
- **Различие «нет данных» vs. «недоступно»:** Если источник доступен, но период не содержит данных, `data_available: false` и числа = 0, `source_status: available`. Потребитель показывает пустой график. Если источник упал, `source_status: unavailable`, числа = `null` — потребитель показывает ошибку.

### 5.3. Безопасность/доступ (сводно)
| Граница | Проверка | Точка enforcing | Роль | Действие |
|---------|----------|-----------------|------|---------|
| `/api/admin/activity/summary` | Наличие роли `Administrator` | Arsenal backend (middleware) | Administrator | Может читать данные |
| `/api/admin/activity/summary` | Наличие роли `Administrator` | Arsenal backend (middleware) | Оператор, другие | Получит 403 |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟡 подтверждено аналитиком (не по коду): **Фундамент #0 выкатывается раньше потребителей.** После успешного деплоя узла #0 (бэк с контрактом INT-0 готов) дочерние узлы (фронты) могут быть развёрнуты в любом порядке — они будут вызывать стабильный контракт.

### 6.2. Обратная совместимость
Узел #0 — новый контракт. Потребители (дочерние узлы фронтов) будут созданы вместе или после #0, поэтому вопроса обратной совместимости нет. Если позже потребуется расширение контракта (новые поля в `period_aggregates`), они добавляются опционально (не обязательные), чтобы старые потребители игнорировали неизвестные поля.

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком (не по коду): **Фиче-флагов нет.** Контракт #0 и эндпоинт выкатываются атомарно; все потребители его сразу получают после деплоя бэка.

### 6.4. План отката
- **Откат только бэка (Arsenal):** Если бэк откатывается, эндпоинт `/api/admin/activity/summary` вернёт 404 или 500. Дочерние узлы (фронты), уже развёрнутые, будут получать ошибки. Требуется **синхронный откат фронтов** вместе с бэком, либо оставить фронты на версии, которая не вызывает эндпоинт.
- **Откат фронтов после деплоя бэка:** Если бэк уже развёрнут и фронты нужно откатить, бэк продолжит отдавать контракт; фронты просто не будут его вызывать. Безопасно.
- **Миграции:** Не требуются — новых таблиц нет.

### 6.5. Преднастройка до релиза (чек-лист)
- [x] **Роли в системе авторизации:** Роль `Administrator` уже существует в Arsenal (🟡 подтверждено аналитиком). Не требуется создание новых ролей.
- [x] **DDL-миграция:** Не применимо — новых таблиц нет.
- [x] **Конфиги по окружениям:** Таймаут (5 сек) и TTL кэша (30 сек) задаются констант в коде бэка Arsenal. Перед релизом проверить значения в dev/staging/prod.
- [x] **Сервисные аккаунты:** Не применимо — узел #0 не вызывает другие сервисы.
- [x] **Фиче-флаги:** Не требуются.
- [x] **Алерты/мониторинг:** Мониторить HTTP 500 и таймауты на эндпоинте `GET /api/admin/activity/summary`; алерт при превышении % ошибок.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс |
|----------|-------------------|-----------|
| FR-1 (счётчик активных в шапке) | INT-0: `GET /api/admin/activity/summary?period=current` | Дано админ с ролью Administrator, когда запросит текущую активность, тогда получит актуальное число (`current_active_users`) |
| FR-2 (обновление счётчика без перезагрузки) | INT-0: периодические запросы `?period=current` | Дано шапка с счётчиком, когда активность изменилась, тогда счётчик обновляется в пределах 30 сек + таймаут запроса |
| FR-3 (график за период) | INT-0: `GET /api/admin/activity/summary?period=last_hour|last_day|last_week` | Дано открытую модалку, когда запросит агрегаты за период, тогда получит структурированные данные (peaks, averages) |
| FR-4 (переключение периода) | INT-0: параметр `period` с разными значениями | Дано модалку с графиком, когда переключить период, тогда новый запрос INT-0 с новым `period` и график перестраивается |
| FR-5 (выгрузка сводки) | INT-0: `GET /api/admin/activity/summary` для запроса данных перед выгрузкой | Дано модалку с периодом, когда нажать выгрузку, тогда фронт вызывает INT-0, получает сводку и выгружает в файл |

## 8. Допущения и открытые вопросы

**Все технические решения приняты. Спецификация готова к разработке.**

### Подтверждено аналитиком (не по коду)
- Arsenal backend собирает данные активности самостоятельно; внешних сервисов для сбора не привлекаем.
- Проверка роли `Administrator` выполняется на стороне Arsenal backend.
- При недоступности источника отдаём признак `source_status: unavailable` и `null` вместо устаревшего значения.
- Агрегаты активности вычисляются на лету; новых таблиц не заводим.
- Синхронный контракт, кэш 30 секунд в бэке Arsenal, таймаут 5 секунд.
- Фундамент выкатывается раньше потребителей; фиче-флагов нет.

### Унаследовано из БТ (бизнес-пробелы)
- Точный механизм сбора данных активности (какие события считаются активностью, как вычисляются агрегаты) закрепляется на стороне Arsenal; бизнес-слой БТ не специфицирует эти детали. На уровне техспеки это подтвержденный допуск (Arsenal владеет логикой).
