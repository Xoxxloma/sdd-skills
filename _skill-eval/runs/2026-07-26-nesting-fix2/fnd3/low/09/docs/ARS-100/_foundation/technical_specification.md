## 1. Обзор изменения

### 1.1. Тип и стороны
🟢 **BE-only.** Узел-фундамент #0 — это бэк-сервис, который предоставляет унифицированный контракт данных активности пользователей. Фронтенды-потребители (дочерние узлы ARS-101, ARS-102, ARS-103) независимо опираются на этот контракт для отображения счётчика, графиков и выгрузок.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| «Арсенал» (бэк) | Источник данных активности; предоставляет контракт | Тимлид Arsenal-Core | 🟡 подтверждено аналитиком (не по коду) |
| Фронтенды дочерних узлов (ARS-101, -102, -103) | Потребители контракта | (тимлиды детских фронтов) | 🟢 проектируется |

### 1.3. Связь с бизнес-требованиями
Этот фундамент обслуживает FR-1…FR-5 эпика в части данных активности: текущее число активных пользователей (FR-1, FR-2) и агрегированная активность за выбранный период (FR-3, FR-4, FR-5).

## 2. Взаимодействия (ядро)

### INT-0. Запрос текущей активности и агрегатов за период — 🟢 (фундамент, наследуется детьми)

**Граница/направление:** Бэк «Арсенал» → фронтенды-потребители (дочерние узлы)

**Триггер:**
- Загрузка страницы/модального окна администратором.
- Переключение периода в модальном окне.
- Автоматическое обновление счётчика (раз в 30 секунд по кэшу).

**Контракт (запрос):**

Метод: `GET /api/admin/activity-summary` (концептуально; стек-агностично)

Параметры запроса:
- `period_start` (ISO 8601 datetime, обязательный): начало выбранного периода для агрегатов (напр. `2024-12-01T00:00:00Z`).
- `period_end` (ISO 8601 datetime, обязательный): конец периода (напр. `2024-12-31T23:59:59Z`).
- `granularity` (enum: `hour` | `day` | `week`, опциональный, по умолчанию `day`): уровень детализации агрегатов для графика.

**Контракт (ответ):**

Поля ответа:
- `current_active_count` (int ≥ 0 | null): число активных пользователей в данный момент. `null` → источник недоступен (см. ниже ошибки).
- `period_total` (int ≥ 0 | null): общее число уникальных пользователей, активных за выбранный период. `null` → источник недоступен или нет данных.
- `period_has_data` (bool): `true` если за период есть какие-то записи; `false` если период пуст по данным.
- `aggregates` (array | null): массив агрегатов по периодам времени (часам / дням / неделям в зависимости от `granularity`).
  - Каждый элемент: `{ "timestamp": "2024-12-01T00:00:00Z", "active_count": <int ≥ 0> }`.
  - `null` → источник недоступен (не отдаём пустой массив, а `null`, чтобы фронт мог различить «недоступно» от «нет данных»).
- `data_source_available` (bool): `true` если источник активности доступен и данные свежие; `false` если источник недоступен.
- `cache_timestamp` (ISO 8601 datetime): момент, когда данные были закэшированы на бэке (для отладки и UX).

**Пример запроса:**
```
GET /api/admin/activity-summary?period_start=2024-12-01T00:00:00Z&period_end=2024-12-31T23:59:59Z&granularity=day
```

**Пример ответа (успех, источник доступен, период с данными):**
```json
{
  "current_active_count": 42,
  "period_total": 156,
  "period_has_data": true,
  "aggregates": [
    {
      "timestamp": "2024-12-01T00:00:00Z",
      "active_count": 12
    },
    {
      "timestamp": "2024-12-02T00:00:00Z",
      "active_count": 18
    },
    {
      "timestamp": "2024-12-03T00:00:00Z",
      "active_count": 15
    }
  ],
  "data_source_available": true,
  "cache_timestamp": "2024-12-26T14:30:15Z"
}
```

**Пример ответа (источник недоступен):**
```json
{
  "current_active_count": null,
  "period_total": null,
  "period_has_data": false,
  "aggregates": null,
  "data_source_available": false,
  "cache_timestamp": "2024-12-26T14:30:15Z"
}
```

**Пример ответа (период без данных, источник доступен):**
```json
{
  "current_active_count": 42,
  "period_total": 0,
  "period_has_data": false,
  "aggregates": [],
  "data_source_available": true,
  "cache_timestamp": "2024-12-26T14:30:15Z"
}
```

**Ошибки:**

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 | `{ "error": "invalid_period", "message": "period_start must be before period_end" }` | Некорректный интервал (start ≥ end) | Ошибка валидации (не должна попасть в UI, но если попала — сообщение об ошибке + retry) |
| 403 | `{ "error": "forbidden", "message": "Only administrators can access activity data" }` | Пользователь не в роли «Администратор» | «Нет доступа» |
| 408 | `{ "error": "timeout", "message": "Request to activity data source timed out" }` | Таймаут 5 сек при запросе к источнику | `error_source` (см. §4.3) — сообщение об ошибке + retry |
| 500 | `{ "error": "internal_error", "message": "Failed to fetch activity data" }` | Внутренняя ошибка бэка | `error_source` — сообщение об ошибке + retry |

**Семантика `null` и различие ошибок:**
- `current_active_count: null` и `data_source_available: false` → **источник недоступен**, фронт показывает «—» / пустой график и сообщение типа «Данные недоступны, проверьте соединение».
- `period_total: 0`, `period_has_data: false`, `aggregates: []` (при `data_source_available: true`) → **за период нет данных** (но источник работает), фронт показывает «—» / пустой график с пояснением «За этот период нет записей о активности».
- HTTP коды 403, 408, 500 → ошибки, фронт отображает соответствующее состояние (см. §5.3 ниже).

**Авторизация:**

- **Граница:** проверка выполняется на бэке «Арсенала» (BE-only).
- **Кто вправе:** только пользователи с ролью «Администратор» (подтверждено аналитиком из ролевой модели БТ).
- **Где enforced:** при обработке запроса к `/api/admin/activity-summary` бэк проверяет наличие роли в контексте запроса; если её нет → HTTP 403.
- **Негативный случай:** пользователь с ролью «Оператор» или иной, не-«Администратор» получает 403 при любом запросе к этому эндпоинту.

**Происхождение:** 🟢 новое (узел-фундамент #0)

**Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (все требуют данных активности)

## 3. Backend — ответственность

### 3.1. По сервисам

**«Арсенал» (бэк):**
- 🟢 Реализует INT-0: эндпоинт `/api/admin/activity-summary`, который:
  - Принимает параметры периода и детализации.
  - Проверяет авторизацию (роль «Администратор»).
  - Собирает текущее число активных пользователей.
  - Вычисляет агрегаты активности за период (на основе существующих данных; см. §3.2).
  - Возвращает контракт INT-0 с соответствующей семантикой `null` и флагами доступности.
  - Кэширует результат на 30 секунд (см. §5.1).
  - Обрабатывает таймауты и недоступность источника (см. §5.2).

### 3.2. Данные и хранение

🟡 **Подтверждено аналитиком (не по коду):** Данные активности пользователей собираются бэком «Арсенала» из существующего источника (механика источника — за границей этого фундамента). Новых таблиц под агрегаты создавать не нужно; агрегаты вычисляются на лету.

- **Что не меняется:** отсутствуют новые сущности и таблицы.
- **Что подлежит валидации:** точный источник данных активности и механика его запроса (будет уточнено при интеграции).

### 3.3. Авторизация/доступ на бэке

🟢 Контроль доступа к `/api/admin/activity-summary`:
- На входе эндпоинта проверяется наличие роли «Администратор» в контексте авторизации запроса (token / сессия / иное).
- Если роль отсутствует → возвращается HTTP 403 с сообщением `{ "error": "forbidden", "message": "Only administrators can access activity data" }`.
- Никаких других ролевых проверок для этого контракта нет; доступ открыт всем администраторам.

## 4. Frontend — ответственность

Фронтенды-потребители (дочерние узлы) используют INT-0 для:
- Отображения счётчика активных пользователей (FR-1, FR-2).
- Построения графика активности за выбранный период (FR-3, FR-4).
- Подготовки данных для выгрузки сводки (FR-5).

Каждый фронт-ребёнок проектирует свои UI-состояния и сценарии, опираясь на поля контракта INT-0.

### 4.3. Состояния (именованные)

Фронтенды должны различать следующие состояния при обработке INT-0 (рекомендуемая таблица; финальное оформление — на стороне каждого ребёнка):

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | запрос к INT-0 в полёте | спиннер / скелетон |
| `value` | 2xx, `data_source_available: true`, `current_active_count ≠ null`, `current_active_count > 0` | число активных пользователей |
| `zero` | 2xx, `data_source_available: true`, `current_active_count = 0` (валидный ноль) | «0» (не «—») |
| `empty` | 2xx, `data_source_available: true`, `period_has_data: false` (для периода/графика) | «—» / «нет данных за период» |
| `error_source` | 408 / 500 / 5xx / таймаут / сетевая ошибка | сообщение об ошибке + кнопка retry |
| `error_forbidden` | 403 | «Нет доступа» (обычно не должна возникнуть при корректной авторизации) |
| `error_unavailable` | 2xx, но `data_source_available: false` | «Данные недоступны» (в отличие от state_source — это не ошибка, а состояние, когда источник недоступен, но эндпоинт отозвался) |

Фронты должны явно различать `error_source` (источник недоступен, сеть/таймаут) и `error_unavailable` (источник сообщил, что недоступен), так как UX-подсказки могут отличаться.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

🟡 **Подтверждено аналитиком (не по коду):**
- **Синхронность:** запрос к INT-0 обрабатывается синхронно (нет очередей, событий; прямой вызов).
- **Кэш:** на бэке «Арсенала» результат INT-0 кэшируется на **30 секунд**. Каждый запрос внутри окна 30 сек возвращает закэшированное значение (field `cache_timestamp` указывает момент кэширования).
- **Таймаут:** максимальное время ожидания ответа от источника активности — **5 секунд**. По истечении → HTTP 408, тело `{ "error": "timeout", ... }`.
- **Нагрузка:** точный объём запросов неизвестен; кэш на 30 сек рассчитан на умеренную нагрузку (заказчик открывает админку несколько раз в день). При масштабировании — тема для мониторинга.

### 5.2. Надёжность/деградация

🟡 **Подтверждено аналитиком (не по коду):**
- **При недоступности источника активности:** эндпоинт возвращает 2xx с `data_source_available: false`, `current_active_count: null`, `aggregates: null`. **Не** отдаётся устаревшее значение.
- **Различие:** фронт явно видит, что источник недоступен, и может выбрать UX (пусто-графика, пояснение в UI).
- **Таймаут источника:** если запрос к источнику превышает 5 сек → HTTP 408, фронт видит ошибку и предлагает retry.

### 5.3. Безопасность/доступ (сводно)

| Участник | Действие | Результат |
|----------|----------|-----------|
| Администратор | Запрос INT-0 | HTTP 200, данные |
| Оператор / иная роль | Запрос INT-0 | HTTP 403 |
| Неавторизованный пользователь | Запрос INT-0 | HTTP 403 |

3. Выкат дочерних фронтов (ARS-101, ARS-102, ARS-103) в любом порядке; они опираются на готовый INT-0.

### 6.2. Обратная совместимость

🟡 **Подтверждено аналитиком (не по коду):** фиче-флаги НЕ используются. Фундамент выкатывается атомарно и доступен всем администраторам без переключений.

- [x] Кэш на 30 сек: конфигурируется в коде бэка или конфигах.

- [x] Алерты на ошибки: рекомендуется мониторить HTTP 408 и 500 на `/api/admin/activity-summary`.

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано администратор открыл админку, когда страница загрузилась и бэк ответил с `current_active_count`, тогда счётчик отображает число активных пользователей. |
| FR-2 | INT-0 | Дано счётчик отображается, когда `current_active_count` изменился на бэке (кэш истёк или выслан новый запрос), тогда значение счётчика обновляется без перезагрузки в пределах минуты (30-сек кэш + запрос). |
| FR-3 | INT-0 | Дано счётчик видна в шапке, когда администратор кликает по счётчику, тогда фронт запрашивает INT-0 с периодом по умолчанию и открывает модалку с графиком. |
| FR-4 | INT-0 | Дано модалка открыта, когда администратор выбирает другой период (start/end), тогда фронт запрашивает INT-0 с новыми параметрами и график перестраивается. |
| FR-5 | INT-0 | Дано модалка с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт подготавливает файл на основе данных INT-0 (поле `aggregates` и `period_total`). |
