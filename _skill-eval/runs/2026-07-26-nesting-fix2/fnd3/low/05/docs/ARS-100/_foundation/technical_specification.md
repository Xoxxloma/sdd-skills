## 1. Обзор изменения

### 1.1. Тип и стороны
BE-only. Узел-фундамент #0 — чистая реализация слоя получения и агрегирования данных активности пользователей. Фундамент обслуживает контракты, которые потребляют дочерние узлы (фронт-панели, экспорт сводки, обновление счётчика). На границе: фронты детских фич ↔ бэк Арсенала.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Бэк Арсенала | Реализует контракты активности, собирает и агрегирует данные | Команда Арсенал-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Фундамент реализует общий слой получения данных активности (текущее число + агрегаты за период), на который опираются все три дочерние фичи: счётчик в шапке (FR-1, FR-2), график в модалке (FR-3, FR-4) и выгрузка сводки (FR-5).

## 2. Взаимодействия (ядро)

### INT-1. Текущее число активных пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Детский фронт → Бэк Арсенала
- **Триггер:** Загрузка страницы админки; периодический опрос детским фронтом (интервал = частность обновления счётчика, зависит от реализации FR-2)
- **Контракт (запрос):** GET `/api/arsenal/activity/current` — без параметров и тела
- **Контракт (ответ):**
  - `count` (number | null): текущее число активных пользователей. Семантика: `null` = источник недоступен (не устаревшее значение, а отсутствие данных); 0 = валидный ноль (активных нет)
  - `timestamp` (ISO 8601): момент, на который указан `count`
  - `available` (boolean): `true` = данные актуальны (источник доступен); `false` = источник недоступен
  - `lastUpdated` (ISO 8601): последняя успешная выборка данных из источника
- **Пример запроса:** Тело отсутствует; GET-запрос без параметров
- **Пример ответа (успех):**
  ```json
  {
    "count": 247,
    "timestamp": "2026-07-26T14:32:15Z",
    "available": true,
    "lastUpdated": "2026-07-26T14:32:15Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null,
    "timestamp": "2026-07-26T14:32:15Z",
    "available": false,
    "lastUpdated": "2026-07-26T14:30:00Z"
  }
  ```
- **Ошибки:**
  - 401: Unauthorized — клиент не авторизован → дочерний фронт показывает «нет доступа»
  - 403: Forbidden — роль не Администратор → дочерний фронт скрывает панель
  - 500: Internal Server Error — ошибка на бэке Арсенала → дочерний фронт показывает «ошибка при получении данных» + retry
  - Таймаут (> 5с) — не отвечает за 5 секунд → дочерний фронт показывает «ошибка соединения» + retry
- **Состояния UI по ответу (маппинг для дочерних фронтов):**
  - `value` — `available=true`, `count` ≠ null и ≥ 0 → отобразить число
  - `zero` — `available=true`, `count = 0` → отобразить «0» (не прочерк)
  - `error_source` — `available=false` → отобразить «—» (прочерк) или «данные недоступны»
  - `error_forbidden` — 403 Forbidden → скрыть панель или показать «нет доступа»
  - `error_network` — таймаут, 5xx → показать сообщение об ошибке с кнопкой retry
- **Авторизация:** Доступен только ролям Администратор. Проверка на бэке Арсенала (по токену/сессии). При отсутствии прав — 403 Forbidden.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2 (источник данных счётчика активности)

### INT-2. Агрегаты активности за период — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Детский фронт → Бэк Арсенала
- **Триггер:** Открытие модального окна или переключение периода графика; возможна загрузка предыдущих периодов при листании истории
- **Контракт (запрос):** GET `/api/arsenal/activity/aggregates?period=<PERIOD>&start=<START>&end=<END>`
  - `period` (enum: "hour" | "day" | "week"): детальность агрегата. Определяет размер интервала на диаграмме. Обязателен.
  - `start` (ISO 8601): начало диапазона (включительно). Обязателен.
  - `end` (ISO 8601): конец диапазона (включительно). Обязателен.
  - Ограничения: `end - start` не должен превышать 90 дней; детальность `hour` не применима к интервалам > 7 дней (если больше → ошибка 400 или нормализация с предупреждением). 🟡 к валидации: точное поведение при нарушении.
- **Контракт (ответ):**
  - `period` (enum: "hour" | "day" | "week"): отражает запрошенный период
  - `start` (ISO 8601): начало диапазона ответа (может отличаться от запроса, если он был нормализован)
  - `end` (ISO 8601): конец диапазона ответа
  - `available` (boolean): `true` = есть данные за диапазон; `false` = источник недоступен
  - `dataPoints` (array): массив временных срезов активности. Пусто, если нет данных или источник недоступен.
    - `timestamp` (ISO 8601): момент среза
    - `activeUsers` (number): количество активных пользователей на этот момент (≥ 0)
    - `interval` (enum: "hour" | "day" | "week"): совпадает с `period`
  - `metadata` (object):
    - `calculationTime` (number): время расчёта агрегата в миллисекундах
    - `pointsCount` (number): количество точек в `dataPoints`
    - `lastUpdated` (ISO 8601): последняя успешная выборка данных из источника
  - Семантика:
    - `available=true, dataPoints.length > 0` = есть данные за период → отобразить график
    - `available=true, dataPoints.length = 0` = данные пусты (за период активности не было) → отобразить пустой график или «нет активности»
    - `available=false` = источник данных недоступен → отобразить ошибку (прочерк) вместо графика
- **Пример запроса:** GET `/api/arsenal/activity/aggregates?period=day&start=2026-07-20T00:00:00Z&end=2026-07-26T23:59:59Z`
- **Пример ответа (данные есть):**
  ```json

    "start": "2026-07-20T00:00:00Z",
    "end": "2026-07-26T23:59:59Z",
    "available": true,

        "activeUsers": 145,
        "interval": "day"

      {
        "timestamp": "2026-07-22T00:00:00Z",
        "activeUsers": 0,
        "interval": "day"

      {
        "timestamp": "2026-07-23T00:00:00Z",
        "activeUsers": 89,

      {
        "timestamp": "2026-07-24T00:00:00Z",
  ```

- **Пример ответа (период пустой, но источник доступен):**
  ```json

    "start": "2026-06-01T00:00:00Z",
  ```

- **Пример ответа (источник недоступен):**
  ```json

    "start": "2026-07-20T00:00:00Z",
    "end": "2026-07-26T23:59:59Z",
    "available": false,

    "metadata": {
      "calculationTime": 0,
      "pointsCount": 0,
      "lastUpdated": "2026-07-26T14:15:00Z"
  ```

- **Ошибки:**
  - 400 Bad Request: неверные параметры (например, некорректная дата, end < start, некорректный enum) → вернуть ошибку с описанием
  - 401 Unauthorized: клиент не авторизован

  - 500 Internal Server Error: ошибка на бэке Арсенала
  - Таймаут (> 5с): не отвечает за 5 секунд
- **Состояния UI по ответу (маппинг для дочерних фронтов):**
  - `value` — `available=true`, `dataPoints.length > 0` → отобразить график с точками

  - `error_source` — `available=false` или таймаут, 5xx → отобразить прочерк или «данные недоступны» вместо графика

  - `error_network` — таймаут → показать сообщение об ошибке с retry
- **Авторизация:** Доступен только ролям Администратор. Проверка на бэке Арсенала. При отсутствии прав — 403 Forbidden.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3, FR-4, FR-5 (источник данных графика и выгрузки)

## 3. Backend — ответственность

### 3.1. По сервисам
**Бэк Арсенала:**
- Реализует INT-1 (GET `/api/arsenal/activity/current`) — отдаёт текущее число активных пользователей.
- Реализует INT-2 (GET `/api/arsenal/activity/aggregates`) — отдаёт агрегаты активности за период.
- Собирает данные активности пользователей из собственных таблиц (🟡 подтверждено аналитиком: Арсенал владеет этими данными, не полагается на внешние сервисы).
- Вычисляет агрегаты (count, timeline) на лету на каждый запрос (не заводит отдельные таблицы агрегатов).

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: Никаких новых таблиц не заводится. Данные активности пользователей уже существуют в базе Арсенала; фундамент #0 реализует слой чтения и агрегирования.

**Концептуально:**
- Источник данных: существующие таблицы сессий/активности в БД Арсенала (имя и структура — 🟡 к валидации при интеграции).
- Агрегирование: на лету по запросу, группировка по периодам (час / день / неделя).
- Миграции: не требуются.

### 3.3. Авторизация/доступ на бэке
- INT-1 и INT-2 доступны только ролям Администратор.
- Проверка ролей: на бэке Арсенала при обработке запроса (по токену/сессии/заголовкам контекста).
- Негативный случай: если роль ≠ Администратор → 403 Forbidden.
- 🟡 подтверждено аналитиком: роль «Администратор» уже существует в security-модели Арсенала; фундамент проверяет её при каждом вызове.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Три компонента (дочерние фичи) будут потреблять данные из INT-1 и INT-2:
- **Счётчик в шапке (FR-1, FR-2):** вызывает INT-1 периодически → показывает текущее число или прочерк/ошибку.
- **График в модалке (FR-3, FR-4):** вызывает INT-2 с периодом и диапазоном дат → отрисовывает линейную диаграмму.
- **Выгрузка сводки (FR-5):** использует данные из INT-2, форматирует в файл (CSV/Excel).

Фундамент #0 не отвечает за UI-компоненты (это забота дочерних узлов). #0 определяет только контракты на границе.

### 4.2. Пользовательские сценарии
Сценарии находятся в компетенции дочерних узлов (счётчик, график, выгрузка). Фундамент обеспечивает данные для этих сценариев.

### 4.3. Состояния (именованные)
Дочерние фронты должны различать эти состояния при обработке ответов INT-1 и INT-2:

| Имя состояния | Условие | Маппинг из контракта |
|---------------|---------|----------------------|
| `loading` | первый запрос / после инвалидации | показать спиннер, пока INT-1/INT-2 загружаются |
| `value` | INT-1: `available=true, count ≠ null, count ≥ 0` | отобразить число активных |
| `zero` | INT-1: `available=true, count = 0` | отобразить «0» (не прочерк) |
| `empty` | INT-2: `available=true, dataPoints.length = 0` | отобразить график пустым или текст «нет активности» |
| `error_source` | `available=false` или таймаут/5xx | отобразить «—» (прочерк) или «данные недоступны» + retry |
| `error_forbidden` | 403 Forbidden | скрыть панель или показать «нет доступа» (в зависимости от role checking) |
| `error_network` | таймаут, сетевая ошибка | показать «ошибка соединения» + retry кнопка |

### 4.3.1. Loading и таймауты
- **Cold-path (первый запрос):** таймаут = 5 секунд. Если за это время не пришёл ответ → показать ошибку соединения и retry.
- **Warm-path (периодические или повторные запросы):** таймаут = 5 секунд (один и тот же, без различий).
- **Polling для INT-1:** интервал определяет дочерний фронт (согласно FR-2 — обновление «в пределах минуты»), но не превышает 30 секунд на стороне бэка (см. §5.1).
- **Jitter:** рекомендуется для polling'а на стороне фронта, чтобы избежать synchronized thundering (все клиенты не бьют одновременно).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** INT-1 и INT-2 отдаются синхронно (не через очереди / события).
- **Кэш:** на стороне бэка Арсенала, TTL = 30 секунд. 🟡 подтверждено аналитиком: данные в кэше инвалидируются каждые 30с, свежие данные перечитываются из БД.
- **Таймаут запроса:** 5 секунд. Если запрос к бэку занимает > 5с → дочерний фронт получает таймаут и показывает ошибку соединения.
- **Частота опроса (polling):** FR-2 требует обновления счётчика «в пределах минуты», поэтому дочерний фронт может опрашивать INT-1 не чаще чем раз в 30 секунд (согласуется с TTL кэша).
- **Нагрузка:** ожидается, что много дочерних фронтов (разные страницы админки, разные администраторы) будут периодически вызывать INT-1/INT-2. Кэш на 30с помогает амортизировать нагрузку на БД.

### 5.2. Надёжность/деградация
- **Недоступность источника (БД, сервис):** вместо устаревшего значения отдаём признак недоступности: `available=false`, `count=null` в INT-1 или пустой `dataPoints` в INT-2. Дочерний фронт показывает пустой график или прочерк.
- **Различие между «нет данных за период» и «источник недоступен»:** INT-2 разводит через `available` флаг:
  - `available=true, dataPoints.length=0` — за этот период активности не было (валидный 0).
  - `available=false` — источник недоступен, мы не знаем, есть ли данные.
  - Дочерний фронт разводит состояния `empty` и `error_source`.

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто | Может | Проверка |
|---------|-----|-------|----------|
| INT-1 (бэк Арсенала ← фронт) | Администратор | GET `/api/arsenal/activity/current` | Роль в токене/сессии на бэке |
| INT-1 | Оператор или другая роль | — | 403 Forbidden |
| INT-2 (бэк Арсенала ← фронт) | Администратор | GET `/api/arsenal/activity/aggregates` | Роль в токене/сессии на бэке |
| INT-2 | Оператор или другая роль | — | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката
1. **Фундамент #0 (бэк Арсенала):** реализует INT-1 и INT-2, включает кэш, проверки ролей. Выкатывается **первым**.
2. **Дочерние узлы (фронты):** счётчик, график, выгрузка — выкатываются **после** #0. Они потребляют контракты #0 без изменений.

**Обоснование:** дочерние фронты полагаются на контракты #0; если #0 не выкачен, дочерние фронты не смогут сделать запросы.

### 6.2. Обратная совместимость
- Нового кода на текущих потребителей нет (это новые эндпоинты).
- При откате #0 (удаление INT-1/INT-2) → дочерние фронты получат 404 и должны обработать это как `error_source` состояние.

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: фиче-флаги не используются. Релизим атомарно — #0 выкатывается целиком с обоими эндпоинтами.

### 6.4. План отката
- **Откат только #0 (бэк):** INT-1/INT-2 становятся недоступны (404 или 503 на все запросы) → дочерние фронты показывают `error_source` состояние (прочерк, ошибка соединения). Пользователь видит панель активности неработающей, но админка в целом остаётся доступна.
- **Откат только фронта (дочернего узла):** #0 остаётся работающим, но если ребёнок был выкачен и откачен — его вызовы INT-1/INT-2 прекращаются. Данные на бэке не теряются.
- **Откат DDL:** не требуется (новых таблиц нет).

### 6.5. Преднастройка до релиза
- [ ] Роли в security-сервисе — роль «Администратор» уже существует (🟡 подтверждено аналитиком), нет новых ролей.
- [ ] DDL-миграция в репо Арсенала — не требуется (новых таблиц нет).
- [ ] Конфиги по окружениям (dev/staging/prod) — параметры кэша (TTL=30с, таймаут=5с) должны быть настроены одинаково или согласованы.
- [ ] Сервисные аккаунты — не требуется (INT-1/INT-2 обращаются к Арсеналу же).
- [ ] Фиче-флаги — не требуется (релизим без флагов).
- [ ] Алерты/мониторинг — рекомендуется отслеживать:
  - Доля 5xx ошибок на INT-1/INT-2
  - Доля 403 (возможное падение ролевых правил)
  - Доля таймаутов (> 5с)
  - Перцентили latency (p50, p95, p99) для гарантии 5с таймаута

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано открытую админку на странице, когда страница загрузилась и запрос INT-1 вернул `available=true, count=42`, тогда в шапке видно число 42 |
| FR-2 | INT-1 (polling) | Дано открытую админку, когда число активных пользователей изменилось (INT-1 вернул новое значение), тогда счётчик обновляется в пределах 30с (согласно периодичности opoll'а и кэша) без перезагрузки страницы |
| FR-3 | INT-2 | Дано открытую админку со счётчиком, когда администратор кликает на счётчик и открывается модалка, тогда выполняется запрос INT-2 с периодом по умолчанию (напр. `period=day`) и отрисовывается график активности |
| FR-4 | INT-2 (период) | Дано открытую модалку с графиком, когда администратор переключает период (на другой день, неделю и т.п.), тогда выполняется новый запрос INT-2 с изменённым периодом и график перестраивается |
| FR-5 | INT-2 (выгрузка) | Дано открытую модалку с выбранным периодом (INT-2 загрузил данные), когда администратор нажимает кнопку выгрузки, тогда данные из INT-2 форматируются в CSV/Excel и скачиваются файл со сводкой активности за этот период |

## 8. Допущения и открытые вопросы

**Все технические решения приняты, спецификация готова к разработке.**

### Подтверждено аналитиком (не по коду)
- Арсенал владеет данными активности пользователей; чужих сервисов не привлекаем.
- Роль «Администратор» уже существует в security-модели.
- Кэш 30 секунд на стороне бэка Арсенала.
- При недоступности источника — отдаём признак недоступности, а не устаревшее значение.
- Различаем «данных за период нет» (валидный 0) и «источник недоступен».
- Синхронные ответы, таймаут 5 секунд.

### Приложения из БТ
- Пожелание по UX (счётчик неяркий) — реализуется на уровне дочерних узлов (стилизация компонентов), не влияет на контракт #0.
