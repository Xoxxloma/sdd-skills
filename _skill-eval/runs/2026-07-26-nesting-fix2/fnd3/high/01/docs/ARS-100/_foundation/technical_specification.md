## 1. Обзор изменения

### 1.1. Тип и стороны

🟢 **BE-only** (бэк-only). Узел-фундамент #0 спроектирован как контракт данных активности пользователей (поставляет).
Потребители контракта (дочерние фронты админки) реализуются отдельно, наследуя этот контракт без изменений.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Сбор и агрегация данных активности; отдача контракта данных | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Узел-фундамент #0 обслуживает общую часть FR-1..FR-5 эпика (бизнес-контекст § 1.1 БТ): 
данные об активности пользователей (текущее число + агрегированная активность за период). 
Все три UI-элемента (счётчик в шапке, график в модали, экспорт) опираются на один контракт.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Дочерние фронты админки (наследуют контракт)

- **Триггер:** Инициируется дочерним фронтом для:
  - загрузки текущего счёта активных пользователей (FR-1);
  - загрузки агрегированных данных активности за выбранный период для графика (FR-3, FR-4);
  - выгрузки сводки данных (FR-5).

- **Контракт (запрос):** 

  ```
  GET /api/arsenal/activity
  
  Query parameters (все опциональны):
  - period: string — "current" | "hour" | "day" | "week" (по умолчанию: "current")
  - timestamp_from: ISO 8601 string — начало пользовательского диапазона (опционально)
  - timestamp_to: ISO 8601 string — конец пользовательского диапазона (опционально)
  ```

- **Контракт (ответ):** 

  | Поле | Тип | Обязательность | Семантика |
  |------|-----|---|---|
  | `current_active_users` | `integer` ≥ 0 | Всегда | Текущее число активных пользователей (обновляется в реальном времени) |
  | `period_type` | `string` | Всегда | Тип запрошенного периода: `"current"` \| `"hour"` \| `"day"` \| `"week"` \| `"custom"` |
  | `aggregated_data` | `array<{timestamp, active_users}>` | Если есть данные | Массив данных активности за период: каждая точка содержит timestamp (ISO 8601) и count (integer ≥ 0). Пуст (`[]`), если нет данных за период, но источник доступен. |
  | `is_available` | `boolean` | Всегда | `true` = источник данных доступен; `false` = источник недоступен (сеть, таймаут, 5xx) |
  | `has_data_for_period` | `boolean` | Если `is_available=true` | `true` = есть данные за выбранный период; `false` = данных за период нет, но источник доступен. Поле присутствует ТОЛЬКО при `is_available=true` |
  | `updated_at` | ISO 8601 string | Если `is_available=true` | Момент последнего обновления данных в Arsenal Backend |

- **Пример запроса:** 
  ```
  GET /api/arsenal/activity?period=day
  ```

- **Пример ответа (успех — есть данные за день):**
  ```json
  {
    "current_active_users": 42,
    "period_type": "day",
    "aggregated_data": [
      { "timestamp": "2026-07-26T00:00:00Z", "active_users": 15 },
      { "timestamp": "2026-07-26T06:00:00Z", "active_users": 8 },
      { "timestamp": "2026-07-26T12:00:00Z", "active_users": 35 },
      { "timestamp": "2026-07-26T18:00:00Z", "active_users": 42 }
    ],
    "is_available": true,
    "has_data_for_period": true,
    "updated_at": "2026-07-26T23:45:30Z"
  }
  ```

- **Пример ответа (успех — нет данных за период, но источник доступен):**
  ```json
  {
    "current_active_users": 42,
    "period_type": "week",
    "aggregated_data": [],
    "is_available": true,
    "has_data_for_period": false,
    "updated_at": "2026-07-26T23:45:30Z"
  }
  ```

- **Пример ответа (ошибка — источник недоступен):**
  ```json
  {
    "current_active_users": null,
    "period_type": "day",
    "aggregated_data": null,
    "is_available": false
  }
  ```
  *(Поля `has_data_for_period` и `updated_at` отсутствуют при `is_available=false`)*

- **Ошибки:**

  | Код | Сценарий | Сообщение / тело | Действие фронта |
  |-----|----------|-----------------|--|
  | `200` | Успех (данные доступны) | `is_available=true` + данные | Использовать как есть |
  | `200` | Данные недоступны (источник упал) | `is_available=false`, остальные поля: `null` | Показать состояние `error_source` |
  | `403` | Нет доступа (не роль Администратор) | `{ "error": "Forbidden", "message": "Only Administrator role can access activity data" }` | Показать состояние `error_forbidden` |
  | `408` | Таймаут на стороне бэка (5s) | `{ "error": "Request timeout", "message": "Activity data source did not respond within timeout" }` | Показать состояние `error_source` с сообщением таймаута |
  | `5xx` | Ошибка бэка Arsenal | Стандартное 5xx тело | Показать состояние `error_source` |

- **Состояния UI по ответу:**
  - **`loading`** — идёт запрос (холодная дорога в первый раз, горячая дорога при инвалидации)
  - **`value`** — 200, `is_available=true`, `has_data_for_period=true`, `aggregated_data` не пусто → показать данные / график
  - **`zero`** — 200, `is_available=true`, `current_active_users=0` (валидный ноль) → показать «0» (не прочерк)
  - **`empty`** — 200, `is_available=true`, `has_data_for_period=false` (нет данных за период, но источник доступен) → показать «—» / «нет данных за период»
  - **`error_source`** — 5xx, 408, сеть, таймаут, или `is_available=false` (источник данных недоступен) → показать сообщение об ошибке + retry
  - **`error_forbidden`** — 403 (нет роли Администратор) → показать «нет доступа»

- **Авторизация:**
  - **Кто вправе:** Роль `Administrator` в Arsenal (подтверждено аналитиком)
  - **Где проверяется:** 🟡 подтверждено аналитиком — на бэке Arsenal, в процессе обработки запроса к `/api/arsenal/activity`
  - **Негативный случай:** Отсутствие роли → 403 Forbidden

- **Происхождение:** 🟢 новое (узел-фундамент #0, контракт наследуется всеми детьми без изменений)

- **Трассировка:** FR-1 (текущий счёт), FR-2 (обновление счёта), FR-3/FR-4 (данные график), FR-5 (данные для экспорта)

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- Реализует INT-0 (контракт `/api/arsenal/activity`) в соответствии со спецификацией выше
- 🟡 подтверждено аналитиком — собирает данные активности пользователей самостоятельно (источник данных — собственная логика Arsenal, внешних сервисов не привлекаем)
- Отдаёт текущий счёт активных пользователей (`current_active_users`) и агрегированные данные за выбранный период
- Проверяет авторизацию по ролям перед отдачей контракта

### 3.2. Данные и хранение

🟢 Новых таблиц не заводится. Агрегаты активности считаются **на лету** из существующих данных Arsenal (сессии, логи активности и т.п.).

🟡 подтверждено аналитиком — точные источники данных активности в Arsenal (какие таблицы, какие поля) валидируются при интеграции; спека содержит контракт ответа, реализация выбирает источник.

**Индексы:** Если запросы к активности часто фильтруются по временному диапазону — рекомендуется индекс по полям временных меток (точный DDL и выбор индекса — решение arsenalCore).

**Кэш:** 🟡 подтверждено аналитиком — кэш 30 секунд на стороне Arsenal Backend (инвалидация при изменении активности, если трекируется в реальном времени).

### 3.3. Авторизация/доступ на бэке

- 🟡 подтверждено аналитиком — проверка роли `Administrator` на стороне Arsenal Backend (использование существующего механизма ролевого контроля)
- Запрос без роли Администратор → 403 Forbidden
- Ошибка при проверке роли (сервис авторизации недоступен, и т.п.) → 5xx

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Спецификация контракта INT-0 (фундамент) покрывает три компонента, которые разрабатываются дочерними фронтами, наследующими этот контракт:
1. Счётчик в шапке админки (FR-1, FR-2)
2. График активности в модальном окне (FR-3, FR-4)
3. Экспорт сводки активности (FR-5)

Все три вызывают INT-0 с разными параметрами (`period=current` для счётчика, `period=hour/day/week` для графика и экспорта).

### 4.2. Пользовательские сценарии

Основной поток (наследуется дочерними фронтами):
1. Фронт загружает страницу → вызывает INT-0 с `period=current` → показывает текущий счёт в шапке (FR-1)
2. Счёт периодически обновляется без перезагрузки → повторно вызывает INT-0 → обновляет счётчик в пределах 30с (кэш на бэке) + 5s таймаут (FR-2)
3. По клику на счётчик → вызывает INT-0 с `period=day` (по умолчанию) → открывает модалку с графиком (FR-3)
4. В модалке админ выбирает другой период → вызывает INT-0 с новым `period` → график перестраивается (FR-4)
5. По нажатию выгрузки → вызывает INT-0 с текущим `period` → получает агрегированные данные → формирует файл (FR-5)

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---|---|---|
| `loading` | Первый запрос INT-0 / инвалидация счётчика | Спиннер или скелетон вместо счётчика / графика |
| `value` | 200, `is_available=true`, `has_data_for_period=true`, есть данные | Счётчик / график с актуальными данными |
| `zero` | 200, `is_available=true`, `current_active_users=0` | Счётчик отображает «0» (не прочерк) |
| `empty` | 200, `is_available=true`, `has_data_for_period=false` | Счётчик / график отображает «—» или «нет данных за выбранный период» |
| `error_source` | 5xx, 408, таймаут, сеть, или `is_available=false` | Сообщение об ошибке: «Данные об активности временно недоступны. Попробуйте позже.» + кнопка retry |
| `error_forbidden` | 403 (нет роли Администратор) | «Нет доступа. Только администраторы могут просматривать активность.» |

### 4.3.1. Loading и таймауты

- **Таймаут cold-path (первый запрос в сессии):** 5 секунд (определяется бэком Arsenal)
- **Таймаут warm-path (повторные запросы):** 5 секунд (тот же таймаут)
- **Polling (обновление счётчика):** Интервал обновления счётчика на фронте: **60 секунд максимум** (в соответствии с CR-2 БТ: «обновляется без перезагрузки в пределах минуты»). Рекомендуется jitter ±10% для избежания синхронизации множественных клиентов (опция на усмотрение дочерних фронтов).
- **При таймауте / 5xx / сетевой ошибке:** Показать состояние `error_source` с предложением retry.

### 4.4. Доступ по ролям в UI

Счётчик, график и выгрузка видны **только** пользователям с ролью `Administrator` (подтверждено аналитиком). 
Остальным ролям (напр., `Operator` из БТ) эти элементы не отображаются. 
Проверка ролей происходит на фронте после получения 403 от INT-0 или на фронте заранее (по текущему контексту пользователя).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** 🟡 подтверждено аналитиком — **синхронный запрос** (request-response, без событий / очередей)
- **Кэш:** 🟡 подтверждено аналитиком — **30 секунд на стороне Arsenal Backend**; за пределами 30s данные считаются устаревшими и пересчитываются при новом запросе
- **Таймаут:** 🟡 подтверждено аналитиком — **5 секунд** (максимальное время ожидания ответа от источника данных внутри Arsenal)
- **Частота опроса (polling на фронте):** Счётчик обновляется на фронте каждые ~60 секунд (в соответствии с FR-2 и CR-2); граница обновления = 30s кэш + jitter на фронте
- **Ожидаемая нагрузка:** Дочерние фронты определяют свою нагрузку; контракт предусматривает масштабируемость за счёт кэша на бэке

### 5.2. Надёжность/деградация

🟡 подтверждено аналитиком — **При недоступности источника активности (5xx, таймаут, сеть):**
- Отдаём флаг `is_available=false`, остальные поля (`current_active_users`, `aggregated_data` и т.п.) = `null`
- **НЕ отдаём** устаревшее значение из кэша и **НЕ выгадываем**
- Фронт показывает состояние `error_source` пользователю

🟡 подтверждено аналитиком — **Отдельная семантика для «нет данных за период»:**
- Если источник доступен, но за выбранный период данные не собирались → `is_available=true`, `has_data_for_period=false`, `aggregated_data=[]`
- Фронт показывает состояние `empty` (прочерк «—» или «нет данных»)
- Это **не** ошибка, это валидное состояние

### 5.3. Безопасность/доступ (сводно)

| Граница | Роль | Может вызвать? | Может видеть данные? | Примечание |
|---------|------|---|---|---|
| INT-0 (`/api/arsenal/activity`) | Administrator | Да | Да | Подтверждено аналитиком; проверка на бэке Arsenal |
| INT-0 (`/api/arsenal/activity`) | Operator / иные роли | Да (запрос доходит) | Нет, 403 | Возвращает 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟢 **Узел-фундамент #0 выкатывается ПЕРВЫМ, раньше всех дочерних фронтов.**

Последовательность:
1. **Фаза 1:** Arsenal Backend разворачивается с реализацией INT-0 и контракта `/api/arsenal/activity` (узел-фундамент #0)
2. **Фаза 2 и позже:** Дочерние фронты админки разворачиваются, наследуя контракт без изменений, и потребляют INT-0

Причина: дочерние фронты зависят от контракта INT-0 и не могут работать без него; контракт должен быть стабилен на бэке перед разработкой фронтов.

### 6.2. Обратная совместимость

- 🟢 **При добавлении нового поля в ответ INT-0 (будущие версии):** Поле добавляется в схему; фронты, не знающие о нём, игнорируют. Обратная совместимость сохраняется (forward-compatible addition).
- 🟡 подтверждено аналитиком — **При изменении типа или семантики существующего поля:** Требуется координация с дочерними фронтами (это уже требует версионирования контракта или feature flag; решение на уровне policy Arsenal-Core).
- Текущий выпуск: новых полей нет, контракт стабилен.

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком — **Фиче-флагов нет.** Релизим **атомарно**: узел-фундамент #0 выкатывается полностью, дочерние фронты начинают потреблять контракт сразу после развёртывания бэка.

### 6.4. План отката

Откат узла-фундамента #0 (бэка Arsenal с INT-0):
- **Откат только бэка:** Дочерние фронты, находящиеся на продакшене, получат 5xx (Arsenal неживой) → покажут состояние `error_source` пользователям. **Требуется синхронный откат фронтов** (чтобы они не зависали с ошибкой) или быстрое восстановление бэка.
- **Миграция откатана:** Откат затрагивает только код INT-0 на бэке, не затрагивает схему (новых таблиц нет, новых колонок нет) → откат безопасен.

Рекомендация: в случае отката бэка координировать с дочерними фронтами для синхронного отката.

### 6.5. Преднастройка до релиза

- [x] **Роли в security-сервисе:** Роль `Administrator` должна быть учтена в системе авторизации Arsenal (должна существовать; подтверждено аналитиком что существует)
- [x] **DDL-миграция в репо владеющего сервиса:** Не требуется (новых таблиц нет, агрегаты считаются на лету)
- [x] **Конфиги по окружениям (dev/staging/prod):** Кэш TTL 30s и таймаут 5s — переменные окружения или конфиг Arsenal (уточнить при разработке)
- [x] **Сервисные аккаунты для межсервисных вызовов:** Не требуется (фронты вызывают из браузера, аутентифицируются как пользователь)
- [x] **Фиче-флаги заведены:** Не требуется (релизим атомарно)
- [x] **Алерты/мониторинг на ключевые ошибки:** Рекомендуется мониторинг 5xx ошибок INT-0 и таймаутов источника данных

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие | Тест-кейс |
|---|---|---|
| FR-1 | INT-0 с `period=current` | Дано открытую админку, когда бэк отвечает с `is_available=true`, тогда в шапке видно число активных пользователей из `current_active_users` |
| FR-2 | INT-0 (polling, обновление каждые ~60s) | Дано открытую админку, когда число активных изменилось и прошло время обновления (≤60s), тогда счётчик обновляется без перезагрузки |
| FR-3 | INT-0 с `period=day` (или неуказанный, по умолчанию день) | Дано счётчик в шапке, когда администратор кликает, тогда INT-0 вызывается с `period=day` и открывается модалка с графиком |
| FR-4 | INT-0 с динамическим `period` параметром | Дано открытую модалку, когда администратор выбирает другой период, тогда INT-0 вызывается с новым `period` и график перестраивается |
| FR-5 | INT-0 с текущим `period`, преобразование `aggregated_data` в файл | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда INT-0 отдаёт данные и фронт формирует файл экспорта |
