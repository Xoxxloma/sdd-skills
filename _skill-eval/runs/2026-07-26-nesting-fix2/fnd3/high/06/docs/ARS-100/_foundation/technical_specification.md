## 1. Обзор изменения

### 1.1. Тип и стороны
**BE-only.** 🟡 подтверждено аналитиком (не по коду): узел-фундамент #0 — контракт, отдаваемый бэком «Арсенала» трём потребляющим фронтам (дети эпика ARS-100: счётчик в шапке, график активности, выгрузка сводки). Фронты наследуют контракт; бэк обязан исключительно предоставить эндпоинт с данными активности.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (BE) | Поставщик контракта данных активности | Core team | 🟢 новое взаимодействие |

### 1.3. Связь с бизнес-требованиями
Контракт #0 является основой для реализации FR-1..FR-5 (счётчик активных пользователей, график активности за период, выгрузка сводки). Каждый фронт-потребитель будет опираться на этот контракт для получения текущего числа активных пользователей и агрегированной активности за выбранный период.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Потребляющий фронт (дочерний узел) → BE Арсенала
- **Триггер:** Инициализация панели активности (первый запрос); затем периодический запрос по таймеру (polling) или обновление при переключении периода (дочерний узел решает интервал и стратегию)
- **Контракт (запрос):** 
  ```
  GET /api/admin/activity/aggregate?period=<period>
  ```
  Параметры запроса:
  - `period` (обязательный, enum): `hour` | `day` | `week` — выбранный период для агрегации
  - Заголовок `Authorization: Bearer <token>` (стандартный способ, проверка роли на бэке)
  
- **Контракт (ответ):**
  - `current_active` (целое число ≥ 0, может быть null): число активных пользователей в текущий момент
  - `period_start` (строка ISO 8601): начало периода агрегации (UTC)
  - `period_end` (строка ISO 8601): конец периода агрегации (UTC)
  - `aggregates` (массив объектов, не пустой или пусто): агрегированная активность за период
    - каждый объект: `{ "bucket": "<timestamp ISO 8601>", "count": <целое число ≥ 0> }`
    - `bucket` — начало временного интервала (час / день, в зависимости от периода)
    - `count` — число активных пользователей в этот интервал (0 означает валидный ноль, не отсутствие данных)
  - `data_unavailable` (булевский флаг, опционально): `true` если источник недоступен, `false` или отсутствует если данные свежие; **никогда не отдавай устаревшее значение**
  - `message` (строка, опционально): при `data_unavailable: true` — пояснение (напр. "Источник активности недоступен, повторите попытку позже")

- **Пример запроса:**
  ```
  GET /api/admin/activity/aggregate?period=day
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех — данные свежие):**
  ```json
  {
    "current_active": 42,
    "period_start": "2026-07-26T00:00:00Z",
    "period_end": "2026-07-27T00:00:00Z",
    "aggregates": [
      {
        "bucket": "2026-07-26T00:00:00Z",
        "count": 5
      },
      {
        "bucket": "2026-07-26T01:00:00Z",
        "count": 8
      },
      {
        "bucket": "2026-07-26T02:00:00Z",
        "count": 3
      }
    ],
    "data_unavailable": false
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_active": null,
    "period_start": "2026-07-26T00:00:00Z",
    "period_end": "2026-07-27T00:00:00Z",
    "aggregates": [],
    "data_unavailable": true,
    "message": "Источник данных активности недоступен, повторите попытку позже"
  }
  ```

- **Пример ответа (период без данных, но источник доступен):**
  ```json
  {
    "current_active": 0,
    "period_start": "2026-07-20T00:00:00Z",
    "period_end": "2026-07-21T00:00:00Z",
    "aggregates": [],
    "data_unavailable": false
  }
  ```

- **Ошибки:**
  - `400 Bad Request`: неверный параметр `period` (не из enum `hour|day|week`)
    - Тело: `{ "error": "invalid_period", "message": "Period must be one of: hour, day, week" }`
  - `401 Unauthorized`: отсутствует или невалидный токен
    - Тело: `{ "error": "unauthorized", "message": "Authentication required" }`
  - `403 Forbidden`: токен валиден, но роль не "Администратор"
    - Тело: `{ "error": "forbidden", "message": "This resource is available only to administrators" }`
  - `500 Internal Server Error`: ошибка бэка (не сеть, не таймаут)
    - Тело: `{ "error": "internal_error", "message": "Failed to fetch activity data" }`

- **Состояния UI по ответу (стандартная семантика для потребляющего фронта):**
  - **`loading`** → первый запрос или инвалидация; потребитель показывает спиннер/скелетон
  - **`value`** → 2xx, `data_unavailable: false`, `current_active` ≠ null и ≠ 0; потребитель показывает число / график
  - **`zero`** → 2xx, `data_unavailable: false`, `current_active: 0` (валидный ноль); потребитель показывает «0»
  - **`empty`** → 2xx, `data_unavailable: false`, `aggregates: []` (нет данных за период); потребитель показывает «—» или "нет данных"
  - **`error_source`** → 5xx, таймаут (>5с), сетевая ошибка или `data_unavailable: true`; потребитель показывает сообщение об ошибке + кнопку retry
  - **`error_forbidden`** → 403; потребитель показывает «нет доступа»

- **Авторизация:**
  - Проверка на **бэке Арсенала**: токен в заголовке `Authorization` должен соответствовать роли «Администратор»
  - Негативный случай (403): токен валиден, но роль не администратор → эндпоинт отдаёт 403 Forbidden с пояснением
  - Никаких фиче-флагов и доп. проверок: роль «Администратор» → доступен контракт

- **Происхождение:** 🟢 новое (узел-фундамент #0, унаследуется детьми)
- **Трассировка:** FR-1 (счётчик активных), FR-2 (обновление счётчика), FR-3/FR-4 (график активности за период), FR-5 (выгрузка сводки)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI (потребляющий фронт) |
|-----|----------------|-------|-----------------------------------|
| 400 | `invalid_period` | параметр `period` не из перечисления | `error_source` (некорректный запрос от фронта) |
| 401 | `unauthorized` | отсутствует токен или невалидный | `error_source` |
| 403 | `forbidden` | токен валиден, роль ≠ Администратор | `error_forbidden` |
| 500 | `internal_error` | ошибка BE Арсенала | `error_source` |
| таймаут (>5с) | (нет тела) | BE не ответил за 5 секунд | `error_source` |
| сеть | (нет тела) | сетевая ошибка клиента | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам
**Арсенал (BE):**
- Реализует эндпоинт `GET /api/admin/activity/aggregate?period=<period>` 🟢
- Авторизация на маршруте: проверяет роль «Администратор» в токене (заголовок `Authorization`) 🟢
- На каждый запрос:
  1. проверяет роль (403 если не администратор);
  2. валидирует параметр `period`;
  3. источник активности — 🟡 подтверждено аналитиком (не по коду): **бэк Арсенала собирает данные активности сам, внешних сервисов не привлекаем**;
  4. при недоступности источника отдаёт `data_unavailable: true` и пусто-щик aggreyates, а не устаревшее значение;
  5. при наличии данных — вычисляет агрегаты на лету (по buckets: час, день), без новых таблиц;
  6. ответ кэшируется на 30 секунд на стороне Арсенала (одна копия кэша на весь BE, не per-потребитель).

### 3.2. Данные и хранение
**Новых сущностей не создаём.** 🟡 подтверждено аналитиком (не по коду): источник данных активности уже существует в Арсенале; агрегаты вычисляются на лету в памяти, нет новых таблиц, нет миграций.

**Хранение (существующее):** 🟡 подтверждено аналитиком (не по коду); точный путь к таблице активности и её структуру — валидировать при интеграции (не по спеке).

### 3.3. Авторизация/доступ на бэке
- Маршрут `GET /api/admin/activity/aggregate` защищён: обязателен заголовок `Authorization: Bearer <token>`
- Проверка роли: только «Администратор» получает данные; остальные получают 403 Forbidden
- Регистрация ошибок доступа (401, 403) в логах Арсенала для аудита

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** 🟡 подтверждено аналитиком (не по коду): запрос-ответ синхронный, no streaming, no websocket
- **Кэш:** 🟡 подтверждено аналитиком (не по коду): 30-секундный кэш на стороне BE Арсенала (in-memory или Redis, деталь реализации). Кэш сброшенаться одинаково для всех потребителей (нет per-потребителя).
- **Таймаут:** 🟡 подтверждено аналитиком (не по коду): 5 секунд на ответ от BE; если BE не ответил за 5с → потребитель получает таймаут и переводит UI в `error_source`
- **Ожидаемая нагрузка:** порядка 10–100 запросов в минуту (периодический polling от потребителей в админке); точный расчёт нагрузки и scaling — внутри Арсенала

### 5.2. Надёжность/деградация
- При недоступности источника данных активности (сеть, БД, сервис): отдаём `data_unavailable: true` и null/пусто, **не устаревшее значение** 🟡 подтверждено аналитиком (не по коду)
- Потребитель видит ошибку и предлагает retry (в UI)
- Полная недоступность Арсенала (5xx) — потребитель переводит UI в `error_source`

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Как enforced | Ошибка |
|---------|-----------|-------------|--------|
| GET /api/admin/activity/aggregate | Администратор (по роли в токене) | Проверка роли на BE Арсенала | 403 Forbidden для не-администраторов |
| Таймаут | Не применимо | 5 секунд на ответ | Потребитель прерывает, UI → error_source |

## 6. Релиз и интеграция

### 6.1. Порядок выката
**Узел-фундамент #0 выкатывается раньше дочерних узлов.** 🟡 подтверждено аналитиком (не по коду): 
1. **BE Арсенала** (эндпоинт INT-0) — первым
2. **Дочерние фронты** (ARS-101, ARS-102, ARS-103) — вторым, когда BE готов и контракт стабилен

Это гарантирует, что потребители попадают на готовый контракт и исключает интеграционные сюрпризы.

### 6.2. Обратная совместимость
**Контракт новый, потребителей нет до выката.** 🟡 подтверждено аналитиком (не по коду): пока фундамент не выкатан, дочерние узлы не работают (они опираются на INT-0). После выката всех трёх детей никаких потребителей вне эпика нет → обратная совместимость не требуется (это внутренняя API эпика).

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком (не по коду): **фиче-флагов нет**. Релизим атомарно: все три дочерних узла вкатываются вместе с готовым фундаментом.

### 6.4. План отката
Не применимо: отката эндпоинта отдельно от потребителей нет. Если что-то сломалось:
- **Откат всего эпика** (фундамент + дочерние узлы одновременно) — на уровень до выката

### 6.5. Преднастройка до релиза
- [x] Роли в security-сервисе — не требуется (роль «Администратор» уже существует в системе; проверка встроена в BE Арсенала)
- [x] DDL-миграция — не требуется (используем существующий источник данных активности)
- [x] Конфиги по окружениям — не требуется (таймауты и TTL кэша можно затвердить в коде или конфиге Арсенала)
- [x] Сервисные аккаунты — не требуется (внутреннее взаимодействие фронтов одного эпика)
- [x] Фиче-флаги — не требуется (релизим атомарно)
- [x] Алерты/мониторинг — желательно: настроить алерты на 5xx и таймауты эндпоинта INT-0 в Арсенале

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 (счётчик активных пользователей в шапке) | INT-0 | Дано админка открыта, потребитель (счётчик) запросил INT-0, когда ответ `2xx, data_unavailable: false, current_active: 42`, тогда счётчик показывает `42` |
| FR-2 (счётчик обновляется без перезагрузки) | INT-0 | Дано счётчик уже показывает `42`, когда число активных изменилось на `50` и потребитель запросил INT-0 снова, тогда счётчик обновляется на `50` в пределах 1 минуты |
| FR-3 (модалка с графиком открывается по клику) | INT-0 | Дано счётчик виден, когда администратор кликает по нему, тогда откры вается модалка и потребитель (график) запрашивает INT-0 с `period=day` |
| FR-4 (график переключается при смене периода) | INT-0 | Дано модалка открыта с графиком за `day`, когда администратор переключает на `week`, тогда потребитель запрашивает INT-0 с `period=week` и график перестраивается |
| FR-5 (выгрузка сводки за период) | INT-0 | Дано модалка открыта с графиком за `day`, когда администратор нажимает выгрузку, тогда потребитель запрашивает INT-0 с `period=day` и получает `aggregates`, из которых формируется файл |
