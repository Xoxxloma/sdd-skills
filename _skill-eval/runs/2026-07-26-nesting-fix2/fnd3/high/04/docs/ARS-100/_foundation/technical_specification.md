## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 **BE-only.** Узел-фундамент #0 — чистая реализация данных активности, выдаёт контракт (запрос текущего числа активных пользователей и агрегированной активности за период), который потребляют дочерние фронты (панель в шапке, модальное окно, выгрузка сводки). ### 1.2. Затронутые сервисы и владельцы

## 2. Взаимодействия (ядро)

### INT-0. Получить текущую активность и агрегаты — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Фронты (панель в шапке, модальное окно, выгрузка)

- **Триггер:** 
  - Для текущего счётчика: загрузка страницы админки, периодический опрос (в пределах минуты).
  - Для графика/выгрузки: пользователь открывает модалку или меняет период.

- **Контракт (запрос):**
  - **GET /api/arsenal/activity** (синхронный запрос) или концептуально — endpoint данных активности
  - Query-параметры:
    - `from` (timestamp/ISO 8601) — начало периода (опционально; если не передан — текущее значение)
    - `to` (timestamp/ISO 8601) — конец периода (опционально)
    - `period` (enum: `current` | `hour` | `day` | `week`) — удобный псевдоним для от/до, альтернатива from/to
  - Заголовки: требует авторизации (Bearer token с ролью Администратор)

- **Контракт (ответ):**
  - `status` (enum): 
    - `"available"` — данные успешно получены и актуальны
    - `"unavailable"` — источник не доступен (будь то БД, внешний сервис, таймаут)
  - `current_active_users` (integer | null): текущее число активных пользователей
    - Семантика: неотрицательное число (≥0) или `null` если нет данных за текущий момент
  - `period_aggregates` (object | null): агрегированные данные за выбранный период
    - `null` если период не запрашивался или если статус `"unavailable"`
    - Содержит массив или временной ряд (детали ниже)
  - `period_aggregates.data` (array): временной ряд активности
    - Каждый элемент:
      - `timestamp` (ISO 8601): начало интервала
      - `active_users` (integer): число активных пользователей в этот момент / интервал
      - `null` если за этот интервал данных нет (отличается от `"unavailable"`)
  - `error` (string | null): `null` если успех; иначе код/категория ошибки (см. каталог ниже)

- **Пример запроса:**
  ```
  GET /api/arsenal/activity?period=day
  Authorization: Bearer <token_admin>
  ```

- **Пример ответа (успех, текущее значение и агрегат за день):**
  ```json
  {
    "status": "available",
    "current_active_users": 42,
    "period_aggregates": {
      "data": [
        { "timestamp": "2026-07-26T00:00:00Z", "active_users": 8 },
        { "timestamp": "2026-07-26T01:00:00Z", "active_users": 5 },
        { "timestamp": "2026-07-26T02:00:00Z", "active_users": 3 },
        { "timestamp": "2026-07-26T03:00:00Z", "active_users": 0 },
        { "timestamp": "2026-07-26T04:00:00Z", "active_users": 12 },
        { "timestamp": "2026-07-26T05:00:00Z", "active_users": 28 }
      ]
    },
    "error": null
  }
  ```

- **Пример ответа (успех, нет данных за период):**
  ```json
  {
    "status": "available",
    "current_active_users": 0,
    "period_aggregates": {
      "data": []
    },
    "error": null
  }
  ```

- **Пример ответа (недоступность источника):**
  ```json
  {
    "status": "unavailable",
    "current_active_users": null,
    "period_aggregates": null,
    "error": "source_unavailable"
  }
  ```

- **Ошибки:** 
  - **`source_unavailable`** (5xx or timeout) — БД активности или промежуточный сервис недоступен; клиент видит ошибку, **не** устаревшие данные; должен показать «—» / спиннер ошибки.
  - **`no_data_for_period`** (2xx, но `period_aggregates.data` пуст) — периодически может быть: нет логов активности за выбранный диапазон; это нормально, отличается от `source_unavailable`.
  - **`forbidden`** (403) — роль пользователя не «Администратор»; панель активности и выгрузка должны быть скрыты.
  - **`invalid_parameters`** (400) — неверные параметры (от ≥ до, неизвестный period); клиент должен валидировать перед запросом.
  - **`timeout`** (504 или в рамках контракта `status: "unavailable"`) — запрос превысил 5 сек; то же лечение, что и `source_unavailable`.

- **Состояния UI по ответу:**
  - **`loading`** — первый запрос в полёте, показать спиннер
  - **`value`** — `status: "available"`, `current_active_users > 0` → показать число
  - **`zero`** — `status: "available"`, `current_active_users === 0` → показать «0» (не прочерк)
  - **`empty`** — `status: "available"`, `current_active_users === null` или период без данных → показать «—» / «нет данных»
  - **`error_source`** — `status: "unavailable"` или таймаут → сообщение об ошибке + кнопка retry
  - **`error_forbidden`** — `error: "forbidden"` (403) → панель не показана (скрыта на уровне права доступа)

- **Авторизация:** 
  - Вызов доступен **только** ролям с правом «видеть панель активности». 
  - 🟡 подтверждено аналитиком (не по коду): роль **«Администратор»** имеет это право; роль **«Оператор»** — не имеет.
  - Проверка выполняется на бэке Arsenal, в middleware авторизации перед обработкой запроса.
  - Негативный случай: если токен отсутствует или роль не указана — вернуть 401 (Unauthorized) или 403 (Forbidden).

- **Происхождение:** 🟢 новое (узел-фундамент #0, наследуется всеми дочерними фронтами)

- **Трассировка:** FR-1 (текущее число), FR-2 (автообновление счётчика), FR-3…FR-5 (график, переключение периода, выгрузка — все питаются из этого же контракта)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| `source_unavailable` | `{ status: "unavailable", error: "source_unavailable" }` | БД активности / сервис недоступны, таймаут ≥5с | `error_source` (спиннер ошибки, кнопка retry) |
| `no_data_for_period` | `{ status: "available", period_aggregates: { data: [] }, error: "no_data_for_period" }` | За выбранный период нет ни одной записи активности | `empty` (показать «—» для графика) |
| `forbidden` | HTTP 403, `{ error: "forbidden" }` | Роль пользователя не «Администратор» | `error_forbidden` (панель не видна, скрыта визуально) |
| `invalid_parameters` | HTTP 400, `{ error: "invalid_parameters", details: "..." }` | Неверный формат периода, от ≥ до и т.п. | показать ошибку в консоли разработчика (клиент должен валидировать) |
| `timeout` | HTTP 504 или статус `"unavailable"` | Запрос к источнику занял > 5 сек | `error_source` (то же, что и `source_unavailable`) |

## 3. Backend — ответственность
### 3.1. По сервисам
**Arsenal Backend** реализует INT-0 (контракт данных активности):
- Собирает текущее число активных пользователей (из таблицы сессий / источника сессий — 🟡 подтверждено аналитиком, что Arsenal владеет этими данными)
- Агрегирует активность за выбранный период на лету (час, день, неделя)
- Кэширует результат на 30 секунд на стороне Arsenal Backend (чтобы снизить нагрузку на первичный источник)
- Проверяет авторизацию: перед ответом убедиться, что ролевой контекст — «Администратор»
- Таймаут на источник активности — 5 секунд; превышение → возврат `status: "unavailable"`

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: **новых таблиц не заводим**. Данные активности уже хранятся в Arsenal (или в связанной системе сессий, что Arsenal владеет). Агрегаты считаются на лету из существующих записей, не материализуются в отдельную таблицу.

Никаких миграций BD не требуется.

### 3.3. Авторизация/доступ на бэке
- Проверка роли в middleware авторизации перед доступом к эндпоинту.
- Роли: 🟡 подтверждено аналитиком — **«Администратор»** → доступ; **«Оператор»** и остальные → 403 Forbidden.
- Логирование попыток доступа без прав (для аудита).

## 4. Frontend — ответственность
Дочерние UI-компоненты (панель в шапке, модальное окно, выгрузка) потребляют контракт INT-0 и отображают данные согласно состояниям из §2. Детали — в спеках каждого из дочерних узлов (ARS-101, ARS-102, ARS-103), которые наследуют этот контракт.

Здесь же фиксируем общую логику:

### 4.1. Где и что меняется в UI
- Панель в шапке админки: счётчик текущего числа активных пользователей (вызывает INT-0 с `period=current` или без параметров)
- Модальное окно: график активности за период (вызывает INT-0 с `from`/`to` или `period`)
- Кнопка выгрузки в модалке: готовит файл на основе `period_aggregates.data` из INT-0

### 4.2. Пользовательские сценарии
- **Основной поток (FR-1):** загрузка админки → вызов INT-0 → показ счётчика в шапке
- **Автообновление (FR-2):** периодический опрос INT-0 (в пределах минуты) → обновление счётчика без перезагрузки
- **Открытие модалки (FR-3):** клик на счётчик → вызов INT-0 с `period=day` (по умолчанию) → отрисовка графика
- **Переключение периода (FR-4):** выбор часа/дня/недели → новый вызов INT-0 → обновление графика
- **Выгрузка (FR-5):** клик на кнопку → форматирование данных из последнего ответа INT-0 → скачивание CSV/JSON

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос / переключение периода в полёте | спиннер / скелетон счётчика |
| `value` | INT-0 вернул 2xx, `status: "available"`, `current_active_users > 0` | число (напр. «42») |
| `zero` | INT-0 вернул 2xx, `status: "available"`, `current_active_users === 0` | «0» (не прочерк) |
| `empty` | INT-0 вернул 2xx, `current_active_users === null` или `period_aggregates.data` пуст | «—» / «нет данных» |
| `error_source` | INT-0 вернул `status: "unavailable"` или таймаут (≥5с) | сообщение об ошибке + кнопка retry |
| `error_forbidden` | INT-0 вернул 403 (роль не Администратор) | панель не видна вообще (скрыта визуально, не показана) |

### 4.3.1. Loading и таймауты
- **Cold-path таймаут** (первый запрос после загрузки): 5 секунд (из контракта BE). Если за 5 сек не пришёл ответ → показать `error_source` (сообщение об ошибке + retry).
- **Warm-path таймаут** (последующие обновления, автоопрос): 5 секунд (то же). Если таймаут → показать `error_source`.
- **Polling интервал** для автообновления счётчика: в пределах минуты (из приёмки FR-2), предлагаем 30 секунд (совпадает с кэшем бэка, нет смысла спрашивать чаще). Jitter: да (±10% для разброса), чтобы не грохнуть бэк одновременными запросами всех администраторов.

### 4.4. Доступ по ролям в UI
- **Администратор**: видит счётчик, кнопку открытия модалки, модалку с графиком, кнопку выгрузки.
- **Оператор**: панель активности вообще не показана (состояние `error_forbidden` в коде, визуально — скрыто).

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- 🟡 подтверждено аналитиком: **синхронный** запрос (не async/WebSocket).
- 🟡 подтверждено аналитиком: **кэш 30 секунд** на стороне **Arsenal Backend**. TTL — 30 сек; после истечения — переклик к источнику.
- **Таймаут на источник**: 🟡 подтверждено аналитиком — **5 секунд**. Если за 5 сек не пришёл ответ — возврат `status: "unavailable"`.
- **Частота опроса фронта**: автообновление счётчика в пределах минуты (из приёмки FR-2); предлагаем 30 сек (совпадает с TTL кэша).
- **Ожидаемая нагрузка**: администраторов предполагаются единицы–десятки; нагрузка на источник активности должна быть снижена кэшем.

### 5.2. Надёжность/деградация
- 🟡 подтверждено аналитиком: при недоступности источника (БД, сервис, таймаут) — отдаём признак `status: "unavailable"`, **не устаревшие данные**. UI показывает ошибку, а не вчерашнее число.
- 🟡 подтверждено аналитиком: отдельно различаем **«нет данных за период»** (error code `no_data_for_period`, но `status: "available"`) от **«источник недоступен»** (status `"unavailable"`). Это позволит фронту показать «нет данных» вместо «ошибка при загрузке».
- Логирование ошибок источника для мониторинга (SLA, алерты на 5xx / таймауты).

### 5.3. Безопасность/доступ (сводно)
| Кто / Что | Может | Не может |
|-----------|-------|----------|
| Администратор | запрос INT-0, получает текущее число и агрегаты | — |
| Оператор / неавторизованный | — | запрос INT-0; видит 403 Forbidden |
| Неавторизованный (нет токена) | — | запрос INT-0; видит 401 Unauthorized |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 подтверждено аналитиком: **фундамент выкатывается раньше потребителей** (раньше, чем ARS-101, ARS-102, ARS-103).

Порядок:
1. Развёртывание Arsenal Backend с новым контрактом INT-0 (#0).
2. Проверка (smoke test): INT-0 отвечает, авторизация работает, примеры данных валидны.
3. Развёртывание дочерних узлов (ARS-101, ARS-102, ARS-103), которые потребляют INT-0.

### 6.2. Обратная совместимость
- INT-0 — новый контракт, обратной совместимости не требуется.
- Arsenal Backend должен продолжить обслуживать старые потребителей (если они есть), но новый контракт INT-0 — параллельно.

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **фиче-флаги не используются**. Релизим атомарно: контракт либо готов, либо ещё нет.

### 6.4. План отката
- **Откат только BE** (дети на старой версии): старые фронты не знают о INT-0 (они дети ещё не развёрнуты) → откат не требуется.
- **Откат фундамента после развёртывания детей**: INT-0 будет потребляться UI компонентами; откат BE заставит детей видеть ошибки (`source_unavailable`). Это допустимо, UI должен показывать ошибку с retry. Откатываем BE → дети видят ошибку → администраторы перезагружают страницу или нажимают retry.
- **Откат только FE** (дочерний узел): BE продолжит отдавать INT-0; если дочерний фронт откатился на старую версию, которая не знает INT-0, UI попросту не будет запрашивать контракт (как было до развёртывания). Это безопасно.

### 6.5. Преднастройка до релиза (чек-лист)
- [x] **Роли в security-сервисе:** роль «Администратор» должна быть доступна в токенах администраторов (проверить в security-сервисе). — 🟡 подтверждено аналитиком, что роли уже заведены.
- [x] **DDL-миграция:** не требуется (считаем агрегаты на лету, новых таблиц нет). — 🟡 подтверждено аналитиком.
- [x] **Конфиги по окружениям:** кэш-TTL (30 сек) и таймаут (5 сек) — задать в конфигах dev/staging/prod Arsenal Backend. По умолчанию 30 и 5, но уточнить на стадии разработки.
- [x] **Сервисные аккаунты:** не требуется (IT-0 вызывается от лица авторизованного администратора, а не межсервисного аккаунта).
- [x] **Алерты/мониторинг:** настроить алерты на 5xx ошибки и таймауты источника активности (SLA < 5 сек в 99% случаев). Дашборд: успешные запросы, таймауты, ошибки источника, кэш-хиты.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс |
|----------|-------------------|-----------|
| FR-1 | INT-0 (`period=current`) | Дано открытую админку с авторизацией Администратор, когда страница загрузилась, тогда INT-0 вернул `status: "available"` и `current_active_users: <число>`, и число отображено в шапке. |
| FR-2 | INT-0 (автоопрос каждые 30 сек) | Дано открытую админку, когда число активных пользователей изменилось в БД, и прошло ≤ 30 сек + 30 сек кэша (итого ≤ 60 сек), тогда INT-0 вернул новое значение, счётчик обновился без перезагрузки. |
| FR-3 | INT-0 (`period=day` или `from`/`to`) | Дано счётчик в шапке, когда администратор кликает по нему, тогда вызывается INT-0 с `period=day`, возвращается `period_aggregates.data` за день, и модалка показывает график. |
| FR-4 | INT-0 (переключение `period`) | Дано открытую модалку с графиком, когда администратор переключает период (час → день → неделя), тогда каждый раз INT-0 вызывается с новым `period`, `period_aggregates.data` обновляется, и график перестраивается. |
| FR-5 | INT-0 (того же периода) + выгрузка | Дано открытую модалку с выбранным периодом, когда администратор нажимает кнопку выгрузки, тогда данные из последнего ответа INT-0 форматируются (CSV/JSON) и скачиваются как файл. |
