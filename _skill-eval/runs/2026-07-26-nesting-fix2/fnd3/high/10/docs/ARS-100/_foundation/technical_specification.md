## 1. Обзор изменения

### 1.1. Тип и стороны
🟢 **BE-only.** Узел-фундамент #0 предоставляет контракт (API) для получения данных активности пользователей. Потребители — фронты детских задач (FR-1..FR-5). Межсервисная интеграция не требуется: данные активности собирает и хранит сам бэк Arsenal.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | собирает данные активности, отдаёт контракт для детей | Team Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент обслуживает ядро функционала эпика ARS-100: сбор и предоставление данных текущей активности пользователей и их агрегатов за период. На этих данных строятся FR-1 (счётчик в шапке), FR-2 (автообновление счётчика), FR-3, FR-4, FR-5 (модалка с графиком и выгрузкой).

## 2. Взаимодействия (ядро)

### INT-0. Текущее число активных пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Arsenal backend → Frontend дети
- **Триггер:** фронт инициирует запрос при загрузке и затем периодически для обновления счётчика
- **Контракт (запрос):** `GET /api/admin/activity/current`; без параметров тела; заголовок `Authorization: Bearer <token>`
- **Контракт (ответ):** 
  - `count` (integer, обязательно) — число активных пользователей в данный момент; может быть 0
  - `available` (boolean, обязательно) — `true` если данные доступны, `false` если источник недоступен
  - `timestamp` (ISO 8601 string, обязательно) — момент снимка (UTC)
- **Пример запроса:** `GET /api/admin/activity/current` (без параметров)
- **Пример ответа (успех):**
  ```json
  {
    "count": 42,
    "available": true,
    "timestamp": "2026-07-26T14:23:45.123Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null,
    "available": false,
    "timestamp": "2026-07-26T14:23:45.123Z"
  }
  ```
- **Ошибки:** 
  - `401 Unauthorized` — токен отсутствует, истёк или некорректен (фронт должен инициировать переаутентификацию)
  - `403 Forbidden` — роль пользователя не «Администратор» (фронт скрывает виджет активности)
  - `5xx` — внутренняя ошибка на бэке или недоступность источника данных (см. поле `available` выше)
- **Состояния UI по ответу:**
  - `available: true, count ≠ null` → состояние `value`, вывести число
  - `available: true, count = 0` → состояние `zero`, вывести «0»
  - `available: true, count = null` → состояние `empty`, вывести «—»
  - `available: false` → состояние `error_source`, вывести сообщение об ошибке + кнопку retry
  - `403` → состояние `error_forbidden`, скрыть виджет или вывести сообщение «нет доступа»
  - `5xx` / таймаут → состояние `error_source`
- **Авторизация:** 
  - Требуется роль **Администратор**, проверяется на бэке Arsenal
  - 401/403 возвращаются как описано выше; фронты обязаны их обработать
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (отображение счётчика), FR-2 (автообновление)

### INT-1. Агрегаты активности за период — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Arsenal backend → Frontend дети
- **Триггер:** фронт запрашивает при открытии модалки или смене периода
- **Контракт (запрос):** `GET /api/admin/activity/aggregates?period=<period>`, где `period` — один из значений: `hour`, `day`, `week`; заголовок `Authorization: Bearer <token>`
- **Контракт (ответ):**
  - `period` (string, обязательно) — тот же период, что в запросе
  - `available` (boolean, обязательно) — `true` если данные доступны
  - `data` (array of objects, обязательно, может быть пустым) — массив агрегатов:
    - `timestamp` (ISO 8601 string) — начало интервала (UTC)
    - `count` (integer) — число активных пользователей в интервал
    - `min`, `max` (integer, опционально) — минимум и максимум за интервал
  - `timestamp` (ISO 8601 string, обязательно) — момент снимка (UTC)
- **Пример запроса:** `GET /api/admin/activity/aggregates?period=day`
- **Пример ответа (успех, есть данные):**
  ```json
  {
    "period": "day",
    "available": true,
    "data": [
      {
        "timestamp": "2026-07-26T00:00:00Z",
        "count": 10,
        "min": 5,
        "max": 15
      },
      {
        "timestamp": "2026-07-26T01:00:00Z",
        "count": 12,
        "min": 8,
        "max": 18
      }
    ],
    "timestamp": "2026-07-26T14:23:45.123Z"
  }
  ```
- **Пример ответа (успех, данных за период нет):**
  ```json
  {
    "period": "day",
    "available": true,
    "data": [],
    "timestamp": "2026-07-26T14:23:45.123Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "day",
    "available": false,
    "data": null,
    "timestamp": "2026-07-26T14:23:45.123Z"
  }
  ```
- **Ошибки:**
  - `400 Bad Request` — параметр `period` отсутствует или некорректен (допустимые: `hour`, `day`, `week`)
  - `401 Unauthorized` — токен отсутствует, истёк или некорректен
  - `403 Forbidden` — роль пользователя не «Администратор»
  - `5xx` — внутренняя ошибка на бэке или недоступность источника (см. поле `available` выше)
- **Состояния UI по ответу:**
  - `available: true, data.length > 0` → состояние `value`, вывести график
  - `available: true, data.length = 0` → состояние `empty`, вывести сообщение «нет данных за период»
  - `available: false` → состояние `error_source`, вывести сообщение об ошибке + кнопку retry
  - `403` → состояние `error_forbidden`, скрыть модалку или вывести сообщение «нет доступа»
  - `400` / `5xx` / таймаут → состояние `error_source`
- **Авторизация:**
  - Требуется роль **Администратор**, проверяется на бэке Arsenal
  - 401/403 возвращаются как описано выше
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3 (график за период), FR-4 (переключение периода), FR-5 (выгрузка сводки)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI | INT |
|-----|----------------|-------|--------------|-----|
| 400 | `{ "error": "Invalid period parameter" }` | Параметр `period` отсутствует или не в списке `hour`, `day`, `week` | `error_source` | INT-1 |
| 401 | `{ "error": "Unauthorized" }` | Токен отсутствует, истёк или некорректен | `error_source` | INT-0, INT-1 |
| 403 | `{ "error": "Forbidden" }` | Роль пользователя не «Администратор» | `error_forbidden` | INT-0, INT-1 |
| 500 | `{ "error": "Internal server error" }` | Ошибка на бэке, недоступность источника данных активности | `error_source` (см. также поле `available`) | INT-0, INT-1 |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal backend** реализует оба контракта (INT-0 и INT-1):
- Собирает или получает данные активности пользователей из собственного источника (🟡 подтверждено аналитиком: сам бэк Arsenal владеет и собирает эти данные, новых сервисов не привлекаем)
- Вычисляет агрегаты (текущее число, распределение по временным интервалам) на лету, без отдельного хранилища
- Отдаёт контракты INT-0 и INT-1 в ответ на HTTP GET запросы от фронтов детей

### 3.2. Данные и хранение
🟢 **Новых таблиц не создаётся.** Данные активности существуют в собственном источнике Arsenal и/или в памяти. Агрегаты вычисляются on-the-fly по запросу. Индексы и структура хранения существующего источника — на стороне Arsenal (не пересматривается в этой спеке).

### 3.3. Авторизация/доступ на бэке
🟡 **Подтверждено аналитиком:** проверка роли выполняется на бэке Arsenal средствами security-сервиса.
- Оба контракта (INT-0, INT-1) доступны только пользователям с ролью **Администратор**
- При отсутствии роли возвращается `403 Forbidden`
- Аутентификация проверяется по `Authorization: Bearer <token>` заголовку; при отсутствии/истечении токена возвращается `401 Unauthorized`

## 4. Frontend — ответственность
*(Детальная ответственность фронтов детей из своих БТ; на уровне фундамента —)*
- **Фронты детей** (задачи ARS-101, ARS-102, ARS-103) используют контракты INT-0 и INT-1 для реализации FR-1..FR-5
- Каждый фронт-ребёнок обязан обработать все состояния UI (value, zero, empty, error_source, error_forbidden, loading)
- Таймауты и retry-логика определяются в спеках детей

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
🟡 **Подтверждено аналитиком:**
- Запросы обрабатываются **синхронно** (не async)
- Кэш **30 секунд** на стороне Arsenal backend для оптимизации нагрузки (одинаковые запросы от нескольких фронтов детей получат закэшированный результат)
- **Таймаут 5 секунд** на обработку запроса (если источник данных недоступен или вычисление заняло дольше)
- Периодичность обновления на фронте определяется спеками детей (FR-2: в пределах минуты; конкретный интервал — дело фронта)

### 5.2. Надёжность/деградация
🟡 **Подтверждено аналитиком:**
- При недоступности источника данных активности (сетевая ошибка, таймаут, 5xx) Arsenal backend возвращает `available: false` (INT-0) или `available: false, data: null` (INT-1)
- Устаревшие данные **не отдаются** — либо текущие/корректные, либо флаг недоступности
- Различие между случаями:
  - **Нет данных за период** (выбранный период не содержит записей активности, но источник доступен) → `available: true, data: []`
  - **Источник недоступен** → `available: false, data: null` или `count: null, available: false` (в зависимости от INT)

### 5.3. Безопасность/доступ (сводно)
| Контракт | Роль | Может вызвать | Проверка на | Ошибка |
|----------|------|---------------|-------------|--------|
| INT-0 | Администратор | Да | Arsenal backend | 200 OK |
| INT-0 | Оператор | Нет | Arsenal backend | 403 Forbidden |
| INT-0 | Без токена | Нет | Arsenal backend | 401 Unauthorized |
| INT-1 | Администратор | Да | Arsenal backend | 200 OK |
| INT-1 | Оператор | Нет | Arsenal backend | 403 Forbidden |
| INT-1 | Без токена | Нет | Arsenal backend | 401 Unauthorized |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟢 **Узел-фундамент #0 выкатывается ПЕРВЫМ, раньше всех потребляющих фронтов (ARS-101, ARS-102, ARS-103).** Контракты INT-0 и INT-1 должны быть доступны и стабильны до развёртывания дочерних задач.

### 6.2. Обратная совместимость
🟢 Это новые контракты, backward-compatibility не применима. При развёртывании нужно убедиться, что фронты потребляющих задач готовы к контрактам INT-0 и INT-1 **до** выката фундамента.

### 6.3. Фиче-флаги
🟢 **Фиче-флаги НЕ требуются.** Релизим атомарно: фундамент выкатывается, его контракты становятся доступны всем, детские задачи используют их сразу без условий.

### 6.4. План отката
- **Откат только BE (Arsenal):** если контракты INT-0, INT-1 удалены или нарушены, фронты получат 5xx или 404. Дочерние фронты должны обработать `error_source` (состояние ошибки). Откат BE автоматически восстановит контракты.
- **Откат только FE (дети):** BE продолжит отдавать INT-0, INT-1; старые фронты его могут игнорировать. Откат FE не требует одновременного отката BE.

### 6.5. Преднастройка до релиза
- [ ] Роли в security-сервисе: роль **Администратор** должна быть определена и назначена нужным пользователям (подтверждено: Arsenal использует существующий security-сервис)
- [ ] Конфиги по окружениям: если TTL кэша, таймауты или интервалы опроса источника настраиваются, то занести их в конфиги dev/staging/prod перед выкатом
- [ ] Алерты: поставить мониторинг на 5xx от `/api/admin/activity/*` эндпоинтов
- [ ] Проверка доступа: убедиться, что роль Администратор назначена тестовым пользователям в staging перед prod-релизом
