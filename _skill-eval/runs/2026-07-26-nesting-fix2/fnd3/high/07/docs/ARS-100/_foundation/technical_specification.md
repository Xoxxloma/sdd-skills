## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 BE-only. Узел-фундамент #0 проектирует и реализует контракты данных активности пользователей (текущее число активных + агрегаты за период), которые потребляют клиентские фронты детских задач (счётчик в шапке, граф в модали, выгрузка).

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (BE) | Узел-фундамент: собирает данные активности, отдаёт контракты | Arsenal-Core BE | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
🟢 Фундамент реализует слой данных активности для FR-1..FR-5 из бизнес-требований: узел отдаёт текущее число активных пользователей (FR-1, FR-2) и агрегированную активность за период (FR-3, FR-4, FR-5). Детские фронты потребляют эти контракты и строят счётчик, граф и выгрузку.

## 2. Взаимодействия (ядро)
> Контракты, которые фундамент #0 отдаёт детским фронтам. 🟢 новые; JSON-примеры обязательны.

### INT-1. Получить текущее число активных пользователей — 🟢
- **Граница/направление:** Арсенал (BE) → Фронты детей
- **Триггер:** Инициализация страницы админки; периодическое обновление (polling)
- **Контракт (запрос):** GET `/api/activity/current` (концептуально; стеко-агностично)
  - Параметров и тела нет.
- **Контракт (ответ):** 
  - `count` (integer ≥ 0 | null) — число активных пользователей в данный момент; `null` означает, что данные недоступны (источник недоступен).
  - `data_available` (boolean) — флаг доступности источника; `false` → фронт показывает «недоступно», не берёт `count`.
  - `timestamp_utc` (ISO-8601 string) — время снимка на сервере.
- **Пример запроса:**
  ```
  GET /api/activity/current
  ```
- **Пример ответа (успех):**
  ```json
  {
    "count": 1247,
    "data_available": true,
    "timestamp_utc": "2026-07-26T14:32:15Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null,
    "data_available": false,
    "timestamp_utc": "2026-07-26T14:32:15Z"
  }
  ```
- **Ошибки:** 
  - `403 Forbidden` — роль не «Администратор» (см. ниже).
  - `500 Internal Server Error` — ошибка на сервере Арсенала (маппируется в состояние UI `error_source`).
- **Состояния UI по ответу:**
  - `data_available: true`, `count ≠ null` → состояние `value`: фронт показывает число.
  - `data_available: true`, `count == null` → состояние `zero`: фронт показывает «0» (валидный ноль; не путать с недоступностью).
  - `data_available: false` → состояние `error_source`: фронт показывает «—» (недоступно) + предложение retry.
  - Таймаут (>5s) → состояние `error_source`: фронт показывает «—» (недоступно).
  - 403 → состояние `error_forbidden`: фронт скрывает счётчик.
- **Авторизация:** Только роль «Администратор». Проверяется на сервере Арсенала (BE check). Отрицательный случай: роль не администратор → 403.
- **Происхождение:** 🟢 новое (узел-фундамент #0).
- **Трассировка:** FR-1, FR-2.

### INT-2. Получить агрегированную активность за период — 🟢
- **Граница/направление:** Арсенал (BE) → Фронты детей
- **Триггер:** Открытие модали с графиком; смена периода в модали.
- **Контракт (запрос):** GET `/api/activity/aggregate?period={period}&start={start_utc}&end={end_utc}` (концептуально)
  - `period` (enum: `hour` | `day` | `week`) — гранулярность агрегации.
  - `start_utc` (ISO-8601 string) — начало периода (включительно).
  - `end_utc` (ISO-8601 string) — конец периода (включительно).
- **Контракт (ответ):**
  - `data_points` (array of objects) — массив точек агрегации за период.
    - Каждая точка содержит:
      - `timestamp_utc` (ISO-8601 string) — начало временного окна (часа / дня / недели, в зависимости от `period`).
      - `count` (integer ≥ 0) — число активных пользователей в этом окне.
  - `data_available` (boolean) — флаг: полны ли данные за весь период? `false` → «данные неполные или недоступны».
  - `has_data` (boolean) — отличное от нуля число точек в диапазоне? `false` → за период данные не собраны (например, период в будущем). Фронт различает это от `data_available: false` (источник недоступен).
  - `period_start_utc`, `period_end_utc` (ISO-8601 strings) — границы фактически возвращённого периода (может отличаться от запроса, если запрос уходит за границы известных данных).
- **Пример запроса:**
  ```
  GET /api/activity/aggregate?period=hour&start_utc=2026-07-26T00:00:00Z&end_utc=2026-07-26T23:59:59Z
  ```
- **Пример ответа (успех, данные есть):**
  ```json
  {
    "data_points": [
      { "timestamp_utc": "2026-07-26T00:00:00Z", "count": 542 },
      { "timestamp_utc": "2026-07-26T01:00:00Z", "count": 578 },
      { "timestamp_utc": "2026-07-26T02:00:00Z", "count": 621 },
      { "timestamp_utc": "2026-07-26T03:00:00Z", "count": 598 }
    ],
    "data_available": true,
    "has_data": true,
    "period_start_utc": "2026-07-26T00:00:00Z",
    "period_end_utc": "2026-07-26T23:59:59Z"
  }
  ```
- **Пример ответа (успех, за период нет данных):**
  ```json
  {
    "data_points": [],
    "data_available": true,
    "has_data": false,
    "period_start_utc": "2026-07-26T00:00:00Z",
    "period_end_utc": "2026-07-26T23:59:59Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "data_points": [],
    "data_available": false,
    "has_data": false,
    "period_start_utc": "2026-07-26T00:00:00Z",
    "period_end_utc": "2026-07-26T23:59:59Z"
  }
  ```
- **Ошибки:**
  - `403 Forbidden` — роль не «Администратор».
  - `400 Bad Request` — неверные параметры запроса (напр., `end_utc < start_utc`).
  - `500 Internal Server Error` — ошибка на сервере Арсенала.
- **Состояния UI по ответу:**
  - `data_available: true`, `has_data: true` → состояние `value`: фронт рисует граф с точками.
  - `data_available: true`, `has_data: false` → состояние `empty`: фронт показывает «—» / «нет данных за этот период».
  - `data_available: false` → состояние `error_source`: фронт показывает «—» (недоступно) + retry.
  - Таймаут (>5s) → состояние `error_source`.
  - 403 → состояние `error_forbidden`.
- **Авторизация:** Только роль «Администратор». Проверяется на сервере Арсенала (BE check). Отрицательный случай: 403.
- **Происхождение:** 🟢 новое (узел-фундамент #0).
- **Трассировка:** FR-3, FR-4, FR-5.

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 403 | `{ "error": "Forbidden", "message": "Only Administrator role is allowed" }` | Роль не администратор | `error_forbidden` (скрыть/отключить элемент) |
| 400 | `{ "error": "Bad Request", "message": "Invalid period or date range" }` | Неверные параметры (период, даты) | `error_source` (показать «—» + retry) |
| 500 | `{ "error": "Internal Server Error", "message": "Failed to fetch activity data" }` | Ошибка сервера или источника недоступен | `error_source` (показать «—» + retry) |

## 3. Backend — ответственность
### 3.1. По сервисам
**Арсенал (BE)** реализует INT-1 и INT-2:
- 🟡 Собирает данные об активности пользователей (текущее число активных, историю за период) из собственных источников. Подтверждено аналитиком: Арсенал BE сам собирает эти данные, внешних сервисов не привлекаем.
- Отдаёт INT-1 (текущее число) и INT-2 (агрегаты за период) как 🟢 новые контракты (JSON, с примерами выше).
- Проверяет авторизацию (роль «Администратор») перед каждым вызовом.

### 3.2. Данные и хранение
🟡 Подтверждено аналитиком: агрегаты активности считаются на лету, новых таблиц не заводим. Источник данных — существующие хранилища Арсенала (точный механизм — за BE, не меняем). Индексы и оптимизация запросов — на усмотрение владеющего сервиса.

### 3.3. Авторизация/доступ на бэке
🟡 Подтверждено аналитиком: контракты INT-1 и INT-2 доступны ТОЛЬКО роли «Администратор». Проверка — на сервере Арсенала (BE-check). При отсутствии роли → 403 Forbidden.

## 4. Frontend — ответственность
Не применимо для фундамента #0 (BE-only узел; фронты детей строят свою ответственность поверх контрактов §2).

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- 🟡 Подтверждено аналитиком: **синхронно**. INT-1 и INT-2 возвращают результат в синхронном ответе, без async-очередей.
- 🟡 Подтверждено аналитиком: **кэш 30 секунд на сервере Арсенала**. Данные кэшируются на BE между вызовами; TTL = 30s.
- 🟡 Подтверждено аналитиком: **таймаут 5 секунд**. Запрос не должен ждать больше 5s; если источник не отвечает за 5s → ошибка, `data_available: false` в ответе.
- Полинг на фронте (частота обновления счётчика) — решение детских фронтов, не часть фундамента.

### 5.2. Надёжность/деградация
🟡 Подтверждено аналитиком: при недоступности источника отдаём **флаг недоступности** (`data_available: false`), не устаревшее значение. Фронт различает:
- `data_available: true`, `count: null` → за период нет данных (валидный случай, состояние `zero` для INT-1 или `empty` для INT-2).
- `data_available: false` → источник недоступен (состояние `error_source`, фронт показывает «—» + retry).

### 5.3. Безопасность/доступ (сводно)
| Границ / Действие | Кто может | Проверка | Ошибка при отказе |
|-------------------|-----------|----------|-------------------|
| INT-1, INT-2 (вызов контракта) | Роль «Администратор» | Арсенал BE | 403 Forbidden |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 Подтверждено аналитиком: **фундамент выкатывается раньше потребителей**. Последовательность:
1. Развернуть Арсенал BE с контрактами INT-1 и INT-2.
2. Развернуть детские фронты (ARS-101, ARS-102, ARS-103), которые потребляют эти контракты.

### 6.2. Обратная совместимость
🟡 Подтверждено аналитиком: **фиче-флагов нет**, релизим атомарно. Фундамент выкатывается полностью с контрактами; дети потребляют полный контракт, никаких постепенных включений.

### 6.3. Фиче-флаги
🟡 Подтверждено аналитиком: фиче-флагов нет. Атомарный релиз.

### 6.4. План отката (обязательно)
- **Откат только BE**: Арсенал откатывает контракты INT-1, INT-2 на предыдущую версию. Детские фронты (ARS-101, 102, 103) получают ошибку 500 или 503 (контракт недоступен). Ожидаемый результат: фронты показывают состояние `error_source` («—» с retry), пока BE не развернётся.
- **Откат детей**: Если один из фронтов откатывается, BE остаётся на месте (контракты живы). Фронты, оставшиеся на новой версии, продолжают работать.
- **DDL**: Не применимо — новых таблиц нет.

### 6.5. Преднастройка до релиза
- [ ] Роли в security-сервисе: убедиться, что роль «Администратор» существует и применяется пользователям, которые должны видеть активность.
- [ ] DDL-миграция: не требуется (новых таблиц нет).
- [ ] Конфиги по окружениям: TTL кэша (30s), таймаут (5s) — параметризовать в конфиге Арсенала для dev/staging/prod.
- [ ] Сервисные аккаунты: не требуется (нет межсервисных вызовов; Арсенал вызывает собственные источники).
- [ ] Фиче-флаги: не требуется.
- [ ] Алерты/мониторинг: на ошибки 500, таймауты >5s при вызове INT-1/INT-2, недоступность источника данных.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс |
|----------|-------------------|-----------|
| FR-1 | INT-1 | Дано открытую админку, когда страница загрузилась, тогда GET /api/activity/current возвращает текущее число активных пользователей (200, `data_available: true`, `count ≥ 0`). Фронт отображает это число в шапке. |
| FR-2 | INT-1 | Дано счётчик в шапке с числом активных, когда активность пользователей меняется, тогда фронт периодически запрашивает INT-1; получает новое число и обновляет счётчик без перезагрузки (в пределах ~1min = 1 period + 30s cache). |
| FR-3 | INT-2 | Дано счётчик в шапке, когда администратор кликает по нему, тогда модалка вызывает GET /api/activity/aggregate (с периодом по умолчанию, напр. день), получает `data_points` и рисует граф. |
| FR-4 | INT-2 | Дано открытую модалку с графиком, когда администратор выбирает другой период (час / неделя), тогда модалка вызывает INT-2 с новыми параметрами; получает новые точки и перестраивает граф. |
| FR-5 | INT-2 | Дано открытую модалку с периодом, когда администратор нажимает выгрузку, тогда фронт вызывает INT-2, получает `data_points`, форматирует в CSV/Excel и скачивает как файл. Содержание — timestamp + count для каждой точки. |
