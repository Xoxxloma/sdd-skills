## 1. Обзор изменения
### 1.1. Тип и стороны
BE-only. Узел-фундамент #0 предоставляет контракт данных активности пользователей для потребления детскими узлами (фронт-ы панели активности). Фундамент реализуется на стороне бэка «Арсенала».

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal BE | Поставщик контракта активности; вычисляет агрегаты на лету, кэширует результаты | Команда Arsenal-Core | 🟢 новое взаимодействие |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 обслуживает FR-1…FR-5 эпика в части **данных об активности**: текущее число активных пользователей и агрегированная активность за выбранный период (час/день/неделя). Оба вида данных предоставляются одним контрактом.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Backend Arsenal → Потребители (детские фронты)
- **Триггер:** Запрос на начальную загрузку панели активности; автоматический опрос по таймеру (каждые N секунд); переключение периода в модальном окне
- **Контракт (запрос):** 
  - **Метод + путь (концептуально):** `GET /api/v1/activity/stats` (или эквивалент в выбранном фреймворке)
  - **Параметры запроса:**
    - `period` (строка, обязателен): `current` | `hour` | `day` | `week` — требуемый период агрегации
  - **Заголовки:** стандартные (авторизация; см. §2 Авторизация)

- **Контракт (ответ):** 
  - `current_active_users` (целое число или null): текущее число активных пользователей в данный момент
    - Семантика: `null` означает, что источник недоступен (данные не получены)
  - `period_stats` (объект или null): агрегированная статистика за запрошенный период
    - `period` (строка): `current` | `hour` | `day` | `week` — период, за который данные
    - `total_sessions` (целое число): общее число сессий за период (может быть 0, если данных нет)
    - `peak_concurrent` (целое число): пиковое число одновременно активных сессий за период
    - `avg_concurrent` (вещественное число): среднее число активных сессий за период
    - Семантика: если за период нет данных, поля `total_sessions`, `peak_concurrent`, `avg_concurrent` = 0 (не null); если источник недоступен целиком, `period_stats` = null
  - `source_status` (строка): `available` | `temporarily_unavailable` — статус источника активности
    - `available` — данные получены из источника; `temporarily_unavailable` — источник недоступен, значения не обновлены
  - `cached_at` (ISO 8601 timestamp, опционально): время последнего обновления кэша (для отладки и мониторинга)
  - `is_stale` (булево): `true`, если данные старше установленного лимита (>30с); `false`, если свежие
    - Клиент может использовать этот флаг для отображения пометки «данные устаревают» или запуска новой загрузки

- **Пример запроса:** 
  ```json
  GET /api/v1/activity/stats?period=hour
  ```

- **Пример ответа (успех — данные доступны):**
  ```json
  {
    "current_active_users": 42,
    "period_stats": {
      "period": "hour",
      "total_sessions": 215,
      "peak_concurrent": 47,
      "avg_concurrent": 38.5
    },
    "source_status": "available",
    "cached_at": "2026-07-26T14:35:20Z",
    "is_stale": false
  }
  ```

- **Пример ответа (частичная недоступность — источник недоступен):**
  ```json
  {
    "current_active_users": null,
    "period_stats": null,
    "source_status": "temporarily_unavailable",
    "cached_at": "2026-07-26T14:34:50Z",
    "is_stale": true
  }
  ```

- **Пример ответа (успех — период без данных):**
  ```json
  {
    "current_active_users": 5,
    "period_stats": {
      "period": "week",
      "total_sessions": 0,
      "peak_concurrent": 0,
      "avg_concurrent": 0
    },
    "source_status": "available",
    "cached_at": "2026-07-26T14:35:20Z",
    "is_stale": false
  }
  ```

- **Ошибки:** 
  - `400 Bad Request` — неверный параметр `period` (значение вне списка); тело: `{"error": "invalid_period", "message": "Period must be one of: current, hour, day, week"}`
  - `401 Unauthorized` — отсутствует или невалидна авторизация; тело: `{"error": "unauthorized", "message": "Missing or invalid token"}`
  - `403 Forbidden` — у пользователя/роли нет прав доступа (не администратор); тело: `{"error": "forbidden", "message": "Only Administrator role can access activity statistics"}`
  - `500 Internal Server Error` — ошибка на бэке при вычислении или получении данных (не должна выдаваться как стейл; см. обработку в §5.2); тело: `{"error": "internal_error", "message": "Failed to compute activity statistics"}`
  - `504 Gateway Timeout` — таймаут при получении данных (см. §5.1 про таймаут 5с); тело: `{"error": "timeout", "message": "Activity data source did not respond in time"}`

- **Состояния UI по ответу (если есть фронт):**
  - `value` — `source_status == "available"` и `(current_active_users != null или period_stats != null)` → показать значения (счётчик, график)
  - `zero` — `source_status == "available"` и `current_active_users == 0` → показать «0» (валидный ноль)
  - `empty` — `source_status == "available"` и `period_stats.total_sessions == 0` → показать «нет данных за период» или пустой график
  - `error_source` — `source_status == "temporarily_unavailable"` или 5xx / таймаут / сетевая ошибка → показать сообщение об ошибке + кнопка повтора
  - `error_forbidden` — 403 → показать сообщение «нет доступа»
  - `stale_warning` — (дополнительно) `is_stale == true` → опционально: показать индикатор «данные устаревают» рядом со значением

- **Авторизация:** 
  - Контракт доступен **только для роли «Администратор»** (как подтверждено аналитиком)
  - Проверка: на бэке Arsenal BE перед возвратом данных
  - Негативные случаи: пользователь с ролью «Оператор» → 403 Forbidden
  - Механизм: стандартная проверка роли из security-сервиса Arsenal (не новое; 🟡 подтверждено аналитиком, что такой механизм уже есть)

- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (счётчик в шапке), FR-2 (автообновление счётчика), FR-3 (открытие модалки), FR-4 (переключение периода в модалке), FR-5 (выгрузка сводки)

### Каталог ошибок
| Код | Тело/сообщение | Когда | Состояние UI |

| 401 | `{"error": "unauthorized", "message": "…"}` | Отсутствует/невалидна авторизация | `error_forbidden` (или приглашение переаутентифицироваться) |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal BE** реализует INT-0:
- Контракт новый (🟢), реализуется как описано в §2
- Логика: запрос `GET /api/v1/activity/stats?period=X` → вычисление агрегатов активности за период X на лету → сохранение результата в кэш (30с TTL) → возврат ответа с полями `source_status`, `is_stale`, `cached_at`
- Когда источник активности недоступен: возвращать `source_status: "temporarily_unavailable"` вместо 5xx или стейл-данных (как подтверждено аналитиком)

### 3.2. Данные и хранение
**Новых сущностей и таблиц не заводится.** 🟡 Подтверждено аналитиком: агрегаты активности считаются на лету из существующего источника активности (детали источника — к валидации, но его наличие подтверждено).

Кэширование:
- Где: на стороне бэка Arsenal BE (в памяти процесса, Redis или иной выбор фреймворка)
- TTL: 30 секунд (как подтверждено аналитиком)
- Инвалидация: по таймауту; запрос новых данных всегда заново вычисляет (нет явных событий инвалидации)

Индексы и retention: не требуются — данные не персистируются.

### 3.3. Авторизация/доступ на бэке
- Где: в обработчике `GET /api/v1/activity/stats` на Arsenal BE, перед вычислением и возвратом данных
- Как: проверка роли пользователя через существующий механизм авторизации Arsenal (🟡 подтверждено аналитиком)
- Требуемая роль: `Administrator`
- Если роль не совпадает → 403 Forbidden (сообщение указано в каталоге ошибок §2)

## 4. Frontend — ответственность
**Не применимо:** узел-фундамент #0 предоставляет только контракт данных. Ответственность за UI (счётчик, график, выгрузка) лежит на детских узлах (FE-панель активности), которые наследуют INT-0 и используют его.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** синхронный вызов (как подтверждено аналитиком; асинхронная обработка происходит внутри BE, но ответ отправляется блокирующе)
- **Кэш:** 30 секунд на стороне Arsenal BE (как подтверждено аналитиком)
  - Первый запрос в период TTL → возврат закэшированного значения (поле `is_stale: false`)
  - Запрос после истечения TTL → новое вычисление + обновление кэша
- **Таймаут:** 5 секунд на получение данных из источника активности (как подтверждено аналитиком)
  - При превышении таймаута: возвращать 504 Gateway Timeout (см. каталог ошибок), **не** выдавать кэшированное значение
- **Ожидаемая нагрузка:** каждый клиент (детский фронт) опрашивает INT-0 каждые N секунд (N определяется фронтом, фундамент не накладывает ограничений)

### 5.2. Надёжность/деградация
- При недоступности источника активности: возвращать `source_status: "temporarily_unavailable"` + `current_active_users: null` + `period_stats: null` (как подтверждено аналитиком, вместо кэшированного стейл-значения)
- При таймауте (>5с): возвращать 504 + то же состояние (не кэш)
- Различие между состояниями:
  - **Нет данных за период** — `source_status: "available"`, `total_sessions: 0` (валидный результат)
  - **Источник недоступен** — `source_status: "temporarily_unavailable"` + null (фронт показывает ошибку и retry)
- Логирование: ошибки доступа к источнику логировать на уровне WARN/ERROR для мониторинга

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто | Может | Не может | Где checked |
|---------|-----|-------|----------|-------------|
| INT-0 (GET /api/v1/activity/stats) | Administrator | Читать current_active_users, period_stats | — | Arsenal BE (роль check) |
| INT-0 | Operator, прочие роли | — | Читать (403 Forbidden) | Arsenal BE (роль check) |

## 6. Релиз и интеграция

### 6.1. Порядок выката
1. **Первым:** Arsenal BE с реализацией INT-0 (контракт + вычисление агрегатов + авторизация)
2. **Вторым и далее:** Детские узлы (фронты, которые потребляют INT-0), каждый независимо

**Обоснование:** детские фронты зависят от контракта INT-0, поэтому бэк должен быть готов перед их выкатом.

### 6.2. Обратная совместимость
Новый контракт INT-0 не ломает существующие взаимодействия Arsenal BE (только добавляет новый эндпоинт). Откат:
- Откат только BE: INT-0 перестаёт доступен (404 или 501) → детские фронты получат ошибку доступа и покажут `error_source` (ожидаемо, не критично; фронты повторяют запрос)
- Откат только FE: если фронт откачен, то INT-0 остаётся доступен на бэке (никому не вредит)

### 6.3. Фиче-флаги
**Фиче-флагов нет** (как подтверждено аналитиком) — релизим атомарно: когда бэк готов, детские фронты начинают вызывать INT-0 сразу.

### 6.4. План отката
- **Откат только BE:** Детские фронты получат ошибку (404/501/5xx на INT-0) → state `error_source` → retry по таймеру → пользователь видит retry-UI (соответствует бизнес-требованиям об обработке недоступности)
- **Откат только FE:** Не критично; INT-0 остаётся в live, но не вызывается (никого не трогает)
- **Откат DDL:** Не требуется (новых таблиц не заводится)

### 6.5. Преднастройка до релиза
- [x] Роли в security-сервисе — роль «Administrator» должна быть определена в security-сервисе Arsenal (🟡 подтверждено аналитиком, что такая роль уже есть)
- [x] DDL-миграция — не требуется (новых таблиц не заводится)
- [x] Конфиги по окружениям — значение TTL кэша (30с), таймаут (5с) закреплены в коде или конфигах (фундамент не требует специальных преднастроек)
- [x] Сервисные аккаунты — не требуются (INT-0 вызывают только аутентифицированные пользователи-администраторы)
- [x] Фиче-флаги — не требуются

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано аутентифицирован администратор, когда фронт запрашивает `GET /api/v1/activity/stats?period=current`, тогда ответ содержит `current_active_users` ≠ null и `source_status: "available"` |
| FR-2 | INT-0 | Дано повторный запрос в течение 30с, когда фронт запрашивает INT-0, тогда ответ содержит то же значение `current_active_users` и `is_stale: false` (кэшировано) |
| FR-3 | INT-0 | Дано пользователь кликнул на счётчик, когда фронт запрашивает `GET /api/v1/activity/stats?period=day`, тогда ответ содержит `period_stats` с агрегатами за день |
| FR-4 | INT-0 | Дано открыта модалка, когда администратор выбирает другой период, тогда фронт запрашивает INT-0 с новым `period` и получает свежие агрегаты |
| FR-5 | INT-0 | Дано администратор нажимает выгрузку, тогда фронт запрашивает INT-0 для текущего периода и использует `period_stats` для формирования файла сводки |
