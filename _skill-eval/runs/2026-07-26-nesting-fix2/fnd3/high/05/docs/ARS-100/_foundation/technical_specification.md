## 1. Обзор изменения

### 1.1. Тип и стороны

🟢 BE-only. Узел-фундамент #0 предоставляет контракт данных активности пользователей (текущее число активных + агрегаты за период) консумерам-фронтам эпика ARS-100 (детские задачи ARS-101, ARS-102, ARS-103). Функционал полностью расположен на стороне бэка «Арсенала»; фронты обращаются к контракту за данными.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Сбор и расчёт данных активности; предоставление контрактов #0 | Team Arsenal-Core | 🟡 подтв. аналитиком |

### 1.3. Связь с бизнес-требованиями

Узел-фундамент #0 реализует базовый слой данных активности, необходимый для FR-1..FR-5 эпика ARS-100: счётчик активных пользователей (текущее число) и агрегированная активность за выбранный период (для графика и выгрузки). Все три элемента интерфейса (счётчик в шапке, график в модалке, выгрузка) опираются на единые контракты, спроектированные здесь.

## 2. Взаимодействия (ядро)

### INT-1. Получение текущего числа активных пользователей — 🟢

- **Граница/направление:** Arsenal Backend → Фронты детей (FE-to-BE, фронты запрашивают)
- **Триггер:** Загрузка страницы админки; периодическое обновление счётчика в шапке (polling).
- **Контракт (запрос):** 
  ```
  GET /api/arsenal/activity/current
  ```
  Заголовки: авторизация (см. раздел Авторизация).
  Параметры: нет.

- **Контракт (ответ):**
  - `count` (integer, обязательное): число активных пользователей. Диапазон: 0..N.
  - `available` (boolean, обязательное): флаг доступности источника данных.
    - `true` — данные актуальны и получены от источника;
    - `false` — источник недоступен, значение в `count` игнорировать, показать фронту состояние `error_source`.
  - `timestamp` (ISO 8601 datetime, обязательное): момент последнего обновления кэша на бэке.

- **Пример запроса:**
  ```
  GET /api/arsenal/activity/current HTTP/1.1
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех, данные доступны):**
  ```json
  {
    "count": 42,
    "available": true,
    "timestamp": "2026-07-26T18:55:30Z"
  }
  ```

- **Пример ответа (недоступность источника):**
  ```json
  {
    "count": null,
    "available": false,
    "timestamp": "2026-07-26T18:50:00Z"
  }
  ```

- **Ошибки:** 
  - 401 Unauthorized — токен отсутствует или невалиден.
  - 403 Forbidden — текущий пользователь не имеет роль «Администратор».
  - 500 Internal Server Error — ошибка на бэке (например, тайм-аут подключения к источнику данных).

- **Состояния UI по ответу (если есть фронт):**
  - `available: true, count ≥ 0` → состояние `value`: показать число в счётчике.
  - `available: true, count: null` — не возможно (если данные доступны, `count` всегда число).
  - `available: false` → состояние `error_source`: показать прочерк «—» или значок ошибки + кнопку retry.
  - 403 → состояние `error_forbidden`: скрыть счётчик или показать сообщение «нет доступа».

- **Авторизация:**
  - Доступ: только роль «Администратор» (🟡 подтверждено аналитиком: проверка на стороне Arsenal Backend).
  - Где проверяется: на бэке «Арсенала» при обработке запроса (middleware/guard).
  - Негативный случай: пользователь без роли получает 403 Forbidden.

- **Происхождение:** 🟢 новое (узел-фундамент #0, контракт для детей).

- **Трассировка:** FR-1 (отображение счётчика), FR-2 (автообновление).

### INT-2. Получение агрегированной активности за период — 🟢

- **Граница/направление:** Arsenal Backend → Фронты детей (FE-to-BE, фронты запрашивают).
- **Триггер:** Открытие модального окна графика; переключение периода (час/день/неделя); подготовка данных для выгрузки.
- **Контракт (запрос):**
  ```
  GET /api/arsenal/activity/aggregate?period=<hour|day|week>&date=<YYYY-MM-DD>
  ```
  - `period` (string, обязательный): «hour», «day» или «week».
    - «hour» → данные за текущий час (интервал 1 минута).
    - «day» → данные за текущие сутки (интервал 1 час).
    - «week» → данные за текущую неделю (интервал 1 день).
  - `date` (string, формат YYYY-MM-DD, обязательный): дата, для которой собирать данные (базовая дата периода). Интерпретация:
    - для `period=hour`: ищем час, в который попадает `date` (точнее, если передана конкретная дата+время, берётся часовой интервал, содержащий это время; если только дата — берётся час 00:00 этого дня). Упрощённо: для `period=hour` и `date=2026-07-26` → 2026-07-26 00:00..01:00.
    - для `period=day`: данные за этот день (00:00..23:59).
    - для `period=week`: данные за неделю, содержащую эту дату (понедельник..воскресенье по UTC).
  - Заголовки: авторизация.

- **Контракт (ответ):**
  - `period` (string): повтор запроса, одна из {«hour», «day», «week»}.
  - `date` (string, YYYY-MM-DD): дата запроса.
  - `data` (array of objects, обязательное): точки временного ряда активности внутри периода.
    - Каждый элемент массива (точка):
      - `timestamp` (ISO 8601 datetime, обязательное): начало интервала для этой точки (зависит от `period`: для hour — каждую минуту, для day — каждый час, для week — каждый день).
      - `activeCount` (integer, обязательное): число активных пользователей на момент/в интервал этой точки. Диапазон: 0..N.
  - `available` (boolean, обязательное): флаг доступности источника данных.
    - `true` — данные получены от источника.
    - `false` — источник недоступен; массив `data` может быть пуст или содержать устаревшие значения (см. ниже).
  - `noData` (boolean, обязательное): флаг «нет данных за период».
    - `true` — источник был доступен, но в этот период нет записей активности (например, период в прошлом, за который не собирали данные, или период в будущем). Массив `data` пуст или содержит нули.
    - `false` — данные есть (или источник недоступен, поэтому статус неясен).
  - `timestamp` (ISO 8601 datetime, обязательное): момент формирования ответа (последнее обновление кэша).

- **Пример запроса:**
  ```
  GET /api/arsenal/activity/aggregate?period=hour&date=2026-07-26 HTTP/1.1
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех, данные за час, 4 точки/минуты):**
  ```json
  {
    "period": "hour",
    "date": "2026-07-26",
    "data": [
      { "timestamp": "2026-07-26T18:00:00Z", "activeCount": 5 },
      { "timestamp": "2026-07-26T18:15:00Z", "activeCount": 8 },
      { "timestamp": "2026-07-26T18:30:00Z", "activeCount": 12 },
      { "timestamp": "2026-07-26T18:45:00Z", "activeCount": 10 }
    ],
    "available": true,
    "noData": false,
    "timestamp": "2026-07-26T18:55:30Z"
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "period": "day",
    "date": "2025-01-01",
    "data": [],
    "available": true,
    "noData": true,
    "timestamp": "2026-07-26T18:55:30Z"
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "week",
    "date": "2026-07-26",
    "data": [],
    "available": false,
    "noData": false,
    "timestamp": "2026-07-26T18:50:00Z"
  }
  ```

- **Ошибки:**
  - 400 Bad Request — некорректные параметры (неизвестный `period`, невалидная `date`).
  - 401 Unauthorized — токен отсутствует или невалиден.
  - 403 Forbidden — текущий пользователь не имеет роль «Администратор».
  - 500 Internal Server Error — ошибка на бэке.

- **Состояния UI по ответу (если есть фронт):**
  - `available: true, noData: false, data.length > 0` → состояние `value`: отрисовать график с полученными точками.
  - `available: true, noData: true, data.length == 0` → состояние `empty`: показать «нет данных за этот период».
  - `available: false` → состояние `error_source`: показать сообщение об ошибке (источник недоступен) + кнопку retry.
  - 403 → состояние `error_forbidden`: скрыть график или показать сообщение «нет доступа».
  - 400 → состояние `error_validation`: показать сообщение о некорректных параметрах (например, неизвестный period).

- **Авторизация:**
  - Доступ: только роль «Администратор» (🟡 подтверждено аналитиком: проверка на стороне Arsenal Backend).
  - Где проверяется: на бэке «Арсенала» при обработке запроса.
  - Негативный случай: пользователь без роли получает 403 Forbidden.

- **Происхождение:** 🟢 новое (узел-фундамент #0, контракт для детей).

- **Трассировка:** FR-3 (открытие модалки с графиком), FR-4 (переключение периода), FR-5 (выгрузка сводки).

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- Реализует INT-1 (GET /api/arsenal/activity/current): возвращает текущее число активных пользователей.
- Реализует INT-2 (GET /api/arsenal/activity/aggregate): собирает и возвращает агрегированную активность за период.
- 🟡 подтверждено аналитиком: собирает данные активности самостоятельно (данные поступают от сессионного хранилища / логов / другого внутреннего источника); внешних сервисов для сбора не привлекает.
- Авторизация: проверяет роль «Администратор» (см. §5.3).
- Кэширование: ответы кэшируются на 30 секунд (см. §5.1).
- Тайм-ауты: операция должна завершиться за 5 секунд или вернуть 500 с `available: false`.

### 3.2. Данные и хранение

🟢 Новых таблиц/сущностей не заводим. 🟡 подтверждено аналитиком: агрегаты активности рассчитываются на лету из существующих источников данных (сессионное хранилище, логи). Индексы и оптимизации на существующих таблицах — по необходимости при интеграции (не часть этой спеки).

### 3.3. Авторизация/доступ на бэке

- Перед обработкой INT-1 и INT-2 бэк проверяет наличие у текущего пользователя роли «Администратор».
- Проверка выполняется на основе токена (заголовок `Authorization: Bearer <token>`).
- Если роли нет → ответ 403 Forbidden с телом ошибки (см. раздел Каталог ошибок).
- 🟡 подтверждено аналитиком: проверка роли осуществляется в системе безопасности/аутентификации Arsenal (механика валидации токена — по архитектуре Arsenal; спека не описывает деталь, но предполагает, что она существует).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- 🟡 подтверждено аналитиком: обработка синхронная (FE ждёт ответа).
- 🟡 подтверждено аналитиком: кэш 30 секунд на стороне Arsenal Backend. Все запросы в пределах 30-секундного окна получают одинаковый ответ (даже если данные в источнике обновились). По истечении 30 секунд кэш инвалидируется и следующий запрос перепроводит расчёт.
- 🟡 подтверждено аналитиком: таймаут 5 секунд на выполнение запроса. Если источник не отвечает за 5 секунд, бэк возвращает INT-1/INT-2 с `available: false` (и код 500 или специальный таймаут-код; детали по интеграции).
- Ожидаемая нагрузка: полагаемся на наблюдение операций; масштабирование — по результатам мониторинга (не часть этой спеки).

### 5.2. Надёжность/деградация

- 🟡 подтверждено аналитиком: при недоступности источника (сеть, БД, сервис) бэк **отдаёт признак недоступности** (`available: false`), а не кэшированное/устаревшее значение. Это критично для бизнеса: администратор должен понимать, актуальны ли данные, и не принимать решений на основе устаревших цифр.
- 🟡 подтверждено аналитиком: отдельно различаем две ситуации:
  - Источник недоступен → `available: false, noData: false` (INT-2 для aggregates).
  - Источник доступен, но нет данных за период → `available: true, noData: true` (INT-2).
  - Текущего числа нет (недоступность) → `available: false, count: null` (INT-1).
  Это различие позволяет фронту показать правильное состояние UI и сообщение.

### 5.3. Безопасность/доступ (сводно)

| Граница | Роль | Доступ | Как enforced |
|---------|------|--------|--------------|
| INT-1, INT-2 | Администратор | ✅ Полный (читает данные) | Проверка роли на бэке; 403 при отсутствии |
| INT-1, INT-2 | Оператор / другие | ❌ Запрещено | 403 Forbidden |
| INT-1, INT-2 | Аноним (нет токена) | ❌ Запрещено | 401 Unauthorized |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟢 **Фундамент #0 выкатывается раньше потребителей** (детских фронтов ARS-101, ARS-102, ARS-103).

1. Выкат бэка Arsenal с контрактами INT-1 и INT-2 (пишет `_foundation/technical_specification.md`).
2. Выкат детских фронтов (ARS-101, ARS-102, ARS-103), которые читают контракты #0.

Причина: фронты зависят от наличия эндпоинтов на бэке; если бэк ещё не содержит INT-1/INT-2, фронты получат 404 и не смогут инициализироваться.

### 6.2. Обратная совместимость

🟢 Это новый функционал; обратной совместимости (с версией без панели активности) нет. Но внутри эпика:
- Контракты INT-1 и INT-2 — финальные, не меняются при выкате детей.
- Если детский фронт-потребитель требует изменения контракта → изменение делается в спеке #0, и спека #0 пересылается всем детям (их спеки обновляются с помощью режима B, см. аддитив в скилле). Молчаливых переопределений контракта на стороне ребёнка нет.

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком: фиче-флагов нет. Релизим атомарно: если бэк выкатан с эндпоинтами INT-1 и INT-2, фронты сразу их видят и начинают использовать (через 30-секундный кэш).

### 6.4. План отката

🟢 В случае необходимости отката:
- **Откат BE (Arsenal с INT-1/INT-2):** Фронты получат 404 на запросы к новым эндпоинтам. Это ломает панель активности, но не влияет на остальной интерфейс админки (панель скрывается или показывает ошибку). FE-откат **не требуется** (фронты по-прежнему показывают виджет, но он в состоянии `error_source`). Однако для лучшего UX рекомендуется откатить FE одновременно или перед BE.
- **Откат FE (детские фронты):** BE продолжает отвечать на INT-1/INT-2 (данные остаются доступны). FE скрывает виджет/панель. Потребителей (других фронтов, если будут) нет на этапе выката #0, поэтому синхронный откат BE не требуется.
- **Откат БД/DDL:** не применимо (нет новых таблиц).

### 6.5. Преднастройка до релиза

- [ ] Роли в security-сервисе — роль «Администратор» должна быть определена и работоспособна (обычно уже существует; проверить при интеграции).
- [ ] DDL-миграция в репо владеющего сервиса — не применимо (новых таблиц нет).
- [ ] Конфиги по окружениям (dev/staging/prod) — TTL кэша (30с) и таймаут (5с) могут варьироваться по окружениям; закрепить в конфигах Arsenal.
- [ ] Сервисные аккаунты для межсервисных вызовов — не применимо (no cross-service calls; всё в одном сервисе Arsenal).
- [ ] Фиче-флаги заведены — не применимо (без флагов, релизим атомарно).
- [ ] Алерты/мониторинг на ключевые ошибки (5xx, таймауты) — установить алерты на: (a) частоту 500 на INT-1/INT-2; (b) частоту таймаутов (запросы > 5s); (c) инвалидацию кэша (если логируется).
