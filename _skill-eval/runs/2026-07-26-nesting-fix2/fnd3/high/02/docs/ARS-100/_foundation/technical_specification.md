## 1. Обзор изменения

### 1.1. Тип и стороны
🟢 Узел-фундамент #0 — **BE-only**, выделенный контракт данных активности пользователей, потребляемый фронтовыми реализациями детских требований FR-1..FR-5 эпика. Фундамент не содержит UI-логики; его обязанность — отдать унифицированный контракт всем потребителям.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (backend) | Сбор и агрегация данных активности, отдача контракта | Team Arsenal | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел #0 реализует общее основание, необходимое для FR-1 (отображение текущей активности), FR-2 (автоматическое обновление счётчика), FR-3–FR-5 (график и выгрузка за период). Все три фронтовых элемента потребляют одинаковые данные: текущее число активных пользователей и агрегированную активность за выбранный период.

## 2. Взаимодействия (ядро)

### INT-0. Запрос данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Backend Арсенала → Дочерние фронты (FR-1–FR-5)
- **Триггер:** Фронт инициирует запрос при загрузке, периодическом обновлении или смене периода в модальном окне
- **Контракт (запрос):** 
  - Метод: `GET /api/admin/activity/summary`
  - Параметры:
    - `period_type` (строка, обязателен): `hour` | `day` | `week` — период агрегации
    - `start_date` (ISO 8601 дата, опционально): начало периода; если не указано, текущий момент минус период_type

- **Контракт (ответ):** 
  - `current_active_count` (целое число ≥ 0, обязательно): число активных пользователей на момент запроса
  - `period_type` (строка): отражение переданного period_type
  - `aggregates` (массив объектов, обязательно): агрегированные данные активности за период
    - `timestamp` (ISO 8601): метка времени для каждой точки графика (зависит от period_type: минутная для hour, часовая для day, дневная для week)
    - `active_count` (целое число ≥ 0): число активных пользователей в этот момент
  - `is_available` (булев): `true` если источник активности доступен; `false` если недоступен (см. раздел об ошибках)
  - `has_data_for_period` (булев): `true` если есть данные за запрошенный период; `false` если нет данных (пустой период)
  - `cached_at` (ISO 8601): момент, когда были получены и закэшированы данные (для отладки и инвалидации)

- **Пример запроса:**
  ```
  GET /api/admin/activity/summary?period_type=hour&start_date=2026-07-26T10:00:00Z
  ```

- **Пример ответа (успех — есть данные):**
  ```json
  {
    "current_active_count": 42,
    "period_type": "hour",
    "aggregates": [
      { "timestamp": "2026-07-26T10:00:00Z", "active_count": 35 },
      { "timestamp": "2026-07-26T10:05:00Z", "active_count": 38 },
      { "timestamp": "2026-07-26T10:10:00Z", "active_count": 40 },
      { "timestamp": "2026-07-26T10:15:00Z", "active_count": 42 }
    ],
    "is_available": true,
    "has_data_for_period": true,
    "cached_at": "2026-07-26T10:17:30Z"
  }
  ```

- **Пример ответа (успех — нет данных за период):**
  ```json
  {
    "current_active_count": 42,
    "period_type": "week",
    "aggregates": [],
    "is_available": true,
    "has_data_for_period": false,
    "cached_at": "2026-07-26T10:17:30Z"
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_active_count": null,
    "period_type": "hour",
    "aggregates": [],
    "is_available": false,
    "has_data_for_period": false,
    "cached_at": "2026-07-26T10:00:00Z"
  }
  ```

- **Ошибки:** 
  - `400 Bad Request` — некорректные параметры (period_type не из списка, start_date имеет неверный формат); тело: `{ "error": "invalid_parameters", "message": "..." }`
  - `401 Unauthorized` — отсутствует аутентификация или не валидный токен; тело: `{ "error": "unauthorized" }`
  - `403 Forbidden` — роль пользователя не «Администратор»; тело: `{ "error": "forbidden", "message": "Only administrators can access activity summary" }`
  - `500 Internal Server Error` — внутренняя ошибка при сборке данных (источник активности недоступен из-за сбоя); **не отдавать стоявшие данные, отдавать `is_available: false`** в поле ответа 2xx; 500 возвращать только при критических ошибках самого бэка Арсенала
  - `504 Gateway Timeout` — таймаут источника активности (5 секунд истёк); тело: `{ "error": "source_timeout" }`

- **Состояния UI по ответу (для фронтов FR-1..FR-5):**
  - `value`: `is_available === true && current_active_count !== null` → показать число
  - `zero`: `is_available === true && current_active_count === 0` → показать «0» (не прочерк)
  - `empty`: `has_data_for_period === false` → показать «—» / «нет данных»
  - `error_source`: `is_available === false` → показать сообщение об ошибке + кнопка retry
  - `error_forbidden`: `403 Forbidden` → показать «нет доступа»

- **Авторизация:**
  - Доступ: только роль «Администратор»
  - Где проверяется: 🟡 на бэке Арсенала, перед обработкой запроса (подтверждено аналитиком)
  - Негативный случай: если роль не Администратор → `403 Forbidden`

- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5

### Каталог ошибок
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 | `{ "error": "invalid_parameters", "message": "..." }` | Неверный period_type, некорректный формат даты | `error_source` (retry) |
| 401 | `{ "error": "unauthorized" }` | Отсутствует токен или невалидный | `error_source` |
| 403 | `{ "error": "forbidden", "message": "Only administrators can access activity summary" }` | Роль пользователя не Администратор | `error_forbidden` |
| 500 | `{ "error": "internal_error" }` | Внутренняя ошибка бэка (кроме таймаута) | `error_source` |
| 504 | `{ "error": "source_timeout" }` | Таймаут источника активности (5 сек) | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам
**Арсенал (backend):**
- Реализует эндпоинт `GET /api/admin/activity/summary` (INT-0) в соответствии с контрактом выше
- На каждый запрос собирает текущий счётчик активных пользователей
- По параметру `period_type` агрегирует историческую активность за запрошенный период
- Отдаёт флаг `is_available` в зависимости от доступности источника активности
- Различает состояния: есть данные / нет данных за период / источник недоступен (три разных сценария в ответе)
- Кэширует ответы на 30 секунд (на стороне бэка); см. раздел 5.1

### 3.2. Данные и хранение
🟡 Новых таблиц не заводим; данные активности собираются на лету из существующих источников Арсенала. Точный механизм сбора — подтверждено аналитиком (не по коду) как существующая возможность.

**Уточнение:** агрегаты активности вычисляются в памяти при запросе (no persistent aggregates), не хранятся отдельно.

### 3.3. Авторизация/доступ на бэке
🟡 Проверка роли «Администратор» выполняется на бэке Арсенала перед выполнением логики запроса (подтверждено аналитиком). Если роль не Администратор → немедленно возвращать `403 Forbidden`.

## 4. Frontend — ответственность

Этот раздел не применимо для узла-фундамента #0, так как #0 — BE-only контракт без UI. Фронтовые реализации (FR-1..FR-5) наследуют и потребляют INT-0 и отвечают за свои состояния в собственных спеках.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** 🟡 Синхронный запрос (подтверждено аналитиком); фронты получают ответ в рамках одного HTTP round-trip.
- **Кэш:** 🟢 На стороне бэка Арсенала; TTL = 30 секунд. Если в пределах 30 сек поступит второй запрос с теми же параметрами, вернуть кэшированный ответ.
- **Таймаут:** 🟢 5 секунд на получение данных от источника активности; если таймаут → вернуть `is_available: false` в ответе (или `504` если абсолютный таймаут истёк).
- **Частота опроса:** Фронты сами выбирают, как часто запрашивать (см. FR-2: не реже чем раз в минуту; FR-3–FR-5 запрашивают по клику и смене периода). Кэш 30 сек снижает нагрузку на источник.
- **Ожидаемая нагрузка:** не специфицирована в БТ; подходит текущей пропускной способности Арсенала (TBD если потребуется масштабирование в будущем).

### 5.2. Надёжность/деградация
- **При недоступности источника активности:** не отдавать устаревшие данные; отдать `is_available: false, current_active_count: null, aggregates: []` в ответе 2xx (или `500`/`504` в зависимости от природы сбоя).
- **При отсутствии данных за период:** различить от ошибки: отдать `has_data_for_period: false` и пустой массив `aggregates: []`, но `is_available: true`.

### 5.3. Безопасность/доступ (сводно)
| Граница | Что может | Кто | Где проверяется |
|---------|-----------|-----|-----------------|
| GET /api/admin/activity/summary | Прочитать текущую активность и историю | Администратор | Бэк Арсенала (HTTP-обработчик) |
| | Запрещено | Все остальные роли | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟢 Узел-фундамент #0 (эндпоинт + логика на бэке Арсенала) выкатывается **первым**, раньше дочерних фронтов (FR-1–FR-5). Дочерние реализации исходят из того, что INT-0 уже доступен в production.

### 6.2. Обратная совместимость
🟡 Нет текущих потребителей INT-0 (новый контракт). При будущих изменениях INT-0 (добавление полей, изменение enum) необходимо обеспечить backward-compatible расширение (новые поля в конце, старые не удалять).

### 6.3. Фиче-флаги
🟢 Фиче-флагов нет; релизим атомарно. Если необходимо скрывать панель активности от потребителей до готовности фронтов, это управляется фронтом (например, условный рендер компонента FR-1 в UI).

### 6.4. План отката
Узел #0 — BE-only, откат затрагивает только бэк:
- **Откат только Арсенала:** эндпоинт INT-0 перестаёт отвечать → фронты получат `5xx` → должны отобразить состояние `error_source` (retry). После отката фронты автоматически восстановят логику.
- **Откат за счёт выключения эндпоинта:** возвращать `503 Service Unavailable` вместо отката кода (если нужна плавная деградация).

### 6.5. Преднастройка до релиза (чек-лист)
- [ ] Роль «Администратор» существует в security-сервисе / IAM системе Арсенала

- [ ] Конфиги: TTL кэша (30 сек), таймаут источника (5 сек) — вынесены в конфиг (dev/staging/prod)
- [ ] Алерты на `5xx` ошибки эндпоинта и таймауты источника
- [ ] Логирование запросов с параметрами и ответов для отладки

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано Администратор, когда страница админки загружена, тогда запрашивается INT-0 и на странице отображается `current_active_count` (или «—» при ошибке) |
| FR-2 | INT-0 | Дано Администратор, когда активность пользователей изменилась, тогда INT-0 полингом запрашивается (не реже раза в минуту) и счётчик обновляется |

| FR-4 | INT-0 | Дано Администратор в модалке графика, когда выбирает другой period_type, тогда INT-0 запрашивается с новым period_type и график перестраивается |
