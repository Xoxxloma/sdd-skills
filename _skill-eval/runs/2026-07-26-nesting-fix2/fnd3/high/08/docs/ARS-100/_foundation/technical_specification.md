## 1. Обзор изменения

### 1.1. Тип и стороны
🟢 **BE-only.** Узел-фундамент #0 — чистая реализация на бэке, предоставляющая контракт данных активности пользователей. Потребители (дочерние узлы, фронтэнд-компоненты) наследуют этот контракт и обращаются к нему согласно его спецификации. Новых взаимодействий FE↔BE на уровне #0 нет; всё наследуется дочерними узлами.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (бэк) | Реализует контракт, предоставляет данные активности | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 обслуживает FR-1..FR-5 эпика ARS-100 в части получения данных активности пользователей (текущее число активных + агрегированная активность за выбранный период). Эти данные будут использованы дочерними узлами для отображения счётчика в шапке, графика в модали и выгрузки отчёта.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Потребители (дочерние узлы / фронтэнд-компоненты)
- **Триггер:** 
  - Загрузка страницы админки (получить текущий счётчик + начальный период графика)
  - Регулярный polling (каждые 10–30 сек) для обновления счётчика
  - Смена периода в модальном окне (получить данные за новый период)
  - Инициация выгрузки отчёта (получить данные за выбранный период)

- **Контракт (запрос):** 
  - **Метод + путь (концептуально):** `GET /arsenal/activity?period=<period>&granularity=<granularity>&start=<ISO8601>&end=<ISO8601>`
  - **Параметры:**
    - `period` (обязательный): `"hour"`, `"day"`, `"week"` — интервал для агрегации активности
    - `start` (обязательный): ISO8601 datetime — начало периода (например, `2026-07-26T00:00:00Z`)
    - `end` (обязательный): ISO8601 datetime — конец периода (например, `2026-07-26T23:59:59Z`)
    - `granularity` (опциональный): `"minute"`, `"hour"`, `"day"` — детализация временного ряда (по умолчанию — соответствует `period`)

- **Контракт (ответ):**
  - `current` (object) — текущее состояние активности:
    - `active_count` (integer): число активных пользователей на момент запроса; `null` = данные недоступны
    - `timestamp` (ISO8601): момент измерения
  - `period` (object) — параметры запрошенного периода:
    - `start` (ISO8601): начало периода
    - `end` (ISO8601): конец периода
    - `granularity` (string): используемая детализация (`"minute"`, `"hour"`, `"day"`)
  - `activity_series` (array of objects | null) — временной ряд активности за период:
    - `timestamp` (ISO8601): начало временного интервала
    - `active_count` (integer): число активных пользователей в этом интервале; `null` = нет данных
    - Если `status` = `"no_data_for_period"`, массив пуст или `null`
  - `summary` (object | null) — статистика за период (для экспорта):
    - `min_count` (integer | null): минимум активных за период
    - `max_count` (integer | null): максимум активных за период
    - `avg_count` (number | null): среднее число активных
    - `total_user_sessions` (integer | null): итоговое число сессий за период
    - `data_points_count` (integer): количество измерений в периоде
    - Если `status` = `"no_data_for_period"`, поля могут быть `null` или объект может быть `null`
  - `status` (string) — статус доступности данных:
    - `"available"` — данные свежие, полученные от источника
    - `"source_unavailable"` — источник недоступен, текущие данные не получены; `current` = `null`, `activity_series` = `null`, `summary` = `null`
    - `"no_data_for_period"` — источник доступен, но за запрошенный период активности не обнаружено; `activity_series` пусто, `summary` поля = `null`
  - `error_details` (object | null) — детали ошибки при `status` ≠ `"available"`:
    - `code` (string): код ошибки (`"source_unavailable"`, `"timeout"`, `"no_data"`)
    - `message` (string): описание на русском

- **Пример запроса:**
  ```
  GET /arsenal/activity?period=day&start=2026-07-26T00:00:00Z&end=2026-07-26T23:59:59Z&granularity=hour
  ```

  - `504 Gateway Timeout` — таймаут при обращении к источнику (5 сек). Возвращается JSON с `status: "source_unavailable"` (не текстовая ошибка).
  - `5xx Server Error` — внутренняя ошибка Arsenal. Тело: `{ "error": "Internal server error" }`

  - **`zero`**: 2xx, `status = "available"`, `current.active_count = 0` → отображение «0» (не прочерк)
  - **`empty`**: 2xx, `status = "no_data_for_period"` → отображение «—» / «нет данных за период»
  - **`error_source`**: `status = "source_unavailable"` или 5xx → сообщение об ошибке + retry-кнопка
  - **`error_forbidden`**: 403 → «нет доступа»

  - **Негативный случай:** запрос от пользователя без роли `Administrator` → 403 Forbidden

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- Реализует контракт INT-0: обработка GET-запроса к `/arsenal/activity` с параметрами `period`, `start`, `end`, `granularity`
- Собирает данные активности пользователей из своего источника (🟡 подтверждено аналитиком, не по коду)
- Агрегирует активность по временным интервалам согласно параметру `granularity`
- Вычисляет статистику (`min`, `max`, `avg`, `total_sessions`) для периода
- Кэширует результат на 30 сек (TTL = 30s) для одного и того же набора параметров
- Возвращает корректный статус (`available`, `source_unavailable`, `no_data_for_period`) с `error_details` при необходимости
- Проверяет роль `Administrator` перед возвратом данных (авторизация)

### 3.2. Данные и хранение

🟡 **Подтверждено аналитиком:** Агрегаты активности считаются на лету, новых таблиц не заводим. Arsenal backend использует существующий источник данных активности пользователей (подтвердить при интеграции, какой именно — таблица сессий, external tracking service и т.п.).

**Индексы:** При необходимости добавить индексы на колонки, используемые для фильтрации по временным интервалам в источнике данных (уточнить при интеграции на основе реальной схемы).

**Кэш:** 30 сек на стороне Arsenal backend (in-memory или Redis — по выбору команды). Ключ кэша: хэш параметров `(period, start, end, granularity)`.

**TTL данных:** Поскольку данные вычисляются на лету, никакой специальной retention-политики не требуется; рассчитываются за любой исторический период, запрошенный клиентом.

### 3.3. Авторизация/доступ на бэке

- Проверка роли `Administrator` перед обработкой запроса к INT-0
- Использование security-сервиса для валидации роли текущего пользователя (🟡 подтверждено аналитиком)
- При отсутствии роли → ответ 403 Forbidden

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** 🟢 Синхронный запрос-ответ (REST GET)
- **Кэш:** 🟡 Подтверждено аналитиком — 30 сек на стороне бэка Arsenal (после первого запроса с параметрами `(period, start, end, granularity)` результат кэшируется и переиспользуется для идентичных параметров в течение 30 сек)
- **Таймаут:** 🟡 Подтверждено аналитиком — 5 сек. Если источник данных не ответил в 5 сек, Arsenal возвращает INT-0 ответ с `status = "source_unavailable"` (не текстовая ошибка)
- **Частота опроса:** Зависит от потребителя (дочернего узла). Рекомендация для счётчика (FR-1, FR-2): polling каждые 10–30 сек, детали в спеке дочерних узлов
- **Ожидаемая нагрузка:** Определяется числом администраторов и частотой polling'а; уточнить при планировании мониторинга

### 5.2. Надёжность/деградация

🟡 **Подтверждено аналитиком:**
- При недоступности источника данных активности Arsenal **не кэширует** старое значение и не выдаёт его за актуальное, а возвращает `status = "source_unavailable"` с соответствующей ошибкой в `error_details`
- При таймауте (5 сек) к источнику также возвращается `status = "source_unavailable"`
- Отсутствие данных за период (valid empty result) отличается от источника-недоступен: возвращается `status = "no_data_for_period"` с пустой `activity_series` и `null` в полях `summary`
- Дочерние узлы обязаны различать эти состояния в UI (см. `error_source` и `empty` в §4.3)

### 5.3. Безопасность/доступ (сводно)

| Граница | Потребитель | Условие | Действие |
|---------|-------------|---------|----------|
| INT-0 | Фронтэнд дочерних узлов (компоненты для администраторов) | Роль = `Administrator` | ✅ Доступ к данным |
| INT-0 | Фронтэнд дочерних узлов | Роль ≠ `Administrator` | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 **Подтверждено аналитиком:** Узел-фундамент #0 выкатывается **раньше** дочерних узлов (ARS-101, ARS-102, ARS-103). Дочерние узлы зависят от контракта INT-0, поэтому Backend должен быть готов к запросам по этому контракту до того, как дочерние фронтэнды начнут его вызывать.

**Последовательность:**
1. Backend Arsenal (реализация INT-0, контракт готов)
2. Дочерние узлы (потребляют INT-0)

### 6.2. Обратная совместимость

Поскольку узел-фундамент #0 — новая функциональность, обратная совместимость не критична. Существующие потребители Arsenal admin не будут затронуты (панель активности добавляется, не заменяет существующее).

### 6.3. Фиче-флаги

🟡 **Подтверждено аналитиком:** Фиче-флагов нет. Релизим функцию атомарно: когда контракт INT-0 готов на бэке и дочерние узлы готовы его потреблять, релизим вместе.

### 6.4. План отката

- **Откат только Backend (INT-0):** Дочерние фронтэнды получат ошибку (5xx / timeout). Должны отображать `error_source` состояние (спиннер + retry). Синхронный откат Frontend не требуется (могут остаться на старой версии, увидят ошибку и переопубликуют когда Backend вернётся).
- **Откат только Frontend:** Backend продолжит возвращать INT-0, но никто его не будет вызывать. Безвредно.
- **Откат миграций данных:** Не применимо (новых таблиц нет, данные вычисляются на лету).

### 6.5. Преднастройка до релиза

- [x] Роли в security-сервисе: роль `Administrator` должна быть доступна нужным пользователям (уточнить при интеграции — используется существующая роль или новая)

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано открыта админка пользователем-администратором, когда страница загрузилась, тогда в шапке отображается число активных пользователей из INT-0 (поле `current.active_count`). |
| FR-2 | INT-0 | Дано открыта админка, когда фронтэнд периодически вызывает INT-0 (polling), тогда счётчик обновляется при получении нового значения `current.active_count`. |
| FR-3 | INT-0 | Дано счётчик активности в шапке, когда администратор кликает на него, тогда модальное окно открывается и отображает график активности за период по умолчанию (из INT-0 поле `activity_series`). |
| FR-4 | INT-0 | Дано открытое модальное окно, когда администратор выбирает другой период (hour/day/week), тогда INT-0 вызывается с новыми параметрами `period`, `start`, `end`, и график перестраивается на основе полученного `activity_series`. |
| FR-5 | INT-0 | Дано открытое модальное окно с выбранным периодом, когда администратор нажимает кнопку выгрузки, тогда INT-0 вызывается с параметрами периода и фронтэнд готовит CSV/Excel с данными из `summary` и `activity_series`. |
