### BS2-03
### 4.5. Разбиение на слайсы

**ШАГ 1 — решение.**

1. **Числа:** 4 функциональных требования (FR-1, FR-2, FR-3, FR-4).
2. **Ценность каждого кандидата слайса:**
   - Счётчик активных пользователей (FR-1) — администратор видит текущую нагрузку на систему и может принимать решения на основе текущего статуса.
   - График активности за период (FR-2, FR-3) — администратор видит динамику активности пользователей, выявляет закономерности и выбирает оптимальные окна для работ.
   - Выгрузка сводки (FR-4) — администратор может отчитаться перед руководством и аудитом по нагрузке за период.
3. **Порог:** 4 FR и 3 потенциальных слайса, каждый со своей бизнес-ценностью.
4. **Типовой исход:** Порог ≥4 FR обычно указывает на эпик, но данном случае все три компонента жёстко связаны единой бизнес-целью «видеть активность пользователей» (текущую, историческую, отчётную). Счётчик без возможности посмотреть динамику даёт лишь моментальный снимок; модалка без счётчика лишена удобного входа; выгрузка имеет смысл только в контексте просмотра графика. Разделение на слайсы нарушит целостность ценности: администратор нуждается в полной видимости активности, которую даёт только совокупность всех трёх элементов.

**Вывод:** не применимо — все три функциональных элемента (счётчик, график, выгрузка) являются частями единого функционала наблюдения за активностью пользователей и выпускаются вместе.

### BS2-10
## 4.5. Разбиение на слайсы

**ШАГ 1 — анализ разреза:**

1. Числа: 3 функциональных требования (счётчик, график, выгрузка).
2. Ценность каждого: 
   - Счётчик: администратор видит текущую активность, может оценить нагрузку прямо сейчас.
   - График: администратор видит динамику нагрузки за выбранный период, может анализировать тренды.
   - Выгрузка: администратор может подготовить отчёт по активности за период.
3. Порог: 3 FR, 3 кандидата на ценность — пороговый критерий сработал.
4. Однако: график и выгрузка открываются только по клику на счётчик (модальное окно в отрыве от счётчика нефункционально). Это не архитектурная зависимость, а функциональная необходимость: счётчик — это точка входа, без него граф и выгрузка недоступны и не имеют смысла пользователю.
5. Вывод: **одна работа, схлопываем в один деливербл.**

**Причина:** Счётчик, график и выгрузка компонуют единый пользовательский сценарий наблюдения за активностью. График и выгрузка — не самостоятельные функции, а расширения счётчика через модальное окно, открывающееся по клику. Ни одна часть не даёт администратору полезного результата без остальных в отрыве от этого сценария; модальное окно без счётчика как точки входа — это тупик. Разрез между счётчиком и модалкой технически выполним, но бизнес-смысл не разбивается: обе части вместе — это одна фича «видимость активности».

**Не применимо:** Функционал едина работа, слайцирование не требуется. На этапе реализации тимлид и аналитик определяют этапы разработки; бизнес-слайсов здесь нет.

| 3 | Фильтрация статусов на схеме | FR-3 | Мастер концентрируется на нужном оборудовании, не отвлекаясь на остальное | Слайс 1 |

### BS6-03
## 4.5. Разбиение на слайсы

**Анализ разбиения:**

1. Число требований: 5 FR.
2. Ценность каждого кандидата:
   - FR-1 (загрузка): метролог актуализирует данные о поверках в системе.
   - FR-2 + FR-3 (подсвечивание и фильтрация): мастер видит только нужное оборудование, отсекая остальное.
   - FR-4 (карточка): мастер находит ответственного и плановые сроки.
   - FR-5 (поиск): быстрый поиск нужного прибора по номеру.

3. Порог срабатывает? Есть 5 FR и выглядят как разные функции. Но проверим зависимости:
   - FR-1 (загрузка) — необходимый предусловие. Без него нет данных вообще.
   - FR-2 (подсвечивание) зависит от FR-1: без данных нечего подсвечивать.
   - FR-3 (фильтрация) работает с FR-2: нечего фильтровать, если нет отображения.
   - FR-4 (карточка) зависит от FR-2: клик срабатывает только на видимом приборе.
   - FR-5 (поиск) зависит от FR-2: поиск подсвечивает уже отображённый прибор.

4. Может ли бизнес получить ценность от части? 
   - Только загрузка (FR-1) без отображения: нет, данные не видны.
   - Отображение (FR-2, FR-3) без загрузки: нет, нет данных.
   - Карточка (FR-4) без отображения: нет, как открыть, если прибор невидим?
   - Поиск (FR-5) без отображения: нет, подсветить нечего.
   
   **Вывод:** ни одна часть не даёт бизнесу независимой ценности, пока не выпущены остальные. Каждый компонент — звено единого потока: сначала данные загружаются, затем отображаются и фильтруются, из отображённой схемы открывается карточка, поиск подсвечивает на уже отображённой схеме.

**Решение:**

```
Не применимо: все компоненты функционала образуют единый поток и зависят друг от друга. 
Загрузка без отображения не даёт мастеру информации. Отображение без загрузки невозможно. 
Карточка открывается только со схемы. Поиск работает только на видимой схеме. 
Ни один компонент не может быть выпущен отдельно и дать бизнесу что-либо полезное. 
Вся работа — одна поставка в производство.
```
