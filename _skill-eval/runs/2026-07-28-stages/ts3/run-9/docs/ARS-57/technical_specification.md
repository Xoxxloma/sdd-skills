## 1. Обзор изменения

### 1.1. Тип и стороны
🟢 **Fullstack.** Веб-админка «Арсенал» (фронтенд и бэкенд) добавляет новое взаимодействие с существующим сервисом аутентификации для получения числа активных пользователей и отображает его в шапке.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (фронтенд) | Новое отображение индикатора в шапке | Команда Арсенал-Core | 🟢 новое |
| Арсенал (бэкенд) | Новое взаимодействие с auth-сервисом; кэширование и пуллинг | Команда Арсенал-Core | 🟢 новое |
| Сервис аутентификации | Существующий источник числа активных сессий | Команда Security / Аутентификация | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями
Задача реализует две из трёх бизнес-требований напрямую через фронтенд-бэкенд контракт (FR-1, FR-2) и одно через обработку недоступности (FR-3). Новый индикатор позволяет администратору видеть текущую нагрузку и безопасно планировать регламентные работы.

## 2. Взаимодействия (ядро)

### INT-1. Получить число активных пользователей — 🟢 (новое)
- **Граница/направление:** Веб-фронтенд Арсенала → бэкенд Арсенала
- **Триггер:** Инициализация шапки при загрузке страницы; затем периодический пуллинг (раз в минуту).
- **Контракт (запрос):** 
  - **Метод + путь (концептуально):** `GET /api/arsenal/users/active-count` (или эквивалент в используемом фреймворке)
  - **Параметры/заголовки:** отсутствуют; аутентификация на уровне сессии фронтенда (существующий механизм).
- **Контракт (ответ):**
  - `count` (целое число или `null`): число активных пользователей; `null` → источник недоступен, UI показывает «—» вместо числа.
  - Поля ответа: `{ "count": number | null }`
  - **Семантика `null`:** признак недоступности источника (сервис аутентификации недостижим или вернул ошибку); клиент обрабатывает как «нет данных» и отображает прочерк.
- **Пример запроса:** Тело отсутствует (GET без параметров); заголовки стандартные (авторизация в сессии).
- **Пример ответа (успех):**
  ```json
  { "count": 42 }
  ```
  Успех: число получено и >= 0.
- **Пример ответа (источник недоступен):**
  ```json
  { "count": null }
  ```
  Эта форма выбирается, когда бэк не может получить актуальное число (timeout, ошибка сервиса аутентификации, кэш пуст после перезагрузки сервиса).
- **Ошибки:** 
  - Сервис бэка недоступен → HTTP 5xx или timeout → фронт показывает «—» (то же, что `count: null`).
  - Другие стандартные ошибки (401 Unauthorized, 403 Forbidden) → при ролевых ограничениях; см. авторизацию ниже.
- **Состояния UI по ответу:**
  - Значение (ответ с `count` >= 0) → отображать число в виде текста («42 пользователей» или просто «42»).
  - Загрузка (запрос в пути, до ответа) → показать спиннер / иконку загрузки на месте числа.
  - Пусто/«—» (ответ с `count: null` или ошибка) → отображать прочерк «—» без числа.
  - Ошибка (4xx/5xx при выполнении запроса) → обработать как `count: null`, показать «—» (логически ошибка = нет данных).
- **Авторизация:**
  - Эндпоинт доступен только учётным записям с ролью **Администратор**.
  - Проверка: на уровне бэка Арсенала (middleware/контроллер проверяет роль в сессии/токене).
  - Негативный случай: запрос с ролью Оператор → HTTP 403 Forbidden (бэк отклоняет); фронт обрабатывает как ошибку → показывает «—».
  - Общий механизм авторизации: роли хранятся в сервисе аутентификации и достижимы через механизм, предусмотренный для админки (не меняется в этой задаче).
- **Происхождение:** 🟢 новое (спроектировано полностью)
- **Трассировка:** FR-1 (отображение на странице загрузки), FR-2 (обновление без перезагрузки), FR-3 (показ «—» при недоступности)

### INT-2. Запрос к сервису аутентификации для получения счёта активных сессий — 🟡 (подтверждено, детали к валидации)
- **Граница/направление:** Бэкенд Арсенала → сервис аутентификации
- **Триггер:** Бэк вызывает при получении запроса INT-1 от фронта (если кэш истёк или отсутствует). Логика: при каждом запросе от фронта проверить, актуален ли кэш (TTL 30 сек); если нет — обновить из auth-сервиса.
- **Контракт (запрос/ответ):** 
  - 🟡 подтверждено аналитиком: сервис аутентификации **уже умеет отдавать число активных сессий**. Бэк Арсенала будет вызывать этот существующий эндпоинт.
  - 🟡 к валидации: **точный путь, метод и структура ответа этого эндпоинта** — уточнить у владельца сервиса аутентификации или в документации.
- **Кэширование:** результат кэшируется в бэке Арсенала на **30 секунд**. При TTL истечении кэш признаётся невалидным и следующий вызов INT-1 получит свежие данные с auth-сервиса.
- **Обработка ошибок:** если auth-сервис недоступен или возвращает ошибку, бэк возвращает `{ "count": null }` в INT-1 (состояние: показать «—» на фронте).
- **Происхождение:** 🟡 подтверждено аналитиком (существующий сервис), эндпоинт 🟡 к валидации
- **Трассировка:** опосредованно через FR-1/FR-2 (INT-1 зависит от INT-2)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 | `{ "count": <число> }` | Успешно получено число активных пользователей | Отображать число |
| 200 | `{ "count": null }` | Auth-сервис недоступен, но запрос к Арсеналу обработан | Показать «—» |
| 403 | Forbidden (стандартное сообщение) | Запрашивающий пользователь не имеет роль Администратор | Показать «—» + не запрашивать индикатор дальше |
| 5xx / timeout | (любое) | Бэк Арсенала недоступен или timeout при запросе к auth-сервису | Показать «—» + retry по логике фронта (пуллинг продолжается) |

## 3. Данные и хранение

**Не применимо:** новых сущностей, таблиц или постоянного хранения не требуется. Данные (число активных сессий) получаются от сервиса аутентификации в реальном времени; кэширование — временное, в памяти процесса бэка (TTL 30 сек).

## 4. Логика фронтенда (UI и состояния)

### 4.1. Компонент индикатора
- **Расположение:** в шапке админки (header/top-bar), видимое для роли Администратор.
- **Визуальное оформление:** 🟢 неяркий стиль (пожелание из БТ, §1.3), не отвлекает от основного контента.
- **Отображение:**
  - Число >= 0 и получено: `"42 пользователей онлайн"` или `"42 в сети"` (точный текст — на согласование с дизайном).
  - `null` или ошибка: `"—"` (прочерк, без указания причины, чтобы не пугать администратора).
  - Загрузка данных (первый запрос или refresh): спиннер на месте числа.

### 4.2. Жизненный цикл и обновление
- **Инициализация:** при загрузке страницы фронт отправляет GET INT-1 сразу (→ FR-1).
- **Периодическое обновление:** после получения первого ответа, фронт устанавливает интервал пуллинга **раз в 60 секунд** (→ FR-2).
- **Управление интервалом:** если пуск фронта → очистить интервал (на случай переходов между страницами); если фронт получил ошибку 403 → остановить пуллинг для этого пользователя (роль не поддерживается).

### 4.3. Обработка состояний
| Случай | Действие фронта |
|--------|-----------------|
| Страница загружена | Отправить INT-1 сразу; стартовать интервал на 60 сек |
| Ответ 200 `{ "count": 42 }` | Показать число; обновить интервал (может быть отложен, если число не изменилось, но фронт не оптимизирует пока что) |
| Ответ 200 `{ "count": null }` | Показать «—» |
| Ответ 403 Forbidden | Показать «—»; остановить интервал; индикатор на странице скрыть или сделать неинтерактивным |
| Ответ 5xx / timeout | Показать «—»; сохранить интервал (retry произойдёт в следующий tick) |
| Запрос в пути (до ответа) | Показать спиннер (или затемнить текст, если число было раньше) |

## 5. Нефункциональные требования и интеграция

### 5.1. Производительность и синхронность
- **Синхронизация:** асинхронный пуллинг (не блокирует UI). Фронт использует стандартный fetch / HTTP-клиент админки.
- **Интервал опроса:** 60 секунд (как подтверждено аналитиком). Фронт гарантирует, что интервалы не накладываются (не более одного запроса в полёте одновременно; простой debounce).
- **Кэш на бэке:** TTL = 30 секунд. Логика: при каждом INT-1 от фронта бэк проверяет, прошло ли 30 сек с последнего вызова к auth-сервису; если нет — возвращает кэшированное значение; если да — обновляет.
- **Ожидаемые задержки:** фронт получает ответ в пределах 2–5 сек (SLA по админке); если задержка > 5 сек, фронт может отобразить «—» и пересказать попытку в следующий интервал.

### 5.2. Надёжность и обработка отказов
- **Таймаут запроса:** 5 секунд; при превышении — timeout считается как ошибка (показать «—»).
- **Retry:** не требуется на уровне INT-1; пуллинг каждые 60 сек служит retry-механизмом.
- **Остановка пуллинга:** 
  - При 403 Forbidden (ролевое ограничение) — остановить, не повторять.
  - При 5xx > 3 раз подряд — может быть логировано как проблема; пуллинг может продолжаться (при условии, что бэк не в полном отказе).

### 5.3. Авторизация и безопасность
- **Ролевой контроль:** фронт не скрывает индикатор на клиенте (скрытие — не security); бэк проверяет роль (Администратор) для каждого INT-1.
- **Защита роли Администратор:** настраивается в сервисе аутентификации до релиза (преднастройка, не входит в эту задачу, но указана как этап выката).
- **Логирование:** бэк может логировать запросы INT-1 для аудита доступа к счётчику (уровень: мейнтейнинговый, не критичен для функции).

## 6. Порядок выката и совместимость

### 6.1. Этапы и зависимости
**Расчет:** задача включает одну логику со своей предметной границей — получение и отображение счётчика. Разреза по фронт/бэк хватает для независимых работ, но в данном случае оба куска функционируют как единое целое (фронт без бэка не получает данные, бэк без фронта не вызывается). Однако выкат имеет **жёсткий порядок**.

| # | Этап | Вход (шов) | Выход (шов) | Проверка в одиночку |
|---|------|-----------|-------------|---------------------|
| 01 | Реализация и развёртывание бэка Арсенала (INT-1 эндпоинт + кэширование + вызов auth-сервиса) | — (этап первый) | INT-1: GET `/api/arsenal/users/active-count` с возвратом `{ "count": number\|null }` | Прямой вызов эндпоинта; проверить: а) успешный ответ с числом; б) null при недоступности auth-сервиса; в) 403 при недостаточных правах; г) кэш работает (второй запрос возвращает тот же результат в течение 30 сек) |
| 02 | Реализация и развёртывание фронта Арсенала (компонент индикатора + пуллинг каждые 60 сек) | INT-1 эндпоинт (из этапа 01) | Видимый на странице индикатор в шапке | Загрузить страницу админки; убедиться: а) индикатор загружается и показывает число; б) спиннер появляется при загрузке; в) интервал работает (число обновляется ~1x/мин); г) при 403 индикатор скрывается или показывает «—» |

**Условие для перехода к 02:** бэк развёрнут и INT-1 проверен в prod или staging (шов готов).

**Порядок выката в prod:** 01 (бэк) → 02 (фронт). Нельзя выкатывать фронт раньше бэка (фронт получит 404 или 503).

### 6.2. Обратная совместимость и rollback
- **Обратная совместимость:** нет. Задача добавляет новый эндпоинт INT-1, которого нет в текущем бэке. Старые версии фронта (из кэша браузера) не будут вызывать этот эндпоинт (нет такой логики), поэтому конфликтов нет.
- **Rollback:** если нужно откатить фронт — индикатор просто исчезнет из UI; если откатить бэк — новый фронт получит 404, который обработает как ошибку (показать «—»). Выката за выкат можно делать независимо.

### 6.3. Преднастройки и конфиги до релиза
1. **Роль Администратор:** убедиться, что роль существует в сервисе аутентификации и назначена нужным пользователям (администраторам). Это делается в рамках регулярного управления ролями, но перед релизом проверить, что целевая группа администраторов имеет эту роль.
2. **Фича-флаг (опционально):** если требуется постепенный rollout, можно добавить фича-флаг, который управляет отображением индикатора на фронте (не критично для функции, но рекомендуется для контроля нагрузки на auth-сервис).
3. **Документирование:** обновить документацию админки (Release Notes), чтобы администраторы узнали о новом индикаторе.
