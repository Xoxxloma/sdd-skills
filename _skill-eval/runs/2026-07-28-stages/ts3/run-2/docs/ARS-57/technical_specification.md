## 1. Обзор изменения
### 1.1. Тип и стороны
Fullstack. Админка «Арсенал» (фронт + бэк) получает число активных пользователей из существующего сервиса аутентификации и отображает его в шапке в режиме реального времени (пуллинг).

### 1.3. Связь с бизнес-требованиями
Реализует FR-1, FR-2, FR-3 из БТ: администратор видит в шапке актуальное число активных пользователей и может оценить нагрузку перед регламентными работами; обновление автоматическое без перезагрузки; при недоступности источника показывается «—», не ошибка.

## 2. Взаимодействия (ядро)

### INT-1. Запрос числа активных пользователей (фронт → бэк) — 🟢
- **Граница/направление:** FE Арсенала → BE Арсенала
- **Триггер:** Периодический пуллинг (раз в минуту); первый запрос при загрузке страницы.
- **Контракт (запрос):** `GET /api/admin/active-users-count`; без тела, без параметров.
- **Контракт (ответ):** 
  - `count` (integer | null) — число активных сессий. `null` означает источник недоступен (не ошибка HTTP, а признак деградации). **Семантика**: `null` → показать «—», число ≥ 0 → показать число.
- **Пример запроса:**
  ```
  GET /api/admin/active-users-count
  ```
- **Пример ответа (успех):**
  ```json
  {
    "count": 42
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null
  }
  ```
- **Ошибки:** 
  - 403 Forbidden — пользователь не в роли «Администратор» (не должна возникнуть, т.к. виджет скрыт на уровне UI, но поведение на случай разогласования).
  - 5xx / таймаут сети — бэк обрабатывает как `count: null` и отдаёт 200 с таким телом (см. выше).
- **Состояния UI по ответу:**
  - `loading` — первый запрос или после инвалидации: спиннер/скелетон.
  - `value` — 2xx, `count` — положительное число: показать число.
  - `empty` — 2xx, `count: null`: показать прочерк «—».
  - `error_forbidden` — 403: скрыть виджет (на уровне UI недопустимо; сюда не должны попасть, но поведение определено).
- **Авторизация:** Вызывать может только пользователь в роли «Администратор». Проверка на бэке при входящем запросе.
- **Происхождение:** 🟢 новое взаимодействие
- **Трассировка:** FR-1, FR-2, FR-3

### INT-2. Запрос числа активных сессий (бэк Арсенала → сервис аутентификации) — 🟡 к валидации
- **Граница/направление:** BE Арсенала → сервис аутентификации
- **Триггер:** Когда истекает TTL кэша (30 сек) или кэш инвалидирован.
- **Контракт (запрос):** 🟡-к-валидации
- **Контракт (ответ):** 🟡-к-валидации — TBD, точный формат уточнить при интеграции.
- **Происхождение:** 🟡 к валидации (сервис аутентификации подтверждает, что может считать активные сессии; точный контракт — открытый вопрос).

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 | `{"count": 42}` | Успех, данные есть | `value` |
| 200 | `{"count": null}` | Источник (auth-сервис) недоступен или таймаут | `empty` (показать «—») |

## 2.5. Этапы работ и порядок сборки

Не применимо: одна работа. Задача не разбивается на этапы со своей предметной логикой — это единый fullstack-контракт INT-1 между фронтом и бэком Арсенала (бэк получает от auth-сервиса по INT-2, кэширует и отдаёт фронту; INT-2 — реализация детали INT-1, не отдельный этап). Разработчики фронта и бэка пишут параллельно против одного контракта INT-1.

## 3. Backend — ответственность

### 3.1. По сервисам
**Арсенал (бэк):**
- Реализует эндпоинт INT-1 (`GET /api/admin/active-users-count`).
- Поддерживает кэш числа активных сессий (TTL 30 сек, см. §5.1).
- При каждом запросе INT-1: если кэш свежий (< 30с), отдаёт из кэша; иначе вызывает INT-2, кэширует результат, отдаёт.
- При недоступности INT-2 (5xx, таймаут, сеть): возвращает `{"count": null}` без повторных попыток в пределах одного запроса.
- Авторизация: проверяет, что вызывающий в роли «Администратор» (см. §3.3).
- Трассировка: логирует попытки INT-2 (успех / таймаут / 5xx) в структурированном виде (для мониторинга отказов auth-сервиса).

**Сервис аутентификации:**
- 🟡 Подтверждено аналитиком (не по коду): уже считает активные сессии и может их отдать.
- Точный контракт INT-2 — к валидации (см. §8).

### 3.2. Данные и хранение
Новых сущностей и таблиц нет. Кэш INT-2 держится в памяти бэка Арсенала (ассоциативный массив / dict с TTL), не в БД.

### 3.3. Авторизация/доступ на бэке
- Эндпоинт INT-1 защищен проверкой роли «Администратор». Если роль отсутствует → 403 Forbidden.
- Проверка выполняется до вызова INT-2 (не тратим ресурсы на запрос в auth-сервис для неавторизованного пользователя).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Шапка админки: добавляется новый элемент (индикатор/виджет) с числом активных пользователей или прочерком «—» при недоступности. Расположение: уточнить с дизайном (пожелание из БТ: неяркий, не отвлекает).

### 4.2. Пользовательские сценарии
- **Основной поток (FR-1, FR-2):** Администратор открывает админку → страница загружается → в шапке появляется спиннер → бэк отвечает → виджет показывает число. Далее виджет автоматически обновляется (polling каждую минуту): спиннер между запросами (пока в полёте) → новое число или «—».
- **Ветвление (FR-3):** Если источник данных недоступен (бэк получил INT-2 с ошибкой), виджет показывает «—» вместо числа или ошибки. Не генерирует всплывающие алерты (деградация молчаливая).

### 4.3. Состояния (именованные — обязательно, если есть FE)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | Первый запрос (до первого ответа) или после инвалидации (вручную по кнопке retry) | Спиннер / скелетон числа |
| `value` | 2xx, `count` — положительное целое число (≥ 0, ≠ null) | Число (напр. «42») |
| `empty` | 2xx, `count: null` — источник недоступен | Прочерк «—» |
| `error_forbidden` | 403 Forbidden | Виджет скрыт (на UI не видно, недопустимо попасть, но обработано) |

### 4.3.1. Loading и таймауты
- **Cold-path (первый запрос):** Таймаут ожидания спиннера — **1.5 сек** (обычный таймаут cold).
- **Warm-path (polling):** Таймаут последующих запросов — **3 сек** (спинер виден дольше, т.к. значение уже известно и пользователь может работать).
- **Polling:** Интервал **60 сек** (раз в минуту); jitter ± 5 сек для избежания синхронизации нескольких браузеров.
- **На таймаут / 5xx / сеть:** Показываем `empty` (прочерк «—»), не ошибку; локально логируем (в DevTools) для отладки.

### 4.4. Доступ по ролям в UI
- **Администратор:** Видит виджет с числом (или «—»).
- **Оператор:** Виджет не видит — скрыт на уровне компонента ещё до первого запроса (ролевая модель из БТ).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **INT-1 (фронт → бэк):** Синхронный HTTP GET.
- **INT-2 (бэк → auth-сервис):** Синхронный HTTP; в цепи INT-1 (бэк опрашивает auth-сервис по мере необходимости).
- **Кэш:** В памяти бэка Арсенала, TTL **30 сек**. Выбор 30 сек обоснован: мена по FR-2 — обновление в пределах минуты, 30 сек — разумный баланс между свежестью и нагрузкой на auth-сервис.
- **Polling:** Интервал фронта **60 сек** (раз в минуту из БТ). Jitter ± 5 сек.
- **Ожидаемая нагрузка:** Один запрос INT-1 в минуту на браузер admin'а; на 100 одновременных admin'ов — 1–2 запроса в сек на бэк Арсенала; INT-2 — один раз в 30 сек на бэк Арсенала (за счёт кэша). Детальный расчёт — при проектировании.

### 5.2. Надёжность/деградация
- При недоступности INT-2 (5xx, таймаут, сеть): бэк отдаёт `{"count": null}` с 200 OK (не 5xx). Это не ошибка приложения, а информация о деградации (источник недоступен).
- Фронт показывает «—» и не генерирует ошибку пользователю (требование из БТ, §2.3 risk mitigation).
- Таймаут INT-2 на бэке: **5 сек** (стандартный для cross-service; может быть уточнён при интеграции).
- Никакой retry-логики в цепи INT-1 → INT-2: одна попытка за запрос, затем `count: null`.

### 5.3. Безопасность/доступ (сводно)
- **Авторизация:** Эндпоинт INT-1 защищен проверкой роли «Администратор» на бэке.
- **UI:** Компонент скрыт для других ролей (Оператор).
- **Данные:** Число активных сессий — неконфиденциальная информация (видна админу), уточнить при интеграции.

## 6. Релиз и интеграция

### 6.1. Порядок выката
1. **BE Арсенала** (эндпоинт INT-1 + логика кэша): разворачиваем первым.
2. **FE Арсенала** (компонент виджета + polling): разворачиваем после, когда INT-1 работает.

**Обоснование:** FE зависит от нового контракта INT-1, который изначально не существует. Если развернуть FE раньше BE, FE будет получать 404 при запросе INT-1. Обратный порядок безопасен: BE уже может отдавать INT-1, но старый FE его не запрашивает.

### 6.2. Обратная совместимость
- **Для текущего FE:** BE Арсенала добавляет новый эндпоинт INT-1, не трогает существующие. Текущий FE не знает о INT-1 и не вызывает его → совместимость не ломается.
- **Для текущего BE:** Ничего не меняется (новый эндпоинт).

### 6.3. Фиче-флаги
Релизим атомарно: фиче-флаги не нужны. Новый эндпоинт включен сразу после деплоя BE. Если нужна поэтапная раскатка — уточнить с аналитиком; пока спека исходит из полного выката.

### 6.4. План отката
- **Откат только BE:** Если откатить BE (INT-1 снова 404), новый FE будет получать 404. На это нужен синхронный откат FE (скрыть виджет или показать «—»). **Требует синхронной раскатки обеих сторон.**
- **Откат только FE:** Старый FE не запрашивает INT-1; BE продолжает работать. Безопасен.
- **Откат DDL:** Не применимо (БД не меняется).

**Вывод:** После выката обеих сторон откатываться нельзя независимо. В случае critical issue на BE → откатываем сразу BE + FE (не пытаемся откатить только одну сторону).

### 6.5. Преднастройка до релиза (чек-лист)
- [ ] **Роли в security-сервисе:** Роль «Администратор» должна быть заведена и назначена тестовому пользователю/группе. Валидировать перед выкатом в prod (при выкате в staging можно тестировать на существующих ролях).
- [ ] **DDL-миграция:** Не применимо (новых таблиц нет).
- [ ] **Конфиги по окружениям:** TTL кэша (30 сек), интервал polling (60 сек), таймауты (cold 1.5s, warm 3s, INT-2 5s) — внести в конфиг. Возможны разные значения для dev/staging/prod (обычно staging близок к prod, dev может быть свободнее).
- [ ] **Сервисные аккаунты:** Если INT-2 требует аутентификации сервис-сервис (TBD при валидации INT-2), завести и настроить учётную запись бэка Арсенала в auth-сервисе.
- [ ] **Фиче-флаги:** Не нужны (полный выкат).
- [ ] **Алерты/мониторинг:** На бэке логируем ошибки INT-2 (5xx, таймаут). Завести алерт на частоту ошибок: если > 10% INT-2 за 5 мин → уведомление.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано открытую админку, когда страница загружена и пользователь в роли «Администратор», тогда в шапке отображается число активных пользователей (или «—» если источник недоступен). |
| FR-2 | INT-1 + polling | Дано открытую админку с видимым счётчиком, когда число активных пользователей изменилось на auth-сервисе, тогда счётчик в админке обновляется в пределах 60 сек без перезагрузки страницы. |
| FR-3 | INT-1 (обработка null) | Дано недоступный источник данных (auth-сервис возвращает 5xx / таймаут), когда админка опрашивает INT-1, тогда в шапке отображается «—», не ошибка и не устаревшее число. |
