## 1. Обзор изменения

### 1.1. Тип и стороны

**Fullstack.** Фронтенд админки добавляет визуальный индикатор в шапку; бэкенд админки добавляет новый эндпоинт и интегрируется с сервисом аутентификации.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Админка «Арсенал» (фронт) | Отображение индикатора в шапке | Команда Arsenal-UI | 🟢 новое |
| Админка «Арсенал» (бэк) | Новый эндпоинт счётчика активных пользователей; кэширование запросов к auth-сервису | Команда Arsenal-Core | 🟢 новое |
| Сервис аутентификации | Источник данных о числе активных сессий | — | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями

Задача реализует бизнес-цель: администраторы получают возможность видеть текущее число активных пользователей в шапке админки для планирования регламентных работ без риска прерывания активных сессий. Реализуются FR-1 (отображение счётчика), FR-2 (автоматическое обновление), FR-3 (обработка недоступности источника).

## 2. Взаимодействия (ядро)

### INT-1. Получение числа активных пользователей от бэка Арсенала — 🟢

- **Граница/направление:** Фронтенд Арсенала → Бэкенд Арсенала
- **Триггер:** Периодический опрос из фронтенда (раз в минуту); первый запрос при загрузке страницы.
- **Контракт (запрос):** `GET /api/v1/admin/active-users-count`
  - Параметры: нет
  - Заголовки: стандартные (авторизация через механизм сессии админки)
  - Тело: отсутствует
- **Контракт (ответ):** 
  - `count` (integer | null): число активных пользователей, или null если источник недоступен
- **Пример запроса:**
  ```
  GET /api/v1/admin/active-users-count HTTP/1.1
  Host: arsenal-admin.internal
  Authorization: Bearer <session-token>
  ```
- **Пример ответа (успех):**
  ```json
  {
    "count": 42
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null
  }
  ```
- **Ошибки:** 
  - `403 Forbidden` — пользователь не имеет роль «Администратор» (авторизация не пройдена на уровне бэка).
  - Внутренние ошибки бэка (5xx) — фронтенд трактует как недоступность источника; не показывает ошибку, показывает «—» (см. §4.3).
- **Состояния UI по ответу:**
  - Успешный ответ с `count > 0` → отображать число (значение).
  - Успешный ответ с `count === 0` → отображать «0» (значение).
  - Ответ с `count === null` → отображать «—» (недоступность).
  - Загрузка в процессе → отображать спиннер (loading).
  - `403 Forbidden` или другая ошибка → отображать «—» (error → same as unavailable).
- **Авторизация:** 
  - **Кто вправе:** Только роль «Администратор» (подтверждено аналитиком).
  - **Где проверяется:** На уровне бэка Арсенала перед возвратом эндпоинта; фронтенд может получить 403, но это не должно вызывать видимую ошибку.
  - **Негативный случай:** Оператор (роль не «Администратор») → эндпоинт недоступен, фронтенд не показывает элемент индикатора вообще (проверка ролей на уровне фронта по сессии) или показывает «—» при попытке запроса.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2, FR-3

### INT-2. Получение числа активных сессий от сервиса аутентификации — 🟡 к валидации

- **Граница/направление:** Бэкенд Арсенала → Сервис аутентификации
- **Триггер:** Бэк Арсенала вызывает при получении запроса к INT-1 (если кэш истёк).
- **Контракт (запрос):** 🟡 к валидации — точный эндпоинт, метод и формат запроса неизвестны.
- **Контракт (ответ):** 🟡 к валидации — ожидаем число активных сессий (целое число или структура с полем count), точная форма неизвестна.
- **Происхождение:** 🟡 подтверждено аналитиком (сервис аутентификации умеет считать активные сессии, не по коду); 🟡 к валидации (точный контракт).
- **Трассировка:** Косвенно реализует FR-1/FR-2/FR-3 через INT-1.

### Каталог ошибок (сводно)

| Код / сценарий | Тело/сообщение | Когда | Состояние UI |
|---|---|---|---|
| 200 OK (count present) | `{ "count": <int> }` | Успешный запрос, источник доступен | Число |
| 200 OK (count null) | `{ "count": null }` | Источник auth-сервиса недоступен | «—» |
| 403 Forbidden | Стандартное сообщение 403 | Роль пользователя не «Администратор» | «—» или элемент не показывается |
| 5xx Server Error (бэк) | Ошибка сервера бэка Арсенала | Внутренняя ошибка | «—» |

## 2.5. Этапы работ и порядок сборки

Найдено два куска работы со своей предметной логикой, разделённые контрактом INT-1.

| # | Этап | Вход (шов) | Выход (шов) | Проверка в одиночку |
|---|------|-----------|-------------|---------------------|
| 01 | Backend: эндпоинт INT-1, интеграция с auth-сервисом и кэширование | — | INT-1 эндпоинт готов: `GET /api/v1/admin/active-users-count` возвращает `{ "count": <int|null> }` | Запрос с admin-токеном → 200 + число; без токена → 403; auth-service недоступен → 200 + count: null; таймаут > 5 сек на INT-2 → null |
| 02 | Frontend: компонент индикатора в шапке, логика polling и маппинг состояний | INT-1 эндпоинт готов и доступен | Индикатор работает: отображает число, обновляется каждые ~60 сек, показывает «—» при ошибке | Открыть админку → индикатор видно (админ) / скрыто (оператор); при изменении счёта обновляется в течение минуты; недоступность BE → показывает «—» |

## 3. Данные и хранение

**Не применимо: новых сущностей и таблиц не требуется.** Данные о числе активных сессий источник — сервис аутентификации; бэк Арсенала только кэширует результат в памяти (см. §5.1).

## 4. Фронтенд: состояния и UI

### 4.1. Размещение и визуальное описание

Индикатор располагается в шапке (header) админки, справа от логотипа или в крайнем правом углу, неяркий стиль (серый текст, малый размер), не отвлекает от основной работы (подтверждено в БТ как пожелание UX).

Текст индикатора: "Онлайн: <значение>" или просто число с иконкой; формат уточняется в макете, техспека не диктует.

### 4.2. Состояния и переходы

| Состояние | Условие | Что показывать | Как оно выглядит |
|---|---|---|---|
| **loading** | Первый запрос выполняется или очередной запрос в процессе | Спиннер (анимация) | Маленький спиннер рядом с текстом или вместо числа |
| **value** | `count > 0` или `count === 0` | Число `count` | Обычный текст "Онлайн: 42" или "Онлайн: 0" |
| **empty/dash** | `count === null` (источник недоступен) | Прочерк «—» | "Онлайн: —" серым цветом |
| **error** | Ошибка запроса (403, 5xx) | Прочерк «—» | "Онлайн: —" серым цветом (ошибка не раскрывается) |
| **not-shown** | Роль пользователя не «Администратор» | Элемент полностью скрыт | Индикатор отсутствует в DOM |

### 4.3. Маппинг ответа → состояние UI

- INT-1 возвращает `{ "count": 42 }` → **value** с текстом "42".
- INT-1 возвращает `{ "count": null }` → **empty/dash** с прочерком «—».
- INT-1 возвращает `403 Forbidden` → **error**, фронтенд показывает «—» (не раскрывает ошибку пользователю).
- INT-1 возвращает `5xx` или таймаут → **error**, показывает «—**.
- При загрузке страницы до получения первого ответа → **loading** (спиннер).
- При очередном опросе (polling) со значением в кэше → показываем кэшированное значение, затем обновляем при получении нового; переход между значениями плавный или мгновенный (UI-уточнение).

## 5. Бэкенд и интеграция

### 5.1. Синхронность и кэширование

- **Синхронность:** Синхронный запрос (фронтенд ждёт INT-1, бэк ждёт INT-2 при необходимости).
- **Кэширование:** 🟢 Бэк Арсенала кэширует результат INT-2 на **30 секунд** в памяти (in-memory cache, простой TTL). Если запрос INT-1 приходит в течение 30 сек от последнего вызова INT-2, бэк отдаёт кэшированное значение, не обращаясь к auth-сервису.
- **Частота опроса (фронт):** Фронтенд опрашивает INT-1 **раз в минуту** (polling interval = 60 сек).
- **Таймаут на INT-2:** Если INT-2 подвешивается > 5 сек (уточнить при валидации INT-2 контракта), бэк отдаёт INT-1 ответ `{ "count": null }`, не дожидаясь ответа auth-сервиса.
- **Толерантность к ошибкам:** Если INT-2 вернул ошибку, INT-1 возвращает `{ "count": null }` (не 500-ю ошибку).

### 5.2. Авторизация на границе

- **INT-1 авторизация:**
  - Фронтенд передаёт session-token (через Bearer или cookie, в зависимости от механизма админки).
  - Бэк проверяет, что роль пользователя = «Администратор» (читает из session/token).
  - Если роль не совпадает → `403 Forbidden`, эндпоинт не вызывается.
  - Фронтенд может дополнительно проверить роль перед отправкой запроса и не показывать элемент совсем (не повторять проверку дважды, выбрать удобное место).

- **INT-2 авторизация:** 🟡 к валидации — нужно ли используемому методу auth-сервиса специальное разрешение от бэка Арсенала, или он доступен всем? (Вопрос адресуется аналитику при валидации INT-2.)

### 5.3. Допуски и ограничения

- Число активных пользователей — **моментальное значение** в момент запроса, не историческое среднее.
- Гарантия точности: 🟡 подтверждено аналитиком (auth-сервис считает корректно) и 🟡 к валидации (способ считать нужно уточнить).
- Нет гарантии, что число не устареет между обновлениями (это норма для polling-подхода и явно согласовано в БТ как допустимое).

## 6. Выкат и совместимость

### 6.1. Порядок выката (rollout)

1. **Стадия 1:** Развёртывается **бэк Арсенала** с новым эндпоинтом INT-1. Фронт остаётся без изменений (индикатор ещё не появляется).
   - **Проверка:** Эндпоинт `GET /api/v1/admin/active-users-count` доступен и возвращает корректное значение.
   - **Pre-flight:** Роль «Администратор» в security-сервисе (или в любом месте, где хранятся роли) настроена и назначена нужным администраторам. 🟡 подтверждено аналитиком.

2. **Стадия 2:** Развёртывается **фронт Арсенала** с компонентом индикатора.
   - **Проверка:** Индикатор видно администраторам, обновляется каждую минуту, показывает «—» при недоступности.
   - **Откат:** Если фронт катится отдельным деплоем, откат фронта откатывает только UI; эндпоинт INT-1 остаётся рабочим.

### 6.2. Обратная совместимость

- **Для фронтенда:** Новый эндпоинт INT-1 добавляется; старые версии фронта не знают про него, но и не ломаются (они его не вызывают).
- **Для бэка:** Бэк Арсенала получает новый эндпоинт; это не влияет на существующие эндпоинты.
- **Для auth-сервиса:** Мы делаем запрос к INT-2 (контракт неизвестен); если auth-сервис расширит API, старые версии бэка Арсенала будут по-прежнему вызывать старый метод (если версионирование API это предусматривает).

### 6.3. Фиче-флаги и преднастройка

- **Фиче-флаг:** Опционально — можно добавить флаг в конфиг бэка Арсенала для включения/отключения INT-1 (позволяет откатить функцию без отката кода). Не обязателен.
- **Преднастройка:** 
  - ✅ Роль «Администратор» назначена нужным пользователям (до release).
  - ✅ Эндпоинт INT-2 на auth-сервисе доступен и готов к работе (уточняется при валидации INT-2).

## 7. Трассировка приёмки и тесты

| FR из БТ | Взаимодействие | Тест-кейс |
|---|---|---|
