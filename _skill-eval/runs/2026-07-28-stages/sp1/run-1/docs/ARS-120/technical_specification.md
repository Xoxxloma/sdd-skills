## 1. Обзор изменения

### 1.1. Тип и стороны

Fullstack. Система Арсенал (фронтенд + бэкенд) интегрируется с внешней системой учёта оборудования. На фронте добавляется раздел оборудования в карточку объекта охраны; на бэке — приём потока об оборудовании, хранение, сопоставление по адресу и выдача данных фронту.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (фронтенд) | новый раздел в карточке объекта охраны | Команда Арсенала | 🟢 |
| Арсенал (бэкенд) | приём потока оборудования, хранение, сопоставление, выдача API | Команда Арсенала | 🟢 |
| Внешняя система учёта оборудования | источник потока об оборудовании | Экспертная служба | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями

Реализуется бизнес-цель: инженер видит в карточке объекта охраны перечень установленного оборудования, что снижает повторные выезды и время на ручную сверку двух систем. Функциональные требования FR-1 (приём и хранение), FR-2 (сопоставление) и FR-3 (отображение) реализуются через взаимодействия и компоненты, описанные в §2 и §4.

## 2. Взаимодействия (ядро)

### INT-1. Приём сведений об оборудовании из внешней системы — 🟢

- **Граница/направление:** внешняя система учёта оборудования → бэк Арсенала (потоковая интеграция, событийный канал)
- **Триггер:** внешняя система передаёт событие об изменении, добавлении или удалении записи об оборудовании
- **Контракт (запрос — формат события):**
  - `external_equipment_id` (строка, обязательное) — уникальный идентификатор единицы оборудования во внешней системе; служит ключом идемпотентности для предотвращения дублей при повторной доставке
  - `equipment_type` (строка, обязательное) — классификация оборудования (напр. «Датчик движения», «Кнопка паники»)
  - `address` (строка, обязательное) — адрес установки в свободной форме, как ведётся во внешней системе
  - `timestamp` (ISO-8601, обязательное) — момент времени события на источнике
- **Пример запроса:**
  ```json
  {
    "external_equipment_id": "EQ-00123",
    "equipment_type": "Датчик движения PIR",
    "address": "ул. Ленина, д. 5, кв. 42",
    "timestamp": "2026-07-28T14:30:15Z"
  }
  ```
- **Контракт (хранение и обработка):**
  - Бэк Арсенала принимает событие и создаёт или обновляет запись в сущности `Оборудование` по ключу `external_equipment_id` (upsert).
  - Адрес нормализуется (пробелы, регистр, сокращения) и сохраняется отдельно в поле `address_normalized` для сопоставления.
  - Если `external_equipment_id` уже существует в хранилище, запись обновляется (новый тип, адрес, timestamp).
- **Ошибки:** событие, которое не удаётся разобрать или сохранить, логируется; повторная попытка ожидается в следующем цикле передачи. Ошибка приёма не должна прерывать обработку других событий.
- **Авторизация:** поток принимается от известного источника (проверка по IP-адресу, сертификату или API-ключу на границе системы); не требуется вызов от конечного пользователя.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1

### INT-2. Получить оборудование, привязанное к объекту охраны — 🟢

- **Граница/направление:** фронтенд Арсенала → бэкенд Арсенала (HTTP, синхронный запрос)
- **Триггер:** пользователь открывает карточку объекта охраны; фронт запрашивает список оборудования
- **Контракт (запрос):**
  - Метод: `GET` (концептуально)
  - Путь: `/api/security-objects/{security_object_id}/equipment` (где `security_object_id` — идентификатор объекта охраны в Арсенале)
  - Заголовки: стандартные для Арсенала (авторизация, Content-Type)
- **Контракт (ответ):**
  - `equipment` (массив объектов, обязательное) — список привязанного оборудования; может быть пуст.
    - Каждый элемент массива:
      - `id` (строка) — идентификатор оборудования (копия `external_equipment_id` из источника)
      - `type` (строка) — тип оборудования
      - `address_original` (строка) — адрес в исходной форме из внешней системы
  - `last_sync` (ISO-8601, обязательное) — момент последнего пересчёта сопоставления; фронт использует это значение, чтобы сообщить пользователю актуальность данных
  - `status` (строка, обязательное) — состояние данных:
    - `"ready"` — оборудование получено и готово к показу (может быть пуст или содержать элементы)
    - `"loading"` — данные в процессе сопоставления (используется редко, но возможно при одновременном запросе и пересчёте)
    - `"error"` — ошибка бэка; передавать в ответе нельзя, см. ниже
  - `empty_reason` (строка или null, обязательное) — если массив `equipment` пуст, объясняет причину:
    - `null` — не применимо (если есть данные в `equipment`)
    - `"no_equipment"` — по этому объекту охраны нет оборудования во внешней системе
    - `"no_match"` — оборудование есть, но ни одна запись не совпала по адресу с этим объектом (адреса не совпадают)
    - `"sync_awaiting"` — данные получены, но сопоставление ещё не выполнено (самый первый цикл)
- **Пример ответа (успех, есть оборудование):**
  ```json
  {
    "equipment": [
      {
        "id": "EQ-00123",
        "type": "Датчик движения PIR",
        "address_original": "ул. Ленина, д. 5, кв. 42"
      },
      {
        "id": "EQ-00456",
        "type": "Кнопка паники",
        "address_original": "ул. Ленина, д. 5, кв. 42"
      }
    ],
    "last_sync": "2026-07-28T23:00:00Z",
    "status": "ready",
    "empty_reason": null
  }
  ```
- **Пример ответа (успех, оборудование не найдено):**
  ```json
  {
    "equipment": [],
    "last_sync": "2026-07-28T23:00:00Z",
    "status": "ready",
    "empty_reason": "no_match"
  }
  ```
- **Пример ответа (успех, данные в ожидании синхронизации):**
  ```json
  {
    "equipment": [],
    "last_sync": null,
    "status": "ready",
    "empty_reason": "sync_awaiting"
  }
  ```
- **Ошибки:**
  - `404 Not Found` — объект охраны с переданным `security_object_id` не существует; фронт показывает ошибку.
  - `500 Internal Server Error` — временная ошибка бэка (база данных недоступна и т.п.); фронт показывает ошибку.
- **Состояния UI по ответу (если есть фронт):**
  - `status: "ready", equipment: [...]` (элементы есть) → значение, карточка показывает перечень оборудования
  - `status: "ready", equipment: [], empty_reason: "no_match"` → "— нет привязанного оборудования (не совпадают адреса)"
  - `status: "ready", equipment: [], empty_reason: "no_equipment"` → "— оборудование не известно внешней системе"
  - `status: "ready", equipment: [], empty_reason: "sync_awaiting"` → "— данные в обработке, подождите"
  - `status: "loading"` → загрузка (спиннер)
  - `404` или `500` → ошибка (красная иконка + «ошибка при загрузке»)
- **Авторизация:**
  - Роли `Инженер` и `Диспетчер` → вызов разрешён, возвращается полный список оборудования.
  - Роль `Оператор` → вызов отклоняется с кодом `403 Forbidden`; фронт не показывает раздел оборудования.
  - Проверка авторизации выполняется на уровне middleware/security-сервиса Арсенала.
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |

## 3. Данные и хранение

### 3.1. Новые сущности

#### Сущность `Оборудование` (Equipment)

Хранит сведения об оборудовании, полученные из внешней системы учёта.

**Поля:**
- `external_equipment_id` (строка, первичный ключ, обязательное) — уникальный идентификатор во внешней системе; используется как ключ идемпотентности.
- `equipment_type` (строка, обязательное) — классификация (тип) оборудования.
- `address_original` (строка, обязательное) — адрес в исходной форме из события INT-1.
- `address_normalized` (строка, обязательное) — адрес после нормализации (удаления пробелов, приведения регистра, развёртывания сокращений); используется для сопоставления с адресами объектов охраны.
- `last_updated` (timestamp, обязательное) — момент последнего обновления этой записи (из поля `timestamp` события INT-1 или техническая timestamp сохранения, если событие не несёт timestamp).

**Индексы:**
- PK на `external_equipment_id`.
- Индекс на `address_normalized` для быстрого поиска при сопоставлении.

**Миграция (концептуально):**
- Создать таблицу (если её ещё нет).
- Точный DDL оговаривается в рамках сервиса Арсенала; переносится в реальную миграцию-инструмент (Alembic, Flyway и т.п.).

#### Сущность `Привязка` (Binding)

Хранит результат сопоставления оборудования с объектами охраны.

**Поля:**
- `id` (первичный ключ, целое число или UUID, обязательное) — техническое имя записи.
- `equipment_id` (строка, FK → `Оборудование.external_equipment_id`, обязательное) — ссылка на оборудование.
- `security_object_id` (целое число, обязательное) — идентификатор объекта охраны в Арсенале (ссылка на существующую таблицу объектов охраны).
- `matched_at` (timestamp, обязательное) — момент, когда произошло сопоставление (техническая timestamp).

**Уникальность:**
- Уникальный индекс (composite) на `(equipment_id, security_object_id)` — предотвращает повторные привязки.

**Индексы:**
- PK на `id`.
- FK на `equipment_id`.
- Индекс на `security_object_id` для быстрого поиска оборудования по объекту.

**Миграция (концептуально):**
- Создать таблицу.
- Exact DDL — см. выше.

### 3.2. Сопоставление (reconciliation logic)

**Алгоритм сопоставления (регулярный пересчёт):**

1. **Триггер:** планировщик задач запускает процесс один раз в сутки ночью (время уточняется совместно с командой Арсенала; рекомендуется вне часов пик, напр. 02:00 UTC+3).
2. **Процесс:**
   - Прочитать все записи из `Оборудование`.
   - Прочитать все объекты охраны из существующей БД объектов.
   - Для каждого оборудования:
     - Нормализовать `address_original` оборудования (если ещё не нормализовано; или пересчитать при каждом запуске на случай изменения правил нормализации).
     - Найти все объекты охраны, у которых нормализованный адрес совпадает с адресом оборудования.
     - Если совпадение ровно одно → создать/обновить запись в `Привязка`.
     - Если совпадений ноль или несколько (≥2) → удалить существующую привязку для этого оборудования (если была); оборудование остаётся непривязанным.
3. **Результат:** таблица `Привязка` содержит актуальный результат сопоставления.
4. **Непривязанное оборудование:** остаётся в `Оборудование` без соответствия в `Привязка`. Для аналитики это видно в отчётах (outside scope данной спеки).

**Нормализация адреса (концептуально):**
- Удалить ведущие/конечные пробелы.
- Привести к единому регистру (нижний или верхний).
- Развернуть типичные сокращения (ул. → улица, д. → дом, кв. → квартира и т.п.); правила развёрток уточняются при имплементации.
- Удалить/заменить повторяющиеся пробелы.
- Результат — строка, пригодная для простого string-сравнения.

**Откат привязки:**
- Если между пересчётами оборудование было удалено из внешней системы (не поступило событие об этом), запись в `Оборудование` остаётся; привязка удаляется, если больше не совпадает по адресу.
- Если оборудование поступило повторно с тем же `external_equipment_id` — запись обновляется; пересчёт переоценит привязку.

### 3.3. Существующие сущности (изменения)

Объект охраны (Security Object) — **не меняется**. Адрес объекта охраны, его идентификатор и другие поля остаются в ведении Арсенала. Для сопоставления используется существующее поле адреса; новых полей в таблицу объектов охраны не добавляется.

**Подтверждение аналитиком:** структура Объекта охраны в Арсенале известна и стабильна; изменений в эту сущность не вносится. 🟡 подтверждено аналитиком (не по коду).

## 4. Фронтенд и состояния

### 4.1. Раздел оборудования в карточке объекта охраны

**Размещение:** карточка объекта охраны получает новый раздел «Оборудование» (расположение — на согласование с UX/дизайном; по смыслу рядом с адресом).

**Управление видимостью:** раздел отображается только для ролей `Инженер` и `Диспетчер`. Для роли `Оператор` раздел скрывается (запрос INT-2 отклоняется с 403, фронт не отображает).

### 4.2. Состояния раздела оборудования

| Состояние | Триггер | Отображение | Действие фронта |
|-----------|---------|-----------|-----------------|
| **Loading** | Открытие карточки; запрос INT-2 в полёте | Спиннер, «Загрузка оборудования…» | Ждёт ответа |
| **Ready (есть данные)** | INT-2 вернула `status: "ready", equipment: [...]` с элементами | Перечень оборудования (тип, исходный адрес); снизу — timestamp `last_sync` | Отображает список |
| **Ready (пусто, нет привязки)** | INT-2 вернула `empty_reason: "no_match"` | «— нет привязанного оборудования (адреса не совпадают)» | Информационное сообщение |
| **Ready (пусто, нет в системе)** | INT-2 вернула `empty_reason: "no_equipment"` | «— оборудование не известно внешней системе» | Информационное сообщение |
| **Ready (в ожидании синхра)** | INT-2 вернула `empty_reason: "sync_awaiting"` | «— данные в обработке, попробуйте позже» | Информационное сообщение (может быть редко) |
| **Error (объект не найден)** | INT-2 вернула 404 | Значок ошибки, «Объект охраны не найден» | Критическая ошибка (вероятно, ошибка навигации) |
| **Error (нет прав)** | INT-2 вернула 403 | Раздел не отображается (фронт не делает запрос) | Проверка роли перед запросом, либо раздел скрывается после получения 403 |
| **Error (бэк недоступен)** | INT-2 вернула 500 | Значок ошибки, «Ошибка при загрузке. Повторите попытку.» | Кнопка «Повторить» (в следующей версии: автоматический retry) |

## 5. Нефункциональные требования

### 5.1. Синхронность и производительность

- **Приём потока (INT-1):** асинхронный, потоковый. События обрабатываются по мере поступления из внешней системы; обработка одного события не должна блокировать другие. Задержка обработки зависит от способа доставки (Kafka, HTTP polling и т.п.); приём должен быть отказоустойчивым.
- **Пересчёт сопоставления:** регулярный, один раз в сутки ночью (рекомендуемое время: 02:00 UTC). Запускается как фоновая задача (batch job). Во время выполнения запросы INT-2 возвращают актуальные данные (читают из БД между пересчётами); новый пересчёт не блокирует их.
- **Запрос INT-2 (получить оборудование):** синхронный, HTTP. Ответ из БД; ожидаемое время отклика < 100 мс для типичного объекта (≤ 20 единиц оборудования). Индексы на `security_object_id` и `equipment_id` поддерживают производительность.
- **Кэширование:** локальное кэширование на фронте возможно (напр. TTL 1 час для списка оборудования); уточняется при разработке фронта.

### 5.2. Надёжность и отказоустойчивость

- **Потеря события INT-1:** внешняя система отвечает за доставку (с переповторами); Арсенал предотвращает дубли через `external_equipment_id`. Если событие полностью потеряно — оборудование не появится в Арсенале до следующего события от источника.
- **Ошибка пересчёта:** если пересчёт сопоставления завершился с ошибкой, `last_sync` не обновляется; фронт может это заметить и показать предупреждение. Следующий пересчёт (через сутки) повторит попытку.
- **Недоступность внешней системы:** Арсенал продолжает работать с последним известным состоянием оборудования; новые события не поступают, но пользователи видят последнее синхронизированное состояние.

### 5.3. Безопасность и авторизация

- **Приём INT-1 (потоковый):** источник проверяется по IP-адресу, сертификату или API-ключу на границе; не требует аутентификации конечного пользователя.
- **Запрос INT-2:** требуется валидная сессия пользователя Арсенала. Роли проверяются перед возвратом данных:
  - `Инженер`, `Диспетчер` → доступ разрешён.
  - `Оператор` → доступ запрещён (403).
- **Логирование:** запросы INT-1 и INT-2, ошибки сопоставления логируются для аудита; логи хранят только идентификаторы и события, не персональные данные пользователей.

### 5.4. Масштабируемость

- **Объём оборудования:** архитектура поддерживает хранение до 100K единиц оборудования в Арсенале; сопоставление регулярным пересчётом приемлемо при таком объёме (< 1 мин).
- **Частота запросов INT-2:** при 1000 одновременных пользователей, каждый открывает карточку в среднем раз в 5 минут → ~200 запросов/сек; БД с индексами выдержит; кэширование фронта снизит нагрузку.
- **Пик событий INT-1:** если внешняя система отправляет все события одновременно (напр. при синхре), очередь должна быть достаточной; рекомендуется использовать очередь сообщений (Kafka, RabbitMQ и т.п.).

## 6. Порядок выката и обратная совместимость

### 6.1. Очередность развёртывания

1. **Этап 01: Приём и хранение оборудования**
   - Развёртывается бэкенд Арсенала с поддержкой INT-1 (приём потока) и сущностью `Оборудование`.
   - Внешняя система начинает отправлять события; они накапливаются в БД Арсенала.
   - Фронт ещё не показывает раздел оборудования.
   - **Откат:** прекратить приём событий; таблица `Оборудование` остаётся в БД (можно удалить вручную при откате).

2. **Этап 02: Сопоставление по адресу**
   - Развёртывается процесс пересчёта сопоставления; сущность `Привязка` заполняется.
   - Первый пересчёт выполняется вручную (или планировщик включается после проверки).
   - Фронт ещё не показывает раздел оборудования.
   - **Откат:** прекратить пересчёт; таблица `Привязка` остаётся.

3. **Этап 03: API и интеграция**
   - Развёртывается бэкенд с INT-2 (запрос оборудования по объекту охраны).
   - Фронт получает доступ к новому эндпоинту, но раздел оборудования пока скрыт (feature flag в OFF).
   - Проверяются интеграционные тесты.
   - **Откат:** прекратить доступ к эндпоинту (он остаётся, но фронт не вызывает).

4. **Этап 04: Показ в UI (фронтенд)**
   - Развёртывается фронтенд Арсенала с разделом оборудования в карточке (feature flag переводится в ON для выбранной группы пользователей — rolling-release).
   - Пользователи видят оборудование в карточке объекта охраны.
   - **Откат:** feature flag в OFF; раздел перестаёт отображаться.

### 6.2. Обратная совместимость

- **Версии API INT-2:** если в будущем контракт изменится (добавятся новые поля или коды ошибок), старые версии фронта должны игнорировать неизвестные поля; новые обязательные поля должны иметь разумные default-значения для обратной совместимости.
- **Граждане, не имеющие доступа:** пользователи без ролей `Инженер` / `Диспетчер` не видят раздел оборудования; при попытке прямого запроса к INT-2 получают 403.
- **Отсутствие синхронизации:** если пересчёт сопоставления по какой-то причине не запустился, фронт покажет `last_sync` с прошлого цикла и пользователь это заметит (transparency > silence).

### 6.3. Преднастройка перед релизом

- Роли `Инженер` и `Диспетчер` должны быть созданы в системе управления доступом (security-сервис Арсенала); если их нет, их необходимо добавить перед развёртыванием фронта.
- Feature flag `equipment_section_visible` (или аналогичный) должен быть инициализирован в OFF и включен по расписанию или вручную на stage 4.
- Параметр планировщика для пересчёта сопоставления (время запуска, окно выполнения) должен быть сконфигурирован в системе управления конфигом Арсенала.
