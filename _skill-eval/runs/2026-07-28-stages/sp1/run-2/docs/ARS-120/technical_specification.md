## 1. Обзор изменения

### 1.1. Тип и стороны
**Fullstack-доработка.** Сервис «Арсенал» добавляет хранение сведений об оборудовании и их привязку к объектам охраны. Взаимодействие охватывает:
- новый приём потока от внешней системы учёта оборудования (backend);
- новый API для фронта (backend → frontend);
- новая секция в карточке объекта охраны (frontend).

### 1.3. Связь с бизнес-требованиями
Изменение реализует три функциональных требования:
- **FR-1** — приём сведений об оборудовании из внешней системы и хранение в «Арсенале».
- **FR-2** — сопоставление оборудования с объектами охраны по адресу.

Бизнес-цель: инженер видит в карточке объекта перечень установленного оборудования без необходимости сверяться со второй системой (см. БТ §2.1).

## 2. Взаимодействия (ядро)

### INT-1. Приём потока сведений об оборудовании от внешней системы — 🟢

- **Граница/направление:** внешняя система учёта оборудования → backend Арсенала (асинхронный поток событий).
- **Триггер:** внешняя система публикует сведения об установленном оборудовании: при добавлении, изменении или удалении.
- **Контракт (событие):** каждое сообщение в потоке содержит:
  - `equipment_id` (строка, обязательный) — уникальный идентификатор оборудования во внешней системе; используется как ключ идемпотентности в Арсенале.
  - `equipment_type` (строка, обязательный) — тип оборудования (e.g. «камера видеонаблюдения», «датчик движения», «кнопка тревоги»).
  - `address` (строка, обязательный) — адрес установки в свободной форме (как записано во внешней системе).
  - `timestamp` (ISO 8601 datetime, обязательный) — отметка времени события (UTC).
  - `operation` (enum: «add» | «update» | «delete», обязательный) — тип операции.

- **Пример сообщения:**
  ```json
  {
    "equipment_id": "EXT-SYS-12345",
    "equipment_type": "камера видеонаблюдения",
    "address": "ул. Ленина, д. 10, офис 5",
    "timestamp": "2026-07-28T14:23:45Z",
    "operation": "add"
  }
  ```

- **Семантика и обработка:**
  - **Идемпотентность:** оборудование идентифицируется по `equipment_id`. Повторное получение сообщения с тем же `equipment_id` не создаёт дубль; обновляется существующая запись (upsert).
  - **Операция `delete`:** если оборудование было привязано к объекту, привязка удаляется; сама запись об оборудовании может быть удалена или помечена как неактивная (стратегия удаления уточнить при интеграции).
  - **Адрес:** хранится в исходном виде; нормализация адреса происходит отдельно (см. хранение и сопоставление ниже).

- **Надёжность и гарантии:**
  - Гарантия доставки: по крайней мере один раз (at-least-once). Приём должен быть идемпотентным, так как возможны повторные доставки.
  - Порядок сообщений: если важен порядок, топик потока или разбиение по ключу должны гарантировать, что сообщения об одном `equipment_id` идут в порядке. ⚠️ Требует уточнения: гарантии порядка во внешней системе.

- **Ошибки:**
  - Невалидный JSON: логировать и пропустить.
  - Отсутствуют обязательные поля: логировать и пропустить.
  - Неизвестное значение `operation`: логировать и пропустить.

- **Происхождение:** 🟢 новое (контракт спроектирован в этом документе); 🟡 факт, что внешняя система публикует поток — подтверждено аналитиком; 🟡 к валидации — точный формат сообщения и имя топика.
- **Трассировка:** [FR-1]

### INT-2. Получить оборудование, привязанное к объекту охраны — 🟢

- **Граница/направление:** frontend Арсенала → backend Арсенала (HTTP GET).
- **Триггер:** инженер открыл карточку объекта охраны.
- **Контракт (запрос):** HTTP GET `/api/v1/objects/{objectId}/equipment`
  - Параметр пути: `objectId` (строка, обязательный) — уникальный идентификатор объекта охраны в Арсенале.

- **Контракт (ответ, успех 200 OK):**
  - `equipment` (массив объектов, может быть пусто) — список оборудования, привязанного к объекту.
    - Каждый объект содержит:
      - `equipment_id` (строка) — идентификатор оборудования во внешней системе.
      - `equipment_type` (строка) — тип оборудования.
      - `address` (строка) — адрес установки в исходном виде.
      - `last_updated` (ISO 8601 datetime) — отметка времени последнего обновления из внешней системы.
  - `as_of` (ISO 8601 datetime) — отметка времени данных (момент последнего выполненного пересчёта сопоставления). Показывает, насколько актуальны привязки в этом ответе.
  - `has_unmatched` (boolean) — флаг: есть ли оборудование на этом адресе, не привязанное из-за неоднозначности. Если `true`, для полноты картины может потребоваться отдельный запрос на отчёт неоднозначных случаев (вне текущего скопа).

- **Пример ответа (успех с данными):**
  ```json
  {
    "equipment": [
      {
        "equipment_id": "EXT-SYS-12345",
        "equipment_type": "камера видеонаблюдения",
        "address": "ул. Ленина, д. 10, офис 5",
        "last_updated": "2026-07-28T02:00:00Z"
      },
      {
        "equipment_id": "EXT-SYS-12346",
        "equipment_type": "датчик движения",
        "address": "ул. Ленина, д. 10, офис 5",
        "last_updated": "2026-07-27T14:15:00Z"
      }
    ],
    "as_of": "2026-07-28T02:00:00Z",
    "has_unmatched": false
  }
  ```

- **Пример ответа (успех, нет привязанного оборудования):**
  ```json
  {
    "equipment": [],
    "as_of": "2026-07-28T02:00:00Z",
    "has_unmatched": false
  }
  ```

- **Семантика:**
  - **Пустой список — норма, не ошибка:** значит, на этом адресе нет оборудования в системе учёта или оборудование не привязалось (но тогда `has_unmatched` должен быть `true`).
  - **Поле `as_of`:** позволяет фронту показать пользователю, насколько свежи данные (e.g. «актуально на 28 июля, 02:00»).
  - **Поле `has_unmatched`:** сигнал для фронта: есть ли неоднозначные случаи, которые надо показать отдельно или пологировать (дизайн отчёта — вне текущего скопа).

- **Авторизация:** см. §5.3 ниже.

- **Ошибки:**
  - `400 Bad Request` — `objectId` отсутствует или не валиден (e.g. не UUID).
  - `401 Unauthorized` — пользователь не аутентифицирован.
  - `403 Forbidden` — пользователь не имеет прав видеть оборудование для этого объекта (см. §5.3).
  - `404 Not Found` — объект охраны не существует.
  - `500 Internal Server Error` — ошибка backend'а; логировать и ответить с пустым списком `[]` или `TBD` в зависимости от стратегии (уточнить).

- **Состояния UI по ответу:**
  - **Загрузка:** запрос в полёте, фронт показывает прелоадер в секции оборудования.
  - **Данные (200 OK):** отсутствие equipments полностью нормально: `equipment: []` → состояние UI = «нет данных» (явная строка «Оборудование не привязано»).
  - **Ошибка (4xx/5xx):** фронт показывает ошибку (e.g. «Не удалось загрузить оборудование») с возможностью повтора.

- **Происхождение:** 🟢 новое.
- **Трассировка:** [FR-3]

## 3. Данные и хранение

### 3.1. Новые сущности

#### Сущность: Оборудование

Хранит сведения об оборудовании из внешней системы учёта.

| Поле | Тип | Обязательность | Семантика |
|------|-----|----------------|-----------|
| `id` | UUID | Обязательный | первичный ключ в Арсенале. |
| `external_id` | string, уникальный | Обязательный | идентификатор оборудования во внешней системе (`equipment_id` из INT-1); используется как ключ идемпотентности. |
| `equipment_type` | string | Обязательный | тип оборудования (e.g. «камера видеонаблюдения»). |
| `address_raw` | string | Обязательный | адрес в исходном виде, как пришёл от внешней системы. |
| `address_normalized` | string | Обязательный | адрес в нормализованном виде (приведённый к единому формату для сопоставления). Процесс нормализации — TBD (может включать приведение к нижнему регистру, удаление сокращений, стандартизацию порядка слов и т.п.; уточнить при реализации). |
| `last_updated` | timestamp (UTC) | Обязательный | отметка времени последнего обновления из внешней системы. |
| `created_at` | timestamp (UTC) | Обязательный | отметка времени создания записи в Арсенале. |

**Ограничения:**
- Уникальный индекс по `external_id` (гарантирует идемпотентность при upsert).
- Индекс по `address_normalized` (ускоряет сопоставление).

#### Сущность: Привязка (Equipment-Object Binding)

Результат сопоставления оборудования с объектом охраны по адресу.

| Поле | Тип | Обязательность | Семантика |
|------|-----|----------------|-----------|
| `id` | UUID | Обязательный | первичный ключ. |
| `equipment_id` | UUID (FK) | Обязательный | внешний ключ на сущность Оборудование. |
| `object_id` | UUID (FK) | Обязательный | внешний ключ на сущность Объект охраны (уже существующий в Арсенале). |
| `matched_at` | timestamp (UTC) | Обязательный | отметка времени пересчёта, когда была установлена привязка. |
| `is_active` | boolean | Обязательный | флаг: активна ли привязка (может быть установлен в `false` если оборудование удалено или сопоставление отменено). |

**Ограничения:**
- Уникальный индекс по `(equipment_id, object_id)` (одно оборудование привязано максимум к одному объекту за раз).
- Индекс по `object_id` (ускоряет поиск оборудования при загрузке карточки объекта).

### 3.2. Миграции (концептуально)

**Миграция 1: создание таблицы Оборудование**
```
CREATE TABLE equipment (
  id UUID PRIMARY KEY,
  external_id TEXT NOT NULL UNIQUE,
  equipment_type TEXT NOT NULL,
  address_raw TEXT NOT NULL,
  address_normalized TEXT NOT NULL,
  last_updated TIMESTAMP NOT NULL,
  created_at TIMESTAMP NOT NULL,
  INDEX idx_address_normalized (address_normalized)
);
```

**Миграция 2: создание таблицы Привязка**
```
CREATE TABLE equipment_bindings (
  id UUID PRIMARY KEY,
  equipment_id UUID NOT NULL FOREIGN KEY REFERENCES equipment(id),
  object_id UUID NOT NULL FOREIGN KEY REFERENCES objects(id),
  matched_at TIMESTAMP NOT NULL,
  is_active BOOLEAN NOT NULL DEFAULT true,
  UNIQUE (equipment_id, object_id),
  INDEX idx_object_id (object_id)
);
```

> **Примечание:** точный синтаксис DDL, инструмент миграции и софт удаления — уточнить в процессе реализации со стороной, владеющей backend-сервисом Арсенала.

## 4. Frontend: Отображение оборудования в карточке объекта охраны

### 4.1. UI-состояния и поток

В карточке объекта охраны добавляется новая секция «Оборудование» (в скопе задачи — чтение; редактирование выведено в out-of-scope per БТ §3.2).

| Состояние | Условие | Отображение |
|-----------|---------|-------------|
| **Загрузка (loading)** | Запрос INT-2 в полёте. | Прелоадер/спиннер в секции оборудования. |
| **Данные (data)** | Ответ получен, `equipment` не пусто (≥1 элемент). | Список оборудования в табличном или карточном формате: для каждого — тип, адрес, отметка времени обновления. |
| **Пусто (empty)** | Ответ 200 OK, `equipment: []` (нет привязанного оборудования). | Явная строка: «Оборудование не привязано» (может быть с иконкой вроде пустого состояния). |
| **Ошибка (error)** | Ответ 4xx/5xx. | Сообщение об ошибке: «Не удалось загрузить оборудование» + кнопка «Повторить». |
| **Неоднозначность (unmatched hint)** | Ответ успешен, `has_unmatched: true`. | Опционально: под списком привязанного оборудования — подсказка: «На этом адресе есть оборудование, не привязанное из-за неоднозначности» (если позволяет дизайн). Отдельный отчёт неоднозначных случаев — вне текущего скопа. |

### 4.2. Запуск загрузки

- **Триггер:** открытие карточки объекта (компонент карточки монтируется и сразу делает запрос INT-2).
- **Повторная загрузка:** при ошибке пользователь может нажать кнопку «Повторить» или вернуться на карточку.
- **Рефреш:** автоматический рефреш данных (полинг/сокет) — вне скопа (данные обновляются через ночной пересчёт на backend, реалтайм не требуется).

### 4.3. Авторизация на фронте

- Видимость секции определяется на фронте по ролям пользователя (см. §5.3).
- Если роль = Оператор, секция оборудования не отображается вообще.
- Если роль = Инженер или Диспетчер, секция отображается; запрос INT-2 отправляется с токеном пользователя (backend верифицирует права еще раз, см. §5.3).

## 5. Нефункциональные требования

### 5.1. Синхронность и производительность

#### INT-1: Приём потока
- **Модель:** асинхронный, потоковый приём.
- **Гарантии доставки:** по крайней мере один раз (at-least-once); идемпотентность обеспечивается на уровне БД (уникальный индекс по `external_id`).
- **Таймаут обработки:** каждое сообщение должно быть обработано и сохранено в БД в течение [TBD: уточнить — обычно <1 сек].
- **Объём:** ожидаемая частота поступления — [TBD: уточнить с владельцем внешней системы] (e.g. в секунду, в минуту, в день).
- **Логирование:** каждый приём логировать на уровне DEBUG или INFO, ошибки — на уровне ERROR.

#### INT-2: Получить оборудование
- **Модель:** синхронный HTTP GET.
- **SLA ответа:** <200ms для типовой карточки с 5–10 единицами оборудования (индекс по `object_id` обязателен).
- **Кэширование:** сведения об оборудовании обновляются один раз в сутки (пересчёт), поэтому кэширование ответа на фронте может быть умеренным (e.g. TTL 5–10 минут или зависит от того, как часто инженер открывает карточку в одной сессии).

#### Сопоставление (вне INT)
- **Модель:** асинхронный пакетный пересчёт.
- **Расписание:** один раз в сутки ночью (в момент низкой активности; точное время — TBD).
- **Процесс:**
  1. Взять все оборудование со статусом `is_active = true`.
  2. Нормализовать адреса (если нормализация ещё не выполнена при приёме).
  3. Для каждого объекта охраны найти оборудование с совпадающим нормализованным адресом.
  4. Если совпадение ровно одно — создать/обновить привязку с `is_active = true`.
  5. Если совпадений ноль или несколько (неоднозначность) — оборудование остаётся без привязки или с `is_active = false`; логировать для ручного разбора.
  6. Удалить привязки для оборудования, удалённого из внешней системы (если `operation: delete` в INT-1).
- **Длительность:** [TBD: уточнить — обычно несколько минут для нескольких тысяч единиц].

### 5.2. Надёжность и обработка ошибок

- **Потеря соединения с внешней системой:** сообщения будут повторно доставлены (гарантия по крайней мере один раз). Арсенал должен справиться с повторами (идемпотентность за счёт `external_id`).
- **Ошибка валидации (INT-1):** если сообщение невалидно (отсутствуют поля, некорректный JSON), оно логируется как ошибка и пропускается; обработка других сообщений продолжается.
- **Ошибка при загрузке оборудования в фронте (INT-2):** фронт показывает ошибку и предлагает повторить. Кэширование локального состояния — по усмотрению дизайнера.

### 5.3. Авторизация и управление доступом

#### Уровни ролей (из БТ §5.3):

| Роль | Доступ к оборудованию |
|------|----------------------|
| Инженер | ✅ Видит оборудование в карточке объекта |
| Диспетчер | ✅ Видит оборудование в карточке объекта |
| Оператор | ❌ Не видит секцию оборудования |

#### Реализация авторизации:

**На фронте:**
- Компонент карточки объекта проверяет роль пользователя (из токена или контекста приложения).
- Если роль ≠ Инженер и ≠ Диспетчер → секция оборудования не рендерится.

**На бэке (INT-2):**
- При вызове GET `/api/v1/objects/{objectId}/equipment`:
  1. Верифицировать, что пользователь аутентифицирован (token valid).
  2. Извлечь роль из токена.
  3. Если роль ≠ Инженер и ≠ Диспетчер → ответ 403 Forbidden.
  4. Верифицировать, что пользователь имеет право доступа к объекту `objectId` (может быть, объект принадлежит определённому региону/офису, и нужно проверить).
  5. Если всё ОК → вернуть оборудование.

**Где enforced:**
- Frontend: скрывает UI элементы для Оператора.
- Backend: проверяет права при каждом вызове INT-2 (defence in depth).

## 6. Порядок выката и совместимость

### 6.1. Очередность развёртывания

**Этапы развёртывания (в порядке):**

1. **Этап 1: Backend — приём и хранение оборудования**
   - Развёртывание INT-1 слушателя потока на backend.
   - Создание таблиц `equipment` и `equipment_bindings` (миграции).
   - Включение feature-flag (если используется) для приёма, но БЕЗ отдачи фронту.
   - **Выход этапа:** оборудование принимается и хранится; привязка пока не работает.

2. **Этап 2: Backend — регулярный пересчёт и привязка**
   - Развёртывание scheduler/job для ночного пересчёта сопоставления по адресам.
   - Заполнение таблицы `equipment_bindings` первым пересчётом.
   - **Выход этапа:** привязка работает, данные готовы к отдаче.

3. **Этап 3: Backend — API отдачи оборудования**
   - Развёртывание INT-2 endpoint GET `/api/v1/objects/{objectId}/equipment`.
   - Включение авторизации (проверка роли).
   - **Выход этапа:** фронт может запрашивать оборудование, но ещё не знает об endpoint'е.

4. **Этап 4: Frontend — отображение оборудования**
   - Добавление компонента/секции в карточку объекта охраны.
   - Вызов INT-2 при открытии карточки.
   - **Выход этапа:** инженер видит оборудование в карточке.

**Блокирующие зависимости:**
- Этап 1 должен быть завершён перед Этапом 2 (данные должны быть).
- Этап 2 должен быть завершён перед Этапом 3 (привязка должна быть актуальна).
- Этап 3 должен быть завершён перед Этапом 4 (API должен быть доступен).
- Этап 3 и 4 могут быть развёрнуты параллельно, если API протестирован на stage (backend в production, frontend в beta/canary).

### 6.2. Обратная совместимость

- **Приём потока (INT-1):** не влияет на существующий API Арсенала; новый слушатель работает независимо.
- **API отдачи (INT-2):** новый endpoint, не меняет существующие; старые клиенты продолжают работать.
- **Frontend:** новая секция в карточке объекта; если пользователь использует старую версию фронта (без поддержки оборудования), она просто не отображается; функциональность объекта не нарушается.

### 6.3. Feature flags и преднастройка

- **Feature flag (опционально, если используется):** `EQUIPMENT_BINDING_ENABLED` (по умолчанию off до Этапа 4).
  - Этап 1–2: off — приём и пересчёт работают, но данные не используются.
  - Этап 3: off — API доступен, но на фронте скрыт.
  - Этап 4: on — фронт видит и запрашивает.

- **Преднастройка ролей:** убедиться, что в сервисе авторизации определены роли Инженер, Диспетчер, Оператор и привязаны к пользователям (если ещё не сделано).

### 6.4. Откат

Если на любом этапе найдена критическая ошибка:
- **Откат Этапа 1–2:** отключить слушателя потока; приём останавливается, но уже полученные данные остаются (можно очистить вручную или оставить).
- **Откат Этапа 3:** отключить endpoint или вернуть 503 Service Unavailable; фронт получит ошибку и покажет пользователю.
- **Откат Этапа 4:** скрыть компонент оборудования на фронте за feature flag или откатить версию.

## 7. Трассировка приёмки

| Функциональное требование (FR) | Взаимодействие | Ответственность | Тест-кейс / Критерий |
|--------------------------------|----------------|-----------------|----------------------|
| **FR-1:** Приём и хранение | INT-1; Сущность Оборудование | Backend | Дано сведение об оборудовании с ID, типом, адресом, отметкой времени; когда оно передано через INT-1, тогда оно сохранено в таблице `equipment` с соответствующими полями; повторная передача одного ID не создаёт дубль (upsert). |
| **FR-2:** Сопоставление | Сущность Привязка; пересчёт (§5.1) | Backend | Дано оборудование с адресом и объект охраны с совпадающим адресом (нормализованно); когда выполнен пересчёт (§5.1), тогда создана привязка в таблице `equipment_bindings` с `is_active = true`; при нулевых или множественных совпадениях привязка не создаётся или остаётся на статусе `is_active = false`. |
| **FR-3:** Отображение | INT-2; Компонент UI (§4) | Frontend + Backend | Дано объект охраны с привязанным оборудованием; когда инженер открыл карточку, тогда фронт вызвал INT-2 и отобразил список оборудования; при пустом списке показано явное «Оборудование не привязано» (не пусто). |

> **Примечание:** тестирование проводится на stage после Этапа 3 (backend готов), интеграционное тестирование — после Этапа 4 (фронт готов).

## Итого

Техническая спецификация описывает:

1. **Два новых взаимодействия:**
   - INT-1: асинхронный приём потока от внешней системы (🟢 спроектировано, 🟡 формат к валидации).
   - INT-2: синхронный API для фронта (🟢 спроектировано).

2. **Две новые сущности:**
   - Оборудование: хранилище сведений из внешней системы.
   - Привязка: результат сопоставления по нормализованному адресу.

3. **Четыре этапа разработки** (§6.1) с чёткими зависимостями и точками развёртывания.

4. **Авторизацию** по ролям (Инженер, Диспетчер видят; Оператор нет).

5. **Трассировку** трёх функциональных требований (FR-1, FR-2, FR-3) к взаимодействиям и тест-кейсам.

Одна открытая точка: формат сообщения и топик потока от внешней системы (🟡 к валидации, §2 INT-1, и сводка в «Открытые вопросы»).
