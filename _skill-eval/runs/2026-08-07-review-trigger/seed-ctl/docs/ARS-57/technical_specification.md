## 1. Обзор изменения

### 1.1. Тип и стороны
🟢 Fullstack. В веб-админку «Арсенал» добавляется новый элемент в шапке (фронт), поддерживаемый новым эндпоинтом на бэке Арсенала, который в свою очередь читает данные из существующего сервиса аутентификации.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (фронт) | Отображение индикатора в шапке | команда Арсенал-UI | 🟢 новое |
| Арсенал (бэк) | Получение активных сессий и кэширование | команда Арсенал-Core | 🟢 новое (эндпоинт), 🟡 подтвержденные возможности |
| Сервис аутентификации | Источник данных (счёт активных сессий) | команда Auth | 🟡 подтверждено аналитиком (поставляет данные); 🟡 к валидации (точный контракт) |

### 1.3. Связь с бизнес-требованиями
Реализует назначение администраторам возможности видеть текущее число активных пользователей в шапке админки для безопасного выбора окна регламентных работ (FR-1, FR-2, FR-3).

## 2. Взаимодействия (ядро)

### INT-1. Фронт запрашивает число активных пользователей у бэка — 🟢

- **Граница/направление:** FE Арсенала → BE Арсенала
- **Триггер:** Загрузка страницы админки; затем периодически каждую минуту (полинг).
- **Контракт (запрос):** `GET /api/v1/admin/active-users-count`
  - Параметры: нет
  - Заголовки: Authorization (bearer-токен пользователя)
- **Контракт (ответ):** 
  - Поле `count` — целое число (integer) или `null`; обязательное
  - Семантика `null`: источник данных недоступен (сервис аутентификации не ответил или тайм-аут)
- **Пример запроса:** 
  ```
  GET /api/v1/admin/active-users-count HTTP/1.1
  Host: arsenal.example.com
  Authorization: Bearer eyJhbGc...
  ```
- **Пример ответа (успех):**
  ```json
  {
    "count": 42
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null
  }
  ```
- **Ошибки:**
  - **401 Unauthorized** — не передан токен или токен невалиден; не должно возникать в норме (проверка на фронте перед запросом).
  - **403 Forbidden** — пользователь не имеет роли «Администратор»; индикатор не запросит при такой роли.
  - **500 Internal Server Error** — ошибка бэка Арсенала при обращении к auth-сервису (см. INT-2); фронт получает count: null (тот же результат, что timeout).
- **Состояния UI по ответу:**
  - **loading** (первый запрос или после инвалидации) → спиннер в шапке на месте индикатора.
  - **value** (2xx, count ≠ null, count > 0) → показываем число, напр. «42 активных».
  - **zero** (2xx, count = 0, валидный ноль) → показываем «0».
  - **empty** (2xx, count = null) → показываем прочерк «—» (по пожеланию БТ: не показываем ошибку, показываем graceful деградацию).
  - **error_forbidden** (403) → в логах ошибка, индикатор не рендерится вообще (роль не Администратор; на уровне логики разрешения).
- **Авторизация:** 
  - Запрос требует валиден bearer-токен (проверяется фронтом перед вызовом).
  - Бэк повторно проверяет, что пользователь имеет роль «Администратор» (в контексте запроса или по данным сервиса авторизации); если нет — возвращает 403.
  - Оператор не видит индикатор вообще на фронте (условный рендер).
- **Происхождение:** 🟢 новое взаимодействие, спроектировано в этом документе.
- **Трассировка:** FR-1 (показать число в шапке), FR-2 (обновляться), FR-3 (graceful при недоступности).

### INT-2. Бэк Арсенала получает число активных сессий от сервиса аутентификации — 🟡

- **Граница/направление:** BE Арсенала → Сервис аутентификации
- **Триггер:** Поступил запрос от фронта (INT-1) или запрос из cache-miss при полинге.
- **Контракт (запрос):** 
  - 🟡 **К валидации:** точный путь, метод, параметры и заголовки. По слову аналитика: сервис аутентификации уже умеет считать активные сессии, но деталей эндпоинта аналитик сейчас не помнит. Подтвердить при интеграции.
  - Предварительное предположение (не факт): `GET /api/sessions/active-count` или аналогично; возможны параметры фильтра (напр., по приложению/окружению).
- **Контракт (ответ):** 
  - 🟡 **К валидации:** ожидаем поле, содержащее число активных сессий (имя поля неизвестно; возможны варианты: `count`, `activeCount`, `total` и т.д.).
  - Семантика успеха: 2xx, возвращает число или 0.
  - Семантика ошибки: 5xx или таймаут → BE обрабатывает как недоступность источника (возвращает INT-1 ответ с count: null).
- **Пример запроса:** (не выписываем конкретный, поскольку контракт к валидации; словами: «синхронный GET-запрос без тела»)
- **Пример ответа:** (не выписываем; уточнить)
- **Ошибки:** 
  - 🟡 **К валидации:** уточнить коды и условия (5xx, таймаут, rate-limit и т.д.).
  - Обработка на BE: любая ошибка → INT-1 возвращает { "count": null } (graceful деградация).
- **Состояния UI по ответу:** (не применимо; это бэк-бэк взаимодействие)
- **Авторизация:** 
  - 🟡 Подтверждено аналитиком: Арсенал-бэк имеет учётные данные (service account) для обращения к auth-сервису и может читать счёт активных сессий.
  - 🟡 К валидации: уточнить механизм (API-ключ, OAuth-token, mTLS, иное).
- **Происхождение:** 🟡 существующий сервис (аутентификация уже считает активные сессии); новое взаимодействие (Арсенал-бэк начинает читать эти данные).
- **Трассировка:** FR-1, FR-2, FR-3 (через INT-1).

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 | `{"error": "Unauthorized"}` | Фронт не передал токен или токен невалиден (не должно в норме) | UI не отправляет; ошибка в логах |
| 403 | `{"error": "Forbidden: role Admin required"}` | Пользователь — не Администратор | Индикатор не рендерится (гард на уровне FE) |
| 500 | `{"error": "Failed to fetch active sessions count"}` | Ошибка бэка при обращении к auth-сервису (INT-2 вернул 5xx/таймаут) | empty (count: null → показываем «—») |
| (timeout) | (нет ответа за 5 сек) | Сервис аутентификации не ответил за лимит | empty (count: null → показываем «—») |

## 3. Backend — ответственность

### 3.1. По сервисам

**Арсенал-бэк (Arsenal-Core):**
- Реализует новый эндпоинт INT-1: `GET /api/v1/admin/active-users-count`.
- Проверяет авторизацию входящего запроса: пользователь должен иметь роль «Администратор» (запрос к сервису авторизации или кэш ролей в контексте сеанса).
- Вызывает INT-2 (запрашивает у auth-сервиса число активных сессий).
- Кэширует результат на 30 секунд (описано в §5.1).
- При успехе возвращает INT-1 ответ с числом; при ошибке INT-2 — возвращает count: null.

**Сервис аутентификации:**
- 🟡 Подтверждено аналитиком: уже считает и может вернуть число активных сессий.
- 🟡 К валидации: точный эндпоинт, схема ответа, коды ошибок и условия их возникновения.
- Не требуется новая функциональность; Арсенал просто начинает это использовать.

### 3.2. Данные и хранение

**Новые сущности:** нет. Счёт активных сессий уже ведёт сервис аутентификации (это его доменная ответственность); Арсенал-бэк только их читает.

**Кэш на бэке Арсенала:**
- Тип: в памяти (in-memory) или Redis — 🟡 К валидации (архитектура кэша выбирается Арсенал-Core).
- Ключ: постоянный (никакой шардинг, одно значение на всю систему, напр. `arsenal:active-users-count`).
- TTL: 30 секунд.
- Инвалидация: по TTL; при сбое INT-2 значение expirе остаётся доступно (stale-while-revalidate) или выбрасывается — 🟡 К валидации.

**Никакие таблицы Арсенала не меняются.**

### 3.3. Авторизация/доступ на бэке

- Эндпоинт INT-1 требует bearer-токен в заголовке Authorization.
- Бэк проверяет, что пользователь (из токена) имеет роль «Администратор»:
  - Запрашивает роли у сервиса авторизации, ИЛИ
  - Использует кэш ролей в контексте сеанса (если есть).
- Если роль != «Администратор» → 403 Forbidden.
- Service account для обращения к auth-сервису (INT-2): 🟡 Подтверждено аналитиком, что учётные данные есть; 🟡 К валидации точный механизм (API-key, OAuth, иное).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

**Компонент:** новый виджет в шапке админки («header» / «top bar»).

**Поведение:**
- При загрузке страницы админки компонент проверяет роль пользователя (из контекста сеанса).
- Если роль = «Администратор» → инициирует запрос INT-1.
- Если роль ≠ «Администратор» → компонент не рендерится вообще (не видит пользователь на экране).

**Взаимодействия:**
- INT-1: `GET /api/v1/admin/active-users-count` каждую минуту (полинг, описано в §5.1).

### 4.2. Пользовательские сценарии

**Основной поток (администратор):**
1. Администратор открывает админку.
2. На странице загружается шапка.
3. Компонент запрашивает число активных пользователей (INT-1, первый запрос).
4. Шапка показывает спиннер/скелетон (состояние loading).
5. Приходит ответ 2xx с count = 42.
6. Шапка показывает «42 активных» (состояние value). ✅ *[FR-1]*
7. Спустя минуту компонент повторяет запрос (полинг).
8. Число изменилось на 45.
9. Шапка обновляет значение на «45 активных» без перезагрузки. ✅ *[FR-2]*

**Ветвление: источник недоступен (администратор):**
1. Администратор открывает админку.
2. Сервис аутентификации не ответил (таймаут, 5xx).
3. Бэк обрабатывает ошибку (INT-2), возвращает count: null (INT-1).
4. Фронт получает 2xx с count: null.
5. Шапка показывает прочерк «—» (состояние empty). ✅ *[FR-3]*
6. Значение не обновляется, если оно уже было nil (тихо ждём следующего полинга).

**Ветвление: пользователь — не администратор (оператор):**
1. Оператор открывает админку.
2. Компонент проверяет роль (оператор).
3. Компонент не рендерится; в шапке нет индикатора.
4. Оператор её не видит вообще. ✅ *[из ролевой модели БТ]*

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | Первый запрос INT-1 / после инвалидации | спиннер или скелетон на месте индикатора |
| `value` | 2xx, count > 0 | число, напр. «42 активных» |
| `zero` | 2xx, count = 0 (валидный ноль) | «0» (не прочерк, не пусто) |
| `empty` | 2xx, count = null (источник недоступен) | прочерк «—» |
| `hidden` | Роль пользователя ≠ Администратор | компонент не рендерится |

**Внимание:** `zero` и `empty` различаются на уровне кода (разные условия render), хотя визуально похожи. Разница важна для логики: в `zero` попытаемся обновить полингом (возможно, число изменится), в `empty` — отказ источника означает, что повторный попытка в этот же момент вернёт то же самое (только кэш истечёт через 30s).

### 4.3.1. Loading и таймауты

- **Cold-path (первый запрос):** таймаут 5 секунд. Если за 5s нет ответа → переходим в состояние `empty` (count: null, показываем «—»), логируем в консоль/мониторинг.
- **Warm-path (полинг, 2+й запрос и далее):** таймаут 3 секунды (более мягкий, ожидаем кэш на бэке; если кэш выбил, то это ошибка бэка).
- **Polling:** интервал 60 секунд (1 минута). Jitter: +/- 0–2 секунды (сглаживаем thundering herd, если несколько администраторов откроют админку одновременно). ✅ *[FR-2]*
- **Что показываем при таймауте / 5xx:** состояние `empty` (count: null → прочерк «—»).

### 4.4. Доступ по ролям в UI

- **Роль Администратор** → видит компонент, инициирует полинг INT-1. ✅
- **Роль Оператор** → компонент не рендерится (условный render на уровне React/Vue/и т.д.). ✅ *[из БТ, Таблица ролевой модели]*

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** Sync-запросы (полинг). Бэк вызывает auth-сервис синхронно (INT-2), клиент ждёт INT-1.
- **Кэш на бэке:**
  - Местоположение: в памяти или Redis (🟡 К валидации по Арсенал-Core).
  - TTL: 30 секунд.
  - Ключ: постоянный (одно значение на всю систему).
  - Поведение при expiry: пересчитываем INT-2 при следующем INT-1 запросе.
- **Частота обновления (фронт):** Полинг каждые 60 ± 2 секунды. ✅ *[FR-2: «в пределах минуты»]*
- **Таймауты:**
  - INT-1 (cold): 5 сек.
  - INT-1 (warm): 3 сек.
  - INT-2 (бэк → auth): 🟡 К валидации (выбирает Арсенал-Core; рекомендация — 2–3 сек, чтобы TTL кэша дал пересчёт).
- **Ожидаемая нагрузка:** 
  - Запросы INT-1: ~N * (админки онлайн) * (1 запрос в 60 сек) = в среднем N/60 RPS (N = кол-во администраторов). Для 100 админов ≈ 1.7 RPS. Пиковая нагрузка (все открыли одновременно) смягчается jitter в полинге.
  - Нагрузка на auth-сервис (INT-2): кэш в бэке Арсенала снижает нагрузку к 1 запросу на 30 сек на весь Арсенал (не на администратора).

### 5.2. Надёжность/деградация

- **Недоступность auth-сервиса:** пользователь видит «—» (не ошибка, graceful). Повторный полинг через 60 сек; кэш может быть использован (stale) — 🟡 К валидации (решение Арсенал-Core). ✅ *[FR-3]*
- **Недоступность бэка Арсенала (разве такое?):** 5xx ответ на INT-1 → фронт переходит в `empty` (прочерк).
- **Сетевая ошибка (клиент-бэк):** таймаут INT-1 → `empty`.
- **Нет перезагрузки страницы; значение просто показываем актуальное или «—».**

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Как проверяется | Негативный случай |
|---------|-----------|-----------------|-------------------|
| FE → BE (INT-1) | Администратор | bearer-токен + проверка роли на бэке | Оператор (403) или no-token (401) → компонент не видит или ошибка в логах; фронт может её ловить. |
| BE → Auth (INT-2) | Арсенал-бэк (service account) | 🟡 К валидации (механизм auth) | Неверные credentials → 401/403 на auth-сервисе; бэк обрабатывает как INT-1 ошибку (count: null). |
| UI visibility | Администратор | условный рендер на фронте (проверка роли в контексте) | Оператор → компонент `hidden`, не видит. |

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **Backend (Арсенал-бэк):** выкатываем эндпоинт INT-1 и INT-2 логику первым.
   - Почему: фронт будет вызывать INT-1; если бэка ещё нет, фронт получит 404.
2. **Frontend (Арсенал-UI):** выкатываем компонент вторым.
   - Фронт уже может запрашивать (бэк готов).

### 6.2. Обратная совместимость

- **После выката бэка, до выката фронта:** фронт старой версии не знает про индикатор (не запрашивает INT-1). Новый эндпоинт не затрагивает старую функциональность (изолирован). ✅ Совместимо.
- **После выката обоих:** нет пользователей старых версий фронта (скачивается заново при открытии админки). Старый BE (если кто-то откатится) просто не будет иметь INT-1 → новый FE получит 404 → покажет «—» (graceful). ✅ Совместимо.
- **Изменение контракта INT-2 (auth-сервис):** если auth-сервис изменит формат ответа, INT-2 сломается. Решение: версионировать INT-2 по согласованию с auth-сервисом (🟡 К валидации) или использовать адаптер на бэке Арсенала (обновить парсинг ответа перед выкатом нового auth).

### 6.3. Фиче-флаги

Релизим атомарно (бэк + фронт вместе, в один выкат). Фиче-флаги не требуются.

### 6.4. План отката

- **Откат BE Арсенала:** FE на новой версии продолжает запрашивать INT-1 → получает 404. FE переходит в состояние `error` или `empty`. Необходим **синхронный откат FE** (одновременно откатить бэк и фронт, ИЛИ откатить только фронт и ждать его кэша на клиентах).
  - Рекомендация: откатываем оба вместе (они выкатывались вместе).
- **Откат FE:** BE продолжает работать (INT-1 доступен). Старый фронт не знает про индикатор. Совместимо, откат FE не требует откат BE. ✅ Безопасно.
- **DDL-откат:** не применимо (новых таблиц нет).

### 6.5. Преднастройка до релиза (чек-лист)

- [x] Роли в security-сервисе: роль «Администратор» должна существовать и быть назначена пользователям, которые должны видеть индикатор. *По слову аналитика, роль уже существует (носит ответственность БТ, §5.3); проверить.* ✅
- [x] DDL-миграция в репо владеющего сервиса: не требуется (новых таблиц нет).
- [x] Конфиги по окружениям (dev/staging/prod): пути INT-1 и INT-2 (если они разные по окружениям), таймауты, TTL кэша. *🟡 К валидации.*
- [x] Сервисные аккаунты: учётные данные для Арсенал-бэка, чтобы обращаться к auth-сервису (INT-2). *🟡 Подтверждено аналитиком, что есть; уточнить детали (API-key, OAuth и т.д.).* 
- [x] Фиче-флаги: не требуются (релизим атомарно).
- [x] Алерты/мониторинг: 
  - Алерт на INT-2 ошибки (5xx от auth-сервиса) → бизнес теряет видимость активных сессий.
  - Алерт на INT-1 таймауты (если частотность выше порога, напр. >10% ошибок в мин).
  - Метрика: latency INT-1 (должна быть <100ms в норме благодаря кэшу на бэке).

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано: пользователь — Администратор, открыл админку. Когда: страница загрузилась. Тогда: в шапке видно число активных пользователей. |
| FR-2 | INT-1 (полинг) | Дано: указатель активных пользователей отображается. Когда: число активных пользователей на auth-сервисе изменилось. Тогда: счётчик в шапке обновляется без перезагрузки страницы в пределах 60 сек + TTL кэша (итого ~90 сек в худшем случае). |
| FR-3 | INT-1, INT-2 (обработка ошибок) | Дано: сервис аутентификации недоступен (5xx / таймаут). Когда: фронт запрашивает число активных пользователей. Тогда: в шапке отображается «—», не ошибка и не устаревшее число. |

## 8. Допущения и открытые вопросы

- **🟡 Подтверждено аналитиком (не по коду):**
  - Сервис аутентификации уже считает число активных сессий.
  - Роль «Администратор» существует и назначена нужным пользователям.
  - Арсенал-бэк имеет service account для обращения к auth-сервису (INT-2).

- **🟡 К валидации:**
  - **INT-2 контракт:** точный путь, метод, параметры, имя поля ответа (активные сессии), коды ошибок, таймауты. Уточнить при интеграции с auth-сервисом.
  - **INT-2 авторизация:** точный механизм (API-ключ, OAuth-токен, mTLS, иное) для service account Арсенала.
  - **Кэш на бэке:** выбор хранилища (in-memory vs Redis), поведение при сбое (stale-while-revalidate или сброс).
  - **Конфиги:** значения путей, таймаутов, TTL по окружениям.
  - **Мониторинг:** пороги алертов на INT-2 ошибки и INT-1 таймауты.

- **Приложения из БТ:** пожелание по UX — индикатор неяркий, не отвлекает. *Реализуется на фронте (цвет, размер, позиция в шапке); дизайнер подтвердит.*
