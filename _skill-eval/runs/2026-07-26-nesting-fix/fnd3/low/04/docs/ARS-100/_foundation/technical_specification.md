## 1. Обзор изменения

### 1.1. Тип и стороны

🟡 **BE-only (подтверждено аналитиком):** узел-фундамент #0 — чистая реализация на стороне backend, отдаёт контракт данных активности пользователей потребляющим фронтам (дочерним сервисам админки).

### 1.2. Затронутые сервисы и владельцы

|--------|---------------|------------------|---------------|

Узел-фундамент #0 обеспечивает единый источник истины для данных активности пользователей, который опирают FR-1..FR-5 из бизнес-требований: счётчик в шапке (FR-1), автообновление (FR-2), модальное окно с графиком (FR-3), переключение периода (FR-4) и выгрузка отчёта (FR-5). Дочерние узлы наследуют этот контракт и специализируют его для своих UI-компонентов.

## 2. Взаимодействия (ядро)

### INT-0. Данные активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Backend (Arsenal) → FE children (компоненты панели активности)

- **Триггер:** 
  - Первая загрузка панели / счётчика активности
  - Автоматическое обновление по таймеру (для FR-2)
  - Переключение периода в модальном окне (для FR-4)
  - Запрос выгрузки отчёта (для FR-5)

- **Контракт (запрос):**
  ```
  GET /admin/api/v1/activity
  Query параметры:
  - current: boolean (default: true) — запросить текущее число активных пользователей
  - period_type: string (default: "day") — тип периода: "hour" | "day" | "week"
  - period_start: ISO8601 timestamp (optional) — начало периода; если не указано, по умолчанию "now - period_type duration"
  - period_end: ISO8601 timestamp (optional) — конец периода; если не указано, по умолчанию "now"
  
  Заголовки: Authorization (Bearer token с ролью "Администратор" или выше)
  Тело запроса: отсутствует
  ```

- **Контракт (ответ):**
  - `status` (string, required) — статус данных: 
    - `"available"` — данные доступны и актуальны
    - `"unavailable"` — источник данных недоступен
    - `"no_data"` — нет данных за запрошенный период (валидный ответ, не ошибка)
  - `current_active_users` (int | null, required if `current: true`) — текущее число активных пользователей; `null` только если `status: "unavailable"`
  - `period_aggregates` (array of objects, required if `current: false` or period params provided) — агрегированные данные активности по периодам:
    - `timestamp` (ISO8601, required) — начало периода-ячейки (часовая / суточная / недельная, в зависимости от `period_type`)
    - `count` (int, required) — число активных пользователей в этот период
  - `period_type` (string, required) — повторение типа периода из запроса (эхо)
  - `period_start` (ISO8601, required) — фактическое начало диапазона, отправленное в ответе
  - `period_end` (ISO8601, required) — фактический конец диапазона
  - `cached_at` (ISO8601, optional) — момент, когда данные были закэшированы (для отладки, может не передаваться)
  - `source_unavailable_reason` (string, optional) — если `status: "unavailable"`, причина недоступности (для логирования)

- **Семантика null:**
  - `current_active_users: null` → допустимо только при `status: "unavailable"` (источник данных недоступен); во всех других случаях это ошибка договора.
  - `period_aggregates: []` (пустой массив) → допустимо при `status: "no_data"` (нет данных за период) или при успешном запросе, где реально нет активности (ноль активных). Клиент должен различать по `status`.

- **Пример запроса 1 (текущее число активных):**
  ```
  GET /admin/api/v1/activity?current=true&period_type=day HTTP/1.1
  Host: arsenal-backend.internal
  Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...
  Accept: application/json
  ```

- **Пример запроса 2 (агрегаты за период):**
  ```
  GET /admin/api/v1/activity?current=false&period_type=hour&period_start=2026-07-26T00:00:00Z&period_end=2026-07-26T23:59:59Z HTTP/1.1
  Host: arsenal-backend.internal
  Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...
  Accept: application/json
  ```

- **Пример ответа (успех, текущее число + агрегаты):**
  ```json
  {
    "status": "available",
    "current_active_users": 42,
    "period_type": "day",
    "period_start": "2026-07-25T00:00:00Z",
    "period_end": "2026-07-26T23:59:59Z",
    "period_aggregates": [
      {
        "timestamp": "2026-07-25T00:00:00Z",
        "count": 28
      },
      {
        "timestamp": "2026-07-25T01:00:00Z",
        "count": 15
      },
      {
        "timestamp": "2026-07-26T00:00:00Z",
        "count": 35
      },
      {
        "timestamp": "2026-07-26T01:00:00Z",
        "count": 42
      }
    ],
    "cached_at": "2026-07-26T01:15:30Z"
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "status": "unavailable",
    "current_active_users": null,
    "period_type": "day",
    "period_start": "2026-07-25T00:00:00Z",
    "period_end": "2026-07-26T23:59:59Z",
    "period_aggregates": [],
    "source_unavailable_reason": "internal.activity_service.timeout"
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "status": "no_data",
    "current_active_users": 0,
    "period_type": "week",
    "period_start": "2026-07-20T00:00:00Z",
    "period_end": "2026-07-26T23:59:59Z",
    "period_aggregates": []
  }
  ```

- **Ошибки:**
  - `401 Unauthorized` — отсутствует или неверен Bearer token; детально см. раздел 3.3
  - `403 Forbidden` — токен верен, но у пользователя нет роли "Администратор"; детально см. раздел 3.3
  - `400 Bad Request` — неверные параметры запроса (напр., `period_type` неизвестен или `period_start > period_end`)
  - `500 Internal Server Error` — недокументированная ошибка сервера

- **Состояния UI по ответу (маппинг для детей):**
  - `status: "available"` + `current_active_users: null` → невозможно (ошибка контракта)
  - `status: "available"` + `current_active_users ≠ null` и `> 0` → UI-состояние `value` (показать число)
  - `status: "available"` + `current_active_users: 0` → UI-состояние `zero` (показать «0», не прочерк)
  - `status: "available"` + `period_aggregates: []` → UI-состояние `empty` (показать «—» или «нет данных»)
  - `status: "no_data"` → UI-состояние `empty` (валидная ситуация: нет данных за период)
  - `status: "unavailable"` → UI-состояние `error_source` (показать сообщение об ошибке, предложить retry)
  - `401` или `403` → UI-состояние `error_forbidden` (показать «нет доступа»)
  - `400` или `5xx` (не ловко) → UI-состояние `error_source` (показать ошибку, retry)

- **Авторизация:**
  - **На границе:** проверка на BE (Arsenal backend) в момент обработки запроса
  - **Кто вправе:** пользователь с ролью ≥ «Администратор» (как определено в security-сервисе Arsenal)
  - **Где проверяется:** 🟡 middleware авторизации на маршруте `/admin/api/v1/activity` (подтверждено аналитиком: существует, проверяет Bearer token)
  - **Негативный случай:** пользователь без роли → `403 Forbidden` с сообщением `{ "error": "insufficient_permissions", "required_role": "Administrator" }`
  - **Еще:**  👑 Service-to-service calls (от дочерних фронтов или их BFF) проходят авторизацию через тот же middleware и Bearer token должен быть выдан с правами администратора в контексте запроса.

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (текущее число), FR-2 (автообновление), FR-3 (модалка + график), FR-4 (переключение периода), FR-5 (выгрузка отчёта) — все опираются на этот контракт.

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal (Backend)** отвечает за:
- 🟢 Реализацию эндпоинта `GET /admin/api/v1/activity` (маршрут, логика, HTTP-статусы)
- 🟢 Поддержку параметров запроса (`current`, `period_type`, `period_start`, `period_end`)
- 🟢 Расчёт и возврат текущего числа активных пользователей (в `current_active_users`)
- 🟢 Расчёт агрегированной активности за периоды (в `period_aggregates`, массив с `timestamp` + `count`)
- 🟡 Обработка недоступности источника данных и возврат `status: "unavailable"` вместо устаревшего значения (подтверждено аналитиком: реализуется как политика)
- 🟡 Различение `status: "no_data"` (нет активности за период) от `status: "unavailable"` (источник недоступен) (подтверждено аналитиком)
- 🟢 Кэширование результатов на стороне Arsenal на **30 секунд** (TTL = 30s)
- 🟢 Таймаут запросов к источнику данных: **5 секунд** (если источник не ответил за 5s → `status: "unavailable"`)
- 🟡 Проверка авторизации на эндпоинте через middleware авторизации (подтверждено аналитиком: существует, проверяет Bearer token на роль "Администратор")

### 3.2. Данные и хранение

🟡 **Новых таблиц не заводим (подтверждено аналитиком).** Агрегаты активности рассчитываются **на лету** из существующего источника данных в Arsenal (предположительно логи сессий или счётчики в памяти; точный механизм — 🟡 к валидации при интеграции).

- **Хранение:** данные о текущей активности уже существуют в Arsenal; спека не вводит новые таблицы / сущности.
- **Кэш:** 30-секундный кэш результата запроса `GET /admin/api/v1/activity` хранится **на стороне Arsenal-backend** (in-memory, Redis или аналогично — точный механизм 🟡 к валидации).
- **Retention/TTL:** текущие счётчики активности удерживаются в памяти системы Arsenal; исторические логи активности хранятся по уже существующей политике Arsenal (не меняется).

### 3.3. Авторизация/доступ на бэке

- **Где enforced:** на маршруте `/admin/api/v1/activity` через middleware авторизации Arsenal
- **Как проверяется:** 🟡 Bearer token из заголовка `Authorization` передаётся в security-сервис Arsenal; сервис возвращает контекст пользователя с его ролью (подтверждено аналитиком: такой сервис есть и используется)
- **Необходимая роль:** ≥ "Администратор"
- **Граница:** проверка имеет место на бэке Arsenal перед тем, как запрос достигнет эндпоинта; 403 возвращается, если роль ниже
- **Сценарий без доступа:** пользователь с ролью "Оператор" или ниже отправляет запрос → `403 Forbidden` с телом `{ "error": "insufficient_permissions", "required_role": "Administrator" }`

## 4. Frontend — ответственность

**Не применимо:** узел-фундамент #0 — чистый backend-контракт. FE-ответственности полностью передаются дочерним узлам, которые наследуют этот контракт и реализуют компоненты панели активности (счётчик в шапке, модальное окно, график, выгрузка).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- 🟡 **Синхронность:** Синхронный запрос (подтверждено аналитиком: FE ждёт ответа перед обновлением UI)
- 🟡 **Кэш:** 30-секундный TTL на стороне Arsenal backend (подтверждено аналитиком)
  - Если запрос поступил в пределах 30s после предыдущего → возвращается кэшированный результат (без обращения к источнику)
  - По истечении TTL → свежий запрос к источнику
- 🟡 **Таймаут:** 5 секунд на ответ источника данных (подтверждено аналитиком); если превышен → `status: "unavailable"`
- 🟢 **Polling (обновление на фронте):** частота обновления счётчика в шапке (FR-2: «в пределах минуты») определяется дочерним узлом в его спеке (например, polling каждые 10–30 секунд); узел-фундамент #0 не регулирует.
- 🟢 **Ожидаемая нагрузка:** Каждый запрос к эндпоинту вычисляет агрегаты на лету (O(log n) или O(1) в зависимости от структуры данных в Arsenal); при 30s кэше и типичном refresh-rate фронта (10–30s) ожидается **1–2 запроса к источнику в минуту на активную админку**. Нагрузка низкая; масштабирование зависит от внутренней реализации Arsenal (к валидации).

### 5.2. Надёжность/деградация

- 🟡 **При недоступности источника данных (подтверждено аналитиком):**
  - **Показывать:** `status: "unavailable"` в ответе; FE рендерит ошибку или placeholder
  - **Не показывать:** устаревшие значения из предыдущего кэша
  - **Rationale:** пользователь (администратор) должен знать, что данные недоступны, чтобы не принимать решения на основе старых цифр
- 🟡 **При отсутствии данных за период (подтверждено аналитиком):**
  - **Показывать:** `status: "no_data"` в ответе
  - **Отличие от ошибки:** это валидная ситуация, а не сбой
  - **FE действие:** рендерит «—» или «нет данных» (состояние `empty`)

### 5.3. Безопасность/доступ (сводно)

| Граница | Субъект | Действие | Проверка | Результат |
|---------|---------|---------|----------|-----------|
| GET /admin/api/v1/activity | Администратор | запрос | Bearer token + роль ≥ Admin | 200 OK |
| GET /admin/api/v1/activity | Оператор | запрос | Bearer token + роль < Admin | 403 Forbidden |
| GET /admin/api/v1/activity | анонимный | запрос | нет token | 401 Unauthorized |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 **Фундамент выкатывается РАНЬШЕ потребителей (подтверждено аналитиком):**
1. **Фаза 1:** Deploy узла-фундамента #0 (Arsenal backend с эндпоинтом `/admin/api/v1/activity`)
2. **Фаза 2:** Deploy дочерних узлов (компоненты панели активности в админке), которые наследуют и потребляют контракт #0

**Rationale:** дочерним компонентам нужен рабочий контракт в production перед их запуском. Обратное развёртывание (дети раньше фундамента) вызовет 404/5xx на фронте.

### 6.2. Обратная совместимость

🟡 **Фиче-флаги отсутствуют (подтверждено аналитиком); релизим атомарно.** Фундамент #0 — новый контракт; обратной совместимости не требуется (нет старых потребителей). После выката Фазы 1 дети могут безопасно включать запросы к эндпоинту.

### 6.3. Фиче-флаги

🟡 **Не используются (подтверждено аналитиком).** Контракт выкатывается полностью и безусловно в production.

### 6.4. План отката

**Откат узла-фундамента #0:**
- **Если дети уже задеплоены:** откат #0 → дети получат 404 или 5xx. Нужно откатывать одновременно (фундамент + все дочерние узлы) или вообще не начинать откат, если дети в production.
- **Если дети ещё не задеплоены (Фаза 1, до Фазы 2):** откат #0 допустим без последствий.

**Откат дочерних узлов (при живом #0 в production):**
- Дочерний узел откатывается; фундамент остаётся. Дети просто перестают вызывать эндпоинт. Никаких побочных эффектов.

- [ ] **Фиче-флаги** — не требуются (🟡 не используются, подтверждено аналитиком).
- [ ] **Алерты/мониторинг** — рекомендуется алертинг на:
  - Превышение %доли `status: "unavailable"` ответов (напр., > 5% за 5 мин) → проблема источника данных
  - Превышение latency эндпоинта (напр., > 2s) → оптимизация нужна
  - 4xx / 5xx ошибки на эндпоинте (напр., > 0.1% за период) → отладить

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие | Тест-кейс |
|----------|----------------|----|
| FR-1 | INT-0 (текущее число) | Дано открытую админку, когда страница загрузилась, тогда фундамент отдаёт `current_active_users` в ответе `status: "available"`, и фронт отображает число в шапке. |
| FR-2 | INT-0 (текущее число, polling) | Дано открытую админку, когда число активных изменилось, тогда фронт переопрашивает эндпоинт (через polling ≤ 30s), фундамент отдаёт новое значение, и счётчик обновляется без перезагрузки. |
| FR-3 | INT-0 (период + агрегаты) | Дано счётчик в шапке, когда администратор кликает по нему, тогда фронт вызывает эндпоинт с `current=false&period_type=day`, фундамент отдаёт `period_aggregates`, и модалка открывается с графиком. |
| FR-4 | INT-0 (период + агрегаты) | Дано открытую модалку, когда администратор выбирает другой период (напр., `period_type=week`), тогда фронт переопрашивает эндпоинт с новым периодом, фундамент отдаёт обновлённые `period_aggregates`, и график перестраивается. |
| FR-5 | INT-0 (период + агрегаты) | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт вызывает эндпоинт (или BFF), получает `period_aggregates`, и дочерний узел генерирует файл со сводкой для скачивания. |

## Итоги

**Узел-фундамент #0** поставляет один новый контракт `INT-0: Данные активности пользователей`, который объединяет текущее число активных пользователей и исторические агрегаты по периодам. Контракт обслуживает все пять функциональных требований (FR-1..FR-5) эпика ARS-100 и наследуется дочерними узлами (счётчиком, графиком, выгрузкой). Реализация опирается на существующую инфраструктуру Arsenal (никаких новых таблиц), защищена авторизацией на уровне роли "Администратор", и гарантирует непоказ устаревших данных при недоступности источника.
