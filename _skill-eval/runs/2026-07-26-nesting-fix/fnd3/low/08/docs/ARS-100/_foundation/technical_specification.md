## 1. Обзор изменения

### 1.1. Тип и стороны

🟢 BE-only. Узел-фундамент #0 предоставляет данные контракт для сбора активности пользователей. Потребители — фронтенды детских узлов (ARS-101, ARS-102, ARS-103).

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Собирает и предоставляет данные активности; реализует контракт INT-0 | Arsenal-Core | 🟢 новое взаимодействие |

### 1.3. Связь с бизнес-требованиями

Данный узел реализует общую часть для всех функций эпика ARS-100: сбор и предоставление данных об активности пользователей (текущее число активных и агрегаты за выбранный период), необходимых для FR-1, FR-2, FR-3, FR-4, FR-5.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Фронтенды детских узлов (ARS-101, ARS-102, ARS-103)

- **Триггер:** Детский фронт запрашивает текущую активность (при открытии счётчика) и активность за период (при открытии модала с графиком)

- **Контракт (запрос):**
  - **GET /api/arsenal/activity/current** — текущие данные активности
    - Параметры: нет
  - **GET /api/arsenal/activity/aggregate** — агрегированные данные за период
    - Параметры: 
      - `period_start` (ISO 8601 datetime, обязательно) — начало периода
      - `period_end` (ISO 8601 datetime, обязательно) — конец периода

- **Контракт (ответ):**
  
  **Для `/current`:**
  - `active_count` (integer | null) — число активных пользователей, null если источник недоступен
  - `is_available` (boolean) — флаг доступности источника данных; false → данные недоступны (не стать значение)
  - `timestamp` (ISO 8601 datetime) — момент сбора данных
  
  **Для `/aggregate`:**
  - `data_points` (array of objects) — массив точек агрегации (может быть пуст, если нет данных за период)
    - `timestamp` (ISO 8601 datetime) — момент времени (начало интервала агрегации)
    - `active_count` (integer) — число активных пользователей в этот момент
  - `period_start` (ISO 8601 datetime) — запрошенное начало периода
  - `period_end` (ISO 8601 datetime) — запрошенный конец периода
  - `is_available` (boolean) — флаг доступности источника; false → источник был недоступен, данные нет
  - `has_data` (boolean) — false, если за период нет активности вообще (отличие от ошибки доступности)

- **Пример запроса:**
  ```
  GET /api/arsenal/activity/current
  ```
  
  ```
  GET /api/arsenal/activity/aggregate?period_start=2026-07-26T00:00:00Z&period_end=2026-07-26T23:59:59Z
  ```

- **Пример ответа (успех) — /current:**
  ```json
  {
    "active_count": 42,
    "is_available": true,
    "timestamp": "2026-07-26T14:30:00Z"
  }
  ```

- **Пример ответа (успех) — /aggregate:**
  ```json
  {
    "data_points": [
      { "timestamp": "2026-07-26T00:00:00Z", "active_count": 12 },
      { "timestamp": "2026-07-26T01:00:00Z", "active_count": 15 },
      { "timestamp": "2026-07-26T02:00:00Z", "active_count": 8 },
      { "timestamp": "2026-07-26T03:00:00Z", "active_count": 0 }
    ],
    "period_start": "2026-07-26T00:00:00Z",
    "period_end": "2026-07-26T23:59:59Z",
    "is_available": true,
    "has_data": true
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "data_points": [],
    "period_start": "2026-07-26T00:00:00Z",
    "period_end": "2026-07-26T23:59:59Z",
    "is_available": true,
    "has_data": false
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "active_count": null,
    "is_available": false,
    "timestamp": "2026-07-26T14:30:00Z"
  }
  ```

- **Ошибки:**

  | Код | Тело/сообщение | Когда | Состояние UI |
  |-----|----------------|-------|--------------|
  | 403 | `{ "error": "forbidden", "message": "Доступ запрещен" }` | Роль не Администратор | `error_forbidden` |
  | 400 | `{ "error": "invalid_period", "message": "period_start должно быть раньше period_end" }` | Неверные параметры периода в `/aggregate` | `error_value` (валидация на фронте) |
  | 408 | `{ "error": "timeout", "message": "Истёк таймаут запроса" }` | Запрос занял более 5с | `error_source` |
  | 5xx | `{ "error": "internal", "message": "Ошибка источника данных" }` | Сервис недоступен (СУБД, сервис аутентификации) | `error_source`; фронт покажет флаг is_available=false в следующем запросе |

- **Состояния UI по ответу (если есть фронт):**
  - `value` — 2xx, is_available=true, active_count/has_data > 0 → покажи значение
  - `zero` — 2xx, is_available=true, active_count = 0 → покажи «0»
  - `empty` — 2xx, is_available=true, has_data=false → покажи «—» (нет данных за период)
  - `error_source` — 5xx или таймаут (408) или is_available=false → «Ошибка получения данных. Повторить?»
  - `error_forbidden` — 403 → «Доступ запрещен»

- **Авторизация:**
  - Эндпоинты доступны только пользователям с ролью **Администратор**
  - Проверка выполняется на бэке Arsenal (в middleware, перед обработкой запроса)
  - При отсутствии роли вернуть 403 Forbidden
  - Негативный случай: оператор/пользователь без роли Администратор → 403

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (все функции эпика)

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- Реализует две точки входа INT-0: `GET /api/arsenal/activity/current` и `GET /api/arsenal/activity/aggregate`
- Собирает данные об активности пользователей из собственных источников (сессии, логины и т.п.) — 🟢 новая логика
- Для `/current`: возвращает текущее число активных пользователей или флаг is_available=false при недоступности источника
- Для `/aggregate`: считает агрегаты (количество активных пользователей) за указанный период на лету, возвращает массив точек данных или флаг has_data=false, если за период активности нет
- Кэширует результат `/current` на 30 секунд на стороне Arsenal
- Таймаут запроса — 5 секунд; при превышении вернуть 408
- Проверяет роль Администратор в middleware перед обработкой обоих запросов; при отсутствии → 403

### 3.2. Данные и хранение

🟢 **Новых таблиц не создаём.** Данные об активности пользователей считаются на основе существующих логов сессий/логинов в Arsenal. Концептуально:
- **Источник:** логи активности в СУБД Arsenal (уже существуют для других целей)
- **Агрегация:** SQL-запрос, который считает число уникальных активных пользователей в окно времени
- **Кэш текущего значения:** 30 секунд в памяти Arsenal Backend (напр., Redis или in-memory cache)
- **Миграции:** не требуются; используем существующие логи

Точный DDL и запросы уточняются в коде Arsenal Backend (не в этой спеке).

### 3.3. Авторизация/доступ на бэке

- **Где enforced:** в middleware Arsenal Backend, до обработки запроса на `/api/arsenal/activity/*`
- **Как:** проверка токена/сессии → поиск роли в security-сервисе → роль = Администратор?
- **Роли:** только Администратор имеет доступ
- **Негативные случаи:** 
  - Оператор / пользователь без роли → 403 Forbidden
  - Неаутентифицированный пользователь → 401 Unauthorized (обрабатывается выше, не специфично для этого узла)

## 4. Frontend — ответственность

> Не применимо: узел-фундамент #0 не содержит фронтенда. Фронтенды детских узлов (ARS-101, ARS-102, ARS-103) потребляют контракт INT-0 и реализуют §4 в своих спеках. Здесь фиксируем, что узел-фундамент #0 поставляет ответ и состояния для потребителей.

**Для справки — состояния, которые потребители должны обработать:**
- `value` — значение есть и > 0
- `zero` — значение = 0
- `empty` — нет данных за период
- `error_source` — источник недоступен
- `error_forbidden` — нет доступа

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** оба эндпоинта синхронные (запрос-ответ)
- **Кэш текущего значения:** 30 секунд на стороне Arsenal Backend для `/current` (чтобы не перегружать источник частыми опросами при частых обновлениях на фронте)
- **Кэш `/aggregate`:** не кэшируется (запрос может быть за разные периоды; кэш накладывает сложность без очевидной выгоды для агрегатов за прошлые периоды)
- **Таймаут:** 5 секунд на весь запрос; если источник не ответит за 5с, вернуть 408
- **Ожидаемая нагрузка:** умеренная (запросы от админов; FE кэшира результаты на 30с, поэтому частота запросов ограничена)

### 5.2. Надёжность/деградация

- **При недоступности источника данных об активности:**
  - Для `/current`: вернуть 200 OK с `is_available=false` и `active_count=null` (не стара значение; явный флаг недоступности)
  - Для `/aggregate`: вернуть 200 OK с `is_available=false` и пустым массивом `data_points` (не выдавать кэшированные агрегаты старого периода)
  - **Фронт покажет:** ошибку `error_source` — "Ошибка получения данных. Повторить?"
- **При таймауте:** вернуть 408 → фронт обработает как `error_source`
- **Логирование:** логировать все 5xx и таймауты для алертов/мониторинга

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Проверка | Откат |
|---------|-----------|----------|-------|
| GET /api/arsenal/activity/current | Администратор | Middleware Arsenal (роль) | 403 Forbidden |
| GET /api/arsenal/activity/aggregate | Администратор | Middleware Arsenal (роль) | 403 Forbidden |
| Данные (логи активности) | Arsenal Backend (внутренне) | СУБД-уровень (обычно ACL) | — |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟢 **Узел-фундамент #0 выкатывается ДО потребителей** (детские узлы ARS-101, ARS-102, ARS-103):

1. **Этап 1:** Arsenal Backend с новыми эндпоинтами INT-0 и логикой агрегации (без фич-флага; контракт сразу же доступен)
2. **Этап 2:** Детские фронты (ARS-101, ARS-102, ARS-103) начинают потреблять INT-0

**Обоснование:** детские фронты полагаются на контракт #0; если фронт выкатится раньше, чем бэк предоставит эндпоинты, детские фронты получат 404.

### 6.2. Обратная совместимость

- **Новое взаимодействие:** нет потребителей ДО этого узла (эндпоинты INT-0 только добавляются)
- **Ломаются ли текущие потребители:** нет (они не вызывают `/api/arsenal/activity/*`)
- **Запасной вход:** дети полагаются на эти эндпоинты; откат эндпоинтов → дети получат 404, что они должны обработать как `error_source`

### 6.3. Фиче-флаги

🟢 **Фиче-флагов нет.** Узел выкатывается атомарно; контракт либо полностью доступен, либо нет. Дети знают версию контракта из спеки #0 и поступают с ней.

### 6.4. План отката

- **Откат только BE (Arsenal):** эндпоинты INT-0 удаляются → дети получат 404 → должны обработать как `error_source`, показать "Ошибка получения данных"
  - **Синхронный откат FE необходим?** Нет (фронты детей уже обрабатывают ошибку; они просто останутся в состоянии `error_source`)
  - **Данные в СУБД:** откат эндпоинтов не трогает логи активности; данные остаются, не теряются
- **Откат только FE (детских фронтов):** BE продолжает отдавать INT-0 → новые фронты на старой версии просто не вызывают эндпоинты (или вызывают с ошибкой) → состояние `error_source` → откат детского фронта вернёт старый UI
  - **Локальный стейт на фронте:** дети кэшируют результаты — откат заберёт кэш в старой версии (старый стейт), что нормально
- **Откат DDL:** не применимо (нет новых таблиц)

### 6.5. Преднастройка до релиза

- [x] **Роли в security-сервисе** — роль Администратор должна быть определена в security-сервисе и привязана к пользователям (обычно это предусловие, а не часть этого узла)
- [x] **DDL-миграция** — не требуется (нет новых таблиц)
- [x] **Конфиги по окружениям** — TTL кэша (30с) и таймаут (5с) могут быть параметризованы в конфиге Arsenal Backend; в dev/staging/prod одно и то же
- [x] **Сервисные аккаунты** — не требуются (эндпоинты вызываются прямо фронтом детей; Arsenal → Arsenal — внутренний вызов, не требует отдельного аккаунта)
- [x] **Фиче-флаги** — не требуются (выкат атомарный)
- [x] **Алерты/мониторинг** — установить алерты на: 5xx ошибки на `/api/arsenal/activity/*`, таймауты (408), высокая доля 403 (может означать отсутствие роли у админов)

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 (/current) | Дано: админ вошёл в Arsenal, роль Администратор. Когда: страница админки загрузилась. Тогда: фронт вызывает GET /api/arsenal/activity/current, получает 200 OK с active_count и is_available=true, счётчик отображает значение. |
| FR-2 | INT-0 (/current, кэш 30с) | Дано: счётчик отображает N активных. Когда: число активных пользователей изменяется на N+1. Тогда: в течение 30 секунд счётчик может остаться на N (из-за кэша), но не позже 30с будет обновлён на N+1 (после истечения TTL кэша). |
| FR-3 | INT-0 (/aggregate) | Дано: админ видит счётчик в шапке. Когда: кликает на счётчик. Тогда: открывается модал, фронт вызывает GET /api/arsenal/activity/aggregate с периодом за день (период по умолчанию), получает 200 OK с data_points, график отображает активность за день. |
| FR-4 | INT-0 (/aggregate, параметры period_start/period_end) | Дано: модал открыт с графиком за день. Когда: админ переключает период на неделю. Тогда: фронт вызывает GET /api/arsenal/activity/aggregate с новыми period_start/period_end, получает data_points за неделю, график перестраивается. |
| FR-5 | INT-0 (/aggregate), обработка на фронте | Дано: модал с графиком за выбранный период. Когда: админ нажимает «Выгрузить сводку». Тогда: фронт берёт массив data_points из последнего ответа INT-0, формирует CSV/XLSX со сводкой, браузер скачивает файл. |
