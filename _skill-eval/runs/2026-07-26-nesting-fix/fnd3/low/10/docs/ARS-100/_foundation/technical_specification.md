## 1. Обзор изменения

### 1.1. Тип и стороны

BE-only. Узел-фундамент #0 — чистая реализация, спроектированная один раз для обслуживания нескольких дочерних компонент (фронт счётчика, модальное окно графика, выгрузка сводки). Фундамент предоставляет единый контракт данных активности; потребители (фронты дочерних задач) наследуют этот контракт неизменным.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Собирает и отдаёт данные активности | Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Фундамент реализует общее хранилище и контракт для данных активности, которые питают функциональные требования эпика ARS-100:
- FR-1, FR-2: текущее число активных пользователей (для счётчика в шапке).
- FR-3, FR-4, FR-5: агрегированная активность за период (для графика и выгрузки).

## 2. Взаимодействия (ядро)

### INT-0. Получить текущий снимок активности — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Дочерние фронты (через Arsenal Backend как прокси)
- **Триггер:** Фронт загружается или запрашивает обновление счётчика активных пользователей.
- **Контракт (запрос):** `GET /api/activity/current`
  - Параметры: нет
  - Заголовки: стандартные (авторизация через токен роли Администратор)
- **Контракт (ответ):**
  - `count` (int | null): число активных пользователей. Если `is_unavailable` = true, игнорируется.
  - `is_unavailable` (bool): true если источник данных недоступен (сервис down, таймаут); при true не отдаём устаревшее значение.
  - `timestamp` (ISO8601): момент снимка на бэке (в UTC).
  - `period_no_data` (bool): false для текущего снимка (не применимо). Оставляем для унификации с INT-1.
- **Пример запроса:**
  ```
  GET /api/activity/current
  Authorization: Bearer <admin-token>
  ```
- **Пример ответа (успех, данные доступны):**
  ```json
  {
    "count": 42,
    "is_unavailable": false,
    "timestamp": "2026-07-26T15:34:00Z",
    "period_no_data": false
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null,
    "is_unavailable": true,
    "timestamp": "2026-07-26T15:33:55Z",
    "period_no_data": false
  }
  ```
- **Ошибки:**
  - `403 Forbidden`: вызывающая сторона не имеет роли Администратор. Тело: `{ "error": "insufficient_permissions", "message": "Требуется роль Администратор" }`.
  - `5xx`: внутренняя ошибка бэка. Трактуется как `is_unavailable=true`.
- **Состояния UI по ответу:**
  - `value` → `is_unavailable=false, count > 0`: показать число.
  - `zero` → `is_unavailable=false, count = 0`: показать "0".
  - `empty` → `is_unavailable=false, count = null`: показать "—" (нет данных, но источник доступен — маловероятно для текущего снимка).
  - `error_source` → `is_unavailable=true`: показать "—" и сообщение об ошибке (источник недоступен).
  - `error_forbidden` → `403 Forbidden`: показать "нет доступа" (должно не возникать для администратора).
- **Авторизация:** Роль **Администратор** (проверяется на бэке Arsenal). Без роли — 403. Роль извлекается из токена / сессии.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2 (счётчик активных пользователей в шапке)

### INT-1. Получить агрегированную активность за период — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Дочерние фронты (через Arsenal Backend как прокси)
- **Триггер:** Фронт открывает модальное окно графика либо переключает период.
- **Контракт (запрос):** `GET /api/activity/aggregate`
  - Параметры (query string):
    - `period` (enum: hour | day | week): интервал агрегации. Обязательно.
    - `start_time` (ISO8601): начало периода в UTC. Обязательно.
    - `end_time` (ISO8601): конец периода в UTC (включительно). Обязательно.
  - Заголовки: стандартные (авторизация через токен роли Администратор)
- **Контракт (ответ):**
  - `data` (array of objects | null): массив временных срезов.
    - `timestamp` (ISO8601): начало временного интервала (UTC).
    - `count` (int): число активных пользователей в этом интервале.
    - Если `no_data_for_period=true` или `is_unavailable=true`, `data` может быть пустым массивом или `null`.
  - `no_data_for_period` (bool): true если за запрошенный период нет данных об активности (источник доступен, но записей нет); отличается от `is_unavailable`.
  - `is_unavailable` (bool): true если источник данных недоступен. При true `data` не содержит осмысленное значение.
  - `total_records` (int): количество записей в `data` (для валидации на фронте).
- **Пример запроса:**
  ```
  GET /api/activity/aggregate?period=day&start_time=2026-07-20T00:00:00Z&end_time=2026-07-26T23:59:59Z
  Authorization: Bearer <admin-token>
  ```
- **Пример ответа (успех, данные доступны):**
  ```json
  {
    "data": [
      { "timestamp": "2026-07-20T00:00:00Z", "count": 34 },
      { "timestamp": "2026-07-21T00:00:00Z", "count": 41 },
      { "timestamp": "2026-07-22T00:00:00Z", "count": 39 },
      { "timestamp": "2026-07-23T00:00:00Z", "count": 45 },
      { "timestamp": "2026-07-24T00:00:00Z", "count": 38 },
      { "timestamp": "2026-07-25T00:00:00Z", "count": 42 },
      { "timestamp": "2026-07-26T00:00:00Z", "count": 40 }
    ],
    "no_data_for_period": false,
    "is_unavailable": false,
    "total_records": 7
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "data": [],
    "no_data_for_period": false,
    "is_unavailable": true,
    "total_records": 0
  }
  ```
- **Пример ответа (данные есть, но за период нет активности):**
  ```json
  {
    "data": [],
    "no_data_for_period": true,
    "is_unavailable": false,
    "total_records": 0
  }
  ```
- **Ошибки:**
  - `400 Bad Request`: невалидные параметры (start_time > end_time, неверный period). Тело: `{ "error": "invalid_parameters", "message": "..." }`.
  - `403 Forbidden`: вызывающая сторона не имеет роли Администратор. Тело: `{ "error": "insufficient_permissions", "message": "Требуется роль Администратор" }`.
  - `5xx`: внутренняя ошибка бэка. Трактуется как `is_unavailable=true`.
- **Состояния UI по ответу:**
  - `value` → `is_unavailable=false, no_data_for_period=false, data.length > 0`: показать график/таблицу.
  - `empty` → `is_unavailable=false, no_data_for_period=true`: показать "—" / "нет данных за выбранный период".
  - `zero` → `is_unavailable=false, data.length = 0, no_data_for_period=false`: обработать как `empty` (нет активности, но состояние источника чётко — ноль, а не неизвестно).
  - `error_source` → `is_unavailable=true`: показать "—" и сообщение об ошибке (источник недоступен).
  - `error_forbidden` → `403 Forbidden`: показать "нет доступа".
- **Авторизация:** Роль **Администратор** (проверяется на бэке Arsenal). Без роли — 403.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3, FR-4, FR-5 (модальное окно графика, переключение периода, выгрузка сводки)

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 | `{ "error": "invalid_parameters", "message": "…" }` | Невалидные query-параметры (INT-1) | `error_source` (фронт показывает сообщение об ошибке запроса) |
| 403 | `{ "error": "insufficient_permissions", "message": "Требуется роль Администратор" }` | Вызывающая сторона — не администратор | `error_forbidden` («нет доступа») |
| 5xx | Internal Server Error | Внутренняя ошибка на бэке Arsenal | `error_source` («источник недоступен», retry) |
| таймаут (>5s) | N/A | Запрос зависает дольше лимита | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- Реализует INT-0 (`GET /api/activity/current`) и INT-1 (`GET /api/activity/aggregate`).
- Собирает данные об активности пользователей из **собственных источников** (не полагаясь на чужие сервисы) — как именно собирает (БД, кэш сессий, event-лог) — 🟡 подтверждено аналитиком (не по коду; детализировать при интеграции).
- Проверяет авторизацию: заголовок/токен содержит роль «Администратор» (проверка на бэке Arsenal).
- Кэширует результаты на 30 секунд (время жизни кэша INT-0 и INT-1).
- Логирует ошибки и таймауты для мониторинга.

### 3.2. Данные и хранение

Новых таблиц и сущностей **не заводим**. 🟡 Подтверждено аналитиком: агрегаты активности считаются на лету при каждом запросе (или получаются из существующих источников).

Если в системе Arsenal уже есть таблица сессий / логов активности, используется она; точный механизм расчётов (фильтр по active=true, временной диапазон и т.д.) — 🟡 уточнить при интеграции (детализировать в коде).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** Оба эндпоинта (INT-0 и INT-1) работают синхронно — запрос ждёт ответа, нет async/событий.
- **Таймаут:** 5 секунд максимум для каждого запроса. При превышении — клиент получает таймаут; фронт переводит в состояние `error_source`.
- **Кэш:** На стороне бэка Arsenal, время жизни **30 секунд**.
  - INT-0 (текущий снимок): кэш помогает избежать перегрузки при частых опросах (фронт может опрашивать каждые 10–30 сек).
  - INT-1 (период): кэш остаётся за фундаментом; расчёт агрегатов за период требует работы, кэш на 30s разумен.
- **Инвалидация кэша:** При обновлении данных активности в источнике (создании новой сессии, завершении сессии и т.д.) кэш сбрасывается. 🟡 Подробная стратегия инвалидации — уточнить при интеграции.
- **Ожидаемая нагрузка:** Низкая (только администраторы, периодические запросы). Масштабирование не критично на текущем этапе.

### 5.2. Надёжность / деградация

При недоступности источника данных (сервис down, таймаут, сетевая ошибка):
- Бэк возвращает `is_unavailable=true`, **не старое значение**.
- Фронт видит состояние `error_source` и показывает "—" (вместо устаревшего числа).
- Предусмотрен retry: фронт может переопросить через несколько секунд.

При отсутствии данных за период (но источник доступен):
- INT-1 возвращает `no_data_for_period=true, is_unavailable=false, data=[]`.
- Фронт видит состояние `empty` и показывает "нет данных за период".
- Это отличается от ошибки источника.

### 5.3. Безопасность / доступ (сводно)

| Граница | Субъект | Действие | Проверка | Отказ |
|---------|---------|---------|----------|-------|
| INT-0, INT-1 | Фронт (обычный пользователь) | GET /api/activity/* | Роль = Администратор | 403 Forbidden |
| INT-0, INT-1 | Фронт (администратор) | GET /api/activity/* | Роль = Администратор | — (200 OK) |

Авторизация проверяется на **бэке Arsenal** перед обработкой запроса. Роль извлекается из:
- JWT-токена или сессионной куки (в зависимости от механизма auth Arsenal).
- 🟡 Точный механизм — подтвердить при интеграции.

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **Фундамент (узел #0)** выкатывается **первым** в production.
2. После успешного развёртывания и проверки INT-0 и INT-1 — **затем выкатываются дочерние компоненты** (ARS-101, ARS-102, ARS-103 со своими фронтами).

**Обоснование:** Фронты дочерних задач зависят от контракта фундамента. Если фундамент недоступен, фронты получат ошибку. Порядок гарантирует, что контракт (INT-0, INT-1) уже работает, когда потребители начинают его вызывать.

### 6.2. Обратная совместимость

Фундамент — новое взаимодействие, нет существующих потребителей. Обратной совместимости не требуется.

После выката фундамента дочерние фронты добавляют вызовы INT-0 и INT-1. При изменении контракта фундамента в будущем все дочерние компоненты должны обновиться синхронно — это гарантируется координацией через эпик.

### 6.3. Фиче-флаги

**Не используются.** 🟡 Подтверждено аналитиком: релизим атомарно (фундамент + дочерние компоненты выкатываются вместе без conditional feature flags).

### 6.4. План отката

Если при разработке выясняется дефект INT-0 или INT-1:
- **Откат только BE:** Снимается код INT-0 / INT-1; фронты (если уже выкачены) получают 404 или 5xx. Дочерние фронты должны graceful degrade (показать "—", не падать).
- **Откат только FE:** Фронты откатываются; бэк продолжает отдавать INT-0/INT-1 (потребителей нет) — безопасно.
- **Синхронный откат рекомендуется:** Откатить фундамент и дочерние компоненты вместе.

**DDL-откат:** Новых таблиц нет, миграция БД не требуется.

### 6.5. Преднастройка до релиза (чек-лист)

- [ ] **Роли в security-сервисе:** Роль «Администратор» (она уже существует в системе; подтвердить, что используется в Arsenal для авторизации).
- [ ] **DDL-миграция:** Не требуется (новых таблиц нет).
- [ ] **Конфиги по окружениям:** Timeout 5s, cache TTL 30s — встроить в код Arsenal либо в конфиг по env.
- [ ] **Сервисные аккаунты:** Не требуются (INT-0 и INT-1 вызываются фронтом, заголовки передают роль пользователя).
- [ ] **Фиче-флаги:** Не требуются (релизим без флагов).
- [ ] **Алерты / мониторинг:**
  - 5xx от INT-0, INT-1 (внутренняя ошибка).
  - Таймауты (запросы > 5s).
  - Недоступность источника активности (частые `is_unavailable=true` на короткий промежуток может сигнализировать о проблеме).

## 7. Трассировка приёмки

| FR из БТ (эпик ARS-100) | Взаимодействие(я) из фундамента | Комментарий |
|---------|---------|---------|
| FR-1    | INT-0 | Счётчик активных пользователей в шапке получает число через INT-0. |
| FR-2    | INT-0 | Обновление без перезагрузки — периодический вызов INT-0 (polling). |
| FR-3    | INT-1 | Модальное окно с графиком — запрос INT-1 с периодом по умолчанию. |
| FR-4    | INT-1 | Переключение периода — новый вызов INT-1 с другими параметрами. |
| FR-5    | INT-1 | Выгрузка сводки — использует данные из INT-1. |

**Тест-кейсы (высокоуровневые, детализируются в тестах интеграции):**

- **TC-0.1 [FR-1]** Дано открыта админка от администратора, когда страница загрузилась, тогда фронт вызывает INT-0 и отображает число активных пользователей в шапке.
- **TC-0.2 [FR-2]** Дано открыта админка, когда каждые 30 сек фронт переполрашивает INT-0, тогда счётчик обновляется актуальным числом.
- **TC-0.3 [FR-2 — error]** Дано число активных пользователей изменилось, но источник на бэке недоступен, когда фронт вызывает INT-0, тогда получает `is_unavailable=true` и показывает "—" (не старое число).
- **TC-0.4 [FR-3]** Дано открыта админка и администратор кликает счётчик, когда модальное окно открывается, тогда фронт вызывает INT-1 с периодом по умолчанию (день) и отображает график.
- **TC-0.5 [FR-4]** Дано открыта модалка с графиком, когда администратор переключает период (день → неделя), тогда фронт вызывает INT-1 с новыми параметрами и график перестраивается.
- **TC-0.6 [FR-4 — empty]** Дано период, за который нет данных об активности, когда INT-1 вызывается, тогда возвращает `no_data_for_period=true` и фронт показывает "нет данных".
- **TC-0.7 [FR-5]** Дано открыта модалка с графиком и выбранным периодом, когда администратор нажимает выгрузку, тогда фронт готовит файл на основе данных INT-1 и скачивает.
- **TC-0.8 [AUTH]** Дано обычный (не администратор) пользователь отправляет запрос INT-0, тогда получает 403 Forbidden и фронт показывает "нет доступа".

## 8. Допущения и открытые вопросы

### Подтверждено аналитиком (не по коду — валидировать при интеграции)

- Бэк Arsenal собирает данные об активности пользователей сам, из собственных источников (не от чужих сервисов).
- Агрегаты активности считаются на лету, новые таблицы не создаются.
- При недоступности источника возвращается флаг `is_unavailable=true`, а не стаканое значение.
- Авторизация (проверка роли Администратор) выполняется на бэке Arsenal.
- Кэш 30 секунд находится на стороне бэка.
- Таймаут 5 секунд на запрос.
- Фиче-флаги не используются.
