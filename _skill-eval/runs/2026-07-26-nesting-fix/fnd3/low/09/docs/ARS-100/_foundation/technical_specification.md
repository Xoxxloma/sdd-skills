## 1. Обзор изменения

### 1.1. Тип и стороны
**BE-only.** Фундамент #0 представляет собой контракт доступа к данным активности пользователей, который реализуется на стороне бэка «Арсенала» и потребляется дочерними фронтами (счётчик в шапке, модальное окно графика, выгрузка сводки). Взаимодействие ограничено границей FE↔BE.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (BE) | Собирает и предоставляет данные активности пользователей | Arsenal-Core | 🟡 подтверждено аналитиком |
| Arsenal (FE) — дети (ARS-101, ARS-102, ARS-103) | Потребители контракта | Arsenal-FE | 🟢 новое |

### 1.3. Связь с бизнес-требованиями
Фундамент обслуживает FR-1…FR-5 эпика ARS-100 в части доступа к данным активности. Все три фронтовых элемента (счётчик, график, выгрузка) опираются на единый источник данных: текущее число активных пользователей и агрегированная активность за выбранный период.

## 2. Взаимодействия (ядро)

### INT-1. Получение текущей активности и агрегатов за период — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** FE (Arsenal admin) → BE (Arsenal)
- **Триггер:** 
  - При загрузке страницы (холодный путь)
  - При обновлении счётчика без перезагрузки (тепловой путь, опрос каждые ~30 сек)
  - При переключении периода в модальном окне графика
  - При нажатии выгрузки сводки
- **Контракт (запрос):**
  ```
  GET /api/admin/activity/summary
  Query parameters:
    - period: enum [hour | day | week] (обязателен)
    - from?: ISO8601 timestamp (опционально, для явной границы периода)
  ```
  *Если `from` не указан, период отсчитывается от текущего момента в прошлое.*

- **Контракт (ответ):**
  - **status**: enum [success | unavailable | empty]
    - `success` → есть данные активности
    - `unavailable` → источник данных недоступен (БД/сервис вниз)
    - `empty` → за период данных нет (никакой активности)
  - **current_active_count**: int | null
    - Число активных пользователей сейчас (для FR-1, FR-2)
    - `null` только если `status = unavailable`
  - **aggregates**: array of {timestamp: ISO8601, count: int} | null
    - Агрегированная активность за период с интервалом (зависит от периода: час → 5-мин, день → 1-час, неделя → 1-день)
    - `null` только если `status = unavailable` или `status = empty`
  - **period**: {from: ISO8601, to: ISO8601}
    - Фактический диапазон, за который возвращены агрегаты
  - **message?**: string
    - Человекочитаемое описание ошибки (только если `status = unavailable`)

- **Пример запроса:** (без тела, параметры в query)
  ```
  GET /api/admin/activity/summary?period=day
  ```

- **Пример ответа (успех):**
  ```json
  {
    "status": "success",
    "current_active_count": 42,
    "aggregates": [
      {"timestamp": "2026-07-26T00:00:00Z", "count": 12},
      {"timestamp": "2026-07-26T01:00:00Z", "count": 18},
      {"timestamp": "2026-07-26T02:00:00Z", "count": 9},
      {"timestamp": "2026-07-26T03:00:00Z", "count": 42}
    ],
    "period": {
      "from": "2026-07-26T00:00:00Z",
      "to": "2026-07-27T00:00:00Z"
    }
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "status": "unavailable",
    "current_active_count": null,
    "aggregates": null,
    "period": null,
    "message": "Database connection failed"
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "status": "empty",
    "current_active_count": 0,
    "aggregates": [],
    "period": {
      "from": "2026-07-25T00:00:00Z",
      "to": "2026-07-26T00:00:00Z"
    }
  }
  ```

- **Ошибки:**
  | Код | Сообщение | Когда | Состояние UI |
  |-----|-----------|-------|--------------|
  | 200 + `status: unavailable` | `message: "Database connection failed"` или аналог | источник данных (БД/сервис) недоступен | `error_source` — «—» / перехват ошибки / retry |
  | 200 + `status: empty` | — | за выбранный период нет записей активности | `empty` — «нет данных» / пустой график |
  | 400 | `"Invalid period parameter"` | некорректный `period` или формат timestamp | `error_client` — сообщение об ошибке на фронте |
  | 403 | `"Forbidden"` | роль пользователя не «Администратор» | `error_forbidden` — «нет доступа» |
  | 500 | `"Internal server error"` | неожиданная ошибка BE (логируется) | `error_source` — retry |
  | 504 | `"Gateway timeout"` | таймаут (см. §5.1) | `error_source` — retry |

- **Состояния UI по ответу (фронт-ответственность):**
  - `status: success` + `current_active_count ≠ null и ≠ 0` → **value** — показать число и график
  - `status: success` + `current_active_count = 0` → **zero** — показать «0» (не прочерк, валидный ноль)
  - `status: empty` → **empty** — показать «—» / пустой график / «нет данных»
  - `status: unavailable` → **error_source** — показать ошибку + кнопку retry
  - HTTP 403 → **error_forbidden** — показать «нет доступа»
  - HTTP 400 → **error_client** — показать ошибку на фронте (обычно не видит пользователь, баг разработки)
  - HTTP 5xx / таймаут → **error_source** — показать ошибку + retry

- **Авторизация:**
  - **Кто вправе:** только пользователи с ролью «Администратор»
  - **Где проверяется:** на бэке Arsenal, в middleware/guard до обработки запроса
  - **Негативный случай:** роль не совпадает → 403 Forbidden, тело: `{"code": "forbidden", "message": "Forbidden"}`

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (счётчик), FR-2 (обновление), FR-3 (открытие модали), FR-4 (переключение периода), FR-5 (выгрузка)

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal BE** — реализует INT-1:
- Эндпоинт `GET /api/admin/activity/summary` 🟢 (новый)
- Авторизация: middleware проверки роли «Администратор» перед обработкой 🟢
- 🟡 подтверждено аналитиком: сбор данных активности (сессий) ведётся самим бэком Arsenal, внешних сервисов не привлекаем
- Расчёт текущего числа активных пользователей 🟢 (на лету)
- Расчёт агрегатов активности за период 🟢 (на лету, без новых таблиц)

### 3.2. Данные и хранение

🟡 подтверждено аналитиком: **Новых таблиц не заводим.** Данные активности уже собираются Arsenal'ем (текущие активные сессии). Агрегаты рассчитываются на лету из существующих данных при каждом вызове эндпоинта.

**Что есть в Arsenal BE сейчас (допущение):**
- Таблица или представление с активными сессиями пользователей (время создания, время последней активности, user_id и т.п.)
- Логирование активности или счётчик сессий по интервалам

**Что добавляется:**
- ❌ Новых таблиц нет
- ❌ Новых индексов нет (используются существующие для запроса сессий)
- ✅ Логика расчёта агрегатов в памяти при запросе

### 3.3. Авторизация/доступ на бэке

- Middleware проверяет наличие роли «Администратор» до entry в обработчик INT-1
- 🟡 подтверждено аналитиком: проверка ролей ведётся в сервисе безопасности Arsenal (встроенная интеграция)
- Если роли нет → 403 Forbidden, обработчик не запускается
- Логирование попыток несанкционированного доступа (для аудита)

## 4. Frontend — ответственность

*Фронтовая реализация (счётчик, график, выгрузка) входит в дочерние узлы (ARS-101, ARS-102, ARS-103); здесь только общая ответственность за потребление контракта INT-1.*

### 4.1. Где и что меняется в UI

- Шапка админки: счётчик активных пользователей (FR-1, FR-2)
- Модальное окно: график активности за период (FR-3, FR-4)
- Модальное окно: кнопка выгрузки сводки (FR-5)

### 4.2. Пользовательские сценарии

**Основной поток:**
1. Администратор открывает админку
2. Шапка загружается, фронт вызывает `GET /api/admin/activity/summary?period=day` (холодный путь)
3. Получает текущее число активных пользователей и агрегаты за день
4. Отображает счётчик (FR-1)
5. Фронт периодически опрашивает эндпоинт для обновления счётчика (FR-2)
6. Администратор кликает на счётчик → модальное окно открывается с графиком (FR-3)
7. В модали может выбрать другой период (hour/day/week), фронт пересылает новый запрос (FR-4)
8. Может нажать выгрузку, фронт скачивает файл со сводкой (FR-5)

**Исключения:**
- Источник недоступен → стрелка и ошибка, retry
- Нет доступа (не администратор) → 403, скрыть панель
- Нет данных за период → пусто, не показывать устаревшее

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос / после перезагрузки / переключение периода | спиннер в счётчике / скелетон в графике |
| `value` | 200 + `status: success` + `current_active_count > 0` | число в счётчике + точки на графике |
| `zero` | 200 + `status: success` + `current_active_count = 0` | «0» в счётчике + пустой график |
| `empty` | 200 + `status: empty` | «—» в счётчике / «нет данных» в графике |
| `error_source` | 5xx / таймаут / `status: unavailable` | сообщение об ошибке + кнопка retry |
| `error_forbidden` | 403 | «нет доступа» / панель скрыта |

### 4.3.1. Loading и таймауты

- **Cold-path (первый запрос, холодный кэш):** таймаут 5 сек (соответствует BE таймауту + сетевая задержка)
- **Warm-path (обновление счётчика, кэш 30 сек на BE):** таймаут 2 сек (обычно кэш попадается)
- **Polling (обновление счётчика):** интервал ~30 сек (синхронизирован с BE кэшем)
  - Jitter: ±5 сек (избежать одновременных запросов от всех администраторов)
- При таймауте → состояние `error_source`, retry кнопка

### 4.4. Доступ по ролям в UI

- **Администратор:** видит счётчик, может открыть модаль, выгрузить сводку
- **Оператор / другие роли:** панель активности вообще не отображается (скрыта на уровне компонента или не рендерится)
- Определение роли: читается из контекста пользователя на стороне FE (или передаётся в props из BE)

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** синхронный запрос (не очередь, не события)
- **Кэш на бэке:** 30 сек на стороне Arsenal BE
  - Ключ кэша: `activity_summary:{period}` (отдельный кэш на период или один на «последний результат успеха»)
  - При недоступности источника кэш не используется — сразу возвращается `status: unavailable`
  - 🟡 подтверждено аналитиком: кэш жит в памяти BE Arsenal (не отдельный сервис)
- **Таймаут запроса:** 5 сек (на BE при попытке получить данные)
  - Если за 5 сек не получили ответ → возвращаем `status: unavailable`
- **Частота опроса (polling):**
  - Обновление счётчика в шапке: ~30 сек (синхронизирован с BE кэшем, чтобы не заспамить)
  - При открытии модали: сразу запрос (может быть кэшированный результат, если открыли в течение 30 сек)
- **Ожидаемая нагрузка:** 🟡 к валидации (уточнить с аналитиком, сколько администраторов одновременно)

### 5.2. Надёжность/деградация

- **При недоступности источника (БД вниз, сеть упала):**
  - ✅ Возвращаем `status: unavailable` + флаг в ответе
  - ❌ НЕ возвращаем устаревший кэш (даже если есть)
  - ❌ НЕ скрываем ошибку
  - Фронт видит ошибку, может нажать retry
- **При отсутствии данных за период:**
  - Возвращаем `status: empty` (не `success` с пустым массивом)
  - Фронт различает: «данных нет» ≠ «ошибка получения»
- **Логирование:**
  - 🟢 все вызовы с `status: unavailable` логируются
  - 🟢 попытки несанкционированного доступа (403) логируются для аудита
  - 🟢 таймауты логируются

### 5.3. Безопасность/доступ (сводно)

| Граница | Роль | Может | Нельзя | Проверка |
|---------|------|-------|--------|----------|
| FE → BE (INT-1) | Администратор | читать `current_active_count`, `aggregates` | писать, удалять | BE middleware, 403 если нет роли |
| FE → BE (INT-1) | Оператор / иная роль | ничего | читать данные активности | BE middleware, 403 |

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **Arsenal BE (фундамент #0):** выкатывается ПЕРВЫМ
   - Новый эндпоинт INT-1 доступен, авторизация работает, кэш настроен
2. **Arsenal FE (дочерние узлы ARS-101, ARS-102, ARS-103):** выкатываются после
   - Счётчик, модаль, выгрузка полагаются на готовый контракт INT-1

### 6.2. Обратная совместимость

- **Если откатываем только BE (фронт на старой версии):** 
  - Старый фронт не вызывает INT-1 (он новый), откат безопасен
- **Если откатываем только FE (BE на новой версии):**
  - BE отдаёт INT-1, но старый FE его не вызывает, откат безопасен
- ❌ Парного отката не нужно (слои независимы)

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком: **фиче-флагов нет**, релиз атомарный. Фундамент выкатываем как есть.

### 6.4. План отката

- **Откат BE:** просто выключаем эндпоинт INT-1 (возвращаем 404 или отключаем маршрут)
  - FE на новой версии увидит 404 → состояние `error_source`, покажет ошибку + retry
  - Приемлемо (вывел панель активности, она показывает ошибку, пользователь обновит страницу)
- **Откат FE:** BE продолжает работать, старый FE просто не вызывает INT-1
  - Никакого ущерба
- **DDL:** нет (новых таблиц нет)

### 6.5. Преднастройка до релиза

- [x] **Роли в security-сервисе** — убедиться, что роль «Администратор» определена (уже существует в Arsenal)
- [x] **Кэш** — настроить TTL 30 сек на BE (конфиг или hardcode)
- [x] **Таймаут** — настроить 5 сек на BE при получении данных активности
- [x] **Мониторинг** — настроить alert на 5xx и таймауты INT-1
- [x] **Логирование** — включить логирование вызовов с `status: unavailable` и 403

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 (загрузка, success) | Дано админка, когда загрузилась, тогда счётчик показывает текущее число активных (из INT-1 `current_active_count`) |
| FR-2 | INT-1 (polling, success) | Дано админка открыта, когда активность изменилась, тогда счётчик обновляется без перезагрузки в пределах ~30 сек (polling + кэш BE) |
| FR-3 | INT-1 (period=day по умолчанию) | Дано счётчик видно, когда администратор кликает, тогда модаль открывается с графиком за день (INT-1 ответ с aggregates) |
| FR-4 | INT-1 (переключение period: hour/day/week) | Дано модаль открыта, когда администратор выбирает другой период, тогда вызывается INT-1 с новым period, график перестраивается |
| FR-5 | INT-1 (выгрузка, period выбранный) | Дано модаль с периодом, когда администратор нажимает выгрузку, тогда получает файл со сводкой (данные из INT-1 aggregates) |

## 8. Допущения и открытые вопросы

**🟡 Подтверждено аналитиком (не по коду; валидировать при интеграции):**
- Arsenal BE самостоятельно собирает данные активности пользователей (сессии), внешних сервисов не привлекаем
- При недоступности источника возвращаем флаг `status: unavailable`, а не устаревшие данные
- Отдельно различаем «источник недоступен» vs «данных за период нет» (`status: unavailable` vs `status: empty`)
- Авторизация на основе роли «Администратор», проверка на бэке Arsenal
- Агрегаты рассчитываются на лету (новых таблиц не заводим)
- Синхронный запрос, кэш 30 сек на бэке Arsenal, таймаут 5 сек
- Фундамент выкатывается раньше дочерних узлов
- Фиче-флагов нет, релиз атомарный

**Все технические решения приняты, спецификация готова к разработке.**
