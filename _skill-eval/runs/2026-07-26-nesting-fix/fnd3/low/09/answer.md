## Что входит в спеку

### Основное взаимодействие (INT-1)

Спроектирован единый контракт между фронтом и бэком Arsenal:

**Эндпоинт:** `GET /api/admin/activity/summary?period=[hour|day|week]`

**Ответ содержит:**
- **status:** enum [success | unavailable | empty]
  - `success` — есть данные активности
  - `unavailable` — источник недоступен (БД вниз)
  - `empty` — за период данных нет
- **current_active_count:** число активных пользователей сейчас
- **aggregates:** массив объектов {timestamp, count} — активность за период с интервалами
- **period:** {from, to} — фактический диапазон
- **message** (опционально): описание ошибки при unavailable

**Ключевые особенности:**
1. **Семантика ошибок:** `status: unavailable` (источник вниз) ≠ `status: empty` (данных нет) → фронт может различить состояния UI
2. **Нет устаревших данных:** при недоступности источника кэш не использется
3. **Авторизация:** только роль «Администратор» на бэке Arsenal
4. **Производительность:** синхронный запрос, кэш 30 сек на BE, таймаут 5 сек

## Ответы на все тех-гейты (закрыты)

✅ **Тип и стороны:** BE-only, Arsenal BE отдаёт контракт, дочерние фронты (ARS-101/102/103) потребляют.

✅ **Владение:** Arsenal BE собирает данные активности сам, внешних сервисов не привлекаем (подтверждено аналитиком).

✅ **Ошибки и недоступность:** 
- При недоступности источника → `status: unavailable` (не устаревшее значение)
- Отдельно различаем `status: empty` (за период нет данных)

✅ **Авторизация:** контракт только для роли «Администратор», проверка на бэке Arsenal.

✅ **Данные и хранение:** агрегаты считаются на лету, новых таблиц не заводим.

✅ **Sync/производительность:** синхронно, кэш 30 сек на бэке Arsenal, таймаут 5 сек.

✅ **Порядок выката:** фундамент выкатывается РАНЬШЕ дочерних фронтов.

✅ **Фиче-флаги:** нет, релизим атомарно.

✅ **Трассировка:** INT-1 обслуживает FR-1…FR-5 эпика (счётчик, обновление, модаль, переключение периода, выгрузка).

✅ **Задача/тег:** ARS-100 / узел-фундамент #0 (no task number for #0, используем ключ эпика).

## Содержание спеки

1. **Обзор изменения** — тип (BE-only), затронутые сервисы (Arsenal BE → Arsenal FE дети), связь с БТ.

2. **Взаимодействия (INT-1)** — полный контракт:
   - Граница: FE → BE
   - Триггер: загрузка, обновление счётчика, переключение периода, выгрузка
   - Request: `GET /api/admin/activity/summary?period=...`
   - Response: status, current_active_count, aggregates, period, message
   - JSON примеры: успех, недоступность, пусто
   - Каталог HTTP кодов и маппинг на UI-состояния
   - Авторизация: только Администратор, 403 если нет
   - Провенанс: 🟢 новое (фундамент #0)

3. **Backend** — Arsenal BE:
   - Реализует INT-1 (новый эндпоинт)
   - Авторизация middleware (проверка роли)
   - Данные: используются существующие сессии, новых таблиц нет
   - Логика: расчёт текущего числа и агрегатов на лету
   - Кэш: 30 сек в памяти BE

4. **Frontend** — дочерние узлы:
   - Потребляют INT-1 для счётчика, графика, выгрузки
   - Состояния: loading, value, zero, empty, error_source, error_forbidden
   - Polling: ~30 сек для обновления счётчика
   - Таймауты: cold-path 5 сек, warm-path 2 сек

5. **Нефункциональные требования** — производительность, надёжность, безопасность:
   - Синхронный запрос
   - Кэш 30 сек (не используется при недоступности)
   - Таймаут 5 сек
   - Polling ~30 сек с jitter
   - При ошибке: логирование, сигнал в UI, retry

6. **Релиз и интеграция:**
   - Порядок выката: BE #0 → FE дочерние
   - Откат безопасен в обе стороны (слои независимы)
   - Фиче-флагов нет
   - Преднастройка: роли, кэш TTL, таймаут, мониторинг

7. **Трассировка приёмки** — каждая FR (FR-1…FR-5) → INT-1 → тест-кейс.

8. **Допущения** — все подтверждены аналитиком (не по коду):
   - Arsenal BE собирает данные сам
   - Разделение ошибок (unavailable vs empty)
   - Роль Администратор
   - Агрегаты на лету
   - Кэш 30 сек, таймаут 5 сек
   - Порядок выката
   - Атомарный релиз
