## 2. Взаимодействия (ядро)

### INT-0. Данные активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Арсенал (BE) → Фронты детей (ARS-101, ARS-102, ARS-103)
- **Описание:** Единое семейство контрактов, возвращающих:
  1. **текущее число активных пользователей** (для FR-1, FR-2);
  2. **агрегированную активность за период** (для FR-3, FR-4, FR-5).

#### INT-0a. Получить текущее число активных пользователей
- **Триггер:** 
  - Инициализация страницы администратора.
  - Периодический опрос (параллельно — см. §5.1).
- **Контракт (запрос):** `GET /api/v1/admin/activity/current`
  - Параметры: нет
  - Заголовки: стандартные (авторизация на уровне фреймворка)
- **Контракт (ответ):** 
  - `active_users` (integer | null): текущее число активных пользователей. `null` → источник недоступен.
  - `available` (boolean): `true` если данные актуальны, `false` если источник недоступен.
  - `timestamp` (ISO 8601 string): момент снятия данных на бэке.
- **Пример запроса:**
  ```
  GET /api/v1/admin/activity/current
  ```
- **Пример ответа (успех — данные доступны):**
  ```json
  {
    "active_users": 42,
    "available": true,
    "timestamp": "2026-07-26T14:35:22Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "active_users": null,
    "available": false,
    "timestamp": "2026-07-26T14:35:22Z"
  }
  ```
- **Ошибки:** 
  - `401 Unauthorized`: пользователь не авторизован.
  - `403 Forbidden`: роль не является "Администратор".
  - `5xx`: внутренняя ошибка сервера (обработать как `available: false`).
- **Состояния UI по ответу:**
  - `available: true, active_users ≠ null` → значение (число);
  - `available: true, active_users = null` → `zero` (показать «0»);
  - `available: false` → `error_source` (показать «—» + tooltip о недоступности);
  - `403` → `error_forbidden` (скрыть виджет / показать сообщение).
- **Авторизация:** 
  - Доступ только роли **Администратор**.
  - Проверка на бэке Arsenal: HTTP-код 403 при других ролях.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2

#### INT-0b. Получить агрегированную активность за период
- **Триггер:** 
  - Открытие модального окна (default период).
  - Переключение периода в модальном окне.
  - Запрос выгрузки сводки.
- **Контракт (запрос):** `GET /api/v1/admin/activity/aggregated`
  - **Параметры:**
    - `period` (enum: `hour`, `day`, `week`): требуемая гранулярность временных точек. Обязателен.
    - `start_time` (ISO 8601 string): начало диапазона. Обязателен.
    - `end_time` (ISO 8601 string): конец диапазона (исключительно). Обязателен.
  - **Заголовки:** стандартные (авторизация на уровне фреймворка).
- **Контракт (ответ):**
  - `period` (enum: `hour`, `day`, `week`): гранулярность, как запросили.
  - `start_time` (ISO 8601 string): запросили; даётся в ответе для подтверждения.
  - `end_time` (ISO 8601 string): запросили; даётся в ответе.
  - `available` (boolean): `true` если данные актуальны, `false` если источник недоступен.
  - `data_exists` (boolean): `true` если за диапазон есть хоть одна точка активности; `false` если диапазон не содержит данных (но источник был доступен).
  - `points` (array of objects | null):
    - `time` (ISO 8601 string): момент времени (начало бакета).
    - `active_users` (integer): число активных пользователей в этот момент.
    - Если `available: false`, весь массив = `null`.
  - `timestamp` (ISO 8601 string): момент снятия данных на бэке.
- **Пример запроса:**
  ```
  GET /api/v1/admin/activity/aggregated?period=day&start_time=2026-07-20T00:00:00Z&end_time=2026-07-27T00:00:00Z
  ```
- **Пример ответа (успех, данные есть):**
  ```json
  {
    "period": "day",
    "start_time": "2026-07-20T00:00:00Z",
    "end_time": "2026-07-27T00:00:00Z",
    "available": true,
    "data_exists": true,
    "points": [
      {
        "time": "2026-07-20T00:00:00Z",
        "active_users": 15
      },
      {
        "time": "2026-07-21T00:00:00Z",
        "active_users": 22
      },
      {
        "time": "2026-07-22T00:00:00Z",
        "active_users": 18
      }
    ],
    "timestamp": "2026-07-26T14:35:22Z"
  }
  ```
- **Пример ответа (успех, данных нет за период):**
  ```json
  {
    "period": "day",
    "start_time": "2026-01-01T00:00:00Z",
    "end_time": "2026-01-08T00:00:00Z",
    "available": true,
    "data_exists": false,
    "points": [],
    "timestamp": "2026-07-26T14:35:22Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "day",
    "start_time": "2026-07-20T00:00:00Z",
    "end_time": "2026-07-27T00:00:00Z",
    "available": false,
    "data_exists": null,
    "points": null,
    "timestamp": "2026-07-26T14:35:22Z"
  }
  ```
- **Ошибки:**
  - `400 Bad Request`: отсутствуют параметры, неверный формат даты или диапазон (start ≥ end).
  - `401 Unauthorized`: пользователь не авторизован.
  - `403 Forbidden`: роль не является "Администратор".
  - `5xx`: внутренняя ошибка сервера (обработать как `available: false`).
- **Состояния UI по ответу:**
  - `available: true, data_exists: true` → `value` (график с точками);
  - `available: true, data_exists: false` → `empty` (показать «нет данных за период»);
  - `available: false` → `error_source` (показать «—» + retry + сообщение о недоступности);
  - `403` → `error_forbidden` (скрыть модалку).
- **Авторизация:**
  - Доступ только роли **Администратор**.
  - Проверка на бэке Arsenal: HTTP-код 403 при других ролях.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3, FR-4, FR-5

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI | Действие пользователя |
|-----|----------------|-------|--------------|----------------------|
| 400 | `{"error": "invalid_period_range", "message": "start_time must be before end_time"}` | start_time ≥ end_time или отсутствуют параметры | `error_source` | retry с корректными параметрами |
| 401 | стандартный 401 (сессия истекла) | пользователь не авторизован | redirect на login | ре-авторизация |
| 403 | `{"error": "forbidden", "message": "Administrator role required"}` | роль не "Администратор" | скрыть виджет / сообщение | — |
| 5xx | любое тело | сбой бэка | `error_source` (available: false) | retry |

## 3. Backend — ответственность

### 3.1. По сервисам
**Арсенал (BE):**
- Реализует два эндпоинта (INT-0a, INT-0b) согласно контрактам в §2.
- **INT-0a:** возвращает текущее число активных пользователей (снимается в момент запроса или из кэша).
- **INT-0b:** возвращает временной ряд активности за запрошенный период и гранулярность.
- Оба эндпоинта:
  - Проверяют авторизацию (роль "Администратор") на бэке; возвращают 403 при её отсутствии.
  - Различают недоступность источника (флаг `available: false`) от отсутствия данных (`data_exists: false`).
  - Синхронны; кэшируют на уровне бэка (см. §5.1).

### 3.2. Данные и хранение
🟡 Подтверждено аналитиком: **Новые таблицы не заводятся.** Агрегаты активности считаются на лету из существующего источника данных активности (сеансов, логов, событий). Точный источник и механизм расчёта — на стороне Arsenal (не требует изменения схемы БД).

### 3.3. Авторизация/доступ на бэке
- **Где:** на уровне Арсенала, в обработчиках `/api/v1/admin/activity/*`.
- **Как:** проверка роли пользователя из контекста сессии / токена.
- **Роль:** только "Администратор" имеет доступ.
- **Негативный случай:** другие роли → HTTP 403 (Forbidden).

## 4. Frontend — ответственность
Фронты детей (ARS-101, ARS-102, ARS-103) наследуют контракты INT-0a и INT-0b и строят на них свои UI и логику:
- **FR-1, FR-2 (ARS-101):** используют INT-0a для счётчика в шапке.
- **FR-3, FR-4, FR-5 (ARS-102, ARS-103):** используют INT-0b для модального окна, графика и выгрузки.

Не применимо: фундамент — лишь контракт; UI-ответственность передана детям.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** 🟡 подтверждено аналитиком — обе операции (INT-0a, INT-0b) синхронны.
- **Кэш:** 
  - 🟡 подтверждено аналитиком — кэш сроком **30 секунд** на стороне бэка Arsenal.
  - Каждый запрос к `INT-0a` или `INT-0b` может вернуть кэшированное значение (если вторая обращение в течение 30с к тому же эндпоинту и параметрам).
- **Таймаут:**
  - 🟡 подтверждено аналитиком — **5 секунд** на бэке. По истечении → 5xx, фронт видит `available: false`.
- **Полоса пропускания и нагрузка:**
  - Int-0a вызывается периодически из фронтов (каждые несколько секунд).
  - INT-0b вызывается по инициативе пользователя (при открытии модалки, переключении периода).
  - Ожидаемая нагрузка: средняя (количество администраторов ограничено).

### 5.2. Надёжность/деградация
- **При недоступности источника:** 🟡 подтверждено аналитиком — отдаём `available: false`, а не устаревшее значение. Фронт видит это и показывает ошибку («—» / сообщение).
- **Различие ошибок:**
  - `available: false` (INT-0a) или `available: false` (INT-0b) → источник недоступен (5xx, таймаут, сетевая ошибка).
  - `data_exists: false` (INT-0b) → источник доступен, но за диапазон нет данных (нормальный случай).

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто вправе | Где проверяется | Негативный случай |
|---------|-----------|-----------------|-------------------|
| GET /api/v1/admin/activity/current | Администратор | BE Arsenal | 403 Forbidden |
| GET /api/v1/admin/activity/aggregated | Администратор | BE Arsenal | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟡 **Подтверждено аналитиком:** узел-фундамент #0 выкатывается **раньше потребителей** (ARS-101, ARS-102, ARS-103). 
- **Фаза 1:** Развёртывание BE Arsenal с новыми эндпоинтами INT-0a и INT-0b.
- **Фаза 2:** Развёртывание FE детей, которые начинают вызывать эндпоинты (один или несколько дней спустя).

### 6.2. Обратная совместимость
- **Новые эндпоинты:** `/api/v1/admin/activity/*` — не существовали, не ломают текущих потребителей.
- **Требует старых потребителей:** нет.
- **Безопасность:** новые эндпоинты доступны только "Администратору", остальные не видят (403).

### 6.3. Фиче-флаги
🟡 **Подтверждено аналитиком:** фиче-флагов нет. Релизим атомарно: раз бэк развёрнут, фронты начинают вызывать контракты.

### 6.4. План отката
- **Откат BE:** фронты на старой версии получают 404 на эндпоинты → обработка ошибки (показ ошибки). Требуется синхронный откат FE (старая версия не знает о контрактах).
- **Откат FE:** BE продолжает отдавать эндпоинты (они остаются в продакшене). FE старой версии просто не вызывает. Безопасно.

### 6.5. Преднастройка до релиза
- [x] Роли в security-сервисе — роль "Администратор" должна существовать в системе ролей Arsenal (скорее всего, уже есть).
- [x] DDL-миграция в репо — не требуется (нет новых таблиц).
- [x] Конфиги по окружениям — кэш-TTL (30с), таймаут (5с) можно сделать конфигурируемыми в .env или конфигурационном сервисе.
- [x] Сервисные аккаунты — не требуется (внутренние эндпоинты в пределах одной системы Arsenal).
- [x] Фиче-флаги — не требуется.
- [x] Алерты/мониторинг — рекомендуется отслеживать: 5xx при вызове INT-0a/INT-0b (источник недоступен), таймауты, 403 (проблемы с авторизацией).

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
