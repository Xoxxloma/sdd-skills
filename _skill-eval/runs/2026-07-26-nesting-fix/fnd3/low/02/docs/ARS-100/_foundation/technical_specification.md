## 1. Обзор

### 1.1. Назначение узла-фундамента #0

Узел-фундамент #0 предоставляет единый контракт данных о текущей и исторической активности пользователей. Этот контракт используется несколькими фронтов-потребителями эпика ARS-100:
- панель счётчика активных пользователей в шапке (FR-1, FR-2)
- модальное окно с графиком активности по периодам (FR-3, FR-4)
- выгрузка сводки активности (FR-5)

Все три потребителя обращаются к одному и тому же источнику данных, спроектированному здесь.

### 1.2. Тип и стороны

🟡 **подтверждено аналитиком:** BE-only. Узел-фундамент #0 — бэк-компонент, выдающий контракт данных активности. Потребители — несколько фронтов (детские компоненты UI, разработанные в дочерних задачах ARS-101, ARS-102, ARS-103).

### 1.3. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | Собирает и агрегирует данные активности, выдаёт контракт | Team Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.4. Связь с бизнес-требованиями

Узел #0 обслуживает функциональные требования FR-1–FR-5 в части **передачи данных активности** (текущий счётчик и агрегаты за период). Визуализация и взаимодействие с пользователем — ответственность детских фронтов (ARS-101, ARS-102, ARS-103); БТ для них заведены отдельно.

## 2. Взаимодействия (ядро контракта)

### INT-1. Получить текущее число активных пользователей — 🟢

- **Граница/направление:** Arsenal backend → FE-потребители
- **Триггер:** инициализация фронта; периодический опрос каждые 30 секунд (кэш на стороне бэка)
- **Контракт (запрос):** GET `/api/arsenal/activity/current` (тело отсутствует, параметров нет)
- **Контракт (ответ):**
  - `count` (integer | null): число активных пользователей в данный момент; `null` если источник недоступен
  - `isUnavailable` (boolean): true если источник данных недоступен; false если данные валидны
  - `timestamp` (ISO 8601 string): момент получения данных на бэке
- **Пример запроса:** тело отсутствует
  ```
  GET /api/arsenal/activity/current
  ```
- **Пример ответа (успех, есть активные):**
  ```json
  {
    "count": 42,
    "isUnavailable": false,
    "timestamp": "2026-07-26T14:30:15Z"
  }
  ```
- **Пример ответа (успех, активных нет):**
  ```json
  {
    "count": 0,
    "isUnavailable": false,
    "timestamp": "2026-07-26T14:30:15Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null,
    "isUnavailable": true,
    "timestamp": "2026-07-26T14:30:15Z"
  }
  ```
- **Ошибки:** см. каталог
- **Состояния UI по ответу:**
  - `value`: 2xx, count > 0 → показать число активных пользователей
  - `zero`: 2xx, count = 0 → показать «0»
  - `empty`: 2xx, count = null, isUnavailable = false → показать «—» (нет данных, но источник доступен — не должно происходить в нормальном режиме)
  - `error_source`: 2xx с isUnavailable = true ИЛИ 5xx / таймаут → показать сообщение об ошибке + кнопка retry
  - `forbidden`: 403 → показать «нет доступа»
- **Авторизация:** доступна только роли Администратор; проверка на стороне Arsenal backend. Запрос без роли Администратор возвращает 403.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (отображение счётчика), FR-2 (автоматическое обновление)

### INT-2. Получить агрегированную активность за период — 🟢

- **Граница/направление:** Arsenal backend → FE-потребители
- **Триггер:** запрос фронта при открытии модального окна или смене периода
- **Контракт (запрос):** GET `/api/arsenal/activity/aggregates?period={period}` (параметр period в query string)
  - `period` (string, enum): требуемый период агрегации; допустимые значения: `hour`, `day`, `week`
- **Контракт (ответ):**
  - `period` (string, enum): переданный период (echo); значения: `hour`, `day`, `week`
  - `counts` (array of [timestamp, count]): массив пар [ISO 8601 timestamp, number]; содержит временные ряды активности за период; пусто если noData = true или isUnavailable = true
  - `isUnavailable` (boolean): true если источник данных недоступен; false если данные валидны или отсутствуют, но источник доступен
  - `noData` (boolean): true если источник доступен (isUnavailable = false), но за запрашиваемый период нет данных; false если есть данные или источник недоступен
  - `timestamp` (ISO 8601 string): момент получения данных на бэке
- **Пример запроса:**
  ```
  GET /api/arsenal/activity/aggregates?period=day
  ```
- **Пример ответа (успех, есть данные):**
  ```json
  {
    "period": "day",
    "counts": [
      ["2026-07-26T00:00:00Z", 10],
      ["2026-07-26T01:00:00Z", 15],
      ["2026-07-26T02:00:00Z", 12],
      ["2026-07-26T03:00:00Z", 18],
      ["2026-07-26T04:00:00Z", 20],
      ["2026-07-26T05:00:00Z", 25],
      ["2026-07-26T06:00:00Z", 30],
      ["2026-07-26T07:00:00Z", 28],
      ["2026-07-26T08:00:00Z", 35],
      ["2026-07-26T09:00:00Z", 40],
      ["2026-07-26T10:00:00Z", 42],
      ["2026-07-26T11:00:00Z", 38],
      ["2026-07-26T12:00:00Z", 45],
      ["2026-07-26T13:00:00Z", 48],
      ["2026-07-26T14:00:00Z", 50]
    ],
    "isUnavailable": false,
    "noData": false,
    "timestamp": "2026-07-26T14:30:15Z"
  }
  ```
- **Пример ответа (успех, но данных за период нет):**
  ```json
  {
    "period": "week",
    "counts": [],
    "isUnavailable": false,
    "noData": true,
    "timestamp": "2026-07-26T14:30:15Z"
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "day",
    "counts": [],
    "isUnavailable": true,
    "noData": false,
    "timestamp": "2026-07-26T14:30:15Z"
  }
  ```
- **Ошибки:** см. каталог
- **Состояния UI по ответу:**
  - `value`: 2xx, isUnavailable = false, noData = false, counts.length > 0 → построить и показать график
  - `empty`: 2xx, isUnavailable = false, noData = true → показать «нет данных за этот период»
  - `error_source`: 2xx с isUnavailable = true ИЛИ 5xx / таймаут → показать сообщение об ошибке + кнопка retry; возможно, показать последний доступный график с указанием временной метки
  - `forbidden`: 403 → показать «нет доступа»
- **Авторизация:** доступна только роли Администратор; проверка на стороне Arsenal backend. Запрос без роли Администратор возвращает 403.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3 (открытие модального окна с графиком), FR-4 (переключение периода), FR-5 (выгрузка сводки)

### Каталог ошибок

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 | `{ "error": "invalid_period", "message": "period must be one of: hour, day, week" }` | Запрос INT-2 с неправильным значением period (не hour / day / week) | error (показать сообщение об ошибке от сервера) |
| 401 | `{ "error": "unauthorized", "message": "authentication required" }` | Запрос без JWT/сессии либо сессия истекла | error (предложить пересоздать сессию) |
| 403 | `{ "error": "forbidden", "message": "administrator role required" }` | Роль текущего пользователя — не Администратор | error_forbidden («нет доступа») |
| 500 | `{ "error": "internal_server_error", "message": "failed to fetch activity data" }` | Ошибка на бэке Arsenal при получении данных активности | error_source (показать «Ошибка при загрузке данных» + retry) |
| 504 | `{ "error": "gateway_timeout", "message": "service unavailable" }` | Таймаут при обращении к источнику данных (таймаут 5 сек) | error_source (показать «Данные временно недоступны» + retry) |

## 3. Backend — ответственность

### 3.1. Arsenal backend

🟡 **подтверждено аналитиком:** Backend Arsenal реализует оба контракта (INT-1 и INT-2):
- INT-1: эндпоинт GET `/api/arsenal/activity/current` возвращает текущее число активных пользователей
- INT-2: эндпоинт GET `/api/arsenal/activity/aggregates` возвращает агрегированную активность за период

Данные собираются самим Arsenal backend'ом; внешних сервисов для сбора активности не используется.

🟡 **подтверждено аналитиком:** Кэширование на стороне Arsenal backend; TTL кэша = 30 секунд.

🟡 **подтверждено аналитиком:** Таймаут обращения к источнику данных активности = 5 секунд.

### 3.2. Данные и хранение

🟡 **подтверждено аналитиком:** Новых таблиц/сущностей не заводим. Агрегаты активности считаются на лету из существующих данных об активности/сессиях пользователей, хранимых в Arsenal backend. Точный источник данных (какие таблицы, какие поля) и механизм расчёта агрегатов — определяются при разработке и валидируются на интеграции.

### 3.3. Авторизация на бэке

Оба эндпоинта (INT-1 и INT-2) проверяют, что роль текущего пользователя = `Администратор`. Проверка выполняется на бэке Arsenal. Запрос от пользователя без этой роли возвращает 403 Forbidden.

## 4. Frontend — ответственность

Не применимо: узел-фундамент #0 предоставляет только контракт данных; визуализация и взаимодействие с пользователем — ответственность детских фронтов (ARS-101, ARS-102, ARS-103), описанных в их собственных tech spec'ах.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

🟡 **подтверждено аналитиком:**
- Оба контракта (INT-1, INT-2) работают **синхронно** (FE ждёт ответа).
- **Кэш:** 30 секунд на стороне Arsenal backend. FE может кэшировать результаты локально по собственному усмотрению.
- **Таймаут запроса:** 5 секунд на обращение к источнику данных. Если истекает — возвращается 504 Gateway Timeout.
- **Polling с FE:** FE может опрашивать INT-1 каждые 30 секунд (соответствуя TTL кэша); более частые запросы получат кэшированный ответ.

### 5.2. Надёжность/деградация

🟡 **подтверждено аналитиком:**
- При недоступности источника данных активности эндпоинты возвращают флаг `isUnavailable = true` и `count/counts = null/[]`, **не выдавая устаревшие данные**.
- Отдельно различаем две ситуации:
  - Источник **недоступен** → `isUnavailable = true`
  - Источник **доступен**, но **нет данных за период** → `isUnavailable = false`, `noData = true` (для INT-2)
- FE должна показывать пользователю разные состояния в зависимости от флагов.

### 5.3. Безопасность/доступ

| Граница | Кто может | Проверка | Негативный случай |
|---------|-----------|----------|-------------------|
| INT-1, INT-2 | Роль Администратор | Arsenal backend | Запрос без роли → 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 **подтверждено аналитиком:** Узел-фундамент #0 выкатывается **раньше дочерних фронтов** (ARS-101, ARS-102, ARS-103). Дочерние фронты зависят от контрактов INT-1 и INT-2 и смогут быть развёрнуты только после того, как эти контракты доступны на боевом сервере.

### 6.2. Обратная совместимость

Узел #0 — новое изменение, обратная совместимость неприменима. После выката контракты фиксируются и не меняются без координации с детскими фронтами.

### 6.3. Фиче-флаги

🟡 **подтверждено аналитиком:** Фиче-флагов нет. Релизим **атомарно**: оба эндпоинта становятся доступны одновременно после выката.

### 6.4. План отката

Откат только Arsenal backend: оба эндпоинта становятся недоступны (возвращают 500 / 504). FE, которая уже отката, будет получать ошибки и показывать `error_source` состояние («данные недоступны»). Это допустимо; синхронный откат FE не требуется.

### 6.5. Преднастройка до релиза

- [x] Роли в security-сервисе: роль `Администратор` должна быть определена в системе; эндпоинты проверяют её наличие
- [x] Миграции БД: не требуются (агрегаты считаются на лету)
- [x] Конфиги по окружениям: TTL кэша (30 сек), таймаут (5 сек) — можно сделать конфигурируемыми по окружениям
- [x] Сервисные аккаунты: не требуются (контракт не делает межсервисных вызовов за пределами Arsenal)
- [x] Алерты/мониторинг: заводим на ошибки `error_source` (5xx, 504) и таймауты; отслеживаем SLA на ответ (целевое < 100ms при кэше)

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано открытую админку с ролью Администратор, когда страница загружена, тогда эндпоинт INT-1 вызван и в шапке показано число активных пользователей (или ошибка если недоступно) |
| FR-2 | INT-1 | Дано счётчик активных, когда число активных пользователей меняется, тогда INT-1 вызывается периодически и счётчик обновляется (кэш TTL = 30 сек, FE может опрашивать каждые 30 сек) |
| FR-3 | INT-2 | Дано счётчик в шапке, когда администратор кликает на него, тогда INT-2 вызывается с period=day и в модальном окне показывается график активности за день |
| FR-4 | INT-2 | Дано открытую модалку, когда администратор выбирает другой период, тогда INT-2 вызывается с новым period (hour / day / week) и график перестраивается |
| FR-5 | INT-2 | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда данные из INT-2 используются для генерации файла со сводкой активности за этот период |
