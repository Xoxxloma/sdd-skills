## 1. Обзор изменения
### 1.1. Тип и стороны
BE-only. Узел-фундамент #0 предоставляет контракт данных активности пользователей (текущее число активных и агрегированную активность за период) для потребления детскими фронтами (ARS-101, ARS-102, ARS-103). Бэк «Арсенала» реализует сбор и агрегацию данных; новых таблиц не заводим.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Собирает и отдаёт контракт данных активности | Команда Arsenal-Core | 🟢 НОВОЕ (узел-фундамент #0) |

### 1.3. Связь с бизнес-требованиями
Фундамент обслуживает общий источник данных для FR-1..FR-5 эпика: администраторы видят текущее число активных пользователей и историческую активность за выбранный период (час/день/неделя). Все три элемента UI (счётчик в шапке, график в модалке, выгрузка сводки) опираются на этот одинаковый контракт.

## 2. Взаимодействия (ядро)
### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Arsenal Backend → детские фронты (ARS-101, ARS-102, ARS-103)
- **Триггер:** 
  - Текущая активность: при загрузке страницы и по таймеру (интервал к валидации на стороне потребителя)
  - Активность за период: при открытии модалки и смене выбранного периода
- **Контракт (запрос):** 
  - Текущая активность: GET `/api/arsenal/activity/current` (без параметров)
  - Активность за период: GET `/api/arsenal/activity/history?period=<hour|day|week>` (параметр `period` обязателен)
- **Контракт (ответ):**
  
  **Текущая активность:**
  - `active_users` (int ≥ 0 | null): число активных пользователей в данный момент. `null` → источник недоступен.
  - `is_available` (bool): флаг доступности источника данных. `false` → не показывать значение как актуальное.
  - `timestamp` (ISO8601): время последнего обновления счёта.
  
  **Активность за период:**
  - `period` (string: "hour" | "day" | "week"): запрошенный период (эхо).
  - `period_start` (ISO8601): начало выбранного периода.
  - `period_end` (ISO8601): конец выбранного периода.
  - `is_available` (bool): флаг доступности; `false` → показать «—» вместо графика.
  - `data` (array[object] | null): массив агрегатов активности или `null` если нет данных за период.
    - Каждый элемент: `{ "timestamp": ISO8601, "active_users": int ≥ 0 }` (интервал времени зависит от периода: минута для hour, час для day, день для week).
  - `has_data` (bool): `true` если `data` не пуст, `false` если за период нет активности (но источник доступен). Различает zero/empty.

- **Пример запроса (текущая активность):**
  ```
  GET /api/arsenal/activity/current
  Authorization: Bearer <token>
  ```

- **Пример ответа (текущая активность, успех):**
  ```json
  {
    "active_users": 42,
    "is_available": true,
    "timestamp": "2026-07-26T18:35:00Z"
  }
  ```

- **Пример ответа (текущая активность, источник недоступен):**
  ```json
  {
    "active_users": null,
    "is_available": false,
    "timestamp": "2026-07-26T18:35:00Z"
  }
  ```

- **Пример запроса (активность за период):**
  ```
  GET /api/arsenal/activity/history?period=day
  Authorization: Bearer <token>
  ```

- **Пример ответа (активность за период, есть данные):**
  ```json
  {
    "period": "day",
    "period_start": "2026-07-25T00:00:00Z",
    "period_end": "2026-07-26T00:00:00Z",
    "is_available": true,
    "has_data": true,
    "data": [
      { "timestamp": "2026-07-25T00:00:00Z", "active_users": 10 },
      { "timestamp": "2026-07-25T01:00:00Z", "active_users": 8 },
      { "timestamp": "2026-07-25T02:00:00Z", "active_users": 5 },
      { "timestamp": "2026-07-26T00:00:00Z", "active_users": 12 }
    ]
  }
  ```

- **Пример ответа (активность за период, нет данных, но источник доступен):**
  ```json
  {
    "period": "day",
    "period_start": "2026-07-25T00:00:00Z",
    "period_end": "2026-07-26T00:00:00Z",
    "is_available": true,
    "has_data": false,
    "data": null
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "day",
    "period_start": "2026-07-25T00:00:00Z",
    "period_end": "2026-07-26T00:00:00Z",
    "is_available": false,
    "has_data": false,
    "data": null
  }
  ```

- **Ошибки:**
  - `400 Bad Request`: некорректный параметр `period` (не один из "hour", "day", "week"). Тело: `{ "error": "invalid_period", "message": "期间 должен быть одним из: hour, day, week" }`.
  - `401 Unauthorized`: отсутствует или невалидный токен. Тело: `{ "error": "unauthorized", "message": "Требуется аутентификация" }`.
  - `403 Forbidden`: роль не имеет доступа к данным активности (не Администратор). Тело: `{ "error": "forbidden", "message": "Недостаточно прав для просмотра активности" }`.
  - `408 Request Timeout`: запрос к источнику данных превышен (таймаут 5 сек). Обработать на стороне потребителя как `is_available=false`. Тело: `{ "error": "timeout", "message": "Источник данных не ответил в заданное время" }`.
  - `500 Internal Server Error`: ошибка при вычислении агрегатов. Обработать как недоступность. Тело: `{ "error": "internal_error", "message": "Ошибка при получении данных активности" }`.

- **Состояния UI по ответу (специфичны для потребителей, примеры):**
  - Значение (текущая) / график (период): `is_available=true` и данные присутствуют → показать значение / график.
  - Пусто/«—»: `is_available=true`, `has_data=false` (за период нет активности, но источник исправен) → показать «—» / пустой график.
  - Ошибка/недоступность: `is_available=false` (источник недоступен, таймаут, 5xx) → показать «—» + сообщение об ошибке, предложить retry.
  - Ноль: `is_available=true`, `active_users=0` (валидный ноль активных) → показать «0» (не «—»).

- **Авторизация:**
  - Контракт доступен ТОЛЬКО роли Администратор.
  - Проверка на стороне Arsenal Backend перед возвратом данных.
  - Если роль ≠ Администратор → 403 Forbidden.

- **Происхождение:** 🟢 новое (узел-фундамент #0, спроектировано в этом документе).
- **Трассировка:** FR-1 (счётчик активных), FR-2 (обновление без перезагрузки), FR-3 (клик → модалка), FR-4 (переключение периода), FR-5 (выгрузка сводки).

## 3. Backend — ответственность
### 3.1. По сервисам
**Arsenal Backend:**
- Реализует два эндпоинта INT-0 (текущая активность и история за период).
- Потребляет данные о сессиях пользователей из собственных хранилищ (🟡 подтверждено аналитиком: собирает сам, чужих сервисов не привлекаем).
- Вычисляет агрегаты активности на лету (see §3.2).
- Enforces авторизацию: только Администраторы видят данные (§3.3).

### 3.2. Данные и хранение
**Новых таблиц и хранилищ не заводим** (🟡 подтверждено аналитиком). Arsenal Backend использует существующие логи/записи сессий:
- Источник: действующее хранилище актуальных и исторических сессий (структура: 🟡 к валидации на этапе интеграции — точный реквизит, индексы уточняются в коде владеющей команды).
- Агрегация: на лету по каждому запросу, без кэширования внутри БД.
  - Текущая активность: count(сессии где `ended_at IS NULL или ended_at > now() - TTL`).
  - История за период: группировка по временным бакетам (интервал: минута для hour, час для day, день для week).

**Кэш на стороне Arsenal Backend:** 🟢 30 секунд на результат каждого запроса (в памяти или в shared cache типа Redis). TTL = 30s, inval strategy = time-based (простое истечение, без precompute). Это позволяет избежать повторных дорогих агрегаций за одну минуту.

**Индексы / запросы:** 🟡 к валидации — точная схема и индексы под `(ended_at, user_id)` для быстрого фильтра сессий; 🟡 подтверждено аналитиком, что текущее хранилище позволяет queries за O(log N) на стандартных объёмах.

**Нет миграций:** не заводим новые таблицы/колонки.

### 3.3. Авторизация/доступ на бэке
- **Enforcement:** в обоих эндпоинтах INT-0 (текущая и история) перед возвратом данных проверяется роль из токена (token claim `role`).
- **Правило:** только `role="Administrator"` видит данные активности; иные → 403.
- **Место:** в middleware/controller уровне Arsenal Backend (перед логикой агрегации).
- **Негативный случай:** если клиент — не Администратор, детский фронт получит 403; обработать как в §2 (покажет скрытую панель или сообщение об ошибке, в зависимости от требования детского БТ).

## 4. Frontend — ответственность
Не применимо: фундамент #0 — BE-only. Потребляющие фронты (ARS-101, ARS-102, ARS-103) описывают свой UI и состояния в своих спеках, наследуя контракт INT-0 неизменным.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- **Синхронность:** синхронные запросы (🟡 подтверждено аналитиком).
- **Кэш:** 30 секунд на стороне Arsenal Backend (время-жизнь результата на уровне HTTP-ответа или приложения).
- **Таймаут:** 5 секунд на запрос к источнику данных. Если превышен → 408, обработать как недоступность (is_available=false).
- **Частота:** детские фронты определяют интервалы polling'а для текущей активности и обновления графика (не определяем здесь).
- **Нагрузка:** ожидаемое число административных пользователей — 🟡 к валидации (уточнить при интеграции для оценки load-testing).

### 5.2. Надёжность/деградация
- **При недоступности источника (таймаут, 5xx, сеть):** возвращаем `is_available=false` с `null` данными. НЕ возвращаем устаревшее кэшированное значение (🟡 подтверждено аналитиком: «признак недоступности, а не устаревшее значение»).
- **Различение состояний:** фронт получает точные сигналы:
  - `is_available=true`, `has_data=true` → есть актуальные данные.
  - `is_available=true`, `has_data=false` → данных за период нет, но источник исправен (не ошибка).
  - `is_available=false` → источник недоступен (ошибка, покажи «—»).

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может вызвать | Где проверяется | Негативный случай |
|---------|------------------|-----------------|-------------------|
| GET /api/arsenal/activity/current | Администратор | Arsenal Backend middleware | 403 Forbidden для других ролей |
| GET /api/arsenal/activity/history | Администратор | Arsenal Backend middleware | 403 Forbidden для других ролей |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟢 Фундамент #0 выкатывается **первым, до детских фронтов** (ARS-101, ARS-102, ARS-103). Дети потребляют контракт INT-0, поэтому бэк с новыми эндпоинтами должен быть доступен перед запуском фронтов.

### 6.2. Обратная совместимость
- Новое добавление эндпоинтов в Arsenal Backend (не изменение существующих) → нет нарушения совместимости для текущих потребителей.
- Если будущие версии контракта INT-0 понадобятся → versioning через path (`/api/v2/arsenal/activity/…`) или query-параметр; текущий рельз — v1, implicit.

### 6.3. Фиче-флаги
Не применимо: 🟡 подтверждено аналитиком «фиче-флагов нет», выкатываем атомарно. Фундамент либо весь включен на env, либо полностью выключен (на уровне роутинга, если нужно).

### 6.4. План отката (обязательно)
**Откат только BE (Arsenal Backend):** дети пока на старых версиях, пытаются вызвать новые эндпоинты.
- Старые фронты (до интеграции INT-0) → 404 на новые эндпоинты → детский фронт покажет ошибку / скроет панель активности. **Допустимо**, потому что дети не зависят от фундамента до момента интеграции.

**Откат только FE (детских фронтов):** BE отдаёт новые эндпоинты.
- Старые фронты не вызывают → эндпоинты работают впустую, но не вредят. **Допустимо**, синхронный откат BE не требуется.

**Откат данных:** нет миграций, нет новых таблиц → откат на уровне кода, не DDL.
