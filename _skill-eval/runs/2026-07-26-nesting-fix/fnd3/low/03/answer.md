## Что спроектировано (основное содержание)

**INT-0 — контракт данных активности:**
- Граница: Арсенал (backend) → потребители (фронты детей)
- Запрос: GET параметры (start_time, end_time, granularity)
- Ответ: объект с текущим числом активных (`current_active`), флагом недоступности (`is_unavailable`), статусом данных за период (`available_data`), временным рядом агрегатов (`aggregate`)
- Три примера JSON: успешный ответ с данными, успешный ответ без данных за период, ответ при недоступности
- Семантика: `is_unavailable: true` означает, что источник недоступен (показать ошибку, не старые данные); `available_data: none` означает, что за период никого не было или данных нет (показать пустой график)
- Авторизация: только Администратор, проверка на бэке
- Ошибки: 400 (nevalid params), 403 (forbidden для не-администраторов), 5xx (internal error / timeout)

**Выдержки из конструкции:**
- Нет выдумок о существующих сервисах; всё подтверждено аналитиком
- Новых таблиц нет (агрегаты на лету)
- Синхронно, кэш 30 сек, таймаут 5 сек
- Фундамент выкатывается первым, потом дети наследуют INT-0

## Размещение и следующие шаги

**Файл:** `docs/ARS-100/_foundation/technical_specification.md`
**Статус:** Готово к разработке
**Открытые вопросы:** Нет

Дети (узлы FR-1..FR-5) получают готовый контракт INT-0 и наследуют его в своих собственных спеках без переопределения (с пометкой `🟡 depends-on #0`).

Бэковой команде Арсенала: реализовать эндпоинт INT-0 с указанной семантикой (три примера ответа, две семантики пустоты, авторизация).
Фронтовым командам детей: использовать INT-0 для своих UI-сценариев (счётчик, график, выгрузка); различать ошибки по is_unavailable и available_data.
