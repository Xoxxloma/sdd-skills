## 1. Обзор изменения
### 1.1. Тип и стороны
🟡 BE-only подтверждено аналитиком. Узел-фундамент #0 предоставляет контракт данных активности пользователей (текущее число активных и агрегированные метрики за период) для потребления дочерними компонентами (фронты детей FR-1..FR-5). Нет прямого взаимодействия с фронтом; контракт — полностью бэковый шов между сервисом «Арсенал» и его потребителями.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (backend) | Собирает и отдаёт данные активности; реализует контракт INT-0 | Команда Арсенал-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 реализует общий слой данных, который лежит в основе FR-1..FR-5 эпика ARS-100: текущее число активных пользователей и агрегированная активность за выбранный период (час, день, неделя). Все три UI-компонента (счётчик, график, выгрузка) опираются на этот один источник данных.

## 2. Взаимодействия (ядро)
### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Арсенал (backend) → потребители данных (фронты детей, бэковые компоненты)
- **Триггер:** 
  - Запрос текущего числа активных пользователей (инициируется фронтом шапки при загрузке и в зависимости от polling)
  - Запрос агрегированной активности за период (инициируется фронтом модального окна при открытии или переключении периода)
- **Контракт (запрос):**
  - Метод: `GET` (концептуально; точный путь уточняется на этапе реализации)
  - Параметры:
    - `start_time` (ISO 8601 timestamp, обязательный) — начало периода
    - `end_time` (ISO 8601 timestamp, обязательный) — конец периода
    - `granularity` (enum: `minute` | `hour` | `day`, обязательный) — уровень детализации для агрегатов
  - Заголовки: стандартные (авторизация через существующий механизм Арсенала)

- **Контракт (ответ):**
  - `current_active` (integer ≥ 0 | null) — текущее число активных пользователей; `null`, если источник недоступен
  - `is_unavailable` (boolean, требуется) — признак недоступности источника; `true` → данные считаны не могут быть, `false` → данные свежие
  - `available_data` (enum: `full` | `partial` | `none`, требуется):
    - `full` — есть полный набор данных за период
    - `partial` — данные за период частичны (например, часть сессий потеряна)
    - `none` — данных за период нет (например, никто не был активен, или период в будущем)
  - `aggregate` (array of objects, требуется) — временной ряд активности с указанной детализацией (массив может быть пустым, если `available_data: none`)
    - `timestamp` (ISO 8601) — начало временного окна (для minute — текущая минута, для hour — текущий час и т.д.)
    - `count` (integer ≥ 0) — число активных пользователей в этом окне
  - `period` (object, требуется) — метаданные о запрошенном периоде:
    - `start_time` (ISO 8601) — точное начало, какое вернули
    - `end_time` (ISO 8601) — точный конец
    - `granularity_actual` (enum: `minute` | `hour` | `day`) — фактическая детализация (может отличаться от запроса, если применены ограничения)

- **Пример запроса:**
  ```
  GET /activity?start_time=2026-07-26T00:00:00Z&end_time=2026-07-26T23:59:59Z&granularity=hour
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех — полные данные за день):**
  ```json
  {
    "current_active": 42,
    "is_unavailable": false,
    "available_data": "full",
    "aggregate": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 12 },
      { "timestamp": "2026-07-26T01:00:00Z", "count": 18 },
      { "timestamp": "2026-07-26T02:00:00Z", "count": 15 },
      { "timestamp": "2026-07-26T03:00:00Z", "count": 22 },
      { "timestamp": "2026-07-26T04:00:00Z", "count": 8 }
    ],
    "period": {
      "start_time": "2026-07-26T00:00:00Z",
      "end_time": "2026-07-26T23:59:59Z",
      "granularity_actual": "hour"
    }
  }
  ```

- **Пример ответа (успех — данных за период нет):**
  ```json
  {
    "current_active": 0,
    "is_unavailable": false,
    "available_data": "none",
    "aggregate": [],
    "period": {
      "start_time": "2026-07-26T00:00:00Z",
      "end_time": "2026-07-26T23:59:59Z",
      "granularity_actual": "hour"
    }
  }
  ```

- **Пример ответа (недоступность источника):**
  ```json
  {
    "current_active": null,
    "is_unavailable": true,
    "available_data": "none",
    "aggregate": [],
    "period": {
      "start_time": "2026-07-26T00:00:00Z",
      "end_time": "2026-07-26T23:59:59Z",
      "granularity_actual": "hour"
    }
  }
  ```

- **Ошибки:**
  - **400 Bad Request:** параметры запроса некорректны (неверный формат даты, granularity вне enum'а, start > end и т.п.)
    - Тело: `{ "error_code": "invalid_request", "message": "description" }`
    - Потребитель: пересчитывает запрос или показывает пользователю ошибку (не ожидается в нормальной работе)
  - **403 Forbidden:** роль пользователя не достаточна для доступа (не Администратор)
    - Тело: `{ "error_code": "forbidden", "message": "insufficient_role" }`
    - Потребитель: скрывает UI элемент, не показывает ошибку (ожидается для операторов)
  - **5xx / timeout:** внутренняя ошибка сервера или таймаут при сборке данных
    - Тело: `{ "error_code": "internal_error" | "timeout", "message": "…" }`
    - Потребитель: показывает сообщение об ошибке пользователю, предлагает retry

- **Авторизация:**
  - 🟡 подтверждено аналитиком: контракт доступен **только роли Администратор**, проверка выполняется на стороне бэка Арсенала (существующий механизм auth).
  - Операторы и прочие роли получат 403 Forbidden.
  - Авторизация enforced в точке входа эндпоинта на бэке Арсенала.

- **Происхождение:** 🟢 новое (узел-фундамент #0, контракт спроектирован для общего пользования детьми)
- **Трассировка:** FR-1, FR-2 (текущий счётчик); FR-3, FR-4 (график за период); FR-5 (данные для выгрузки)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние на потребителе |
|-----|----------------|-------|--------------------------|
| 400 | `{ "error_code": "invalid_request", "message": "…" }` | Параметры запроса некорректны (неверная дата, granularity вне enum'а и т.п.) | Ошибка (попросить пользователя пересчитать или retry) |
| 403 | `{ "error_code": "forbidden", "message": "insufficient_role" }` | Роль не достаточна (не Администратор) | Виджет не отображается (ожидается для операторов) |
| 5xx | `{ "error_code": "internal_error" \| "timeout", "message": "…" }` | Внутренняя ошибка сервера или таймаут при сборке агрегатов | Ошибка (показать «—», предложить retry) |

## 3. Backend — ответственность
### 3.1. По сервисам
**Арсенал (backend):**
- Реализует контракт INT-0 (эндпоинт получения данных активности)
- Собирает данные активности со своих внутренних источников (сессий/логов; точный механизм на стороне реализации)
- 🟡 подтверждено аналитиком: чужих сервисов не привлекаем; все данные собирает Арсенал сам
- Enforces авторизацию (роль Администратор) перед возвратом данных
- Возвращает правильные семантические сигналы: `is_unavailable: true` при недоступности, `available_data: none` когда данных за период нет (не "старые" данные вместо текущих)

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: **новых таблиц не заводим**. Агрегаты активности вычисляются на лету из существующих источников сессий/логов бэка Арсенала.
- Нет новых постоянных сущностей.
- Структура INT-0 (aggregate, period и т.д.) — виртуальная, конструируется при обработке запроса.
- Индексы и оптимизация — на сторону реализации (владелец бэка Арсенала определяет, какие индексы нужны для быстрого вычисления за период).

### 3.3. Авторизация/доступ на бэке
- 🟡 подтверждено аналитиком: контракт INT-0 enforced на бэке Арсенала по роли Администратор.
- Не-администраторы (операторы и прочие) получают 403 Forbidden; экран не отдаёт запрос без авторизации.
- Авторизация проверяется в точке входа эндпоинта (middleware или в контроллере).

## 4. Frontend — ответственность
Не применимо: узел-фундамент #0 — чистый бэковый контракт. Frontend-потребители (дети) наследуют INT-0 и реализуют собственные UI-логики (счётчик, график, выгрузка) на его основе в своих спеках.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- 🟡 подтверждено аналитиком: **синхронно** (не async/event-based).
- **Кэш:** 30 секунд на стороне бэка Арсенала. Детали инвалидации (что триггерит обновление кэша) — на сторону реализации.
- **Таймаут:** 5 секунд на уровне HTTP-запроса.
- Ожидаемая нагрузка: детальная нагрузочная оценка — на стороне реализации (зависит от числа пользователей и частоты polling'а со стороны детей).

### 5.2. Надёжность/деградация
- 🟡 подтверждено аналитиком: при недоступности источника отдаём флаг `is_unavailable: true`, а **не устаревшие данные**.
- Отдельно различаем `available_data: none` (данных за период нет) от `is_unavailable: true` (источник недоступен).
- Детям даются оба сигнала, чтобы они могли различить состояния: "зелёная лампочка, но ноль активных" vs. "красная лампочка, данные неизвестны".

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Проверка | Отказ |
|---------|-----------|----------|-------|
| INT-0 (получение данных активности) | Администратор | Бэк Арсенала (существующий механизм auth) | 403 Forbidden для не-администраторов |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 подтверждено аналитиком: **фундамент (#0) выкатывается раньше потребителей** (детей FR-1..FR-5). Детям нужен рабочий контракт INT-0, чтобы кодировать против него.
- Deploy порядок: 1) Арсенал backend с контрактом INT-0, 2) Фронты детей (счётчик, график, выгрузка).

### 6.2. Обратная совместимость
Узел-фундамент — первый выкат в рамках эпика, обратная совместимость не применима. При будущих расширениях контракта INT-0 (добавление полей, новых enum'ов) — гарантировать forward/backward-совместимость на уровне JSON (новые поля опциональны, старые не меняются).

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **фиче-флагов нет**. Релизим атомарно.

### 6.4. План отката (не применимо: узел-фундамент — чистый бэк)
Не применимо: контракт INT-0 — только бэковый шов, нет фронта в режиме #0. На стороне потребителей (дети) откат описывается в их собственных спеках.

### 6.5. Преднастройка до релиза (чек-лист)
- [ ] Роли в security-сервисе — роль Администратор должна быть доступна в Арсенале; авторизация механизма проверяется при интеграции
- [ ] DDL-миграция в репо Арсенала — не требуется (новых таблиц нет)
- [ ] Конфиги по окружениям (dev/staging/prod) — параметры кэша (TTL, инвалидация), таймауты уточняются при реализации
- [ ] Сервисные аккаунты для межсервисных вызовов — не требуется (шов внутри Арсенала)
- [ ] Фиче-флаги заведены — не требуется
- [ ] Алерты/мониторинг на ключевые ошибки (5xx, таймауты) — рекомендуется: отслеживать 5xx на эндпоинте INT-0 и таймауты при сборке агрегатов

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
