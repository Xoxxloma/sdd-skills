## 1. Обзор изменения

### 1.1. Тип и стороны

🟡 BE-only. Узел-фундамент #0 отвечает за сбор и выдачу контракта данных активности пользователей. Потребители контракта — фронтенды дочерних узлов эпика (FR-1 через FR-5).

### 1.2. Затронутые сервисы и владельцы

| Сервис           | Роль в задаче                              | Владелец/команда           | Происхождение                        |
|------------------|-------------------------------------------|-----------------------------|--------------------------------------|
| Arsenal (Backend) | Собирает и отдаёт контракт данных активности | Команда Arsenal-Core | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями

Фундамент реализует общий слой данных для FR-1 (текущее число активных пользователей) и FR-2–FR-5 (агрегированная активность за период). Обслуживает все пять функциональных требований эпика.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** BE Arsenal → потребители (фронты дочерних узлов)
- **Триггер:** Фронтовой код запрашивает текущую активность и/или активность за период
- **Контракт (запрос):** GET `/api/v1/activity/users` с опциональными параметрами:
  - `period` (query param): `current` | `hourly` | `daily` | `weekly` (default: `current`)
  - `from` (query param, ISO 8601, опционально): начало периода
  - `to` (query param, ISO 8601, опционально): конец периода
- **Контракт (ответ):** 
  - `available` (boolean): `true` если данные доступны, `false` если источник недоступен
  - `current_count` (integer | null): число активных пользователей в текущий момент; `null` если `available === false`
  - `aggregates` (array | null): массив агрегированных значений активности за период (только если `period !== "current"`); `null` если `available === false`
    - Каждый элемент: `{ "timestamp": ISO 8601, "count": integer }`
  - `period_mode` (string): отражает запрошенный режим (`current`, `hourly`, `daily`, `weekly`)
  - `cached_at` (ISO 8601): время кэширования ответа на бэке

- **Пример запроса:** 
  ```
  GET /api/v1/activity/users?period=daily&from=2026-07-20T00:00:00Z&to=2026-07-26T23:59:59Z
  ```

- **Пример ответа (успех — данные доступны):**
  ```json
  {
    "available": true,
    "current_count": 42,
    "aggregates": [
      { "timestamp": "2026-07-20T00:00:00Z", "count": 15 },
      { "timestamp": "2026-07-21T00:00:00Z", "count": 28 },
      { "timestamp": "2026-07-22T00:00:00Z", "count": 31 },
      { "timestamp": "2026-07-23T00:00:00Z", "count": 25 },
      { "timestamp": "2026-07-24T00:00:00Z", "count": 38 },
      { "timestamp": "2026-07-25T00:00:00Z", "count": 42 },
      { "timestamp": "2026-07-26T00:00:00Z", "count": 40 }
    ],
    "period_mode": "daily",
    "cached_at": "2026-07-26T15:30:45Z"
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "available": false,
    "current_count": null,
    "aggregates": null,
    "period_mode": "daily",
    "cached_at": "2026-07-26T15:30:45Z"
  }
  ```

- **Ошибки:**
  - `200 OK` с `available: true` — данные получены и корректны
  - `200 OK` с `available: false` — источник недоступен (вместо 5xx); потребитель показывает состояние `error_source`
  - `403 Forbidden` — вызывающая роль не является Администратором
  - `400 Bad Request` — неверные параметры периода/дат (пример: `to < from`)

- **Состояния UI по ответу (для потребителей):**
  - `available: true` → состояние `value` (FR-1: отобразить число; FR-3–5: отобразить график и выгрузку)
  - `available: false` + `current_count: null` → состояние `error_source` (показать «—»/сообщение об ошибке)
  - `available: true` + `current_count: 0` → состояние `zero` (отобразить «0», не «—»)
  - `403 Forbidden` → состояние `error_forbidden` (скрыть виджет для некорректной роли)

- **Авторизация:** 
  - Контракт доступен только роли **Администратор**
  - 🟡 Проверка реализуется на бэке Arsenal перед отдачей ответа (подтверждено аналитиком)
  - 403 Forbidden для остальных ролей

- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (эпик ARS-100)

### Каталог ошибок

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 (available: true) | Данные получены | Источник доступен, данные готовы | `value` / `zero` |
| 200 (available: false) | Источник недоступен | Сервис активности/источник не доступен; вместо 5xx | `error_source` |
| 403 Forbidden | `{ "error": "Insufficient permissions" }` | Роль не является Администратором | `error_forbidden` (скрыть панель) |
| 400 Bad Request | `{ "error": "Invalid period parameters" }` | `to < from` или неверный формат дат | Валидация на фронте + состояние ошибки |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal (Backend):**
- Реализует endpoint `GET /api/v1/activity/users` (INT-0)
- Собирает текущее число активных пользователей из внутреннего источника (не привлекаются внешние сервисы; 🟡 подтверждено аналитиком)
- Агрегирует активность за период на лету (часово, дневно, недельно) — без запросов к внешним сервисам
- Отдаёт флаг `available` при недоступности источника вместо 5xx-ошибки
- Проверяет роль Администратор перед отдачей ответа; для остальных — 403

### 3.2. Данные и хранение

🟡 Новых таблиц и сущностей не заводятся. Агрегаты считаются на лету из существующих данных активности сессий (подтверждено аналитиком, не по коду).

### 3.3. Авторизация/доступ на бэке

- 🟡 Проверка роли Администратор реализуется в Arsenal-Backend (подтверждено аналитиком)
- Для ролей, не являющихся Администратором → 403 Forbidden, без раскрытия данных

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Не применимо на уровне фундамента: фундамент контракта наследуется дочерними узлами (FR-1–FR-5), каждый из которых реализует свой UI (счётчик, модалку, выгрузку).

### 4.2. Пользовательские сценарии

Не применимо: сценарии описаны в БТ и реализуются дочерними узлами, использующими INT-0.

### 4.3. Состояния (именованные)

Дочерние узлы отображают состояния на основе ответа INT-0:

| Имя состояния | Условие | Что видит пользователь |
|---|---|---|
| `loading` | Запрос отправлен, ответа нет | спиннер / скелетон |
| `value` | `available: true`, `current_count ≠ null` и `≠ 0` | число активных пользователей / график |
| `zero` | `available: true`, `current_count == 0` (валидный ноль) | «0» (не прочерк) |
| `empty` | `available: true`, `aggregates: null` или `aggregates: []` | «нет данных» / пустой график |
| `error_source` | `available: false` (источник недоступен, таймаут 5s) | сообщение об ошибке «Источник данных недоступен» + кнопка retry |
| `error_forbidden` | 403 Forbidden (некорректная роль) | Панель скрыта / доступ запрещён |

### 4.3.1. Loading и таймауты

- **Холодный старт (cold-path, первый запрос):** таймаут 5 секунд (если за 5с ответа нет, показать `error_source`)
- **Последующие запросы / обновления (warm-path):** таймаут 5 секунд (то же поведение)
- **Polling:** Если фронт опрашивает INT-0 периодически (для обновления счётчика в FR-2), интервал и jitter согласовываются дочерними узлами в их спеках; фундамент задаёт таймаут и флаг кэширования.

### 4.4. Доступ по ролям в UI

Дочерние узлы проверяют роль (Администратор) и скрывают соответствующие UI-элементы для остальных. Фундамент INT-0 отдаёт 403 для неподходящих ролей.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- 🟡 **Синхронность:** синхронный ответ (не async-очередь) (подтверждено аналитиком)
- 🟡 **Кэш:** 30 секунд на бэке Arsenal; если за 30s была запрос, повторный запрос вернёт закэшированный ответ (подтверждено аналитиком)
- 🟡 **Таймаут:** 5 секунд на получение данных из источника; если источник не ответит за 5s, вернуть `available: false` (не 5xx) (подтверждено аналитиком)
- Агрегаты рассчитываются на лету, индексы под типовые временные фильтры предполагаются на уровне данных активности (не в рамках этого фундамента)

### 5.2. Надёжность/деградация

- При недоступности источника (сеть, таймаут, 5xx от источника) → вернуть `{ "available": false, "current_count": null, "aggregates": null }` с кодом 200 (не 5xx)
- Различаем: «данные недоступны» (`available: false`) vs «данных за период нет» (`aggregates: []`) — оба случая обработаны, UI видит разницу через фронт-состояния
- Не отдаём устаревшие данные вместо недоступности; если источник упал, флаг `available: false`

### 5.3. Безопасность/доступ (сводно)

| Сторона | Условие | Действие |
|---------|---------|---------|
| Роль Администратор | На any запрос к INT-0 | 200 OK + данные (или 200 OK с `available: false`) |
| Роль Оператор / прочие | На any запрос к INT-0 | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 Фундамент #0 выкатывается ПЕРВЫМ, раньше дочерних узлов (FR-1–FR-5), использующих INT-0. Дочерние фронты ждут выката фундамента, чтобы начать интеграцию (подтверждено аналитиком).

### 6.2. Обратная совместимость

Фундамент — новое добавление, обратная совместимость не требуется (arsenalBackend получит новый endpoint).

### 6.3. Фиче-флаги

🟡 Фиче-флагов нет; релизим INT-0 атомарно в рамках выката фундамента (подтверждено аналитиком).

### 6.4. План отката

- **Откат только BE (фундамент #0):** Дочерние фронты получат 404/5xx на INT-0. Дочерние узлы должны обработать это состояние и показать `error_source` пользователю. Требуется синхронный откат дочерних фронтов.
- **Откат только FE (дочерние узлы):** Если BE фундамента жив, но дочерние фронты откачены, счётчик и модалка просто не отобразятся (UI скрыт). BE продолжает отдавать INT-0 для других потребителей (если будут).
- **DDL:** Не применимо (новых таблиц нет).

### 6.5. Преднастройка до релиза

- [x] Роли в security-сервисе: роль Администратор существует (✅, существующая; не требует настройки)
- [x] DDL-миграция: не требуется (новых таблиц нет)
- [x] Конфиги по окружениям (dev/staging/prod): таймаут 5s и кэш 30s прописаны в коде; при необходимости параметризуются через конфиги (на уровне Arsenal)
- [x] Сервисные аккаунты: не требуются (внутренний endpoint Arsenal, нет межсервисных вызовов)
- [x] Фиче-флаги: не требуются (релизим атомарно)
- [x] Алерты/мониторинг: монитор на `available: false` частоту (сколько % запросов вернули недоступность); алерт при превышении пороговой частоты

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|---|---|---|
| FR-1 | INT-0 | Дано роль Администратор с открытой админкой, когда BE отвечает на `/api/v1/activity/users?period=current`, тогда `current_count ≠ null` и фронт может отобразить число |
| FR-2 | INT-0 | Дано счётчик в шапке, когда BE закэшировал ответ на 30s, и фронт снова запросит INT-0, тогда получит тот же ответ (без пересчёта на BE); затем, когда истекут 30s кэша и `current_count` изменится, тогда фронт получит новое значение |
| FR-3 | INT-0 | Дано роль Администратор, когда фронт запросит `/api/v1/activity/users?period=daily`, тогда `aggregates` содержит дневные точки данные для построения графика |
| FR-4 | INT-0 | Дано открытую модалку, когда администратор переключит период (hour/day/week), тогда фронт отправит новый запрос INT-0 с параметром `period`, и BE вернёт агрегаты нужной гранулярности |
| FR-5 | INT-0 | Дано открытую модалку с выбранным периодом, когда администратор запросит выгрузку, тогда фронт использует данные из последнего ответа INT-0 для формирования файла сводки |
