## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Дочерние фронты (детские фронты ARS-101, ARS-102, ARS-103) → Бэк Арсенала

- **Триггер:** 
  - Инициализация компонента, отображающего активность (для FR-1, FR-3)
  - Периодический опрос для обновления счётчика (FR-2)
  - Выбор периода в модальном окне (FR-4)
  - Клик по кнопке выгрузки (FR-5)

- **Контракт (запрос):**
  ```
  GET /api/v1/activity
  Query parameters:
    - period: "hour" | "day" | "week" (по умолчанию "day")
  
  Заголовки:
    - Authorization: Bearer <token> (роль должна быть "Администратор")
  ```

- **Контракт (ответ):**
  - **Поля ответа:**
    - `current` (object, обязательно): текущее состояние активности
      - `activeUsers` (int | null): число активных пользователей на текущий момент; null если данные недоступны
      - `timestamp` (string, ISO8601): момент времени, на который измерены текущие активные (UTC)
    - `availability` (enum): статус доступности данных
      - `"available"` — данные свежие и полные
      - `"unavailable"` — источник активности недоступен; показать ошибку, не выдавать статок значение
      - `"no_data_for_period"` — период валиден, но данных в нём нет (в истории не будут точки)
    - `history` (object, обязательно): исторические данные
      - `period` (string): запрошенный период ("hour" | "day" | "week")
      - `startTime` (string, ISO8601): начало периода (UTC)
      - `endTime` (string, ISO8601): конец периода (UTC)
      - `dataPoints` (array of objects): временной ряд активности
        - `timestamp` (string, ISO8601): момент агрегации (UTC; гранулярность: минуты для hour, часы для day, дни для week)
        - `activeUsers` (int | null): число активных пользователей в этот момент; null если данных нет за этот временной слот
    - `meta` (object, опционально): метаданные
      - `cacheAge` (int, опционально): возраст данных в кэше (секунды); помогает фронту решить, нужен ли перезапрос

- **Пример запроса:**
  ```
  GET /api/v1/activity?period=day
  Authorization: Bearer eyJhbGc...
  ```

- **Пример ответа (успех, availability: available):**
  ```json
  {
    "current": {
      "activeUsers": 142,
      "timestamp": "2026-07-26T14:30:00Z"
    },
    "availability": "available",
    "history": {
      "period": "day",
      "startTime": "2026-07-25T00:00:00Z",
      "endTime": "2026-07-26T00:00:00Z",
      "dataPoints": [
        {
          "timestamp": "2026-07-25T00:00:00Z",
          "activeUsers": 85
        },
        {
          "timestamp": "2026-07-25T01:00:00Z",
          "activeUsers": 62
        },
        {
          "timestamp": "2026-07-25T02:00:00Z",
          "activeUsers": 51
        },
        {
          "timestamp": "2026-07-25T12:00:00Z",
          "activeUsers": 128
        },
        {
          "timestamp": "2026-07-25T23:00:00Z",
          "activeUsers": 103
        }
      ]
    },
    "meta": {
      "cacheAge": 2
    }
  }
  ```

- **Пример ответа (unavailable):**
  ```json
  {
    "current": {
      "activeUsers": null,
      "timestamp": "2026-07-26T14:30:00Z"
    },
    "availability": "unavailable",
  ```

- **Пример ответа (no_data_for_period):**
  ```json
  {

      "activeUsers": 142,
      "timestamp": "2026-07-26T14:30:00Z"
    },
    "availability": "no_data_for_period",
    "history": {
      "period": "day",
      "startTime": "2026-07-26T00:00:00Z",

    }
  }
  ```

- **Ошибки:**
  - `401 Unauthorized`: токен отсутствует или истёк
  - `403 Forbidden`: роль пользователя не «Администратор» (см. раздел Авторизация)
  - `400 Bad Request`: период некорректен (не один из "hour", "day", "week")
  - `500 Internal Server Error` или `503 Service Unavailable`: критическая ошибка источника активности (отражается в `availability: "unavailable"`, а не в HTTP-коде, если контракт может быть обработан)

- **Состояния UI по ответу (если есть фронт):**
  - `value` (availability = "available", activeUsers ≠ null) → показать число активных пользователей; для истории показать точки графика
  - `zero` (availability = "available", activeUsers = 0) → показать «0» (не прочерк)
  - `empty` (availability = "available", activeUsers = null) → показать «—»
  - `no_data_for_period` (availability = "no_data_for_period") → показать сообщение «Нет данных за выбранный период»
  - `error_source` (availability = "unavailable") → показать сообщение об ошибке «Источник данных недоступен» + кнопка retry

- **Авторизация:**
  - Контракт доступен только пользователям с ролью «Администратор» 🟡 подтверждено аналитиком (не по коду).
  - Проверка выполняется на бэке Арсенала в middleware или в обработчике эндпоинта.
  - Негативный случай: пользователь с ролью «Оператор» или ниже получит 403 Forbidden и не будет видеть счётчик/график/выгрузку.

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (счётчик), FR-2 (обновление), FR-3 (модалка с графиком), FR-4 (переключение периода), FR-5 (выгрузка)

## 3. Backend — ответственность

### 3.1. По сервисам

🟡 **подтверждено аналитиком (не по коду):** Бэк Арсенала отвечает за реализацию эндпоинта `GET /api/v1/activity` и логику получения данных активности. Данные активности собирает сам Арсенал; чужих сервисов в качестве источников нет.

Реализовать:
- Обработчик эндпоинта (маршрут, парсинг параметров)
- Логика получения текущего числа активных пользователей
- Логика получения исторических данных (агрегаты за запрошенный период)
- Авторизация по роли «Администратор» в middleware или обработчике
- Кэширование на 30 секунд и таймаут в 5 секунд (см. раздел Нефункциональные требования)
- Обработка недоступности источника (возврат `availability: "unavailable"`, не статок значение)

### 3.2. Данные и хранение

🟡 **подтверждено аналитиком (не по коду):** Новых таблиц не заводим. Агрегаты активности считаются на лету из существующих данных мониторинга сессий Арсенала.

**Точки данных:**
- Текущее число активных пользователей — считается в реальном времени из живых сессий.
- Исторические агрегаты (по часам для "day", по дням для "week", с минутной гранулярностью для "hour") — вычисляются из логов активности; источник и логика — на разработчиках бэка Арсенала (не описываем DDL, т.к. это существующая инфраструктура).

**Индексы и оптимизация:** 🟡 к валидации — какие индексы нужны для быстрого вычисления агрегатов за период (подтвердить при интеграции).

**Кэширование на бэке:** 30 секунд, см. §5.1.

### 3.3. Авторизация/доступ на бэке

🟡 **подтверждено аналитиком (не по коду):** Эндпоинт `GET /api/v1/activity` проверяет роль в токене (Bearer JWT или аналог). Только роль «Администратор» имеет доступ. Роль «Оператор» и прочие получают 403 Forbidden.

Проверка: в middleware или в обработчике перед логикой получения данных.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Три элемента эпика ARS-100 потребляют контракт INT-0:
1. **Счётчик в шапке** (FR-1, FR-2): отображает `current.activeUsers` из ответа; обновляется периодически без перезагрузки страницы.
2. **Модальное окно с графиком** (FR-3, FR-4): отображает `history.dataPoints` в виде линейного графика; переключение `period` перезапрашивает контракт с новым параметром.
3. **Выгрузка сводки** (FR-5): собирает `history.dataPoints` и текущее `current.activeUsers`, формирует файл (CSV/JSON) для скачивания.

### 4.2. Пользовательские сценарии

**Основной поток:**
1. Администратор открывает админку → загружается счётчик активных пользователей в шапке (FR-1).
2. Счётчик автоматически обновляется каждые N секунд (в пределах минуты, FR-2).
3. Администратор кликает на счётчик → открывается модалка с графиком за день (FR-3).
4. Администратор выбирает период (час, неделя) → график перестраивается (FR-4).
5. Администратор нажимает «Выгрузить» → скачивается файл со сводкой (FR-5).

**Обработка ошибок:**
- Если `availability: "unavailable"` → показать сообщение об ошибке в счётчике/графике и предложить retry.
- Если `availability: "no_data_for_period"` → показать «Нет данных за выбранный период» вместо пустого графика.
- Если `activeUsers: null` и `availability: "available"` → показать прочерк «—» (корректно отсутствие данных от отсутствия мониторинга).

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос или перезагрузка | спиннер/скелетон |
| `value` | 2xx, availability = "available", activeUsers ≠ null | число активных (напр. 142) |
| `zero` | 2xx, availability = "available", activeUsers = 0 | «0» (не прочерк) |
| `empty` | 2xx, availability = "available", activeUsers = null | «—» (прочерк, нет данных) |
| `no_data_for_period` | 2xx, availability = "no_data_for_period" | сообщение «Нет данных за выбранный период» |
| `error_source` | 2xx, availability = "unavailable" ИЛИ 5xx/timeout | сообщение об ошибке + retry |
| `error_forbidden` | 403 | сообщение «Недостаточно прав» (компонент скрыт) |

### 4.3.1. Loading и таймауты

- **Cold-path (первый запрос):** таймаут 5 секунд 🟡 подтверждено аналитиком (не по коду). Если за 5с ответ не пришёл, показать `error_source` и предложить retry.
- **Warm-path (последующие запросы):** также 5 секунд (одно значение для обоих).
- **Polling:** счётчик обновляется без перезагрузки в пределах минуты (FR-2); интервал опроса 🟡 к валидации (уточнить: каждые 20с, 30с, 60с?). jitter не требуется для этого простого случая.
- **При таймауте:** показать `error_source` с сообщением и кнопкой retry.

### 4.4. Доступ по ролям в UI

Счётчик, модалка и выгрузка видны только администраторам. Если пользователь с ролью «Оператор» попробует открыть эти элементы, бэк вернёт 403, и фронт покажет сообщение «Недостаточно прав» или скроет компоненты.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

🟡 **подтверждено аналитиком (не по коду):**
- **Синхронность:** эндпоинт отвечает синхронно (не event-based, не async-job).
- **Кэш:** 30 секунд на стороне бэка Арсенала (in-memory, Redis или иной). Агрегаты считаются один раз за 30с, потребители получают кэшированный результат.
- **Таймаут:** 5 секунд на вычисление и возврат ответа. Если за 5s ответ не готов, вернуть 503 или тело с `availability: "unavailable"`.
- **Частота опроса (фронт):** счётчик обновляется в пределах минуты (FR-2); точный интервал 🟡 к валидации (уточнить: 20s, 30s, 60s?).
- **Ожидаемая нагрузка:** 🟡 к валидации (уточнить: сколько администраторов одновременно, какая частота запросов?).

### 5.2. Надёжность/деградация

🟡 **подтверждено аналитиком (не по коду):** При недоступности источника активности (упал мониторинг, БД, сеть):
- НЕ выдавать устаревшее (кэшированное на предыдущем цикле) значение как свежее.
- Возвращать `availability: "unavailable"` явно.
- Фронт показывает сообщение об ошибке и предлагает retry.

При отсутствии данных за конкретный период (напр., запрошен период будущего или исторический период без активности):
- Возвращать `availability: "no_data_for_period"`.
- `dataPoints` пуста, фронт показывает «Нет данных за выбранный период» (не ошибку).

### 5.3. Безопасность/доступ (сводно)

| Граница | Проверка | Результат (да) | Результат (нет) |
|---------|----------|----------------|-----------------|
| GET /api/v1/activity | Токен + роль = «Администратор» | 2xx, данные | 403 Forbidden |
| GET /api/v1/activity | Токен отсутствует | — | 401 Unauthorized |
| — | Параметр period корректен | 2xx | 400 Bad Request |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 **подтверждено аналитиком (не по коду):** Узел-фундамент #0 выкатывается ПЕРВЫМ, раньше дочерних задач (ARS-101, ARS-102, ARS-103). Причина: фронты детей опираются на контракт INT-0; бэк должен быть готов до развёртывания фронтов.

**Порядок:**
1. Выкат бэка с эндпоинтом `/api/v1/activity` (реализация INT-0).
2. Выкат фронтов детей (ARS-101, ARS-102, ARS-103), потребляющих INT-0.

### 6.2. Обратная совместимость

🟢 Новый эндпоинт. Нет обратной совместимости с предыдущими версиями (их не было). Текущие потребители Арсенала не коснулись.

### 6.3. Фиче-флаги

🟡 **подтверждено аналитиком (не по коду):** Фиче-флагов нет. Релизим атомарно: как только бэк выкатан и эндпоинт доступен, фронты детей активируют компоненты счётчика/графика/выгрузки.

### 6.4. План отката

🟢 **Откат только бэка:** Если откатить бэк после выката фронтов, фронты получат 404 или 5xx на вызовах `/api/v1/activity`. Нужен синхронный откат фронтов, иначе они покажут ошибку и не восстановятся.

🟢 **Откат только фронтов:** Бэк продолжает отдавать данные; фронты их не потребляют. Безопасно.

🟢 **Откат DDL:** Новых таблиц нет, откат не требуется.

- [x] Фиче-флаги — не требуются (релизим атомарно).
- [ ] Алерты/мониторинг — установить мониторинг на 503, таймауты, частоту `availability: "unavailable"` (рекомендация, уточнить).

| FR-1 | INT-0 | Дано открыта админка, когда страница загрузилась, тогда в шапке видно число активных пользователей (значение из `current.activeUsers`) |
| FR-2 | INT-0 (polling) | Дано открыта админка, когда число активных пользователей изменилось, тогда счётчик обновляется без перезагрузки в пределах минуты (отражает обновлённое `current.activeUsers`) |
| FR-3 | INT-0 | Дано счётчик в шапке, когда администратор кликает по нему, тогда открывается модальное окно с графиком активности за период по умолчанию (day; `history.dataPoints` визуализируется как линейный график) |
| FR-4 | INT-0 | Дано открытую модалку, когда администратор выбирает другой период (hour/week), тогда график перестраивается под выбранный период (INT-0 запрашивается с новым `period`, результат визуализируется заново) |
| FR-5 | INT-0 | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда он получает файл со сводкой активности за этот период (`history.dataPoints` + `current.activeUsers` экспортируются в CSV/JSON) |

## 8. Допущения и открытые вопросы

- **🟡 Подтверждено аналитиком (не по коду):**
  - Бэк Арсенала отвечает за сбор данных активности (не привлекаем чужие сервисы).
  - Эндпоинт отвечает синхронно, кэш 30s, таймаут 5s.
  - Проверка авторизации на бэке (роль «Администратор»).
  - При недоступности источника возвращаем `availability: "unavailable"`, не устаревшее значение.

- **🟡 К валидации:**
  - Точный интервал опроса фронтом для обновления счётчика (каждые 20s, 30s, 60s за минуту?).
  - Ожидаемая нагрузка (число администраторов, RPS).
  - Какие индексы в БД нужны для вычисления агрегатов за период.
  - Стратегия кэширования (in-memory, Redis, иное).

- **⚠️ Требует уточнения:**
  - Параметр `cacheAge` в мета-поле: стоит ли включать, помогает ли фронту? (опционально в контракте, но уточнить целесообразность).

- **Унаследовано из БТ (бизнес-пробелы):**
  - Нет открытых бизнес-вопросов; БТ готова к разработке.

- **Приложения из БТ:**
  - UX-пожелание: счётчик неяркий, не отвлекает (уточнить с дизайном фронта).
