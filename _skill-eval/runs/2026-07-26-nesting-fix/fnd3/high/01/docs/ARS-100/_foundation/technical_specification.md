## 2. Взаимодействия (ядро)

### INT-0. Получение данных об активности пользователей — 🟢 (фундамент, наследуется дочерними узлами)

- **Граница/направление:** Детские фронты (ARS-101, ARS-102, ARS-103 UI) → Arsenal Backend (#0)

- **Триггер:** 
  1. При загрузке страницы счётчика в шапке (FR-1) — запрос текущего числа активных.
  2. При автообновлении счётчика в шапке (FR-2) — периодический запрос текущего числа.
  3. При открытии модалки графика (FR-3) — запрос исторических данных за выбранный период.
  4. При переключении периода в графике (FR-4) — запрос исторических данных за новый период.
  5. При выгрузке сводки (FR-5) — запрос исторических данных за выбранный период для экспорта.

- **Контракт (запрос):**
  - **Метод/путь (концептуально):** `GET /api/activity/data`
  - **Параметры запроса:**
    - `period_type` (string, обязательно): `"current"` | `"hourly"` | `"daily"` | `"weekly"` — тип данных для возврата.
    - `period_start` (string, ISO 8601, опционально): начало периода для исторических запросов (e.g. `"2026-07-22T00:00:00Z"`). Не используется для `period_type: "current"`.
    - `period_end` (string, ISO 8601, опционально): конец периода для исторических запросов. Не используется для `period_type: "current"`.
  - **Заголовки:** Стандартные (Authorization, Content-Type); авторизация — Bearer token с ролью Администратор.

- **Контракт (ответ):**
  - `status` (string): `"available"` | `"unavailable"` — доступность источника данных активности.
  - `unavailable_reason` (string | null): причина недоступности (если `status: "unavailable"`). Значения: `"source_timeout"`, `"source_error"`, `null` (если доступен).
  - `no_data_for_period` (boolean): `true` если за запрошенный период данных нет (но источник доступен). `false` если данные есть или запрос — текущее число.
  - **Для `period_type: "current"` (если `status: "available"`):**
    - `current` (object):
      - `active_count` (integer, ≥ 0): число активных пользователей в текущий момент.
      - `timestamp` (string, ISO 8601): момент снятия показания.
  - **Для `period_type: "hourly" | "daily" | "weekly"` (если `status: "available"` и `no_data_for_period: false`):**
    - `historical` (array of objects):
      - `period_start` (string, ISO 8601): начало периода агрегации.
      - `period_end` (string, ISO 8601): конец периода агрегации.
      - `average_active` (integer, ≥ 0): среднее число активных пользователей за период.
      - `peak_active` (integer, ≥ 0): пик (максимум) активных пользователей за период.
      - `data_points` (array of objects, опционально, зависит от периода):
        - `timestamp` (string, ISO 8601): момент времени.
        - `active_count` (integer, ≥ 0): число активных в этот момент.
  - **Семантика `null`:** Не используется в полях ответа. Отсутствие исторических данных кодируется `no_data_for_period: true`.

- **Пример запроса 1 (текущее число):**
  ```
  GET /api/activity/data?period_type=current
  Header: Authorization: Bearer <admin_token>
  ```

- **Пример запроса 2 (исторические данные, дневная граница):**
  ```
  GET /api/activity/data?period_type=daily&period_start=2026-07-22T00:00:00Z&period_end=2026-07-26T00:00:00Z
  Header: Authorization: Bearer <admin_token>
  ```

- **Пример ответа 1 (успех, текущее число доступно):**
  ```json
  {
    "status": "available",
    "unavailable_reason": null,
    "no_data_for_period": false,
    "current": {
      "active_count": 42,
      "timestamp": "2026-07-26T12:34:56Z"
    }
  }
  ```

- **Пример ответа 2 (успех, исторические данные есть):**
  ```json
  {
    "status": "available",
    "unavailable_reason": null,
    "no_data_for_period": false,
    "historical": [
      {
        "period_start": "2026-07-22T00:00:00Z",
        "period_end": "2026-07-23T00:00:00Z",
        "average_active": 38,
        "peak_active": 51,
        "data_points": [
          { "timestamp": "2026-07-22T06:00:00Z", "active_count": 25 },
          { "timestamp": "2026-07-22T12:00:00Z", "active_count": 42 },
          { "timestamp": "2026-07-22T18:00:00Z", "active_count": 48 }
        ]
      },
      {
        "period_start": "2026-07-23T00:00:00Z",
        "period_end": "2026-07-24T00:00:00Z",
        "average_active": 41,
        "peak_active": 54,
        "data_points": [
          { "timestamp": "2026-07-23T06:00:00Z", "active_count": 28 },
          { "timestamp": "2026-07-23T12:00:00Z", "active_count": 45 },
          { "timestamp": "2026-07-23T18:00:00Z", "active_count": 51 }
        ]
      }
    ]
  }
  ```

- **Пример ответа 3 (источник недоступен, таймаут):**
  ```json
  {
    "status": "unavailable",
    "unavailable_reason": "source_timeout",
    "no_data_for_period": false
  }
  ```

- **Пример ответа 4 (источник доступен, но за период нет данных):**
  ```json
  {
    "status": "available",
    "unavailable_reason": null,
    "no_data_for_period": true
  }
  ```

- **Ошибки:** см. раздел «Каталог ошибок» ниже (HTTP-коды).

- **Состояния UI по ответу:** 
  - `status: "available"` + значение `≠ null` → UI отображает значение.
  - `status: "available"` + `no_data_for_period: true` → UI отображает «—» / «нет данных».
  - `status: "unavailable"` → UI отображает сообщение об ошибке + предложение retry.
  - Запрос в полёте → UI показывает спиннер/скелетон.

- **Авторизация:** 
  - Доступ только для пользователей с ролью **Администратор** (🟡 подтверждено аналитиком, проверка на бэке Arsenal).
  - Негативный случай: запрос без токена или токен без роли Администратор → `403 Forbidden` (см. каталог ошибок).

- **Происхождение:** 🟢 новое (узел-фундамент #0, спроектировано из требований эпика FR-1..FR-5).

- **Трассировка:** FR-1, FR-2 (счётчик текущего числа активных); FR-3, FR-4 (график за период); FR-5 (выгрузка сводки).

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 | См. примеры ответов выше | Успешный запрос | Значение / пусто / ошибка (по `status` в теле) |
| 400 | `{ "error": "Invalid period_type" }` | Неверное значение `period_type` | Ошибка валидации (при разработке); в продакшене может не быть (FE валидирует) |
| 401 | `{ "error": "Unauthorized" }` | Отсутствует или недействителен token | Перенаправление на вход / сообщение об ошибке |
| 403 | `{ "error": "Forbidden" }` | Пользователь есть, но не Администратор | «Нет доступа» |
| 408 | `{ "error": "Request timeout" }` (или пустое тело) | Запрос превышил 5-секундный таймаут | Сообщение об ошибке + retry (таймаут обрабатывается как `status: "unavailable", unavailable_reason: "source_timeout"`) |
| 500 | `{ "error": "Internal server error" }` | Ошибка внутри Arsenal Backend | Сообщение об ошибке + retry (обрабатывается как `status: "unavailable", unavailable_reason: "source_error"`) |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend** реализует INT-0:
- 🟢 Новый эндпоинт `GET /api/activity/data` с параметрами `period_type`, `period_start`, `period_end`.
- 🟢 Сбор данных об активности пользователей (текущее число + исторические агрегаты).
- 🟢 Возврат контракта (§2 INT-0) с правильной семантикой `status`, `unavailable_reason`, `no_data_for_period`.
- 🟢 Кэширование результатов на 30 секунд в памяти / локальном кэше Arsenal Backend (🟡 подтверждено аналитиком, что кэш живёт в Arsenal, а не в отдельном сервисе).
- 🟢 Таймаут на запрос 5 секунд (если источник активности медленнее — вернуть `{ "status": "unavailable", "unavailable_reason": "source_timeout" }`).
- 🟡 Источник данных активности — сам Arsenal Backend; чужих сервисов не привлекаем (подтверждено аналитиком).

### 3.2. Данные и хранение

🟢 **Нет новых таблиц.** Агрегаты активности (текущее число, исторические значения) **вычисляются на лету** из существующих данных сессий / логов в Arsenal Backend (🟡 подтверждено аналитиком). Новых сущностей не заводим.

- **Что вычисляется:**
  - Текущее число активных пользователей — count сессий/логов со статусом "active" в текущий момент.
  - Исторические агрегаты за период — по интервалам (час / день / неделя) считаем среднее и пик активных пользователей.
  - Квантование данных (количество `data_points` в ответе) — на усмотрение реализации, но достаточно для отрисовки графика (ориентир: 20–50 точек для недельного периода).

### 3.3. Авторизация/доступ на бэке

🟢 Проверка роли **Администратор** перед возвратом данных INT-0:
- 🟡 Роль проверяется на бэке Arsenal (подтверждено аналитиком, не полагаемся на фронт).
- Запрос без роли Администратор → 403 Forbidden.

## 4. Frontend — ответственность

**Не применимо:** узел-фундамент #0 — BE-only, UI не входит. Дочерние узлы (ARS-101, ARS-102, ARS-103) будут потреблять контракт INT-0 и реализовывать UI на его основе.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- 🟢 **Синхронность:** Запрос INT-0 выполняется **синхронно** (нет очереди, нет полинга; ответ даётся в одном ответе).
- 🟢 **Кэш:** 30 секунд, живёт на стороне **Arsenal Backend** (🟡 подтверждено аналитиком). Логика инвалидации кэша (если данные обновились досрочно) — на реализацию Arsenal; инвалидация по временно́й TTL = 30 сек.
- 🟢 **Таймаут:** 5 секунд. Если источник активности (сессии / логи Arsenal) медленнее — вернуть 408 или `{ "status": "unavailable", "unavailable_reason": "source_timeout" }` (выбрать в реализации).
- 🟢 **Ожидаемая нагрузка:** текущее число активных запрашивается часто (каждые несколько секунд от каждого админа); исторические данные запрашиваются реже. Кэш 30 сек должен поглотить всплески от множества админов.

### 5.2. Надёжность/деградация

🟢 **При недоступности источника активности:**
- Вернуть `{ "status": "unavailable", "unavailable_reason": "source_timeout" | "source_error", ... }`, **НЕ** устаревшие кэшированные данные.
- UI (на стороне дочерних узлов) показывает сообщение об ошибке вместо неправдивых значений.

🟢 **Различаем "данных за период нет" от "источник недоступен":**
- `status: "available"` + `no_data_for_period: true` → у источника есть данные вообще, но за этот период их нет (реальная ситуация, а не сбой).
- `status: "unavailable"` → источник упал / таймаут; данные в принципе могли бы быть, но мы не смогли их получить.

### 5.3. Безопасность/доступ (сводно)

| Граница | Роль | Доступ | Проверка |
|---------|------|--------|----------|
| GET `/api/activity/data` | Администратор | Полный: текущее число + исторические данные | На бэке Arsenal |
| GET `/api/activity/data` | Оператор | 403 Forbidden | На бэке Arsenal |
| GET `/api/activity/data` | Неавторизованный | 401 Unauthorized | На бэке Arsenal |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟢 **Узел-фундамент #0 деплоится ПЕРВЫМ, до дочерних узлов (ARS-101, ARS-102, ARS-103).**

Порядок:
1. Deploy Arsenal Backend с INT-0 (`GET /api/activity/data`), кэшем на 30 сек, авторизацией по Администратор.
2. Проверить: эндпоинт доступен, авторизация работает, кэш живёт.
3. Deploy дочерних узлов, которые потребляют INT-0.

### 6.2. Обратная совместимость

🟢 Узел #0 — **новый эндпоинт, бэкв-совместимость не требуется**. Существующий функционал Arsenal Backend не трогаем.

### 6.3. Фиче-флаги

🟢 **Фиче-флагов нет.** Узел #0 деплоится атомарно; дочерние узлы могут использовать флаги для своей работы, но сам контракт INT-0 без флагов.

### 6.4. План отката

🟢 **Откат только BE (Arsenal с INT-0):** FE дочерних узлов, не получив ответ от INT-0 (500 / 408), отображает ошибку. Откат BE → INT-0 недоступен → FE показывает сообщение об ошибке. Допустимо: дочерний FE уже адаптирован к обработке ошибок INT-0 (см. каталог ошибок).

🟢 **Откат только FE (дочерних узлов):** BE Arsenal отдаёт INT-0, FE просто его не вызывает / прячет виджет. BE остаётся со своей логикой кэширования и вычисления агрегатов.

🟢 **Откат DDL:** не применимо (нет миграций, агрегаты вычисляются на лету).

### 6.5. Преднастройка до релиза (чек-лист)

- [x] Роли в security-сервисе: роль **Администратор** уже существует в Arsenal (🟡 подтверждено аналитиком); новой роли не заводим.
- [x] DDL-миграция: не требуется (нет новых таблиц, всё вычисляется на лету).
- [x] Конфиги по окружениям: кэш-TTL (30 сек), таймаут (5 сек) — вынести в конфиги или захардкодить? На усмотрение Arsenal; в спеке зафиксировано.
- [x] Сервисные аккаунты: не требуются (INT-0 вызывается от пользователя-администратора, не от другого сервиса).
- [x] Фиче-флаги: не требуются (деплой атомарный).
- [x] Алерты/мониторинг: рекомендуется алерт на 5xx / 408 на INT-0 (узел-фундамент, всё на нём зависит); метрика кэш-хитов; P95 latency на 5 сек (таймаут).

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 (текущее число) | Дано открытую админку с ролью Администратор, когда страница загрузилась, тогда система запрашивает INT-0 (`period_type=current`), получает `{ "status": "available", "current": { "active_count": N } }`, и в шапке отображается число N. |
| FR-2 | INT-0 (текущее число, периодически) | Дано открытую админку, когда число активных пользователей изменилось и прошло ≤ 30 секунд кэша, тогда счётчик обновляется без перезагрузки (т.е. фронт повторно вызывает INT-0 через заданный интервал, получает новое значение и перерисовывает). |
| FR-3 | INT-0 (исторические данные за период) | Дано счётчик в шапке, когда администратор кликает по нему, тогда открывается модалка; она запрашивает INT-0 с `period_type=daily` за период по умолчанию (напр. последние 7 дней), получает историческое распределение активных, и отображает график. |
| FR-4 | INT-0 (исторические данные за новый период) | Дано открытую модалку, когда администратор выбирает другой период (напр. часовой вместо дневного), тогда фронт запрашивает INT-0 с новыми параметрами `period_start` / `period_end` / `period_type`, получает данные за новый период, и график перестраивается. |
| FR-5 | INT-0 (исторические данные за период для экспорта) | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт запрашивает INT-0 с параметрами выбранного периода, получает данные (array историческ записей), формирует файл (CSV / Excel / JSON) и предлагает скачивание пользователю. |
