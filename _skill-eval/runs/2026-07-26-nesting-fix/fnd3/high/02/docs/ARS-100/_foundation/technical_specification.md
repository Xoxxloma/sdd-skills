## 1. Обзор изменения
### 1.1. Тип и стороны
🟡 **BE-only** — узел-фундамент отдаёт контракт данных активности пользователей; потребители — фронты детей (компоненты панели активности в админке «Арсенал»). Подтверждено аналитиком.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | собирает, отдаёт контракт активности | Arsenal Core | 🟡 подтверждено аналитиком |
| Arsenal Admin UI (дети) | потребляет данные активности | Arsenal UI | 🟢 новое |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 реализует единый источник данных об активности пользователей, необходимый для FR-1 (счётчик в шапке), FR-2 (автообновление), FR-3/FR-4 (модальное окно с графиком и переключением периодов) и FR-5 (выгрузка сводки). Без этого общего контракта дети не могли бы единообразно получать текущее число активных пользователей и агрегированные данные за период.

## 2. Взаимодействия (ядро)

### INT-1. Текущее число активных пользователей — 🟢
- **Граница/направление:** Arsenal Backend → компоненты FE детей
- **Триггер:** инициализация счётчика в шапке (FR-1), обновление счётчика по расписанию (FR-2)
- **Контракт (запрос):** `GET /api/arsenal/activity/current` — без тела; без параметров
- **Контракт (ответ):**
  | Поле | Тип | Обязательность | Описание |
  |------|-----|---|---|
  | `activeUsers` | `number \| null` | обязательно | Число активных пользователей, если доступно; `null` если источник недоступен |
  | `available` | `boolean` | обязательно | `true` если источник активности доступен; `false` если недоступен (показывать «—» в UI, не использовать старевшие данные) |
  | `timestamp` | `ISO 8601 datetime` | обязательно | Время получения снимка |
  | `cacheTime` | `number` (сек) | обязательно | Время жизни кэша на стороне бэка (сек) |
- **Пример запроса:** `GET /api/arsenal/activity/current`
- **Пример ответа (успех):**
  ```json
  {
    "activeUsers": 42,
    "available": true,
    "timestamp": "2026-07-26T14:30:15Z",
    "cacheTime": 30
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "activeUsers": null,
    "available": false,
    "timestamp": "2026-07-26T14:30:15Z",
    "cacheTime": 30
  }
  ```
- **Ошибки:** 
  | Код | Тело/сообщение | Когда | Состояние UI |
  |-----|---|---|---|
  | 200 | успешный ответ с available=true | источник доступен | показать значение `activeUsers` или обновить счётчик |
  | 200 | успешный ответ с available=false | источник недоступен | показать «—» вместо числа (не выдавать старевшее) |
  | 401 | `{ "error": "Unauthorized" }` | нет авторизации или роль не «Администратор» | показать «нет доступа» или скрыть счётчик |
  | 503 | `{ "error": "Service Unavailable" }` | бэк Арсенала недоступен | показать «—» (ошибка источника) |
  | 5xx | `{ "error": "Internal Server Error" }` | внутренняя ошибка бэка | показать «—» (ошибка источника) |
- **Состояния UI по ответу:** 
  - значение (200, available=true, activeUsers=N) → показать число N
  - ноль (200, available=true, activeUsers=0) → показать «0» (отличать от «нет данных»)
  - пусто/«—» (200, available=false) → показать прочерк «—»
  - ошибка (401) → «нет доступа» или скрыть элемент
  - ошибка (503, 5xx) → сообщение об ошибке + retry-кнопка
- **Авторизация:** только роль «Администратор»; проверка на бэке Арсенала; при 401 → показать «нет доступа»
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (отображение счётчика), FR-2 (автообновление счётчика)

### INT-2. Агрегированные данные активности за период — 🟢
- **Граница/направление:** Arsenal Backend → компоненты FE детей
- **Триггер:** открытие модального окна с графиком (FR-3), переключение периода в модальном окне (FR-4), подготовка к выгрузке сводки (FR-5)
- **Контракт (запрос):** 
  ```
  GET /api/arsenal/activity/aggregate
  Query параметры:
    period: "hour" | "day" | "week" (обязательно)
    from?: ISO 8601 datetime (опционально; если не передан, используется "period" назад от now)
    to?: ISO 8601 datetime (опционально; если не передан, используется now)
  ```
- **Контракт (ответ):**
  | Поле | Тип | Обязательность | Описание |
  |------|-----|---|---|
  | `period` | `"hour" \| "day" \| "week"` | обязательно | Запрошенный период агрегации |
  | `from` | `ISO 8601 datetime` | обязательно | Начало периода |
  | `to` | `ISO 8601 datetime` | обязательно | Конец периода |
  | `available` | `boolean` | обязательно | `true` если источник активности доступен; `false` если недоступен |
  | `hasDataForPeriod` | `boolean` | обязательно | `true` если за период есть хотя бы одна точка данных; `false` если период пуст (отличать от ошибки недоступности) |
  | `points` | `array of objects` | обязательно | Точки графика, упорядочены по времени |
  | `points[].timestamp` | `ISO 8601 datetime` | обязательно | Момент времени для этой точки |
  | `points[].activeUsers` | `number` | обязательно | Число активных пользователей (0 и выше; `0` — валидное значение) |
  | `points[].hasData` | `boolean` | обязательно | `true` если значение измерено; `false` если данных нет за этот слот (напр. система была недоступна) |
  | `cacheTime` | `number` (сек) | обязательно | Время жизни кэша на стороне бэка (сек) |
- **Пример запроса:** `GET /api/arsenal/activity/aggregate?period=day`
- **Пример ответа (успех, есть данные):**
  ```json
  {
    "period": "day",
    "from": "2026-07-25T00:00:00Z",
    "to": "2026-07-26T00:00:00Z",
    "available": true,
    "hasDataForPeriod": true,
    "points": [
      {
        "timestamp": "2026-07-25T00:00:00Z",
        "activeUsers": 10,
        "hasData": true
      },
      {
        "timestamp": "2026-07-25T01:00:00Z",
        "activeUsers": 15,
        "hasData": true
      },
      {
        "timestamp": "2026-07-25T02:00:00Z",
        "activeUsers": 0,
        "hasData": true
      },
      {
        "timestamp": "2026-07-25T03:00:00Z",
        "activeUsers": 0,
        "hasData": false
      }
    ],
    "cacheTime": 30
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "day",
    "from": "2026-07-25T00:00:00Z",
    "to": "2026-07-26T00:00:00Z",
    "available": false,
    "hasDataForPeriod": false,
    "points": [],
    "cacheTime": 30
  }
  ```
- **Пример ответа (период пуст, но источник доступен):**
  ```json
  {
    "period": "week",
    "from": "2026-07-19T00:00:00Z",
    "to": "2026-07-26T00:00:00Z",
    "available": true,
    "hasDataForPeriod": false,
    "points": [],
    "cacheTime": 30
  }
  ```
- **Ошибки:** 
  | Код | Тело/сообщение | Когда | Состояние UI |
  |-----|---|---|---|
  | 200 | успешный ответ, available=true | источник доступен | отрисовать график по `points` |
  | 200 | успешный ответ, available=false | источник недоступен | показать сообщение об ошибке + retry |
  | 200 | успешный ответ, hasDataForPeriod=false, available=true | период без данных | показать «нет данных за период» |
  | 400 | `{ "error": "Invalid period" }` | period не в [hour, day, week] | показать ошибку ("некорректный период") |
  | 401 | `{ "error": "Unauthorized" }` | нет авторизации или роль не «Администратор» | показать «нет доступа» или скрыть модальное окно |
  | 503 | `{ "error": "Service Unavailable" }` | бэк Арсенала недоступен | показать «—» (ошибка источника) |
  | 5xx | `{ "error": "Internal Server Error" }` | внутренняя ошибка бэка | показать сообщение об ошибке + retry |
- **Состояния UI по ответу:**
  - график (200, available=true, hasDataForPeriod=true) → отрисовать линейный график с точками `points[].activeUsers`
  - пусто (200, available=true, hasDataForPeriod=false) → показать «нет данных за выбранный период»
  - ошибка источника (200, available=false) → показать «источник активности недоступен» + retry-кнопка
  - ошибка авторизации (401) → показать «нет доступа» или скрыть окно
  - ошибка сервера (5xx, 503) → показать сообщение об ошибке + retry-кнопка
- **Авторизация:** только роль «Администратор»; проверка на бэке Арсенала; при 401 → показать «нет доступа»
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3 (отображение графика в модальном окне), FR-4 (переключение периода), FR-5 (подготовка данных для выгрузки)

## 3. Backend — ответственность
### 3.1. По сервисам
**Arsenal Backend** реализует оба взаимодействия (INT-1 и INT-2):
- INT-1: GET /api/arsenal/activity/current → возвращает текущее число активных пользователей (🟢 новое)
- INT-2: GET /api/arsenal/activity/aggregate → возвращает агрегированные данные активности за период (🟢 новое)
- Оба эндпоинта проверяют авторизацию: только роль «Администратор» получает доступ (🟡 подтверждено аналитиком: проверка на бэке Арсенала)
- Данные активности собирает сам бэк Арсенала, внешних сервисов не привлекаем (🟡 подтверждено аналитиком)

### 3.2. Данные и хранение
🟡 **Новых таблиц не заводим** — агрегаты активности считаются на лету из существующих источников (подтверждено аналитиком). Концептуально:
- Источник текущей активности: счётчик активных сессий (где именно считается — 🟡 к валидации; бэк Арсенала знает, как это делается)
- Источник исторических данных: логи активности или события сессий (где именно хранятся — 🟡 к валидации)
- Агрегация: вычисляется на лету при запросе INT-2 (не сохраняется в новую таблицу)

Индексы: существующие индексы в источниках должны поддерживать быструю агрегацию за период (точный список индексов — 🟡 по реальной схеме владеющего сервиса Арсенала).

### 3.3. Авторизация/доступ на бэке
- Оба эндпоинта INT-1 и INT-2 доступны только для ролей «Администратор» (🟡 подтверждено аналитиком)
- Проверка авторизации enforced на бэке Арсенала (в middleware или guard эндпоинта)
- При отсутствии авторизации → возвращается 401 Unauthorized
- Роли и их определение в security-сервисе — вне области узла #0 (управляется на уровне эпика/платформы)

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Три компоненты-потребители (дети узла #0) используют эти контракты:
1. **Счётчик в шапке админки** — вызывает INT-1 при инициализации и по расписанию (FR-1, FR-2)
2. **Модальное окно с графиком** — вызывает INT-2 при открытии и при переключении периода (FR-3, FR-4)
3. **Кнопка выгрузки** — готовит данные из INT-2 для скачивания в файл (FR-5)

Точные места в UI-дереве и навигация — в спеках детей (ARS-101, ARS-102, ARS-103).

### 4.2. Пользовательские сценарии
*Сценарии на уровне фронт-части фундамента отсутствуют* (узел #0 — чистая реализация контракта). Сценарии и взаимодействия пользователя с компонентами описаны в бизнес-требованиях эпика (FR-1..FR-5) и будут детализированы в спеках детей (ARS-101, ARS-102, ARS-103).

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь / как это используется компонентом |
|---|---|---|
| `loading` | первый запрос INT-1 или INT-2 in flight | спиннер/скелетон (пока идёт запрос) |
| `value` | 200, available=true, activeUsers/points ≠ null ≠ empty | числовое значение (для INT-1) или график (для INT-2) |
| `zero` | 200, available=true, activeUsers=0 | показать «0» (не путать с пустотой) |
| `empty` | 200, available=true, hasDataForPeriod=false (для INT-2) или очередь пуста | показать «нет данных» / «—» |
| `error_source` | 200 available=false / 503 / 5xx / таймаут | сообщение об ошибке + retry-кнопка |
| `error_forbidden` | 401 | скрыть счётчик/модальное окно или показать «нет доступа» |

### 4.3.1. Loading и таймауты
- **Таймаут cold-path (первый запрос INT-1 для счётчика):** 5 сек (как наложено аналитиком)
- **Таймаут warm-path (обновление счётчика по расписанию):** 5 сек (одинаковый, т.к. опрос не критичен, и 5 сек даёт пользователю видимый feedback)
- **Polling для INT-1 (автообновление счётчика, FR-2):** каждые 30 сек или менее (зависит от решения детей; бэк-кэш тоже 30 сек, так что polling ≤ 30 сек оптимален)
  - jitter: да (рекомендуется ±10% для распределения нагрузки)
  - Причина: равномерно распределить запросы, избежать всплесков от одновременных клиентов
- **При таймауте:** переходить в состояние `error_source`, показать retry-кнопку
- **При 5xx / 503:** переходить в состояние `error_source`, показать retry-кнопку

### 4.4. Доступ по ролям в UI
- **Роль «Администратор»:** видит счётчик, может открыть модальное окно, может выгрузить сводку (все элементы видны)
- **Другие роли (напр. «Оператор»):** счётчик и модальное окно скрыты (не отображаются вообще) или показывается «нет доступа»
- Проверка ролей в UI по результату 401 от бэка (дети обрабатывают 401 и скрывают элементы)

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- **Синхронность:** синхронные REST-запросы (GET) — оба взаимодействия INT-1 и INT-2 (🟡 подтверждено аналитиком)
- **Кэш:** на стороне бэка Арсенала, TTL = 30 сек (🟡 подтверждено аналитиком)
  - Клиентская кэширование: не указано аналитиком; дети решают сами (рекомендуется: для INT-1 кэш в памяти компонента между polling-циклами; для INT-2 кэш за время открытого модального окна)
- **Частота опроса INT-1 (FR-2 автообновление счётчика):** ≤ 30 сек (не чаще, чем TTL бэка; точная частота решает детский компонент)
- **Таймаут запроса:** 5 сек на обоих эндпоинтах (🟡 подтверждено аналитиком)
- **Ожидаемая нагрузка:** 
  - INT-1 (счётчик): запрос каждые ~30 сек на каждого администратора (обновление счётчика + спиннер в UI)
  - INT-2 (график): запросы при открытии/переключении модального окна (эпизодически, не фоновый polling)
  - Точная оценка нагрузки (QPS, RPS) — в PLAN.md эпика или на stage-тестировании

### 5.2. Надёжность/деградация
- **При недоступности источника активности:** возвращать флаг `available=false` вместо устаревших данных (🟡 подтверждено аналитиком)
  - INT-1: `available=false, activeUsers=null` → UI показывает «—»
  - INT-2: `available=false, hasDataForPeriod=false, points=[]` → UI показывает «ошибка источника»
- **Разные ошибочные состояния:**
  - Нет данных за период (но источник доступен): `hasDataForPeriod=false, available=true` → UI показывает «нет данных за период»
  - Источник недоступен: `available=false` → UI показывает сообщение об ошибке
  - Никогда не выдавать устаревший кэш при недоступности (🟡 подтверждено аналитиком)
- **Откат деградации:** если источник восстановился, следующий запрос вернёт `available=true` с актуальными данными

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Как проверяется | Негативный случай |
|---|---|---|---|

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 **Узел-фундамент #0 выкатывается ПЕРВЫМ, ДО дочерних узлов** (ARS-101, ARS-102, ARS-103) — подтверждено аналитиком.

- Если нужен откат, откатываем весь эпик вместе

### 6.4. План отката
- **Откат только BE (бэк Арсенала):** FE детей попадают на 404 / 5xx при вызове INT-1, INT-2 → должны gracefully обработать (показать ошибку, скрыть компоненты). Требуется проверка обработки 404/5xx в спеках детей.

Итог: откатывать узел #0 и дочерние узлы вместе (атомарно по эпику).
