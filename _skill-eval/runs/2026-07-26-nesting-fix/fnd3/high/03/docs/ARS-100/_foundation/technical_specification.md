BE-only. Узел-фундамент #0 предоставляет BE-контракт для получения данных об активности пользователей. Потребители — фронтенды детей эпика (счётчик в шапке, модалка с графиком, выгрузка).

### 1.2. Затронутые сервисы и владельцы

|--------|---------------|------------------|---------------|

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 реализует общий слой для FR-1..FR-5 эпика: предоставляет данные о текущей активности пользователей и агрегированной активности за выбранный период. Каждый ребёнок (счётчик, график, выгрузка) потребляет этот же контракт без дублирования логики.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности (текущее значение и агрегаты за период) — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → потребляющие фронты (дети эпика)
- **Триггер:** Фронт инициирует запрос на получение (1) текущего числа активных пользователей и (2) агрегированной активности за выбранный период (час / день / неделя).
- **Контракт (запрос):** 
  - Метод: `GET /api/arsenal/activity` (концептуально)
  - Параметры:
    - `period`: строка, обязательный — период агрегации (`hour` | `day` | `week`)
    - (необязательно) `from` / `to`: ISO 8601 дата/время для пользовательского диапазона (опционально для FR-5 выгрузки, но базовый контракт опирается на предзаданные периоды)

- **Контракт (ответ):**
  - `current_active_users`: целое число ≥ 0 | `null` (см. семантику ниже)
  - `availability`: `"available"` | `"unavailable"` (флаг доступности источника)
  - `aggregates`: массив объектов с полями:
    - `timestamp`: строка ISO 8601, начало интервала агрегации (напр., час, день, неделя в зависимости от `period`)
    - `active_users_count`: целое число ≥ 0 | `null` (см. семантику ниже)
  - `aggregates_empty`: булево — `true`, если за выбранный период данных нет (отличается от `availability: "unavailable"`)

- **Семантика полей:**
  - `current_active_users`: 
    - число ≥ 0 → валидный текущий счёт активных пользователей
    - `null` → нет данных (в т.ч. если активных пользователей ровно 0; различай `null` от `0` на фронте)
  - `availability`:
    - `"available"` → источник доступен, значения актуальны
    - `"unavailable"` → источник недоступен, значения могут быть устаревшими или отсутствовать; фронт показывает «—» / пустой график
  - `aggregates[*].active_users_count`:
    - число ≥ 0 → валидный счёт активных пользователей за интервал
    - `null` → нет данных за этот интервал
  - `aggregates_empty`:
    - `true` → за выбранный период и в источнике нет данных (уточнение для фронта: не это источник-недоступен, а просто за этот период активности не было)
    - `false` → данные либо есть (в `aggregates`), либо источник недоступен (см. `availability`)

- **Пример запроса:**
  ```
  GET /api/arsenal/activity?period=day
  ```

- **Пример ответа (успех, текущий день, данные доступны):**
  ```json
  {
    "current_active_users": 42,
    "availability": "available",
    "aggregates": [
      {
        "timestamp": "2026-07-26T00:00:00Z",
        "active_users_count": 35
      },
      {
        "timestamp": "2026-07-26T01:00:00Z",
        "active_users_count": 42
      },
      {
        "timestamp": "2026-07-26T02:00:00Z",
        "active_users_count": 38
      }
    ],
    "aggregates_empty": false
  }
  ```

- **Пример ответа (успех, но период пуст):**
  ```json
  {
    "current_active_users": 42,
    "availability": "available",
    "aggregates": [],
    "aggregates_empty": true
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_active_users": null,
    "availability": "unavailable",
    "aggregates": [],
    "aggregates_empty": false
  }
  ```

- **Ошибки:**
  - `400 Bad Request` — параметр `period` некорректен (не одно из: `hour` | `day` | `week`). Тело: `{ "error": "invalid_period", "message": "Period must be one of: hour, day, week" }`
  - `401 Unauthorized` — отсутствует авторизация или токен недействительный. Тело: `{ "error": "unauthorized" }`
  - `403 Forbidden` — авторизация есть, но роль не имеет доступа (не Administrator). Тело: `{ "error": "forbidden", "message": "Only Administrator role can access activity data" }`
  - `500 Internal Server Error` — ошибка на сервере. Тело: `{ "error": "internal_error" }`. Фронт должен различать это от `availability: "unavailable"` в 200-ответе.

- **Состояния UI по ответу (сюда заглядывают дети в своей спеке):**
  - 2xx, `availability: "available"`, `current_active_users: число` → значение (показать число)
  - 2xx, `availability: "available"`, `current_active_users: null` → пусто (показать «—» или пустой график)
  - 2xx, `availability: "unavailable"` → error_source (показать «недоступны»)
  - 401/403/5xx → error (показать сообщение об ошибке, предложить retry)

- **Авторизация:** 
  - Доступ к контракту проверяется на Arsenal Backend при каждом вызове.
  - Только роль **Administrator** имеет право получать данные активности.
  - При попытке вызова с другой ролью или без авторизации вернуть 403 / 401.

- **Происхождение:** 🟢 новое (узел-фундамент #0, спроектировано полностью)
- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (все зависят от этого контракта)

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal Backend** реализует контракт INT-0:
- 🟢 Предоставляет эндпоинт `GET /api/arsenal/activity` с параметром `period`
- 🟡 подтверждено аналитиком: сам Arsenal Backend собирает данные об активности пользователей (чужих источников не привлекаем)
- 🟢 Возвращает текущий счёт активных пользователей
- 🟢 Вычисляет и возвращает агрегированную активность за выбранный период (час / день / неделя) на лету
- 🟢 Обеспечивает авторизацию (только Administrator, 403 для остальных)
- 🟢 При недоступности источника активности возвращает `{ "availability": "unavailable", ... }`, а не устаревшие данные

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: новых таблиц не заводим. Агрегаты активности вычисляются на лету из существующих данных логов/событий Arsenal Backend. (Точная схема таблиц-источников и индексы — на стороне Arsenal Backend, не входят в спеку фундамента.)

### 3.3. Авторизация/доступ на бэке
- Проверка роли `Administrator` выполняется на Arsenal Backend при каждом запросе к `/api/arsenal/activity`.
- Запрос без авторизации → 401 Unauthorized.
- Запрос с ролью ≠ Administrator → 403 Forbidden.

## 4. Frontend — ответственность

*Не применимо: узел-фундамент #0 — BE-only контракт. Фронтенды детей применяют этот контракт в своих спеках (FR-1..FR-5).*

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- 🟡 подтверждено аналитиком: запрос к контракту выполняется **синхронно** (блокирующий ответ).
- 🟡 подтверждено аналитиком: результат кэшируется на стороне Arsenal Backend на **30 секунд**. (Кэш инвалидируется при новой активности, не строго по TTL, но гарантированно обновляется за 30с.)
- 🟡 подтверждено аналитиком: таймаут ответа — **5 секунд**. Если источник активности не ответил в течение 5с, вернуть 504 / `availability: "unavailable"`. *(Уточнение: проверить, возвращает ли 504 или 200 с unavailable-флагом; вероятнее второе, но обсудить при интеграции.)*
- Ожидаемая нагрузка: несколько запросов в секунду со стороны фронтенд-потребителей.

### 5.2. Надёжность/деградация
- При недоступности источника активности фронт **обязан показать специальное состояние** (пусто / ошибка), а не устаревшие данные.
- Различаются три случая:
  1. Данные доступны → значения в `current_active_users` и `aggregates`
  2. Период пуст (нет активности за этот срок) → `aggregates_empty: true`
  3. Источник недоступен → `availability: "unavailable"`, `current_active_users: null`

### 5.3. Безопасность/доступ (сводно)
| Роль | Доступ к INT-0 |
|------|-----------------|
| Administrator | ✅ полный доступ |
| Оператор | ❌ 403 Forbidden |
| Прочие | ❌ 401 Unauthorized (без токена) |

### 6.2. Обратная совместимость
Узел-фундамент #0 — новое взаимодействие (ранее не было). Обратной совместимости не требуется.

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: фиче-флаги **не используются**. Контракт INT-0 выкатывается атомарно вместе с логикой вычисления активности; потребляющие фронты могут полагаться на его наличие сразу после выката фундамента.

### 6.4. План отката (не применимо: узел-фундамент без UI)
Узел #0 — BE-only контракт без пользовательского интерфейса. Откат практики FE-only, возможна синхронная откат обеих сторон или пошаговый откат (сначала BE, потом FE, если она унаследовала контракт).

### 6.5. Преднастройка до релиза

- [ ] DDL-миграция: не требуется (новых таблиц нет)
- [ ] Конфиги: TTL кэша (30с), таймаут источника (5с) — вынести в конфиги Arsenal Backend по окружениям (dev/staging/prod) если требуется гибкость
- [ ] Сервисные аккаунты: не требуются (внутренний вызов внутри Arsenal Backend)

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие | Тест-кейс |
|----------|---|---|
| FR-1 | INT-0 | Дано: запрос с авторизацией Administrator, когда: первая загрузка админки, тогда: вернуть текущее число активных пользователей в 200 ответе с `availability: "available"` |
| FR-2 | INT-0 | Дано: счётчик в шапке показывает N активных, когда: число активных изменилось до M, тогда: в течение 30 сек кэш инвалидируется и счётчик обновляется (новый запрос к INT-0 вернёт новое значение) |
| FR-3 | INT-0 | Дано: клик на счётчик, когда: открывается модалка, тогда: модалка запрашивает активность за период по умолчанию через INT-0 и получает `aggregates` для графика |
| FR-4 | INT-0 | Дано: открытая модалка, когда: пользователь переключает период на день/неделю, тогда: запрос к INT-0 с новым параметром `period=day|week` вернёт новый `aggregates` массив, график перестроится |
| FR-5 | INT-0 | Дано: модалка с выбранным периодом, когда: кнопка выгрузки, тогда: выгрузка используется `current_active_users` и `aggregates` из последнего ответа INT-0 (или новый запрос) для формирования файла |
