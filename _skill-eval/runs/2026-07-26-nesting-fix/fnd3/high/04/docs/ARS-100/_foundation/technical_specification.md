## 1. Обзор изменения

### 1.1. Тип и стороны
🟡 **BE-only.** Узел-фундамент #0 предоставляет контракт данных об активности пользователей (текущее число активных пользователей + агрегированная активность за период: час / день / неделя). Этот контракт потребляют фронты трёх дочерних задач: счётчик в шапке админки, модальное окно с графиком активности, функция выгрузки сводки. Сам #0 не реализует фронтальные компоненты — только BE-контракт (эндпоинт с данными).

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---|---|---|
| Arsenal (Backend) | Предоставляет контракт активности (INT-0) | команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 обслуживает данные активности для FR-1..FR-5 эпика ARS-100: 
- FR-1 (отображение текущего числа активных) — требует `current`
- FR-2 (автообновление счётчика) — требует периодических вызовов INT-0 за `current`
- FR-3 (открытие модалки с графиком) — требует `aggregates` для периода `day` (по умолчанию)
- FR-4 (переключение периода) — требует `aggregates` для `hour` / `week`
- FR-5 (выгрузка сводки) — требует `aggregates` за выбранный период

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Arsenal BE → потребители (FE дочерних узлов через BE или напрямую)
- **Триггер:** запрос актуальных данных об активности; инициируется при загрузке админки, обновлении счётчика, открытии модалки, переключении периода, подготовке выгрузки
- **Контракт (запрос):**
  - **Метод + путь:** `GET /api/v1/arsenal/activity` (концептуально; стеко-агностично)
  - **Параметры:**
    - `period` (string, обязательный): `hour` | `day` | `week` — за какой период агрегировать
    - `from` (ISO 8601 timestamp, опционально): начало периода; если не передан, подразумевается текущее время минус длительность `period`

- **Контракт (ответ):**
  - `current` (integer, ≥ 0, обязательный): число активных пользователей на текущий момент запроса (по часовому поясу сервера)
  - `aggregates` (array, обязательный): хронологически упорядоченный список агрегатов активности за период
    - `timestamp` (ISO 8601, обязательный): начало временного интервала агрегата (начало часа, начало дня, начало недели — в зависимости от `period`)
    - `count` (integer, ≥ 0, обязательный): число активных пользователей в этот интервал
  - `period` (string, обязательный): уточнение периода: `hour` | `day` | `week` — совпадает с запросом
  - `unavailable` (boolean, опционально): если `true`, то источник активности недоступен; в этом случае `current: 0` и `aggregates: []` — это признак недоступности, а не отсутствия данных
  - `cached_at` (ISO 8601, опционально): момент последнего обновления кэша (для отладки, потребитель может игнорировать)

- **Пример запроса:**
  ```
  GET /api/v1/arsenal/activity?period=day
  ```
  
- **Пример ответа (успех — данные есть):**
  ```json
  {
    "current": 42,
    "aggregates": [
      { "timestamp": "2026-07-25T00:00:00Z", "count": 35 },
      { "timestamp": "2026-07-25T04:00:00Z", "count": 38 },
      { "timestamp": "2026-07-25T08:00:00Z", "count": 48 },
      { "timestamp": "2026-07-25T12:00:00Z", "count": 45 },
      { "timestamp": "2026-07-25T16:00:00Z", "count": 40 },
      { "timestamp": "2026-07-25T20:00:00Z", "count": 37 },
      { "timestamp": "2026-07-26T00:00:00Z", "count": 40 }
    ],
    "period": "day",
    "cached_at": "2026-07-26T12:00:30Z"
  }
  ```

- **Пример ответа (успех — данных за период нет):**
  ```json
  {
    "current": 0,
    "aggregates": [],
    "period": "day"
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current": 0,
    "aggregates": [],
    "period": "day",
    "unavailable": true,
    "cached_at": "2026-07-26T11:59:00Z"
  }
  ```

- **Ошибки:**
  - **403 Forbidden:** Вызывающей стороне недостаточно прав (роль не Администратор). Тело: `{ "error": "Forbidden", "message": "Only Administrator role can access activity data" }`. Происхождение: 🟡 подтверждено аналитиком.
  - **400 Bad Request:** Неверный параметр `period` (не в списке `hour|day|week`) или неверный формат `from`. Тело: `{ "error": "Bad Request", "message": "Invalid period: must be one of hour, day, week" }`. Происхождение: 🟢.
  - **408 Request Timeout / 504 Gateway Timeout:** Бэк не ответил за 5 секунд (таймаут исчерпан). Происхождение: 🟡 подтверждено аналитиком (таймаут 5 сек).
  - **500 Internal Server Error:** Непредвиденная ошибка в Arsenal. Тело: `{ "error": "Internal Server Error" }`. Потребитель должен обработать как `error_source`.

- **Состояния UI по ответу (для потребителей):**
  - `value` → `current > 0` или `aggregates` содержит хотя бы одно значение > 0; значение показывается как есть
  - `zero` → `current = 0` и `aggregates` непусты с валидными данными; показать «0» (отличать от пусто)
  - `empty` → `current = 0` и `aggregates = []` и `unavailable !== true`; показать «—» или «нет данных»
  - `error_source` → `unavailable: true` или 408/500/504/сетевая ошибка; показать сообщение об ошибке + кнопка retry
  - `error_forbidden` → 403; показать «Недостаточно прав»

- **Авторизация:**
  - Контракт доступен **только** роли **Администратор** (по подтверждению аналитика)
  - Проверка enforced на бэке Arsenal при каждом вызове (по JWT-токену, сессии или другому механизму, который уточняется при интеграции)
  - Негативный случай: вызов с ролью Оператор или без авторизации → ответ 403 Forbidden

- **Происхождение:** 🟢 новое (узел-фундамент #0, спроектировано в этом документе)
- **Трассировка:** FR-1 (текущее число), FR-2 (обновление счётчика), FR-3 (открытие модалки), FR-4 (переключение периода), FR-5 (выгрузка сводки)

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI (потребителя) |
|---|---|---|---|

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal Backend** реализует INT-0:
- 🟢 Новый эндпоинт `GET /api/v1/arsenal/activity` со схемой контракта выше (путь, методы, параметры, ответ)
- 🟡 подтверждено аналитиком: источник активности (логи сессий, события входа/выхода) существует и Arsenal BE собирает данные активности сам, чужих сервисов не привлекаем
- 🟢 Вычисляет текущее число активных пользователей (свежее значение на момент запроса)
- 🟢 Агрегирует активность за запрошенный период (час/день/неделя) путём подсчёта активных пользователей в каждом интервале; выполняется **на лету** (не хранится в таблице)
- 🟡 подтверждено аналитиком: кэширует результат на стороне Arsenal BE с TTL = 30 секунд; если в течение 30 сек поступает второй запрос с теми же параметрами, отдаёт кэшированный результат
- 🟡 подтверждено аналитиком: таймаут запроса — 5 секунд; если логика не ответила за 5 сек, возвращает 408 или 504 (уточнять при интеграции)
- 🟡 подтверждено аналитиком: при недоступности источника активности (сервис логов упал, БД сессий недоступна) отдаёт флаг `unavailable: true` вместо кэшированного или устаревшего значения

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: **новых таблиц не заводим**, агрегаты вычисляются на лету.

Концептуально:
- Существующий источник активности (например, таблица сессий или лог событий входа/выхода) — не меняется, используется как есть
- 🟢 Новая логика: функция/процедура агрегирования активности за период (час/день/неделя) и вычисления текущего активных на основе существующего источника
- 🟢 Кэш-уровень (in-memory, Redis или другой — уточняется при разработке): 30-секундное кэширование ответов INT-0 по ключу `period`; инвалидация по TTL
- 🟡 к валидации: если индекс по временным меткам на существующей таблице активности отсутствует и требуется для производительности, то добавить индекс на поле временной метки (DDL уточняется в репо Arsenal при интеграции)

Миграции БД: не требуются (по подтверждению).

### 3.3. Авторизация/доступ на бэке
- 🟡 подтверждено аналитиком: эндпоинт INT-0 охраняется проверкой роли Администратор

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- 🟡 подтверждено аналитиком: **синхронный вызов** (не очередь, не async, не event-driven) — потребитель вызывает, ждёт ответа INT-0
- 🟡 подтверждено аналитиком: **кэш на стороне Arsenal BE**, TTL = 30 секунд
  - Если кэш горячий (возраст < 30 сек), отдаём кэшированный результат
  - Если TTL истёк (возраст ≥ 30 сек), идём к источнику активности и пересчитываем
  - Если источник недоступен (ошибка при доступе к логам/сессиям), отдаём флаг `unavailable: true`, не используем кэш как fallback (не выдавать устаревшее за свежее — требование из БТ)
- 🟡 подтверждено аналитиком: **таймаут запроса = 5 секунд** (от получения запроса до начала отправки ответа); если источник не ответил за 5 сек, возвращаем 408 или 504, не ждём
- Частота опроса: не является требованием #0 (это решение дочерних FE), но FE обычно переполучат данные каждые 30–60 сек
- Ожидаемая нагрузка: 🟡 к валидации (уточнить при интеграции: сколько одновременных пользователей админки, сколько запросов в сек)

### 5.2. Надёжность/деградация
- 🟡 подтверждено аналитиком: **Если источник активности недоступен** (сервис логов упал, БД сессий перезагружается, сеть обрвана) → Arsenal отдаёт `{ "unavailable": true, "current": 0, "aggregates": [] }` вместо кэшированного/устаревшего значения
  - Это дисциплина: не выдавать старые данные за свежие, когда пользователь может принять на них решение (сроки регламентных работ)
  - Потребитель видит `error_source` → показывает «—» или сообщение об ошибке + retry
- **Если данных за период нет** (например, новая система, активности не было) → отдаём `{ "current": 0, "aggregates": [], "unavailable": false/omit }` — это норма, не ошибка
  - Потребитель видит `empty` → показывает «—» или «нет данных»
- **Таймаут** (≥ 5 сек): Arsenal не ответил вовремя → потребитель получит 408 или 504 → обработает как `error_source`
- **Откат:** если Arsenal откатить, его соседи (дочерние фронты) получат 404 или 503 на вызов INT-0 → обработают как `error_source`

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто | Может | Не может | Происхождение |
|---|---|---|---|---|
| INT-0 `/api/v1/arsenal/activity` | Пользователь с ролью Администратор | Вызвать, получить `current` и `aggregates` | — | 🟡 подтверждено аналитиком |
| INT-0 `/api/v1/arsenal/activity` | Пользователь с ролью Оператор или без авторизации | — | Вызвать (получит 403) | 🟡 подтверждено аналитиком |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟡 подтверждено аналитиком: **фундамент выкатывается РАНЬШЕ потребителей**.

1. **Первый этап:** выкатывается узел-фундамент #0 (эндпоинт INT-0 в Arsenal BE)
   - Проверяем: INT-0 отвечает 200 с корректными данными, авторизация работает (403 для неадминов)
   - Кэш включён и работает (второй запрос быстрее)
   - Таймаут соблюдается

2. **Второй этап:** (после прогрева #0) выкатываются дочерние узлы (счётчик в шапке, модалка с графиком, выгрузка)
   - Каждый дочерний узел начинает вызывать INT-0

**Почему в таком порядке:** дочерние фронты опираются на контракт INT-0 и не могут работать без него; если развернуть дочерей раньше #0, они получат 404/503.

### 6.2. Обратная совместимость
- 🟢 Новый эндпоинт `GET /api/v1/arsenal/activity` не ломает существующих интеграций (это новый путь, никто его раньше не вызывал)
- 🟢 Админка arsenalчас работает без панели активности; после выката #0 панель добавляется параллельно
- 🟡 подтверждено аналитиком: **откат только #0:** дочерние фронты получат 404 на вызов INT-0 → обработают как `error_source`, покажут ошибку (синхронный откат FE не требуется, т.к. дочерние фронты сами работают с ошибкой)
- 🟡 подтверждено аналитиком: **откат одной из дочерних FE:** #0 продолжит работать, другие дочерние компоненты не пострадают

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **релизим атомарно, без фиче-флагов**. Когда #0 готов, выкатываем; когда дочерние фронты готовы, они начинают вызывать INT-0 — нет постепенного roll-out по процентам пользователей.

### 6.4. План отката (обязательно для BE)
- **Откат только BE (#0):** дочерний FE получит 404/503 на вызов INT-0
  - Для FE это `error_source` → покажет «—» или сообщение об ошибке
  - Синхронный откат FE **не требуется** — дочерние фронты сами обработают ошибку, админка остаётся функциональной (только панель активности недоступна)
  - Временной откат: обновить DNS/маршрут, чтобы INT-0 был недоступен, или откатить версию Arsenal на предыдущую

- **Откат только FE (одного из дочерних узлов):** BE #0 продолжит работать; другие дочерние фронты (счётчик, модалка, выгрузка) не пострадают

- **Откат DDL:** не применимо (миграций нет)

### 6.5. Преднастройка до релиза

- [x] **Роли в security-сервисе:** роль «Администратор» должна существовать и быть применима к пользователям-администраторам; уточнить механизм проверки в middleware Arsenal (JWT-claim, session attribute, другое)
- [ ] **DDL-миграция:** не требуется (новых таблиц нет)
- [x] **Конфиги по окружениям:** параметры кэша (TTL = 30 сек), таймаут (5 сек) — могут быть константами в коде или загружаться из конфига (dev/staging/prod)
- [ ] **Сервисные аккаунты:** не требуются (нет межсервисных вызовов; Arsenal собирает данные сам)
- [ ] **Фиче-флаги:** не требуются (релизим атомарно)
- [x] **Алерты/мониторинг:**
  - На ошибки INT-0: 408, 504, 500 (если их > порога за период)
  - На признак недоступности источника (`unavailable: true` > N раз за период)
  - На taймауты (если TTL 5 сек исчерпывается регулярно)

## 8. Допущения и открытые вопросы

- **🟡 Подтверждено аналитиком (не по коду; валидировать при интеграции):**
  - Arsenal BE собирает данные активности сам, чужих сервисов не привлекаем (источник активности — внутренний)
  - Агрегаты вычисляются на лету, новых таблиц не заводим
  - Кэш на стороне Arsenal BE: TTL = 30 сек
  - Таймаут запроса = 5 сек
  - При недоступности источника отдаём флаг `unavailable: true`, а не кэшированное/устаревшее значение
  - Контракт доступен только роли Администратор; проверка на бэке Arsenal
  - Релизим фундамент раньше потребителей; без фиче-флагов, атомарно

- **🟡 К валидации:**
  - Точный источник активности (таблица, событие, сервис) — какую таблицу/логи читаем для определения текущих активных и истории
  - Механизм кэша (in-memory, Redis, другое) — где хранится 30-секундный кэш
  - Способ проверки роли Администратор (JWT-claim, session attribute, обращение к auth-сервису) — как middleware Arsenal извлекает роль
  - Нужен ли индекс на существующей таблице активности по временной метке для производительности
  - Ожидаемая нагрузка (сколько одновременных пользователей админки, сколько запросов в сек на INT-0)

- **Унаследовано из БТ (бизнес-пробелы — не блокируют тех-спеку):**
  - Точные механизмы получения и хранения данных активности (какая таблица, какие события) — закрываются на стороне БТ при уточнении деталей реализации

- **Все технические решения приняты, спецификация готова к разработке.**
