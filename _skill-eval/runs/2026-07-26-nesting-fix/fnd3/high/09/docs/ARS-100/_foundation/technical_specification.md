## 1. Обзор изменения

### 1.1. Тип и стороны

**BE-only.** Узел-фундамент #0 — общий слой для нескольких детских фронтов (ARS-101, ARS-102, ARS-103 и др.). Задача #0 не добавляет UI, а спроектировает общий контракт данных активности, который все дети потребляют в своих взаимодействиях с Arsenal backend. Узел выкатывается отдельно, раньше потребителей.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal backend | Сервис, отдающий контракт; собирает и отдаёт данные активности | Arsenal Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Узел #0 реализует общую сущность, на которой опираются FR-1..FR-5 эпика: текущее число активных пользователей и агрегированная активность за период. Данные служат источником для всех трёх UI-элементов (счётчик в шапке, график в модали, выгрузка сводки).

## 2. Взаимодействия (ядро)

### INT-0. Контракт данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal backend → фронты детей (FE-дети получают контракт, используют его для отображения)
- **Триггер:** Дочерний фронт инициирует запрос текущей и исторической активности (при загрузке, по таймеру, по клику пользователя)
- **Контракт (запрос — концептуально):**
  - Метод + путь: `GET /api/activity/users?period=<period>` (концептуально; стеко-агностично; точный путь уточнит Arsenal при интеграции)
  - Параметры:
    - `period` (строка, обязательно): `hour` | `day` | `week` — период, за который получить агрегаты
- **Контракт (ответ):**
  - `current` (число, обязательно): текущее число активных пользователей на момент запроса; может быть 0 (валидный ноль), `null` только при недоступности источника
  - `data` (массив объектов, обязательно): агрегированная активность за выбранный период; каждый объект:
    - `timestamp` (число, UNIX ms, обязательно): момент начала временного окна
    - `active_count` (число, обязательно): число активных пользователей в этом окне; может быть 0
  - `unavailable` (булев, опционально): `true` если источник данных недоступен; при `true` остальные поля игнорировать (не отправлять или `null`)
  - Семантика `null`: встречается только в `data[i].active_count`, когда окно имело техническую ошибку (тогда `active_count: null` → UI показывает пропуск); в остальных полях `null` запрещён (либо число, либо отсутствует поле)
- **Пример запроса:**
  ```
  GET /api/activity/users?period=day
  ```
- **Пример ответа (успех):**
  ```json
  {
    "current": 42,
    "data": [
      { "timestamp": 1690000000000, "active_count": 38 },
      { "timestamp": 1690003600000, "active_count": 41 },
      { "timestamp": 1690007200000, "active_count": 42 },
      { "timestamp": 1690010800000, "active_count": 40 }
    ],
    "unavailable": false
  }
  ```
- **Пример ответа (данных за период нет, но источник доступен):**
  ```json
  {
    "current": 5,
    "data": [],
    "unavailable": false
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "unavailable": true
  }
  ```
- **Ошибки:**
  - **200 OK:** успешно; смотри выше (включая `"unavailable": true` как валидный ответ)
  - **400 Bad Request:** неподдерживаемое значение `period` или иная ошибка валидации параметров
  - **401 Unauthorized:** отсутствует аутентификация (не должно быть; см. авторизацию ниже)
  - **403 Forbidden:** аутентифицирован, но роль не «Администратор»
  - **500 Internal Server Error:** ошибка на бэке; тело: `{ "error": "Internal error" }` (или более описательное)
  - **504 Gateway Timeout:** истёк таймаут 5 секунд при запросе к источнику (возможен и при прямом подключении, если источник сам долго считает)
- **Состояния UI по ответу:**
  - `value`: ответ 200, `current ≠ null ≠ 0`, `unavailable ≠ true` → показывать число в счётчике, точки графика в модали
  - `zero`: ответ 200, `current = 0`, `unavailable ≠ true` → показывать «0» (не прочерк)
  - `empty`: ответ 200, `data: []`, счётчик может быть `null`/`0`, `unavailable ≠ true` → показывать прочерк «—» (данных за период нет, но это валидное состояние)
  - `error_source`: 500, 504 или сетевая ошибка → показать сообщение об ошибке + кнопку retry
  - `error_forbidden`: 403 → показать «нет доступа» (не должно быть для Администратора)
  - `loading`: первый запрос начат / инвалидация кэша → показать спиннер/скелетон
- **Авторизация:**
  - Кто вправе: только пользователи с ролью **«Администратор»** (поле роли/группа в Arsenal auth)
  - Где проверяется: на бэке Arsenal; проверка — перед выдачей ответа (ко всем трём полям доступ одинаков: либо всё видит, либо 403)
  - Негативный случай: если роль не «Администратор» → ответ 403 Forbidden
- **Происхождение:** 🟢 новое (узел-фундамент #0, спроектировано с нуля)
- **Трассировка:** FR-1 (счётчик на загрузку), FR-2 (обновление счётчика), FR-3..FR-5 (модалка, график, выгрузка)

### Каталог ошибок

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 | (см. примеры выше) | успех; включает `"unavailable": true` как валидный ответ | `value` / `zero` / `empty` / `loading` |
| 400 | `{ "error": "Invalid period: <value>" }` | неподдерживаемый `period` или прочие ошибки валидации | `error_source` (показать сообщение об ошибке) |
| 403 | `{ "error": "Forbidden" }` | роль не «Администратор» | `error_forbidden` |
| 500 | `{ "error": "Internal error" }` | ошибка на бэке Arsenal | `error_source` |
| 504 | `{ "error": "Timeout" }` | таймаут 5s при запросе к источнику | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal backend:**
- Реализует `GET /api/activity/users?period=<period>` (или эквивалентный концептуально, точная схема уточнится при интеграции)
- На входе: парметр `period` (hour/day/week)
- На выходе: контракт INT-0 (см. §2)
- Логика:
  - Получить текущее число активных пользователей (из источника данных активности)
  - Получить агрегированную активность за выбранный период (окна по часам для `hour`, по дням для `day`, по дням тоже или неделям для `week` — точная разбивка уточнится)
  - Если источник недоступен → отправить `{ "unavailable": true }`; никогда не отправлять устаревшие данные
  - Если данных за период нет, но источник доступен → отправить `{ "current": <число>, "data": [] }`
  - Проверить авторизацию (роль = «Администратор»); если нет → 403

### 3.2. Данные и хранение

🟡 Подтверждено аналитиком (не по коду): **новых таблиц/сущностей не заводим.** Данные активности считаются на лету из существующего источника (как именно — уточнит Arsenal при интеграции, может быть Redis, in-memory store, счётчики в логах и т.п.). Агрегаты тоже считаются на лету, без кэширования в БД; кэш 30s на стороне бэка (см. §5.1) живёт в памяти/сессии, не в таблице.

**Новых сущностей нет — явно подтверждено.**

### 3.3. Авторизация/доступ на бэке

- Проверка роли: перед выдачей ответа INT-0 Arsenal проверяет, что пользователь (из сессии/токена) имеет роль «Администратор»
- Где enforced: в хэндлере эндпоинта (middleware / декоратор / guard в начале метода)
- Роли: согласно ролевой модели из БТ (§5.3 business_requirements.md): Администратор, Оператор и др.
- Negативный случай: Оператор или иная роль → 403 Forbidden
- 🟡 Подтверждено аналитиком: в Arsenal есть встроенная проверка ролей; она используется (не заводим новую систему авторизации)

## 4. Frontend — ответственность

**Не применимо: узел-фундамент #0 не содержит UI.** Ответственность за перевод контракта INT-0 в UI-состояния (§4.3) несут дочерние фронты (они наследуют этот контракт и добавляют к нему визуальное представление). Узел #0 отвечает только за контракт данных.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** синхронный запрос (не фоновый job, не событие); фронты синхронно ждут ответа
- **Кэш:** 🟡 подтверждено аналитиком — 30 секунд на стороне **Arsenal backend**. Как именно (in-memory, Redis, TTL в session-store) — определяет Arsenal при реализации; для фронтов это прозрачно (кэш не видно в контракте). При каждом запросе фронт получает закэшированный или свежий ответ
- **Таймаут:** 5 секунд на запрос к источнику (если источник считает дольше — таймаут, фронт получит 504)
- **Ожидаемая нагрузка:** TBD (уточнить при планировании производительности; прогноз: число админов × 2–3 запроса в минуту, не критично для нагрузки на бэк)

### 5.2. Надёжность/деградация

- **При недоступности источника:** не отдавать устаревшие данные; вернуть `{ "unavailable": true }` → фронты покажут ошибку или пустое состояние (в зависимости от своей логики)
- **При таймауте:** вернуть 504 Gateway Timeout → фронты покажут ошибку + retry
- **Потребители (фронты) обязаны обрабатывать:**
  - ✅ успешный ответ с `current` и `data`
  - ✅ успешный ответ с `"unavailable": true` (не как ошибку, а как информацию)
  - ✅ ошибки 4xx/5xx и сетевые таймауты

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто вправе | Где проверяется |
|---------|-----------|-----------------|
| GET /api/activity/users | Администратор | Arsenal backend (middleware/decorator) |
| Оператор и иные роли | Запрещено | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **Arsenal backend** (узел #0) выкатывается **первым** с новым эндпоинтом INT-0
2. **Дочерние фронты** (ARS-101, ARS-102, ARS-103 и т.д.) выкатываются **после**, когда они видят стабильный контракт #0

**Обоснование:** фронты зависят от контракта INT-0, поэтому бэк должен быть готов к запросам перед тем как фронты начнут их слать. Нет фиче-флагов — релизим атомарно по времени.

### 6.2. Обратная совместимость

- **Контракт INT-0** — новый, нет старых потребителей. Не ломается ничего.
- **Возможные будущие изменения** (не в этой спеке): если вида-то изменится структура ответа (добавим новое поле) — добавляем опционально, старые потребители игнорируют неизвестные поля; если изменится формат `timestamp` или `period` — необходима миграция потребителей одновременно

### 6.3. Фиче-флаги

🟡 Подтверждено аналитиком: **фиче-флагов нет.** Контракт #0 вводится атомарно; фронты-дети при выкате получают обновление также атомарно. Если требуется постепенный rollout (по % пользователей), это решается на уровне дочерних фронтов, не на уровне #0.

### 6.4. План отката

- **Откат только Arsenal BE (INT-0):** дочерние фронты, не получив ответ, покажут ошибку или спиннер (логика зависит от каждого ребёнка). Потребуется синхронный откат фронтов, если они уже её поддерживают; не рекомендуется откатывать BE без FE — лучше откатить всё сразу
- **Откат только FE (дети):** Arsenal отдаёт новый контракт (никто не потребляет) — это OK, данные никуда не идут; действия: откатить FE, потом можно откатить BE
- **Откат DDL:** не применимо, новых таблиц/миграций нет

### 6.5. Преднастройка до релиза (чек-лист)

- [x] **Роли в security-сервисе** — роль «Администратор» уже существует; не требуется новая конфигурация (подтверждено аналитиком)
- [x] **DDL-миграция в репо Arsenal** — не применимо: новых таблиц нет
- [x] **Конфиги по окружениям (dev/staging/prod)** — таймаут 5s, кэш 30s — встроить как константы в код или как env-vars (по практике Arsenal); не требуется специальная конфигурация на разные окружения (значения одинаковы)
- [x] **Сервисные аккаунты для межсервисных вызовов** — не применимо: INT-0 отдаёт Arsenal, потребляют фронты в контексте пользователя (не межсервисный вызов)
- [x] **Фиче-флаги заведены** — не требуются (см. §6.3)
- [x] **Алерты/мониторинг на ключевые ошибки** — рекомендуется: мониторить 504 (таймауты при недоступности источника) и 500 на эндпоинте INT-0; установить алерт на растущий процент ошибок > 5%

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано открытую админку с ролью Администратор, когда страница загрузилась, тогда GET /api/activity/users?period=day вернул 200 с `{ "current": <число> }` в шапке показывается это число |
| FR-2 | INT-0 (polling/timer) | Дано открытую админку, когда число активных пользователей изменилось на источнике, тогда через ≤30s (кэш) + <5s (запрос) счётчик обновляется без перезагрузки |
| FR-3 | INT-0 | Дано счётчик в шапке, когда администратор кликает по нему, тогда модальное окно открывается; фронт вызывает GET /api/activity/users?period=day (по умолчанию), получает 200 с `data: [...]` |
| FR-4 | INT-0 | Дано открытую модалку, когда администратор выбирает период `week`, тогда фронт вызывает GET /api/activity/users?period=week, получает 200, график перестраивается |
| FR-5 | INT-0 (данные) | Дано открытую модалку, когда администратор нажимает выгрузку, тогда локальный скрипт берёт текущие данные из `response.data` (из последнего GET /api/activity/users), формирует файл CSV/JSON, скачивает |
