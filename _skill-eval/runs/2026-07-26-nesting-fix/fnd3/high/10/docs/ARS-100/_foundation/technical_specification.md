## 1. Обзор изменения

### 1.1. Тип и стороны

**BE-only** — 🟢 Узел-фундамент #0 отдаёт контракт данных активности, потребители (дочерние узлы с фронтом) опираются на один канал. Новых взаимодействий между сервисами нет; фундамент — это единственный новый сервис-слой, который потребляет бэк Арсенала.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (бэк) | Собирает и отдаёт контракт данных активности; владеет логикой агрегации | Core Арсенала | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Фундамент реализует общий источник данных активности, на которой опираются FR-1 (текущий счётчик), FR-2 (обновление без перезагрузки), FR-3–FR-5 (график и выгрузка за период). Три детских узла (счётчик в шапке, модальный график, выгрузка) наследуют этот контракт и различают его состояния (значение, пусто, ошибка источника).

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Арсенал-BE → Узел-фундамент #0 (BE-BE, внутренний)
- **Триггер:** Фронт дочернего узла запрашивает либо текущий счётчик, либо агрегаты за период; бэк Арсенала зовёт фундамент-бэк
- **Контракт (запрос):**
  - Метод: `GET` (концептуально; конкретная транспортировка — на владельце Арсенала)
  - Параметры запроса:
    - `type` (обязательно, enum) — `current` (текущее число активных) или `aggregate` (агрегаты за период)
    - Для `aggregate`: `period_type` (enum) — `hour`, `day`, `week`; `start_time` (ISO 8601 timestamp), `end_time` (ISO 8601 timestamp) — оба обязательны
  
- **Контракт (ответ):** 
  - Для `type=current`:
    - `count` (integer ≥ 0 или null) — число активных пользователей прямо сейчас, либо null если данных нет
    - `source_available` (boolean) — true если источник активности был доступен при этом ответе; false если источник недоступен и мы отдаём признак ошибки
    - `data_exists` (boolean) — true если есть валидные данные за этот момент; false если за период нет данных вообще (отличие от `count=0` — это означает, что данных не было собрано)
  - Для `type=aggregate`:
    - `points` (массив объектов с полями ниже, может быть пусто)
      - `timestamp` (ISO 8601) — начало интервала агрегации
      - `count` (integer ≥ 0 или null) — усреднённое/максимальное число активных за интервал (семантика выбирается аналитиком и фиксируется); может быть null в одной из точек, если там нет данных
    - `source_available` (boolean) — true если все данные за период собраны; false если источник был недоступен хотя бы часть периода (фронту нужно показать обозначение неполноты)
    - `data_exists` (boolean) — true если в points есть хотя бы одна точка с валидными данными; false если за весь период данных нет (фронту нужно показать «нет данных за период»)
    - `aggregate_type` (enum, строка) — `avg`, `max`, `current_snapshot` (какой тип агрегации использован за каждый интервал) — выбирает аналитик, но должно быть известно фронту для правильной интерпретации графика

- **Пример запроса (текущий счётчик):**
  ```
  GET /<endpoint>/activity?type=current
  ```
  
- **Пример запроса (агрегаты за день):**
  ```
  GET /<endpoint>/activity?type=aggregate&period_type=day&start_time=2026-07-26T00:00:00Z&end_time=2026-07-27T00:00:00Z
  ```

- **Пример ответа (успех, текущий счётчик):**
  ```json
  {
    "count": 1247,
    "source_available": true,
    "data_exists": true
  }
  ```

- **Пример ответа (успех, текущий счётчик, источник недоступен):**
  ```json
  {
    "count": null,
    "source_available": false,
    "data_exists": false
  }
  ```

- **Пример ответа (успех, агрегаты за день, с промежутками):**
  ```json
  {
    "points": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 450 },
      { "timestamp": "2026-07-26T04:00:00Z", "count": 120 },
      { "timestamp": "2026-07-26T08:00:00Z", "count": null },
      { "timestamp": "2026-07-26T12:00:00Z", "count": 2100 },
      { "timestamp": "2026-07-26T16:00:00Z", "count": 1850 },
      { "timestamp": "2026-07-26T20:00:00Z", "count": 620 }
    ],
    "source_available": false,
    "data_exists": true,
    "aggregate_type": "avg"
  }
  ```

- **Пример ответа (успех, агрегаты за день, данных за период вообще нет):**
  ```json
  {
    "points": [],
    "source_available": true,
    "data_exists": false,
    "aggregate_type": "avg"
  }
  ```

- **Ошибки:**
  - Код HTTP 5xx (500, 503) — источник активности недоступен на бэке Арсенала; фронт переводит это в `error_source` состояние (показать «—» или ошибку, дать retry)
  - Код HTTP 400 — неправильные параметры запроса (например, недопустимый `period_type` или неправильный формат timestamp); фронт может залогировать как programmatic error
  - Код HTTP 403 — требуется роль администратора (см. авторизацию ниже)
  - Код HTTP 401 — не аутентифицирован; фронт перенаправляет на логин

- **Состояния UI по ответу (если есть фронт):**
  - `value` → 2xx, `source_available=true`, `data_exists=true`, значение > 0 → показать число/график
  - `zero` → 2xx, `source_available=true`, `data_exists=true`, `count=0` (или все точки = 0) → показать «0» (не прочерк)
  - `empty` → 2xx, `data_exists=false` → показать прочерк «—» или «нет данных»
  - `error_source` → 5xx, таймаут, сетевая ошибка, или `source_available=false` → показать обозначение ошибки/недоступности + кнопку retry
  - `error_forbidden` → 403 → «нет доступа»

- **Авторизация:**
  - 🟡 подтверждено аналитиком: только роль **Администратор** может получить данные активности; проверка выполняется на бэке Арсенала (до передачи в фундамент или в фундаменте)
  - Негативный случай: если пользователь не администратор → 403 Forbidden; фронт показывает «вам недоступна эта функция»

- **Происхождение:** 🟢 новое (узел-фундамент #0, общий контракт для детей FR-1..FR-5)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5

## 3. Backend — ответственность

### 3.1. По сервисам

**Арсенал-BE (владелец фундамента #0):**
- Реализует эндпоинт (или RPC, в зависимости от транспорта), который отдаёт INT-0 контракт (текущий счётчик и агрегаты за период)
- Собирает и хранит данные активности (сами источники, механизм сбора — на уровне реализации Арсенала; спека фиксирует только контракт, не внутренность)
- Вычисляет агрегаты на лету из имеющихся данных (никаких новых таблиц-кэшей) 🟡 подтверждено аналитиком
- Отдаёт `source_available=false` если источник активности недоступен в момент запроса или был недоступен часть периода (за что отвечает реализация Арсенала)
- Отдаёт `data_exists=false` если за запрошенный период нет вообще ни одного измерения (отличие от нулей — это говорит фронту «нечего показывать»)
- Проверяет авторизацию (роль Администратор) на уровне Арсенала перед отдачей данных

### 3.2. Данные и хранение

🟡 подтверждено аналитиком: **никаких новых таблиц**. Агрегаты считаются из существующих данных активности, которые Арсенал уже собирает. Точная схема источника активности (какие поля, как хранятся, в какой таблице) — на уровне реализации Арсенала; спека не предписывает внутреннее хранилище. Индексы, retention, TTL — по усмотрению Арсенала, но должны быть оптимизированы под синхронные запросы агрегатов (таймаут 5 секунд).

### 3.3. Авторизация/доступ на бэке

🟡 подтверждено аналитиком: проверка роли **Администратор** выполняется на бэке Арсенала (в точке входа INT-0 эндпоинта). Пользователь без роли получает 403. Как именно Арсенал интегрируется с сервисом аутентификации для проверки ролей — деталь реализации (спека не предписывает механизм, указывает только факт: проверка есть).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Три дочерних узла (детские элементы FR-1..FR-5) одновременно потребляют INT-0:
1. **Счётчик в шапке** (FR-1, FR-2) — вызывает INT-0 с `type=current` для показа живого числа
2. **Модальный график** (FR-3, FR-4) — вызывает INT-0 с `type=aggregate` для выбранного периода и рендера линии
3. **Выгрузка сводки** (FR-5) — вызывает INT-0 с `type=aggregate` для формирования данных файла

Фундамент не содержит UI сам (это BE-only слой); каждый дочерний узел отвечает за визуализацию и обработку ошибок.

### 4.2. Пользовательские сценарии

**Основной поток (все три элемента):**
- Фронт дочернего узла инициирует запрос INT-0 (текущий счётчик или агрегаты)
- Фундамент-бэк отдаёт 2xx с данными (поле `data_exists`, `source_available`, значение)
- Фронт переводит ответ в одно из именованных состояний (см. ниже)
- Фронт отображает значение или ошибку

**Исключения:**
- Источник активности недоступен (`source_available=false`) → фронт показывает обозначение неполноты / ошибки; для графика — неполная линия (промежутки с null)
- За период нет данных вообще (`data_exists=false`) → фронт показывает прочерк / «нет данных за этот период»
- Таймаут ≥ 5 секунд → фронт переходит в состояние `error_source`, дает retry (подробнее в §4.3)

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос INT-0 или после инвалидации / refresh | спиннер или скелетон |
| `value` | 2xx, `data_exists=true`, `source_available=true`, и значение > 0 (для счётчика) или точки есть (для графика) | число активных / построенная линия графика |
| `zero` | 2xx, `data_exists=true`, `source_available=true`, и `count=0` или все точки = 0 | «0» (не прочерк) |
| `empty` | 2xx, но `data_exists=false` → нет данных за период | прочерк «—» или «нет данных за выбранный период» |
| `error_source` | 5xx, таймаут 5 секунд, сетевая ошибка, или `source_available=false` | обозначение ошибки: сообщение типа «данные не полные» (для частичной недоступности) или «ошибка загрузки» с кнопкой retry |
| `error_forbidden` | 403 | «вам недоступна эта функция» (у вашей роли нет доступа) |

### 4.3.1. Loading и таймауты

- **Cold-path (первый запрос):** таймаут 5 секунд; если ответ не пришёл за 5 сек, переходим в `error_source`, показываем ошибку + retry
- **Warm-path (последующие запросы):** таймаут также 5 секунд 🟡 подтверждено аналитиком (одинаковый таймаут для обоих путей)
- **Polling (обновление счётчика):** 🟡 подтверждено аналитиком, синхронно, кэш 30 сек на стороне бэка Арсенала; фронт может переподразумевать интервал автообновления ≈ 30 сек (или с jitter, чтобы не перегружать; это деталь реализации фронта)

### 4.4. Доступ по ролям в UI

- **Администратор:** видит счётчик, график, выгрузку
- **Оператор (и иные):** панель активности скрыта полностью; INT-0 им не доступен (403 на бэке)

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- 🟡 подтверждено аналитиком: **синхронно** (блокирующий вызов, не событие)
- 🟡 подтверждено аналитиком: **кэш 30 секунд** на стороне бэка Арсенала (храниться кэш внутри бэка, не в отдельном кэш-сервисе)
- **Таймаут:** 🟡 подтверждено аналитиком, **5 секунд** на запрос INT-0
- **Нагрузка:** не регламентирована в БТ (обычный объём админ-панели, много запросов не ожидается)

### 5.2. Надёжность/деградация

- 🟡 подтверждено аналитиком: при недоступности источника активности отдаём **признак недоступности** (`source_available=false`), **не выдаём устаревшее значение**. Это критично для правильности отчётности администраторов.
- Если источник был недоступен часть периода (для агрегатов) → `source_available=false`, но точки, которые есть, остаются валидны (фронт может показать неполный график с обозначением пропусков)
- Таймаут или 5xx → фронт видит `error_source`, показывает ошибку

### 5.3. Безопасность/доступ (сводно)

| Кто | Может ли вызвать INT-0? | Механизм проверки |
|-----|------------------------|-------------------|
| Администратор | Да | Проверка роли на бэке Арсенала (HTTP 200) |
| Оператор / прочие роли | Нет | Проверка роли на бэке Арсенала (HTTP 403) |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 подтверждено аналитиком: **Фундамент #0 (бэк Арсенала с контрактом INT-0) выкатывается раньше всех дочерних узлов** (счётчика, графика, выгрузки). Дети полагаются на стабильный контракт; контракт должен быть готов и работать перед началом работ на детях. После выката фундамента все три дочерних узла могут деплоиться независимо или параллельно.

### 6.2. Обратная совместимость

🟡 подтверждено аналитиком: это новый контракт (никаких существующих потребителей INT-0 нет на момент создания фундамента). Обратная совместимость не применяется.

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком: **фиче-флагов нет**. Фундамент и дети релизятся атомарно (в смысле: как только фундамент готов, дети могут включаться). Никаких градированных включений.

### 6.4. План отката

**Откат только бэка (#0):** если INT-0 контракт на бэке Арсенала обнаружит баг и его откатывают, дети (фронты) получат 5xx; их state переходит в `error_source`, они показывают ошибку. Синхронное откатывание фронтов не требуется (они просто перестанут видеть данные до следующего обновления INT-0). Однако если это критичная ошибка данных (например, неправильные числа), лучше откатить фронты одновременно, чтобы не возбудить недоверие администраторов.

**Откат только детей (фронта):** Арсенал-бэк продолжит отдавать INT-0, но если фронты откатываются, они перестанут его вызывать. Синхронности не требуется; дети независимы друг от друга.

**Откат DDL:** не применимо (никаких новых таблиц).

### 6.5. Преднастройка до релиза (чек-лист)

- [x] Роли в security-сервисе: роль **Администратор** должна быть известна сервису аутентификации и проверяться на бэке Арсенала
- [N/A] DDL-миграция: не применимо (агрегаты считаются на лету)
- [x] Конфиги по окружениям: кэш-TTL 30 секунд настроен в конфиге Арсенала для dev/staging/prod (если отличается)
- [x] Сервисные аккаунты: не применимо (INT-0 вызывается от имени пользователя, а не от сервисного аккаунта)
- [N/A] Фиче-флаги: не применимо (фундамент выкатывается без флагов)
- [x] Алерты: настроить алерты на:
  - 5xx ошибки при вызове INT-0 (источник активности недоступен)
  - Таймауты ≥ 5 сек при вызове INT-0 (перегруз или зависание)
  - Частоту запросов INT-0 (контроль нагрузки)

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 (type=current) | Дано открытую админку администратора, когда страница загрузилась, тогда INT-0 возвращает `data_exists=true, source_available=true`, фронт показывает `value` состояние и число активных пользователей |
| FR-2 | INT-0 (type=current) + polling | Дано счётчик активных в шапке, когда число активных изменилось и прошли ~30 сек (интервал кэша), тогда фронт перезапрашивает INT-0, получает обновлённое значение, переходит в `value`, счётчик обновляется без перезагрузки |
| FR-3 | INT-0 (type=aggregate) | Дано счётчик в шапке, когда администратор кликает по нему, тогда фронт вызывает INT-0 с `type=aggregate` для периода по умолчанию (напр. день), получает points с линией активности; модалка открывается и показывает график |
| FR-4 | INT-0 (type=aggregate, разные period_type) | Дано открытую модалку с графиком, когда администратор выбирает другой период (час / день / неделя), тогда фронт вызывает INT-0 с новыми start_time/end_time и period_type, получает обновленные points, график перестраивается |
