## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 **BE-only.** Узел-фундамент #0 предоставляет контракт данных активности пользователей, который потребляют несколько детских фронтов (задачи внутри эпика ARS-100). Контракт описывает две взаимодействия: текущее число активных пользователей и агрегированная активность за выбранный период (час / день / неделя).

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend («Арсенал» BE) | Владелец; собирает данные активности и отдаёт контракт #0 | Team Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 обслуживает функциональные требования FR-1 через FR-5 эпика ARS-100, предоставляя единый договор о форме данных активности, который потребляют детские фронты счётчика, графика и выгрузки сводки.

## 2. Взаимодействия (ядро)
Два взаимодействия образуют контракт данных активности, которые детские фронты используют независимо. Оба служат для заполнения дисплея счётчика и модали с графиком.

### INT-0.1. Получение текущего числа активных пользователей — 🟢
- **Граница/направление:** Arsenal Backend → детские фронты (admin panel)
- **Триггер:** Загрузка страницы админки; периодический опрос детским фронтом
- **Контракт (запрос):** GET `/api/v1/activity/current` (концептуально)
  - Параметры: нет
  - Тело: отсутствует
- **Контракт (ответ):** 
  - `activeCount`: целое число ≥ 0 (или null, если недоступно или нет данных)
  - `unavailable`: boolean; `true` → источник недоступен, показать «—»
  - `noDataForPeriod`: не применимо (это текущее значение, всегда есть или нет источника)
- **Пример запроса:** 
  ```
  GET /api/v1/activity/current
  ```
- **Пример ответа (успех — есть данные):**
  ```json
  {
    "activeCount": 42,
    "unavailable": false
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "activeCount": null,
    "unavailable": true
  }
  ```
- **Ошибки:** 
  | Код | Тело | Когда | Состояние UI |
  |-----|------|-------|-------------|
  | 200 | `unavailable: false` + `activeCount` | Данные доступны | Показать значение или 0 |
  | 200 | `unavailable: true` | Источник недоступен | Показать «—» / плейсхолдер ошибки |
  | 403 Forbidden | `{ "error": "forbidden" }` | Роль не «Администратор» | Скрыть панель активности |
  | 5xx, таймаут (5s) | – | Внутренняя ошибка или сеть | Обработать как `unavailable: true` |
  
- **Состояния UI по ответу:** 
  - **value** → activeCount ≠ null и unavailable = false: показать число
  - **zero** → activeCount = 0 и unavailable = false: показать «0»
  - **empty** → activeCount = null или нет данных: показать «—»
  - **error_source** → unavailable = true: показать иконку ошибки + сообщение о недоступности
  - **error_forbidden** → 403: не показывать панель активности
  
- **Авторизация:** 
  - 🟡 Доступен только роли «Администратор». Проверка на стороне Arsenal Backend. Дочерний фронт получает 403 Forbidden, если роль ≠ «Администратор».
  - Негативный случай: оператор попробует загрузить страницу → 403 → панель активности скрыта.
  
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (отображение счётчика), FR-2 (автообновление без перезагрузки)

### INT-0.2. Получение агрегированной активности за период — 🟢
- **Граница/направление:** Arsenal Backend → детские фронты (admin panel modal)
- **Триггер:** Открытие модали; смена периода в модали (часовой / дневной / недельный)
- **Контракт (запрос):** GET `/api/v1/activity/aggregates?period={period}&from={from}&to={to}` (концептуально)
  - Параметры запроса:
    - `period`: enum `"hour"` | `"day"` | `"week"` (обязателен; определяет интервал агрегации)
    - `from`: ISO 8601 timestamp (обязателен; начало периода, например `2026-07-26T00:00:00Z`)
    - `to`: ISO 8601 timestamp (обязателен; конец периода)
  - Тело: отсутствует
- **Контракт (ответ):** 
  - `period`: enum `"hour"` | `"day"` | `"week"` (тот же, что передан в запросе)
  - `from`: ISO 8601 timestamp (начало периода)
  - `to`: ISO 8601 timestamp (конец периода)
  - `data`: массив объектов, каждый:
    - `timestamp`: ISO 8601 (начало интервала агрегации; напр. начало часа для `period=hour`)
    - `count`: целое число ≥ 0 (число активных пользователей в этот интервал; может быть 0)
  - `unavailable`: boolean; `true` → источник недоступен
  - `noDataForPeriod`: boolean; `true` → источник доступен, но за этот период данных нет (напр., будущая дата)
- **Пример запроса:** 
  ```
  GET /api/v1/activity/aggregates?period=day&from=2026-07-26T00:00:00Z&to=2026-07-26T23:59:59Z
  ```
- **Пример ответа (успех — есть данные):**
  ```json
  {
    "period": "day",
    "from": "2026-07-26T00:00:00Z",
    "to": "2026-07-26T23:59:59Z",
    "data": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 10 },
      { "timestamp": "2026-07-26T01:00:00Z", "count": 15 },
      { "timestamp": "2026-07-26T02:00:00Z", "count": 8 },
      { "timestamp": "2026-07-26T03:00:00Z", "count": 0 }
    ],
    "unavailable": false,
    "noDataForPeriod": false
  }
  ```
- **Пример ответа (нет данных за период):**
  ```json
  {
    "period": "day",
    "from": "2099-12-31T00:00:00Z",
    "to": "2099-12-31T23:59:59Z",
    "data": [],
    "unavailable": false,
    "noDataForPeriod": true
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "day",
    "from": "2026-07-26T00:00:00Z",
    "to": "2026-07-26T23:59:59Z",
    "data": null,
    "unavailable": true,
    "noDataForPeriod": false
  }
  ```
- **Ошибки:** 
  | Код | Тело | Когда | Состояние UI |
  |-----|------|-------|-------------|
  | 200 | `unavailable: false`, `noDataForPeriod: false`, `data: [...]` | Данные есть | Отобразить график |
  | 200 | `unavailable: false`, `noDataForPeriod: true`, `data: []` | За период данных нет | Показать «Нет данных за выбранный период» |
  | 200 | `unavailable: true` | Источник недоступен | Показать ошибку и retry |
  | 400 Bad Request | `{ "error": "invalid_period" }` или `{ "error": "invalid_dates" }` | Неверные параметры (period ∉ {hour, day, week} или dates некорректны) | Логировать, retry с корректными параметрами |
  | 403 Forbidden | `{ "error": "forbidden" }` | Роль не «Администратор» | Не показывать модаль |
  | 5xx, таймаут (5s) | – | Внутренняя ошибка или сеть | Обработать как `unavailable: true` |
  
- **Состояния UI по ответу:** 
  - **loading** → первый запрос / переключение периода: спиннер
  - **value** → unavailable = false и data.length > 0: отобразить график
  - **empty** → unavailable = false и noDataForPeriod = true: показать «Нет данных за этот период»
  - **zero** → unavailable = false и все count = 0: отобразить график с нулями (не схлопывать с empty)
  - **error_source** → unavailable = true: показать иконку ошибки, попробовать позже, кнопка retry
  - **error_forbidden** → 403: не показывать модаль (как и для INT-0.1)
  
- **Авторизация:** 
  - 🟡 Доступен только роли «Администратор», как INT-0.1. Проверка на стороне Arsenal Backend.
  - Дочерний фронт получает 403 Forbidden, если роль ≠ «Администратор», и не открывает модаль.
  
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3 (открытие модали с графиком), FR-4 (переключение периода), FR-5 (выгрузка сводки использует те же данные)

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI | Взаимодействие |
|-----|---|---|---|---|
| 200 + `unavailable: true` | Явный флаг | Источник недоступен | Показать «—» (INT-0.1) или retry (INT-0.2) | Оба |
| 200 + `noDataForPeriod: true` | Явный флаг + `data: []` | За период нет данных (БД пуста, будущая дата) | Показать «Нет данных за период» | INT-0.2 |
| 403 Forbidden | `{ "error": "forbidden" }` | Роль ≠ «Администратор» | Скрыть панель активности / модаль | Оба |
| 400 Bad Request | `{ "error": "invalid_period" \| "invalid_dates" }` | Параметры вне enum или дата некорректна | Retry с исправленными параметрами (клиент) | INT-0.2 |
| 5xx, таймаут | – | Внутренняя ошибка BE или сеть | error_source (как unavailable) | Оба |

## 3. Backend — ответственность
### 3.1. По сервисам
🟡 **Arsenal Backend** (подтверждено аналитиком):
- Собирает данные активности пользователей самостоятельно (никаких внешних сервисов).
- Реализует INT-0.1 (текущий счётчик активных).
- Реализует INT-0.2 (агрегаты активности за период).
- На обоих эндпоинтах проверяет авторизацию (только роль «Администратор»).
- Кэширует результаты на 30 секунд на своей стороне (TTL 30s) для снижения нагрузки.
- Таймаут ответа: 5 секунд.

### 3.2. Данные и хранение
🟡 **Подтверждено аналитиком:** Новых таблиц не заводим. Агрегаты активности (текущее число и аналитика за период) считаются на лету из существующих данных активности Arsenal Backend.

**Что это означает:**
- Текущее число активных пользователей: вычисляется из живых сессий / состояния пользователей в реальном времени.
- Агрегированная активность за период: считается на основе логов/событий активности, группируется по интервалам (час / день / неделя) в памяти или через быстрый SQL-запрос.
- DDL-миграций: **не требуется**.

### 3.3. Авторизация/доступ на бэке
🟡 **Подтверждено аналитиком:**
- Оба эндпоинта доступны только пользователям с ролью «Администратор».
- Проверка роли выполняется на стороне Arsenal Backend (через встроенный сервис аутентификации / авторизации).
- Ролевая модель соответствует §5.3 БТ эпика: роль «Администратор» → доступ; роль «Оператор» → 403 Forbidden.

## 4. Frontend — ответственность
*(Специфика детских фронтов выходит за рамки узла #0. Детские задачи определяют, как они отображают эти данные (счётчик, график, экспорт). Здесь — только общее описание того, как они потребляют контракт #0.)*

### 4.1. Где и что меняется в UI
Детские фронты интегрируют INT-0.1 и INT-0.2:
- **Счётчик активных в шапке:** вызывает INT-0.1 при загрузке и с интервалом (полинг).
- **Модаль с графиком:** вызывает INT-0.2 при открытии; снова вызывает при смене периода.
- **Выгрузка сводки:** использует данные из INT-0.2 для заполнения файла.

### 4.2. Пользовательские сценарии
*(Опускаются, так как это детализация детских задач, а не #0.)*

### 4.3. Состояния (именованные)
Детский фронт должен различать состояния на основе ответа INT-0.1 и INT-0.2:

| Имя состояния | Условие | Что видит пользователь |
|---|---|---|
| `loading` | Первый запрос / переключение периода | Спиннер / скелетон |
| `value` | 2xx, activeCount ≠ null, unavailable = false (INT-0.1) | Число активных |
| `zero` | 2xx, activeCount = 0, unavailable = false (INT-0.1) | «0» (не «—») |
| `empty` | 2xx, activeCount = null (INT-0.1) или noDataForPeriod = true (INT-0.2) | «—» / «Нет данных за период» |
| `error_source` | unavailable = true (либо 5xx/таймаут) | Иконка ошибки, сообщение, кнопка retry |
| `error_forbidden` | 403 | Панель не показана (роль не Администратор) |

### 4.3.1. Loading и таймауты
- **Cold-path** (первый запрос): таймаут 5 секунд (совпадает с таймаутом бэка). Если не ответил → error_source.
- **Warm-path** (полинг / переключение периода): 5 секунд.
- **Polling** (INT-0.1 счётчик): интервал 30–60 секунд (детская задача конкретизирует; рекомендация: 30 секунд, совпадает с TTL кэша бэка). Jitter: опционально, рекомендуется для распределения нагрузки.

### 4.4. Доступ по ролям в UI
🟡 Подтверждено аналитиком: «Администратор» видит счётчик, модаль и выгрузку; «Оператор» не видит панель активности. Реализуется через 403 Forbidden от INT-0.1 / INT-0.2, которые детский фронт обрабатывает, скрывая UI.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
🟡 **Подтверждено аналитиком:**
- **Синхронность:** Синхронно (не async/event).
- **Кэш:** 30 секунд на стороне Arsenal Backend (TTL = 30s). Детский фронт может дополнительно кэшировать локально (в памяти / IndexedDB) на своё усмотрение.
- **Полинг счётчика (INT-0.1):** Детский фронт периодически опрашивает текущий счётчик; интервал — на усмотрение детской задачи (рекомендация: 30–60 секунд, синхронизированно с TTL кэша).
- **Таймауты:**
  - INT-0.1 (текущее значение): **5 секунд**.
  - INT-0.2 (агрегаты за период): **5 секунд**.
  - Если таймаут → обработать как `unavailable: true` / error_source.
- **Ожидаемая нагрузка:** 
  - Счётчик: частотный полинг (30–60s интервал) × количество открытых админок (дневная нагрузка на операторов).
  - Агрегаты: редкие запросы (открытие модали, смена периода).
  - Вычисление на лету (no table scans для каждого запроса) → приемлемая нагрузка.

### 5.2. Надёжность/деградация
🟡 **Подтверждено аналитиком:**
- При недоступности источника данных активности:
  - INT-0.1 возвращает `unavailable: true` (не выдаёт устаревшее значение).
  - INT-0.2 возвращает `unavailable: true` (не выдаёт старые данные).
- Отдельно различаем:
  - `unavailable: true` — источник упал / недоступен → ошибка источника (error_source).
  - `noDataForPeriod: true` — источник доступен, но за этот конкретный период данных нет → пустое состояние (не ошибка).
- Детский фронт обрабатывает оба случая по-разному (показывает иконку ошибки vs. «Нет данных»).

### 5.3. Безопасность/доступ (сводно)
| Граница | INT | Проверка | Роли с доступом | Роли без доступа | Негативный результат |
|---|---|---|---|---|---|
| Arsenal BE → детский FE | INT-0.1, INT-0.2 | На Arsenal BE | Администратор | Оператор | 403 Forbidden |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟢 Узел-фундамент #0 выкатывается **ПЕРВЫМ**, раньше потребителей (детских фронтов ARS-101, ARS-102, ARS-103 и т.д.). Порядок:
1. Arsenal Backend с реализацией INT-0.1 и INT-0.2.
2. Дочерние фронты (задачи внутри эпика), которые потребляют контракт #0.

Это гарантирует, что при развёртывании детских фронтов контракт уже в production.

### 6.2. Обратная совместимость
🟢 Новое взаимодействие. Обратной совместимости нет. Детские фронты разработаны одновременно с #0, поэтому они ожидают этого контракта.

### 6.3. Фиче-флаги
🟡 Подтверждено аналитиком: **Фиче-флагов нет.** Релизим атомарно: #0 выкатывается в production, и детские фронты начинают использовать его эндпоинты.

### 6.4. План отката
- **Откат только BE (#0 откатывается, FE остаётся новой версией):**
  - Детский FE получит 5xx / таймауты от INT-0.1 и INT-0.2.
  - Должен обработать как error_source и показать сообщение об ошибке.
  - Требуется **синхронный откат FE** (иначе панель будет неработающей).
  - Рекомендация: откатывать FE и BE одновременно или откатить FE сразу при проблеме BE.

- **Откат только FE (FE откатывается, BE остаётся):**
  - Не применимо (FE новый, нечего откатывать).

- **Откат DDL:**
  - Не применимо (новых таблиц нет, миграций нет).

### 6.5. Преднастройка до релиза
- [ ] Роли в security-сервисе: убедиться, что роль «Администратор» существует и различается от «Оператор» (вероятно, уже есть в Arsenal).
- [ ] DDL-миграция: не требуется (агрегаты считаются на лету).
- [ ] Конфиги по окружениям (dev/staging/prod): параметры кэша (TTL = 30s) и таймаута (5s) — константы в коде, или конфиги если переменные по окружению.
- [ ] Сервисные аккаунты: не требуется (это внутренний контракт Arsenal).
- [ ] Фиче-флаги: не требуется (релизим без флагов).
- [ ] Алерты/мониторинг: рекомендуется отслеживать 5xx ошибки на INT-0.1 и INT-0.2; таймауты; посчитать latency агрегирования для периода (> 5s = проблема).
