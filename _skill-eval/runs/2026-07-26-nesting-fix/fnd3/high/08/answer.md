# Техническая спецификация — узел-фундамент #0

Спецификация фундамента для эпика ARS-100 завершена.

## Статус

**Готово к разработке.** Все технические решения приняты, контракт спроектирован, нет открытых пунктов.

## Основное содержание

**Узел #0 предоставляет единственное взаимодействие INT-0:** Backend "Арсенал" выдаёт контракт данных активности пользователей (GET `/admin/api/activity-data`) с параметром `period` (hour/day/week). Ответ включает:
- `current`: текущее число активных пользователей
- `aggregates`: агрегированная активность за выбранный период (массив {time, count})
- `hasDataForPeriod`: есть ли данные за период
- `isSourceAvailable`: доступен ли источник данных (ключевой флаг для различения ошибок от пустого периода)

Контракт спроектирован полностью с JSON-примерами для трёх случаев (успех, пусто за период, источник недоступен). Авторизация: только роль Администратор, проверка на бэке. Ошибки: 403 (forbidden), 500/504 (source error). Синхронный ответ, кэш 30s на бэке, таймаут 5s.

## Ключевые решения (от аналитика)

1. **Тип и стороны:** BE-only, фундамент #0 отдаёт контракт для фронтенд-детей
2. **Владение:** Backend "Арсенал" собирает активность сам, чужих сервисов не привлекаем
3. **Ошибки/недоступность:** флаг `isSourceAvailable` отличает source-error от empty-period; не выдавать стаое значение
4. **Авторизация:** Администратор only, проверка на бэке
5. **Данные:** агрегаты на лету, новых таблиц нет
6. **Sync/perf:** синхронно, кэш 30s, таймаут 5s
7. **Rollout:** фундамент выкатывается первым; фиче-флагов нет
8. **Трассировка:** FR-1..FR-5 эпика

## Трассировка к бизнес-требованиям

- **FR-1** (счётчик активных в шапке) → INT-0 текущий count
- **FR-2** (обновление без перезагрузки) → polling INT-0 каждые ~30s
- **FR-3** (открытие модалки) → INT-0 за period=day
- **FR-4** (переключение периода) → INT-0 с новым period
- **FR-5** (выгрузка сводки) → данные из INT-0, экспорт в файл
