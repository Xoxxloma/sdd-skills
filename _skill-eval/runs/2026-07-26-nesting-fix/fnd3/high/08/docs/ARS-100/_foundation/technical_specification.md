## 1. Обзор изменения
### 1.1. Тип и стороны
**BE-only.** Узел-фундамент #0 предоставляет Backend API контракт для получения данных активности пользователей. Потребители контракта — фронтенд-приложения дочерних узлов (FR-1 счётчик, FR-3..FR-5 модалка с графиком). Backend "Арсенал" отдаёт контракт на границе FE↔BE для детей.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Backend "Арсенал" | Собирает и агрегирует данные активности, отдаёт контракт | Команда Арсенал-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел #0 реализует фундамент для FR-1..FR-5 эпика: предоставляет синхронный API с текущим числом активных пользователей и агрегированной активностью за период (час/день/неделя). На основе этого контракта дочерние узлы строят счётчик в шапке, модалку с графиком и выгрузку сводки.

## 2. Взаимодействия (ядро)

### INT-0. Данные активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Backend "Арсенал" → Frontend (дочерние приложения)
- **Триггер:** Периодический запрос при загрузке страницы, открытии модалки, переключении периода, автообновлении счётчика
- **Контракт (запрос):** 
  - Метод: GET
  - Путь (концептуально): `/admin/api/activity-data`
  - Query параметры: `period` (hour | day | week), по умолчанию day
  - Заголовки: стандартные (включая Authorization)
- **Контракт (ответ):**
  - `current` (integer | null): число активных пользователей на текущий момент. null если источник недоступен.
  - `period` (string: hour | day | week): запрошенный период
  - `aggregates` (array of {time: ISO8601 string, count: integer}): агрегированная активность по периоду. Пусто, если данных нет или источник недоступен.
    - Для period=hour: 60 точек (минуты) за последний час
    - Для period=day: 24 точки (часы) за последние сутки
    - Для period=week: 7 точек (дни) за последние 7 дней
  - `hasDataForPeriod` (boolean): true если период содержит хотя бы один записанный результат активности; false если период пуст (нет записей за период) или источник недоступен
  - `isSourceAvailable` (boolean): true если источник активности доступен и данные свежие; false если источник был недоступен на момент запроса
- **Пример запроса:**
  ```

  Authorization: Bearer <token>
  ```

## 3. Backend — ответственность
### 3.1. По сервисам
**Backend "Арсенал" (единственный участник):** 
- 🟡 Реализует INT-0 контракт: отдаёт текущее число активных пользователей и агрегированную активность за выбранный период (подтверждено аналитиком, не по коду; валидировать при интеграции)
- 🟢 Собирает и агрегирует данные активности на лету (нет новых таблиц, реализуется на основе существующих источников)
- 🟢 Возвращает контракт с явными флагами isSourceAvailable и hasDataForPeriod для различения состояний (доступность источника vs. отсутствие данных за период)
- 🟡 Проверяет авторизацию (роль Администратор) на бэке перед возвратом данных (подтверждено аналитиком)
- 🟢 Реализует таймаут 5с при запросе к источнику; при timeout возвращает 504 или 200 с isSourceAvailable=false (не устаревшее значение из кэша)

### 3.2. Данные и хранение
🟢 **Новых таблиц не заводится.** Агрегаты активности считаются на лету из существующих источников Арсенала (реализуется на уровне логики запроса, без DDL). 

🟢 **Кэш:** 30 секунд на стороне бэка Арсенала для результатов конкретного периода (hour/day/week). При hit кэша возвращается cached-ответ без обращения к источнику. При miss или expiry — свежий запрос к источнику.

🟢 **Индексы:** не применимо (агрегирование на лету, новых таблиц нет).

### 3.3. Авторизация/доступ на бэке
🟡 **Проверка роли на бэке Арсенала:** только Администраторы имеют доступ к INT-0 контракту. Роль проверяется middleware (или auth-service интеграция) перед возвратом данных — подтверждено аналитиком, не по коду.

🟢 **Негативный случай:** Оператор, пользователь без роли или неавторизованный запрос → HTTP 403 Forbidden с сообщением об ошибке.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Фронтенд дочерних узлов (FR-1..FR-5):
- FR-1/FR-2: Счётчик активных пользователей в шапке админки (вызывает INT-0 при загрузке и затем периодически)
- FR-3/FR-4: Модальное окно с графиком активности за выбранный период (вызывает INT-0 при открытии и переключении периода)
- FR-5: Кнопка выгрузки сводки (получает данные из INT-0, экспортирует в файл)

### 4.2. Пользовательские сценарии
Описаны в эпик-БТ (FR-1..FR-5 и их критерии приёмки). Здесь фронт реализует эти сценарии, используя INT-0 контракт:
- **Основной поток:** загрузка страницы → запрос INT-0 → отображение счётчика → периодическое обновление (без перезагрузки) → клик на счётчик → запрос INT-0 за выбранный период → отображение графика → выгрузка сводки
- **Ветвления и исключения:** см. состояния UI (§4.3)

### 4.3. Состояния (именованные — обязательно, если есть FE)
🟢 Фронт дочерних узлов использует следующие именованные состояния для отображения счётчика и графика активности:

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос INT-0 / после инвалидации | спиннер или скелетон вместо счётчика |
| `value` | 2xx, current > 0, hasDataForPeriod=true, isSourceAvailable=true | счётчик: число активных, график: данные за период |
| `zero` | 2xx, current = 0, hasDataForPeriod=true, isSourceAvailable=true | счётчик: «0» (не прочерк), график: 0 для всех точек |
| `empty` | 2xx, current ≠ null, hasDataForPeriod=false, isSourceAvailable=true | счётчик: текущее число (если есть), график: «—» / пустой (нет данных за период) |
| `error_source` | 5xx / 504 / таймаут / network error / isSourceAvailable=false | счётчик: «—», график: «—» с кнопкой retry |
| `error_forbidden` | 403 Forbidden | счётчик и график: «нет доступа» (UI может быть полностью скрыта для неадминистраторов) |

**Различие empty vs error_source (критическое):**
- `empty`: источник работает, но данные за период не записаны (валидное состояние, нет retry)
- `error_source`: источник недоступен (ошибка, нужен retry)

### 4.3.1. Loading и таймауты
- **Cold-path таймаут** (первый запрос, нет закэшированных данных): ~ 2-3s на фронте (user-facing timeout для показа скелетона вместо спиннера, чтобы не зависнуть)
- **Warm-path таймаут** (последующие запросы, есть кэш на фронте): ~ 1-2s (быстрее, так как кэш есть и можно show-old-data-while-fetching)
- **Polling** (автообновление счётчика): 
  - Интервал: ~30s (с tolerances до ±5s jitter для разброса нагрузки)
  - Jitter: да (чтобы не создавать spike запросов)
  - Стратегия: exponential backoff при ошибках (первый retry 2s, затем 4s, 8s, макс 60s)
- **При таймауте / 5xx / сеть:** показать ошибку, button retry (см. error_source в §4.3)

### 4.4. Доступ по ролям в UI
🟡 Панель активности (счётчик + модалка) отображается только для роли **Администратор** — подтверждено аналитиком. Для роли Оператор счётчик и модалка скрыты (FE может conditionally render на основе информации о роли пользователя из auth-контекста).

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- **Синхронность:** 🟡 Синхронный ответ (RPC / HTTP GET, не async/event-based) — подтверждено аналитиком
- **Кэш:** 🟡 30 секунд на стороне бэка Арсенала (подтверждено аналитиком). Кэш-ключ включает период (hour/day/week), так что разные периоды кэшируются отдельно.
- **Таймаут:** 🟡 5 секунд максимум для запроса к источнику данных активности (подтверждено аналитиком). Если источник не ответит за 5с, вернуть 504 или 200 с isSourceAvailable=false.
- **Частота обновления:** 
  - Автообновление счётчика на фронте: ~30s (см. 4.3.1 polling)
  - Минимальное обновление графика: по клику пользователя на переключение периода (manuel refresh)
- **Ожидаемая нагрузка:** не специфицирована в БТ, фундамент спроектирован для масштабирования (кэш + синхронность без очередей)

### 5.2. Надёжность/деградация
- **При недоступности источника:** возвращается 503 Service Unavailable или 200 с isSourceAvailable=false (не выдавать устаревшее значение из кэша). Пользователь видит ошибку с retry.
- **При пустом периоде:** возвращается 200 с hasDataForPeriod=false и пустым aggregates-ом (не ошибка, валидное состояние).
- **При таймауте (5s):** возвращается 504 Gateway Timeout или 200 с isSourceAvailable=false.

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Кто не может | Проверка |
|---------|-----------|-------------|----------|
| INT-0: GET /admin/api/activity-data | Администратор | Оператор, неавторизованный | Role-based на бэке Арсенала (middleware / auth-service) → 403 если не Администратор |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 **Порядок:** Узел-фундамент #0 выкатывается **ПЕРВЫМ**, раньше всех дочерних узлов (FR-1..FR-5 приложений) — подтверждено аналитиком. Дети опираются на INT-0 контракт, поэтому бэк должен быть готов до деплоя фе дочерних узлов.

### 6.2. Обратная совместимость
🟢 Контракт INT-0 — новый (дизайн с нуля), обратная совместимость не применима (нет текущих потребителей).

### 6.3. Фиче-флаги
🟡 **Релизим атомарно без фиче-флагов** (подтверждено аналитиком). Узел #0 — фундамент, потребители дети контролируют свои feature flags для включения/отключения функции на их стороне.

### 6.4. План отката (не применимо: узел #0 чистая реализация, не имеет user-facing UI; откат BE контракта контролируется потребителями детей)

### 6.5. Преднастройка до релиза (чек-лист)
- [x] **Роли в security-сервисе:** Роль Администратор должна быть заведена (обычно есть); проверить доступ — подтверждено аналитиком
- [x] **DDL-миграция:** не требуется (новых таблиц нет, агрегирование на лету)
- [x] **Конфиги по окружениям:** кэш TTL (30s), таймаут источника (5s) — вынести в конфиг Арсенала (dev/staging/prod)
- [x] **Сервисные аккаунты:** не требуется (вызов внутри одного сервиса)
- [x] **Фиче-флаги:** не требуется на уровне #0 (потребители дети контролируют)
- [x] **Алерты/мониторинг:** 
  - Алерт на 503 / 504 (источник недоступен)
  - Метрика: время ответа INT-0 (should be < 1s для cached, < 5s для fresh)
  - Метрика: hit rate кэша (ожидается high, ~90%+)
