## 1. Обзор изменения

### 1.1. Тип и стороны

**BE-only.** Узел-фундамент #0 — это чистая реализация, без собственных бизнес-требований. Он отдаёт канонический контракт данных активности пользователей (текущее число активных и агрегированные метрики за период), который потребляют несколько фронтальных элементов эпика ARS-100 (счётчик в шапке, модальное окно с графиком, выгрузка сводки).

Фронты реализуют отдельно (каждый со своим БТ и спекой); #0 обеспечивает им единую, согласованную границу данных.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | отдаёт контракт данных активности | Команда Arsenal-Core | 🟡 подтвержено аналитиком |

### 1.3. Связь с бизнес-требованиями

Узел-фундамент #0 реализует общий источник данных для FR-1 (счётчик активных), FR-2 (обновление без перезагрузки), FR-3 (модаль с графиком), FR-4 (переключение периода) и FR-5 (выгрузка сводки). Каждый фронтальный элемент обращается к одному и тому же контракту, гарантируя консистентность показываемых чисел.

## 2. Взаимодействия (ядро)

### INT-0. Запрос данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Любой фронт (счётчик в шапке, модальное окно, выгрузка) → Backend Arsenal
- **Триггер:** 
  - Счётчик в шапке инициирует запрос при загрузке страницы и периодически (каждые 30 секунд, кэш на стороне бэка).
  - Модаль с графиком запрашивает агрегаты за выбранный период (час / день / неделя) при открытии и смене периода.
  - Выгрузка запрашивает полную сводку за выбранный период.
- **Контракт (запрос):** HTTP GET, путь (концептуально): `/api/arsenal/activity-metrics` или `/arsenal/activity`
  - Параметры запроса:
    - `period_start` (ISO8601 timestamp) — дата/время начала периода; для текущей активности — опционально
    - `period_end` (ISO8601 timestamp) — дата/время конца периода; для текущей активности — опционально
    - `granularity` (enum: `current` | `hourly` | `daily` | `weekly`) — что вернуть: текущее значение, почасовые агрегаты, дневные или недельные
  - Заголовки: стандартные, с авторизацией (см. ниже)
  
- **Контракт (ответ):** JSON объект с двумя вариантами в зависимости от `granularity`:
  
  **Вариант A: `granularity = current`** (для счётчика в шапке)
  ```json
  {
    "data": {
      "active_users_count": 42,
      "timestamp": "2026-07-26T14:30:00Z"
    },
    "status": "available"
  }
  ```
  
  **Вариант B: `granularity = hourly | daily | weekly`** (для графика и выгрузки)
  ```json
  {
    "data": {
      "period_start": "2026-07-26T00:00:00Z",
      "period_end": "2026-07-27T00:00:00Z",
      "granularity": "hourly",
      "points": [
        {
          "timestamp": "2026-07-26T00:00:00Z",
          "active_users_count": 10
        },
        {
          "timestamp": "2026-07-26T01:00:00Z",
          "active_users_count": 15
        },
        {
          "timestamp": "2026-07-26T02:00:00Z",
          "active_users_count": 8
        }
      ],
      "summary": {
        "min": 8,
        "max": 15,
        "average": 11.0,
        "total_periods": 24
      }
    },
    "status": "available"
  }
  ```
  
  **Поля общего контракта:**
  - `data` (object | null) — данные активности; `null` если `status !== "available"`
  - `status` (enum) — статус источника данных:
    - `"available"` — данные получены успешно
    - `"unavailable"` — источник недоступен (таймаут, сеть, 5xx); значения в `data` нет
    - `"no_data"` — период валиден, но данных в источнике за этот период нет (фронт отображает пусто, не ошибку)
  - `timestamp` (ISO8601, только для `current`) — время составления ответа
  - `period_start`, `period_end`, `granularity`, `points`, `summary` (только для агрегатов)
  
  **Семантика null:**
  - `data === null` → источник недоступен или период без данных (см. `status`).
  - `active_users_count` — всегда число ≥ 0 (не null); если нет активных пользователей — 0, не null.

- **Пример запроса:**
  ```
  GET /api/arsenal/activity-metrics?granularity=current
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех, текущая активность):**
  ```json
  {
    "data": {
      "active_users_count": 42,
      "timestamp": "2026-07-26T14:30:00Z"
    },
    "status": "available"
  }
  ```

- **Пример ответа (успех, недельные агрегаты):**
  ```json
  {
    "data": {
      "period_start": "2026-07-20T00:00:00Z",
      "period_end": "2026-07-27T00:00:00Z",
      "granularity": "weekly",
      "points": [
        { "timestamp": "2026-07-20T00:00:00Z", "active_users_count": 120 },
        { "timestamp": "2026-07-21T00:00:00Z", "active_users_count": 135 },
        { "timestamp": "2026-07-22T00:00:00Z", "active_users_count": 128 },
        { "timestamp": "2026-07-23T00:00:00Z", "active_users_count": 110 },
        { "timestamp": "2026-07-24T00:00:00Z", "active_users_count": 95 },
        { "timestamp": "2026-07-25T00:00:00Z", "active_users_count": 105 },
        { "timestamp": "2026-07-26T00:00:00Z", "active_users_count": 142 }
      ],
      "summary": {
        "min": 95,
        "max": 142,
        "average": 119.3,
        "total_periods": 7
      }
    },
    "status": "available"
  }
  ```

- **Пример ответа (недоступность источника):**
  ```json
  {
    "data": null,
    "status": "unavailable"
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "data": null,
    "status": "no_data"
  }
  ```

- **Ошибки:** см. «Каталог ошибок» ниже.

- **Состояния UI по ответу (для фронтов-потребителей):**
  - `status === "available"` → значение / график (фронт проверяет `data !== null`, затем `active_users_count`)
  - `active_users_count === 0` → состояние `zero` (показать «0»)
  - `status === "no_data"` → состояние `empty` (показать «—» / «нет данных»)
  - `status === "unavailable"` → состояние `error_source` (показать сообщение об ошибке + кнопка retry)
  - загрузка (первый запрос, ожидание ответа) → состояние `loading` (спиннер)

- **Авторизация:** 
  - Контракт доступен **ТОЛЬКО** роли **«Администратор»** (проверка на стороне Backend Arsenal).
  - При запросе от другой роли или неавторизованного пользователя — ответ 403 Forbidden (см. ошибки).
  - Авторизация проверяется на входе эндпоинта (до попытки получить данные).

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (все требования опираются на этот контракт)

### Каталог ошибок

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 OK | `{ "data": {...}, "status": "available" }` | Успешный запрос, данные получены | `value` / `zero` / `loading` → resolved |
| 200 OK | `{ "data": null, "status": "unavailable" }` | Источник данных недоступен (таймаут, 5xx, сеть) | `error_source` |
| 200 OK | `{ "data": null, "status": "no_data" }` | Период валиден, но данных нет | `empty` |
| 400 Bad Request | `{ "error": "invalid_period" }` | `period_start` > `period_end` или некорректный формат ISO8601 | `error_source` |
| 403 Forbidden | `{ "error": "insufficient_permissions", "required_role": "Administrator" }` | Запрашивающий пользователь — не администратор | `error_forbidden` |
| 401 Unauthorized | `{ "error": "missing_or_invalid_token" }` | Отсутствует авторизационный токен или он невалиден | `error_forbidden` |
| 500 Internal Server Error | `{ "error": "internal_error" }` | Ошибка на стороне Arsenal Backend (не ошибка источника, а сбой в обработке) | `error_source` |
| 504 Gateway Timeout | `{ "error": "request_timeout" }` | Запрос превысил таймаут 5 секунд | `error_source` |

## 3. Backend — ответственность

### 3.1. По сервисам

**Backend Arsenal** реализует эндпоинт INT-0:
- Принимает параметры `granularity`, `period_start`, `period_end`.
- Проверяет авторизацию: только роль «Администратор» имеет доступ.
- Опрашивает источник данных активности (см. 3.2).
- **Вычисляет агрегаты на лету** — не создаёт новые таблицы хранения. При запросе агрегатов (granularity = hourly/daily/weekly) получает raw события/логи активности из источника и группирует на лету.
- Отвечает с указанием статуса (`available` / `unavailable` / `no_data`).
- Кэширует ответ на 30 секунд на своей стороне (для холодного пути).
- Соблюдает таймаут 5 секунд на весь запрос (включая опрос источника).

### 3.2. Данные и хранение

🟡 **Подтверждено аналитиком:** Данные активности пользователей собирает сам Backend Arsenal (не привлекаются внешние сервисы). Источник существует.

🟡 **Подтверждено аналитиком:** Новых таблиц/сущностей для фундамента #0 не заводится. Агрегаты вычисляются на лету из существующих логов/событий активности.

Индексы/оптимизация: предполагается, что источник активности уже оптимизирован для типовых запросов по временному диапазону. Если не оптимизирован — рекомендуется добавить индекс по полю timestamp при интеграции (деталь реализации, не блокирует спеку).

### 3.3. Авторизация/доступ на бэке

- Эндпоинт INT-0 проверяет роль запрашивающего на входе (до обращения к источнику).
- Только пользователи с ролью «Администратор» получают доступ.
- Ответ 403 Forbidden для других ролей (см. каталог ошибок).

## 4. Frontend — ответственность

Не применимо для узла-фундамента #0 (BE-only, контракт потребляется фронтами детских задач).

Каждый фронтальный элемент эпика (счётчик, модаль, выгрузка) наследует контракт INT-0 и реализует свою часть логики отображения и взаимодействия в отдельной спеке (собственное БТ, собственная тех.спека).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

🟡 **Подтверждено аналитиком:**
- **Синхронность:** запрос — синхронный (блокирующий), нет async/event-based альтернативы.
- **Кэш:** 30 секунд на стороне Backend Arsenal. При холодном пути (первый запрос счётчика после загрузки страницы) фронт ждёт вычисления; при тёплом пути (последующие запросы) получает закэшированный ответ (при условии, что прошло < 30 сек).
- **Таймаут:** 5 секунд на весь запрос (от приёма до ответа). Если источник откликается дольше — возвращается `status: "unavailable"`, не ошибка 5xx.
- **Частота обновления счётчика:** фронт может запрашивать каждые N секунд (точное N задаёт фронтовая спека); бэк кэширует на 30 сек, т.е. реально обновления не чаще чем раз в 30 сек.

### 5.2. Надёжность/деградация

🟡 **Подтверждено аналитиком:**
- При недоступности источника данных активности — Backend Arsenal **возвращает флаг `status: "unavailable"`**, не отправляет устаревшее значение.
- Фронт отличает `unavailable` (ошибка источника, показать retry) от `no_data` (период валиден, нет данных — показать «—»).
- Сам фронт отвечает за UX обработки этих состояний.

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Чего не может |
|---------|-----------|--------------|
| INT-0 (любое обращение) | Администратор | Оператор, гость, неавторизованный → 403 |
| Данные в ответе | Администратор видит точные числа активности | — |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟡 **Подтверждено аналитиком:** Узел-фундамент #0 деплоится **РАНЬШЕ** всех фронтальных потребителей (счётчик в шапке, модаль, выгрузка). Новый контракт INT-0 должен быть доступен на прде перед выкатом любого фронта, который его потребляет.

### 6.2. Обратная совместимость

Узел-фундамент #0 — новый контракт, не изменяет существующие. Обратная совместимость не применима (это первый выпуск контракта).

### 6.3. Фиче-флаги

🟡 **Подтверждено аналитиком:** Фиче-флаги не используются. Релизим атомарно: #0 выкатывается, контракт становится доступным, дети его сразу потребляют.

### 6.4. План отката

**Откат только BE (фронты остаются старой версией):** Если откатить Backend Arsenal (удалить эндпоинт INT-0), фронты получат 404 → состояние `error_source` → retry. Это допустимо, если откат быстрый. Синхронный откат фронтов не требуется (они уже обработают ошибку).

**Откат только FE:** Не применимо (узел-фундамент BE-only, фронты реализуют отдельно).

**Откат DDL:** Не применимо (новых таблиц нет, только кэш на памяти).

### 6.5. Преднастройка до релиза

- [x] Роли в security-сервисе — роль «Администратор» должна быть определена в системе авторизации и назначена пользователям-администраторам.
- [x] DDL-миграция — не требуется (новых таблиц нет).
- [x] Конфиги по окружениям — таймаут 5 сек и TTL кэша 30 сек могут быть вынесены в конфиг (dev/staging/prod); значения согласовать перед релизом.
- [x] Сервисные аккаунты — не требуется (контракт потребляют фронты того же приложения, общая авторизация).
- [x] Фиче-флаги — не требуются.
- [x] Алерты/мониторинг — рекомендуется мониторить:
  - Частоту ошибок 5xx на эндпоинте INT-0.
  - Частоту таймаутов (504).
  - Время отклика источника активности (предупреждение, если близко к 5 сек).

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие | Тест-кейс (Дано–Когда–Тогда) |
|----------|---------------|------------------------------|
| FR-1     | INT-0 (granularity=current) | Дано открытую админку, когда страница загрузилась, тогда бэк возвращает текущее число активных в формате `{ "data": { "active_users_count": N }, "status": "available" }` |
| FR-2     | INT-0 (granularity=current, кэш 30с) | Дано открытую админку, когда число активных изменилось, тогда при следующем запросе (через < 30 сек) значение обновляется |

| FR-4     | INT-0 (переключение granularity/period) | Дано открытую модаль, когда администратор выбирает другой период, тогда бэк вычисляет и возвращает агрегаты для нового периода |
| FR-5     | INT-0 (granularity=hourly/daily/weekly) | Дано открытую модаль с периодом, когда администратор запрашивает выгрузку, тогда бэк предоставляет данные (полную сводку за период) в формате контракта |
