## 1. Обзор изменения

### 1.1. Тип и стороны
**🟢 BE-only.** Фундамент #0 — новый сервисный контракт, выход бэка «Арсенала» — отдаёт данные активности пользователей. Потребители — фронты детских узлов эпика (счётчик в шапке, граф активности, выгрузка сводки). Новых взаимодействий между сервисами нет; #0 обслуживает уже существующий узел «Арсенал».

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Бэк «Арсенала» | Реализует контракт активности; отдаёт текущее число и агрегаты | Arsenal-Core | 🟢 новое взаимодействие |

### 1.3. Связь с бизнес-требованиями
Фундамент обслуживает общую часть для FR-1..FR-5 эпика: предоставляет данные о текущей активности и историческую активность за выбранный период. Все три фронтовых элемента (счётчик, граф, выгрузка) опираются на этот контракт и не требуют иных источников данных.

## 2. Взаимодействия (ядро)

### INT-0. Запрос данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Фронты детских узлов (FR-1, FR-2, FR-3, FR-4, FR-5) → Бэк «Арсенала»
- **Триггер:** Загрузка админки (текущее число); открытие модалки (агрегаты за период); смена периода в модалке; инициация выгрузки сводки.
- **Контракт (запрос):**
  - **Метод/путь:** `GET /api/admin/activity-stats` (концептуально, стеко-агностично)
  - **Параметры запроса:**
    - `period` (обязателен): `"current" | "hour" | "day" | "week"` — тип периода
    - `startTime` (строка ISO8601, опционален для `period: "current"`): начало периода
    - `endTime` (строка ISO8601, опционален для `period: "current"`): конец периода
    - `granularity` (опционален, по умолчанию соответствует периоду): `"minute" | "hour" | "day"` — зернистость агрегатов

- **Контракт (ответ):**
  - `currentCount` (число | null): текущее число активных пользователей. `null` — если источник недоступен.
  - `aggregates` (массив объектов | null | []): агрегированная активность за период. Пустой массив — нет данных за этот период; `null` — источник недоступен.
    - Каждый элемент: `{ "timestamp": ISO8601, "count": число ≥ 0 }`
  - `isAvailable` (boolean): `true` — источник данных активности доступен; `false` — недоступен (сетевая ошибка, таймаут, зависимость упала).
  - `hasData` (boolean): `true` — есть данные за запрошенный период; `false` — период валиден, но данных нет (напр. выходной день без активности).
  - `period` (объект): информация о запрошенном периоде:
    - `type`: `"current" | "hour" | "day" | "week"`
    - `startTime`: ISO8601 (начало периода; при `type: "current"` — момент последнего обновления счётчика)
    - `endTime`: ISO8601 (конец периода; при `type: "current"` — текущий момент)

- **Пример запроса:** (параметры в URL)
  ```
  GET /api/admin/activity-stats?period=current
  GET /api/admin/activity-stats?period=hour&startTime=2026-07-26T10:00:00Z&endTime=2026-07-26T11:00:00Z&granularity=minute
  GET /api/admin/activity-stats?period=day&startTime=2026-07-26T00:00:00Z&endTime=2026-07-27T00:00:00Z&granularity=hour
  ```

- **Пример ответа (успех, текущий счёт):**
  ```json
  {
    "currentCount": 127,
    "aggregates": null,
    "isAvailable": true,
    "hasData": true,
    "period": {
      "type": "current",
      "startTime": "2026-07-26T18:20:00Z",
      "endTime": "2026-07-26T18:22:37Z"
    }
  }
  ```

- **Пример ответа (успех, агрегаты за день по часам):**
  ```json
  {
    "currentCount": 127,
    "aggregates": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 45 },
      { "timestamp": "2026-07-26T01:00:00Z", "count": 12 },
      { "timestamp": "2026-07-26T02:00:00Z", "count": 8 },
      { "timestamp": "2026-07-26T10:00:00Z", "count": 89 },
      { "timestamp": "2026-07-26T11:00:00Z", "count": 127 }
    ],
    "isAvailable": true,
    "hasData": true,
    "period": {
      "type": "day",
      "startTime": "2026-07-26T00:00:00Z",
      "endTime": "2026-07-27T00:00:00Z"
    }
  }
  ```

- **Пример ответа (источник недоступен — сетевая ошибка, таймаут и т.п.):**
  ```json
  {
    "currentCount": null,
    "aggregates": null,
    "isAvailable": false,
    "hasData": null,
    "period": {
      "type": "current",
      "startTime": "2026-07-26T18:20:00Z",
      "endTime": "2026-07-26T18:22:37Z"
    }
  }
  ```

- **Пример ответа (нет данных за период, но источник доступен):**
  ```json
  {
    "currentCount": 127,
    "aggregates": [],
    "isAvailable": true,
    "hasData": false,
    "period": {
      "type": "day",
      "startTime": "2026-07-25T00:00:00Z",
      "endTime": "2026-07-26T00:00:00Z"
    }
  }
  ```

- **Ошибки:**
  - **401 Unauthorized:** Клиент не аутентифицирован; требуется авторизация.
  - **403 Forbidden:** Клиент аутентифицирован, но роль не «Администратор»; доступ запрещён.
  - **400 Bad Request:** Некорректные параметры запроса (неверный `period`, поврежденный ISO8601 timestamp и т.п.); тело: `{ "error": "invalid_params", "message": "…" }`.
  - **500 Internal Server Error (внутренняя обработка):** Если источник данных активности недоступен, это НЕ 500; вместо этого возвращается 2xx с `isAvailable: false` (см. примеры выше). 500 возвращается только при ошибках самого эндпоинта (багу коде, конфиге и т.п.).

- **Состояния UI по ответу (для детских узлов):**
  - **`loading`** — первый запрос или после инвалидации; показывать спиннер/скелетон.
  - **`value`** — 2xx, `isAvailable: true`, `currentCount !== null` или `aggregates` не пусто; показывать значение/граф.
  - **`zero`** — 2xx, `isAvailable: true`, `currentCount === 0` (валидный ноль); показывать «0» (не «—»).
  - **`empty`** — 2xx, `isAvailable: true`, но `hasData: false` (нет данных за период); показывать «—» / «нет данных».
  - **`error_source`** — 5xx, таймаут (>5s), сетевая ошибка, или 2xx но `isAvailable: false`; показывать: «Источник активности недоступен. Повторить?» + кнопка retry.
  - **`error_forbidden`** — 403; показывать «Нет доступа к данным активности» (не показывать счётчик/модалку/выгрузку).

- **Авторизация:**
  - **Кто вправе:** Только пользователи с ролью «Администратор» (подтверждено аналитиком).
  - **Где проверяется:** На бэке «Арсенала» перед возвратом данных; проверка выполняется в мидлваре или в хендлере эндпоинта.
  - **Негативный случай:** Пользователь с ролью «Оператор» или неавторизованный пользователь получает 403 (или 401 если не авторизован).

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (счётчик активных), FR-2 (обновление без перезагрузки), FR-3 (модалка с графиком), FR-4 (переключение периода), FR-5 (выгрузка сводки)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 | `{ "error": "unauthorized", "message": "Authentication required" }` | Отсутствует токен авторизации | `error_auth` → скрыть панель, перенаправить на логин |
| 403 | `{ "error": "forbidden", "message": "Administrator role required" }` | Роль не «Администратор» | `error_forbidden` → не показывать панель активности |
| 400 | `{ "error": "invalid_params", "message": "Invalid period or timestamp format" }` | Неверные параметры (период, format timestamp) | `error_input` → показать сообщение об ошибке, предложить retry |
| 500 | `{ "error": "internal_error", "message": "…" }` | Ошибка в логике эндпоинта (редко) | `error_server` → показать «Ошибка сервера» + retry |
| Timeout | нет (запрос > 5s) | Источник или сеть медленны/не отвечают | `error_source` → показать «Источник недоступен» |
| Network | (сетевая ошибка) | Нет соединения / DNS / сеть | `error_network` → показать «Нет соединения» + retry |

## 3. Backend — ответственность

### 3.1. По сервисам
**Бэк «Арсенала»:**
- Реализует эндпоинт `GET /api/admin/activity-stats` (INT-0), который отдаёт контракт активности.
- Проверяет авторизацию (только роль «Администратор»); возвращает 403, если нет прав.
- Считает текущее число активных пользователей (по текущему моменту времени).
- Считает агрегаты активности за запрошенный период (час / день / неделя) с указанной зернистостью.
- При недоступности источника (внутренняя ошибка, сетевая, таймаут сервиса-зависимости) возвращает 2xx с `isAvailable: false`, не 5xx.
- Кэширует ответ на 30 секунд со стороны бэка (следующий запрос того же клиента в течение 30с получает кэшированный ответ).
- Таймаут запроса (внутреннего, к источнику данных) — 5 секунд; если превышен, отдаёт `isAvailable: false`.

### 3.2. Данные и хранение
**🟢 Новых таблиц не заводим.** Агрегаты активности рассчитываются на лету из существующих данных источника (подтверждено аналитиком: текущие данные активности уже собирает сервис; #0 только их отдаёт). Миграции не требуются. Расчёт агрегатов за период — встроенная логика эндпоинта (условие по временным меткам и группировка по зернистости).

### 3.3. Авторизация/доступ на бэке
- **Где проверяется:** Перед расчётом и возвратом данных (мидлваре или в хендлере).
- **Как:** По контексту запроса (из токена / сессии) извлекается роль пользователя.
- **Роли:** Только «Администратор» может вызвать эндпоинт.
- **Ответ при отказе:** 403 с сообщением «Administrator role required» (не отдаём данные).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Реализуется ТРИ компонента фронта, каждый консумирует INT-0:
1. **Счётчик в шапке** (FR-1, FR-2) — вызывает INT-0 с `period: "current"` при загрузке и далее с интервалом для live-обновления.
2. **Модальное окно с графиком** (FR-3, FR-4) — вызывает INT-0 с `period: "hour"|"day"|"week"` и параметрами `startTime`/`endTime` по выбору периода.
3. **Кнопка выгрузки сводки** (FR-5) — использует данные из модалки (уже загруженные через INT-0) для генерации файла.

### 4.2. Пользовательские сценарии
1. **[FR-1]** Администратор открывает админку → фронт запрашивает INT-0 с `period: "current"` → получает `currentCount` → показывает число в шапке.
2. **[FR-2]** После загрузки админки фронт периодически (каждые ~30s, но не чаще чем раз в 30s, из-за кэша) запрашивает INT-0 → счётчик обновляется без перезагрузки.
3. **[FR-3]** Администратор кликает на счётчик → открывается модалка → фронт запрашивает INT-0 с `period: "day"` (по умолчанию) → получает `aggregates` → строит граф.
4. **[FR-4]** В модалке администратор выбирает период (час / день / неделя) → фронт пересчитывает `startTime`/`endTime` → запрашивает INT-0 → получает новые `aggregates` → граф перестраивается.
5. **[FR-5]** Администратор нажимает выгрузку в модалке → фронт берёт текущие `aggregates` и информацию о периоде → генерирует CSV/JSON/другой формат → скачивает файл.

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | Первый запрос INT-0 или после инвалидации | Спиннер / скелетон (счётчик / граф) |
| `value` | 2xx, `isAvailable: true`, `currentCount > 0` или `aggregates.length > 0` | Число / граф с данными |
| `zero` | 2xx, `isAvailable: true`, `currentCount === 0` | Число «0» (не прочерк) |
| `empty` | 2xx, `isAvailable: true`, `hasData: false` (нет данных за период) | Прочерк «—» или «нет данных» |
| `error_source` | 2xx но `isAvailable: false`, или 5xx, или таймаут >5s, или сетевая ошибка | Сообщение: «Источник активности недоступен. Повторить?» + кнопка retry |
| `error_forbidden` | 403 Forbidden | «Нет доступа к данным активности»; счётчик и модалка не показываются |

### 4.3.1. Loading и таймауты
- **Cold-path (первый запрос):** таймаут ожидания ответа — **3 сек** (пользователь видит спиннер; если ответ не пришёл → перейти в `error_source`).
- **Warm-path (инвалидация / переключение периода):** таймаут — **2 сек** (граф уже загружен, ждём обновления; при таймауте → показать попытку retry).
- **Polling (live-счётчик в шапке):** интервал запросов — **30 сек** (соответствует TTL кэша на бэке); jitter: ±2 сек (чтобы избежать синхронизированных пиков нагрузки).

### 4.4. Доступ по ролям в UI
- **Администратор:** видит счётчик, может открыть модалку, может выгрузить сводку.
- **Оператор:** счётчик, модалка и выгрузка не отображаются (если они попадают в один визуальный блок с другим контентом, скрыть весь блок или показать «Нет доступа»).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** INT-0 работает **синхронно** — запрос → вычисление → ответ (не асинхронная рассылка, не очередь).
- **Кэш:** На стороне бэка «Арсенала» — **30 секунд** (ключ кэша: `activity:current` для текущего счёта и `activity:aggregates:<period>:<startTime>:<endTime>` для агрегатов). Инвалидация — по TTL или явная очистка при изменении источника данных.
- **Частота обновления:** Фронт запрашивает INT-0 каждые 30 сек (не чаще, чтобы соответствовать кэшу) для счётчика; для модалки — по инициативе пользователя (смена периода).
- **Таймауты:** 
  - Внешний таймаут (фронт ↔ бэк) — **5 сек** (поде к соглашению аналитика; если нет ответа → `error_source`).
  - Внутренний таймаут (бэк к источнику данных) — **5 сек** (если превышен → бэк отдаёт `isAvailable: false`).
- **Ожидаемая нагрузка:** ~100–1000 администраторов, каждый запрашивает ~2 раза в минуту (счётчик + периодическое обновление); пик нагрузки — при открытии модалки (все запрашивают агрегаты одновременно). Кэш поглощает пиковую нагрузку.

### 5.2. Надёжность/деградация
- **При недоступности источника данных:** Не возвращаем устаревшее значение. Вместо этого отдаём 2xx с `isAvailable: false` и `currentCount: null` / `aggregates: null`. Пользователь видит: «Источник активности недоступен. Повторить?» и может нажать retry.
- **Различие ошибок:**
  - **«Источник недоступен» (`isAvailable: false`)** — сетевая ошибка, таймаут, зависимость упала. Пользователь: retry.
  - **«Нет данных за период» (`hasData: false`)** — период валиден, но данных действительно нет (напр. выходной день). Пользователь: граф пуст, но система работает нормально.
- **Эскалация:** Если INT-0 недоступна 5+ минут подряд, алерт в мониторинге; команда Arsenal-Core расследует.

### 5.3. Безопасность/доступ (сводно)
| Кто | Видит / может | Где проверяется |
|-----|---------------|----|
| Администратор | Счётчик, модалка, выгрузка | 403 на INT-0 если роль не совпадает |
| Оператор | Ничего из активности | 403 на INT-0 |
| Неавторизованный | Ничего | 401 на INT-0 |

## 6. Релиз и интеграция

### 6.1. Порядок выката
1. **Фундамент #0 (INT-0) — первым.** Бэк «Арсенала» реализует эндпоинт `/api/admin/activity-stats`, тестирует авторизацию, кэш, таймауты.
2. **Детские узлы (FR-1..FR-5, фронты) — после фундамента.** Фронты обновляются и начинают вызывать INT-0, пока эндпоинт уже доступен и тестирован.

### 6.2. Обратная совместимость
- **Старый фронт (до этого прогона):** Нет, не зависит от INT-0 → на него не влияет.
- **Новый фронт → старый бэк:** Старый бэк не имеет `/api/admin/activity-stats` → фронт получает 404 или 400 → переходит в `error_source` → показывает «Источник недоступен» → приглашает retry. Приемлемо, так как это временное состояние во время синхронного выката.

### 6.3. Фиче-флаги
**Фиче-флагов нет** (подтверждено аналитиком). Релизим атомарно: INT-0 выкатывается, дети сразу начинают его вызывать. Если срочный откат — откатываем обе стороны (бэк и фронты детей) синхронно.

### 6.4. План отката
- **Откат только бэка (INT-0):** Фронты получат 404 / 500 на INT-0 → перейдут в `error_source` → покажут «Источник недоступен» → retry. Фронты продолжают работать (счётчик скрыт, модалка не открывается, но админка не упала). **Откат только бэка допустим.**
- **Откат только фронтов:** Бэк продолжает отдавать INT-0. Фронты старой версии не вызывают INT-0 → счётчик и модалка не работают, но админка не упала. **Откат только фронтов допустим.**
- **Откат DDL:** Миграций нет; данных не теряются.

### 6.5. Преднастройка до релиза
