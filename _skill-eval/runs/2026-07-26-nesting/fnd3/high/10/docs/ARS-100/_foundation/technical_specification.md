## 1. Обзор изменения
### 1.1. Тип и стороны
**BE-only.** Узел-фундамент #0 — контрактный слой на бэке Arsenal, отдающий актуальные данные об активности пользователей (текущее число активных + агрегированная активность за период). Потребители — фронтенды детских компонентов (FR-1..FR-5).

### 1.2. Затронутые сервисы и владельцы

### 1.3. Связь с бизнес-требованиями

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Arsenal Backend (узел #0) → детские фронтенды
- **Триггер:** Фронтенд запрашивает:
  1. Текущий счёт активных пользователей (для счётчика в шапке, FR-1).
  2. Агрегированную активность за выбранный период (час / день / неделя для графика, FR-3..FR-4).
  3. Сводку активности за период (для выгрузки, FR-5).
- **Контракт (запрос):** 
  - Метод + путь: `GET /api/admin/activity` (концептуально)
  - Параметры: 
    - `period`: перечисление (`"current"`, `"hour"`, `"day"`, `"week"`) — обязательно
    - `tz` (timezone): строка, опционально, по умолчанию UTC
  - Авторизация: Header `Authorization: Bearer <token>`, роль проверяется на бэке
- **Контракт (ответ):** 
  - `current_count` (число целое): текущее число активных пользователей либо null, если источник недоступен
  - `is_available` (boolean): признак доступности источника данных активности. `true` = данные актуальны; `false` = источник недоступен (должно быть отдельное сообщение об ошибке в UI)
  - `no_data_for_period` (boolean): `true` = нет данных за запрошенный период (отдельно от недоступности источника; UI должна различать)
  - `aggregates` (массив объектов, опционально если period != "current"): агрегированная активность за период
    - `timestamp` (ISO 8601): начало интервала (час / день в зависимости от period)
    - `count` (число целое): число активных пользователей в этом интервале
  - `summary_data` (объект, опционально если требуется выгрузка): сводка для скачивания файла
    - `period_start` (ISO 8601): начало периода
    - `period_end` (ISO 8601): конец периода
    - `min` (число): минимум за период
    - `max` (число): максимум за период
    - `avg` (число, дробная): среднее за период
    - `total_sessions` (число): суммарно сессий (если релевантно)

- **Пример запроса:** 
  ```
  GET /api/admin/activity?period=day&tz=Europe%2FMoscow
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех, period=current):**
  ```json
  {
    "current_count": 42,
    "is_available": true,
    "no_data_for_period": false,
    "aggregates": null,
    "summary_data": null
  }
  ```

- **Пример ответа (успех, period=day):**
  ```json
  {
    "current_count": 42,
    "is_available": true,
    "no_data_for_period": false,
    "aggregates": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 15 },
      { "timestamp": "2026-07-26T01:00:00Z", "count": 18 },
      { "timestamp": "2026-07-26T02:00:00Z", "count": 22 },
      { "timestamp": "2026-07-26T03:00:00Z", "count": 35 }
    ],
    "summary_data": {
      "period_start": "2026-07-26T00:00:00Z",
      "period_end": "2026-07-27T00:00:00Z",
      "min": 15,
      "max": 35,
      "avg": 22.5,
      "total_sessions": 450
    }
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_count": null,
    "is_available": false,
    "no_data_for_period": false,
    "aggregates": null,
    "summary_data": null
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "current_count": 42,
    "is_available": true,
    "no_data_for_period": true,
    "aggregates": [],
    "summary_data": null
  }
  ```

- **Ошибки:** 
  - `401 Unauthorized`: отсутствует или невалидный токен
  - `403 Forbidden`: роль пользователя не "Администратор"
  - `400 Bad Request`: невалидное значение `period` или другие параметры
  - `504 Gateway Timeout`: таймаут 5 секунд (превышен) при обращении к источнику активности
  - В теле ошибки: `{ "error": "<код ошибки>", "message": "<описание>" }`

- **Состояния UI по ответу (если есть фронт):** 
  - `is_available=true` + `current_count≠null` → **value**: показать число
  - `current_count=0` → **zero**: показать "0" (не прочерк)
  - `is_available=true` + (`current_count=null` ИЛИ `no_data_for_period=true`) → **empty**: показать прочерк "—" или "нет данных"
  - `is_available=false` → **error_source**: показать ошибку "Источник данных недоступен" + кнопку retry
  - `status=403` → **error_forbidden**: показать "нет доступа"

- **Авторизация:** 
  - **Кто вправе:** только роль "Администратор"
  - **Где enforced:** на бэке Arsenal, в обработчике `GET /api/admin/activity`
  - **Негативный случай:** если роль не "Администратор" → `403 Forbidden`

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (счётчик), FR-2 (обновление счётчика), FR-3 (модалка с графиком), FR-4 (переключение периодов), FR-5 (выгрузка сводки)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 401 Unauthorized | `{ "error": "unauthorized", "message": "Токен отсутствует или невалидный" }` | Отсутствует/истекла авторизация | Redirect на вход; скрыть виджет активности |
| 403 Forbidden | `{ "error": "forbidden", "message": "Роль не Администратор" }` | Пользователь — не администратор | error_forbidden: "нет доступа" |
| 400 Bad Request | `{ "error": "bad_request", "message": "Невалидное значение period: ..." }` | Неверный параметр `period` или `tz` | Скрыть виджет; залогировать ошибку в консоль |
| 504 Gateway Timeout | `{ "error": "timeout", "message": "Источник данных не ответил (таймаут 5c)" }` | Источник активности не ответил за 5 сек | error_source: "Источник недоступен, повторите попытку" |
| 5xx (общие ошибки сервера) | `{ "error": "internal_error", "message": "Ошибка обработки запроса" }` | Внутренняя ошибка Arsenal Backend | error_source: "Ошибка на сервере" + retry |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal Backend (узел #0):**
- Реализует INT-0 контракт (обработчик `GET /api/admin/activity`).
- Проверяет авторизацию: роль пользователя должна быть "Администратор".
- Собирает данные активности пользователей из внутреннего источника (механизм — см. ниже).
- Считает агрегаты за запрошенный период (час / день / неделя) на лету — **новых таблиц не заводит**.
- Кэширует результат на 30 сек на стороне Arsenal Backend (не в отдельном сервисе).
- Отличает недоступность источника (`is_available=false`) от отсутствия данных за период (`no_data_for_period=true`).
- Возвращает точно контракт из INT-0, не добавляет и не меняет поля.

### 3.2. Данные и хранение
**Новых таблиц не заводится.** 🟡 подтверждено аналитиком (не по коду): Arsenal Backend уже собирает данные об активности (текущий счёт сессий, историю по времени). Узел #0 обращается к этому существующему источнику, считает агрегаты на лету и отдаёт через INT-0.

Хранилище:
- Текущий счёт активных пользователей: 🟡 к валидации — уточнить, откуда именно берётся (кэш сессий, Redis, таблица Sessions и т.д.).
- Исторические данные для периодов: 🟡 к валидации — подтвердить, что есть источник с историей (лог сессий, временные ряды в БД).
- Индексы: если они нужны для типовых запросов (по времени, по периодам) — должны быть в собственности Arsenal Backend, точный DDL — за ними.

**Ограничение TTL/retention:** не установлено в спеке; 🟡 к валидации — уточнить политику хранения исторических данных.

### 3.3. Авторизация/доступ на бэке
- Проверка роли "Администратор" — в обработчике INT-0 на Arsenal Backend.
- Если роль не совпадает → `403 Forbidden`.
- Негативный тест: пользователь "Оператор" + запрос INT-0 → должен получить 403.

## 4. Frontend — ответственность

**Узел #0 не включает фронтенд-часть.** Это контрактный слой, фронты детских компонентов (счётчик, модалка, выгрузка) потребляют INT-0 и преобразуют ответ в свои UI-состояния (см. раздел § 2, «Состояния UI по ответу»). Фронты детей наследуют INT-0 без переопределения и разводят состояния `value` / `zero` / `empty` / `error_source` / `error_forbidden` независимо для своих нужд.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- **Синхронность:** синхронный обработчик (request–response, не async job).
- **Кэш:** на стороне Arsenal Backend, TTL = 30 секунд. Кэш ключ — `activity:{period}:{tz}` (если период зависит от timezone).
- **Таймаут:** 5 секунд при обращении к источнику активности (внутреннему). Если превышен → `504 Gateway Timeout`.
- **Частота обновления счётчика на фронте:** FR-2 требует обновления "в пределах минуты"; с кэшем 30с рекомендуется polling интервал 30–45с на фронте (с jitter).
- **Ожидаемая нагрузка:** 🟡 к валидации — сколько админов одновременно смотрят панель; за счёт кэша нагрузка на источник активности минимальна (1 запрос к источнику на 30 сек за все фронты).

### 5.2. Надёжность/деградация
- **При недоступности источника:** возвращать `{ "is_available": false }` + `current_count: null`, **а не** устаревшее кэшированное значение. UI должна показать ошибку.
- **Отличие от "нет данных":** если источник доступен, но за период нет активности → `no_data_for_period: true` (отдельно от `is_available`). UI показывает "—" / "нет данных", а не ошибку.
- **Таймаут источника:** если источник не ответил за 5 сек → `504 Gateway Timeout` (не ждать дольше, не возвращать partial data).

### 5.3. Безопасность/доступ (сводно)
| Граница | Роль | Действие | Результат |
|---------|------|---------|-----------|
| INT-0 → GET /api/admin/activity | Администратор | Запрос активности | 2xx, полный контракт |
| INT-0 → GET /api/admin/activity | Оператор | Запрос активности | 403 Forbidden |
| INT-0 → GET /api/admin/activity | Аноним (нет токена) | Запрос активности | 401 Unauthorized |

## 6. Релиз и интеграция
### 6.1. Порядок выката
**Узел-фундамент #0 выкатывается ПЕРВЫМ**, раньше детских компонентов (счётчика, модалки, выгрузки). Причина: дети наследуют контракт INT-0 без изменений; если #0 изменится после выката детей, потребуется синхронный откат или несовместимость.

Порядок:
1. **Deploy Arsenal Backend (узел #0)** с новым обработчиком INT-0 и кэшем.
2. **Deploy детские фронты** (по очереди или одновременно — они независимы, опираются на один контракт #0).

### 6.2. Обратная совместимость
- Если контракт INT-0 расширяется новыми полями в `summary_data` или `aggregates` — добавлять с опциональностью (не требовать у потребителей).
- Если меняется структура существующего поля (напр. `current_count` был int, становится object) — это breaking change → требуется новая версия API или feature flag.
- В первом выкате новых полей нет, потреблиев на них быть не может → совместимость не нарушается.

### 6.3. Фиче-флаги
**Фиче-флагов нет.** 🟡 подтверждено аналитиком: релизим атомарно (вместе с #0 выкатываются все потребители или используется rollback как откат).

### 6.4. План отката (обязательно, если задача деплоится)
- **Откат BE (#0)**: если новый INT-0 отдаёт ошибку — откатиться на старый обработчик. FE старого поколения (на стареньком коде) будет видеть 404 или 5xx, должна иметь fallback (скрыть виджет / показать ошибку).
- **Откат FE (детей)**: старые фронты, остались на старом коде, получают новый INT-0 (если #0 уже выкатан) — должны игнорировать новые поля в ответе или обойти их (если они опциональны). Синхронный откат #0 не требуется, если контракт расширяется без breaking changes.
- **DDL откат**: не требуется, новые таблицы не создаются.

- [ ] **DDL-миграция в репо Arsenal Backend:** не требуется (новых таблиц нет).
- [ ] **Конфиги по окружениям:** TTL кэша (30c) и таймаут (5c) параметризовать конфигом (dev/staging/prod могут быть разные).

## 7. Трассировка приёмки

|----------|-------------------|------------------------------|
| FR-1 | INT-0 (period=current) | Дано открытую админку с авторизацией "Администратор", когда страница загрузилась, тогда INT-0 возвращает `current_count ≠ null` и он отображается в шапке. |

## 8. Допущения и открытые вопросы
- **🟡 Подтверждено аналитиком (не по коду):**
  - Arsenal Backend уже собирает данные об активности пользователей (текущий счёт и историю).
  - Роль "Администратор" настроена в системе безопасности Arsenal.
  - Источник активности находится внутри Arsenal Backend, внешних зависимостей нет.
  - Агрегаты считаются на лету, новых таблиц не заводим.
  - Контракт #0 отличает недоступность источника от отсутствия данных за период.

- **🟡 К валидации:**
  - Точный источник текущего счёта активных пользователей (кэш, Redis, БД) — уточнить при интеграции.
  - Точный источник исторических данных для периодов (логи сессий, временные ряды) — уточнить.
  - Политика хранения исторических данных (retention) — сколько месяцев/лет.
  - Ожидаемая нагрузка на INT-0 (сколько админов одновременно) и размер агрегатов.

- **Унаследовано из БТ (бизнес-пробелы, не блокируют спеку):** нет.

- **Приложения из БТ:** UX-пожелание — счётчик неяркий, не отвлекает. Это требование к фронтам детей (стиль, opacity, placement в шапке), не к контракту #0.
