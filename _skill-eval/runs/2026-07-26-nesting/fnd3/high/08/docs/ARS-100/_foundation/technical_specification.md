## 1. Обзор изменения
### 1.1. Тип и стороны
**BE-only.** Узел-фундамент #0 предоставляет контракт данных активности пользователей (текущее число активных и агрегированная активность за период). Контракт потребляют фронтенд-дети эпика, реализующие счётчик, график и выгрузку сводки в админке «Арсенал». #0 не осуществляет собственный UI и существует исключительно как сервисный слой для детских фронтов.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Реализует контракт данных активности; владеет источником данных сессий | Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел #0 обслуживает ядро функциональных требований FR-1..FR-5 эпика: предоставляет текущее число активных пользователей и исторические данные активности за выбранный период (час / день / неделя), на которых строятся счётчик в шапке, график в модальном окне и сводка для выгрузки.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Дочерний фронтенд (через REST API)

- **Триггер:** Дочерний фронтенд запрашивает данные при загрузке/обновлении счётчика и при открытии модального окна с графиком

- **Контракт (запрос):**
  - **Метод и путь (концептуально):** `GET /api/activity/stats`
  - **Параметры запроса:**
    - `period` (query string, обязательный): строка, одно из значений: `"hour"`, `"day"`, `"week"`
  - **Заголовки:** Авторизация передаётся стандартным механизмом (see §2, авторизация)

- **Контракт (ответ):**
  - `status` (строка): одно из `"available"`, `"unavailable"`, `"empty"`
    - `"available"` — текущие данные получены, есть как текущий счёт, так и исторические точки
    - `"unavailable"` — источник данных активности не доступен (сервис сессий / БД вниз); текущее значение и точки неопределены
    - `"empty"` — источник доступен, но за выбранный период нет данных (никто не был активен)
  - `current` (объект или null):
    - `count` (целое число или null): текущее число активных пользователей; null, если статус ≠ `"available"`
    - `timestamp` (ISO 8601 строка или null): время последнего обновления счёта; null, если статус ≠ `"available"`
  - `aggregates` (объект):
    - `period` (строка): повтор переданного значения периода (`"hour"`, `"day"`, `"week"`)
    - `data_points` (массив объектов): упорядочены по времени (от старого к новому)
      - `timestamp` (ISO 8601): временная метка (начало интервала)
      - `count` (целое число ≥ 0): число активных пользователей в этот интервал
        - Для `"hour"` — интервалы по 5 минут, всего ≤ 12 точек
        - Для `"day"` — интервалы по 1 часу, всего 24 точки
        - Для `"week"` — интервалы по 1 дню, всего 7 точек
      - Пустой массив, если `status = "empty"`
    - `summary` (объект, если массив не пуст, иначе опускается):
      - `min` (целое число ≥ 0): минимальное число активных за период
      - `max` (целое число ≥ 0): максимальное число активных за период
      - `avg` (число с плавающей точкой, 1 знак): среднее число активных за период
      - `total_hours` (целое число): количество часов в периоде (38 для часа, 24 для дня, 168 для недели)

- **Пример запроса:**
  ```
  GET /api/activity/stats?period=day
  ```
  (тело отсутствует, авторизационный заголовок в стандартном месте)

- **Ошибки:**
  | Код | Тело/сообщение | Когда | Статус запроса |
  |-----|----------------|-------|----------------|
  | 200 | JSON как выше | Успех (данные есть, недоступны или пусты) | значение / loading / empty / error_source |
  | 400 | `{ "error": "invalid_period", "message": "period must be 'hour', 'day', or 'week'" }` | Передан неверный `period` | error (UI игнорирует, перепроверяет входные параметры) |
  | 401 | `{ "error": "unauthorized", "message": "Authentication required" }` | Заголовок авторизации отсутствует или неверен | error_source (UI: «Требуется повторная авторизация») |
  | 403 | `{ "error": "forbidden", "message": "Only Administrator role can access this endpoint" }` | Роль не Administrator | error_forbidden (UI: «Доступ запрещён») |
  | 503 | `{ "error": "service_unavailable", "message": "Activity data service is temporarily unavailable" }` | Целевой сервис (источник сессий) вниз | error_source (обработать как 5xx) |

- **Состояния UI по ответу (если есть фронт — дочерний UI):**
  - `value` → status = `"available"` и count ≠ null и count ≠ 0 (показать число)
  - `zero` → status = `"available"` и count = 0 (показать «0»)
  - `empty` → status = `"empty"` (показать «—» или «нет данных»)
  - `error_source` → status = `"unavailable"` или HTTP 5xx / таймаут (показать «—» + сообщение об ошибке)
  - `error_forbidden` → HTTP 403 (показать «доступ запрещён»)
  - `loading` → первый запрос или после инвалидации (показать спиннер/скелетон)

  - **Негативный случай:** Если роль не Administrator → HTTP 403 с сообщением
  - **Где enforced:** До вычисления ответа, в контексте HTTP-обработчика (middleware / контроллер)

- **Происхождение:** 🟢 новое (узел-фундамент #0, наследуется всеми детьми без изменений)

- **Трассировка:** FR-1 (текущее число активных), FR-2 (обновление), FR-3 (график за период), FR-4 (переключение периода), FR-5 (сводка для выгрузки)

## 3. Backend — ответственность

### 3.1. Реализация на сервисе Arsenal

**Arsenal Backend** реализует эндпоинт `GET /api/activity/stats?period=<hour|day|week>`:

1. **Проверка авторизации:** Извлечь роль из контекста запроса (security-сервис). Если роль ≠ Administrator → вернуть 403.

2. **Валидация параметра period:** Если `period` не одно из `["hour", "day", "week"]` → вернуть 400.

3. **Получение текущего счёта активных:**
   - Запросить у сервиса сессий (🟡 подтверждено аналитиком, что такой интерфейс существует) текущее число активных сессий.
   - Если сервис отвечает с таймаутом (>5 секунд) или ошибкой 5xx → вернуть `status: "unavailable"` с пустыми данными.
   - Если ответ получен → извлечь `count` и `timestamp` последнего обновления.

4. **Получение агрегированных данных за период:**
   - Запросить у сервиса сессий исторические данные активности за выбранный период.
   - Если сервис отвечает с таймаутом или 5xx → вернуть пустой массив `data_points`, `status: "unavailable"`.
   - Если данные получены:
     - Если массив пуст (никого не было) → `status: "empty"`, заполнить `data_points: []`, `summary: null`.
     - Если есть точки → вычислить `min`, `max`, `avg` и заполнить `summary`.

5. **Кэширование на бэке Arsenal:**
   - Результат кэшируется на 30 секунд. Ключ кэша = `activity_stats:{period}`. Инвалидация по TTL.
   - Повторный запрос в окне 30 секунд возвращает закэшированное значение (включая статус).

6. **Таймаут:**
   - Если запрос к сервису сессий занимает >5 секунд → прервать, вернуть `status: "unavailable"`.

### 3.2. Данные и хранение

**Новых сущностей и таблиц не добавляется.** 🟡 Подтверждено аналитиком: агрегаты считаются на лету при каждом запросе, без предварительной выгрузки и хранения.

- Источник данных о сессиях: существующий сервис сессий (🟡 подтверждено аналитиком, собирает Arsenal сам).
- Хранение: нет дополнительного хранилища; агрегация выполняется в памяти процесса на каждый запрос.
- Индексы: при наличии на стороне сервиса сессий (не в зоне ответственности #0).
- Миграции: не требуются.

### 3.3. Авторизация/доступ на бэке

- **Где enforced:** В контроллере / middleware Arsenal Backend перед вычислением ответа.
- **Проверка:** Роль `Administrator` (из security-сервиса, 🟡 подтверждено аналитиком).
- **Негативный случай:** Роль ≠ Administrator → HTTP 403 (`error: "forbidden"`).
- **Сервис сессий:** Вызов к нему выполняется из контекста бэка Arsenal (server-to-server), авторизация там — внутренняя (не часть этого контракта).

## 4. Frontend — ответственность

**Не применимо:** узел-фундамент #0 не содержит фронтенда. UI реализуется в детских узлах (ARS-101, ARS-102, ARS-103), которые потребляют INT-0 и строят на его основе счётчик, график и выгрузку.

Дочерние фронты обязаны:
- Вызывать INT-0 с авторизационным заголовком (наследуется из контекста текущего пользователя).
- Обрабатывать все три статуса: `available` (показать значение), `unavailable` (показать ошибку), `empty` (показать «—»).
- Различать состояния `value`, `zero`, `empty`, `error_source`, `error_forbidden` (см. INT-0).
- Обновлять счётчик не реже чем раз в 30 секунд (кэш на бэке гарантирует этот интервал).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** Запрос-ответ синхронный (HTTP GET).
- **Кэш:** На бэке Arsenal, TTL = 30 секунд. Ключ = `activity_stats:{period}`.
- **Таймаут запроса:** До 5 секунд на вызов сервиса сессий; превышение → `status: "unavailable"`.
- **Частота обновления:** Дочерний фронт может обновлять счётчик каждые 10–30 секунд; данные будут свежие не более чем на 30 секунд (TTL кэша).
- **Ожидаемая нагрузка:** Узел #0 обслуживает N фронтов, каждый может запрашивать INT-0 раз в 10–30 секунд. На одного администратора — ≤6 запросов в минуту.

### 5.2. Надёжность/деградация

- **При недоступности сервиса сессий:** Вернуть `status: "unavailable"`, не отдавать устаревшие кэшированные данные из предыдущего успешного ответа. Это критично для бизнеса: администратор не должен принимать решения на основе устаревших данных активности.
- **Различие между «недоступен» и «нет данных»:** Если сервис сессий вниз → `"unavailable"`; если сервис вверх, но в выбранном периоде не было активности → `"empty"`. Дочерний UI отображает их по-разному: ошибку vs пусто.

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Проверка |
|---------|-----------|----------|
| INT-0 (GET /api/activity/stats) | Administrator | HTTP 403 если роль не Administrator |
| Доступ к сервису сессий | Arsenal Backend (server-to-server) | Внутренняя авторизация сервиса сессий |

## 6. Релиз и интеграция

### 6.1. Порядок выката

**Узел-фундамент #0 выкатывается ПЕРВЫМ**, раньше всех дочерних фронтов (ARS-101, ARS-102, ARS-103).

1. **Phase 1:** Развёртывание нового эндпоинта `GET /api/activity/stats` на бэке Arsenal (с логикой подсчёта, кэшем, проверкой авторизации).
2. **Phase 2+:** После проверки #0 (функции работают, авторизация enforced) дочерние фронты (ARS-101 и т.п.) начинают разработку и выкат своих UI-компонентов, опираясь на INT-0.

**Обоснование:** Дочерние фронты зависят от контракта #0; он должен быть на месте и протестирован до того, как дети начинают потреблять.

### 6.2. Обратная совместимость

Узел #0 — новый слой, отдельный контракт. Обратной совместимости с предыдущими версиями нет (их не было). После выката #0 дочерние фронты принимают контракт как НОВЫЙ, не конфликтуя с существующими потребителями (их нет).

### 6.3. Фиче-флаги

**Релизим атомарно.** 🟡 Подтверждено аналитиком: фиче-флаги не требуются. Эндпоинт INT-0 выкатывается включённым и доступным сразу для всех Administration-ролей.

### 6.4. План отката

**Откат только BE (останавливаем INT-0):**
- Если выкатили #0, но выявилась критическая ошибка, откатываем бэк Arsenal.
- Дочерние фронты в этот момент либо ещё не выкачены (Phase 2 не началась), либо получат 5xx на INT-0 и покажут `error_source`.
- Дочерний UI должен корректно обработать 5xx и degradation (показать ошибку, не крашиться).

**Откат только FE (если дочерний фронт сломал интеграцию):**
- Откатить дочерний фронт; бэк #0 остаётся работать; другие дочерние фронты продолжают потреблять INT-0.
- Локальное состояние UI инвалидируется, пользователь видит загрузку при возврате.

**Откат БД:**
- Не применимо (новых таблиц нет).

- [x] **Роли в security-сервисе:** Роль `Administrator` должна быть определена в security-сервисе. 🟡 Подтверждено аналитиком, что роль существует.
- [ ] **DDL-миграция:** Не требуется (агрегация на лету, нет новых таблиц).
- [ ] **Конфиги по окружениям:** TTL кэша (30 секунд) и таймаут (5 секунд) могут быть вынесены в конфиг окружения (dev/staging/prod). Значения по умолчанию — как в спеке.
- [ ] **Сервисные аккаунты:** Вызов INT-0 выполняется от текущего пользователя (admin), server-to-server (в Arsenal → сервис сессий) — на стороне сервиса сессий.

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие | Тест-кейс (Дано–Когда–Тогда) |
|----------|----------------|------------------------------|
| FR-1 | INT-0 (текущий счёт) | Дано: администратор авторизован. Когда: фронт отправляет GET /api/activity/stats?period=day. Тогда: ответ содержит `current.count` = актуальное число активных пользователей в статусе 2xx. |
| FR-2 | INT-0 (обновление) | Дано: счётчик загрузился (INT-0 получен). Когда: число активных пользователей изменилось, фронт переотправляет запрос через 10–30 секунд. Тогда: новый ответ INT-0 содержит обновлённое `current.count`. |
| FR-3 | INT-0 (график) | Дано: фронт открыл модальное окно. Когда: фронт отправляет GET /api/activity/stats?period=week. Тогда: ответ содержит `aggregates.data_points` с 7 дневными точками, готовыми к рендеру графика. |
| FR-4 | INT-0 (переключение периода) | Дано: модальное окно открыто с графиком на неделю. Когда: администратор переключает период на день (GET /api/activity/stats?period=day). Тогда: ответ содержит 24 часовых точки, фронт перестраивает график. |
| FR-5 | INT-0 (выгрузка сводки) | Дано: модальное окно открыто с выбранным периодом. Когда: администратор кликает выгрузку. Тогда: фронт формирует файл, используя `aggregates.summary` (min, max, avg) и `data_points` из последнего ответа INT-0. |
