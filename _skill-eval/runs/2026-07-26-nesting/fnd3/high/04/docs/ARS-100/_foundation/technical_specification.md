> **Задача:** ARS-100 / узел-фундамент #0
> **Источник (БТ):** docs/ARS-100/business_requirements.md (эпик-БТ)
>
> **Статус готовности:** Готово к разработке
>
> **Открытые вопросы:** Нет.

## 1. Обзор изменения

### 1.1. Тип и стороны
BE-only. Узел-фундамент #0 выполняет роль общего поставщика контракта данных активности пользователей (текущее число активных + агрегированная активность за выбранный период). Детские узлы (FR-1..FR-5) потребляют этот контракт, не переопределяя его.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | Реализует контракт активности (новое взаимодействие INT-0) | Arsenal-Core | 🟢 новое |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 обеспечивает единую точку доступа к данным активности пользователей, на которой базируются все пять функциональных требований (FR-1..FR-5) эпика ARS-100: отображение текущего счётчика, его автоматическое обновление, график активности за период и выгрузка сводки.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Frontend (админка)
- **Триггер:** Инициируется фронтом админки: загрузка страницы (для текущего счётчика), клик на счётчик (для открытия модала с периодом), переключение периода в модале, запрос выгрузки.
- **Контракт (запрос):** HTTP GET, пример пути: `/api/admin/activity` (концептуально, точный путь — в BE-спеке).
  - Параметры запроса:
    - `scope` (обязателен): `current` — только текущее число; `aggregated` — данные за период.
    - `period` (обязателен для `scope=aggregated`): `hour` | `day` | `week` — длина периода.
    - `from` (обязателен для `scope=aggregated`): ISO 8601 дата-время начала периода.
    - `to` (обязателен для `scope=aggregated`): ISO 8601 дата-время конца периода.
  - Тело: отсутствует.

- **Контракт (ответ):**
  - `status` (строка, обязательно): `ok` | `unavailable` | `no_data`.
    - `ok` → данные доступны, значение актуально.
    - `unavailable` → источник недоступен; ни актуального значения, ни кэша отдавать не будем, фронт видит пустой график/пустой счётчик.
    - `no_data` → данные за выбранный период отсутствуют (напр., период выходит за границы сбора, или на нём нет активности и это валидное состояние); фронт различает от ошибки.
  
  - Для `scope=current` (при `status=ok`):
    - `current_active_count` (целое число, ≥ 0): число активных пользователей в данный момент.
  
  - Для `scope=aggregated` (при `status=ok`):
    - `current_active_count` (целое число, ≥ 0, опционально): текущее число активных (опорная точка).
    - `data_points` (массив объектов): агрегированные точки активности за период.
      - `timestamp` (ISO 8601): момент (или начало временного бакета, напр. начало часа/дня).
      - `active_count` (целое число, ≥ 0): число активных пользователей в этот момент/интервал.
    - `period_info` (объект):
      - `from` (ISO 8601): начало периода (как в запросе).
      - `to` (ISO 8601): конец периода (как в запросе).
      - `granularity` (строка): `hourly` | `daily` | `weekly` — фактическая детальность точек в `data_points` (может отличаться от запроса, если период очень большой и нужна агрегация по часам вместо минут).

  - Семантика `null`:
    - `current_active_count` может быть `null` при `status=no_data` (если значения нет за период).
    - Поля `data_points` и `period_info` отсутствуют при `status != ok`.

- **Пример запроса:**
  ```
  GET /api/admin/activity?scope=current
  ```
  или
  ```
  GET /api/admin/activity?scope=aggregated&period=day&from=2026-07-20T00:00:00Z&to=2026-07-21T00:00:00Z
  ```

- **Пример ответа (успех, `scope=current`):**
  ```json
  {
    "status": "ok",
    "current_active_count": 42
  }
  ```

- **Пример ответа (успех, `scope=aggregated`):**
  ```json
  {
    "status": "ok",
    "current_active_count": 42,
    "data_points": [
      { "timestamp": "2026-07-20T00:00:00Z", "active_count": 15 },
      { "timestamp": "2026-07-20T01:00:00Z", "active_count": 22 },
      { "timestamp": "2026-07-20T02:00:00Z", "active_count": 38 }
    ],
    "period_info": {
      "from": "2026-07-20T00:00:00Z",
      "to": "2026-07-21T00:00:00Z",
      "granularity": "hourly"
    }
  }
  ```

- **Пример ответа (недоступность источника):**
  ```json
  {
    "status": "unavailable"
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "status": "no_data",
    "current_active_count": null
  }
  ```

- **Ошибки:**
  - `400 Bad Request` — некорректный запрос (отсутствует обязательный параметр, неверный формат даты, неверное значение `period`).
  - `401 Unauthorized` — нет авторизации (токен отсутствует или невалиден).
  - `403 Forbidden` — роль не имеет доступа (не Administrator).
  - `5xx Server Error` — ошибка бэка (обрабатывается как `unavailable` на фронте, если кэш пуст).

- **Состояния UI по ответу (если есть фронт):**
  - `value` → `status=ok` и `current_active_count > 0` → показать число.
  - `zero` → `status=ok` и `current_active_count = 0` → показать «0».
  - `empty` → `status=no_data` или `current_active_count=null` → показать «—» / пусто.
  - `error_source` → `status=unavailable` или 5xx / таймаут → показать сообщение об ошибке.
  - `error_forbidden` → 403 → показать «нет доступа».

- **Авторизация:**
  - **Кто вправе:** роль Administrator только.
  - **Где проверяется:** на бэке Arsenal (в middleware или обработчик эндпоинта проверяет роль из контекста пользователя).
  - **Негативный случай:** пользователь без роли Administrator получает 403 Forbidden.

- **Происхождение:** 🟢 новое (узел-фундамент #0).

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5.

### Каталог ошибок
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 Bad Request | `{ "error": "invalid_period_value" }` | неверное значение `period` или формат даты | сообщение об ошибке (уровень фронта) |
| 401 Unauthorized | `{ "error": "missing_token" }` или `{ "error": "invalid_token" }` | нет авторизационного заголовка или он невалиден | перенаправить на логин |
| 403 Forbidden | `{ "error": "insufficient_role" }` | роль не Administrator | `error_forbidden` — «нет доступа» |
| 5xx Server Error | (может быть пусто) | ошибка на бэке Arsenal | `error_source` — сообщение об ошибке + retry |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal Backend:**
- Реализует эндпоинт `/api/admin/activity` (концептуально; точный маршрут в BE-спеке).
- Выполняет обработку параметров запроса: парсит `scope`, `period`, `from`, `to`; валидирует формат дат.
- Проверяет авторизацию (роль Administrator).
- Вычисляет и отдаёт контракт INT-0:
  - Для `scope=current`: текущее число активных пользователей.
  - Для `scope=aggregated`: временной ряд активных пользователей за период.
- При недоступности источника данных об активности возвращает `status=unavailable` (признак, а не статок).
- Отличает отсутствие данных (`status=no_data`) от технической недоступности (`status=unavailable`).

### 3.2. Данные и хранение
🟡 подтверждено аналитиком (не по коду): агрегаты активности считаются на лету, новых таблиц не заводим. Источник данных об активности пользователей — существующая инфраструктура логирования/отслеживания сессий Arsenal.

Кэширование:
- 🟢 новое: кэш результатов на стороне Arsenal backend, TTL = 30 секунд (потребители получают данные за последние 30 секунд, свежесть достаточна для потребителей).
- Инвалидация кэша: по TTL (не требуется ручная инвалидация в рамках этого узла).

Новых сущностей/таблиц не требуется.

### 3.3. Авторизация/доступ на бэке
- Проверка роли Administrator выполняется в обработчике эндпоинта `/api/admin/activity`.
- Источник ролей: система авторизации Arsenal (как правило, в контексте пользователя или токене).
- Отсутствие роли → 403 Forbidden.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
**Админка Arsenal:**
- Заголовок/шапка: счётчик активных пользователей (интегрирует INT-0, `scope=current`).
- Модальное окно (открывается по клику на счётчик): график активности за выбранный период (интегрирует INT-0, `scope=aggregated`); переключатель периода (hour / day / week); кнопка выгрузки.

### 4.2. Пользовательские сценарии
- **Основной сценарий (FR-1, FR-2):** 
  - Администратор открывает админку.
  - Фронт запрашивает `GET /api/admin/activity?scope=current` при загрузке.
  - Фронт получает `{ "status": "ok", "current_active_count": 42 }`.
  - Показывает число в шапке.
  - Каждые N секунд (где N << 30 сек кэша; рекомендуемо полировать согласованность, напр. 10–15 сек) фронт запрашивает обновление.
  
- **Модальный сценарий (FR-3, FR-4):**
  - Администратор кликает на счётчик в шапке.
  - Модальное окно открывается с периодом по умолчанию (напр., сегодня).
  - Фронт запрашивает `GET /api/admin/activity?scope=aggregated&period=day&from=<today>&to=<tomorrow>`.
  - Получает ответ с `data_points` и строит график.
  - Администратор переключает период (напр., неделя).
  - Фронт переформирует запрос и обновляет график.

- **Сценарий выгрузки (FR-5):**
  - Администратор нажимает кнопку выгрузки в модале.
  - Фронт берёт `data_points` из последнего успешного ответа INT-0.
  - Форматирует CSV/XLSX со строками (timestamp, active_count).
  - Инициирует скачивание файла (браузерная функция).

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | Первый запрос INT-0 / после переключения периода; ожидание ответа | спиннер рядом со счётчиком / скелетон графика |
| `value` | INT-0 ответила `status=ok`, `current_active_count > 0` | число счётчика или точки на графике |
| `zero` | INT-0 ответила `status=ok`, `current_active_count = 0` | счётчик показывает «0» (не пусто, не «—») |
| `empty` | INT-0 ответила `status=no_data`, или `current_active_count = null` | счётчик и график пусты, показывают «—» / «нет данных» |
| `error_source` | INT-0 ответила `status=unavailable`, или сеть/таймаут/5xx | сообщение об ошибке («Источник недоступен»), кнопка retry |
| `error_forbidden` | INT-0 ответила 403 | сообщение («Нет доступа к панели активности», может быть скрыто само окно) |

### 4.3.1. Loading и таймауты
- **Cold-path** (первый запрос): таймаут = 5 секунд (🟡 подтверждено аналитиком; если истёк → `error_source`).
- **Warm-path** (refresh счётчика каждые N сек, где N < 30 сек кэша): таймаут = 5 секунд (тот же, для консистентности).
- **Polling** (автоматический refresh счётчика в шапке): интервал ≈ 15 секунд; jitter = да (избежать штамповки запросов от всех админок); при таймауте молча перейти в `error_source` и предложить retry.

### 4.4. Доступ по ролям в UI
- Счётчик и модальное окно видны **только** администраторам (роль Administrator).
- Другие роли (напр., Operator) не видят эти элементы.
- Если уровень доступа пользователя изменился, панель скрывается без перезагрузки (опционально: требует уточнения процедуры смены ролей).

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** синхронно (HTTP GET, response-based, нет задач в очереди, нет webhook).
- **Кэш:** 🟡 подтверждено аналитиком — кэш на стороне Arsenal backend, TTL = 30 секунд.
- **Частота обновления:**
  - Счётчик в шапке: refresh каждые ~15 секунд (фронт инициирует; может быть оптимизировано до коротких интервалов на лету, но не быстрее кэша).
  - Модальный график: обновляется по переключению периода (пользователем), нет автообновления графика.
- **Таймауты:**
  - 🟡 подтверждено аналитиком — таймаут 5 секунд (как для холодного пути, так и для теплого).
  - При истечении таймаута фронт показывает `error_source`.
- **Ожидаемая нагрузка:** 🟡 к валидации (оценка не подтверждена; полагаем, что нагрузка на `/api/admin/activity` умеренная — не более несколько запросов в секунду от всех админок вместе; точную метрику должен подтвердить BE-аналитик).

### 5.2. Надёжность/деградация
- При недоступности источника данных об активности (напр., логирование падает, сессии не отслеживаются):
  - Возвращаем `status=unavailable` (флаг, а не старые/кэшированные данные).
  - Фронт переходит в `error_source` и предлагает retry.
  - Важно: не выдавать устаревшие данные как актуальные (бизнес-риск из БТ).
- При отсутствии данных за выбранный период (напр., період выходит за границы сбора):
  - Возвращаем `status=no_data`.
  - Фронт различает это от технической ошибки и показывает `empty` («—» / «нет данных»).

### 5.3. Безопасность/доступ (сводно)
| Граница | Субъект | Право | Где enforced |
|---------|---------|-------|-------------|
| FE → Arsenal API (`/api/admin/activity`) | Пользователь с ролью Administrator | GET/read | BE middleware / эндпоинт Arsenal |
| FE → Arsenal API (`/api/admin/activity`) | Пользователь без роли Administrator | (запрещено) | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟢 новое: узел-фундамент #0 выкатывается **первым**, раньше детских узлов (FR-1..FR-5). 

Детские узлы могут деплоиться одновременно или в любом порядке, после того как #0 выкачена (они не имеют взаимных зависимостей, опираются только на INT-0 из #0).

### 6.2. Обратная совместимость
Нет текущих потребителей эндпоинта `/api/admin/activity` (это новое). Обратная совместимость не актуальна на первый выкат.

При будущих изменениях контракта INT-0:
- Добавление опциональных полей в ответ → совместимо.
- Добавление новых значений `status` → детей нужно обновить, чтобы обработать новые значения (могут быть не совместимы).
- Удаление полей → несовместимо (детей требуется обновить).

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: фиче-флагов нет; релизим атомарно. Если нужна фазированная раскатка, детские узлы управляют видимостью панели на фронте, но INT-0 отдаётся без флагов.

### 6.4. План отката
**Откат только BE:**
- FE на старой версии попытается вызвать `/api/admin/activity`, получит 404 (эндпоинт не существует).
- Панель активности не загружается; фронт показывает `error_source` или скрывает элемент.
- Требуется **синхронный откат FE** (убрать импорт/вызов INT-0 из шапки и модала) или использовать фиче-флаг на фронте.

**Откат только FE:**
- BE продолжает отдавать INT-0; FE на старой версии не обращается.
- Безопасно (нет побочных эффектов); достаточен откат только FE.

**Откат данных:**
- Не применимо: новых таблиц нет, кэш чистится автоматически по TTL.

### 6.5. Преднастройка до релиза
- [ ] ✅ Роли в security-сервисе (роль Administrator должна существовать; подтверждено как факт).
- [ ] ✅ DDL-миграция в репо Arsenal — не требуется (новых таблиц нет).
- [ ] ✅ Конфиги по окружениям — кэш TTL (30 сек) может быть переменной конфига для dev/staging/prod; уточнить в BE-спеке.
- [ ] Сервисные аккаунты для межсервисных вызовов — не требуется (INT-0 вызывается пользовательским фронтом, не сервис-сервис).
- [ ] ✅ Фиче-флаги — не требуются (релизим атомарно).
- [ ] Алерты/мониторинг на ключевые ошибки (5xx на `/api/admin/activity`, таймауты) — рекомендовано; уточнить в BE-спеке.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 (`scope=current`) | Дано открытую админку, когда страница загрузилась, тогда фронт запросил INT-0 с `scope=current` и получил `{ "status": "ok", "current_active_count": N }`, в шапке отображается число N. |
| FR-2 | INT-0 (`scope=current`, polling) | Дано открытую админку, когда число активных пользователей изменилось и прошло 15 сек, тогда фронт запросит INT-0 снова и счётчик обновится без перезагрузки (состояние `value`/`zero` или `empty`). |
| FR-3 | INT-0 (`scope=aggregated`, default period) | Дано счётчик активных в шапке, когда администратор кликает по нему, тогда открывается модальное окно, фронт запрашивает INT-0 с `scope=aggregated` за период по умолчанию (напр., сегодня), получает `{ "status": "ok", "data_points": [...] }` и строит график. |
| FR-4 | INT-0 (`scope=aggregated`, period switch) | Дано открытую модалку с графиком за день, когда администратор переключает на неделю, тогда фронт переформирует запрос INT-0 с новым периодом, получает свежий `data_points` и перестраивает график. |
| FR-5 | INT-0 (`scope=aggregated`) + export | Дано открытую модалку с графиком за выбранный период, когда администратор нажимает выгрузку, тогда фронт берёт `data_points` из INT-0, форматирует CSV/XLSX (timestamp, active_count) и инициирует скачивание файла. |

## 8. Допущения и открытые вопросы

Все технические решения приняты, спецификация готова к разработке.

**🟡 Подтверждено аналитиком (не по коду):**
- Данные активности пользователей собирает бэк Arsenal сам, чужих сервисов не привлекаем.
- При недоступности источника отдаём признак недоступности (`status=unavailable`), а не устаревшее значение.
- Авторизация контракта INT-0: только роль Administrator, проверка на бэке Arsenal.
- Агрегаты активности считаются на лету, новых таблиц не заводим.
- Синхронно, кэш 30 секунд на стороне бэка Arsenal, таймаут 5 секунд.
- Фундамент выкатывается раньше потребителей, фиче-флагов нет.

**🟡 К валидации:**
- Ожидаемая нагрузка на `/api/admin/activity` (сколько запросов в секунду от админок).
- Конкретный маршрут эндпоинта в Arsenal API (концептуально: `/api/admin/activity`; точный путь и метод в BE-спеке).
- Точные механизмы логирования/отслеживания активности пользователей в Arsenal (кто/что собирает данные о сессиях).
