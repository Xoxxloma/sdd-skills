## 1. Обзор изменения

### 1.1. Тип и стороны

BE-only. Узел-фундамент #0 — это Backend-only контракт данных активности, который Arsenal backend предоставляет фронтальным детям (счётчик, график, выгрузка). Новое взаимодействие между Arsenal backend и фронтенд-компонентами, потребляющими данные об активности.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Собирает данные активности и отдаёт контракт | Arsenal-Core | 🟡 подтверждено аналитиком |
| Arsenal Frontend (Админка) | Потребитель контракта через три UI-компоненты (счётчик, график, выгрузка) | Arsenal-Frontend | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Фундамент обслуживает общую часть эпика ARS-100: данные об активности пользователей (текущее число активных и агрегированные показатели за период) необходимы для реализации всех пяти FR (счётчик, график, выгрузка). Контракт спроектирован один раз, разбирается детьми без изменений.

## 2. Взаимодействия (ядро)

### INT-0. Получение текущего числа активных пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Arsenal Frontend
- **Триггер:** Фронт загружает страницу админки (FR-1, счётчик), или обновляет счётчик по таймеру (FR-2), или открывает модалку (FR-3 инициирует запрос за данными).
- **Контракт (запрос):** GET `/api/arsenal/activity/current` (концептуальный путь)
  - Параметры запроса: нет
  - Авторизация: передана через заголовок Authorization; роль проверяется на бэке
- **Контракт (ответ):** 
  - `count` (int ≥ 0 или null) — число активных пользователей; null если источник недоступен (см. ошибки)
  - `timestamp` (ISO 8601) — момент снятия данных (для фронта, чтобы показать свежесть)
  - `isAvailable` (boolean) — true если данные от источника получены; false если источник недоступен (признак для UI: показать «—», не выдавать устаревшее)
- **Пример запроса:**
  ```
  GET /api/arsenal/activity/current
  Headers:
    Authorization: Bearer <token>
  ```
- **Пример ответа (успех, данные есть):**
  ```json
  {
    "count": 42,
    "timestamp": "2026-07-26T15:30:00Z",
    "isAvailable": true
  }
  ```
- **Пример ответа (успех, источник недоступен):**
  ```json
  {
    "count": null,
    "timestamp": "2026-07-26T15:30:00Z",
    "isAvailable": false
  }
  ```
- **Ошибки:**
  - 403 Forbidden — роль пользователя не «Администратор» (проверка на бэке)
  - 5xx — внутренняя ошибка бэка (обработать как недоступность источника со стороны фронта)
- **Состояния UI по ответу:**
  - `isAvailable: true, count: число ≥ 1` → `value`: показать число
  - `isAvailable: true, count: 0` → `zero`: показать «0» (валидный ноль, не «—»)
  - `isAvailable: true, count: null` → `empty`: показать «—» (данных нет, но источник доступен)
  - `isAvailable: false, count: null` → `error_source`: показать «—» и алерт об ошибке (источник недоступен)
  - 403 → `error_forbidden`: скрыть счётчик или показать «нет доступа»
  - 5xx, таймаут, сеть → `error_source`: как недоступность
- **Авторизация:** 
  - Доступно только роли «Администратор»
  - Проверка на бэке Arsenal; если роль не подходит — 403 Forbidden
  - FE должен перехватить 403 и не показать компонент (или показать placeholder «нет доступа»)
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2

### INT-1. Получение агрегированной активности за период — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Arsenal Frontend
- **Триггер:** Фронт открывает модальное окно (FR-3), переключает период графика (FR-4), или запрашивает данные для выгрузки (FR-5).
- **Контракт (запрос):** POST `/api/arsenal/activity/aggregate` (концептуальный путь)
  - Параметры запроса:
    - `period` (enum: "hour" | "day" | "week") — период агрегации
    - `endTime` (ISO 8601, опционально) — конец периода; если не указано, то текущий момент
  - Авторизация: передана через заголовок Authorization; роль проверяется на бэке
- **Контракт (ответ):**
  - `period` (enum: "hour" | "day" | "week") — отражение запрошенного периода
  - `points` (array of objects) — массив точек времени с активностью:
    - `timestamp` (ISO 8601) — момент/интервал
    - `activeUsers` (int ≥ 0 или null) — число активных пользователей в этот момент/интервал; null если нет данных за этот интервал (но разные от недоступности источника — см. `isAvailable`)
    - `sessionCount` (int ≥ 0 или null) — дополнительно: число активных сессий (для выгрузки и аналитики)
  - `startTime` (ISO 8601) — начало периода (для фронта, чтобы показать диапазон)
  - `endTime` (ISO 8601) — конец периода
  - `isAvailable` (boolean) — true если данные получены от источника; false если источник недоступен
- **Пример запроса:**
  ```json
  POST /api/arsenal/activity/aggregate
  Headers:
    Authorization: Bearer <token>
  Body:
  {
    "period": "day",
    "endTime": "2026-07-26T23:59:59Z"
  }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "period": "day",
    "points": [
      {
        "timestamp": "2026-07-26T00:00:00Z",
        "activeUsers": 5,
        "sessionCount": 8
      },
      {
        "timestamp": "2026-07-26T01:00:00Z",
        "activeUsers": 12,
        "sessionCount": 18
      },
      {
        "timestamp": "2026-07-26T02:00:00Z",
        "activeUsers": null,
        "sessionCount": null
      },
      {
        "timestamp": "2026-07-26T03:00:00Z",
        "activeUsers": 7,
        "sessionCount": 10
      }
    ],
    "startTime": "2026-07-26T00:00:00Z",
    "endTime": "2026-07-26T23:59:59Z",
    "isAvailable": true
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "period": "day",
    "points": [],
    "startTime": "2026-07-26T00:00:00Z",
    "endTime": "2026-07-26T23:59:59Z",
    "isAvailable": false
  }
  ```
- **Ошибки:**
  - 403 Forbidden — роль пользователя не «Администратор»
  - 400 Bad Request — неверный формат `period` или `endTime` (пиши в том числе пример ошибки)
  - 5xx — внутренняя ошибка бэка
- **Состояния UI по ответу (для графика и выгрузки):**
  - `isAvailable: true, points: не пусто` → `value`: отрисовать график с точками, составить выгрузку
  - `isAvailable: true, points: пусто (все null или массив пуст)` → `empty`: показать «нет данных за период» (но источник доступен)
  - `isAvailable: false, points: пусто` → `error_source`: показать «—» на графике и сообщение об ошибке (источник недоступен, нельзя показать устаревшее)
  - 403 → `error_forbidden`: скрыть модалку или показать «нет доступа»
  - 400 → `error_request`: показать сообщение об ошибке ввода (неверный период)
  - 5xx, таймаут, сеть → `error_source`: как недоступность
- **Авторизация:**
  - Доступно только роли «Администратор»
  - Проверка на бэке Arsenal; если роль не подходит — 403 Forbidden
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3, FR-4, FR-5

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 OK (но `isAvailable: false`) | `{ "count": null, "isAvailable": false, ... }` | Источник активности недоступен, данные получить не удалось | `error_source` — показать прочерк и алерт, не выдавать устаревшее |
| 200 OK (но `points: []`) | Массив точек пуст | Данные за период не собраны / период без активности | `empty` — показать прочерк или «нет данных» |
| 403 Forbidden | `{ "error": "Access denied: Administrator role required" }` | Пользователь не администратор | `error_forbidden` — скрыть компонент или показать «нет доступа» |
| 400 Bad Request | `{ "error": "Invalid period: expected 'hour', 'day', or 'week'" }` | Неверный параметр `period` (для INT-1) | `error_request` — показать сообщение ошибки |
| 5xx Server Error | Стандартная ошибка сервера | Внутренняя ошибка Arsenal Backend | `error_source` — показать алерт об ошибке сервера |
| (таймаут, сетевая ошибка) | Фронт не получил ответ в течение таймаута | Сеть / бэк не отвечает | `error_source` — показать алерт, предложить retry |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- Реализует INT-0 (GET `/api/arsenal/activity/current`): собирает текущее число активных пользователей, кэширует на 30 сек, возвращает с признаком доступности источника.
- Реализует INT-1 (POST `/api/arsenal/activity/aggregate`): собирает агрегированную активность за период (hour/day/week), считает на лету, кэширует на 30 сек, возвращает массив точек с признаком доступности.
- Обе точки требуют проверки роли «Администратор» перед возвратом данных (при недоступности роли возвращает 403).
- При недоступности источника активности (даже если кэш есть) отдаёт `isAvailable: false` и не выдаёт устаревшее значение.

### 3.2. Данные и хранение

Новых таблиц не заводим. 🟡 Данные об активности собираются Arsenal Backend-ом из существующего источника (подтверждено аналитиком, что своих допущений нет: Arsenal собирает сам). Агрегаты считаются на лету, не персистируются. Индексы и оптимизация запросов к источнику активности — на стороне Arsenal, в рамках существующей схемы.

### 3.3. Авторизация/доступ на бэке

- Оба контракта INT-0 и INT-1 защищены проверкой роли на бэке Arsenal.
- Проверка: если в токене/сессии пользователя роль ≠ «Администратор», вернуть 403 Forbidden с пояснительным сообщением.
- 🟡 Система авторизации (где и как хранятся роли) уже существует в Arsenal (подтверждено аналитиком, что роли управляются в Arsenal, новых сервисов не привлекаем).

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Три компоненты (по три детских узла):
- **Счётчик активных** (ARS-101, FR-1, FR-2): вызывает INT-0 на загрузку страницы и далее по таймеру (например, каждые 30 сек или по триггеру фронта), отображает результат в шапке админки.
- **График активности** (ARS-102, FR-3, FR-4): вызывает INT-1 с выбранным периодом, отрисовывает график по точкам `points`, позволяет переключать период (пересчитывает INT-1 с новым `period`).
- **Выгрузка** (ARS-103, FR-5): вызывает INT-1 с выбранным периодом, формирует файл на основе `points` и `sessionCount`.

Все три работают через унаследованный контракт из узла-фундамента (маркер 🟡 depends-on #0).

### 4.2. Пользовательские сценарии

1. **Основной поток (FR-1, FR-2, счётчик):**
   - Администратор открывает админку → фронт загружает страницу → вызов INT-0 → показать `count` в шапке → таймер обновления (каждые ~30 сек или по сигналу) → повторный вызов INT-0 → обновить значение в шапке.

2. **График активности (FR-3, FR-4):**
   - Администратор кликает на счётчик → открывается модальное окно → вызов INT-1 с `period: "day"` (по умолчанию) → отрисовка графика → администратор выбирает другой период (hour/week) → вызов INT-1 с новым `period` → граф перестраивается.

3. **Выгрузка (FR-5):**
   - В открытой модальке администратор нажимает кнопку Выгрузить → вызов INT-1 с текущим выбранным `period` → на основе ответа составить сводку (CSV/JSON/PDF) и скачать файл.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | Идёт запрос INT-0 или INT-1, результата ещё нет | Спиннер / скелетон на месте счётчика / графика |
| `value` | INT-0: count ≥ 1; INT-1: points не пусто и isAvailable: true | Счётчик: число активных пользователей; График: заполненный график |
| `zero` | INT-0: count = 0, isAvailable: true | Счётчик: «0» (не прочерк) |
| `empty` | INT-0: count = null, isAvailable: true; INT-1: points пусто, isAvailable: true | Счётчик / график: «—» с пояснением «нет данных» |
| `error_source` | INT-0/INT-1: isAvailable = false, или 5xx, таймаут, сеть | Счётчик / график: «—» + красный алерт «Источник данных недоступен» + кнопка retry |
| `error_forbidden` | Ответ 403 | Счётчик / модалка: не отображаются вообще, или placeholder «нет доступа» |
| `error_request` | INT-1: ответ 400 (неверный период) | График: сообщение об ошибке ввода |

### 4.3.1. Loading и таймауты

- **Cold-path (первый запрос):** 5 сек таймаут (из ответов аналитика). Если ответ не пришёл за 5 сек → переходит в состояние `error_source` с сообщением о таймауте.
- **Warm-path (последующие запросы, таймер обновления счётчика):** 5 сек таймаут. Перезапрос после таймаута (retry).
- **Polling счётчика:** Интервал примерно 30 сек (из гейта: кэш 30 сек на бэке, фронт может запрашивать чуть реже). Jitter: не нужен (синхронный запрос, не критичен).
- **При таймауте или 5xx:** показать `error_source`, предложить кнопку retry; не показывать устаревшее значение.

### 4.4. Доступ по ролям в UI

- **Администратор:** видит счётчик, может открыть модалку, может выгрузить.
- **Оператор и другие роли:** панель активности (счётчик + модалка) не отображается.
- На фронте можно предварительно скрыть компоненты по ролям (если известна роль в сессии); окончательная проверка и 403 на бэке гарантирует безопасность.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** оба контракта INT-0 и INT-1 работают синхронно (HTTP request-response, без очередей/событий). 🟡 Данные считаются на лету; сложных асинхронных процессов нет (подтверждено аналитиком).
- **Кэш:** 30 секунд на бэке Arsenal (на уровне контроллера или кэш-слоя). 🟡 Кэш живёт в бэке Arsenal, не в отдельном сервисе (подтверждено аналитиком, что своих допущений нет).
- **Таймаут запроса:** 5 сек (из гейтов). Если запрос к источнику активности + вычисления займут больше — вернуть 5xx и `isAvailable: false`.
- **Частота опроса на фронте:** счётчик обновляется из UI-таймера примерно каждые 30 сек (или реже, не критично). Граф обновляется по клику администратора на смену периода.
- **Ожидаемая нагрузка:** все админки один-два раза в день → low load на контракт; кэш на 30 сек достаточен.

### 5.2. Надёжность/деградация

- При недоступности источника активности (сеть, сервис offline, таймаут): 🟡 **не выдавать устаревшее, отдать флаг недоступности** (подтверждено аналитиком).
  - Механизм: вернуть `isAvailable: false, count: null` (INT-0) или `isAvailable: false, points: []` (INT-1).
  - Фронт показывает прочерк или сообщение об ошибке, не выдаёт администратору неправильные данные.
- 🟡 **Отдельно различать «данных за период нет» от недоступности источника** (подтверждено аналитиком).
  - Нет данных: `isAvailable: true, points: []` (источник доступен, но за период не было активности).
  - Недоступность: `isAvailable: false, points: []` (источник offline или таймаут).
- Fallback: нет. Если источник недоступен, показать «—» / алерт; нет кэширования устаревших данных.

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто имеет доступ | Как проверяется | Негативный случай |
|---------|------------------|-----------------|-------------------|
| INT-0, INT-1 | Роль «Администратор» | Проверка роли на бэке Arsenal | 403 Forbidden, панель не отображается на фронте |
| INT-0, INT-1 | Только внутри админки Arsenal | CORS / сессия / токен (по текущим механизмам Arsenal) | Внешние запросы будут заблокированы на уровне CORS/auth |

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. **Узел-фундамент #0 (текущая спека):** Deploy arsenral backend с INT-0 и INT-1.
2. **Дети (ARS-101, ARS-102, ARS-103):** Deploy фронтенд-компонентов (счётчик, график, выгрузка), которые потребляют INT-0 и INT-1.

Фундамент **раньше** потребителей. Backend выкатывается первым, чтобы фронт мог вызывать готовые контракты.

### 6.2. Обратная совместимость

- 🟡 Новые контракты INT-0 и INT-1 (подтверждено аналитиком, что это новые эндпоинты, не переделываются существующие).
- Для текущих потребителей Arsenal Backend (если есть) — новые пути `/api/arsenal/activity/current` и `/api/arsenal/activity/aggregate` не конфликтуют.
- Если в будущем потребуется изменить контракт — добавить новую версию эндпоинта (например, `/api/arsenal/activity/v2/…`), старую оставить для совместимости или явно удалить, согласовав миграцию потребителей.

### 6.3. Фиче-флаги

Флагов нет. 🟡 Контракт выкатывается атомарно: backend готов → frontend готов → включаем в админке (подтверждено аналитиком, что фиче-флаги не требуются).

### 6.4. План отката

**Откат только backend (frontend на старой версии):**
- Старый фронт пытается вызвать INT-0/INT-1 → получает 404 (эндпоинты удалены).
- Это приемлемо только если старый фронт уже обработан. Практически: требуется **синхронный откат фронта**.
- Рекомендация: откатывать BE и FE вместе (они связаны новым контрактом).

**Откат только frontend:**
- Новый backend отдаёт INT-0/INT-1, старый фронт их не вызывает → safe. Счётчик и граф исчезают, но админка работает.

**Откат DDL (down-миграция):**
- Не применимо: нет новых таблиц, миграции не нужны.
