## 1. Обзор изменения
### 1.1. Тип и стороны
Backend-only (BE-only). Узел-фундамент #0 — чистая реализация, без собственных бизнес-требований. Проектирует и отдаёт единый контракт данных активности пользователей, который потребляют дочерние узлы (фронтовые элементы: счётчик в шапке, модаль с графиком, выгрузка).

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (Backend) | Собирает и отдаёт данные активности пользователей | Команда Arsenal | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 обслуживает общие данные для FR-1 (текущий счётчик активных) и FR-2..FR-5 (графики и агрегаты за период). Контракт этого узла — единый источник для всех UI-детей; его стабильность и полнота критичны для согласованного отображения активности.

## 2. Взаимодействия (ядро)

### INT-1. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Backend (Arsenal) → Потребители (фронтовые дети: счётчик, модаль, выгрузка)
- **Триггер:** 
  - На инициализацию / загрузку страницы администратора (текущие данные).
  - На клик счётчика или переключение периода в модали (агрегаты за период).
- **Контракт (запрос):**
  - **Метод/путь (концептуально):** GET `/activity/summary` (или аналогичный в Arsenal BE).
  - **Параметры запроса:**
    - `period_type` (required): `current` | `hourly` | `daily` | `weekly` — какой срез/агрегацию запрашиваем.
    - `period_start` (required для period_type !== current): ISO 8601 дата-время (UTC).
    - `period_end` (required для period_type !== current): ISO 8601 дата-время (UTC).

- **Контракт (ответ):**
  - `status`: `"available"` | `"unavailable"` — доступность источника данных.
  - `timestamp`: ISO 8601 дата-время (UTC) — время сборки ответа.
  - `current_active_users` (int | null): текущее число активных пользователей; `null`, если статус = `unavailable` или нет данных.
  - `period_data` (object | null): 
    - Присутствует и заполнена при `period_type` !== `current` и `status` = `"available"`.
    - Null при `status` = `unavailable` или при пустом периоде.
    - Структура:
      - `period_type`: эхо запроса (`hourly` | `daily` | `weekly`).
      - `period_start`, `period_end`: границы периода (эхо запроса).
      - `data_points` (array): массив точек для графика.
        - `timestamp`: ISO 8601 (начало интервала агрегации).
        - `active_users`: int — число активных в интервале.
      - `summary`: объект с итогами периода.
        - `total_peak`: int — пик активности за период.
        - `total_average`: float — среднее за период.
        - `total_sessions`: int — всего сессий (если известно).

- **Пример запроса (текущие данные):**
  ```
  GET /activity/summary?period_type=current
  ```

- **Пример запроса (агрегаты за день):**
  ```
  GET /activity/summary?period_type=daily&period_start=2025-07-25T00:00:00Z&period_end=2025-07-26T00:00:00Z
  ```

- **Пример ответа (успех, current, данные доступны):**
  ```json
  {
    "status": "available",
    "timestamp": "2025-07-26T14:30:45Z",
    "current_active_users": 42,
    "period_data": null
  }
  ```

- **Пример ответа (успех, daily, период с данными):**
  ```json
  {
    "status": "available",
    "timestamp": "2025-07-26T14:30:45Z",
    "current_active_users": 42,
    "period_data": {
      "period_type": "daily",
      "period_start": "2025-07-25T00:00:00Z",
      "period_end": "2025-07-26T00:00:00Z",
      "data_points": [
        {"timestamp": "2025-07-25T00:00:00Z", "active_users": 5},
        {"timestamp": "2025-07-25T01:00:00Z", "active_users": 3},
        {"timestamp": "2025-07-25T02:00:00Z", "active_users": 1},
        {"timestamp": "2025-07-25T03:00:00Z", "active_users": 0},
        {"timestamp": "2025-07-25T04:00:00Z", "active_users": 8},
        {"timestamp": "2025-07-25T05:00:00Z", "active_users": 15}
      ],
      "summary": {
        "total_peak": 15,
        "total_average": 5.33,
        "total_sessions": 127
      }
    }
  }
  ```

- **Пример ответа (успех, период без данных):**
  ```json
  {
    "status": "available",
    "timestamp": "2025-07-26T14:30:45Z",
    "current_active_users": 42,
    "period_data": {
      "period_type": "daily",
      "period_start": "2099-01-01T00:00:00Z",
      "period_end": "2099-01-02T00:00:00Z",
      "data_points": [],
      "summary": {
        "total_peak": 0,
        "total_average": 0,
        "total_sessions": 0
      }
    }
  }
  ```

- **Пример ответа (ошибка, источник недоступен):**
  ```json
  {
    "status": "unavailable",
    "timestamp": "2025-07-26T14:30:45Z",
    "current_active_users": null,
    "period_data": null
  }
  ```

- **Ошибки:** (см. Каталог ошибок в конце §2)

- **Состояния UI по ответу (если есть фронт):**
  - `status="available"` + `current_active_users=<число>` → UI состояние `value` (отрисовать число).
  - `status="available"` + `current_active_users=0` → UI состояние `zero` (отрисовать «0», не прочерк).
  - `status="available"` + `current_active_users=null` + для периода `data_points=[]` → UI состояние `empty` (отрисовать «—» / «нет данных»).
  - `status="unavailable"` → UI состояние `error_source` (показать сообщение об ошибке, предложить retry).
  - Во время первого запроса / инвалидации → UI состояние `loading` (спиннер/скелетон).

- **Авторизация:** 
  - Доступ ограничен ролью **Администратор**.
  - 🟡 подтверждено аналитиком: проверка роли выполняется на стороне Arsenal BE перед возвратом данных.
  - Негативный случай: пользователь без роли Администратор получит HTTP 403 Forbidden.

- **Происхождение:** 🟢 новое (узел-фундамент #0); контракт полностью спроектирован как общий шов для всех дочерних потребителей.

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (все зависят от этого контракта для получения данных активности).

### Каталог ошибок
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 400 Bad Request | `{"error": "invalid_period_type"}` | Неизвестное значение `period_type` | error_source |
| 400 Bad Request | `{"error": "invalid_date_format"}` или `{"error": "period_start_after_period_end"}` | Неверный формат дат или период инверсирован | error_source |
| 403 Forbidden | `{"error": "forbidden"}` | Пользователь не в роли Администратор | error_forbidden |
| 500 Internal Server Error | `{"error": "source_unavailable"}` | Источник данных активности недоступен; альтернатива — ответ 2xx с `status="unavailable"` | error_source |
| 504 Gateway Timeout | (таймаут) | Превышен timeout 5 секунд при сборке ответа | error_source |

## 3. Backend — ответственность
### 3.1. По сервисам
**Arsenal (Backend):**
- Реализует INT-1: эндпоинт (или внутренний API) `/activity/summary` с поддержкой параметров `period_type`, `period_start`, `period_end`.
- Собирает данные текущей активности пользователей из внутренних источников (логирование сессий, heartbeat, или эквивалент) — источник подтверждён, 🟡 подтверждено аналитиком.
- Вычисляет агрегаты (пик, среднее, число сессий) на лету при каждом запросе (не хранит предвычисленные таблицы).
- Применяет авторизацию (роль Администратор) перед возвратом ответа.
- При недоступности источника данных активности возвращает `status="unavailable"` (2xx), не стаевшее значение.
- Кэширует ответ (на уровне обслуживающего сервиса, напр. in-memory cache) на 30 секунд.

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: **Новых таблиц не заводим.** Данные активности собираются из существующих источников (логирование сессий, heartbeat, метрики), агрегаты считаются на лету. Индексы и оптимизация доступа к историческим данным — на уровне существующей инфраструктуры сбора логов/метрик. DDL не требуется.

### 3.3. Авторизация/доступ на бэке
- 🟡 подтверждено аналитиком: перед возвратом ответа по INT-1 проверяется, имеет ли текущий пользователь роль Администратор.
- Реализация: middleware/guard на уровне Arsenal BE (деталь реализации ведется на стороне Arsenal).
- Негативный случай (403): пользователь Оператор не получит данные; фронт получит 403 и отрисует состояние `error_forbidden`.

## 4. Frontend — ответственность
Потребители данных (дочерние узлы: счётчик, модаль, выгрузка) отвечают за:
- Вызов INT-1 с нужными параметрами (текущие данные, график за период).
- Обработку состояний из §2 (value, zero, empty, error_source, error_forbidden, loading).
- Отрисовку UI элементов в соответствии с полученными данными и состояниями.
- Реализация логики переключения периодов, выгрузки, обновления счётчика — в рамках своих FR-*.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- 🟡 подтверждено аналитиком: **Синхронно.** Ответ возвращается немедленно (не асинхронно, не в фоне).
- 🟡 подтверждено аналитиком: **Кэш на 30 секунд на стороне Arsenal BE.** Каждый вызов INT-1 проверяет кэш; если кэш свежий (< 30с), возвращается кэшированный ответ; если устарел, данные пересчитываются.
- 🟡 подтверждено аналитиком: **Таймаут 5 секунд.** Если сборка ответа занимает > 5 секунд, возвращается 504 или завершение по таймауту.
- Ожидаемая нагрузка: запросы от нескольких потребителей (фронтовые дети) + периодические обновления; объём данных невелик (число + точки графика). Кэш на 30 секунд достаточен для типичных UI-паттернов (обновление счётчика на ~1 запрос в секунду, опрос за период реже).

### 5.2. Надёжность/деградация
- 🟡 подтверждено аналитиком: **При недоступности источника активности отдаём признак недоступности** (`status="unavailable"`), **а не устаревшее значение.** Фронт получит `error_source` и покажет пользователю сообщение об ошибке с предложением повторить попытку (retry).
- 🟡 подтверждено аналитиком: **Отдельно различаем «данных за период нет»** — это валидный ответ с `status="available"`, но `period_data.data_points=[]` (состояние `empty` на фронте).
- Откат: если backend недоступен, фронт переходит в `error_source` (спиннер → сообщение об ошибке).

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Как проверяется | Кто не может |
|---------|-----------|-----------------|--------------|
| INT-1 (GET /activity/summary) | Администратор | Роль на Arsenal BE | Оператор (403) |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 подтверждено аналитиком: **Фундамент выкатывается раньше потребителей.** Сначала разворачиваем Arsenal BE с INT-1, потом — дочерние узлы (UI-счётчик, модаль, выгрузка), которые будут вызывать INT-1.

### 6.2. Обратная совместимость
Узел-фундамент #0 выкатывается первым; потребители (дочерние UI-узлы) разворачиваются после, когда INT-1 уже онлайн. Никаких обратных вызовов от старых версий потребителей к новому #0 не ожидается. Когда все дети поднялись, система полностью готова.

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **Фиче-флагов нет.** Релизим атомарно (фундамент → дети).

### 6.4. План отката
- **Откат только BE (Arsenal):** INT-1 отвалилась; UI-потребители получат 500/503. Откат: развернуть предыдущую версию Arsenal без INT-1 (или отключить эндпоинт). UI-дети ждут восстановления или показывают стандартное сообщение об ошибке.
- **Откат только FE (потребители):** Arsenal продолжает работать; UI-дети откатаны. Фронт не вызывает INT-1 или показывает UI заглушку. Arsenal стоит без потребителей — OK.
- **Откат DDL:** не применимо (новых таблиц нет).

### 6.5. Преднастройка до релиза
- [x] Роли в security-сервисе — роль Администратор уже существует в Arsenal; INT-1 опирается на неё.
- [x] DDL-миграция — не требуется (новых таблиц нет).
- [x] Конфиги по окружениям — параметры кэша (30 секунд) и таймаута (5 секунд) отнести в конфиги Arsenal (dev/staging/prod могут различаться).
- [ ] Сервисные аккаунты для межсервисных вызовов — не применимо (INT-1 вызывают фронты, не другие сервисы).
- [x] Фиче-флаги — не требуются.
- [x] Алерты/мониторинг — настроить алерты на 500/504 при вызове INT-1, отслеживать время отклика (должно быть < 5 секунд), отслеживать хит-рейт кэша.

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1: Система отображает в шапке число активных пользователей | INT-1 (period_type=current) | Дано пользователь с ролью Администратор, когда он загружает админку, тогда Arsenal BE возвращает current_active_users (число или null), фронт отрисует счётчик в шапке |

| FR-4: В модальном окне администратор может переключать период графика | INT-1 (period_type=daily/hourly/weekly, период_start/end) | Дано открытую модалку, когда администратор выбирает другой период (день/неделю), тогда фронт вызывает INT-1 с новыми параметрами, получает data_points за новый период, график перестраивается |
| FR-5: В модальном окне есть кнопка выгрузки сводки активности за выбранный период в файл | INT-1 (period_type=daily/hourly/weekly) | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт использует уже полученные period_data (из INT-1) для формирования файла и скачивания; Arsenal не требует дополнительного вызова для выгрузки |
