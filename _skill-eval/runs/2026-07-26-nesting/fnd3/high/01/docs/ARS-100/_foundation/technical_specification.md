## 1. Обзор изменения

### 1.1. Тип и стороны

**BE-only узел-фундамент.** Обслуживает контракт активности пользователей для потребления дочерними фронтами администраторской панели (счётчик, график, выгрузка). Не имеет собственного фронта; реализуется как бэк-сервис со своим набором контрактов.

### 1.2. Затронутые сервисы и владельцы

| Сервис           | Роль в задаче                               | Владелец/команда | Происхождение |
|------------------|---------------------------------------------|------------------|---------------|
| Арсенал (BE)     | Собирает данные активности, отдаёт контракт | Arsenal-Core     | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Фундамент #0 обслуживает данные об активности пользователей (текущее число активных и агрегаты за период), которые требуются для реализации FR-1 (счётчик в шапке), FR-2 (обновление без перезагрузки), FR-3/FR-4 (график и выбор периода), FR-5 (выгрузка сводки). Один контракт — для всех дочерних фронтов.

## 2. Взаимодействия (ядро)

### INT-0. Получить данные активности пользователей (текущее и за период) — 🟢

- **Граница/направление:** Дочерний фронт (Арсенала) ← Бэк Арсенала (узел-фундамент #0)

- **Триггер:** 
  - Начальная загрузка страницы счётчика / модали графика
  - Переключение периода (час / день / неделя)
  - Периодический рефреш (по таймеру или событию на фронте)

- **Контракт (запрос):**
  - **Метод/путь (концептуально):** `GET /api/admin/user-activity`
  - **Параметры запроса:**
    - `period_type` (обязательно): enum — `current` | `hour` | `day` | `week`
    - `date_end` (если период != `current`): ISO 8601 дата (напр. `2026-07-26`); по умолчанию сегодня
    
- **Контракт (ответ):**
  - `current_active` (int | null): текущее число активных пользователей; `null` если источник недоступен
  - `period_type` (string): отзеркалено из запроса (для синхронизации на фронте)
  - `period_aggregates` (array | null): агрегаты активности за выбранный период; `null` если нет данных
    - каждый элемент:
      - `timestamp` (ISO 8601 datetime): мометн времени (гранулярность зависит от периода — часовая для дня, дневная для недели и т.п.)
      - `active_count` (int): число активных пользователей в этот момент
  - `period_empty` (boolean): `true` если данные за период не найдены (но источник доступен); отличает "нет данных" от "ошибка"
  - `source_unavailable` (boolean): `true` если источник активности недоступен; в этом случае `current_active` = `null`, `period_aggregates` = `null`, `period_empty` = `false`
  - `cache_metadata` (object, опционально):
    - `cached_at` (ISO 8601 datetime): время кеширования на бэке
    - `cache_valid_for_seconds` (int): TTL текущего кеша (30)

- **Пример запроса (успех, текущий счёт):**
  ```json
  {
    "period_type": "current"
  }
  ```

- **Пример ответа (успех, текущий счёт):**
  ```json
  {
    "current_active": 42,
    "period_type": "current",
    "period_aggregates": null,
    "period_empty": false,
    "source_unavailable": false,
    "cache_metadata": {
      "cached_at": "2026-07-26T14:35:10Z",
      "cache_valid_for_seconds": 30
    }
  }
  ```

- **Пример запроса (период: день):**
  ```json
  {
    "period_type": "day",
    "date_end": "2026-07-26"
  }
  ```

- **Пример ответа (успех, период с данными):**
  ```json
  {
    "current_active": 42,
    "period_type": "day",
    "period_aggregates": [
      { "timestamp": "2026-07-26T00:00:00Z", "active_count": 5 },
      { "timestamp": "2026-07-26T01:00:00Z", "active_count": 3 },
      { "timestamp": "2026-07-26T02:00:00Z", "active_count": 8 },
      { "timestamp": "2026-07-26T03:00:00Z", "active_count": 15 },
      { "timestamp": "2026-07-26T04:00:00Z", "active_count": 28 },
      { "timestamp": "2026-07-26T05:00:00Z", "active_count": 42 }
    ],
    "period_empty": false,
    "source_unavailable": false,
    "cache_metadata": {
      "cached_at": "2026-07-26T05:15:22Z",
      "cache_valid_for_seconds": 30
    }
  }
  ```

- **Пример ответа (период без данных):**
  ```json
  {
    "current_active": 42,
    "period_type": "week",
    "period_aggregates": null,
    "period_empty": true,
    "source_unavailable": false,
    "cache_metadata": {
      "cached_at": "2026-07-26T14:35:10Z",
      "cache_valid_for_seconds": 30
    }
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_active": null,
    "period_type": "current",
    "period_aggregates": null,
    "period_empty": false,
    "source_unavailable": true,
    "cache_metadata": null
  }
  ```

- **Ошибки:**

| Код | Тело/сообщение | Когда | Что показывает фронт |
|-----|----------------|-------|----------------------|
| 200 OK | (см. выше) | Запрос успешен; ответ содержит флаги `source_unavailable`, `period_empty` для разных случаев | Значение / пустой график / ошибка недоступности (см. §4.3) |
| 400 Bad Request | `{"error": "invalid_period_type"}` | Неверное значение `period_type` или отсутствует | Ошибка валидации (не должна видеться пользователю; повторить запрос) |
| 400 Bad Request | `{"error": "invalid_date_format"}` | Неверный формат `date_end` | Ошибка валидации |
| 403 Forbidden | `{"error": "insufficient_permissions"}` | Роль текущего пользователя не является администратором | Сообщение «нет доступа» |
| 500 Internal Server Error | `{"error": "service_error"}` | Необработанное исключение в бэке | Ошибка недоступности источника |
| 504 Gateway Timeout | (сеть) | Таймаут 5 секунд при обращении к источнику активности | Ошибка недоступности источника |

- **Состояния UI по ответу:**
  - **200 с `current_active` ≠ null:** состояние `value`, показать число
  - **200 с `current_active` = 0:** состояние `zero`, показать «0» (не прочерк)
  - **200 с `current_active` = null и `source_unavailable` = true:** состояние `error_source`, показать «—» и сообщение о недоступности
  - **200 с `period_empty` = true:** состояние `empty`, показать «нет данных за период» или пустой график
  - **200 с `period_aggregates` != null:** состояние `value`, отрисовать график с точками
  - **403 Forbidden:** состояние `error_forbidden`, показать «нет доступа»
  - **400, 500, 504:** состояние `error_source`, показать сообщение об ошибке + кнопка повтора

- **Авторизация:**
  - **Кто вправе:** Только пользователи с ролью «Администратор» (подтверждено аналитиком)
  - **Где проверяется:** 🟡 На бэке Арсенала, в middleware проверки ролей перед обработкой запроса (подтверждено аналитиком, не по коду; валидировать при интеграции)
  - **Негативный случай:** Если роль не администратор, вернуть 403 с сообщением `insufficient_permissions`

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (все требования основаны на этом контракте)

## 3. Backend — ответственность

### 3.1. По сервисам

**Бэк Арсенала** (узел-фундамент #0):
- 🟢 Реализует контракт INT-0: обрабатывает запросы к `GET /api/admin/user-activity`, применяет авторизацию по роли «Администратор»
- 🟡 Собирает данные активности пользователей из внутреннего источника (подтверждено аналитиком: данные собирает сам Arsenal, не привлекаем чужие сервисы)
- 🟢 Вычисляет текущее число активных пользователей (on-the-fly)
- 🟢 Вычисляет агрегаты активности за выбранный период (на лету; часовая гранулярность для периодов «день» и больше)
- 🟢 Кэширует результат в памяти бэка на 30 секунд (см. §5.1)
- 🟢 При недоступности источника возвращает `source_unavailable: true`, не выдаёт устаревшее значение (подтверждено аналитиком)

### 3.2. Данные и хранение

🟡 **Новых таблиц не заводим** (подтверждено аналитиком: агрегаты считаем на лету, никакого хранения дополнительного). Данные об активности пользователей хранятся в существующих структурах Arsenal (точная схема — 🟡 к валидации: не по коду, валидировать при интеграции).

🟢 **Кэш вычисленных агрегатов:** В памяти бэка Arsenal, время жизни 30 секунд (реализация: простой in-memory cache с TTL или аналог; стеко-агностично).

**Не применимо:** Миграции БД (данные существуют, вычисления на лету).

### 3.3. Авторизация/доступ на бэке

- 🟡 Проверка роли «Администратор» выполняется на бэке Arsenal (подтверждено аналитиком), скорее всего в middleware или в handler перед обработкой INT-0
- 🟢 Если текущий пользователь не администратор, вернуть 403 Forbidden с кодом `insufficient_permissions`
- 🟢 Пользователь не может запросить данные другого пользователя (запрос не содержит параметра `user_id`; данные — всегда по текущему юзеру или только со стороны системы)

## 4. Frontend — ответственность

**Не применимо:** фундамент BE-only. Фронтовые компоненты (счётчик, график, выгрузка) реализуют дочерние узлы; они наследуют контракт INT-0 и отображают данные согласно состояниям из §2.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** Синхронный вызов (GET) — дочерний фронт жду́т ответа перед отрисовкой
- **Кэш:** 
  - В памяти бэка Арсенала (не в отдельном сервисе)
  - TTL = 30 секунд (🟡 подтверждено аналитиком)
  - Инвалидация по TTL (стеко-агностично; стандартный подход in-memory cache)
- **Таймауты:**
  - Обращение к источнику активности: 5 секунд (🟡 подтверждено аналитиком)
  - Если таймаут превышен, вернуть `source_unavailable: true`
- **Частота опроса:** Дочерний фронт сам решает, как часто запрашивать INT-0 (напр. каждые 10 сек для счётчика, или по требованию для графика модали); контракт поддерживает оба режима
- **Ожидаемая нагрузка:** 🟡 К валидации (не по коду; оценить при интеграции на основе числа администраторов и частоты рефреша)

### 5.2. Надёжность/деградация

- **При недоступности источника активности:** 🟡 Показываем признак недоступности `source_unavailable: true`, не возвращаем устаревшее значение (подтверждено аналитиком); фронт видит состояние `error_source` и показывает соответствующее сообщение
- **Различие** между "нет данных за период" (`period_empty: true`, источник доступен) и "источник недоступен" (`source_unavailable: true`) явно заложено в контракт
- **Отсутствие обратной совместимости:** Фундамент выкатывается первым, дочерние фронты ещё не активны; нет старых потребителей, требующих поддержки старого контракта

### 5.3. Безопасность/доступ (сводно)

| Компонент | Ограничение | Проверка |
|-----------|-------------|----------|
| INT-0 запрос | Только для администраторов | На бэке Арсенала, в middleware/handler |
| INT-0 ответ | Данные общей активности (не конкретные юзеры) | Контракт не содержит PII; агрегированные числа |
| Кэш | Нет; кэш in-memory на бэке, не персонализирован | Один кэш для всех администраторов (данные одинаковые) |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟢 **Фундамент #0 выкатывается ПЕРВЫМ**, раньше всех дочерних фронтов (счётчика, графика, выгрузки). Причина: дочерние узлы опираются на контракт INT-0; он должен быть доступен, прежде чем дочерние компоненты начнут его вызывать.

**Синхронный откат:** не требуется; фундамент и дочерние узлы деплоятся отдельно в разные сервисы.

### 6.2. Обратная совместимость

🟢 **На выкате фундамента:** нет старых потребителей (дочерние узлы ещё не выкачены); новый контракт INT-0 вводится впервые; обратная совместимость не требуется.

🟡 **На выкате дочерних узлов (после #0):** Фронты начинают вызывать INT-0; если в будущем контракт нужно изменить, будет требоваться версионирование или feature-flag (не в объеме этой задачи, но учесть при проектировании дочерних узлов).

### 6.3. Фиче-флаги

🟢 **Без фиче-флагов.** Фундамент и дочерние узлы деплоятся атомарно в своём порядке (§6.1); управления видимостью через флаги не требуется.

### 6.4. План отката

- **Откат только BE (фундамента #0):** Если после выката #0, но до выката дочерних узлов, обнаружена ошибка, откатываем #0. Дочерние узлы ещё не вызывают INT-0, поэтому никому не повредит.
- **Откат только FE (дочерних узлов):** Если откатываем счётчик / график / выгрузку (дочерние узлы), фундамент #0 остаётся; при необходимости можно перевыкатить дочерние узлы позже.
- **Данные:** Фундамент не хранит новые данные; откат не требует down-миграции БД.

### 6.5. Преднастройка до релиза

- [ ] 🟡 Убедиться, что роль «Администратор» существует в системе безопасности Арсенала (подтверждено аналитиком; валидировать при интеграции)
- [ ] 🟡 Убедиться, что middleware проверки ролей работает для новых эндпоинтов (🟡 подтверждено аналитиком; валидировать)
- [ ] 🟢 Настроить in-memory cache с TTL 30 сек в бэке (если не было раньше)
- [ ] 🟢 Настроить таймаут 5 сек для запроса к источнику активности (если источник — RPC/HTTP; если БД, то по умолчанию)
- [ ] 🟡 Включить мониторинг `source_unavailable` — алерт при частых недоступностях источника (🟡 к валидации: настройка мониторинга)
- [ ] 🟢 Алерт на 500 / 504 ошибки INT-0

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс |
|----------|-------------------|-----------|
| FR-1 | INT-0 (запрос `current`, ответ `current_active`) | Дано открытую админку, когда она загружена, тогда отправляется GET /api/admin/user-activity?period_type=current и возвращается число активных ≠ null, показывается в счётчике |
| FR-2 | INT-0 (рефреш `current`) | Дано счётчик в шапке, когда число активных изменилось, тогда счётчик запрашивает INT-0 заново (каждые N сек) и обновляет отображение без перезагрузки |
| FR-3, FR-4 | INT-0 (запрос с параметром `period_type` = hour/day/week) | Дано счётчик, когда пользователь кликает и открывается модалка, тогда отправляется GET /api/admin/user-activity?period_type=day (или выбранный период) и возвращается `period_aggregates` с точками для графика |
| FR-5 | INT-0 (получение `period_aggregates`), затем выгрузка на фронте | Дано открытую модалку с графиком за период, когда пользователь нажимает выгрузку, тогда на фронте генерируется файл (CSV/JSON/иное) со сводкой; контракт INT-0 предоставляет данные, выгрузка их обрабатывает |

## 8. Допущения и открытые вопросы

**Все технические решения приняты.**

- **🟡 Подтверждено аналитиком:**
  1. Данные активности собирает бэк Арсенала сам; чужих сервисов не привлекаем
  2. При недоступности источника отдаём признак недоступности, не устаревшее значение
  3. Авторизация контракта: только роль «Администратор», проверка на бэке Арсенала
  4. Кэш 30 секунд в памяти бэка Арсенала; таймаут источника 5 секунд
  5. Синхронный контракт (GET)
  6. Фундамент выкатывается раньше потребителей; фиче-флагов нет
  7. Агрегаты активности считаем на лету, новых таблиц не заводим

- **Унаследовано из БТ (бизнес-пробелы, не меняют статус тех-спеки):** Нет.

- **Приложения из БТ:** UX-пожелание — счётчик неяркий, не отвлекает (реализуется дочерними узлами через стили).
