## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 **BE-only.** Узел-фундамент #0 предоставляет контракт данных активности (текущее число активных пользователей и агрегированные данные за период). Потребители — фронтенды детей эпика (FR-1..FR-5).

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (Backend) | Предоставляет контракт активности; собирает и агрегирует данные на лету | Arsenal Team | 🟢 новое взаимодействие |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 обеспечивает данные, необходимые для реализации FR-1..FR-5 эпика ARS-100: текущий счётчик активных пользователей (FR-1, FR-2) и агрегированную активность за период для графика и выгрузки (FR-3, FR-4, FR-5). Это общий шов, который потребляют все фронтенды эпика.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Фронтенды детей (FR-1..FR-5)
- **Триггер:** Фронтенд инициирует запрос; для FR-1/FR-2 — при загрузке и по таймеру (автообновление); для FR-3/FR-4/FR-5 — по клику и переключению периода
- **Контракт (запрос):** HTTP GET (концептуально: `/api/admin/activity`)
  - Параметры: 
    - `period` (string, обязательный): `current` | `hour` | `day` | `week` (текущее число либо агрегат за период)
    - `start` (ISO 8601, опционально): начало периода, если `period` не стандартный
    - `end` (ISO 8601, опционально): конец периода
  - Заголовки: стандартная авторизация (роль)
- **Контракт (ответ):** JSON
  - `current` (объект):
    - `count` (int ≥ 0): число активных пользователей сейчас
    - `status` (enum): `available` | `unavailable` | `no_data`
      - `available`: счёт свежий
      - `unavailable`: источник недоступен (внутренняя ошибка, сеть, таймаут)
      - `no_data`: нет данных активности за запрашиваемый период (период прошлого, данные на перегрузке)
  - `period` (объект):
    - `type` (string): `current` | `hour` | `day` | `week` (как запрошено)
    - `start` (ISO 8601): начало периода
    - `end` (ISO 8601): конец периода
    - `data_points` (array of objects, опционально если `status` = `no_data`):
      - `timestamp` (ISO 8601): момент снимка
      - `count` (int ≥ 0): число активных на этот момент
      - `status` (enum): `available` | `unavailable` | `no_data` (статус этого конкретного снимка, если есть сбой в подпериоде)
    - `status` (enum): `available` | `unavailable` | `no_data` (статус периода в целом)
- **Пример запроса:** 
  ```
  GET /api/admin/activity?period=day&start=2026-07-26T00:00:00Z&end=2026-07-26T23:59:59Z
  ```

## 3. Backend — ответственность
### 3.1. По сервисам
**Arsenal Backend:**
- 🟢 Реализует INT-0 (контракт `/api/admin/activity`).
- 🟢 Собирает данные активности пользователей собственными механизмами (не привлекает чужие сервисы — подтверждено аналитиком).
- 🟡 подтверждено аналитиком: при недоступности источника отдаёт флаг `status: unavailable`, а не устаревшее значение.
- 🟡 подтверждено аналитиком: отдельно различает `no_data` (данных за период нет) и `unavailable` (источник упал).
- 🟢 Реализует авторизацию INT-0 на уровне контракта: проверка роли "Администратор" перед отдачей данных (403 иначе).

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: **новых таблиц не заводим.** Агрегаты активности считаются на лету из существующих источников (какие именно источники — факт о существующей системе, валидировать при интеграции). Индексы для типовых запросов по временным диапазонам и активности — релевантны, но точный DDL по схеме Arsenal — на стороне Arsenal (не описываем здесь).

### 3.3. Авторизация/доступ на бэке
🟡 подтверждено аналитиком: контракт доступен только роли "Администратор", проверка выполняется на бэке Arsenal перед отдачей ответа. Роли "Оператор" и иные не имеют доступа (403 Forbidden).

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Фронтенды детей (FR-1..FR-5) потребляют контракт INT-0:
- FR-1/FR-2: счётчик активных пользователей в шапке админки (периодическое обновление)
- FR-3/FR-4/FR-5: модальное окно с графиком активности за выбранный период и выгрузка сводки

Каждый фронт отображает состояния UI согласно маппингу в INT-0 (§2, «Состояния UI по ответу»).

### 4.2. Пользовательские сценарии
Сценарии детей основаны на данных INT-0:
- **FR-1.** Администратор открывает админку → фронт загружает текущий счётчик (период = `current`) → показывает число активных.
- **FR-2.** Администратор видит счётчик в шапке → фронт периодически запрашивает обновление (период = `current`) с интервалом, согласованным с кэшем 30 сек (см. §5.1) → счётчик обновляется без перезагрузки.
- **FR-3/FR-4/FR-5.** Администратор кликает счётчик → открывается модалка; выбирает период → фронт запрашивает данные за периода (период = `hour` | `day` | `week`) → показывает график и кнопку выгрузки.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | идёт запрос данных | спиннер / скелетон |
| `value` | 200, `status: available`, `count > 0` | число/график |
| `zero` | 200, `status: available`, `count = 0` | «0» (не прочерк, не пусто) |
| `empty` | 200, `status: no_data` | прочерк «—» / «нет данных за период» |
| `error_source` | 500 / таймаут / 400 / `status: unavailable` | сообщение об ошибке + кнопка Повтор |
| `error_forbidden` | 403 | «нет доступа» |

### 4.3.1. Loading и таймауты
- **Таймаут cold-path (первый запрос при загрузке модалки):** 5 секунд → если не ответил → `error_source`, показать ошибку.
- **Таймаут warm-path (обновление счётчика в фоне по таймеру):** 5 секунд → если не ответил → остановить обновления, показать ошибку (либо оставить последнее значение с индикатором «может быть устаревшим»).
- **Polling (обновление счётчика в фоне для FR-1/FR-2):** интервал 30 сек (синхронизируется с кэшем на бэке, см. §5.1). Jitter не требуется (поскольку один потребитель, нет штампа в пики). При ошибке на одном цикле не прерывать polling — переходить в ошибку, затем при следующем цикле повторять.

### 4.4. Доступ по ролям в UI
Согласно БТ и INT-0:
- **Администратор:** видит счётчик (FR-1), график (FR-3/FR-4), выгрузку (FR-5).
- **Оператор:** панель активности не отображается (контракт возвращает 403, UI скрывает виджет).

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
🟡 подтверждено аналитиком:
- **Синхронность:** контракт INT-0 работает **синхронно** (запрос-ответ в одном цикле).
- **Кэш:** 30 секунд на стороне бэка Arsenal. Таким образом, обновления текущего счётчика отражаются с задержкой до 30 секунд.
- **Таймаут:** 5 секунд на отдачу ответа. При превышении → таймаут на фронте, состояние `error_source`.
- **Ожидаемая нагрузка:** синхронные запросы от фронтендов детей (1-2 тысячи администраторов в пиков, умеренная частота). Точные метрики и спецификация рассчитываются при проработке детей и интеграции.

### 5.2. Надёжность/деградация
🟡 подтверждено аналитиком:
- **При недоступности источника активности:** возвращаем флаг `status: unavailable` (не устаревшее значение). Фронт показывает ошибку.
- **При отсутствии данных за период:** возвращаем флаг `status: no_data`. Фронт показывает «—» / «нет данных», а не ошибку (это нормальное состояние).
- **Кэш защищает от перегрузки:** 30 сек гарантирует, что даже частые запросы одного администратора попадают в кэш.

### 5.3. Безопасность/доступ (сводно)
| Сторона | Граница | Правило | Исполнение |
|---------|---------|---------|-----------|
| Frontend → Backend (INT-0) | GET /api/admin/activity | Только роль "Администратор" | Проверка на бэке, 403 иначе |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 подтверждено аналитиком: **узел-фундамент выкатывается раньше потребителей (детей эпика).** Последовательность:
1. Развернуть Arsenal Backend с контрактом INT-0.
2. Развернуть фронтенды детей (FR-1..FR-5), которые потребляют контракт.

Это гарантирует, что фронтенды всегда работают с доступным контрактом.

### 6.2. Обратная совместимость
🟢 Контракт новый, обратная совместимость не требуется. При эволюции контракта (добавление полей, новые периоды) — использовать добавление полей, а не удаление; старые потребители игнорируют новые поля.

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **фиче-флагов нет.** Релизим атомарно: контракт доступен сразу после деплоя бэка.

### 6.4. План отката
- **Откат только BE:** фронты детей будут получать 503 / таймауты → переходят в `error_source`, показывают ошибку.
- **Откат только FE:** если фронт откачен, а BE остаётся с новым контрактом — данные остаются актуальными на бэке (кэш живёт), фронты не потребляют. Безопасно.
- **Откат DDL:** новых таблиц нет, миграций нет → откат тривиален.

### 6.5. Преднастройка до релиза
- [ ] Роли в security-сервисе: роль "Администратор" должна быть установлена/подтверждена в security-сервисе (используется при проверке 403 на бэке).
- [ ] DDL-миграция: не требуется (новых таблиц нет).
- [ ] Конфиги по окружениям: TTL кэша (30 сек) и таймаут (5 сек) — скорее всего параметры конфига бэка, финализируются при разработке Arsenal.
- [ ] Сервисные аккаунты: не требуются (Arsenal сам собирает данные, не вызывает чужие сервисы).
- [ ] Фиче-флаги: не требуются (релизим атомарно).
- [ ] Алерты/мониторинг: на 5xx / таймауты INT-0 (значительный процент ошибок может быть сигналом недоступности источника активности).

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1     | INT-0 (period=current) | Дано открытую админку, когда страница загрузилась, тогда BE отдаёт INT-0 с текущим count и status=available, фронт отображает число в шапке. |
| FR-2     | INT-0 (period=current, polling) | Дано счётчик в шапке, когда число активных пользователей изменилось на бэке (за пределами кэша 30с), тогда BE отдаёт новое значение, фронт обновляет счётчик без перезагрузки. |
| FR-3     | INT-0 (period=hour/day/week) | Дано счётчик в шапке, когда администратор кликает по нему, тогда BE отдаёт INT-0 за период по умолчанию, фронт открывает модальное окно с графиком. |
| FR-4     | INT-0 (period переключение) | Дано открытую модалку с графиком, когда администратор выбирает другой период, тогда BE отдаёт новые data_points, фронт перестраивает график. |
| FR-5     | INT-0 (периодные данные для выгрузки) | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт использует данные из INT-0 для формирования файла сводки. |

## 8. Допущения и открытые вопросы

**Все технические решения приняты, спецификация готова к разработке.**

### 🟡 Подтверждено аналитиком (не по коду; валидировать при интеграции):
- Arsenal BE собирает данные активности пользователей собственными механизмами (не привлекает чужие сервисы).
- При недоступности источника отдаём флаг `status: unavailable`, а не устаревшее значение.
- Отдельно различаем `no_data` (данных за период нет) и `unavailable` (источник упал).
- Контракт доступен только роли "Администратор", проверка на бэке Arsenal.
- Агрегаты активности считаются на лету, новых таблиц не заводим.
- Синхронно; кэш 30 сек на бэке Arsenal; таймаут 5 сек.
- Фундамент выкатывается раньше потребителей; фиче-флагов нет.
