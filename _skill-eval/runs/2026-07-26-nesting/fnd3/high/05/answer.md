## Основные компоненты спецификации

### INT-0: Получение данных активности пользователей (🟢 новое)

**Контракт:**
- Запрос: `GET /api/admin/activity?period=[current|hour|day|week]`
- Ответ содержит два блока:
  - **current:** текущее число активных пользователей + статус
  - **period:** агрегированные данные за выбранный период + массив data_points с почасовой/ежедневной детализацией + статус

**Семантика статусов:**
- `available` — данные свежие, можно использовать
- `unavailable` — источник недоступен (таймаут, сеть, ошибка), count/data_points = null
- `no_data` — данных за выбранный период нет (исторические данные ещё не собраны), count/data_points = null

**Примеры ответов** включены для трёх сценариев: успешный текущий запрос, полный дневной график, недоступность источника.

### Состояния UI (6 названных состояний)
- `loading` — идёт запрос
- `value` — успешно, число > 0
- `zero` — успешно, но count = 0 (показывать «0», не прочерк)
- `empty` — status = no_data (показывать «—» / «нет данных»)
- `error_source` — 5xx / таймаут / status = unavailable (показывать ошибку и кнопку Повтор)
- `error_forbidden` — 403 (показывать «нет доступа»)

### Авторизация и безопасность
- Роль "Администратор" — полный доступ (видит счётчик, график, выгрузку)
- Роль "Оператор" — 403 Forbidden (UI скрывает виджет)
- Проверка на бэке Arsenal

### Нефункциональные характеристики
- **Синхронность:** запрос-ответ в одном цикле
- **Кэш:** 30 сек на бэке (обновления задерживаются на 30 сек)
- **Таймаут:** 5 сек
- **Polling (для FR-1/FR-2):** интервал 30 сек (синхронизируется с кэшем); jitter не требуется
- **Откат:** безопасен в обе стороны (фронты переходят в error_state, BE остаётся стабильным)

## Примечания для реализации

1. **Точные механизмы сбора данных активности на Arsenal BE** — это 🟡 факт о существующей системе (валидировать при интеграции). Спека не предписывает, какие источники и какая логика агрегации; ответ должен иметь описанный контракт.

2. **Роль "Администратор"** должна быть установлена/подтверждена в security-сервисе до релиза (преднастройка).

3. **Дети эпика** при разработке согласно своим БТ:
   - Наследуют контракт INT-0 без изменений (никаких переопределений полей/enum'ов)
   - Оборачивают его в свои UI-состояния и пользовательские сценарии
   - Если обнаружится, что фундамент требует дополнительного поля — не менять молча, а вернуть в режим A (обновление фундамента и переразделение контракта).

4. **Порядок разработки:** сначала Arsenal Backend (INT-0), затем фронты FR-1..FR-5. BE должен быть развёрнут до FE.
