## 1. Обзор изменения

### 1.1. Тип и стороны
**BE-only.** Узел-фундамент #0 — это общий контракт данных активности пользователей, который бэк-сервис «Арсенал» предоставляет потребляющим фронт-приложениям (детским узлам). Контракт определяет форму ответа, семантику полей, обработку ошибок и авторизацию на границе BE → потребитель.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (BE) | Источник данных активности, провайдер контракта #0 | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Контракт #0 обслуживает в части данных активности все функциональные требования эпика ARS-100 (FR-1..FR-5): текущее число активных пользователей, агрегированная активность за период для графика и выгрузки. Данные собирает сам бэк Arsenal без привлечения внешних сервисов.

## 2. Взаимодействия (ядро)

### INT-1. Получение данных активности пользователей — 🟢

- **Граница/направление:** Arsenal BE → Потребитель (фронт-дети, другие BE-сервисы)
- **Триггер:** Запрос фронта при загрузке страницы администратора, периодическое обновление счётчика, переключение периода в графике.
- **Контракт (запрос):** Синхронный запрос (метод GET, концептуально: `/activity/current-and-periods`).
  - **Параметры запроса:**
    - `periods` (array[string], обязательный): список периодов для агрегации. Допустимые значения: `"hour"`, `"day"`, `"week"`, `"month"`.
    - `tz` (string, опционально): временная зона для выравнивания периодов (например, `UTC`, `Europe/Moscow`). По умолчанию — UTC.

- **Контракт (ответ):** Объект с полями:
  - `current_count` (int | null): Число активных пользователей в настоящий момент.
    - Семантика null: `null` — данные недоступны (источник недоступен); это означает, что пользователь должен увидеть пустой график или сообщение об ошибке, но НЕ устаревшее значение.
  - `is_available` (boolean): Флаг доступности источника данных.
    - `true` → данные актуальны, `current_count` и `periods` заполнены.
    - `false` → источник недоступен; `current_count` = null, `periods` = пусто; клиент показывает ошибку.
  - `periods` (object): Агрегированная активность по периодам.
    - Ключ (string): идентификатор периода (например, `hour`, `day`, `week`, `month`).
    - Значение (object): объект периода с полями:
      - `data` (array[{timestamp: string (ISO 8601), count: int}] | null): массив временных точек и значений активности.
        - Если в ответе на запрос периода не было данных (например, в выбранный день никогда не было активности), `data` = null (отличается от пустого массива).
        - Каждое значение `count` ≥ 0 (неотрицательное целое).
      - `is_available` (boolean): доступность данных за этот конкретный период.
        - `true` → `data` заполнен (может быть пусто [], но актуально).
        - `false` → `data` = null (период недоступен).
  - `cached_at` (string, ISO 8601): момент времени кэширования на стороне Arsenal (информационное, для отладки).
  - `error` (object | null): объект ошибки, если возникла.
    - `code` (string): код ошибки (см. каталог).
    - `message` (string): описание ошибки.

- **Пример запроса:**
  ```
  GET /activity/current-and-periods?periods=hour&periods=day&periods=week&tz=Europe%2FMoscow
  ```

- **Пример ответа (успех):**
  ```json
  {
    "current_count": 42,
    "is_available": true,
    "periods": {
      "hour": {
        "data": [
          {"timestamp": "2026-07-26T14:00:00Z", "count": 35},
          {"timestamp": "2026-07-26T14:15:00Z", "count": 38},
          {"timestamp": "2026-07-26T14:30:00Z", "count": 42}
        ],
        "is_available": true
      },
      "day": {
        "data": [
          {"timestamp": "2026-07-26T00:00:00Z", "count": 10},
          {"timestamp": "2026-07-26T12:00:00Z", "count": 28},
          {"timestamp": "2026-07-26T20:00:00Z", "count": 42}
        ],
        "is_available": true
      },
      "week": {
        "data": [
          {"timestamp": "2026-07-20T00:00:00Z", "count": 5},
          {"timestamp": "2026-07-23T00:00:00Z", "count": 25},
          {"timestamp": "2026-07-26T00:00:00Z", "count": 42}
        ],
        "is_available": true
      }
    },
    "cached_at": "2026-07-26T14:35:17Z",
    "error": null
  }
  ```

- **Пример ответа (недоступность источника):**
  ```json
  {
    "current_count": null,
    "is_available": false,
    "periods": {
      "hour": {"data": null, "is_available": false},
      "day": {"data": null, "is_available": false},
      "week": {"data": null, "is_available": false}
    },
    "cached_at": "2026-07-26T14:35:17Z",
    "error": {
      "code": "source_unavailable",
      "message": "Источник данных активности недоступен. Попробуйте позже."
    }
  }
  ```

- **Пример ответа (частичная доступность — период пуст):**
  ```json
  {
    "current_count": 15,
    "is_available": true,
    "periods": {
      "hour": {
        "data": [
          {"timestamp": "2026-07-26T14:00:00Z", "count": 15}
        ],
        "is_available": true
      },
      "day": {
        "data": null,
        "is_available": true
      }
    },
    "cached_at": "2026-07-26T14:35:17Z",
    "error": null
  }
  ```
  *Пояснение: за выбранный день нет данных активности (это валидный случай, `is_available=true` означает, что периодическое хранилище доступно, но данных там просто нет). Фронт отобразит пустой график, а не ошибку.*

- **Ошибки:** См. «Каталог ошибок» ниже.

- **Состояния UI по ответу (инструкция для потребителей):**
  - `is_available=true, current_count > 0` → состояние `value`: показать число активных пользователей.
  - `is_available=true, current_count=0` → состояние `zero`: показать «0» (валидный ноль, не прочерк).
  - `is_available=true, current_count=null, data=null (для периода)` → состояние `empty`: показать прочерк «—» / «нет данных».
  - `is_available=false` → состояние `error_source`: показать сообщение об ошибке из `error.message` + предложение повторить.
  - При загрузке → состояние `loading`: спиннер/скелетон.

- **Авторизация:** 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
  - **Кто вправе:** Роль `Administrator` (только администраторы системы Arsenal).
  - **Где проверяется:** На стороне бэка Arsenal при обработке запроса. Проверка выполняется до того, как начинается подготовка данных.
  - **Негативный случай (403 Forbidden):** Если потребитель (или его роль) не имеет прав, возвращается `403` с сообщением об ошибке (см. каталог).

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (эпик ARS-100)

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI | HTTP код |
|-----|----------------|-------|--------------|----------|
| `source_unavailable` | «Источник данных активности недоступен. Попробуйте позже.» | Сервис сбора активности или БД недоступны | `error_source` | 500 |
| `access_denied` | «Нет доступа к данным активности. Требуется роль администратора.» | Потребитель не имеет роли `Administrator` | `error_forbidden` | 403 |
| `invalid_periods` | «Некорректный список периодов: допустимы hour, day, week, month.» | Переданы недопустимые значения `periods` | `error_source` | 400 |
| `timeout` | «Превышено время ожидания ответа. Попробуйте позже.» | Запрос к источнику данных занял > 5 сек | `error_source` | 504 |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal BE:**
- Реализует эндпоинт INT-1 (🟢): `/activity/current-and-periods`.
- Собирает и агрегирует данные активности пользователей самостоятельно (🟡 подтверждено аналитиком: чужих сервисов не привлекаем).
- Вычисляет агрегаты `current_count` и `periods[*].data` на лету при каждом запросе (нет отдельного хранилища агрегатов).
- Обеспечивает кэширование ответа (30 сек, см. §5.1).
- Проверяет авторизацию по ролям (только `Administrator`).
- Обрабатывает недоступность источника, возвращая `is_available=false` вместо устаревших данных.

### 3.2. Данные и хранение

**Новых таблиц/сущностей не заводим.** 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)

Агрегаты активности рассчитываются на лету из существующих данных о пользовательских сессиях. Миграции не требуются. Точные источники данных сессий и схему их хранения уточнить при интеграции (🟡 к валидации).

### 3.3. Авторизация/доступ на бэке

🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- Проверка выполняется перед обработкой запроса: если роль потребителя ≠ `Administrator`, возвращается HTTP 403 с кодом ошибки `access_denied`.
- Роль извлекается из контекста аутентификации (механизм — уточнить при интеграции).
- Нет частичного доступа: либо полный доступ к полному контракту, либо 403.

## 4. Frontend — ответственность

Не применимо на уровне фундамента #0. Потребляющие фронт-приложения (дети) реализуют пользовательский интерфейс, опираясь на контракт INT-1.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Синхронность:** Запрос синхронный (GET).
- **Кэш:** На стороне бэка Arsenal. TTL = 30 секунд. Все потребители получают закэшированный ответ в пределах окна кэша.
- **Таймаут:** 5 секунд. Если запрос к источнику данных превышает таймаут, вернуть ошибку `timeout` (HTTP 504).
- **Ожидаемая нагрузка:** Уточнить при интеграции (🟡 к валидации: сколько одновременных потребителей, какие пики нагрузки).
- **Производительность:** Агрегация на лету без преддия должна завершиться в пределах таймаута. Если становится узким местом — рассмотреть предварительное вычисление (за пределами текущего скопа).

### 5.2. Надёжность/деградация

🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **При недоступности источника:** Вернуть `is_available=false` + `error.code="source_unavailable"`, а не кэшированное устаревшее значение. Пользователь получит сообщение об ошибке и сможет повторить запрос.
- **Различие между «нет данных за период» и «недоступностью»:** Оба случая возвращают `data=null`, но:
  - Нет данных → `is_available=true` (источник работает, но данных нет за этот период).
  - Недоступность → `is_available=false` (источник не доступен вообще).
- **Мониторинг:** Алерты на ошибки `source_unavailable` и таймауты (см. §6.5).

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Что видит | Проверка |
|---------|-----------|-----------|----------|
| INT-1 (BE → потребитель) | Роль `Administrator` | Полный контракт (текущий счёт, графики, ошибки) | На бэке Arsenal, HTTP 403 при отказе |
| INT-1 (BE → потребитель) | Другие роли | Ничего | HTTP 403 |

## 6. Релиз и интеграция

🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Узел-фундамент #0 выкатывается ПЕРВЫМ**, до всех потребляющих детских узлов.
- Причина: дети опираются на контракт #0 и должны найти его в production перед своим развёртыванием.
- Детские узлы (фронт-приложения) развёртываются после #0.

### 6.2. Обратная совместимость

Фундамент #0 — новый контракт, обратную совместимость сохранять не требуется. Потребители получают актуальную версию контракта с момента развёртывания.

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- Фиче-флаги не используются. Контракт #0 релизится атомарно (полностью или не выкатывается).

### 6.4. План отката

Не применимо: фундамент #0 — BE-only контракт. Откат, если понадобится, выполняется на стороне бэка Arsenal; потребители получают ошибку `source_unavailable` до откат завершения.

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-1 | Дано открыта админка и пользователь имеет роль Administrator, когда загружается страница, тогда на бэк поступает запрос INT-1 и фронт получает `current_count` > 0, отображает число в шапке. |
| FR-2 | INT-1 | Дано открыта админка со счётчиком, когда активность пользователей меняется и кэш истекает (>30 сек), тогда следующий запрос INT-1 возвращает новое значение `current_count`, счётчик обновляется без перезагрузки в пределах минуты. |
| FR-3 | INT-1 | Дано счётчик в шапке, когда администратор кликает на счётчик, тогда фронт отправляет INT-1 с `periods=[hour, day, week]`, получает агрегаты, модальное окно откроется с графиком. |
| FR-4 | INT-1 | Дано открыта модалка с графиком, когда администратор выбирает другой период, тогда фронт отправляет новый INT-1 запрос, получает агрегаты за выбранный период, график перестраивается. |
| FR-5 | INT-1 | Дано открыта модалка с выбранным периодом, когда администратор нажимает кнопку выгрузки, тогда фронт готовит сводку из полученных ранее данных INT-1 (по `periods[*].data`) и предлагает её для скачивания. |

## 8. Допущения и открытые вопросы

**🟡 Подтверждено аналитиком (не по коду, валидировать при интеграции):**
- Бэк Arsenal собирает данные активности пользователей самостоятельно, без привлечения внешних сервисов.
- При недоступности источника возвращается флаг `is_available=false`, а не устаревшее кэшированное значение.
- Авторизация проверяется по ролям: только роль `Administrator` имеет доступ к контракту INT-1.
- Кэш живёт 30 секунд на стороне бэка Arsenal.
- Таймаут запроса — 5 секунд.
- Агрегаты рассчитываются на лету, новых таблиц не заводим.
- Фиче-флаги не используются, релизим атомарно.

**🟡 К валидации (уточнить при интеграции):**
- Точные источники данных пользовательских сессий и их схема хранения в Arsenal.
- Механизм управления ролью `Administrator` в security-сервисе Arsenal.
- Ожидаемая нагрузка: количество одновременных потребителей, пики нагрузки, требования к задержке отклика.
- Если производительность агрегации на лету становится узким местом, рассмотреть оптимизацию (предварительное вычисление, асинхронные обновления — в следующих итерациях).

**Унаследовано из БТ (бизнес-пробелы, закрываются на стороне БТ, не влияют на статус спеки):**
- Пожелание по UX: счётчик должен быть неярким, не отвлекает от основной работы (реализуется на стороне потребляющего фронта, в детских узлах).
