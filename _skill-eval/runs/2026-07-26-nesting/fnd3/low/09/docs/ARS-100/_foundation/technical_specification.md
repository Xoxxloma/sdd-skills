## 1. Обзор изменения
### 1.1. Тип и стороны
BE-only. Узел-фундамент #0 предоставляет контракт данных активности пользователей (текущее число активных + агрегаты за период). Потребители — фронты дочерних узлов (ARS-101, ARS-102, ARS-103). Сам бэк «Арсенала» является источником и владельцем данных.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | Источник и поставщик данных активности; вычисляет агрегаты на лету | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Фундамент реализует общий источник данных активности, обслуживающий FR-1…FR-5 эпика: текущее число активных пользователей и динамика за период требуются счётчику (FR-1, FR-2), графику (FR-3, FR-4) и выгрузке (FR-5).

## 2. Взаимодействия (ядро)

### INT-0. Получение текущего числа активных пользователей и агрегатов активности за период — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Backend Arsenal → Фронт дочерних узлов (ARS-101, ARS-102, ARS-103)
- **Триггер:** (1) Загрузка страницы администратора; (2) Обновление UI без перезагрузки (polling); (3) Запрос график для выбранного периода
- **Контракт (запрос):** 
  - **Метод:** GET (концептуально; стеко-агностично)
  - **Параметры:**
    - `start_ts` (обязателен, число): Unix timestamp начала периода (мс)
    - `end_ts` (обязателен, число): Unix timestamp конца периода (мс)
    - `period_type` (опционально, строка, enum): `hour` | `day` | `week` (подсказка для укруп­ления бакетов; сервер может вернуть данные за фиксированные интервалы на основе периода)
  - Авторизация: заголовок запроса (стандартная, подтверждена на бэке; подробнее в авторизации ниже)

- **Контракт (ответ):**
  - `status` (строка, обязателен): статус ответа
    - Значения: `success` (данные получены) | `unavailable_source` (источник недоступен) | `no_data_for_period` (нет данных за выбранный период)
  - `current_active_count` (число или null, опционально): текущее число активных пользователей в этот момент (только в момент запроса, не историческое)
    - Семантика null: невозможно определить текущее число (источник недоступен)
    - Диапазон: ≥ 0 (неотрицательное целое)
  - `aggregates` (массив, опционально): агрегированная активность за период
    - Элемент массива:
      - `timestamp` (число, обязателен): Unix timestamp начала интервала (мс)
      - `duration_minutes` (число, обязателен): длительность интервала в минутах (для удобства фронта)
      - `active_count` (число, обязателен): число активных пользователей в этом интервале
        - Семантика: это число эвристическое (на основе логов/событий за интервал), гарантированно ≥ 0
      - `sessions_started` (число, опционально): число новых сессий, начатых в интервале (для аналитики)
      - `sessions_ended` (число, опционально): число закончившихся сессий в интервале
  - `period_info` (объект, опционально): метаинформация о периоде
    - `start_ts` (число, обязателен): эхо переданного start_ts
    - `end_ts` (число, обязателен): эхо переданного end_ts
    - `actual_granularity_seconds` (число, обязателен): реальная гранулярность данных в ответе (напр. 300 для 5-минутных бакетов, 60 для 1-минутных)
  - `error_code` (строка, опционально): код ошибки, если status ≠ `success` (подробнее см. Ошибки)
  - `error_message` (строка, опционально): читаемое описание ошибки (только для логирования и отладки, UI не показывает)

- **Пример запроса:**
  ```
  GET /api/arsenal/activity/stats
  ?start_ts=1690000000000&end_ts=1690086400000&period_type=day
  Authorization: Bearer <token> (или заголовок вида X-Session-Id, по текущей схеме Arsenal)
  ```

- **Пример ответа (успех — текущее число + график):**
  ```json
  {
    "status": "success",
    "current_active_count": 42,
    "aggregates": [
      {
        "timestamp": 1690000000000,
        "duration_minutes": 60,
        "active_count": 35,
        "sessions_started": 5,
        "sessions_ended": 3
      },
      {
        "timestamp": 1690003600000,
        "duration_minutes": 60,
        "active_count": 40,
        "sessions_started": 8,
        "sessions_ended": 2
      },
      {
        "timestamp": 1690007200000,
        "duration_minutes": 60,
        "active_count": 45,
        "sessions_started": 6,
        "sessions_ended": 1
      }
    ],
    "period_info": {
      "start_ts": 1690000000000,
      "end_ts": 1690086400000,
      "actual_granularity_seconds": 3600
    }
  }
  ```

- **Пример ответа (нет данных за период):**
  ```json
  {
    "status": "no_data_for_period",
    "current_active_count": null,
    "aggregates": [],
    "period_info": {
      "start_ts": 1690000000000,
      "end_ts": 1690086400000,
      "actual_granularity_seconds": null
    }
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "status": "unavailable_source",
    "current_active_count": null,
    "aggregates": null,
    "period_info": null,
    "error_code": "SOURCE_TIMEOUT",
    "error_message": "Could not reach session tracking service (timeout after 5s)"
  }
  ```

- **Ошибки:**
  | Код | Тело/сообщение | Когда | Состояние UI потребителя |
  |-----|----------------|-------|----------|
  | `SUCCESS` | status: "success", данные в aggregates | Данные получены успешно | `value` (если active_count > 0) / `zero` (если активных = 0) |
  | `NO_DATA_FOR_PERIOD` | status: "no_data_for_period", aggregates: [], error_code: null | За выбранный период в системе нет записей активности (в т.ч. первые часы после деплоя) | `empty` (пусто, показать «—» или «нет данных») |
  | `SOURCE_TIMEOUT` | 408 (или 5xx в зависимости от имплементации), status: "unavailable_source", error_code: "SOURCE_TIMEOUT" | Таймаут при обращении к источнику (5 секунд на BE Arsenal) | `error_source` (показать «ошибка, повторить») |
  | `SOURCE_ERROR` | 5xx, status: "unavailable_source", error_code: "SOURCE_ERROR" | Внутренняя ошибка источника (сервиса отслеживания сессий) | `error_source` |
  | `FORBIDDEN` | 403, status: (не дополняется), error_code: "FORBIDDEN" | Пользователь не является администратором | `error_forbidden` (показать «нет доступа») |

- **Состояния UI по ответу (если есть фронт):**
  - `loading` → спиннер/скелетон
  - `value` → status = success, current_active_count > 0 или aggregates.length > 0 → показать число/график
  - `zero` → status = success, current_active_count = 0 и aggregates существуют → показать «0» (не «—»)
  - `empty` → status = no_data_for_period, или aggregates.length = 0 при success → показать «—»/«нет данных»
  - `error_source` → status = unavailable_source → показать сообщение об ошибке + кнопка retry
  - `error_forbidden` → error_code = FORBIDDEN → показать «нет доступа»

- **Авторизация:** 
  - Контракт доступен только роли **Администратор** на стороне BE Arsenal
  - 🟡 подтверждено аналитиком: проверка роли выполняется на бэке Arsenal перед отдачей данных (используется существующий механизм ролевого управления)
  - Негативный случай (не администратор): возвращается 403 с error_code: "FORBIDDEN"

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (текущее число активных), FR-2 (обновление без перезагрузки), FR-3 (загрузка графика при открытии модалки), FR-4 (переключение периода), FR-5 (данные для выгрузки)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|------------|
| `SUCCESS` | 2xx, status: "success" | Данные получены | `value` / `zero` (в зависимости от count) |
| `NO_DATA_FOR_PERIOD` | 2xx, status: "no_data_for_period" | За период нет записей | `empty` |
| `SOURCE_TIMEOUT` | 5xx (или 408), status: "unavailable_source", error_code: "SOURCE_TIMEOUT" | Таймаут 5с при обращении к источнику | `error_source` |
| `SOURCE_ERROR` | 5xx, status: "unavailable_source", error_code: "SOURCE_ERROR" | Ошибка источника | `error_source` |
| `FORBIDDEN` | 403, error_code: "FORBIDDEN" | Недостаточная роль | `error_forbidden` |

## 3. Backend — ответственность

### 3.1. По сервисам
**Backend Arsenal** реализует INT-0 (контракт данных активности):
- Предоставляет эндпоинт GET `/api/arsenal/activity/stats` (или эквивалент по схеме Arsenal) для получения текущего числа активных пользователей и агрегированной активности за период
- 🟡 подтверждено аналитиком: бэк Arsenal собирает данные активности сам (не привлекает сторонние сервисы; используется существующий механизм отслеживания сессий)
- Вычисляет агрегаты на лету (не создаёт новые таблицы)
- Кэширует результат на 30 секунд на стороне BE Arsenal
- Таймаут запроса к источнику: 5 секунд
- Проверяет роль **Администратор** перед отдачей данных

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: **новых сущностей и таблиц не создаётся**. Узел-фундамент #0 опирается на существующий механизм отслеживания сессий (логи, события) в бэке Arsenal. Агрегаты вычисляются на лету из этих логов при каждом запросе.

- **Индексы:** 🟡 подтверждено аналитиком (к валидации при интеграции): существующие индексы по временным меткам (timestamp) в таблице сессий/логов достаточны для эффективного агрегирования за период
- **Retention:** 🟡 подтверждено аналитиком: определяется существующей политикой хранения сессий в Arsenal (обычно 90 дней или по конфигу)
- **Миграции БД:** не требуются

### 3.3. Авторизация/доступ на бэке
- Роль **Администратор** (из существующей модели ролей Arsenal): имеет доступ к эндпоинту
- Проверка роли выполняется на бэке Arsenal перед обработкой запроса
- Другие роли (Оператор и т.п.) получают 403 FORBIDDEN
- 🟡 подтверждено аналитиком: механизм ролевого управления в Arsenal уже реализован и используется для других эндпоинтов

## 4. Frontend — ответственность
Не применимо: узел-фундамент #0 — это BE-only контракт. Фронты дочерних узлов (ARS-101, ARS-102, ARS-103) наследуют этот контракт и реализуют свой UI относительно него.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
- **Синхронность:** 🟢 синхронный запрос (блокирующий)
- **Кэш:** 🟡 подтверждено аналитиком — 30-секундный кэш на стороне BE Arsenal (на уровне приложения или проксирующего слоя)
  - Инвалидация: по TTL (30 сек), явная инвалидация при фоновом обновлении логов (если применимо)
- **Таймауты:**
  - Таймаут запроса к источнику (логам сессий): 🟡 подтверждено аналитиком — **5 секунд**
  - Таймаут для холодного пути (первый запрос): фронт должен ожидать не более 5 секунд + сетевая задержка (на фронте считать TBD, в BE это 5с)
  - Таймаут для тёплого пути (из кэша): < 100 мс (кэш лежит в памяти BE)
- **Ожидаемая нагрузка:** 🟡 подтверждено аналитиком — умеренная (дочерние узлы опрашивают этот эндпоинт при загрузке и при переключении периода); кэш на 30 сек должен скрыть всплески от одновременных запросов разных админов

### 5.2. Надёжность/деградация
- **При недоступности источника (таймаут 5 сек):** 🟡 подтверждено аналитиком — отдаём признак недоступности (`status: "unavailable_source"`), **НЕ** устаревшее кэшированное значение
  - Фронт видит состояние `error_source` и показывает ошибку + retry
- **Отдельно различаем случаи:**
  - `no_data_for_period` — данных за период нет в базе (фронт видит `empty`, показывает «—»)
  - `unavailable_source` — источник был недоступен прямо сейчас (фронт видит `error_source`, предлагает retry)
  - Кэш **не используется** при недоступности (т.е. если источник упал, даже если есть кэшированное значение из 29 сек назад, мы отдаём ошибку)

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Как проверяется | Что не может |
|---------|-----------|-----------------|--------------|
| GET `/api/arsenal/activity/stats` | Администратор | Роль на бэке Arsenal | Оператор, гост (403) |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟡 подтверждено аналитиком: **узел-фундамент #0 выкатывается раньше дочерних узлов** (ARS-101, ARS-102, ARS-103). 
- Причина: дочерние узлы наследуют контракт INT-0 и не могут работать без него. Фундамент должен быть доступен до того, как фронты начнут запрашивать эти данные.

### 6.2. Обратная совместимость
- Новый эндпоинт, не трогаем существующие
- Добавление новых полей в ответ (`sessions_started`, `sessions_ended`, `error_message`) не ломает старые потребители (если они были), т.к. эти поля опциональны

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **фиче-флагов нет**, релизим атомарно. Контракт INT-0 либо доступен полностью, либо вообще не доступен (после деплоя фундамента).

### 6.4. План отката
Не применимо: узел-фундамент #0 — это чистая реализация BE (никаких FE-зависимостей). Откат BE кода вернёт на старое поведение (эндпоинт недоступен или возвращает старую схему).

### 6.5. Преднастройка до релиза
- [ ] Роль **Администратор** должна существовать в security-сервисе Arsenal (🟡 подтверждено аналитиком: уже есть)
- [ ] Конфиг для кэша (TTL = 30 сек) и таймаута (5 сек) в окружениях dev/staging/prod
- [ ] Мониторинг/алерты на ошибки (5xx, `SOURCE_TIMEOUT`, отсутствие данных за период) на эндпоинте `/api/arsenal/activity/stats`
- [ ] Логирование запросов (для отладки)

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|-------------------------------|
| FR-1 | INT-0 | Дано: открытая админка, когда страница загрузилась, тогда фронт (потребитель) вызывает INT-0 и получает current_active_count, фронт отображает это число в шапке |
| FR-2 | INT-0 | Дано: открытая админка, когда число активных изменилось на бэке, тогда фронт (потребитель) периодически опрашивает INT-0 (polling), получает обновлённое значение, счётчик обновляется без перезагрузки в пределах 30 сек (кэш) + 1 опрос |
| FR-3 | INT-0 | Дано: счётчик в шапке, когда администратор кликает по нему, тогда фронт (потребитель) открывает модалку и вызывает INT-0 с периодом (start_ts/end_ts), получает aggregates, отображает график |
| FR-4 | INT-0 | Дано: открытую модалку, когда администратор выбирает другой период, тогда фронт вызывает INT-0 с новыми start_ts/end_ts и period_type, получает aggregates, график перестраивается |
| FR-5 | INT-0 | Дано: открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт (потребитель) вызывает INT-0, получает aggregates за период, формирует и скачивает файл сводки |
