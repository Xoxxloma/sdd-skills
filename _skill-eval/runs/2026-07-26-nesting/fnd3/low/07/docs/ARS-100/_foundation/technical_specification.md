## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 **BE-only узел-фундамент**: бэк-сервис «Arsenal» предоставляет контракт данных активности пользователей, который потребляют фронты дочерних задач (счётчик, график, выгрузка). Это чистая реализация общей границы, обслуживающей FR-1…FR-5 эпика в части сбора и агрегации данных активности.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (бэк) | Реализует контракт данных активности, собирает текущее число активных пользователей и считает агрегаты за период | Команда Arsenal | 🟡 подтверждено аналитиком (собирает данные сам, внешних зависимостей нет) |

### 1.3. Связь с бизнес-требованиями
Обслуживает FR-1…FR-5 эпика ARS-100 в части базового контракта данных активности. Счётчик (FR-1), автообновление (FR-2), график за период (FR-3..FR-4) и выгрузка (FR-5) строятся поверх этого единого контракта, поэтому контракт проектируется один раз и наследуется всеми детскими задачами.

## 2. Взаимодействия (ядро — контракт фундамента)
> Единая 🟢 новая граница: дочерние фронты потребляют данные активности от бэка Arsenal.

### INT-0. Получение данных активности пользователей (текущее + агрегаты периода) — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** FE (дочерний фронт) → BE (Arsenal)
- **Триггер:** инициирует дочерний фронт при загрузке, периодическом обновлении счётчика (FR-1, FR-2) или смене периода в графике (FR-4)
- **Контракт (запрос):** `GET /api/activity`
  - **Параметры:**
    - `period`: `hour` | `day` | `week` — гранулярность агрегации (обязательный)
    - `start_time`: ISO 8601 timestamp — начало периода для выборки данных (опциональный; если не указан, используется «сейчас»)
    - `end_time`: ISO 8601 timestamp — конец периода для выборки данных (опциональный; если не указан, используется «сейчас»)

- **Контракт (ответ):** 
  - **current_active_users**: `number | null` — текущее число активных пользователей; `null` если источник недоступен
  - **is_available**: `boolean` — флаг доступности источника (true = данные свежие; false = источник недоступен, значения могут быть устаревшими или отсутствовать)
  - **has_data_for_period**: `boolean` — флаг наличия данных за запрошенный период (true = есть данные; false = за этот период данных нет)
  - **aggregates**: array of objects — агрегированные данные активности по гранулам периода
    - `timestamp`: ISO 8601 timestamp — начало гранулы (часа/дня/недели в зависимости от `period`)
    - `active_count`: `number` — число активных пользователей в эту гранулу
  - **period_total**: `number` — сумма активных пользователей за весь запрошенный период (вспомогательное поле для сводки/выгрузки)
  - **message**: `string | null` — пояснительное сообщение в случае ошибок (напр. «источник недоступен», «нет данных за период»)

- **Пример запроса:**
  ```
  GET /api/activity?period=day&start_time=2026-07-24T00:00:00Z&end_time=2026-07-26T23:59:59Z
  ```

- **Пример ответа (успех, данные доступны):**
  ```json
  {
    "current_active_users": 1247,
    "is_available": true,
    "has_data_for_period": true,
    "aggregates": [
      {
        "timestamp": "2026-07-24T00:00:00Z",
        "active_count": 890
      },
      {
        "timestamp": "2026-07-25T00:00:00Z",
        "active_count": 1150
      },
      {
        "timestamp": "2026-07-26T00:00:00Z",
        "active_count": 1247
      }
    ],
    "period_total": 3287,
    "message": null
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_active_users": null,
    "is_available": false,
    "has_data_for_period": false,
    "aggregates": [],
    "period_total": 0,
    "message": "источник данных активности недоступен, повторите попытку"
  }
  ```

- **Пример ответа (данные доступны, но за период нет записей):**
  ```json
  {
    "current_active_users": 42,
    "is_available": true,
    "has_data_for_period": false,
    "aggregates": [],
    "period_total": 0,
    "message": "за выбранный период данных активности не найдено"
  }
  ```

- **Ошибки:**
  - **200 OK** — успех (даже если `is_available: false` или `has_data_for_period: false` — в теле есть флаги, фронт их обрабатывает)
  - **400 Bad Request** — невалидные параметры (напр. неверный формат `period` или timestamps); тело: `{"error": "invalid_period", "message": "…"}`
  - **403 Forbidden** — вызывающий не имеет роли «Администратор»; тело: `{"error": "access_denied", "message": "только администраторы могут запрашивать данные активности"}`
  - **500 Internal Server Error** — внутренняя ошибка бэка Arsenal (не путать с недоступностью *источника* — см. `is_available`); тело: `{"error": "internal_error", "message": "…"}`
  - **504 Gateway Timeout** — таймаут при запросе к источнику (если такой есть) или внутренний таймаут (5 сек); фронт должен обработать как `is_available: false`

- **Состояния UI по ответу (для детских фронтов):**
  - `value` — 200, `is_available: true`, `has_data_for_period: true` → показать `current_active_users` и `aggregates`
  - `loading` — запрос в полёте → спиннер/скелетон
  - `empty` — 200, `has_data_for_period: false` → показать «—» / «нет данных»
  - `zero` — 200, `current_active_users: 0`, `is_available: true` → показать `0` (не «—»)
  - `error_source` — 504, 500 или `is_available: false` → сообщение об ошибке + retry
  - `error_forbidden` — 403 → сообщение «нет доступа»

- **Авторизация:**
  - 🟡 подтверждено аналитиком: только роль «Администратор» имеет доступ; проверка на бэке Arsenal (по сессии/JWT).
  - Отрицательный случай (не админ) → 403 Forbidden.

- **Происхождение:** 🟢 новое (узел-фундамент #0, единый контракт, наследуется детьми ARS-101, ARS-102, ARS-103)

## 3. Backend — ответственность
### 3.1. По сервисам
**Arsenal (бэк):**
- 🟡 подтверждено аналитиком: реализует эндпоинт `GET /api/activity` согласно INT-0, возвращает контракт из §2.
- 🟡 подтверждено аналитиком: собирает данные активности пользователей сам, внешних сервисов не привлекает (своих допущений нет).
- 🟢 новое: вычисляет текущее число активных пользователей на лету в момент запроса.
- 🟢 новое: агрегирует активность по гранулам (часы/дни/недели) на лету — постоянного хранилища агрегатов не создаёт.
- 🟢 новое: обрабатывает флаги доступности источника (если источник недостижим → `is_available: false`, `current_active_users: null`).
- 🟢 новое: различает два состояния отсутствия данных:
  - источник недоступен (network/timeout/5xx) → `is_available: false`
  - источник доступен, но за период нет активности → `is_available: true`, `has_data_for_period: false`

### 3.2. Данные и хранение
🟢 **Новых таблиц не заводятся.** Arsenal уже имеет источник данных активности (логи сессий, события входа/выхода или иное); спецификация не предусматривает создание отдельного хранилища агрегатов. 
- Текущее число активных пользователей вычисляется на лету (напр., SELECT COUNT DISTINCT user_id WHERE session_active = true).
- Агрегаты за период вычисляются на лету при каждом запросе (GROUP BY по гранулам периода из существующего источника).
- 🟡 подтверждено аналитиком: хранилище и структура источника — на стороне Arsenal, спецификация не вводит ограничений; ответственность бэка удостовериться, что данные достаточно свежие и доступны за требуемые периоды.

### 3.3. Авторизация/доступ на бэке
- 🟡 подтверждено аналитиком: доступ проверяется на бэке Arsenal по текущей сессии/токену перед ответом.
- Только пользователи с ролью «Администратор» получают 200 и данные.
- Остальные ролевые поля (напр. Оператор) получают 403 Forbidden без деталей (не раскрывать, что эндпоинт существует).

## 4. Frontend — ответственность (для дочерних задач)
### 4.1. Наследование контракта
Дочерние фронты (ARS-101, ARS-102, ARS-103) используют этот контракт INT-0 как основу:
- ARS-101 (счётчик + автообновление) → вызывает INT-0 при загрузке и по таймеру (раз в ~10–15 сек для FR-2), отображает `current_active_users`.
- ARS-102 (график за период) → вызывает INT-0 с указанным `period` и диапазоном дат (FR-3, FR-4), отображает `aggregates`.
- ARS-103 (выгрузка сводки) → вызывает INT-0 с нужным периодом (FR-5), использует `aggregates` и `period_total` для генерации файла.

Детали реализации (компоненты, состояния, УХ) — в спецификациях соответствующих дочерних задач; здесь закреплены только общие состояния из §2.

### 4.2. Обработка состояний
Все дочерние фронты должны различать 6 состояний из §2 («Состояния UI по ответу») и отображать соответствующий UI:
- `value` → показать число, график или включить кнопку выгрузки с учётом `current_active_users`, `aggregates`, `period_total`.
- `empty` → показать «—» / placeholder / отключить кнопку выгрузки.
- `zero` → показать `0` (не путать с `empty`).
- `error_source` / `error_forbidden` → сообщение об ошибке, retry-кнопка или скрытие панели.
- `loading` → спиннер до получения первого ответа.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- 🟡 подтверждено аналитиком: **синхронный** вызов (фронт ждёт ответа, не асинхронная фоновая загрузка).
- 🟡 подтверждено аналитиком: **кэш 30 сек** на стороне бэка Arsenal: если две сессии запрашивают `GET /api/activity` с одинаковыми параметрами в течение 30 сек, вторая получает кэшированный ответ первого (без пересчёта агрегатов).
- 🟡 подтверждено аналитиком: **таймаут 5 сек** на запрос в целом; если ответ не получен за 5 сек, фронт получает таймаут (504 или эквивалент), трактует как `is_available: false`.
- Ожидаемая нагрузка: админка используется нечасто (несколько раз в смену), не требуется оптимизация под DDoS; кэш 30 сек достаточен для удобства.

### 5.2. Надёжность/деградация
- 🟡 подтверждено аналитиком: при недоступности источника (timeout, 5xx, сеть) возвращается **флаг недоступности** (`is_available: false`, `current_active_users: null`), **не** устаревшее значение.
- Различие: «источник недоступен» (ошибка) ≠ «за период нет данных» (валидное состояние); оба случая кодируются разными флагами в одном 200-ответе.
- Фронт отображает сообщение об ошибке или retry-кнопку (см. состояние `error_source` в §4.2).

### 5.3. Безопасность/доступ (сводно)
| Кто / Граница | Может ли вызвать INT-0 | Получит ли 200 + данные | Получит ли 403 | Примечание |
|---|---|---|---|---|
| Администратор | ✅ | ✅ | — | основной сценарий |
| Оператор | ✅ (может отправить) | ❌ | ✅ | проверка на бэке Arsenal |
| Аноним / без сессии | ✅ (может отправить) | ❌ | ✅ (или редирект на логин) | зависит от реализации Arsenal |

## 6. Релиз и интеграция
### 6.1. Порядок выката
🟡 подтверждено аналитиком: **фундамент #0 выкатывается раньше всех потребителей** (ARS-101, ARS-102, ARS-103).
- **Этап 1:** Deploy бэка Arsenal с эндпоинтом `GET /api/activity` (спека §2). На этом этапе фронты ещё не используют эндпоинт.
- **Этап 2:** Deploy дочерних фронтов ARS-101, ARS-102, ARS-103 — они начинают вызывать INT-0.

### 6.2. Обратная совместимость
- Фундамент — новая граница, обратной совместимости не требуется (нет текущих потребителей).
- Дочерние фронты разрабатываются параллельно с фундаментом, но деплоятся после его выката.
- Если после выката фундамента потребуется изменить контракт INT-0 (добавить поле, изменить тип), это требует координации со всеми потребителями; избежать разломов помогает версионирование контракта (напр. `?api_version=v1` или отдельный путь).

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **фиче-флагов нет**; фундамент и фронты деплоятся атомарно в соответствии с порядком §6.1.

### 6.4. План отката
- **Откат бэка Arsenal (эндпоинт INT-0):** фронты получат 404 → нужно откатить и фронты синхронно, иначе они сломаны. Откат дочерних фронтов при живом бэке безопасен — они перестанут отображать счётчик/график.
- **Откат фронтов:** бэк остаётся, эндпоинт работает, никакого ущерба нет.

### 6.5. Преднастройка до релиза (чек-лист)
- [ ] 🟡 Роли в security-сервисе: роль «Администратор» должна существовать в системе управления доступом Arsenal и быть назначена эксплуатационным администраторам (подтвердить, что работает проверка на INT-0).
- [x] DDL-миграция в репо Arsenal: **не применимо** — новых таблиц не заводятся; используется существующий источник данных активности.
- [ ] 🟡 Конфиги по окружениям: убедиться, что источник данных активности доступен в dev/staging/prod; настроить таймауты и параметры кэша в соответствии с инфраструктурой.
- [ ] 🟡 Сервисные аккаунты: если int-0 требует доступа к отдельному сервису, подготовить учётные записи (на данный момент этого нет по подтверждению аналитика).
- [x] Фиче-флаги: **не применимо** — деплояем атомарно.
- [ ] Алерты/мониторинг: включить мониторинг на 5xx/504 от `GET /api/activity`, алерт при > N% ошибок за период (для быстрого обнаружения проблем с источником).

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано открытую админку с ролью Администратор, когда страница загрузилась, тогда вызывается INT-0, получается текущее число активных пользователей, отображается в счётчике |
| FR-2 | INT-0 | Дано открытую админку, когда число активных пользователей изменилось на источнике, тогда счётчик обновляется (в течение таймера ~30 сек из-за кэша + обновление фронта). Граница: INT-0 отдаёт свежее значение за счёт кэша 30 сек. |
| FR-3 | INT-0 | Дано счётчик активности в шапке, когда администратор кликает по нему, тогда вызывается INT-0 с `period=day` (по умолчанию), получаются агрегаты, открывается модалка с графиком |
| FR-4 | INT-0 | Дано открытую модалку, когда администратор выбирает другой период (hour/week), тогда фронт вызывает INT-0 с новым `period`, получаются новые агрегаты, график перестраивается |
| FR-5 | INT-0 | Дано открытую модалку с периодом, когда администратор нажимает выгрузку, тогда фронт использует последний ответ INT-0 (поля `aggregates`, `period_total`) для генерации файла сводки |
