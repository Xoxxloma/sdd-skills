## 1. Обзор изменения
### 1.1. Тип и стороны
**BE-only.** Узел-фундамент #0 — чистая реализация backend-контракта для доступа к данным об активности пользователей. Контракт потребляют несколько фронтенд-потребителей (дочерние узлы эпика ARS-100); фундамент не содержит UI-логики, только сервис данных.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend core) | Сервис данных активности; собирает и отдаёт контракт | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел #0 обеспечивает данные активности (текущее число активных пользователей + агрегаты за период) для всех фиче-требований эпика (FR-1..FR-5). Данные обслуживают счётчик в шапке админки, график активности и выгрузку сводки.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности (текущее значение и агрегаты за период) — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Backend (Arsenal) → Потребители (фронты дочерних узлов ARS-101/102/103)
- **Триггер:** Фронт запрашивает текущую активность или агрегированные данные за выбранный период (при открытии счётчика, переключении периода, подготовке выгрузки)
- **Контракт (запрос):** 
  - Метод + путь (концептуально): `GET /api/admin/activity/data`
  - Параметры запроса:
    - `period_type` (строка, обязателен): `current` | `hour` | `day` | `week` — тип периода, за который нужны агрегаты; `current` = только текущий счётчик
    - `since` (ISO-8601 datetime, опционально): начало периода для агрегатов; если не указано, по умолчанию «сейчас минус [период_type]»
    - `until` (ISO-8601 datetime, опционально): конец периода для агрегатов; если не указано, «сейчас»

- **Контракт (ответ):**
  - Поля ответа:
    - `available` (boolean, обязателено): `true` если данные доступны, `false` если источник недоступен. **Семантика:** если `false`, остальные поля (`current_count`, `aggregates`) = `null`, фронт показывает «—» / состояние `error_source`.
    - `current_count` (integer или null, обязателено в структуре): число активных пользователей в данный момент. `null` = нет данных за текущий момент (мало данных для оценки) или источник недоступен (см. `available`). 0 = валидный ноль, фронт показывает «0». 
    - `current_count_unavailable_reason` (строка или null, опционально): код причины недоступности текущего счётчика, если `current_count = null` и `available = true`. Значения: `insufficient_data` (данных недостаточно для оценки). Если `available = false`, это поле игнорируется.
    - `aggregates` (массив объектов или null, обязателено в структуре): агрегированные данные активности за выбранный период.
      - Каждый объект в массиве:
        - `timestamp` (ISO-8601 datetime): момент начала интервала (часа/дня/недели в зависимости от `period_type`)
        - `count` (integer): число активных пользователей в этот интервал. 0 = валидный ноль (был интервал без активности).
      - Пустой массив `[]` = нет данных за выбранный период (период в будущем, период до начала сбора, или период пуст), но источник доступен. Фронт показывает пустой график, не ошибку.
      - `null` = источник недоступен или `period_type = current` (тогда агрегаты не запрашивали). **Семантика:** `null` ≠ пустой массив.
    - `aggregates_unavailable_reason` (строка или null, опционально): код причины недоступности агрегатов, если `aggregates = null` и `available = true`. Значения: `insufficient_data` (данных недостаточно).
    - `generated_at` (ISO-8601 datetime): момент, в который эти данные были сгенерированы/закэшированы (для понимания свежести на фронте).

  - Enum'ы:
    - `period_type`: `current`, `hour`, `day`, `week`
    - `available`: `true` или `false`
    - `*_unavailable_reason`: `insufficient_data`, `source_unreachable` (выдаёт backend, если источник совсем недоступен)

- **Пример запроса:**
  ```json
  {
    "period_type": "current"
  }
  ```

- **Пример ответа (успех — текущий счётчик доступен):**
  ```json
  {
    "available": true,
    "current_count": 42,
    "current_count_unavailable_reason": null,
    "aggregates": null,
    "aggregates_unavailable_reason": null,
    "generated_at": "2026-07-26T14:30:00Z"
  }
  ```

- **Пример ответа (успех — текущий счётчик + агрегаты за день):**
  ```json
  {
    "available": true,
    "current_count": 42,
    "current_count_unavailable_reason": null,
    "aggregates": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 10 },
      { "timestamp": "2026-07-26T01:00:00Z", "count": 15 },
      { "timestamp": "2026-07-26T02:00:00Z", "count": 8 },
      { "timestamp": "2026-07-26T03:00:00Z", "count": 42 }
    ],
    "aggregates_unavailable_reason": null,
    "generated_at": "2026-07-26T14:30:00Z"
  }
  ```

- **Пример ответа (успех — нет данных за выбранный период, но источник доступен):**
  ```json
  {
    "available": true,
    "current_count": 42,
    "current_count_unavailable_reason": null,
    "aggregates": [],
    "aggregates_unavailable_reason": null,
    "generated_at": "2026-07-26T14:30:00Z"
  }
  ```

- **Пример ответа (ошибка — источник недоступен):**
  ```json
  {
    "available": false,
    "current_count": null,
    "current_count_unavailable_reason": null,
    "aggregates": null,
    "aggregates_unavailable_reason": null,
    "generated_at": "2026-07-26T14:30:00Z"
  }
  ```

- **Пример ответа (успех — недостаточно данных для текущего счётчика, но есть исторические):**
  ```json
  {
    "available": true,
    "current_count": null,
    "current_count_unavailable_reason": "insufficient_data",
    "aggregates": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 10 },
      { "timestamp": "2026-07-26T01:00:00Z", "count": 15 }
    ],
    "aggregates_unavailable_reason": null,
    "generated_at": "2026-07-26T14:30:00Z"
  }
  ```

- **Ошибки:**
  - **500 Internal Server Error** — источник данных недоступен; фронт должен интерпретировать как `available: false` (семантика совпадает с 500 и `available: false` в теле).
  - **403 Forbidden** — роль не имеет прав на доступ к активности; фронт показывает «нет доступа».
  - **400 Bad Request** — параметры запроса невалидны (неизвестный `period_type`, некорректный datetime).

- **Состояния UI по ответу (семантика для фронта):**
  - **`value`** → `available = true`, `current_count ≠ null` и `current_count ≠ 0`: показать число
  - **`zero`** → `available = true`, `current_count = 0`: показать «0» (не прочерк)
  - **`empty`** → `available = true`, `current_count = null`, `current_count_unavailable_reason = "insufficient_data"`: показать прочерк «—» (нет данных, но не ошибка)
  - **`error_source`** → `available = false` или HTTP 5xx: показать сообщение об ошибке, предложить retry
  - **`error_forbidden`** → HTTP 403: показать «нет доступа»
  - Для графиков за период: `aggregates = []` (пустой массив, но `available = true`) = пустой график, не ошибка (период пуст или в будущем)

- **Авторизация:**
  - Доступен только ролям: **Администратор**
  - Проверка: на стороне backend (Arsenal) при парсе запроса; если роль ≠ Администратор, ответ 403 Forbidden
  - Негативный случай: Оператор пытается вызвать endpoint → 403, сообщение «Insufficient permissions»

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5

| 200 + `aggregates: []` | Пустой массив, `available: true` | Нет данных за выбранный период (период пуст или в будущем) | Пустой график, не ошибка |

## 3. Backend — ответственность
### 3.1. По сервисам
**Arsenal (backend core):**
- Реализует INT-0: endpoint GET /api/admin/activity/data, парсит параметры, проверяет авторизацию по роли (только Администратор), вызывает внутренний сервис подсчёта активности, формирует ответ с правильной семантикой `available` / `current_count` / `aggregates`.
- При недоступности источника активности: возвращает 500 или ответ с `available: false`, но **не отдаёт устаревшие данные**.
- Разделяет семантику: `current_count = null` с причиной `insufficient_data` (недостаточно данных) отличается от `available = false` (источник недоступен).

### 3.2. Данные и хранение
**Новых сущностей и таблиц нет.** 🟡 Подтверждено аналитиком: агрегаты активности рассчитываются на лету, не сохраняются в новых таблицах; используются существующие логи/события активности в системе Arsenal.

Концептуально:
- **Входная сущность:** логи активности пользователей (существуют в Arsenal, уточнить схему при интеграции)
- **Преобразование:** при запросе агрегируются текущее значение и историческая статистика за указанный период
- **Выход:** INT-0 контракт

Индексы: 🟡 к валидации — если добавляются новые индексы на таблицах логирования для ускорения агрегации, уточнить при разработке.

### 3.3. Авторизация/доступ на бэке
- Роль **Администратор** имеет доступ к INT-0
- Роль **Оператор** не имеет доступа (ответ 403)
- Проверка: в middleware/filter на стороне Arsenal перед обработкой запроса к /api/admin/activity/data
- Откат доступа: убрать роль из списка авторизованных в конфиге Arsenal

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- **Синхронность:** Synchronous (синхронный запрос-ответ, не async/event-driven).
- **Кэш:** 30-секундный кэш на стороне backend (Arsenal). 🟡 Подтверждено аналитиком.
  - Место: в памяти сервиса Arsenal (Redis или аналог, уточнить при разработке)
  - TTL: 30 секунд с момента вычисления агрегатов
  - Инвалидация: по TTL (никаких ручных инвалидаций при обновлении)
- **Таймаут:** 5 секунд на вызов INT-0 из фронта. 🟡 Подтверждено аналитиком.
  - Если backend не отвечает за 5 сек, фронт должен показать `error_source`
- **Частота опроса:** Дочерние узлы устанавливают свою частоту (FR-2 говорит об обновлении «в пределах минуты», точный интервал — в спеке каждого узла); INT-0 не навязывает polling.
- **Ожидаемая нагрузка:** 🟡 к валидации — уточнить при разработке (сколько админов одновременно, какой RPS ожидается).

### 5.2. Надёжность/деградация
- При недоступности источника данных активности (БД логов, сервис анализа — что бы то ни было): 🟡 Подтверждено аналитиком — backend отдаёт 500 или ответ с `available: false`, **не старые кэшированные данные**.
- Таймаут ответа источника (>5сек) = 503 Service Unavailable или ответ с `available: false`
- Пользователь видит: ошибку, не устаревшие данные (критичный момент: во время регламентных работ админ должен видеть точный статус, не стареющее значение)

### 5.3. Безопасность/доступ (сводно)

## 6. Релиз и интеграция
### 6.1. Порядок выката
1. **Backend (Arsenal, INT-0)** — выкатывается **первым**. Дочерние узлы (ARS-101/102/103) зависят от контракта #0; фронты этих узлов не будут работать без backend-контракта.
2. **Фронты дочерних узлов** — выкатываются **после** backend, в любом порядке между собой. Каждый дочерний узел выписывает свою спеку с наследованием INT-0 из #0.

Обоснование: фундамент = общий шов, выкатывается раньше потребителей; потребители встраиваются в него и друг в друга.

### 6.2. Обратная совместимость
- **Текущая версия Arsenal** (без INT-0): фронты текущего контракта не вызывают /api/admin/activity/data, панель активности отсутствует → нет конфликтов, обновление добавляет только новый endpoint.
- **Новая версия Arsenal с INT-0 + старые фронты**: старые фронты не знают о /api/admin/activity/data, панель не видят → безопасно. Новый endpoint не трогает старые API.
- **Новая версия Arsenal + новые фронты**: оба понимают INT-0, работает как спроектировано.
- **Откат Arsenal до версии без INT-0**: новые фронты получат 404 на /api/admin/activity/data → фронты должны обработать как `error_source` (не имеет роли, что 404 vs 500).

### 6.3. Фиче-флаги
🟡 Подтверждено аналитиком: **фиче-флагов нет.** Выкатываем атомарно (backend + дочерний фронт одновременно или backend раньше). Если нужна постепенная раскатка фронта для отдельных админов, это решается на уровне дочерних узлов (они могут вводить флаги для своих UI-элементов).

### 6.4. План отката (обязательно)
- **Откат только Backend (Arsenal):** если INT-0 откатить до версии без endpoint, фронты получат 404 → обрабатывают как `error_source`, показывают ошибку → допустимо (ошибка лучше, чем устаревшие данные).
- **Откат только Frontend (дочерного узла):** backend продолжает отдавать INT-0, новый фронт откатиться на старую версию без UI-панели → старый фронт просто не вызывает endpoint, обновление потеряется → допустимо.
- **Полный откат:** откатить backend + все фронты одновременно на версию без изменений.
- **Откат DDL:** не требуется (новых таблиц нет, используются существующие логи).

### 6.5. Преднастройка до релиза (чек-лист)
- [x] Роли в security-сервисе: роль **Администратор** должна быть определена и привязана к пользователям, которые должны видеть панель активности. 🟡 Подтверждено аналитиком: проверка прав делается на бэке Arsenal, роль передаётся в запросе.
- [x] DDL-миграция: не требуется (новых таблиц нет).
- [x] Конфиги по окружениям: уточнить при разработке (dev/staging/prod могут иметь разные TTL кэша или источники данных, но INT-0 контракт остаётся одинаковым).
- [x] Сервисные аккаунты: 🟡 к валидации — если Arsenal при подсчёте активности вызывает другой сервис (что не подтверждено аналитиком), потребуется аккаунт; уточнить при разработке.
- [x] Фиче-флаги: не заводим (выкатываем атомарно, без постепенного включения).
- [x] Алерты/мониторинг: 🟡 к валидации — добавить алерт на 5xx ошибки на /api/admin/activity/data и на таймауты (время ответа > 5сек), чтобы заметить проблемы с источником данных. Уточнить при разработке мониторинга Arsenal.

|----------|-------------------|------------------------------|
| FR-1 | INT-0 (current) | Дано открытую админку с ролью Администратор, когда страница загрузилась, тогда вызов GET /api/admin/activity/data с period_type=current возвращает available=true, current_count=число |
