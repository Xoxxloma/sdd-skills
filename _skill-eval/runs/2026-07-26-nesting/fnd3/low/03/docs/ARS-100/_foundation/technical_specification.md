## 1. Обзор изменения

### 1.1. Тип и стороны
Backend-only (BE). Узел-фундамент #0 предоставляет контракт данных об активности пользователей. Потребители — фронтендные части детей (ARS-101, ARS-102, ARS-103) через бэк Arsenal. Никаких новых межсервисных взаимодействий не создаётся: фундамент — чистая реализация данных внутри одного бэка.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | Сбор и выдача данных активности, расчёт агрегатов | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Фундамент обслуживает сквозные требования всех трёх слайсов эпика ARS-100: текущее число активных пользователей (FR-1, FR-2) и исторические агрегаты за период (FR-3, FR-4, FR-5). Без этих данных невозможны ни счётчик в шапке, ни график, ни выгрузка.

## 2. Взаимодействия (ядро)

### INT-0. Запрос данных активности — 🟢 (фундамент, наследуется детьми)

**Граница/направление:**
Внутри бэка Arsenal. Фронтенд детей (ARS-101/102/103) → бэк Arsenal → логика фундамента.

**Триггер:**
- Загрузка шапки админки (запрос текущего числа активных).
- Инициализация и переключение периода в модальном окне (запрос агрегатов за период).

**Контракт (запрос):**
```
GET /api/arsenal/activity/current
GET /api/arsenal/activity/range
  Query parameters:
    - period_start: ISO 8601 datetime (required for /range)
    - period_end: ISO 8601 datetime (required for /range)
```

**Контракт (ответ):**

Для текущего числа активных (`/current`):
- `count`: integer (≥ 0) — число активных пользователей на текущий момент.
- `is_available`: boolean — `true`, если данные достоверны; `false`, если источник недоступен.
- `timestamp`: ISO 8601 datetime — время последнего обновления внутри кэша.
- `cached_at`: ISO 8601 datetime — время, когда это значение было спроектировано в кэш (для мониторинга свежести).

Для агрегатов за период (`/range`):
- `period_start`: ISO 8601 datetime — начало запрошенного периода (эхо запроса).
- `period_end`: ISO 8601 datetime — конец запрошенного периода (эхо запроса).
- `data_points`: array of objects, каждый содержит:
  - `timestamp`: ISO 8601 datetime — точка времени в пределах периода (гранулярность — час).
  - `count`: integer (≥ 0) — число активных пользователей в этот момент; может быть `0` (валидный ноль).
- `is_available`: boolean — `true`, если все агрегаты вычислены успешно; `false`, если источник был недоступен на время периода.
- `is_empty`: boolean — `true`, если за весь период нет ни одной записи об активности (отличаем от недоступности: если `is_available=true` и `is_empty=true`, то данных просто не было, не ошибка).
- `data_points` становится пустым массивом, если `is_available=false` или `is_empty=true` (контракт остаётся чистым, логику разводит фронт по этим флагам).

**Пример запроса:**
```
GET /api/arsenal/activity/current
GET /api/arsenal/activity/range?period_start=2026-07-26T00:00:00Z&period_end=2026-07-26T23:59:59Z
```

**Пример ответа (успех, текущее число):**
```json
{
  "count": 42,
  "is_available": true,
  "timestamp": "2026-07-26T15:35:22Z",
  "cached_at": "2026-07-26T15:35:12Z"
}
```

**Пример ответа (успех, агрегаты за день):**
```json
{
  "period_start": "2026-07-26T00:00:00Z",
  "period_end": "2026-07-26T23:59:59Z",
  "data_points": [
    { "timestamp": "2026-07-26T00:00:00Z", "count": 5 },
    { "timestamp": "2026-07-26T01:00:00Z", "count": 3 },
    { "timestamp": "2026-07-26T02:00:00Z", "count": 0 },
    { "timestamp": "2026-07-26T15:00:00Z", "count": 42 },
    { "timestamp": "2026-07-26T23:00:00Z", "count": 28 }
  ],
  "is_available": true,
  "is_empty": false
}
```

**Пример ответа (источник недоступен):**
```json
{
  "count": null,
  "is_available": false,
  "timestamp": "2026-07-26T15:30:00Z",
  "cached_at": "2026-07-26T15:30:00Z"
}
```

**Пример ответа (период без данных об активности, но источник доступен):**
```json
{
  "period_start": "2026-01-01T00:00:00Z",
  "period_end": "2026-01-02T23:59:59Z",
  "data_points": [],
  "is_available": true,
  "is_empty": true
}
```

**Ошибки:**
- **400 Bad Request** — неверный формат параметров (период_start > period_end или невалидный ISO 8601).
  ```json
  { "error": "invalid_period", "message": "period_start must be before period_end" }
  ```
- **401 Unauthorized** — отсутствует токен авторизации или он невалиден.
  ```json
  { "error": "unauthorized", "message": "valid token required" }
  ```
- **403 Forbidden** — токен валиден, но роль не имеет доступа (не Administrator).
  ```json
  { "error": "forbidden", "message": "only Administrator role has access to activity data" }
  ```
- **408 Request Timeout** — запрос превысил таймаут (5 секунд). Фронт видит это как `is_available=false`.
- **500 Internal Server Error** — внутренняя ошибка сервера.
  ```json
  { "error": "internal_error", "message": "failed to fetch activity data" }
  ```

**Состояния UI по ответу (если есть фронт):**
Детализация происходит на стороне каждого детского фронта (ARS-101 FE, ARS-102 FE, ARS-103 FE):
- `is_available=true` + `count > 0` → состояние `value` (показать число).
- `is_available=true` + `count == 0` (при текущем запросе) → состояние `zero` (показать «0» буквально).
- `is_available=true` + `is_empty=true` (при запросе диапазона) → состояние `empty` (показать «—» или «нет данных»).
- `is_available=false` → состояние `error_source` (показать иконку ошибки и предложить retry).

**Авторизация:**
- Проверка роли на бэке Arsenal: только роль **Administrator** имеет доступ.
- При отсутствии прав возвращается 403 Forbidden с сообщением.
- Проверка выполняется для каждого запроса (no session hijacking concerns specific to this contract).

**Происхождение:** 🟢 новое (узел-фундамент #0)

**Трассировка:**
- FR-1 (отображение текущего числа) → INT-0 с `/current`.
- FR-2 (обновление счётчика без перезагрузки) → INT-0 с периодическим запросом `/current`.
- FR-3 (открытие модалки с графиком) → INT-0 с `/range` для периода по умолчанию.
- FR-4 (переключение периода) → INT-0 с `/range` для выбранного периода.
- FR-5 (выгрузка сводки) → INT-0 с `/range`, данные форматируются в файл на фронте.

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal (backend):**
- Реализует контракт INT-0 (оба эндпоинта: `/current` и `/range`).
- Сам собирает данные активности пользователей (🟡 подтверждено аналитиком: чужих сервисов не привлекаем).
- Рассчитывает агрегаты на лету (no pre-computed tables).
- Кэширует результаты `/current` на 30 секунд на стороне бэка.
- Для `/range` кэширование на уровне инфраструктуры (HTTP cache-control headers: max-age=30).
- Авторизация: проверяет роль Administrator в каждом запросе.
- Таймаут обработки запроса: 5 секунд (если источник медленнее → вернуть is_available=false вместо стейла).

### 3.2. Данные и хранение

🟡 подтверждено аналитиком (не по коду): новых таблиц не заводим. Агрегаты активности считаются на лету из существующих логов или счётчиков сессий, которыми владеет Arsenal. Точный источник данных (логи, счётчики в памяти, БД сессий) — уточняется в интеграции на основе реальной архитектуры Arsenal.

Хранение состояния ответов: только 30-секундный in-memory кэш для `/current` (волатильное), no persistent storage new objects.

### 3.3. Авторизация/доступ на бэке

- Точка enforcement: обработчик эндпоинтов `/current` и `/range`.
- Способ: проверка роли из JWT/session (в заголовке или cookie).
- Негативный случай (non-Administrator): сразу вернуть 403, не отдавать даже is_available=false (не выдавать информацию о наличии сервиса).

## 4. Frontend — ответственность

Не применимо на уровне фундамента #0 (нет собственного UI). Каждый детский фронт (ARS-101 FE, ARS-102 FE, ARS-103 FE) самостоятельно:
- Вызывает INT-0.
- Разводит ответы по своим состояниям (в §4.3 каждого детского спека).
- Отображает UI с учётом `is_available`, `is_empty`, `count`.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** Синхронно. Фронт ждёт ответа (нет polling на бэке).
- **Кэш на бэке:** 30 секунд для результатов `/current` (in-memory, простой TTL).
- **Кэш HTTP:** Cache-Control: max-age=30 для `/range` (если внедрена).
- **Таймаут:** 5 секунд max на обработку запроса. Если источник недоступен дольше → вернуть is_available=false.
- **Polling на фронте:** каждый детский фронт сам решает (обычно 30–60 сек для счётчика в шапке).
- **Ожидаемая нагрузка:** тысячи администраторов, запросы спорадические (не hammering). Точная оценка TBD при интеграции.

### 5.2. Надёжность/деградация

🟡 подтверждено аналитиком (не по коду):
- При недоступности источника (5xx, таймаут, сеть) возвращаем `is_available=false`, НЕ устаревшее значение.
- Различаем три состояния для фронта:
  - `is_available=true` → данные свежие, доверяем.
  - `is_available=false` → источник недоступен, фронт показывает ошибку/retry.
  - `is_available=true, is_empty=true` → источник доступен, но за период данных нет, фронт показывает пусто.

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Проверка | Отказ |
|---------|-----------|----------|-------|
| GET /api/arsenal/activity/current | Administrator | роль в токене | 403 Forbidden |
| GET /api/arsenal/activity/range | Administrator | роль в токене | 403 Forbidden |

## Резюме для разработчиков

Узел-фундамент #0 реализует один контракт (INT-0) с двумя эндпоинтами:
1. **GET /api/arsenal/activity/current** — текущее число активных (кэш 30 сек).
2. **GET /api/arsenal/activity/range** — агрегаты за период (часовая гранулярность).

Оба требуют роли Administrator. Оба различают недоступность (is_available=false) от отсутствия данных (is_empty=true). JSON примеры в INT-0 показывают формат для всех случаев.

Детские фронты (ARS-101, 102, 103) наследуют этот контракт (🟡 depends-on #0) и адаптируют его UI под свои требования (счётчик, график, выгрузка).
