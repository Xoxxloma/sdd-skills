## 1. Обзор изменения

### 1.1. Тип и стороны

BE-only. Узел-фундамент #0 проектирует единый контракт для данных активности пользователей, который потребляют все три дочерних узла (ARS-101, ARS-102, ARS-103). Бэк «Арсенала» собирает данные активности и отдаёт их через стандартный контракт.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (backend) | Сбор данных активности, отдача контракта | Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Фундамент #0 обслуживает FR-1..FR-5 эпика в части единого источника данных об активности пользователей. Три дочерних узла (АР-101 за FR-1/FR-2, АР-102 за FR-3/FR-4, АР-103 за FR-5) наследуют этот контракт и строят свою UI на его основе.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Бэк Arsenal → Фронты детей (ARS-101/102/103)
- **Триггер:** Инициализация панели активности (FR-1); периодический запрос (FR-2); выбор периода в модальном окне (FR-3/4); подготовка выгрузки (FR-5)
- **Контракт (запрос):** 
  - HTTP GET `/api/admin/activity-data`
  - Параметры запроса:
    - `period_type` (обязателен): `current` | `hour` | `day` | `week` — что агрегировать
    - `period_start` (опционально): ISO 8601 дата/время начала периода (если не передана, по умолчанию сейчас для `current`, вчера для `day`, неделю назад для `week` и т.п.)
    - `period_end` (опционально): ISO 8601 дата/время конца периода
- **Контракт (ответ):**
  - `is_available` (boolean): всегда передаётся; `true` → данные актуальны, `false` → источник недоступен
  - `current_active_count` (int ≥ 0 | null): текущее число активных пользователей
    - `null` → данные сейчас неизвестны (таймаут запроса, временная недоступность); отличается от нуля — это **empty**, а не **zero**
  - `period_data` (array): агрегаты за выбранный период
    - **Если `is_available = false`**: массив пуст, `current_active_count = null`
    - **Если `is_available = true` и данные есть**: один элемент на временной срез (час/день/неделя по period_type)
      - Каждый элемент: `{ "timestamp": "ISO 8601", "active_count": int ≥ 0 }`
    - **Если `is_available = true`, но за выбранный период нет данных** (напр., запрос на период в будущем): массив пуст, но `is_available = true` (важно: различаем "нет данных за период" от "источник недоступен")
  - `last_update_at` (string ISO 8601): момент последнего обновления данных на сервере
  - `cache_ttl_seconds` (int): оставшееся время кэша (для отладки и клиентского кэша)
- **Пример запроса:** 
  ```
  GET /api/admin/activity-data?period_type=current HTTP/1.1
  Host: arsenal-backend
  Authorization: Bearer <token>
  ```
- **Пример ответа (успех, current):**
  ```json
  {
    "is_available": true,
    "current_active_count": 42,
    "period_data": [],
    "last_update_at": "2026-07-26T18:45:00Z",
    "cache_ttl_seconds": 28
  }
  ```
- **Пример ответа (успех, день):**
  ```json
  {
    "is_available": true,
    "current_active_count": 42,
    "period_data": [
      { "timestamp": "2026-07-26T00:00:00Z", "active_count": 12 },
      { "timestamp": "2026-07-26T01:00:00Z", "active_count": 8 },
      { "timestamp": "2026-07-26T02:00:00Z", "active_count": 5 },
      { "timestamp": "2026-07-26T03:00:00Z", "active_count": 3 },
      { "timestamp": "2026-07-26T04:00:00Z", "active_count": 2 },
      { "timestamp": "2026-07-26T05:00:00Z", "active_count": 1 },
      { "timestamp": "2026-07-26T06:00:00Z", "active_count": 4 },
      { "timestamp": "2026-07-26T07:00:00Z", "active_count": 15 },
      { "timestamp": "2026-07-26T08:00:00Z", "active_count": 38 },
      { "timestamp": "2026-07-26T09:00:00Z", "active_count": 51 }
    ],
    "last_update_at": "2026-07-26T18:45:00Z",
    "cache_ttl_seconds": 28
  }
  ```
- **Пример ответа (источник недоступен, is_available = false):**
  ```json
  {
    "is_available": false,
    "current_active_count": null,
    "period_data": [],
    "last_update_at": "2026-07-26T18:35:00Z",
    "cache_ttl_seconds": 5
  }
  ```
- **Пример ответа (данные есть, но за выбранный период нет; period_data пуст, is_available = true):**
  ```json
  {
    "is_available": true,
    "current_active_count": 42,
    "period_data": [],
    "last_update_at": "2026-07-26T18:45:00Z",
    "cache_ttl_seconds": 28
  }
  ```
- **Ошибки:**
  - `400 Bad Request`: неверный `period_type` или формат даты
  - `401 Unauthorized`: токен отсутствует или невалидный
  - `403 Forbidden`: токен валидный, но роль не «Администратор»
  - `500 Internal Server Error`: ошибка бэка (попадает в `is_available = false` в успешном ответе, не в 5xx, если это мер.недоступность источника; см. далее)
  - `504 Gateway Timeout` / таймаут соединения → см. таймауты в §5.1
- **Состояния UI по ответу (если есть фронт):**
  - `value` → `is_available = true`, `current_active_count > 0` или `period_data` не пуст → показываем числа/график
  - `zero` → `is_available = true`, `current_active_count = 0` → показываем «0» (не «—»)
  - `empty` → `is_available = true`, но `current_active_count = null` И `period_data` пуст → показываем «—» / «нет данных»
  - `error_source` → `is_available = false` ИЛИ 5xx/таймаут → показываем «источник недоступен», предлагаем повтор
  - `error_forbidden` → 403 → показываем «нет доступа»
- **Авторизация:**
  - Контракт доступен **только** роли «Администратор»
  - Проверка на бэке Arsenal (в middleware или в обработчике эндпоинта)
  - Негативный случай: роль «Оператор» получает 403 Forbidden при попытке вызова
  - Токен передаётся в заголовке `Authorization: Bearer <token>` (стандартно для Arsenal)
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal (backend):**
- Реализует эндпоинт `GET /api/admin/activity-data` согласно INT-0
- Принимает параметры `period_type`, `period_start`, `period_end`
- Проверяет авторизацию: только роль «Администратор» (🟡 подтверждено аналитиком, что такая роль существует в auth-сервисе Arsenal)
- На основе `period_type` определяет интервал временных срезов (часовой, дневной, еженедельный)
- Собирает текущий счёт активных сессий и агрегаты за период из собственного источника данных (🟡 подтверждено аналитиком, что Arsenal собирает эти данные сам, чужих сервисов не привлекаем)
- Кэширует ответ на 30 секунд на своей стороне (реализация кэша — по выбору: in-memory, Redis и т.п.)
- При недоступности источника (внутренняя ошибка, таймаут) возвращает `{ "is_available": false, ... }` (не 5xx; это обрабатывается как управляемая деградация), а не устаревшее значение

### 3.2. Данные и хранение

🟡 подтверждено аналитиком: **новых таблиц и структур данных не заводим.** Arsenal уже ведёт счёт активных сессий; мы агрегируем и выдаём эти данные через новый эндпоинт. Если для агрегации требуется индекс на таблице активных сессий (по временным срезам), это — внутреннее оптимизационное решение Arsenal, в спеке указано только концептуально.

- Новые таблицы: **нет**
- Новые индексы: 🟡 по необходимости на таблице активных сессий Arsenal (индекс по timestamp для быстрой фильтрации при агрегации) — подтверждено аналитиком, что это вписывается в текущую архитектуру
- Миграции: **не требуются** (используются существующие структуры)

### 3.3. Авторизация/доступ на бэке

- Проверка роли «Администратор» в middleware или в обработчике эндпоинта `GET /api/admin/activity-data`
- Сущность роли 🟡 подтверждена аналитиком: существует в auth-системе Arsenal
- Проверка выполняется на основе токена в заголовке `Authorization: Bearer <token>`
- Негативный случай (роль ≠ «Администратор»): возврат 403 Forbidden
- Позитивный случай (роль = «Администратор»): запрос обрабатывается, ответ отдаётся согласно INT-0

## 4. Frontend — ответственность

Фронты дочерних узлов (ARS-101, ARS-102, ARS-103) на основе этого контракта:
- Вызывают INT-0 с нужным `period_type` и параметрами периода
- Обрабатывают `is_available`, `current_active_count`, `period_data` согласно состояниям из INT-0
- Отображают значение / пусто / ошибку согласно маппингу состояний

Сам фундамент #0 не содержит фронтовых изменений; контракт наследуется детьми.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** синхронный запрос-ответ (без очередей, событий)
- **Кэш:** 30 секунд на стороне бэка Arsenal (перетирается при каждом новом обновлении счёта активных сессий или спустя 30с)
- **Таймаут:**
  - Холодный путь (первый запрос, холодный кэш): максимум 5 секунд
  - Тёплый путь (кэш попал): < 100 мс
- **Polling:** фронты детей периодически опрашивают INT-0 в зависимости от собственной логики (FR-2 требует обновления в пределах минуты; точный интервал — в спеке дочерних узлов)
- **Ожидаемая нагрузка:** 🟡 к валидации (оцениваем количество одновременных запросов админов; скорее всего, низкая — несколько человек в час)

### 5.2. Надёжность/деградация

- **При недоступности источника данных:** возвращаем `{ "is_available": false, ... }`, а не устаревшее значение (🟡 подтверждено аналитиком)
- **Различаем два сценария:**
  1. Источник недоступен → `is_available = false`, `current_active_count = null`, `period_data = []`
  2. Источник доступен, но за выбранный период нет данных → `is_available = true`, `period_data = []` (важно: разные семантики!)
- **Таймаут запроса:** если запрос к источнику превышает 5 секунд, возвращаем управляемую ошибку `is_available = false` (не зависаем на клиенте)

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Проверка |
|---------|-----------|----------|
| GET /api/admin/activity-data | Роль = Администратор | Бэк Arsenal, заголовок Authorization |
| GET /api/admin/activity-data | Роль ≠ Администратор | 403 Forbidden, запрос отклоняется |

## 6. Релиз и интеграция

### 6.1. Порядок выката

Фундамент #0 выкатывается **раньше всех дочерних узлов** (ARS-101, ARS-102, ARS-103). Когда контракт INT-0 доступен на боевой версии Arsenal, дочерние фронты могут безопасно стартовать с вызовом этого эндпоинта.

### 6.2. Обратная совместимость

Новое взаимодействие INT-0 не ломает существующие вызовы к Arsenal. Старые фронты продолжают работать, новый эндпоинт доступен отдельно.

### 6.3. Фиче-флаги

Флагов нет; релизим атомарно (🟡 подтверждено аналитиком).

### 6.4. План отката

- **Откат только BE (Arsenal):** новый эндпоинт становится недоступен (404 или 503) → дочерние фронты обрабатывают ошибку и показывают error_source. Допустимо: фронты готовы к такому сценарию.
- **Откат только FE (одного из детей):** Arsenal по-прежнему выдаёт INT-0 → старый фронт его не вызывает. Данные по-прежнему доступны остальным детям. Допустимо.
- **Откат DDL:** новых таблиц нет → откат не требуется.

### 6.5. Преднастройка до релиза

- [ ] Роль «Администратор» в auth-системе Arsenal (🟡 подтверждено аналитиком, что она уже существует; проверить, что запросы от админов пропускаются)
- [ ] Кэш настроен на 30 секунд в конфиге Arsenal

- [ ] Индекс на таблице активных сессий (если требуется для производительности при агрегации)
- [ ] Алерты на 5xx и таймауты эндпоинта `/api/admin/activity-data`

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 (period_type=current) | Дано админ с ролью Администратор, когда страница загружается, тогда вызывается GET /api/admin/activity-data?period_type=current, получаем is_available=true и current_active_count=42, тогда в шапке видно число 42 |
| FR-2 | INT-0 (period_type=current, периодический вызов) | Дано счётчик активных пользователей изменился на бэке, когда фронт через ≤60s повторно вызывает INT-0, тогда получает обновлённое значение current_active_count |
| FR-3 | INT-0 (period_type=day/week/hour) | Дано счётчик в шапке, когда администратор кликает, тогда открывается модалка, фронт вызывает INT-0 с period_type=day (по умолчанию) и получает period_data со сторками активности за день |
| FR-4 | INT-0 (period_type переключается) | Дано открытую модалку с period_type=day, когда администратор выбирает неделю, тогда фронт переделает запрос с period_type=week, получает новый period_data, график перестраивается |
| FR-5 | INT-0 (period_type выбранного периода) | Дано открытую модалку с выбранным периодом, когда администратор нажимает выгрузку, тогда фронт вызывает INT-0 с текущим period_type, получает period_data, генерирует и скачивает файл со сводкой |
