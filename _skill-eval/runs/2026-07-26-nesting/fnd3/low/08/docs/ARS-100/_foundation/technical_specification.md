## 1. Обзор изменения
### 1.1. Тип и стороны
BE-only. Узел-фундамент #0 — не принадлежит ни одному дочернему узлу; проектируется один раз, первым, и предоставляет единый контракт для данных активности, который потребляют дочерние фронты (FR-1..FR-5). Никаких новых таблиц, данные агрегируются на лету из существующих логов сессий.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (BE) | Предоставляет контракт данных активности | Команда Arsenal-Core | 🟡 подтверждено аналитиком |
| Arsenal (FE) — дочерние узлы | Потребители контракта | Группа разработки админки | 🟢 (определяется в спеках детей) |

### 1.3. Связь с бизнес-требованиями
Спецификирует единую точку доступа к данным текущей активности пользователей (число активных) и агрегированной активности за период (для графика и выгрузки сводки), удовлетворяя FR-1..FR-5 эпика.

## 2. Взаимодействия (ядро)
### INT-0. Текущее число активных пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Фронт-консумер (дочерний FE) ← Бэк Arsenal
- **Триггер:** Инициализация страницы (FR-1); периодический polling (FR-2)
- **Контракт (запрос):** `GET /api/activity/current` (концептуально, стеко-агностично)
  - Заголовки: `Authorization: Bearer <token>`
  - Тело запроса: отсутствует
- **Контракт (ответ):**
  - `count` (number, nullable) — число активных пользователей в момент опроса; `null` → источник недоступен
  - `last_updated_at` (ISO 8601 timestamp) — момент последнего обновления счётчика на бэке
  - `is_available` (boolean) — флаг доступности источника данных (true = данные свежие, false = источник недоступен)
- **Пример запроса:**
  ```
  GET /api/activity/current HTTP/1.1
  Host: arsenal.internal
  Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
  ```
- **Пример ответа (успех — данные доступны):**
  ```json
  {
    "count": 1847,
    "last_updated_at": "2026-07-26T14:32:45.123Z",
    "is_available": true
  }
  ```
- **Пример ответа (успех — источник недоступен):**
  ```json
  {
    "count": null,
    "last_updated_at": "2026-07-26T14:30:00.000Z",
    "is_available": false
  }
  ```
- **Ошибки:** 
  - `401 Unauthorized` — токен отсутствует или невалиден
  - `403 Forbidden` — роль не `Administrator`
  - См. каталог ошибок ниже
- **Состояния UI по ответу (для фронт-потребителя):**
  - `is_available: true, count != null` → `value`: показать число
  - `is_available: true, count == null` → `zero`: показать «0» (допустимый ноль)
  - `is_available: false` → `error_source`: показать «—» или иконку ошибки с возможностью retry
  - `403` → `error_forbidden`: скрыть панель, показать «нет доступа»
- **Авторизация:** Только роль `Administrator`; проверяется на бэке Arsenal по токену в заголовке `Authorization`. Любой запрос без токена или с ролью не-администратора возвращает `401` / `403`.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2

### INT-1. Агрегированная активность за период — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Фронт-консумер (дочерний FE) ← Бэк Arsenal
- **Триггер:** Открытие модального окна (FR-3); переключение периода (FR-4); запрос выгрузки сводки (FR-5)
- **Контракт (запрос):** `GET /api/activity/timeseries` (концептуально, стеко-агностично)
  - Параметры:
    - `period`: enum = `"hour"` | `"day"` | `"week"` (обязателен)
    - `end_at` (ISO 8601 timestamp, опционально) — конец периода; по умолчанию = сейчас
  - Заголовки: `Authorization: Bearer <token>`
  - Пример: `/api/activity/timeseries?period=hour&end_at=2026-07-26T14:32:45Z`
- **Контракт (ответ):**
  - `period` (string) — период запроса (`hour` / `day` / `week`)
  - `start_at` (ISO 8601 timestamp) — начало периода
  - `end_at` (ISO 8601 timestamp) — конец периода
  - `is_available` (boolean) — доступны ли данные из источника
  - `has_data` (boolean) — есть ли вообще данные за этот период (true = есть хотя бы один семпл; false = период пуст или нет данных)
  - `datapoints` (array of objects, может быть пусто) — временные точки активности:
    - `timestamp` (ISO 8601) — момент снимка
    - `count` (number ≥ 0) — число активных пользователей в этот момент
  - Семантика `null` и отсутствия:
    - Если `is_available: false` → `datapoints: []` пусто, `has_data: false`, `count` невидимы
    - Если `is_available: true, has_data: false` → `datapoints: []`, это означает «за период нет данных» (не ошибка, валидное состояние)
    - Если `is_available: true, has_data: true` → `datapoints` заполнен, каждая точка имеет `count ≥ 0`
- **Пример запроса:**
  ```
  GET /api/activity/timeseries?period=day&end_at=2026-07-26T14:32:45Z HTTP/1.1
  Host: arsenal.internal
  Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
  ```
- **Пример ответа (успех — данные есть):**
  ```json
  {
    "period": "day",
    "start_at": "2026-07-25T14:32:45.000Z",
    "end_at": "2026-07-26T14:32:45.000Z",
    "is_available": true,
    "has_data": true,
    "datapoints": [
      { "timestamp": "2026-07-25T14:32:45.000Z", "count": 1200 },
      { "timestamp": "2026-07-25T14:45:00.000Z", "count": 1350 },
      { "timestamp": "2026-07-25T15:00:00.000Z", "count": 1420 },
      { "timestamp": "2026-07-25T23:59:00.000Z", "count": 145 }
    ]
  }
  ```
- **Пример ответа (успех — период пуст, нет данных):**
  ```json
  {
    "period": "day",
    "start_at": "2026-07-24T00:00:00.000Z",
    "end_at": "2026-07-25T00:00:00.000Z",
    "is_available": true,
    "has_data": false,
    "datapoints": []
  }
  ```
- **Пример ответа (успех — источник недоступен):**
  ```json
  {
    "period": "week",
    "start_at": "2026-07-19T14:32:45.000Z",
    "end_at": "2026-07-26T14:32:45.000Z",
    "is_available": false,
    "has_data": false,
    "datapoints": []
  }
  ```
- **Ошибки:**
  - `400 Bad Request` — invalid `period` parameter (не одно из `hour`/`day`/`week`)
  - `401 Unauthorized` — токен отсутствует или невалиден
  - `403 Forbidden` — роль не `Administrator`
  - См. каталог ошибок ниже
- **Состояния UI по ответу (для фронт-потребителя):**
  - `is_available: true, has_data: true, datapoints ≠ []` → `value`: отрисовать график по datapoints
  - `is_available: true, has_data: false` → `empty`: показать «нет данных за период» (не ошибка)
  - `is_available: false` → `error_source`: показать «—» или иконку ошибки с возможностью retry
  - `400` → `error_validation`: показать сообщение об ошибке параметра
  - `403` → `error_forbidden`: скрыть модалку, показать «нет доступа»
- **Авторизация:** Только роль `Administrator`; проверяется на бэке Arsenal по токену. Запрос без токена или с ролью не-администратора возвращает `401` / `403`.
- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-3, FR-4, FR-5

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| `401 Unauthorized` | `{ "error": "unauthorized", "message": "Missing or invalid authorization token" }` | Нет токена или токен невалиден | `error_forbidden` (повторный вход) |
| `403 Forbidden` | `{ "error": "forbidden", "message": "Only Administrator role can access this resource" }` | Роль отличается от `Administrator` | `error_forbidden` (скрыть панель) |
| `400 Bad Request` | `{ "error": "invalid_period", "message": "Period must be one of: hour, day, week" }` (для INT-1 только) | Параметр `period` невалиден | `error_validation` (показать ошибку параметра) |
| `5xx Server Error` | `{ "error": "internal_error", "message": "..." }` | Ошибка на бэке Arsenal | `error_source` (показать «—» + retry) |
| `504 Gateway Timeout` | (сетевой таймаут, 5 сек) | Источник активности недоступен или не отвечает в течение 5 сек | `error_source` (показать «—» + retry) |

## 3. Backend — ответственность

### 3.1. По сервисам
**Arsenal (BE)** реализует оба контракта INT-0 и INT-1:
- INT-0: синхронно отдаёт текущее число активных пользователей (кэшировано, TTL = 30 сек)
- INT-1: синхронно отдаёт агрегированные данные активности за выбранный период (также кэшировано, TTL = 30 сек)
- Оба эндпоинта требуют авторизации (роль `Administrator`)
- Оба считывают данные активности из существующих логов сессий (нет новых таблиц)
- Оба различают состояния: «данные доступны» (is_available: true) и «источник недоступен» (is_available: false, count/datapoints пусто)

### 3.2. Данные и хранение
🟡 подтверждено аналитиком (не по коду): новых таблиц не заводим. Агрегаты активности считаются на лету из существующих логов сессий в Arsenal. 

Логика агрегации (концептуально):
- Текущее число активных (INT-0): счёт активных сессий в логе на момент запроса (или на момент последнего обновления кэша)
- Агрегированная активность (INT-1): срезы счёта активных на регулярные интервалы за выбранный период (периодичность снимков — детали реализации, не специрована здесь)

Индекс: на лог сессий по timestamp (для эффективной выборки за период).

### 3.3. Авторизация/доступ на бэке
- Оба контракта (INT-0, INT-1) доступны **только** роли `Administrator`
- Проверка: токен в заголовке `Authorization` → валидация и извлечение роли из security-сервиса 🟡 подтверждено аналитиком
- При отсутствии токена: `401 Unauthorized`
- При роли не-администратора: `403 Forbidden`

## 4. Frontend — ответственность
(Не применимо: узел-фундамент #0 — чистая реализация контракта; ответственность фронта за состояния (§4.3) лежит на дочерних узлах, которые наследуют эти контракты.)

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
- **Синхронность:** Оба контракта синхронные (не async)
- **Кэш:** На стороне бэка Arsenal, TTL = 30 секунд для обоих INT-0 и INT-1
- **Таймаут:** 5 секунд на ответ от источника данных; при таймауте возвращаем is_available: false, count: null, datapoints: []
- **Частота опроса:** Дочерние фронты решают сами (FR-2 оговаривает обновление счётчика не реже чем раз в минуту; INT-0 позволяет это, кэш 30с обеспечивает экономию)
- **Ожидаемая нагрузка:** 🟡 подтверждено аналитиком: потребители — только дочерние фронты в админке (не массовое потребление)

### 5.2. Надёжность/деградация
При недоступности источника активности (ошибка запроса к логам, таймаут, сетевая ошибка):
- Возвращаем `is_available: false` (не ошибку 5xx) с пустыми данными
- Не отдаём устаревшее значение из кэша предыдущего периода (честная сигнализация о недоступности)
- Фронт по `is_available: false` показывает «—» / иконку ошибки и предлагает retry

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто может | Как проверяется | Негативный случай |
|---------|-----------|-----------------|-------------------|
| INT-0, INT-1 | `Administrator` только | Токен + роль на бэке Arsenal | `401` / `403` |
| Внешние сервисы | Нет новых вызовов во внешние сервисы | — | — |

## 6. Релиз и интеграция
### 6.1. Порядок выката
1. **Arsenal (BE) — INT-0 и INT-1** выкатывается ПЕРВЫМ (фундамент)
2. **Дочерние фронты** выкатываются после, когда фундамент стабилен и проверен

Это обеспечивает, что потребители встречают готовый контракт и не сталкиваются с `404` / несовместимостью.

### 6.2. Обратная совместимость
- INT-0 и INT-1 — новые эндпоинты, не ломают существующее потребление
- Будущие версии контракта должны сохранить семантику `is_available` и `has_data` (они критичны для различия ошибок); добавление новых полей не-критично (фронты будут игнорировать)

### 6.3. Фиче-флаги
Фиче-флаги не требуются. Эндпоинты выкатываются атомарно с авторизацией по ролям: фундамент защищён на бэке (роль `Administrator`), недоступные дочерние узлы не получат данные.

### 6.4. План отката (обязательно)
- **Откат только BE (Arsenal):** Если INT-0/INT-1 откатываются, дочерние фронты получат `404` / `503`. Сценарий требует синхронного отката фронтов (они не смогут работать без контракта). **Рекомендация:** координированный откат одновременно.
- **Откат только FE:** Фундамент остаётся в production. Если дочерний фронт откатывается, бэк продолжает отдавать данные (они просто не потребляются). Этот сценарий безопасен.
- **Откат DD**L: Нет новых таблиц, миграции не требуются.

### 6.5. Преднастройка до релиза (чек-лист)
- [x] **Роли в security-сервисе:** роль `Administrator` уже существует в системе 🟡 подтверждено аналитиком; новых ролей не заводим
- [ ] **DDL-миграция в репо Arsenal BE:** не требуется (нет новых таблиц)
- [ ] **Конфиги по окружениям (dev/staging/prod):** TTL кэша (30 сек), таймаут (5 сек) — настроить параметрами конфига
- [ ] **Сервисные аккаунты для межсервисных вызовов:** не требуются (Arsenal сам вызывает свой лог)
- [ ] **Фиче-флаги:** не требуются
- [ ] **Алерты/мониторинг:** алерты на частые `5xx`, таймауты, недоступность источника активности

## 7. Трассировка приёмки
| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано открытую админку с ролью Administrator, когда страница загрузилась, тогда получаем INT-0 с `is_available: true` и видим число активных |
| FR-2 | INT-0 (polling) | Дано обновление активности на бэке, когда прошло ≤ 30 сек (TTL кэша), тогда FR-2 должен вызвать INT-0 и получить обновленное число (или is_available: false, если источник упал) |
| FR-3 | INT-1 | Дано открытую админку, когда администратор кликает на счётчик, тогда вызывается INT-1 с `period=day` (по умолчанию), получаем datapoints и отрисовываем график |
| FR-4 | INT-1 (с переменным period) | Дано открытую модалку, когда администратор выбирает `period=hour` вместо `day`, тогда вызывается INT-1 с новым period, получаем корректные datapoints за выбранный промежуток |
| FR-5 | INT-1 (экспорт) | Дано открытую модалку с `period=week`, когда администратор нажимает выгрузку, тогда вызывается INT-1, данные преобразуются в CSV/JSON и скачиваются файлом |

## 8. Допущения и открытые вопросы
- **Подтверждено аналитиком (не по коду, валидировать при интеграции):**
  1. Backend Arsenal собирает данные активности сам из существующих логов сессий; чужих сервисов не привлекаем.
  2. Роль `Administrator` уже существует в security-сервисе и используется для проверки доступа.
  3. Источник данных активности (лог сессий) имеет индекс по timestamp для выборки за период.

- **Все технические решения приняты. Спецификация готова к разработке.**
