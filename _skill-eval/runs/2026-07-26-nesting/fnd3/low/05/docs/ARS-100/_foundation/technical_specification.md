## 1. Обзор изменения

### 1.1. Тип и стороны

**BE-only.** Узел-фундамент #0 — это слой на стороне бэка «Арсенала», который собирает и отдаёт контракт данных активности. Фронты детей (АР-101, АР-102, АР-103) потребляют этот контракт независимо и реализуют свои UI поверх него. 🟢

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Собирает данные активности и отдаёт контракт; владеет сущностью | Arsenal Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Фундамент реализует общую часть эпика ARS-100: обслуживает FR-1..FR-5 в части данных активности (текущее число активных пользователей и исторические агрегаты за период). Фронты детей строят на этом контракте независимо.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей (текущая и историческая) — 🟢

- **Граница/направление:** Backend Arsenal → фронты детей (ARS-101, ARS-102, ARS-103)
- **Триггер:** Инициируется фронтом детей по выбору периода (текущий / за час / за день / за неделю) и при автообновлении счётчика
- **Контракт (запрос):** 
  - **Метод:** HTTP GET
  - **Путь:** `/api/v1/admin/activity` (концептуальный)
  - **Параметры запроса:**
    - `period` (string, обязателен): `current`, `1h`, `24h`, `7d`
    - Семантика: `current` возвращает момент-в-момент + агрегаты за последний час; `1h`, `24h`, `7d` возвращают агрегаты за соответствующий период
  - **Заголовки:** Авторизация (см. §2 Авторизация)

- **Контракт (ответ):**
  - `current_active` (integer | null): Текущее число активных пользователей. `null` → источник недоступен (см. статус `unavailable`). Если данных за период нет, это поле содержит `0` или `null` в зависимости от статуса (см. ниже).
  - `period` (string): Запрошенный период (`current`, `1h`, `24h`, `7d`)
  - `status` (string enum): Статус запроса:
    - `available` — данные получены и актуальны
    - `unavailable` — источник активности недоступен; `current_active` = `null`
    - `no_data` — период запрошен, но нет данных за него (валидное состояние; клиент отображает пусто, не ошибку)
  - `source_error` (string | null): Если `status: unavailable`, код ошибки источника (`service_timeout`, `connection_failed`, `internal_error`). `null` если успех.
  - `aggregates` (array of objects): Агрегированные данные активности за период:
    - `timestamp` (ISO 8601 string): Момент времени агрегата (зависит от периода: минута для `1h`, 5-минут интервал для `24h`, час для `7d`)
    - `count` (integer): Число активных пользователей в этот момент
    - Пустой массив если `status: no_data` или `status: unavailable`
  - `last_updated` (ISO 8601 string): Момент последнего обновления данных на бэке (UTC)
  - `cache_ttl_seconds` (integer): TTL кэша этого ответа на стороне Arsenal (`30` секунд)

- **Пример запроса:**
  ```
  GET /api/v1/admin/activity?period=24h
  Authorization: Bearer <token>
  ```

- **Пример ответа (успех, есть данные):**
  ```json
  {
    "current_active": 142,
    "period": "24h",
    "status": "available",
    "source_error": null,
    "aggregates": [
      { "timestamp": "2026-07-25T10:00:00Z", "count": 98 },
      { "timestamp": "2026-07-25T10:05:00Z", "count": 101 },
      { "timestamp": "2026-07-25T10:10:00Z", "count": 105 },
      { "timestamp": "2026-07-25T10:15:00Z", "count": 103 },
      { "timestamp": "2026-07-25T10:20:00Z", "count": 142 }
    ],
    "last_updated": "2026-07-26T10:22:15Z",
    "cache_ttl_seconds": 30
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "current_active": null,
    "period": "24h",
    "status": "unavailable",
    "source_error": "service_timeout",
    "aggregates": [],
    "last_updated": null,
    "cache_ttl_seconds": 30
  }
  ```

- **Пример ответа (период запрошен, но нет данных):**
  ```json
  {
    "current_active": 0,
    "period": "7d",
    "status": "no_data",
    "source_error": null,
    "aggregates": [],
    "last_updated": "2026-07-26T10:22:15Z",
    "cache_ttl_seconds": 30
  }
  ```

- **Ошибки:**

| Код | Тело/сообщение | Когда | Состояние UI на фронте |
|-----|----------------|-------|--------------------------|
| 200 OK + `status: available` | см. пример выше | Данные получены успешно | значение / загрузка (по таймеру) / пусто (если нет данных) |
| 200 OK + `status: unavailable` | см. пример выше | Источник активности на бэке недоступен (таймаут, ошибка соединения) | `error_source` — сообщение об ошибке + retry-кнопка |
| 200 OK + `status: no_data` | см. пример выше | За запрошенный период нет данных (например, ещё не накоплены) | `empty` — «нет данных за период» |
| 400 Bad Request | `{ "error": "invalid_period", "message": "period must be one of: current, 1h, 24h, 7d" }` | Параметр `period` некорректен | Ошибка на фронте (разработчик); не показывать пользователю |
| 401 Unauthorized | `{ "error": "unauthorized" }` | Токен отсутствует или невалиден | Перенаправить на логин (или скрыть контрол, если есть предварительная проверка роли на фронте) |
| 403 Forbidden | `{ "error": "forbidden", "message": "only Administrator role can access activity data" }` | Роль пользователя не «Администратор» | Скрыть контрол панели активности |
| 5xx (500, 502, 503) | Стандартный текст ошибки сервера | Внутренняя ошибка Arsenal backend | `error_source` — сообщение об ошибке + retry |

  **Примечание к семантике status:** Ответ всегда возвращает HTTP 2xx (успех на уровне сети и авторизации), но `status` внутри JSON различает три состояния:
  - `available` — данные актуальны, используй их
  - `unavailable` — источник активности на бэке был недоступен в момент запроса; не показывай устаревшее; покажи ошибку
  - `no_data` — данные не найдены за период (не ошибка, просто пусто); используй для `empty`-состояния UI

- **Состояния UI по ответу:**
  - `loading`: Первый запрос / после инвалидации (спиннер/скелетон)
  - `value`: 200 OK, `status: available`, `current_active ≠ null`, значение показано (число или граф)
  - `zero`: 200 OK, `status: available`, `current_active = 0` (показать «0», не «—»)
  - `empty`: 200 OK, `status: no_data` (показать «нет данных», «—», пусто)
  - `error_source`: 200 OK, `status: unavailable` (показать ошибку источника) или 5xx / таймаут / сетевая ошибка (показать ошибку)
  - `error_forbidden`: 403 Forbidden (скрыть контрол)

- **Авторизация:**
  - **Кто вправе:** Только пользователи с ролью «Администратор»
  - **Где проверяется:** На бэке Arsenal (middleware / контроллер); сначала valididate токен, потом проверь роль пользователя
  - **Негативный случай:** 403 Forbidden if роль ≠ Administrator. Фронт на основе ошибки должен скрыть панель активности (не показывать, что она существует).

- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1 (отображение счётчика), FR-2 (автообновление), FR-3 (открытие графика), FR-4 (переключение периода), FR-5 (выгрузка)

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- Реализует INT-0: эндпоинт GET `/api/v1/admin/activity` с параметром `period`
- Собирает данные активности (текущий счётчик активных пользователей) в реальном времени; источник — 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции). Arsenal владеет механизмом сбора данных; внешних сервисов для этого не привлекаем. 
- Вычисляет агрегаты на лету по запросу: не хранит историю в отдельной таблице, а агрегирует из текущих логов/событий
- Кэширует ответ на 30 секунд на стороне Arsenal (Cache-Control заголовок и/или in-process кэш)
- При недоступности источника возвращает `status: unavailable`, `current_active: null` (не отдаёт устаревшее значение)
- Различает «источник недоступен» (status: unavailable) от «нет данных за период» (status: no_data)

### 3.2. Данные и хранение

**Новых таблиц нет.** 🟡 подтверждено аналитиком

Агрегаты активности считаются **на лету** из существующих источников данных (сессии, логи событий, или текущий счётчик). Миграции не требуются. 🟡 подтверждено аналитиком

### 3.3. Авторизация/доступ на бэке

- Проверка роли: middleware/контроллер Arsenal Backend проверяет роль пользователя перед тем, как отдать данные
- Только роль «Администратор» получает доступ к контракту INT-0
- Проверка происходит после валидации токена (на уровне приложения)
- 403 Forbidden возвращается для иных ролей

## 4. Frontend — ответственность

*Не применимо: узел-фундамент #0 — это BE-only слой. Фронты реализуются в детских узлах (ARS-101, ARS-102, ARS-103).*

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** Синхронный запрос (HTTP GET) с ответом и без очереди
- **Кэш:** 30 секунд на стороне Arsenal Backend (Cache-Control: max-age=30 или эквивалент)
- **Таймаут:** 5 секунд на таймаут запроса на бэке (если источник активности не ответит за 5с, возвращаем `status: unavailable`)
- **Частота опроса:** Фронты детей определяют сами (см. их спеки). Рекомендуется не чаще 1 раза в 5 секунд для счётчика (для экономии запросов; кэш 30с уже сглаживает нагрузку).
- **Ожидаемая нагрузка:** 🟡 подтверждено аналитиком: детей несколько (ARS-101, ARS-102, ARS-103), каждый может делать 1–2 запроса в минуту; пиковая нагрузка ~10 RPS на эндпоинт INT-0 🟡 подтверждено аналитиком

### 5.2. Надёжность/деградация

- **При недоступности источника активности:** Возвращаем признак недоступности (`status: unavailable`, `current_active: null`), **не** отдаём устаревшее значение
- **При отсутствии данных за период:** Возвращаем `status: no_data` (отличаем от ошибки) и пустой `aggregates: []`
- **Таймауты:** Если источник не ответит за 5 секунд, прерываем ожидание и возвращаем `status: unavailable` + код ошибки `service_timeout`
- Фронты на основе `status` и `source_error` решают, показать ошибку или переключиться на `empty`-состояние

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто | Что может | Как проверяется |
|---------|-----|-----------|-----------------|
| FE детей ↔ INT-0 (Arsenal BE) | Администратор | GET `/api/v1/admin/activity` с любым `period` | Роль в токене, проверка на бэке Arsenal |
| FE детей ↔ INT-0 (Arsenal BE) | Оператор, другие роли | Доступ запрещён | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟢 Фундамент **выкатывается раньше потребителей** (ARS-101, ARS-102, ARS-103). Детские фронты развёртываются только после того, как контракт INT-0 уже доступен в production. Это гарантирует, что фронты детей могут начать вызывать INT-0 без 404-ошибок.

### 6.2. Обратная совместимость

Фундамент — новый слой, обратная совместимость не требуется (нет старых потребителей). При будущих изменениях контракта INT-0 нужно:
- Добавлять поля в ответ (опциональные; старые фронты их игнорируют)
- Расширять enum `status` (новые статусы добавляются; старые фронты обрабатывают через `default` в switch)
- Не удалять обязательные поля и не менять их семантику без версионирования

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком: **Флагов нет.** Фундамент выкатывается атомарно вместе с детьми в окончательном виде; rollout не нуждается в постепенном включении.

### 6.4. План отката

- **Откат только BE (фундамента):** Фронты детей получат 404 или 5xx на INT-0. Это недопустимо, откат должен быть синхронным с откатом фронтов или произойти после подтверждения, что фронты перестроены.
- **Откат только FE (детей):** BE фундамента продолжает работать и отдавать INT-0. Ничего страшного; можно откатить одного ребёнка независимо.
- **DDL откат:** На сей день нет (новых таблиц нет). Если будущие версии добавят хранение, план откатывается на том этапе.

### 6.5. Преднастройка до релиза (чек-лист)

- [ ] Роли в security-сервисе: убедиться, что роль «Администратор» существует и может быть присвоена пользователям
- [ ] DDL-миграция в репо Arsenal: не требуется (новых таблиц нет)
- [ ] Конфиги по окружениям: параметры таймаута (5с), TTL кэша (30с), путь эндпоинта (`/api/v1/admin/activity`) — проверить в dev/staging/prod
- [ ] Сервисные аккаунты: не требуется (INT-0 использует пользовательский токен)
- [ ] Фиче-флаги: не требуется (выкат атомарный)
- [ ] Алерты на ошибки: 
  - [ ] Тревога, если `/api/v1/admin/activity` начинает отдавать 5xx или таймауты (>50% за 1 минуту)
  - [ ] Тревога, если источник активности становится недоступным (source_error != null за последние 2 запроса подряд)

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс (Дано–Когда–Тогда) |
|----------|-------------------|------------------------------|
| FR-1 | INT-0 | Дано фронт детей авторизован как Администратор, когда он загружается, тогда он вызывает INT-0 с `period=current` и получает 200 с `status: available`, `current_active: <число>` |
| FR-2 | INT-0 | Дано счётчик в шапке, когда число активных пользователей изменилось на источнике, тогда фронт перезапрашивает INT-0 в пределах 30 секунд и счётчик обновляется без перезагрузки страницы |
| FR-3 | INT-0 | Дано фронт открывает модальное окно, когда пользователь кликает на счётчик, тогда фронт вызывает INT-0 с `period=24h` (или другой, по умолчанию) и получает 200 с графиком активности |
| FR-4 | INT-0 | Дано модальное окно открыто, когда пользователь выбирает другой период (1h/7d/etc), тогда фронт вызывает INT-0 с новым `period` и граф перестраивается |
| FR-5 | INT-0 | Дано модальное окно с выбранным периодом, когда пользователь нажимает выгрузку, тогда фронт вызывает INT-0 с соответствующим `period`, получает агрегаты и генерирует файл со сводкой |

Тест-кейсы ошибок:
- **Недоступность источника:** Дано INT-0 недоступен (BE source_error), когда фронт вызывает контракт, тогда получает 200 с `status: unavailable`, `current_active: null` и отображает ошибку в UI (state: `error_source`)
- **Нет доступа (не администратор):** Дано пользователь с ролью Оператор, когда он пытается вызвать INT-0, тогда получает 403 Forbidden и фронт скрывает панель активности
- **Нет данных за период:** Дано INT-0 запрошен с периодом, за который нет данных, когда фронт вызывает контракт, тогда получает 200 с `status: no_data`, `aggregates: []` и отображает пусто (state: `empty`)
