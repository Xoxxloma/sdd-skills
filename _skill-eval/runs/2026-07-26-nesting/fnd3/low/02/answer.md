# Техническая спецификация: узел-фундамент #0 — контракт данных активности

Номер задачи: **ARS-100 / узел-фундамент #0** (из переданного эпик-БТ)

### Что спроектировано

**Единое взаимодействие INT-0** — контракт для получения данных активности пользователей:

- **Синхронный запрос** (GET): параметр `period` выбирает, что вернуть (текущее число активных / почасовые данные за час/день/неделю)
- **Ответ** с явным `status`:
  - `"available"` — данные готовы (current_count, data с точками)
  - `"source_unavailable"` — источник недоступен (current_count=null, data=null) — НЕ показываем устаревшее
  - `"no_data"` — период выбран, но за него нет данных (data=[]) — отличается от ошибки
- **Авторизация**: 403 если не администратор
- **Кэш**: 30 сек на бэке Arsenal, таймаут 5 сек
- **JSON-примеры**: приведены для всех основных сценариев (текущий счёт, данные за день/неделю, ошибки)

### Назначение узла #0

Фундамент — общий технический слой для трёх детских фич (ARS-101 счётчик, ARS-102 график, ARS-103 выгрузка). Все они потребляют один и тот же контракт INT-0:
- **ARS-101** читает current_count каждые 30 сек
- **ARS-102** читает data за выбранный период (hour/day/week)
- **ARS-103** читает data для форматирования и выгрузки в файл

Узел #0 не имеет собственного БТ (это узел реализации), его бизнес-обоснование трассируется к эпик-БТ и FR-1..FR-5.

### Порядок разработки

1. Разрабатывается и деплоится **узел #0** (backend Arsenal — контракт INT-0)
2. После stabilization #0 в production параллельно разрабатываются дети (ARS-101, ARS-102, ARS-103) с кодированием против контракта #0
3. Дети наследуют контракт через спеку (режим B — «дочерний узел наследует контракт #0»), не переопределяют его
