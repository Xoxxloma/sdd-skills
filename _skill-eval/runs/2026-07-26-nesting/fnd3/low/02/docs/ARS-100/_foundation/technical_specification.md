## 1. Обзор изменения
### 1.1. Тип и стороны
🟢 BE-only. Узел-фундамент #0 (чистая реализация, без собственного БТ) спроектирует и реализует на бэке «Арсенала» единый контракт данных активности пользователей. Этот контракт потребляют дочерние фичи (АRS-101, ARS-102, ARS-103), реализующие элементы админки: счётчик в шапке, график в модале и выгрузку. Фронт-дети будут оборачивать этот контракт в UI, бэк-#0 отвечает за сбор и агрегацию.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| «Арсенал» (Backend) | Собирает данные активности, рассчитывает агрегаты, отдаёт контракт | Команда Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями
Узел-фундамент #0 реализует технический слой, общий для FR-1..FR-5 эпика: счётчик в шапке (FR-1, FR-2), график и выгрузка (FR-3..FR-5) — все они потребляют один и тот же источник данных активности (текущее число активных пользователей + агрегаты за период).

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)
- **Граница/направление:** Backend «Арсенала» ← дочерние фиче (фронт детей через фронт «Арсенала»)
  - Фактически: фронт-дитя (напр. в ARS-101) запрашивает у бэка-«Арсенала», бэк отвечает; связь всегда через Backend Arsenal (BE-to-BE для сервис-сервис вызовов или BE-to-FE для фронт-запросов).
- **Триггер:** 
  - Холодный путь: загрузка UI-компонента (счётчик, график, модаль)
  - Тёплый путь: автоматический опрос счётчика (каждые ~30 сек на фронте детей); переключение периода в графике (момент выбора нового периода)
- **Контракт (запрос):**
  - Метод/путь (концептуально): `GET /api/arsenal/activity/summary` (конкретная реализация уточняется на стороне Arsenal, это предложение для согласования)
  - Параметры запроса:
    - `period` (optional, string): период для агрегации активности — `current` (только текущее число) | `hour` | `day` | `week`. По умолчанию: `current`.
- **Контракт (ответ):** 
  - `status` (string, enum): 
    - `"available"` — данные готовы и актуальны
    - `"source_unavailable"` — источник активности недоступен (5xx или таймаут); значения null, поля данных пустые
    - `"no_data"` — период не имеет данных (например, запрос активности за час, когда ещё никто не активен); отличается от `source_unavailable`: это валидный 2xx, но историческое значение = 0 или пусто
  - `current_count` (integer | null): число активных пользователей прямо сейчас. При `status="source_unavailable"` → null. При `status="no_data"` и `period="current"` → 0 (активных нет).
  - `data` (array | null): время-сортированный массив точек данных для выбранного периода (только если `period ≠ "current"`). Каждая точка:
    - `timestamp` (ISO 8601, string): начало интервала агрегации (например, начало часа)
    - `count` (integer): число активных пользователей за этот интервал (может быть 0)
    - `interval_duration_seconds` (integer): длительность интервала (3600 для часа, 86400 для дня, 604800 для недели)
  - При `status="source_unavailable"` → `data` = null
  - При `status="no_data"` и период задан → `data` = [] (пустой массив)
  - Семантика null:
    - `current_count = null` → источник недоступен (не путать с `current_count = 0`, что означает активных нет)
    - `data = null` → ошибка, источник недоступен
    - `data = []` → период выбран, но данных нет (валидный результат)
- **Пример запроса (current):**
  ```
  GET /api/arsenal/activity/summary?period=current
  ```
  Тело отсутствует, параметр в query-строке.
  
- **Пример ответа (успех, текущий счёт доступен):**
  ```json
  {
    "status": "available",
    "current_count": 42,
    "data": null
  }
  ```

- **Пример запроса (период день):**
  ```
  GET /api/arsenal/activity/summary?period=day
  ```

- **Пример ответа (успех, день с данными):**
  ```json
  {
    "status": "available",
    "current_count": 42,
    "data": [
      {
        "timestamp": "2026-07-26T00:00:00Z",
        "count": 15,
        "interval_duration_seconds": 3600
      },
      {
        "timestamp": "2026-07-26T01:00:00Z",
        "count": 22,
        "interval_duration_seconds": 3600
      },
      {
        "timestamp": "2026-07-26T02:00:00Z",
        "count": 28,
        "interval_duration_seconds": 3600
      }
    ]
  }
  ```

- **Пример ответа (источник недоступен):**
  ```json
  {
    "status": "source_unavailable",
    "current_count": null,
    "data": null
  }
  ```

- **Пример ответа (период выбран, но данных нет):**
  ```json
  {
    "status": "no_data",
    "current_count": 5,
    "data": []
  }
  ```

- **Ошибки:**
  - `403 Forbidden` — пользователь не имеет роли «Администратор» (см. авторизацию ниже). Тело: `{ "code": "FORBIDDEN", "message": "Доступ запрещён: требуется роль Администратор" }`
  - `400 Bad Request` — неверный параметр `period` (не один из допустимых значений). Тело: `{ "code": "INVALID_PERIOD", "message": "Параметр period должен быть: current, hour, day или week" }`
  - `5xx` / таймаут — обработка см. в семантике ответа выше (status="source_unavailable")
  - Клиент интерпретирует таймаут / сетевую ошибку как `status="source_unavailable"`

- **Состояния UI по ответу (если есть фронт):**
  - `status="available"` и `current_count ≠ null` → **значение**: показать число (текущий счёт) или график (если период)
  - `status="available"` и `current_count = 0` → **zero**: показать «0», не прочерк
  - `status="no_data"` и `data = []` → **empty**: показать прочерк «—» или «нет данных»
  - `status="source_unavailable"` → **error_source**: показать «Источник активности недоступен» + кнопка Retry
  - Таймаут (FE timeout 5s) → **error_source**: показать сообщение об ошибке сети

- **Авторизация:** 
  - 🟡 подтверждено аналитиком: контракт доступен только пользователям с ролью «Администратор»
  - Проверка выполняется на бэке «Арсенала» перед возвратом данных (раньше запроса к источнику активности)
  - Отсутствие роли → `403 Forbidden`
  - Роль «Оператор» и ниже не видят этот контракт (должно явно скрыть UI в детях)

- **Происхождение:** 🟢 новое (узел-фундамент #0)
- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (все требования эпика опираются на этот контракт для данных)

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| `403 Forbidden` | `{ "code": "FORBIDDEN", "message": "Доступ запрещён: требуется роль Администратор" }` | Пользователь не администратор | Скрыть панель активности, показать сообщение (если перейти напрямую через URL) |
| `400 Bad Request` | `{ "code": "INVALID_PERIOD", "message": "Параметр period должен быть: current, hour, day или week" }` | Передан неверный period | Показать ошибку валидации (внутренняя ошибка FE) |
| `5xx` / таймаут | — | Источник активности недоступен / требуемое время обработки превышено | `error_source` в UI; показать сообщение об ошибке + Retry |

## 3. Backend — ответственность

### 3.1. По сервисам
🟡 подтверждено аналитиком: Backend «Арсенала» реализует контракт INT-0 полностью:
- Сбирает сырые данные об активности пользователей (вход этих данных уточняется на стороне Arsenal; может быть логирование сессий, события, очередь и т.п. — техническая реализация источника за рамками #0)
- Рассчитывает текущее число активных пользователей (снимок прямо сейчас)
- Рассчитывает агрегированные данные активности за периоды (час, день, неделя) — почасовая детализация
- Возвращает ответ в формате INT-0 с проверкой авторизации (роль «Администратор» ниже ползователя по умолчанию)

🟢 Трёх дочерних фичей (ARS-101, ARS-102, ARS-103) достаточно знать этот контракт и вызывать его при необходимости (счётчик → чтение `current_count`; график → чтение `data` за выбранный период; выгрузка → чтение `data` и форматирование).

### 3.2. Данные и хранение
🟡 подтверждено аналитиком: агрегаты активности **вычисляются на лету**, новых постоянных таблиц не заводится. Хранилище источника активности (логи сессий, события и т.п.) — в ответственности Arsenal, это ДО узла #0. Кэш результата агрегации (см. §5.1) может быть in-memory или кэш-слой (рассчитывается на лету с кэшем в памяти BE «Арсенала»).

### 3.3. Авторизация/доступ на бэке
🟡 подтверждено аналитиком: перед вычислением и возвратом данных BE «Арсенала» проверяет, что запрашивающий пользователь имеет роль «Администратор» (используя сервис авторизации Arsenal). Если нет → возвращает `403 Forbidden`.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Фронт-дети (компоненты в ARS-101, ARS-102, ARS-103) потребляют контракт INT-0:
- **ARS-101** (счётчик в шапке): вызывает INT-0 с `period=current`, отображает `current_count`, обновляет периодически
- **ARS-102** (график в модале): вызывает INT-0 с `period` = выбранное значение (hour/day/week), отображает `data` в виде графика
- **ARS-103** (выгрузка): вызывает INT-0 с выбранным `period`, форматирует `data` и скачивает файл

Видимость: все три элемента показываются только пользователям с ролью «Администратор» (проверка на фронте — если `403 Forbidden`, скрыть элементы).

### 4.2. Пользовательские сценарии
**Основной поток (счётчик):**
- Дано: открыта админка, пользователь — администратор
- Когда: страница загрузилась
- Тогда: счётчик запрашивает текущее число активных (INT-0 с `period=current`), показывает `current_count`
- И: счётчик переопрашивает каждые ~30 сек (кэш на бэке), обновляет число без перезагрузки

**Основной поток (график):**
- Дано: администратор кликнул на счётчик
- Когда: открылась модаль
- Тогда: фронт запрашивает активность за день по умолчанию (INT-0 с `period=day`), рисует график
- И: администратор может выбрать другой период (час/неделя) → фронт переопрашивает INT-0 с новым period, перестраивает график

**Основной поток (выгрузка):**
- Дано: модаль открыта с графиком за выбранный период
- Когда: администратор нажимает кнопку «Выгрузить»
- Тогда: фронт берёт `data` из уже загруженного ответа (или переопрашивает для верности), форматирует сводку (CSV/XLSX/JSON), скачивает файл

**Исключения:**
- Если `status="source_unavailable"` или таймаут → показать сообщение об ошибке, предложить повторить
- Если `status="no_data"` и `data=[]` → показать «нет данных за этот период»

### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос или после смены периода | спиннер / скелетон счётчика или графика |
| `value` | 2xx, `status="available"`, значение > 0 | число в счётчике или график с точками |
| `zero` | 2xx, `status="available"`, `current_count=0` (активных нет, но источник доступен) | «0» в счётчике, пустой график (или график с нулевыми значениями) |
| `empty` | 2xx, `status="no_data"`, `data=[]` (период выбран, но данных нет) | прочерк «—» / «нет данных за этот период» |
| `error_source` | 5xx / таймаут / сеть / `status="source_unavailable"` | сообщение «Источник активности недоступен» + кнопка Retry |
| `error_forbidden` | 403 | сообщение «Нет доступа: требуется роль Администратор» (должно быть скрыто на UI обычно) |

### 4.3.1. Loading и таймауты
- **Таймаут холодного пути** (первый запрос счётчика или график при открытии модали): 5 секунд (по аналитику)
- **Таймаут тёплого пути** (опрос счётчика каждые 30 сек): 5 секунд (абсолютный таймаут запроса)
- При таймауте показать `error_source` вместо значения, предложить Retry
- **Polling** (счётчик): интервал 30 секунд, кэш на бэке 30 сек → фронт получит обновление в пределах 30 сек после изменения активности (как в CR: «в пределах минуты»)

### 4.4. Доступ по ролям в UI
- **Администратор**: видит счётчик, может открыть модаль, выгружать сводку
- **Оператор и ниже**: панель активности полностью скрыта (см. БТ ролевую модель §5.3)

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
🟡 подтверждено аналитиком:
- **Синхронность**: INT-0 отвечает синхронно (блокирующий вызов)
- **Кэш**: результат агрегации кэшируется на 30 секунд на стороне бэка «Арсенала» (in-memory кэш или Redis — реализация)
- **Таймаут**: 5 секунд на выполнение запроса (это бизнес-таймаут; если обработка занимает дольше, вернуть ошибку 5xx, FE переведёт в `error_source`)
- **Частота опроса**: фронт опрашивает счётчик каждые ~30 сек; при смене периода в графике — немедленный запрос
- **Ожидаемая нагрузка**: рассчитывается на лету за счёт кэша; нагрузка на источник активности зависит от количества администраторов, но кэш 30s существенно снижает её (максимум раз в 30 сек один вызов источника)

### 5.2. Надёжность/деградация
🟡 подтверждено аналитиком:
- **При недоступности источника**: BE возвращает `status="source_unavailable"`, текущее число = null, data = null (не выдаёт устаревшее значение, даже если знает его)
- **При отсутствии данных за период**: BE различает это от недоступности и возвращает `status="no_data"` (валидный 2xx), `current_count` = текущее число (если доступно), `data = []`
- **Пользователь видит**: в первом случае — сообщение об ошибке (retry); во втором — «нет данных» (не ошибка)

### 5.3. Безопасность/доступ (сводно)
| Граница | Кто вправе | Проверка | Отказ |
|---------|-----------|---------|-------|
| INT-0 (GET /api/arsenal/activity/summary) | Пользователь с ролью «Администратор» | Бэк Arsenal проверяет роль (сервис авторизации) ДО возврата данных | 403 Forbidden |

## 6. Релиз и интеграция

### 6.1. Порядок выката
🟡 подтверждено аналитиком: **узел-фундамент #0 выкатывается ПЕРВЫМ**, раньше дочерних фич (ARS-101, ARS-102, ARS-103). Дети кодятся и деплоятся только после того, как #0 готов в production и контракт INT-0 стабилен.

### 6.2. Обратная совместимость
🟢 Новый контракт; вопрос совместимости не встаёт. Дочерние фичи при разработке привязываются к этому контракту.

### 6.3. Фиче-флаги
🟡 подтверждено аналитиком: **фиче-флагов нет**, релизим атомарно. Узел #0 либо полностью готов, либо нет; дети добавляют флаги если нужно (решается на уровне детских спек).

### 6.4. План отката
Узел #0 — BE-only интеграция (контракт). Откат:
- **Откат BE (Arsenal)**: вернуться на старую версию BE → INT-0 недоступен. Дети (FE) получат ошибку 404 или 5xx → они покажут `error_source`. Допустимо при краткосрочном откате (дети разработаны с учётом обработки ошибок). Если длительный откат — может потребоваться синхронный откат FE-детей (решается в их спеках).
- **Откат исторических данных (if ever stored)**: не применимо, т.к. данные вычисляются на лету.

### 6.5. Преднастройка до релиза (чек-лист)
- [ ] Роли в security-сервисе: убедиться, что роль «Администратор» существует и у нужных пользователей
- [ ] DDL-миграция в репо Arsenal: не требуется (таблиц не заводится)
- [ ] Конфиги по окружениям: настроить таймауты, кэш-TTL (30 сек) по окружениям (dev/staging/prod если отличаются)
- [ ] Сервисные аккаунты: не требуется (интеграция внутри Arsenal)
- [ ] Фиче-флаги: не требуется
- [ ] Алерты/мониторинг: настроить алерты на 5xx от INT-0, таймауты, недоступность источника активности (важно видеть, когда данные невалидны)

| FR-2 | INT-0 (polling текущего счёта) | Дано счётчик в шапке с числом 42, когда число активных пользователей изменилось на 50, тогда фронт через ~30 сек переопросит INT-0 и обновит счётчик на 50 без перезагрузки |

| FR-5 | INT-0 (получить данные для выгрузки) | Дано модаль с графиком за выбранный период, когда администратор нажал кнопку выгрузки, тогда фронт использовал data из последнего ответа INT-0, сформировал сводку (CSV/XLSX) и предложил скачать файл |
