## 1. Обзор изменения

### 1.1. Тип и стороны

BE-only. Узел-фундамент #0 обеспечивает универсальный контракт для отдачи данных активности пользователей (текущее число активных и исторические агрегаты за период). Потребители — фронтовые дети эпика (FR-1..FR-5).

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal (BE) | Собирает и отдаёт данные активности | Team Arsenal | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Узел-фундамент #0 поставляет единый источник данных активности для всех функциональных требований эпика (FR-1..FR-5): текущий счётчик активных пользователей и исторические агрегаты за выбранный период для графика и выгрузки.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal BE → Frontends (дети эпика)

- **Триггер:** Инициализация представления активности (загрузка страницы для FR-1/2) или клик на счётчик/выбор периода (для FR-3/4/5)

- **Контракт (запрос):** HTTP GET, концептуальный путь `/admin/api/activity`
  - Параметр `mode` (обязательный): `current` | `aggregate`
  - При `mode=current`: нет доп. параметров
  - При `mode=aggregate`:
    - `period` (обязательный): `hour` | `day` | `week` | `custom`
    - `fromDate` (строка ISO8601, обязателен при `period=custom`)
    - `toDate` (строка ISO8601, обязателен при `period=custom`)

- **Контракт (ответ):**
  - `status` (строка): `ok` | `unavailable` | `no_data`
    - `ok` → данные доступны и успешно получены
    - `unavailable` → источник недоступен (сервис/БД вверх или ошибка получения)
    - `no_data` → период валиден, но данных за этот период нет
  - `timestamp` (строка ISO8601): момент формирования ответа
  - При `status=ok` и `mode=current`:
    - `currentCount` (число): текущее число активных пользователей (≥ 0)
  - При `status=ok` и `mode=aggregate`:
    - `periodStart` (строка ISO8601): начало периода
    - `periodEnd` (строка ISO8601): конец периода
    - `dataPoints` (массив объектов): временной ряд активности
      - `timestamp` (строка ISO8601): момент точки данных
      - `count` (число): количество активных пользователей в этот момент
    - `summary` (объект): агрегированные метрики за период
      - `peak` (число): пиковое количество активных пользователей за период
      - `average` (число, может быть дробным): среднее активных за период
      - `min` (число): минимальное количество активных за период
  - При `status=unavailable`:
    - `errorMessage` (строка): описание ошибки (напр. «Источник данных недоступен» или «Таймаут при получении данных»)
  - При `status=no_data`:
    - `reason` (строка): причина отсутствия (напр. «Нет записей активности за выбранный период»)

- **Пример запроса (mode=current):**
  ```
  GET /admin/api/activity?mode=current
  ```

- **Пример ответа (mode=current, успех):**
  ```json
  {
    "status": "ok",
    "currentCount": 42,
    "timestamp": "2026-07-26T14:30:00Z"
  }
  ```

- **Пример ответа (mode=current, недоступность):**
  ```json
  {
    "status": "unavailable",
    "timestamp": "2026-07-26T14:30:00Z",
    "errorMessage": "Таймаут при получении данных активности"
  }
  ```

- **Пример запроса (mode=aggregate):**
  ```
  GET /admin/api/activity?mode=aggregate&period=day&fromDate=2026-07-26T00:00:00Z&toDate=2026-07-26T23:59:59Z
  ```

- **Пример ответа (mode=aggregate, успех):**
  ```json
  {
    "status": "ok",
    "timestamp": "2026-07-26T14:30:00Z",
    "periodStart": "2026-07-26T00:00:00Z",
    "periodEnd": "2026-07-26T23:59:59Z",
    "dataPoints": [
      { "timestamp": "2026-07-26T00:00:00Z", "count": 5 },
      { "timestamp": "2026-07-26T01:00:00Z", "count": 8 },
      { "timestamp": "2026-07-26T02:00:00Z", "count": 12 },
      { "timestamp": "2026-07-26T14:30:00Z", "count": 42 }
    ],
    "summary": {
      "peak": 52,
      "average": 18.5,
      "min": 2
    }
  }
  ```

- **Пример ответа (mode=aggregate, нет данных):**
  ```json
  {
    "status": "no_data",
    "timestamp": "2026-07-26T14:30:00Z",
    "periodStart": "2026-07-26T00:00:00Z",
    "periodEnd": "2026-07-26T23:59:59Z",
    "reason": "Нет записей активности за выбранный период"
  }
  ```

- **Ошибки:** 
  - HTTP 200 со `status=unavailable` → источник данных недоступен (DB, внутренний сервис, таймаут)
  - HTTP 200 со `status=no_data` → период валиден, но нет активности
  - HTTP 400 → некорректные параметры запроса (напр. `fromDate` > `toDate`, отсутствуют обязательные параметры при `mode=aggregate`)
  - HTTP 401 → не авторизирован
  - HTTP 403 → роль не имеет доступа (не Администратор)
  - HTTP 500 → неожиданная ошибка бэка

- **Состояния UI по ответу (если есть фронт):** 
  - HTTP 200, `status=ok`, `currentCount ≥ 1` → значение: отображить счётчик с числом
  - HTTP 200, `status=ok`, `currentCount = 0` → ноль: отображить «0» (не прочерк)
  - HTTP 200, `status=ok`, `dataPoints[]` непусто → данные графика: построить график по точкам
  - HTTP 200, `status=no_data` → пусто/прочерк: «—» или «Нет данных за период»
  - HTTP 200, `status=unavailable` → ошибка_источника: «Данные недоступны», retry кнопка
  - HTTP 403 → ошибка_доступа: «Нет доступа к этой функции»
  - HTTP 5xx, таймаут, сеть → ошибка_сети: «Ошибка при загрузке данных», retry кнопка

- **Авторизация:** 
  - Контракт доступен **только роли Администратор**. Проверка выполняется на стороне Arsenal BE (включена в логику `/admin/api/activity`).
  - Негативный случай (роль Оператор): HTTP 403 Forbidden с сообщением «Доступ запрещён».
  - 🟡 подтверждено аналитиком: проверка роли Администратор осуществляется на бэке Арсенала (не по коду; валидировать при интеграции).

- **Происхождение:** 🟢 новое (узел-фундамент #0)

- **Трассировка:** FR-1 (счётчик в шапке), FR-2 (обновление счётчика), FR-3 (открытие модалки с графиком), FR-4 (переключение периода), FR-5 (выгрузка сводки)

### Каталог ошибок (сводно)

| HTTP код | Тело/статус | Когда | Состояние UI | Действие клиента |
|----------|-------------|-------|--------------|------------------|
| 200 | `status=ok` | Данные успешно получены | Отобразить данные (счётчик, график, сводка) | Использовать данные |
| 200 | `status=unavailable` | Источник недоступен (DB down, сервис не отвечает, таймаут ≥ 5s) | Ошибка: «Данные недоступны» + retry | Повторить запрос через UI |
| 200 | `status=no_data` | Период валиден, но активности не найдено | Пусто: «—» или «Нет данных за период» | Показать пустое состояние |
| 400 | `{"error": "Invalid parameters"}` | Некорректные параметры (отсутствуют обязательные, диапазон дат некорректен) | Ошибка: «Проверьте введённые данные» | Исправить ввод |
| 401 | `{"error": "Unauthorized"}` | Сессия истекла / нет токена | Перенаправить на логин | Переавторизоваться |
| 403 | `{"error": "Forbidden"}` | Роль не Администратор | Скрыть панель активности | Панель скрыта для роли |
| 500 | `{"error": "Internal server error"}` | Непредвиденная ошибка бэка | Ошибка: «Технический сбой» + retry | Повторить запрос |

## 3. Backend — ответственность

### 3.1. Arsenal BE

Реализует INT-0:
- Собирает текущие данные активности пользователей (в реальном времени из сессионного хранилища).
- При запросе с `mode=current`: возвращает актуальный счётчик активных пользователей.
- При запросе с `mode=aggregate`: читает исторические данные активности за запрошенный период и вычисляет агрегаты (пик, среднее, минимум) на лету.
- При недоступности источника данных: возвращает `status=unavailable` с описанием ошибки, никогда не отдаёт устаревшие данные.
- При отсутствии данных за период: возвращает `status=no_data` (отличает от `unavailable`).
- Проверяет роль Администратор до обработки запроса; при отсутствии роли возвращает HTTP 403.
- Применяет 30-секундный кэш ответа на стороне Arsenal BE для `mode=current` (повышает производительность при частых обновлениях счётчика в шапке).
- Таймаут обработки запроса: 5 секунд (если источник не отвечает, вернуть `status=unavailable`).

🟡 подтверждено аналитиком (не по коду; валидировать при интеграции):
- Arsenal BE имеет доступ к источнику данных активности (сессионное хранилище, БД активности или иной источник).
- Проверка роли Администратор интегрирована в маршрут `/admin/api/activity`.
- Возможность расчёта агрегатов (пик, среднее) за произвольный период выполнима при текущей архитектуре.

### 3.2. Данные и хранение

**Новых таблиц и сущностей не заводим.** 🟡 подтверждено аналитиком: агрегаты активности считаются на лету из существующих данных об активности (сессиях пользователей).

Существующие данные (по подтверждению аналитика):
- 🟡 подтверждено аналитиком: Arsenal BE уже хранит информацию об активных сессиях пользователей или логирует активность, из которой можно извлечь текущий счётчик и исторические метрики.
- На-лету при запросе агрегат-мода: фильтрация активности по временному диапазону, подсчёт пика/среднего/минимума.

### 3.3. Авторизация/доступ на бэке

- Эндпоинт `/admin/api/activity` защищен проверкой роли **Администратор**.
- 🟡 подтверждено аналитиком: проверка выполняется средствами security-сервиса / middleware Arsenal BE на уровне маршрута.
- При отсутствии роли Администратор: HTTP 403 Forbidden.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

Не применимо в рамках узла-фундамента #0: это чистая реализация контракта на стороне BE. Фронтовые дети (FR-1..FR-5) потребляют контракт INT-0 и строят свои UI-компоненты:
- **FR-1/FR-2:** Счётчик в шапке админки (использует `mode=current`).
- **FR-3/FR-4:** Модальное окно с графиком (использует `mode=aggregate`).
- **FR-5:** Выгрузка сводки (использует `mode=aggregate`, преобразует `summary` в CSV/Excel).

Каждый фронтовый ребёнок наследует контракт INT-0 и строит свои состояния UI вокруг ответов.

### 4.2. Пользовательские сценарии

Не применимо: узел-фундамент #0 не содержит пользовательского взаимодействия. Сценарии —в дочерних узлах.

### 4.3. Состояния (именованные)

Не применимо: управление состояниями UI находится на уровне потребителей контракта (фронтовых детей). Узел-фундамент определяет только семантику ответов (`ok` / `unavailable` / `no_data`), которые дети преобразуют в свои UI-состояния.

### 4.4. Доступ по ролям в UI

Не применимо: авторизация выполняется на бэке (HTTP 403 для не-администраторов). Фронт получает либо данные, либо 403, и действует соответственно.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- **Синхронность:** Запрос–ответ синхронный (HTTP GET, без очереди/background jobs).
- **Кэш:** 30 секунд на стороне Arsenal BE для `mode=current`. Кэш обновляется при изменении активности или по TTL. 🟡 подтверждено аналитиком: кэширование выполнимо средствами Arsenal BE (Redis, в памяти или иное).
- **Таймаут:** 5 секунд на получение данных. При истечении таймаута: HTTP 200 со `status=unavailable`.
- **Частота опроса (на стороне фронта):** Определяется детьми эпика (FR-1..FR-5); узел-фундамент не регулирует.
- **Ожидаемая нагрузка:** Определяется потребителями (фронтовыми детьми). Arsenal BE должен справиться с ежесекундными запросами счётчика в шапке при наличии кэша.

### 5.2. Надёжность/деградация

- **При недоступности источника данных:** Возвращаем `status=unavailable` с описанием ошибки. **НЕ отдаём устаревшие кэшированные данные.** 🟡 подтверждено аналитиком: это поведение соответствует бизнес-требованию (п. 2.3).
- **При отсутствии данных за период:** Возвращаем `status=no_data` (отличие от ошибки). Фронт отображает пустое состояние (пусто/«—»), а не ошибку.
- **Повторные попытки:** Фронт может повторить запрос при ошибке `unavailable` или сетевой ошибке. Кэш на бэке не препятствует повторным попыткам.

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто | Может | Не может |
|---------|-----|-------|----------|
| GET /admin/api/activity | Администратор | Запросить текущие данные и агрегаты | — |
| GET /admin/api/activity | Оператор (не админ) | — | Запросить данные (получает 403) |
| GET /admin/api/activity | Неавторизирован | — | Запросить данные (получает 401) |

## 6. Релиз и интеграция

### 6.1. Порядок выката

**Узел-фундамент #0 выкатывается РАНЬШЕ фронтовых детей (FR-1..FR-5).**

1. **День 1:** Выкатить Arsenal BE с эндпоинтом INT-0 (`/admin/api/activity`) и кэшем.
2. **День 2+:** Выкатить фронтовых детей (FR-1..FR-5), которые потребляют INT-0.

Причина: дети не могут работать без контракта фундамента. Контракт разработан, тестирован и стабилен перед выкатом потребителей.

### 6.2. Обратная совместимость

- Эндпоинт INT-0 новый (не замена существующего).
- Откат Arsenal BE откатывает INT-0; фронты получают 404. Фронтовые дети должны обработать 404 как `unavailable`.
- Фронтовые дети новые; откат фронта = откат виджета активности (скрыт из меню или 404-страница).
- 🟡 подтверждено аналитиком: обратная совместимость не требуется (новая функция, нет текущих потребителей).

### 6.3. Фиче-флаги

🟡 подтверждено аналитиком: **фиче-флагов нет**. Релизим атомарно:
- Контракт INT-0 выкатывается без флага (сразу рабочий, но потребителей ещё нет).
- Фронтовые дети выкатываются без флага; они сами решают, когда показать виджет (напр. по версии бэка или по ролям).

### 6.4. План отката

- **Откат только Arsenal BE:** Эндпоинт INT-0 недоступен (404 или 503). Фронтовые дети получают 5xx, переводят состояние в `unavailable`. Пользователи видят ошибку и retry кнопку.
- **Откат только фронта:** Arsenal BE продолжает отдавать INT-0. Виджет активности скрыт из меню или откачен. Переавторизация или очистка кэша браузера требуется для видимости откатанного состояния.
- **Откат DDL:** Не применимо — новых таблиц нет (см. §3.2).

### 6.5. Преднастройка до релиза

- [ ] Роли в security-сервисе: роль Администратор уже существует (БТ п. 5.3); проверить, что проверка на эндпоинте `/admin/api/activity` использует её. 🟡 подтверждено аналитиком: интеграция с существующим security-сервисом.
- [ ] DDL-миграция в репо Arsenal BE: не требуется (новых таблиц нет; п. 3.2).
- [ ] Конфиги по окружениям (dev/staging/prod): таймаут 5 сек, кэш 30 сек. Проверить, что значения установлены в config Arsenal BE.
- [ ] Сервисные аккаунты: не требуется (Arsenal BE не обращается к новым внешним сервисам; п. 3.1).
- [ ] Фиче-флаги заведены: не требуется (п. 6.3).
- [ ] Алерты/мониторинг: настроить алерты на ошибки INT-0 (5xx, таймауты, частые `status=unavailable`). 🟡 подтверждено аналитиком: мониторинг Arsenal BE покрывает эндпоинт.
