> **Задача:** ARS-100 / узел-фундамент #0
> **Источник (БТ):** docs/ARS-100/business_requirements.md (эпик)
>
> **Статус готовности:** Готово к разработке
>
> **Открытые вопросы:** Все технические решения приняты, спецификация готова к разработке.

## 1. Обзор изменения

### 1.1. Тип и стороны

🟢 **BE-only.** Фундамент #0 — чистая реализация, не связанная с одним ребёнком. Предоставляет унифицированный контракт данных активности пользователей, который потребляют несколько детских узлов (FR-1..FR-5 эпика): счётчик в шапке, график в модалке, выгрузка сводки. Дети реализуют независимо каждый свой интерфейс, опираясь на один и тот же источник данных.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Arsenal Backend | Собирает данные активности, отдаёт контракт; кэширует, авторизует | Arsenal-Core | 🟡 подтверждено аналитиком |

### 1.3. Связь с бизнес-требованиями

Фундамент обслуживает общий слой данных для FR-1..FR-5: текущее число активных пользователей и агрегаты активности за период (час / день / неделя). Без этого контракта дети не смогут отобразить ни счётчик, ни график, ни выгрузку.

## 2. Взаимодействия (ядро)

### INT-0. Получение данных активности пользователей — 🟢 (фундамент, наследуется детьми)

- **Граница/направление:** Arsenal Backend → Потребители (фронты детей)
- **Триггер:** 
  - FR-1: инициализация админки (первый запрос счётчика)
  - FR-2: периодический опрос счётчика (в пределах 30с)
  - FR-3: открытие модального окна (первый запрос графика)
  - FR-4: смена периода в модалке (новый запрос графика)
  - FR-5: нажатие кнопки выгрузки (запрос данных для выгрузки)
- **Контракт (запрос):**
  - **Метод/Путь:** `GET /api/arsenal/activity` (концептуально; уточняется при реализации)
  - **Параметры запроса:**
    - `period_type` (обязателен; enum): `current` | `hour` | `day` | `week`
      - `current` → текущее число активных пользователей и статус доступности
      - `hour` / `day` / `week` → агрегаты активности за последний час/день/неделю + статус
    - `reference_date` (опционально, ISO8601): дата для расчёта периода; по умолчанию текущий момент
  - **Авторизация в запросе:** заголовок `Authorization` с токеном; проверяется на стороне Arsenal Backend
- **Контракт (ответ):**
  - **period_type** (string): отражение запрошенного типа периода
  - **timestamp** (string, ISO8601): момент снятия данных на бэке
  - **status** (string, enum):
    - `available` → данные доступны и актуальны
    - `unavailable` → источник недоступен / таймаут (не возвращаем устаревшие данные)
    - `no_data` → источник доступен, но данных за этот период нет (напр. граница времени суток, новая система)
  - **current_active_count** (integer | null):
    - Для `current`: число активных пользователей прямо сейчас (≥ 0)
    - Для `hour` / `day` / `week`: null (не заполняется для агрегатов за период)
  - **period_data** (object | null):
    - Только при `period_type` != `current`
    - Содержит агрегированные данные активности за период:
      - **total_sessions** (integer): общее число активных сессий за период
      - **peak_concurrent** (integer): пик одновременно активных за период
      - **average_concurrent** (number, float): среднее число одновременно активных за период
      - **period_start** (string, ISO8601): начало периода (UTC)
      - **period_end** (string, ISO8601): конец периода (UTC)
    - Для `period_type` == `current` или при `status` != `available`: null
  - **error_code** (string | null):
    - Только при `status` != `available`
    - `source_unavailable` → источник данных не отвечает / таймаут
    - `source_error` → ошибка источника (500+)
    - `no_data_for_period` → данные за период отсутствуют
    - Иные: `invalid_period` (невалидный period_type)
  - **error_message** (string | null): текст ошибки (в технических логах; в UI скрывается за статусом)
- **Пример запроса (текущая активность):**
  ```
  GET /api/arsenal/activity?period_type=current
  Authorization: Bearer <token>
  ```
- **Пример ответа (успех, текущие данные):**
  ```json
  {
    "period_type": "current",
    "timestamp": "2026-07-26T14:32:15Z",
    "status": "available",
    "current_active_count": 42,
    "period_data": null,
    "error_code": null,
    "error_message": null
  }
  ```
- **Пример запроса (агрегаты за день):**
  ```
  GET /api/arsenal/activity?period_type=day&reference_date=2026-07-25
  Authorization: Bearer <token>
  ```
- **Пример ответа (успех, агрегаты за день):**
  ```json
  {
    "period_type": "day",
    "timestamp": "2026-07-26T14:32:15Z",
    "status": "available",
    "current_active_count": null,
    "period_data": {
      "total_sessions": 1240,
      "peak_concurrent": 89,
      "average_concurrent": 42.5,
      "period_start": "2026-07-25T00:00:00Z",
      "period_end": "2026-07-25T23:59:59Z"
    },
    "error_code": null,
    "error_message": null
  }
  ```
- **Пример ответа (недоступность источника):**
  ```json
  {
    "period_type": "current",
    "timestamp": "2026-07-26T14:32:15Z",
    "status": "unavailable",
    "current_active_count": null,
    "period_data": null,
    "error_code": "source_unavailable",
    "error_message": "Activity data source did not respond within 5s timeout"
  }
  ```
- **Пример ответа (нет данных за период):**
  ```json
  {
    "period_type": "week",
    "timestamp": "2026-07-26T14:32:15Z",
    "status": "no_data",
    "current_active_count": null,
    "period_data": null,
    "error_code": "no_data_for_period",
    "error_message": "No activity data available for the requested week"
  }
  ```
- **Ошибки (сводно — см. «Каталог ошибок»):**
  - 200 OK + `status: available` → данные доступны
  - 200 OK + `status: unavailable` + `error_code: source_unavailable` → источник не отвечает (таймаут ≥5s)
  - 200 OK + `status: unavailable` + `error_code: source_error` → ошибка источника (5xx)
  - 200 OK + `status: no_data` + `error_code: no_data_for_period` → нет данных за период (валидное состояние)
  - 400 Bad Request + `error_code: invalid_period` → невалидный период в запросе
  - 403 Forbidden → нарушение авторизации (см. раздел авторизации)
  - 5xx → собственная ошибка Arsenal Backend (редко; логируется, в UI → `status: unavailable`)
- **Состояния UI по ответу (для потребителей FR-1..FR-5):**
  - `status: available` + `current_active_count` (не null, ≠ 0) → **FE state: `value`** — отобразить число
  - `status: available` + `current_active_count` = 0 → **FE state: `zero`** — отобразить «0» (не прочерк)
  - `status: available` + `current_active_count` = null → **FE state: `empty`** — отобразить «—» (нет данных за период / граница)
  - `status: unavailable` (источник не отвечает) → **FE state: `error_source`** — показать сообщение об ошибке + retry
  - `status: no_data` (нет данных за период) → **FE state: `empty`** — показать «—» / «нет данных»
  - `status: unavailable` + `error_code: source_error` (5xx источника) → **FE state: `error_source`** — сообщение об ошибке
  - 403 Forbidden → **FE state: `error_forbidden`** — «нет доступа» (не должно видеть, но на случай изменения прав)
- **Авторизация:**
  - 🟡 подтверждено аналитиком (не по коду): контракт доступен **только ролям `Administrator`** в Arsenal
  - Проверка: на стороне Arsenal Backend перед ответом; в запросе — стандартный bearer-token
  - Негативный случай: если не Администратор → 403 Forbidden (не 401, т.к. аутентификация пройдена, авторизация — нет)
- **Происхождение:** 🟢 новое (узел-фундамент #0, спроектировано в этом документе)
- **Трассировка:** FR-1, FR-2, FR-3, FR-4, FR-5 (эпика ARS-100)

### Каталог ошибок (сводно)

| Код | Тело/статус | Когда | Состояние UI (детям) |
|-----|-----------|-------|------------|
| 200 `available` | полные данные | источник отвечает | `value` / `zero` / `empty` (в зависимости от значения) |
| 200 `unavailable` / `source_unavailable` | без данных; `error_message` | источник не отвечает или таймаут ≥5s | `error_source` — показать сообщение об ошибке + retry |
| 200 `unavailable` / `source_error` | без данных; `error_message` | источник вернул 5xx | `error_source` |
| 200 `no_data` / `no_data_for_period` | без данных; граница периода / новая система | данные за период отсутствуют (не ошибка) | `empty` — показать «—» |
| 400 `invalid_period` | некорректный параметр `period_type` | клиент отправил невалидный период | отклонить на фронте до запроса |
| 403 Forbidden | авторизация не пройдена | роль не `Administrator` | `error_forbidden` — «нет доступа» |

## 3. Backend — ответственность

### 3.1. По сервисам

**Arsenal Backend:**
- 🟢 Реализует INT-0: эндпоинт `GET /api/arsenal/activity`
  - Принимает параметры `period_type` и `reference_date`
  - Для `period_type: current` → возвращает актуальное число активных пользователей (или маркер недоступности)
  - Для `period_type: hour|day|week` → вычисляет агрегаты активности за указанный период
  - Авторизует запрос: проверяет роль `Administrator` (возвращает 403 при отсутствии)
  - При недоступности источника отдаёт маркер `status: unavailable` (не устаревшие данные)
  - Кэширует результат на 30 секунд (см. §5.1)
  - Таймаут на источник активности: 5 секунд (см. §5.1)
- 🟡 подтверждено аналитиком (не по коду): данные активности собирает сам Arsenal Backend, чужих сервисов не привлекает — нет зависимостей от сервиса аутентификации или третьих сторон

### 3.2. Данные и хранение

🟡 подтверждено аналитиком (не по коду): **новых таблиц не заводим.** Агрегаты активности (текущее число, пик, среднее за период) рассчитываются **на лету** из существующих источников данных Arsenal Backend. Индексы и схема существующих таблиц — 🟡 по подтверждению аналитика, точный DDL уточняется при реализации в репо Arsenal.

### 3.3. Авторизация/доступ на бэке

- Контракт INT-0 доступен **только ролям `Administrator`** в системе безопасности Arsenal
- Проверка выполняется на стороне Arsenal Backend **перед** сборкой и отправкой данных
- Негативный случай: роль не `Administrator` → ответ 403 Forbidden (не 401)
- 🟡 подтверждено аналитиком (не по коду): роль проверяется в security-сервисе Arsenal (деталь реализации)

Детям передаётся унифицированный контракт INT-0; они независимо отображают данные и отводят на состояния дочерних узлов.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- 🟢 **Синхронность:** запрос к INT-0 **синхронный** (блокирующий). Фронт ждёт ответа.
- 🟢 **Кэш:** на стороне **Arsenal Backend**, время жизни **30 секунд**. Одновременные запросы в пределах 30с получают закэшированный результат (во избежание штурма источника). При истечении 30с → перезапрос к источнику.
- 🟢 **Таймаут:** на вызов источника активности — **5 секунд**. При превышении → ответ с `status: unavailable` + `error_code: source_unavailable` (не устаревшие данные, не retry на клиенте).
- 🟢 **Нагрузка:** фундамент предназначен для синхронного запроса от админки при загрузке и периодических опросов (FR-2 обновление счётчика в пределах минуты). Ожидаемая нагрузка зависит от числа администраторов; точная оценка — 🟡 к валидации при интеграции.

### 5.2. Надёжность/деградация

- 🟢 При недоступности источника активности (таймаут, ошибка 5xx) → эндпоинт INT-0 отдаёт маркер `status: unavailable` + `error_code`, а **не** закэшированные / устаревшие данные. Потребители (дети) визуально показывают ошибку (состояние `error_source`), а не неправдивые числа.
- 🟢 Различаем случаи:
  - `unavailable` / `source_unavailable` или `source_error` → временная ошибка, потребитель показывает сообщение + кнопку retry
  - `no_data` / `no_data_for_period` → не ошибка, данных просто нет (граница периода, новая система) → потребитель показывает прочерк «—»

### 5.3. Безопасность/доступ (сводно)

| Граница | Кто может | Где enforced | Примечание |
|---------|-----------|-------------|-----------|
| `GET /api/arsenal/activity` | Роль `Administrator` | Arsenal Backend (перед ответом) | Остальные → 403 Forbidden |
| Передача токена | Заголовок `Authorization: Bearer <token>` | Arsenal Backend + security-сервис | Стандартная схема |
| Данные в ответе | Только админ видит точные числа активности | На уровне контракта INT-0 | Потребители (дети) фильтруют по ролям FE-side |

## 6. Релиз и интеграция

### 6.1. Порядок выката

🟢 **Фундамент #0 выкатывается первым**, раньше всех потребителей (детей FR-1..FR-5). После деплоя #0 → дети могут безопасно вызывать INT-0 и отображать данные. Обратный порядок (дети раньше #0) недопустим — дети получат 404 или 5xx.

### 6.2. Обратная совместимость

🟢 Фундамент #0 — новый контракт, нет текущих потребителей. Обратная совместимость не применима в первом выкате. При будущих изменениях INT-0 → соблюдать:
- Новые поля в ответе — добавлять в конец (не переносить существующие)
- Старые поля не удалять без координации с детьми
- Изменение семантики `status` или `error_code` → новые значения, старые сохранять

### 6.3. Фиче-флаги

🟢 **Релизим атомарно, без фиче-флагов.** Фундамент — общая реализация, которую потребляют дети; разрывать логику флагом не имеет смысла. Дети (если потребуют) управляют видимостью своих компонентов (счётчик, модалка) на FE-side.

### 6.4. План отката (обязательно, если задача деплоится)

- **Откат только #0 (дети уже работают на новой версии):** дети получат 404 / 5xx на INT-0 → переходят в состояние `error_source` (на FE-side), показывают сообщение об ошибке. Пользователь видит: счётчик/график скрыты или показывают «—». Синхронный откат детей не требуется (они graceful-ошибаются).
- **Откат FE-детей (BE #0 остаётся новым):** бэк продолжает работать и кэшировать, но фронт-потребители не обращаются. Роллбэк фронта — асинхронно, без синхронизации с #0.
- **Откат DDL:** не применимо (новых таблиц нет).

### 6.5. Преднастройка до релиза (чек-лист)

- [x] Роли в security-сервисе — роль `Administrator` должна существовать и быть применима к нужным пользователям. 🟡 подтверждено аналитиком (не по коду): роль существует в Arsenal, уточнить маппинг при интеграции.
- [ ] DDL-миграция в репо Arsenal — не применимо: новых таблиц нет, агрегаты вычисляются на лету.
- [ ] Конфиги по окружениям (dev/staging/prod) — уточнить таймауты (5s), TTL кэша (30s) при деплое в каждое окружение; нужны ли отличия. 🟡 к валидации.
- [ ] Сервисные аккаунты для межсервисных вызовов — не применимо: #0 не делает исходящих вызовов.
- [ ] Фиче-флаги заведены — не применимо: релизим атомарно.
- [ ] Алерты/мониторинг на ключевые ошибки (5xx, таймауты) — рекомендуется:
  - Алерт на `status: unavailable` в ответах (тренд ошибок)
  - Алерт на p95/p99 latency эндпоинта (порог — TBD; ориентировочно <1s)
  - Логирование таймаутов источника (error_code: `source_unavailable`)

## 7. Трассировка приёмки

| FR из БТ | Взаимодействие(я) | Тест-кейс |
|----------|-------------------|-----------|
| FR-1 | INT-0 (period_type: `current`) | Дано открытую админку, когда страница загрузилась, тогда Arsenal Backend отдаёт число активных пользователей (status: `available`, current_active_count: N) и фронт отображает его. |
| FR-2 | INT-0 (period_type: `current`, кэш 30s) | Дано запущенную админку, когда число активных изменилось, тогда счётчик обновляется в пределах 30s (без перезагрузки страницы). Проверить: при изменении данных на бэке через 5s фронт получит новое значение (30s TTL + частый опрос). |
| FR-3 | INT-0 (period_type: `day`) | Дано счётчик в шапке, когда администратор кликает по нему, тогда фронт запрашивает агрегаты за день (period_type: `day`) и открывает модалку с графиком. |
| FR-4 | INT-0 (period_type: `hour` / `day` / `week`) | Дано открытую модалку, когда администратор выбирает период, тогда фронт запрашивает агрегаты за новый период (period_type: выбранный) и перестраивает график. |
| FR-5 | INT-0 (period_type: выбранный период) | Дано открытую модалку с периодом, когда администратор нажимает выгрузку, тогда фронт запрашивает данные за период (INT-0) и формирует файл выгрузки со сводкой (peak_concurrent, average_concurrent, total_sessions). |

- ✅ Авторизация: роль Administrator на бэке
- ✅ Данные и хранение: агрегаты на лету, новых таблиц нет
- ✅ Sync/производительность: синхронно, кэш 30s, таймаут 5s
- ✅ Порядок выката: фундамент раньше потребителей
