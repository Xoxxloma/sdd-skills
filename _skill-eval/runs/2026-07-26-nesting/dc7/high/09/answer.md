## Гейт 1 & 2: Тип и стороны + инвентарь взаимодействий

**Предложение:** Fullstack изменение. Arsenal admin (FE) начинает потреблять данные об активности пользователей.

**Структура данных:** Я вижу три логических запроса:
- **INT-1.** Текущий счёт активных пользователей (для счётчика в шапке) — обновляется периодически без перезагрузки.
- **INT-2.** Агрегированная активность за период (час/день/неделя) — для графика в модали.
- **INT-3.** Выгрузка файла со сводкой — результат запроса INT-2 в формате, пригодном для скачивания.

Могут ли эти три быть едиными (одна граница с параметром на период / null для текущего) или разделить на отдельные эндпоинты? 

Какие сервисы участвуют:
- **Arsenal admin (FE)** — потребитель (новый вызов).
- **Arsenal backend** — есть ли отдельный сервис мониторинга активности или эта логика живёт в основном бэке Арсенала?

## Гейт 4: Контракт взаимодействий

**Предложение 🟢:** Для каждого INT спроектирую запрос/ответ.

**INT-1 (текущий счёт):**
- Граница: Arsenal FE → Arsenal BE
- Запрос: GET `/admin/activity/current` (параметров нет)
- Ответ: `{ "active_users": <int>, "timestamp": <ISO-8601> }`
  - `active_users` = null если источник недоступен
  - `timestamp` = когда обновлены данные
- Пример ответа: `{ "active_users": 42, "timestamp": "2026-07-26T15:30:45Z" }`

**INT-2 (график за период):**
- Граница: Arsenal FE → Arsenal BE
- Запрос: GET `/admin/activity/history?period=<hour|day|week>&date=<ISO-date>`
- Ответ: `{ "period": "hour|day|week", "data": [ { "bucket": <timestamp>, "count": <int> }, … ], "total": <int> }`
- Пример: 24 бакета за день с часовыми интервалами

**INT-3 (выгрузка):**
- Граница: Arsenal FE → Arsenal BE
- Запрос: POST `/admin/activity/export?period=<hour|day|week>&date=<ISO-date>`
- Ответ: File (CSV/JSON) с summary-таблицей

Подходит ли такой контракт? Нужно ли разделить INT-1/INT-2 или оставить как есть?
