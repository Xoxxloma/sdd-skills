## Технические вопросы для аналитика (Turn 1 — гейты, требующие подтверждения)

### Gate 1–3. Источник данных об активности пользователей (владение и допущения)

**Предположение:** Данные об активных сессиях и их истории уже существуют — либо в сервисе аутентификации (текущее число активных), либо в Arsenal-Core. 

**Вопросы:** 
- На какой сервис (или сервисы) опираемся? Авторизация? Arsenal-Core? Отдельный analytics-сервис?
- Есть ли там уже доступный счётчик текущих активных сессий?
- Есть ли историческая запись — либо события start/end сессий, либо агрегированные числа активных за временные интервалы (за каждый час, день)?
- Или мы **добавляем новое хранилище/сервис** для отслеживания активности?

### Gate 2, 4. Инвентарь и контракты взаимодействий

Спроектировал два основных взаимодействия:

**INT-1. Получить текущее число активных пользователей** (для счётчика в шапке)
- Гипотеза: `GET /api/activity/active-count` → `{ "count": <number|null> }`
- Обновляется периодически (polling), без перезагрузки страницы

**INT-2. Получить активность пользователей за период** (для графика и выгрузки)
- Гипотеза: `GET /api/activity/timeline?from=ISO8601&to=ISO8601` → массив данных о активности
- Ответ может быть разным форматом (см. ниже)

**Вопросы:**
- Один API или два отдельных? (Предлагаю два — они независимы.)
- Какой формат ответа для INT-2? Опции:
  - **A) Временной ряд (по часам/дням):** `[ { "timestamp": ISO, "activeCount": <int> }, ... ]`
  - **B) Агрегированные данные:** `{ "total": <int>, "average": <float>, "byHour": [...], "byDay": [...] }`
  - **C) Другое** — пожалуйста, опишите
- Какая минимальная и максимальная ширина периода запроса? (в ТТ говорится о часе/дне/неделе)

### Gate 4. Формат и содержание выгрузки файла

Кнопка в модали выгружает сводку активности за выбранный период.

**Вопросы:**
- Какой формат выходного файла? (CSV / JSON / PDF / другое?)
- Какие данные должны быть в выгрузке? (например: таблица «время | число активных» / сводка за период / etc.)
- Название файла? (предложение: `activity_summary_<dateFrom>_<dateTo>.csv`)

### Gate 5, 8. Таймауты и ошибки (состояния и производительность)

BR говорит: при недоступности источника показывать «—» или пустой график.

**Гипотезы:**
- Если 5xx или таймаут: показать состояние ошибки / пусто
- Не кэшировать и не показывать устаревшие данные

**Вопросы:**
- Таймаут для первого запроса активного счёта (cold path)? (предложение: 3–5 сек)
- Таймаут для переходящих запросов (warm path)? (предложение: 2–3 сек)
- Интервал polling для счётчика активных? (предложение: 30–60 сек)
- Нужен ли клиентский кэш для исторических данных (INT-2)? Если да — TTL?

### Gate 6. Авторизация

BR чётко говорит: только роль «Администратор» видит панель и может выгружать.

**Подтверждение:** Авторизация на уровне endpoint-а в BE? Или проверка роли уже в FE при отображении UI?

### Gate 9. Порядок выката и совместимость

**Гипотеза:** BE-сервис выкатывается первым (новые эндпоинты), затем FE.

**Вопрос:** Нужны ли фиче-флаги для постепенного включения, или атомарный выкат?
