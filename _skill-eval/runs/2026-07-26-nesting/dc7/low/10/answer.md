# Техническая спецификация: Выгрузка сводки (ARS-93) — Интервью гейтов

Из БТ я выделил подтверждённый бизнес-слой:
- **Проблема:** Администраторы не видят активность пользователей (текущую и историческую).
- **Потребители:** Администраторы системы «Арсенал» (внутренние сотрудники).
- **Цель:** Видеть активность сейчас, в динамике и в виде выгружаемой сводки для планирования работ.
- **Роли:** Администратор (видит всё), Оператор (не видит).
- **FR-5:** В модальном окне есть кнопка выгрузки сводки активности за выбранный период в файл.
- **Критерий приёмки FR-5:** Дано открытую модалку с периодом → когда администратор нажимает выгрузку → он получает файл со сводкой.

## Вопросы по техническим гейтам

### 1. **Тип и стороны + карта сервисов**

Я предполагаю это **fullstack-задача**:
- **Frontend:** модальное окно с графиком, кнопка выгрузки, счётчик в шапке.
- **Backend:** API для текущей активности, график (агрегированные данные), генерация файла.

Вопросы:
- **1.1 Архитектура сервисов:** Активность пользователей — это отдельный сервис (счётчик сессий, события логина/логаута) или часть Arsenal-бэка? Подтвердите, кто владелец этих данных (какая команда).
- **1.2 Владельцы сторон:** Кто владеет Arsenal-фронтом и Arsenal-бэком (одна команда или разные)?

### 2. **Инвентарь взаимодействий**

Я спроектировал три новых взаимодействия (или возможно две, если объединить):
- **INT-1:** FE → BE: Get current active user count (периодический запрос для счётчика).
- **INT-2:** FE → BE: Get activity graph data (for hour/day/week — запрос при открытии модали).
- **INT-3:** FE → BE: Export summary as file (POST или GET с file-response при клике на кнопку).

Вопросы:
- **2.1 Объединение или разделение?** Это три отдельных endpoint или можно объединить в один (например, одно INT для fetch, другое для export)?
- **2.2 Периоды:** БТ упоминает час/день/неделю — это единственные поддерживаемые периоды или может быть произвольный диапазон дат?

### 3. **Владение и допущения о существующем**

Вопросы:
- **3.1 Источник активности:** Существует ли уже сервис / API / таблица, которая отдаёт текущее число активных сессий (или пользователей)? Подтвердите как аналитик:
  - Если ДА → какой сервис, какой эндпоинт (примерно), как часто обновляется?
  - Если НЕТ → нужно ли создавать новый механизм отслеживания активности?
- **3.2 Исторические данные:** Для графика активности за период (час/день/неделя) — нужны ли исторические агрегированные данные? Где они хранятся (БД, event-stream, другое)?
- **3.3 Экспорт:** Существует ли уже механизм генерации отчётов/файлов, или это с нуля?

### 4. **Контракты каждого взаимодействия**

Вопросы:
- **4.1 Формат ответа для счётчика (INT-1):** Предлагаю `{ "activeUsers": <int>, "timestamp": <ISO-8601> }`. Годится или добавить/изменить поля?
- **4.2 Структура графика (INT-2):** Предлагаю ответ типа:
  ```json
  {
    "period": "day",
    "data": [
      { "time": "2026-07-26T10:00:00Z", "count": 42 },
      ...
    ],
    "summary": { "min": 10, "max": 100, "avg": 55 }
  }
  ```
  Это подходит или нужна другая структура (например, почасовые/дневные бакеты)?
- **4.3 Формат выгрузки (INT-3):** Какой формат файла — CSV, JSON, XLSX или PDF-отчёт? Какие данные должны быть в сводке (график-данные + summary-статистика)?

### 5. **Ошибки и состояния UI**

Вопросы:
- **5.1 Недоступность источника:** Если источник активности недоступен — по БТ надо показать «—» на счётчике и пустой график. Но какой HTTP-код вернёт API? (503, 500, или особый? Предлагаю 503 Service Unavailable.)
- **5.2 Состояния UI для модали:** Основные состояния при загрузке графика:
  - `loading` → спиннер;
  - `value` → график с данными;
  - `empty` → «нет активности за период» или пустой график?
  - `error` → сообщение об ошибке + кнопка retry.
  Правильно ли я понимаю?

### 6. **Авторизация на границе**

Вопросы:

  - На уровне каждого endpoint'а?
  - Какой существующий сервис ролей/auth это делает?
- **6.2 Негативный случай:** Если Оператор попробует вызвать INT-3 (экспорт), какой ответ? (403 Forbidden с сообщением?)

### 7. **Данные и хранение**

Вопросы:
- **7.1 Новые сущности:** Нужно ли создавать новые таблицы/коллекции для хранения исторической активности? Или это уже есть?
- **7.2 Агрегация:** Как агрегируются данные активности? (примеры: почасовые snapshots, event-log с подсчётом, redis-счётчик?)
- **7.3 Retention:** Как долго хранить исторические данные активности? (неделя? месяц? год?)
- **7.4 Индексы:** Какие индексы нужны для быстрого запроса за период?

### 8. **Синхронность, кэш, производительность**

Вопросы:
- **8.1 Счётчик в шапке (INT-1):** Как часто должен обновляться счётчик?

- **8.2 Таймауты:** Какой максимальный таймаут для запроса графика за неделю? (Предлагаю 5 сек для cold-path, 2 сек для warm-path.)
- **8.3 Кэш:** Нужно ли кэшировать график-данные на FE или на BE? TTL?
- **8.4 Экспорт:** Если сводка большая (за долгий период), экспорт синхронный или асинхронный с ссылкой?

### 9. **Порядок выката и совместимость**

Вопросы:
- **9.1 Очередность:** FE зависит от новых BE endpoint'ов, поэтому BE должен выкатиться первым. Согласны?

- **9.3 Откат:** Если откатить BE, FE будет получать 404/5xx на INT-1,2,3 — спрячем счётчик и модалку или показываем ошибку?
