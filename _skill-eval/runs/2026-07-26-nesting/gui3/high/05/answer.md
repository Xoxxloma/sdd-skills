# Анализ фундамента эпика ARS-100

## Прочитанные БТ

**ARS-101 (Счётчик активных):**
- FR-1: Display current active user count in header
- FR-2: Auto-update counter without page reload
- Запрашивает: текущее число активных пользователей

**ARS-102 (Модалка с графиком):**
- FR-3: Modal with activity graph for selected period (hour/day/week)
- FR-4: Period switching on graph
- Запрашивает: агрегированная активность за период

**ARS-103 (Выгрузка сводки):**
- FR-5: Export button to download activity summary for period
- Запрашивает: агрегированная активность за период

## Найденный cross-sibling паттерн

**Фундамент #0 определён:** все три ребёнка (A, B, C) опираются на **ОДИН И ТОТ ЖЕ источник** — данные об активности пользователей.

Как сказано в разделе 3.3 обоих БТ:
> "Все три элемента опираются на одни и те же данные об активности пользователей (текущее число активных и агрегированная активность за период)."

**Что должен обслуживать #0:**
- Текущее число активных пользователей (для FR-1, FR-2 из ARS-101)
- Агрегированная активность с поддержкой периодов (для FR-3, FR-4 из ARS-102 и FR-5 из ARS-103)

Это единый **User Activity Data Service** — интерфейс доступа к данным активности, который:
- Возвращает текущее число активных пользователей
- Возвращает агрегированные данные активности за выбранный период (час, день, неделя)
- Наследуется всеми тремя детьми без изменения состава контракта

## Рекомендация

Разбил на 3 ребёнка: ARS-101, ARS-102, ARS-103. Вижу: все они опираются на один источник — данные об активности пользователей (текущее число активных и агрегированная активность за период). Оформить как общий тех-фундамент (узел #0) — спроектировать один раз, дети наследуют его контракт?

**Важно:** своего БТ у #0 не будет — это слой реализации.

Опции:
- **Спроектировать User Activity Data Service один раз (узел #0)** — спека #0 идёт первой, дети наследуют её контракт неизменным
- **Общего фундамента нет** — каждый ребёнок проектирует доступ к источнику сам
