# Анализ и рекомендация по фундаменту эпика ARS-100

Я прочитал все три детских БТ (ARS-101, ARS-102, ARS-103). Вот что вижу:

## Текущее состояние эпика ARS-100

- Детские БТ готовы к оценке (статус: Готово к оценке у всех трёх)
- Разрез уже сделан на 3 слайса: A (счётчик), B (модалка), C (выгрузка)
- Все БТ явно указывают общий источник данных (раздел 3.3 каждого БТ идентичен):

> "Все три элемента опираются на одни и те же данные об активности пользователей (текущее число активных и агрегированная активность за период). Админка «Арсенал» начинает потреблять эти данные."

## Cross-sibling источник найден

- A (FR-1, FR-2) → нужны: текущее число активных + данные для live-обновления
- B (FR-3, FR-4) → нужны: агрегированная активность за период + история за разные интервалы
- C (FR-5) → нужны: агрегированная активность за выбранный период (для выгрузки)

**Вывод:** Три ребёнка опираются на ОДИН источник — «User Activity Data» (число активных + агрегированная активность за период).

## Что дальше по фундаменту?

По правилам, этот случай требует оформления **техфундамента #0** — единая точка доступа к данным об активности, которую все три ребёнка унаследуют без изменения контракта.

**Вопрос перед рекомендацией:**

Как ты видишь источник этих данных? Это:
1. **Существующий API/сервис** в системе, который просто потребляет админка?
2. **Новый сервис**, который нужно спроектировать специально для этого эпика?
3. **Другое** — расскажи, как видишь архитектуру?

Это важно, чтобы понять, оформляем ли мы #0 как интеграционный узел (подключение к существующему) или как новый сервис данных.
