# Анализ фундамента для эпика ARS-100

## Картина состояния

Эпик `ARS-100` разбит на три независимых слайса с детскими БТ:
- **ARS-101** (Счётчик активных) — FR-1, FR-2
- **ARS-102** (Модалка с графиком) — FR-3, FR-4
- **ARS-103** (Выгрузка сводки) — FR-5

Статус детей: все три готовы к оценке, открытых вопросов нет.

## Выявленная кросс-сиблинг зависимость

Прочитал детские БТ. **Вижу явный признак общего фундамента:**

Все три элемента опираются на **один и тот же источник данных** об активности пользователей:
- ARS-101 запрашивает: текущее число активных пользователей (для счётчика)
- ARS-102 запрашивает: агрегированная активность за период (для графика)
- ARS-103 запрашивает: агрегированная активность за период (для выгрузки)

Это видно из раздела 3.3 каждого детского БТ: **«Все три элемента опираются на одни и те же данные об активности пользователей»**.

## Рекомендация

Оформить **общий тех-фундамент (узел #0)** для этого источника данных об активности:
- Узел #0 спроектирует один раз контракт сервиса (какие поля возвращает, типы, семантика null/ошибок)
- Все три ребёнка унаследуют его контракт без изменения состава — те же поля, типы, enum'ы и семантика null

**Важно:** фундамента #0 не будет своих бизнес-требований — это слой реализации, а не бизнес-фича. БТ остаются только у детей.

## Следующий шаг

Согласны ли оформить сервис активности пользователей как узел-фундамент #0?
- **Да, проектировать #0** — спека #0 идёт первой, потом все три ребёнка наследуют её контракт
- **Нет, каждый ребёнок сам** — каждый спроектирует доступ к данным независимо (риск рассинхрона контрактов)
