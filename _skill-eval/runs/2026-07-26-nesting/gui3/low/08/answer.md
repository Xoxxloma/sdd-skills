# Анализ фундамента эпика ARS-100

Прочитал все три детских БТ. Вот что дальше по фундаменту.

## Cross-sibling анализ

Три ребёнка эпика:
- **ARS-101** (Счётчик активных): FR-1, FR-2 — отображает текущее число активных, обновляется без перезагрузки
- **ARS-102** (Модалка с графиком): FR-3, FR-4 — модальное окно с графиком активности за период (час/день/неделя)
- **ARS-103** (Выгрузка сводки): FR-5 — кнопка выгрузки сводки активности

**Ключевой признак (Section 3.3 — одинаков во всех трёх):**

> "Все три элемента опираются на одни и те же данные об активности пользователей (текущее число активных и агрегированная активность за период)."

## Вывод: есть общий фундамент #0

ВСЕ ТРИ ребёнка опираются на ОДИН источник — сервис данных активности пользователей. Этот сервис должен предоставлять:
1. **Текущее число активных пользователей** (для ARS-101: FR-1, FR-2)
2. **Агрегированная активность за период** (для ARS-102: FR-3, FR-4 и ARS-103: FR-5)

Это классический case для **foundation #0**: единый контракт данных, который все трое потребляют и наследуют без изменения состава полей, типов и семантики.

## Рекомендация

Спроектировать узел-фундамент #0 — "Сервис данных активности пользователей" (User Activity Data Service). Черновая форма контракта будет содержать:

```
{
  "current_active_users": <number>,
  "activity_metrics": {
    "timestamp": <ISO8601>,
    "period": <"hour"|"day"|"week">,
    "data_points": [
      { "timestamp": <ISO8601>, "active_count": <number> }
    ],
    "summary": {
      "min": <number>,
      "max": <number>,
      "avg": <number>
    }
  }
}
```

- `current_active_users` — требуется ARS-101 (FR-1, FR-2)
- `activity_metrics` — требуется ARS-102 (FR-3, FR-4) и ARS-103 (FR-5)

**Важно:** узел #0 не имеет собственного БТ — это слой реализации, не бизнес-требование. Вся бизнес-логика (показать счётчик, нарисовать график, выгрузить сводку) остаётся в детских БТ и спеках; #0 отвечает только за унифицированный контракт источника данных.

## Следующий шаг

Согласны ли вы оформить сервис активности как общий тех-фундамент (узел #0)?

**Вариант A:** Спроектировать сервис активности как узел #0 — спека #0 идёт первой, дети наследуют её контракт неизменным, риск расхождений минимален.

**Вариант B:** Общего фундамента нет — каждый ребёнок проектирует свой способ получения данных, контракты рискуют разъехаться.
