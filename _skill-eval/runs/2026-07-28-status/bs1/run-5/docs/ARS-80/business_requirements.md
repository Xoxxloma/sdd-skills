# Бизнес-требования: Наблюдение активности пользователей в админке «Арсенал»

> **Статус готовности:** Требуются уточнения

> **Открытые вопросы (требуют уточнения перед оценкой):**

## 1. Введение и контекст

### 1.0. Тип изменения
Доработка существующего — в веб-админку «Арсенал» добавляются элементы для наблюдения за активностью пользователей.

### 1.1. Описание проблемы (Problem Statement)
Администраторы системы не видят ни текущую, ни историческую активность пользователей. Невозможно быстро оценить нагрузку на систему, посмотреть динамику за период и подготовить сводку для отчётности. Регламентные работы планируются вслепую, без понимания нагрузки.

### 1.2. Конечные потребители (End Users)
Администраторы системы «Арсенал» (внутренние сотрудники отдела эксплуатации).

### 1.3. Заказчик и стейкхолдеры (Stakeholder / Sponsor)
**Заказчик:** руководитель отдела эксплуатации.  
**Эксперт для консультации:** тимлид команды «Арсенал-Core».

## 2. Бизнес-требования (цели и ценность)

### 2.1. Бизнес-цель
Я как администратор должен иметь возможность видеть активность пользователей — сейчас, в динамике и в виде выгружаемой сводки, — чтобы планировать безопасные окна для регламентных работ и отчитываться по нагрузке.

### 2.2. Ценность для бизнеса
- Меньше прерванных пользовательских сессий во время регламентных работ (улучшение стабильности);
- Прозрачная отчётность по нагрузке для аудита и планирования (улучшение управления).

### 2.3. Бизнес-риски и меры по снижению (Mitigation)

| Риск | Вероятность / влияние | Меры по снижению |
|------|-----------------------|------------------|
| Неточные данные активности вводят в заблуждение при планировании работ | Среднее / высокое | При недоступности источника данных показываем пусто или прочерк («—»), не устаревшее значение; значение обновляется в пределах минуты. |
| Выгрузка доступна не авторизованным лицам | Среднее / высокое | Панель активности и выгрузка доступны только администраторам; оператору элементы не отображаются. |

## 3. Объём проекта (Scope)

### 3.1. Входит в проект (In-scope)
- Счётчик числа активных пользователей в шапке админки;
- Автоматическое обновление счётчика без перезагрузки страницы;
- Модальное окно с графиком активности за выбранный период (с возможностью выбора периода: час, день, неделя);
- Переключение периода в пределах модального окна (перестроение графика);
- Выгрузка сводки активности за выбранный период в файл.

### 3.2. Не входит в проект (Out-of-scope)
- Список конкретных пользователей, находящихся онлайн (только агрегированные числа);
- Автоматическая рассылка отчётов по активности;
- Прогнозирование будущей активности.

### 3.3. Архитектурные изменения и интеграции
Все три элемента доработки (счётчик, график, выгрузка) опираются на один и тот же источник данных об активности пользователей. Админка «Арсенал» начинает потреблять агрегированные данные о текущем числе активных пользователей и активности за период. Точные механизмы получения, хранения и обновления этих данных определяются на этапе технической спецификации.

## 4. Функциональные требования

### 4.1. Описание функционала / бизнес-процесса

**FR-1:** Администратор видит в шапке админки счётчик числа активных пользователей.

**FR-2:** Счётчик обновляется автоматически, без перезагрузки страницы, в пределах минуты после изменения активности.

**FR-3:** По клику на счётчик открывается модальное окно с графиком активности за выбранный период.

**FR-4:** В модальном окне администратор может переключать период наблюдения (час, день, неделя); при смене периода график перестраивается.

**FR-5:** В модальном окне присутствует кнопка выгрузки сводки активности за выбранный период в файл.

**FR-6:** Счётчик виден сразу после загрузки страницы админки.

**FR-7:** Оператору панель активности и выгрузка не отображаются (видны только администраторам).

### 4.2. Критерии приёмки (Acceptance Criteria)

- **[FR-1, FR-6]** Дано: пользователь-администратор открыл админку; когда: страница загрузилась; тогда: в шапке видна область со счётчиком активных пользователей.

- **[FR-2]** Дано: счётчик отображается; когда: активность пользователей изменилась; тогда: счётчик обновляется в пределах одной минуты, страница не перезагружается.

- **[FR-3]** Дано: счётчик отображается; когда: администратор кликает на счётчик; тогда: открывается модальное окно с графиком активности за период по умолчанию (неделя или день, как определено на этапе тех-спеки).

- **[FR-4]** Дано: модальное окно открыто с графиком; когда: администратор выбирает другой период; тогда: график перестраивается для выбранного периода.

- **[FR-5]** Дано: модальное окно открыто; когда: администратор нажимает кнопку выгрузки; тогда: скачивается файл со сводкой активности за выбранный период.

- **[FR-7]** Дано: в систему входит оператор (не администратор); когда: он открывает админку; тогда: счётчик активности и панель не отображаются.

## 4.5. Разбиение на слайсы

**Анализ по пунктам (перед таблицей):**

1. **Числа:** в §4.1 семь FR (FR-1…7), три из них — ядро доработки (счётчик, график, выгрузка), остальные — условия использования или ограничения доступа. По числу обособленных деливерблов: счётчик + график в одном окне — это единый интерфейс; выгрузка — отдельное действие, но внутри того же окна.

2. **Ценность каждого кандидата:**
   - **Счётчик и график** — администратор видит текущую и историческую активность, может оценить нагрузку за период и планировать работы. Это одна ценность, одна фича (просмотр активности).
   - **Выгрузка сводки** — администратор может подготовить данные для отчёта и отправить заказчику. Это отдельная ценность (экспорт данных).
   - **Контроль доступа (FR-7)** — не отдельный деливербл, это требование безопасности, пронизывающее обе фичи.

3. **Порог:** 2 обособленных деливербла (просмотр + выгрузка) × 2+ FR в каждом = эпик.

4. **Исход: РЕЖЕМ.**
