## 1. Обзор изменения
### 1.1. Тип и стороны
Fullstack. В шапку веб-админки «Арсенал» добавляется индикатор числа активных пользователей онлайн. Фронт админки получает данные с бэка Арсенала; бэк Арсенала кэширует и агрегирует число активных сессий из сервиса аутентификации.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Админка «Арсенал» (фронт) | Новый UI-элемент в шапке | Команда Арсенал-Core | 🟢 |
| Админка «Арсенал» (бэк) | Новый эндпоинт для получения счётчика | Команда Арсенал-Core | 🟢 |
| Сервис аутентификации | Существующее хранилище: число активных сессий | [владелец сервиса] | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями
Реализует бизнес-цель FR-1/FR-2/FR-3: администратору доступно в реальном времени число активных пользователей, чтобы безопасно планировать регламентные работы. Снижает риск разрыва сессий.

## 2. Взаимодействия (ядро)

### INT-1. Получить число активных пользователей (фронт → бэк Арсенала) — 🟢

- **Граница/направление:** FE Арсенала → BE Арсенала
- **Триггер:** (1) Загрузка страницы админки; (2) периодический пулл каждые 60 секунд
- **Контракт (запрос):** `GET /api/admin/active-users/count`; тело отсутствует
- **Контракт (ответ):**
  - `count` (int | null): число активных пользователей. `null` означает, что источник недоступен (см. семантику null ниже).
  - Семантика null: `null` — источник данных (сервис аутентификации) недоступен либо запрос к нему завершился ошибкой; UI интерпретирует как «показать "—"».

- **Пример запроса:** Параметры/заголовки отсутствуют.
  ```
  GET /api/admin/active-users/count
  ```

- **Пример ответа (успех — данные доступны):**
  ```json
  {
    "count": 42
  }
  ```

- **Пример ответа (успех — источник недоступен):**
  ```json
  {
    "count": null
  }
  ```

- **Ошибки:** Сервис всегда возвращает HTTP 200 с телом `{ "count": <число или null> }`. Сценарии недоступности источника обрабатываются как `count: null` (не выбрасывают исключение). Если сам эндпоинт Арсенала недоступен (5xx, таймаут), фронт обрабатывает это как сетевую ошибку и показывает UI-состояние «ошибка» (см. §4).

- **Состояния UI по ответу:**
  - `count: <число ≥ 0>` → показать число в виде текста/бейджа в шапке (напр. «Онлайн: 42»).
  - `count: null` → показать «—» (прочерк).
  - Загрузка (запрос в полёте) → обычный спиннер или скелетон в месте индикатора.
  - Сетевая ошибка (таймаут, 5xx) → показать UI-состояние «ошибка» (по аналогии с null: «—»).

- **Авторизация:** Эндпоинт доступен всем аутентифицированным пользователям (независимо от роли); однако индикатор в UI отображается **только** для пользователей с ролью «Администратор» — проверка ролей осуществляется на фронте при рендеринге компонента.

- **Происхождение:** 🟢 новое

- **Трассировка:** FR-1, FR-2, FR-3

### INT-2. Получить число активных сессий (бэк Арсенала → сервис аутентификации) — 🟡

- **Граница/направление:** BE Арсенала → BE сервиса аутентификации
- **Триггер:** Запрос фронта Арсенала к INT-1; бэк запрашивает число активных сессий из кэша или сервиса аутентификации.
- **Контракт (запрос):** 🟡 к валидации — точный путь, метод и параметры неизвестны. Предполагается `GET /sessions/active/count` или аналогичный эндпоинт сервиса аутентификации.
- **Контракт (ответ):** 🟡 к валидации — ожидается число активных сессий. Формат (JSON-поле, XML и т.п.) требует подтверждения.
- **Пример запроса:** 🟡 к валидации — структура неподтверждена.
- **Пример ответа:** 🟡 к валидации — точный формат и структура требуют уточнения.
- **Ошибки:** При недоступности эндпоинта аутентификации (таймаут, ошибка подключения) бэк Арсенала возвращает в INT-1 `count: null` и логирует ошибку.
- **Состояния UI по ответу:** не применимо (это внутренний контракт BE).
- **Авторизация:** 🟡 подтверждено аналитиком (не по коду) — сервис аутентификации уже умеет считать активные сессии и отдавать это значение; авторизация/квота-лимиты на этом эндпоинте требуют уточнения у владельца сервиса при интеграции.
- **Происхождение:** 🟡 подтверждено аналитиком, контракт 🟡 к валидации
- **Трассировка:** FR-1, FR-2, FR-3

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 | `{ "count": <число> }` | INT-1 успешно получена, источник доступен | Число отображается |
| 200 | `{ "count": null }` | INT-1 успешно вызвана, но источник (сервис аутентификации) недоступен | Показать «—» |
| 5xx, таймаут (INT-1) | сообщение об ошибке | BE Арсенала недоступен | Показать «—» (обрабатывается как ошибка) |
| 5xx, таймаут (INT-2) | — | BE сервиса аутентификации недоступен | В INT-1 вернёт `count: null` |

## 2.5. Этапы работ и порядок сборки

**Анализ:** Задача чисто интеграционная — фронт выводит счётчик, бэк запрашивает и кэширует данные из существующего сервиса. Единственная новая работа — INT-1 (эндпоинт Арсенала) и кэширование в бэке. Фронт и бэк работают на едином контракте (INT-1); разрез по «фронт / бэк» не даёт двух независимых этапов, это две стороны одного куска. Этапов разрезать нечего.

**Вывод:** не применимо — одна сквозная работа (новый эндпоинт + UI-компонент).

## 3. Данные и хранение

Не применимо: новых сущностей, таблиц и миграций схемы не требуется. Число активных сессий уже хранится и поддерживается сервисом аутентификации; бэк Арсенала только читает и кэширует это значение.

## 4. Состояния фронта (детально)

### 4.1. Компонент индикатора в шапке

**Видимость:**
- Видно для пользователя с ролью «Администратор»; скрыто для «Оператора» и прочих ролей.

**Возможные состояния:**
1. **Загрузка (Loading):** компонент видно, но вместо числа отображается спиннер или скелетон (во время первого запроса при загрузке страницы).
2. **Значение (Value):** число (напр. «42»), отформатированное кратко (не показываем нули слева). Иконка/лейбл на усмотрение дизайна (напр. «👥 42» или просто «42 онлайн»).
3. **Прочерк (Empty):** «—» (одиночный прочерк) при `count: null`, что означает недоступность источника.
4. **Ошибка (Error):** При сетевой ошибке (5xx, таймаут) показывается «—» (не отличается от Empty визуально; логирование ошибки — на стороне фронта).

**Переходы между состояниями:**
- Page load → Loading → (INT-1 response) → Value | Procherk.
- Poll timer fires (каждые 60 сек) → Loading → Value | Procherk.
- Network error during poll → показать «—», остаться в режиме Loading (спиннер остаётся; не выбрасывать ошибку в общий UI).

### 4.2. UX-пожелание (из БТ)
Индикатор неяркий, не отвлекает от основной работы. Рекомендация: нейтральный цвет (серый или приглушённый), размер меньше основных элементов.

## 5. Нефункциональные требования

### 5.1. Синхронность и производительность
- **Пулл (polling):** Фронт запрашивает INT-1 один раз при загрузке страницы, затем каждые 60 секунд.
- **Кэш на бэке:** BE Арсенала кэширует результат запроса к INT-2 (сервис аутентификации) на 30 секунд. Все запросы фронта в пределах 30 сек получают закэшированное значение; по истечении TTL кэш инвалидируется и бэк запрашивает свежее значение.
- **Ожидаемая нагрузка:** Один запрос INT-1 в минуту на администратора; допустимое число одновременно ответивших запросов — в пределах штатной нагрузки на Арсенал (уточнение нагрузки при интеграции).
- **Таймаут:** Рекомендуется таймаут на INT-2 не более 2 сек; если бэк Арсенала не получит ответ за это время, вернуть INT-1 с `count: null`.

### 5.2. Авторизация и безопасность
- **AUTHZ на INT-1:** Проверка должна полагаться на сессию (предполагается, что все запросы из админки авторизованы). Ролевая проверка — на уровне фронта (не показывать компонент для неуполномоченных).
- **AUTHZ на INT-2:** 🟡 подтверждено аналитиком (не по коду) — сервис аутентификации предоставляет этот эндпоинт; вопрос квоты/лимитов при интеграции требует уточнения.

### 5.3. Мониторинг и логирование
- Логировать ошибки INT-2 (недоступность сервиса аутентификации) на уровне бэка Арсенала.
- Фронт может логировать ошибки сети при INT-1.

## 6. Порядок выката и совместимость

### 6.1. Последовательность деплоя
1. **BE Арсенала:** развернуть эндпоинт INT-1 + логика кэширования INT-2 **перед** фронтом.
2. **Настройка ролей:** убедиться, что роль «Администратор» уже присутствует в системе и у тестовых администраторов она назначена; это преднастройка, выполняется до или одновременно с деплоем BE.
3. **FE Арсенала:** развернуть компонент индикатора; фронт будет вызывать INT-1 немедленно (бэк уже готов).

### 6.2. Обратная совместимость
- Старые версии фронта (без компонента индикатора) продолжат работать.
- Новый эндпоинт BE не конфликтует с существующими API.

### 6.3. Откат
Откат фронта — удалить компонент из шапки. Откат бэка — удалить эндпоинт INT-1 (кэширование INT-2 не воздействует на остальную систему). Независимые откаты.
