## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. В веб-админку «Арсенал» добавляется новый элемент UI в шапку. На фронте появляется компонент отображения счётчика; на бэке — эндпоинт для получения текущего числа активных пользователей. Оба связаны новым контрактом.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Админка «Арсенал» (фронт) | Новый компонент счётчика в шапке, периодический опрос бэка | команда Арсенал-Core | 🟢 новое |
| Админка «Арсенал» (бэк) | Новый эндпоинт для счёта активных пользователей, опрос auth-сервиса, кэширование | команда Арсенал-Core | 🟢 новое |
| Сервис аутентификации | Существующее: источник актуального числа активных сессий | владелец auth-сервиса | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями
Решает FR-1, FR-2, FR-3 из БТ: администратор видит в шапке число активных пользователей, которое обновляется автоматически без перезагрузки, и при недоступности источника видит «—» вместо ошибки.

## 2. Взаимодействия (ядро)

### INT-1. Получить число активных пользователей (FE Арсенала → BE Арсенала) — 🟢

- **Граница/направление:** Frontend (компонент шапки) → Backend админки
- **Триггер:** 
  - Инициализация: при загрузке страницы админки.
  - Периодический: автоматический опрос каждые 60 секунд (пуллинг).
- **Контракт (запрос):** 
  - Метод: GET
  - Путь: `/api/v1/admin/online-users-count` (или аналогичный, не стеко-специфично)
  - Параметры: нет
  - Тело: отсутствует
- **Контракт (ответ):** 
  - `count` (обязательное, число или null): текущее число активных пользователей. `null` — источник недоступен, UI должен показать «—».
  - Типы: `count: number | null`
  - Семантика null: `null` означает, что число активных пользователей неизвестно (auth-сервис недоступен, ошибка при запросе и т.п.); UI интерпретирует как состояние "unavailable" и показывает «—» вместо числа.
- **Пример запроса:** 
  ```
  GET /api/v1/admin/online-users-count
  Без параметров, без тела.
  ```
- **Пример ответа (успех):**
  ```json
  {
    "count": 42
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null
  }
  ```
- **Ошибки:** 
  - Если auth-сервис недоступен или возвращает ошибку: BE Арсенала возвращает `200 OK { "count": null }` (не ошибка HTTP; недоступность кодируется через null в ответе, на уровне приложения).
  - Если запрос к BE Арсенала упал (500, timeout, сетевая ошибка): FE показывает кэшированное значение из памяти (если есть) или перейти в состояние "loading" с ожиданием следующего пуллинга.
- **Состояния UI по ответу (если есть фронт):**
  - Значение (count > 0): показать число в компоненте счётчика (например, "Онлайн: 42").
  - Значение (count === 0): показать число (например, "Онлайн: 0").
  - Null (源недоступна): показать «—» (тире, отсутствие числа) вместо числа.
  - Загрузка (запрос отправлен, ответ не пришёл): показать спиннер или иной индикатор загрузки рядом с компонентом счётчика (если компонент первый раз загружается; при периодических обновлениях спиннер не показывается — обновление фоновое).
  - Ошибка BE Арсенала (5xx, timeout): показать последнее успешно полученное значение (если есть в памяти) или «—». Уведомление об ошибке в UI не выводится (ошибка не критична для основного функционала).
- **Авторизация:** 
  - Доступ: только пользователи с ролью «Администратор».
  - Проверка: на BE Арсенала; отклонить запросы от операторов и других ролей.
  - Негативный случай: если оператор попытается запросить эндпоинт, BE вернёт `403 Forbidden` или аналогичный код (зависит от имплементации; нужно валидировать); FE должен изначально не отправлять запрос, если текущий пользователь — не администратор.
- **Происхождение:** 🟢 новое (спроектировано в этом документе)
- **Трассировка:** FR-1 (показать число в шапке); FR-2 (обновлять автоматически); FR-3 (показать «—» при недоступности)

### INT-2. Получить число активных сессий (BE Арсенала → сервис аутентификации) — 🟡 к валидации

- **Граница/направление:** Backend админки → Сервис аутентификации
- **Триггер:** BE Арсенала получил запрос INT-1 (от фронта); проверяет кэш; кэш пуст или устарел → выполняет межсервисный запрос к auth-сервису.
- **Контракт (запрос):** 
  - Метод: 🟡 к валидации (скорее всего GET, но точный метод и путь надо уточнить с владельцем auth-сервиса или читать документацию сервиса).
  - Путь: 🟡 к валидации (не выдумываю конкретный endpoint; оставляю для интеграции).
  - Параметры: 🟡 к валидации.
  - Тело: 🟡 к валидации.
- **Контракт (ответ):** 
  - 🟡 к валидации: ожидается, что auth-сервис вернёт число активных сессий (скорее всего поле типа `activeSessionsCount` или `sessionCount`, но структуру точного ответа надо уточнить).
  - Семантика null / значение по умолчанию: 🟡 к валидации.
- **Пример запроса:** 🟡 к валидации
- **Пример ответа (успех):** 🟡 к валидации (структура и формат неизвестны)
- **Ошибки:** 
  - Если auth-сервис недоступен (connection refused, timeout, 500 и т.д.): BE Арсенала ловит исключение/ошибку и возвращает фронту `{ "count": null }` (недоступность кодируется как null для фронта, чтобы UI показал «—»).
  - Если auth-сервис возвращает ошибку (4xx, 5xx): BE также преобразует в `{ "count": null }` для фронта.
- **Авторизация:** 
  - 🟡 подтверждено аналитиком: auth-сервис уже умеет считать активные сессии, допуск к эндпоинту должен быть в порядке.
  - Точный механизм auth между Арсеналом и auth-сервисом (API-ключ, mTLS, JWT и т.п.): 🟡 к валидации.
- **Происхождение:** 🟡 подтверждено аналитиком (не по коду): auth-сервис умеет считать активные сессии; точный контракт к валидации.
- **Трассировка:** Поддерживает INT-1.

## 2.5. Этапы работ и порядок сборки

**Анализ:** Из §2 видна одна сквозная работа со своей логикой: получить число активных пользователей из auth-сервиса, кэшировать результат в бэке, отдать фронту, фронт периодически опрашивает с обработкой ошибок и отображением состояний.

**Контракт FE↔BE** (INT-1) — это граница между двумя реализациями (фронт пишет компонент + логику опроса; бэк пишет эндпоинт + логику кэша + запрос к auth), но это не два этапа работы: это две стороны одного шва. Оба реализуют одну функцию: «показать число активных пользователей в шапке».

Вывод: **одна работа, в разделе нет отдельных этапов.**

**Не применимо:** разработка ведётся параллельно по фронт и бэк, но это две стороны одного контракта, а не два независимых этапа. Швы зафиксированы в INT-1 и INT-2 (запрос к auth-сервису — внутренний, деталь бэка). Выкат: бэк Арсенала раньше фронта (требование из §6).

## 3. Данные и хранение

### 3.1. Новые/изменённые сущности и поля
🟢 Новое: счётчик активных пользователей — это вычисляемое значение, не сущность (берётся из auth-сервиса, не сохраняется в БД Арсенала).

Новых таблиц, полей или миграций схемы в Арсенале не требуется. Данные читаются из auth-сервиса в реальном времени.

### 3.2. Хранение и кэширование
🟢 Кэш на BE Арсенала:
- **Уровень:** кэш в памяти процесса бэка (или встроенная кэш-библиотека типа Redis, если используется; подробности имплементации — зависят от стека Арсенала, концептуально это in-process или distributed cache).
- **Ключ:** фиксированный ключ (например, `active_users_count`), один экземпляр кэша на бэк.
- **Значение:** число (int) или null.
- **TTL (время жизни):** 30 секунд. По истечении TTL кэш инвалидируется; следующий запрос фронта → BE запрашивает auth-сервис заново.
- **Механика:** 
  1. Фронт отправляет GET INT-1 → BE проверяет кэш.
  2. Если кэш есть и не устарел → BE возвращает `{ "count": <cached_value> }`.
  3. Если кэш пуст или истёк → BE запрашивает auth-сервис (INT-2), получает число, записывает в кэш с TTL 30 сек, возвращает фронту.
  4. Если auth-сервис ошибается → BE возвращает `{ "count": null }` (кэш не обновляется на ошибке).

### 3.3. Миграции
Не требуются. 🟢 Новое взаимодействие не требует изменения схемы.

## 4. Frontend: состояния и поведение

### 4.1. Компонент счётчика в шапке

🟢 Новый компонент UI, который отображается только администраторам.

**Размещение:** в шапке (header) админки, рядом с прочей информацией пользователя (например, иконка пользователя, выход).

**Видимость:** 
- Показывается, если текущий пользователь имеет роль «Администратор» 🟡 подтверждено аналитиком.
- Не показывается операторам и прочим ролям.

**UX-пожелание:** 🟡 подтверждено аналитиком: индикатор неяркий, не отвлекает от основной работы. Цвет и стиль — уточнить с дизайнером Арсенала (не является блокирующим); рекомендуется нейтральный или серый оттенок, небольшой размер шрифта.

**Макет (концептуально):**
```
[Иконка пользователя] [Имя] [Онлайн: 42] [Выход]
```
или
```
[Иконка пользователя] [Имя] [Онлайн: —] [Выход]
```

### 4.2. Логика опроса и состояния

🟢 Спроектировано:

| Состояние | Триггер | Отображение | Поведение |
|---|---|---|---|
| **Инициализация** | Страница админки загрузилась | Спиннер или краткий индикатор загрузки | FE отправляет GET INT-1; ожидает ответ |
| **Значение получено** (count ≥ 0) | BE вернул `{ "count": N }` | Число в компоненте: "Онлайн: N" | Компонент отображается стабильно; запускается таймер для следующего опроса через 60 сек |
| **Null (недоступно)** | BE вернул `{ "count": null }` | Тире: "Онлайн: —" | Компонент отображается; таймер на следующий опрос через 60 сек |
| **Загрузка (периодическая)** | 60 секунд прошли; таймер сработал | Текущее значение (N или —) остаётся; нет видимого спиннера | FE отправляет GET INT-1 в фоне; затем обновляет компонент новым значением |
| **Ошибка BE** (5xx, timeout) | BE не ответил или вернул ошибку HTTP | Последнее известное значение или «—» | Компонент не обновляется; логируется ошибка; повтор по расписанию пуллинга (следующие 60 сек) |

### 4.3. Обработка ошибок в FE

🟢:
- **Если первый запрос при загрузке упал:** показать «—» и продолжить пуллинг. Сообщение об ошибке пользователю не выводить (не критично).
- **Если периодический запрос упал:** сохранить последнее успешное значение в памяти; повторить запрос по расписанию (следующие 60 сек).
- **Timeout запроса:** 🟡 к валидации (рекомендуется 5–10 сек в зависимости от SLA бэка).
- **Очищение памяти при навигации:** кэш опроса в памяти FE очищается либо при закрытии вкладки админки, либо остаётся (если администратор открывает другой экран админки, опрос продолжается).

## 5. Нефункциональные требования и операционные вопросы

### 5.1. Синхронность и производительность

🟢:
- **Характер взаимодействия INT-1 (FE↔BE):** синхронный HTTP GET с таймаутом.
- **Характер взаимодействия INT-2 (BE↔Auth):** синхронный (вероятнее всего HTTP; точный механизм 🟡 к валидации); в случае timeout/ошибки BE пробрасывает null фронту, не тормозя основной запрос.
- **Частота опроса:** каждые 60 секунд (2 запроса в минуту с учётом наложений маловероятны).
- **Кэширование:** на BE — 30 сек (сокращает нагрузку на auth-сервис).
- **Ожидаемая нагрузка:** низкая. Каждый администратор (их мало, <<100) отправляет один запрос в минуту → auth-сервис получает <<100 req/min от Арсенала. Кэш на 30 сек → реальных запросов к auth-сервису ещё меньше (примерно 2 в минуту per BE instance, если есть несколько инстансов).

### 5.2. Надёжность и отказоустойчивость

🟡 подтверждено аналитиком / 🟢 спроектировано:
- **Недоступность auth-сервиса:** BE возвращает фронту `{ "count": null }` → UI показывает «—». Бизнес-риск «неточный счётчик вводит в заблуждение» (из БТ) миtigated: вместо ошибки показывается явный индикатор неизвестного значения.
- **Недоступность BE Арсенала:** фронт показывает последнее известное значение или «—» и повторяет запрос по расписанию.
- **Сетевые задержки / таймауты:** 🟡 к валидации (timeout стратегия уточнить; рекомендуется fail-fast, чтобы не задерживать загрузку страницы).

### 5.3. Безопасность и авторизация

🟢 спроектировано:
- **Аутентификация:** фронт отправляет запрос в контексте сессии администратора (cookie/header с токеном); BE Арсенала его уже проверил на уровне админки.
- **Авторизация:** BE Арсенала проверяет, что текущий пользователь имеет роль «Администратор»; отклоняет запросы от других ролей (403 Forbidden).
- **Логирование:** 🟡 к валидации (опционально: логировать запросы доступа операторов к эндпоинту в целях аудита).

## 6. Порядок выката и совместимость

### 6.1. Порядок деплоя

🟡 подтверждено аналитиком:
1. **Этап 1: Backend Арсенала.** Выкатить новый эндпоинт GET /api/v1/admin/online-users-count. На этом этапе фронт не вызывает его, поэтому выкат безопасен (эндпоинт «висит» неиспользованным).
2. **Этап 2: Frontend Арсенала.** Выкатить компонент счётчика и логику опроса. После этого фронт начинает вызывать BE; оба работают вместе.

**Причина:** если выкатить фронт раньше бэка, пользователи увидят спиннер/неопределённость до выката бэка. Выкат бэка первым избегает этого.

### 6.2. Обратная совместимость

🟢:
- Новый эндпоинт не трогает существующие. Старые клиенты (если есть) не будут его вызывать.
- На BE Арсенала: добавляется новый эндпоинт, существующая логика не изменяется.
- На фронте: добавляется новый компонент в шапке, остальной UI не меняется.

### 7.2. Список тест-кейсов (свободной формы)

🟢 спроектировано:
- **TC-1 (Happy path).** Администратор открывает админку → компонент счётчика загружается и показывает актуальное число из auth-сервиса.
- **TC-2 (Периодическое обновление).** Счётчик обновляется каждые ~60 сек без перезагрузки страницы; обновление видно в UI.
- **TC-3 (Недоступность источника).** Auth-сервис недоступен → счётчик показывает «—» вместо ошибки.
- **TC-4 (Ошибка BE Арсенала).** BE Арсенала вернул 500 → FE показывает последнее известное значение или «—»; не падает.
- **TC-5 (Авторизация).** Оператор (не администратор) открывает админку → счётчик не показывается (не видим в UI). Если оператор попытается запросить API напрямую → 403 Forbidden.
- **TC-6 (Кэширование).** BE Арсенала получает три запроса фронта в течение 30 сек → проверяет, что auth-сервис был опрошен только один раз (кэш сработал для остальных двух).
- **TC-7 (Граничные значения).** count=0, count=1, count=999999 → компонент корректно отображает.
- **TC-8 (Очистка и переход).** Администратор переходит на другой экран админки → опрос продолжается (если компонент в шапке на всех страницах) или останавливается (если компонент локален на конкретной странице) — уточнить поведение.
