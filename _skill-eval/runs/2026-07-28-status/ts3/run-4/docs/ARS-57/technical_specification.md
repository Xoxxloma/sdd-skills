## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. В шапку веб-админки «Арсенал» добавляется новый элемент UI (фронт), который опрашивает BE Арсенала (бэк), а BE в свою очередь вызывает сервис аутентификации для получения актуального числа активных пользователей.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Админка «Арсенал» (фронт) | новый UI-элемент в шапке | Арсенал-Core | 🟢 |
| Админка «Арсенал» (бэк) | новый эндпоинт, агрегация, кэширование | Арсенал-Core | 🟢 |
| Сервис аутентификации | существующий источник счёта активных сессий | Auth-Team | 🟡 подтверждено аналитиком (не по коду) |

### 1.3. Связь с бизнес-требованиями
Спецификация реализует FR-1, FR-2, FR-3: администраторы видят число активных пользователей в шапке, значение обновляется без перезагрузки, при недоступности источника показывается «—» вместо ошибки.

## 2. Взаимодействия (ядро)

### INT-1. Запрос числа активных пользователей — FE → BE Арсенала — 🟢

- **Граница/направление:** Фронт Арсенала → Бэк Арсенала (HTTP, REST).
- **Триггер:** Загрузка страницы админки + периодический опрос каждые 60 секунд (пуллинг).
- **Контракт (запрос):** `GET /api/arsenal/users/active-count`; параметров/тела нет.
- **Контракт (ответ):** 
  - `count` — число активных пользователей (целое число, может быть `null`);
  - семантика: `null` означает, что источник недоступен / данные устарели, на фронте показать «—».
- **Пример запроса:** 
  ```
  GET /api/arsenal/users/active-count
  ```
- **Пример ответа (успех):**
  ```json
  { "count": 23 }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  { "count": null }
  ```
- **Ошибки:** 
  - `200` с `count: null` — источник недоступен (не HTTP-ошибка, а валидный ответ).
  - `500` — внутренняя ошибка сервера (редко, обработать как «—» на фронте).
- **Состояния UI по ответу:**
  - **значение → число** — `count` > 0: показать число как есть (напр. «23»).
  - **загрузка → спиннер** — запрос в пути: маленький спиннер рядом с числом (ранее было число или «—», теперь подменяется спиннер).
  - **пусто / недоступно → «—»** — `count: null` или HTTP 5xx: показать тире, не показывать ошибку.
  - **ошибка (редко)** — если HTTP 5xx и нет fallback'а: логировать, показать «—» (не красный крест).
- **Авторизация:** Доступен только пользователям с ролью «Администратор». Проверяется на уровне Бэка Арсенала перед вызовом auth-сервиса. Оператор при вызове этого эндпоинта получает `403 Forbidden`.
- **Происхождение:** 🟢 новое.
- **Трассировка:** FR-1, FR-2, FR-3.

### INT-2. Получение числа активных сессий — BE Арсенала → сервис аутентификации — 🟡

- **Граница/направление:** Бэк Арсенала → Сервис аутентификации (механизм TBD).
- **Триггер:** Получение запроса к INT-1, если кэш истёк (см. §5.1).
- **Контракт (запрос):** 🟡 к валидации — путь, метод, параметры не известны.
- **Контракт (ответ):** 🟡 к валидации — точный формат ответа не известен. Ожидаемое: число активных сессий (целое число или структура, из которой его извлечь).
- **Происхождение:** 🟡 к валидации (контракт существующего сервиса не подтвержден).

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 + `count: null` | `{ "count": null }` | Источник (auth-сервис) недоступен, кэш пуст, или данные устарели | «—» (тире, не ошибка) |
| 500 | Внутренняя ошибка | Отказ Арсенала при обработке запроса | «—» + логирование |
| 403 | Forbidden | Пользователь не имеет роли «Администратор» | элемент UI не отображается или ошибка 403 перехватывается фронтом |

## 2.5. Этапы работ и порядок сборки

**Анализ:** Задача содержит два взаимодействия (INT-1 в фронте и INT-2 в бэке), но это две стороны **одного** шва — контракта между админкой и auth-сервисом. Логика каждой стороны проста: фронт показывает пришедшее число (или «—» при `null`), бэк кэширует вызов к auth-сервису и возвращает кэшированное значение. Нет раздельных **логических этапов** со своей предметной логикой — это одна работа, разрезанная по границе FE/BE.

**Вывод:** не применимо — одна работа, нет этапов.

| # | Этап | Вход (шов) | Выход (шов) | Проверка в одиночку |
|---|------|-----------|-------------|---------------------|
| — | Единая работа: фронт показывает счётчик, бэк его кэширует | — | — | — |

Разработка ведётся параллельно (шов зафиксирован в INT-1), выкат идёт бэк раньше фронта (см. §6).

## 3. Данные и хранение

🟢 Новых таблиц, полей сущностей или миграций нет. Бэк Арсенала использует встроенный механизм кэширования (напр. Redis, in-process cache или другое — на выбор команды) для хранения счётчика на 30 секунд. Концептуально: `cache[last_active_count] = <int | null>`, TTL = 30 сек.

## 4. Frontend

### 4.1. Интеграция в UI
🟢 В шапку админки добавляется новый элемент — индикатор числа онлайн-пользователей. Расположение: рядом с другими системными индикаторами в шапке. Стиль: неяркий, не отвлекает (как указано в УХ-пожелании БТ).

### 4.2. Состояния элемента
- **Число видно** — `count` от INT-1 получено и > 0, отображаем число.
- **Загрузка** — запрос в пути: спиннер на месте числа.
- **Недоступно** — `count: null` или ошибка: тире «—», ошибка не показывается.
- **Нет прав** — роль != Администратор: элемент скрыт (не запрашивается, не видит Оператор).

### 4.3. Опрос и повторные попытки
Фронт опрашивает INT-1 каждые 60 секунд. При ошибке сети или HTTP 5xx показать «—» и повторить на следующем интервале (без backoff, без явного retry).

## 5. Backend

### 5.1. Кэширование
🟢 Бэк Арсенала кэширует ответ от auth-сервиса на **30 секунд**. Логика:
- При GET INT-1: проверить кэш.
- Если кэш свежий → вернуть кэшированное значение.
- Если кэш истёк или не инициализирован → вызвать INT-2 (auth-сервис), обновить кэш, вернуть результат.
- Если INT-2 завершилась ошибкой и кэш пуст → вернуть `{ "count": null }` (не падать с 5xx, не показывать ошибку).

### 5.2. Авторизация
🟢 На уровне Бэка Арсенала перед обработкой INT-1 проверить, имеет ли текущий пользователь роль «Администратор». Если нет — вернуть `403 Forbidden`. Проверка происходит в middleware или контроллере, до вызова кэша и auth-сервиса.

### 5.3. Контракт с auth-сервисом
🟡 к валидации — точный путь, метод и формат ответа auth-сервиса не подтверждены (см. INT-2). Ожидаемое: сервис отдаёт число активных сессий, либо в виде числа, либо в структуре, из которой его можно извлечь. Во время интеграции уточнить формат и обработать ошибки (если auth-сервис недоступен, вернуть `count: null`).

## 6. Выкат и совместимость

### 6.1. Порядок деплоя
1. **Бэк Арсенала** выкатывается первым (добавлен INT-1 эндпоинт + кэширование, авторизация).
2. **Фронт Арсенала** выкатывается вторым (элемент в шапке, опрос INT-1).

Причина: фронт опирается на новый бэк-контракт (INT-1); если фронт развернуть раньше, бэк не будет готов.

### 6.2. Обратная совместимость
- Старый фронт (если он есть и не был обновлен) не знает о INT-1, не стонет. Новый фронт работает с новым бэком.
- Бэк при разворачивании ещё до включения фронта предоставляет INT-1, но его никто не вызывает — это нормально.

### 6.3. Преднастройка
До релиза убедиться, что роль **«Администратор»** существует в системе управления доступом (security/auth-сервис) и настроена корректно. Пользователи с этой ролью будут видеть индикатор.
