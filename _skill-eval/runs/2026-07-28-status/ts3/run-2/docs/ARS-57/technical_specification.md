## 1. Обзор изменения

### 1.1. Тип и стороны
🟢 Fullstack — добавление нового взаимодействия между фронтом и бэком админки «Арсенал», а также между бэком Арсенала и существующим сервисом аутентификации.

### 1.2. Затронутые сервисы и владельцы

|--------|---------------|------------------|---------------|
| Админка «Арсенал» (FE + BE) | Новое взаимодействие: получение числа активных пользователей, отображение в шапке | Команда Арсенал | 🟢 новое |

### 1.3. Связь с бизнес-требованиями

## 2. Взаимодействия (ядро)

### INT-1. Получение числа активных пользователей (FE Арсенала) — 🟢

- **Граница/направление:** FE Арсенала → BE Арсенала
- **Триггер:** 
  - При загрузке страницы админки;
  - При периодическом опросе (polling) каждые 60 секунд.
- **Контракт (запрос):** 
  - Метод/путь: `GET /api/v1/stats/active-users` (концептуально)
  - Тело отсутствует; параметры отсутствуют.
- **Контракт (ответ):**
  - Поле `count`: `int | null`
    - Тип `int` (≥ 0): число активных пользователей
    - Тип `null`: источник данных (сервис аутентификации) недоступен или не ответил в срок
  - Семантика null: **не ошибка**, а штатное состояние недоступности источника; UI показывает «—» вместо ошибки
- **Пример запроса:**
  ```
  GET /api/v1/stats/active-users
  (тело отсутствует, параметров нет)
  ```
- **Пример ответа (успех):**
  ```json
  {
    "count": 42
  }
  ```
- **Пример ответа (источник недоступен):**
  ```json
  {
    "count": null
  }
  ```
- **Ошибки:** Сервис не возвращает ошибки в смысле HTTP-кодов. Любая недоступность источника (таймаут, сервис аутентификации не ответил, сетевая ошибка) трансформируется в `count: null` в успешном ответе `200 OK`.
- **Состояния UI по ответу:**
  - **Значение (count = число)** → Отображаем число активных пользователей в шапке (текстовое представление, напр. "Онлайн: 42").
  - **Загрузка (запрос в полёте)** → Отображаем спиннер или плейсхолдер в месте индикатора.
  - **Недоступность (count = null)** → Отображаем «—» (прочерк/тире) вместо числа; это НЕ ошибка, сообщаем неявно через отсутствие значения.
  - **Ошибка (HTTP 4xx/5xx)** → Маловероятно в штатном потоке; если произойдёт, UI показывает «—» (эквивалент недоступности).
- **Авторизация:**
  - Кто вправе: только пользователи с ролью **Администратор**.
  - Где проверяется: в middleware/обработчике бэка Арсенала перед тем, как обратиться к сервису аутентификации.
  - Негативный случай: если пользователь не администратор, эндпоинт возвращает `403 Forbidden` или `401 Unauthorized` (на выбор команды; контракт для фронта: в обоих случаях индикатор не показывается, пользователь видит пусто).
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1 (отображение), FR-2 (обновление без перезагрузки), FR-3 (отображение «—» при недоступности)

### INT-2. Получение числа активных сессий у сервиса аутентификации — 🟡

- **Граница/направление:** BE Арсенала → Сервис аутентификации
- **Триггер:** BE Арсенала получает запрос на INT-1 и обращается к источнику данных.
- **Контракт (запрос):** 
  - Метод, путь, параметры, заголовки: **🟡 к валидации**. Аналитик подтвердил, что сервис аутентификации **умеет** считать число активных сессий, но точный интерфейс сейчас не помнит.
- **Контракт (ответ):** 
  - Ожидается одно числовое поле (или поле, из которого можно извлечь число) с числом активных сессий.
  - **Точная схема: 🟡 к валидации.** Требует уточнения с командой аутентификации или проверки в коде сервиса.
- **Примеры:** Не приводим конкретные JSON, чтобы не выдумать контракт существующего сервиса. При интеграции будет использован реальный контракт из исходного кода/документации сервиса аутентификации.
- **Ошибки:** 
  - **Таймаут/недоступность сервиса аутентификации:** 🟡 к валидации. Поведение (какой HTTP-код, какой таймаут, retry-логика) требует уточнения.
  - **Авторизационные ошибки:** 🟡 к валидации. Зависит от того, как авторизуется BE Арсенала при обращении к сервису аутентификации.
  - **Трансформация в INT-1:** Любая ошибка / недоступность на этом уровне преобразуется в `count: null` для клиента (INT-1).
- **Состояния:** Прозрачны для UI (обрабатываются бэком).
- **Авторизация:** 
  - **Между сервисами:** 🟡 к валидации. Требует уточнения механизма (API-ключ, JWT, mTLS и т.п.) и прав BE Арсенала на доступ к счётчику аутентификации.
- **Происхождение:** 🟡 подтверждено аналитиком (сервис существует и умеет считать сессии; точный контракт к валидации)
- **Трассировка:** Опосредованно через INT-1 трассируется к FR-1, FR-2, FR-3.

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 OK + `count: null` | Успешный ответ, но источник недоступен | Таймаут к сервису аутентификации, сетевая ошибка, любая недоступность источника | Показать «—» (прочерк) |
| 200 OK + `count: число` | Успешный ответ с числом активных пользователей | Нормальный успех | Показать число |
| 403 Forbidden | Пользователь не имеет роль Администратор | Авторизационная проверка не пройдена | Не показывать индикатор |
| 401 Unauthorized | Пользователь не аутентифицирован | Сессия истекла или отсутствует | Не показывать индикатор |

## 2.5. Этапы работ и порядок сборки

**Анализ разреза по содержанию:**
Задача реализует одну логику: получить число активных пользователей из вышестоящего сервиса и отобразить в UI. Хотя на границе FE↔BE есть контракт, это одно взаимодействие, а не две независимые работы: фронт просто отображает то, что бэк отдаёт; логика вся в бэке (опрос auth-сервиса, кэширование, трансформация null → «—»).

**Вывод:** Один этап, разрезать нечего.

**Не применимо: Задача реализует одно взаимодействие FE↔BE с одной предметной логикой (получение и кэширование счётчика сессий). Разрезать между фронтом и бэком — значит рассечь одну работу по границе фронт/бэк, что не создаёт независимых этапов.**

## 3. Данные и хранение

**Не применимо:** Новых сущностей и таблиц не создаётся. Число активных пользователей берётся из существующего сервиса аутентификации, а бэк Арсенала кэширует его в памяти (TTL = 30 секунд) без персистентного хранилища.

**Кэширование (производительность):**
- 🟢 Место кэша: в памяти BE Арсенала.
- 🟢 TTL: 30 секунд.
- 🟢 Логика: при приходе запроса INT-1 бэк проверяет, не истёк ли кэш; если истёк или кэша нет — обращается к сервису аутентификации, иначе возвращает кэшированное значение.

## 4. Состояния фронта и пользовательский опыт

### 4.1. Состояния и переходы индикатора
- **Состояние «Значение»** (значение загружено): отображаем число, напр. "Онлайн: 42".
- **Состояние «Загрузка»** (запрос в полёте): отображаем спиннер или пульсирующий плейсхолдер вместо числа.
- **Состояние «Недоступно»** (count = null): отображаем «—» (прочерк); это штатное состояние, а не ошибка.
- **Состояние «Запрещено»** (нет доступа): индикатор не показывается совсем (только для ролей ≠ Администратор).

### 4.2. Видимость по ролям
- **Администратор:** индикатор виден, значение периодически обновляется (polling каждые 60 секунд).
- **Оператор и прочие роли:** индикатор не отображается.

### 4.3. UX-пожелание
Индикатор неяркий, не отвлекает от основной работы (требование из БТ §6). Рекомендуется: серый цвет текста, маленький размер шрифта, размещение в углу шапки.

## 5. Нефункциональные требования

### 5.1. Производительность и синхронность
- 🟢 **Polling интервал:** FE опрашивает BE раз в 60 секунд (обновление значения в пределах минуты, требование FR-2).
- 🟢 **Кэш бэка:** 30 секунд. Не требует опроса auth-сервиса при каждом запросе; экономит нагрузку.
- 🟢 **Таймаут к auth-сервису:** 🟡 к валидации. Точное значение требует согласования (рекомендуется 5–10 секунд); при превышении возвращаем `count: null`.
- 🟢 **Кэширование на фронте:** нет. Фронт всегда выполняет запрос, даже если он был недавно.

### 5.2. Безопасность и авторизация
- 🟢 **Контроль доступа:** Эндпоинт INT-1 проверяет роль пользователя; только Администраторы видят индикатор. Проверка на уровне middleware бэка.
- 🟡 **Межсервисная авторизация:** механизм авторизации BE Арсенала перед сервисом аутентификации (к валидации; см. INT-2).

### 5.3. Надёжность
- 🟡 **Graceful degradation:** При недоступности auth-сервиса INT-1 возвращает `count: null` вместо ошибки. UI показывает «—» вместо числа. Процесс не прерывается.
- ⚠️ **Логирование:** Требует уточнения. Рекомендуется логировать ошибки/таймауты к auth-сервису на уровне WARN для последующей диагностики.

## 6. Порядок выката и совместимость

### 6.1. Очередность деплоя
1. **Этап 1 (BE):** Развёртывание бэка Арсенала с новым эндпоинтом INT-1 и логикой опроса auth-сервиса.
2. **Этап 2 (FE):** Развёртывание фронта Арсенала с UI-компонентом индикатора и polling-логикой.
3. **Этап 3 (Config):** Роль «Администратор» доступна в системе управления ролями (если требуется создание или включение; во многих системах роль уже существует).

**Обоснование:** BE выкатываем первым, потому что FE зависит от контракта INT-1. После выката BE контракт есть, FE может опрашивать его без ошибок. FE выкатываем вторым; если выкатить первым, фронт попадёт на 404 или 500 от бэка.

### 6.2. Обратная совместимость
- 🟢 **BE совместимо:** Новый эндпоинт не трогает существующие API; не ломает ничего.
- 🟢 **FE совместимо:** Новый элемент UI в шапке добавляется, не вытесняя существующие; не нарушает вёрстку.
- 🟢 **Миграция данных:** Не требуется.

### 6.3. Преднастройка до релиза
- 🟢 **Роль Администратор:** должна быть заведена в системе управления ролями до релиза (если её ещё нет). После выката индикатор появится только для пользователей с этой ролью.
- 🟡 **Права доступа BE Арсенала к auth-сервису:** Требует валидации. Убедиться, что у BE Арсенала есть учётные данные / сертификаты для обращения к auth-сервису (к валидации вместе с INT-2).

## 7. Трассировка приёмки и тестирование

### 7.1. Связь FR → Взаимодействие → Тест-кейс

| FR | Описание | Взаимодействие | Тест-кейс |
|----|----------|---|-----------|
| FR-1 | Система отображает число активных пользователей в шапке | INT-1 (GET /api/v1/stats/active-users) | Открыть админку как администратор → проверить, что в шапке видно число (напр. 42); закрыть, открыть другой экран → число должно быть на месте |
| FR-2 | Значение обновляется автоматически без перезагрузки | INT-1 + polling-логика (60 сек) | Открыть админку, наблюдать счётчик в течение 2 минут → значение должно измениться, если число активных пользователей поменялось → проверить, что обновление произошло (с учётом интервала + кэша 30 сек, максимум 90 сек) |
| FR-3 | При недоступности источника показывается «—» вместо ошибки | INT-1 (count: null) | Выключить сервис аутентификации / создать таймаут → открыть админку → проверить, что в шапке показывается «—» (прочерк), а не ошибка или пусто; админка продолжает работать нормально |

### 7.2. Ролевое тестирование
- **Роль Администратор:** индикатор видна, число обновляется.
- **Роль Оператор:** индикатор не видна (скрыта, или пусто в шапке).
- **Анонимный / без роли:** индикатор не видна (или 401 Unauthorized).

### 7.3. Граничные случаи
- **count = 0:** Отображаем "Онлайн: 0" (ноль активных пользователей — штатное состояние, не ошибка).
- **count = null:** Отображаем «—» (недоступность источника).
- **Очень большое число (млн):** Отображаем как есть (ограничение на представление — на усмотрение фронта; может быть сокращено, напр. "1.2M" вместо "1200000").
- **Таймаут к auth-сервису:** Через 5–10 сек возвращаем `count: null` → UI показывает «—» (не зависает).
