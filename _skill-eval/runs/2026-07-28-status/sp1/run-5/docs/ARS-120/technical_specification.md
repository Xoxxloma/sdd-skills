## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. Фронт и бэк «Арсенала» + потребление потока сведений от внешней системы учёта оборудования. Система получает сведения об оборудовании из внешнего источника, хранит их, сопоставляет с объектами охраны по адресу и показывает привязанное оборудование в карточке объекта.

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (бэк) | новое хранилище сведений об оборудовании, сопоставление по адресу, эндпоинт отдачи | Команда «Арсенала» | 🟢 |
| Арсенал (фронт) | отображение оборудования в карточке объекта охраны | Команда «Арсенала» | 🟢 |
| Система учёта оборудования (внешняя) | источник потока сведений об оборудовании | внешний владелец | 🟡 подтверждено аналитиком (уже публикует поток; формат пока не уточнен) |

### 1.3. Связь с бизнес-требованиями
Реализует цель: инженер видит оборудование в карточке объекта без необходимости искать его во внешней системе по адресу. Это сокращает повторные выезды и экономит время на ручную сверку. Ограничение: привязка только при однозначном совпадении адреса; неоднозначные и непривязанные случаи остаются явными для ручного разбора (согласно бизнес-рискам из БТ).

## 2. Взаимодействия (ядро)

### INT-1. Приём потока сведений об оборудовании от внешней системы — 🟢
- **Граница/направление:** Система учёта оборудования → Бэк Арсенала
- **Триггер:** Сведения об оборудовании создаются, обновляются или удаляются во внешней системе
- **Контракт (входящее сообщение события):** 🟡 Точный формат и имя/тип топика — к валидации. Концептуально:
  - `external_equipment_id` (строка, обязательно) — идентификатор единицы оборудования во внешней системе; служит ключом идемпотентности в Арсенале
  - `type` (строка enum, обязательно) — тип оборудования (напр. «видеокамера», «датчик движения», «сирена»; точный перечень — по внешней системе, к валидации)
  - `address` (строка, обязательно) — адрес установки в исходном виде (как он есть во внешней системе)
  - `timestamp` (unix seconds / ISO 8601, обязательно) — момент последнего обновления сведений во внешней системе
- **Пример входящего события (концептуальный, формат к валидации):**
  ```json
  {
    "external_equipment_id": "EQ-2024-00456",
    "type": "видеокамера",
    "address": "ул. Ленина, д. 42, кв. 5",
    "timestamp": "2026-07-28T14:30:00Z"
  }
  ```
- **Обработка и состояние:** Сообщение обрабатывается асинхронно по мере поступления. Повторная доставка того же `external_equipment_id` с тем же или позднейшим `timestamp` обновляет существующую запись (upsert); ранняя повторная доставка (старый timestamp) игнорируется. Идемпотентность гарантирована: повторный приём не создаёт дублей.
- **Ошибки и недоступность:** 
  - Валидация: если `external_equipment_id` отсутствует или пусто → сообщение отклоняется (логируется, не сохраняется).
  - Если `address` пусто → сохраняется, но такое оборудование не участвует в сопоставлении (остаётся непривязанным).
  - Если `type` неизвестен → сохраняется как есть; тип не влияет на сопоставление, только на отображение.
- **Авторизация:** Приём выполняется системно (без пользовательского действия); авторизация между Арсеналом и внешней системой — на уровне сервис-сервис (учётные данные, сертификаты — способ доставки топика, к валидации).
- **Происхождение:** 🟢 новое взаимодействие, INT-1
- **Трассировка:** FR-1 (Система принимает сведения об оборудовании из внешней системы учёта и хранит их)

### INT-2. Получить оборудование, привязанное к объекту охраны — 🟢
- **Граница/направление:** Фронт Арсенала → Бэк Арсенала
- **Триггер:** Инженер открывает карточку объекта охраны; фронт загружает раздел оборудования
- **Контракт (запрос):** `GET /api/v1/guarded-objects/{guardedObjectId}/equipment`
  - `guardedObjectId` (параметр пути, uuid или числовой id — по существующей схеме объектов в Арсенале) — идентификатор объекта охраны в Арсенале
  - Авторизация: заголовок `Authorization: Bearer <token>` (стандартная аутентификация Арсенала)
- **Контракт (ответ — успех 200):**
  - `equipment` (массив объектов, может быть пустым) — список оборудования, привязанного к объекту
    - `equipment_id` (строка, уникален внутри Арсенала) — первичный ключ записи оборудования в Арсенале
    - `external_equipment_id` (строка) — идентификатор во внешней системе (для перекрёстных ссылок)
    - `type` (строка enum) — тип оборудования
    - `original_address` (строка) — адрес в исходном виде из внешней системы (для справки)
    - `normalized_address` (строка) — адрес после нормализации (для отладки)
    - `last_updated` (unix seconds / ISO 8601) — время последнего обновления сведений об этом оборудовании
    - `matched_at` (unix seconds / ISO 8601 или null) — время установки привязки к этому объекту (по результату последнего пересчёта сопоставления). Null, если привязка была восстановлена вручную (см. out-of-scope).
  - `actual_at` (unix seconds / ISO 8601) — время, на которое актуальны эти сведения (момент последнего пересчёта сопоставления). Используется фронтом для отображения метки «данные актуальны на …».
- **Пример ответа (успех, есть оборудование):**
  ```json
  {
    "equipment": [
      {
        "equipment_id": "eq-uuid-001",
        "external_equipment_id": "EQ-2024-00456",
        "type": "видеокамера",
        "original_address": "ул. Ленина, д. 42, кв. 5",
        "normalized_address": "ленина ул. д.42 кв.5",
        "last_updated": "2026-07-28T14:30:00Z",
        "matched_at": "2026-07-28T02:15:00Z"
      }
    ],
    "actual_at": "2026-07-28T02:15:00Z"
  }
  ```
- **Пример ответа (успех, пусто — нет привязанного оборудования):**
  ```json
  {
    "equipment": [],
    "actual_at": "2026-07-28T02:15:00Z"
  }
  ```
- **Ошибки:**
  - **404 Not Found** — объект охраны с заданным id не найден. Тело: `{ "error": "guarded_object_not_found", "message": "Объект охраны не найден" }`
  - **403 Forbidden** — пользователь не имеет доступа к этому объекту или раздел оборудования недоступен его роли (см. ниже авторизацию). Тело: `{ "error": "access_denied", "message": "Доступ запрещён" }`
  - **500 Internal Server Error** — бэк недоступен или внутренняя ошибка. Тело: `{ "error": "internal_error", "message": "Внутренняя ошибка сервера" }`
- **Состояния UI по ответу:**
  - **Загрузка** (в момент запроса): спиннер или скелет списка
  - **Перечень (успех, equipment.length > 0):** отображается список карточек оборудования; каждая содержит: тип, адрес, время последнего обновления; под списком — отметка «данные актуальны на: {actual_at}»
  - **«Нет данных» (успех, но equipment.length === 0):** явное сообщение «Оборудование не привязано» или «На этом объекте оборудование не установлено»; по-прежнему показывается время актуальности
  - **Ошибка (4xx/5xx):** сообщение об ошибке с предложением повторить; если 404 — сообщение о том, что объект не найден
  - ⚠️ Эти состояния различны и не должны сливаться: «нет данных» — это успешный ответ с пустым списком, а ошибка — это отказ. UI должна разделять их.
- **Авторизация:** 
  - Проверка роли при выполнении запроса: только роли «Инженер» и «Диспетчер» имеют доступ к разделу оборудования. Роль «Оператор» получит 403.
  - Проверка доступа к объекту: пользователь должен иметь доступ к этому объекту охраны (существующее ограничение в Арсенале, не новое).
  - Enforcement: на стороне бэка, в обработчике эндпоинта, перед возвратом данных.
- **Происхождение:** 🟢 новое взаимодействие, INT-2
- **Трассировка:** FR-3 (В карточке объекта охраны отображается привязанное к нему оборудование)

### Каталог ошибок (сводно)

## 3. Данные и хранение

### 3.1. Новые сущности

**Сущность: Оборудование**
Хранит сведения об оборудовании, полученные из внешней системы учёта.
- `equipment_id` (PK, uuid или generated string) — первичный ключ; уникален в пределах Арсенала
- `external_equipment_id` (строка, NOT NULL, UNIQUE) — идентификатор во внешней системе; служит ключом идемпотентности при приёме
- `type` (строка enum или просто строка, NOT NULL) — тип оборудования
- `original_address` (строка, NOT NULL) — адрес в исходном виде из внешней системы
- `normalized_address` (строка, NOT NULL) — адрес после нормализации (для сопоставления); вычисляется при приёме или при пересчёте
- `last_updated` (timestamp, NOT NULL) — время последнего обновления сведений (переносится из события внешней системы)
- `created_at` (timestamp, NOT NULL, default=NOW) — время создания записи в Арсенале
- `updated_at` (timestamp, NOT NULL, default=NOW, on-update=NOW) — время последнего обновления в БД Арсенала
- Индекс: по `external_equipment_id` (для идемпотентности); по `normalized_address` (для сопоставления); по `type` (опционально, для фильтрации)

**Сущность: Привязка (Equipment-GuardedObject mapping)**
Хранит результаты сопоставления: какое оборудование привязано к какому объекту охраны.
- `mapping_id` (PK, uuid или generated string) — первичный ключ
- `equipment_id` (FK на Оборудование, NOT NULL) — ссылка на оборудование
- `guarded_object_id` (FK на GuardedObject, NOT NULL; тип — по существующей схеме объектов в Арсенале) — ссылка на объект охраны
- `matched_at` (timestamp, NOT NULL) — время установки привязки (момент завершения пересчёта сопоставления)
- `created_at` (timestamp, NOT NULL, default=NOW)
- `updated_at` (timestamp, NOT NULL, default=NOW, on-update=NOW)
- Ограничение: уникальность пары (equipment_id, guarded_object_id) — одно оборудование может быть привязано к одному объекту только один раз
- Индекс: по (equipment_id, guarded_object_id); по guarded_object_id (для быстрого поиска оборудования по объекту); по equipment_id

### 3.2. Нормализация адреса
🟢 **Алгоритм нормализации:** приведение адреса к унифицированному формату для сопоставления.
- Входной формат: строка в свободной форме (из внешней системы и из карточки объекта в Арсенале)
- Процесс: 
  1. Приведение к нижнему регистру
  2. Удаление диакритических знаков (если применимо)
  3. Нормализация сокращений (напр. «ул.» → «улица», «д.» → дом», но не добавляется логика поиска по справочнику адресов)
  4. Нормализация пунктуации (удаление лишних пробелов, запятых)
  5. Упорядочивание компонентов адреса по форме (без переведения в иерархический вид — просто текстовое упорядочивание)
- Выход: нормализованная строка (напр. «ул. Ленина, д. 42, кв. 5» → «ленина улица д 42 кв 5» или аналогичный формат)
- ⚠️ Точный алгоритм нормализации требует уточнения с аналитиком: нужны ли справочники адресов, какие сокращения поддерживать, какой порядок компонентов. Концептуально: это текстовое приведение к единому виду, не полнотекстовый поиск и не привязка к справочнику ГИС.

### 3.3. Пересчёт сопоставления
🟢 **Запуск:** Регулярно, раз в сутки (ночью, в определённый час — напр. 02:00 UTC; точный час согласуется во время разработки)
🟢 **Процесс:**
1. Для каждого объекта охраны в Арсенале:
   - Извлечь нормализованный адрес объекта
   - Найти ВСЕ единицы оборудования (из сущности Оборудование) с совпадающим нормализованным адресом
   - Если совпадений ровно одна: создать или обновить Привязку; если Привязка уже существует — обновить `matched_at`
   - Если совпадений ноль или несколько (≥2): оборудование остаётся или переходит в статус непривязанного; Привязка удаляется или не создаётся; такие случаи логируются для ручного разбора
2. Обновить глобальную отметку времени последнего успешного пересчёта (для отображения в UI через `actual_at`)
3. Пересчёт выполняется в одной транзакции (для консистентности)

🟡 **Детали хранения пересчёта:** как ведётся отчёт о непривязанном оборудовании и многозначных совпадениях (таблица, логи, отдельный API для аналитики) — к валидации. Концептуально: результат доступен как для диспетчера через отчёт, так и для автоматизированной обработки.

### 3.4. Миграции (концептуально)
- **Таблица Оборудование:** создание; индексы по external_equipment_id, normalized_address
- **Таблица Привязка:** создание; индексы по (equipment_id, guarded_object_id), guarded_object_id, equipment_id; FK-ограничения на обе таблицы
- **Таблица GuardedObject:** добавление поля `equipment_address_normalized` (опционально, если адреса хранятся отдельно; иначе используется существующее поле адреса) — для ускорения сопоставления. Если поле уже есть, обновить индекс.
- Точный DDL, инструменты миграции (Flyway, Alembic и т.п.), откат — по владеющему сервису (Арсенал), не часть этой спеки.

## 4. Состояния и UI

### 4.1. Раздел «Оборудование» в карточке объекта охраны
🟢 **Новый раздел:** добавляется в карточку объекта охраны. Доступен только для ролей Инженер и Диспетчер (Оператор не видит раздел вообще).

### 4.2. Состояния загрузки и ошибок

**Состояние 1: Загрузка (pending)**
- Внешний вид: спиннер или скелет списка («загружается…»)
- Когда: запрос к INT-2 отправлен, ответ не пришёл
- Как выйти: ответ INT-2 получен (→ перечень / пусто / ошибка)

**Состояние 2: Перечень (success)**
- Внешний вид: карточки оборудования, каждая с полями: тип, адрес, время последнего обновления
- Когда: INT-2 вернул 200 и equipment.length > 0
- Данные: тип, original_address (или обе адреса для отладки), last_updated
- Дополнительно: под списком отметка времени актуальности: «Данные актуальны на: {actual_at}»
- Действие: нажатие на карточку (если нужно, из out-of-scope) — не часть этой спеки

**Состояние 3: Нет данных (empty)**
- Внешний вид: явное сообщение на месте списка: «Оборудование не привязано» или «На этом объекте оборудование не установлено»
- Когда: INT-2 вернул 200, но equipment.length === 0 (успешный ответ с пустым списком)
- Дополнительно: отметка времени актуальности всё равно показывается
- Отличие от ошибки: это НЕ ошибка, это корректное состояние (объект просто не имеет привязанного оборудования)

**Состояние 4: Ошибка (error)**
- Внешний вид: сообщение об ошибке с иконкой или красным фоном; кнопка «Повторить»
- Когда: INT-2 вернул ошибку (4xx, 5xx)
- Сообщение: в зависимости от кода
  - 403: «У вас нет доступа к этим данным»
  - 404: «Объект не найден»
  - 5xx: «Не удалось загрузить данные; повторите попытку позже»
  - Иное: «Ошибка при загрузке данных»
- Действие: кнопка «Повторить» переотправляет запрос (рассчитано на временные сбои)
- Отличие от пусто: это ОШИБКА, не нормальное состояние

### 4.3. Диаграмма переходов состояний UI
```
[Не загружено] —(открыть раздел)→ [Загрузка]
[Загрузка] —(200, items > 0)→ [Перечень]
[Загрузка] —(200, items = 0)→ [Нет данных]
[Загрузка] —(4xx/5xx)→ [Ошибка]
[Перечень] —(нажать повторить)→ [Загрузка]
[Нет данных] —(нажать повторить)→ [Загрузка]
[Ошибка] —(нажать повторить)→ [Загрузка]
```

### 4.4. Требования к отображению
- Время (last_updated, actual_at): переводить в локальное время пользователя, формат «дата время» или относительное («1 час назад»)
- Адрес: показывать original_address (как он есть во внешней системе); normalized_address может быть скрыто или доступно для отладки/админов
- Тип оборудования: отображать в выбранной классификации (уточнить, если нужны иконки по типам)
- Список: сортировка по типу, по времени обновления (уточнить при разработке)

## 5. Нефункциональные требования

### 5.1. Синхронность и производительность
- **Приём потока (INT-1):** асинхронный, по мере поступления сообщений. Latency: не критична (сообщения о новом оборудовании поступают в бэк, не требуя ответа пользователю). Обработка одного сообщения: < 1s (включая валидацию, нормализацию, upsert в БД).
- **Пересчёт сопоставления:** запускается раз в сутки (ночью). Длительность: зависит от объёма оборудования и объектов охраны. На момент разработки — оценка требуется; ориентировочно: на тысячу объектов и десять тысяч единиц оборудования — несколько минут. Тайм-аут: уточнить при разработке.
- **Запрос INT-2 (фронт → бэк):** синхронный, по открытию карточки. Latency: < 1s (SLA, не критичное). Кэширование: возможно (результат не меняется, пока не запущен пересчёт); TTL = до следующего пересчёта или явный инвалид; уточнить при разработке.
- **Нагрузка:** приём потока может быть высокочастотным (зависит от частоты обновлений во внешней системе); INT-2 — низкочастотный (единичные запросы от пользователей). Оба режима должны быть протестированы.

### 5.2. Обратная совместимость
- Приём: старые версии внешней системы могут отправлять сообщения без поля `timestamp` или с другим форматом. 🟡 Как обрабатывать: к валидации. Концептуально: или требовать обновления внешней системы, или проставлять серверное время как fallback.
- Выход (INT-2): ответ может быть расширен новыми полями в будущем (напр. координаты GPS оборудования). Фронт должен игнорировать неизвестные поля (стандартное поведение JSON); пересчёт и добавление полей не требуют изменения фронта.

### 5.3. Безопасность и авторизация
- Авторизация INT-1: между сервисами (Арсенал и внешняя система). Способ: Bearer token, API-ключ, mTLS или иное. 🟡 Какой способ: к валидации (зависит от инфраструктуры).
- Авторизация INT-2: по ролям пользователя (Инженер, Диспетчер видят; Оператор нет) + по доступу пользователя к объекту охраны (существующее ограничение).
- Валидация данных: входящие события (INT-1) проверяются на формат и обязательные поля; некорректные отклоняются.
- Логирование: приём, ошибки валидации, результаты пересчёта — логируются для отладки и аудита.

### 5.4. Отказоустойчивость
- Идемпотентность приёма (INT-1): гарантирована уникальным ключом external_equipment_id и проверкой timestamp; повторное сообщение не создаёт дублей.
- Сбой пересчёта: если пересчёт завершился с ошибкой, существующие привязки остаются без изменений; время актуальности не обновляется; пересчёт повторяется в следующее время (в соответствии с расписанием).
- Сбой приёма: если сообщение не обработано (валидация, БД недоступна), оно логируется; механизм повтора — в ответственности системы передачи (внешняя система, очередь сообщений, и т.п.); 🟡 детали — к валидации.

## 6. Порядок выката и совместимость

### 6.1. Очередность деплоя
Фиксированный порядок (нельзя нарушить):
1. **Этап 1: Хранилище и приём** — развёртывается табличная база (Оборудование, миграции), эндпоинт приёма потока на бэке, обработчик сообщений. Внешняя система начинает отправлять, Арсенал принимает и хранит. Проверка: приём работает, сведения записываются без дублей.
2. **Этап 2: Пересчёт сопоставления** — развёртывается логика сопоставления, таблица Привязка, регулярный job пересчёта. Сопоставление начинает работать. Проверка: результаты видны в логах, Привязка заполняется.
3. **Этап 3: Эндпоинт отдачи** — развёртывается INT-2 на бэке. Проверка: запросы к `/api/v1/guarded-objects/{id}/equipment` возвращают корректные данные (или пусто, если нет привязок).
4. **Этап 4: Карточка на фронте** — развёртывается новый раздел в карточке объекта, вызывающий INT-2 и отображающий результат. Проверка: раздел видим инженерам и диспетчерам, пусто отображается корректно, ошибки обрабатываются.

### 6.2. Зависимости между этапами
- Этап 1 независим (может запуститься в любой момент).
- Этап 2 зависит от Этапа 1 (нужны данные в сущности Оборудование).
- Этап 3 зависит от Этапа 2 (эндпоинт вернёт пусто до пересчёта, но технически может работать).
- Этап 4 зависит от Этапа 3 (фронт вызывает INT-2, который должен быть готов).

Рекомендуемый порядок: 1 → 2 → 3 → 4 (как выше). При правильной реализации Этапа 3 (возврат пустого массива, если нет привязок), Этап 4 можно развёртывать параллельно с Этапом 3 (но не раньше).

### 6.3. Обратная совместимость
- БД: новые таблицы не мешают существующему коду. Миграции не редактируют существующие структуры (только добавляют).
- INT-2: эндпоинт новый, не меняет существующие контракты.
- Фронт: раздел добавляется в карточку, не удаляя других разделов. Скрыт для Оператора (существующая ролевая модель Арсенала расширяется, не меняется).
- Откат: удаление этапов в обратном порядке (4 → 3 → 2 → 1) вернёт систему в исходное состояние.

### 6.4. Преднастройка и фиче-флаги
- **Фиче-флаг:** раздел оборудования в карточке объекта может быть включён флагом (для пошагового rollout по пользователям, если нужно). 🟡 Использовать ли: к валидации. Если да, флаг: `feature_equipment_display_in_object_card` (напр.); значение: boolean.
- **Ролевые настройки:** роли Инженер и Диспетчер должны существовать в системе. Если их нет, создать. Оператор должен быть явно исключён из доступа к разделу (в коде INT-2 или на уровне ролевой матрицы).
- **Конфигурация пересчёта:** время запуска (02:00 UTC или иное) должно быть настраиваемо через конфиг или переменную окружения.

### 7.2. Покрытие и зависимости тестов
- Тесты FR-1 и FR-2 — независимы от фронта, могут быть интеграционные (БД + бэк).
- Тесты FR-3 — зависят от FR-1, FR-2 (нужны данные и привязки); требуют e2e или интеграционного теста с фронтом и бэком.
- Негативные случаи: ошибка приёма (валидация), многозначное совпадение адреса, отсутствие доступа (403), объект не найден (404).
