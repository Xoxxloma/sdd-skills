## 1. Обзор изменения

### 1.1. Тип и стороны

**Fullstack**. Арсенал получает поток сведений об оборудовании из внешней системы, сохраняет их и показывает привязанные единицы в карточке объекта охраны на фронте. На фронте добавляется новая секция; на бэке — приём потока, хранение, регулярный пересчёт привязки, новый API-эндпоинт.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (Backend) | приём сведений из потока, хранение оборудования и привязок, API отдачи | Team Backend (Арсенал) | 🟢 (новый компонент в существующем сервисе) |
| Арсенал (Frontend) | отображение привязанного оборудования в карточке объекта | Team Frontend (Арсенал) | 🟢 (новая секция в существующей карточке) |
| Система учёта оборудования (внешняя) | источник, публикует поток изменений | Другая команда / внешний партнёр | 🟡 подтверждено аналитиком (уже публикует поток) |

### 1.3. Связь с бизнес-требованиями

Реализует три FR из БТ: приём и хранение сведений об оборудовании (FR-1), автоматическое сопоставление с объектами охраны (FR-2), отображение в карточке (FR-3). Инженер видит комплект оборудования на объекте и не обращается ко второй системе.

## 2. Взаимодействия (ядро)

### INT-1. Приём сведений об оборудовании из внешней системы — 🟢

- **Граница/направление:** Система учёта оборудования → Backend Арсенала (событийный поток)
- **Триггер:** Появление/изменение единицы оборудования во внешней системе. Внешняя система публикует событие для каждой единицы.
- **Контракт (событие):** Сообщение о единице оборудования содержит:
  - `external_equipment_id` (string, обязательно) — уникальный идентификатор единицы в системе учёта;
  - `equipment_type` (string, обязательно) — тип оборудования (напр. "Датчик движения", "Клавиатура", "Видеокамера");
  - `address_original` (string, обязательно) — адрес установки в свободной форме, как указан в системе учёта;
  - `timestamp` (ISO 8601 datetime, обязательно) — момент регистрации / обновления в системе учёта.
- **Пример сообщения (при успехе):**
  ```json
  {
    "external_equipment_id": "ext-eq-67890",
    "equipment_type": "Датчик движения",
    "address_original": "Москва, ул. Примера, д. 5, офис 301",
    "timestamp": "2026-07-28T14:32:15Z"
  }
  ```
- **Ошибки:** Обработка ошибок на уровне потока:
  - Сообщение с дублирующимся `external_equipment_id` → не создаёт дубль в хранилище Арсенала (идемпотентность). Проверка выполняется по `external_equipment_id` как ключу идемпотентности; если запись с таким ID уже есть, она обновляется с новыми значениями, не создаётся вторая копия.
  - Сообщение с недостаточными данными (отсутствует обязательное поле) → логируется как ошибка обработки, событие пропускается, поток продолжается.
  - Общая недоступность / сбой коннектора → логируется; восстановление и ретрай — на уровне инфраструктуры потока (точные механизмы по коду в сервисе учёта).
- **Авторизация:** Поток публикуется внешней системой; Backend Арсенала слушает с правами сервис-сервис (учётные данные подтверждаются при интеграции).
- **Происхождение:** 🟢 новое взаимодействие; точный формат контракта (JSON / Protobuf / иное) и имя топика/очереди: 🟡 к валидации.
- **Трассировка:** FR-1 (приём и хранение сведений об оборудовании).

### INT-2. Получить оборудование по объекту охраны — 🟢

- **Граница/направление:** Frontend Арсенала → Backend Арсенала (HTTP GET)
- **Триггер:** Инженер открывает карточку объекта охраны; фронт запрашивает привязанное оборудование.
- **Контракт (запрос):** Метод GET, путь `/api/v1/security-objects/{security_object_id}/equipment` (концептуально; точный путь уточняется при разработке).
  - Параметр пути: `security_object_id` (UUID или число, тип определяется по существующей схеме Арсенала).
  - Заголовок авторизации: стандартный для Арсенала (Bearer token или session cookie).
- **Контракт (ответ):**
  - `equipment` (массив объектов, всегда присутствует, может быть пуст):
    - `internal_equipment_id` (string) — ключ единицы оборудования в Арсенале;
    - `equipment_type` (string) — тип оборудования;
    - `address_original` (string) — адрес из системы учёта;
    - `address_normalized` (string) — адрес после нормализации (используется для сопоставления);
    - `external_equipment_id` (string) — идентификатор из системы учёта (для трассировки при интеграции);
    - `updated_at` (ISO 8601 datetime) — момент последнего обновления сведений в Арсенале.
  - `data_actual_at` (ISO 8601 datetime) — момент последнего успешного пересчёта привязок. Показывает, на какой момент актуальны данные привязки.
  - `status` (string, enum: `loaded`, `no_data`, `error`) — cм. ниже.
- **Пример запроса:**
  ```
  GET /api/v1/security-objects/obj-12345/equipment
  Authorization: Bearer <token>
  ```
- **Пример ответа (успех, есть привязанное оборудование):**
  ```json
  {
    "equipment": [
      {
        "internal_equipment_id": "eq-int-001",
        "equipment_type": "Датчик движения",
        "address_original": "Москва, ул. Примера, д. 5, офис 301",
        "address_normalized": "Москва ул Примера д 5 офис 301",
        "external_equipment_id": "ext-eq-67890",
        "updated_at": "2026-07-28T14:32:15Z"
      },
      {
        "internal_equipment_id": "eq-int-002",
        "equipment_type": "Видеокамера",
        "address_original": "Москва, ул. Примера, д. 5",
        "address_normalized": "Москва ул Примера д 5",
        "external_equipment_id": "ext-eq-67891",
        "updated_at": "2026-07-28T10:15:22Z"
      }
    ],
    "data_actual_at": "2026-07-28T03:00:00Z",
    "status": "loaded"
  }
  ```
- **Пример ответа (успех, привязанного оборудования нет):**
  ```json
  {
    "equipment": [],
    "data_actual_at": "2026-07-28T03:00:00Z",
    "status": "no_data"
  }
  ```
- **Пример ответа (ошибка недоступности бэка):**
  ```json
  {
    "equipment": [],
    "data_actual_at": null,
    "status": "error",
    "error_message": "Internal server error"
  }
  ```
- **Ошибки:** 
  - HTTP 404 — объект охраны не найден.
  - HTTP 401 — нет авторизации.
  - HTTP 403 — авторизован, но роль не видит этот объект / раздел оборудования.
  - HTTP 500 — ошибка на сервере (включая недоступность компонента привязки).
- **Состояния UI по ответу:**
  - `status: "loaded"` (equipment не пуст) → отобразить перечень оборудования с типами и адресами; показать дату актуальности (`data_actual_at`) маленьким текстом; каждая единица кликабельна / доступна для скопирования информации.
  - `status: "no_data"` (equipment пуст, но без ошибки) → показать явное сообщение «На объекте нет привязанного оборудования»; дата актуальности видна.
  - `status: "error"` → показать сообщение об ошибке: «Не удалось загрузить сведения об оборудовании. Попробуйте позже.»; секция оборудования либо скрывается, либо отображается как недоступная.
  - Состояние загрузки (пока запрос идёт) → показать спиннер или placeholder.
  - Четыре состояния UI остаются **отдельными** и не сливаются.
- **Авторизация:** Видят роли Инженер и Диспетчер. Оператор не видит раздел оборудования.
  - Проверка выполняется на бэке перед возвратом данных: если роль Оператор, вернуть HTTP 403 или пустой результат с признаком недоступности.
  - Выбор механизма (403 vs. пустой результат) — по существующему паттерну Арсенала (уточнить при интеграции).
- **Происхождение:** 🟢 новое взаимодействие.
- **Трассировка:** FR-3 (отображение оборудования в карточке объекта).

### Каталог ошибок (сводно)

| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 404 | `{"error": "Security object not found"}` | Объект охраны не существует | Ошибка: «Объект не найден» |
| 401 | `{"error": "Unauthorized"}` | Нет токена или токен истёк | Перенаправить на авторизацию |
| 403 | `{"error": "Forbidden"}` или пустой результат с флагом | Роль Оператор или другие ограничения доступа | Раздел оборудования скрыт; status: "error" |
| 500 | `{"error": "Internal server error"}` | Ошибка на сервере (включая недоступность привязок) | status: "error"; сообщение: «Не удалось загрузить»; спиннер → сообщение об ошибке |

## 2.5. Этапы работ и порядок сборки

### ШАГ 1 — анализ логики

Выделяю три логически независимых куска:
1. **Приём и идемпотентное сохранение** — слушание потока, сохранение оборудования в таблицу Арсенала с проверкой дублей по внешнему ID.
2. **Регулярное сопоставление** — фоновый процесс (крон ночью), сравнение адресов, создание/обновление связей в таблице привязок.
3. **API отдачи и фронтовая карточка** — новый эндпоинт на бэке, возврат привязанного оборудования; фронт запрашивает при открытии карточки.

Этап 1 и 2 не зависят от 3 логически, но 3 ждёт результатов 1 и 2. Выкат: 1 → 2 → 3.

### ШАГ 2 — таблица этапов

| # | Этап | Вход (шов) | Выход (шов) | Проверка в одиночку |
|---|------|-----------|-------------|---------------------|
| 01 | Приём потока и идемпотентное сохранение оборудования | — (запуск коннектора) | Таблица `equipment` (сущность Оборудование) | Дано: сообщение с external_equipment_id, Когда: проверяется наличие в `equipment` Тогда: либо вставляется (первый раз), либо обновляется (повторная доставка). Пример: приходит дважды одно и то же сообщение → в таблице одна запись с обновлённым timestamp. |
| 02 | Регулярный пересчёт привязок по нормализованному адресу | Таблица `equipment` и существующая таблица `security_objects` | Таблица `equipment_binding` (сущность Привязка); поле `binding_recalc_at` обновляется в ответе INT-2 | Дано: оборудование и объект охраны с совпадающим адресом (после нормализации), Когда: крон запустит пересчёт, Тогда: создаётся связь в `equipment_binding`; при ноле или нескольких совпадениях оборудование остаётся без привязки. Проверка: ровно одно совпадение → в таблице одна запись, указывающая на это оборудование и этот объект. |
| 03 | API отдачи оборудования и фронтовая секция | Таблица `equipment_binding`; INT-2 запрос | Ответ INT-2 с массивом equipment и статусом | Дано: запрос GET /api/v1/security-objects/{id}/equipment от инженера, когда таблица привязок заполнена, Тогда: возвращается список привязанного оборудования. Проверка: инженер видит то оборудование, которое было привязано на этапе 02; пустой список → status "no_data"; ошибка доступа → status "error". Фронт получает ответ и отображает четыре состояния (loaded / no_data / error / загрузка). |

> **Разработка:** Этапы 01 и 02 логически независимы; могут разрабатываться параллельно (разные люди/потоки). Этап 03 зависит от выхода 01 и 02 и может начинаться одновременно (если контракты таблиц ясны), но тестирование её завершается после 01/02.
>
> **Выкат:** 01 → 02 → 03 (в порядке).

## 3. Данные и хранение

### 3.1. Новые сущности

#### Сущность «Оборудование» (Equipment)

Хранится в Арсенале; ведённый источник — внешняя система учёта через поток.

| Поле | Тип | Обязательность | Семантика |
|------|-----|---|----------|
| `internal_equipment_id` | UUID или string | Обязательно, первичный ключ | Ключ в Арсенале (генерируется при первой вставке). |
| `external_equipment_id` | string | Обязательно, уникальное | Идентификатор из системы учёта. **Ключ идемпотентности**: повторное сообщение с тем же ID не создаёт дубль. |
| `equipment_type` | string | Обязательно | Тип оборудования (напр. "Датчик движения"). |
| `address_original` | string | Обязательно | Адрес из системы учёта, в свободной форме. |
| `address_normalized` | string | Обязательно | Адрес после нормализации (удаление дублей пробелов, преобразование в нижний регистр, стандартизация сокращений). Заполняется при сохранении либо при регулярном пересчёте. Алгоритм нормализации — уточнить по примерам адресов и наличию внешнего сервиса нормализации. |
| `received_at` | ISO 8601 datetime | Обязательно | Момент первого приёма сообщения в Арсенал. |
| `updated_at` | ISO 8601 datetime | Обязательно | Момент последнего обновления сведений из системы учёта (берётся из `timestamp` входящего сообщения). |

**Индексы:** PRIMARY KEY(`internal_equipment_id`), UNIQUE(`external_equipment_id`), INDEX(`address_normalized`) для ускорения сопоставления.

#### Сущность «Привязка» (EquipmentBinding)

Результат сопоставления оборудования с объектом охраны. Создаётся и обновляется только регулярным пересчётом.

| Поле | Тип | Обязательность | Семантика |
|------|-----|---|----------|
| `binding_id` | UUID | Обязательно, первичный ключ | Ключ привязки в Арсенале. |
| `equipment_id` | UUID (внешний ключ на `equipment.internal_equipment_id`) | Обязательно | Единица оборудования. |
| `security_object_id` | UUID или число (внешний ключ на существующую таблицу объектов охраны) | Обязательно | Объект охраны. |
| `matched_at` | ISO 8601 datetime | Обязательно | Момент, когда привязка была создана / обновлена. |
| `recalc_timestamp` | ISO 8601 datetime | Обязательно | Момент последнего пересчёта (общий для всех привязок в одном прогоне). Используется в ответе INT-2 как `data_actual_at`. |

**Индексы:** PRIMARY KEY(`binding_id`), UNIQUE(`equipment_id`, `security_object_id`), INDEX(`security_object_id`) для быстрого поиска оборудования по объекту, INDEX(`recalc_timestamp`) для отслеживания актуальности.

### 3.2. Миграции (концептуально)

- Создать таблицу `equipment` с полями выше.
- Создать таблицу `equipment_binding` с полями выше и внешними ключами.
- Добавить индексы по полям выше.
- Точный DDL и tool-специфичный синтаксис (Liquibase / Flyway / иное) — по реальной схеме и инструментам Арсенала (уточнить при разработке).

### 3.3. Изменения существующих сущностей

🟡 **к валидации**: Запросить у аналитика при интеграции — нужно ли добавлять поле отметки актуальности в существующую таблицу `security_objects` или этот момент берётся из таблицы привязок (как в текущем дизайне). Сейчас предполагаем, что `data_actual_at` хранится в `equipment_binding` и подтягивается при запросе по объекту.

## 4. Фронтовые состояния и UI

### 4.1. Новая секция в карточке объекта охраны — раздел «Оборудование»

**Где:** На карточке объекта охраны, новая секция ниже существующих полей (положение уточняется с дизайном).

**Заголовок:** «Установленное оборудование» или «Оборудование» (выбирается в процессе разработки).

**Содержимое:** Зависит от состояния загрузки и ответа сервера (4 отдельных состояния, см. ниже).

### 4.2. Четыре состояния отображения

#### Состояние 1: `status: "loaded"` — Оборудование загружено

Отображается перечень с элементами:
- Для каждой единицы: **Тип** (`equipment_type`) и **Адрес** (`address_original`).
- Дополнительно (маленький текст или иконка): Адрес нормализованный (если отличается от исходного, для отладки интеграции) или скрыт.
- В подвале секции: дата актуальности данных (`data_actual_at`) в формате «Данные актуальны на [дата]» или символом ℹ.
- Визуальный статус: нейтральный, без икон ошибок.

#### Состояние 2: `status: "no_data"` — Оборудование не привязано

- Сообщение: «На объекте нет привязанного оборудования» (или уточнённое по UX).
- Дата актуальности: видна, как в Состоянии 1.
- Пустой список НЕ сливается с ошибкой — это нормальный случай.

#### Состояние 3: `status: "error"` — Ошибка загрузки

- Сообщение: «Не удалось загрузить сведения об оборудовании. Попробуйте позже.» (либо специализированное для разных кодов ошибок: 403 → «У вас нет доступа к этому разделу», 500 → «Ошибка сервера»).
- Кнопка «Обновить» (retry) либо автоматический ретрай через N секунд (уточняется с дизайном).
- Дата актуальности: не показывается (она = null при ошибке).

#### Состояние 4: Загрузка (in-flight)

- Спиннер, placeholder (скелет списка) или простое сообщение «Загрузка…».
- Отображается только во время HTTP-запроса.

### 4.3. Логика переходов между состояниями

```
[начало] → Загрузка 
  ↓
  Получен ответ с status: "loaded" → Оборудование (Состояние 1)
  ↓
  Нет → status: "no_data" → Нет данных (Состояние 2)
  ↓
  Ошибка → status: "error" → Сообщение об ошибке (Состояние 3)
  ↓
Пользователь кликает «Обновить» → Загрузка (повтор)
```

### 4.4. Дизайн (примечание)

- Стиль и расположение — по существующему дизайну Арсенала.
- Макеты и иконки — уточняются в процессе разработки.
- Текст — согласован с UX/Product (пока используются примеры выше).

## 5. Нефункциональные требования

### 5.1. Производительность и синхронность

- **Приём потока:** Асинхронный, потребитель слушает события по мере их поступления от внешней системы. Обработка одного сообщения — в рамках одной транзакции (запись в `equipment`).
- **Пересчёт привязок:** Фоновый процесс, запускается по расписанию ночью (точное время уточняется). Частота: один раз в сутки (если требуется более частый пересчёт, это изменение дизайна, вопрос к аналитику).
- **Запрос оборудования (INT-2):** Синхронный, вызывается фронтом при открытии карточки. Ожидаемое время ответа: < 1 с (прямой запрос к таблице привязок по индексу). Если время превышает, фронт показывает спиннер.
- **Кэширование:** Нет явного кэша на стороне API; кэширование на уровне браузера/клиента (стандартные HTTP-заголовки ETag / Cache-Control). Рекомендуется Cache-Control: max-age=300 для INT-2 (5 минут).
- **Объём данных:** На один объект охраны может быть десятки единиц оборудования (уточнить верхний лимит). Ответ INT-2 содержит только привязанное оборудование, лишние не передаются.

### 5.2. Авторизация и доступ

- **INT-2 (фронтовой запрос):** Проверка роли перед возвратом данных. Инженер и Диспетчер видят, Оператор — нет. Механизм (возврат 403 или пустой результат) уточняется по существующему паттерну Арсенала.
- **Приём потока (INT-1):** Проверка учётных данных внешней системы (сервис-сервис, подтверждается при интеграции).

### 5.3. Надёжность и идемпотентность

- **Приём потока:** Каждое сообщение обрабатывается идемпотентно по `external_equipment_id`. Повторная доставка одного и того же сообщения не создаёт дубль и не вызывает ошибку; запись обновляется.
- **Пересчёт привязок:** Не критичен, если один прогон пропустится (например, при ночной перезагрузке). При запуске пересчёта удаляются все старые привязки для переиндексации (либо обновляются, по выбору; механизм — при разработке). Результат пересчёта атомарен (либо выполнено полностью, либо откачено).
- **Обработка ошибок:** Сообщение с ошибкой (нарушение контракта, недостаточные данные) логируется и пропускается; поток не падает.

### 5.4. Мониторинг и логирование

- **INT-1 (приём потока):** Логировать каждое сообщение (на уровне DEBUG или INFO); логировать дубли и ошибки обработки (WARNING / ERROR).
- **INT-2 (запрос оборудования):** Логировать запросы и ошибки (ошибки БД, недоступность, 403 и т.п.).
- **Пересчёт привязок:** Логировать начало, конец, количество обработанных единиц, ошибки. Алерты, если пересчёт не выполнился долгое время.

## 6. Порядок выката и совместимость

### 6.1. Последовательность деплоя

1. **Фаза 1 — Приём и хранение (этап 01):**
   - Развёртывается таблица `equipment`, коннектор слушания потока.
   - Фронт и существующие API остаются без изменений.
   - **Обратная совместимость:** полная (добавляется новая таблица, не трогаются существующие).
   - **Проверка:** В `equipment` появляются новые записи по мере поступления сообщений от внешней системы.

2. **Фаза 2 — Регулярный пересчёт (этап 02):**
   - Развёртывается таблица `equipment_binding` и крон-задача пересчёта.
   - Фронт и INT-2 еще не существует.
   - **Обратная совместимость:** полная (новая таблица, крон-задача в фоне).
   - **Проверка:** После первого прогона крона в `equipment_binding` появляются связи между оборудованием и объектами охраны.

3. **Фаза 3 — API отдачи и фронтовая секция (этап 03):**
   - На бэке развёртывается эндпоинт INT-2 (`GET /api/v1/security-objects/{id}/equipment`).
   - На фронте добавляется новая секция карточки.
   - **Обратная совместимость:** Карточка открывается корректно и для старых, и для новых объектов. Объекты без привязанного оборудования показывают `status: "no_data"`.
   - **Проверка:** Инженер открывает карточку, видит либо перечень оборудования, либо сообщение «Нет данных» (оба — нормальные).

### 6.2. Фиче-флаги и преднастройка

- **Фиче-флаг (опционально):** Для постепенного раката новой секции можно использовать флаг, позволяющий показывать раздел оборудования определённому проценту пользователей. Но так как функция критична (часть главной фичи задачи), рекомендуется полный раскат на фазе 3.
- **Преднастройка ролей:** Роли Инженер и Диспетчер должны иметь доступ к разделу оборудования. Это может быть заложено в ролевой модели Арсенала до раката или конфигурировано отдельно. Проверить: какие роли уже существуют и как в них включается новая функция.

### 6.3. Откат

- Если на фазе 3 обнаружена ошибка в фронте или INT-2, откат: отключить новую секцию (фиче-флаг OFF или удалить код), оставить таблицы `equipment` и `equipment_binding` в БД (откат БД не требуется).
- Если на фазе 2 крон не работает, откат: отключить крон, оставить коннектор приёма (фаза 1 остаётся).
- Если на фазе 1 коннектор неработает, откат: отключить коннектор, оставить таблицу (структура уже есть для будущих попыток).
