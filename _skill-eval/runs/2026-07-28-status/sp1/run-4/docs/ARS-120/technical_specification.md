## 1. Обзор изменения
### 1.1. Тип и стороны
Fullstack (фронт + бэк «Арсенала»). Система начинает принимать сведения об оборудовании из внешней системы учёта, хранить их у себя, сопоставлять с объектами охраны по адресу и показывать в карточке объекта. Взаимодействия: приём потока оборудования от внешней системы (событие), запрос привязанного оборудования по идентификатору объекта (HTTP).

### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| Арсенал (фронт) | Отображение привязанного оборудования в карточке объекта охраны | TBD | 🟢 новое |
| Арсенал (бэк) | Приём, хранение оборудования; сопоставление с объектами; выдача привязанного оборудования по запросу фронта | TBD | 🟢 новое (на существующем сервисе) |
| Внешняя система учёта оборудования | Источник сведений об оборудовании | TBD | 🟡 подтверждено аналитиком (уже публикует поток) |

### 1.3. Связь с бизнес-требованиями
Реализует цель, чтобы инженер видел в карточке объекта охраны перечень установленного оборудования и выезжал с нужным комплектом, не обращаясь ко второй системе. Снижает повторные выезды и потери времени на ручную сверку.

## 2. Взаимодействия (ядро)

### INT-1. Приём потока оборудования от внешней системы — 🟢
- **Граница/направление:** Внешняя система учёта оборудования → бэк Арсенала (событие)
- **Триггер:** Внешняя система опубликовала сообщение об оборудовании в поток
- **Контракт (сообщение):** 
  - `equipment_id_external` (строка, обязателен): уникальный идентификатор единицы оборудования во внешней системе — служит ключом идемпотентности
  - `type` (строка, обязателен): тип оборудования (напр. «датчик движения», «камера», «сирена»)
  - `address` (строка, обязателен): адрес установки в свободной форме (как заполнено во внешней системе)
  - `timestamp` (ISO 8601, обязателен): отметка времени создания/обновления записи во внешней системе
- **Пример сообщения:**
  ```json
  {
    "equipment_id_external": "EQ-2026-07-28-00142",
    "type": "датчик движения",
    "address": "ул. Ленина, 15, офис 302",
    "timestamp": "2026-07-28T10:30:00Z"
  }
  ```
- **Обработка:**
  - Если сообщение с тем же `equipment_id_external` уже обработано ранее, обновить существующую запись (не создавать дубль)
  - Если адрес отличается от сохранённого, обновить `address` и установить флаг, что требуется пересчёт сопоставления
- **Ошибки:** 
  - Сообщение отклонено и залогировано, если отсутствуют обязательные поля — повторная доставка гарантирована внешней системой
  - Если сообщение невозможно разобрать (некорректный JSON, неправильные типы), оно отклоняется, ошибка логируется
- **Происхождение:** 🟢 новое (контракт полностью спроектирован)
- **Трассировка:** FR-1

### INT-2. Получение привязанного оборудования по объекту охраны — 🟢
- **Граница/направление:** Фронт Арсенала → бэк Арсенала (HTTP GET)
- **Триггер:** Инженер / диспетчер открыл карточку объекта охраны
- **Контракт (запрос):** 
  - Метод: `GET /api/security-objects/{objectId}/equipment`
  - Параметр пути: `objectId` (строка/UUID, обязателен) — идентификатор объекта охраны в Арсенале
- **Контракт (ответ):**
  - `equipment_list` (массив объектов): список оборудования, привязанного к объекту; пусто, если привязано нечего
    - Для каждого элемента:
      - `equipment_id` (строка): внутренний id записи об оборудовании в Арсенале
      - `equipment_id_external` (строка): id во внешней системе (для отсылки при необходимости)
      - `type` (строка): тип оборудования
      - `address_original` (строка): адрес в исходном виде из внешней системы
  - `data_snapshot_timestamp` (ISO 8601): отметка времени, на которую актуальны сведения об оборудовании (конец последнего пересчёта сопоставления)
  - `http_status` (число): 200 при успехе, 404 если объект не найден, 403 если доступ запрещён
- **Пример запроса:** `GET /api/security-objects/obj-12345/equipment`
- **Пример ответа (успех):**
  ```json
  {
    "equipment_list": [
      {
        "equipment_id": "1",
        "equipment_id_external": "EQ-2026-07-28-00142",
        "type": "датчик движения",
        "address_original": "ул. Ленина, 15, офис 302"
      },
      {
        "equipment_id": "2",
        "equipment_id_external": "EQ-2026-07-28-00143",
        "type": "камера",
        "address_original": "ул. Ленина, 15, коридор"
      }
    ],
    "data_snapshot_timestamp": "2026-07-28T03:00:00Z"
  }
  ```
- **Пример ответа (пусто):**
  ```json
  {
    "equipment_list": [],
    "data_snapshot_timestamp": "2026-07-28T03:00:00Z"
  }
  ```
- **Состояния UI по ответу:**
  - **Загрузка:** запрос в процессе (сервер обрабатывает)
  - **Перечень:** status 200 и `equipment_list` не пусто → вывести список оборудования с типами и адресами
  - **«Нет данных»:** status 200 и `equipment_list` пусто → явное сообщение «Оборудование не привязано» (не пусто, не удалить с экрана)
  - **Ошибка недоступности:** status 5xx → сообщение об ошибке сервера; повторный запрос можно предложить
  - **Доступ запрещён:** status 403 → ничего не выводить (см. авторизация)
  - **Объект не найден:** status 404 → это внутренняя ошибка (страница открыта, объект должен быть), залогировать и показать техническую ошибку
- **Авторизация:**
  - Доступ разрешён: роли **Инженер** и **Диспетчер**
  - Доступ запрещён: роль **Оператор** (вернуть status 403, Forbidden)
  - Проверка: в бэке на входе, перед выдачей данных
- **Происхождение:** 🟢 новое (контракт полностью спроектирован)
- **Трассировка:** FR-3

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 200 | (успех, пусто или с данными) | INT-2: запрос выполнен | Перечень (если data) / «Нет данных» (если пусто) |
| 400 | `{ "error": "invalid_object_id", "message": "Некорректный идентификатор объекта" }` | INT-2: objectId не соответствует формату (не UUID или некорректен) | Техническая ошибка (клиент) |
| 403 | `{ "error": "forbidden", "message": "Нет доступа к разделу оборудования" }` | INT-2: роль Оператор / недостаточные права | Раздел не отображается (ничего не показывать) |
| 404 | `{ "error": "object_not_found", "message": "Объект охраны не найден" }` | INT-2: объект с таким id не существует в системе | Техническая ошибка |
| 500 | `{ "error": "internal_error", "message": "Внутренняя ошибка сервера" }` | INT-2: неожиданная ошибка при обработке | Ошибка сервера, возможно повторить |
| (обработка событий INT-1) | логирование и отклонение | Некорректное сообщение, отсутствуют обязательные поля | (бэк-сторона; для анализа операций) |

## 3. Данные и хранение

### 3.1. Новые сущности

**Сущность: Оборудование**
- **Назначение:** Хранение сведений об оборудовании, поступивших из внешней системы учёта
- **Поля:**
  - `equipment_id` (UUID / автоинкремент, первичный ключ): внутренний идентификатор записи в Арсенале
  - `equipment_id_external` (строка, уникальный индекс): идентификатор во внешней системе (ключ идемпотентности)
  - `type` (строка): тип оборудования
  - `address_original` (строка): адрес в исходном виде из внешней системы
  - `address_normalized` (строка): адрес после нормализации (для сопоставления; может быть NULL до первого пересчёта)
  - `updated_at` (timestamp): время последнего обновления этой записи (из `timestamp` события или время приёма события)
  - `created_at` (timestamp): время создания записи в Арсенале
- **Индексы:** 
  - `UNIQUE(equipment_id_external)` — для идемпотентности при приёме событий
  - `INDEX(address_normalized)` — для поиска при пересчёте сопоставления
  - `INDEX(updated_at)` — для отслеживания свежести
- **Происхождение:** 🟢 новое
- **Конценпция миграции:** добавить таблицу (DDL синтаксис определяется владеющим сервисом)

**Сущность: Привязка**
- **Назначение:** Связь между оборудованием и объектом охраны, результат пересчёта сопоставления
- **Поля:**
  - `binding_id` (UUID / автоинкремент, первичный ключ): идентификатор привязки
  - `equipment_id` (UUID, внешний ключ к Оборудование.equipment_id): на какое оборудование указывает
  - `security_object_id` (UUID, внешний ключ к таблице объектов охраны): к какому объекту охраны привязано
  - `matched_at` (timestamp): время, когда сопоставление было установлено (во время пересчёта)
  - `match_confidence` (опционально): если логика сопоставления предусматривает оценку, может содержать степень уверенности (например, 1.0 для однозначного совпадения)
- **Индексы:**
  - `UNIQUE(equipment_id, security_object_id)` — одно оборудование не может быть привязано к одному объекту дважды
  - `INDEX(security_object_id)` — для быстрого поиска оборудования по объекту (используется в INT-2)
  - `INDEX(matched_at)` — для очистки/истории
- **Происхождение:** 🟢 новое
- **Концепция миграции:** добавить таблицу (DDL синтаксис определяется владеющим сервисом)

### 3.2. Логика сопоставления (алгоритм, не DDL)
- **Триггер:** регулярный пересчёт, раз в сутки ночью (время: ~3:00 UTC, настраивается)
- **Процесс:**
  1. Для каждого оборудования в таблице Оборудование:
     - Нормализовать адрес (`address_original` → `address_normalized`): привести к единому формату (удалить лишние пробелы, сокращения, привести порядок слов)
  2. Для каждого оборудования:
     - Ищем объекты охраны в Арсенале, у которых адрес совпадает с `address_normalized` оборудования (точное совпадение после нормализации обеих сторон)
     - Ровно одно совпадение → создаём запись в таблице Привязка
     - Ноль совпадений → оборудование остаётся непривязанным (может быть выведено в отдельный отчёт для ручного разбора, но это вне scope текущей спеки)
     - Несколько совпадений → оборудование остаётся непривязанным, логируется, может быть выведено в отчёт (вне scope)
  3. После пересчёта удаляются старые привязки (если оборудование удалили или адрес изменился): выполняется очистка привязок, у которых нет соответствия в новом наборе
- **Результат:** таблица Привязка содержит актуальный снимок связей (на момент `matched_at`)
- **Происхождение:** 🟢 новое (спроектировано в этом документе)

### 3.3. Нет новых полей в существующих сущностях
Объекты охраны уже содержат адрес; новых полей в них не добавляется.

## 4. Интеграция с фронтом

### 4.1. Карточка объекта охраны — раздел оборудования
- **Вид раздела:** новый блок на карточке объекта охраны в Арсенале
- **Шаг 1. Запрос данных:** при открытии карточки или при необходимости обновления фронт выполняет `GET /api/security-objects/{objectId}/equipment` (INT-2)
- **Шаг 2. Отображение результата:**
  - Во время запроса: показать спиннер/индикатор загрузки в области раздела
  - После получения 200 с `equipment_list`:
    - Если список не пусто: вывести таблицу или список с полями type и address_original для каждого элемента
    - Если список пусто: показать явное сообщение «Оборудование не привязано» (не исчезать, не оставлять пусто)
  - При 403 (Оператор): раздел не отображается вообще (ни спиннера, ни текста, полностью скрыт)
  - При 5xx или 404 (ошибки сервера): показать сообщение об ошибке с предложением повторить попытку
- **Дата и время актуальности:** под блоком оборудования показать строку «Данные актуальны на [data_snapshot_timestamp]» (для информирования инженера, на какой момент это данные)
- **Происхождение:** 🟢 новое (UI-поведение спроектировано)

### 4.2. Ролевой контроль
- Роли **Инженер** и **Диспетчер**: раздел оборудования видим и содержит данные
- Роль **Оператор**: раздел оборудования скрыт полностью, INT-2 вернёт 403

## 5. Нефункциональные требования

### 5.1. Синхронность и производительность
- **Приём оборудования (INT-1):** асинхронный, потоковый (событие из внешней системы). Сообщения обрабатываются по мере поступления, может быть задержка в секунды-минуты — это приемлемо.
- **Сопоставление:** синхронный, плановый, раз в сутки ночью (~3:00 UTC). Фронт не блокируется. Результат попадает в таблицу Привязка и становится доступен INT-2 сразу после завершения пересчёта.
- **Выдача данных (INT-2):** синхронный, HTTP. Ожидаемое время ответа < 1 сек (стандартный запрос к таблице Привязка по индексу).
- **Кэширование:** не применяется на этом уровне (фронт может кэшировать результат INT-2 локально, но это не требуется спекой).
- **Ожидаемая нагрузка:** раз в сутки пересчёт ~N оборудования (где N — общее количество единиц во внешней системе, порядок сотен–тысяч); INT-2 вызывается при открытии карточки (стандартная нагрузка фронта на бэк).

### 5.2. Толерантность к сбоям
- **Повторная доставка события INT-1:** гарантирована внешней системой (обычно с гарантией at-least-once); бэк должен обеспечить идемпотентность через `UNIQUE(equipment_id_external)` — повторная доставка обновит существующую запись, не создаст дубль.
- **Сбой пересчёта сопоставления:** если пересчёт упал, старые привязки остаются в таблице; пересчёт будет переоткрыт на следующий цикл (~24ч). Это приемлемо, так как инженер увидит застарелые данные, но не пустоту.
- **Недоступность внешней системы:** не влияет на INT-2 (фронт получит то, что уже в Привязке); приём INT-1 прекратится до восстановления (внешняя система не пошлёт, или будет повторять).

### 5.3. Авторизация (детально)
- **INT-1:** приём потока от внешней системы — проверка выполняется на уровне интеграции (например, API-ключ внешней системы, TLS-сертификат, IP белый список). Текущая спека не требует ролевого контроля на приёме; авторизация — это забота интеграционного канала.
- **INT-2:** проверка ролей перед выдачей данных — роль читается из контекста запроса (авторизованный пользователь, его роль); если роль != Инженер и != Диспетчер → вернуть 403. Если роль Оператор, раздел скрыт на фронте, INT-2 вернёт 403 (defence in depth).

## 6. Порядок выката и совместимость

### 6.1. Порядок развёртывания этапов
1. **Этап 1: Приём и хранение оборудования.** Развернуть на бэке схему таблицы Оборудование, логику приёма INT-1 (обработка событий, идемпотентность). Внешняя система начинает отправлять события. На этом этапе оборудование пусто в Арсенале (ждёт, пока внешняя система пошлёт данные).

2. **Этап 2: Сопоставление и хранение привязок.** Развернуть на бэке таблицу Привязка и запустить периодический пересчёт (задача раз в сутки). После первого запуска пересчёта (конец первых суток) будут установлены привязки.

3. **Этап 3: Выдача оборудования по запросу (бэк).** Развернуть логику INT-2 на бэке — эндпоинт `/api/security-objects/{objectId}/equipment`, авторизация по ролям, возврат привязанного оборудования и timestamp.

4. **Этап 4: Отображение в карточке (фронт).** Развернуть на фронте раздел оборудования, вызов INT-2 при открытии карточки, отображение результата с учётом ролей.

### 6.2. Обратная совместимость
- **Этап 1–3:** бэк только добавляет новые таблицы и эндпоинт, не трогает существующие объекты охраны. Совместимость полная.
- **Этап 4:** фронт добавляет новый раздел на карточке. Старые версии фронта не будут его вызывать (не совместимо в обратном направлении, но это нормально — обновление фронта = обновление клиента). Совместимость: не требуется (фронт всегда свежий).

### 6.3. Предварительная настройка (перед релизом)
- Убедиться, что внешняя система учёта правильно настроена на отправку событий (канал доставки, аутентификация, адрес эндпоинта бэка).
- Если требуется регулярный пересчёт в другое время, чем 3:00 UTC, настроить в конфиге бэка до развёртывания (параметр типа `equipment_sync_time`).
- Роли Инженер, Диспетчер, Оператор уже существуют в системе безопасности Арсенала; никакой дополнительной настройки ролей не требуется.

## 8. Дополнительно

### 8.1. Вопросы для ручной разработки
- **Логика нормализации адреса:** точный алгоритм (какие сокращения, порядок слов, кодировка символов) будет согласован с владельцем таблицы объектов охраны и системой учёта во время разработки. Спека предполагает функцию нормализации `normalize_address(address_original) → address_normalized`, реализацию которой определяет владелец бэка.
- **Формат сообщения INT-1:** точный формат (JSON-структура, тип данных каждого поля, возможные enum для type и т.п.) подлежит уточнению с владельцем внешней системы учёта.

### 8.2. Не входит в scope (из БТ)
- Ручное редактирование привязки инженером (не предусмотрено).
- Заведение и правка оборудования в Арсенале (источник остаётся внешним).
- История изменений состава оборудования (логирование событий — опционально, не требуется спекой).
