## 2. Взаимодействия (ядро)

### INT-1. Приём потока сведений об оборудовании от внешней системы учёта — 🟢 новое
- **Граница/направление:** Внешняя система учёта → бэк Арсенала (событие/сообщение в топике)
- **Триггер:** Внешняя система публикует изменение (создание, изменение, удаление или переполучение) единицы оборудования
- **Контракт (сообщение/событие):** 
  - `equipment_id` (строка, обязательное) — идентификатор оборудования во внешней системе (ключ идемпотентности)
  - `type` (строка, обязательное) — тип оборудования (например, «датчик движения», «видеокамера»)
  - `address` (строка, обязательное) — адрес установки в свободной форме (как пришёл из внешней системы)
  - `timestamp` (ISO 8601 datetime, обязательное) — время события во внешней системе
- **Пример сообщения:**
  ```json
  {
    "equipment_id": "EXT-42891",
    "type": "видеокамера",
    "address": "ул. Пушкина, д. 10, кв. 5",
    "timestamp": "2026-07-28T14:23:45Z"
  }
  ```
- **Идемпотентность:** Повторное получение сообщения с тем же `equipment_id` не должно создавать дубль в Арсенале. Проверка ведётся по идентификатору `equipment_id`; повторное сообщение обновляет существующую запись (или игнорируется, если данные не изменились).
- **Обработка:** Сообщение принимается асинхронно, по мере поступления из топика. Запись сохраняется в сущности «Оборудование» бэка.
- **Происхождение:** 🟢 новое взаимодействие (проектировано в этом документе)
- **Точный формат и имя топика:** 🟡 к валидации (аналитик передал список полей, но точный формат сообщения во внешней системе не помнит; уточнить при интеграции с её владельцами)
- **Трассировка:** FR-1

### INT-2. Получить оборудование, привязанное к объекту охраны — 🟢 новое
- **Граница/направление:** Фронт Арсенала → бэк Арсенала (HTTP/JSON)
- **Триггер:** Инженер или диспетчер открывает карточку объекта охраны
- **Контракт (запрос):**
  - Метод: `GET /objects/{objectId}/equipment`
  - Параметры пути:
    - `objectId` (строка, обязательное) — идентификатор объекта охраны в Арсенале
  - Заголовки авторизации: стандартные для Арсенала
- **Пример запроса:**
  ```
  GET /objects/OBJ-12345/equipment
  Authorization: Bearer <token>
  ```
- **Контракт (ответ):**
  - `equipment` (массив объектов, обязательное) — список привязанного оборудования; может быть пуст
    - `id` (строка) — идентификатор оборудования в Арсенале (первичный ключ)
    - `external_id` (строка) — идентификатор оборудования во внешней системе (`equipment_id`)
    - `type` (строка) — тип оборудования
    - `address_original` (строка) — адрес в исходной форме (как пришёл из внешней системы)
    - `address_normalized` (строка) — нормализованный адрес (используется для сопоставления)
  - `last_sync` (ISO 8601 datetime, обязательное) — время последнего пересчёта привязок (отметка актуальности данных)
  - `status` (строка, обязательное) — статус заполнения карточки; значения:
    - `loaded` — данные загружены
    - `no_data` — нет привязанного оборудования (пустой список — это нормально, ошибка отсутствует)
    - `error` — ошибка при получении данных
- **Пример ответа (успех, с оборудованием):**
  ```json
  {
    "equipment": [
      {
        "id": "ARS-EQ-001",
        "external_id": "EXT-42891",
        "type": "видеокамера",
        "address_original": "ул. Пушкина, д. 10, кв. 5",
        "address_normalized": "ул. пушкина, д. 10, кв. 5"
      },
      {
        "id": "ARS-EQ-002",
        "external_id": "EXT-42892",
        "type": "датчик движения",
        "address_original": "Пушкина ул., 10/5",
        "address_normalized": "ул. пушкина, д. 10, кв. 5"
      }
    ],
    "last_sync": "2026-07-28T03:00:00Z",
    "status": "loaded"
  }
  ```
- **Пример ответа (успех, без оборудования):**
  ```json
  {
    "equipment": [],
    "last_sync": "2026-07-28T03:00:00Z",
    "status": "no_data"
  }
  ```
- **Пример ответа (ошибка):**
  ```json
  {
    "equipment": [],
    "last_sync": "2026-07-28T03:00:00Z",
    "status": "error",
    "error_code": "BACKEND_UNAVAILABLE",
    "error_message": "Не удалось получить данные: сервис недоступен"
  }
  ```
- **Ошибки:** см. «Каталог ошибок»
- **Состояния UI по ответу:**
  - `status: "loaded"` + `equipment` не пуст → отображение перечня с деталями
  - `status: "loaded"` + `equipment` пуст → явное "Нет данных"
  - `status: "no_data"` → явное "Нет данных"
  - `status: "error"` → отображение ошибки с пояснением
  - Во время загрузки (запрос в полёте) → состояние "загрузка" (спиннер)
- **Авторизация:** Видят роли «Инженер» и «Диспетчер». Роль «Оператор» не имеет доступа; при попытке вызова эндпоинта возвращается 403 Forbidden. Проверка ведётся на стороне бэка по роли пользователя в сессии.
- **Происхождение:** 🟢 новое взаимодействие (проектировано в этом документе)
- **Трассировка:** FR-3

## 2.5. Этапы работ и порядок сборки

Работа разрезана на **четыре этапа** с самостоятельной логикой каждого. Швы между этапами — контракты INT-1 и INT-2 (из §2) и таблицы Equipment / Привязка (из §3). Разработка этапов может вестись параллельно; выкат — по порядку (см. §6).

| # | Этап | Вход (шов) | Выход (шов) | Проверка в одиночку |
|---|------|-----------|-------------|---------------------|
| 01 | Приём и хранение оборудования | INT-1 (топик внешней системы) | Таблица Equipment с нормализованными адресами | Отправить сообщение INT-1 → проверить запись в Equipment; повторное сообщение с тем же equipment_id → проверить идемпотентность (дубль не создан) |
| 02 | Пересчёт сопоставления | Таблица Equipment | Таблица Привязка (привязки equipment_id → object_id) | Запустить пересчёт → проверить привязки в Привязка; оборудование с однозначным совпадением адреса → привязано; несколько совпадений или нет → непривязанное |
| 03 | API отдачи оборудования | INT-2 (запрос GET /objects/{objectId}/equipment) | Таблица Привязка (дочитывается) | Вызвать INT-2 по объекту с привязанным оборудованием → проверить ответ (статус, список, last_sync); роль Оператор → 403 |
| 04 | Фронтовой компонент | INT-2 (ответ) | Компонент отображения в карточке | Открыть карточку объекта → компонент вызывает INT-2; данные есть → отображается список; нет данных → "Нет данных"; ошибка → отображается ошибка и кнопка "Повторить" |

**Выкат: 01 → 02 → 03 → 04.** Порядок регулируется зависимостями (см. §6.1): Этап 1 создаёт таблицу Equipment, этап 2 заполняет Привязка (зависит от Equipment), этап 3 читает Привязка (зависит от этапа 2), этап 4 вызывает INT-2 (зависит от этапа 3).

## 3. Данные и хранение

### 3.1. Новые сущности

#### Сущность: Оборудование (Equipment)
🟢 Новая таблица/коллекция в бэке Арсенала.

Поля:
- `id` (PK, строка) — первичный ключ (UUID или последовательный, по выбору реализации)
- `external_id` (строка, unique) — идентификатор оборудования во внешней системе; **ключ идемпотентности** (повторное сообщение с тем же `external_id` не создаёт дубль)
- `type` (строка) — тип оборудования (например, «видеокамера», «датчик движения»)
- `address_original` (строка) — адрес в исходной форме (как пришёл из внешней системы)
- `address_normalized` (строка) — адрес после нормализации (используется для сопоставления); нормализация применяется в момент сохранения первичной записи
- `updated_at` (timestamp) — время последнего обновления записи в Арсенале

Индексы:
- `external_id` (unique) — для быстрого поиска и проверки идемпотентности
- `address_normalized` (non-unique) — для сопоставления по адресу

#### Сущность: Привязка (EquipmentMapping)
🟢 Новая таблица/коллекция в бэке Арсенала.

Поля:
- `id` (PK, строка) — первичный ключ
- `equipment_id` (FK на Equipment.id, строка) — ссылка на оборудование
- `object_id` (строка) — идентификатор объекта охраны в Арсенале
- `matched_at` (timestamp) — время создания привязки (результат пересчёта)
- `match_confidence` (строка, опционально) — уровень уверенности (например, «exact» для однозначного совпадения по адресу); может быть полезно для отладки и аналитики

Индексы:
- `object_id` (non-unique) — для быстрого получения оборудования по объекту (используется в INT-2)
- `equipment_id` (non-unique) — для обратного поиска

### 3.2. Логика сопоставления (нетривиальная бизнес-правила)

**Триггер:** Регулярный пересчёт один раз в сутки, ночью (во время минимальной нагрузки; точное время уточняется с DevOps). ⚠️ Требует уточнения: назвать конкретное время запуска и временную зону.

**Алгоритм сопоставления:**
1. Для каждого оборудования в таблице Equipment, у которого нет привязки в текущем пересчёте (обработка с чистого листа каждый цикл):
2. Возьми нормализованный адрес оборудования (`address_normalized`).
3. Найди все объекты охраны в Арсенале, адреса которых после нормализации **совпадают ровно с этим адресом**.
4. Если совпадений ровно одно:
   - Создай новую запись в Привязка (equipment_id → object_id).
   - Отметь в логе как успешное совпадение.
5. Если совпадений ноль или несколько:
   - Не создавай привязку (оборудование остаётся непривязанным).
   - Добавь оборудование в **отчёт для ручного разбора** (отдельный лог или экспорт).
   - Пометь причину (ноль или несколько совпадений).

**Нормализация адреса:** Применяется один раз, при сохранении оборудования из внешней системы (в момент приёма INT-1). Нормализация включает (конкретные правила уточнить с аналитиком при интеграции, если снизу нет регулярки):
- Приведение к нижнему регистру
- Удаление лишних пробелов
- Стандартизация сокращений («ул.» / «улица», «д.» / «дом», «кв.» / «квартира» и т.п.)
- Удаление дублей слов

Результат нормализации сохраняется в `address_normalized` и используется для всех сопоставлений.

**Переполучение оборудования:** Если оборудование с тем же `external_id` приходит повторно (после INT-1), то:
- В таблице Equipment обновляется запись (все поля перезаписываются).
- Привязка из предыдущего цикла удаляется или становится неактивной (пересчёт пересчитает с нуля).
- В следующем цикле пересчёта оборудование участвует заново.

### 3.3. Миграции (концептуально)
- Создать таблицу Equipment с полями и индексами (см. 3.1).
- Создать таблицу Привязка с полями и индексами (см. 3.1).
- Синхронизация: внешняя система может быть источником большого объёма оборудования; уточнить ожидаемый размер при проектировании (тысячи, миллионы записей) для выбора стратегии миграции и индексов.

## 4. Фронтовая часть

### 4.1. Компонент: Карточка оборудования в объекте охраны
🟢 Новый компонент в карточке объекта охраны.

Где отображается: В карточке объекта охраны, после основной информации (секция «Оборудование»).

**Содержимое и состояния:**
1. **Состояние «загрузка» (во время запроса INT-2):**
   - Спиннер или лоадер.
   - Надпись «Загрузка данных об оборудовании…»

2. **Состояние «с данными»** (INT-2 вернул `status: "loaded"` и `equipment` не пуст):
   - Заголовок: «Оборудование» (или «Установленное оборудование»)
   - Список оборудования в виде карточек, построчно:
     - **Название:** тип оборудования (из `type`)
     - **Адрес:** адрес_original (из поля `address_original`)
     - **Нормализованный адрес:** (из поля `address_normalized`, может быть скрыто по умолчанию или отображаться в серой текстуре для отладки — уточнить с UX)
   - Под списком: «Данные актуальны на [last_sync]» (форматировать дату читаемо, например «28 июля 14:23»)

3. **Состояние «нет данных»** (INT-2 вернул `status: "no_data"` или `status: "loaded"` с пустым `equipment`):
   - Текст: «Нет данных об оборудовании» или «Оборудование не привязано»
   - Под текстом: «Последняя синхронизация: [last_sync]»
   - Серая или нейтральная текстура (не красная, это не ошибка)

4. **Состояние «ошибка»** (INT-2 вернул `status: "error"`):
   - Текст (красный): ошибка (например, «Не удалось загрузить данные об оборудовании»)
   - Под текстом: код ошибки для отладки (например, «BACKEND_UNAVAILABLE»)
   - Кнопка: «Повторить» → повторный вызов INT-2

5. **Состояние «доступ запрещён»** (INT-2 вернул 403):
   - Раздел может быть скрыт вообще (если роль всегда будет без доступа), либо отображаться пустым с текстом «Нет доступа».
   - Уточнить по UX и требованиям безопасности.

### 4.2. Отображение ошибок
- Ошибки INT-2 отображаются пользователю в компоненте (не вываливаются в общий лог ошибок).
- Кнопка «Повторить» позволяет перезагрузить без перезагрузки страницы.
- Для ошибок 500 и 503 рекомендовать повторить позже (в подсказке).

### 4.3. Авторизация на фронте
- Раздел «Оборудование» видим только для ролей «Инженер» и «Диспетчер».
- Для роли «Оператор» компонент вообще не рендерится (или скрывается); попытка вызвать INT-2 вернёт 403.

## 5. Нефункциональные требования

### 5.1. Синхронность и производительность
- **Приём потока оборудования (INT-1):** асинхронный, по мере поступления из топика внешней системы. Обработка не должна блокировать другие запросы к бэку.
- **Пересчёт сопоставления:** запускается один раз в сутки в ночное время (⚠️ точное время уточняется). Операция может быть долгой (если оборудования много); работает в фоне, не блокирует пользовательские запросы.
- **Запрос INT-2:** синхронный, открытие карточки ждёт ответа; таймаут — 5 секунд (⚠️ значение уточняется). Если ответ не пришёл, INT-2 возвращает `status: "error"`.
- **Кэширование:** INT-2 можно кэшировать на фронте в рамках открытой карточки (например, пока карточка открыта, повторные запросы в течение 10 секунд читают кэш); уточнить стратегию с фронтендером.

### 5.2. Нагрузка (capacity planning)
Ожидается: 🟡 подтверждено аналитиком (не по коду), уточняется при интеграции и нагрузочном тестировании.
- Количество единиц оборудования: ⚠️ к валидации (аналитик не уточнил в интервью).
- Количество запросов INT-2 в час: зависит от активности инженеров; пиковая нагрузка — рабочее время.
- Частота INT-1 (приём): зависит от внешней системы; гарантировать пиковая пропускная способность топика ≥ [X msg/sec] — уточнить с владельцем внешней системы.

### 5.3. Безопасность и авторизация
- INT-2: авторизация по роли пользователя (проверка на бэке).
- INT-1: приём из внешней системы; убедиться, что топик имеет ограничения доступа (только внешняя система может писать; бэк Арсенала может читать).
- Данные оборудования: открыты для инженеров и диспетчеров; не экспортировать внешних систем без согласования.

## 6. Порядок выката и совместимость

### 6.1. Последовательность деплоя
Строгий порядок:
1. **Фаза 1 — БЭК (приём и хранение):**
   - Развернуть изменения бэка: новые таблицы Equipment и Привязка, обработчик INT-1 (приём из топика).
   - Запустить сборку миграций (создание таблиц).
   - Внешняя система начинает публиковать события в топик; бэк Арсенала их принимает и сохраняет.
   - На этапе 1 фронт ещё не знает об оборудовании; данные накапливаются.

2. **Фаза 2 — БЭК (сопоставление):**
   - Развернуть логику пересчёта сопоставления и планировщик (запуск один раз в сутки ночью).
   - Запустить первый пересчёт вручную (или дождаться ночного запуска).
   - Таблица Привязка начинает заполняться.
   - Фронт всё ещё не знает об оборудовании.

3. **Фаза 3 — БЭК (API отдачи):**
   - Развернуть эндпоинт INT-2 (GET /objects/{objectId}/equipment) на бэке.
   - Эндпоинт готов отдавать данные фронту.

4. **Фаза 4 — ФРОНТ (компонент):**
   - Развернуть компонент карточки оборудования на фронте Арсенала.
   - Компонент вызывает INT-2 при открытии карточки объекта.
   - Инженер видит оборудование в карточке.

**Обоснование порядка:**
- Фазы 1–2 можно выполнять параллельно (независимые работы в бэке).
- Фаза 3 (API) должна быть готовой до фазы 4 (фронт), иначе фронт получит ошибки.
- Фронт разворачивается последним, чтобы инженеры сразу видели актуальные данные.

### 6.2. Обратная совместимость
- **Фронт старой версии → новый бэк:** Старый фронт не знает о INT-2 и не вызывает эндпоинт; новый эндпоинт существует и работает, но старый клиент его не использует. Совместимо.
- **Фронт новой версии → старый бэк:** Новый фронт вызывает INT-2; старый бэк его не имеет → 404 или ошибка. Несовместимо; старый бэк должен быть обновлён перед новым фронтом.
- **Откат фазы:** Если откатить фронт на старую версию (без компонента), оборудование просто не отображается, но приём в бэке продолжается; откат бэка — сложнее (таблицы остаются). План отката согласовать с DevOps.

### 6.3. Фиче-флаги и преднастройка
- **Фиче-флаг (рекомендуется):** Раздел оборудования можно прятать за флагом на фронте, чтобы поэтапно показывать инженерам или отключить быстро при проблемах. Флаг: `SHOW_EQUIPMENT_SECTION` (по имени можно судить, что скрывает, и легко включить для тестирования).
- **Роли:** Убедиться, что в системе безопасности Арсенала определены роли «Инженер» и «Диспетчер» (если их нет, их нужно создать или переиспользовать существующие; уточнить с владельцем security-сервиса).
- **Топик внешней системы:** Предварительно согласовать доступ бэка к топику (имя, права на чтение, retention policy). ⚠️ Требует уточнения: уточнить имя топика и параметры при согласовании с владельцами внешней системы.

### Тест-кейсы (развёрнуто)

**TC-1 (FR-1): Идемпотентность приёма оборудования**
- Предусловие: очищена таблица Equipment.
- Действие: отправить сообщение INT-1 с `equipment_id: "EXT-001"`, дождаться записи.
- Проверка: в Equipment есть одна запись с `external_id: "EXT-001"`.
- Действие: отправить то же сообщение повторно.
- Проверка: в Equipment всё ещё одна запись (дубль не создан); поле `updated_at` обновлено (или не обновлено, в зависимости от логики обновления — уточнить).

**TC-2 (FR-2): Сопоставление при однозначном совпадении адреса**
- Предусловие: таблица Equipment с записью `{external_id: "EXT-002", address_normalized: "ул. пушкина, д. 10"}`, таблица объектов охраны с записью `{id: "OBJ-001", address: "ул. Пушкина, д. 10"}`.
- Действие: запустить пересчёт сопоставления вручную.
- Проверка: в Привязка появилась запись `{equipment_id: (ID из Equipment), object_id: "OBJ-001"}`.

**TC-3 (FR-2): Отсутствие привязки при нулевом совпадении**
- Предусловие: Equipment с `address_normalized: "ул. пушкина, д. 10"`, нет объектов охраны с такой адресом.
- Действие: запустить пересчёт.
- Проверка: в Привязка нет записи; оборудование попадает в лог непривязанных.

**TC-4 (FR-2): Отсутствие привязки при множественном совпадении**
- Предусловие: Equipment с `address_normalized: "ул. пушкина, д. 10"`, объекты охраны с ID OBJ-001 и OBJ-002, оба с нормализованным адресом `ул. пушкина, д. 10`.
- Действие: запустить пересчёт.
- Проверка: в Привязка нет записи; оборудование попадает в лог как "несколько совпадений".

**TC-5 (FR-3): Отображение оборудования в карточке**
- Предусловие: объект охраны OBJ-001 с привязанным оборудованием (2 единицы в Привязка).
- Действие: открыть карточку объекта в фронте.
- Проверка: компонент вызвал INT-2 (GET /objects/OBJ-001/equipment); фронт отобразил список 2 единиц оборудования с типами и адресами; внизу — отметка времени `last_sync`.

**TC-6 (FR-3): Отображение "Нет данных"**
- Предусловие: объект охраны без привязанного оборудования.
- Действие: открыть карточку объекта.
- Проверка: INT-2 вернул `{status: "no_data", equipment: []}` или `{status: "loaded", equipment: []}`; фронт отобразил текст "Нет данных об оборудовании".

**TC-7 (FR-3): Обработка ошибки**
- Предусловие: внутренняя ошибка бэка (например, таблица недоступна).
- Действие: открыть карточку объекта.
- Проверка: INT-2 вернул `{status: "error", error_code: "BACKEND_UNAVAILABLE"}`; фронт отобразил сообщение об ошибке и кнопку "Повторить".

**TC-8 (FR-3): Авторизация (роль Инженер)**
- Предусловие: пользователь с ролью "Инженер" авторизован.
- Действие: открыть карточку объекта.
- Проверка: INT-2 доступна; данные отображаются.

**TC-9 (FR-3): Авторизация (роль Оператор)**
- Предусловие: пользователь с ролью "Оператор" авторизован.
- Действие: открыть карточку объекта.
- Проверка: INT-2 возвращает 403; раздел оборудования скрыт или отображает "Нет доступа".
