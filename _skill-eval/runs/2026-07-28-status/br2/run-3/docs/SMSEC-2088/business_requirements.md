# Бизнес-требования: Выгрузка истории операций в PDF

>
> **Статус готовности:** Готово к оценке
>
> **Открытые вопросы (требуют уточнения перед оценкой):**
>

## 1. Введение и контекст

### 1.0. Тип изменения
Доработка существующего функционала — расширение личного кабинета клиента новой возможностью выгрузки истории операций.

### 1.1. Описание проблемы (Problem Statement)
Клиенты не могут получить историю операций в виде документа для предоставления в бухгалтерию, вынуждены обращаться в поддержку с просьбой отправить выписку.

### 1.2. Конечные потребители (End Users)
Клиенты — физические лица.

### 1.3. Заказчик и стейкхолдеры (Stakeholder / Sponsor)
- **Заказчик:** Руководитель клиентского сервиса.
- **Эксперт для консультации:** Тимлид личного кабинета.

## 2. Бизнес-требования (цели и ценность)

### 2.1. Бизнес-цель
Я как клиент должен иметь возможность выгружать историю своих операций в PDF, чтобы предоставить её в бухгалтерию без обращения в поддержку.

### 2.2. Ценность для бизнеса
Снижение числа обращений в службу поддержки за выписками; улучшение опыта пользователя путём предоставления возможности самообслуживания.

### 2.3. Бизнес-риски и меры по снижению (Mitigation)

| Риск | Вероятность / влияние | Меры по снижению |
|------|-----------------------|------------------|
| Выгрузка PDF с операциями другого клиента (утечка данных) | Низкая / Критичное | Обязательная проверка прав доступа: клиент может выгружать только свои операции |

## 3. Объём проекта (Scope)

### 3.1. Входит в проект (In-scope)
- Возможность клиента выбрать период для выгрузки истории операций.
- Генерация PDF-файла со своими операциями за выбранный период.
- Скачивание готового файла.
- Вывод понятного сообщения в случае отсутствия операций за период.

### 3.2. Не входит в проект (Out-of-scope)
- Выгрузка в Excel и другие форматы (только PDF).
- Массовая выгрузка по нескольким клиентам одновременно.
- Выгрузка для операторов поддержки.

### 3.3. Архитектурные изменения и интеграции
Использование существующего механизма генерации файлов; конкретика использованных технологий и сервисов определяется на этапе технической спецификации.

## 4. Функциональные требования

### 4.1. Описание функционала / бизнес-процесса

**FR-1:** Клиент открывает историю операций в личном кабинете.

**FR-2:** Клиент выбирает период (дату начала и дату окончания), за который требуется выгрузить операции.

**FR-3:** Клиент нажимает кнопку «Выгрузить в PDF».

**FR-4:** Система генерирует PDF-файл со списком операций клиента за выбранный период.

**FR-5:** Система выдаёт клиенту готовый PDF-файл для скачивания.

**FR-6:** Если за выбранный период операций не найдено, система выводит понятное информационное сообщение вместо пустого файла.

### 4.2. Критерии приёмки (Acceptance Criteria)

- **[FR-2–FR-5]** Дано: клиент авторизован в личном кабинете и открыл историю операций. Когда: клиент выбирает период и нажимает «Выгрузить в PDF». Тогда: система генерирует и предоставляет скачать PDF с операциями клиента за этот период; PDF содержит только данные авторизованного клиента.

- **[FR-6]** Дано: клиент авторизован и выбрал период, в котором нет операций. Когда: клиент нажимает «Выгрузить в PDF». Тогда: система выводит сообщение о том, что операций за период не найдено, и не генерирует пустой файл.

## 4.5. Разбиение на слайсы

**Анализ:**
1. **Числа:** 6 функциональных требований (FR-1–FR-6).
2. **Ценность:** Все требования обслуживают одну цель — дать клиенту возможность выгружать историю операций в PDF для бухгалтерии. Каждое требование — часть единого потока: без выбора периода (FR-2) нет смысла генерировать файл; без генерации (FR-4) нечего скачивать; без скачивания (FR-5) весь функционал бесполезен. Вывод о пустом результате (FR-6) — исключение, необходимое для полноты, но не обособленный деливербл.
3. **Порог:** Одна бизнес-цель (выгрузка в PDF), одна ценность (клиент получает выписку для бухгалтерии), все требования сцеплены потоком.
4. **Исход:** Не применимо — работа представляет собой один деливербл; разбиение не требуется.

**Разбиение на слайсы не применимо.** Все функциональные требования образуют единый поток значимой функциональности: выбор периода → генерация → выдача файла. Ни одна часть не даёт бизнесу отдельной ценности без остальных — это звенья одной цепочки.

## 5. Ограничения и атрибуты качества

### 5.1. Приоритет
**High.** Проблема касается опыта пользователя в критичном процессе (бухгалтерский отчёт); ожидается значительное снижение нагрузки на поддержку.

### 5.2. Сроки и обоснование
**Дедлайн:** конец квартала (отчётный период).

**Обоснование:** Сроки совпадают с квартальным отчётным циклом, в котором клиентам требуются выписки для бухгалтерии.

### 5.3. Ролевая модель

| Роль | Права / доступные действия |
|------|----------------------------|
| Клиент | Может просматривать свою историю операций, выбирать период и выгружать в PDF только собственные операции |
| Оператор поддержки | Не имеет доступа к функции выгрузки в PDF |
