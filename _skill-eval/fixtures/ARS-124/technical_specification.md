## 1. Обзор изменения
### 1.1. Тип и стороны
Fullstack. В шапке «Арсенала» появляется число активных пользователей; бэк «Арсенала» берёт его
у сервиса аутентификации и отдаёт фронту.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| incident-api | новый эндпоинт, потребитель счёта сессий | команда «Арсенал» | 🟢 |
| incident-web | показывает индикатор в шапке | команда «Арсенал» | 🟢 |
| auth | отдаёт счёт активных сессий | команда безопасности | 🟡 подтверждено аналитиком |
### 1.3. Связь с бизнес-требованиями
Дежурный видит в шапке, сколько коллег сейчас в системе, и не уточняет это в мессенджере.

## 2. Взаимодействия (ядро)

### INT-1. Число активных пользователей для шапки — 🟢
- **Граница/направление:** фронт «Арсенала» → бэк «Арсенала»
- **Триггер:** загрузка страницы и периодическое обновление шапки
- **Контракт (запрос):** тело отсутствует, параметров нет
- **Контракт (ответ):** `count` (integer | null) — число активных пользователей; `null` означает «источник недоступен», `0` — валидный ноль; `updatedAt` (string ISO-8601) — когда значение получено от источника
- **Пример запроса:** тело отсутствует
- **Пример ответа (успех):**
  ```json
  { "count": 17, "updatedAt": "2026-07-31T08:40:00Z" }
  ```
- **Ошибки:** `500` — бэк не смог обратиться к источнику; тело `{"error":"internal"}`
- **Состояния UI по ответу:** `count` > 0 → число; `count` = 0 → «0», не прочерк; `count` = null → «—»; ожидание → загрузка; `500` → «—» и повтор по таймеру
- **Авторизация:** любой авторизованный пользователь «Арсенала»; неавторизованный получает `401`
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1, FR-2

### INT-2. Счёт активных сессий из сервиса аутентификации — 🟡 подтверждено аналитиком
- **Граница/направление:** бэк «Арсенала» → сервис аутентификации
- **Триггер:** запрос от фронта по INT-1
- **Контракт (запрос):** к валидации — путь и параметры уточняются при интеграции
- **Контракт (ответ):** к валидации — сервис аутентификации отдаёт число активных сессий и отметку времени; аналитик подтвердил, что такая возможность у сервиса есть
- **Пример запроса:** не приводится — контракт существующего сервиса, конкретика к валидации
- **Пример ответа (успех):** не приводится — см. выше
- **Ошибки:** недоступность источника отражается в INT-1 как `count: null`
- **Состояния UI по ответу:** через INT-1
- **Авторизация:** сервисная учётная запись «Арсенала» в сервисе аутентификации 🟡 подтверждено аналитиком
- **Происхождение:** 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Трассировка:** FR-1

## 3. Backend — ответственность
### 3.1. По сервисам
`incident-api` реализует INT-1 и потребляет INT-2. Собственной логики между ними нет: полученное
от источника число отдаётся фронту как есть, недоступность источника превращается в `count: null`.
### 3.2. Данные и хранение
Новых сущностей нет, миграций нет: значение не хранится.
### 3.3. Авторизация/доступ на бэке
INT-1 — любой авторизованный пользователь; проверка на границе эндпоинта. Обращение к сервису
аутентификации идёт под сервисной учётной записью.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
Шапка приложения: рядом с именем пользователя появляется число активных пользователей. Новых
роутов нет.
### 4.2. Пользовательские сценарии
Дежурный открывает любую страницу и видит в шапке число коллег в системе (FR-1, FR-2).
### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос | скелетон на месте числа |
| `value` | 2xx, `count` > 0 | число |
| `zero` | 2xx, `count` = 0 | «0» |
| `empty` | 2xx, `count` = null | «—» |
| `error_source` | 500 / таймаут | «—», повтор по таймеру |
### 4.3.1. Loading и таймауты
Таймаут cold-path 4 с, warm-path 2 с. Обновление раз в 60 с с джиттером ±10 с, чтобы клиенты
не синхронизировались.
### 4.4. Доступ по ролям в UI
Индикатор виден всем авторизованным ролям.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Синхронный вызов. Кэш в бэке «Арсенала», TTL 30 с. Опрос фронтом раз в 60 с.
### 5.2. Надёжность/деградация
Источник недоступен — `count: null`, фронт показывает «—»; ошибка не всплывает модальным окном.
### 5.3. Безопасность/доступ (сводно)
INT-1 — любой авторизованный. INT-2 — сервисная учётная запись.
