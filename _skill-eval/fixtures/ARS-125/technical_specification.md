## 1. Обзор изменения
### 1.1. Тип и стороны
Fullstack. Бэк «Арсенала» начинает принимать поток сведений об оборудовании, хранить его,
сопоставлять с объектами охраны по адресу и отдавать результат фронту; фронт показывает
оборудование в карточке объекта охраны.
### 1.2. Затронутые сервисы и владельцы
| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| incident-api | принимает поток, хранит, сопоставляет, отдаёт | команда «Арсенал» | 🟢 |
| incident-web | показывает оборудование в карточке объекта | команда «Арсенал» | 🟢 |
| внешняя система учёта оборудования | источник потока | смежная компания | 🟡 к валидации |
### 1.3. Связь с бизнес-требованиями
Инженер видит в карточке объекта охраны, какое оборудование там установлено, не запрашивая
выгрузку у смежной системы вручную.

## 2. Взаимодействия (ядро)

### INT-1. Приём сведений об оборудовании — 🟢
- **Граница/направление:** внешняя система учёта → бэк «Арсенала» (событие на единицу оборудования)
- **Триггер:** установка, замена или снятие единицы оборудования во внешней системе
- **Контракт (запрос):** `externalId` (string, обязателен) — идентификатор единицы во внешней системе; `type` (enum: `camera` | `sensor` | `panel`); `address` (string) — адрес установки как есть; `occurredAt` (string, ISO-8601)
- **Контракт (ответ):** подтверждение приёма без тела; повторная доставка того же `externalId` с тем же или более ранним `occurredAt` не создаёт дубль и не изменяет запись
- **Пример запроса:**
  ```json
  { "externalId": "EQ-90114", "type": "camera", "address": "г. Тула, ул. Мира, д. 4, подъезд 2", "occurredAt": "2026-07-14T09:12:00Z" }
  ```
- **Пример ответа (успех):**
  ```json
  { "accepted": true, "externalId": "EQ-90114" }
  ```
- **Ошибки:** `422` — `type` вне перечисления или пустой `externalId`, сообщение отбрасывается в очередь разбора; `409` не возникает, повтор идемпотентен
- **Состояния UI по ответу:** не применимо, фронта в этом взаимодействии нет
- **Авторизация:** сервисная учётная запись внешней системы; сквозной пользовательский токен здесь не используется
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-1

### INT-2. Оборудование по объекту охраны — 🟢
- **Граница/направление:** фронт «Арсенала» → бэк «Арсенала»
- **Триггер:** открытие карточки объекта охраны
- **Контракт (запрос):** `siteId` (string, обязателен) — идентификатор объекта охраны
- **Контракт (ответ):** `items` (array) — привязанное оборудование: `externalId` (string), `type` (enum: `camera` | `sensor` | `panel`), `address` (string, нормализованный); `matchedAt` (string ISO-8601 | null) — отметка актуальности последнего пересчёта, `null` означает «пересчёт ни разу не выполнялся»; пустой `items` — не ошибка
- **Пример запроса:** тело отсутствует, параметр пути `siteId`
- **Пример ответа (успех):**
  ```json
  { "items": [ { "externalId": "EQ-90114", "type": "camera", "address": "тула мира 4" } ], "matchedAt": "2026-07-15T02:00:00Z" }
  ```
- **Ошибки:** `403` — роль без доступа к разделу оборудования; `500` — источник недоступен
- **Состояния UI по ответу:** непустой `items` → перечень; пустой `items` → «нет данных»; ожидание → загрузка; `403` → «нет доступа»; `500`/таймаут → ошибка с повтором
- **Авторизация:** роли «Инженер» и «Диспетчер»; «Оператор» раздел не видит; проверяется на бэке
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### Каталог ошибок (сводно)
| Код | Тело/сообщение | Когда | Состояние UI |
|-----|----------------|-------|--------------|
| 422 | `{"error":"invalid_equipment_event"}` | `type` вне перечисления, пустой `externalId` | не применимо |
| 403 | `{"error":"forbidden"}` | роль без доступа к разделу оборудования | `error_forbidden` |
| 500 | `{"error":"internal"}` | источник недоступен | `error_source` |

## 3. Backend — ответственность
### 3.1. По сервисам
`incident-api` реализует INT-1 и INT-2, владеет сущностями «Оборудование» и «Привязка», выполняет
регулярный пересчёт сопоставления.
### 3.2. Данные и хранение
- **Оборудование** (новая сущность): `externalId` (string, ключ идемпотентности), `type` (enum), `addressRaw` (string), `addressNormalized` (string), `updatedAt` (timestamp). Индекс по `addressNormalized` под пересчёт.
- **Привязка** (новая сущность): `externalId` (string), `siteId` (string), `matchedAt` (timestamp). Уникальность по `externalId`.
- Миграции нужны: две новые таблицы и один индекс; точный DDL — 🟡 по реальной схеме владеющего сервиса.
### 3.3. Авторизация/доступ на бэке
INT-1 — сервисная учётная запись внешней системы. INT-2 — роли «Инженер» и «Диспетчер»,
проверяется на границе эндпоинта; «Оператор» получает `403`.

## 4. Frontend — ответственность
### 4.1. Где и что меняется в UI
В карточке объекта охраны появляется блок «Оборудование»; новых роутов нет. Блок вызывает INT-2.
### 4.2. Пользовательские сценарии
Инженер открывает карточку объекта охраны и видит перечень установленного оборудования (FR-3).
### 4.3. Состояния (именованные)
| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос | скелетон блока |
| `value` | 2xx, `items` непустой | перечень оборудования |
| `empty` | 2xx, `items` пустой | «нет данных» |
| `error_forbidden` | 403 | «нет доступа» |
| `error_source` | 500 / таймаут | сообщение об ошибке + повтор |
### 4.3.1. Loading и таймауты
Таймаут cold-path 5 с, warm-path 2 с. Polling нет: блок запрашивает данные по открытию карточки.
### 4.4. Доступ по ролям в UI
Блок виден ролям «Инженер» и «Диспетчер»; «Оператору» блок не отрисовывается.

## 5. Нефункциональные требования
### 5.1. Синхронность, кэш, производительность
Приём — потоковый, по мере поступления. Пересчёт сопоставления — регулярный, раз в сутки ночью.
Кэша нет. Карточка ходит в бэк по открытию.
### 5.2. Надёжность/деградация
Внешняя система недоступна — приём простаивает, ранее принятое оборудование продолжает
отдаваться; `matchedAt` показывает, насколько давно был пересчёт.
### 5.3. Безопасность/доступ (сводно)
INT-1 — только сервисная учётная запись. INT-2 — «Инженер», «Диспетчер».

## 6. Релиз и интеграция
### 6.1. Порядок выката
01 приём и хранение → 02 сопоставление → 03 отдача и карточка. Бэк с новым контрактом INT-2
выкатывается раньше фронта.
### 6.2. Обратная совместимость
Ничего не ломается: контракты новые, существующих потребителей у них нет.
### 6.3. Фиче-флаги
Флагов нет, релизим атомарно по этапам.
### 6.4. План отката
- **Откат только BE:** фронт получает `500` на INT-2 и показывает `error_source` — допустимо.
- **Откат только FE:** бэк отдаёт данные, блок в карточке не отрисовывается; локального стейта нет.
- **Откат DDL:** down-миграция удаляет обе таблицы; принятые события теряются, повторная доставка восстановит их.
