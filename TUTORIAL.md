# Петля coDDoc: туториал по сценариям

Петля — набор скиллов, которые ведут задачу от идеи, дефекта или мелкой правки до `technical_specification.md`. Спека — конечный продукт: по ней пишет код разработчик или агент. Всё живёт в репозитории **AI-SDD**: карточки сервисов в `services/`, ваши документы в `context/`, задачи в `docs/<КЛЮЧ>/`.

Установка и таблица скиллов — в [README](README.md). Здесь — как этим пользоваться.

## Общие правила

- **Одна задача — одна ветка** `feature/<КЛЮЧ>`. Ветка ходит между владельцем продукта, аналитиком и разработчиком.
- **Каждый этап — с чистого контекста**: новая сессия, либо `/clear` в текущей. Перед БТ, перед спекой, перед архивацией, при переключении задач. Переписка прошлого этапа портит следующий.
- **Точка входа — `/analyst-workspace`.** Скилл сам спрашивает, что у вас на руках, и сам зовёт нужный под-скилл. Имена под-скиллов знать не нужно.
- **Приёмка автоматическая.** После каждого записанного документа его читает агент с чистым контекстом и возвращает список нарушений. Много нарушений — выбирайте «Доработать», не правьте руками: на новую редакцию запустится новая приёмка.
- **`/analyst-workspace --no-review`** выключает приёмку на всю сессию. Отключается только проверка структуры готового документа. Проверка каждого пункта по ходу интервью и гейт по статусу остаются.
- **Прерванная работа** — `/analyst-workspace` → «Продолжить начатое».
- **Коммит и пуш делаете вы.** Скиллы git не трогают.
- Модель DeepSeek-V4-Flash, effort `high` и выше. Кодовая база рядом нужна только для `service-map` и архивации.

## Сценарий 1. Собрать карточки сервисов: `service-map`

Делается один раз при старте и точечно после релизов.

1. Склонируйте репозитории сервисов рядом с AI-SDD, на одном уровне.
2. В AI-SDD: `/service-map`. Скилл найдёт соседние репозитории, спросит, какие читать, и напишет `services/manifest.yaml` и по карточке `services/<имя>.md`.
3. Прочитайте карточки. Плохая карточка — перечитать сервис по имени: `/service-map auth geo`. Карточка перезаписывается целиком.
4. В `manifest.yaml` заполните `notes`: договорённости, которых нет в коде. Они переносятся в карточку дословно.
5. Закоммитьте `services/`.

Ограничения:

- До пяти сервисов за один запуск. Больше — по именам, партиями: `/service-map auth geo billing`. Партии можно гнать параллельно в нескольких окнах, каждая пишет свои карточки.
- `--refresh` перечитывает все сервисы из манифеста. Без аргументов — только те, у кого карточки ещё нет.
- Чего нет в коде, в карточку не попадает: там будет `не определено`. Это честнее догадки.
- Кандидат, которого проверка не пустила поверх старой карточки, ложится в `services/_pending/`. Принять — переместить файл, отклонить — удалить.

## Сценарий 2. Положить свои заметки: `context-doc`

В `context/` лежит то, чего нет в коде: регламенты, глоссарий, договорённости с внешними командами, правила оформления API. Эту папку читают скиллы БТ и спеки.

1. `/context-doc путь/к/файлу`. Форматы: txt, md, csv, json, html, pdf, docx, xlsx, папка или текст прямо в чате.
2. Скилл переносит содержимое дословно и предлагает строку `description`. Утвердите или поправьте её.
3. Один документ — одна тема. Сборный регламент режется на несколько файлов, каждый со своим описанием.
4. Положили файл руками — запустите `/context-doc` без аргументов. Он найдёт файлы без `description` и допишет её.

Почему `description` обязательна: скиллы ищут контекст одним грепом по этой строке. Файл без неё и не-`.md` файл для петли не существуют.

**Правила оформления в `context/` улучшают спеку.** Когда в спеке проектируются новые контракты и сервисы, скилл сверяет их с правилами из `context/`: форма пути, коды ошибок, формат дат, именование полей, семантика `null`. Нет такого файла — каждый аналитик получает свой стиль. Положите туда стандарты API, архитектурные соглашения, правила именования. Правило применяется ровно к тому решению, которое оно называет: правило про таймаут не задаёт интервал опроса. Пишите правила конкретно.

Правила из `context/` применяются молча и с кодом не сверяются. Держите папку актуальной.

## Сценарий 3. Новая возможность: ветка БТ

Самый длинный маршрут: БТ → (разрез на детей?) → (фундамент #0?) → спека → (этапы?).

**Владелец продукта или бизнес-аналитик:**

1. `git checkout -b feature/SMSEC-12345`.
2. `/analyst-workspace` → «Бизнес» → «идея / новая возможность».
3. Первым вопросом скилл спросит ключ задачи. Без ключа файл не пишется.
4. Отвечайте на вопросы. Скилл спрашивает гипотезой: предлагает вариант, вы подтверждаете или поправляете. То, что вы уже сказали, он не переспрашивает.
5. Получаете `docs/SMSEC-12345/business_requirements.md` и отчёт приёмки. Прочитайте документ.
6. `git push`, ветку передаёте аналитику.

**Системный аналитик:**

1. `git pull && git checkout feature/SMSEC-12345`.
2. Новая сессия или `/clear`, затем `/analyst-workspace` → «Аналитика», путь к БТ.
3. Скилл прочитает в БТ раздел о разбиении и решит, резать ли на детей (см. ниже).
4. Пишется `technical_specification.md`. Прочитайте спеку и отчёт приёмки.
5. `/spec-readiness docs/SMSEC-12345/technical_specification.md` (Сценарий 6).
6. Скилл спросит, делить ли работу на этапы (см. ниже).
7. `git push`, ветку передаёте разработчику.

### Когда БТ бьётся на детей

Когда в БТ есть две и более независимые ценности, каждую из которых можно зарелизить отдельно, агент предложит разбить БТ на детей. Финальное слово за человеком: скажете «разбей» или «не надо» — сделает так.

БТ режется, когда:

- **В БТ записано разбиение на два и более слайса.** Слайс — группа уже написанных требований, которую можно выпустить отдельно и получить бизнес-ценность. Этот раздел заполняется при написании БТ.
- **Разбиения в БТ нет** — скилл считает сам: эпик, если в БТ две и более обособленные фичи **или** четыре и более требования про разные куски, каждый с самостоятельной ценностью.
- **Жёсткий минимум — два требования.** С одним требованием декомпозиция откажет.

БТ **не** режется, когда результат один: ни одну часть нельзя выпустить отдельно и получить ценность.

Что не является доводом против разреза:

- Общая бизнес-цель. Это определение эпика, а не возражение.
- Общий источник данных, общий сервис, общий UI-модуль. Это признак фундамента #0, а не повод слепить всё в одну фичу.

Что нужно заранее: **реальные ключи подзадач в трекере, по одному на слайс.** Плейсхолдеры декомпозиция не принимает. Заведите их до интервью разреза.

Как устроены дети: каждый ребёнок — самостоятельный БТ в `docs/<ЭПИК>/<РЕБЁНОК>/`, с требованиями, скопированными из родителя дословно. Требование, нужное двум детям, отдаётся одному, второй зависит от него. Сквозное требование в обоих детях — только по вашему явному решению, и это риск: две спеки спроектируют для него два контракта.

### Фундамент #0

После разреза скилл читает детей и ищет общий источник: ≥2 ребёнка опираются на одну сущность, сервис или справочник. Если да — предложит узел #0: спроектировать общее один раз, дети наследуют контракт неизменным.

- У #0 своего БТ нет. Это слой реализации, интервью по бизнес-требованиям на него не будет.
- Спека #0 пишется первой, потом дети.
- Источники у детей разные — фундамента нет, и это нормально. Скилл его не выдумает.

### Когда спеку можно разбить на этапы

Этапы `stages/stage-NN.md` — необязательный шаг. Скилл спрашивает об этом один раз, после готовой спеки. Единственная причина сказать «да»: **работу делят между несколькими исполнителями**, людьми или агентами, и каждому нужен свой файл задачи.

Разрез считается механически, по новым контрактам спеки: новые API и события 🟢 и новые сущности. Отсюда следствия:

- **Ни одного нового контракта** (чисто фронтовая доработка, изменение внутри существующего API) — «не применимо». Штатный исход, не ошибка.
- **Один новый контракт — один этап.** Файл будет, но раздавать нечего.
- **Независимые контракты — разные этапы**, даже если их отдаёт один сервис из одной таблицы.
- **По границе фронт/бэк не режется никогда.** У фронтовой стороны контракта нет своего выхода.
- **Существующие сервисы (🔵/🟡) и контракт #0** — вход извне, а не новый контракт. Своего этапа под них нет.
- Открытые пункты в спеке разрезу не мешают, но могут его потом изменить.
- «Один этап на всё» допустимо, но ничего не даёт: получите «не применимо».

Не режьте «на всякий случай»: каждый этап — копия куска спеки. Правка спеки после нарезки означает правку всех этапов. Поэтому `spec-readiness` запускайте **до** нарезки.

## Сценарий 4. Дефект прода: ветка баг

Маршрут короткий: баг-репорт → спека с флагом багфикса → (этапы?). Разреза и фундамента нет.

1. `git checkout -b feature/SMSEC-12345`, `/analyst-workspace` → «Бизнес» → «дефект».
2. Скилл фиксирует шаги воспроизведения, факт, ожидание, критичность. Причину и код он не ищет: это работа спеки и разработчика.
3. Получаете `bug_report.md`. `git push`, передаёте аналитику.
4. Аналитик: новая сессия или `/clear`, затем `/analyst-workspace` → «Аналитика», путь к репорту. Тип определится по имени файла.
5. Спека, `spec-readiness`, пуш.

Если в описании дефекта на самом деле новая возможность, скилл остановит и отправит в БТ.

## Сценарий 5. Мелкая правка

Решение уже принято: поменять текст, поднять версию, добавить поле, сменить лимит. БТ не заводится.

1. `/analyst-workspace` → «Бизнес» → «правка». Ключ задачи обязателен.
2. Скилл разложит правку по пяти строкам: контракт, данные, интерфейс, зависимость, конфигурация. Для каждой тронутой строки нужна пара «как сейчас → как должно стать» конкретной фразой.
3. Тронуто три строки и больше, или появился новый потребитель, новая функция — скилл скажет «выше порога» и спросит, идти правкой или разворачиваться в БТ. Решаете вы. Пример «выше порога»: «поле хранить, отдавать в ответе и показывать в карточке».
4. Получаете `change_request.md`. Дальше как с дефектом: аналитик пишет спеку с флагом правки.

Скилл не пересматривает решение и не достраивает его. Соседнее поле, которое «логично добавить заодно», в документ не идёт.

## Сценарий 6. Проверить любую спеку: `spec-readiness`

Приёмка отвечает за форму: разделы заполнены, пометки расставлены. `spec-readiness` отвечает на другой вопрос: можно ли по этой спеке писать код. Три агента с чистым контекстом читают спеку как бэкенд, фронтенд и интеграция между ними, четвёртый вычёркивает вопросы, на которые спека уже отвечает. Остаток — решения, которые исполнитель иначе примет сам.

```
/spec-readiness docs/SMSEC-12345/technical_specification.md
```

- Работает на любой спеке: одиночной, детской, #0, багфикса, правки.
- Не работает на БТ и на `stages/stage-NN.md`.
- Ничего не пишет на диск. Ответы дописываете в спеку вы, через «Доработать» в `analyst-workspace` или руками.
- Пустой список — законный исход. Он значит «исполнитель не встанет на отсутствии данных», а не «спека хорошая».
- Карточка существующего сервиса (🔵/🟡) дырой не считается. Требовать контракт у чужого сервиса значит просить аналитика его выдумать.

Запускайте перед передачей разработчику и до нарезки на этапы. После правок спеки можно запустить ещё раз.

## Сценарий 7. Архивация после релиза

Фича уехала в прод — код изменился, карточки затронутых сервисов устарели. Архивация перечитывает эти сервисы через `service-map` и кладёт метку `.archived` в папку задачи.

1. Обновите локальные клоны затронутых сервисов. Карточка честна настолько, насколько свежа рабочая копия.
2. Новая сессия или `/clear`, затем `/analyst-workspace` → «Доработка готова». Или напрямую: `/archive-spec SMSEC-12345`.
3. Скилл перечислит, что архивирует, и остановится. Подтвердите список. Для эпика это важно: дети, которые ещё в разработке, из списка убираются.
4. Скилл запустит перечитывание сервисов и отчитается: что перечитано, что не нашлось в коде, что пропущено.
5. Закоммитьте карточки и `.archived` одним коммитом. Метка без карточек в истории приведёт к повторному перечитыванию.

**Архивируйте пачкой, сразу за релиз.** Каждая архивация перезаписывает карточки `services/*.md` целиком. Две фичи одного релиза, заархивированные в разных ветках, дадут конфликт на одних и тех же карточках, и разрешать его придётся руками. Правильно: после релиза в одной ветке архивировать все уехавшие задачи подряд, потом один коммит с карточками и метками. Эпик архивируется по ключу эпика разом.

Что ещё делать по отчёту:

- «Пункт не найден в коде» — либо не уехало, либо названо иначе. Проверьте.
- Эндпоинты и поля, которые спека помечает устаревшими, — если их уже нет в коде, впишите в `notes` манифеста. Иначе этот факт скан не сохранит.
- Незавершённые спеки не архивируйте: метка помешает перечитать сервисы, когда фича действительно уедет.

## Сценарий 8. Обновить скиллы

```
/analyst-skills-update
```

Скилл запускает скрипт из своей папки, подтягивает свежие версии в `.gigacode/skills/` и печатает список «скилл — версия». Нужны `git` и `bash` (на Windows — Git Bash) и доступ к репозиторию со скиллами.

Обновляйте перед новой задачей, не посреди неё: под-скиллы меняют шаблоны документов, и спека, начатая одной версией, может не пройти приёмку другой.

## Бест практисы

**Контекст**

- Без `services/` и `context/` скиллы работают, но вопросы общие, а варианты ответов агент выдумывает сам. Соберите контекст до первой задачи.
- Правила оформления API, архитектурные соглашения, общие сведения о системе (роли, домены) — в `context/` с `description`. Они напрямую влияют на качество новых контрактов в спеке и помогают формировать релиз с нуля, когда готовых сервисов и карточек ещё нет.
- После релиза соседнего сервиса — `/service-map <имя>`. Не ждите, пока карточка соврёт в спеке.

**Интервью**

- Отвечайте на вопросы фактами, не описаниями процесса. Атомарные вещи (ключи, версии, имена) скилл не угадывает — их нужно назвать.
- Ключ задачи — первый вопрос и жёсткий блокер. Заведите задачу в трекере до запуска.
- Для эпика заведите ключи подзадач до интервью разреза.

**Приёмка и проверки**

- Список нарушений приёмки передавайте как есть, с цитатами и номерами строк.
- Много нарушений — «Доработать», а не ручная правка.
- `--no-review` — для быстрых итераций, когда документ будете вычитывать сами. Гейт по статусу всё равно сработает.
- `spec-readiness` — перед передачей и до нарезки на этапы.

**Метки в спеке**

- 🟢 — новое, спроектировано здесь. Строить как написано.
- 🔵 — существующий чужой сервис, аналитик подтвердил на интервью, по коду не проверено. Сверить при интеграции.
- 🟡 — существующий чужой сервис, не подтверждено. Пункт открыт.
- Не просите скиллы дописать контракт под 🔵 или 🟡: кода чужого сервиса у агента нет, он его выдумает. Подтвердите у владельца сервиса и снимите метку.

**Разрез**

- Эпик режется по бизнес-ценности, потом ищется общая часть. Общие данные — довод разделить **и** оформить #0, а не слепить в одну фичу.
- Этапы — только если работу реально раздают нескольким исполнителям.
- Открытые пункты закрывайте до передачи. Гейт держит процесс, пока вы не выберете «Доработать» или явно не примете документ. Разработчик спеку не дописывает: нехватка в документе — возврат к аналитику.

**Git**

- Одна задача — одна ветка. Пушьте после каждого этапа, ветка ходит между ролями.
- Архивация — пачкой за релиз, в одной ветке, одним коммитом с карточками.
- Скиллы ничего не коммитят. Дифф читаете вы.
