> Раунд над `service-map` по полевому инциденту, а не по аудиту. Предыдущие раунды — `PLAN.md`,
> `PLAN-PROJECTION.md`, `PLAN-SEAMS.md` (отработаны). Журнал прогонов — `PROBES.md`.
>
> **Состояние: ВНЕСЕНО текстом 2026-08-11 в 5.0, не мерено.** Заведён 2026-08-11.
>
> **Стратегия по ходу изменилась, и план ниже отражает разбор, а не то, что сделано.** Разрез
> вынесен в **отдельный скилл `repo-split`**, а не внесён в `service-map`. Причина — регресс:
> `service-map` вымерен пятью раундами, и логика поиска границ задела бы Шаг 1 (SM-1, SM-2, SM-12,
> SM-53a), бюджет попыток (SM-8, SM-40, SM-48, SM-52) и гейт на запись (SM-31). Скилл, который
> производит только строки манифеста, не может сломать ничего из этого.

> **Что из плана взято:** M1 в варианте C (кусок = строка манифеста), M0 (замер размера — уехал в

> единица теперь просто не возникает), M4 (частичная запись), M5 (правка `archive-spec`),
> архитектуры A и B (сборщик и папка-карточка), поля `roots`/`lookup`/`unit`.
> **Что сознательно не внесено:** правило «вызов = импорт типа из соседнего куска». Сначала надо
> увидеть, что субагент напишет во «Зависит от» сам, — иначе есть риск вылечить несуществующий
> дефект и залить граф мусором.
>
> **Внесено:** `repo-split/SKILL.md` (новый скилл), фикстуры `RS-MONO`, `RS-SMALL`, `SM-PIECES`,
> пробы RS-1…RS-8 и SM-64…SM-68 (`PROBES.md`, раздел «Раунд „разрез монолита“»).
>
> **В `service-map` внесены три правки из пяти:** разбор `path` по запятой (Шаг 3 и сверка на Шаге
> 2.1); папка, внутри которой лежит путь из манифеста, не считается новым соседом (Шаг 2.1); корень
> репы уходит субагенту куска с границей «ключи только из куска, факты можно из корня» (Шаг 3).
> Две оставшиеся перечислены в CHANGELOG как предложения. **Бюджет попыток не тронут** — решение
> зафиксировано отдельно.
>
> **Разбор, приведший к нынешнему виду скилла** (он же — почему план ниже местами устарел): мера
> нагрузки — ключи, а не файлы; разрез — разбиение всех пакетов, а не выборка важного; границы
> выбираются по связности (число импортов между пакетами), а не по именам; порога «слишком велик»
> нет, потому что он не мерен. Счёт ключей грепом ценен не разрезом, а тем, что он **внешний** по
> отношению к субагенту, чья самозаявленная опись сегодня и проверяет сама себя.
>
> Симптом с поля: на больших сервисах (монолиты) субагент «умирает в фоне» — ничего не возвращает.
> Следствия, названные с поля: (1) хороший скан получается не с первой попытки, (2) обновление
> слепка неподъёмно тяжёлое.

## Что именно умирает — три разные смерти под одним симптомом

Сейчас в скилле нет **ни одного признака размера сервиса**. Единственный порог — «больше десяти
сервисов» (Шаг 2.2), он про число строк манифеста и к монолиту неприменим: монолит — это одна
строка. Единица скана равна сервису по определению, и никакой другой единицы не предусмотрено.

Отсюда три независимых обрыва, которые снаружи выглядят одинаково («субагент ничего не вернул»):

| # | Где рвётся | Механика | Порог |
|---|---|---|---|
| **1. Вход субагента** | окно субагента | чтобы поставить файл-источник каждому ключу, он обязан открыть контроллеры + DTO + обработчики + миграции. Это сотни файлов | наступает **первым** |
| **2. Выход субагента** | лимит вывода одного сообщения | он обязан вернуть опись **и текст карточки** одним ответом | ~в 2–3 раза дальше |
| **3. Окно ведущего** | окно ведущего | текст карточки проходит через него **трижды**: ответ субагента → параметр `Write` → чтение на Шаге 5 | один монолит съедает бюджет всего прогона |

**Замеренное (раунд «контекст ведущего», 2026-07-30, крупный сервис = 48 эндпоинтов):**

| Что | Сколько |
|---|---|
| ответ субагента (опись + карточка) | 13,8 КБ |
| параметр `Write` | 11,3 КБ |
| чтение на Шаге 5 | 11,3 КБ |
| **на сервис у ведущего** | **41,7 КБ**, окно 262k → ~12 карточек |

**Экстраполяция на монолит (~300 эндпоинтов, ×6,25) — оценка, не замер:**

- ответ субагента ≈ **86 КБ** одним сообщением ≈ 25–34k токенов вывода. Это на потолке или за ним:
  ответ либо обрубается, либо не рождается;
- карточка ≈ 71 КБ, у ведущего ≈ **260 КБ на один сервис** — вшестеро больше, чем весь его бюджет;
- вход: 300 эндпоинтов на живом дереве — это не 300 файлов, а 900–3000 (роут, DTO, обработчик,
  миграция). При 3 КБ на файл — 2,7–9 МБ, то есть 0,8–3,6 млн токенов против окна в 200k.

**Смерть наступает на входе, до того как написана первая строка карточки.** Поэтому она молчаливая:
агент не падает с ошибкой, он вытесняет историю и возвращает короткое или пустое. Ведущий видит ровно
то же, что при случайной пустоте пула, и обращается с ней по правилу, написанному для случайной.

## Почему это даёт ровно те две беды, что пришли с поля

**«Хороший скан не с первой попытки».** Правило Шага 3: пустой ответ → перезапуск **тем же промптом**,
одна попытка, дальше «прекрати». Правило верное для случайной пустоты (она замерена и бывает без
причины) и неверное для смерти от объёма: та **детерминирована**, второй прогон гарантированно
повторит первый. Итог: два дорогих прогона субагента, ноль записанных байт, «прежняя карточка
байт-в-байт», человек запускает скилл снова — и получает то же самое. Диска не касается ничего, то
есть повторный запуск начинает с нуля.

**«Ультра тяжёлое обновление».** Карточка перезаписывается целиком (это доктрина, и она правильная
для нормального сервиса), значит любое обновление монолита = полное перечитывание монолита. Плюс
гард на утоньшение требует ключей прежней и новой карточки у ведущего, то есть тех же 3× текста.
Дешёвого частичного обновления в конструкции нет вообще — ни по модулю, ни по секции.

**Стенд этого не видит.** Самая крупная фикстура с живым деревом — `SM-E2E`: 21 файл, 53 КБ,
31 эндпоинт, 5/5 зелёных. `SM-BULK` (48 эндпоинтов) — вообще один файл текста. Ни один замер репы
никогда не выходил за 53 КБ исходников. **Дефект не измерен ни разу, и без новой фикстуры любая
правка будет вслепую.**

## Пять рычагов

Порядок — по зависимостям, не по важности.

### M0. Признак размера появляется до диспатча

Сейчас размер выясняется единственным способом — субагент умирает. Нужен дешёвый **ограниченный по
стоимости** замер до Шага 3.

Ведущему нельзя мерить размер глобом: `Glob "**/*.kt"` по монолиту вернёт три тысячи путей ему же в
контекст — это та же смерть, только у ведущего. Ограниченный сверху приём есть:

```
Grep pattern="<маркер роутов стека>" path="<путь сервиса>" output_mode="files_with_matches" head_limit=120
```

`head_limit` режет вывод по построению: вернулось ровно 120 — значит файлов ≥120, дальше считать не
надо. Стоимость ≤6 КБ независимо от размера репы. Это механическое наблюдаемое, а не оценка.

Второй вариант (дороже, точнее, годится и когда маркер стека неизвестен) — **субагент-разведчик**:
читает структуру и точки регистрации роутов, возвращает **≤30 строк**: список модулей/групп
префиксов, точки входа, порядок числа ключей на модуль. Не читает DTO и миграции, поэтому сам не
умирает.

Порог, за которым сервис перестаёт быть одной единицей скана, — **гипотеза, требующая замера**.
Отправная: ≤50 ключей / ≤150 файлов на единицу (`SM-E2E` даёт 31 ключ / 21 файл и работает 5/5).

### M1. Единица скана перестаёт быть равной сервису

Три архитектуры. Различаются не механикой скана, а тем, **что становится файлом на диске** — то есть
ценой для потребителей (`technical-spec-doc`, `business-requirements-doc`, `domain-glossary`; все
ходят `Grep path="services" glob="*.md"` и `Glob services/*.md`).

> Правка 2026-08-13: четвёртым потребителем здесь стоял `project-conventions` — скилл удалён вместе
> с `CONVENTIONS.md`, правила оформления человек кладёт файлом в `context/`. На выводы раздела это
> не влияет: `context/` читается своим грепом и от формы карточек не зависит.

| | **A. Один файл + сборщик** | **B. Папка-карточка** | **C. Монолит = N строк манифеста** |
|---|---|---|---|
| Что на диске | `services/<name>.md`, склеен из фрагментов в `services/.parts/` | `services/<name>/<модуль>.md` | `services/<name>-<модуль>.md` — обычные карточки |
| Потребители | не трогаются | **патчить всех потребителей** (глоб + агрегация «сколько сервисов делают одинаково» обязана группировать по папке) | не трогаются |
| Кто склеивает | ещё один субагент-сборщик (риск: перескажет вместо склейки) | никто | никто |
| Фрагменты в git | дублируют карточку (диф ×2) либо `.gitignore` — и тогда у соседа рескан полный | фрагмент **и есть** карточка, дубля нет | дубля нет |
| Обновление модуля | перечитать модуль + пересобрать (без чтения кода) | перечитать модуль | обычный `service-map <name>-<модуль>` |
| Сервисные секции (Назначение, Стек, Что умеет, Зависит от, Роли) | нужен отдельный проход: ни один шард их не видит целиком | то же | **не проблема**: каждая строка — полноценный сервис |
| Цена внесения | средняя | высокая | **низкая** |

**Рекомендация — C.** Причины:

1. Она ничего не ломает и почти ничего не добавляет: `path` строки манифеста начинает указывать
   **внутрь** репозитория (`path: ../monolith/modules/billing`), и вся существующая механика —
   гейт на запись, гард на утоньшение, `scanned`, рёбра Шага 5, добор, бюджет попыток — работает
   без единой правки.
2. Она ложится в доктрину, которая уже написана: «манифест — это **отбор**, а не опись соседнего
   каталога», и ведёт его человек. Разрезать монолит на двенадцать ограниченных контекстов — это
   именно отбор, и решать его должен человек, как и всё остальное в манифесте.
3. Она чинит обновление сама собой: перечитывается один модуль, потому что модуль — это строка.
4. `Grep "^description:"` начинает давать двенадцать честных маршрутных строк вместо одной
   бесполезной («монолит; всё»). Для потребителей это **улучшение**, а не издержка.

Что C стоит и о чём надо сказать вслух:

- общие DTO/миграции монолита попадут в несколько карточек или не попадут никуда — правило
  «владеет данными» разрешает это (владелец один), но проверить его никто не может;
- рёбра **внутри** монолита станут межсервисными строками «Зависит от». Это скорее правда, чем
  ложь, но граф раздувается;
- Шаг 2.1 сверяет соседний каталог **по `.git`** и новых модулей внутри монолита не заметит
  никогда. Нужна отдельная ветка: для строк, чей `path` лежит внутри репозитория, сверять братские
  папки, а не соседние репы;
- разрез предлагает разведчик (M0), утверждает человек. Это ровно форма Шага 1.3/1.5, которая уже
  написана и замерена, — новой механики диалога не нужно.

**B — конечная точка, если монолиты окажутся нормой, а не исключением.** A — компромисс на случай,
если потребителей трогать нельзя ни при каких условиях; из-за дублирования фрагментов в git она
слабейшая.

### M2. Субагент пишет файл, ведущий грепает

Нужно при любом выборе в M1 и отмечено в `PROBES.md` как «архитектура 4.0» ещё в июле. Это
единственное, что убирает главный член бюджета: текст карточки перестаёт проходить через ведущего
трижды и не проходит ни разу. Ведущий получает **числа** (≤300 байт: «ключей 42, с фактами 31,
блоков 42, записано») и проверяет их грепом по файлу:

```
Grep pattern="^### " path="services/<name>.md" output_mode="count"
```

Оценка после: ≈41,7 КБ на сервис → ≈6 КБ. Окно ведущего перестаёт быть ограничением вообще.

Три вещи, которые это ломает и которые надо решить до внесения:

1. **Субагент `Explore` писать не умеет** (у него нет `Write`). Нужен пишущий тип, а у него есть и
   `Bash` — значит запрет на shell и на запись куда-либо, кроме `services/`, придётся написать в
   промпт явно, и завести на него пробу. Сейчас запрет держится тем, что инструмента просто нет.
2. **Гейт на запись переворачивается.** Сейчас порядок «проверки → `Write`», и вся его сила в том,
   что после `Write` слово «не записывай» ничего не значит. При пишущем субагенте проверка
   становится послезаписной.
3. **Гард на утоньшение теряет опору** по той же причине.

Развязка (2) и (3) — не «ослабить гард», а перенести откат: прежнюю карточку субагент копирует
байт-в-байт в `services/.prev/<name>.md` (текст у него в контексте уже есть; точка вне `services/*.md`,
потребители её не видят). Гард срабатывает — ведущий называет числа, имена ключей и путь отката.
Настоящая страховка при этом всё равно git: слепок лежит в репе со спеками и коммитит его человек.

### M3. Ретрай различает случайную смерть и смерть от объёма

Правило «перезапусти тем же промптом один раз» остаётся **только для единиц, которые M0 назвал
малыми**. Для крупной единицы повтор того же промпта запрещён: он детерминированно повторит обрыв и
сожжёт вторую попытку, после которой скилл обязан прекратить. Вместо повтора — разрез единицы и
диспатч частей. Бюджет считается по единице скана, а не по сервису.

### M4. Частичный результат переживает смерть

Сегодня смерть одного субагента = ноль байт на диске по всему сервису. При любом варианте M1
неудачная единица должна стоить только себя: остальные записаны, неудачная **названа в отчёте и
помечена в карточке** идиомой, которая в шаблоне уже есть, — `не определено: модуль <X> не прочитан
(скан <дата>)`. Молча неполная карточка — худший исход из возможных, он прямо запрещён доктриной, и
частичная запись без пометки его как раз и производит.

Следствие: повторный запуск подбирает недочитанное сам — Шаг 2.2 без аргументов уже умеет это на
уровне сервисов, при C он умеет это на уровне модулей без единой правки.

### M5. Обновление читает только названный кусок

Следует из M1 (при C — бесплатно) плюс: `archive-spec` называет затронутые сервисы, а если спека
называет модуль — должен называть и модуль. Отдельная мелкая правка `archive-spec`, после того как
разрез утверждён.

## Порядок работ

1. **M0 + M3** — самое дешёвое и снимает главную боль сразу: смерть перестаёт быть способом узнать
   размер, вторая попытка перестаёт быть гарантированно сожжённой.
2. **M1=C** — разрез монолита строками манифеста + ветка Шага 2.1 для модулей внутри репы.
3. **M4** — пометка недочитанного (после C — почти бесплатно).
4. **M2** — самая крупная правка, отдельным раундом, со своими пробами: она трогает гейт и гард,
   то есть ровно те две механики, которые последние два раунда чинились по замеру.
5. **M5** — правка `archive-spec`, последней.

## Чем мерить

**Без новой фикстуры мерить нечем.** Максимум стенда — 53 КБ исходников; дефект живёт на трёх
порядках выше.

- **`SM-MONO`** — генерируемое скриптом дерево: ~150 эндпоинтов в 6 модулях, ~400 файлов, факты
  разнесены по DTO/обработчикам/миграциям (то есть по механике, на которой уже замерена плотность).
  Инвентарь известен точно, поэтому грейдится теми же грейдерами, что `SM-BULK`/`SM-NEUTRAL`.
  Генератор обязателен: руками такое дерево не поддерживается.
- **Полевая проба** на настоящем монолите — один фиксированный промпт, грейд по одному вопросу:
  оказалось ли на диске хоть что-то и помечено ли честно.

Новые пробы:

| ID | Что проверяет |
|---|---|
| **SM-58** | размер единицы назван **до** диспатча; способ ограничен по стоимости (`head_limit` или разведчик ≤30 строк) |
| **SM-59** | монолит не уходит одним субагентом: предъявлен разрез, ход остановлен до ответа человека |
| **SM-60** | смерть одной единицы стоит только её: остальные на диске, недочитанное помечено в карточке и названо в отчёте |
| **SM-61** | ретрай тем же промптом не применяется к крупной единице |
| **SM-62** | обновление одного модуля не читает остальные (наблюдаемое — какие пути открывались) |
| **SM-63** | (после M2) текст карточки не проходит через ведущего — меряется как SM-50, байтами промпта и ответа |

**Обязательный перезамер регрессии:** SM-29/SM-29' (полнота инвентаря) и SM-38 (семантика) — правки
садятся ровно в опись; SM-56 (гард по ключам), SM-52 (`scanned` не двигается без чтения),
SM-13/14/15 (рёбра Шага 5), SM-51 (число сервисов названо человеку — при C число строк манифеста
вырастет, и правило «больше десяти» начнёт срабатывать на каждом монолите: **порог придётся
пересчитать или увязать с M2**).

## Что решает человек, а не этот план

1. **M1: C, B или A.** План рекомендует C и объясняет чем; выбор меняет объём работ втрое.
2. **Порог «крупной единицы»** — 50 ключей / 150 файлов взяты по аналогии с `SM-E2E`, не замерены.
3. **Делать ли M2 вообще.** Без него C работает, но каждый монолит превращается в 6–12 обычных
   карточек, и потолок «≈12 карточек на прогон» упирается в один монолит.
4. **Кто пишет генератор `SM-MONO`** — без него раунд не меряется.
