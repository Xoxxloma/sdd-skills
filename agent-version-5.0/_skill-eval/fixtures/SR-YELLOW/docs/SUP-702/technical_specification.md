## 1. Обзор изменения

### 1.1. Тип и стороны
Fullstack. `portal-api` принимает обращение из портала, регистрирует его в системе тикетов и
отдаёт сотруднику список его обращений; `portal-web` получает форму обращения и список.

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| `portal-api` | приём и список обращений | Внутренний портал | 🟢 |
| `portal-web` | форма и список | Фронт | 🟢 |
| `itsm` | регистрация тикета | Служба поддержки | 🟡 подтв. аналитиком |
| `sms-gw` | смс автору о смене статуса | Платформа | 🟡 подтв. аналитиком |

### 1.3. Связь с бизнес-требованиями
`docs/SUP-702/business_requirements.md` — FR-1, FR-2, FR-3.

## 2. Взаимодействия (ядро)

### INT-1. Подача обращения — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** сотрудник отправляет форму обращения
- **Контракт (запрос):** `POST /v1/support/tickets`, тело — `subject: string`, `body: string`,
  `category: hardware|access|other`, `clientRequestId: uuid` — идентификатор попытки, генерируется
  экраном один раз на открытие формы
- **Контракт (ответ):** `id: uuid`, `number: string` — номер, под которым обращение зарегистрировано,
  `status: registered`, `createdAt: iso8601`
- **Пример ответа (успех):**
  ```json
  {
    "id": "9a2e77c1-05b4-4f8e-8d13-6bb0e4a72f51",
    "number": "SD-114902",
    "status": "registered",
    "createdAt": "2026-08-17T10:22:41+03:00"
  }
  ```
- **Повторная доставка:** обращения различаются по `clientRequestId`. Второй запрос с тем же
  значением **возвращает уже созданное обращение тем же ответом** и второго тикета не создаёт;
  уникальность обеспечена индексом по `(requesterId, clientRequestId)`.
- **Ошибки:** `422` — тело ответа содержит `fields: массив` с парами «поле — причина», по ним
  экран подсвечивает поля формы; `503` — система тикетов недоступна, обращение не создано
- **Состояния UI по ответу:** успех — `value` со списком; `422` — `error_validation` с подсветкой
  названных полей; `503` — `error_source`
- **Авторизация:** аутентифицированный сотрудник; обращение создаётся от его имени, чужим автором
  подписать нельзя — поле автора в запросе отсутствует
- **Происхождение:** 🟢
- **Трассировка:** FR-1

### INT-2. Список моих обращений — 🟢
- **Граница/направление:** FE → BE
- **Триггер:** открытие раздела «Поддержка»
- **Контракт (запрос):** `GET /v1/support/tickets`
- **Контракт (ответ):** `items: массив`, элемент — `id: uuid`, `number: string`,
  `subject: string`, `status: registered|in_progress|done|rejected`, `updatedAt: iso8601`
- **Пример ответа (успех):**
  ```json
  {
    "items": [
      { "id": "9a2e77c1-05b4-4f8e-8d13-6bb0e4a72f51", "number": "SD-114902", "subject": "Не работает принтер на 5 этаже", "status": "in_progress", "updatedAt": "2026-08-17T12:10:00+03:00" }
    ]
  }
  ```
- **Объём и порядок:** отдаются обращения за последние 12 месяцев целиком, по `updatedAt` по
  убыванию; при совпадении — по `number`. Потолок на сотрудника — 200 обращений за год по журналу
  поддержки, постраничной выборки не вводим
- **Ошибки:** `503` — система тикетов недоступна
- **Состояния UI по ответу:** непустой `items` — `value`; пустой — `zero`; `503` — `error_source`
- **Авторизация:** аутентифицированный сотрудник видит только свои обращения; фильтр по автору
  применяется на сервере до любой другой выборки
- **Происхождение:** 🟢
- **Трассировка:** FR-2

### INT-3. Регистрация тикета в системе поддержки — 🟡
- **Граница/направление:** Сервис `portal-api` → Сервис `itsm`
- **Триггер:** подача обращения
- **Контракт (запрос):** тема, текст, категория и автор обращения
- **Контракт (ответ):** идентификатор и номер зарегистрированного тикета
- **Ошибки:** обрабатываются как недоступность системы тикетов
- **Авторизация:** сервисная учётная запись `portal-api`, выдаётся службой поддержки
- **Происхождение:** 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Трассировка:** FR-1

### INT-4. Смс автору о смене статуса — 🟡
- **Граница/направление:** Сервис `portal-api` → Сервис `sms-gw`
- **Триггер:** смена статуса обращения на `done` или `rejected`
- **Контракт (запрос):** номер телефона автора, шаблон сообщения и номер обращения
- **Контракт (ответ):** подтверждение приёма сообщения к отправке
- **Ошибки:** обрабатываются как недоступность канала
- **Происхождение:** 🟡 подтверждено аналитиком (не по коду; валидировать при интеграции)
- **Трассировка:** FR-3

| `422` | поля обращения не прошли проверку | `error_validation`, подсветка полей из `fields` |

## 3. Backend — ответственность

### 3.1. По сервисам
`portal-api` принимает обращение, регистрирует его в системе тикетов и сохраняет у себя ссылку на
результат. Регистрация в системе тикетов идёт **до** фиксации собственной записи: не удалась —
запись не создаётся и сотрудник получает `503`, то есть обращения без тикета не остаётся. Смс о
смене статуса отправляется **после** фиксации изменения статуса; отправка вне транзакции, её отказ
статус не откатывает.

### 3.2. Данные и хранение
Новая сущность `SupportTicketRef` — ссылка на тикет, а не его копия:

| Поле | Тип | Обязательность | Примечание |
|------|-----|----------------|------------|
| `id` | uuid | да | первичный ключ |
| `requesterId` | string | да | автор |
| `clientRequestId` | uuid | да | попытка отправки; уникальность с `requesterId` |
| `externalNumber` | string | да | номер, присвоенный системой тикетов |
| `status` | enum | да | `registered`, `in_progress`, `done`, `rejected` |
| `createdAt` | timestamp | да | |
| `updatedAt` | timestamp | да | |

Индексы: уникальный по `(requesterId, clientRequestId)`; по `(requesterId, updatedAt)` — список.
Переходы статуса приходят из системы тикетов и записываются как есть; порядок переходов портал не
проверяет и своей логики жизненного цикла не имеет. Время хранится в UTC, отдаётся в
`Europe/Moscow`.

Происхождение: 🟢

### 3.3. Авторизация/доступ на бэке
Все эндпоинты требуют аутентификации. Ролей задача не вводит: у обращения один автор, и он же
единственный, кто его видит. Прямого обращения по чужому идентификатору нет — эндпоинта «тикет по
id» задача не заводит. К системе тикетов и к смс-шлюзу `portal-api` ходит сервисными учётными
записями, пользовательский контекст не передаётся.

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI
Новый раздел «Поддержка» (`/support`): форма обращения и список обращений сотрудника.

### 4.2. Пользовательские сценарии
Сотрудник заполняет тему, текст и категорию и отправляет обращение. `clientRequestId` создаётся
один раз при открытии формы и не меняется при повторной отправке, поэтому двойное нажатие
«Отправить» второго обращения не создаёт. Кнопка на время запроса блокируется. Сервер отверг с
`422` — введённое остаётся на месте, подсвечиваются поля из `fields`. После успеха форма
закрывается, список перезапрашивается, новое обращение первое в нём.

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | запрос списка в процессе | скелетон строк |
| `value` | `items` непустой | список обращений |
| `zero` | `items` пуст | «обращений пока нет», кнопка создания |
| `error_source` | ответ `503` | «поддержка недоступна, попробуйте позже» |
| `error_validation` | ответ `422` | форма открыта, поля из `fields` подсвечены |

### 4.3.1. Loading и таймауты
Раздел рисуется сразу, список догружается отдельно. Таймаут списка — 5 секунд, подачи — 15 секунд
(регистрация идёт во внешней системе); по истечении — `error_source`, повторная отправка с тем же
`clientRequestId` безопасна.

### 4.4. Доступ по ролям в UI
Не применимо: ролевого ветвления задача не вводит, раздел одинаков для всех сотрудников.

### 4.5. Формат показа полей
`status` показывается подписями: `registered` — «зарегистрировано», `in_progress` — «в работе»,
`done` — «решено», `rejected` — «отклонено». `updatedAt` — «ДД.ММ в ЧЧ:ММ», зона `Europe/Moscow`.
`subject` длиннее ширины колонки обрезается многоточием, полностью виден в подсказке.

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность
Подача синхронная: сотрудник ждёт номера. Список отдаётся из собственного хранилища, кэша нет.

### 5.2. Надёжность/деградация
Система тикетов недоступна — подача отклоняется с `503`, обращение не создаётся, сотрудник видит
предложение повторить. Смс-шлюз недоступен — статус всё равно меняется, сообщение теряется:
статус виден в списке.

### 5.3. Безопасность/доступ (сводно)
Текст обращения может содержать персональные данные, поэтому в журналы приложения тело обращения
не пишется. Сервисные учётные записи хранятся в секретах `portal-api`.

## 6. Релиз и интеграция

### 6.1. Порядок выката
Сначала `portal-api` с миграцией и эндпоинтами, затем `portal-web` с разделом.

### 6.2. Обратная совместимость
Существующие разделы портала не меняются, ничего не удаляется.

### 6.3. Фиче-флаги
Флаг `portal.support`, по умолчанию выключен.

### 6.4. План отката
Выключить флаг — раздел исчезает. Таблица `SupportTicketRef` остаётся: в ней ссылки на уже
зарегистрированные тикеты.

### 6.5. Преднастройка до релиза
- Сервисная учётная запись `portal-api` в системе тикетов — запросить у службы поддержки.
- Сервисная учётная запись `portal-api` в смс-шлюзе — запросить у платформы.
- Шаблон смс — согласовать со службой поддержки.
