# Фикстура SM-GRAPH — сбор обратных рёбер

Синтетический слепок. Подаётся модели как текст: она НЕ ходит по диску, а работает с этим
описанием как с содержимым папок.

Меряет **только Шаг 5** `service-map` — сбор секции «Кто меня потребляет» по всему слепку. Кода
сервисов здесь намеренно нет: карточки уже собраны, прогон идёт по слепку.

Текущая директория — `/work/specs`.

## `/work/specs/services/manifest.yaml`

```yaml
services:
  - name: auth
    path: ../auth-service
    type: backend

  - name: user-profile
    path: ../user-profile
    type: backend

  - name: incident-web
    path: ../incident-web
    type: frontend
```

## `/work/specs/services/` — что лежит на диске

```
manifest.yaml  auth.md  user-profile.md  incident-web.md  legacy-billing.md
```

`legacy-billing.md` строки в манифесте **не имеет**: сервис выделили в другую группу и убрали из
отбора полгода назад, а файл карточки остался.

## Что здесь проверяется

- **SM-25. Безвызовное ребро зеркалится.** `auth → user-profile` идёт через «Зависит от», где
  колонки вызова нет вообще — у backend секции «Потребляемые API» не существует. Значит в
  `user-profile.md` должно появиться:

  ```
  | `auth` | — | проверка блокировки пользователя |
  | `auth` | — | чтение отображаемого имени для журнала входов |
  ```

  Две строки, а не одна: «Зависит от» схлопывает их по имени сервиса, зеркало — нет. Красные
  исходы: **выдуманный** метод и путь в колонке «Что вызывает»; **одна** строка вместо двух;
  строка выброшена «потому что вызов неизвестен».

- **SM-24. Мёртвая карточка не участвует в графе.** `legacy-billing` в манифесте отсутствует,
  значит в слепок не входит. В `auth.md` строки `legacy-billing | … | проверка активной сессии`
  быть **не должно**. Это симметрично уже действующему правилу «ребро в сервис без карточки не
  зеркалится»: узел вне отбора не порождает рёбер ни в одну сторону. Сама `legacy-billing.md`
  не удаляется и не переписывается — она называется в отчёте как карточка без строки в манифесте.

- **SM-14 (регресс). Симметрия не режет живое.** У `auth` теперь два вида входящих: зеркало от
  `incident-web` (с вызовом) и ничего от `legacy-billing`. Проверка симметрии не должна удалить
  первое и не должна воскресить второе.

- **SM-15 (регресс).** `API-шлюз` и `notifications-svc` карточек не имеют — зеркалить некуда,
  и выдуманных карточек под них не создаётся. `notifications-svc` при этом **остаётся** строкой
  в «Потребляемых API» `incident-web` с пометкой про манифест: вызов есть в коде, значит строка
  есть в карточке.

## Ловушка

Инвариант симметрии сформулирован жёстко: «односторонняя строка означает, что ты либо потерял
ребро, либо выдумал его». На этой фикстуре у него три законных исключения подряд — безвызовное
ребро, узел вне манифеста и мёртвая карточка. Модель, применившая инвариант буквально, начнёт
чинить симметрию удалением: это и есть красный исход. Правильное поведение — пересобрать
«Кто меня потребляет» из живых карточек и назвать исключения в отчёте.
