# Раунд «асинхронщина в карточке» — журнал прогонов

Модель прогонов — Haiku (прокси слабой модели), запуск — `./run.sh <проба> <N>`, грейд —
`node ../../grade-async.mjs sandbox`. Песочницы в `sandbox/` (в `.gitignore`), промпт в `stand/`,
снимок скилла до правки — в `before/`.

**Что мерится.** Правки от 2026-08-12: «События» блоками, новая секция «Фоновые задачи», счёт
классов ключей по отдельности (SM-68…SM-73, SM-79; описание в `../../PROBES.md`). Зеркала
асинхронных рёбер откачены и не мерятся.

**Две пробы на одном материале.** `async` — скилл после правки, `async-before` — снимок до.

## Замер: 10 + 10 прогонов (2026-08-12)

| Проба | ДО правки (измерено 9 из 10) | ПОСЛЕ (измерено 8 из 10) |
|---|---|---|
| SM-69 факты событий | **3.7/11** | **10.4/11** |
| SM-70 факты задач | **0.0/5** | **5.0/5** |
| SM-68 все четыре класса ключей сошлись | **0 из 9** | **8 из 8** |
| SM-72 задача без расписания | красных 9 из 9 | зелёных 7, частичных 1, красных 0 |
| SM-79 пустая форма у сервиса без задач | 0 из 9 | 7 из 8 |
| SM-73 REST-контроль | 2.9/3 | 2.8/3 |
| заражение примером из шаблона | 0 | 0 |

**Правка работает, и разрыв не тонет в разбросе.** События 3.7 → 10.4 из 11, задачи 0 → 5 из 5.
До правки **ни один** прогон не собрал все четыре класса ключей (секции «Фоновые задачи» нет по
построению), после — все восемь измеренных. REST-контроль не просел: 2.9 против 2.8 — это один
недобравший прогон, а не тенденция.

**Разброс базы шире, чем показал пилот.** Пилотный прогон «до» дал 1/11 по событиям, десять дали
среднее 3.7 при размахе 3…6. Вывод по пилоту («1 против 10») был бы верен по знаку и неверен по
величине — ровно та причина, по которой N=10 в этом наборе базовый.

**Три прогона из двадцати не дошли до записи** (2 «после», 1 «до»): субагент дважды не вернул
маркерную строку `шаблон прочитан…`, бюджет попыток исчерпан, карточка не записана. Ведущий во всех
трёх отработал верно — не выдумал карточку и назвал сервис в отчёте. **Это дефект Шага 3, не этой
правки:** он встречается по обе стороны сравнения (2 из 10 и 1 из 10) и к форме секций отношения не
имеет. Частота ~15% — самостоятельный повод для отдельного раунда.

**SM-79 промахнулся один раз из восьми:** в `async-04` у `billing-worker` секции «Фоновые задачи»
нет вовсе вместо пустой формы. Один случай на восемь — не тенденция, но и не ноль: правило «пустая
секция сохраняет свою форму» на новой секции держится хуже, чем на старых.

## Два дефекта грейдера, найденные пулом

Оба — тот же класс, что ловился раньше: **регулярка, написанная под латиницу, на кириллице молчит.**

1. **`\w` не покрывает кириллицу.** `внешн\w*\s+планировщик` не совпало с «внешним планировщиком»,
   и прогон, честно написавший «расписание НЕ в коде — дёргается внешним планировщиком», получил
   «про расписание не сказано ничего».
2. **Поиск блока был чувствителен к регистру.** Прогон назвал задачу по имени класса
   (`SyncMeterCatalogJob`), точное вхождение `syncMeterCatalog` не сработало — грейдер объявил ключ
   потерянным там, где он на месте.

Оба исхода в первой самопроверке отсутствовали: эталонная карточка была написана ровно так, как
ожидал грейдер. Добавлены отдельным случаем, самопроверка — 17/17. **До починки итог «после» был
7 зелёных SM-72 из 8 вместо реальных 8 из 8** — то есть грейдер занижал результат правки, а не
завышал.
