# Архивация спеки в карточки сервисов

Спека описывает изменение, которое уже уехало в прод. Твоя работа — перенести его в **описание
сервисов**, чтобы следующий аналитик читал актуальную картину, а не спрашивал заново.

Ты **не читаешь код**. Спека уже описывает результат, и именно поэтому архивация стоит дёшево:
перечитыванием сервисов из исходников занимается `service-map`, а не ты.

**Прочитай `reference/merge-map.md` перед шагом 4.** Там карта «§ спеки → секция карточки», гейт
происхождения, правила переписывания и список того, что не вливается никогда. Без неё ты будешь
решать это на глаз, а на глаз половина спеки выглядит уместной в карточке.

**Папка `reference/` лежит рядом с этим `SKILL.md`, в каталоге скилла, а не в репозитории со
спеками.** Путь считай от файла, который читаешь. Не открылся — остановись и скажи человеку, что
скилл установлен не полностью. Вливать по памяти нельзя: ты правишь чужие карточки, и ошибка
маршрута тихо переживёт много релизов.

## Правило, которое важнее всех остальных

**Вливается только 🟢 и 🟡 подтверждено аналитиком.** 🟡 к валидации, ❓ и ⚠️ — не вливаются.

Метка стоит в самой спеке: в §1.2 это колонка «Происхождение», в каждой INT-карточке §2 — поле
«Происхождение». Смотри в поле, а не оценивай текст.

Почему это первое правило, а не деталь: карточка сервиса — вход для **следующей** спеки. Через
неделю `technical-spec-doc` прочитает её и понесёт аналитику словами «в `services/auth.md`
описано, что…». Допущение, которое аналитик не подтверждал, к этому моменту неотличимо от факта, и
дальше оно расходится по всем спекам, которые трогают этот сервис.

## Процедура

### Шаг 1 — Найти, что архивировать

Передан путь — бери его. Передан ключ — ищи `Glob docs/**/<KEY>/`: **поиск рекурсивный**, потому
что ребёнок эпика лежит в `docs/<EPIC-KEY>/<CHILD-KEY>/`, а не в `docs/<CHILD-KEY>/`.

Ничего не нашлось → скажи об этом и остановись. Не угадывай похожий ключ.

### Шаг 2 — Собрать спеки внутри

`Glob <папка>/**/technical_specification.md`. Для листовой задачи найдётся одна, для эпика —
`_foundation/` плюс по одной на каждого ребёнка.

Отбрось те, у кого `.archived` лежит в их собственной папке **или в любой родительской до `docs/`**.
Так частичная архивация не ломается: ребёнок, влитый неделю назад, при архивации эпика пропускается,
а не вливается второй раз.

Ничего не осталось → «всё уже влито», выход.

**Порядок вливания фиксированный:** сначала `_foundation/`, затем дети в порядке `order` из
`decomposition.md` (нет индекса — по возрастанию ключа). Две спеки эпика могут трогать один и тот
же блок карточки, и без заданного порядка результат зависит от того, как лёг обход. Порядок именно
такой, потому что в нём спеки и писались: фундамент задаёт контракт, дети его наследуют, и поздний
ребёнок законно перекрывает раннего.

### Шаг 3 — Подтвердить состав

**Перечисли, что именно вливаешь, и дождись подтверждения.**

Для листовой задачи это формальность в одну строку. Для эпика — нет: метка на эпике означает
«уехало всё», и если часть детей ещё в разработке, их спеки попадут в карточки как описание
работающего сервиса. Молча грести поддерево нельзя.

**Отдельно назови узлы БЕЗ спеки.** Метка ляжет на переданную папку и накроет всё поддерево — а
значит и тех детей, у кого спеки пока нет: когда её напишут, она окажется «под меткой» родителя и
при следующей архивации будет пропущена как влитая, хотя не вливалась.

Скажи это прямо: «в `<KEY>` спеки ещё нет; метка на эпике накроет и его — когда спека появится, её
придётся архивировать явно по её собственному ключу». Аналитик вправе так решить, но решать это
должен он, а не ты молчанием.

Инструмента вопросов нет → спроси прозой и останови ход.

### Шаг 4 — Влить

Прочитай `reference/merge-map.md`, если ещё не читал. Затем по каждой спеке:

1. **Кто затронут** — из §1.2 «Затронутые сервисы и владельцы». Это готовая таблица, гадать не
   нужно. Строки с происхождением 🟡 к валидации пропускай.
   Сервис в §1.2 есть, а по тексту спеки про него ничего нет (обычно роль «потребитель» без
   изменения контракта) — **пропусти молча**. Это не ошибка и не повод что-то дописывать в его
   карточку.
2. Сервиса нет в `services/manifest.yaml` → карточку **не создавай**, назови его в отчёте:
   манифест ведёт человек.
3. Сервис в манифесте есть, а `services/<name>.md` нет → тоже не создавай. Тебе нечем заполнить
   «Назначение» и «Стек», а файл из одних влитых спек будет выглядеть описанием сервиса, не будучи
   им. Скажи: «по `<name>` карточки нет, запустите `service-map <name>`».
4. **Прочитай карточку и посмотри её `type`** — секции ветвятся по типу.
5. **Пройди спеку по секциям сверху вниз, от §1 до §8, и по каждой скажи вслух, что берёшь.**
   Список ниже — не справка, а маршрут: идёшь по нему подряд, а не вспоминаешь, что где лежит.

   | Секция спеки | Что из неё берёшь |
   |---|---|
   | §1.1 Тип и стороны | ничего — про задачу, не про сервис |
   | §1.2 Затронутые сервисы | список сервисов и их происхождение (шаг 4.1) |
   | §1.3 Связь с БТ | вместе с §7 → «Что умеет для пользователя» |
   | §2 INT-карточки | контракты, события, потребляемые API — по направлению |
   | §2 Каталог ошибок | ничего; смысловые ошибки уже взяты в тело блока |
   | §3.1 По сервисам | кто владелец; для `lib` — «Публичный API» |
   | §3.2 Данные и хранение | «Владеет данными» |
   | §3.3 Авторизация на бэке | «Роли и доступ» |
   | §4.1 Где меняется UI | «Экраны» — **только если появился НОВЫЙ роут** |
   | §4.2 Пользовательские сценарии | ничего — сценарий идёт через несколько сервисов, в карточке одного он неполон |
   | §4.3 Состояния, §4.3.1 loading | ничего — отрисовка UI |
   | §4.4 Доступ по ролям в UI | «Роли и доступ» |
   | §5 Нефункциональные | ничего |
   | §6.1, §6.3–§6.5 Релиз | ничего |
   | **§6.2 Обратная совместимость** | **депрекейт — берёшь обязательно**, см. ниже |
   | §7 Трассировка приёмки | вместе с §1.3 → «Что умеет для пользователя» |
   | §8 Допущения и вопросы | ничего — по определению неподтверждённое |

   **§6.2 — единственное исключение из «релизное не вливаем», и его чаще всего теряют.** Нашёл в
   §6.2 слова «устаревший», «deprecated», «будет удалён», «не использовать» про конкретный эндпоинт
   или поле — пометь его в карточке владельца. Блок с таким ключом есть → допиши строку
   «устаревший». Блока нет → **заведи блок** с одной этой строкой. Срок удаления не пиши: это план
   релиза, он не переживёт сам себя.

   Почему нельзя пропустить: депрекейт — это состояние контракта, а не событие релиза. Потеряв его,
   ты оставляешь следующего автора спеки проектировать интеграцию с эндпоинтом, который выключают,
   и карточка ему в этом не помешает — она выглядит полной.

   Детали по каждой строке таблицы — в `reference/merge-map.md`. Но **маршрут задан здесь**: если
   ты идёшь по спеке и не открывал карту, ты всё равно обязан пройти все восемнадцать строк.
6. Переписывай по ключу: блок с тем же заголовком — **тело целиком**; строка таблицы с тем же
   ключом — строку. Нет такого ключа — добавь новый элемент.

Результат читается как описание текущего состояния. Ни «добавлено поле», ни «изменено с…», ни дат:
карточка — не журнал изменений. Читателю через месяц нужно знать, как есть сейчас, а не как было.

**Frontmatter не трогай.** `scanned` отвечает на вопрос «когда карточку читали из кода», а ты кода
не читал. Обновишь его своей датой — и человек, решая, что пора перечитать, посмотрит на дату
архивации и решит, что сервис свежий.

### Шаг 5 — Возможности: сформулировать, спросить, записать ОДНУ строку

Строки секции **«Что умеет для пользователя»** — единственные без механического ключа: совпадение
там смысловое, а не текстовое. Отсюда три правила, и они нужны все три.

**1. Возможность есть всегда, когда спека что-то даёт пользователю.** §1.3 и §7 для того и
читаются. Спека добавляет поле, которое человек увидит на экране, — это возможность, даже если
слово «возможность» в спеке не встречается. Не найдя строки-кандидата, перечитай §1.3: там сказано,
зачем задача делалась.

**2. Спроси аналитика — новая это возможность или переформулировка существующей.** Батчем, а не по
одной: инструмент заканчивает ход, и десять заходов растянут архивацию на десять ходов.

**Больше четырёх кандидатов за ход инструмент не возьмёт.** Задай первые четыре, остальные —
следующим ходом. Не выбрасывай лишних и не склеивай разные возможности в один вопрос, чтобы
уместиться: у каждой свой ответ, и склеенная пара запишется одной строкой вместо двух.

**Ответ уже получен** (аналитик сказал «новые» или указал, что переформулировать) — не спрашивай
повторно, записывай.

**3. Одна возможность — ОДНА строка. Разные права живут в колонке «Для кого».**
Не заводи вторую строку под ту же способность с другой ролью:

❌ `| Посмотреть IP своего входа | Любой авторизованный |`
   `| Посмотреть IP чужого входа | Аналитик безопасности |`

✅ `| Посмотреть IP последнего входа | Любой авторизованный — свой; аналитик безопасности — чужой |`

Причина: иначе таблица растёт при каждом изменении прав, а колонка «Для кого» затем и существует,
чтобы права жили в ней. Через три задачи разделённые строки разъедутся по формулировкам, и станет
непонятно, одна это возможность или две.

Во всех остальных секциях ключ решает сам — там вопросов не задавай.

### Шаг 6 — Обновить индексы

**Ребро между сервисами всегда двустороннее, и ты обязан записать обе стороны.**

Влил в «Потребляемые API» или «Зависит от» новую строку — положи её зеркало в карточку сервиса, на
который она указывает, в секцию **«Кто меня потребляет»**: `<сервис-источник> | <вызов> | <зачем>`.
И наоборот: убрал строку — убери зеркало.

Пример. Спека добавляет фронту вызов `geo | GET /v1/chops`. Значит меняются **две** карточки:
у `incident-web` появляется строка в «Потребляемых API», у `geo` — строка
`incident-web | GET /v1/chops | …` в «Кто меня потребляет».

Зачем: карточка сама знает только исходящие связи. Автор следующей спеки по `geo` откроет
`services/geo.md`, чтобы понять, кого сломает изменение контракта, — и увидит это только если ты
записал вторую сторону. Односторонняя запись означает, что связь есть, но невидима ровно тому, кому
она нужнее всего.

Сервис, на который указывает строка, карточки не имеет (внешняя система, `API-шлюз`) — зеркалить
некуда, пропусти.

### Шаг 7 — Пометить и отчитаться

**Кладёшь метку на папку эпика — повтори вслух, что она накроет.** Узлы без спеки внутри этого
поддерева (Шаг 3) после метки будут пропускаться как влитые: их будущие спеки окажутся под меткой
родителя. Не рассуждай, что «их обработают отдельно» — не обработают, механика проверки смотрит и
родительские папки. Одна строка в отчёте: «`<KEY>` остался без спеки и теперь под меткой эпика —
когда спека появится, архивируй её явно по её ключу».

**Метку блокирует ровно одно: отсутствующая карточка у сервиса, в который ты СОБИРАЛСЯ вливать.**

Порядок проверок важен, поэтому он задан явно:

1. Сначала гейт происхождения (Шаг 4.1). Сервис отсеян как `🟡 к валидации` — он **выбывает из
   списка затронутых совсем**, и есть у него карточка или нет, уже неважно.
2. Потом — есть ли карточка у тех, кто остался. Нет → `.archived` НЕ клади, скажи «по `<name>`
   карточки нет, запустите `service-map <name>` и повторите архивацию».

Без этого порядка спека, упомянувшая неподтверждённый сервис, у которого ещё нет карточки, не
заархивируется никогда: сработают оба условия сразу, и непонятно, какое сильнее.

Причина: метка означает «эта спека учтена». Поставив её, когда часть не влилась **по устранимой
причине**, ты теряешь эту часть навсегда — при следующем запуске спека будет отброшена как влитая.
Лишний прогон `service-map` дешевле молча потерянного сервиса.

**Что метку НЕ блокирует — не путай.** ❓ и 🟡 к валидации не влиты **по правилу, а не по
недоработке**: это штатный исход, и он не изменится от повторного запуска. Считать их блокером —
значит не архивировать ни одну спеку с открытым вопросом, а такие спеки нормальны и составляют
заметную долю. Слепок тогда замрёт навсегда, что хуже любой из проблем, от которых ты страхуешься.
То же с сервисом, который в §1.2 числится потребителем без изменений контракта.

Разница простая: карточки нет — **починяемо**, метку держим. Гейт происхождения — **решение**,
метку ставим.

Всё влилось → положи пустой файл `.archived` в папку, которую передали аргументом. **Он должен
попасть в тот же коммит, что и карточки** — если маркер останется только локальным, после чистки
рабочей копии всё вольётся повторно и карточки задублируются.

Коммит делает **человек**, не ты. Твоё дело — файлы: изменённые карточки и метка. `git` ты не
запускаешь вообще — ни `add`, ни `commit`, ни что-либо ещё. Историю ведёт тот, кто просмотрел дифф.

Отчёт одним блоком **в чат** — какие спеки влиты, какие карточки изменены, какие сервисы пропущены
и почему (нет в манифесте / нет карточки / только 🟡 к валидации), какие возможности аналитик
подтвердил как новые.

**Файлом отчёт не клади.** На диск от тебя идут ровно две вещи: изменённые карточки и `.archived`.
Спек-репа лежит под гитом, и `ARCHIVE_REPORT.md` рядом с каждой архивированной задачей — это мусор
в истории, который никто потом не читает.

Заверши строкой: «если по этим сервисам давно не запускали `service-map`, стоит перечитать их из
кода — влитая спека описывает изменение, а не весь сервис».

## Чего не делать

- **Не вливай примеры JSON целиком.** Из «Контракт (ответ)» бери смысл полей, значения enum'ов и
  семантику `null`. Образец тела устаревает первым и занимает место, где должно быть знание.
- **Не создавай секцию не по типу.** Спека просит добавить экран, а у сервиса `type: backend` —
  остановись и скажи в отчёте: либо тип в манифесте неверный, либо ты ошибся сервисом.
- **Не заходи в `Назначение`, `Стек` и `Состояние и данные`.** Их ведёт `service-map`, читая код.
  Спека про них молчит, поэтому всё, что ты можешь там сделать, — выдумать.
- **Не архивируй незавершённую спеку.** Если аналитик просит влить то, что ещё в разработке,
  скажи прямо: карточка описывает работающий сервис, и запись о ненаписанном коде сделает её
  ложной для всех, кто прочитает её раньше релиза.
