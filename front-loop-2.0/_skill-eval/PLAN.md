# front-loop — план доработки и верификации

Рабочий план: **что делаем, что правим, как проверяем.** Ведём по нему статусы.

**Раскладка:** `front-loop/` — заморожен, чистые 5 скиллов = baseline «до» (не трогаем).
Все правки A–H идут в **`front-loop-2.0/`**; сравнение — папка-против-папки (как
`agent-version` → `agent-version-2.0`).

## 1. Контекст и цель

`front-loop` — фронтовый SDD-цикл: `business-baseline`+`project-baseline` заводят живые
доки → `writing-plans-front` пишет plan pack → `executing-plans-front` исполняет →
`sync-project-doc` вкатывает инкремент обратно.

Текущая оценка ревью: **B / ~3.3 из 5** — отличный дизайн, переписанный прозой и
недособранный по тулингу, с хрупкой несущей механикой (`<!--i-->`) и без эвалов.
**Цель правок:** снизить плотность (главный риск на слабой модели), убрать хрупкую
механику, зафиксировать коллизии владения, завести эвалы.

**Целевые модели (подтверждено):** deepseek flash v4, qwen 3.5, minimax, gigachat ultra —
3 из 4 без ризонинга; основная работа на minimax-с-ризонингом. То есть **слабо-модельный
кейс**: слим + вынос механики из прозы обязательны, не опциональны.

## 2. Зафиксированные решения

- **Владение — блоками, не невидимым маркером.** В §3/§4/§8 два видимых подблока
  «**Факты**» (правит `sync`) / «**Почему**» (не трогает); §1-назначение, §9, §10 —
  целиком человеческие зоны. Ломаться нечему: нет построчного `<!--i-->`, нарушение видно
  в диффе. `BUSINESS.md` уже так устроен (`sync` правит только `## Capabilities`) → весь
  пайплайн на видимых границах.
- **Скрипт-валидатор отклонён.** Любой внешний интерпретатор (питон/node/shell) тащит
  зависимость «а вдруг не установлено» — на кластерных раннерах гарантий нет. Робастность
  берём огрублением владения, не внешним чекером.
- **Few-shot — стек-агностичные.** Учат РЕШЕНИЕ, не стек. Шапка-дисклеймер + разные
  носители между примерами, чтобы модель не приняла стек примера за предписание.

## 4. Порядок и фазы

Каждая правка меряется **сразу по мере готовности** — для этого сначала каркас эвалов.

- **Фаза 0 — каркас.** `front-loop/` уже заморожен как baseline (5 скиллов «до»); работа
  идёт в `front-loop-2.0/`. Поднять `_skill-eval/` + болванки фикстур (§5.4). *(часть F)*
- **Фаза 1 — A.** Правим владение → мерим A-1..A-4 **против baseline-маркера**
  (head-to-head: доказать, что блоки робастнее).
- **Фаза 2 — B, C, D.** Структурный рефактор + few-shot → мерим B-1, C-1, D-1..D-4.
- **Фаза 3 — E, G.** Слим планировщика + рамка business → мерим E-1..E-3, G-1.
- **Фаза 4 — H.** Статик-грепом по шаблонам, без ранов модели.
- **Фаза 5 — регрессия.** Полный цикл R-1..R-3 против финальной модели.

Зависимость: **A первой** (меняет форму, на которую опираются B и D). B/C/D после того,
как A устаканила контент. E/G/H независимы.

## 5. Как проверяем

### 5.1 Метод (шапка харнесса — из SDD)

- **Baseline = `front-loop/` (заморожен)**, head-to-head vs `front-loop-2.0/`
  папка-против-папки (не полагаться на SHA — гонять листовые пробы).
- **Haiku low-effort** — прокси qwen/deepseek/gigachat (без ризонинга); **+ high-effort
  сабсет** на дискриминирующих пробах — прокси minimax-с-ризонингом.
- **N=10, пул до N=20** на пограничных (n=5 и один n=10 врут — проверено).
- **Детерминированный грейдинг по тексту артефакта** (string-checks), НЕ self-report модели.
- Сабагенты **не пишут файлы** → возвращают док/план текстом, грейдим текст.
- Write-пробы — **нейтральная преамбула** «выведи, что записал бы», без ask-nudge.
- Всегда смотреть **сырой артефакт**; ждать ~2 грейдер-артефакта/сессию; метрики считать
  **от ответивших** ранов (Haiku ~2–3% теряет на непарсимых tool-call).

Блочное владение (A) само упрощает грейдинг: зоны «Почему/§1/§9/§10» диффятся побайтово,
промах размещения ловится по коннекторам («потому/чтобы» в «Фактах» = промах).

### 5.3 Регрессионные гейты (end-to-end, фаза 5)

- **R-1** гейт-до-записи срабатывает (вопросы всплыли до write, или явно «вопросов нет»).
- **R-2** анти-фабрикация: отклонённое → `TBD`, не догадка; ноль выдуманного назначения/роли.
- **R-3** полный цикл create→plan→execute→sync даёт связные доки без коллизий владения.

### 5.4 Фикстуры (frontend-домен — у нас пока только backend ARS-xx)

- **FE-BROWN** — небольшой brownfield-фронт, mainstream-стек (A-1, B-1, C-1, D-1..3, R-2).
- **FE-BROWN-NOGATE** — то же без ответов пользователя, под гейт-до-записи (R-1).
- **FE-PLAN-INPUT** — approved-дизайн, задачи 3 классов + мульти-компонент (E-1..3).
- **FE-PLAN-DONE** — завершённый plan pack + status (A-2, G-1, sync SY1).
- **FE-EXOTIC** — нарочно немейнстрим-стек (Vue/Svelte/SSR/не-web) для D-4.
- **FE-MEANING** — инкремент, меняющий *смысл* человеческой строки (A-3).
- **FE-REFINE** — brownfield с «планировалось»-строками в «Почему» под handover (A-4).
- **FE-LEGACY**, **FE-LEGACY-CANON** — доки старого `<!--i-->`-формата под миграцию (M-1, M-2).
- **FE-DIRTY** — грязное рабочее дерево против коммита (W-1).
- **FE-DESIGN-B/C/CHAKRA/D**, **FE-DESIGN-POINTERS**, **FE-SLOP** — дизайн-набор.

> **FE-GREEN так и не завели.** A-4 фактически прогнана на `FE-REFINE` (4/4 ✅ — см. PROBES,
> «Добор непокрытой поверхности»), R-2 — на `FE-BROWN`. Строка про greenfield-скаффолд полтора
> раунда описывала фикстуру, которой нет.

Целевая метрика ↑ vs baseline на **N=20**, и **ноль регрессии** на R-1..R-3. Хвосты, что
промптом не чинятся (по образцу status в SDD), — явно помечаем «нужен рунер-постстеп», не
выдаём за победу.
